# 章节写作与验收规范

编写、重写或验收章节时读取；实验设计与结果解释另见 [实验规范](experiment-guidelines.md)。

## 章节要求

每章均须满足以下五项。未满足的项目记录为缺口，不标验收完成。

1. **机制深度。** 给出推导、固定版本的真实 `file:line`、必要代码原文和可复现的 mini 实现，让读者能自己写出核心机制。
2. **实现广度。** 围绕同一问题比较同层方案，说明结构、适用条件和代价。下表是各层最低覆盖范围；未测路线标 `UNVERIFIED`，说明原因与补测条件。
3. **原始材料。** 每章保留未经改写的配置、词表、权重清单、日志、图文本、PTX/SASS 或真实报错，并给出完整文件入口和采集方式。
4. **可检查的细节。** 机制涉及的字节布局、图边、张量 shape/stride、block table、bitmask、通信次序等，应实际打印、导出或绘制。正文解释关键字段，完整材料放折叠区或源码页。
5. **设计取舍。** 源码解析后说明不变量、边界、状态归属、增加后端的改动范围及错误发现位置。比较替代方案及代价；声称某方案被上游否决时引用原始讨论，自行提出的对照明确标为分析。M0 集中复盘不能代替各章的设计分析。

| 层 | 最低对照范围 |
|---|---|
| 推理引擎 | vLLM、SGLang；按章节需要补 TensorRT-LLM、llama.cpp、HF |
| kernel | CUDA、Triton、CuTe-DSL、TileLang、ThunderKittens |
| 训练 | FSDP2、DeepSpeed、Megatron、TorchTitan |
| 分布式 | NCCL、NVSHMEM、DeepEP、UCCL |

### 固定结构

1. 本章回答的三个具体问题。
2. 心智模型，配内联 SVG。
3. 机制拆解与推导。
4. 工程实现：源码解析；其后紧接「设计取舍」小节。
5. 工程实现：mini 实现。
6. 动手 lab：命令、实测数字和消融建议。
7. 原始现场：未经加工的材料。
8. 前沿。
9. 陷阱。
10. 自测题，答案折叠。

长源码和输出使用 `::: fold` 或 `{{srcfold:path}}`。整文件展开超过 40 行自动折叠；`site/code/` 中的完整源码不折叠，并保留行锚点。

## 写作要求

教程命令默认从项目根目录执行，使用 `python` 和项目相对路径；依赖读者环境的目录使用已解释的变量。不要把维护者机器上的绝对路径、SSH 别名或 venv 路径写成读者的操作前提，具体环境位置留在 `ENVIRONMENTS.md`。原始日志不改写；确实与机制有关的路径应解释其意义。

正文使用地道流畅的技术中文，技术术语保留英文，首次出现时用一句白话解释。先写结论，再给机制和依据；一句话讲一件事。

**语言与用词规范：**

1. **拒绝生硬句式与翻译腔（自然流畅的技术中文）**
   - **禁绝反常词汇与行业黑话错用**：禁止使用“走读”代指代码阅读与机制剖析（“走读”在标准中文中是“寄宿”的反义词，用于代码极其违和），统一使用“源码剖析”、“实现分析”、“深入源码”或“代码研读”；动词使用“剖析”、“分析”、“研读”、“实现”。避免俚语直译（如将 takeaway 译为“可以带走的”，统一使用“核心结论”、“关键要点”；不使用“走完/走一遍整条链”，使用“跑通/遍历/执行整条链”）。
   - **消除同义反复与残缺句断裂**：删除生硬倒装与无意识的同义叠词（如“这些位置在序列中的位置”、“实测数据吻合实测”）；避免行末无谓逗号直接连接代码块的悬空句式，主谓宾结构必须完整。
   - **避免第一人称与心路叙事**：技术文档应保持客观中立的观察者口吻，避免出现“我写了两个 kernel”、“我测出的数字超过了上限”、“我本来想演示……被我推翻了”或“写这个实现时我踩的坑”。统一改为客观陈述（如“通过两个 kernel 对比测试”、“基准测试中的纯指令上限为……”、“直觉上常预期……但实测揭示了更复杂的行为”）。
   - **剔除无信息量套话**：严禁“值得注意的是”、“显而易见的是”、“众所周知”、“毋庸置疑的是”等空洞垫话；删繁就简，一句话说明一个事实或因果。

2. **严禁“审计腔”与纠错包袱（读者视角而非交接复盘）**
   - **面向读者最终心智，而非编写者历史心路**：读者阅读教程是为了建立清晰、正确的技术认知与工程判断，不需要了解编写过程中的版本迭代、旧稿错误、内部撤回声明或交接备忘。
   - **禁绝纠错声明与撤回式语言**：正文中严禁出现“撤回‘编码容量为 16 倍’的推论”、“原稿中推导段落已撤回”、“下表保留原稿的换算”、“由于旧脚本计算错误”等审计腔调。错误的旧推论直接以最新实证分析取代，并客观说明不同配置或测算法之间的边界（如说明“两者显存机制不同，不能直接外推容量倍数”）。
   - **避免过度防御性陈述**：不需要反复使用“已有历史采集文件表明……”、“历史记录显示……”等防御性交代。区分事实、理论与待验假设：实测数据直接陈述结果；未覆盖项使用 `UNVERIFIED` 并客观标明待验证条件，不展开成自我检讨。

3. **剔除读者无关的内部元数据**
   - 不在面向读者的页面、标题与正文中展示“数据时间”、“数据日期”等采集时间戳芯片（Chips），避免干扰阅读。环境与机器规格保留核心配置（如 GPU 型号、驱动与关键库版本），时间戳仅作为内部归档证据留存。

提高可读性时保留必要推导、代码与证据。长材料给出阅读指引，避免用日志堆积代替解释，也不能把源码解析压成一句总结。


## 覆盖与页面检查

coverage 检查机制族，不枚举模型实例；`results/crater/option_spaces.json` 应与所核对的库版本一致，升级后重新导出并保留旧工件。

按改动范围检查离线资源、MathML、代码高亮、深浅色、iPad 可读性、折叠与横向溢出；完整源码页保留可访问的行锚点。实际检查过的范围才能标为通过。
