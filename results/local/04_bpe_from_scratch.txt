[0] 一个字符串在内存里是什么
    '风' 的 Unicode 码点：U+98CE
    UTF-8 编码：[233, 163, 142]  = e9 a3 8e  （3 个字节）
    'a'    U+00061  1 字节  61
    'é'    U+000E9  2 字节  c3 a9
    '风'    U+098CE  3 字节  e9 a3 8e
    '🌊'    U+1F30A  4 字节  f0 9f 8c 8a

    UTF-8 是变长的：ASCII 1 字节，多数汉字 3 字节，emoji 4 字节。
    模型看不到「字符」，它看到的是 token id；而 token 是从字节合并出来的。
------------------------------------------------------------------------------
[1] 为什么从字节开始
    如果从「字符」开始，词表就要覆盖所有 Unicode 字符（十几万个），
    而且永远会遇到没见过的字符（生僻字、新 emoji）-> 需要 <UNK>。
    从**字节**开始只要 256 个起始符号，任何输入都能表示，永远不会 OOV。
    代价：一个汉字起手就是 3 个 token，要靠合并把它压回 1 个。

[3] merges 表：它是有序的，顺序就是算法
      序号            左            右             合并结果
       0          ' '          't'             ' t'
       1          'h'          'e'             'he'
       2         ' t'         'he'           ' the'
       3         <ef>         <bc>          <ef bc>
       4      <ef bc>         <8c>              '，'
       5         <e4>         <b8>          <e4 b8>
     ...
     116      <e9 87>         <8c>              '里'
     117         <e7>         <9c>          <e7 9c>
     118      <e7 9c>         <8b>              '看'
     119          '不'          '说'             '不说'

    编码时必须**按这个顺序**尝试合并。换顺序会切出不同的结果，
    模型就认不出来了——所以 merges 表和词表一样，是模型文件的一部分。

[4] 编码：把一段新文本切开
    '风吹过山谷'            15 字节 ->  9 个 token: '风' | <e5> | <90> | <b9> | '过' | '山' | <e8> | <b0> | <b7>
    '风很大'               9 字节 ->  3 个 token: '风' | '很' | '大'
    'the wind blows'   14 字节 ->  7 个 token: 't' | 'he' | ' wind' | ' ' | 'b' | 'l' | 'ows'
    '量子力学'             12 字节 -> 10 个 token: <e9 87> | <8f> | <e5> | <ad> | <90> | <e5 8a> | <9b> | <e5> | <ad> | <a6>

    三件值得注意的事：
    1. 语料里频繁出现的字（风、过、山、很、大）已经被压成 1 个 token；
       没出现过的字（吹、谷、量、子）还是 2~3 个字节 token。
    2. 'the wind blows' 开头的 'the' 被切成 't' | 'he'，
       而中间的 ' wind' 是一个 token —— 因为词表里学到的是 ' the'（带空格），
       句首的 'the' 没有前导空格，匹配不上。**同一个词在不同位置切法不同。**
    3. 空格归到后一个词的前面，所以真实词表里满是 ' the' ' and' 这种 token。

    逐步看 '风吹过' 的合并过程：
      第 1 步：合并 (232, 191) -> 269，剩 8 个 token
      第 2 步：合并 (269, 135) -> 287，剩 7 个 token
      第 3 步：合并 (233, 163) -> 306，剩 6 个 token
      第 4 步：合并 (306, 142) -> 307，剩 5 个 token

[5] 解码与往返一致性
    '风吹过山谷，云落在水面。'
      -> 19 个 token -> '风吹过山谷，云落在水面。'   往返一致：True
    'the wind blows over the valley'
      -> 16 个 token -> 'the wind blows over the valley'   往返一致：True

    字节级 BPE 的往返总是无损的：token 就是字节串，拼起来就是原文。

[6] 词表大小的影响
    对同一句 '风吹过山谷，云落在水面。'（36 字节）：
        合并次数     词表大小  token 数      压缩比
           0      256       36     1.00
          20      276       29     1.24
          60      316       21     1.71
         120      376       19     1.89
         300      406       19     1.89

    合并越多，词表越大，同一句话的 token 越少。
    真实模型的取舍：词表大 -> 序列短（省算力）但 embedding 表大（占显存）。
    Qwen3 的词表约 15 万，Llama 3 约 12.8 万，GPT-2 只有 5 万。

[A] 为什么一个中文字常常是 2~3 个 token
       字       在语料中出现  token 数  切法
       风            4        1  '风'
       水            8        1  '水'
       量            0        2  <e9 87> | <8f>

    '量' 在本语料里出现 0 次，却只切成 2 个 token 而不是 3 个。
    因为 '量' = e9 87 8f，而语料里有 '里' = e9 87 8c——
    前两个字节相同，<e9 87> 这个合并是从 '里' 学来的，'量' 白捡了。
    **字节级 BPE 的一个副作用：没见过的字也能部分复用别的字学到的合并。**

    一个汉字 3 个字节。只有当它在训练语料里足够频繁，
    这 3 个字节才会被合并成 1 个 token；否则它就是 2~3 个 token。
    所以中文在英文为主的 tokenizer 上「token 效率」低——
    同样的意思要更多 token，推理更贵、上下文窗口更快用完。

[B] 坑：token 边界不是字符边界
    '量子' -> 5 个 token
      i     id             字节        单独 decode
      0    371          e9 87           无法单独解码
      1    143             8f           无法单独解码
      2    229             e5           无法单独解码
      3    173             ad           无法单独解码
      4    144             90           无法单独解码

    流式输出时如果每收到一个 token 就单独 decode，会得到乱码或替换字符。
    正确做法是维护一个字节缓冲：拼上新 token 的字节，
    只把能构成完整字符的部分吐出去，剩下的留到下一个 token。
    这就是「增量 detokenize」，L0.5 会实现它。

    验证：逐个 token 单独 decode 再拼接
      朴素做法 -> '�����'
      正确做法 -> '量子'

[C] 预切分（pre-tokenization）为什么必要
    BPE 只统计「相邻对」，它不知道什么是词、什么是句子。
    不做预切分时，它会合并跨越空格甚至跨越标点的组合：

           不预切分学到的 token                            预切分后学到的 token
    第 10轮 'nd'                                     ' s'
    第 30轮 '山'                                      're'
    第 60轮 <ef bc 8c e4 ba>                         <e5 8a>
    第 90轮 'y '                                     'ig'
    第119轮 '里'                                      '不说'

    不预切分时，学到的 token 里有 25 个**内部含空格**，例如：
      'e ' ' the ' 's ' 'nd ' ' the s' 'es '
    也就是说 25/120 = 21% 的词表预算
    花在了「某个词 + 它后面那个空格」这种依赖上下文的组合上。

    在**训练语料里出现过**的句子上，不预切分反而更省 token：
      不预切分： 8 个 token   （'the wind comes from the sea'）
      预切分： 9 个 token   （'the wind comes from the sea'）
    因为它把整段上下文背下来了。换成没见过的句子：
      不预切分：25 个 token   （'a bird sings near the old bridge'）
      预切分：25 个 token   （'a bird sings near the old bridge'）

    **两者一样。** 在这个语料规模上，预切分并没有带来压缩优势——
    这是个诚实的负面结果，不要硬说它更省 token。
    预切分真正的理由是词表预算：上面那 25 个含空格的 token 各占一个词表槽，
    它们只在特定上下文里有用。真实词表有 15 万个槽、训练语料有几百 GB 时，
    这类浪费会累积成显著差距，而且会让同一个词在不同位置切法不一致。
    另一个理由是可控性：预切分保证 token 不跨越数字、标点与文字的边界，
    这对后面要讲的约束解码（L5.6）和数字处理很重要。

[D] 一个容易得出错误结论的陷阱：语料没有多样性
    如果语料只是同一句话重复 20 遍，训练 60 轮之后：
      这句话被切成 4 个 token：'风吹过山谷' | '，' | '云落在水面' | '。'
    整句变成一个 token，压缩比看起来惊人——但这毫无意义：
    换任何一句新话都会退回逐字节。

    这类实验最容易得出的错误结论是「BPE 压缩率很高」。
    评价一个 tokenizer 必须用**它没见过的文本**：
      重复语料训练的词表在留出句上：28 个 token，压缩比 1.18
      多样语料训练的词表在留出句上：17 个 token，压缩比 1.94
