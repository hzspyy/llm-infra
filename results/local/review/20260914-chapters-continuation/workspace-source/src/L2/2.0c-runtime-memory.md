# 2.0c PyTorch 运行时内存：三个生命周期与异步语义

本章连接 Python 引用、CUDACachingAllocator 块状态和 CUDA 异步执行，解释张量何时失去引用、存储何时可复用、GPU 何时真正完成使用。通过四组实验和一个最小块池实现，演示跨流同步、碎片化和 CUDA Graph 内存池的实际行为。

---

## 本章回答的三个问题

1. **del tensor、allocator 可复用与 GPU 使用结束分别发生在何时？**  
   Python 对象在 `del` 后立即失去引用，但 allocator 需要等待 GPU kernel 完成才能将内存标记为可复用。三个时刻通常不同步。

2. **wait_stream 和 record_stream 分别建立什么约束？**  
   `wait_stream` 让一个流等待另一个流的所有先前操作，确保数据依赖顺序；`record_stream` 告诉 allocator 某个张量将被另一个流使用，防止过早释放。

3. **动态形状、碎片与 CUDA Graph 如何改变内存生命周期？**  
   变长分配导致碎片积累，即使 allocated 很小，reserved 也可能很大；CUDA Graph 使用独立内存池，与普通分配隔离。

## 三个生命周期

### 生命周期 1：Python 引用

```python
x = torch.randn(2000, 2000, device='cuda')  # Python 对象创建
del x  # Python 引用立即消失，refcount 降为 0
```

`del` 后 Python 对象被回收，但这**不意味着内存可以立即复用**。

### 生命周期 2：Allocator 可复用

CUDACachingAllocator 在 `del` 后将内存块标记为 "pending"（待回收），但需要等待 GPU 完成才能标记为 "free"（可复用）。

```python
x = torch.randn(2000, 2000, device='cuda')
y = x * 2
del x  # allocated 减少，但 reserved 不变
torch.cuda.synchronize()  # 等待 GPU 完成
# 现在 x 的内存变为 free，可以被新分配复用
```

### 生命周期 3：GPU 使用结束

CUDA kernel 是异步的。`x * 2` 提交后立即返回，kernel 可能仍在 GPU 上运行。

```python
y = x * 2  # kernel 提交，Python 继续
del x      # Python 引用消失，但 kernel 可能仍在读 x
# 如果此时复用 x 的内存，会导致竞态
```

Allocator 通过 stream 和 event 确保安全：只有 stream 上的所有先前操作完成后，内存才能复用。

## 跨流依赖与同步

### 问题场景：竞态

```python
s1 = torch.cuda.Stream()
s2 = torch.cuda.Stream()

with torch.cuda.stream(s1):
    x = torch.randn(1000, 1000, device='cuda')
    y = x * 2  # s1 上提交 kernel

with torch.cuda.stream(s2):
    z = y * 3  # s2 上提交 kernel，可能在 y 计算完成前启动
```

**错误**：s2 的 kernel 可能在 s1 的 `y = x * 2` 完成前就读取 y，导致读到未完成的数据。

### 解决方法 1：wait_stream

```python
with torch.cuda.stream(s2):
    s2.wait_stream(s1)  # s2 等待 s1 的所有先前操作完成
    z = y * 3
```

`wait_stream(s1)` 在 s2 上插入一个等待点，确保 s1 的所有先前 kernel 完成后，s2 才继续。

### 解决方法 2：record_stream

```python
with torch.cuda.stream(s1):
    x = torch.randn(1000, 1000, device='cuda')
    y = x * 2

with torch.cuda.stream(s2):
    y.record_stream(s2)  # 告诉 allocator：y 将被 s2 使用
    z = y * 3
```

`record_stream(s2)` 告诉 allocator："y 的内存将被 s2 使用，在 s2 完成前不能释放"。

### 区别

- **wait_stream**：控制执行顺序，确保数据依赖
- **record_stream**：控制内存生命周期，防止过早释放

两者通常需要同时使用：
```python
s2.wait_stream(s1)      # 确保 y 计算完成
y.record_stream(s2)     # 防止 allocator 在 s2 使用前释放 y
```

## 实验 2：跨流竞态的两个独立错误

`labs/L2/stream_races.py` 把两类错误分开测，各自都有"错"与"对"两条路径，
并记录同一时间轴上两个 stream 的 kernel 起止时刻 —— 重叠区间就是竞态窗口。

### 2A 执行顺序错误：缺 `wait_stream`

s1 先忙 40 次 2048² matmul（约 50 ms）再把缓冲写成 1.0；s2 不做任何等待，
直接对同一缓冲求和（期望 1048576）：

```
[顺序] 两个流：s1 延时后写 1.0，s2 立刻求和（期望 1048576）
  缺 wait_stream：20 次里 19 次读到旧值
  加 wait_stream：20 次里 0 次读到旧值
  缺 wait_stream 的时间线（重叠区间就是竞态窗口）：
    s1: =================================================  [ 0.000 → 49.819 ms]
    s2:                                         ==========  [40.966 → 51.710 ms]
```

s2 的 kernel 从 40.97 ms 开始，落在 s1 写完缓冲（49.82 ms）之前 ——
那 8.9 ms 的重叠就是竞态窗口。注意结果是 **19/20 而不是 20/20**：
竞态是否触发取决于调度时机，"跑一遍没出错"从来不是证据。

### 2B 存储过早复用：缺 `record_stream`

s2 延后 60 次 matmul 再读 `buf * 2`（期望 2.0）；与此同时 s1 申请同尺寸新张量
并写入 7.0。只要 allocator 把刚释放的块交给 s1，s2 就会读到 14.0：

```
[复用] s2 延时后读 buf*2（期望 2.0）；s1 随即申请同尺寸新张量
  缺 record_stream：20 次里地址被复用 20 次，读到被覆盖的值 20 次
  加 record_stream：20 次里地址被复用 0 次，读到被覆盖的值 0 次
  样本地址：旧 0x7e8cf2000000 → 新 0x7e8cf2000000（同一块），out[0]=14.0
```

两类错误的边界很清楚：

| 修法 | 保证什么 | 不保证什么 |
|---|---|---|
| `s2.wait_stream(s1)` | s2 的后续 kernel 在 s1 已有工作之后开始 | 读完之前那块存储不被 allocator 复用 |
| `t.record_stream(s2)` | 这块存储要等 s2 的**后续**工作完成才能被复用 | 数据依赖的执行顺序 |

两者管的是两件不同的事，所以真实代码里通常会同时出现。
同步本身的开销（同一 lab 的小分配微基准）约 6.6%：1.63 → 1.74 ms。

## 碎片化

### 什么是碎片

Allocator 以 segment 为单位向操作系统申请内存（通常 20 MB），然后在 segment 内部分配 block。当分配和释放的尺寸不规则时，segment 内部会产生碎片：

```
Segment (20 MB)
[4MB used] [2MB free] [3MB used] [1MB free] [10MB used]
```

即使有 3 MB 的 free 空间，也无法满足一个 5 MB 的分配请求（因为碎片不连续），allocator 只能申请新的 segment。

### 实验 3A：固定大小无碎片

{{results/crater/2.0c/memory_fragmentation.json:experiment_3a}}

10 次迭代，allocated 和 reserved 保持不变，碎片率 80.9%（因为 20 MB segment 只用了 3.81 MB）。

### 实验 3B：变长分配产生碎片

{{results/crater/2.0c/memory_fragmentation.json:experiment_3b}}

分配 500/1000/1500/2000 的张量，碎片率在 30%～95% 之间波动。第 2 次迭代（1000→1500→2000）后，reserved 从 2 MB 跳到 22 MB，说明 allocator 申请了新的 segment。

### 实验 3D：KV cache 模拟

模拟变长序列的 KV cache：

{{results/crater/2.0c/memory_fragmentation.json:experiment_3d}}

```
seq_len   allocated   reserved   fragmentation
128       16 MB       16 MB      0.0%
256       32 MB       48 MB      33.3%
512       64 MB       112 MB     42.9%
1024      128 MB      240 MB     46.7%
512       64 MB       240 MB     73.3%
256       32 MB       240 MB     86.7%
128       16 MB       240 MB     93.3%
```

**关键观察**：从 1024 回到 128 时，allocated 只有 16 MB，但 reserved 仍为 240 MB。这个 93.3% 是
"reserved 远大于 allocated"，不等于 93.3% 的内存被碎片吃掉 —— 见下一节的口径拆分。

### 实验 3F：真实变长分配轨迹与 `expandable_segments` 对照

`labs/L2/alloc_trace.py` 用 200 个固定长度（16…4096）的请求分批到达、
按各自完成时刻释放（完成顺序与到达顺序不同），一共 35 步。每步记录六个口径：

| 口径 | 含义 | 来源 |
|---|---|---|
| active | 已分配出去的请求字节 | `memory_allocated()` |
| reserved | 向驱动要来的总字节 | `memory_reserved()` |
| cached free | `reserved − active`，**可复用的缓存，不是碎片** | 相减 |
| inactive_split | 段内已释放、被切碎的空闲块 | `memory_snapshot()` 的块状态 |
| inactive | 整块可复用的空闲块 | 同上 |
| pending | 已释放但 GPU 可能还在用的块 | 同上（本负载为 0） |

同一份请求序列，两种分配器配置的峰值：

| 配置 | peak active | peak reserved | reserved/active | inactive_split | segments | retries |
|---|---:|---:|---:|---:|---:|---:|
| 默认分配器 | 307.94 MB | 382.00 MB | 1.24× | 0.00 MB | 35 | 0 |
| `expandable_segments:True` | 300.94 MB | 350.00 MB | 1.16× | 0.00 MB | 2 | 0 |
| 默认分配器 + 尺寸升序到达 | 728.00 MB | 888.00 MB | 1.22× | 0.00 MB | 76 | 0 |

三条结论：

1. **缓存可复用不等于碎片。** 默认模式下 74 MB 的 `reserved − active` 里，
   `inactive_split` 为 0 —— 这些空闲块都是整块可复用的，allocator 只是没还给驱动。
   把 `reserved − allocated` 直接叫碎片，会得出"74 MB 碎片"的错误结论。
2. **`expandable_segments` 省的是段数与 reserved。** 同一份活跃轨迹下
   382 → 350 MB、段数 35 → 2，比值 1.24× → 1.16×。它用"一段虚拟地址连续"
   换掉了 N 段物理内存，代价是与 IPC/RDMA 注册的兼容性。
3. **尺寸顺序主要改变峰值占用，不改变碎片比。** 把同样的长度集合改成升序到达，
   峰值 active 从 307.94 涨到 728.00 MB（大请求同时驻留），
   但 `reserved/active` 只从 1.24× 变到 1.22×，`inactive_split` 仍是 0。
   **这一行不能直接和上面两行比 reserved** —— 它的活跃数据量本来就不同。

比较两种配置前必须确认**活跃数据相同**：脚本自带一份"存活张量字节"账本，
逐 step 完全一致；allocator 的 `active` 轨迹在默认模式下比这份账本最多高 8 MB
（对部分尺寸按块取整，实测一个 2 MiB 的请求占了 3 MiB 的 active 块），
`expandable_segments` 下该残差为 0。两个口径都记录下来，不用其中一个冒充另一个。
三行的请求总量相同（1027.4 MB），这是这一组比较的另一半前提。

### 实验 3G：CUDA Graph 的内存池

固定形状的步骤跑 200 次，对比"逐个 launch"与"捕获一次 + replay"：

| 配置 | peak reserved | peak allocated | 结束后 allocated | retries |
|---|---:|---:|---:|---:|
| 不捕获 | 54 MB | 44 MB | 36 MB | 0 |
| 捕获 + replay | 140 MB | 112 MB | 104 MB | 0 |

图的池要长期持有静态输入/输出与 cuBLAS workspace，所以 reserved 与 allocated
都明显更高；换来的是 replay 不再经过 allocator。**CUDA Graph 省的是 CPU 提交，
不是显存** —— 把它当省显存手段会失望。

### 实验 3H：`expandable_segments` × CUDA Graph 的组合

上面两件事是分开测的：`expandable_segments` 改的是段的管理方式，
CUDA Graph 用的是另一套私有池。两者同时打开会怎样？
四种配置各起一个进程（分配器配置必须在 CUDA 初始化之前生效），
每种配置再按两种顺序各跑一遍（`labs/L2/alloc_graph_combo.py`）：

| 配置 | 顺序 | 峰值 active | 峰值 reserved | 段数 | inactive_split | 图池增量 | 捕获 |
|---|---|---:|---:|---:|---:|---:|---|
| native | 轨迹→图 | 307.94 MB | 382 MB | 35 | 0 | 88 MB | 成功 |
| native | 图→轨迹 | 371.94 MB | 446 MB | 37 | 0 | 88 MB | 成功 |
| expandable | 轨迹→图 | 300.94 MB | 350 MB | 2 | 0 | 84 MB | 成功 |
| expandable | 图→轨迹 | 364.94 MB | 430 MB | 3 | 0 | 84 MB | 成功 |
| native | 无图 | 307.94 MB | 382 MB | 35 | 0 | — | — |
| expandable | 无图 | 300.94 MB | 350 MB | 2 | 0 | — | — |

四点结论：

1. **两者可以共存。** 在 torch 2.13.0+cu130 上，`expandable_segments:True`
   下捕获成功、replay 正常，两种顺序都没有报错。
   早期版本上这组组合有过限制，所以这条结论要绑定版本读（版本写在实验环境一节）。
2. **图池不参与段扩展。** `expandable` 下轨迹本身只有 2 个段，
   加上图池后变成 3 个 —— 多出来的一段就是图池，增量 84 MB
   与 native 下的 88 MB 几乎相同。**图池是一块独立、不参与 expandable 的池。**
3. **先建图会抬高变长轨迹的峰值。** 同一份 200 请求轨迹，
   峰值 reserved 从 382 MB 涨到 446 MB（native）、350 MB 涨到 430 MB（expandable），
   峰值 active 也同步上升。图池常驻的那部分会计入 allocator 的计数，
   轨迹自己的分配只能复用其中已经空闲的块。
   **做容量规划时要把图池算进常驻，不能只看轨迹自身的账。**
4. **删掉图之后池不归还。** `del graph` + `empty_cache()` 之后，native 下仍有
   84 MB reserved / 68 MB active，expandable 下 80 MB / 68 MB。
   图池的生命周期与 Python 对象不绑定 —— 这与陷阱 6（"以为 CUDA Graph 省显存"）
   是同一件事的两个方向。

顺带一条统计口径的坑：`segment.all.allocated/freed` 这两个计数器在 native 下
会随 `empty_cache()` 变动（45/42），在 `expandable` 下始终是 0/0 ——
**跨配置比较段的数量要用 `memory_snapshot()`，不要用这两个计数器。**

## CUDA Graph 内存池

### 普通分配 vs CUDA Graph

CUDA Graph 捕获时会记录所有内存分配，replay 时使用**独立的内存池**，与普通分配隔离。

### 实验 4A：普通迭代

{{results/crater/2.0c/memory_cuda_graph.json:experiment_4a}}

5 次迭代，allocated 和 reserved 保持不变（11.44 MB / 20 MB），allocator 复用了内存。

## 最小块池实现

为了理解 allocator 的核心逻辑，我们实现一个最小块池，支持：
1. 流归属
2. 延迟回收（pending）
3. Event 完成检查

### 核心数据结构

```python
class Block:
    def __init__(self, size, stream):
        self.size = size
        self.stream = stream
        self.event = None
        self.allocated = True
```

### 分配逻辑

```python
def allocate(size, stream):
    # 1. 查找可复用的 free block
    for block in free_blocks:
        if block.size >= size:
            block.allocated = True
            block.stream = stream
            return block
    
    # 2. 检查 pending blocks（等待 event 完成）
    process_events()
    for block in free_blocks:
        if block.size >= size:
            block.allocated = True
            block.stream = stream
            return block
    
    # 3. 申请新 segment
    segment = allocate_segment(size)
    block = Block(size, stream)
    return block
```

### 释放逻辑

```python
def free(block):
    # 标记为 pending，记录当前 stream 的 event
    block.allocated = False
    block.event = block.stream.record_event()
    pending_blocks.append(block)
```

### Event 完成检查

```python
def process_events():
    for block in pending_blocks:
        if block.event.query():  # 检查 event 是否完成
            free_blocks.append(block)
            pending_blocks.remove(block)
```

### 实验 5：最小块池演示

完整实现在 `labs/L2/mini_block_allocator.py`。

{{results/crater/2.0c/mini_block_allocator.txt}}

解读：
- **实验 5A**：分配 → 释放 → synchronize → 复用。释放后 block 进入 pending，同步后进入 free，然后被复用。
- **实验 5B**：跨流分配。stream2 释放的 block 在 stream1 event 完成后才能被复用。
- **实验 5C**：碎片化。释放 block 1/3/5 后，分配 8 MB 需要扩展新 segment（因为碎片不连续）。
- **实验 5D**：变长分配。碎片率在 40%～90% 之间波动。

### 实验 5E：三个生命周期时刻、split/merge 与术语对照

整块分配看不出"切分"和"合并"。5E 给最小块池补上 owner stream、pending event、
`split`/`merge` 事件，并把三个时刻分别打印：

```
-- 时刻 1：Python 引用被丢掉，但 GPU 可能还在用 --
   free(a) 之后：allocated=0.00 MB  pending=4.00 MB  inactive_split=16.00 MB
   块的 owner stream 仍记为 0，pending event = 0；此刻复用它是竞态

-- 时刻 2：event 完成，allocator 可以复用 --
   complete(event=0) 之后：pending=0.00 MB  inactive_split=0.00 MB
   块状态 = free；只有到这一刻，下一次 malloc 才能拿到它

-- 时刻 3：真正分配给下一个请求（复用 + 切分）--
   malloc(1 MiB) → block 0，是否复用了刚释放的 block？是
   split 事件：{'op': 'split', 'block': 0, 'kept': 4194304, 'rest': 1, 'rest_size': 16777216}
   reuse 事件：{'op': 'reuse', 'block': 0, 'size': 1048576, 'stream': 0}

-- merge：相邻空闲块在 event 完成后合并 --
   释放两个相邻块后：inactive_split=12.00 MB
   全部 event 完成后：inactive=20.00 MB  inactive_split=0.00 MB
   合并事件：[{'op': 'merge', 'into': 0, 'absorbed': 1, 'size': 8388608}, ...]
```

三个时刻对应三件不同的事，术语不能混：**Python 引用消失**（`free` 调用）→
**allocator 可复用**（event 完成）→ **GPU 真正用完**（event 本身就是这个证据）。
最小池的 `stats()` 与真实分配器使用同一套口径
（allocated / reserved / active / inactive / inactive_split / pending），
`memory_snapshot()` 里各状态块的字节数与它逐项对照，避免"用同一个词指两件事"。

## 源码入口

### CUDACachingAllocator

**文件**：`pytorch/c10/cuda/CUDACachingAllocator.cpp`

核心函数：
- `malloc()`：分配内存，查找 free block → 检查 pending → 申请新 segment
- `free()`：释放内存，记录 event 并标记为 pending
- `process_events()`：检查 pending 队列，将完成的 block 移到 free

关键数据结构：
- `Block`：包含 size、stream、event、allocated 标志
- `Segment`：一次向操作系统申请的大块内存（默认 20 MB）

### Stream 与 Event

**文件**：
- `pytorch/c10/cuda/CUDAStream.h`
- `pytorch/c10/cuda/CUDAEvent.h`

核心函数：
- `record()`：在 stream 上记录 event
- `query()`：查询 event 是否完成
- `wait()`：让当前 stream 等待 event 完成

### Python 绑定

**文件**：`pytorch/torch/csrc/cuda/Module.cpp`

核心函数：
- `THCPModule_cudaSynchronize()`：同步所有 stream
- `THCPStream_wait_stream()`：stream 等待另一个 stream
- `THPVariable_record_stream()`：记录张量将被另一个 stream 使用

## 常见陷阱

### 1. 把 reserved 当作泄漏

```python
x = torch.randn(1000, 1000, device='cuda')
del x
torch.cuda.synchronize()
# reserved 仍为 20 MB，这不是泄漏！
```

Allocator 保留内存以供复用，只有 `empty_cache()` 才会归还给操作系统。

### 2. 跨流未同步

```python
with torch.cuda.stream(s1):
    y = x * 2

with torch.cuda.stream(s2):
    z = y * 3  # 错误：未等待 s1
```

必须 `s2.wait_stream(s1)` 或者在主流上同步。

### 3. 跨流未记录使用者

```python
with torch.cuda.stream(s1):
    y = x * 2

del x  # 错误：allocator 可能在 s1 完成前释放 x
```

必须 `x.record_stream(s1)` 告诉 allocator。

### 4. 把 "20 次都没错" 当成没有竞态

缺 `__syncthreads` 的共享内存竞态、缺 `wait_stream` 的跨流顺序问题，都不是每次都触发：
本章实测跨流顺序错误 20 次里错 19 次，仍有 1 次"看起来是对的"。
判断依据只能是工具与机制，不是重复次数 —— 跨流用事件与依赖显式表达，
共享内存用 `compute-sanitizer --tool racecheck`（2.1 有完整对照）。

### 5. 把 `reserved − allocated` 全叫碎片

这段差值绝大部分是**整块可复用的缓存**。本章的真实变长轨迹里，
默认分配器峰值 `reserved − allocated = 74 MB`，而 `inactive_split`（真正被切碎、
无法直接合并的空闲）为 0。要看碎片，得从 `memory_snapshot()` 的块状态里取，
并且先确认两次比较的活跃数据量相同。

### 6. 以为 CUDA Graph 省显存

捕获后图有自己的池，静态输入/输出与 workspace 长期驻留：
本章实测固定形状步骤 200 次，不捕获 peak reserved 54 MB，
捕获 + replay 是 140 MB。图省的是 CPU 提交，不是显存。

### 7. 测量工具触发初始化

```python
torch.cuda.memory_allocated()  # 这会触发 CUDA 初始化
x = torch.randn(10, 10, device='cuda')
# 此时 reserved 可能包含初始化开销
```

测量前先 `reset_peak_memory_stats()`。

### 8. 把图池当成"轨迹之外的东西"来算容量

图池常驻的那部分会计入 allocator 的 active/reserved 计数：
同一份 200 请求轨迹，先建图再跑，峰值 reserved 从 382 MB 涨到 446 MB（native）、
350 MB 涨到 430 MB（expandable）。**服务里同时有图和变长请求时，
容量要按"图池 + 轨迹"一起算**，不能只算轨迹。

### 9. 用 `segment.all.allocated` 比较两种分配器的段数

这个计数器在 native 下随 `empty_cache()` 变动（本章 45/42），
在 `expandable_segments` 下恒为 0/0。段的数量与状态一律从
`memory_snapshot()` 里取。

## 自测题

<details markdown="1">
<summary>1. `del graph` 之后为什么 reserved 不下降？</summary>

因为 CUDA Graph 的内存池与 Python 对象不绑定。捕获时图会记录所有分配，
replay 用一套私有池；删掉 `CUDAGraph` 对象并不销毁这份池，
allocator 也不能把它当成普通空闲块复用。

本章实测：`del graph` + `empty_cache()` 之后，native 下仍有 84 MB reserved /
68 MB active，`expandable_segments` 下 80 MB / 68 MB。
要真正回收，得销毁图池本身（PyTorch 侧没有公开的单池释放接口，
实践做法是把图放在进程生命周期的末尾、或者在需要时重启 worker）。

**这条与"图省显存"是同一件事的两面**：图省的是 CPU 提交，池是它的代价。
</details>

<details markdown="1">
<summary>2. `expandable_segments` 下段数只有 2 个，native 有 35 个。这能说明 expandable"更省显存"吗？</summary>

不能这么说。本章同一份轨迹下：峰值 active 300.94 MB 对 307.94 MB、
峰值 reserved 350 MB 对 382 MB。省的是 32 MB 的 reserved 与 33 个段，
**不是 33 倍的显存**。

原因：native 分配器每申请一块大的地址空间就形成一个段，段内切块；
`expandable_segments` 用一个可以继续增长（并支持物理页回收）的段来承载同样的数据。
段的"个数"是管理方式差异，不是用量差异。

判据要分开写：**用量看 active/reserved，碎片看 `inactive_split`**。
这组实验里两者的 `inactive_split` 都是 0。
</details>

<details markdown="1">
<summary>3. 为什么 `expandable_segments` 下 `segment.all.allocated` 恒为 0？</summary>

`segment.all.allocated` 统计的是"从驱动申请新段"的次数。
`expandable_segments` 只维护少量（这里是 2–3 个）可增长的段，
后续需求靠扩展既有段满足，所以不增加这个计数。

后果是：**跨分配器比较"分配了多少次"用这个计数器会得到错误结论**
（expandable 看起来一次都没分配）。段的数量与状态从 `memory_snapshot()` 里取，
本章的段数（35 对 2）就是这么来的。
</details>

<details markdown="1">
<summary>4. 服务里同时用 CUDA Graph 和变长请求，容量怎么算？</summary>

按"图池 + 轨迹峰值"一起算，而不是只看轨迹：

1. 先按引擎的 batch 分桶确定要捕获几张图、每张图多大；
2. 图池的 reserved 是一次性成本，但它的 **active 部分长期占住**
   （本章一组图池：native 84 MB reserved / 68 MB active）；
3. 变长请求的轨迹峰值要在**图池已经驻留**的前提下测 ——
   同样的轨迹，先建图再跑的峰值比先跑轨迹再建图高 64 MB（native）/ 80 MB（expandable）。

本章的 `alloc_graph_combo.py` 的 `graph-first` 顺序就是在测这件事：
它比 `trace-first` 更接近真实服务的启动顺序（先捕获图，再接请求）。
</details>
