[1] logits / logprob / prob 三者的关系
    logits 是模型直接输出的实数，没有归一化，加一个常数不改变分布。
    prob    = softmax(logits)            —— 归一化，和为 1
    logprob = log_softmax(logits)        —— log(prob)，永远 <= 0

    验证 1：给所有 logit 加 100，softmax 不变
      最大绝对差 = 5.274e-16
    验证 2：exp(logprob) == prob
      最大绝对差 = 7.451e-09
    验证 3：概率之和 = 1.000024

    为什么 API 返回的是 logprob 而不是 prob：
    概率会小到 1e-30，fp32 存不下也没法比较；取对数之后是 -70 这种数，
    而且多个 token 的联合概率取对数就变成求和，数值稳定。
    例：连续采 10 个概率各 0.5546 的 token，
        联合概率 = 2.754e-03，而 logprob 相加 = -5.89

[3] top-k 与 top-p 的截断
    策略                    候选数       覆盖概率 候选
    原始                 151936     1.0000   ['北京', '哪里', '____', '什么']
    top_k=1                 1     0.5546   ['北京']
    top_k=5                 6     0.7515   ['北京', '哪里', '____', '什么']
    top_k=50               52     0.9075   ['北京', '哪里', '____', '什么']
    top_p=0.5               1     0.5546   ['北京']
    top_p=0.9              46     0.9008   ['北京', '哪里', '____', '什么']
    top_p=0.99           1598     0.9900   ['北京', '哪里', '____', '什么']

    top-k 固定候选个数，top-p 固定覆盖的概率质量。
    区别在模型确定时最明显：模型很确定时 top-p 只留 1~2 个，
    top-k=50 却仍会保留 50 个（包括一堆概率极低的）。
    两者常常一起用：先 top-k 砍掉长尾，再 top-p 动态收紧。

[5] 增量 detokenize：流式输出的坑
    '风吹过山谷' -> 3 个 token
      i       id      单独 decode 字节
      0   109520           '风吹' e9 a3 8e e5 90 b9
      1    38182            '过' e8 bf 87
      2   113599           '山谷' e5 b1 b1 e8 b0 b7

    这三个 token 各自都是完整字符，所以逐个 decode 恰好没问题。
    但这只是运气好。换一个词表里没有的罕见字：
    '𩸽' (4 字节) -> 3 个 token
      i       id token         单独 decode
      0   103914 'ð©'                '�'
      1      116 '¸'                 '�'
      2      121 '½'                 '�'

      逐 token decode 再拼接 -> '���'   ← 三个替换符
      整体 decode            -> '𩸽'
      两者相同：False

    流式接口是一个 token 一个 token 往外吐的，如果每次都单独 decode，
    用户就会先看到几个 '�' 再看到正确的字——或者永远看不到正确的字。

    用字节缓冲的正确做法（本脚本的 IncrementalDetokenizer）：
      推入 id=103914   字节 f0 a9        -> 吐出 ''  缓冲剩 2 字节
      推入 id=116      字节 b8           -> 吐出 ''  缓冲剩 3 字节
      推入 id=121      字节 bd           -> 吐出 '𩸽'  缓冲剩 0 字节
      拼接结果 '𩸽'

[6] 停止条件
    三条独立的路径，在不同的层判断：
    1. eos token：采到 '<|im_end|>' (id 151645) 就停。
       在采样之后、detokenize 之前判断，属于引擎的调度层。
    2. stop string：生成的**文本**里出现了指定字符串就停。
       必须在 detokenize 之后判断，而且要处理跨 token 的情况——
       停止串可能横跨两个 token，只看单个 token 会漏。
    3. max_tokens：计数到了就停。这是唯一保证会终止的一条。

[7] 与引擎对齐：自己实现的 top-p 对不对
    用同一组 logits，比较自己的实现与 torch 官方写法：
      top_p=0.5: 候选集相同 = True  (我的 1 个 / 参照 1 个)
      top_p=0.9: 候选集相同 = True  (我的 46 个 / 参照 46 个)
      top_p=0.95: 候选集相同 = True  (我的 146 个 / 参照 146 个)

    两种写法在边界上的差别：一个用「含自己的累计 > p」再右移，
    一个用「不含自己的累计 > p」。数学上等价，实现上容易写错一个位置——
    差一个 token 在温度低时会显著改变输出。
