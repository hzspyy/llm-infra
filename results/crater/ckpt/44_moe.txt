--- ⚠ 跨层求和会把不均衡抹掉 -----------------------------------------------------------
  总体那张表看着还行（最热/最冷 3.7×，CV 0.295），
  但逐层表里最热/最冷动辄几百倍、CV 在 1.0 以上，而且**每层都有专家拿到 0.00%**。
  原因：不同层的热专家不是同一批，加起来互相填平了。
  **而系统关心的是每一层**——每一层都要做一次 grouped GEMM，
  每一层的最热专家各自决定那一层的关键路径。所以看总体是看错了对象。

--- 对系统的直接含义（用逐层的数） ---------------------------------------------------------
  每层 985 个 token × top-8 = 7880 次选择，均匀应为每专家 123 个
  实测最热的专家拿到该层的 11.8%，即 933 个 token —— 是均匀值的 7.6 倍
  grouped GEMM 若各段并行执行，总时间由最大的那一段决定，
  所以并行效率的上界就是 1/7.6 = 13%。
  在专家并行（EP）里，这直接变成**某张卡在算、其它卡在等**（L6.3）。

[C] grouped GEMM：分组本身要多少代价
==============================================================================
  H=2048 I=1024 专家数=64 top-8  一步 4096 个 token

  做法                                        ms    TFLOP/s
  grouped GEMM（含排序）                  1.379       99.7
  其中只排序                                0.255          —   占 18.5%
  同样 FLOP 的单个大 GEMM                  0.627      219.3   <- 上界

  分成 64 个小 GEMM 相对一个大 GEMM 慢 2.2×。
  原因：每个小 GEMM 的 M 只有 ~512，远小于 tensor core 喜欢的形状
  （2.7 §六 测过：瘦长 GEMM 的效率远低于方阵）。
  真实实现用专门的 grouped GEMM kernel（一次 launch 处理所有分段），
  比这里的 python 循环好得多 —— 这里量的是**上界**。

--- 不均衡会让情况更糟 ---------------------------------------------------------------
  均匀                     max=   575 min=  462 max/mean= 1.12×
  倾斜（一个专家占 20%）          max=  7061 min=  357 max/mean=13.79×
  分段 GEMM 的总时间由最大的那一段决定（若并行执行），
  所以 max/mean 就是并行效率的直接上界。

==============================================================================
[D] 显存与带宽的账
==============================================================================
  一个专家 12.00 MB (bf16)
  一层 64 个专家 = 768.0 MB
  16 层 = 12.00 GiB 的专家权重

--- decode 时到底要读多少权重 --------------------------------------------------------
  batch=1 时每 token 只碰 K 个专家：
    读 8×16 = 128 个专家 = 1536.0 MB
  但 batch 一大，不同 token 路由到不同专家，读取量迅速逼近全部：
    batch            期望被碰到的专家数/层       读取量 MB      占全部
        1                    8.0       1536.0   12.5%
        4                   26.5       5085.0   41.4%
       16                   56.4      10837.2   88.2%
       64                   64.0      12285.6  100.0%
      256                   64.0      12288.0  100.0%
     1024                   64.0      12288.0  100.0%

  batch≥64 时基本每层的所有 64 个专家都要读一遍 ——
  **MoE 的稀疏性在大 batch 下从带宽角度基本消失**，
  只在算力上仍然稀疏（每 token 仍只算 K 个）。
  这就是为什么 MoE 适合「算力受限」的场景，
  而在小 batch decode（带宽受限，3.3）上优势有限。
