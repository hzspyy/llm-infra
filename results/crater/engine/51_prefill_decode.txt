==============================================================================
[C] 一个请求的时间构成：TTFT 与 TPOT
==============================================================================
  [显存] 空闲 30.5/31.4 GiB，留 4 GiB 给他人 -> gpu_memory_utilization=0.55

  TTFT = time to first token（含排队 + prefill）
  TPOT = time per output token（decode 每步）

    prompt 长度     生成    TTFT ms    TPOT ms      总时长 ms    TTFT 占比
          128     64       5.73      4.489       293.1      2.0%
          512     64      11.15      4.510       299.8      3.7%
         2048     64      37.13      4.511       325.8     11.4%
         4096     64      76.20      4.562       368.2     20.7%

  prompt 越长，TTFT 越大而 TPOT 基本不变（3.3 说过 decode 由 KV 决定，
  这里 KV 还很小）。所以「长 prompt + 短输出」的负载 TTFT 占主导，
  「短 prompt + 长输出」的负载 TPOT 占主导。**两者要用不同的指标衡量。**

==============================================================================
[D] 长度不齐的浪费
==============================================================================
  [显存] 空闲 30.5/31.4 GiB，留 4 GiB 给他人 -> gpu_memory_utilization=0.55

  静态批处理：一批一起开始、一起结束，最长的那条决定整批时长。
  连续批处理（continuous batching）：谁结束谁就退出，空位立刻补新请求。
  这里量一下「长度不齐」造成的浪费有多大。

  长度一致（都生成 64）
    实际生成 1024 token，耗时 335.1 ms，吞吐 3056 tok/s
    最长 64，若静态批处理要按最长算：1024 个 step 的位置
    利用率 = 1024 / 1024 = 100.0%

  长度不齐（1..128 均匀）
    实际生成 949 token，耗时 562.4 ms，吞吐 1687 tok/s
    最长 114，若静态批处理要按最长算：1824 个 step 的位置
    利用率 = 949 / 1824 = 52.0%

  读这两行要小心，它们说的是两件事：
  1. 「利用率」是**静态批处理**会浪费掉的比例（不齐时只有约一半）。
  2. 但两行的**吞吐**也差了近一倍，而 vLLM 已经是连续批处理 ——
     原因是这里**没有排队的新请求可以补位**。批在跑的过程中不断有请求
     结束，活跃数从 16 一路掉到 1，最后几步是在按 batch=1 的速度跑。
  **连续批处理消除的是「等最慢的那条」，不是「没活干」。**
  它的收益要在有队列的开环压测下才看得到（5.3 / L8.3）。

--- 补位实验：给它一个队列 -------------------------------------------------------------
  一次提交 64 条（长度同样 1..128 不齐）
    实际生成 4162 token，耗时 751.6 ms，吞吐 5537 tok/s
    对照上面 16 条不齐时的 1710 tok/s —— 有更多请求可调度时，
    早结束的请求空出的位置立刻被后面的补上，吞吐回来了。
