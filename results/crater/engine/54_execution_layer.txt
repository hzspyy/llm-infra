[A] eager vs CUDA Graph：decode 吞吐
==============================================================================
  2.6b 实测：CPU 侧 launch 14,003 -> 863（16.2×），GPU kernel 数不变。
  launch 省下的是 CPU 时间，所以收益应当在**CPU 提交是瓶颈**的地方最大，
  也就是 **batch 小、模型小** 的时候（L1.4：每次 launch 2.68 µs）。



   batch    eager ms/步      图 ms/步   eager tok/s     图 tok/s       加速
       1         4.400       3.149           227         318    1.40×
       4         4.522       3.717           885        1076    1.22×
      16         4.521       3.854          3539        4152    1.17×
      64         5.064       3.744         12638       17094    1.35×

  eager 每步 4.40 -> 5.06 ms（随 batch 增长）
  图   每步 3.15 -> 3.85 ms（基本不随 batch 变）
  这是本节最清楚的一条：**开图之后每步时间几乎与 batch 无关**，
  说明这个区间里的 step 时间由 CPU 提交主导，而图把它压成了常数。

  ⚠ 加速比**不是单调的**（batch=16 是最低点，64 又回升）。
  我原本预期它随 batch 单调下降（batch 大 -> GPU 忙 -> CPU 提交被藏住），
  数据不支持这个说法。**没有查清原因，不要引用这条趋势。**
  可能的方向：eager 路径在大 batch 上的 python/dispatch 开销、
  或图捕获尺寸的 padding（见 [C]）。判据：用 2.6 的 nsys 方法
  分别抓两条路径在 batch=16 和 64 上的 CPU 时间线对比。

[B] 代价一：捕获时间与显存
==============================================================================

  eager（无图）      启动    5.48 s   启动后驱动可见空闲   9.45 GiB

  CUDA Graph     启动    9.50 s   启动后驱动可见空闲   9.63 GiB

  图捕获发生在启动时：要为每个准备捕获的 batch 尺寸各跑一遍前向并录下来。
  代价是**启动更慢**，以及**图本身占的显存池**（2.0 §4.3 里
  vLLM 的 `cudagraph_memory_estimate_applied` 就是这一项）。
  注意上面两行的空闲显存差不能直接当图的开销 —— 
  vLLM 会按 gpu_memory_utilization 把剩下的全分给 KV，两者是此消彼长的。
  **真正被图吃掉的那部分，表现为 KV cache 变小、可容纳的并发变少。**

==============================================================================
[C] 代价二：只有捕获过的尺寸能用图
==============================================================================
  CUDA Graph 把张量地址和形状都固化在图里，所以**每个 batch 尺寸**
  都要单独捕获一份。vLLM 捕获一组离散的尺寸，
  运行时把实际 batch **向上取整**到最近的那个捕获尺寸（padding）。


  本次捕获的尺寸（共 51 个）：
    [1, 2, 4, 8, 16, 24, 32, 40, 48, 56, 64, 72, 80, 88, 96, 104, 112, 120, 128, 136, 144, 152, 160, 168, 176, 184, 192, 200, 208, 216, 224, 232, 240, 248, 256, 272, 288, 304, 320, 336, 352, 368, 384, 400, 416, 432, 448, 464, 480, 496, 512]

  判据：若 padding 真的有代价，batch=17 的每步时间应当
  接近 batch=24（它被 pad 成 24），而明显高于 batch=16。
   batch    pad 到      浪费      ms/步     tok/s
       8        8   1.00×     3.747      2135
      16       16   1.00×     3.859      4146
      17       24   1.41×     3.505      4850
      24       24   1.00×     3.623      6624
      32       32   1.00×     3.580      8940
      33       40   1.21×     3.549      9299
      40       40   1.00×     3.584     11162
      48       48   1.00×     3.627     13233
      64       64   1.00×     3.731     17154

  所有 batch 的每步时间落在 3.505–3.859 ms，极差只有 10.1%。
  **padding 的代价在这个区间里量不出来** —— 因为每步时间由 CPU
  提交主导（[A] 节已经看到图路径的每步时间几乎与 batch 无关），
  多算几行 GPU 计算根本不构成瓶颈。

  所以 padding 什么时候才要紧？**当 step 变成算力受限时**：
  batch 大到 GPU 真的忙起来（5.1 算过 batch≈72 越过平衡点），
  或者序列很长。本 lab 的 batch 上限 64 还没到那里。
  要看到 padding 的代价，把 batch 扫到几百（见消融 3）。

[D] 什么时候图没有收益
==============================================================================
  图省的是 CPU 提交时间。以下两种情况它帮不上忙：
    1. prefill —— 形状随 prompt 长度变，且 GPU 本来就很忙
    2. batch 很大 —— CPU 提交已经被 GPU 执行藏住了



  prefill（4 条，只生成 1 个 token）
    prompt 长度   eager ms      图 ms       加速
          512      36.30     34.14    1.06×
         2048     135.86    134.64    1.01×

  prefill 上基本没有差别 —— 印证 2.6b 的结论：
  图减少的是**提交次数**，而 prefill 的时间由 GPU 计算主导。
