==============================================================================
[A] decode 的算术强度：为什么它必然是访存受限
==============================================================================
  一步 decode，单头：Q 是 1×D，K/V 各是 S×D。
    FLOP: qK^T 2SD + pV 2SD = 4SD
    字节: 读 K/V = 2·S·D·2 = 4SD（bf16）；Q 与 O 只有 O(D)，忽略
    算术强度 = 4SD / 4SD = **1 FLOP/byte**

  而这张卡的机器平衡点是 144.2 FLOP/byte。
  1 远小于它，**而且与 S、D 都无关** —— 再怎么调也走不出访存一侧。
  batch 能帮忙：B 条请求共享一次权重读取，但 KV 是各自的，读取量线性增长。
  所以 decode attention 的上限就是：把 KV cache 按带宽读一遍要多久。

  H=32 D=128 bf16，逐个 (batch, kv_len) 量实际带宽
  参照：只读带宽 1608.6 GB/s。L2=96 MiB —— 工作集小于它时量的是 L2，不是 DRAM。

[B] GQA / MQA：直接砍 KV 的读取量
==============================================================================
  MHA：每个 query 头有自己的 K/V 头     -> KV 头数 = H
  GQA：若干 query 头共享一组 K/V        -> KV 头数 = H/g
  MQA：所有 query 头共享一组 K/V        -> KV 头数 = 1

  decode 是访存受限（[A] 节），KV 读取量按比例下降，时间就该按比例下降。

  B=32 kv_len=8192 D=128 query 头=32 bf16

[C] 并行度：单请求长上下文 decode 为什么需要 split-K
==============================================================================
  这张卡 170 个 SM。decode 时 Q 只有 1 行：
  沿 batch×head 切分能得到的并行单元只有 B·H 个。
  B=1、H=32 时只有 32 个单元 —— 一多半 SM 闲着，无论上下文多长。

  FlashDecoding 的做法：**再沿 KV 长度切分**（split-K），
  每段各自算局部的 m/l/O，最后用 3.1 的合并公式归约到一起。
  判据：固定 B·H 很小，把 kv_len 拉长。
  若没有 split-K，带宽利用率会随 kv_len 停在低位；有的话会随之上升。

[D] 分页布局要付多少代价
==============================================================================
  vLLM 的 KV cache 不是每条序列一段连续内存，而是若干固定大小的块，
  用 block table 记录逻辑块->物理块（5.2）。好处是不用预留最大长度；
  代价是读 KV 时要先查表再 gather。这里量一下 gather 本身有多贵。

  B=8 H=8 kv_len=8192 D=128 块大小=16 -> 每条序列 512 块

  布局                                ms      GB/s      相对连续
  连续                            0.1722    1559.0     1.00×
  分页 + 显式 gather            0.8522     315.0     0.20×

  注意：这里的 gather 是**显式物化**成连续张量再算，
  是分页代价的**上界**。真实的 paged attention kernel 在 kernel 内部
  按 block table 直接寻址，不产生这份拷贝 —— 5.2 会看真实实现。
