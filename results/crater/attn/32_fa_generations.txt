[A] 并行度：kernel 沿哪些维度切分
==============================================================================
  这张卡有 170 个 SM。
  FA1 只沿 (batch × head) 切分：并行单元数 = B·H。
  B·H 小于 SM 数时，一部分 SM 无事可做，和序列多长无关。
  FA2 增加了沿**查询块**的切分：并行单元数 = B·H·⌈S/块⌉。

  判据：固定 S，把 B·H 从远小于 SM 数扫到远大于。
  如果只沿 B·H 切分，达到的 TFLOP/s 会在 B·H≈SM 数处才饱和；
  如果也沿序列切分，B·H 很小时就已经接近饱和。

==============================================================================
[B] 因果 mask 省掉了多少
==============================================================================
  因果 attention 只需算下三角，理想省一半（时间比 0.50）。
  但块粒度下，对角线上那一排块只有一半有效，整块仍要算。
  设 N = S/Bk 个 key 块，query 块 i 要算 (i+1) 个 key 块：
      因果块数 = N(N+1)/2，非因果 = N²  ->  比值 = (N+1)/(2N) = 0.5 + 1/(2N)
  所以块粒度带来的额外开销只有 1/(2N)，S 越大越可以忽略。

        S      非因果 ms      因果 ms      实测比       块粒度预测       差额
      512       0.062      0.045    0.734       0.625   +0.109
     1024       0.113      0.084    0.746       0.562   +0.183
     2048       0.215      0.154    0.714       0.531   +0.183
     4096       0.422      0.295    0.699       0.516   +0.183
     8192       0.835      0.574    0.687       0.508   +0.180
    16384       1.662      1.104    0.664       0.504   +0.160

  实测比一路下降，方向和块粒度预测一致 —— 说明整块在未来的块**确实被跳过了**。
  但差额没有随 S 收敛到 0：S 大时块粒度只该贡献 0.004，实测仍高出 0.16 左右。
  所以还有别的原因。最可能的是**负载不均**：因果下 query 块 i 的工作量
  正比于 i+1，最后一个块是第一个块的 N 倍。如果块按简单顺序分给 SM，
  整个 kernel 要等最重的那些块结束。
  这是一个**假设**，本轮没有验证。要证实它，用 2.6 那个 %smid+%globaltimer
  的自制 profiler 记录每个 block 的起止时间，看尾部是否被少数重块拖住。
