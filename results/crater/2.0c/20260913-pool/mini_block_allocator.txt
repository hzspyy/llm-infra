==============================================================================================================
实验 5E：三个生命周期时刻、split/merge 与真实 allocator 对照
==============================================================================================================

-- 时刻 1：Python 引用被丢掉，但 GPU 可能还在用 --
   free(a) 之后：allocated=0.00 MB  pending=4.00 MB  inactive_split=16.00 MB
   块的 owner stream 仍记为 0，pending event = 0；此刻复用它是竞态
   最近事件：{'op': 'free', 'block': 0, 'owner_stream': 0, 'event': 0}

-- 时刻 2：event 完成，allocator 可以复用 --
   complete(event=0) 之后：allocated=0.00 MB  pending=0.00 MB  inactive_split=0.00 MB
   块状态 = free；只有到这一刻，下一次 malloc 才能拿到它

-- 时刻 3：真正分配给下一个请求（复用 + 切分）--
   malloc(1 MiB) → block 0，是否复用了刚释放的 block？是
   reuse 事件：{'op': 'reuse', 'block': 0, 'size': 1048576, 'stream': 0}
   split 事件：{'op': 'split', 'block': 0, 'kept': 4194304, 'rest': 1, 'rest_size': 16777216}
   split 事件：{'op': 'split', 'block': 0, 'kept': 1048576, 'rest': 2, 'rest_size': 19922944}

-- merge：相邻空闲块在 event 完成后合并 --
   释放两个相邻块后：inactive_split=12.00 MB
   全部 event 完成后：inactive=20.00 MB  inactive_split=0.00 MB
   合并事件：[{'op': 'merge', 'into': 0, 'absorbed': 1, 'size': 8388608}, {'op': 'merge', 'into': 0, 'absorbed': 2, 'size': 20971520}]

-- 与真实 allocator 对照（同一组尺寸，torch memory_snapshot）--
   （两组数字来自不同负载，这里只对齐术语与状态分类，不做性能对比）
   口径                       mini pool    torch snapshot
   ------------------------------------------------------
   allocated                     1.00             12.00
   reserved                     20.00             22.00
   active                        1.00             12.00
   inactive_split               19.00              0.00
   inactive                      0.00             10.00
