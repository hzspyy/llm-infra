## 本章回答的三个问题

1. **原生 Omni 的容量账怎么算？** Thinker / Talker / Code2Wav 三段各占多少参数与字节，计划的 TP=2 + 一卡 + 一卡能否装下？

## 机制拆解

### 容量账：按总量买显存，按激活量用算力

`Qwen/Qwen3-Omni-30B-A3B-Instruct` 的 config 与 safetensors index（只下载这两者，不下载 30B 权重）给出：

| 阶段 | 组成 | 参数量 | bf16 字节 |
|---|---|---:|---:|
| **Thinker** | 文本 MoE（48 层、128 专家 top-8、hidden 2048、moe_inter 768）+ audio encoder（32 层、d_model 1280）+ vision encoder（27 层、hidden 1152） | 31.263 B | 58.23 GiB |
| **Talker** | 文本塔（20 层、hidden 1024）+ 16 码本头 + code predictor（5 层） | 0.369 B | 0.69 GiB |
| **Code2Wav** | DiT（8 层、hidden 1024）+ 16 个码本（2048×512）+ 上采样 | 0.128 B | 0.24 GiB |
| **合计** | | **31.760 B** | **59.16 GiB** |

对照 index：**28,010 个张量、total_size 65.68 GiB（= 35.26 B 参数 @2 字节）**。解析模型覆盖了 index 总量的 **90.1%**——差值主要来自 config 未显式给出的额外张量（专家偏置、encoder 的辅助层等）。**绝对数字应以 index 为准，解析模型用来分阶段归因。**

**激活量与总量的对比**（这是计划里反复强调的一条）：

```
Thinker 每 token 激活 8/128 专家 → 3.030 B（占总参数 9.5%）
但显存必须放下 31.760 B（59.16 GiB bf16）
Talker / Code2Wav 是稠密的：激活即总量（0.497 B）
```

**"30B-A3B"里的 3B 是算力口径，不是容量口径。** 计划里的部署方案是 Thinker TP=2、Talker 一卡、Code2Wav 一卡，实测账如下：

| 卡 | 权重 | 8k 上下文的 KV | 合计 | 32 GB 卡余量 |
|---|---:|---:|---:|---:|
| GPU0-1（Thinker TP=2） | 29.12 GiB/卡 | 0.75 GiB/卡 | **29.87 GiB** | **2.13 GiB** |
| GPU2（Talker） | 0.69 GiB | 0 | 0.69 GiB | 31.31 GiB |
| GPU3（Code2Wav） | 0.24 GiB | 0 | 0.24 GiB | 31.76 GiB |

Thinker 的单 token KV 是 `2(K/V) × 48 层 × 4 KV 头 × 128 × 2 B = 196,608 B` → 8k 上下文单会话 1.50 GiB（TP=2 每卡 0.75 GiB）。

两条结论：

- **bf16 + TP=2 只剩 2.13 GiB 余量**，而激活峰值、通信缓冲与 Code2Wav 的中间张量都还没算进去——**这个配置处在临界线上**，要么降精度（fp8：每卡 14.56 GiB，余量 16.69 GiB），要么换更细的切分。
- **Talker 与 Code2Wav 各占一整张卡是巨大的浪费**（0.69 / 0.24 GiB）。它们的显存需求小，但**延迟敏感**（在生成链路上串行），所以计划把它们独立部署的原因不是容量，而是**跨阶段流水线不能被 Thinker 的 batching 拖住**。这正是"阶段队列"存在的原因。

### 背压：谁决定 underrun

用一张**成本表**驱动会话模拟（每项的来源都标注，这是本章可核查性的基础）：

| 阶段 | 成本 | 来源 |
|---|---:|---|
| ASR encoder | 30 ms | **假设**（4.9 的 B/C 被权重键前缀阻塞，未实测） |
| Thinker prefill | 33.8 ms | **实测**（4.8：vLLM 单图首 token） |
| Thinker decode step | 12.1 ms | **实测**（4.8：单图重复请求） |
| Talker 每帧 | 80 ms | **定义**（4.10 实测码帧 80 ms；生成速度未实测。同章用非自回归替代模型 VITS 实测到的是 RTF 0.002–0.009、首可播放=全部生成时间——**那是另一种架构的形状**，不能替换这里的 AR 假设） |
| Code2Wav 每帧 | 5 ms | **假设** |
| 播放每帧 | 80 ms | **定义** |

生成一帧需要 85 ms（80 + 5），播放一帧占 80 ms → **RTF = 1.06 > 1**。这个 >1 是结构性的：**只要生成比播放慢，任何队列大小都无法避免断流**。队列上限 × 消费延迟的扫描（40 帧，1 ms 步长）：

| 队列上限 | 消费延迟 | 播放 | 丢弃（队列满） | underrun | 首可播放 |
|---:|---:|---:|---:|---:|---:|
| 无界 | 0 ms | 40/40 | 0 | 3 | 0.0 ms |
| 无界 | 500 ms | 40/40 | 0 | 0 | 0.0 ms |
| ≤1 | 100 ms | 20/40 | 20 | 0 | 0.0 ms |
| ≤1 | 500 ms | 7/40 | 33 | 0 | 0.0 ms |
| ≤4 | 500 ms | 10/40 | 30 | 0 | 0.0 ms |
| ≤8 | 500 ms | 14/40 | 26 | 0 | 0.0 ms |

四条读法：

- **无界队列 + 快消费者**：全部帧都能播，但启动期有 3 次 underrun（生成速度略慢于播放，缓冲被抽空）。
- **有界队列**把过载转成**丢弃**：队列越小、消费者越慢，丢得越多（≤1 + 500 ms 只播 7/40）。丢弃在音频里是**可听的断裂**，不是"降低质量"。
- **队列越大丢得越少**（≤1→≤8 在 500 ms 下：7→10→14 帧），但代价是**延迟与内存**：队列里的帧要等。
- **首可播放恒为 0**，因为模拟里第一帧一生成就开始播。真实系统里首可播放 ≥ 首帧生成 + 解码 + 缓冲填充——**这就是"首响应时间不等于首可播放"的量化形式**。

### 打断：清空队列不够，必须作废在途帧

打断可以发生在四个位置：Thinker（还在生成 hidden）、Talker（还在出码本）、Code2Wav（还在解码音频）、播放（已经在出声）。时间轴模拟（队列≤8、无消费延迟）：

```
在 Thinker（生成中）打断：旧 epoch 丢弃 0 帧，播放 40/40 帧
在 Talker（第 5 帧）打断：旧 epoch 丢弃 1 帧，播放 39/40 帧
在 Code2Wav（第 12 帧）打断：旧 epoch 丢弃 1 帧，播放 39/40 帧
在 播放（第 20 帧）打断：旧 epoch 丢弃 1 帧，播放 39/40 帧
```

**清空队列只影响"已排队"的那 1 帧。** 真正的风险在**在途帧**：打断发生时，已经离开 codec、正在网络/播放缓冲里的旧 epoch 音频仍会到达。对照实验：

```
在途 1 帧：有 epoch 校验 → 播放 0 帧（丢弃 1）；无校验 → 播放 1 帧
在途 3 帧：有 epoch 校验 → 播放 0 帧（丢弃 3）；无校验 → 播放 3 帧
在途 8 帧：有 epoch 校验 → 播放 0 帧（丢弃 8）；无校验 → 播放 8 帧
```

**没有 epoch 校验时，在途的旧音频会全部播放出来**——用户打断之后又听到上一轮的语音，这是最典型的"打断失败"。所以打断协议必须三件事同时做：

1. **计算**：取消 Thinker/Talker/Code2Wav 的当前步（释放 KV 与中间张量）；
2. **传输**：让在途 chunk 携带 epoch（或 session 版本），接收端丢弃不匹配的包；
3. **播放**：清空播放缓冲，并把"当前 epoch 已播放到哪一帧"记账，避免交错。

### 设计取舍

**为什么 Talker/Code2Wav 要独立成阶段而不是塞进 Thinker。** 容量上它们很小（0.69 / 0.24 GiB），但**它们的输出速率决定首可播放**：Thinker 负责理解（可以 batching），Talker 负责逐帧生成（延迟敏感），Code2Wav 负责把码本变成波形（吞吐敏感）。把三者放在一条串行链上时，**任何一个阶段的队列积压都会直接变成首可播放的延迟**。

**为什么"按激活参数估显存"是错的。** 本章实测：3.03 B 激活 / 31.76 B 总量。MoE 的每 token 激活只决定算力与带宽需求，权重必须全部驻留。**容量规划用总量，性能规划用激活量**——两个数字混用会得到"这张卡放得下"的错误结论（29.87 GiB 对 32 GB 只剩 2.13 GiB 余量，而激活峰值还没算）。

**为什么本章的 B/C 是模拟而不是实测。** 原生 Omni 需要 vLLM-Omni / SGLang-Omni（本机没有）与 6.2 的 TP 基础（未做）。在这个约束下，能确定的是**容量算术**（来自真实 config 与 index）与**协议机制**（队列、epoch、丢弃语义）；不能确定的是**绝对延迟与真实音质**。把两者分开写，是这一章唯一诚实的做法。

## 工程实现 · 源码解析：config 揭示的阶段契约

```
config.json
  architectures          ["Qwen3OmniMoeForConditionalGeneration"]   ← transformers 5.17 有此类
  thinker_config.text_config
      hidden 2048 / 48 层 / 32 头 / 4 KV 头 / head_dim 128
      num_experts 128 / num_experts_per_tok 8 / moe_intermediate_size 768
      vocab_size 152064
  thinker_config.audio_config   32 层 / d_model 1280 / ffn 5120 / mel 128
  thinker_config.vision_config  depth 27 / hidden 1152 / ffn 4304 / patch 16 / merge 2
  talker_config.text_config     hidden 1024 / 20 层 / vocab 3072
  talker_config.num_code_groups 16    accept_hidden_layer 24
  talker_config.code_predictor_config  5 层 / hidden 1024 / 16 组
  code2wav_config              8 层 / hidden 1024 / num_quantizers 16 / codebook 2048 / decoder_dim 1536
```

三处值得单独读：

- **`accept_hidden_layer: 24`**：Talker 取 Thinker 第 24 层的 hidden 作为条件（48 层的一半）。这是"跨阶段传输"的契约：**传的是中间层 hidden，不是最终 logits**，所以 Thinker 必须在第 24 层就能输出给 Talker（流水线切分点）。
- **`position_id_per_seconds: 13` 与 `seconds_per_chunk: 2`**：音画共享时间轴时，位置编号按"每秒 13"推进，chunk 为 2 秒。**音频位置与视频位置用的是同一套时间刻度**，这是"音画共享时间轴"的配置级依据。
- **`num_semantic_quantizers: 1`**：第 1 个码本是语义层（codebook 4096），其余 15 个是声学层（2048）——**语义与声学在同一 RVQ 结构里，但码本大小不同**，生成侧的码本头必须按层区分大小。

## 工程实现 · 自己写一遍

```python
class Session:                       # epoch 打断的核心
    def __init__(self, bound):
        self.q, self.bound, self.epoch = collections.deque(), bound, 0
    def produce(self, frame_id, epoch):
        if epoch != self.epoch:      # 旧 epoch 的产物直接丢
            return "stale"
        if self.bound is not None and len(self.q) >= self.bound:
            return "full"            # 队列满：丢弃（可听断裂），不无限排队
        self.q.append((frame_id, epoch))
    def interrupt(self):
        self.epoch += 1              # 关键：让所有在途包失效
        n = len(self.q); self.q.clear(); return n
```

时间步进模拟（生成与播放同一时间轴）：

```python
gen_per_frame = talker + code2wav      # 85 ms
play_per_frame = 80 + consumer_delay   # 播放一帧
while t <= t_end:
    if t >= next_gen and produced < n: produce(...); next_gen = t + gen_per_frame
    if t >= next_play: play_or_underrun(); next_play = t + play_per_frame
    t += 0.001
```

## 前沿

**原生 Omni 的工程难点已经从"模型能不能做"转到"阶段之间怎么背压"。** 本章的容量账显示：Thinker 占 98.4% 的权重（31.26/31.76 B），而 Talker + Code2Wav 合计 0.50 B 却决定了**首可播放**。这意味着部署方案不能按参数量分配卡（否则 Talker/Code2Wav 各占一整卡是浪费），而要按**延迟链路**分配——三段独立阶段、跨阶段队列、以及能被 epoch 作废的传输协议。

**打断协议正在成为多模态会话的第一类需求。** 本章的在途帧反例说明：**只清空队列是无效的**。完整协议需要三件事一起做——取消计算、作废在途包（epoch/session 版本）、清空播放缓冲并记账。这与 5.8 的失败路径是同一条主线：**一个 stage 成功不代表全链路成功**，而"停止"也必须是一条能被验证的完整路径。

**共享时间轴是音画能力的配置级前提。** `position_id_per_seconds: 13` 与 `seconds_per_chunk: 2` 说明音频与视频位置共用一套时间刻度；`accept_hidden_layer: 24` 说明 Talker 直接吃 Thinker 的中间层 hidden。**这两条把"原生 Omni"与"ASR→VLM→TTS 级联"区分开**：级联方案里每一段都有自己独立的时间基准与输出契约，把它们接起来需要额外的对齐层；而原生方案在配置里就把时间轴与层间接口固定了。

## 陷阱

1. **"30B-A3B"里的 3B 是算力口径**：显存必须放下 31.76 B（59.16 GiB bf16）。
2. **bf16 + TP=2 只剩 2.13 GiB 余量**（29.87 / 32 GiB），激活峰值还没算。
3. **Talker/Code2Wav 各占一整卡是延迟需要，不是容量需要**（0.69 / 0.24 GiB）。
4. **生成 RTF > 1 时，任何队列大小都无法避免断流**（本章 85 ms 生成 vs 80 ms 播放）。
5. **有界队列把过载变成丢弃**：队列≤1 + 500 ms 消费延迟只播 7/40 帧，丢弃是可听断裂。
6. **首可播放 ≠ 首响应**：模拟里首可播放恒为 0，真实系统要加上解码与缓冲填充。
7. **清空队列拦不住在途帧**：无 epoch 校验时，1/3/8 帧在途旧音频会全部播放（打断失败）。
8. **打断要在四个位置都能发起**（Thinker/Talker/Code2Wav/播放），并且都要释放资源。
9. **解析模型的参数账只覆盖 index 的 90.1%**：绝对数字以 index 为准。
10. **`accept_hidden_layer: 24` 是流水线切分点**：跨阶段传的是中间层 hidden，不是 logits。
11. **`num_semantic_quantizers: 1`**：语义码本（4096）与声学码本（2048）大小不同，生成侧要分开处理。
12. **本章的 B/C 是成本驱动的模拟**（ASR 30 ms 与 Code2Wav 5 ms 是假设值；原生推理未运行）；**B（音画片段）、E（运行时矩阵）、F/G/H（训练与 RL）未执行**，不能把本章的机制结论当作原生实测。

## 自测题

<details markdown="1">
<summary>1. 计划里的部署是 Thinker TP=2、Talker 一卡、Code2Wav 一卡，各卡余量多少？哪里最紧？</summary>

按本章的解析账（bf16，8k 上下文）：

| 卡 | 权重 | KV | 合计 | 32 GB 余量 |
|---|---:|---:|---:|---:|
| Thinker TP=2（每卡） | 29.12 GiB | 0.75 GiB | 29.87 GiB | **2.13 GiB** |
| Talker | 0.69 GiB | 0 | 0.69 GiB | 31.31 GiB |
| Code2Wav | 0.24 GiB | 0 | 0.24 GiB | 31.76 GiB |

**最紧的是 Thinker 的两张卡**：只剩 2.13 GiB。而激活峰值、NCCL 通信缓冲、Code2Wav 的中间张量都还没计入。所以这个配置在临界线上；可行的缓解是 fp8（每卡 14.56 GiB，余量 16.69 GiB，但要注意 KV 与激活的精度）、或把 vision/audio encoder 也切出去。

反过来说，Talker 与 Code2Wav 各占一整卡是**延迟设计**：它们串在生成链路上，不能被 Thinker 的 batching 阻塞。

</details>

<details markdown="1">
<summary>2. 为什么"每 token 只激活 3B"不能用来估显存？</summary>

因为 MoE 的稀疏性只作用于**计算与带宽**，不作用于**驻留**：所有 128 个专家的权重都必须在显存里，router 才知道该走哪几个。

本章实测：Thinker 每 token 激活 8/128 专家 = 3.030 B（9.5%），但权重总量 31.263 B（58.23 GiB bf16）。**如果按 3B 估容量（约 6 GiB），实际需要 58 GiB —— 差近 10 倍。**

正确的两个口径：

- **容量**（显存/部署）用**总参数**（31.76 B / 59.16 GiB）；
- **性能**（算力/带宽/延迟）用**激活参数**（3.03 B）。

4.4 的 MoE 章节给出过同一条结论的另一个侧面：decode 32 个 token 就碰到 58.4/64 的专家、读掉 93% 的专家权重——**稀疏的是算力，不是流量**。

</details>

<details markdown="1">
<summary>3. 打断时清空队列为什么不够？需要哪三件事？</summary>

因为音频帧在"生成完成"和"播放出来"之间还有两段路：codec 输出缓冲与网络/播放缓冲。**打断时这些在途帧已经离开队列了**，清空队列对它们无效。本章的反例：

```
在途 1/3/8 帧：无 epoch 校验 → 播放 1/3/8 帧（旧音频全部放出来）
             有 epoch 校验 → 播放 0 帧
```

完整协议要三件事一起做：

1. **取消计算**：停止 Thinker/Talker/Code2Wav 的当前步，释放 KV 与中间张量（否则后台还在烧算力）；
2. **作废在途包**：给每个 chunk 带 epoch（session 版本），接收端丢弃不匹配的包；
3. **清空播放缓冲并记账**：记录"当前 epoch 播放到哪一帧"，避免新响应的帧与旧帧交错。

验收判据（计划里的要求）：**打断至静音的时间**、**旧响应不得重新播放**、**资源被回收**、**同会话下一请求正常**。本章只验证了第 2 条的机制（epoch 丢弃）与第 3 条的队列语义，**没有测打断至静音的真实时间，也没有做真实的资源回收观测**。

</details>

<details markdown="1">
<summary>4. 生成 RTF = 1.06 意味着什么？加队列能解决吗？</summary>

RTF > 1 意味着**生成一帧音频所需的时间比播放一帧的时间长**（本章：85 ms 生成 vs 80 ms 播放）。

后果：**播放端迟早会耗尽缓冲**。加队列只能把断流推迟（缓冲越多，撑得越久），不能消除；而且缓冲越大，首可播放越晚（用户等待更久）。

本章的模拟给出这个结构：

- 无界队列 + 快消费者：40/40 帧都播了，但启动期有 3 次 underrun（缓冲一直很薄）；
- 有界队列 + 慢消费者：变成丢弃（≤1 + 500 ms 只播 7/40）。

真正的解法只有三条：**加快生成**（更小的 talker/更快的解码）、**降低播放速率需求**（更高的压缩率或更低的采样率）、或**改变交互形式**（不要实时流式，改为"生成完再播"）。这正是 TTS 服务里"首包/首可播放/RTF"必须一起报的原因。

</details>

<details markdown="1">
<summary>5. `accept_hidden_layer: 24` 与 `position_id_per_seconds: 13` 各说明了什么？</summary>

**`accept_hidden_layer: 24`（Thinker 48 层的一半）**：Talker 不是吃 Thinker 的输出 logits，而是直接取第 24 层的 hidden 作为条件。含义：

- **跨阶段传的是中间层表示**，所以流水线可以在第 24 层切分（Thinker 的前半算完就能喂 Talker）；
- Talker 的输入维度必须与 Thinker 第 24 层的 hidden 对齐（都是 2048）——这是配置级的接口契约；
- 这也解释了为什么"原生 Omni"不等于"ASR + LLM + TTS 级联"：级联传递的是**文本**（离散符号），原生传递的是**hidden**（连续表示），后者能保留韵律与副语言信息。

**`position_id_per_seconds: 13` 与 `seconds_per_chunk: 2`**：位置编号按每秒 13 推进、chunk 为 2 秒。音频与视频如果用同一套时间刻度，就能在同一个位置空间里对齐——**这是"音画共享时间轴"的配置依据**（4.7 的 MRoPE 是文本/图像/视频三轴，这里是时间轴的统一刻度）。

</details>

<details markup="1">
<summary>6. 本章哪些数字可以直接用于容量规划，哪些不能？</summary>

**可以直接用（真实 config 与 index 的算术）**：

- 分阶段参数量与字节（Thinker 31.26 B / Talker 0.37 B / Code2Wav 0.13 B；合计 31.76 B = 59.16 GiB bf16）；
- index 的权威总量（28,010 张量 / 65.68 GiB = 35.26 B @2 字节）；
- KV 账：196,608 B/token → 8k 单会话 1.50 GiB；
- 部署余量：Thinker TP=2 每卡 29.87 GiB（余量 2.13 GiB），fp8 每卡 14.56 GiB。

**不能直接用**：

- B/C 的绝对时间（ASR 30 ms、Code2Wav 5 ms 是假设值；Talker 生成速度未实测）；
- 真实音质、可懂度、音画一致性（原生推理未运行）；
- 两运行时的调度差异（vLLM-Omni / SGLang-Omni 本机都没有）；
- 训练与 RL 相关的一切（F/G/H 未执行）。

**判据**：本章给出的是"**能不能装下**"与"**协议是否自洽**"两个问题的答案；"**跑起来多快、听起来怎样**"需要 6.2 的 TP 基础与 vLLM-Omni/SGLang-Omni，属于下一阶段的工作。

</details>
