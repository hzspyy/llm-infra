## 机制拆解

### safetensors 的三段结构

```
[0..8)      u64 小端       —— JSON 头部的字节长度 N
[8..8+N)    UTF-8 JSON     —— 每个张量的 dtype / shape / data_offsets
[8+N..)     裸字节         —— 所有张量的数据，紧挨着排，没有分隔符
```

没有魔数、没有版本号、没有压缩、没有 pickle。**"safe" 指的就是这个**：解析它不需要执行任何代码，而 PyTorch 的 `.bin`/`.pth` 是 pickle，加载等于执行任意代码。

格式只有三行，所以可以直接写一个审计器：读 8 字节长度、解析 JSON、检查每个张量的 `data_offsets` 是否落在数据区内、是否与前一个张量重叠、`shape × dtype 字节数` 是否等于区间长度。四个 checkpoint 的检查结果：

```
Qwen/Qwen3-1.7B                        分片 2  张量  311  问题 0
Qwen/Qwen3-8B                          分片 5  张量  399  问题 0
Qwen/Qwen2.5-1.5B-Instruct-AWQ         分片 1  张量  731  问题 0
Qwen/Qwen2.5-1.5B-Instruct-GPTQ-Int4   分片 1  张量  926  问题 0
```

自洽的区间意味着：把 `8 + 头长度 + data_offsets[0]` 当作文件内绝对偏移去 `dd` 取字节，读到的就是 `safe_open` 返回的那个张量。抽 12 个张量（embedding、QKV、MLP、norm），各取头尾 4 个元素，用手算偏移读原始字节，按 bf16 位模式与张量值比对——不一致 0 个。

### 分片与 index

Qwen3-8B 的 5 个分片合计 15.26 GiB，`model.safetensors.index.json` 的 `weight_map` 有 399 条。按分片看层号范围：

```
model-00001-of-00005.safetensors   layers 0..7     另有 model.embed_tokens.weight
model-00002-of-00005.safetensors   layers 7..17
model-00003-of-00005.safetensors   layers 17..27
model-00004-of-00005.safetensors   layers 27..35   另有 model.norm.weight
model-00005-of-00005.safetensors   无 layer         另有 lm_head.weight
```

范围在第 7 层重叠，说明分片不按层边界切。逐张量查第 7 层的 11 个张量：

```
7.self_attn.q_proj.weight    1-of-00005.safetensors
7.self_attn.k_proj.weight    1-of-00005.safetensors
7.self_attn.v_proj.weight    1-of-00005.safetensors
7.self_attn.o_proj.weight    2-of-00005.safetensors
7.mlp.gate_proj.weight       2-of-00005.safetensors
...
```

q/k/v 在第一个文件，同属第 7 层的其余 8 个张量在第二个文件。分片按单文件体积（约 4 GB）机械切分，不考虑 Transformer 的层边界。想在加载时按层流水启动，必须自己处理跨文件的协调。

定位一个具体张量：

```
model.layers.20.self_attn.q_proj.weight
  文件      model-00003-of-00005.safetensors
  dtype     BF16   shape [4096, 4096]
  数据区偏移 [1317078528, 1350632960)  共 33554432 字节
  文件内绝对偏移 = 8 + 12824 + 1317078528 = 1317091360
  校验: 16777216 元素 × 2 字节(bf16) = 33554432 ✓
```

### 三套名字

Qwen3-1.7B 第 0 层在磁盘上有 11 个张量：`input_layernorm`、`post_attention_layernorm`、`mlp.{gate,up,down}_proj`、`self_attn.{q,k,v,o}_proj`、`self_attn.{q,k}_norm`。三件事可以直接读出来：

- **q/k/v 是三个独立张量**。vLLM 里是一个融合的 `QKVParallelLinear`，一次 GEMM 代替三次（本章第二节给出逐元素对拍）。
- **`k_proj` 是 `[1024, 2048]` 而 `q_proj` 是 `[2048, 2048]`**：16 个 query 头、8 个 KV 头，GQA $g=2$。
- **`q_norm`/`k_norm` 的 shape 是 `[128]`，不是 `[2048]`**：128 是 head_dim，说明这个 RMSNorm 作用在每个头内部。这是 Qwen3 相对 Qwen2 新增的 QK-Norm，实现里漏掉它模型能跑但输出是错的（4.1 逐层对齐）。

非 layer 的只有 `model.embed_tokens.weight [151936, 2048]` 和 `model.norm.weight [2048]`。

### config 声明与文件内容

`tie_word_embeddings=True` 的意思是输出层复用 embedding 矩阵。实测：

```
Qwen/Qwen3-1.7B
  config: tie_word_embeddings = True
  文件字节 3875.3 MiB（2 个分片）
  lm_head.weight                在 model-00002-of-00002.safetensors
  model.embed_tokens.weight     在 model-00001-of-00002.safetensors
  两者 shape (151936, 2048)，逐位完全相同: True
  lm_head 那份 593.5 MiB，占文件 15.3%

Qwen/Qwen3-8B
  config: tie_word_embeddings = False
  两者 shape (151936, 4096)，逐位完全相同: False
```

Qwen3-1.7B 声明了绑定，文件里却存了一份逐位相同的独立副本，占 15.3%，并且单独占了第二个分片。按 tie=True 走绑定路径的加载器不会用到这 593.5 MiB。

由此得到两个不同的口径：

| 问的是 | 依据 | Qwen3-1.7B 的值 |
|---|---|---|
| 模型有多少参数 | `config.json` 的结构 + `parameters()` | 1,720,574,976（1.72 B） |
| 下载要多少字节 | 文件头逐个张量相加 | 3875.3 MiB |
| 加载进进程多少常驻 | 进程 RSS | 见下节 |

**`config.json` 描述模型结构，不描述文件内容。** 想知道文件里有什么，只能读文件头。

### 加载路径上的三个口径

同一个 checkpoint，三个数字互不相等（Qwen3-1.7B，bf16）：

```
文件字节                              3875.3 MiB
parameters() × 2 字节                 3281.7 MiB    差 +593.5 MiB（重复的 lm_head）
加载完成时进程 RSS 增量                  635.1 MiB    （0.219 s）
触碰全部参数页后 RSS 增量               4498.5 MiB
```

第一行与第二行的差就是那份冗余副本。第三行远小于第二行，因为 `low_cpu_mem_usage=True` 走的是 safetensors 的 mmap 路径：加载函数返回时数据页大多还没被触碰。第四行是把每个参数都求和一遍之后的常驻高水位，比权重逻辑字节多约 1.2 GiB——多出的部分来自加载期间触碰过的文件映射页与分配器保留，而不是多出来一份权重（加载结束后进程里已经没有 checkpoint 文件的映射页）。

同样的陷阱在单算子尺度上更直观（`results/crater/ckpt/40_formats.txt`）：

```
文件 model-00001-of-00002.safetensors  3281.8 MiB
张量 model.layers.0.mlp.down_proj.weight  shape (2048, 6144)  24.0 MiB
  get_tensor()             0.231 ms  ->    109.0 GB/s
  之后完整读一遍           9.697 ms  ->      2.6 GB/s
  .to('cuda')            211.612 ms  ->      0.1 GB/s
```

这里的 109.0 GB/s 对应 `get_tensor` 建立映射/张量视图的时间，不能解释为完整数据读取吞吐。触页、page cache 命中与磁盘读取是不同路径：即使真正遍历了数据，热缓存的内存读取也可能超过存储介质带宽。应同时记录触页方式、冷/热缓存、page fault、RSS 与实际 I/O 字节。

### 量化格式：一个矩阵被拆成三四个张量

同一个位置（Qwen2.5-1.5B 第 0 层 q_proj）：

```
未量化  weight            [1536, 1536]     F16

AWQ    qweight           [1536, 192]      I32   沿输出维打包
       qzeros            [12, 192]        I32
       scales            [12, 1536]       F16

GPTQ   qweight           [192, 1536]      I32   沿输入维打包
       qzeros            [12, 192]        I32   沿输出维打包
       scales            [12, 1536]       F16
       g_idx             [1536]           I32   AWQ 没有
```

`group_size=128` 是缩放的分组：每 128 个权重共享一个 fp16 scale（GPTQ 还共享一个 4 bit 零点）。`qweight` 的方向决定 kernel 怎么取数：**AWQ 沿输出维打包，GPTQ 沿输入维打包**，两者互为转置，kernel 不能互换。

### 等效位宽不是 4

每 128 个权重需要 $128\times4$ 位 qweight + 1 个 fp16 scale（16 位）+ 1 个 4 位零点 $=532$ 位：

$$\frac{532}{128}=4.16\ \text{bit/权重} \qquad \text{压缩比}\ \frac{16}{4.16}=3.85\times$$

AWQ 与 GPTQ 算出来一样。而"4 bit 模型"这个说法只描述了线性层：

```
Qwen2.5-1.5B-Instruct-AWQ        文件 1539.7 MiB
Qwen2.5-1.5B-Instruct-GPTQ-Int4  文件 1096.7 MiB
  model.embed_tokens.weight  [151936, 1536]  F16  445.1 MiB  ← 占 GPTQ 文件的 41%
  lm_head.weight             [151936, 1536]  F16  445.1 MiB
```

embedding 表没有被量化，两边都是 F16 的 445.1 MiB。词表 151936、hidden 1536 的模型里它占 GPTQ 文件的 41%。**模型越小、词表越大，量化的实际收益越低。**

## 工程实现 · 源码解析：加载器如何把名字翻译成布局

### 融合 QKV：`QKVParallelLinear.weight_loader`

vLLM 0.29.0 的 `vllm/model_executor/layers/linear.py:1189` 定义了这个函数。`loaded_shard_id is None` 分支处理"磁盘上已经融合成一个张量"的情况，它按下面的偏移把输入切成三段再逐段放置（`linear.py:1211`）：

```python
shard_offsets = [
    # (shard_id, shard_offset, shard_size)
    ("q", 0, self.total_num_heads * self.head_size),
    ("k", self.total_num_heads * self.head_size,
          self.total_num_kv_heads * self.head_size),
    ("v", (self.total_num_heads + self.total_num_kv_heads) * self.head_size,
          self.total_num_kv_heads * self.v_head_size),
]
```

按 `shard_id` 传入时（磁盘上是 q/k/v 三个张量，走的就是这条路，`linear.py:1258` 起），每一段放到自己的偏移，TP 下标决定取哪一段：

```python
if loaded_shard_id == "q":
    shard_offset = 0
    shard_size = self.num_heads * self.head_size
elif loaded_shard_id == "k":
    shard_offset = self.num_heads * self.head_size
    shard_size = self.num_kv_heads * self.head_size
...
if loaded_shard_id == "q":
    shard_rank = self.tp_rank
else:
    shard_rank = self.tp_rank // self.num_kv_head_replicas
start_idx = shard_rank * shard_size
loaded_weight = loaded_weight.narrow(output_dim, start_idx, shard_size)
```

Qwen3-1.7B 的 `hidden=2048, num_heads=16, num_kv_heads=8, head_dim=128`，单卡融合后的行数是 $16\times128 + 8\times128 + 8\times128 = 4096$。实测这个融合结果是精确拼接（不是近似）：

```
model.layers.0.self_attn.qkv_proj.weight (4096, 2048)  <- 3 个磁盘张量  逐元素相同 True  max|diff| 0.000e+00
model.layers.0.mlp.gate_up_proj.weight  (12288, 2048)  <- 2 个磁盘张量  逐元素相同 True  max|diff| 0.000e+00
model.layers.20.self_attn.qkv_proj.weight (4096, 2048) <- 3 个磁盘张量  逐元素相同 True  max|diff| 0.000e+00
```

### TP 分片：同一个 loader，不同的下标

把 `get_tensor_model_parallel_world_size` / `get_tensor_model_parallel_rank` 替换成期望值，再用同一个 `QKVParallelLinear.weight_loader` 装载，就能在单卡上复现多卡的分片结果（`linear.py:1041` 读这两个函数决定切分）：

| tp | 每片行数 | 其中 q | k+v |
|---:|---:|---:|---:|
| 1 | 4096 | 2048 | 1024 + 1024 |
| 2 | 2048 | 1024 | 512 + 512 |
| 4 | 1024 | 512 | 256 + 256 |

校验两个方向：

- **tp=1 的复现**与真实引擎加载后的 `qkv_proj.weight` 逐元素完全相同。
- **tp=2/4 的回拼**：把各片按 `shard_id` 分段取出再拼接，得到的张量与 tp=1 完全相同；直接把各片整体按行拼起来则**不**相同，因为每片内部的布局是 `[q_r, k_r, v_r]`，不是全局的 `[q, k, v]`。

`num_kv_heads` 小于 `tp` 时走另一条分支（`linear.py:1042`）：每个 rank 持有一个 KV 头，多出来的 rank 复制同样的头（`num_kv_head_replicas > 1`）。这解释了为什么 GQA 模型在小 KV 头数上仍能开到较大的 TP。

### 量化格式的选择与 repack

磁盘上的量化格式不是执行时的格式。AWQ checkpoint 走 `auto_awq.py:285` 的 `get_quant_method`：在 CUDA 上先探测 `check_marlin_supported`（`auto_awq.py:305`），通过就选 `AutoAWQMarlinLinearMethod`（`auto_awq.py:388`）；GPTQ 走 `auto_gptq.py:306` 的 `AutoGPTQLinearMethod`，它的 `process_weights_after_loading`（`auto_gptq.py:455`）把工作交给 kernel。

kernel 侧的第一步是重排布局（`vllm/model_executor/kernels/linear/mixed_precision/marlin.py:129`）：

```python
permute_param_layout_(x, input_dim=0, output_dim=1, packed_dim=0)
x.data = ops.gptq_marlin_repack(
    marlin_pad_qweight(x.data.contiguous(), size_n, size_k, padded_n, padded_k),
    perm=layer.g_idx_sort_indices,
    size_k=padded_k, size_n=padded_n, num_bits=c.weight_type.size_bits, ...
)
```

函数名里的 `padded_n/padded_k` 说明 Marlin 还要把形状补齐到 tile 的整数倍。加载前后对照（第 0 层 `qkv_proj`，输出维融合后为 2048）：

| | AWQ 磁盘 | AWQ 加载后 | GPTQ 磁盘 | GPTQ 加载后 |
|---|---|---|---|---|
| qweight | `[1536, 192]` | `[96, 4096]` | `[192, 1536]` | `[96, 4096]` |
| scales | `[12, 1536]` | `[12, 2048]` | `[12, 1536]` | `[12, 2048]` |
| qzeros | `[12, 192]` | `[12, 256]` | `[12, 192]` | `[0]` |
| g_idx | — | `[0]` | `[1536]` | `[0]` |
| g_idx_sort_indices | — | `[0]` | — | `[0]` |

元素总数不变（$1536\times192=96\times4096=294912$，乘 8 个 4 bit 值），但排列完全变了：`scales` 沿输出维被补齐到 2048，对称量化且无 act-order 时 `qzeros` 与 `g_idx` 直接被换成空张量。`g_idx_sort_indices` 来自 `marlin_utils.py:456` 的 `torch.argsort(g_idx)`；`bias` 也被重排过（`marlin.py:218` 的 `marlin_permute_bias`），所以加载后的 `bias` 参数已经不是数学意义上的顺序——用零输入探层的输出作为"引擎实际使用的 bias"才能消掉这一项。

### 设计取舍

**为什么 safetensors 故意做得这么简单。** 对比它替代的 pickle：pickle 能存任意 Python 对象，代价是加载即执行代码。safetensors 只能存"张量的字典"，换来安全性、可 mmap（数据区裸字节、紧密排列，可以按需缺页）、以及任何语言十几行就能解析。代价是表达力：存不了自定义对象、稀疏结构或元数据以外的东西。当格式要被大量不受信任的来源分发时，"能表达什么"的优先级低于"解析它要不要承担风险"。

**为什么磁盘上存中性形式。** 引擎的最优布局依赖部署方式：张量并行切 2 路和 8 路的切分点不同，不同引擎的融合策略不同。checkpoint 如果按某一种布局存，就绑死了一种部署方式。所以磁盘上存数学定义的中性形式（每个 Linear 一个张量），加载器在启动时翻译。代价是每个引擎维护一张名字映射表，模型一出新结构就要更新。这是"通用格式 + 适配层"的经典形态：把变化限制在适配层，让格式保持稳定。

**量化格式的碎片化是另一面。** AWQ 与 GPTQ 同样 4 bit、同样 `group_size=128`、同样存 qweight/scales/qzeros，但 qweight 的打包轴互为转置，位顺序也不同（AWQ 在 8 个 4 bit 值上做了一次交错置换，见 `awq_triton.py:57`）。结果是两套反量化 kernel、两套加载路径、两套 repack。设计原则：**当一个领域的格式由"当前最优实现"倒推出来时，碎片化几乎是必然的**；要避免它，需要在性能还没定型时就先定一个稍微次优但中立的格式，而那个时机通常没人愿意付代价。

## 工程实现 · 自己写一遍：解析器、审计器与解包器

`labs/L4/checkpoint_load_path.py` 把本章的三件事写成了可运行的代码。

**① 解析器与审计器。** 只做偏移算术，不执行任何代码：

```python
def parse_safetensors(path):
    size = os.path.getsize(path)
    with open(path, "rb") as f:
        n = struct.unpack("<Q", f.read(8))[0]
        header = json.loads(f.read(n))
    data_len = size - 8 - n
    problems, prev_end = [], 0
    for name, info in header.items():
        if name == "__metadata__":
            continue
        a, b = info["data_offsets"]
        want = math.prod(info["shape"]) * DT_SIZE[info["dtype"]]
        if b - a != want:
            problems.append(f"{name}: shape/dtype 需要 {want} 字节，头声明 {b - a} 字节")
        if a < prev_end:
            problems.append(f"{name}: 与前一张量重叠（起点 {a} < 前终点 {prev_end}）")
        if b > data_len:
            problems.append(f"{name}: 超出数据区（终点 {b} > {data_len}）")
        prev_end = max(prev_end, b)
    if prev_end != data_len:
        problems.append(f"数据区尾部不齐：{prev_end} vs {data_len}")
    return header, n, data_len, problems
```

`raw_slice` 按 `8 + 头长度 + data_offsets[0]` 直接 `seek` 读原始字节，`bits_equal` 把它按位模式与 `safe_open` 的结果比对。位模式比较而不是浮点比较，是因为这里要验证的是**字节到数值的映射**，不是数值精度。

**② 损坏输入的报错。** 自己构造最小 safetensors（JSON 头 + 数据），再制造四种损坏：

| 损坏 | 手写解析器 | safetensors |
|---|---|---|
| 截断（文件短 8 字节） | 超出数据区 + 尾部不齐 | `incomplete metadata, file not fully covered` |
| 重叠 offset | 与前一张量重叠（起点 0 < 前终点 64） | `invalid offset for tensor `w`` |
| dtype/shape 与区间不符 | shape/dtype 需要 128 字节，头声明 64 | `invalid shape, data type, or offset for tensor` |
| 缺分片（index 指向的文件不存在） | 最小加载器 `FileNotFoundError` | 该分片文件本身结构正常（111 个张量） |

核心要点在于最后一行：缺少分片**并非**文件数据损坏。分片文件本身结构完全合法，只有在按 index 组装完整模型时才会暴露——错误信息必须带上缺失的文件名，否则无从精确定位。

**③ AWQ 解包器。** qweight `[in, out/8]` 沿输出维打包，位顺序是交错置换而非顺序：

```python
AWQ_SHIFTS = [0, 16, 4, 20, 8, 24, 12, 28]   # 即 [0,4,1,5,2,6,3,7] × 4

def awq_unpack(qweight, scales, qzeros, group_size, bits=4):
    in_f, out_f = qweight.shape[0], qweight.shape[1] * (32 // bits)
    sh = torch.tensor(AWQ_SHIFTS, device=qweight.device)
    q = ((qweight.unsqueeze(-1) >> sh) & 0xF).reshape(in_f, out_f)
    z = ((qzeros.unsqueeze(-1) >> sh) & 0xF).reshape(qzeros.shape[0], out_f)
    z_row = z.int().repeat_interleave(group_size, dim=0)
    s_row = scales.repeat_interleave(group_size, dim=0).float()
    return ((q.int() - z_row).float() * s_row).to(scales.dtype)
```

这个解包与官方 kernel `ops.awq_dequantize(qweight, scales, qzeros, 0, 0, 0)` 在 1536×1536 上**逐元素完全相同**（相同比例 1.000000，`max|diff|` 0.0）。位重排规则严格源自底层张量内存布局契约：vLLM 的 Triton 参考实现 `awq_dequantize_kernel`（`awq_triton.py:12`）里先做三次 `tl.interleave` 把每个 32 位字展开成 8 列，再用 `reverse_awq_order_tensor`（`awq_triton.py:57`）构造移位序列。

**④ GPTQ 解包器。** 三处与 AWQ 不同：qweight 沿输入维打包、qzeros 沿**输出**维打包（两者不同轴）、零点在文件里存的是 `zero - 1`：

```python
def gptq_unpack(qweight, scales, qzeros, g_idx, group_size, bits=4):
    out_f, in_f = qweight.shape[1], qweight.shape[0] * (32 // bits)
    sh = torch.arange(0, 32, bits, device=qweight.device)
    q = ((qweight.unsqueeze(-1) >> sh) & 0xF).permute(0, 2, 1).reshape(in_f, out_f).int()
    z = ((qzeros.unsqueeze(-1) >> sh) & 0xF).reshape(qzeros.shape[0], out_f).int() + 1
    g = g_idx.to(torch.long)
    return ((q - z[g]).float() * scales[g].float()).to(scales.dtype)
```

`+1` 有源码依据：vLLM 的 Exllama kernel 会先把零点加一，加载器在对称量化下甚至要**造假**一份全是 `8-1=7` 的零点张量来配合（`exllama.py:89` 起，注释里写明这是 GPTQ checkpoint 格式的历史问题）。

三处约定各自都有独立验证：

| 验证对象 | 方法 | 结果 |
|---|---|---|
| AWQ 解包 | vs `ops.awq_dequantize` | 逐元素相同比例 1.000000 |
| GPTQ 解包 | vs 未量化 Qwen2.5-1.5B 的同位置权重 | cosine 0.987205，相对最大差 0.1646 |
| GPTQ 解包 | vs 真实 vLLM GPTQ 层的输出（去掉零输入响应） | 相对差 8.66e-3 |
| 两种布局 | dense → 量化 → 打包 → 解包 往返 | 逐元素一致 |

第二行是 4 bit 量化的固有误差量级，不是解包错误。第三行更有说服力：同样的权重换成 torch 的 fp16 GEMM 计算，与引擎的相对差是 8.64e-3——**手写解包与 fp16 GEMM 的残差相同，说明差的这一点来自 kernel 的累加精度，不是解包约定**。

**⑤ Marlin 布局与加载阶段事件。** 把 `MarlinLinearKernel.process_weights_after_loading` 包一层计时，就得到 repack 阶段的实际开销；vLLM 自身还会打印三段日志，凑成一条完整的加载时间线：

```
[awq]  引擎 init 6.36 s；quant 层 repack 112 层共 0.061 s
  [vllm] Loading weights took 0.17 seconds
  [vllm] Model loading took 1.1 GiB memory and 1.97 seconds
  [vllm] init engine (profile, create kv cache, warmup model) took 2.52 s

[gptq] 引擎 init 5.97 s；quant 层 repack 112 层共 0.022 s
  [vllm] Loading weights took 0.13 seconds
  [vllm] Model loading took 1.1 GiB memory and 1.51 seconds
  [vllm] init engine (profile, create kv cache, warmup model) took 2.54 s
```

1.5B 的量化模型上，读权重只占 0.1–0.2 s，模型落到显存约 1.5–2.0 s，剩下的 2.5 s 花在 KV cache 分配、预热与 profiling 上。repack 本身（112 个线性层）只要几十毫秒。这条时间线是 8.7 冷启动与权重分发的基线：**要缩短启动，优先动的不是反序列化，而是权重搬运和预热。**

```
（kv 头数 8、tp=4 → tp < nkv，每片持 2 个 kv 头，num_kv_head_replicas=1）
```

**该看哪些字段**：`直接行拼接还原 False` 是这张表的关键。每片内部的布局是 `[q_r, k_r, v_r]`，整体拼接会把 `q_1` 接到 `v_0` 后面，顺序错乱；正确做法是按段取出再拼。tp=1 的复现与真实引擎完全相同，说明这条 monkeypatch 复现路径与真实加载路径一致。

采集命令：`python labs/L4/checkpoint_load_path.py B`
完整输出：`results/crater/4.0/20260913-loadpath/run.log`

## 前沿

**量化格式正在往统一元数据层收敛。** 本章的 AWQ 与 GPTQ 各自把打包约定硬编码在 kernel 里，靠 `quantization_config.quant_method` 字符串分派。新一代做法是把"格式"拆成可组合的描述：`compressed-tensors` 0.17.0 的 `QuantizationArgs` 用 `num_bits / type / symmetric / group_size / strategy / block_structure / dynamic / actorder / scale_dtype / zp_dtype` 描述每个量化张量，`CompressionFormat` 再声明容器格式（`pack-quantized`、`marlin-24`、`float-quantized` 等），per-layer 的 `config_groups` 允许同一模型里不同层用不同方案。这样"磁盘布局"与"执行布局"之间的翻译从字符串分派变成了一次声明式解释。本地没有 compressed-tensors 打包的 checkpoint，本章只按安装库的字段与格式名做结构对照，**没有实例对拍，标 `UNVERIFIED`**。

**加载阶段的预算正在被显式建模。** vLLM 会根据文件系统类型决定是否预取权重：

```
[weight_utils.py:863] Filesystem type for checkpoints: OVERLAY. Checkpoint size: 3.78 GiB. Available RAM: 18.89 GiB.
[weight_utils.py:886] Auto-prefetch is disabled because the filesystem (OVERLAY) is not a recognized network FS (NFS/Lustre).
```

`OVERLAY` 不在可识别网络文件系统列表里，于是预取被关掉，加载退化成同步读。在 NFS/Lustre 上这套判断会打开预取；在容器 overlay 上则不会。这类"环境自适应的加载策略"是 8.7 冷启动与权重分发的直接输入：同一个 checkpoint 在本地容器与网络存储上的启动时间可能差出一段可观测的开销，而当前实现只按文件系统类型做二值判断。

**并行加载与格式转换的边界在移动。** 本章测到 repack 只占几十毫秒，而权重搬运与 KV/预热占 4 秒以上。这决定了优化方向：把加载拆成"按层并行 + 边到边算"的收益，主要来自提前开始计算，而不是加速反序列化或 repack。对应的机制（分片流水、层就绪信号、量化权重在设备端原地 repack）在 8.7 展开。

## 陷阱

1. **给 `get_tensor()` 计时量不到 I/O。** 它只建 mmap 视图，真正的读在第一次访问时发生（109.0 GB/s vs 2.6 GB/s）。
2. **`config.json` 的字段描述模型结构，不描述文件内容。** `tie_word_embeddings=True` 不保证文件里没有 `lm_head`（Qwen3-1.7B 多存了 593.5 MiB）。
3. **分片不保证一层的张量在同一个文件里**（Qwen3-8B 第 7 层被切开）。
4. **文件字节、参数口径、进程 RSS 是三个不同的量。** 同一个 checkpoint 分别是 3875.3 MiB、3281.7 MiB、4498.5 MiB（全触碰后）。报数字时必须说清用的是哪个。
5. **高于磁盘带宽不能单独判定没有读取。** page cache 命中后读取的是内存；高于标称 DRAM 带宽也应先核对流量公式、计时边界与计数器，再判断缓存贡献。
6. **"4 bit"不是等效位宽。** 算上 scales/zeros 是 4.16 bit，压缩比 3.85× 不是 4×。
7. **量化模型里 embedding 通常没被量化。** GPTQ 文件里它占 41%。
8. **AWQ 与 GPTQ 的 `qweight` 打包轴互为转置，位顺序也不同**，kernel 不能互换；磁盘布局也不等于执行布局，两者之间还有一次 repack。
9. **GPTQ 的零点在文件里存的是 `zero - 1`。** 不加这个偏移，反量化会整体偏一个量化步长。
10. **加载后的 `bias` 参数可能已被重排**（Marlin），用零输入响应而不是参数值来判断。
11. **`.bin`/`.pth` 是 pickle，加载等于执行代码。** 来源不明的权重不要用这两种格式。
12. **别用张量数量判断模型大小。** 量化模型的张量数是原来的 2–3 倍（AWQ 731 个 vs 未量化 311 个）。

## 自测题

<details markdown="1">
<summary>1. 只给你一个 .safetensors 文件和标准库，怎么列出所有张量名？</summary>

读前 8 字节当 u64 小端得到 $N$，再读接下来 $N$ 字节做 JSON 解析，key 就是张量名（除了 `__metadata__`）。

```python
import json, struct
with open(path, "rb") as f:
    n = struct.unpack("<Q", f.read(8))[0]
    hdr = json.loads(f.read(n))
print([k for k in hdr if k != "__metadata__"])
```

不需要读数据区，也不需要任何第三方库。每个张量的 `dtype`、`shape`、`data_offsets` 也都在这个 JSON 里。
</details>

<details markdown="1">
<summary>2. 你测出某个 checkpoint 的加载速度是 100 GB/s，磁盘是 NVMe（约 7 GB/s）。哪里错了？</summary>

几乎肯定是在给 mmap 建立映射计时，而不是给真实 I/O 计时。

`safe_open(...).get_tensor(name)` 返回一个映射到文件的张量视图，函数返回不保证已经遍历全部数据。后续访问是否产生缺页或磁盘 I/O，取决于页面是否已映射、驻留或命中 page cache。验证方法：拿到张量后强制碰每一页（例如 `t.float().abs().sum()` 或 `t.reshape(-1).sum()`），给这一步单独计时。本章实测 `get_tensor` 0.231 ms（109.0 GB/s），完整读一遍 9.697 ms（2.6 GB/s）。

同样要小心的是"加载完成"的定义：`low_cpu_mem_usage=True` 下加载函数返回时 RSS 只涨 635 MiB，把每个参数都求和一遍才涨到 4498 MiB。
</details>

<details markdown="1">
<summary>3. 一个模型 config 写 tie_word_embeddings=True，你数参数量时该怎么算？</summary>

按**结构**算：embedding 和输出层共用一份权重，只算一次。Qwen3-1.7B 得到 1,720,574,976 个参数。

但**文件大小**是另一回事：同一个 checkpoint 里额外存了一份逐位相同的 `lm_head.weight`，占文件的 15.3%（593.5 MiB），单独占了第二个分片。所以：

- 报"模型有多少参数"→ 按 config，算一份
- 报"下载要多少字节 / 加载要多少显存"→ 去读文件头，别猜

两个数字不一致是正常的，把它们混为一谈才是错。
</details>

<details markdown="1">
<summary>4. 把一个 1.5B 模型量化到 4 bit，文件应该从 3 GB 降到多少？实际是多少？为什么？</summary>

朴素预期：$16/4=4\times$，3 GB → 0.75 GB。

实际（本章 GPTQ）：**1096.7 MiB**。两个原因：

1. **等效位宽是 4.16 而不是 4**：每 128 个权重要额外存一个 fp16 scale 和一个 4 位零点。压缩比 3.85× 不是 4×。
2. **embedding 没被量化**：`[151936, 1536]` 的 F16 表占 445.1 MiB，是文件的 41%。

第 2 条影响大得多。词表 151936、hidden 只有 1536 时，embedding 本身就占原模型很大比例。**模型越小、词表越大，量化的实际收益越低。**
</details>

<details markdown="1">
<summary>5. 为什么不把 checkpoint 直接按推理引擎需要的融合布局存？</summary>

因为最优布局**依赖部署方式**，而 checkpoint 要服务所有部署方式。

QKV 要不要融合、怎么融合，取决于张量并行切几路（切 2 路和切 8 路的切分点不同）、用哪个引擎、什么硬件。按某一种布局存，就把模型绑死在那种部署上。所以磁盘上存数学定义的中性形式（每个 Linear 一个张量），加载器在启动时翻译。代价是每个引擎维护一张名字映射表。

反例就是量化格式：AWQ 与 GPTQ 的布局各自跟着自己的 kernel 走，结果谁也读不了谁的；而两者的执行布局在 Marlin 上又都变成了 `[96, 4096]`——说明"磁盘中性、执行专用"这条分工在量化这一层还没有真正建立起来。
</details>

<details markdown="1">
<summary>6. AWQ 的 qweight 是 `[1536, 192]`，GPTQ 的是 `[192, 1536]`。写出两者解包的第一行代码。</summary>

AWQ 沿**输出**维打包，`[in, out/8]`，位顺序是交错置换：

```python
AWQ_SHIFTS = [0, 16, 4, 20, 8, 24, 12, 28]
q = ((qweight.unsqueeze(-1) >> torch.tensor(AWQ_SHIFTS)) & 0xF).reshape(1536, 1536)
```

GPTQ 沿**输入**维打包，`[in/8, out]`，位顺序是顺序的：

```python
sh = torch.arange(0, 32, 4)
q = ((qweight.unsqueeze(-1) >> sh) & 0xF).permute(0, 2, 1).reshape(1536, 1536)
```

两者都得到 `[in, out]` 的整数值，再各自减去零点、乘以 scale。AWQ 的零点不加偏移，GPTQ 的零点要 `+1`。
</details>

<details markdown="1">
<summary>7. 你写的 GPTQ 反量化与引擎层输出的相对差是 8.7e-3。怎样判断这是解包错了还是精度差？</summary>

换一个参照：用同一份手写解包出来的权重，走 torch 的 fp16 GEMM 再算一次，与引擎比。本章实测这个参照的相对差是 8.64e-3，与 fp32 累加版的 8.66e-3 几乎相同。

两条路径的残差相同，说明差异不是解包约定造成的——如果打包轴或位顺序错了，误差会是"完全不同的权重"的量级（例如 AWQ 用错移位顺序时最大差 6.25，而不是 1e-1）。剩下的 1e-2 来自 kernel 的累加精度与 fp16 表示，属于正常范围。

更严格的判据是找一个**逐元素**可比的参照：本章 AWQ 解包与官方 `ops.awq_dequantize` 在 1536×1536 上逐元素完全相同（相同比例 1.000000），这一条没有容差空间。
</details>

<details markdown="1">
<summary>8. index 指向的分片文件被删掉了，报错应该长什么样？为什么这个错误不在文件解析阶段出现？</summary>

应该带上缺失的文件名，例如 `FileNotFoundError: index 指向的分片不存在: model-00003-of-00005.safetensors`。

因为 safetensors 的解析只针对单个文件：被删的是 `model-00003`，而剩下的 4 个分片每一个都结构完好（实测 `model-00003` 现有的 111 个张量都能正常列出）。损坏发生在**组装**这一层——只有把 `weight_map` 里的名字逐条映射到文件、发现某个文件不存在时才会暴露。这也是为什么加载器必须把"读取失败的张量名"与"它应该在哪个分片"一起报出来，否则面对 399 条映射无从定位。
</details>
