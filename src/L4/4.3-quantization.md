## 本章回答的三个问题

4.0 拆开了量化 checkpoint 的字节，4.2 给出了浮点格式的误差口径。这一章问的是量化本身：

1. 量化要最小化的到底是什么？RTN、clipping、GPTQ、AWQ 各自在优化什么，差距从哪来？
2. INT4、FP8、MXFP4、NVFP4 这些格式各自把位花在哪里？实际 bits/weight 是多少？
3. 换到真实的 shape 与 kernel 上，"4 bit 更快"成立吗？哪些成本没有被量化的位数覆盖？

误差口径与 4.2 一致：**权重误差** $=\lVert\hat W-W\rVert_F/\lVert W\rVert_F$，**输出误差** $=\lVert X\hat W^\top-XW^\top\rVert_F/\lVert XW^\top\rVert_F$。两者经常给出相反的结论，所以每个实验都同时报。

## 机制拆解

### 目标函数：为什么不最小化权重误差

线性层为 $Y=XW^\top$，令 $\Delta W=\hat W-W$，其重建目标为

$$
\|X\Delta W^\top\|_F^2=\operatorname{tr}(\Delta W H\Delta W^\top),\qquad H=X^\top X.
$$

按输入列分组后，完整展开是 $\sum_{g,h}\operatorname{tr}(\Delta W_g H_{gh}\Delta W_h^\top)$，其中 $H_{gh}=X_g^\top X_h$。只留下 $g=h$ 是块对角近似；scale 的分组不会使跨组相关项自动消失。X=[1,1]、ΔW=[1,1] 的误差平方为 4，只算两个对角块则得到 2。

在 X=[256,128]、W=[64,128]、group=32、FP64 的参照中，表内误差分别是 $\|\Delta W\|_F/\|W\|_F$ 和 $\|X\Delta W^\top\|_F/\|XW^\top\|_F$：

| 方法 | 相对权重误差 | 相对输出误差 |
|---|---:|---:|
| RTN | 9.7172e-02 | 1.0018e-01 |
| clipping（相同比例分组，裁剪比例 0.98） | 9.5935e-02 | 9.8842e-02 |
| GPTQ（完整 Hessian，静态 scale group） | 1.7034e-01 | 8.5625e-02 |
| AWQ（激活缩放 p=0.30） | 1.1450e-01 | 6.4819e-02 |

校准激活每 16 个通道有一个 ×10 的离群通道。GPTQ 在这份校准数据上降低输出误差，却增大权重误差；这说明两个目标不同，不说明它在所有输入分布上更优。clipping 与 RTN 保持相同的量化轴和 group；ratio=1 的两条路径逐元素相等，才能把后续差异归因于裁剪。

### 中间状态：固定一列后，剩余问题发生什么变化

设当前剩余变量的逆 Hessian 为 $K$。量化第 i 列时，$e=w_i-q_i$，补偿为 $-eK_{i,:}/K_{ii}$。固定该列后必须更新剩余逆矩阵；高效实现可以预先计算 $U=\operatorname{chol}(H^{-1},\text{upper=True})$，再使用 $e/U_{ii}$ 和 U 的第 i 行。始终复用原始完整逆矩阵的后续行不等价。

两列情况下，先固定第 0 列，对第 1 列的补偿为

$$-e\frac{H^{-1}_{01}}{H^{-1}_{00}}=+e\frac{H_{01}}{H_{11}}.$$

这里的逆矩阵下标与原矩阵下标不能互换。参照使用非等对角 H 检查符号和分母，再用逐列重算剩余 Hessian 的独立实现对拍 U 路径。列顺序会改变后续舍入点；某个两列例子在相关项为零时没有补偿，不代表一般 GPTQ 与顺序无关。

固定的[官方 GPTQ 实现](https://github.com/IST-DASLab/gptq/blob/2d65066eeb06a5c9ff5184d8cebdf33662c67faf/gptq.py#L99)先对 H 求逆，再取上三角 Cholesky；完成一个 block 后仍向后续 block 传播误差。scale group 与计算 block 是两个不同概念。

### 校准集与评测集必须分开

冻结校准得到的 scale、裁剪比例和补偿结果，再用独立随机样本评测；三组输入分别保留或改变校准分布的特征：

| 评测输入 | RTN | clipping | GPTQ | AWQ |
|---|---:|---:|---:|---:|
| 偏移-普通高斯 | 9.6464e-02 | 9.6214e-02 | 1.7304e-01 | 1.1410e-01 |
| 同分布-独立离群样本 | 9.8874e-02 | 9.7829e-02 | 1.1358e-01 | 6.3526e-02 |
| 偏移-独立相关样本 | 9.8060e-02 | 9.7321e-02 | 1.6661e-01 | 1.1485e-01 |

同分布这一行仍含每 16 通道 ×10 的离群值，但样本没有参与校准。普通高斯与相关通道两组是分布偏移，相关组也从新样本生成。这里 GPTQ 在校准集上改善、在独立同分布样本上退化；结论应保留这项差异，不能只展示校准收益。普通高斯一行 clipping 低于 RTN。该小实验不产生真实语言模型的质量排名。

### 格式：位花在哪里

同一个权重矩阵 [64,128] 上实现的五种格式（误差同为输出误差）：

| 格式 | 实际 bits/weight | 权重误差 | 输出误差 |
|---|---:|---:|---:|
| INT4 group=32 | 4.500 | 9.857e-02 | 9.847e-02 |
| INT4 group=64 | 4.250 | 1.096e-01 | 1.099e-01 |
| INT4 group=128 | 4.125 | 1.206e-01 | 1.195e-01 |
| FP8 per-tensor | 8.004 | 2.635e-02 | 2.628e-02 |
| FP8 per-channel | 8.250 | 2.545e-02 | 2.547e-02 |
| FP8 block-64 | 8.500 | 2.505e-02 | 2.517e-02 |
| FP8 block-32 | 9.000 | 2.391e-02 | 2.378e-02 |
| MXFP4（E2M1 + E8M0/32） | 4.250 | 2.551e-01 | 2.522e-01 |
| NVFP4（E2M1 + E4M3/16 + fp32 global） | 4.504 | 9.609e-02 | 9.554e-02 |

读法：

- **本例中较小 group 的误差较低，scale 元数据更多**：INT4 从 g128 到 g32，误差 1.195e-1 → 9.847e-2（-18%），位宽 4.125 → 4.500（+9%）。FP8 从 per-tensor 到 block-32，误差 2.628e-2 → 2.378e-2（-10%），位宽 8.004 → 9.000（+12%）。**"几 bit"必须连同 scale 粒度一起说。**
- **本例 MXFP4 的误差为 2.52e-1，INT4 为 1.10e-1，两者均约 4.25 bit。** 非均匀值域、scale 与分组共同影响误差，不能仅凭这两行分离各项贡献。E8M0 是纯指数 scale，只能表示 $2^e$，把一个 block 的幅度向上取整到 2 的幂，可能降低可用格点的利用率；这不是所有还原值必定偏小的保证。E2M1 有 7 个正幅度值（0.5/1/1.5/2/3/4/6），另有零和符号。
- **NVFP4 用同一个 E2M1 却把误差拉回 9.55e-2**，代价是 scale 从 E8M0（8 位/32 元素）换成 E4M3（8 位/16 元素）加一个 fp32 全局 scale：4.50 bit vs 4.25 bit，多花 0.25 bit 换来 2.6× 的误差改善。

位宽账可以逐项复算。NVFP4 每个元素占 4 bit，每 16 个元素共享 8 bit E4M3 scale，另有全张量 32 bit scale；忽略 padding、设总元素数为 N：

$$b=4+\frac{8}{16}+\frac{32}{N}\quad \text{bits/element}.$$

本章的 `bits/weight` 一列就是按实际存储字节数（`packed.numel()*4 + scales.numel()*2` 等）算出来的，不是按标称位宽填的。

### 与官方实现对齐

自写的编码器必须与官方算子严格对齐，否则后续推导仅能证明自写逻辑的局部自洽，无法保证工程正确性：

- **INT4**：GPTQ 布局的打包/解包做了逐元素往返断言（负数走补码 nibble），必须完全相等。
- **FP8**：与 vLLM 的 `scaled_fp8_quant`（动态模式）对拍——scale 完全相同（相对差 0.00e+00），**8192 个 fp8 字节逐字节相同（8192/8192）**。
- **NVFP4**：官方 `scaled_fp4_quant` 输出 `(64, 64)` 的打包权重与 `(128, 8)` 的 scale——注意这个 scale 不是"每 16 个元素一个"的直观布局，而是 8×4 的 swizzle 布局，专为 tensor core 的取数模式设计。本章只对照了它的形状与可运行性，**没有逐元素对拍编码**（`UNVERIFIED`）。

### 引擎接受的其余方法族

上面四类（INT4/GPTQ、FP8、NVFP4、KV cache）是本章实测过的。vLLM 0.29.0 的 `--quantization` 还接受另外五个名字，它们解决的是同一个问题的不同切面：**量化哪一部分、权重的位宽从哪里来、激活怎么办**。下面按结构、适用条件与代价逐个看，性能一节**不含实测**（本章没有运行这五条路径），只给源码事实与门控条件。

| 方法 | 量化对象 | 位宽来源 | 激活 | 关键约束 |
|---|---|---|---|---|
| `moe_wna16` | 只量化 MoE 专家权重 | 权重 N 位（4 或 8），来自 checkpoint | 保持 16 位 | 靠 override 认领；linear 层只能配 GPTQ 或 AWQ |
| `experts_int8` | 只量化 MoE 专家权重 | **在线**从 bf16 权重压成 int8 | 未量化 | 需要原始 bf16 checkpoint；sm_80+ |
| `int8_per_channel_weight_only` | 只量化 MoE 专家权重 | checkpoint 里的 int8 + 逐输出通道对称 scale | 未量化 | linear 层保持未量化 |
| `fp_quant` | 权重与激活 | 权重经 Hadamard 旋转后压到 MXFP4 | 前向时在线量化 | 激活 dtype 只支持 bf16 |
| `quark` | 权重（含 MoE） | AMD Quark 导出的格式 | 由其 scheme 决定 | 需要 `amd-quark` 包 |

**`moe_wna16`：MoE 专用，权重 N 位 + 激活 16 位。** 它不是一个由用户显式指定的格式，而是**覆盖式方法**：vLLM 把带 `override_quantization_method` 的方法排成一张偏好表，`moe_wna16` 就在其中（`config/model.py:1266`），由它自己从 checkpoint 的量化配置里认领模型。权重只压 MoE 专家，激活保持 16 位——这也是名字的来历（Weight N-bit, Activation 16-bit）。

它有并行的三条 kernel 路径：CUDA（`fused_moe/fused_moe.py:615` 调 `ops.moe_wna16_gemm`）、Triton（同文件 `:673`），以及 Marlin 变体（`_custom_ops.py:2562`）。CUDA 快路径不是无条件启用的，判据写死在 `should_moe_wna16_use_cuda`（`fused_moe.py:1288-1296`）：

```python
return (
    current_platform.is_cuda()
    and bit == 4
    and group_size in [32, 64, 128]
    and num_valid_tokens / num_experts <= 6
)
```

四个条件同时成立才走 CUDA，其中最后一条最容易被忽略：**每专家平均 token 数不超过 6**。batch 一大，`num_valid_tokens / num_experts` 升高，这条路径就主动退回 Triton——选择 kernel 的依据不是设备型号，而是这一步的实际负载形状。

`moe_wna16` 还有一个容易看漏的结构：它只接管**专家**，linear 层交给另一套方法，由 `linear_quant_method` 指定，而合法取值只有两个（`model_executor/layers/quantization/moe_wna16.py:70-84`）。取 `"gptq"` 时直接通过；取 `"awq"` 或 `"awq_marlin"` 时还要过一道算力门：

```python
awq_min_capability = AutoAWQConfig.get_min_capability()
if device_capability < awq_min_capability:
    raise ValueError(
        "The quantization method moe_wna16 + awq is not supported "
        "for the current GPU. "
        f"Minimum capability: {awq_min_capability}. "
        f"Current capability: {device_capability}."
    )
```

其余取值一律拒绝：`moe_wna16 only support gptq and awq.`。所以"专家用 WNA16、其余层用 AWQ"这种混搭不是无条件可用的——它取决于当前设备的算力是否达到 AWQ 的下限，报错信息会把两个能力值都打出来。**这正是量化格式组合比单个格式更难排查的地方：错误来自两个方法的交叉约束，而不是其中一个本身。**

**`experts_int8`：不读量化 checkpoint 的在线量化。** 它的配置类是 `ExpertsInt8Config`（`layers/quantization/experts_int8.py:22`），自述是"面向 `--quantization experts_int8` 的向后兼容配置"（`:26`），`from_config` 直接返回默认实例、不看 checkpoint 里的量化字段。分配到层上的行为很干脆（`:56-59`）：`LinearBase` 拿 `UnquantizedLinearMethod`，只有 `RoutedExperts` 换成 `Int8OnlineMoEMethod`。最低算力要求 `sm_80`（`:42`）。

这条路径的含义与前面几种完全不同：**它不需要一份已经量化好的权重，而是拿原始 bf16 checkpoint，在加载时把专家权重在线压成 int8**。省下来的是专家权重的常驻显存（对应 4.4 那个"按总参数量买显存"的账），不是权重读取带宽——因为在线量化发生在加载期，推理时读到的是已经压好的副本。

**`int8_per_channel_weight_only`：静态 int8 权重，逐输出通道对称。** 它是 `--quantization` 的一个简写名，在配置表里只有一行加一句注释（`config/quantization.py:139-141`）：

```python
# INT8 weight-only on MoE; linear stays unquantized (no `linear` field).
"int8_per_channel_weight_only": QuantizationConfigArgs(
    moe=QuantSpec(weight=kInt8StaticChannelSym),
),
```

注释里的两个信息点：作用范围**只有 MoE**，linear 层不量化（连 `linear` 字段都没有）；scale 是**逐输出通道**且对称。与 `experts_int8` 的差别是"静态"——权重和 scale 都从 checkpoint 读，不需要原始 bf16 权重；与 `moe_wna16` 的差别是它不承诺激活走 16 位路径，而是根本不量化激活。

**`fp_quant`：旋转 + MXFP4 的工程化版本。** `FPQuantConfig` 的构造参数是 `hadamard_group_size=32, forward_dtype="mxfp4", forward_method="abs_max", modules_to_not_convert`（`layers/quantization/fp_quant.py:30-36`），文件头注明对应 FP-Quant 压缩（arXiv 2509.23202）。

它就是本章前面「旋转 + 低精度」那组实验的工程化形态，而且解释了那张表里的一个反常结果。回顾那个结论：旋转把 per-tensor FP8 的输出误差降了 8%，却让 NVFP4 变差 9%，因为 NVFP4 按 16 个元素一块缩放、离群值已被局部吸收，旋转只额外引入 bf16 舍入。`fp_quant` 的 `hadamard_group_size=32` 把旋转的块宽与 MX 的块宽对齐——**旋转和量化用同一个分组，才不会在两级分组之间重复引入舍入**。激活是前向时在线量化的（`forward_method="abs_max"`），走 `fusedQuantizeMx`/`matmul_mxf4_bf16_tn` 这类融合 kernel，支持的激活 dtype 只有 bf16（`:59`）。

**`quark`：既是格式，也是一组可被复用的算子。** `QuarkConfig`（`layers/quantization/quark/quark.py:58`）是注册在 `QuantizationMethods` 里的完整方法，自带 `schemes/`、`quark_moe.py` 与 `utils.py`。它同时出现在另外两条路径上：MXFP4 的模拟实现会检查 `has_quark()`，缺包时给出"amd-quark package not available"（`kernels/linear/mxfp4/emulation.py:72-73`）；`quark_quantize_weight_to_mxfp4` 被 MLA attention 的权重预处理调用（`layers/attention/mla_attention.py:1130-1139`）。在 MoE 一侧，它与 compressed-tensors、modelopt 并列作为 NVFP4 的来源之一（`fused_moe/experts/fused_humming_moe.py:336` 的注释）。

**这五个名字的共同点与选型含义。** 三个是 MoE 权重专用（`moe_wna16`、`experts_int8`、`int8_per_channel_weight_only`），两个覆盖更广（`fp_quant`、`quark`）。它们的差异不在"位宽高低"，而在三个正交的选择上：

- **量化谁**：只量化专家权重，还是连 linear 一起；`fp_quant` 还量化激活。
- **权重从哪来**：从 checkpoint 读已经量化好的（`int8_per_channel_weight_only`、`moe_wna16`、`quark`），还是在加载时在线压（`experts_int8`）。
- **激活怎么办**：不动（`experts_int8`、`int8_per_channel_weight_only`）、保持 16 位（`moe_wna16`）、在线量化（`fp_quant` 与本章实测的 FP8 在线路径）。

这三条正好解释了本章前面那个结论为什么成立：**在线激活量化会吃掉一半收益**（FP8 从 0.052 涨到 0.083 ms）。凡是把激活留在 16 位或完全不动的方案，省的是权重带宽与专家显存；凡是要压激活的，每一次调用都要多付一遍 amax 与转换。

### 真实 shape 上的成本

Qwen3-1.7B 的两个真实 shape，M 从 1 到 2048（每个配置 10 次预热 + 50 次计时）：

| shape | M | bf16 | INT4 反量化+bf16 | FP8 kernel | FP8 含在线量化 | NVFP4 kernel |
|---|---:|---:|---:|---:|---:|---:|
| q_proj 2048×2048 | 1 | 0.008 ms | 0.008 ms | 0.011 ms | 0.032 ms | 0.024 ms |
| q_proj | 128 | 0.015 | 0.014 | 0.011 | 0.033 | 0.024 |
| q_proj | 2048 | 0.098 | 0.098 | **0.052** | 0.083 | **0.032** |
| down_proj 2048×6144 | 1 | 0.011 | 0.011 | 0.013 | 0.032 | 0.038 |
| down_proj | 128 | 0.023 | 0.023 | 0.021 | 0.041 | 0.037 |
| down_proj | 2048 | 0.251 | 0.252 | **0.144** | 0.214 | **0.069** |

四条结论：

- **INT4 显式反量化完全没省时间**（0.098 vs 0.098、0.252 vs 0.251）。读权重的字节少了一半，但多了一遍解包与转换，而且矩阵乘仍然是 bf16——省下的带宽被额外的 kernel 与中间缓冲吃掉了。
- **FP8 的收益在融合 kernel**：M=2048 时 0.052 vs 0.098 ms（1.9×）、down_proj 0.144 vs 0.251（1.7×）。
- **在线激活量化会吃掉一半收益**：FP8 从 0.052 涨到 0.083 ms，因为每次调用都要算激活的 amax 并做一次 fp8 转换。
- **NVFP4 的 kernel 最快**（0.032 / 0.069 ms，M=2048 时比 bf16 快 3.1× / 3.6×），代价是输出误差 1.4e-1（激活也用 E2M1 量化）。**速度与精度在同一次测量里必须一起报。**

### 位数没覆盖的成本

**L2 轮转。** down_proj 单份权重 24 MiB，8 份共 192 MiB，超过 96 MiB 的 L2：

```
单份（驻留）0.025 ms/次；8 份轮转 0.280 ms/轮（平均 0.035 ms/份，即 1.41× 单份）
```

权重工作集一旦超过 L2，每份的实际耗时涨 41%。量化把权重的**存储**压小了，但**访问模式**没变：低精度权重仍然要按同样的顺序流过 SM。

**旋转的代价与收益。** 把一个 Hadamard 旋转折进权重与激活（$(XH)(WH)^\top=XW^\top$，浮点对拍最大差 2.4e-6），再量化：

| 变体 | FP8 输出误差 | NVFP4 输出误差 | $\lvert x\rvert_{\max}$ | $\lvert w\rvert_{\max}$ |
|---|---:|---:|---:|---:|
| identity | 3.743e-02 | 1.239e-01 | 73.00 | 0.492 |
| Hadamard | **3.442e-02** | 1.400e-01 | 20.25 | 0.116 |

旋转把激活的最大幅度从 73 压到 20.25、权重从 0.492 压到 0.116，**per-tensor FP8 的误差随之降了 8%**；而 NVFP4 反而变差（1.24e-1 → 1.40e-1）——它本来就按 16 个元素一块缩放，离群值已经被局部吸收了，旋转只额外引入了 bf16 舍入。**"旋转消离群"对不同的量化粒度效果不同，不能当通用技巧。** 旋转本身耗时 31.8 ms（一次性，可离线折进权重，不进入推理热路径）。

### KV cache 量化：字节账与数值

权重侧的量化不改变 KV cache；KV 侧单独量化能直接换并发。同一引擎、同一显存预算（13.22 GiB KV），只改 `kv_cache_dtype`：

| kv_cache_dtype | KV 容量 | 32k 请求的并发上限 | 显存预算 |
|---|---:|---:|---:|
| auto（bf16） | 123,728 token | 3.78× | 13.22 GiB |
| fp8 | **247,472 token** | **7.55×** | 13.22 GiB |

同样的显存预算（13.22 GiB）下容量正好翻倍（2.00×）——KV 的字节宽度从 2 降到 1，容量按反比增长；32k 上下文的并发上限从 3.78× 提到 7.55×。这是 3.3 的字节账在真实引擎上的兑现。

**K/V 误差的传播**（同一提示、同一引擎，只改 `kv_cache_dtype`；关闭前缀缓存以保证 prefill 计时真实）：

| 上下文 S | prefill（auto / fp8） | 解码 32 token（auto / fp8） | top-1 logprob 差 | 32 token 逐位相同 |
|---:|---|---:|---:|---:|
| 2,048 | 133.8 / 138.0 ms | 164.8 / 184.1 tok/s | 0.0000 | 32/32 |
| 8,192 | 164.3 / 170.9 ms | 105.3 / 105.8 tok/s | 0.0000 | 32/32 |
| 32,768 | 1,101.9 / 1,125.9 ms | 24.9 / 25.3 tok/s | **0.0444** | 32/32 |

四条读法：

- **误差随上下文长度累积但很小**：S=2048/8192 时 top-1 的 logprob 完全相同（该处的 top-1 概率为 1.0，属确定性 token），S=32768 时差 0.0444。**K/V 量化影响的是注意力读到的历史，历史越长、被量化的元素越多**。
- **分布变了，贪心序列没变**：三个长度上 32 个贪心 token 全部逐位相同。这说明该量级下 FP8 KV 不改变生成轨迹；但**不能据此说"质量不变"**——它只覆盖一条 32 token 的贪心轨迹（质量评测见本章 E 段）。
- **解码吞吐的收益随上下文增大**：S=2048 时 fp8 快 12%（184.1 vs 164.8 tok/s），S=8192 基本持平（105.8 vs 105.3），S=32768 只快 1.6%（25.3 vs 24.9）。长上下文下解码时间由 KV 读取主导，理论上 KV 减半应该更明显——这里的差距说明**该 shape 下其他开销（权重读取、kernel 启动）仍占主导**，与 3.3 的 roofline 分析一致。
- **KV 量化买的是并发，不是单请求速度**：容量 2.00×、并发 2.00×，而单请求 prefill/decode 几乎不变（1.102 → 1.126 s、24.9 → 25.3 tok/s）。

**KV 的 dtype 路线对照**（同一提示 8192 token、同一引擎，只改 `kv_cache_dtype`；vLLM 0.29 支持这些取值）：

| kv_cache_dtype | KV 容量 | 32k 并发 | prefill | 解码 | top-1 logprob 差 | 32 token 逐位相同 |
|---|---:|---:|---:|---:|---:|---:|
| auto（bf16） | 123,728 | 3.78× | 164.3 ms | 105.3 tok/s | — | 32/32 |
| fp8 | 247,472 | 7.55× | 170.9 ms | 105.8 tok/s | 0.0000 | 32/32 |
| turboquant_4bit_nc | 336,992 | 10.28× | 259.6 ms | 83.3 tok/s | 0.0000 | 32/32 |
| int4_per_token_head | **465,840** | **14.22×** | 663.1 ms | 56.9 tok/s | 0.0002 | 32/32 |

三点读法：

- **容量按位宽近似反比**：1× → 2.00×（fp8）→ 2.72×（turboquant 4bit）→ 3.77×（int4 per-token-head）。
- **代价是 prefill 的在线量化**：164 → 171 → 260 → 663 ms（int4 是 bf16 的 4.0×），解码也从 105 掉到 57 tok/s。**压缩越狠，每步的量化/反量化越贵**——这与 4.3-C 段"显式反量化不省时间"是同一类现象。
- **四个配置在 8k 上生成轨迹完全一致**（32/32 逐位相同），logprob 差最大 0.0002。质量侧的结论仍只覆盖一条 32 token 的贪心轨迹。

**B=8 的批处理与块池字节账**（S=8192；字节账用「引擎自报的 KV 显存预算 ÷ 引擎自报的 KV token 容量」）：

| kv_cache_dtype | prefill | 解码（B=8 总） | 每请求 | KV 字节/token | 相对 bf16 | 解析式（2×层×KV头×head_dim×字节） |
|---|---:|---:|---:|---:|---:|---:|
| auto（bf16） | 1.303 s | 157.4 tok/s | 19.7 tok/s | 114,726 | 1.00× | 114,688 |
| fp8 | 1.336 s | 165.4 tok/s | 20.7 tok/s | 57,359 | 2.00× | 57,344 |
| turboquant_4bit_nc | — | — | — | 42,122 | 2.72× | — |
| int4_per_token_head | 2.267 s | 96.6 tok/s | 12.1 tok/s | 30,472 | 3.77× | — |

两条读法：

- **字节账可以被独立复算**：解析式 `2(K/V) × 28 层 × 8 KV 头 × 128 × 2 字节 = 114,688 B/token`，引擎自报 114,726 B/token（差 0.03%，来自块池的对齐/元数据）。**fp8 正好是一半**（57,359 vs 57,344），说明量化只改了每元素的字节宽度，没有额外开销。这条闭合了"字节账要直接算自块池"的要求。
- **批处理把总吞吐抬起来，但不改变 dtype 的排序**：B=1→B=8 时 auto 从 105.3 → 157.4 tok/s 总吞吐（每请求 19.7）；fp8 比 auto 快 5%，int4 掉到 96.6 tok/s。**KV 量化的收益在并发容量（1→2→2.72→3.77×），代价在每一步的量化开销**（int4 的 prefill 是 bf16 的 1.7×，B=1 时是 4.0×）。

**同一协议下的服务扫描**（Qwen2.5-1.5B-Instruct 的三个精度；S=1024、B=1/8、贪心、先预热一次、关闭前缀缓存、每个模型独立进程）：

| 模型 | 权重显存 | KV 容量 | 4k 并发 | B=1 首 token | B=1 解码 | B=8 首 token | B=8 总吞吐 | 每请求 | 首 token logprob |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| bf16 | 2.98 GiB | 383,376 token | 93.60× | 104.0 ms | **223.3 tok/s** | 116.2 ms | **1026.5 tok/s** | 128.3 | -0.0004 |
| AWQ | 1.10 GiB | 455,696 token | 111.25× | 104.1 ms | 196.3 tok/s | 126.5 ms | 923.8 tok/s | 115.5 | -0.0011 |
| GPTQ-Int4 | 1.10 GiB | 455,184 token | 111.13× | 105.0 ms | 193.7 tok/s | 121.3 ms | 935.8 tok/s | 117.0 | -0.0003 |

四条读法：

- **权重显存 2.98 → 1.10 GiB（2.7×）**：这是 4-bit 量化最确定、最大的收益。
- **KV 容量反而增加 19%**（383k → 456k token）：同一 `gpu_memory_utilization` 预算下，权重省下的显存全部变成了 KV 块。**"量化省显存"的真实形态是"把权重的显存换成 KV 的容量"。**
- **首 token 延迟几乎不变**（104.0 / 104.1 / 105.0 ms）：S=1024 的 prefill 是算力主导，权重读取不是瓶颈。
- **单请求解码反而更慢**（223.3 → 196.3 / 193.7 tok/s，-12%），B=8 总吞吐也低 9–10%：低精度权重需要反量化与专用 kernel，**在本 shape 下量化的收益是显存而不是速度**——与 C 段"显式反量化不省时间"的结论一致。

**注意第一格曾被冷启动污染**：首轮未预热时 AWQ 的 B=1 解码测出 29,824 ms（1.1 tok/s），预热后是 163.0 ms（196.3 tok/s）。**任何服务扫描都必须先预热**，否则会把 kernel 首次编译算成性能。

**SLO 曲线：换的是显存，不是延迟**（S=1024，B=1/4/16，`max_tokens=1` 测首 token、`max_tokens=32` 测解码）：

| 模型 | B=1 首 token | B=4 首 token | B=16 首 token | B=1 每请求 | B=4 每请求 | B=16 每请求 | B=16 总吞吐 |
|---|---:|---:|---:|---:|---:|---:|---:|
| bf16 | 104.4 ms | 61.8 ms | **225.8 ms** | 227.4 tok/s | 169.0 | **88.3** | **1413.3** |
| AWQ | 103.4 ms | 64.0 ms | 247.7 ms | 195.3 | 150.1 | 79.9 | 1278.7 |
| GPTQ-Int4 | 102.3 ms | 62.0 ms | 236.7 ms | 193.9 | 142.9 | 81.3 | 1300.8 |

三条读法：

- **首 token 对 batch 非单调**（104 → 62 → 226 ms）：B=4 比 B=1 快，说明单请求的 prefill 在这个 shape 上并没有打满机器，batch 4 的 kernel 形状反而更高效；B=16 才进入排队与共享算力的区间。**用单点数据推 SLO 会得出错误结论。**
- **每请求解码吞吐随 batch 单调下降**（227 → 169 → 88 tok/s），而总吞吐单调上升（B=16 时 1413 tok/s）——这是 batching 的基本权衡。
- **三精度在 B=16 的 SLO 表现几乎相同**（TTFT 226/248/237 ms、每请求 88.3/79.9/81.3 tok/s，差 ≤9%）。**4-bit 没有换来延迟余量**：它换的是权重显存（2.7×）与 KV 容量（+19%），也就是"同样一张卡能同时服务多少请求"，而不是"单个请求多快"。

### 设计取舍

**为什么没有一种格式通吃。** 位预算的分配有三个独立的维度：值域（指数位）、分辨率（尾数位）、以及 scale 的粒度与类型。INT4 把所有元素压到 4 位、靠 group scale 补回动态范围；FP8 用 4 位指数保住范围、3 位尾数换来 8 bit 的分辨率；MXFP4 用共享的 2 的幂 scale 换取"解包零成本"；NVFP4 用 fp8 的块内 scale 换精度。离群值、分组方式和算子布局会共同影响误差与成本；是否使用 block scale、旋转或 per-tensor 格式需要在目标张量与任务上比较，不能仅由分布外观决定。

**为什么"量化后更快"不是自动的。** 量化改变的是内存流量，而时间由 kernel 决定。三个反例都在本章的表里：INT4 显式反量化不省时间；FP8 的收益被在线激活量化吃掉一半；权重超过 L2 后每份慢 41%。**判断量化收益的正确方式是在目标 shape 上测完整调用，而不是按位宽比例外推。**

**为什么校准集的选择是一个工程决策。** 同一套方法在三种评测分布上的排序会翻转（见上表）。校准集要覆盖部署时会遇到的分布，并且必须与最终评测分开——否则测的是"针对这套题的调参效果"，不是量化质量。

## 前沿

**本组格式对照展示了 scale 粒度与布局的影响。** MXFP4 与 NVFP4 用同一套 4 位值（E2M1），本例主要差别包括 scale：E8M0/32 元素 vs E4M3/16 元素加 fp32 全局。本章实测这两者的误差差 2.6 倍、位宽只差 0.25 bit。接下来的问题是 scale 自身怎么被硬件取用——vLLM 的 NVFP4 权重 scale 是 8×4 swizzle 布局（实测 `scaled_fp4_quant` 输出 `(128, 8)`），为的是让 tensor core 在一个 warp 内连续取到 scale。数值误差与 kernel 布局契约需要分别通过验证。

**旋转类方法的效果取决于量化粒度。** 本章的 Hadamard 消融给出一个反直觉结果：同一个旋转把 per-tensor FP8 的误差降了 8%，却让 block-scaled NVFP4 变差 13%。这只支持本组输入与实现的观察。QuaRot/MR-GPTQ 的旋转位置、权重与激活量化、分组方式都要按真实方法另作对照，不能据这两个读数概括整类方法的收益。**"要不要旋转"必须与"scale 多细"一起决定**，不能当成通用前置步骤。

**KV cache 的量化空间比权重更宽。** 权重侧的选择主要是位宽与 scale 粒度；KV 侧还要决定"沿哪个维度量化"。vLLM 0.29 的 `CacheDType` 枚举里除了 `auto`/`fp8`/`fp8_e4m3`/`fp8_e5m2`/`fp8_inc`/`fp8_ds_mla` 之外，还有按 head 粒度的 `int4_per_token_head`、`int8_per_token_head`，以及 TurboQuant 系列的 `turboquant_3bit_nc`、`turboquant_4bit_nc`、`turboquant_k3v4_nc`、`turboquant_k8v4`（K/V 可用不同位宽）与 Humming 系列。这些名字来自本章按库版本导出的选项空间（`results/crater/option_spaces.json`），**本章只完成了格式层面的参照实现（B 段）**：INT4 已做打包往返，FP8 已有官方字节对照；MXFP4/NVFP4 仍需区分自写格式参照与官方逐元素编码对拍，但把它们接到真实的分页 attention 上（按 head 粒度量化、K 与 V 分开、长上下文的质量与状态字节账）属于任务 D，本轮未执行，保持未验证。

**KV 量化的收益是并发而不是延迟。** 本章在真实分页接口上测得：同样的 13.22 GiB，fp8 KV 把容量从 123,728 token 提到 247,472（2.00×），而单请求解码只快 5.2%，首个 token 的 logprob 差 0.053。这条结论与 3.3 的 roofline 分析互相印证——KV 量化改变的是"能同时服务多少请求"，而单请求速度取决于权重读取与 kernel 启动。**在这个意义上，KV 量化的评测必须报并发与吞吐，而不是单请求延迟。**

**质量评测仍然只覆盖了"建模 + 选择题"两类。** 本章的 E 段给出 WikiText-2 PPL（bf16 9.1629 / AWQ 9.9582 / GPTQ 10.1742）与 C-Eval 分层 199 题（0.598 / 0.553 / 0.538），校准/调参/评测三套样本完全不重叠。但真实的量化解收益还要看：长上下文生成质量、结构化输出与工具调用是否退化、以及同一 SLO 下三种精度的完整服务成本曲线。这些属于 5.x 的服务评测与 8.x 的生产章节，本章只把质量—成本曲线的两端（PPL/选择题 与 kernel 时间）钉住。

## 陷阱

1. **权重误差小不等于输出误差小。** 本次 GPTQ 校准输出误差较低，但独立样本上的结果可能更差；分别保留两组测量。
2. **校准集决定排序。** 同一套四种方法在三种评测分布上的排名会翻转（第 2 张原始现场表）。
3. **"4 bit"不等于 4 bit/权重。** INT4 g128 是 4.125、g32 是 4.500；NVFP4 是 4.504。位宽必须连同 scale 粒度一起报。
4. **位宽相同的格式可以差 2 倍以上误差。** MXFP4 4.25 bit 的输出误差（2.52e-1）远差于 INT4 g64 的 4.25 bit（1.10e-1）。
5. **INT4 显式反量化不省时间。** 省下的带宽被解包 kernel 与中间缓冲吃掉（0.098 vs 0.098 ms）。
6. **FP8 的收益在融合 kernel，不在激活量化。** 在线量化让 0.052 ms 变成 0.083 ms。
7. **`cutlass_scaled_mm` 的 `b` 必须是转置视图。** 加 `.contiguous()` 会被拒，报错只有文件行号。
8. **`cutlass_scaled_fp4_mm` 的 `alpha` 在 `out_dtype` 之前**；`scaled_fp8_quant` 的第二个位置参数是静态 scale；动态量化使用 None。
9. **权重工作集超过 L2 时，每份慢 41%**（96 MiB L2 vs 192 MiB 工作集）。量化不改访问模式。
10. **旋转不是通用技巧。** 它改善 per-tensor FP8，却让块量化的 NVFP4 变差。
11. **NaN/零点约定仍然是坑。** 4.0 的 `+1`、本章的补码 nibble 与 `uint4b8` 的偏移 8，任何一处错位都得到"能跑但全错"的结果（Marlin 独立调用就是例子）。
12. **独立算子调通不等于引擎路径正确。** 反之亦然：本章 Marlin 独立调用失败，但 4.0 的引擎层对拍是正确的。

## 自测题

1. 为什么 scale group 不能让重建目标自动拆成互不相关的几项？
::: fold
因为输出误差中还含 $X_g^\top X_h$ 的跨组项；除非明确采用块对角近似或证明这些项为零，完整目标需要对 g、h 求和。
:::

2. 固定第 i 列后，能继续使用原始 H⁻¹ 的第 i+1 行吗？
::: fold
不能。剩余自由变量的逆 Hessian 已经改变。可显式消元/重新求逆，或用逆 Hessian 的上三角 Cholesky 因子实现等价的逐列补偿。
:::

3. group 更小是否保证权重误差更低？
::: fold
不保证。W=[1,0,6/7,4/7] 的对称 4-bit RTN 在 group=4 时精确；group=2 改变了第二组的 scale，误差反而非零。新旧格点不是必然嵌套，任务质量更没有单调保证。
:::

4. GPTQ 在校准集改善而独立样本退化，应该报告哪一组？
::: fold
两组都报告。冻结校准/调参选择，再用独立样本与真实任务评估泛化；不能通过换掉不利评测集来支持一种方法。
:::

5. 一个低比特 kernel 更快，是否完成了量化的成本与质量验收？
::: fold
还没有。需包括在线 scale/旋转/重排、额外缓冲、完整调用、状态字节和独立任务质量；未测的路线保持明确边界。
:::
