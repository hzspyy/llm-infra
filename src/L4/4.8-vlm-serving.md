## 机制拆解

### 三层缓存：键不同、失效条件不同

多模态请求里有三种可以复用的东西，它们的键与生命周期完全不同：

| 层 | 缓存内容 | 键 | 失效条件 |
|---|---|---|---|
| **L1 processor** | resize/normalize 后的像素张量 | 图像内容 + 尺寸策略 | 图变、目标尺寸变 |
| **L2 encoder** | 视觉塔的 4 个载荷（4.6：3×DeepStack + 主出口） | revision + processor 配置签名 + 内容 + 尺寸 + 帧采样 | 上面任一项变 |
| **L3 KV** | 视觉 token 与文本 token 的 KV | 序列身份（含位置） | 序列里任何位置变化都会改变视觉段的 RoPE 相位 |

本章实现的最小缓存（`FeatureCache`）只做 L1 与 L2，实测命中矩阵：

| 场景 | L1 命中 | L2 命中 | 说明 |
|---|---|---|---|
| 同图重复（同尺寸） | [miss, **hit**] | [miss, **hit**] | 三层都能复用 |
| 同图不同 crop（尺寸不同） | [hit, **miss**] | [hit, **miss**] | 内容同、尺寸不同 → 键不同 |
| 不同图（同尺寸） | [hit, **miss**] | [hit, **miss**] | 内容进键 |
| 同帧不同时间戳 | [hit, **hit**] | [hit, **miss**] | 像素相同，但帧采样身份进 L2 键 |
| 同图像 + 不同文本 | [hit, **hit**] | [hit, **hit**] | L1/L2 命中，**KV 不能复用** |

（矩阵按场景顺序累积，所以要看每行的**第二个**请求；第一个请求的命中来自上一场景缓存的内容。）

两条设计结论：

- **"同图不同尺寸"与"不同图"一样是 L1 未命中**：尺寸策略（4.5 的像素预算）是键的一部分。想要跨尺寸复用，需要把 resize 从"预处理"变成"编码后"——代价是塔内序列更长。
- **把帧采样身份放进 L2 键会让"像素完全相同但采样身份不同"的帧不命中**（矩阵第 4 行）。这是保守的做法：同一帧在 `t=0.0` 与"无时间戳"下的编码结果其实相同，键里可以只用像素哈希；但这样会失去"这份特征属于哪一帧"的语义。**键的设计是"复用率"与"语义清晰"之间的取舍。**

省下的时间（单张 640×480 图）：视觉编码 **10.41 ms**、processor **0.69 ms**，载荷 **6.738 MiB**。注意缓存**不省 LLM 的 prefill**：视觉 token 仍然要进序列（单图 300 token、双图 600 token），预填充与 KV 写入照旧。

### 引擎里缓存真的有效：vLLM 的实测

用 vLLM 0.29 加载同一个模型，请求组合为纯文本 / 单图 / 双图 / 16 帧视频，每个组合做三次调用（1 token 首延迟、重复一次、32 token 完整生成）：

| 组合 | 提示 token（视觉/文本） | 首 token | 重复 | 32 token |
|---|---|---:|---:|---:|
| 纯文本 | 14（0 / 14） | 16.5 ms | 10.3 ms | 230.3 ms |
| 单图 | 315（300 / 15） | 33.8 ms | **12.1 ms** | 78.2 ms |
| 双图 | 618（600 / 18） | 30.5 ms | **12.7 ms** | 233.2 ms |
| 视频 16 帧 | 192（160 / 32） | 186.3 ms | **17.6 ms** | 91.6 ms |

关闭多模态缓存（`mm_processor_cache_gb=0`）后重跑，**重复**值变成：

| 组合 | 缓存开 | 缓存关 | 差 |
|---|---:|---:|---:|
| 纯文本 | 10.3 ms | 10.5 ms | 0.2（不受影响） |
| 单图 | 12.1 ms | 17.0 ms | **4.9 ms** |
| 双图 | 12.7 ms | 21.7 ms | **9.0 ms** |
| 视频 16 帧 | 17.6 ms | 22.8 ms | **5.2 ms** |

四条读法：

- **缓存只对多模态请求有效**（纯文本 10.3 vs 10.5 ms 在噪声内），因为要复用的是视觉输入的处理结果。
- **收益是"重复请求的 processor 段"**：单图 4.9 ms、双图 9.0 ms。它与 6.738 MiB 的载荷、10.41 ms 的塔内编码是同一件事的两个侧面——**引擎缓存的是 processor 产物（L1）**，塔内编码是否被缓存取决于引擎的 encoder cache（启动日志里可见 "Encoder cache will be initialized with a budget of 16384 tokens"）。
- **首 token 与重复的差（33.8 → 12.1 ms）比缓存开关的差（17.0 → 12.1 ms）大得多**，说明首次请求里还有一次性的成本（kernel/分配器预热、encoder cache 首次填充）。**只报"首 token 与重复的差"会把冷启动算成缓存收益。**
- **视频答案正确**：合成视频是 16 帧 4 fps（3.75 s），模型回答"视频里描述了3.75秒"。这是本章唯一的质量侧证据，样本量为 1。

### 慢模态的长尾：文本请求被谁拖慢

用上面测到的服务时长做单 worker 排队模拟（泊松到达，服务时长取实测首 token）：

| 到达率 | ρ | 队列 | p50 | p99 | 纯文本 p99 | 丢弃率 |
|---|---:|---|---:|---:|---:|---:|
| 24.85/s | 0.80 | 无界 | 41.8 ms | 313.2 ms | 281.5 ms | 0.0% |
| 24.85/s | 0.80 | ≤8 | 41.1 ms | 313.2 ms | 281.5 ms | 0.5% |
| 31.06/s | 1.00 | 无界 | 120.4 ms | 567.9 ms | 537.4 ms | 0.0% |
| 31.06/s | 1.00 | ≤8 | 102.1 ms | 496.0 ms | 465.7 ms | 3.5% |
| 37.27/s | 1.20 | 无界 | 551.9 ms | 876.9 ms | **849.9 ms** | 0.0% |
| 37.27/s | 1.20 | ≤8 | 148.2 ms | 362.7 ms | **342.1 ms** | **10.5%** |

**纯文本请求的服务时长只有 16.5 ms，但它的 p99 从 281.5 ms 涨到 849.9 ms（3.0×）**——被 186 ms 的视频请求排在前面拖慢。这是"慢模态影响文本请求"的可量化证据，也是准入控制（限制视频分辨率/帧数、给不同模态分配不同容量）的动机。

**有界队列把尾延迟换成丢弃。** ρ=1.2 时，把等待队列限制到 8：纯文本 p99 从 849.9 ms 降到 342.1 ms（2.5×），代价是 10.5% 的请求被拒；ρ=1.0 时 p99 从 567.9 降到 496.0 ms、丢弃 3.5%；ρ=0.8 时两者几乎相同（丢弃 0.5%）——**过载越严重，准入控制的收益越大**。这正是"保护文本请求"的量化形式：排队不降低总工作量，有界队列主动丢弃才把延迟从多数请求身上转移走。

**这一段的边界必须说清楚**：C 段是**排队模拟**（单服务器 FIFO、到达为泊松、服务时长取 B 段实测），不是引擎实测。真实引擎有 continuous batching、chunked prefill、抢占与 encoder 准入，单 worker FIFO 是最保守的模型；真实系统里"有界"更可能表现为**拒绝新请求**而不是丢弃已接受的请求（本章的模型丢弃的是排队中的请求）。

### 取消：同一 API 在不同阶段行为不同

用 vLLM v1 的 `AsyncLLM`（进程内引擎）在独立定时任务里触发 `abort`，三种请求各测一次（预热后；每个用例之后立刻发一个纯文本请求作为健康检查）：

| 用例 | abort 触发 | 取消前 chunk | **取消后 chunk** | abort→生成器结束 | 随后纯文本首 token |
|---|---|---:|---:|---:|---:|
| 纯文本长生成（512 token，150 ms 时 abort） | 是 | 20 | **1** | 0 ms | 13.2 ms |
| 单图 1280×720（100 ms 时 abort） | 是 | 8 | **1** | 0 ms | 16.8 ms |
| 4 图 1280×720（200 ms 时 abort） | 是 | 0 | **32** | **4,855 ms** | 10.5 ms |
| 损坏的 PNG 字节 | — | — | — | — | 11.7 ms（客户端 `UnidentifiedImageError`） |

四条读法：

- **在解码阶段取消是有效的**：纯文本与单图的请求在 abort 之后只多收到 **1 个在途 chunk**，生成器立即结束。这个"1"不是缺陷，而是**流水线的在途步**——取消的语义是"不再产生新的步"，而不是"撤回已经算完的那一步"。
- **取消的语义是"不再产生新的步"**：abort 之后观察到的输出上限是**1 个在途 chunk**（12 组受控扫描里 10 组如此，另 2 组是"abort 早于首个 token"的情形，也只多出 1 个 chunk）。这个"1"不是缺陷，而是流水线的在途步——取消撤回不了已经算完的那一步。
- **上一轮观察到的极端反例没有复现**：首轮曾出现"4 张大图在预处理阶段 abort 后仍跑完 32 token（4.9 s 后才结束）"，随后的 12 组扫描（1/2/4 图 × abort 20/100/300/800 ms）里**取消后最多只多 1 个 chunk**，没有出现"取消后继续产出"。该极端观察因此降级为**未复现的一次性记录**（`UNVERIFIED`）。
- **扫描本身有一个方法缺陷**：300/800 ms 两组在 abort 时请求已经生成完 32 token（墙钟约 250 ms），这些行**不构成取消测试**，列出来是为了说明"abort 时刻必须相对请求实际时长选取"。

- **错误输入是"客户端失败"，不是引擎故障**：损坏的 PNG 在 processor 解码时就抛 `UnidentifiedImageError`，引擎没有进入该请求；随后的请求正常（11.7 ms）。
- **引擎在四种情形之后都健康**：健康检查的首 token 10.5–16.8 ms，与基线同量级（基线的 53.7 ms 含首次调用的预热）。

**资源回收：设备级显存给不出证据。** 一次单独的实验里连续提交 8 个"4 张大图"的重请求，全部在 50 ms 时取消，然后观测显存与引擎健康：

```
基线：设备空闲 6397 / 32109 MiB；块池 None
8 个重请求全部在 50 ms 时取消；立即空闲 6397 MiB，等待 3 s 后 6397 MiB（差 +0 MiB）
健康检查首 token 11.8 ms（基线 54.3 ms，含预热）；每个取消请求只多 1 个在途 chunk
```

**结论要分两层**：

- **设备级空闲显存在取消前后完全不变**——因为 KV 池在引擎初始化时就按 `gpu_memory_utilization` 预分配好了。**这意味着"用设备显存看是否泄漏"对预分配池是无意义的**（一个常见的错误判据）。
- **块级回收没有被直接观测到**：尝试读取引擎内部的块池计数器失败（返回 `None`）。所以"KV/队列资源被回收"目前只有间接证据——8 个取消请求之后引擎仍然健康（首 token 11.8 ms）、且没有陈旧输出（每个请求只多 1 个在途 chunk）。

这两条都标 `UNVERIFIED`：**没有观测到不等于没有回收，但没有证据就不能声称回收了。**



### 设计取舍

**为什么 KV 不能按图像哈希复用。** 4.7 的实测：位置值 = 网格坐标 + `current_pos`，而 `current_pos` 取决于前面有多少 token；同一张图在序列的不同位置得到不同的 RoPE 相位，KV 值因此不同。所以：
- **特征缓存（L1/L2）与序列位置无关** → 可以跨请求、跨位置复用；
- **KV 缓存与序列位置强相关** → 只能做前缀复用（5.2），一旦前缀里的图像位置发生变化，整段 KV 失效。

**为什么"缓存收益"必须以"省下的工作"为单位报告。** 本章的引擎实测里，首 token 从 33.8 ms 降到 12.1 ms 看起来是"快 2.8×"，但缓存开关的干净对照只有 4.9 ms（单图）。两个数字都对，但含义不同：前者包含冷启动，后者是稳态复用收益。**报告缓存效果要用"重复请求 + 开关对照"。**

**为什么慢模态需要准入而不是排队。** 排队模拟显示视频请求把文本的 p99 拖到 850 ms（ρ=1.2）。排队本身不降低总工作量，只是把延迟分配出去；要保护文本请求，必须在**准入**层面区分模态（限帧数/分辨率、独立队列、或给多媒体请求设并发上限）。这与 5.3 的调度策略、5.8 的失败路径是同一组机制。

## 工程实现 · 源码解析：引擎侧的缓存与准入

vLLM 0.29 的启动日志暴露了多媒体路径上的两级缓存与准入：

```
[encoder_runner.py:131] Encoder cache will be initialized with a budget of 16384 tokens,
                        and profiled with 1 image items of the maximum feature size.
[gpu_worker.py:625]     Available KV cache memory: 6.19 GiB
[kv_cache_utils.py]     GPU KV cache size: 45,072 tokens (Maximum concurrency 5.50x)
```

- **encoder cache（16384 token 预算）**：视觉塔输出的缓存，按特征大小计费；它决定"同一张图第二次请求时是否还要过塔"。
- **processor 缓存（`mm_processor_cache_gb`）**：像素张量的缓存，本章的引擎实测就是它的开关对照。
- **KV cache 与视觉无关地按 token 计费**：45,072 token 的容量，一个 16 帧视频（160 视觉 token + 文本）就占了 192 token。

调用约定上也踩了两个坑：

```
vLLM chat 的内容类型是 image_pil / image_url / video_url / …，
  不是 HF processor 的 image / video；
本地视频文件需要 allowed_local_media_path 才会被读取，
  否则报 RuntimeError: Cannot load local files without `--allowed-local-media-path`。
```

**两条链路的内容类型不通用**：HF 侧写 `{"type": "image", "image": PIL}`，vLLM 侧要写 `{"type": "image_pil", "image_pil": PIL}`，写错会得到 `VLLMValidationError: Unsupported chat content part type`。

## 工程实现 · 自己写一遍

`labs/L4/multimodal_serving.py`。缓存的核心是"键里放什么"：

```python
class FeatureCache:
    def l1_key(self, im, policy):                      # processor 产物
        return (img_hash(im), policy)
    def l2_key(self, im, policy, frames=None):         # 视觉塔载荷
        k = (self.rev, self.proc_sig, img_hash(im), policy)
        return k + (frames,) if frames is not None else k
```

引擎侧的测量只需要切换一个参数（并注意重复请求）：

```python
llm = LLM(model=d, limit_mm_per_prompt={"image": 4, "video": 1},
          allowed_local_media_path=outdir, mm_processor_cache_gb=cache_gb)
llm.chat([conv], SamplingParams(max_tokens=1))     # 首 token
llm.chat([conv], SamplingParams(max_tokens=1))     # 重复（缓存效应）
```

## 前沿

**引擎开始把"多模态缓存"做成显式的容量参数。** vLLM 0.29 的启动日志里有两条与视觉相关的预算：encoder cache 的 token 预算（16384）与 `mm_processor_cache_gb`（processor 产物的字节预算）。本章实测它们在重复请求上省下 4.9–9.0 ms（单图/双图），而纯文本请求完全不受影响。**这意味着多模态服务需要按"图像/视频的比例"来配置缓存容量**，而不是按请求数——这正是 5.3 的调度与 5.9 的容量规划要接的地方。

**慢模态的代价会外溢到其他请求，准入比排队更有效。** 排队模拟给出量级：ρ=1.2 时纯文本 p99 被拖到 850 ms（自身服务时长 16.5 ms）。真实引擎用 continuous batching 与 chunked prefill 缓解，但**根本手段是准入**：限制视频分辨率/帧数（4.5 的预算就是这里的杠杆）、给多媒体请求单独的并发上限、或把编码阶段与解码阶段解耦（encoder 独立限流）。SGLang 与 vLLM 在这条路线上的差异（多媒体输入的表达、encoder 调度）本章**没有测到**——vLLM 侧可测，SGLang 0.5.19 没有 Qwen3-VL 实现。

**取消与资源回收是缺失的一环。** 计划要求"在预处理、encoder、decode 三个阶段取消，插入慢视频与错误图像，比较有界与无界队列，验证特征/KV/CPU buffer/队列资源均被回收"。本章只做到"慢模态对文本长尾的模型化量化"，**三段取消与回收验证没有做**（见 STATUS 的 4.8 行）。它是 5.8 的失败路径在本章的延续，需要真实的异步客户端（`AsyncLLM.abort`）与显存/CPU 内存的逐阶段观测。

## 陷阱

1. **缓存有三层，键不同**：L1 processor（内容+尺寸）、L2 encoder（再加 revision/配置/帧采样）、L3 KV（序列位置相关）。
2. **KV 不能按图像哈希复用**：同一张图在不同序列位置得到不同的 RoPE 相位（4.7 实测）。
3. **"同图不同尺寸"与"不同图"一样是未命中**——尺寸策略在键里。
4. **把帧采样身份放进 L2 键会让像素相同但采样身份不同的帧不命中**（复用率与语义清晰之间的取舍）。
5. **缓存不省 prefill**：视觉 token 仍要进序列（单图 300、双图 600），预填充与 KV 写入照旧。
6. **首 token 与重复的差会把冷启动算成缓存收益**：单图 33.8→12.1 ms，但开关对照只有 4.9 ms。
7. **引擎实测要用"重复请求 + 开关对照"报告缓存效果**，不要用第一次请求的数字。
8. **SGLang 对照没有做成**：`sglang 0.5.19` 的 models 里没有 Qwen3-VL 实现；本章的引擎结论只来自 vLLM（不是两引擎对比）。
9. **HF 与 vLLM 的内容类型不通用**：HF 用 `image`/`video`，vLLM 用 `image_pil`/`video_url`，写错报 `VLLMValidationError`。
10. **本地视频文件需要 `allowed_local_media_path`**，否则 `RuntimeError: Cannot load local files`。
11. **多媒体请求直接吃 KV 容量**：16 帧视频（160 视觉 token）在 45,072 token 的池子里占 192 token。
12. **有界队列的收益要用丢弃率换**：ρ=1.2 时纯文本 p99 849.9→342.1 ms，但丢弃 10.5%；只报延迟不报丢弃率会得出错误的容量结论。另：**取消的实验证据见「取消：同一 API 在不同阶段行为不同」——预处理阶段的取消存在反例（UNVERIFIED）**。

## 自测题

<details markdown="1">
<summary>1. 同一张图被两个请求使用（内容相同、尺寸相同、文本不同），哪些层能命中？</summary>

- **L1 processor**：命中（键是内容+尺寸策略，与文本无关）。
- **L2 encoder**：命中（键同上，加 revision/配置/帧采样）。
- **L3 KV**：**不能命中**。视觉 token 与文本 token 一起构成序列，位置值随序列变化；文本不同 → 视觉段的 `current_pos` 不同 → RoPE 相位不同 → KV 不同。

所以"同图不同文本"的收益是**省下编码（10.41 ms + processor 0.69 ms）与 6.738 MiB 的重复计算**，而 prefill 与 KV 写入照旧。本章的引擎实测也印证了这一点：单图的重复请求从 33.8 ms 降到 12.1 ms（省的是视觉输入的处理），而不是降到"只算文本"的水平。

</details>

<details markdown="1">
<summary>2. 为什么说"缓存让请求快 2.8×"这句话不严谨？</summary>

因为它把两个不同的差混在一起了。本章引擎实测（单图）：

```
首 token 33.8 ms → 重复 12.1 ms      （2.8×）
缓存开 12.1 ms ←→ 缓存关 17.0 ms     （4.9 ms 的收益）
```

第一个差里包含**一次性成本**：kernel/分配器预热、encoder cache 首次填充、首次走多媒体路径的额外初始化。第二个差才是稳态下的缓存收益。

正确报告方式：**同一批请求、重复执行、只切换缓存开关**，并且明确"重复几次之后才计入稳态"。本章的做法是"每个组合调三次，取第二次为重复值"，虽然粗糙但方向正确。

</details>

<details markdown="1">
<summary>3. C 段的排队模拟给出了什么结论？</summary>

**成立的**：

- **慢模态对文本请求长尾的量化影响**：纯文本自身服务时长只有 16.5 ms，但在 ρ=1.2、5% 视频请求的混合下，它的 p99 是 849.9 ms（ρ=0.8 时 281.5 ms，3.0×）。一个 186 ms 的视频请求排在前面就会拖慢后面 16.5 ms 的文本请求。
- **有界队列（准入控制）的收益与代价**：ρ=1.2 时把等待队列限制到 8，纯文本 p99 从 849.9 → 342.1 ms（2.5×），代价是 10.5% 的请求被丢弃；ρ=1.0 时 567.9 → 496.0 ms、丢弃 3.5%；ρ=0.8 时两者几乎无差别。**过载越严重，准入的收益越大，但必须同时报丢弃率。**

**仍然成立的边界**：

- 它是**单服务器 FIFO 排队模拟**，服务时长来自引擎实测但排队模型不是引擎：真实引擎有 continuous batching、chunked prefill、抢占与 encoder 准入。
- 三方对比（预处理/encoder/decode 三段取消与资源回收）**仍未做**。

</details>

<details markdown="1">
<summary>4. 视频请求的"3.75 秒"这个正确答案说明了什么？</summary>

它说明这条链路端到端是通的：HF processor 按 fps 采帧并写入时间戳文本（4.7 的机制）、vLLM 读取本地 mp4（需要 `allowed_local_media_path`）、视觉塔编码、DeepStack 注入、LLM 生成答案。合成视频是 16 帧 4 fps，末帧时间戳 3.75 s，模型回答"视频里描述了3.75秒"✓。

但要注意它能证明什么、不能证明什么：

- **能**：多媒体输入在引擎里全程可用，时间戳文本确实被模型读到了。
- **不能**：样本量为 1，不能据此说"视频理解质量如何"；也不能区分"模型读的是文本时间戳"还是"从帧内容推断的时长"。要区分必须做 4.7 C 段那种受控干预——而那一章的实验因为基线未命中而没有结论。

**一次成功 + 一次失败（4.7 的干预）合起来说明**：多模态链路的"能跑通"和"能测出因果"是两件事。

</details>

<details markdown="1">
<summary>5. 如果让你给一个图文混排的服务做容量规划，本章的哪些数字可以直接用？</summary>

**可以直接用**：

- 视觉 token 账：单图 300（640×480）、双图 600、16 帧视频 160；纯文本 14。它们直接进入 KV 池（45,072 token 的池子里一个 16 帧视频占 192）。
- 服务时长量级：纯文本 16.5 ms、单图 33.8 ms、视频 16 帧 186 ms（首 token，vLLM 0.29，RTX 5090 D）。
- 缓存收益：重复的多模态请求省 4.9–9.0 ms（processor 段）；encoder cache 的预算决定塔内编码是否复用。
- 混合负载的尾延迟趋势：ρ 从 0.8 到 1.2，纯文本 p99 从 281 ms 到 850 ms。

**不能直接用**：

- 排队模型（单 worker FIFO）——真实引擎有 batching 与抢占；
- 视频的"帧数—时长"关系（只有 16 帧 4 fps 一个点）；
- SGLang 侧的数字（没有测）；
- 取消/错误输入下的资源回收行为（没有测）。**容量规划必须为"取消与失败"留余量**，而这一项本章是空白。

</details>

<details markdown="1">
<summary>6. 为什么"把 resize 挪到编码之后"能提高缓存复用率，但通常不划算？</summary>

**复用率**：L1 的键里包含目标尺寸。如果所有尺寸的原图都先编码、再在特征层面 resize/池化，那么"同图不同尺寸"的键就只剩内容哈希，复用率提高。

**为什么不划算**：视觉塔的算力与序列长度成正比，而 resize 要解决的就是"把塔内序列压到可接受的长度"（4.6 的实测：1280×720 是 880 token，640×480 是 300 token，ViT 时间 25.68 vs 9.90 ms）。把 resize 后移意味着**塔要处理原图分辨率**：一张 1280×720 的图按原分辨率进塔，序列长度是 4.5 倍，而且还可能撞上 `max_pixels` 的上界。

所以正确做法是**分层**：processor 层按尺寸缓存（L1 的键带上尺寸），而把"跨尺寸的复用"交给更高层（例如对同一张图的多种分辨率做多尺度特征缓存，只在需要时用）。**复用的粒度与算力的粒度要匹配**——这与 4.5 的"预算越小损失越大且不可逆"是同一条约束的两面。

</details>
