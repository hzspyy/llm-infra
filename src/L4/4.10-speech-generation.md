## 本章回答的三个问题

1. **多码本怎么组成音频？** 16 个 RVQ 码本、每个 2048 项，一帧到底是多少采样、多少字节、多少秒？
2. **码流怎么打包与拼接？** 手写打包/解包要做到什么程度，拼接队列在 chunk 边界上会发生什么？
3. **首包与首可播放为什么不是一回事？** 播放侧的时间线里有哪些事件，哪些量必须一起报？

本章**只完成了第 1、2 问的实测**（任务 A）：码本账、手写打包/解包、拼接队列与边界。任务 B–H（离线与真实 chunk 生成、播放事件、两运行时消融、F5-TTS NFE 扫描、DAC 训练、SFT 与 GRPO）**没有执行**，原因是一个明确的环境缺口：本机的 `transformers 5.17` 没有 `Qwen3TTSTokenizerV2Model`/talker 类，也没有 vLLM-Omni 与 SGLang-Omni。正文把已测与未测分开写，未测部分只给机制与源码级的说明。

## 机制拆解

### 码本账：16 个码本、80 ms 一帧、275 B/s

`Qwen/Qwen3-TTS-12Hz-0.6B-Base` 的两个配置给出了全部换算依据：

```
speech_tokenizer/config.json
  architectures              Qwen3TTSTokenizerV2Model
  encoder_valid_num_quantizers 16          decoder.codebook_size 2048
  input/output_sample_rate   24000          encode_downsample_rate 1920
  decoder.codebook_dim 512                 latent_dim 1024
config.json
  tts_model_type base    tts_model_size 0b6
  talker_config.num_code_groups 16    code_predictor 5 层（vocab 2048）
  speaker_encoder_config {enc_dim 1024, sample_rate 24000}
```

推导（A1 段实测输出）：

| 量 | 值 | 来源 |
|---|---|---|
| 一帧采样数 | 1920 | `encode_downsample_rate` |
| 一帧时长 | **80 ms** | 1920 / 24000 |
| 帧率 | **12.5 Hz** | 1 / 0.08 |
| 一帧码值数 | 16 | `encoder_valid_num_quantizers` |
| 每码值位宽 | 11 bit | log2(2048) |
| 一帧字节 | **22 B** | 16 × 11 = 176 bit → 22 B |
| 码率 | 2200 bit/s = **275 B/s** | 176 bit × 12.5 |
| PCM 码率 | 384 kbit/s | 24000 × 16 |
| 压缩比 | **175×** | 384000 / 2200 |

长度换算（同一张表，用于播放侧预算）：

| 时长 | 帧数 | 采样 | 码流字节 | PCM 字节 |
|---:|---:|---:|---:|---:|
| 1 s | 12.5 | 24,000 | 275 | 48,000 |
| 10 s | 125 | 240,000 | 2,750 | 480,000 |
| 60 s | 750 | 1,440,000 | 16,500 | 2,880,000 |

两个细节值得单独说：

- **模型名里的 "12Hz" 与配置算出的 12.5 Hz 差 0.5 Hz**（24000/1920 = 12.5）。本章按配置记录（12.5），并在正文标注这个差异——它以配置为准，命名是市场化的整数。
- **"一帧"有三个不同的对象**：LLM 侧的一个 token 步（16 个码值）、codec 侧的一个 80 ms 帧、播放侧的一个 buffer 块。三者在实现里经常被混用，`22 字节/帧`只对第二个成立。

### 手写打包/解包：11 bit × 16 → 22 字节

码流的最小单元是"一帧 16 个 11 bit 码值"。两种独立实现：

```python
def pack_frame_shift(codes, bits=11, n=16):        # 整数位移累加
    acc = 0
    for i, c in enumerate(codes):
        if not (0 <= c < (1 << bits)):
            raise ValueError(f"码值越界: {c}")
        acc |= (int(c) & ((1 << bits) - 1)) << (i * bits)
    return acc.to_bytes((n * bits + 7) // 8, "little")

def pack_frame_bits(codes, bits=11, n=16):          # numpy.packbits
    arr = np.array(codes, dtype=np.uint32)
    out = np.zeros(n * bits, dtype=np.uint8)
    for i in range(bits):
        out[i::bits] = (arr >> i) & 1
    return np.packbits(out, bitorder="little").tobytes()
```

实测（64 帧随机码）：

```
两种实现逐字节相同 = True；解包往返全部一致 = True
第一帧码 [1742, 1304, 1046, 552, 630, 83]… → 22 字节 cec6a8055164a7296822046609b44c9b7e406d12dfba
全 0 / 全 2047 / 混合边界：各 22 字节，往返一致 True
越界码值 2048 → ValueError: 码值越界: 2048
```

三条设计结论：

- **越界校验必须在打包前做**（`2048` 与 `-1` 都报 `ValueError`）。位运算会把越界值截断成合法值的低 11 位——**静默错误**，下游听不出来源。
- **11 bit 刚好用满 2048**（log2(2048) = 11.000），16 码本凑成 176 bit，字节对齐后 22 字节、**零浪费**。这解释了为什么码本大小选 2048 而不是 3000：位宽与字节对齐同时最优。
- **码流大小与内容无关**：静音帧照样占 22 字节（A4 实测 RMS=0 的 4 帧仍占 88 字节）。**"安静的部分可以少传"不成立**——码率恒定，这与 3.3 的 KV cache 按 token 计费是同一类账。

### 拼接队列：什么时候会有"爆音"

把码流按 chunk 喂给 vocoder/播放端，队列要做三件事：**凑够一帧、按 chunk 输出、处理尾包**。以 220 Hz 正弦按帧拼接，chunk = 4/8/16 帧：

| chunk | chunk 数 | 采样数 | 期望采样 | 拼接处最大跳变 |
|---:|---:|---:|---:|---:|
| 4 帧 | 10 | 76,800 | 76,800 | 2.88e-02 |
| 8 帧 | 5 | 76,800 | 76,800 | 2.38e-02 |
| 16 帧 | 3 | 76,800 | 76,800 | 2.38e-02 |

- **采样数精确等于 帧数 × 1920**，与 chunk 大小无关：这是 `encode_downsample_rate` 的直接后果，也是"有效采样点"账的基础。
- **拼接处跳变 2.4–2.9e-2 属于块边界舍入量级**（正弦相邻采样差本身就在这个量级），**不构成爆音**。

再人为**丢 1 帧**：

```
长度 74880 采样（少 1920 = 80 ms），间隙处跳变 2.94e-01（连续信号该处应≈0）
```

**跳变放大约 10 倍**（2.9e-2 → 2.94e-1）。丢帧同时造成两个后果：时长少 80 ms（音画不同步）与波形不连续（爆音）。**这两个后果必须分别报**：时间线正确但波形有爆音、或者波形平滑但被静音填充，都是不同的失败。

尾包：40 帧按 16 分块会剩 8 帧（15,360 采样）。**队列必须支持"最后一块不足一个 chunk"**，否则会丢 640 ms 音频，或者让播放端一直等超时（A4 的"空流应立即结束，而不是等超时"是同一类问题）。

### 边界与运行时缺口

| 情形 | 实测 |
|---|---|
| 空流（0 帧） | 0 采样、0 字节；播放端应立刻结束 |
| 单帧 | 1920 采样 = 80 ms、22 字节（首包可播放的最小单位） |
| 静音 4 帧 | RMS 0.0，仍占 88 字节 |
| 越界码值 -1 / 2048 | `ValueError` |

```

```

`Qwen3-TTS-12Hz-0.6B-Base` 的 `speech_tokenizer/config.json` 声明的类是 **`Qwen3TTSTokenizerV2Model`**，transformers 5.17 里没有这个类，本机也没有 vLLM-Omni / SGLang-Omni。因此**模型侧的 encode/decode 无法运行**；B–H 里只有时序部分用非自回归替代模型（VITS）完成，其余未执行。

**Base 的参考音频条件不能省略**：`config.json` 里有 `speaker_encoder_config`（24000 Hz、`enc_dim` 1024），checkpoint 的键前缀是 `speaker_encoder.*` 与 `talker.*`——也就是说 `tts_model_type: base` 的模型**依赖参考音频提取的说话人条件**；`CustomVoice` 变体才是文本直出。这一点决定了 A/B 段的所有生成实验都必须带固定参考音频与转写（本章没有跑到这一步，但配置已经说明了约束）。

### 生成时序：AR 与 flow/vocoder 是两种形状（替代模型实测）

主例 `Qwen3-TTS-12Hz-0.6B-Base` 在本环境没有可用的类（见陷阱一节），所以这里用计划里的**非自回归替代 TTS `facebook/mms-tts-eng`（VITS）**量文本到波形的时序。**数字属于替代模型，不能当作 Qwen3-TTS 的能力**：

| 文本（字符数） | 音频时长 | 生成耗时 | RTF | 每秒音频 |
|---|---:|---:|---:|---:|
| 短（43） | 2.62 s | 24.2 ms | 0.009 | 9.2 ms |
| 中（172） | 11.90 s | 33.2 ms | 0.003 | 2.8 ms |
| 长（454） | 25.71 s | 63.3 ms | **0.002** | 2.5 ms |

峰值显存 556 MiB（5 次取中位数）。

**两种架构的形状完全不同**，这是本章最该记住的一点：

| | 非自回归（VITS，本表实测） | 自回归 talker（Qwen3-TTS 的路线） |
|---|---|---|
| 生成方式 | 一次前向出整段波形 | 逐帧生成码本（每帧 80 ms） |
| RTF | **0.002–0.009** | 每帧一个解码步，**RTF ≈ 1**（4.11 的假设值） |
| 首可播放 | **等于全部生成时间**（24–63 ms），中间没有可播片段 | 约等于第一帧的时间，之后靠缓冲维持 |
| 代价 | 长文本要等全部算完（延迟随文本增长） | 首片段快，但持续输出受解码速度约束 |

**RTF 低与首可播放快不是同一件事**：VITS 的 RTF 极低却必须等整段算完才能出声；AR talker 的 RTF≈1 但可以边生成边播。用哪个指标评价 TTS 的实时性取决于架构，混用会得出相反的结论。

### 设计取舍

**为什么用 16 个码本而不是 1 个大码本。** 单码本的码率要么太低（音质差），要么码本过大（LLM 的词表爆炸）。RVQ 用 16 层残差量化分摊：第一层决定粗结构，后续层补细节。代价是**每帧要预测 16 个 token**（talker 的 `num_code_groups=16` 与 5 层 code predictor 就是为这个服务），以及**层层依赖**——第 k 层的输入包含前 k−1 层的量化误差。这直接决定生成侧的形状：AR talker + 一个专门预测剩余码本的 code predictor，而不是一次输出 16 个头。

**为什么码流便宜不代表播放简单。** 275 B/s 意味着网络传输几乎不是瓶颈（1 小时语音 990 KB）。播放侧的成本在**时间线**：解码、缓冲、调度，以及"什么时候能出声"。首包（网络层）与首可播放（播放层）相差一个 buffer 的时长——**这两个量必须分别报**，否则"低延迟"会被理解成"立刻出声"。

**为什么本章的结论停在 codec 层。** 码本账、位打包、拼接队列都是与模型无关的确定性算术，可以在没有权重的情况下核对到底（本章的做法）；而音质、可懂度、说话人相似度必须跑模型与听检。**把能确定的先确定，把不能确定的标清楚**——这也是 STATUS 里 4.10 行区分「已交付 A 与 B 的时序」与「其余未执行」的原因。

## 工程实现 · 源码解析：配置里的码本契约

本章没有可读的运行时源码（缺类），但配置本身就是契约：

```
config.json
  model_type          qwen3_tts
  tts_model_type      base                        ← 需要参考音频（speaker_encoder）
  tokenizer_type      qwen3_tts_tokenizer_12hz
  tts_bos/eos/pad_token_id  151672 / 151673 / 151671
  talker_config.num_code_groups 16               ← 每帧 16 个码值
  talker_config.code_predictor_config
      num_hidden_layers 5, hidden_size 1024, num_code_groups 16, vocab_size 2048
  speaker_encoder_config { enc_dim 1024, sample_rate 24000 }
speech_tokenizer/config.json
  architectures            ["Qwen3TTSTokenizerV2Model"]
  encoder_valid_num_quantizers 16
  input_sample_rate / output_sample_rate 24000
  encode_downsample_rate 1920 / decode_upsample_rate 1920
  decoder_config { codebook_size 2048, codebook_dim 512, latent_dim 1024, decoder_dim 1536 }
```

读法：

- **`encode_downsample_rate = decode_upsample_rate = 1920`**：编解码对称，一帧对应固定 1920 个采样点。这是"码流长度 ↔ 音频时长"的唯一换算系数（时长 = 帧数 × 80 ms）。
- **`encoder_valid_num_quantizers = 16` 与 talker 的 `num_code_groups = 16` 必须一致**：前者是 codec 编出来的层数，后者是 LLM 要预测的组数。不一致会让生成侧少预测若干层（音质下降但形状仍然合法）。
- **`tts_bos/eos/pad` 是特殊 token 而不是码值**：它们在 LLM 词表里（151671–151673），与 codec 词表（0–2047）分开。**码值与文本 token 不能混用同一套索引**——这类混用在实现里表现为"能生成但内容是噪声"。

## 工程实现 · 自己写一遍

```python
def pack_frame(codes, bits=11, n=16):        # 一帧 16 码值 → 22 字节
    acc = 0
    for i, c in enumerate(codes):
        if not (0 <= c < (1 << bits)):
            raise ValueError(f"码值越界: {c}")   # 校验必须在打包前
        acc |= (int(c) & ((1 << bits) - 1)) << (i * bits)
    return acc.to_bytes((n * bits + 7) // 8, "little")

class ConcatQueue:                            # 拼接队列
    def __init__(self, chunk_frames=8, frame_samples=1920):
        self.buf, self.chunk = [], chunk_frames * frame_samples
        self.frame_samples = frame_samples
        self.emitted = 0                      # 有效采样点账
    def push(self, frame_pcm):
        self.buf.append(frame_pcm)
    def pop_chunks(self, flush=False):
        pcm = np.concatenate(self.buf) if self.buf else np.zeros(0, np.float32)
        out = []
        while len(pcm) >= self.chunk:
            out.append(pcm[:self.chunk]); pcm = pcm[self.chunk:]
        if flush and len(pcm):                # 尾包不足一块也要发
            out.append(pcm); pcm = pcm[:0]
        self.buf = [pcm] if len(pcm) else []
        self.emitted += sum(len(b) for b in out)
        return out
```

长度账（必须能对上）：

```
帧数 × 1920 = 采样数；采样数 / 24000 = 秒数
码流字节 = 帧数 × 22；码流字节 / 275 ≈ 秒数
```

## 前沿

**TTS 的接口正在从"文本→波形"变成"文本→码流→流式播放"。** 本章实测的码率（275 B/s、22 字节/帧、80 ms/帧）说明码流本身很便宜，瓶颈在**播放时间线**：首包、首可播放、buffer 阈值、underrun。这也是 vLLM-Omni / SGLang-Omni 这类运行时出现的原因——它们要解决的不是码本算术，而是"AR 生成 + codec 解码 + 播放"三段流水线的调度与背压。

**codec 与 vocoder 的训练不能由 TTS SFT 代替。** `speech_tokenizer` 是独立子模型（650.7 MiB 的 `model.safetensors`），它的 RVQ 码本、commitment loss、重建目标与 TTS 的 next-token SFT 是完全不同的训练问题（计划中的 E 段要读 DAC 的 `scripts/train.py`，D 段要扫 F5-TTS 的 NFE）。**"TTS 微调做好了"不等于"codec 训好了"**：前者只更新 talker/SubTalker，后者决定码本本身的质量上限。

**参考音频条件是 Base 模型的硬约束。** `tts_model_type: base` 加上 `speaker_encoder_config`（24000 Hz、enc_dim 1024）与 checkpoint 里的 `speaker_encoder.*` 键，说明 Base 的推理必须带参考音频与转写；`CustomVoice` 才是文本直出。**省掉参考音频不是"简化流程"，而是换了一个模型契约**——这也是为什么 A/B 段的生成实验必须固定参考音频。

## 陷阱

1. **"12Hz" 与配置算出的 12.5 Hz 差 0.5 Hz**（24000/1920）。按配置记录换算，不要用名字做算术。
2. **一帧有三个含义**：LLM 的一个 token 步（16 码值）、codec 的 80 ms 帧、播放的 buffer 块。`22 字节/帧`只对 codec 帧成立。
3. **越界码值必须在打包前校验**：位运算会静默截断成合法值。
4. **码流大小与内容无关**：静音帧同样 22 字节。
5. **丢帧的两个后果要分开报**：时长少 80 ms（同步问题）与波形跳变 2.94e-1（爆音）。
6. **尾包不足一个 chunk 必须 flush**，否则丢音频或让播放端等超时。
7. **`encoder_valid_num_quantizers` 与 `num_code_groups` 必须一致**，不一致时形状合法但内容错。
8. **特殊 token（tts_bos/eos/pad，151671–151673）不是码值**（0–2047）：混用同一套索引会生成噪声。
9. **Base 依赖参考音频**（`speaker_encoder.*`）；把它当文本直出会得到错误的说话人。
10. **首包 ≠ 首可播放**：两者相差一个 buffer 的时长，必须分别报。
11. **本环境没有 `Qwen3TTSTokenizerV2Model` / vLLM-Omni / SGLang-Omni**：模型侧 encode/decode 未运行；B 的时序部分用非自回归替代模型（VITS）完成并明确标注，其余 B–H 未执行——正文里的相关结论要么是机制级说明，要么是替代模型结果。
12. **合成正弦上的拼接跳变（2.4e-2）不是爆音证据**：真正的爆音要在真实 vocoder 输出上测，并配合听检。

## 自测题

<details markdown="1">
<summary>1. 一段 10 秒的语音，Qwen3-TTS 的码流有多大？一帧对应多少采样？</summary>

由 `encode_downsample_rate = 1920` 与 `output_sample_rate = 24000`：

- 一帧 = 1920 采样 = 80 ms → 帧率 12.5 Hz；
- 10 s → 125 帧 → 采样 125 × 1920 = 240,000（= 10 × 24000 ✓）；
- 码流 = 125 帧 × 22 字节 = **2,750 B**（PCM 同长度是 480,000 B，压缩 175×）。

**核对式**：`采样数 = 帧数 × 1920`、`秒数 = 帧数 × 0.08`、`字节 = 帧数 × 22`。三个式子必须同时成立，任何一个对不上就说明帧的边界错了。

</details>

<details markdown="1">
<summary>2. 为什么 16 个码本不打包成 176 bit 的整数边界，而是 22 字节？</summary>

因为 176 bit = 22 字节**恰好整除**（176 / 8 = 22）。这不是巧合，而是码本大小选择的结果：2048 = 2¹¹，11 × 16 = 176，176 能被 8 整除。

换句话说：**码本大小 2048 同时满足"接近 2048 个码值"与"整字节对齐"**。如果码本大小是 3000（12 bit），16 × 12 = 192 bit = 24 字节，也能整除但每帧多 2 字节（+9% 码率）；如果是 1500（约 10.55 bit），就必须引入跨字节的非对齐或填充。

设计含义：**码本大小不是一个纯质量参数，它同时决定打包方式的简洁性**。本章的两种实现（位移累加与 packbits）能逐字节一致，前提就是 11 bit 的固定位宽。

</details>

<details markdown="1">
<summary>3. 拼接队列里丢了一帧，会有哪两个后果？分别怎么测？</summary>

**后果一：时长少了 80 ms**（1920 采样 / 24000 Hz）。测法：累计输出采样数与 `帧数 × 1920` 对账——本章实测丢 1 帧后是 74,880 而不是 76,800。

**后果二：波形在拼接处不连续**（听感上是爆音）。测法：在拼接点比较相邻采样差，与"正常拼接"的差做对照——本章实测正常拼接最大跳变 2.4e-2，丢帧处 2.94e-1（约 10 倍）。

**为什么必须分开报**：两种失败可以独立出现。用静音填充丢掉的帧 → 时长正确、波形不连续；移动后续样本对齐时长 → 波形平滑但音高/节奏被压缩。只报其中之一会漏掉另一半问题（这与 4.7 的"位置错了不报错"是同一类教训：**形状合法不等于语义正确**）。

</details>

<details markdown="1">
<summary>4. 为什么"码流只有 275 B/s"不能推出"播放很容易"？</summary>

因为码流大小只决定**网络传输**这一段，播放是否顺畅取决于时间线：

| 事件 | 含义 | 由什么决定 |
|---|---|---|
| 首包 | 收到第一块数据 | 网络 + 服务端 prefill |
| 首可播放 | 累计样本够填满播放缓冲 | buffer 阈值（如 200 ms）+ 解码速度 |
| 播放开始 | 声卡真正出声 | 播放器调度 |
| underrun | 缓冲被抽空 | 生成速度 < 播放速度 |

275 B/s 让"传输"几乎不花时间，但**生成速度**（AR talker 的 token/s × 16 码值/帧）与**解码速度**（vocoder）才是决定 underrun 的量。而且**首包可以很快而首可播放很晚**（例如生成比播放慢）：此时用户等的是缓冲，不是网络。

所以 A/B 段的验收要求是"首包、首可播放、播放开始、underrun、RTF 一起报"——本章**没有跑到这一步**，只给出了码率与帧长的账。

</details>

<details markdown="1">
<summary>5. 为什么 Base 模型不能省略参考音频？</summary>

看配置与权重键：

- `config.json` 的 `tts_model_type = base`，且有 `speaker_encoder_config {enc_dim 1024, sample_rate 24000}`；
- checkpoint（478 个键）的前缀是 `speaker_encoder.*` 与 `talker.*`。

也就是说 Base 的推理路径是"参考音频 → speaker_encoder → 说话人条件 → talker 生成码流"。`CustomVoice` 变体才是文本直出（说话人信息来自模型内部的映射，配置里体现为 `spk_id`/`spk_is_dialect`）。**省掉参考音频不是简化，而是换了一个模型契约**：Base 在没有条件时要么报错，要么生成一个不属于任何目标说话人的声音。

工程含义：所有生成实验必须**固定参考音频与转写**（可重复、可对比），并把参考音频的时长/采样率记进实验清单——参考音频是输入的一部分，不是可选项。

</details>

<details markdown="1">
<summary>6. 本章的结论哪些可以迁移到真实 TTS 服务，哪些不能？</summary>

**可以迁移（与模型无关的确定性算术）**：

- 码本账：16 × 2048 × 11 bit = 22 字节/帧，80 ms/帧，275 B/s，压缩 175×；
- 与帧数/采样数/秒数之间的三个换算式；
- 打包/解包的位序与越界校验（两种独立实现逐字节一致）；
- 拼接队列的采样数对账、尾包 flush、丢帧的两个后果及其测法。

**不能迁移（未测）**：

- 音质、可懂度、说话人相似度（需要真实 vocoder 输出与听检）；
- 首包/首可播放/underrun/RTF（需要 AR talker + vocoder + 播放端）；
- 两运行时（vLLM-Omni / SGLang-Omni）的调度差异；
- F5-TTS 的 NFE—质量曲线、DAC 的训练流程（E/F/G 段的内容）。

**判据**：本章给出的是"码流层的账"与"队列层的正确性"，它们是真实现服务的前提，但**不是服务结论**。下一步要做的第一件事是把 `decode(encode(x))` 的采样数与 `帧数 × 1920` 对账——这一步通过之后，才谈得上首包与 RTF。

</details>
