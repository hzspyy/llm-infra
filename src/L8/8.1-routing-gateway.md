## 本章回答三个问题

1. **缓存亲和与排队均衡什么时候冲突？** 把请求都送给"已经缓存了这段前缀"的副本，会让它的队列比别的副本长；实测里亲和策略在 2048 token 前缀上的尾时延比最短队列差 18 倍。
2. **全局缓存目录怎样保持有效？** 网关靠 worker 发布的 KV 事件维护"哪台机器有哪个块"。订阅起点、驱逐事件和链式哈希重建决定了这个目录是精确的还是过期的。
3. **难度路由怎样约束质量？** 小模型预检 + 大模型兜底在真实 GSM8K 上省不省钱，取决于"重跑子集的批处理效率"和"升级判据的召回"，而不是直觉。

::: note 本章的立场
命中率是过程指标。网关的判据只能是**在任务质量约束下的端到端时延与成本**。本章先用两个真实副本测出"多命中是否真的更快"，再检查事件目录在什么条件下会骗人，最后用真实评测回答级联路由值不值。
:::

## 机制拆解与推导

### 1. 亲和与排队的盈亏平衡

把一次请求路由到 worker $w$ 的预期首字时延写成两项之和：

$$\text{TTFT}_w = \underbrace{q_w \cdot \bar{S}_w}_{\text{排队}} + \underbrace{T_{\text{base}} + (P - L_w)\alpha}_{\text{prefill}}$$

其中 $q_w$ 是在途请求数、$\bar{S}_w$ 是它们剩余的平均服务时间、$L_w$ 是该副本已缓存的前缀长度、$\alpha$ 是每 token 的 prefill 时间。热副本与冷副本的临界条件是

$$q_{\text{hot}} \cdot \bar{S} < L \cdot \alpha$$

对 Qwen3-1.7B 在 L40S 上，$L=2048$ 的前缀大约值 $L\alpha \approx 40\text{–}80$ ms（本次 0.3× 档的 TTFT p50 是 61 ms，可以当作同量级参照）。而一个正在解码的请求占住副本的时间是它的**剩余输出时间**：输出 32 token、TPOT ~10 ms 时约 0.3 s。于是

$$q_{\text{threshold}} \approx \frac{L\alpha}{\bar{S}} \approx \frac{0.05}{0.3} < 1$$

**热副本队列里只要还有一条请求在解码，亲和带来的收益就已经被吃掉了。** 这个估计不需要精确：它说明临界队列阈值是个位数——本次实验的 8 QPS 负载下两台副本的队列深度都不到 2，所以三种策略的 p50 几乎一样（0.019–0.067 s），差别只在命中和尾部。要看到亲和显著获胜，需要把负载推到队列开始堆积，这正是 8.4 混合负载要做的事。

### 2. 缓存命中需要容量、时间与身份三者同时成立

一次前缀命中要求：

1. **容量**：这段前缀的 KV 还在显存里（没被驱逐）；
2. **时间**：它是在这次请求之前被写入的（同一副本上）；
3. **身份**：模型权重、量化格式、adapter revision、KV layout、位置编码都一致。

第 3 条是网关最容易出错的地方。同一个 prompt 文本在不同 adapter 或不同量化版本下产生的 KV 完全不同；网关的前缀键必须包含完整身份元组，而 vLLM 的 KV 事件里 `BlockStored.lora_name`、`extra_keys` 和 `group_idx` 正是为此存在的字段。本次实验只用单模型单 adapter，所以身份维度没有进入实验，但它是生产环境里的真实失败面。

### 3. 目录为什么会过期

网关的目录有三个必然后果：

- **订阅起点晚于缓存建立**：网关启动时，worker 的显存里已经有块了。这些块永远不会再发一次 `BlockStored`，除非网关触发一次全量重建。本次每个 case 都新建网关，所以目录从空开始——这直接反映在预测值上（见第 4 节）。
- **驱逐事件多于写入事件**：实测 `BlockStored ≈ BlockRemoved`（例如 ratio25/RR 一次运行里 16194 存 / 16193 删），说明 KV 在持续换出。目录必须真的消费 `BlockRemoved`，否则会持续高估命中。
- **链式哈希的上下文**：vLLM 的块身份是链式的（第 $i$ 块的哈希含父块哈希），所以网关重建自己的键时需要知道父链。当 `BlockStored` 的 `parent_block_hash` 指向一个网关没见过的哈希时，重建会断链——本次运行里 `unknown_remove` 有 5 163–10 837 条，正是这个现象的计数。

## 工程实现：源码解析与设计取舍

### SGLang 网关：两套策略，各自处理"亲和 vs 负载"

固定 commit `5c2de3f` 的 `sgl-model-gateway/src/policies/` 下同时存在两条路线：

**`cache_aware.rs`（完整基数树路线）**。`CacheAwarePolicy` 为每个 (pool, model) 维护一棵近似基数树，配置项包括 `cache_threshold`、`balance_abs_threshold`、`balance_rel_threshold`、`eviction_interval_secs`。路由主循环先判负载是否失衡（`:412-413`）：

```rust
let is_imbalanced = max_load.saturating_sub(min_load) > self.config.balance_abs_threshold
    && (max_load as f32) > (min_load as f32 * self.config.balance_rel_threshold);
if is_imbalanced {
    return self.select_worker_min_load(...);
}
```

负载均衡时才算缓存匹配率 $= \text{matched\_char\_count} / \text{input\_char\_count}$，`match_rate > cache_threshold` 才走"缓存命中路径"（按树里记录的 URL 选中该 worker），否则退回"最小负载"（`:444` 与 `:493`）。**它是字符级而不是 token 级**：网关在转发前不做 BPE，用很小的边界误差换掉整轮 tokenize 的开销。近似树还带周期性 LRU 驱逐（`evict_cache`，`:301`），避免目录无界增长。

**`prefix_hash.rs`（一致性哈希路线）**。文件开头写明它是"A lightweight alternative to the full radix tree cache_aware policy"。它取前 `prefix_token_count` 个 token 做 xxh3 哈希（`:104-110`），用带界负载的一致性哈希环选副本，分支枚举是 `RingHit / LoadBalanceWalk / FallbackLeastLoad`（`:64-88`）。这条路线的代价是**粒度固定**：前缀只有前 N 个 token 参与哈希，第 N 个 token 之后的差异不影响归属；收益是不维护树、不消费驱逐事件、无内存增长。

两条路线的接口一致（`impl LoadBalancingPolicy for ...`，`cache_aware.rs:386`、`prefix_hash.rs:225`），所以能在同一网关里按负载特征切换。这个设计说明了一件本章实验也印证的事：**亲和目录的精度与它的维护成本是一对取舍，不是越精确越好。**

### 设计取舍

| 选择 | 代价 | 依据 |
|---|---|---|
| 网关用字符/字节前缀而不是 token id | 边界误差、`match_rate` 与引擎的块命中不完全一致 | 转发路径不能承担每请求 tokenize；`cache_aware.rs` 明确用 `matched_char_count` |
| 近似树 + 周期驱逐，而不是精确镜像 | 会短时高估命中 | 精确镜像要消费全部驱逐事件，且订阅起点问题无法自愈 |
| 负载失衡时直接放弃亲和 | 短期命中下降 | `is_imbalanced` 用绝对差 $\times$ 相对比双阈值，避免低负载下的抖动 |
| 一致性哈希（`prefix_hash`） | 前缀只有前 N token 参与 | 无状态、无驱逐、无内存增长，适合超大规模副本数 |
| 本章的 mini 实现用 token 级链式哈希 | 与 SGLang 的字符级不同，命中数不可直接对比 | 本项目要能和 vLLM 的真实块哈希对齐（见 mini 实现） |

## 工程实现：mini 实现

`labs/L8/request_router.py` 实现三种策略、两类目录和可重放决策日志：

::: fold labs/L8/request_router.py 链式块键与精确目录
```python
def block_key(parent: bytes, tokens: Sequence[int]) -> bytes:
    """块键 = H(父块键, 本块 token 序列)。与 vLLM 的链式块哈希同语义:
    同样的 token 片段出现在不同位置不会被误判为同一块。"""
    h = hashlib.sha1()
    h.update(parent)
    h.update(struct.pack("<I", len(tokens)))
    for t in tokens:
        h.update(struct.pack("<I", t))
    return h.digest()

class EventDirectory:
    """精确目录: 由真实 KV 事件驱动, 消费 BlockStored / BlockRemoved / AllBlocksCleared。"""
    def on_block_stored(self, worker, block_hashes, token_ids, block_size=None,
                        parent_block_hash=None):
        ...
        parent = hmap.get(parent_block_hash, ROOT_KEY) if parent_block_hash is not None else ROOT_KEY
        for i in range(len(block_hashes)):
            key = block_key(parent, token_ids[i*bs:(i+1)*bs])
            cached.add(key); hmap[block_hashes[i]] = key; parent = key
```
:::

`gateway.py` 是一个真实的 aiohttp 网关：对上层暴露 OpenAI 兼容流式接口，对下层按策略选 worker，并把每个决策（候选、队列、预测命中、最终选择）通过响应头 `x-lb-worker` / `x-lb-predicted-hit` 回给客户端；后台用 ZMQ SUB 订阅每个 worker 的 KV 事件流（`(topic, seq, msgpack(EventBatch))`），支持注入丢事件、延迟与重复。

### 8.1-A/B 策略对比

150 条请求、8 QPS、输出 32 token；共享前缀比例 0 / 25% / 75%，前缀长度 2048（单轴扫描），再在 75% 上补 4096 与 128 两点。命中 token 来自两个 worker `/metrics` 的 `vllm:prefix_cache_hits_total` 前后差值（真实累计量），请求数来自 `/metrics` 的 `prefix_cache_queries_total`。

| 75% / 2048 | round_robin | 186 368 | 312 000 | 0 | 0.025 | 0.061 |

读法（每条都是实测，不是模型推算）：

1. **没有共享前缀时，缓存亲和无从发挥**：三种策略的命中都是 0，查询 312 000 全部落空。0% 档 round_robin 的 p99 = 7.498 s 是本次唯一的异常尾，出现在运行最开始（首请求触发编译），不能当成策略差异。
2. **亲和策略不是恒优**：75%/2048 上最短队列命中 309 600 token（占全部 prompt token 的 99.2%），而 prefix_aware 只有 215 344，且 p99 差 18 倍。原因是 KV 容量足够容纳全部 16 个热前缀，最短队列把热前缀在**两台**上各养了一份，而亲和策略把全部流量压在一台上，另一台的命中恒为 0。
3. **前缀越长，亲和的相对收益越大**：4096 上 prefix_aware 反超（411 536 vs 382 464），因为单个前缀的 KV 占用翻倍、跨副本复制两份的代价上升。
4. **网关预测值系统性低于真实命中**：prefix_aware 预测 256–83 856，真实 17 840–411 536。这是目录冷启动造成的——每个 case 新建网关，而 worker 的缓存从上个 case 继承，所以"预测不到"的块其实在显存里。这个偏差不是算法错误，而是**订阅起点**问题。

### 8.1-C 事件目录与丢失注入

固定 75% / 4096 配置，只跑 prefix_aware，分别用"事件目录"和"近似目录"（只记网关自己发过的请求，不知道驱逐），并注入 0 / 20% / 50% 的事件丢弃：

| 目录 | 丢事件 | 真实命中 token | 查询 token | 网关预测命中 | TTFT p50 | p99 |
|---|---:|---:|---:|---:|---:|---:|
| 近似 | 0% | 419 728 | 619 200 | 405 504 | 0.032 | 0.117 |
| 近似 | 20% | 419 728 | 619 200 | 405 504 | 0.033 | 0.118 |
| 近似 | 50% | 419 728 | 619 200 | 405 504 | 0.035 | 0.118 |
| 精确事件 | 0% | 395 200 | 615 072 | 100 288 | 2.197 | 7.986 |
| 精确事件 | 20% | 419 728 | 619 200 | 12 288 | 0.034 | 0.116 |
| 精确事件 | 50% | 419 728 | 619 200 | 51 088 | 0.033 | 0.116 |

**这里的结论是一个负结果，必须原样保留**：在这个负载下，注入 20%/50% 的事件丢失**没有改变真实命中**（三行都是 419 728）。原因是亲和在 warmup 之后已经收敛到单一副本，路由决策对目录的细节不敏感——丢事件只影响"预测值"，不影响"选谁"。

关于目录有效性，实测到的三条事实：

1. **事件确实在流动**。一次 ratio25/RR 运行里，`w0` 收到 215 个批次、应用 8 630 条事件，`w1` 收到 209 批、应用 7 986 条，**序列号缺口为 0**。这两个数字也说明订阅端没有丢包。
2. **驱逐是常态**。`BlockStored` 与 `BlockRemoved` 数量几乎相等（16 194 / 16 193），目录必须真的消费删除事件。
3. **断链与迟到订阅有明确计数**。`unknown_remove` 达到 5 163–10 837 条，来自两类情况：网关订阅前已经存在于显存里的块被删除；以及 `BlockStored` 的 `parent_block_hash` 指向网关没重建过的父块。**这解释了预测值为何系统性偏低**，也说明"订阅即精确"是个错误的假设。

**没有做成的部分**：vLLM 0.29 的 OpenAI 兼容 `/v1/completions` 不返回逐请求的 `cached_tokens`（`--enable-prompt-tokens-details` 只在另一套 generate 接口里），所以"预测命中但实际未命中"的假阳性只能按窗口聚合核对，无法逐请求判定。计划里"注入延迟与 worker 重启、比较精确事件与近似前缀索引"的完整矩阵因此只完成了丢事件一维；延迟、重复与真实重启保留为未完成。

### 8.1-D GSM8K 级联路由

固定题集（`openai/gsm8k` test 前 400 题，固定顺序），前 150 题做标定、后 250 题做评测；小模型 `Qwen3-1.7B`、大模型 `Qwen3-4B`，贪心解码、`max_tokens=768`、关前缀缓存，置信度取生成答案的均摊 token logprob。阈值在标定集上按"升级率 ≤ 35% 时准确率最高"选取，冻结后不再改动。

| 运行方式 | 评测集准确率 | 升级率 | 评测集 GPU-秒 | 输出 token |
|---|---:|---:|---:|---:|
| 全部小模型 | 0.804 | 0 | 5.06 | 73 347 |
| 全部大模型 | **0.904** | 0 | **10.08** | 64 705 |
| 级联路由 | 0.848 | 0.24 | **11.05** | 90 667 |

冻结阈值 `-0.0746`，标定集上升级率 0.34、准确率 0.88。

**这个结果是负的：级联既没有更准，也没有更便宜。** 它比全量大模型多花 9.6% 的 GPU 秒，却低了 5.6 个百分点。两个原因都是真实机制：

1. **重跑子集丢掉批处理效率**。大模型在全量 400 题上跑 16.08 s（0.040 s/题），在 60 题升级子集上跑 5.99 s（**0.0998 s/题**）——子集小、并发低，单位成本涨了 2.5 倍。级联的账必须把这段低效算进去。
2. **平均 logprob 作为置信度的召回不够**。250 题里有 28 题"小模型答错但没被升级"，10 题"升级了但大模型也答错"；升级的 60 题只挽回了部分错误。标定集上"升级率 34% 换 +8.7 个点"，到评测集变成"升级率 24% 换 +4.4 个点"。

计划要求"路由拒绝、升级模型和错误答案均计入；不以牺牲质量获得的低成本宣称更优"。按实测，这次级联既没牺牲质量也没拿到成本优势——它是一个应当在正文里明确写出的负面结论，而不是需要调参掩盖的结果。

## 前沿

1. **精确块哈希路由。** llm-d 把请求调度做成 Gateway API 的 Endpoint Picker（EPP），用 `prefix-cache-scorer` 给每个 pod 打分，并区分"估算"与"精确"两种 scorer：估算版只看请求前缀，精确版消费引擎上报的块级事件。这正好对应本章的两类目录。参考：llm-d 的 [Prefix-Cache Aware Routing](https://llm-d.ai/docs/architecture/advanced/kv-management/prefix-cache-aware-routing) 与 [Gateway API Inference Extension](https://gateway-api-inference-extension.sigs.k8s.io/)。
2. **无树的一致性哈希路线。** SGLang 网关在 `prefix_hash.rs` 里给出"前 N token 的 xxh3 一致性哈希 + 有界负载"作为完整基数树（`cache_aware.rs`）的轻量替代；两者共用 `LoadBalancingPolicy` 接口，可按副本规模切换。
3. **级联与路由的理论边界。** RouteLLM（[arXiv:2406.18665](https://arxiv.org/abs/2406.18665)）用偏好数据学路由器，把"用便宜模型保住多少前沿质量"写成可优化目标；Cascadia（[arXiv:2506.04203](https://arxiv.org/abs/2506.04203)）进一步把级联的**部署**与**路由**联合优化，明确指出子集重跑的批处理效率是级联收益的关键变量——本章 8.1-D 测到的"子集单位成本涨 2.5 倍"正是这个变量。
4. **服务状态的跨请求复用。** Pensieve（[arXiv:2312.05516](https://arxiv.org/abs/2312.05516)）把 KV 状态在请求间显式建模复用；[LLM Inference Serving 综述](https://arxiv.org/abs/2407.12391) 与 [GPU 数据中心调度综述](https://doi.org/10.1145/3638757) 覆盖了本章没有展开的集群调度与隔离部分。

## 陷阱

1. **把命中率当目标。** 本次 75%/2048 上亲和策略命中 215 344 token，比最短队列少 30%，尾部还差 18 倍。命中是手段。
2. **假设网关启动时目录是空的、worker 缓存也是空的。** 二者不同步：本次每个 case 新建网关但 worker 缓存继承，预测值只有真实命中的 4%–20%。
3. **忘记 `BlockRemoved`。** 实测写入与删除数量几乎相等；只消费 `BlockStored` 的目录会持续高估。
4. **同名模型不等于同一份缓存。** 量化格式、adapter、KV layout 不同，块就不同；身份元组不能省。
5. **级联路由不能只报"节省百分比"。** 本次级联既不省也不准；子集重跑的批处理效率必须计入，否则结论会偏向级联。
6. **用不同 case 之间的命中数做绝对比较。** 同一个 worker 进程在多个 case 间持续运行，后面的 case 继承了前面的缓存；跨 case 只能比同一起跑线的量，或者每次重启副本。

## 自测题

::: fold 1. 为什么在 75% 共享前缀、2048 token 的配置下，最短队列反而比缓存亲和命中更多？
**答案：**
因为 KV 容量足够装下全部 16 个热前缀。最短队列把请求摊到两台副本上，两台都会把热前缀缓存下来，之后每一条共享请求都能命中；缓存亲和把全部流量压到一台，另一台的命中恒为 0，而请求本身也没有更多命中可拿。亲和的优势只有在容量不足、需要靠"专机专前缀"避免互相驱逐时才出现——本次 4096 token 前缀就更接近这个条件。
:::

::: fold 2. 网关的预测命中为什么系统性地低于引擎的真实命中？
**答案：**
因为目录的订阅起点晚于缓存的建立。网关是每个 case 新建的，而 worker 进程与它的 KV 缓存跨 case 连续存在；订阅前已经写入显存的块不会再补发 `BlockStored`，网关自然预测不到。实测里 `unknown_remove`（删除一个网关没见过的块）有几千条，正是同一现象的另一面。生产网关需要用"新 worker 加入即从空目录开始、并接受一段低估期"或"触发一次全量重建"来处理，而不是假设订阅即精确。
:::

::: fold 3. 本次注入 20%/50% 的事件丢失，为什么真实命中没有变化？
**答案：**
因为路由决策已经收敛到单一副本，丢事件只改变了"预测值"，没有改变"选谁"。这说明一个负结果：当工作负载的亲和性足够强、目录的预测误差不影响排序时，目录精度不是瓶颈。要验证丢事件的危害，需要构造"两台副本命中接近、必须逐请求比较"的负载，或者让驱逐频繁到预测与真实持续背离。
:::

::: fold 4. 级联路由为什么可能比"全部用大模型"更贵？
**答案：**
因为两段成本相加，而第二段的单位成本更高。本次全量大模型在 400 题上 0.040 s/题，而升级子集只有 60 题、并发低，单位成本 0.0998 s/题。级联付了"小模型全量跑一遍"的固定成本，再用更高的单价重跑一部分题目；只有升级判据足够准（把真正难的题挑出来）且子集规模足够大（保住批处理效率）时，总成本才会低于直接上大模型。
:::

::: fold 5. 网关用字符前缀做匹配，而引擎按 token 块缓存。这会产生什么错误？
**答案：**
两边的切分边界不同。字符匹配率是个连续值，块命中是离散的（整块命中或不命中），所以 `match_rate > cache_threshold` 可能选中一个只匹配了半个块边界的副本，实际命中会低于预测。反过来，前缀里含多字节字符时字符数与 token 数不成比例，同一个阈值在不同语言上的严格程度不同。SGLang 选择接受这个误差，是因为网关在转发路径上做完整 tokenize 的代价更高。
:::
