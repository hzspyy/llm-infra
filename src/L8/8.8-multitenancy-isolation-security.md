## 本章回答三个问题

1. **租户身份如何贯穿缓存和 adapter？** 请求上的租户、会话与 adapter revision 必须在**缓存键、调度配额和执行归属**三处都出现。本章实测的一件事是：vLLM 0.29.0 的前缀缓存把 LoRA 的**名字**进哈希（`_gen_lora_extra_hash_keys` 只返回 `lora_request.lora_name`），因此同一个名字下就地换权重，缓存身份不变。
2. **共享资源怎样造成干扰？** 在同一个引擎里，两类请求进来之后共享同一份算力：模拟里把总速率固定后按在途请求数均分，租户 A 的 p50 从独跑时的 0.107 s 涨到 1.5–2.8 s；把 B 的份额从 0 加到 1.0，A 的 p99 在 4.69 s 与 39.7–67.4 s 之间摆动。A 的并发上限（配额）只把 p50 从 2.76 s 压到 2.47 s，**配额并不改变"进来之后按份共享"这一事实**。
3. **隔离机制各自提供哪些边界？** 应用层配额限制的是"谁进来"，进程隔离限制的是"谁和谁共享同一份状态"。本章在引擎侧对比了共享单实例与两租户各自一个实例的部署，并核对 MIG/MPS 在本机的可用性：MIG 两台机器都没有可切分设备，MPS 在共享机器上未启用，因此这两条路径只记录机制与条件。

::: note 本章的边界
多租户的**真实系统**实验集中在单机单卡、两个合成租户与一个公开 LoRA adapter 上。MIG/MPS 不做实验（硬件与权限不支持，且不修改共享机器）；Kubernetes 的租户边界（NetworkPolicy、ResourceQuota、RBAC）不在本机范围内，只在 8.2 的字段映射基础上说明职责分工。所有输入都是合成 token 与合成租户，没有使用真实用户数据。
:::

## 机制拆解与推导

### 1. 缓存身份的四个字段

把缓存键拆成"逻辑身份"和"必须校验的物理身份"两半（8.6 已展开），多租户在逻辑身份上多出两个字段：

```text
key = H(tenant ‖ adapter_revision ‖ prefix_hash)
```

`tenant` 决定"同一段文本属于谁"，`adapter_revision` 决定"用哪份权重算出来的"。本次把这两个字段分别从键里去掉，直接观察后果：

| 配置 | A0（tenant A, rev-a） | B0（tenant B, rev-b1） | B1（tenant B, rev-b2） | 结果 |
|---|---:|---:|---:|---|
| 正确键（tenant + revision） | 0 | 0 | 0 | 三次都是 miss，各算各的 |
| 去掉 adapter revision | 0 | 0 | **2048** | B1 拿到 B0 的 2048 token KV |
| 去掉 tenant | 0 | 0 | 0 | B0/B1 仍按 revision 分开 |
| 两个都去掉 | 0 | **2048** | **2048** | B0 拿到 A0 的 KV，B1 也拿到 |

三种配置下 KV 块的归属账都是闭合的（驻留块 + 空闲块 = 容量），差异只体现在**谁能命中谁的块**：正确配置下三条缓存条目各自只有一个租户与一个 revision；去掉 revision 后其中一条记录里出现 `revisions_seen = {rev-b1, rev-b2}`；两个都去掉时出现 `tenants_seen = {A, B}` 与三个 revision 混在一条记录上。这说明"命中"本身不是正确性证据，**归属审计**才是。

### 2. 共享算力下的干扰

只要两个租户进入同一个引擎的同一批，它们的请求就共享同一份算力。把引擎建模成"总算力固定、按在途请求数均分"（processor sharing），并用同一份到达清单跑四个策略：

| 策略 | B 的份额 | A 的 p50 | A 的 p95 | A 的 p99 | B 的 p99 |
|---|---:|---:|---:|---:|---:|
| 独跑（份额 0） | 0 | 0.107 s | 0.213 s | 4.69 s | — |
| 共享（无配额） | 0.5 | 2.76 s | 2.76 s | 67.43 s | 157.4 s |
| 共享（无配额） | 1.0 | 1.46 s | 1.46 s | 39.71 s | 549.7 s |
| 配额（A≤8、B≤16） | 0.5 | 2.47 s | 2.48 s | 61.53 s | 157.4 s |
| 配额 | 1.0 | 1.46 s | 1.46 s | 39.71 s | 549.7 s |
| 配额 + 优先级排序 | 0.5 | 2.47 s | 2.48 s | 61.53 s | 157.4 s |

表中的份额 0.5 与 1.0 两行对应的到达清单不同（B 的请求数分别是 20 与 40，长 prompt 比例 0.34 与 1.0），因此**跨行比较的是"有 B 与没有 B"和"换策略"，不是份额的单调性**。两个必须说清的事实：

- **A 的尾延迟被 B 拉长一个量级以上**：份额 0.5 时 A 的 p50 从 0.107 s 涨到 2.76 s，p99 从 4.69 s 涨到 67.4 s。这不是"平均吞吐下降"，而是"交互请求排在长请求后面"。
- **配额与优先级排序只挪动了很小一部分**：配额把 p50 从 2.76 s 压到 2.47 s（−10.5%），优先级排序没有再改；原因是它限制的是"同时进来多少"，而进来之后每个请求拿到的份额仍由在途总数决定。要在共享引擎里真正保护交互流量，需要的是**给它保留算力**（例如把长请求的 prefill 分块、或按 token 预算分批），而不是只加并发上限。这一结论与 8.4 的准入实验一致：准入决定谁进来，配额决定进来多少，二者都不等于隔离。

### 3. 取消、崩溃与重启之后的归属

多租户下最容易被忽略的是"失败路径也要按租户记账"。模拟里逐项检查：

- **跨租户取消**：取消租户 B 的一个在跑请求后，B 的条目被移除、它占的 4 个块归还；同一时刻租户 A 的空闲块数、token 用量与完成数都不变（`tenant_a_free_blocks_restored`、`tenant_a_used_tokens_unchanged`、`tenant_a_done_unchanged` 三项都为 true）。取消一个不存在的请求返回 `{"cancelled": false}`，不做任何清理。
- **引用计数**：取回中取消把引用减回 0 再抛错；持引用期间不允许驱逐；`release` 次数多于 `get` 直接报错。审计在结束时检查每一条缓存记录的 `refs` 是否为 0，以及驻留块 + 空闲块是否等于容量。
- **重启与幂等**：20 个请求完成后把"幂等键 → 结果"写成同一个提交记录；重启后重放同一批请求，20 个全部按记录返回（`replayed = 20`、`recomputed = 0`），提交记录数不变（`no_duplicate_results = true`）。这回答的是"重试不会重复计费、不会重复执行"。

### 4. 隔离机制的能力边界

| 机制 | 提供什么 | 不提供什么 | 本机状态 |
|---|---|---|---|
| 应用层配额（并发/令牌桶） | 限制某租户的进入量与在途数 | 不改算力分配；超载时是拒绝不是隔离 | 可用，见 8.4-D |
| 独立进程 + 独立引擎 | 权重、KV、adapter、队列、崩溃域各自独立 | 仍共享 GPU 带宽、显存容量、功耗与温度 | 可用，见第 3 节实测 |
| MPS | 同一 GPU 上的进程级并发（按 SM/显存配额） | 不提供故障隔离；配置需改共享机器 | 未启用（共享机器，不改驱动配置） |
| MIG | 硬件切分的独立 GPU 实例（显存/计算/带宽隔离） | 需要设备支持与管理员权限 | 不可用（两台机器 `nvidia-smi mig -lgip` 均报无可切分设备） |
| 提示词/模板约束 | 约束模型的输出形态 | 既不限制资源，也不限制数据可见性 | 不属于隔离机制 |

后三行是**机制与条件**的记录，不是实测；把它们写成"已支持"会把配置开关当成硬件能力。

## 工程实现：源码解析

### vLLM 0.29.0：LoRA 名字进哈希，权重版本不进

前缀缓存的块哈希是 `H(parent_hash, token_ids, extra_keys)`（`vllm/v1/core/kv_cache_utils.py:621` 的 `hash_block_tokens`）。`extra_keys` 由 `generate_block_hash_extra_keys`（`:583`）拼装，来源有四类：

```python
extra_keys = lora_extra_keys + mm_extra_keys + cache_salt_keys + prompt_embeds_keys
```

其中 LoRA 那一项的实现是（`:542`）：

```python
def _gen_lora_extra_hash_keys(request: Request) -> list[str]:
    if not request.lora_request:
        return []
    return [request.lora_request.lora_name]
```

**只有名字。** 适配器的权重版本、`lora_int_id` 都不参与哈希。这带来一个可验证的推论：如果同一个名字下的权重被换掉，而该前缀的 KV 还在缓存里，下一次请求会命中**上一版权重算出来的 KV**。第 3 节用 `/v1/load_lora_adapter` 的 `load_inplace` 与 `cache_salt` 直接检验了这条推论。

另两类 extra key 对多租户有直接作用：`cache_salt` 在块 0 上进入哈希（`:604`），等于给同一段文本提供"强制不同缓存身份"的开关；多模态特征的 identifier 也进哈希，避免不同图像/音频复用同一段文本的 KV。`cache_salt` 在 OpenAI 兼容接口上暴露（`entrypoints/openai/completion/protocol.py:198`）。

### vLLM 0.29.0：adapter 的加载、卸载与就地更新

- 运行时增删 adapter 由环境变量 `VLLM_ALLOW_RUNTIME_LORA_UPDATING` 门控（`entrypoints/serve/lora/api_router.py:25`）；打开后才有 `POST /v1/load_lora_adapter` 与 `POST /v1/unload_lora_adapter`。
- `LoadLoRAAdapterRequest` 的字段是 `lora_name`、`lora_path`、`load_inplace`、`is_3d_lora_weight`。`load_inplace` 为真时不换名字、沿用同一个 `lora_int_id`（`entrypoints/openai/models/serving.py:179-188`），也就是说**引擎内部认为这还是同一个 adapter**；为假时同名会报错，要求的做法就是换名字（`:250-253`）。
- 调度侧的租户相关开关是 `--scheduling-policy {fcfs,priority}`、`--enable-lora`、`--lora-modules`、`--max-loras`、`--max-cpu-loras`。它们控制的是"先服务谁"与"同时装载几个 adapter"，不改变缓存身份。

把这两件事放在一起就能得到工程结论：**`load_inplace` 适合"同一份权重的热修补"，不适合"换一版 adapter"**；换版本要么换名字（缓存身份随之改变），要么在换之前清理该前缀的缓存（例如 `POST /reset_prefix_cache`）。

### LMCache：键里没有 adapter 字段，但有标签

LMCache 的键是 `CacheEngineKey(model_name, world_size, worker_id, chunk_hash, dtype, tags)`（`lmcache/utils.py:389`），`__hash__`/`__eq__` 与 `to_string()`（`:438`）都只用这六个字段：**模型名、并行度、worker id、块哈希、dtype、标签**。它没有 adapter 字段；要区分 adapter，只能通过 `lmcache.tag.*` 形式的请求配置（`:399-411`），而 vLLM 侧这些标签来自请求的 `sampling_params.extra_args["kv_transfer_params"]` 中以 `lmcache.` 开头的项（`vllm/distributed/kv_transfer/kv_connector/v1/lmcache_integration/vllm_v1_adapter.py:102`）。

这意味着：**多租户的隔离程度取决于调用方有没有把租户与 adapter 版本传进去**。默认配置下不同租户请求同一段文本会落到同一个键上——共享缓存本身不一定错（如果权重的确相同），但它把"身份是否正确"的责任交给了上层。

### Mooncake：把租户配额做成账户

Mooncake 的存储侧把租户配额做成显式对象（`mooncake-store/include/tenant_quota.h`）：`TenantQuotaSnapshot`（快照）、`TenantQuotaError` 与 `TenantQuotaChargeFailure`（计费失败的两种返回）、`TenantQuotaAccount`（单租户账户）与 `TenantQuotaTable`（账户表，`TenantQuotaAccount` 是它的友元）。这与 8.6 里 Mooncake 的 NVMe 对象身份、冲突策略是一套设计的两面：**身份决定"这份数据是谁的"，配额决定"谁还能再写多少"**。相比之下，本章模拟里的租户预算就是这张账户表的最小版本。

### 设计取舍

1. **缓存键放不放进 tenant。** 放进键会降低命中率（同一段公共前缀在不同租户间无法共享），不放则要求租户之间本来就可以共享这份 KV。判断依据是数据边界而不是性能：跨租户共享系统提示的 KV 通常是安全的，共享含私有上下文的 KV 不是。本次模拟把两种情况都实现了，并把"谁能命中谁"作为审计项输出。
2. **配额放在准入还是放在调度。** 准入实现简单、可复算，但它只能拒绝；调度侧（优先级、抢占）能改变顺序，代价是被抢占的请求要重算。本次两种都测了，结论是"顺序改变不等于算力保留"。
3. **隔离用进程还是用设备。** 进程隔离用显存换边界，MIG 用硬件换边界。前者随时可用、代价可算（副本数 × 权重），后者依赖设备与权限，本章本机不可用。
4. **`load_inplace` 还是换名字。** 就地更新省一次加载、保住缓存身份（对同一份权重有利），但它也让缓存无法察觉权重变化；换名字会丢掉该 adapter 的全部缓存。**正确性优先时选换名字或显式清缓存。**

## 工程实现：mini 实现

`labs/L8/tenant_scheduler.py` 是一个确定性的多租户调度与状态归属模拟，四个可检查的设计点：

1. **身份**：`cache_key(r)` 由 `tenant`、`adapter_revision` 与 `prefix_hash(prefix)` 拼成；两个 `--ignore-*` 开关分别把对应字段去掉，用来复现跨租户/跨版本命中。
2. **预算**：每个租户有 `token_budget`、`max_concurrency`、`max_adapters`；准入返回 `(bool, reason)`，拒绝原因逐条记入事件流。
3. **抢占**：`preempt_for` 只抢优先级数值更大（更低）的租户，被抢请求立即释放 KV 块、归还引用，记一次 `preempt`，不计入完成。
4. **持久状态**：完成时把 `idem_key → 结果` 写成同一条提交记录；`replay()` 只按快照恢复，已提交的直接返回。

审计函数 `audit()` 在结束时检查三件事：每条缓存记录的 `refs` 是否为 0；是否出现 `tenants_seen` 多于一个（未开启 `--ignore-tenant` 时）；驻留块 + 空闲块是否等于容量。第 1 节的四组身份实验结果就是这四条的组合。

```bash
python labs/L8/tenant_interference.py identity --out-dir <out>/identity --prompt-len 2048
```

流程是：同一段 2048 token 前缀在 adapter `rev`（revA 权重）上建立缓存 → `POST /v1/load_lora_adapter {"load_inplace": true}` 就地把权重换成 revB → 分别用**同一个 `cache_salt`**（可能命中旧 KV）与**新的 `cache_salt`**（必然重算）请求同一段前缀，比较首个 token 的 top-5 logprob。revB 是把公开 adapter 的 `lora_B` 取负得到的合成权重，只用于让两份 revision 的函数确实不同。

实测（Qwen3-4B + 该 adapter，2048 token 前缀，引擎就绪 42.0 s）：

| 请求 | `cache_salt` | top-1 token | top-5 里的前两位 |
|---|---|---|---:|
| revA 首算 | s1 | `"\n"` | `"\n"` −4.566 / `" "` −4.816 |
| revA 再算（新 salt） | s2 | `"\n"` | `"\n"` −4.569 / `" "` −4.819 |
| revA 热缓存（第三次） | s1 | `"\n"` | `"\n"` −4.566（`prefix_cache_hits_total` 在 warm 阶段累计 4 064） |
| 就地换权重后，同一 salt | s1 | `"\n"` | `"\n"` −4.538 / `" "` −4.663 |
| 换权重后，新 salt（真值） | s3 | `" "` | `" "` −3.912 / `"\n"` −4.225 |
| 换名字重新加载 revB，同一 salt | s1 | `" "` | `" "` −3.917 / `"\n"` −4.292 |

读法：

- **两份 revision 的函数确实不同**：同一段前缀在 revB 上首 token 的 top-1 从 `"\n"` 变成 `" "`（logprob −3.912），两者不是同一个分布。
- **同名就地换权重后，缓存把旧 KV 用上了**：`load_inplace` 返回 `Success: LoRA adapter 'rev' added successfully.`，随后用同一个 salt 请求同一段前缀，首 token 仍是 `"\n"`（−4.538），与真值 revB 的 `" "` 不同；分布相对 revA 略有移动（−4.566 → −4.538），因为最后一层之后的部分用了新权重，而前缀的 KV 来自旧权重。
- **换名字就恢复了正确性**：把同一份 revB 权重以 `rev-next` 名字加载后，同一个 salt 的请求给出 `" "`（−3.917），与"新 salt 真值"一致。这与源码一致：哈希里的 LoRA 项只有名字。

对照组的确定性也要交代：revA 的两次计算用了不同 `cache_salt`（都必然重算），首 token 与 logprob 在 −4.566/−4.569 上一致，说明"不同 salt 导致的重算"本身不改变结果，上面第三行的差别不是 salt 引入的。

### C. 共享实例 vs 进程隔离（引擎）

```bash
python labs/L8/tenant_interference.py interference --out-dir <out>/interference
```

同一份到达清单跑两种部署：`shared` 是一个引擎同时服务两个租户（各挂一个 adapter），`isolated` 是两个引擎各服务一个租户。分租户记录 TTFT/TPOT/状态，并按 0.5 s 采样显卡的显存与利用率。**消融建议**：把 `--b-prompt-len` 从 6144 降到 2048（B 的 prefill 变短），观察 A 的 TTFT 尾部分位是否随之改善；把 `--interval-s` 从 1.0 调到 0.5（A 的到达率翻倍），看拒绝与排队是否先出现在 A 上。

实测（Qwen3-4B + 两个 adapter，A：60 个 1024 token 前缀请求、每 1 s 一个；B：12 个 6144 token 前缀请求、每 1 s 一个；输出 32/64 token）：

| 部署 | 引擎就绪 | 峰值显存 | 租户 | 成功率 | TTFT p50 | TTFT p95 | TTFT p99 | TPOT p50 |
|---|---|---:|---|---:|---:|---:|---:|---:|
| shared（一个引擎） | 30.0 s | 14 432 MiB | A | 60/60 | 17.1 ms | 26.7 ms | 79.6 ms | 7.4 ms |
| | | | B | 12/12 | **273.6 ms** | 277.0 ms | 277.0 ms | 8.0 ms |
| isolated（两个引擎） | 30.0 / 28.0 s | 22 439 MiB | A | 60/60 | 16.6 ms | 34.0 ms | 63.0 ms | 7.1 ms |
| | | | B | 12/12 | **47.2 ms** | 103.6 ms | 103.6 ms | 11.6 ms |

读法：

- **隔离把长 prefill 租户的 TTFT 改善 5.8 倍**（273.6 → 47.2 ms）。共享引擎里 B 的 6144 token prefill 最可能被分块并与 A 的解码步交错（本次没有关闭 chunked prefill，也没有记录分块次数，这一点是解释而非实测），TTFT 因此被拉长；独立引擎里它独占批次。代价是 B 的解码变慢：TPOT p50 从 8.0 ms 涨到 11.6 ms，因为它失去了与 A 的请求同批的机会。
- **交互租户本来就被缓存保护**：A 的前缀被前缀缓存命中（共享引擎两侧合计 `prefix_cache_hits_total = 126 880 / 135 168` = 93.9%），prefill 本来就短，因此共享与隔离的 p50 只差 0.5 ms；隔离后 A 的 p99 从 79.6 ms 降到 63.0 ms，说明共享仍会给它带来约 17 ms 的尾部扰动。
- **隔离的代价写在显存上**：共享 14 432 MiB、隔离 22 439 MiB（两块权重与两个 KV 池），多出来的 8.0 GiB 就是"边界"的价格；两块引擎并行启动用时 30.0 s，与单引擎相同（两个进程的初始化本来就可以并行）。
- 这个结果修正了"隔离总是更好"的直觉：**隔离改善的是被共享拖慢的那一类（长 prefill），损害的是本来受益于批处理的指标（解码吞吐）**。选择哪一种取决于哪一类指标在你的 SLO 里更硬。

## 前沿

1. **把租户身份写进缓存键的显式开关。** vLLM 的 `cache_salt` 在块 0 上进入哈希（`kv_cache_utils.py:604`），等于给"同一段文本、不同租户"提供了一个不改变模型行为的隔离旋钮；本次实验用它构造"必然重算"的对照。它的边界也很清楚：salt 相同的两次请求仍然共享，所以 salt 必须由可信侧生成（例如网关），不能来自客户端。
2. **就地更新与缓存一致性。** `load_inplace` 让 adapter 的权重可以在不换名字的情况下替换，但缓存哈希只看名字，因此引擎需要额外的失效动作。类似的"身份没变、内容变了"问题在 8.6 的 KV 存储层以另一个形式出现（对象身份与校验和），两章可以用同一组判据检查：**内容版本是否进入了身份**。
3. **租户配额的存储侧表达。** Mooncake 把配额做成 `TenantQuotaAccount` / `TenantQuotaTable` 与应用层令牌桶是同一件事的不同层：应用层配额限制"请求"，存储层配额限制"字节"。多租户服务通常两层都要有，否则一类租户可以通过长上下文把存储层写满。
4. **进程隔离的成本结构。** 进程隔离把边界做得最干净，代价是每个租户一份权重与一份 KV 池；8.5 的能量账与 8.7 的启动账可以直接相乘：每多一个常驻副本，就多一份空闲功耗与一次扩容滞后。

## 陷阱

1. **把命中当正确。** 缓存命中的前提是身份一致；本次在 `--ignore-revision` 下 B1 拿到了 2048 token 的"命中"，但那是别人的 KV。
2. **把配额当隔离。** 配额限制进入量，不改变共享算力的分配；实测里 A 的 p50 只从 2.76 s 降到 2.47 s。
3. **提示词约束不是资源或数据隔离。** 它约束输出形态，不限制其他租户看到什么、也不限制算力占用。
4. **同名 adapter 就地换权重后继续用旧缓存。** `load_inplace` 不换名字，前缀缓存的哈希只含名字；要么换名字，要么显式清缓存。
5. **取消/抢占不记账。** 失败路径必须归还 KV 块与 adapter 槽位，否则资源会静默地记在别的租户账上；本次审计把"引用为 0"与"块账闭合"作为退出条件。
6. **把配置开关当硬件能力。** `nvidia-smi` 里出现 MIG 字段不代表设备可切分；本机 `mig -lgip` 明确返回无可切分设备。
7. **独立进程就等于不争用。** 两个实例仍共享 GPU 带宽与显存容量，隔离的是状态与故障域，不是物理资源。

## 自测题

::: fold 1. 为什么"同一段文本、不同租户"是否应该共享 KV，取决于内容而不是性能？
**答案：**
KV 是这段文本在该模型/权重下的中间状态，本身不含额外的权限信息。如果这段文本是公共系统提示，两个租户共享它的 KV 不泄漏任何一方的东西；如果它包含某一租户的私有上下文，共享就等于把别人的上下文状态注入到自己的注意力里。所以判断依据是数据边界：能共享的前提是"这段内容对两边都可见"。工程上把 tenant 放进键是最保守的做法，代价是公共前缀的命中率下降。
:::

::: fold 2. 本次实验里 A 的 p50 从 0.107 s 涨到 2.76 s，为什么加上"配额"只降回 2.47 s？
**答案：**
因为配额限制的是"同一租户能有多少请求同时在里面"，而请求进来之后每个请求拿到的算力份额由**在途总数**决定。配额把 B 的并发限制在 16，但 A 自己的 8 个请求仍然和 B 的 16 个共享同一份总算力，所以 A 的每个请求还是被摊薄。要真正保护交互流量，需要给它的请求保留算力（例如限制长请求的 prefill 批量、按 token 预算分批），而不只是限制并发数。
:::

::: fold 3. 为什么"就地换 adapter 权重"之后，前缀缓存会给出上一版权重的 KV？
**答案：**
因为块哈希是 `H(parent_hash, token_ids, extra_keys)`，而 LoRA 那一项 extra key 只有 `lora_request.lora_name`（vLLM 0.29.0 的 `_gen_lora_extra_hash_keys`）。`load_inplace` 不换名字，哈希输入完全不变，前缀缓存自然认为这就是同一份 KV。要避免它，要么换 adapter 名字（哈希随之改变），要么在换权重前清理该前缀的缓存（如 `POST /reset_prefix_cache`），要么用不同的 `cache_salt` 把两版隔离。
:::

::: fold 4. 进程隔离解决了什么，又没有解决什么？
**答案：**
它让每个租户拥有独立的权重、KV 缓存、adapter 槽位、队列和崩溃域：一个实例 OOM 或崩溃不会带走另一个实例的请求，缓存身份也不会互相污染。它没有解决的是物理资源共享——两个实例仍共用同一张卡的带宽、显存容量和功耗预算，一个实例把带宽打满时另一个的 TPOT 一样会退化；代价则是每个租户多一份权重常驻显存和一次独立的启动/扩容滞后。
:::
