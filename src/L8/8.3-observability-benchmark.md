## 本章回答三个问题

1. **一次请求的"完整时延"由哪些事件组成？** 计划到达、实际发送、首字节、首个有效 token、每个输出 token、完成或错误——少记哪一个，后面的结论就会偏。
2. **开环与闭环发生器为什么会对同一台服务给出完全不同的排队结论？** 同一个 2 秒卡顿，闭环压测报出的 TTFT p99 是 61 ms，开环报出 2.13 s。
3. **质量、SLO、错误与样本量怎样共同决定 goodput？** 谁进分母、SLO 什么时候冻结、多少样本才配叫 p99。

::: note 本章的立场
吞吐（token/s）和 QPS 都是**过程指标**。服务能不能用，取决于"在什么时延门槛下、有多少请求真正拿到了合格输出"。8.3 定义的这套事件口径会被 8.1、8.4、8.6、8.7、8.8 直接复用，所以它必须先把三件事做对：**分母不删样本、时间戳可回溯到计划到达、SLO 在比较策略之前冻结**。
:::

## 机制拆解与推导

### 1. 一条请求的六个事件

| 事件 | 含义 | 时间戳来源 |
|---|---|---|
| `planned_arrival` | 发生器计划让这条请求到达的时刻 | 客户端预先排好的清单 |
| `actual_send` | 请求真正写出去的时刻 | 客户端 |
| `first_byte` | 读到 HTTP 响应体的第一个字节 | 客户端 |
| `first_token` | 第一个**带内容的**输出 token | 客户端（服务端 usage 只给总数，不给时刻） |
| `token_timestamps` | 后续每个 SSE 数据块的到达时刻 | 客户端 |
| `finish` | 正常结束 / 超时 / 拒绝 / 连接错误 | 客户端 |

由这些事件导出的量：

$$\text{client\_queue\_delay} = \text{actual\_send} - \text{planned\_arrival}$$

$$\text{observed\_TTFT} = \text{first\_token} - \text{actual\_send},\qquad \text{true\_TTFT} = \text{first\_token} - \text{planned\_arrival}$$

$$\text{TPOT} = \frac{\text{finish} - \text{first\_token}}{N_{\text{token}} - 1}$$

两个必须写清楚的边界。**一，token 数只能信 usage。** 高负载下引擎会把多个 token 合并进一个 SSE 数据块，用块数当 token 数会把完整的响应误判成截断。实测里 128 token 的请求出现 127 个数据块，而 `usage.completion_tokens` 始终是 128。**二，TPOT 的分母与粒度不一致。** 标准计算以 usage 返回的 token 数为分母，以首 token 到 `finish` 的跨度为分子；客户端能逐块观测到的是块间隔（ITL），块内多个 token 的间隔无法从流式协议里还原。

### 2. 协调遗漏：闭环为什么会漏掉卡顿

wrk2 的作者把这件事说得很直白：闭环负载发生器"会与服务端协调，在服务端高延迟的时段里停止测量"（`giltene/wrk2` README，commit `44a94c1`）。设并发 $C$、单请求服务时间 $S$，闭环的稳态完成速率是 $C/S$。注入一段时长 $D$ 的全局卡顿时：

- **闭环**：$C$ 个在途请求全部被卡住，客户端不再发新请求；这段时间内**本应到达**的 $D \cdot C / S$ 条请求没有任何记录。
- **开环**：到达过程与响应无关，这 $D$ 秒内照常投入请求，它们全部排队，等待时间直接进入 TTFT。

将实测参数代入：$C=2$、$S=0.3214$ s、$D=2.0$ s，则 $C/S = 6.22$ QPS，漏掉的请求约 $12.4$ 条。实测闭环完成时间线上的最大空档是 **2.344 s**，按 6.22 QPS 折算约 **14.6 条**请求从未被任何记录覆盖。

修正的标准做法是 HdrHistogram 的 `recordValueWithExpectedInterval`（commit `de84b0a`）：已知测量的期望间隔 $E$ 时，一个记录为 $L$ 的样本要补记 $\lfloor L/E \rfloor - 1$ 个 $E$。wrk2 走的是等价路线——延迟从"请求**应该**发出的时刻"开始算。本章基准测试同时涵盖两种修正机制：开环将计时起点锚定在 `planned_arrival`，闭环则额外给出 expected-interval 修正后的分位数。

这里有一个容易被忽略的细节：**修正在哪个指标上生效，取决于卡顿打在哪一段**。本次实验的卡顿发生在请求已经拿到首 token 之后，所以：

| 口径 | 闭环 | 开环 |
|---|---:|---:|
| TTFT p50 / p99 | 41.8 ms / 61.4 ms | 1.296 s / 2.135 s |
| 真实端到端 p99 | **2.381 s** | 2.468 s |
| goodput（SLO 1 s / 50 ms） | 0.973 | 0.412 |

闭环的 TTFT 修正前后都是 61 ms——因为受影响的 2 条请求早已越过首 token；卡顿只出现在端到端时延里。也就是说，**"闭环没看出问题"不等于修正后就能看出来**：当卡顿只影响解码段时，闭环的 TTFT 分布结构性缺失，任何后处理都补不回来。

### 3. 过载拐点：0.9 倍还很稳，1.1 倍就雪崩

把服务看成一个服务率 $\mu$ 的队列，到达率 $\lambda$，利用率 $\rho = \lambda/\mu$。$\rho < 1$ 时排队长度有界，$\rho > 1$ 时队长以 $(\lambda-\mu)$ 的速度线性增长，等待时间随窗口长度无界上升。Little 定律给出在途请求数 $L = \lambda W$，所以过载时**吞吐不再涨，时延线性涨**。

实测（Qwen3-1.7B，输入 2048 token，输出固定 128，关前缀缓存，单张 L40S）：

| 档位 | 到达率 | 完成数/窗口 | true TTFT p50 | p95 | p99 | 输出 tok/s | goodput 0.5s/25ms | 1s/50ms |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 0.3× | 3.10 | 353–381 | 0.060 s | 0.092 s | 0.116 s | 395 | 1.000 | 1.000 |
| 0.6× | 6.19 | 719–773 | 0.072 s | 0.130 s | 0.168 s | 798 | 1.000 | 1.000 |
| 0.9× | 9.29 | 1096–1155 | 0.110 s | 0.198 s | 0.241 s | 1210 | 0.805 | 1.000 |
| 1.1× | 11.35 | 1350–1396 | **0.199–12.392 s** | **8.138–32.886 s** | **10.245–34.697 s** | 1466 | 0.076 | 0.323 |
| 突发 | 0.6×（每 2 s 20 条） | 1220 | 0.566 s | 0.977 s | 0.999 s | 1301 | 0.342 | 0.989 |
| 长短混合 | 0.6×（512/4096 交替） | 719–773 | 0.113 s | 0.170 s | 0.210 s | 798 | 1.000 | 1.000 |

三个可以直接读出来的结论：

1. **0.9× 到 1.1× 之间是悬崖，不是斜坡。** 吞吐只从 1210 涨到 1466 tok/s（+21%），p99 从 0.24 s 涨到 10–35 s（41× 到 146×）。用 tokens/s 看，"1.1 倍负载还能多吐 21% 的 token"；用 SLO goodput 看，能满足 1 s TTFT 的请求只剩 32.3%。
2. **过载档的 p50 跨种子不可复现。** 三个种子分别给出 0.199 s / 10.935 s / 12.392 s——差异来自积压位置，不是测量噪声。所以本档只报区间，不报单一 p99。
3. **突发与均值同负载不同体验。** 突发档平均到达率与 0.6× 相同（6.19 QPS），但 p50 从 0.072 s 抬到 0.566 s：20 条同时到达把瞬时并发推到 20，超出了稳定区间。

### 4. goodput：分母纪律 + 冻结门槛

$$\text{goodput} = \frac{\#\{r : r \text{ 成功} \wedge \text{TTFT} \le \tau_{\text{ttft}} \wedge \text{TPOT} \le \tau_{\text{tpot}} \wedge \text{输出完整}\}}{\#\{\text{计划到达的请求}\}}$$

分母是**计划到达数**，不是完成数，也不是成功数。拒绝、超时、取消、连接错误、用量不足、缺少结束标记的请求，全部留在分母里。8.3-C 冻结的三档教学门槛写在 `labs/L8/request_metrics.py` 的 `TEACHING_SLOS` 里，在跑任何策略之前确定，之后不允许按结果调整。

本次实验里引擎一次拒绝都没有（1200–1400 条/窗口全部 200），这说明"没有拒绝"不代表"服务可用"：1.1× 档 67.7% 的请求在 1 s 门槛外，goodput 只有 0.323。

### 5. 分位数与样本量

分位数用最近秩定义：$\text{rank} = \lceil p/100 \cdot n \rceil - 1$，不做线性插值——插值会把尾部的稀疏样本抹平。样本量决定能说什么：

- $n < 100$ 时 p99 退化成最大值，`summarize()` 会标 `insufficient_tail`；
- 本次每档每个种子有 353–1396 个样本、3 个时间窗，p99 有值可算；
- 但项目实验规范要求"不足 10000 请求不宣称 p99 稳定"。120 秒窗口在这个服务上最多给出约 1400 个样本，**满足可计算，不满足可稳定宣称**。因此上表的尾部分位数一律按"3 个种子的区间"读，不按点值读。

## 工程实现：源码解析与设计取舍

### vLLM 侧暴露了什么

服务端能提供的事件分成三类，来源都在固定版本 vLLM 0.29.0 的 wheel 里：

1. **聚合计数器**（`vllm/v1/metrics/loggers.py`）。`vllm:num_requests_waiting` 在 `:504`、`vllm:num_requests_waiting_by_reason` 在 `:514`（按 `capacity` / `deferred` 分因），前缀缓存计数器 `vllm:prefix_cache_queries` 在 `:585`、`vllm:prefix_cache_hits` 在 `:596`。这些是**进程级累计量**，只能前后取差，不能回答"哪条请求命中了多少"。
2. **逐请求 usage**。`usage.prompt_tokens` / `completion_tokens` 给出准确 token 数，`prompt_tokens_details.cached_tokens` 给出该请求真实命中的前缀 token 数——8.1 判断路由预测是否假阳性就靠它。
3. **KV 事件流**（`vllm/distributed/kv_events.py`）。`EventBatch` 在 `:25`，三类事件 `BlockStored` / `BlockRemoved` / `AllBlocksCleared` 在 `:50` / `:101` / `:122`；`ZmqEventPublisher` 在 `:297`，用 `send_multipart((topic, seq, payload))` 发出（`:471`），payload 是 msgspec 编码的 msgpack。配置项在 `vllm/config/kv_events.py`：`endpoint`（默认 `tcp://*:5557`）、`replay_endpoint`、`buffer_steps`（默认 10000）、`hwm`、`topic`。事件自带 `ts` 与单调递增的 seq，订阅端可以据此发现缺口并按 seq 向 `replay_endpoint` 补拉——这是"目录重建"的真实机制。

**没有的东西**：vLLM 不提供逐请求的服务端时间戳。请求在引擎内部的入队、调度、首 token 时刻都不可见，客户端只能看到自己这一侧的事件。所以任何"服务端处理时间"都必须由客户端时间减出来，并且要把网络和客户端排队单独列出——这正是 `client_queue_delay` 存在的理由。

### 设计取舍

| 选择 | 代价 | 为什么仍然这么选 |
|---|---|---|
| 客户端时间戳全部用 `time.monotonic` | 跨进程/跨机不可直接比较 | 墙钟会被 NTP 调整；同进程内的时延分解必须用单调时钟。跨机比较另行校准（见 8.3-D） |
| SSE 数据块时刻当 token 时刻 | 高负载下块内多 token，ITL 被低估 | 流式协议只到块粒度；token 数改用 usage 修正，避免把完整响应判成截断 |
| 分母用计划到达数 | 需要发生器先排好完整清单 | 只有这样，"没发出去的请求"才会被计入；用完成数做分母会把过载洗成健康 |
| 分位数用最近秩 | 小样本下 p99 = max | 线性插值会掩盖尾部；宁可让 `insufficient_tail` 暴露样本不足 |
| SLO 冻结在代码常量里 | 改门槛要改代码 | 门槛必须早于结果存在。写在可 diff 的文件里，比写在报告里更难被事后调整 |

::: fold labs/L8/request_metrics.py 事件 schema 与 goodput 分母
```python
@dataclasses.dataclass
class RequestRecord:
    request_id: str
    planned_arrival_s: float
    actual_send_s: Optional[float] = None
    first_byte_s: Optional[float] = None
    first_token_s: Optional[float] = None
    token_timestamps_s: List[float] = dataclasses.field(default_factory=list)
    finish_s: Optional[float] = None
    status: str = STATUS_SUCCESS
    ...

    @property
    def client_queue_delay_s(self) -> Optional[float]:
        return max(0.0, self.actual_send_s - self.planned_arrival_s)

    @property
    def true_ttft_s(self) -> Optional[float]:
        return max(0.0, self.first_token_s - self.planned_arrival_s)

    @property
    def num_tokens(self) -> int:
        # SSE 块数不等于 token 数: 优先信服务端 usage。
        if self.server_reported_output_tokens is not None:
            return self.server_reported_output_tokens
        return len(self.token_timestamps_s)
```

```text
闭环完成时间线最大空档 = 2344ms; 按可持续 6.22 QPS 折算, 卡顿期间约有 14.6 个请求从未被任何记录覆盖
```

三条要看的对照：闭环的开环侧客户端排队 p99 只有 1.19 ms（说明开环真的没被客户端卡住，2.13 s 是服务端排队）；缺失结束标记的 20 条请求全部被标出来并计入分母（goodput 归零）——**协议层不给正常结束的证据时，不能凭"token 数够了"就当成功**。

**消融建议**：把 `--stall-start` 提前到请求刚开始时，观察 TTFT 修正的差异；把 `--arrival burst` 与 `poisson` 在相同平均速率下对比；把 `drop_events` 改成丢中间 token，确认截断被计数方式的变化。

## 前沿

1. **协调遗漏的原始论述与修正。** wrk2（`giltene/wrk2`，commit `44a94c1`）在 README 里给出了闭环发生器漏测的完整论证，并改用"从请求应当发出的时刻起算延迟"；HdrHistogram（commit `de84b0a`）提供 `recordValueWithExpectedInterval` 作为事后修正，两者互斥、只能选一。
2. **面向 goodput 的服务评测。** DistServe（[arXiv:2401.09670](https://arxiv.org/abs/2401.09670)）把服务目标写成"在 TTFT 与 TPOT 约束下的每 GPU goodput"，并按此拆分解码与预填充；SGLang（[arXiv:2312.07104](https://arxiv.org/abs/2312.07104)）与 Preble（[arXiv:2407.00023](https://arxiv.org/abs/2407.00023)）分别把前缀复用与提示调度放进同一个 SLO 框架。本章的 SLO 冻结与严格分母沿用这一口径。
3. **引擎自带的压测入口。** vLLM 0.29 已把压测收进 CLI：`vllm bench serve`（实现见 `vllm/benchmarks/serve.py`，commit `435c96f`），SGLang 对应 `python -m sglang.benchmark.serving`。两者默认按闭环定并发发压，因此它们的时延分位数同样带协调遗漏，只能用于相对比较；本章的开环发生器是用来补这个缺口的。
4. **面向多模态与跨实例的统一事件口径（8.3-D，部分完成）。** 同一份 schema 需要覆盖四类"首个可用输出"：文本首个有效 token、语音首个可播放 chunk、视频首个有效帧、跨实例 KV 传输完成。前两者在本项目已有可用锚点——1.7 的实时闭环用"取用/丢弃"事件描述了音频 chunk 的 deadline（含 NTP 式时钟校准，注入 250 ms 被恢复到 0.6 ms）；6.4 定义了 15 字段的 KV 交接描述符并在 worldvln 上实测 GPU→GPU 10.88 GB/s。视频首个有效帧依赖 10.3/10.5 的扩散调度，尚未产出可引用工件。**因此 8.3-D 的"跨机时间段重叠核对"没有执行**：本阶段所有运行都在单机内完成，跨机计时需要先做与 1.7 同口径的时钟校准，条件不具备时保留未完成。

## 陷阱

1. **闭环压测的尾分位数不能跨系统比较。** 它的数值取决于发生器的并发数，而不是服务本身；并发取得越大，漏掉的卡顿越多。要比，就用开环或至少固定同一并发。
2. **"没有拒绝"不等于"服务可用"。** 1.1× 档 4124 条请求全部返回 200，但只有 32.3% 满足 1 s TTFT。只统计成功率会把雪崩写成满分。
3. **token 数不要数 SSE 块。** 实测 128 token 的响应出现 127 个块；用块数判截断会产生假失败，用块数算 TPOT 会低估解码成本。
4. **过载档不要报单点 p99。** 本次 1.1× 三 seed 的 p50 相差 60 倍；样本量够也不代表可复现，因为系统状态本身不可复现。
5. **客户端排队要单独列。** 本次所有档位的 `client_queue_delay` p99 都 ≤ 15 ms，所以观测时延没有被发生器污染；如果这个值变大，说明是客户端或网络先撑不住，服务端的结论作废。
6. **profiler 与计时不要混跑。** 端到端分位数只能从原始请求记录算，不能从 profiler 的 kernel 时间里加出来；两者分开采集。

## 自测题

::: fold 1. 为什么同一台服务在闭环下 TTFT p99 是 61 ms，在开环下变成 2.13 s？
**答案：**
闭环发生器在每个连接上"收到响应才发下一个请求"，服务端卡顿的 2 秒里它没有请求可发，于是这段时间本应到达的约 14.6 条请求从未进入样本；开环发生器按预先排好的到达清单派发，卡顿期间的请求照常投入并在队列里等待，等待时间完整进入 TTFT。差别在发生器的到达过程，不在服务端。
:::

::: fold 2. 为什么这次闭环的 TTFT 做完 expected-interval 修正后仍然是 61 ms？
**答案：**
因为卡顿发生在请求已经拿到首 token 之后（解码段）。expected-interval 修正补的是"被压住没发出去的请求"，而这些补齐的样本即使计入，也只是低延迟样本；受影响请求的 TTFT 早在卡顿之前就测完了。卡顿只出现在端到端时延里（闭环真实 e2e p99 = 2.381 s）。修正能在哪个指标上生效，取决于卡顿打在哪一段。
:::

::: fold 3. 0.9× 档 goodput(0.5 s/25 ms) 是 0.805，1.1× 档是 0.076；但吞吐只从 1210 涨到 1466 tok/s。这两个数字矛盾吗？
**答案：**
不矛盾。利用率跨过 1 之后，队列长度随时间线性增长，吞吐被服务率钉死（多出来的 21% 来自更大的批处理规模），而等待时间无界上升。过程指标（token/s）看到的是"还能多吐一点"，SLO 指标看到的是"满足门槛的请求占比崩塌"。这正是不能用吞吐替代 goodput 的原因。
:::

::: fold 4. 一条请求的 `usage.completion_tokens` 是 128，但客户端只收到 127 个 SSE 数据块。它算不算成功？
**答案：**
算成功，输出完整。SSE 数据块只是流式传输的分帧单位，一个块可以携带多个 token；判断输出是否完整必须用服务端 usage 的 token 数，不能用块数。反过来说，如果 usage 缺失，就只能靠块数下界估计，并在事件完整性里标出来。
:::

::: fold 5. 为什么 goodput 的分母用"计划到达数"而不是"完成数"？
**答案：**
因为对用户而言，一条本该在某个时刻到达的请求没被服务，和它被服务了但很慢，损失是一样的。用完成数做分母，会把"客户端在过载时少发了请求"这件事从统计里抹掉——这正是协调遗漏的另一种形式。计划到达数由发生器预先排定，与响应无关，是唯一不受服务端状态污染的分母。
:::
