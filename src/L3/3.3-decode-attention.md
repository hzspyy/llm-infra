## 本章回答三个问题

prefill 中 Q 有 $S$ 行，完整 attention 的计算量随序列长度平方增长。单步 decode 中 Q 只有一行，但仍需读取历史 KV，计算量和读取量随上下文长度增长。

1. 哪些假设下 decode attention 的算术强度接近 1，何时会改变？
2. GQA/MQA/MLA 到底省了什么？收益是线性的吗？
3. 单请求长上下文 decode，只有 $B\cdot H$ 个并行单元，如何提高 170 个 SM 的利用率？

## 机制拆解

### bf16 MHA 的简化算术强度为 1

一步 decode，单头：$Q$ 是 $1\times D$，$K/V$ 各是 $S\times D$。

$$\text{FLOP} = \underbrace{2SD}_{qK^\top} + \underbrace{2SD}_{pV} = 4SD$$
$$\text{字节} = \underbrace{2\cdot S\cdot D\cdot 2}_{\text{读 K 和 V, bf16}} = 4SD \qquad (Q, O \text{ 只有 } O(D)\text{，忽略})$$

$$I = \frac{4SD}{4SD} = \boxed{1\ \text{FLOP/byte}}$$

在上述 bf16 精度、标准 MHA 架构且每组 K/V 仅对应单个 Query 头的场景下，算术强度恒等于极低的值（1 FLOP/byte），与上下文长度 $S$ 和向量维度 $D$ 完全无关。对比本机实测的机器平衡点（约 144.2 FLOP/byte），decode attention 处于极其深度的 memory-bound 状态。

这意味着：**单步 decode attention 的理论时间下限，完全取决于将历史 KV cache 从显存以峰值带宽读取一次所需的耗时。** 针对 decode attention 的工程优化方向只有两条核心路径：
1. **读得更快**：利用精细的访存合并与调度将物理带宽彻底榨满；
2. **读得更少**：通过 GQA/MQA/MLA 减少头数、量化压缩 KV 字节、或引入稀疏注意力跳过无关历史。

实测（$H=32$, $D=128$, bf16）：

| batch | kv_len | KV 大小 | 在 L2? | ms | GB/s | 占只读峰值 |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 1024 | 16.0 MiB | 是 | 0.0168 | 999.6 | 62.1% |
| 1 | 4096 | 64.0 MiB | 是 | 0.0432 | 1552.3 | 96.5% |
| 1 | 16384 | 256.0 MiB | 否 | 0.1735 | 1547.1 | 96.2% |
| 1 | 65536 | 1024.0 MiB | 否 | 0.6500 | 1652.0 | 102.7% |
| 8 | 4096 | 512.0 MiB | 否 | 0.3350 | 1602.4 | 99.6% |
| 32 | 4096 | 2048.0 MiB | 否 | 1.4656 | 1465.3 | 91.1% |
| 256 | 4096 | 16384.0 MiB | 否 | 10.4607 | 1642.3 | 102.1% |

除了最小的那一档（工作集太小，喂不饱），**其余全部贴着带宽上限**。
这就是"访存受限"的样子：不是"慢"，是"已经到顶了"。

::: warning 参照量选错会得到 >100% 的假象
若使用 **copy 带宽 1519.3 GB/s** 作为分母，会得到 102%、108% 等结果。
decode attention **只读不写** KV，正确的参照是**只读带宽 1608.6 GB/s**
（L1.1 的 `hw_crater_5090.json` 里两个数都有，注释写着
"copy_ 计入读+写两份流量；readonly 用 reduction 近似纯读"）。

换了分母之后仍有几行在 101–103%。这不是又错了——它说明
decode kernel 达到甚至略超过那个只读微基准，两者是不同的访存模式，
差几个百分点不奇怪。**能说的是"已经饱和"，不能说"达到了 102.7% 的峰值"。**

教训：报"占峰值多少"之前，先确认分子和分母**是同一种访存**。
:::

::: note 工作集大小与缓存命中不同
表中的容量判断只说明 KV 是否小于已记录的 96 MiB L2，并不证明实际命中 L2。其他张量、访问顺序和缓存策略都会影响驻留。大于 L2 的工作集是检查持续显存带宽的必要条件之一；实际层级流量仍需计数器。
:::

### GQA / MQA：把读取量按比例砍掉

- **MHA**：每个 query 头有自己的 K/V 头 → KV 头数 $= H$
- **GQA**：若干 query 头共享一组 K/V → KV 头数 $= H/g$
- **MQA**：所有 query 头共享一组 K/V → KV 头数 $= 1$

既然 decode 由 KV 读取量决定（第一节），KV 头数减半，时间就该减半。
$B=32$, kv_len$=8192$, $D=128$, query 头 $=32$：

| KV 头数 | 名称 | KV 大小 | 在 L2? | ms | GB/s | 相对 MHA | 字节比 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 32 | MHA | 4096.0 MiB | 否 | 2.9300 | 1465.8 | 1.00× | 1× |
| 16 | GQA | 2048.0 MiB | 否 | 1.6606 | 1293.2 | 1.76× | 2× |
| 8 | GQA | 1024.0 MiB | 否 | 0.6508 | 1649.8 | 4.50× | 4× |
| 4 | GQA | 512.0 MiB | 否 | 0.3333 | 1610.6 | 8.79× | 8× |
| 2 | GQA | 256.0 MiB | 否 | 0.1739 | 1544.0 | 16.85× | 16× |
| 1 | MQA | 128.0 MiB | 否 | 0.0947 | 1417.2 | 30.94× | 32× |

实测速度趋势与 KV 字节量模型相容。在实际搬运量、并行度和有效带宽相近时，可用
$$\text{耗时} \approx \frac{\text{实际搬运字节数}}{\text{有效显存带宽}}$$
解释容量和时间的关系。表中的 GB/s 由估计 KV 字节除以同一实测耗时得到，不能再把它作为独立证据，证明速度差来自块寻址或某个 kernel 优化。区分这些原因还需要实际 kernel 路径、缓存命中/流量计数器和受控对照；尚未采集的归因保持 `UNVERIFIED`。

### 换算成真实模型

Qwen3-1.7B：28 层，16 query 头，**8 KV 头**（GQA $g=2$），head_dim 128。

每 token 每层 KV = $2 \times 8 \times 128 \times 2\text{B} = 4096$ B，
28 层合计 **114688 B = 112 KiB/token**：

| 上下文 | 单请求 KV |
|---:|---:|
| 4096 | 448.0 MiB |
| 32768 | 3584.0 MiB |
| 131072 | 14336.0 MiB |

**131072 上下文的单条请求要 14 GB KV**，而这张卡总共 32 GB。
如果是 MHA（16 个 KV 头），要 28 GB——一条请求就把卡占满了。
这就是 GQA 被普遍采用的原因：它不是省了一点带宽，
它决定了**一张卡能同时服务几条长请求**（0.2 那本账）。

### 用 split-K 增加 decode 并行度

decode 时 Q 只有 1 行，沿 batch×head 切分只能得到 $B\cdot H$ 个并行单元。
$B=1$、$H=8$ 时只有 8 个——占 170 个 SM 的 5%。

FlashDecoding 的做法是**再沿 KV 长度切分**（split-K）：
把 KV 分成若干段，每段各自算局部的 $m$、$l$、$O$，
最后用 3.1 那个合并公式归约到一起。合并公式是精确的，所以结果不变。

判据：固定 $B\cdot H$ 很小，把 kv_len 拉长。
没有 split-K，带宽利用率会停在低位；有的话会随 kv_len 上升。

**$B=1$, $H=8$（$B\cdot H = 8$，占 SM 的 5%）**

| kv_len | KV 大小 | 在 L2? | ms | GB/s | 占只读峰值 |
|---:|---:|---:|---:|---:|---:|
| 1024 | 4.0 MiB | 是 | 0.0106 | 393.9 | 24.5% |
| 4096 | 16.0 MiB | 是 | 0.0207 | 808.6 | 50.3% |
| 16384 | 64.0 MiB | 是 | 0.0413 | 1623.7 | **100.9%** |
| 65536 | 256.0 MiB | 否 | 0.1764 | 1522.1 | 94.6% |
| 262144 | 1024.0 MiB | 否 | 0.6604 | 1625.9 | **101.1%** |

**8 个并行单元把 170 个 SM 的带宽跑满了。**
如果只沿 $B\cdot H$ 切分，8 个单元最多用 8/170 = 4.7% 的 SM，
不可能达到 100% 的带宽。这些吞吐结果支持继续检查其他并行维度，但不能仅凭 SM 占比证明 split-K；需核对 kernel grid 与实现。

前两行的 24.5% 和 50.3% 不是并行度不足的证据——那是工作集太小
（4 MiB、16 MiB），根本没有足够的字节去填满流水。

$H=32$ 那组同样在长上下文上贴顶（102.5%、104.8%）。

### 分页布局与块表机制

vLLM 的 KV cache 不是每条序列一段连续内存，而是若干固定大小的块，
用 block table 记录逻辑块→物理块（5.2 会拆这个结构）。
好处是不必按最大长度预留；代价是读 KV 要先查表再 gather。

$B=8$, $H=8$, kv_len$=8192$, 块大小 16（每条序列 512 块，物理块打乱）：

| 布局 | ms | GB/s | 相对连续 |
|---|---:|---:|---:|
| 连续 | 0.1722 | 1559.0 | 1.00× |
| 分页 + 显式 gather | 0.8522 | 315.0 | **0.20×** |

慢 5 倍。

::: warning 该比值只描述 gather 模拟，不是性能上界
本章模拟的做法是**先把分散的块 gather 成一个连续张量，再跑普通 attention**。
这多了一次全量的读+写，本身就要 2× 的流量，加上 gather 的不规则访存。

真实的 paged attention kernel **在 kernel 内部按 block table 直接寻址**，
不产生这份拷贝——K/V 仍然只读一遍，只是地址来自查表。
因此它与框架层 gather 的流量不同；真实代价尚未测量，不能由此给出严格大小关系。

**本节量的是"如果你用最朴素的方式实现分页会有多贵"**，
它的用处是说明为什么必须写专门的 kernel，而不是在框架层 gather。
:::

### FlashInfer 的主场：变长批与分页解码

| B | H | Hkv | kv_len | SDPA ms | FlashInfer ms | 比值 |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 32 | 8 | 8192 | 0.0269 | **0.0147** | **1.83×** |
| 1 | 32 | 8 | 65536 | 0.1757 | 0.1683 | 1.04× |

对照 3.2 的那张表：在**单条定长 prefill** 上 FlashInfer 是慢的（0.410 vs 0.295）；
在**单条 decode** 上它快 1.83×。

这不矛盾，是分工不同：FlashInfer 是为**服务端的变长批 + 分页 KV** 设计的。
prefill 那种规整的大矩阵是 FlashAttention 的主场；
decode 那种"小而碎、长度各异、KV 分散在块里"的形状是 FlashInfer 的主场。

kv_len=65536 时优势缩到 1.04×——长上下文下两者都被带宽钉死，
kernel 的巧劲没有发挥空间。**这也再次印证第一节：到了带宽上限，谁都一样。**

批量接口（`plan()` + 变长批）在同节的 [D] 里已经用真实 block table 测过：
分页 kernel 0.0207 ms vs 连续 0.0276 ms（1.33×），而框架层 gather 是 0.2422 ms。
**所以"FlashInfer 在 decode 上更快"不是靠单次调用对比得出的**，
它在有 block table 的批量形状上确实更快（5.2/5.3 会在真实引擎里继续验证）。

### MLA：用 DeepSeek-V2-Lite 的真实单层权重实测

MLA（DeepSeek 的 Multi-head Latent Attention）把 K/V 压成一个低秩隐向量存起来，
用时再投影回去。每 token 每层只存 $d_c + d_{\text{rope}}$ 个元素，
而不是 $2HD$ 个。本节用 **DeepSeek-V2-Lite 第 0 层 attention 的真实权重**
（`labs/L3/mla_absorption.py`，用 HTTP Range 只取 5 个张量、26.25 MB，
不下载整个 8.59 GB 分片）把两条路径都对拍过。

抽取到的权重（文件的字节偏移也记在工件里，可逐个核对）：

| 张量 | dtype | shape | 字节 | 文件偏移 |
|---|---|---:|---:|---:|
| `kv_a_proj_with_mqa.weight` | BF16 | [576, 2048] | 2359296 | 973514480 |
| `kv_a_layernorm.weight` | BF16 | [512] | 1024 | 973513456 |
| `kv_b_proj.weight` | BF16 | [4096, 512] | 4194304 | 975873776 |
| `o_proj.weight` | BF16 | [2048, 2048] | 8388608 | 980068080 |
| `q_proj.weight` | BF16 | [3072, 2048] | 12582912 | 988456688 |

配置：`kv_lora_rank=512`、`qk_nope_head_dim=128`、`qk_rope_head_dim=64`、
`v_head_dim=128`、`num_heads=16`、`q_lora_rank=null`。

两条路径：

- **重建**：$c\to W_{kb}\to k_{nope},v$，再走普通 attention。
- **吸收**：$\text{score}=(q_{nope}W_{kb,K}^\top)\cdot c+q_{pe}\cdot k_{pe}$，
  输出 $=\sum_j p_j c_j$ 再乘 $W_{kb,V}$（可进一步吸收进 `o_proj`），
  attention 直接在隐空间上做。

同一组输入下对拍：

| 数值类型 | 吸收 vs 重建 | 再吸收 o_proj |
|---|---:|---:|
| float32 | 2.68e-07 | 6.56e-07 |
| float64 | 4.44e-16 | 8.47e-16 |

两条路径在实数算术下等价。**差别在什么时候做哪个矩阵乘**：重建要为每个 KV 头
物化 $k_{nope}/v$（$[H,\,nope+v]$ 维），吸收则把 $W_{kb}$ 的 K 部分挪到 Q 侧、
V 部分挪到输出侧，缓存里只留 $c$。

与 FlashInfer 的 MLA paged kernel（`BatchMLAPagedAttentionWrapper`）对拍：
它返回的是**隐空间**的输出 $\sum_j p_j c_j$（形状 $[T,H,rank]$），
V 侧吸收由调用方在 kernel 外完成——这正是引擎里 MLA decode 的分工。
本 lab 的调用与结果记在 `results/crater/3.3/20260913-mla/`。

字节账（按配置算，不是实测带宽）：

| 配置 | 每 token 每层 | 相对 MHA |
|---|---:|---:|
| MHA（Hkv=Hq=16） | 8192 B | 1.00× |
| MLA（rank=512+rope64） | **1152 B** | **7.11×** |

| 上下文 | MHA 全模型 | MLA 全模型 | MHA 可并发 | MLA 可并发 |
|---:|---:|---:|---:|---:|
| 4096 | 864.0 MB | 121.5 MB | 16 | 117 |
| 32768 | 6912.0 MB | 972.0 MB | 2 | 14 |
| 131072 | 27648.0 MB | 3888.0 MB | 0 | 3 |
| 1048576 | 221184.0 MB | 31104.0 MB | 0 | 0 |

注意这是**字节账**：吸收路径把投影挪到 Q 与输出侧，省下的是缓存读取，
多出来的算力开销要单独核算，不能由维度比直接推出端到端时间比。

### 4.1 真实 paged kernel 的实测

`labs/L3/paged_decode.py` 用 FlashInfer 的 `BatchDecodeWithPagedKVCacheWrapper`
直接在 kernel 内部按 block table 寻址（物理页随机打乱、尾页按真实长度计）：

| 实现 | ms | GB/s | 相对连续 |
|---|---:|---:|---:|
| 连续（预留最大长度） | 0.0276 | 1216.9 | 1.00× |
| **分页 kernel（FlashInfer）** | **0.0207** | **1623.7** | **1.33×** |
| 框架层 gather + SDPA | 0.2422 | 138.5 | **0.11×** |

**真实分页 kernel 比连续布局还快 1.33×**，因为它的格子不受"按最大长度预留"
的形状约束；框架层 gather 慢 9 倍（0.11×），与上一节那个 5× 量级一致，
来源是多了一次全量读 + 写。`plan`（建 block table 与调度）单独计时 27.5 µs。

正确性覆盖了要求里的每一项：

```
page=16/32/64，长度 [page−1, page, page+1, 2048, 8192, 32768] 同批：
  max|err| vs 连续参照 3.9e-03…7.8e-03（bf16 量级），顶部 1 基本一致
尾页：S=100（尾页 4/16）、S=17（1/16）、S=16（16/16） 全部对拍通过
共享页：两条同长请求指向同一批物理页 → 输出逐位相同
页大小 16/32/64/128 的时间差在 1% 以内（工作集 67 MB < L2，属 L2 带宽），
  256 时慢 11%
```

尾页那一档最值得看：`S=17` 时尾页只有一个有效槽位，kernel 必须按
`last_page_len` 屏蔽其余 15 个；屏蔽错就会读到相邻物理页的数据，
而那种错误在随机权重下不一定立刻显形——所以参照必须是**同一批物理页**拼出的
连续张量，不能另造一份随机 KV。

页大小的取舍还要算碎片：页越小表越长、寻址越碎（本工作集下差别 1%），
页越大内部碎片越多（平均浪费半页）。本 lab 的时间曲线在这个工作集下
被 L2 盖住了，**要量页大小的真实代价，工作集必须大于 L2**。

### 设计取舍

#### prefill 与 decode 是两道题，不该用一个 kernel

| | prefill | decode |
|---|---|---|
| Q 的行数 | $S$ | 1 |
| 复杂度 | $O(S^2)$ | $O(S)$ |
| 算术强度 | $S/2$（3.1） | **1** |
| 瓶颈 | 算力（3.1 实测 85% 峰值） | 带宽（本章实测 ~100%） |
| 并行度来源 | $B\cdot H\cdot\lceil S/B_q\rceil$ | $B\cdot H$，**必须**再加 split-K |
| 优化方向 | 分块、异步、流水（3.2） | 少读（GQA/MLA/量化）、split-K |

两列**没有一行是相同的**。所以引擎里 prefill 和 decode 走不同的 kernel、
不同的调度、甚至不同的机器（PD 分离，L6.4）。
把它们当成"同一个算子的两种输入形状"是这一层最常见的误解。

这也解释了 3.2 那个看似矛盾的结果：同一个库在两种形状上排名相反。
**问"哪个 attention 实现最快"是一个没有答案的问题**，
必须先说是哪一相、什么长度、多大批。

#### GQA 减少 KV 容量，也改变模型参数化

query 头数固定时，减少 KV 头数按比例减少缓存元素，也减少 K/V 投影矩阵的参数。多个 query 头若能复用同一份 K/V 读取，算术强度会随共享程度提高；是否达到该复用取决于 kernel。

这不是对已有 MHA 模型的无损存储变换。GQA 和 MLA 各自有训练与质量约束，不能从缓存字节量直接推断表达能力或端到端加速。MLA 还可通过矩阵吸收避免显式还原完整 K/V；本章已用 DeepSeek-V2-Lite 的真实单层权重把两条路径对拍（§二），但**没有**在完整模型上量端到端收益。

#### split-K 用中间存储和归约换取并行度

split-K 需要把 KV 切段、各段独立算、最后归约。
归约用的是 3.1 那个合并公式，**它是精确的**——所以 split-K 在实数算术下等价；浮点结果仍需按容限验证。

代价只有两项：一点额外的中间存储（每段的 $m,l,O$），
和一次小规模归约。相比它换来的东西（并行度从 8 提到几百），
这笔交易几乎没有反对理由。

这也是为什么 FlashDecoding 能被迅速普遍采用：
和 3.1 §7.1 说的一样，实数等价的优化仍需做数值、边界和端到端回归检查。

### 3.1 把 split-K 写出来：grid、workspace 与不变量

`labs/L3/decode_attention.py` 的 [F] 节把 split-K 写成显式循环
（每段各算 $m,l,O$，最后用 3.1 的合并公式归并），$B{=}1$、$H_q{=}16$、
$H_{kv}{=}2$、$S{=}4096$、$D{=}128$、FP64：

| NSPLIT | grid | workspace | max\|err\| vs 不分段 |
|---:|---:|---:|---:|
| 1 | 16 | 8.1 KB | 0 |
| 4 | 64 | 32.5 KB | 4.5e-17 |
| 8 | 128 | 65.0 KB | 4.2e-17 |
| 32 | 512 | 260.0 KB | 6.2e-17 |

`grid = B·Hq·NSPLIT`、`workspace = NSPLIT×(m+l+O)` 的 fp32 部分状态——
两个数都是打印出来的，不是算出来贴上去的。

不变量（改变切分不改变语义）也逐项查过：

```
page=16/32/64，S=page−1/page/page+1：NSPLIT∈{2,3,8,16} 最大差 3.3e-16…8.9e-16
有效长度 100（S=21/37/69）：切段最大差 4.4e-16
```

**换了切分，有效序列边界与 mask 一个都没变**。真实 kernel 里这份部分状态
会多一个 combine kernel（3.2 的 `labs/L3/fa_loop_variants.py` 里有一份 Triton 实现，
NSPLIT=1/2/4/8 时结果一致，误差 0…9.8e-04 属 bf16 累加）。

代价是显存的：$S{=}65536$、$H_{kv}{=}8$、$D{=}128$、$B{=}1$ 时 KV 是
256 MiB，按 1608.6 GB/s 只读一遍是 **0.167 ms**——这是单步 decode 的下限，
split-K 不改变它，只改变能不能把 SMs 填满。

## 陷阱

1. **只读的工作负载要用只读带宽做分母。** 用 copy 带宽会得到 >100% 的假象。
2. **工作集掉进 L2 会伪造超线性收益。** 第二节的对照展示了这一影响。
   把"在 L2?"做成一列，比每次事后排查便宜。
3. **算术强度依赖假设。** MHA、GQA、量化 KV 与多个 query 位置具有不同复用度。
4. **"哪个 attention 实现最快"没有答案。** 同一个库在 prefill 和 decode 上排名相反
   （FlashInfer：prefill 0.70×，decode 1.83×）。
5. **框架层 gather 不是 paged attention。** 本章测的 5× 是一个具体模拟实现的时间比，
   不是 vLLM 的代价。
6. **单次调用的对比会低估需要 plan 的库。** FlashInfer 的批量接口要先建调度状态。
7. **MLA 的 57× 是按配置算的，不是实测。** 投影回去的矩阵乘会不会吃掉收益，
   本章没有验证。
8. **小工作集测不出带宽上限。** 本章 kv_len=1024 只有 24.5%，
   小数据量下的提交和并行度限制也会降低有效带宽，不能仅据此判断实现优劣。
9. **分页的字节数与连续相同，差别只在寻址。** 说"分页读得更多"不成立；
   代价在 block table 查表、碎片与表长。本章真实 kernel 实测反而快 1.33×。
10. **页大小的代价要在大于 L2 的工作集上量。** 本章 8×8192（67 MB）
    在 96 MiB L2 之内，16–128 的页大小差 1%；换大工作集才会显形。
11. **尾页测试要用同一批物理页拼出的参照。** 自己另造一份随机 KV
    无法暴露"读到了相邻物理页"这类越界。
12. **MLA 的后端返回隐空间输出。** FlashInfer 的 MLA paged kernel 返回
    $\sum_j p_j c_j$（$[T,H,rank]$），V 侧吸收在 kernel 外做；
    按 $[T,H,v]$ 去 reshape 会直接报形状错误。

## 自测题

<details markdown="1">
<summary>1. 为什么 decode attention 的算术强度是 1，而 prefill 的分块实现是 S/2？</summary>

decode 时 Q 只有 1 行：FLOP $=4SD$，读 KV 的字节 $=4SD$（bf16 两字节 × K和V两份），
比值 1。**每读一个 KV 元素，只能做一次乘加**——没有复用。

prefill 时 Q 有 $S$ 行：同一块 KV 被 $S$ 行 Q 复用，
FLOP $=4S^2D$ 而字节仍是 $O(SD)$，比值 $S/2$。

数据复用会提高算术强度。上述简化模型假定单个 query 对历史 KV 的复用较少，未覆盖 GQA、量化与提交开销等因素。
</details>

<details markdown="1">
<summary>2. 你把 KV 头数从 8 降到 4，decode 却只快了 1.3 倍。可能是什么原因？</summary>

预期是 2×（字节减半）。只有 1.3× 说明时间不再由 KV 读取量主导。按可能性排：

- **工作集掉进了 L2**：4 头的 KV 可能小于 96 MiB，量的是 L2 带宽。
  查法：算 $2 \cdot B \cdot H_{kv} \cdot S \cdot D \cdot 2$ 和 L2 比。
- **其它开销占了大头**：kv_len 太短时，kernel launch（2.68 µs）
  和 Q/O 的固定开销不随 KV 头数缩小。查法：把 kv_len 拉长再测。
- **测量里混进了别的算子**：比如 GQA 的 expand 被显式物化了。
  查法：用 `enable_gqa=True` 而不是手工 `expand().contiguous()`。

本章实测在 $B=32$、kv_len=8192 下 8→4 是 4.50×→8.79×，即 1.95×，接近理论值。
</details>

<details markdown="1">
<summary>3. B=1、H=8 时测得较高带宽，能否直接证明采用了 split-K？</summary>

不能。它说明朴素的并行度模型可能不完整，但显存带宽不按“活跃 SM 数/总 SM 数”严格线性分配。应检查实际 kernel 符号、grid 和沿 KV 长度切分的代码；只靠带宽比例不能确定算法。

</details>

<details markdown="1">
<summary>4. GQA 与减少层数，对资源和模型结构的影响有何不同？</summary>

GQA 固定 query 头数，减少 KV 头和 K/V 投影参数；减少层数则同时改变计算深度、权重和每请求状态。两者都可能影响质量，不能只按缓存压缩比例判断哪一个更好。容量可以按结构计算，性能与质量需要对应实验。

</details>

<details markdown="1">
<summary>5. 有人报告"分页 KV 让 attention 慢 5 倍，所以 PagedAttention 不划算"。怎么反驳？</summary>

先问他怎么测的。本章确实测出 5×（0.20×），但那是**在框架层把分散的块
gather 成连续张量再跑普通 attention**——多了一次全量读+写。

真实的 paged attention kernel 在 kernel 内部按 block table 寻址，
K/V 仍然只读一遍，不产生拷贝。5× 是"朴素实现"的代价，不是"分页"的代价。

其次，即使有一些代价，也要和它换来的东西比：不必按最大长度预留显存，
因此能容纳的并发请求数大幅上升（5.2）。
attention 慢一点但并发翻几倍，整体吞吐是涨的。

**这是一个典型的"测了错的东西然后推广结论"**——
应始终区分框架层模拟与真实 kernel 的测量对象。
</details>

<details markdown="1">
<summary>6. split-K 的 grid 与 workspace 怎么算？换切分会不会改变 mask 的语义？</summary>

`grid = B·Hq·NSPLIT`；workspace 是 NSPLIT 份 $(m,l,O)$ 的 fp32 部分状态，
本章实测 $B{=}1,H_q{=}16,S{=}4096,D{=}128$：NSPLIT=4 时 32.5 KB，
NSPLIT=32 时 260 KB。

不会改语义。归并用的是 3.1 的合并公式，实数算术下精确；
本章在 page−1/page/page+1 与有效长度掩码下都验证过，
NSPLIT∈{2,3,8,16} 的差在 1e-16 量级（FP64）。

真正要小心的是**实现**：把局部 $m$ 当全局 $m$、
或者在归并时漏掉某一段而没报错（段数变了但结果没变说明有段没被算进去）。
所以判据要同时看"结果一致"和"grid/workspace 随 NSPLIT 变化"。

<summary>7. 为什么真实 paged kernel 能比连续布局更快？</summary>

因为连续布局通常要**按最大长度预留**，形状被最长的那条请求绑死；
paged kernel 按 block table 取页，形状随实际长度。
本章实测 8×8192、Hkv=2、D=128：分页 0.0207 ms vs 连续 0.0276 ms（1.33×）。

它不省字节（两者读的 KV 一样多），省的是**形状自由度**与
"不用为了留余量而扫过没用的槽位"。
这与"分页是纯代价"的直觉相反——代价在表长与碎屏，
不在读取量。
</details>
