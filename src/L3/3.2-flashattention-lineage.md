## 机制拆解

### FA1 之后还剩什么：三个可测的瓶颈

#### 并行度不够（FA1 → FA2 的主要改动）

FA1 只沿 **batch × head** 切分：并行单元数 $= B\cdot H$。
这张卡有 170 个 SM，$B\cdot H < 170$ 时一部分 SM 无事可做，**与序列多长无关**。
FA2 增加了沿**查询块**的切分，并行单元数变成 $B\cdot H\cdot\lceil S/B_q\rceil$。

判据很直接：固定 $S$，把 $B\cdot H$ 从远小于 SM 数扫到远大于。
如果只沿 $B\cdot H$ 切分，达到的 TFLOP/s 要到 $B\cdot H\approx 170$ 才饱和。

$S=4096$, $D=128$, bf16, causal：

| B·H | 占 SM 比例 | ms | TFLOP/s | 相对峰值 |
|---:|---:|---:|---:|---:|
| 1 | 0.01× | 0.040 | **107.7** | **46.4%** |
| 2 | 0.01× | 0.066 | 130.3 | 56.1% |
| 4 | 0.02× | 0.120 | 142.9 | 61.6% |
| 8 | 0.05× | 0.293 | 117.1 | 50.5% |
| 16 | 0.09× | 0.456 | 150.7 | 65.0% |
| 32 | 0.19× | 0.786 | 174.9 | 75.4% |
| 64 | 0.38× | 1.433 | 191.8 | 82.7% |
| 128 | 0.75× | 2.732 | 201.2 | 86.7% |
| 170 | 1.00× | 3.592 | 203.3 | 87.6% |
| 512 | 3.01× | 10.607 | 207.3 | 89.4% |

**$B\cdot H = 1$ 就已经跑到峰值的 46.4%。** 如果并行度只来自 $B\cdot H$，
一个并行单元占 1/170 的 SM，应该在 0.6% 附近，不可能是 46%。
所以 PyTorch 用的这个 kernel **确实沿序列切分了**——它是 FA2 之后的形态。

固定总工作量、把并行度在 $B\cdot H$ 与 $S$ 之间挪动，也能看到同一件事：

| B·H | S | 总 FLOP(G) | ms | TFLOP/s |
|---:|---:|---:|---:|---:|
| 4 | 16384 | 274.9 | 1.755 | 156.6 |
| 16 | 8192 | 274.9 | 1.533 | 179.3 |
| 64 | 4096 | 274.9 | 1.437 | 191.2 |
| 256 | 2048 | 274.9 | 1.438 | 191.1 |

同样的 FLOP，$B\cdot H$ 从 256 降到 4 只慢 1.22×。
只沿 $B\cdot H$ 切分的实现在这里会慢几十倍。

::: note 待解释的非单调点
$B\cdot H = 8$ 那一行（117.1）比 $B\cdot H = 4$（142.9）**更慢**，
打断了整体的上升趋势。重跑该现象仍存在。
最可能是 wave quantization（2.6 里量过：1020→1021 个 block 慢 16%），
该解释尚未验证。检查方法：用 ncu 读 `sm__warps_active` 的分布，
或者用 2.6 那个 `%smid` 自制 profiler 看 block 到 SM 的分配。
在验证之前，该异常点仅作为待测现场记录。
:::

#### 因果 mask 的收益没有拿满

因果 attention 只需算下三角，理想省一半。块粒度下有个可算的损失：
设 $N = S/B_k$ 个 key 块，query 块 $i$ 要算 $i+1$ 个 key 块，于是

$$\frac{\text{因果块数}}{\text{非因果块数}} = \frac{N(N+1)/2}{N^2} = \frac{1}{2} + \frac{1}{2N}$$

$S$ 越大，$1/(2N)$ 越可以忽略。实测（$D=128$，假设 $B_k=128$）：

| S | 非因果 ms | 因果 ms | 实测比 | 块粒度预测 | 差额 |
|---:|---:|---:|---:|---:|---:|
| 512 | 0.060 | 0.046 | 0.760 | 0.625 | +0.135 |
| 1024 | 0.113 | 0.084 | 0.746 | 0.562 | +0.183 |
| 2048 | 0.215 | 0.154 | 0.714 | 0.531 | +0.183 |
| 4096 | 0.420 | 0.294 | 0.699 | 0.516 | +0.183 |
| 8192 | 0.832 | 0.572 | 0.688 | 0.508 | +0.180 |
| 16384 | 1.661 | 1.101 | 0.663 | 0.504 | **+0.159** |

实测比一路下降，方向和预测一致——说明**整块在未来的块确实被跳过了**。
但差额没有收敛到 0：$S=16384$ 时块粒度只该贡献 0.004，实测仍高出 0.16。

块数模型不能解释全部差额。一个待验证的原因是负载不均：
因果下 query 块 $i$ 的工作量正比于 $i+1$，最后一个块是第一个块的 $N$ 倍。
如果块按简单顺序分给 SM，整个 kernel 要等最重的那几个块结束。
（这也正是后续代际反复调整调度的原因之一。）

差额在 $S=1024..8192$ 上稳定在 **+0.18**，几乎不随 $S$ 变——
这种"常数偏移"的形状本身就提示是结构性原因而不是噪声。

判据：用 2.6 那个 `%smid` + `%globaltimer` 的自制 profiler 记录每个 block 的起止，
看尾部是否被少数重块拖住。**在做这件事之前，上面那段只是假设。**

### 1.3 exp 有多贵：FA4 的出发点

FA1 把 $S\times S$ 从 DRAM 里赶走之后，attention 就落到算力一侧了（3.1 实测 85% 峰值）。
那么下一个问题是：算力这一侧，**softmax 和矩阵乘各占多少**？

矩阵乘走 tensor core，softmax 的 `exp` 走 SFU（特殊功能单元）。
这两条流水的宽度完全不同。用 1.2 的同一套方法测（8 条独立链，测吞吐不是延迟）：

```
运算                         G op/s 每 SM 每周期     相对 FMA
--------------------------------------------------------------------
__expf  (SFU 快速)           7334.4            17.92         0.129×
exp2f   (SFU 原生)           7441.6            18.19         0.131×
expf    (精确)               5799.1            14.17         0.102×
__frcp_rn (SFU)                2836.8             6.93         0.050×
FMA     (普通流水)        56918.7           139.10         1.000×
```

FMA 测出 139.10/clk/SM，而 FP32 FMA 的硬件发射率是确定的
（每 SM 128 条 FP32 lane，即 128/clk/SM）。用它反标定真实频率：

```
标定：FMA 实测 139.10/clk/SM，硬件确定值 128/clk/SM
      => 被测区间真实频率约 2.62 GHz（标称 2.41 GHz）

运算                 标定后 每 SM 每周期
--------------------------------------------
__expf  (SFU 快速)                  16.49
exp2f   (SFU 原生)                  16.73
expf    (精确)                      13.04
__frcp_rn (SFU)                        6.38
FMA     (普通流水)               128.00
```

标定之后 `__expf` 与 `exp2f` 都落在 **16/clk/SM**——正是 SFU 的硬件宽度
（每个处理分区 4 个 SFU × 4 个分区）。这个自洽性说明标定是对的。

::: note 用已知指令发射率估算运行时钟
标称 boost 时钟（2.41 GHz）不等于被测区间的真实频率（2.62 GHz）——
L1.2 中也观察到频率采样时机对结果的影响。
可以通过发射率已知的运算估算被测区间的时钟频率，再与其他测量交叉检查。
判据是标定之后别的量应该落到整数上：这里 16.49 和 16.73 都指向 16。
:::

对照 1.2 在同一张卡上实测的 bf16 tensor core **511 FLOP/clk/SM**（标称 512）：

$$\frac{511}{16} \approx 31$$

**一次 `exp` 的时间里，tensor core 能做约 31 次浮点运算。**

每个打分元素 $S[i,j]$ 需要：矩阵乘一侧 $4D$ 次浮点运算（$QK^\top$ 贡献 $2D$，$PV$ 贡献 $2D$），
softmax 一侧 1 次 `exp`（还有 max/加/乘若干，这里只算 `exp`，是下界）：

| D | 矩阵乘 (clk) | exp (clk) | exp 占比 |
|---:|---:|---:|---:|
| 32 | 0.2505 | 0.0606 | **24.2%** |
| 64 | 0.5010 | 0.0606 | 12.1% |
| 128 | 1.0020 | 0.0606 | 6.1% |
| 256 | 2.0039 | 0.0606 | 3.0% |

$D=128$（最常见）时 `exp` 只占 6.1%，看起来不多。
但注意两件事：

1. 这是**下界**——只算了 `exp`，没算 max、求和、修正因子、除法。
2. 这个比值会随硬件代际**变差**：tensor core 每代大幅加宽，SFU 基本不变。

::: warning 第 2 条仅在单卡上完成单点实测
"tensor core 变宽而 SFU 不变"属于**未跨代验证**的趋势，需后续实测确认。
要证实它，需要在至少两代卡上跑同一个 `exp_throughput.cu`，
比较 (tensor core FLOP/clk/SM) / (SFU exp/clk/SM) 这个比值。
手上 worldvln 是 sm_89、spark 是 sm_121，可以补两个点。
**在补上之前，本章只断言 sm_120 上的 31 这个数。**
:::

### 四代各自解决什么

把上面三个可测的瓶颈和各代的改动对上。**带 ✅ 的为硬件实测项，
带 ⚪ 的为源码分析推导、在当前硬件上保持 UNVERIFIED 的项。**

| 代 | 针对的矛盾 | 主要手段 | 本章证据 |
|---|---|---|---|
| **FA1** | $S\times S$ 过 DRAM，算术强度被钉在 $D/3$ | 分块 + online softmax + 反向重算 | ✅ 3.1 全章 |
| **FA2** | ① 并行度只有 $B\cdot H$；② 非矩阵乘运算太多；③ warp 间共享内存往返 | 增加序列维切分；调换内外循环（Q 在外）；减少 rescale 次数 | ✅ 并行度（1.1 节）；⚪ 后两项 |
| **FA3** | Hopper 的异步能力闲置：TMA、wgmma、warp specialization | 生产者/消费者 warp 分工、ping-pong 调度、FP8 | ⚪ **本卡不支持（cc 必须 9.x）** |
| **FA4** | tensor core 与 SFU 的宽度差越拉越大 | 探索不同执行单元上的 `exp` 近似；具体实现待源码核对、更细的软件流水 | ⚪ 本卡不支持（cc 需 9.x/10.x/11.x）；但 §1.3 的 31× 是它的动机 |

### 2.1 FA2 的循环顺序为什么要换

FA1 外层遍历 K/V 块、内层遍历 Q 块；FA2 反过来。
3.1 里的 `flash_like` 实现采用的正是 FA2 的顺序：

{{src:labs/L3/online_softmax.py:190-200}}

差别在**谁需要在外层维护状态**：

- **Q 在外**（FA2）：$m$、$l$、$O$ 累加器都属于当前 Q 块，
  在内层循环里一直待在寄存器/共享内存里，最后写一次 $O$。
- **K/V 在外**（FA1）：每个 K/V 块要对**所有** Q 块更新一次 $m,l,O$，
  这些状态没法一直留在片上，要反复读写。

所以换方向之后，$O$ 的读写次数从 $O(N_q N_k)$ 降到 $O(N_q)$。
这是 FA2 论文里"减少非矩阵乘运算与共享内存往返"的具体含义。

该差异在当前环境为 UNVERIFIED——对比验证需要两个独立 kernel 对照，
而当前环境仅部署了 FA2 之后的实现。3.1 的消融建议 4 提供了 Python 版本的验证路径
把方向换过来，那能验证"结果不变"，但验证不了访存差异
（python 版本的中间量本来就在显存里）。

### 2.2 FA4 与 §1.3 的联系

关于 FA4 如何实现指数函数，本章缺少可核对的具体源码，不能据此断言使用了 tensor core。仅从资源模型看，
既然 tensor core 有 31 倍于 SFU 的吞吐，把一部分 `exp` 的工作挪到
tensor core 上做，即使算法上更绕，总时间也可能更短。

§1.3 那个 31 就是这个取舍的分母。它只是 sm_120 微基准下的资源比，不能直接解释另一架构上的 FA4 实现，
但 FA4 依赖更高算力特性，在当前硬件上保持 UNVERIFIED，其实际收益未行实测。

### 四代各自解决什么

把上面三个可测的瓶颈和各代的改动对上。**带 ✅ 的为硬件实测项，
带 ⚪ 的为源码分析推导、在当前硬件上保持 UNVERIFIED 的项。**

| 代 | 针对的矛盾 | 主要手段 | 本章证据 |
|---|---|---|---|
| **FA1** | $S\times S$ 过 DRAM，算术强度被钉在 $D/3$ | 分块 + online softmax + 反向重算 | ✅ 3.1 全章 |
| **FA2** | ① 并行度只有 $B\cdot H$；② 非矩阵乘运算太多；③ warp 间共享内存往返 | 增加序列维切分；调换内外循环（Q 在外）；减少 rescale 次数 | ✅ 并行度与循环顺序（1.1、2.1 节，自写 fa1/fa2 两个 kernel 对照）；✅ rescale 次数（2.2 节小数值） |
| **FA3** | Hopper 的异步能力闲置：TMA、wgmma、warp specialization | 生产者/消费者 warp 分工、ping-pong 调度、FP8 | ⚪ 本卡不支持（cc 必须 9.x）；已按固定 commit 标出 barrier/phase/warp 分工的源码位置（2.2 节） |
| **FA4** | tensor core 与 SFU 的宽度差越拉越大 | 条件 rescale、FMA 上的软件 exp、TMEM、2-CTA | ⚪ 本卡不支持（cc 需 9.x/10.x/11.x）；源码位置 + rescale/exp 的小数值验证见 2.2 节，性能不给结论 |

#### §1.3 那个 31 在 FA4 里是什么角色

FA4 把 `exp` 从 SFU 挪到 FMA 上（2.2 节的源码与论文原文），
所以 §1.3 那个比值不是"tensor core 替 exp"，而是**SFU 与 FMA 各自的余量**：
在矩阵乘把 SFU 喂满的形状里，FMA 发射口还有空，把 exp 搬过去能提高总吞吐。

本卡上的微基准给的是反面对照：孤立看，软件 exp 只有 SFU 的
$6.9/16.65 \approx 0.41$ 倍，混用也不相加（10.3 < 16.65）。
这说明**这条路只在特定瓶颈组合下成立**，不是"FMA 更宽所以更快"。
FA4 依赖的数据中心特性（TMEM、2-CTA、更宽的 MM）在 RTX 5090 D 上不可用，
其实际收益保持 `UNVERIFIED`。

### 接到真实模型：attention 占总体多少

Qwen3-1.7B（28 层、Hq=16、Hkv=8、D=128、`attn_implementation=sdpa`）
在 2048 token 输入上按 CUDA kernel 汇总：

```

attention 类 1.129 ms 占 5.5%
GEMM 类      16.315 ms 占 79.3%
其它         3.125 ms 占 15.2%
   7.181 ms  void cutlass::Kernel2<cutlass_80_tensorop_bf16_s16816gemm_relu_...>
   0.913 ms  void pytorch_flash::flash_fwd_splitkv_kernel<...>
```

**这个形状下 attention 只占 5.5%。** 也就是说：把一个 attention kernel
优化 20%，整模型只快 1.1%。组件提升与端到端提升之间隔着一个随 $S$、
batch、dtype 变化的系数——**先量这个系数，再决定要不要优化**。

真实模型允许的 mask/layout 也有约束：GQA 原生（`enable_gqa`）可用；

（mem-efficient），因为 FlashAttention 类内核不接受任意 4D mask。
这条在服务里很实际：要用自定义 mask 就得接受另一条较慢的路径。

### 设计取舍

#### 为什么四代都在改调度，而不是改算法

FA1 之后，算法本身（分块 + online softmax）**没有再变过**。
FA2/3/4 改的全是：怎么切分、谁在外层、哪些 warp 干什么、
用哪条流水做哪一步。

原因在 3.1 §7.1 已经埋下：分块之所以能被普遍采用，
是因为它**结果不变**。任何一代只要还保持这个性质，
就可以直接替换掉上一代，不需要任何人重新评估质量。
一旦某一代改了数值语义，就必须重新经历完整的质量验证流程。

**代价是每一代都强绑定硬件。** 本章开头那个版本门就是账单：
FA3 只能跑在 cc 9.x，FA4 排除了 12.0。
上层框架因此必须维护一个"按硬件选实现"的分发层——
2.0 §3 的 dispatcher、0.3 的后端选择、3.3 会讲的 vLLM attention backend，
都是这一层的不同侧面。

#### 优化方向由实际资源瓶颈决定

FA 的演进史给出了一条可复用的判据：**当算法已经把某个资源用满之后，
下一步的收益来自把"闲着的那部分硬件"用起来，而不是继续优化那个已经用满的资源。**

- FA1 用满了片上存储 → 但 SM 有一半闲着（并行度不够）→ FA2
- FA2 用满了 SM → 但 Hopper 的异步单元闲着 → FA3
- FA3 用满了 tensor core → 但 SFU 成了新瓶颈（§1.3 的 31×）→ FA4

每一步都要先**量出哪个部件闲着**。这正是 2.6 那一整章的方法：
先有计数器，再谈优化。缺乏测量的直觉猜测，
在这条链上一次都没有出现过。

## 工程实现 · 自己写一遍

### FA1 与 FA2 的循环顺序：两个 kernel 的实测

FA1 外层遍历 K/V 块、内层遍历 Q 块；FA2 反过来。
差别在**谁需要在外层维护状态**：

- **Q 在外**（FA2）：$m$、$l$、$O$ 累加器都属于当前 Q 块，
  在内层循环里一直待在寄存器/共享内存里，最后写一次 $O$。
- **K/V 在外**（FA1）：每个 K/V 块要对**所有** Q 块更新一次 $m,l,O$，
  这些状态没法一直留在片上，要反复读写。

所以换方向之后，$O$ 的读写次数从 $O(N_q N_k)$ 降到 $O(N_q)$。

这条以前只能读论文。现在写两个只差**网格划分**的 Triton kernel
（`labs/L3/fa_loop_variants.py`）：`fa1` 的序列维循环留在 program 内部，
`fa2` 每个 query 块一个 program。$S{=}4096$、$D{=}128$、bf16、causal：

| $B\cdot H$ | fa1 grid | fa2 grid | fa1 ms | fa2 ms | fa1 TFLOP/s | fa2 TFLOP/s |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 1 | 32 | 5.034 | 0.311 | 0.9 | 13.8 |
| 4 | 4 | 128 | 5.080 | 0.316 | 3.4 | 54.4 |
| 16 | 16 | 512 | 5.127 | 0.689 | 13.4 | 99.7 |
| 64 | 64 | 2048 | 5.359 | 2.182 | 51.3 | 126.0 |
| 170 | 170 | 5440 | 5.566 | 5.457 | 131.2 | 133.8 |
| 256 | 256 | 8192 | 10.766 | 8.123 | 102.1 | 135.4 |

**grid 是直接读出来的**，不是推断：`fa1` 的 grid 恒等于 $B\cdot H$，
`fa2` 是 $B\cdot H\cdot\lceil S/B_M\rceil$。$B\cdot H=1$ 时前者只用到
170 个 SM 里的 1 个（0.9 TFLOP/s），后者靠 32 个 query 块拿到 13.8。
两者在 $B\cdot H\approx170$ 处相遇，之后 fa1 因为每个 program 串行处理太多
query 块而开始掉。

$B\cdot H=256$ 时 fa1 反而变慢（10.766 ms，比 170 时差 1.9×）：
grid 是 256 而 SM 只有 170，多出来的 86 个 program 要等第一波结束。
这是**波量化**（2.6 量过：1020→1021 个 block 慢 16%），不是并行度不够。

### 条件 rescale 与软件 exp 算法验证

**（二）两条能验证的机制。** `labs/L3/fa34_mechanisms.py`：

*条件 rescale*：当块最大值没有超过运行最大值时，修正因子 $e^{m_{old}-m_{new}}$
恰好是 1。$S{=}2048$、$H{=}4$、块长 64 的随机打分上，262144 次
"（块, 行）"判定中：

```
需要抬基准（m_new > m_old）： 33473 次（12.8%）
不需要抬基准（因子恰好为 1）：228671 次（87.2%）
始终 rescale vs 仅在 d>0 时 rescale：逐位相同 = True，最大差 = 0.000e+00
```

**87% 的 rescale 是白做的，跳过它们结果逐位不变**——因为乘 1.0 是精确的。
再做一个阈值延迟版本（这是本章自己的对照，不是论文里的条件）：
阈值 1e-3 / 1e-2 / 1e-1 时相对误差 3.3e-16 / 4.4e-16 / 7.8e-16，
**在这一档上省下的 rescale 是免费的**；阈值再大就要开始付精度。

*软件 exp* 放进 attention 的误差（与 FP64 参照比，$S{=}1024$、$D{=}64$、causal）：

| exp 实现 | 相对误差 | top-1 一致 |
|---|---:|---|
| 硬件 exp2 | 9.3e-07 | 是 |
| 软件 exp2 6 阶 | 1.6e-06 | 是 |
| 软件 exp2 4 阶 | 2.2e-05 | 是 |

低阶多项式把误差放到 2e-05 量级，对 bf16 的注意力输出没有影响
（bf16 本身是 1e-2 档），但要报出来。

::: note 本节哪些是实测、哪些是文献
实测：源码的 file:line 与 SHA256、rescale 的跳过比例与逐位不变、
软件 exp 的误差、三个架构上的 exp/FMA 吞吐。
文献（未在本卡验证）：FA4 的收益来自"矩阵乘挤满 SFU 而 FMA 空闲"这一具体形状，
以及 2-CTA 对共享内存流量的削减幅度。
:::

## 陷阱

1. **别用「相对峰值」判断 kernel 好坏而不看形状。** 本章 $B\cdot H=1$ 时 46.4%，
   $B\cdot H=512$ 时 89.4%，同一个 kernel。
2. **标称 boost 时钟不是被测区间的真实频率**（本章 2.41 vs 标定出的 2.62 GHz）。
   用一个硬件发射率已知的运算（FP32 FMA = 128/clk/SM）反标定。
3. **测吞吐必须用独立链。** `CHAINS=1` 测出来的是延迟。
4. **CUDA 13 起 `cudaDeviceProp` 没有 `clockRate`**，要用
   `cudaDeviceGetAttribute(..., cudaDevAttrClockRate, ...)`。
5. **因果的时间比不会等于 0.5。** 本章 $S=16384$ 实测 0.663，
   块粒度只解释 0.004，其余未验证。**不要把"接近一半"当成"拿满了收益"。**
6. **FA3/FA4 不是"更新所以更好"，它们有硬性的 cc 门槛。**
   sm_120 两者都不支持。写代码时要查 `is_fa_version_supported`，
   不要假定装上就能用。
7. **FlashInfer 在单条定长 prefill 上不占优不代表它慢。** 它的目标是变长批 + 分页 KV。
   拿错场景比较是常见误用。
8. **非单调的数据点要么解释、要么标注。** 本章 $B\cdot H=8$ 那一行没解释，
   已明确标为不可引用。
9. **软件 exp 不是"FMA 更宽所以更快"。** 三个架构上孤立测量都比 SFU 慢
   （6.9–8.6 vs 16.7–20.1 /clk/SM），混用也不相加（10.3–12.6）。
   它只在"SFU 被矩阵乘喂满、FMA 发射口空闲"的形状里可能划算。
10. **条件 rescale 的门槛是"因子恰好为 1"**，不是"差不多为 1"。
    前者逐位不变（本章实测 87.2% 的判定属于这一类），后者要付精度。
11. **跨库调 attention 要按实际签名。** vLLM 自带 FA2 的 `max_seqlen_q`
    在 `cu_seqlens_q` 之前，照抄上游文档调用会在 `cu_seqlens_k` 报类型错误。
12. **量化的 TFLOP/s 不能和 bf16 的并列。** SageAttention 按 INT8 计算，
    用 bf16 的 FLOP 数折算会得到超过本卡 bf16 上限的数字；
    与它一起报的必须是量化误差与质量。

## 自测题

<details markdown="1">
<summary>1. 你测到某个 attention kernel 在 B·H=1 时达到峰值的 46%。这能说明什么？</summary>

能说明它**沿序列维切分了**，不只沿 batch×head。

如果并行度只来自 $B\cdot H$，那么 $B\cdot H=1$ 意味着只有 1 个并行单元，
在 170 个 SM 上最多用掉 1/170 ≈ 0.6%。测出 46% 与之矛盾。

不能说明的是：具体切成了多少块、用了什么调度、是不是 FA2 的官方实现。
要确认这些得看 kernel 名或反汇编（2.2 的方法）。
</details>

<details markdown="1">
<summary>2. 为什么用 FP32 FMA 来标定时钟，而不是直接用 <code>nvidia-smi</code> 报的频率？</summary>

因为要的是**被测 kernel 运行那一小段时间内的实际频率**，
而不是空闲时或平均的频率。GPU 会随负载和温度调频，
`nvidia-smi` 采样点和 kernel 执行区间对不上。

FP32 FMA 的硬件发射率是结构决定的（每 SM 128 条 FP32 lane，1 op/clk/lane），
不随频率变化。所以「实测 ops/s ÷ 128 ÷ SM 数」就是真实频率。

自检方法：标定之后别的量应该落在硬件的整数上。本章标定后
`__expf` 是 16.49、`exp2f` 是 16.73，都指向 SFU 宽度 16——这说明标定合理。
如果标定后出来 11.3 这种数，说明标定或测量有问题。
</details>

<details markdown="1">
<summary>3. exp 只占矩阵乘时间的 6%（D=128），为什么还值得为它专门做一代优化？</summary>

三个理由，前两个本章有数据，第三个没有：

1. **6% 是下界。** 只算了 `exp`，没算 max、求和、修正因子的乘法、最后的除法。
   真实的非矩阵乘开销更高。
2. **$D$ 小时占比迅速上升**：$D=64$ 是 12.1%，$D=32$ 是 24.2%。
   而 MLA、GQA 等结构会让有效 $D$ 变小（3.3）。
3. **代际趋势**：tensor core 每代加宽，SFU 基本不变，比值会持续恶化。
   **这一条本章只测了一个点，是待验证项。**

另外 6% 放在一个已经跑到峰值 85% 的 kernel 上，
意味着它占了剩余可优化空间的相当一部分。
</details>

<details markdown="1">
<summary>4. 因果 attention 实测时间比是 0.663，块粒度只能解释 0.004。你会怎么查剩下的 0.16？</summary>

先看这个差额的形状：它在 $S=1024..8192$ 上稳定在 +0.18，几乎不随 $S$ 变。
**常数偏移提示结构性原因，不是随 $S$ 增长的某种开销。**

按可查性排：

1. **负载不均**（首要竞争假设）：query 块 $i$ 的工作量 $\propto i+1$。
   查法：用 `%smid`+`%globaltimer` 记录每个 block 起止，看尾部是否被重块拖住。
2. **固定开销不halve**：Q/O 的读写、kernel launch、尾块处理。
   查法：把 $D$ 加大（矩阵乘占比上升），看差额是否下降。
3. **两条路径走了不同 kernel**：causal 与非 causal 可能命中不同的模板实例。
   查法：nsys 抓 kernel 名对比（2.6 的方法）。

第 3 条最便宜，应该先做——如果 kernel 名就不同，前两条的分析前提都不成立。
</details>

<details markdown="1">
<summary>5. 有人建议"升级到 FA3 提升性能"。在动手之前你要先确认什么？</summary>

先确认**硬件支不支持**。`vllm_flash_attn` 的门是明写的：
FA3 要求 compute capability **family 9.x**（Hopper）。
本章在 sm_120 上查询直接得到
`FA3 is only supported on devices with compute capability 9.x`。

所以在消费级 Blackwell、Ada、Ampere 上，"升级到 FA3"这句话没有意义。
FA4 的门是 9.x/10.x/11.x，同样排除 12.0。

确认支持之后还要问：你的瓶颈是不是 FA3 针对的那个？
FA3 优化的是 Hopper 的异步单元利用率。如果你的负载是
小 batch decode（3.3），瓶颈根本不在这里，换代不会有收益。
</details>

<details markdown="1">
<summary>6. 你的 kernel 在 B·H=1 时只跑到峰值的 0.4%，换一个网格划分后到 6%。这说明什么？</summary>

说明后者的 grid 里含**序列维**。本章两个只差网格划分的 Triton kernel：
`fa1` 的 grid 恒等于 $B\cdot H$，`fa2` 是 $B\cdot H\cdot\lceil S/B_M\rceil$。
$B\cdot H=1$、$S=4096$ 时前者 5.034 ms（0.9 TFLOP/s），后者 0.311 ms（13.8）。

要注意的是：能说明的只是"grid 里有没有序列维"，
不能反推具体切分、调度或实现来源。要看 kernel 名与资源（本章第 3.1 节）。
</details>

<details markdown="1">
<summary>7. 为什么"跳过不需要的 rescale"是精确的，而"延迟小幅度 rescale"不是？</summary>

块最大值没有变大时，$m_{new}=m_{old}$，修正因子 $e^{m_{old}-m_{new}}=e^0=1$。
乘 1.0 在浮点里是精确操作，所以跳过它逐位不变——本章实测
262144 次判定里 87.2% 属于这一类，两种写法逐位相同、最大差 0。

阈值版本不同：当 $m_{new}-m_{old}=\delta>0$ 时因子是 $e^{-\delta}\ne 1$，
跳过就等于把这一段的贡献按错误的比例缩放。$\delta$ 小的时候误差也小
（本章阈值 1e-3 时相对误差 3.3e-16），但它**不是零**，
需要误差预算而不是"反正很小"。
</details>

<details markdown="1">
<summary>8. 要在自己的服务里选一个 attention 后端，你会先量哪三件东西？</summary>

1. **形状与相**：prefill 还是 decode，$S$、$B$、$H_{kv}$、$D$ 各是多少。
   本章同一库在 prefill 与 decode 上排名相反（FlashInfer 0.41 vs 0.295 的
   prefill，decode 上 1.83× 领先）。
2. **后端在目标形状上是否可用**：mem-efficient 在 $H_q\ne H_{kv}$ 时直接
   没有 kernel；flash 类不接受任意 4D mask（本章实测会掉到
   `fmha_cutlassF_..._sm80`）。
3. **attention 在整体里占多少**：本章 Qwen3-1.7B 在 2048 token 上只有 5.5%，
   这时把 attention 优化 20% 换不到 1.1% 的端到端。

顺序不能反——先选后端再量形状，等于用排行榜回答一个取决于形状的问题。
</details>
