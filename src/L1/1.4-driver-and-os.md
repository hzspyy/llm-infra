## 本章回答三个问题

1. CPU 提交一次 kernel 时做了哪些工作？CPU 时间统计能说明什么，又不能说明什么？
2. `libcuda.so` 和 `libcudart.so` 到底是什么关系？为什么 L0.1 里能用 pip 换掉半个工具链？
3. 统一内存（UVM）让编程变简单，代价是多少？

先分清两个容易混淆的“内核”：GPU kernel 是在 GPU 上执行的函数，
操作系统内核则负责设备、内存和权限管理。CPU 调用 CUDA API 提交工作，
通常不需要在该调用返回前等 GPU 完成；遇到同步操作时才可能等待。
下文把初始化、提交、执行和同步分开讨论。

## 机制拆解

### CUDA 工具链组件由不同软件包提供

L0.1 的陷阱一节里，我们用 pip 把 `nvcc`、`cicc`、`ptxas` 全换成 13.0.88，
却没有动驱动。为什么可以？看链接关系（实测）：

```
$ ldd .../torch/lib/libtorch_cuda.so | grep -E "cuda|nvidia"
libcudart.so.13 => .../site-packages/nvidia/cu13/lib/libcudart.so.13     ← pip wheel
libcusparse.so.12 => .../site-packages/nvidia/cu13/lib/libcusparse.so.12 ← pip wheel
libnccl.so.2 => .../site-packages/nvidia/nccl/lib/libnccl.so.2           ← pip wheel
...

$ ls -la /usr/lib/x86_64-linux-gnu/libcuda.so*
libcuda.so   -> libcuda.so.1
libcuda.so.1 -> libcuda.so.580.95.05                                     ← 驱动安装的
```

**两条完全不同的来源**：

- **`libcudart`（Runtime API）与所有数学库**：来自 pip wheel，
  跟着你的 venv 走。所以每个项目可以有自己的 CUDA 版本。
- **`libcuda`（Driver API）**：版本号 `580.95.05` **就是驱动版本**。
  它由驱动安装（容器里由 `nvidia-container-toolkit` 从宿主机注入），
  **不能用 pip 换**。

内核模块本身：

```
$ cat /proc/driver/nvidia/version
NVRM version: NVIDIA UNIX Open Kernel Module for x86_64  580.95.05  Release Build
GCC version:  gcc version 13.3.0 (Ubuntu 13.3.0-6ubuntu2~24.04)
```

`libcuda.so.580.95.05` 与 `NVRM 580.95.05` **版本必须严格一致**——
它们是同一次驱动安装的两半。这就是"驱动版本"的真正含义。

**向后兼容规则**：新驱动能跑旧 runtime（`libcuda` 580 能带 `libcudart` 12.x），
反过来不行。升级前应检查目标 runtime 对驱动的最低要求及兼容条件；不要默认必须修改共享机器的驱动。

### 设备节点：ioctl 的入口

```
$ ls -la /dev/nvidia*
crw-rw-rw- 1 root root 195, 254  /dev/nvidia-modeset
crw-rw-rw- 1 root root 505,   0  /dev/nvidia-uvm         ← 统一内存
crw-rw-rw- 1 root root 505,   1  /dev/nvidia-uvm-tools
crw-rw-rw- 1 root root 195,   0  /dev/nvidia0            ← 第 0 号 GPU
crw-rw-rw- 1 root root 195, 255  /dev/nvidiactl          ← 控制通道
/dev/nvidia-caps/                                         ← MIG 能力节点
```

**容器里的 GPU 就是这几个设备节点 + 注入的 `libcuda.so`。**
`docker run --gpus all` 做的事就是：把这些字符设备挂进容器，
把宿主机的 `libcuda.so.<版本>` 和 `nvidia-smi` bind-mount 进去。

这也解释了一个常见故障：容器里 `nvidia-smi` 能跑但 `torch.cuda.is_available()` 是 False——
通常是 `/dev/nvidia-uvm` 没挂进来（UVM 是 torch 初始化必须的）。

### 一次性启动成本：为什么引擎必须常驻

实测（crater）：

| 阶段 | 耗时 | 做了什么 |
|---|---|---|
| `import torch` | **582.1 ms** | 加载几百 MB 的 .so、注册几千个算子 |
| `torch.cuda.init()` | **160.0 ms** | `cuInit`：枚举设备、与驱动握手 |
| 首次分配（建 context） | **80.8 ms** | 创建 CUDA context：分配页表、命令环、本地内存池 |
| 第一个 kernel | **15.1 ms** | 模块加载 + 可能的 JIT |
| **合计** | **≈ 838 ms** | |

**每个进程都要付一遍这 0.8 秒。** 这就是为什么：

- 推理引擎是**常驻进程**，不是每请求一进程（对比传统 CGI）
- vLLM 的 EngineCore 是**长生命周期**的（L0.1 第 7 阶段的 `run_busy_loop`）
- RL 训练里 rollout 引擎要用 **sleep/wake** 而不是重启（L7.5）
- 弹性伸缩时新副本的**冷启动**至少 1 秒起步，还没算加载权重（L8.2）

### launch 开销：与数据量无关

```
[B] 单次 launch 的 host 侧耗时（不等 GPU，只看下发）
    空操作(python 基线)            0.050 µs
    1 元素 add_                    2.760 µs   (扣掉基线 2.710)
    4M 元素 add_                   2.750 µs   (扣掉基线 2.700)
    512x512 matmul                 5.660 µs   (扣掉基线 5.610)
    torch.empty(1024)              1.110 µs   (扣掉基线 1.060)
```

**1 个元素和 400 万个元素的下发耗时完全一样（2.76 vs 2.75 µs）。**
launch 开销是**每次调用**的固定成本，与工作量无关。

推论：**把很多小算子融合成一个大算子，收益不只是访存，还有 launch 次数。**
L0.1 实测 decode 每步 444 次 launch × 2.68 µs ≈ 1.19 ms，占墙钟 27%。

`matmul` 的 5.66 µs 比 `add_` 高一倍——因为 cuBLAS 要做启发式选 kernel、
准备 workspace。**不是所有 launch 都一样贵。**

### CPU 时间统计：观察与限制

先读取 `/proc/self/stat` 的 utime / stime，分别记录用户态和内核态 CPU 时间。
这是一种粗粒度统计，不是系统调用跟踪。

```python
def cpu_times():
    f = open(f"/proc/{os.getpid()}/stat").read().rsplit(") ", 1)[1].split()
    return int(f[11]) / HZ, int(f[12]) / HZ        # utime, stime（秒）
```

实测 20 万次 launch：

```
[F] kernel launch 走内核态还是用户态？
    200000 次 launch：墙钟    538.5 ms
    用户态 CPU    540.0 ms (100.3%)   内核态 CPU      0.0 ms ( 0.0%)
    每次 launch 的内核态时间 ≈ 0 ns
```

以上保留历史输出。能从中读出的结论是：在这次统计的粒度下，
没有观察到 stime 增量。它不能证明“没有系统调用”，也不能确定命令缓冲区
和 doorbell 的具体实现。原稿中从零读数推导这些机制的段落已撤回。

`stime` 的单位是 clock ticks，需用 `SC_CLK_TCK` 换算；
延长测试能增加累计时间，但不能把时间统计变成调用计数。
参见 [Linux 的字段定义](https://man7.org/linux/man-pages/man5/proc_pid_stat.5.html)。

若要继续追踪，应把初始化与稳定提交区间分开，记录对应区间的系统调用，
再结合驱动版本和源码解释。跟踪工具会影响延迟，因此轨迹用于确认路径，
不直接用作无工具干扰的性能结果。

### 系统调用计数与测量范围

上面那一步已经做了。方法是**差分**，而不是去猜哪些系统调用属于启动：
同一段负载跑两个规模，相减。`import torch` 的几万次 `openat`/`mmap`、
建 context、加载 cubin 这些一次性开销在相减时抵消。

$$\text{每次 launch 的系统调用数} = \frac{\text{total}(N_2) - \text{total}(N_1)}{N_2 - N_1}$$

本实验将 `strace` 的 `.deb` 解包到独立工具目录，
用一个设 `LD_LIBRARY_PATH` 的包装脚本调用（`dpkg -l` 里查不到它）。

```
模式        N=50000     N=200000   每次调用   说明
--------------------------------------------------------------------------
idle            34181        34179      -0.000013   基线：N 不影响它，差分应当≈0
launch          34181        34186       0.000033   纯下发
sync            34181        34200       0.000127   每次 launch 后 cudaDeviceSynchronize
graph           34434        47844       0.089400   100 次 launch 录成一张图后 replay
d2h             34196        34215       0.000127   每次 launch 后 .item() 回读
```

读法：

- **`idle` 的差分是 −0.000013**，也就是噪声量级。这一行是基线，它说明
  差分方法本身是干净的 —— 不随 N 变化的东西确实抵消掉了。
- **`launch` 每次 0.000033**。15 万次额外的 kernel 下发，一共只多了 5 次系统调用。
  这才是「launch 不进内核态」的证据，`stime = 0` 不是。
- **`sync` 每次 0.000127**。`cudaDeviceSynchronize` 也几乎不进内核 ——
  它在用户态自旋等一块映射内存里的值，不是睡在内核里等唤醒。
- **`graph` 每次 0.0894**，比前几行高三个数量级。

### 0.0894 的计数口径

先定位它是哪个系统调用、哪个线程、哪个阶段，再解释。

**哪个调用**：用名字取并集再补 0 之后（第一版用 `join` 求交集，
把只在一侧出现的调用漏掉了，于是显示"没有任何调用增长"），只有一个：

```
--- graph ---
  sched_yield                0 ->     13411   delta=    13411   每次 0.08941
```

**哪个线程**：同一负载跑三次，`sched_yield` 分别是 14307 / 16000 / 12960
（run-to-run 差 ±11%，所以只能当量级看），而按 tid 分布是

```
    tid 2365994  14307      <- 主线程
    tid 2366027      1
    tid 2366028      1
    tid 2366029      1
```

几乎全部来自**主线程**，不是某个后台轮询线程。

**哪个阶段**：在 worker 里插 `write` 标记，把提交和同步分开数：

```
=== k=100 （200000 kernel，2000 次 replay）===
  提交阶段 sched_yield: 14008
  同步阶段 sched_yield: 0
```

全部在**提交**阶段，同步阶段一次都没有。

**为什么**：假设是提交队列满了在等。检验方法是把队列深度压到 1 ——
每次 `replay()` 之后立刻同步，让队列里最多只有一张未完成的图：

```
graph:100        提交阶段 sched_yield=13482    墙钟=1236ms
graphsync:100    提交阶段 sched_yield=0        墙钟=1177ms
graph:1          提交阶段 sched_yield=12933    墙钟=1382ms
graphsync:1      提交阶段 sched_yield=0        墙钟=2038ms
```

**降到 0。** 所以这些系统调用不是「图执行的固定开销」，而是
**CPU 提交得比 GPU 消费得快时，驱动在提交路径上自旋让出 CPU**。
最后一行同时给出了代价：`graphsync:1` 的墙钟从 1382 ms 涨到 2038 ms
（慢 48%）—— 消掉这些 `sched_yield` 的办法是让 CPU 停下来等 GPU，
那正是你用图想避免的事。

::: note 这一节的结论边界
测的是 crater 的这一份驱动与这一份 CUDA 版本（见页首）。
`sched_yield` 的计数 run-to-run 差 ±11%，只能当量级读，不要引用具体数值。
"launch 不进内核态"这条结论只对**稳定提交阶段**成立：
初始化阶段有几万次系统调用，那部分没有被差分抵消掉，是因为它本来就不随 N 变化。
:::

### CUDA Graph 减少重复提交开销

```
[C] CUDA Graph：把 N 次下发压成 1 次
         N    eager µs/kernel    graph µs/kernel       加速
        32              2.812              0.892    3.15×
       128              2.692              0.786    3.43×
       512              2.679              0.759    3.53×
```

**N 越大，加速比越高**（3.15 → 3.53×）：因为 graph 的一次性重放开销被摊薄了。

这里的 0.76 µs/kernel，是整次图重放及同步耗时除以节点数得到的平均值。
它没有把 CPU 提交、GPU 调度、kernel 执行和同步分别计时，
因此不能全部归到某一种硬件开销上。

CUDA Graph 可以减少重复提交开销，但并不把图中的多个 kernel 自动融合成一个。
vLLM 还会按配置和后端能力选择整图、分段图或 eager 路径，
不是只能使用 piecewise。详见 L2.6b 和
[vLLM 0.29.0 的图执行设计](https://docs.vllm.ai/en/v0.29.0/design/cuda_graphs/)。

### 同步原语与 `.item()` 的等待成本

```
[E] 同步原语的 host 侧代价
    cudaDeviceSynchronize (空闲)          2.260 µs
    event.record()                       2.330 µs
    stream.query() (非阻塞)                0.320 µs
    tensor.item() (强制同步+拷回)          4.760 µs
```

`stream.query()` 只要 0.32 µs（纯读一个用户态标志），
而 `.item()` 要 4.76 µs —— 它必须**等 GPU 全部做完**再把一个标量拷回来。

**在 decode 循环里写一次 `.item()`，就等于每步插入一个全局同步点，
把 CPU 与 GPU 的流水打断。** 这是 PyTorch 代码里最常见的性能杀手，
而且不会报任何错。L2.6 会讲怎么用 `nsys` 一眼看出这种"锯齿状"的时间线。

### 统一内存：方便的代价是 5 倍

`labs/L1/uvm_probe.cu` 实测（256 MB）：

```
[1] 托管内存，CPU 先写过
    GPU 首次访问（含缺页迁移）    30.812 ms  ->     8.7 GB/s
    GPU 再次访问（页已在显存）     0.176 ms  ->  1525.2 GB/s
    缺页迁移让首次访问慢了 175.1 倍

[2] cudaMemPrefetchAsync 显式预取
    预取 256 MB                    6.018 ms  ->    44.6 GB/s
    预取后 GPU 访问                0.191 ms  （已无缺页）

[3] 对照：cudaMalloc + pinned H2D
    显式 H2D 拷贝                  5.882 ms  ->    45.6 GB/s
    之后 GPU 访问                  0.199 ms  ->  1348.7 GB/s
```

三行数字讲完了整个故事：

| 路径 | 有效带宽 | 相对 PCIe 上限 |
|---|---|---|
| **按需缺页迁移** | **8.7 GB/s** | **19%** |
| 显式 prefetch | 44.6 GB/s | 98% |
| pinned 显式拷贝 | 45.6 GB/s | 100% |

**缺页驱动的迁移只有显式拷贝的 1/5。** 因为每次缺页都要：
GPU 触发中断 → 驱动介入 → 找到页 → 建立映射 → 迁移 → 恢复执行。
这条路径的固定开销远大于 DMA 本身。

**UVM 的价值是编程方便与显存超额订阅**（可以分配超过显存的量，靠换页跑），
**不是速度**。热路径上要可预测的性能，就用显式拷贝 + pinned 缓冲——
所有推理引擎都是这么做的。

（例外：Grace-Hopper / GB10 这类有 NVLink-C2C 一致性互连的平台上，
UVM 的代价小得多。L8.5 会在 `spark` 上对照。）

## 工程实现 · 源码走读：这些成本在引擎里对应什么

### 1. 常驻进程与 sleep/wake

L0.1 测出的 838 ms 冷启动，直接决定了几个设计：

- vLLM 的 `EngineCore.run_busy_loop`（`v1/engine/core.py:1411`）是无限循环，
  进程从不退出。
- SGLang 的 RL 集成提供 **sleep/wake**：释放 KV cache 与权重但**保持进程存活**，
  避免重复付 context 创建与 CUDA Graph 重捕获的成本（L7.5）。
- vLLM 有 `v1/engine/tensor_ipc.py`：跨进程传张量走 **CUDA IPC**
  （共享显存句柄）而不是序列化——因为进程边界已经存在，
  只能想办法让穿过它的代价变小。

### 2. CUDA Graph 的显存代价

L0.2 的源码走读里提到 `gpu_worker.py:513` 的这段：

```python
self.available_kv_cache_memory_bytes = (
    self.requested_memory
    - profile_result.non_kv_cache_memory
    - cudagraph_memory_estimate_applied      # ← 这一项
)
```

**开 CUDA Graph 要预留显存池**，直接从 KV cache 的预算里扣。
本章测出 graph 能省 3.5× 的 launch 开销，但代价是并发度下降。
**延迟与吞吐的直接交易**，L5.4 会量化。

### 3. 为什么引擎避免 `.item()`

vLLM 的采样全在 GPU 上做（L0.1 第 13 阶段，`v1/sample/sampler.py`），
采样结果通过**异步拷贝 + 事件**回到 CPU，而不是 `.item()`。
本章测出 `.item()` 是 4.76 µs —— decode 每步只有 4.3 ms，
一步里插几次就吃掉可观比例。

<summary>③ 一段被我删掉的错误代码，以及它的教训</summary>

本章的 UVM 实验最初是用 ctypes 在 Python 里直接调驱动 API 写的：

```python
cudart = ctypes.CDLL("libcudart.so.13", mode=ctypes.RTLD_GLOBAL)
rc = cudart.cudaMallocManaged(ctypes.byref(ptr), ctypes.c_size_t(nbytes), 1)
...
cudart.cudaMemPrefetchAsync(ptr, ctypes.c_size_t(nbytes), 0, None)   # ← 错
cudart.cudaDeviceSynchronize()
```

测出来：

```
cudaMemPrefetchAsync 到 GPU     0.03 ms  (9923.6 GB/s)
```

**9923 GB/s 超过了显存带宽的 6 倍**，物理上不可能。而且更糟的是，
这段代码**污染了 CUDA 上下文**，导致后面所有 kernel 都报
`CUDA error: invalid argument`。

改用 CUDA C 重写时，编译器一句话点破了根因：

```
uvm_probe.cu(61): error: no suitable constructor exists to convert
                  from "int" to "cudaMemLocation"
      cudaError_t pf = cudaMemPrefetchAsync(um, nbytes, 0, 0);
```

**CUDA 13 改了签名**：设备参数从 `int` 变成了 `cudaMemLocation` 结构体。
C++ 编译器会拦下来，ctypes 不会——它没有类型信息，参数就那样传过去了，
返回错误码被我忽略。

三条教训：
1. **ctypes 调 C ABI 一定要设 `argtypes` / `restype` 并检查返回码。**
2. **能用编译型语言就用**——类型检查能提前发现部分错误，但不能代替运行时与数值测试。
3. **荒谬的数字是好事**，一眼就能识破。危险的是"看起来合理但错了"的数字。

## 前沿

| 方向 | 内容 |
|---|---|
| **用户态提交与 doorbell** | 本章实测证实的机制。更进一步是 **GPU 自己发起工作**（device-side launch、CUDA Dynamic Parallelism、以及 DeepEP 的 GPU-initiated 通信），彻底把 CPU 移出环路（L6.3） |
| **IBGDA** | NVSHMEM 的 InfiniBand GPUDirect Async：让 GPU 直接驱动网卡的 doorbell，不经过 CPU。和本章的 MMIO 环形缓冲是同一个思想，只是对象换成 NIC（L6.3） |
| **CUDA Graph 的演进** | 条件节点（conditional nodes）让图里能带分支，减少"形状一变就要重捕获"的痛点。vLLM 的 piecewise graph 是当下的折中（L5.4） |
| **MPS vs MIG vs 时间片** | 三种多租户方案：MPS 共享 context（低隔离、高利用率）、MIG 硬件分区（强隔离、Blackwell 消费级不支持）、时间片（默认，抖动大）（L8.2） |
| **统一内存的翻身** | Grace-Hopper / GB10 的 NVLink-C2C 让 CPU-GPU 一致性访问变便宜，UVM 从"方便但慢"变成"可用"。`spark` 上会对照（L8.5） |
| **开源内核模块** | 本机跑的就是 `NVIDIA UNIX Open Kernel Module`。开源之后，社区可以看到显存管理与调度的实现——对理解 MIG、抢占、故障恢复很有价值 |

> 除本章实测外的内容来自各自文档，**未在本站复现**<span class="unverified">未实测</span>。

## 陷阱

**1. 把 CUDA API 调用与系统调用当成同一个概念。** 一次 API 调用可能完成多种工作。
是否进入内核、进入多少次，应查轨迹，不能由 stime 的零增量判断。
本章「补测」一节给出了轨迹版的答案，以及一个反例：CUDA Graph 的提交路径**确实**会进内核。
优化 launch 开销要看**用户态**的调用链（Python 层、参数打包），不是 syscall。

**2. 用 pip 装 CUDA 就以为换了驱动。** `libcuda.so` 来自驱动，pip 换不掉。
只能换 `libcudart` 和数学库。

**3. 容器里 `nvidia-smi` 能跑就以为 GPU 好了。** `torch.cuda.is_available()` 还要 `/dev/nvidia-uvm`。

**4. 在热路径里写 `.item()` / `print(tensor)` / `assert tensor > 0`。**
每次都是一个全局同步点，4.76 µs 起步，还会打断流水。

**5. 关掉 persistence mode。** 没有进程持有 GPU 时驱动状态会卸载，
下次 `cuInit` 慢几百毫秒。

**6. 用 ctypes 调 C API 不设 argtypes。** 本章踩过：签名变了，静默失败，
测出 9923 GB/s，还污染了后续所有 CUDA 调用。

**7. 用 UVM 做热路径数据搬运。** 缺页迁移只有显式拷贝的 1/5。

**8. 忽略 CPU 时间统计的粒度。** 用 `SC_CLK_TCK` 查询换算单位；
无论重复多少次，stime 统计都不是系统调用计数器。

## 自测题

<details markdown="1">
<summary>1. 我的服务需要在 100 ms 内完成冷启动扩容。可行吗？瓶颈在哪？</summary>

**不可行。** 本章实测光是进程初始化就要 838 ms：

```
import torch 582 ms + cuInit 160 ms + context 81 ms + 首个 kernel 15 ms
```

**还没加载权重。** 1.7B 模型的权重加载（L1.3 自测题 1）至少还要 340–680 ms，
再加上 CUDA Graph 捕获（L5.4）、FlashInfer JIT（首次可能几十秒）。
现实的冷启动是**几秒到几十秒**。

**工程解法**（都指向 L8.2）：
- **预热池**：保持一批已初始化但空闲的副本
- **权重预加载到 page cache**：让第二次加载走内存而不是磁盘
- **CUDA Graph 与 JIT 缓存持久化**：避免每次重编译
- **不要用冷启动做扩容**，用它做故障替换；扩容靠提前预测
</details>

<details markdown="1">
<summary>2. GPU 计算还没有结束，为什么一次提交调用本身也需要时间？</summary>

CPU 要先为 GPU 准备工作。以下是需要沿源码或 trace 检查的环节，
并不是本章已经分别计时的开销分解：

1. **Python → C++ 的调用开销**（本章基线测出 Python 空调用是 0.05 µs，
   但 torch 的 dispatcher 要做类型分发、设备分发、autograd 检查）
2. **算子分发**：`add_` 要根据 dtype、device、layout 找到具体的 kernel
3. **参数打包**：把 tensor 指针、形状、stride 打成命令包
4. **驱动提交**：将准备好的工作交给设备，具体缓冲和通知机制取决于实现

**证据**：`torch.empty(1024)` 只要 1.11 µs（没有算子分发），
而 `matmul` 要 5.66 µs（cuBLAS 还要选 kernel、准备 workspace）。
这些调用包含的工作不同，不能把耗时差全部归到一个环节。
比较不同语言实现的推理引擎时，也需要同时对齐调度、kernel 和执行配置。
</details>

<details markdown="1">
<summary>3. 我想用 UVM 让模型"超额订阅"显存，跑一个装不下的模型。会发生什么？</summary>

**能跑，但慢到没有实用价值。**

按本章实测，缺页迁移是 8.7 GB/s。假设模型权重 40 GB、显存 32 GB，
每次前向要换进换出约 8 GB：

$$8\,\text{GB} / 8.7\,\text{GB/s} = 920\ \text{ms}$$

而正常的 decode 一步只要 4.3 ms（L0.3 实测）。**慢 200 倍以上。**

**正确的做法**是显式的分层管理：
- **权重卸载**：把部分层放主机内存，用显式异步拷贝 + 双缓冲预取
  （accelerate、DeepSpeed-Inference 的 offload 都是这么做的）
- **量化**：把 40 GB 压到 20 GB（L4.3）
- **多卡**：pipeline 或 tensor 并行（L6.2）

**共同点是"显式"**——你知道什么时候搬什么，可以预取和重叠。
UVM 的按需迁移做不到这一点。
</details>

<details markdown="1">
<summary>4. CUDA Graph 之后每 kernel 还要 0.76 µs。这部分能消除吗？</summary>

不能把这个均摊值当成不可优化的 GPU 固定成本。它来自一次重放及同步的总耗时，
还没有分解各阶段。减少节点数量是一种候选方法，
例如通过算子融合减少独立 kernel；实际效果仍需用完整调用验证：
- `torch.compile` / Inductor 把逐元素算子融合（L2.7）
- FlashAttention 把整个 attention 融成一个 kernel（L3.2）
- vLLM 的 `fused_add_rms_norm`（L0.1 trace 里能看到）把残差加和 norm 合成一个

L0.1 实测 decode 每步 444 个 kernel。如果能融合到 200 个，
graph 之后的开销就从 337 µs 降到 152 µs。**这是 L2.7 的直接目标。**
</details>

<details markdown="1">
<summary>5. 同一张卡上跑两个 vLLM 进程，会发生什么？怎么让它们和平共处？</summary>

**默认（compute_mode=Default，无 MPS）：时间片轮转。**
驱动在两个 context 之间切换，每个进程大约拿到一半的 GPU 时间，
但**上下文切换有代价**，而且延迟抖动会明显变大（对 SLO 是灾难）。

更糟的是**显存**：两个进程各自按 `gpu_memory_utilization` 预留 KV 池，
很容易一个起来后另一个 OOM（本章 L5.2 的实验就撞过这个）。

三种方案：

| 方案 | 隔离性 | 利用率 | 本机可用性 |
|---|---|---|---|
| **时间片**（默认） | 弱，抖动大 | 中 | 可用 |
| **MPS** | 弱（共享 context，一个崩全崩） | **高**（kernel 可真正并发） | 需启动 `nvidia-cuda-mps-control`，本机未运行 |
| **MIG** | **强**（硬件分区） | 中（分区固定） | **sm_120 不支持**，只有数据中心卡有 |

**实践中更常见的是不共享**：一张卡一个引擎实例，
靠上层的 router 做负载均衡（L8.1），靠 K8s 的 device plugin 做整卡分配（L8.2）。
共享 GPU 主要用在开发环境和小模型场景。
</details>
