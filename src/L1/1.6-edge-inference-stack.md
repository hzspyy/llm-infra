## 本章回答三个问题

1. 统一内存和独立显存的成本如何不同？
2. 预编译部署受哪些 ABI/算子限制？
3. 持续运行怎样改变最优配置？

端侧推理与数据中心的差别不在「模型变小了」，而在**三个约束同时收紧**：
内存与显存共享同一块物理内存、可用的预编译二进制由平台 SDK 版本决定、
功耗和温度预算先于算力成为上限。本章用同一份 `Qwen/Qwen3-1.7B`（固定 revision
`70d244cc`）在 Jetson AGX Orin 64GB 上把这三件事各测一遍，并与 crater（RTX 5090 D）
的口径对照。

## 机制拆解

### GGUF：一个文件里混着四种数值格式

先看转换的结果。`convert_hf_to_gguf.py`（llama.cpp b10941，commit `4a89937`）
把 HF 权重写成 F16 GGUF，再用同一个 commit 的 `llama-quantize` 生成 Q4_K_M：

```
F16     3.79 GiB   311 个张量   有效 16.001 bpw
Q4_K_M  1.19 GiB   311 个张量   有效  5.030 bpw
体积比 3.18×；张量名集合一致，shape/元素数一致
```

`labs/L1/gguf_inspect.py` 按 GGUF 规范逐字节解析文件头、元数据与张量表
（不依赖任何 GGUF 库），得到的类型直方图是本章第一个关键事实：

```
          类型    张量数           字节           权重    bpw
        Q4_K    169      812.7 MiB    1514.93 M   4.50
        Q6_K     29      404.2 MiB     516.69 M   6.56
         F32    113        0.5 MiB       0.12 M  32.00
    合计 1.19 GiB，有效 5.03 bpw，文件额外开销 5.68 MiB

[布局核对] 每个张量的块数×块字节数与下一个张量的偏移完全吻合
[量化块原始字节] output.weight（Q6_K）数据区前 16 字节：0a7ae63f5fc19e807202aa4a38db0381
    每 256 个权重一个块，块长 210 字节，共 1215488 块
```

三点读法：

- **「Q4_K_M」不是一个位宽，而是一份配方**。169 个张量是 Q4_K（144 字节/256 权重，
  4.50 bpw），29 个是 Q6_K（210 字节/256 权重，6.56 bpw），113 个 1 维张量
  （各类 norm）保持 F32。所以「4 bit 模型」实际是 5.03 bpw。
- **哪些张量被提高精度是配方的一部分**：`output.weight`（输出投影）、
  `attn_v`、`ffn_down` 走 Q6_K。它们要么直接决定 logits，要么是残差通路上
  被反复累加的项，量化误差在这里不会像中间层那样被后续非线性吸收。
- **布局可核对**：块数 × 块字节数逐张量与下一个张量的文件偏移吻合，
  说明解析出的块结构（QK_K = 256）就是文件里真实的布局，
  而不是从类型名猜出来的。

### 统一内存上的解码：带宽先到顶，去量化接棒

`llama-bench`（同一份权重、`-ngl 99`、`r=2`）给出的后端与吞吐：

```
ggml_cuda_init: found 1 CUDA devices (Total VRAM: 62840 MiB)
  Device 0: Orin, compute capability 8.7, VMM: yes, VRAM: 62840 MiB

| model              |   size    |  backend | ngl |  test |        t/s |
| qwen3 1.7B F16     | 3.79 GiB |  CUDA    |  99 | pp128 | 3023.56 ± 349.74 |
| qwen3 1.7B F16     | 3.79 GiB |  CUDA    |  99 |  tg32 |   42.41 ± 0.11   |
| qwen3 1.7B Q4_K-M  | 1.19 GiB |  CUDA    |  99 | pp128 | 3193.65 ± 318.08 |
| qwen3 1.7B Q4_K-M  | 1.19 GiB |  CUDA    |  99 |  tg32 |   82.04 ± 0.57   |
```

`Total VRAM: 62840 MiB` 与 `free -g` 报出的 61 GiB 是同一块物理内存——
这就是「统一内存」在工具链里的样子：CUDA 把整机内存当成自己的显存池。

把 decode 的算术强度算出来，两个数字才有意义。解码每个 token 必须把全部权重
读一遍，于是「权重字节 × token/s」就是有效读取带宽：

| 权重 | 体积 | tg32 | 有效权重带宽 | 占 LPDDR5 峰值（204.8 GB/s） |
|---|---|---|---|---|
| F16 | 4.07 GB | 42.41 t/s | **172.6 GB/s** | 84% |
| Q4_K_M | 1.28 GB | 82.04 t/s | **105.2 GB/s** | 51% |

**F16 的解码几乎就是纯带宽受限**（84% 峰值），Q4_K_M 反而只有一半——
说明后者的瓶颈已经不在字节流上，而在**去量化与 kernel 效率**。
这解释了那个容易被忽略的反直觉结果：**权重体积缩小 3.18 倍，解码只快了 1.93 倍**。
「字节少一半、速度就翻倍」这类推断，在量化上是不成立的。

prefill 侧则相反：`pp128` 两档几乎相同（3023 vs 3194 t/s），因为 prefill 是
算力受限、权重只读一遍，量化省下的带宽换不来吞吐。

长上下文会把这个差异放大。扫描中 prompt≈6469 token（`n_predict=128`，并发 1）
的 TTFT 是 **F16 1593 ms、Q4_K_M 1896 ms**——量化模型在 prefill 上反而更慢，
而去量化开销与 attention/KV 的工作量在同一段里叠加。

### 预编译部署：按 JetPack × CUDA × SM 切分

端侧没有「装个 pip 包就行」的自由度。三组证据：

1. **llama.cpp 走的是本地编译**：CUDA 12.6 来自 JetPack，`nvcc` 编 sm_87，
   `GGML_CUDA=ON` 产出与平台 CUDA 运行库绑定的二进制。cmake 必须显式
   `-DCMAKE_CUDA_COMPILER=/usr/local/cuda/bin/nvcc`——非交互 shell 里
   `nvcc` 不在 PATH，cmake 会报 "CMakeCUDACompilerId.cu failed"。
2. **预编译生态按三元组分发**：jetson-ai-lab 的包索引把 `jp6/cu126` 与 `sbsa/cu130`
   分成两个目录，前者给 JetPack 6 + CUDA 12.6 的 Orin，后者给 SBSA（DGX Spark/GB10）
   这类 aarch64 平台。同一个 `vllm` 在两个目录里是不同的构建。
3. **TensorRT Edge-LLM 的支持矩阵**（文档 v0.10.1，2026-09-13 抓取）把这件事写成了表：

```
Jetson Orin    Official  JetPack 7.2   CUDA 13.2  JetPack package  FP16/INT8/INT4 only
NVIDIA DGX Spark (GB10) Official  DGX Spark 软件栈  CUDA 13.0  系统包  Model-dependent
aarch64 轮子矩阵：Jetson Orin: JetPack 7.2, CUDA 13, SM87, platform TensorRT 10
                  DGX Spark: 当前 DGX Spark 软件栈, CUDA 13, SM121, platform TensorRT 10
Jetson Orin does not run FP8 or FP4 model engines.
```

本机的两个平台与这张表的关系：

| 机器 | 实际平台 | Edge-LLM 要求 | 结论 |
|---|---|---|---|
| jetson-64 | L4T r36.4（JetPack 6.2）+ CUDA 12.6 + TensorRT 10.3 | JetPack 7.2 + CUDA 13 | **不匹配**，不运行 |
| spark | DGX Spark（GB10, SM121）+ CUDA 13.0 | CUDA 13.0 + 系统 TensorRT 10.x | 平台匹配，但机器上**没有系统 TensorRT**（`dpkg` 无 `tensorrt`/`nvinfer`），且 Edge-LLM 只发布源码（维护路线是 ONNX→engine→C++ 构建），PyPI 也没有 aarch64 的 TensorRT 轮子 |

所以本章的 Edge-LLM 路线记为 `UNVERIFIED`，理由与复现条件都写清楚：
**预编译产物不存在**，而计划明确规定「没有兼容预编译环境时保留相应路线 UNVERIFIED，
不能回退为本机编译」。要在 spark 上补测，需要先按平台软件栈把 TensorRT 10.x
解包到学习目录（不走 `apt`），再按维护路线导出 ONNX、构建 engine。

::: warning 「架构名」和「格式名」都不是后端
`Orin` 有三个不同含义：芯片架构（sm_87）、JetPack 版本（R36）、以及
SDK 支持的平台名（支持矩阵里的 "Jetson Orin" 指的是 JetPack 7.2 那一行）。
`GGUF` 也只是容器格式：同一个 Q4_K_M 文件在 CUDA 后端、CPU 后端、
不同量化 kernel 下的性能完全不同。**报一个端侧结果时必须带上
平台三元组（JetPack/CUDA/SM）与量化配方**，否则数字无法复现。
:::

## 工程实现 · 源码解析

### llama.cpp 的图、KV 与后端选择

`llama-server` 的启动日志给出了可核对的槽位结构：

```
load_model: loading model 'models/qwen3-1.7b-gguf/Qwen3-1.7B-Q4_K_M.gguf'
init: llama threadpool init, n_threads = 12
load_model: initializing, n_slots = 2, n_ctx_slot = 2048, kv_unified = 'false'
```

`-c 4096 -np 2` 得到的是**每槽 2048**——上下文预算按槽位切分，不是每个请求
独享 `-c`。扫描阶段用 `-c 40960 -np 4` 时日志里的 `n_ctx_slot` 是 10240，
与公式一致。

KV cache 的字节数可以直接算，Qwen3-1.7B 是 GQA（28 层、8 个 KV 头、head_dim 128）：

$$\text{KV/token} = 2 \times 28 \times 8 \times 128 \times 2\ \text{B} = 114{,}688\ \text{B} \approx 112\ \text{KiB(F16)}$$

4096 个 token 的槽位就是 448 MiB。这个数在统一内存上不是免费的：
30 分钟持续运行的 tegrastats 显示进程常驻 10.5 GiB（模型 1.19 GiB + KV +
compute buffer + 页缓存），而整机只有 61 GiB。

::: note 为什么必须用 llama-bench 而不是「跑得快就是 GPU」
这个 build 的 `llama-server` 在默认 verbosity 下**不打印设备与 offload 细节**，
日志里搜 `CUDA0` 一次都命中不了。只凭「TTFT 50 ms 很快」推断「一定在用 GPU」
是不成立的——CPU 上的小模型也能给出这个量级。可核对的证据来自：
`llama-bench` 表格里的 `backend` 列、`ggml_cuda_init` 打印的设备与 SM、
以及 `-ngl 99` 的 offload 层数。**后端是查出来的，不是推断出来的。**
:::

### 设计取舍：量化配方与栈的选择

| 决策 | 选择 | 代价 | 依据 |
|---|---|---|---|
| 权重量化 | Q4_K_M（混合配方） | PPL 16.73 → 18.39（+9.9%），长上下文 prefill 变慢 | 体积 3.18×、解码 1.93×、仍能塞进 61 GiB 统一内存并留出 KV 预算 |
| 运行栈 | llama.cpp（GGUF，本地编译） | 需要按平台三元组自建，升级 CUDA 要重编 | 对量化配方与 KV 布局有完整控制，源码可读 |
| 预编译栈 | jetson-ai-lab `jp6/cu126`（torch/Vulkan/vLLM 等） | 只有平台三元组匹配才能用 | 避免在设备上编译依赖 |
| Edge-LLM | 本轮不运行 | —— | 无兼容预编译产物（见上） |

量化配方的取舍不能只看平均值：Q4_K_M 把 `output.weight` 提升到 Q6_K，
是因为输出投影的误差直接影响采样分布；把 113 个 norm 张量留在 F32，
是因为它们的元素数极小（0.12 M，占 0.5 MiB），量化它们省不下体积却会放大误差。
**「按张量分工」是端侧量化的默认做法，不是实现偷懒。**

## 工程实现 · 自己写一遍

`labs/L1/gguf_inspect.py` 是一份**不依赖 GGUF 库**的解析器：读文件头、元数据
KV、张量表，再按 `GGML_TYPES` 表把「类型 → 块内权重数 → 块字节数」换算成
每个张量的字节数与 bpw，最后用「下一个张量的偏移」做布局自检。

关键的三段逻辑：

```python
# 1) 张量表：名字 / 维度 / 类型 / 数据区偏移
name = r.string(); nd = u32(); dims = [u64() for _ in range(nd)]
ttype = u32(); off = u64()

# 2) 类型表把「类型名」翻译成「块结构」，这是最容易错的一步
GGML_TYPES = {..., 12: ("Q4_K", 256, 144), 14: ("Q6_K", 256, 210), ...}
blocks = numel // per_block          # QK_K = 256
bytes_ = blocks * type_bytes         # Q4_K: 144 B / Q6_K: 210 B

# 3) 布局自检：每个张量的字节数必须正好顶到下一个张量的偏移
gap = (data_start + next_offset) - (data_start + off + bytes_)
```

自检通过意味着解析出的块结构就是文件里的真实布局。这一步比任何「看起来能用」
的验证都硬：**块大小猜错一个字节，gap 立刻不等于 0。**

| Q4_K_M | 2048 | 1585 | 4 | 1735.9 | 1975.6 | 4221.2 | 125.1 |
| Q4_K_M | 8192 | 6469 | 1 | 1896.0 | 1896.2 | 4008.4 | 31.9 |
| Q4_K_M | 8192 | 6469 | 4 | 6170.4 | 7891.9 | 11754.9 | 43.6 |

四个结论：

1. **decode 与 prefill 的最优方向相反**：短 prompt 下并发 4 把聚合吞吐从
   77.8 推到 271.9 tok/s（3.5×）；长 prompt 下并发 4 只把 31.9 推到 43.6 tok/s
   （1.37×），同时 TTFT 从 1.90 s 涨到 6.17 s。**在统一内存的端侧设备上，
   并发买吞吐的代价是排队延迟，长上下文时这笔交易很不划算。**
2. **F16 与 Q4_K_M 的差距随 prompt 变长而收窄**：prompt 128 时聚合吞吐
   271.9 vs 161.8（1.68×），prompt 6469 时 43.6 vs 42.9（1.02×）——
   长上下文里 KV 读取与 attention 成了共同瓶颈，权重量化不再是决定项。
3. **TTFT 的 p95/p50 比值**在并发 4、长 prompt 时到 1.28（F16）与 1.28（Q4），
   说明排队已经不均匀；这个比值是 SLO 设计的直接输入（L1.7）。
4. **总计 p95 而不是均值**才看得出体验：Q4_K_M/128/4 并发下 p95 是 1882 ms，
   而单看聚合吞吐 271.9 tok/s 会得出「很快」的错误印象。

### 实测：质量代价

同一份 `wiki.test.raw`、`-c 512`、8 个 chunk：

| 量化 | 体积 | PPL |
|---|---|---|
| F16 | 3.79 GiB | **16.7262** |
| Q4_K_M | 1.19 GiB | **18.3905**（+9.9%） |

用 3.18× 的体积缩减换 9.9% 的困惑度上升，是端侧常见的工作点；但**必须和
具体任务一起验收**——困惑度不等于下游任务质量（L4.3 的边界同样适用）。

### 实测：30 分钟持续运行

`Q4_K_M`、prompt 2048、输出 128、并发 1、`njobs=2`（每槽 4096），MAXN 模式，
共 **839 轮**：

| 指标 | 值 |
|---|---|
| 冷机 p50（前 1/6 轮） | 2147.6 ms |
| 热稳态 p50（后 1/6 轮） | 2147.1 ms |
| 热衰减比 | **1.000**（无节流） |
| 每轮总延迟 min / max | 2145.3 / 2157.6 ms |
| tj（结温）first → last（峰值） | 55.4 → 72.9 °C（72.9） |
| GPU 温度均值/峰值 | 68.9 / 71.7 °C |
| GR3D 占用均值/峰值 | 95.8% / 99% |
| 功耗轨和 均值/峰值 | 44.3 / 45.1 W |
| 30 分钟能量 | 79 890.9 J |
| 输出 token 总数 | 107 392 |
| **能量/输出 token** | **0.744 J/token**（1.344 token/J） |

三个可交付的读法：

- **在这套配置下没有热衰减**：热衰减比 1.000，逐轮 p50 的极差只有 12 ms。
  散热与功耗在这个负载下没有成为限制——**但这是「这个负载」的结论**：
  GR3D 已经 96% 满载、结温 72.9 °C，继续提高并发或换更长的上下文会改变结论，
  必须重测。
- **能量账要按 token 算**：44.3 W 的均值功耗对应 0.744 J/token。
  这个数字让「端侧省电」变成可计算的量：给定电池能量与目标 token 数，
  就能算出可用时长；反之，功耗轨和不是单轨读数，报的时候要说清楚是哪几条轨。
- **冷机与热稳态必须分开报**：本例两者相同，正因如此才需要把 839 轮全部保留，
  否则「跑了 30 分钟没变慢」这句话没有任何证据。

### 消融建议

| 改什么 | 你应该看到什么 |
|---|---|
| 把 `-ngl` 从 99 改成 0 | `llama-bench` 的 backend 列变成 CPU，tg32 掉一个量级；这是「后端证据」的对照 |
| 把 `-c` 从 8192 改成 40960 而 `-np` 不变 | 每槽上下文变大，KV 占用的统一内存按 112 KiB/token 线性增长 |
| 用 `Q8_0` 再量化一档 | PPL 与 F16 更接近、体积约为 Q4_K_M 的 1.7 倍；解码速度介于两者之间 |
| 把 `--prompt-tokens` 固定为 8192，只扫并发 | 聚合吞吐几乎不涨而 TTFT 线性上涨——排队主导区 |
| 把持续运行改成 2 分钟 | 温度还没到稳态（本例结温从 55 °C 爬到 72.9 °C 用了十几分钟），热结论不成立 |
| 在 spark 上重跑同一份 GGUF | 平台三元组变了（CUDA 13/SM121），必须重新记录 backend 与吞吐，不能沿用 Orin 的数字 |

## 陷阱

**1. 把「架构名」当成「后端可用」。** `Orin` 只是芯片名；Edge-LLM 支持矩阵里
的 "Jetson Orin" 指的是 JetPack 7.2 那一行。**平台三元组（JetPack/CUDA/SM）缺一个都别下结论。**

**2. 用「跑得快」推断「走了 GPU」。** 本章的 `llama-server` 默认日志里
一条 `CUDA0` 都没有。后端名要来自 `llama-bench` 的 `backend` 列或
`ggml_cuda_init` 的设备行。

**3. 以为量化是「整体降到 N bit」。** 同一个 Q4_K_M 文件里有 Q4_K、Q6_K、F32
三种格式，有效 5.03 bpw。**报量化模型时要报有效 bpw，不是类型名里的数字。**

**4. 把体积比当成加速比。** 3.18× 的体积缩减只换来 1.93× 的解码加速，
因为 F16 已经贴着内存带宽、Q4_K_M 的瓶颈换成去量化。**字节数减少不能自动解释收益。**

**5. 用短时间冷机成绩替代持续运行。** 结温从 55 °C 爬到 72.9 °C 需要十几分钟。
跑 2 分钟就宣称「无热衰减」，测到的是冷机。

**6. 只看平均延迟。** 并发 4、长 prompt 时 p95/p50 到 1.28，
总计 p95 是均值的 1.2–1.3 倍。**SLO 要吃的是尾延迟。**

**7. 在没有兼容预编译产物时现场编译。** 计划对此有明确规定；正确做法是
把路线标 `UNVERIFIED`，写清平台要求与复现条件，而不是在设备上临时拼依赖。

**8. 把统一内存当独立显存做容量规划。** 61 GiB 是 CPU 与 GPU 共享的，
KV、权重、页缓存互相挤占；`Total VRAM` 报的是整池大小，不是可用余量。

## 自测题

<details markdown="1">
<summary>1. 同一份 Qwen3-1.7B，Q4_K_M 的体积只有 F16 的 1/3.18，为什么解码只快 1.93 倍？</summary>

因为两者的瓶颈不同。解码每个 token 要把全部权重读一遍，所以「权重字节 × token/s」
是有效读取带宽：

- F16：4.07 GB × 42.41 t/s = **172.6 GB/s**（LPDDR5 峰值的 84%）→ 带宽受限
- Q4_K_M：1.28 GB × 82.04 t/s = **105.2 GB/s**（峰值的 51%）→ 已经不是带宽受限

Q4_K_M 每个权重块要先解出 scale/min 再去量化，这部分算术与访存一起进入关键路径，
所以体积缩小 3.18 倍只换来 1.93 倍。**要判断量化收益，先算有效带宽占比：**
贴着峰值的那个配置才是带宽受限，另一个的优化空间在 kernel 里。

如果把这个模型换到带宽更宽、算力更弱的设备（或反过来），结论会变——
所以每个平台都要重算这两个数。
</details>

<details markdown="1">
<summary>2. 在当前 61 GiB 统一内存的 Orin 上部署 8B 模型且 KV 上下文开到 8192，容量是否可行？</summary>

把账拆成三笔（统一内存 61 GiB）：

1. **权重**：8B 模型 F16 约 16 GiB；Q4_K_M 约 5 GiB。
2. **KV**：按本章公式 $2 \times L \times H_{kv} \times d \times 2$ 字节/token。
   以 Qwen3-8B（36 层、8 个 KV 头、head_dim 128）为例：
   $2 \times 36 \times 8 \times 128 \times 2 = 147{,}456$ B ≈ 144 KiB/token。
   8192 token ⇒ **1.15 GiB**（单序列）。
3. **compute buffer 与页缓存**：扫描时 `-c 40960` 的配置常驻 10.5 GiB 里，
   模型只占 1.19 GiB，其余大部分是 KV 与 compute buffer。

所以 F16 的 8B 模型确实装得下，但留给 KV 与并发的余量不多；
**统一内存里没有「显存」这一层可以单独扩容**，要并发就得从权重或上下文里省。
</details>

<details markdown="1">
<summary>3. 为什么短 prompt 时并发 4 能把吞吐提高 3.5 倍，长 prompt 时只有 1.37 倍？</summary>

两种负载的瓶颈不同：

- **短 prompt（133 token）**：每步的工作量小，单序列时 GPU 有大量空闲；
  并发把空闲填满，聚合吞吐 77.8 → 271.9 tok/s。
- **长 prompt（6469 token）**：prefill 已经是算力受限，TTFT 随并发近似线性增长
  （1896 → 6170 ms）。并发只是把队列拉长，聚合吞吐受限于同一份算力，
  所以只从 31.9 涨到 43.6 tok/s。

工程含义：**端侧服务的并发上限由「可接受的 TTFT」决定，而不是由吞吐决定。**
L1.7 会把这条约束写成 deadline。
</details>

<details markdown="1">
<summary>4. 换用新设备（比如 DGX Spark）时，能直接沿用本章的数字吗？</summary>

不能，必须重跑至少三件事：

1. **后端证据**：`llama-bench` 的 backend 列与设备行（CUDA 13 / SM121 与
   CUDA 12.6 / SM87 的 kernel 选择不同）。
2. **有效带宽占比**：换平台后峰值带宽与算力比变了，F16/Q4_K_M 谁受限会翻转。
3. **持续运行的功耗与热**：DGX Spark 与 AGX Orin 的功耗轨命名、散热形态都不同
   （本章的 tegrastats 解析就同时支持 `VDD_IN` 与 `VIN_SYS_5V0` 两套命名）。

可以沿用**方法**：先固定平台三元组与量化配方，再用「权重字节 × token/s」
判断瓶颈，最后把冷机与热稳态分开报。**数字不能沿用，方法可以。**
</details>

<details markdown="1">
<summary>5. Edge-LLM 的文档说支持 "Jetson"，为什么本章不在这台 Orin 上跑？</summary>

因为支持矩阵里的 "Jetson Orin" 是**一行具体的平台组合**：
JetPack 7.2 + CUDA 13.2 + JetPack 自带的 TensorRT 10，精度限 FP16/INT8/INT4。
本机是 L4T r36.4（JetPack 6.2）+ CUDA 12.6 + TensorRT 10.3(cuda12.5)，
aarch64 轮子矩阵要求 CUDA 13 —— 不匹配。

而且 Edge-LLM 只发布源码：维护路线是「ONNX 导出 → C++ engine 构建 → C++ 推理」，
Python wheel 路径在文档里被标为 experimental 且「不是通用发布产物」；
TensorRT 在 PyPI 上也没有 aarch64 轮子。

**结论**：这台设备上不跑，标 `UNVERIFIED`；要在 spark（DGX Spark，CUDA 13.0/SM121，
平台匹配）上补测，需要先把平台软件栈的 TensorRT 10.x 落到学习目录，
再按维护路线构建 engine。**不因为「文档说有 Jetson 支持」就在不匹配的平台上有样学样。**
</details>
