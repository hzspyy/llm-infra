## 本章回答三个问题

1. 输入年龄与处理时延有什么区别？
2. 排队和抖动如何造成 deadline miss？
3. action chunk 怎样与控制频率协调？

上一章测的是「推理要多久」。闭环系统关心的是**决策时刻手上的输入有多旧**，
以及这个年龄的**分布**能不能落进控制周期里。本章把一条最小闭环
（采样 → 入队 → 推理 → 动作取用/丢弃）拆成可观测事件，用 Jetson 上真实的
`llama.cpp` 推理作为负载，测频率、队列容量、过期策略、抖动与 action chunk。

## 机制拆解

### 定义先对齐：五个事件、两个时间量

`labs/L1/closed_loop_budget.py` 把闭环拆成五个事件，全部打在同一时钟域
（同一进程用 `time.monotonic()`，跨进程先做偏移校准）：

| 事件 | 含义 |
|---|---|
| `enqueue` | 采样值进入队列（记录采样时刻 `t_sampled` 与队列深度） |
| `infer_start` | 某条输入被选中并开始推理（同时记录排队年龄） |
| `infer_end` | 推理返回（记录服务端/客户端延迟） |
| `action_use` | 动作在某个控制周期被取用（记录 `age_ms`） |
| `action_drop` / `action_none` / `deadline_miss` | 丢弃、本周期无输入、动作没赶上 deadline |

两个时间量的区别是整个章节的支点：

- **处理时延** `latency = infer_end − infer_start`：模型/引擎有多快。
- **输入年龄** `age = action_use − t_sampled`：决策时手上的数据有多旧。
  它包含**采样抖动 + 排队 + 推理 + chunk 复用**四段。

只优化第一个量会把第二个量养大：推理更快 ⇒ 队列排空更快 ⇒ 但如果策略是
FIFO，动作可能来自更早的样本。**闭环的 SLO 必须写在年龄上，不是写在时延上。**

### 抖动：把 p50 挪一点，把 p95 挪很多

固定 `freq=10 Hz、queue=4、policy=latest`，只改采样抖动（均匀分布，±j 毫秒）：

| 抖动 | 有效动作率 | 输入年龄 p50 | 输入年龄 p95 | 丢弃（latest） |
|---|---|---|---|---|
| 0 ms | 1.000 | 45.1 ms | 50.1 ms | 0 |
| 5 ms | 0.993 | 46.7 ms | 339.9 ms | 126 |
| 20 ms | 0.993 | 63.0 ms | 431.9 ms | 92 |
| 50 ms | 0.993 | 98.4 ms | **330.5 ms** | 72 |

**抖动只把 p50 挪了几十毫秒，却把 p95 从 50 ms 推到 340–430 ms。**
原因是 `latest` 策略在抖动下会偶尔选到「上一个周期剩下的那条」：
采样提前到达时它被立刻取用（年龄小），采样迟到时只能等下一个周期（年龄大）。
均值/中位数看不见这件事，**只看 p50 的调参会把尾延迟留给现场**。

### 排队：容量换的是有效动作率

固定 `freq=10 Hz、jitter=20 ms`，扫描队列容量与策略：

| 队列 | 策略 | 有效动作率 | 年龄 p50 | 年龄 p95 | 丢弃原因 |
|---|---|---|---|---|---|
| 1 | 任意 | 0.760–0.767 | 54.9–56.9 ms | 134.5–136.4 ms | `queue_full` 36–37 |
| 4 | FIFO | 0.993 | **142.9 ms** | 166.0 ms | — |
| 4 | latest | 0.993 | **62.2 ms** | 430.7 ms | `latest` 91 |
| 4 | drop-stale | 0.993 | 62.6 ms | 431.4 ms | `drop-stale` 92 |
| 16 | FIFO | 0.993 | 142.5 ms | 165.1 ms | — |
| 16 | latest | 0.993 | 62.6 ms | 431.7 ms | `latest` 92 |

三条读法：

1. **容量 1 会丢输入**：推理占用期间到达的样本被直接丢弃，有效动作率掉到 0.76。
   端侧设备上这是常见配置（省内存），代价是控制指令的更新率下降。
2. **队列 4 与 16 没有区别**：`latest` 会在每个周期把多余的丢掉，
   所以容量超过「一个控制周期内可能到达的样本数」就不再有收益。
   **队列不是越大越好，它是策略的输入。**
3. **FIFO 的年龄高而尾部长**（p50 143 ms / p95 166 ms），`latest` 相反
   （62 ms / 431 ms）。两者不是「谁更好」，而是**面向不同的失败模式**：
   FIFO 保证顺序、延迟稳定；`latest` 保证新鲜度、但偶尔很旧。

### deadline：一个悬崖，不是一条斜坡

真实推理负载（Jetson + llama.cpp Q4_K_M），固定 `jitter=20 ms、queue=4、latest`，
只改 deadline：

| 负载 | 推理耗时 p50 | deadline | 有效动作率 | deadline miss 率 | 年龄 p50 |
|---|---|---|---|---|---|
| 32 token | ~450 ms | 200 ms | 0.016 | **0.976** | 190 ms |
| 32 token | ~450 ms | 400 ms | 0.000 | **0.984** | —（无动作） |
| 32 token | ~450 ms | 800 ms | 0.984 | 0.000 | 491 ms |
| 128 token | ~2.1 s | 500 ms | 0.000 | **0.988** | — |
| 128 token | ~2.1 s | 1500 ms | 0.000 | **0.964** | — |
| 128 token | ~2.1 s | 3000 ms | 0.962 | 0.000 | 1849 ms |

**有效动作率从 0.98 掉到 0，中间只隔了几百毫秒的 deadline 变化。**
这不是渐变，而是「deadline 是否跨过推理耗时」的二元结果：

- deadline < 推理耗时 ⇒ 动作永远赶不上 ⇒ 有效动作率 ≈ 0，输入全部白采；
- deadline > 推理耗时 ⇒ 动作来得及 ⇒ 有效动作率 ≈ 1，但**年龄等于排队 + 推理**。

所以端侧闭环的参数选择只有两个自由度：**要么把推理压到 deadline 以内，
要么把 deadline 放大到推理之上并接受相应的输入年龄。** 没有第三条路。

::: warning 表里那些「—」是有信息量的
当有效动作率为 0 时，`年龄 p50` 是空的——因为**没有任何动作被取用**，
自然没有「取用时的年龄」。这时该报的是「本周期无动作」的比例与丢弃原因，
而不是把空的年龄写成 0 或者用没取用的样本凑一个数。
:::

### action chunk：用新鲜度换计算次数

策略一次算 k 步动作（action chunk），控制周期逐条取用。固定
`freq=10 Hz、queue=4、latest、jitter=20 ms`：

| chunk | 有效动作率 | 年龄 p50 | 年龄 p95 | 丢弃 |
|---|---|---|---|---|
| 1 | 0.993 | 62.6 ms | 339.9 ms | `latest` 83 |
| 4 | 0.993 | **204.2 ms** | 401.6 ms | `queue_full` 110 + `latest` 111 |
| 8 | 0.993 | **401.7 ms** | 723.4 ms | `queue_full` 129 + `latest` 54 |

**计算次数变成 1/k，年龄中位数涨了 6.4 倍。** 这就是「计算更快但消费旧动作」
的反例：如果只看「每步推理调用次数」，chunk=8 是最省的选择；把年龄放进来看，
它把动作的时效性打到了 400 ms 量级——对一个 10 Hz 的控制器来说，
这已经超过了三个控制周期。

真实推理上同样成立：`freq=2 Hz、128 token` 时，chunk=4 的年龄 p50 是 2118 ms、
p95 是 3080 ms，而单步模式的 p50 是 1849 ms。**chunk 的收益要按「最老动作」
计价，而不是按调用次数计价。**

## 工程实现 · 源码解析

### 事件与时钟：为什么必须校准

跨进程（更不用说跨设备）时，各进程的 `time.monotonic()` 起点不同：
`T0` 是进程启动时刻，所以「A 的时间戳减 B 的时间戳」在默认情况下毫无意义。
`AgentBackend` 用 NTP 式的四时间戳法估计偏移：

```
t1 = 本地发送前      t2 = agent 收到      t3 = agent 回复前      t4 = 本地收到后
offset = ((t2 − t1) + (t3 − t4)) / 2      精度上界 ≈ RTT / 2
```

实现上重复 11 次并**取 RTT 最小的一次**（离群样本通常来自调度抖动，
而不是时钟本身）。实测（同一台 Orin 上两个进程，注入 ±0/250 ms 偏移）：

```
agent offset 0   → 校准结果 2999.038 ms   RTT 0.880 ms（±0.44）
agent offset 250 → 校准结果 3250.176 ms   RTT 0.885 ms（±0.44）
Δoffset = 251.1 ms   ← 注入的 250 ms 被恢复出来
```

2999 ms 的那部分是两个进程 `T0` 的差值（epoch 差），**它本身就是「不校准就错多少」的量级**。
把 agent 的时间戳换算到本地域后，每次推理的 start skew（本地估计起点 − agent 起点）：

| 配置 | 样本数 | start skew p50 | min / max |
|---|---|---|---|
| 已校准 | 97 | **+0.6 ms** | 0.5 / 0.9 |
| 未校准 | 49 | **+43 686.4 ms** | 43686.3 / 43688.9 |

**43.7 秒的偏差不是推理慢，而是两个进程的时钟起点不同。**
如果不校准就把 agent 的时间戳当成「本地时间」，重建出的关键路径会整体错位——
把推理时延算成 43 秒，任何预算分析都失去意义。

### 控制循环：deadline 是 join 的超时

核心循环只有四步（省略日志）：

```python
while now_ms() < t_end:
    period_start = now_ms()
    deadline = period_start + args.deadline_ms

    with lock:                       # 1) 按策略取输入（或复用 chunk）
        chosen, dropped = pick(queue, args.policy, period_start, max_age)

    if chosen is not None:           # 2) 起一个 worker 跑推理
        th = threading.Thread(target=worker, args=(chosen,))
        th.start()
        th.join(timeout=max(0.0, (deadline - now_ms()) / 1000.0))
        if th.is_alive():            # 3) 没赶上：记 miss，本周期的动作不用
            metrics.deadline_miss += 1
            chunk_left = 0
        else:
            chunk_input, chunk_left = chosen, args.chunk

    if chunk_left > 0:               # 4) 取用动作（记录年龄）
        age = now_ms() - chunk_input.t_sampled
        metrics.ages.append(age)
        chunk_left -= 1
    time.sleep(max(0.0, (period_start + period - now_ms()) / 1000.0))
```

三处容易写错的细节：

1. **miss 之后必须继续走周期对齐**。早期实现用 `continue` 跳过末尾的 sleep，
   结果 deadline 很紧时循环空转，控制频率被人为放大——测出来的是 harness 的
   节奏，不是控制器的节奏。
2. **worker 线程不能跨周期复用同一个输入对象**：`chosen.t_infer_end` 会被下一个
   周期覆盖，事件日志就对不上了。每次取输入都新起一个 worker。
3. **`age` 用采样时刻算，不用推理开始时刻算**。排队时间必须计入年龄，
   否则「队列越长年龄越大」这个最关键的结论会消失。

### 设计取舍

| 决策 | 选择 | 替代方案与代价 |
|---|---|---|
| 时钟 | `time.monotonic()` + NTP 式偏移校准 | 用墙钟（`time.time()`）：会被 NTP 跳变打断；用固定偏移：平台一换就错 |
| 指标 | 事件 JSONL + 分位数 | 只存聚合值：能看出 p50，看不出「为什么慢」；JSONL 可以重算任何分位数 |
| 推理后端 | 可插拔（sleep / http / agent） | 只接真实后端：时序逻辑无法在无设备时回归；只接模型：结论无法与硬件解耦 |
| 过期策略 | 显式四种（fifo/latest/drop-stale/queue-full 丢弃） | 隐式「总是用最新的」：会把丢失与丢弃混在一起，无法定位 |

::: note 本轮的边界
任务 C 要求「离线动作误差、系统时延和闭环任务结果分别验收」。本轮完成了
**系统时延与时间预算**（含 chunk 反例），但**没有接真实策略**：
动作头依赖 10.6 的 DROID 策略，本环境没有机器人与策略 checkpoint，
因此「离线动作误差」与「闭环任务结果」保持 `UNVERIFIED`。
sleep 后端的 chunk 实验验证的是时序逻辑；真实推理上的 chunk 只测到年龄，
没有测动作质量。
:::

## 工程实现 · 自己写一遍

`labs/L1/closed_loop_budget.py` 的三种模式对应三种问题：

- `--mode agent`：端侧进程，用自己的时钟给「收到 / 开始 / 结束」打点，
  可注入时钟偏移；
- `--mode calibrate`：只跑偏移估计，输出 offset 与精度上界；
- `--mode run/matrix`：重放 + 周期消费，扫描抖动、频率、队列、策略与 chunk。

`--backend` 三选一让同一份时序逻辑可以对着不同负载跑：
`sleep`（纯延迟模型，验证逻辑）、`http`（真实 llama-server，量系统）、
`agent`（跨进程 + 时钟校准）。**把「时序逻辑」与「推理实现」解耦，
是无设备环境下仍能回归测试的前提。**

```bash
# 1) 纯时序逻辑（不需要模型）：抖动、队列、策略、chunk 三条轴
python labs/L1/closed_loop_budget.py --mode matrix --backend sleep \
    --latency-ms 40 --seconds 15 --deadline-ms 80 \
    --events events_sleep.jsonl --out matrix_sleep.json

# 2) 时钟偏移与校准：agent 注入 250 ms 偏移
python labs/L1/closed_loop_budget.py --mode agent --port 19081 --backend http \
    --endpoint http://127.0.0.1:8080/completion --clock-offset-ms 250 &
python labs/L1/closed_loop_budget.py --mode calibrate \
    --agent-url http://127.0.0.1:19081 --calibrate-rounds 11 --out calibrate.json

# 3) 真实推理负载下的闭环（Jetson + llama.cpp）
llama-server -m Qwen3-1.7B-Q4_K_M.gguf -c 8192 -ngl 99 -np 4 --port 8080 &
python labs/L1/closed_loop_budget.py --mode run --backend http \
    --endpoint http://127.0.0.1:8080/completion \
    --freq 5 --queue 4 --policy latest --jitter-ms 20 --n-predict 32 \
    --deadline-ms 800 --seconds 40 --out run_http32.json
```

### 消融建议

| 改什么 | 你应该看到什么 |
|---|---|
| `--policy fifo`（同队列、同频率） | 年龄 p50 从 62 ms 涨到 143 ms，但 p95 从 431 ms 降到 166 ms |
| `--queue 1` | `queue_full` 丢弃出现，有效动作率掉到 0.76 |
| `--jitter-ms` 0 → 50 | p50 只涨几十毫秒，p95 从 50 ms 涨到 330 ms |
| `--deadline-ms` 跨过推理耗时 | 有效动作率在 0.98 与 0 之间跳变，没有中间值 |
| `--chunk 8` | 调用次数降到 1/8，年龄 p50 涨到约 6.4 倍 |
| 去掉 `--no-calibrate` 里的校准（即加该开关） | agent 时间戳与本地相差数十秒，关键路径整体错位 |

## 陷阱

**1. 把处理时延当输入年龄。** 前者从 `infer_start` 起算，后者从**采样**起算，
中间还夹着排队、抖动与 chunk 复用。端侧实测里两者差 4–8 倍。

**2. 跨设备直接用两个时间戳相减。** 不同进程的单调时钟起点不同，实测偏差
43.7 秒。**先校准，再算关键路径。**

**3. 只报均值或 p50。** 抖动 5 ms 就能把年龄 p95 从 50 ms 推到 340 ms，
而 p50 只动了 1.6 ms。

**4. 把队列开大当解法。** 队列 4 与 16 在 `latest` 策略下完全一样；
队列开大只对 FIFO 有意义，而且会把年龄推高。

**5. 用「调用次数少了」论证 chunk 更好。** chunk=8 把调用降到 1/8，
同时把年龄中位数推到 6.4 倍。**按最老动作计价。**

**6. 把各段均值相加当闭环分位数。** 年龄的 p95 不是各段 p95 之和，
它由同一批样本的联合分布决定；本章的做法是从事件日志重算，而不是拼装。

**7. 有效动作率为 0 时把年龄填 0。** 那是「没有动作」而不是「年龄为零」，
两者在 SLO 里的含义完全相反。

**8. 在紧 deadline 下用 `continue` 跳过周期对齐。** 会让 harness 空转、
控制频率失真，测出来的是测量代码的节奏。

## 自测题

<details markdown="1">
<summary>1. 若推理单次耗时 300 ms、控制周期 100 ms、deadline 为 900 ms，系统行为会如何？</summary>

按本章的实测形态：deadline（900 ms）跨过了推理耗时（300 ms），
所以**有效动作率会接近 1**，但输入年龄的中位数大约等于
「排队 + 推理」≈ 300–400 ms，也就是 3–4 个控制周期。

这不是「系统坏了」，而是**控制回路变成了 300 ms 的等效延迟**。
后果取决于被控对象：位置控制可能振荡，而慢过程（温度、流速）完全没问题。
要做的是把年龄写进 SLO，而不是把 deadline 调小——后者会让有效动作率直接掉到 0。
</details>

<details markdown="1">
<summary>2. 为什么 deadline 从 400 ms 调到 800 ms，有效动作率从 0 跳到 0.98，中间没有过渡？</summary>

因为推理耗时几乎是确定的（同一台设备、同一份模型、同一序列长度，
p50 与 p95 相差不到 20 ms）。当 deadline < 推理耗时时，**每一次**都赶不上；
当 deadline > 推理耗时时，**几乎每一次**都赶得上。
中间那段之所以窄，是因为推理耗时的分布本身很窄。

反过来，如果推理耗时的分布很宽（比如并发下排队严重、或热节流导致抖动），
这条曲线就会被拉成斜坡。**悬崖的陡峭程度是推理耗时稳定性的直接体现。**
</details>

<details markdown="1">
<summary>3. action chunk=4 让推理调用减少到 1/4，为什么年龄反而涨了 3 倍？</summary>

因为动作被复用了 4 个周期。第 1 个周期用的是刚算出来的动作（年龄 ≈ 排队+推理），
第 4 个周期用的还是同一批动作，年龄就多了 3 个周期。
在 10 Hz 下这是 300 ms，实测 p50 从 62.6 ms 涨到 204.2 ms（约 +141 ms 的观测差，
因为并非所有 chunk 都被完整用满）。

**正确的计价方式**：chunk 的收益是调用次数与能耗，代价是「最老动作」的年龄；
两者都要进 SLO。10.6 会在真实动作头上把「动作误差随 age 的增长」也测出来。
</details>

<details markdown="1">
<summary>4. 时钟校准为什么要取 RTT 最小的一次，而不是平均？</summary>

四时间戳法假设「去程与回程延迟对称」，偏移估计的误差上界是 RTT/2。
RTT 越大，这个假设越不可靠（路径不对称的可能性越高），误差也越大。
取最小 RTT 的样本，等于挑选**最接近对称假设**的那次测量。

本章实测的 RTT 在 0.88–0.885 ms，估计误差上界 ±0.44 ms；
而未校准的偏差是 43 686 ms —— 相差五个数量级。
**先校准，再讨论毫秒级的优化。**
</details>

<details markdown="1">
<summary>5. 队列容量设成 1 省内存，为什么有效动作率只有 0.76？</summary>

因为容量 1 时，「推理占用中」到达的样本没有位置可放，只能丢弃
（`queue_full`）。10 Hz 控制周期是 100 ms，而推理要 40 ms（本章的 sleep 模型）
或 450 ms（真实端侧），后者意味着**大部分周期都在丢样本**。

三个选择：把容量加到「一个推理时长 / 控制周期 + 1」、
改用 latest 策略并接受年龄、或者换更小/更快的模型。
**容量应该由「推理耗时 ÷ 控制周期」决定，不是由内存预算决定**——
这也是 L1.6 里 KV 与权重挤占统一内存的同一笔账。
</details>
