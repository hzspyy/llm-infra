`del x` 只去掉一个 Python 引用。其它别名或 autograd 保存值仍可持有 storage。最后一个持有者释放后，allocator 的复用策略还取决于创建流和其它使用流；GPU 是否完成是另一件事。

## 三个生命周期与两种依赖

### 同流：CPU 复用可以早于 GPU 完成

在同一流中执行分配、计算和再次分配，GPU 命令按提交顺序消费内存。没有额外使用流时，native allocator 的 `free` 可以立即把块放回对应创建流的缓存；之后同流的新写入排在旧读取之后，不需要每次释放都查询 event。

```python
x = torch.randn(2000, 2000, device="cuda")
y = x * 2
del x
z = torch.empty(2000, 2000, device="cuda")
# 即使地址被重用，同流上的新写入也在先前读取之后执行。
```

`memory_allocated()` 衡量当前张量分配的块字节；`memory_reserved()` 是 allocator 持有的段字节。差值还可能包含等待其它流完成的块，不等于立即可复用空间，更不等于全部都是碎片。

### 跨流：数据就绪与存储寿命分别处理

```python
producer = torch.cuda.Stream()
consumer = torch.cuda.Stream()
with torch.cuda.stream(producer):
    x = torch.randn(1024, device="cuda")
    y = x * 2
with torch.cuda.stream(consumer):
    consumer.wait_stream(producer)  # 等待 y 的生产
    z = y * 3
    y.record_stream(consumer)       # 防止在 consumer 用完之前复用 y 的 storage
del y
```

只调用 `record_stream` 不会让 consumer 等待 producer；只建立生产依赖，也不自动把 consumer 的后续使用告诉 allocator。如果调用方掌握完整生命周期，可以在释放前让创建流等待使用流，例如 `producer.wait_stream(consumer)`，再释放 y；这样后续创建流上的复用也有正确顺序。无需把所有设备工作同步到 CPU。

[官方 record_stream 说明](https://docs.pytorch.org/docs/2.13/generated/torch.Tensor.record_stream.html)明确区分了这两条保证。

### 两类竞态的实测

`stream_races.py` 分别移除执行依赖与使用流记录；两组错误不能混成“跨流不安全”一个开关。

| 条件 | 观察 |
|---|---|
| 缺少 wait_stream | 20 次中 19 次读到旧值 |
| 建立 wait_stream | 同组 20 次未读到旧值 |
| 缺少 record_stream 且提前释放 | 20 次都观察到地址复用与错误读值 |
| 补全寿命依赖 | 同组未发生提前复用或错误读值 |

## Snapshot 与碎片口径

| 字段或计数器 | 含义 | 使用限制 |
|---|---|---|
| `active_allocated` | 块仍被张量占用 | snapshot 的 block state |
| `active_awaiting_free` | 张量已释放，仍等待其它使用流 | 不能计入可用 free block |
| `inactive` | 块可供复用 | 可能属于仍有活跃块的 segment |
| `inactive_split_bytes.all.current` | native allocator 的非可释放 split 字节统计 | 来自 memory_stats；不统计 expandable segment |
| `segment_pool_id` | 段所属池，区分普通池与图私有池 | 同时记录图的 `pool()` 身份 |
| `is_expandable` | 段是否使用可扩展映射 | 直接观察，不能由段数猜测 |

`inactive_split` 不是 snapshot 的 state 名。若要在所有模式下观察空洞，可另算“仍含活跃/等待块的 segment 中的 inactive 字节”，但它与 native 的不可释放 split 计数不是同一指标：expandable 的部分映射可回收，不能把两种定义混用。

### 设计取舍

同流缓存利用已经存在的执行顺序，减少主机同步；跨流跟踪以 event、轮询和延迟复用换取调用方便利。手工把使用流同步回创建流可以少做跟踪，但同步点过早会减少重叠。

普通池与图私有池分开保证捕获地址在 replay 期间有效；“私有”并不排除 expandable 映射。自定义 allocator 的 user pool、内部构建开关与不同 PyTorch 版本须另核对。统计既要说明分配器 backend，也要说明字段的适用范围。

| 配置 | 轨迹期间有存活图 | allocated 峰值 MiB | reserved 峰值 MiB | native inactive_split 峰值 MiB |
|---|---|---:|---:|---:|
| native | 否 | 307.94 | 382.00 | 151.94 |
| expandable | 否 | 300.94 | 350.00 | 不适用；该计数器为 0 |
| native，graph-first | 是 | 410.94 | 496.00 | 86.53 |

同一到达轨迹的存活张量字节账相同。native 的 allocated 与 requested 字节可能因块取整而不同；两种分配器的 reserved 变化可比较，但不能把 expandable 的计数器零值当成没有空洞。无图时，“活跃段内 inactive 字节”的峰值分别是 151.94 与 323.75 MiB，这仍不是跨 backend 的统一不可释放碎片指标。

### 图私有池与运行库工作区

直接匹配 `g.pool()` 和 `segment_pool_id`，native 的图池占 54 MiB；expandable 为 42 MiB，对应段的 `is_expandable` 为 true。释放所有图句柄和静态张量后，进程仍分别保留 64/80 MiB reserved；本次再清除 cuBLAS workspace 后均回到 0。这支持对这些进程残留的解释，不是“删图永不归还”的一般规律。

trace-first 的轨迹发生在图建立前，其轨迹峰值与无图一致；不能将它与 graph-first 的轨迹峰值混称为相同驻留状态。CUDA Graph 的提交节省与容量变化要分别测量。

## 前沿

可扩展映射、图池共享与基于图拓扑的跨流复用都在改变容量和同步成本。新增接口先核对版本、池类型和实际路径。多图 bucket 可以按明确约束共享 pool，不能无条件用“图数 × 单图峰值”估算所有场景。真实引擎的变长分配与 OOM 行为仍应连接 5.2/5.4 的请求负载，合成轨迹不替代服务容量验证。

## 陷阱

- `del` 不是 GPU barrier，也不保证所有 storage 引用已经释放。
- record_stream 管寿命，wait_stream/event 管执行顺序；它们不能互换。
- reserved−allocated 还可能含等待回收的块，不能全部算作可用缓存或碎片。
- `memory_allocated()` 在尚未初始化 CUDA 时返回空统计的零值，不会为了读这个值初始化 CUDA；峰值归零也不等于清空缓存。
- 非零残留必须按活跃对象、pool 与运行库 workspace 归因；仅观察 Python 图对象的删除不足以解释所有显存。

## 自测题

1. 同流的新张量为什么能在旧 kernel 完成前拿到同一地址？
::: fold
allocator 将块交给相同创建流，GPU 的新写入排在旧使用之后；CPU 分配发生得早，不代表 GPU 写入越过了旧读取。
:::

2. 为什么“调用 record_stream 后输出仍错”不矛盾？
::: fold
它防止 storage 提前复用，但不负责等待数据生产；consumer 仍需等待 producer。
:::

3. expandable 的 inactive_split 计数为零，能得出没有碎片吗？
::: fold
不能。这个 native 计数器不统计 expandable 段。需查看实际块状态与映射回收条件，并标明所用空洞/不可释放量的定义。
:::

4. 如何证明 graph-first 测到了存活图与请求轨迹共存？
::: fold
轨迹执行期间保留图、静态输入输出和 stream 句柄；在轨迹前后按 pool ID 保存 snapshot。只先 capture、随后删除图再跑轨迹不满足这个条件。
:::
