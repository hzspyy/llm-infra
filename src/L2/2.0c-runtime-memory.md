# 2.0c PyTorch 运行时内存：三个生命周期与异步语义

本章连接 Python 引用、CUDACachingAllocator 块状态和 CUDA 异步执行，解释张量何时失去引用、存储何时可复用、GPU 何时真正完成使用。通过四组实验和一个最小块池实现，演示跨流同步、碎片化和 CUDA Graph 内存池的实际行为。

---

## 本章回答的三个问题

1. **del tensor、allocator 可复用与 GPU 使用结束分别发生在何时？**  
   Python 对象在 `del` 后立即失去引用，但 allocator 需要等待 GPU kernel 完成才能将内存标记为可复用。三个时刻通常不同步。

2. **wait_stream 和 record_stream 分别建立什么约束？**  
   `wait_stream` 让一个流等待另一个流的所有先前操作，确保数据依赖顺序；`record_stream` 告诉 allocator 某个张量将被另一个流使用，防止过早释放。

3. **动态形状、碎片与 CUDA Graph 如何改变内存生命周期？**  
   变长分配导致碎片积累，即使 allocated 很小，reserved 也可能很大；CUDA Graph 使用独立内存池，与普通分配隔离。

## 三个生命周期

### 生命周期 1：Python 引用

```python
x = torch.randn(2000, 2000, device='cuda')  # Python 对象创建
del x  # Python 引用立即消失，refcount 降为 0
```

`del` 后 Python 对象被回收，但这**不意味着内存可以立即复用**。

### 生命周期 2：Allocator 可复用

CUDACachingAllocator 在 `del` 后将内存块标记为 "pending"（待回收），但需要等待 GPU 完成才能标记为 "free"（可复用）。

```python
x = torch.randn(2000, 2000, device='cuda')
y = x * 2
del x  # allocated 减少，但 reserved 不变
torch.cuda.synchronize()  # 等待 GPU 完成
# 现在 x 的内存变为 free，可以被新分配复用
```

### 生命周期 3：GPU 使用结束

CUDA kernel 是异步的。`x * 2` 提交后立即返回，kernel 可能仍在 GPU 上运行。

```python
y = x * 2  # kernel 提交，Python 继续
del x      # Python 引用消失，但 kernel 可能仍在读 x
# 如果此时复用 x 的内存，会导致竞态
```

Allocator 通过 stream 和 event 确保安全：只有 stream 上的所有先前操作完成后，内存才能复用。

## 跨流依赖与同步

### 问题场景：竞态

```python
s1 = torch.cuda.Stream()
s2 = torch.cuda.Stream()

with torch.cuda.stream(s1):
    x = torch.randn(1000, 1000, device='cuda')
    y = x * 2  # s1 上提交 kernel

with torch.cuda.stream(s2):
    z = y * 3  # s2 上提交 kernel，可能在 y 计算完成前启动
```

**错误**：s2 的 kernel 可能在 s1 的 `y = x * 2` 完成前就读取 y，导致读到未完成的数据。

### 解决方法 1：wait_stream

```python
with torch.cuda.stream(s2):
    s2.wait_stream(s1)  # s2 等待 s1 的所有先前操作完成
    z = y * 3
```

`wait_stream(s1)` 在 s2 上插入一个等待点，确保 s1 的所有先前 kernel 完成后，s2 才继续。

### 解决方法 2：record_stream

```python
with torch.cuda.stream(s1):
    x = torch.randn(1000, 1000, device='cuda')
    y = x * 2

with torch.cuda.stream(s2):
    y.record_stream(s2)  # 告诉 allocator：y 将被 s2 使用
    z = y * 3
```

`record_stream(s2)` 告诉 allocator："y 的内存将被 s2 使用，在 s2 完成前不能释放"。

### 区别

- **wait_stream**：控制执行顺序，确保数据依赖
- **record_stream**：控制内存生命周期，防止过早释放

两者通常需要同时使用：
```python
s2.wait_stream(s1)      # 确保 y 计算完成
y.record_stream(s2)     # 防止 allocator 在 s2 使用前释放 y
```

## 碎片化

### 什么是碎片

Allocator 以 segment 为单位向操作系统申请内存（通常 20 MB），然后在 segment 内部分配 block。当分配和释放的尺寸不规则时，segment 内部会产生碎片：

```
Segment (20 MB)
[4MB used] [2MB free] [3MB used] [1MB free] [10MB used]
```

即使有 3 MB 的 free 空间，也无法满足一个 5 MB 的分配请求（因为碎片不连续），allocator 只能申请新的 segment。

### 实验 3A：固定大小无碎片

{{results/crater/2.0c/memory_fragmentation.json:experiment_3a}}

10 次迭代，allocated 和 reserved 保持不变，碎片率 80.9%（因为 20 MB segment 只用了 3.81 MB）。

### 实验 3B：变长分配产生碎片

{{results/crater/2.0c/memory_fragmentation.json:experiment_3b}}

分配 500/1000/1500/2000 的张量，碎片率在 30%～95% 之间波动。第 2 次迭代（1000→1500→2000）后，reserved 从 2 MB 跳到 22 MB，说明 allocator 申请了新的 segment。

### 实验 3D：KV cache 模拟

模拟变长序列的 KV cache：

{{results/crater/2.0c/memory_fragmentation.json:experiment_3d}}


**关键观察**：从 1024 回到 128 时，allocated 只有 16 MB，但 reserved 仍为 240 MB。碎片率达到 93.3%。

## CUDA Graph 内存池

### 普通分配 vs CUDA Graph

CUDA Graph 捕获时会记录所有内存分配，replay 时使用**独立的内存池**，与普通分配隔离。

## 最小块池实现

为了理解 allocator 的核心逻辑，我们实现一个最小块池，支持：
1. 流归属
2. 延迟回收（pending）
3. Event 完成检查

### 核心数据结构

```python
class Block:
    def __init__(self, size, stream):
        self.size = size
        self.stream = stream
        self.event = None
        self.allocated = True
```

### 分配逻辑

```python
def allocate(size, stream):
    # 1. 查找可复用的 free block
    for block in free_blocks:
        if block.size >= size:
            block.allocated = True
            block.stream = stream
            return block
    
    # 2. 检查 pending blocks（等待 event 完成）
    process_events()
    for block in free_blocks:
        if block.size >= size:
            block.allocated = True
            block.stream = stream
            return block
    
    # 3. 申请新 segment
    segment = allocate_segment(size)
    block = Block(size, stream)
    return block
```

### 释放逻辑

```python
def free(block):
    # 标记为 pending，记录当前 stream 的 event
    block.allocated = False
    block.event = block.stream.record_event()
    pending_blocks.append(block)
```

### Event 完成检查

```python
def process_events():
    for block in pending_blocks:
        if block.event.query():  # 检查 event 是否完成
            free_blocks.append(block)
            pending_blocks.remove(block)
```

## 源码入口

### CUDACachingAllocator

**文件**：`pytorch/c10/cuda/CUDACachingAllocator.cpp`

核心函数：
- `malloc()`：分配内存，查找 free block → 检查 pending → 申请新 segment
- `free()`：释放内存，记录 event 并标记为 pending
- `process_events()`：检查 pending 队列，将完成的 block 移到 free

关键数据结构：
- `Block`：包含 size、stream、event、allocated 标志
- `Segment`：一次向操作系统申请的大块内存（默认 20 MB）

### Stream 与 Event

**文件**：
- `pytorch/c10/cuda/CUDAStream.h`
- `pytorch/c10/cuda/CUDAEvent.h`

核心函数：
- `record()`：在 stream 上记录 event
- `query()`：查询 event 是否完成
- `wait()`：让当前 stream 等待 event 完成

### Python 绑定

**文件**：`pytorch/torch/csrc/cuda/Module.cpp`

核心函数：
- `THCPModule_cudaSynchronize()`：同步所有 stream
- `THCPStream_wait_stream()`：stream 等待另一个 stream
- `THPVariable_record_stream()`：记录张量将被另一个 stream 使用

## 常见陷阱

### 1. 把 reserved 当作泄漏

```python
x = torch.randn(1000, 1000, device='cuda')
del x
torch.cuda.synchronize()
# reserved 仍为 20 MB，这不是泄漏！
```

Allocator 保留内存以供复用，只有 `empty_cache()` 才会归还给操作系统。

### 2. 跨流未同步

```python
with torch.cuda.stream(s1):
    y = x * 2

with torch.cuda.stream(s2):
    z = y * 3  # 错误：未等待 s1
```

必须 `s2.wait_stream(s1)` 或者在主流上同步。

### 3. 跨流未记录使用者

```python
with torch.cuda.stream(s1):
    y = x * 2

del x  # 错误：allocator 可能在 s1 完成前释放 x
```

必须 `x.record_stream(s1)` 告诉 allocator。

### 4. 测量工具触发初始化

```python
torch.cuda.memory_allocated()  # 这会触发 CUDA 初始化
x = torch.randn(10, 10, device='cuda')
# 此时 reserved 可能包含初始化开销
```

测量前先 `reset_peak_memory_stats()`。
