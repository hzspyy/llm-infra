## 本章回答三个问题

1. warp 分支发散的代价是不是"N 路发散就慢 N 倍"？实测和理论差多少，为什么？
2. **占用率（occupancy）越高越快吗**？memory-bound 与 compute-bound 的答案一样吗？
3. 为什么 `grid = 1021` 会比 `grid = 1020` **慢 17%**？

CUDA 用三个层次组织工作：线程执行代码，线程组成 block，多个 block 组成 grid。
GPU 的 SM 接收并执行 block；资源允许时，一个 SM 可以同时容纳多个 block。
occupancy（占用率）描述常驻 warp 数相对于硬件上限的比例，
并不直接表示 GPU 有多忙，也不直接表示程序有多快。

## 机制拆解

### 分支发散：实测 6.02×，理论 8×

理解分支发散时，可以先看同一 warp 中哪些线程在执行哪条路径。
不同路径可能需要分开发射，并用活跃掩码控制参与线程。
现代 GPU 的独立线程调度不能简单等同于“32 个线程始终共用一个程序计数器”。

实验：让每条分支做**完全相同**的工作量（一条 `fmaf`），唯一的区别是有几条路：

```cpp
int branch = (threadIdx.x % 32) % ways;      // ways=1 时全 warp 走同一条
for (int it = 0; it < iters; ++it) {
    switch (branch) {
        case 0: acc = fmaf(acc, 1.0001f, 0.1f); break;
        case 1: acc = fmaf(acc, 1.0002f, 0.2f); break;
        ...
    }
}
```

实测：

| 发散路数 | 耗时 ms | 相对 1 路 | 理论 |
|---|---|---|---|
| 1 | 3.912 | 1.00× | 1× |
| 2 | 5.653 | **1.45×** | 2× |
| 4 | 12.838 | **3.28×** | 4× |
| 8 | 23.544 | **6.02×** | 8× |

**实测始终低于理论。** 原因是编译器把短分支转成了**谓词执行（predication）**：
不跳转，两条路的指令都发，用谓词寄存器决定哪些线程的结果生效。

这样省掉了分支指令与流水线冲刷，但**算力照付**——所以还是慢，只是没那么慢。
L0.1 的 SASS 原始现场里那 273 条 `FSEL`（条件选择）和 225 条 `ISETP`（置谓词），
就是谓词执行的实物。

::: note 什么时候真的会跳转
分支体足够长时，编译器会判断"两边都算"不划算，改用真正的跳转 + 掩码
（SASS 里是 `BSSY`/`BSYNC` 配对）。这时代价才接近 N 倍。

**一般规律：短分支 ≈ 谓词执行（算力惩罚），长分支 ≈ 真发散（时间惩罚）。**
两种都要避免，但前者温和得多。
:::

### 占用率：1 → 2 有用，2 → 6 无用

「提高占用率」是最常被误当成目标的指标。用共享内存做旋钮
（只改占用率、算法完全不变）实测：

| smem/block | 驻留 block/SM | memory-bound (GB/s) | compute-bound (TFLOPS) |
|---|---|---|---|
| 96 KB（动态） | **1** | **1545.0** | — |
| 64 KB（动态） | **1** | **1546.1** | — |
| 48 KB | 2 | **1678.8** | 115.5 |
| 32 KB | 3 | 1687.3 | 115.6 |
| 16 KB | 5 | 1694.5 | 115.9 |
| 8 KB | 6 | 1699.3 | 116.4 |
| 1 KB | 6 | 1685.1 | 116.2 |

两个结论：

**(1) 1 → 2 block/SM 涨 9%，2 → 6 完全不涨。**
这精确复现了 L1.1 的 Little's Law 结果：带宽-延迟积是 536 KB，
2 block/SM（2720 warp × 512 B 在途）就已经超过它。**再多的 warp 无处可用。**

**(2) compute-bound 对占用率几乎完全不敏感**（115.5 → 116.4，差 0.8%）。

因为它靠的不是线程级并行，而是**指令级并行（ILP）**——kernel 里写了 4 条独立的 FMA 链：

```cpp
float x0 = a, x1 = a + 1, x2 = a + 2, x3 = a + 3;   // 4 条独立链填流水
for (int i = 0; i < iters; ++i) {
    x0 = fmaf(x0, b, c); x1 = fmaf(x1, b, c);
    x2 = fmaf(x2, b, c); x3 = fmaf(x3, b, c);
}
```

一个 warp 自己就能填满 FMA 流水线，不需要别的 warp 来接力。

顺带一个数字：**116 TFLOPS 是 CUDA core 的 FP32 吞吐**。
对照 L1.2 测出的 tensor core bf16 251.9 TFLOPS —— **tensor core 快 2.2 倍**。
核算一下：$170\ \text{SM} \times 128\ \text{FP32 单元} \times 2\ \text{FLOP} \times 2.9\ \text{GHz} = 126$ TFLOPS，
实测 116 = **92%**，对得上。

::: warning 「提高占用率」不是目标
占用率是**掩盖延迟的手段**。一旦延迟已经被掩盖住（本机 2 block/SM 就够了），
再提高它只会挤占寄存器和共享内存，**反而伤害每线程的工作效率**。

L1.1 的自测题 4 讲过同一件事：GEMM 的 tile 从 128×128 缩到 64×64 能让占用率翻倍，
但数据复用率减半，净效果是变慢。**唯一的目标是墙钟时间。**
:::

### 多流并发：只有 kernel 占不满 GPU 时才有意义

用一个只占 24% SM 的小 kernel（42 blocks / 170 SM）：

| 并发 kernel 数 | 同一条流 | 各自一条流 | 重叠倍数 |
|---|---|---|---|
| 1 | 0.316 ms | 0.330 ms | **0.96×**（略亏） |
| 2 | 0.627 ms | 0.322 ms | **1.95×** |
| 4 | 1.254 ms | 0.333 ms | **3.77×** |

**1 个 kernel 时多流是净亏损**（多一次流切换开销）。
2 个和 4 个时接近线性加速——因为 4 × 24% = 96%，正好把 GPU 填满。

**这直接对应推理里的场景**：decode 每步有 444 个 kernel（L0.1 实测），
其中 RMSNorm、RoPE、SwiGLU 这些小算子在 batch=1 时根本占不满 GPU。
理论上可以多流并发，但实际上它们之间有数据依赖（层与层串行），
所以真正的解法是**融合**（L2.7）而不是并发。

多流真正有用的地方是**无依赖的工作**：H2D 传输与计算重叠（L1.3）、
不同请求的 prefill 与 decode 重叠、以及 CPU 侧调度与 GPU 执行重叠（L5.4）。

### 尾效应：耗时是阶梯，不是斜线

这是本章最实用的一个结论。

一"波"能同时驻留的 block 数 = `SM 数 × 每 SM 可驻留 block 数`。
本机对这个 kernel 是 $170 \times 6 = 1020$。扫描 grid 大小：

```
每 SM 可驻留 6 个 block ⇒ 一波 = 1020 个 block
blocks    波数    耗时 ms    每 block 摊销 µs
510       0.50      0.611        1.20
1018      1.00      1.074        1.05
1019      1.00      1.075        1.06
1020      1.00      1.080        1.06
1021      1.00      1.263        1.24    ← 跨过波次边界，跳了一台阶
1022      1.00      1.265        1.24
2039      2.00      2.096        1.03
2040      2.00      2.096        1.03
2041      2.00      2.264        1.11    ← 又一个台阶
3060      3.00      3.100        1.01
3061      3.00      3.271        1.07    ← 又一个
```

**1020 → 1021 只多了 1 个 block，耗时涨了 17%。**
新增 block 需要等某个 SM 释放足够资源后才能开始。
这里的“波”是分析并发容量的模型，不是所有 block 之间存在全局屏障。

而 1018 / 1019 / 1020 三者耗时几乎相同（1.074 / 1.075 / 1.080）——
**波内加 block 是免费的**。

这解释了三件事：

1. **grid 要按「SM 数 × 每 SM 可驻留 block 数」对齐。**
   多一个 block 的代价可能是整整一波。
2. **persistent kernel 的动机**：固定开一波 block，内部循环取任务。
   这样永远只有一波，没有尾效应。FlashAttention-4 的
   "longest-processing-time-first tile scheduler" 就是在做这件事（L3.2）。
3. **小 batch 推理为什么效率低**：batch=1 时很多 kernel 的 grid 远小于一波，
   GPU 大部分 SM 空着。这是 L0.2 里"算力利用率不到 6%"的另一个侧面。

## 工程实现 · 源码走读：引擎在哪里对齐 grid

### 1. vLLM 的 `reshape_and_cache_flash`

L0.1 的 trace 里这个 kernel 每步调用 28 次（每层一次）。
它的 grid 是**按 token 数**决定的：batch=1 时只有 1 个 block，
170 个 SM 里 169 个闲着。

这就是为什么小算子在 decode 阶段的**绝对时间**很小（0.8% 的 GPU 时间），
但**launch 次数**却是大头（L1.4 测出 444 次 × 2.68 µs = 1.19 ms）。
**问题不在 kernel 慢，在 kernel 太多太小。**

### 2. FlashAttention 的 tile scheduler

L1.1 走读过 `Flash_fwd_kernel_traits<128, 64, 128, 4>`。
grid 维度是 `(ceil(seqlen_q / 64), batch, heads)`。

对 Qwen3-1.7B、seqlen=1024、batch=1：$\lceil 1024/64 \rceil \times 1 \times 16 = 256$ 个 block。
不能用前一个测试 kernel 的 1020-block 容量评估这个 attention kernel。
每个 kernel 的寄存器、共享内存和 block 大小不同，需要单独计算可驻留 block 数。

而 `flash_fwd_splitkv_kernel`（L0.1 trace 里 decode 用的那个）之所以要 split-K，
正是因为 decode 时 seqlen_q=1，不 split 的话 grid 只有 `1 × batch × heads`，
远远填不满 GPU。**split-K 是在制造并行度**（L3.3）。

### 3. `cudaOccupancyMaxActiveBlocksPerMultiprocessor`

本章的实验和引擎都用同一个 API 来问"一个 SM 能塞几个 block"：

```cpp
int blocks_per_sm = 0;
cudaOccupancyMaxActiveBlocksPerMultiprocessor(&blocks_per_sm, kernel, 256, smem_bytes);
int grid = SMS * blocks_per_sm;         // 正好一波
```

这是写 persistent kernel 的标准起手式。**不要硬编码 grid 大小**——
它依赖于 kernel 的寄存器用量，而寄存器用量会随编译器版本变化。

## 工程实现 · 自己写一遍

三个实验设计上的要点。

**(1) 测发散要让每条路工作量相同。**

否则你测的是"工作量不同"而不是"发散本身"。本实验每条分支都是一条 `fmaf`，
只是常数不同（避免编译器合并它们）。

**(2) 用共享内存当占用率旋钮，而不是改 block 大小。**

改 block 大小会同时改变很多东西（每 block 的工作量、访存模式、尾效应）。
共享内存是唯一一个**只影响驻留 block 数**的旋钮：

```cpp
template <int SMEM_KB>
__global__ void occupancy_mem_kernel(...) {
    __shared__ char pad[SMEM_KB * 1024];
    pad[threadIdx.x] = (char)threadIdx.x;      // 防止 smem 被优化掉
    ...
}
```

那行 `pad[threadIdx.x] = ...` 是必需的——不写的话编译器发现 `pad` 没被用，
直接把 `__shared__` 声明删掉，占用率根本不会变。

**(3) 突破 48 KB 静态上限要显式 opt-in。**

静态 `__shared__` 最多 48 KB。想压到 1 block/SM 必须用动态共享内存：

```cpp
extern __shared__ char dpad[];              // 动态
...
CK(cudaFuncSetAttribute(occ_mem_dyn,
       cudaFuncAttributeMaxDynamicSharedMemorySize, 96 * 1024));
occ_mem_dyn<<<grid, 256, kb * 1024>>>(...);  // 第三个参数是动态 smem 字节数
```

这就是 L1.1 里讲的 `sharedMemPerBlockOptin` —— 所有现代 attention/GEMM kernel
都要调这个 API，忘了调会在启动时报 `invalid argument`。

**(4) 波长要现场问，不能算。**

```cpp
int bps = 0;
cudaOccupancyMaxActiveBlocksPerMultiprocessor(&bps, tail_kernel, 256, 0);
int wave = SMS * bps;                       // 一"波"
```

本机这个 kernel 是 6 block/SM，但换个 kernel（寄存器多一点）可能就是 4。
**写死数字的实验第二天就不对了。**

### 建议你做的消融

| 改什么 | 你应该看到什么 |
|---|---|
| 把发散实验的分支体加长（每条 10 条 `fmaf`） | 编译器改用真跳转，倍数应该更接近理论的 N× |
| 把 `pad[threadIdx.x] = ...` 那行删掉 | 占用率不再变化——**亲手见一次"编译器把你的实验删了"** |
| 把 compute-bound kernel 的 4 条独立链改成 1 条 | ILP 消失，此时占用率**才会**开始起作用 |
| 多流实验里把 `small_grid` 改成 `SMS * 6`（占满） | 重叠倍数应该掉到 1×——满负载时多流无意义 |
| 用 `compute-sanitizer ./exec_model` 跑一遍 | 检查有没有越界访问、竞态。本机已装（`nvidia/cu13/bin/compute-sanitizer`） |

```
ptxas info    : Used 16 registers, used 0 barriers, 49152 bytes smem
    0 bytes stack frame, 0 bytes spill stores, 0 bytes spill loads
ptxas info    : Used 12 registers, used 0 barriers, 32768 bytes smem
    0 bytes stack frame, 0 bytes spill stores, 0 bytes spill loads
ptxas info    : Used 16 registers, used 0 barriers, 16384 bytes smem
```

四个字段，每个都直接决定性能：

- **`Used N registers`**：每线程用了多少寄存器。每 SM 的寄存器文件是 64K 个 32 位寄存器，
  所以最多能驻留 $65536 / N$ 个线程。本例只用 12–16 个，不是瓶颈。
- **`bytes smem`**：静态共享内存。本例是我们故意加的旋钮。
- **`stack frame` / `spill stores` / `spill loads`**：**寄存器溢出**。
  全为 0 说明没溢出。一旦不为 0，说明寄存器不够用，变量被踢到 local memory
  （其实在显存里，延迟 929 周期——L1.1 实测），性能会断崖式下跌。

**写 kernel 时第一件事就是看这四行。** 尤其是 spill：
它不会报错，只会让你的 kernel 莫名其妙慢 3 倍。L2.4 优化 GEMM 时会反复用到。
</details>

## 前沿

| 方向 | 内容 |
|---|---|
| **Thread Block Cluster（Hopper 起）** | 在 grid 与 block 之间新增一层"cluster"，同 cluster 的 block 可以访问彼此的共享内存（DSMEM）。等于把本章的"一波"概念显式化，并让 tile 可以更大。**sm_120 不支持**（L1.2） |
| **Cluster Launch Control（Blackwell）** | 让 kernel 在运行时动态获取下一批 tile，硬件层面的 persistent kernel。L1.2 前沿提到的 sm_120 NVFP4 GEMM 达到 80% 效率就用了它 |
| **persistent kernel + 软件流水** | 固定开一波，内部循环取任务，彻底消灭尾效应。FA4 的 LPT（最长处理时间优先）tile 调度器是这条路线的代表（L3.2） |
| **warp specialization** | 同一个 block 里不同 warp 干不同的活（一组搬数据、一组算），用 `__syncthreads` 或 named barrier 协调。这是 Hopper/Blackwell 上高性能 kernel 的标准结构（L2.4、L3.2） |
| **CUDA Graph 条件节点** | 图里能带分支与循环，减少"形状一变就要重新捕获"。vLLM 目前用 piecewise graph 折中（L5.4） |
| **绿色上下文 / MPS 分区** | 把 SM 划分给不同的上下文，让本章的"占不满 GPU"问题在多租户下有解（L8.2） |

> 除本站实测外的内容来自各自文档，**未在本站复现**<span class="unverified">未实测</span>。

## 陷阱

**1. 把占用率当目标。** 本机 2 block/SM 就打满带宽，再高无用。
占用率是手段，墙钟时间才是目标。

**2. 忘了防优化。** 共享内存不被读就会被删掉，占用率实验会完全失效。
compute-bound 的累加值不被使用，整个循环会被删掉。

**3. 用改 block 大小来调占用率。** 它同时改变了太多变量，实验不干净。
共享内存是唯一的单变量旋钮。

**4. 硬编码 grid 大小。** 波长取决于 kernel 的寄存器用量，
换个编译器版本就变了。用 `cudaOccupancyMaxActiveBlocksPerMultiprocessor` 现场问。

**5. 以为多流总是有用。** 单个 kernel 已经占满 GPU 时，多流是净亏损（实测 0.96×）。

**6. 忽略 `-Xptxas -v` 里的 spill。** 寄存器溢出不报错，只会让 kernel 悄悄慢几倍。

**7. 以为发散一定慢 N 倍。** 短分支会被转成谓词执行，实测 8 路只慢 6.02×。
但这不代表可以随便写发散——6 倍也是 6 倍。

## 自测题

<details markdown="1">
<summary>1. 我的 kernel 用了 64 个寄存器，block 是 256 线程，没有共享内存。每 SM 能驻留几个 block？</summary>

每 SM 的寄存器文件是 **65536 个 32 位寄存器**（Blackwell 消费级）。

每 block 需要：$256\ \text{线程} \times 64\ \text{寄存器} = 16384$ 个。

$$65536 / 16384 = 4\ \text{个 block}$$

但还要检查另外两个上限：
- 每 SM 最大线程 1536 → $1536/256 = 6$ 个 block
- 每 SM 最大 block 数（通常 16–32）

**取三者最小值 = 4 个 block/SM**，对应 $4 \times 256/32 = 32$ 个 warp，
占用率 $32/48 = 67\%$。

**但请注意**：本章实测显示 2 block/SM 就够打满带宽了。
所以 67% 的占用率**完全够用**，不必为了提高它去砍寄存器——
砍寄存器很可能触发 spill，那才是灾难。

（实际写代码时不用手算，直接调 `cudaOccupancyMaxActiveBlocksPerMultiprocessor`。）
</details>

<details markdown="1">
<summary>2. 我把 grid 从 1020 改成 1024（凑成 2 的幂，看起来更整齐）。会发生什么？</summary>

**会慢 17%。** 因为一波是 1020，1024 要开第二波来跑那 4 个 block，
而那 4 个 block 独占一整波的时间。

本章实测：1020 → 1.080 ms，1021 → 1.263 ms。1024 会在同一个台阶上。

**"凑成 2 的幂"在 GPU 上是个坏习惯。** 该对齐的是
`SM 数 × 每 SM 可驻留 block 数`，本机是 $170 \times 6 = 1020$ —— 
一个既不是 2 的幂也不好看的数。

**唯一正确的做法是问 API，不是猜。**
</details>

<details markdown="1">
<summary>3. 为什么 compute-bound kernel 对占用率不敏感，而 memory-bound 从 1 到 2 block/SM 会涨 9%？</summary>

因为两者掩盖延迟的方式不同。

**memory-bound**：延迟是访存的 929 周期（L1.1 实测），
必须靠**足够多的在途请求**掩盖。按 Little's Law，需要 536 KB 在途。
1 block/SM 时只有 1360 warp × 512 B = 0.70 MB —— 看起来够，
但考虑到不是所有 warp 时刻都有未完成的 load，边际上不足，所以掉到 1546 GB/s。
2 block/SM 时富余，打满 1690 GB/s。

**compute-bound**：延迟是 FMA 的几个周期，而 kernel 里写了 **4 条独立的 FMA 链**，
**一个 warp 自己就能填满流水线**（ILP）。不需要别的 warp 来接力，所以占用率无关。

**推论**：如果把那 4 条链改成 1 条（纯依赖链），ILP 消失，
compute-bound 就会变得和 memory-bound 一样依赖占用率。
**这正是本章建议你做的消融之一。**
</details>

<details markdown="1">
<summary>4. decode 每步有 444 个 kernel，很多都很小、占不满 GPU。既然多流能重叠 3.77×，为什么引擎不用多流跑它们？</summary>

因为**它们之间有数据依赖**。

Transformer 的一层是严格串行的：
`RMSNorm → QKV投影 → RoPE → attention → O投影 → 残差 → RMSNorm → SwiGLU`。
每一步的输入是上一步的输出，没有并发空间。

本章的多流实验之所以能重叠 3.77×，是因为那 4 个 kernel **完全独立**。

**真正的解法是融合（L2.7）**：把 RMSNorm + 残差加合成一个 kernel
（L0.1 trace 里的 `fused_add_rms_norm` 就是），把 SwiGLU 的 silu 与 mul 合成一个
（`act_and_mul_kernel`）。融合同时减少 launch 次数和访存往返。

**多流在推理里真正有用的地方**是无依赖的工作：
- H2D 权重加载与计算重叠（L1.3）
- 不同请求的 prefill 与 decode 重叠（chunked prefill，L5.3）
- CPU 调度与 GPU 执行重叠（L5.4）
</details>

<details markdown="1">
<summary>5. 我写了一个 attention kernel，<code>-Xptxas -v</code> 显示 <code>Used 168 registers, 48 bytes spill stores</code>。该怎么办？</summary>

**先确认 spill 有多严重，再决定。**

48 字节的 spill 很少（大约 12 个寄存器），可能只在某个冷路径上。
但 spill 写的是 **local memory，物理上在显存里**（L1.1 实测延迟 929 周期），
如果它在内循环里，代价是灾难性的。

**诊断顺序**：

1. **看 spill 在哪**：用 `-Xptxas -v --generate-line-info` 加上 SASS 反汇编
   （`nvdisasm`，本机可用），找 `LDL`/`STL`（local load/store）指令在哪一行。
2. **如果在内循环**：必须消除。手段是减少活跃变量——
   比如把 accumulator 分块、把常量移出循环、或者缩小 tile。
3. **如果在冷路径**（初始化、收尾）：可以忽略。

**不要用 `__launch_bounds__` 强行限制寄存器来"解决"它**——
那只会让编译器 spill 得更多。`__launch_bounds__` 是告诉编译器
"我需要这个占用率"，编译器会为此牺牲寄存器，是**用 spill 换占用率**。
按本章的结论，本机 2 block/SM 就够了，**没必要为占用率牺牲寄存器**。
</details>
