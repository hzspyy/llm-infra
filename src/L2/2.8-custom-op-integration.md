## 本章回答三个问题

L2 到这里已经会写 kernel（2.1–2.5）、会看编译器（2.6b、2.7）、
会读 dispatcher（2.0）。这一章把它们接起来：**把一个自己写的 CUDA kernel
变成 PyTorch 里的一等公民**——能求导、能被 `torch.compile` 捕获、
能在别人的模型里当作普通算子使用。

1. `torch.compile` 遇到一个它不认识的算子会怎么办？
2. 自定义算子怎么参与反向？`fake`（meta）函数是干什么的？
3. 注册之后它能被融合吗？为什么？

本章用的算子：

$$\text{out}[i] = \sum_j \mathrm{relu}(x[i,j] \cdot w[j])$$

反向（后面会用 `gradcheck` 验）：

$$\frac{\partial L}{\partial x[i,j]} = g[i] \cdot w[j] \cdot \mathbf{1}[x_{ij} w_j > 0], \qquad
\frac{\partial L}{\partial w[j]} = \sum_i g[i] \cdot x[i,j] \cdot \mathbf{1}[x_{ij} w_j > 0]$$

选它是因为：它含一个归约（复用 2.3 的两段式归约结构）、
有两个需要求导的输入、而且反向里有一个**很容易忘掉的 relu 掩码**——
后面会故意忘一次，看 `gradcheck` 能不能抓住。

## 一 · 裸 kernel 调用不自动具备框架语义

先用 `load_inline` 编出来，确认它是对的：

```
前向对不对: max|err| = 5.684e-14
返回类型: <class 'torch.Tensor'>  shape=(64,)
```

数值没问题。但它在 PyTorch 眼里什么也不是：

```
l28::fused_scale_sum         **不存在**
aten::add.Tensor             存在
```

dispatcher 里没有它——它只是一个 pybind 出来的 python 可调用对象。
后果有两个。

**第一，没有反向：**

```
out.requires_grad = False   grad_fn = None
```

autograd 根本不知道发生过这次计算。把它放进模型里，反向传播会在这里断掉，
而且**不报错**。

**第二，`torch.compile` 装作没看见。** 这一条有个陷阱：

```
explain(): 图数量 1   图断裂 0   捕获算子 1
```

看起来一切正常。但把捕获到的图打印出来：

```python
def forward(self, L_stack0_ : torch.Tensor):
    l_stack0_ = L_stack0_
    mul = l_stack0_ * 2;  l_stack0_ = None
    return (mul,)
```

**kernel 调用根本不在图里。** 图的入参 `L_stack0_` 是"栈上第 0 号槽"——
也就是**已经算好的结果**。Dynamo 在图外 eager 执行了这次调用，
只从它的返回值开始捕获，于是图里只剩一个 `* 2`。

设置 `fullgraph=True`，让未完整捕获的情况显式报错：

```
Unsupported: Attempted to call function marked as skipped
```

::: warning explain() 报 0 次断裂，不等于全部被捕获
断裂计数只统计捕获过程中被打断的次数；
如果不支持的调用恰好在区域**开头**，Dynamo 直接从它之后开始，
计数是 0，但你的算子完全在编译范围之外。

判据有两个，都比 `explain` 的计数可靠：
把图打印出来看有没有你的算子；或者直接上 `fullgraph=True`。
:::

Dynamo 自己也给了提示（运行时的 UserWarning）：

```
Dynamo does not know how to trace the builtin `l28_fss...fss_forward`.
This function is either a Python builtin ... or a third-party C/C++ Python
extension (perhaps created with pybind). ... please either wrap it into a
PyTorch-understood custom operator ... or, if it is traceable, use
`torch.compiler.allow_in_graph`.
```

## 二 · 注册成一个真正的算子

```python
@torch.library.custom_op("l28::fused_scale_sum", mutates_args=())
def fused_scale_sum(x: torch.Tensor, w: torch.Tensor) -> torch.Tensor:
    return m.fss_forward(x, w)
```

`mutates_args=()` 是在告诉框架"这个算子不改写任何输入"。
这不是可选的礼貌信息——functionalization 和内存规划都依赖它，
写错会导致难查的错误。

注册之后 dispatcher 里就有它了：

```
name: l28::fused_scale_sum
schema: l28::fused_scale_sum(Tensor x, Tensor w) -> Tensor
debug: registered at .../torch/_library/custom_ops.py:1104
alias analysis kind: FROM_SCHEMA
Meta: registered at .../custom_ops.py:1104 :: (none) [ boxed ]
Autograd[alias]: registered at .../custom_ops.py:1104 :: (none) [ boxed ]
CompositeExplicitAutograd[alias]: registered at .../custom_ops.py:1104 :: (none) [ boxed ]
```

对照 2.0 里 `aten::add.Tensor` 那张 97 行的表，这里只有三行。注意它落在哪个键上：

| key | 有 kernel |
|---|---|
| CUDA | **False** |
| CPU | **False** |
| Meta | True |
| Autograd | True |
| CompositeExplicitAutograd | **True** |

`CUDA` 和 `CPU` 都是 False，而 `CompositeExplicitAutograd` 是 True：
`torch.library.custom_op` 默认注册的是**与后端无关**的实现，
由这个别名键覆盖所有后端。（想按设备分别注册，用
`custom_op(..., device_types="cuda")` 或 `register_kernel`。）

`Meta` 和 `Autograd` 虽然显示 True，注册的是**占位实现**——
调用时会报错提示你还没写。接下来两节就是补这两个。

### 二之二 · 边界输入与 opcheck（任务 A 的检查清单）

注册完四份契约，还要回答"输入不合法时错误出在哪"。本章的算子在
`(4, 8)` 上跑通之后，逐项喂边界输入（crater 实测）：

| 输入 | 结果 |
|---|---|
| 连续 `(4, 8)` | 与参照 `(x*w).relu().sum(-1)` 的 `max|d|` = **0** |
| 转置视图（非连续） | 通过，与参照一致（包装层做了 `.contiguous()`） |
| 空 tensor `(0, 8)` | 返回 `(0,)`，不报错（见下面的说明） |
| `int64` 输入 | `RuntimeError: x 必须是浮点张量，实际 torch.int64` |
| 1D 输入 | `RuntimeError: x 必须是 2D，实际 1D` |
| `w` 长度 16（cols=8） | `RuntimeError: w 必须是长度 8 的 1D 张量，实际 shape=(16,)` |
| `w` 长度 4（cols=8） | 同上（短于 cols 时会越界读，更危险） |

**这三条 `RuntimeError` 是包装层自己抛的。** 裸 kernel 的 schema 只声明
`(Tensor, Tensor) -> Tensor`，不检查形状兼容：`w` 更长时 kernel 只读前 8 个元素，
**静默给出一个"看起来正常"的结果**；`w` 更短时会读到张量之外的内存。
所以自定义算子的第一层契约检查要自己写在包装层里，位置就在调用 kernel 之前。

**opcheck 四项全过**（`torch.library.opcheck`）：

```
test_schema=SUCCESS  test_autograd_registration=SUCCESS
test_faketensor=SUCCESS  test_aot_dispatch_dynamic=SUCCESS
```

这四项正好对应本章开头那张图的四份契约：schema/alias、autograd 注册、
fake 实现、以及"能不能被 AOTAutograd 追踪"。**它们不是可选的自测**，
少哪一项就对应少一份契约。

**空 tensor 的边界要单独说。** 本章的 kernel 按行发射，`rows=0` 时
grid 就是 0 —— 本机（驱动 580.95.05 + CUDA 13.0）实测不报错、返回 `(0,)`，
也不需要特判。但"grid=0 的发射"是否被容忍依赖驱动与架构，
包装层显式特判（`if x.shape[0] == 0: return x.new_empty((0,))`）才是稳妥写法。
同一批次另一次运行里，这个用例之后出现过一次异步 `cudaErrorInvalidValue`，
未能复现，因此不作为结论记录。

## 三 · fake（meta）函数：不执行也要知道形状

`torch.compile` 在追踪时不执行真实计算，而是用 FakeTensor 进行符号推导，
只关心形状和 dtype（2.0 §3.3 里 `Meta` 键上注册了 1614 个算子，比 CUDA 还多）。
若自定义算子缺少 meta 实现，追踪过程便会直接报错：

```
TorchRuntimeError
  RuntimeError when making fake tensor call
    Explanation: Dynamo failed to run FX node with fake tensors:
      call_function l28.no_fake.default(*(FakeTensor(..., device='cuda:0', size=(64, 512)), ...
```

补上：

```python
@no_fake.register_fake
def _(x, w):
    torch._check(x.dim() == 2, lambda: "x 必须是二维")
    torch._check(w.dim() == 1, lambda: "w 必须是一维")
    return x.new_empty(x.shape[0])
```

**它只描述形状与 dtype，不做任何真实计算。** `new_empty` 分配的是
FakeTensor（追踪时）或真实空张量（不追踪时），里面的值从不被读取。
`torch._check` 是给符号形状用的断言——它会变成约束求解器的一条约束，
而不是普通的 `assert`（普通 assert 在动态形状下会强制特化）。

补上之后编译成功，图里的样子：

```python
def forward(self, L_a_ : torch.Tensor, L_b_ : torch.Tensor):
    l_a_ = L_a_
    l_b_ = L_b_
    no_fake_default = torch.ops.l28.no_fake.default(l_a_, l_b_);  l_a_ = l_b_ = None
    mul = no_fake_default * 2;  no_fake_default = None
    return (mul,)
```

和第一节那个图对比：现在 `torch.ops.l28.no_fake.default` **在图里**，
两个输入也都是真正的图输入（`L_a_`、`L_b_`），不再是"栈上算好的值"。

它是图里的一个**不透明节点**：Inductor 知道它的形状、知道要在这里调用它，
但不知道它内部在算什么。这一点决定了第五节的融合结论。

## 四 · 反向：注册 + gradcheck

```python
def setup_context(ctx, inputs, output):
    x, w = inputs
    ctx.save_for_backward(x, w)

def backward(ctx, grad):
    x, w = ctx.saved_tensors
    gx, gw = m.fss_backward(grad, x, w)
    return gx, gw

with_grad.register_autograd(backward, setup_context=setup_context)
```

`setup_context` 与 `backward` 分开，是因为前向可能在 no_grad 下运行——
那时根本不需要保存任何东西。这个拆分让框架可以跳过保存。
（这正是 0.0b 里"前向要为反向存中间量"的那一步，
以及 2.6b 里 AOTAutograd 前向返回 6 个值、其中 5 个给反向的原因。）

### gradcheck 通过

```
Autograd key 现在有 kernel 了: True
gradcheck 通过: True

dx max|err| = 0.000e+00
dw max|err| = 0.000e+00
```

`gradcheck` 用有限差分逐元素扰动输入，比较数值雅可比与解析雅可比。
必须用 `float64`——float32 的舍入误差比差分信号还大。
（本章的 kernel 用 `AT_DISPATCH_FLOATING_TYPES` 同时支持 float 和 double，
就是为了能跑 gradcheck。这也是真实算子的标准做法。）

### 失败现场：反向写错，前向完全正确

故意把 relu 的掩码忘掉：

```python
def bad_backward(ctx, grad):
    x, w = ctx.saved_tensors
    gx = grad.unsqueeze(1) * w.unsqueeze(0)      # 少了 1[x*w>0]
    gw = (grad.unsqueeze(1) * x).sum(0)
    return gx, gw
```

```
前向仍然正确: max|err| = 0.000e+00
gradcheck 抓到了:
  Jacobian mismatch for output 0 with respect to input 0,
  numerical:tensor([[ 0.5888,  0.0000,  0.0000,  ...,
  analytical:tensor([[ 0.5888,  0.0000,  0.0000,  ...
```

**前向误差精确为 0，反向是错的。** 这类 bug 在训练里的表现是
"loss 下降得有点慢"或"某个配置下不收敛"——没有任何一处会报错。
0.0b 里那个"损失曲线看不出问题"的教训，在这里是同一件事的另一面。

`gradcheck` 是唯一能在写完当场抓住它的工具。**写反向就要写 gradcheck**，
成本是三行代码。

### 四之二 · 四条路径、二阶梯度，与"反向也是算子"这条规则

**四条路径的对拍。** 同一个 `op(x, w).sum()` 分别走 eager、
`torch.compile`、`compile(mode="reduce-overhead")`（自动套 CUDA Graph）
与 `torch.export`（crater 实测）：

| 路径 | loss | dx 范数 | dw 范数 | 首次调用 |
|---|---:|---:|---:|---:|
| eager | 7.974125 | 3.074641 | 5.210002 | 0.019 s |
| `torch.compile` | 7.974125 | 3.074641 | 5.210002 | 0.333 s |
| `compile(reduce-overhead)` | 7.974125 | 3.074641 | 5.210002 | 0.025 s |
| `torch.export` | 5 个节点，含 `l28c.masked_sum.default` | — | — | — |

四条的 loss 与两组梯度**逐位相同**，说明"注册过的反向"在四条路径上走同一份公式；
`export` 图中自定义算子表现为一个节点（不透明边界），
这个边界在 2.6b/2.7 里已经量化过代价。

**二阶梯度。** 用 fp64 的公式版跑
`torch.autograd.gradcheck` 与 `gradgradcheck`：两项都通过。
这里要说清验证的对象：**gradcheck 验的是你注册的反向公式，不是 fp32 kernel 本身**
—— 公式对、kernel 的 fp32 实现对（本章 kernel 反向与公式的 `max|Δ|` 为 0），
两条一起成立才算梯度可用。

**"反向也要做成算子"这条规则是实测踩出来的。** 最初的反向直接在
`backward()` 里调 CUDA 扩展：

```python
def backward(ctx, g):
    x, w = ctx.saved_tensors
    dx, dw = ext().masked_sum_bwd(g, x, w)   # 裸 kernel
    return dx, dw
```

eager 下没问题，`torch.compile` 直接失败：

```
BackendCompilerFailed: backend='inductor' raised:
RuntimeError: The tensor has a non-zero number of elements, but its data is not allocated yet.
```

原因是 AOTAutograd 会把反向也追成图，追踪时传进来的是 **fake tensor**；
在反向里调裸 kernel，等于拿没有存储的 fake tensor 去跑真实 CUDA 计算。
修法是把反向也注册成一个带 fake 实现的 custom op，
`backward()` 里调用它：

```python
@torch.library.custom_op("l28c::masked_sum_backward", mutates_args=())
def masked_sum_backward(g, x, w) -> tuple[torch.Tensor, torch.Tensor]:
    dx, dw = ext().masked_sum_bwd(g, x, w)
    return dx, dw

@masked_sum_backward.register_fake
def _(g, x, w):
    return x.new_empty(x.shape), w.new_empty(w.shape)
```

改完之后上面四条路径全部通过。**契约是递归的：前向要 fake，反向也要。**

## 五 · 不透明算子形成融合边界

不能。自定义算子在 Inductor 眼里是不透明的。

同一个表达式 `(op(x, w) * 2).relu() + 1`，两种写法：

```
自定义算子 + 后续逐元素
  Inductor 生成 triton kernel: 1
  图里对外部算子的调用: [..., 'torch.ops.l28.fusible_probe']

等价的纯 torch 写法
  Inductor 生成 triton kernel: 1
  图里对外部算子的调用: [...]（没有外部算子）
```

自定义算子路径中，GPU 上实际执行的是**自写 kernel + 1 个 Inductor 生成的 kernel**；
纯 torch 路径下，Inductor 将归约和后续逐元素**融合**在一起生成。

时间（4096×4096 fp32，crater）：

| 写法 | 时间 |
|---|---:|
| 纯 torch（编译后） | **0.013 ms** |
| 自写 kernel（裸调，不含后续算子） | 0.018 ms |
| 自定义算子（编译后，含后续算子） | 0.027 ms |
| 纯 torch（eager） | 0.138 ms |

三件事：

1. **手写的单一 kernel（0.018 ms）比 Inductor 融合生成的整段代码（0.013 ms）还慢**，
   而且 Inductor 那 0.013 里还包含了后面的 `*2`、`relu`、`+1`。
2. **包成自定义算子之后是 0.027 ms**，比裸调多 0.009 ms：多了一次不透明边界，
   后续的逐元素算子只能另起一个 kernel。
3. 编译相对 eager 有 10.6×，但该项加速**原生 PyTorch 即可获取**，
   无需额外引入手写 kernel。

### 五之二 · 边界代价与真实 block 替换（实测）

上面那张表是旧材料。本轮用同一套口径重测了"不透明 vs 可分解"
（`labs/L2/custom_op_contract.py --mode c`，crater，`(64, 512)` fp32）：

| 写法（都在 `torch.compile` 下） | 生成的 kernel 种类 | 稳态 |
|---|---:|---:|
| 可分解（`(x*w).relu().sum(-1).sum()`） | 5 | **0.0281 ms** |
| 不透明（`op(x, w).sum()`） | 6 | 0.0422 ms |

差一个 kernel、慢 50%。这与上一节的方向一致：**"能不能融合"不是风格问题，
是能不能看到内部循环的问题。**

**换成真实模型的一次替换。** 把 Qwen3-1.7B 第 0 层 MLP 的激活路径
（`silu(gate_proj(x)) * up_proj(x)`）换成一个自定义算子
（`l28c::silu_mul`，同样带 schema、fake 与 autograd 三件套），
其余部分不动：

| 配置 | 时间 | kernel 种类 |
|---|---:|---:|
| eager 原版 | 0.776 ms | 10 |
| eager + 自定义算子替换 | **0.942 ms** | 12 |
| `torch.compile` 原版 | 0.793 ms | 8 |
| `torch.compile` + 自定义算子替换 | 未测 | — |

三点：

1. **替换之后更慢**（0.776 → 0.942 ms，慢 21%），kernel 数还多了 2 个。
   原因是 `silu` 原本在 Inductor 里可以和投影/乘法融合，
   换成不透明算子后只能单独起 kernel；而自写独立 kernel 相比融合后的实现并无优势。
2. **`torch.compile` 原版（0.793 ms）也几乎不比 eager 快**：
   Qwen3 的 MLP 主要由三个大 GEMM 组成（都走 cuBLAS），
   可融合的只有激活那一段 —— 这解释了为什么"编译器在这里没什么可做"。
3. 因此这次替换是**负面结果**：没有收益，还有边界代价。
   要让它值得，前提是自定义 kernel 在**同一份工作**上比库实现快
   （例如算子本身就是瓶颈，或者库没有对应实现），
   而不是"把一段能融合的代码包成算子"。

**新增一个后端要动哪些地方**（本次替换实际涉及的改动）：

| 位置 | 改动 |
|---|---|
| 注册 | `torch.library.custom_op("l28c::silu_mul", mutates_args=())` 定义 schema 与 alias |
| 实现 | CUDA kernel（`load_inline` 编译）+ Python 包装层显式检查 dtype/形状 |
| 形状推导 | `@op.register_fake` 返回 `torch.empty_like(gate)` |
| 反向 | 再注册一个 `silu_mul_backward` custom op，并给它自己的 fake |
| 部署 | 该算子进入 `torch.export` 图后是一个节点；AOTI 制品要把扩展一起带上 |
| 布局 | 输入必须 contiguous（或由包装层 `.contiguous()`），
否则 kernel 的下标假设不成立 |

## 六 · 设计取舍

### 6.1 不透明边界的可组合性与优化限制

Inductor 要融合两个算子，前提是它**知道两者在算什么**——
知道循环结构、访存模式、哪些维度可以合并。对一个只有 schema
`(Tensor x, Tensor w) -> Tensor` 的黑盒，这些全都不知道。

可选的设计：

| 方案 | 代价 |
|---|---|
| A. 不透明节点（PyTorch 的选择） | 无法融合；但注册成本极低，任何语言写的 kernel 都能接 |
| B. 要求提供循环结构描述 | 能融合；但注册门槛变成"用编译器的 IR 重写一遍" |
| C. 只允许用 Triton/框架 DSL 写 | 能融合、能重排；但排除了 CUDA/汇编/闭源库 |

真实生态里三种都存在：cuBLAS / FlashAttention 走 A；
Inductor 自己生成的走 C；`torch.library.triton_op` 是一条中间路，
让 Inductor 知道这是个 Triton kernel 从而能做一部分处理。

判据是**边界划在哪**。A 把边界划在"函数调用"这个最小公约数上，
换来的是任何东西都能接进来。这是一个有意识的取舍，不是能力不足。

### 6.2 自定义算子的功能与性能目标

本章的测量给出了一个直接的判据：**若目标是加速，需要你的 kernel 比编译器生成的快，
而且快出的部分能覆盖不透明边界的代价。**

本章 kernel 未达到这一目标。一个待核对的实现差异是：一个 block 归约一行（4096 个元素），
grid 只有 4096 个 block，且每行只有一个 block 在做归约——
2.3 中阐述的两段式切分中，此处仅实现了 block 内局部归约。Inductor 生成的版本
按 `size_hints={'x': 512, 'r0_': 8192}` 两级切分（2.7 §3），并行度更高。

自定义 kernel 通常用于以下情况：
**编译器表达不出来的算法**（FlashAttention 的在线 softmax + 分块）、
**特殊指令**（tcgen05、FP4，L1.2）、
**融合了编译器不会跨越的边界**（PagedAttention 跨 block table 的 gather）。
是否更快仍需与现有实现比较。

### 6.3 schema、fake 与 autograd 各自负责不同契约

`custom_op` → `register_fake` → `register_autograd`，
对应三个不同的 dispatch key：`CompositeExplicitAutograd` → `Meta` → `Autograd`。
缺哪个就在哪一层失败，而且失败方式不同：

| 缺什么 | 什么时候炸 | 表现 |
|---|---|---|
| 全都没有（裸 pybind） | 追踪时 | **不报错**，悄悄留在图外（第一节） |
| 缺 fake | `torch.compile` 时 | `RuntimeError when making fake tensor call` |
| 缺 autograd | `.backward()` 时 | 报错说算子不支持 autograd |
| autograd 写错 | 可能不报错 | 用 gradcheck、解析梯度与多输入对照检查 |

最危险的是第一行和最后一行——它们都不报错。
这就是 2.0 §4.6 说的"错误在第几层被发现"：
注册的价值一半在功能，一半在**把静默失败变成显式失败**。

## 八 · 陷阱

1. **`explain()` 报 0 次断裂不等于全部被捕获。** 不支持的调用如果在区域开头，
   Dynamo 直接从它之后开始，计数是 0 而你的算子在图外。
   用 `fullgraph=True` 或把图打出来。
2. **裸 pybind 函数没有反向，且不报错。** `requires_grad=True` 的输入进去，
   出来的张量 `grad_fn=None`，反向在这里静默断掉。
3. **`custom_op` 默认注册到 `CompositeExplicitAutograd`**，不是 CUDA。
   查 `_dispatch_has_kernel_for_dispatch_key(name, "CUDA")` 会得到 False，
   这不是注册失败。
4. **`gradcheck` 必须用 float64。** float32 的舍入误差比有限差分的信号还大，
   会给出假的失败或假的通过。
5. **反向写错前向不受影响。** 本章实测前向 `max|err| = 0.000e+00`，
   反向完全错。写反向就写 gradcheck。
6. **`mutates_args` 写错会导致难查的错误**，因为 functionalization
   和内存规划都信任这个声明。
7. **fake 函数里不要做真实计算**，也不要读输入张量的值——追踪时那是 FakeTensor，
   没有数据。要断言形状关系用 `torch._check`，不要用 `assert`
   （后者在动态形状下会强制特化）。
8. **自定义算子是融合边界。** 包一层的代价在本章是 0.009 ms，
   小算子上可能比 kernel 本身还贵。
9. **只给前向写 fake、反向里直接调裸 kernel。** 这是本节实测的失败：
   前向能跑、eager 反向能跑，`torch.compile` 追反向时拿 fake tensor 去调真实
   CUDA kernel，报 `The tensor has a non-zero number of elements, but its data is
   not allocated yet`。反向也要做成带 fake 的算子。
10. **依赖 schema 检查形状。** schema 只声明类型，不检查
    `w.numel() == x.shape[-1]`；`w` 更长时静默截断，更短时越界读。
    契约检查要写在自己的包装层里，位置在调 kernel 之前。
11. **以为"包成算子"就能变快。** 本章把 Qwen3 MLP 的激活换成自定义算子后
    反而慢 21%（0.776 → 0.942 ms），kernel 数还多了 2 个：
    原本能融合的一段被切成了不透明边界。

## 九 · 自测题

<details markdown="1">
<summary>1. 你把一个 pybind 出来的 kernel 直接用在模型里，训练能跑、loss 也在降，但精度始终差一截。最可能是什么？</summary>

那个 kernel 没有注册成算子，所以它没有反向。经过它的那条路径上，
autograd 图是断的——它前面的所有参数**收不到梯度**。

loss 仍然会降，因为其它路径（比如残差分支、后面的层）照常更新。
这就是它难查的原因：没有任何报错，只是一部分参数从未被训练过。

判据：拿一个 `requires_grad=True` 的输入过一遍，检查输出的 `grad_fn`
是不是 `None`；或者 `.backward()` 之后检查上游参数的 `.grad` 是不是 `None`。
</details>

<details markdown="1">
<summary>2. fake 函数为什么不能直接调用真实实现来得到输出形状？</summary>

因为追踪时传进来的是 FakeTensor：它有形状、dtype、device，
但**没有数据**，底层也没有真实显存。真实 kernel 会去读 `data_ptr`，
那里什么都没有。

而且在动态形状下，`x.shape[0]` 可能是一个符号量 `s0` 而不是具体整数，
真实 kernel 也没法拿它去启动 grid。

fake 函数的职责就是从"输入的形状"算出"输出的形状"，
这是一个纯符号运算，不碰任何数据。
</details>

<details markdown="1">
<summary>3. 注册之后 <code>torch.compile</code> 不再图断裂了，为什么性能反而可能变差？</summary>

因为自定义算子是**不透明节点**。Inductor 不能把它前后的算子融进它，
也不能拆开重排。

本章实测：等价的纯 torch 写法编译后 0.013 ms（归约和后续逐元素融在一起），
自定义算子路径耗时 0.027 ms（自写 kernel + 另起一个 kernel 处理后续逐元素操作）。
慢了一倍多，尽管两者数值完全一致。

所以注册解决的是**正确性和可组合性**（有反向、能进图、别人能用），
不自动带来性能。性能要单独量。
</details>

<details markdown="1">
<summary>4. 什么情况下写自定义算子是划算的？给出一个可操作的判据。</summary>

判据：**你的 kernel 的时间 + 不透明边界的代价 < 编译器为同一段表达式生成的时间。**

三个量都要实测：
1. 你的 kernel 裸调的时间；
2. 包成自定义算子后、连同上下游算子一起编译的时间；
3. 等价纯 torch 写法编译后的时间。

本章这个例子里三个数是 0.018 / 0.027 / 0.013——不划算，
因为自写归约仅处理了 block 内的单级归约，全局并行度不如 Inductor 的两级分块切分。

真正划算的场景通常是编译器**表达不出来**的算法（FlashAttention 的
在线 softmax 分块）、需要特殊指令（FP4、tcgen05），
或者要跨越编译器不会跨越的边界（PagedAttention 的 block table gather）。
</details>

<details markdown="1">
<summary>5. 缺 fake、缺 autograd、autograd 写错，这三种情况分别在什么时候暴露？哪个最危险？</summary>

- 缺 fake：`torch.compile` 时报 `RuntimeError when making fake tensor call`。eager 正常。
- 缺 autograd：`.backward()` 时报错说算子不支持 autograd。前向正常。
- autograd 写错：可能不报错；前向正确不保证梯度正确，需要独立检查反向。

最危险的是第三种，其次是完全不注册（第一节那种：悄悄留在图外，也不报错）。

一般规律：一个失败越晚被发现、越不产生显式信号，就越贵。
完整的注册和检查有助于尽早发现这些不一致。
</details>

<details markdown="1">
<summary>6. 我的算子 eager 下前向、反向都对，gradcheck 也过，是不是就齐了？</summary>

不够。本章实测还有三件事要过：

1. **四条路径对拍**：eager / `torch.compile` / `compile(mode="reduce-overhead")` /
   `torch.export`。本章四条路径的 loss 与梯度逐位相同，这是"注册过的反向在四条路径上
   走同一份公式"的证据。
2. **反向也要有 fake**。最初的反向直接在 `backward()` 里调 CUDA 扩展，
   eager 正常、`torch.compile` 报
   `The tensor has a non-zero number of elements, but its data is not allocated yet`
   —— 追踪反向时传进来的是 fake tensor。把反向也注册成带 fake 的 custom op 后才通过。
3. **`opcheck` 四项**：`test_schema`、`test_autograd_registration`、
   `test_faketensor`、`test_aot_dispatch_dynamic`，正好对应四份契约。

同时需执行二阶梯度验证（`gradgradcheck`），
并断言输入张量未发生原地修改（版本计数保持不变）。
</details>

<details markdown="1">
<summary>7. 把模型里一段能融合的代码包成自定义算子，为什么变慢了？</summary>

因为不透明边界让编译器无法把那一段与邻居融合。本章实测两处：

- 同一个算式（`(64,512)`）：不透明 6 种 kernel / 0.0422 ms，
  可分解 5 种 / 0.0281 ms；
- 真实 Qwen3-1.7B 第 0 层 MLP：把 `silu(gate) * up` 换成自定义算子后
  0.776 → 0.942 ms（慢 21%），kernel 数 10 → 12。

自定义算子值得付边界代价的前提是**它在同一份工作上比库/编译器更快**
（例如库没有对应实现、或原实现不是瓶颈），而不是"把能融合的代码包起来"。
</details>
