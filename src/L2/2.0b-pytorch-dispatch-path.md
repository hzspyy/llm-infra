## 本章回答三个问题

2.0 讲了张量如何描述内存（storage、stride、view），但没讲「一次算子调用如何找到实际实现」。本章沿 `aten.linear` 贯通 Python binding、schema、dispatcher、redispatch 和 native 实现，解释注册、分解和实际执行的观察层次。

1. 一次 Python 算子调用如何找到实际实现？
2. dispatch key、线程局部状态与 redispatch 如何共同决定路径？
3. 同一操作在 hook、export 图和 GPU trace 中为什么可能具有不同名字与粒度？

::: note 观察层次的核心
M1 讲了五层观察窗口，本章用 `aten.linear` 具体演示第 1-3 层：Python 调用、框架分发、编译图。第 4-5 层（运行时 launch 和 GPU kernel）在 2.1/2.2 讲。
:::

## 第一步：从 Python 到 binding

### Python 层的入口

```python
# labs/L2/trace_linear_layers.py
import torch
import torch.nn.functional as F

print("=== Layer 1: Python 入口 ===")
print(f"F.linear 是什么: {F.linear}")
print(f"类型: {type(F.linear)}")
print(f"模块: {F.linear.__module__}")
print()

# 文档字符串
doc = F.linear.__doc__
if doc:
    print(f"文档前 150 字符:\n{doc[:150]}...")
```

运行输出：

```
=== Layer 1: Python 入口 ===
F.linear 是什么: <built-in function linear>
类型: <class 'builtin_function_or_method'>
模块: torch.nn.functional

文档前 150 字符:
linear(input, weight, bias=None) -> Tensor

Applies a linear transformation to the incoming data: :math:`y = xA^T + b`.

This operation supports...
```

**这一层告诉你什么**：
- `F.linear` 是一个内置函数（C++ 实现）
- 签名：`(input, weight, bias?) → Tensor`
- 文档说它做 `xA^T + b`

**这一层不能告诉你什么**：
- 实际调用了哪个 C++ 函数
- 有没有被分解成其他算子
- CPU 和 CUDA 是不是同一个实现

### Binding 层：生成的 C++ 代码

PyTorch 用代码生成器（`tools/codegen/gen.py`）从 `native_functions.yaml` 生成 Python binding。

**查找方式**（需要源码）：

```bash
# 在 PyTorch 源码目录
$ cd pytorch
$ git checkout v2.14.0

# 找到 linear 的 binding 生成代码
$ grep -r "linear" torch/csrc/autograd/generated/python_functions.cpp | head -5
```

你会看到类似：

```cpp
// torch/csrc/autograd/generated/python_functions.cpp (代码生成)
static PyObject* THPVariable_linear(
    PyObject* self, 
    PyObject* args, 
    PyObject* kwargs
) {
  // 参数解析
  // 调用 at::linear(input, weight, bias)
}
```

**这一层告诉你什么**：
- Python 调用被转发到 C++ 的 `at::linear`
- 参数类型检查和转换在这一层

**这一层不能告诉你什么**：
- `at::linear` 内部做了什么
- 有没有被 dispatcher 重定向

## 第二步：Dispatcher 的分发与分解

### Schema 定义

PyTorch 的每个算子都有一个 schema（在 `native_functions.yaml` 中）：

```yaml
# aten/src/ATen/native/native_functions.yaml (简化)
- func: linear(Tensor input, Tensor weight, Tensor? bias=None) -> Tensor
  dispatch:
    CompositeExplicitAutograd: linear
  tags: core
```

**关键字段**：
- `func`: 算子签名
- `dispatch`: 分发规则
  - `CompositeExplicitAutograd`: 用其他算子组合实现，autograd 需要显式定义

### Dispatcher hook：看到实际分解

```python
# labs/L2/trace_linear_dispatch.py
import torch
import torch.nn.functional as F

class DispatchTracer(torch.utils._python_dispatch.TorchDispatchMode):
    def __torch_dispatch__(self, func, types, args=(), kwargs=None):
        print(f"  {func}")
        return func(*args, **(kwargs or {}))

print("=== Dispatcher 层的观察 ===")
x = torch.randn(2, 3)
w = torch.randn(4, 3)
b = torch.randn(4)

print("\n调用 F.linear(x, w, b):")
with DispatchTracer():
    out = F.linear(x, w, b)

print(f"\n输出形状: {out.shape}")
```

运行输出：

```
=== Dispatcher 层的观察 ===

调用 F.linear(x, w, b):
  aten.t.default
  aten.addmm.default

输出形状: torch.Size([2, 4])
```

**观察到什么**：
- `F.linear` 在 dispatcher 层被分解成 `t` (transpose) 和 `addmm`
- 没有直接调用一个叫 `linear` 的 kernel

**为什么这样设计**：
- `linear` 是高层语义（`y = xA^T + b`）
- 分解成低层原语（`t` + `addmm`）后，只需要为低层原语实现 CPU/CUDA/autograd
- 减少代码重复

### 分解的实现位置

```cpp
// aten/src/ATen/native/Linear.cpp (简化)
Tensor linear(
    const Tensor& input,
    const Tensor& weight,
    const optional<Tensor>& bias
) {
  // 分解实现
  auto output = at::matmul(input, weight.t());  // 等价于 t + mm
  if (bias.has_value()) {
    output.add_(bias.value());
  }
  return output;
}
```

**这段代码的位置**：
- 文件：`aten/src/ATen/native/Linear.cpp`
- 版本：v2.14.0
- 观察层次：第 3 层（Dispatcher 分解）

**这段代码不是**：
- GPU kernel（那在 cuBLAS 或 cutlass 里）
- 唯一的实现（还有其他 dispatch key 的版本）

## 第三步：Dispatch key 与路径选择

### Dispatch key 是什么

Dispatcher 根据**张量的属性**和**线程局部状态**选择实现：

| Dispatch key | 触发条件 | 做什么 |
|---|---|---|
| `CPU` | 所有输入都在 CPU | 调用 CPU native 实现 |
| `CUDA` | 至少一个输入在 CUDA | 调用 CUDA native 实现 |
| `AutogradCPU` | CPU + 需要梯度 | 包装 CPU 实现，注册 autograd |
| `AutogradCUDA` | CUDA + 需要梯度 | 包装 CUDA 实现，注册 autograd |
| `Autocast` | 在 autocast 上下文中 | 类型转换后重新分发 |
| `FuncTorchBatched` | 在 vmap 中 | 批处理语义 |

### 实际路径演示

```python
# labs/L2/dispatch_key_demo.py
import torch
import torch.nn.functional as F

class VerboseDispatch(torch.utils._python_dispatch.TorchDispatchMode):
    def __torch_dispatch__(self, func, types, args=(), kwargs=None):
        # 打印 dispatch key set
        print(f"{func} | keys: {[t.__name__ for t in types]}")
        return func(*args, **(kwargs or {}))

# 场景 1: CPU, no grad
print("=== 场景 1: CPU, requires_grad=False ===")
x = torch.randn(2, 3, requires_grad=False)
w = torch.randn(4, 3, requires_grad=False)
with VerboseDispatch():
    F.linear(x, w)

# 场景 2: CPU, with grad
print("\n=== 场景 2: CPU, requires_grad=True ===")
x = torch.randn(2, 3, requires_grad=True)
w = torch.randn(4, 3, requires_grad=True)
with VerboseDispatch():
    F.linear(x, w)

# 场景 3: CUDA (如果可用)
if torch.cuda.is_available():
    print("\n=== 场景 3: CUDA, requires_grad=True ===")
    x = torch.randn(2, 3, device='cuda', requires_grad=True)
    w = torch.randn(4, 3, device='cuda', requires_grad=True)
    with VerboseDispatch():
        F.linear(x, w)
```

典型输出（CPU）：

```
=== 场景 1: CPU, requires_grad=False ===
aten.t.default | keys: ['Tensor']
aten.mm.default | keys: ['Tensor']

=== 场景 2: CPU, requires_grad=True ===
aten.t.default | keys: ['Tensor']
aten.mm.default | keys: ['Tensor', 'AutogradCPU']
```

**观察到什么**：
- `requires_grad=True` 时多了 `AutogradCPU` key
- 但分解后的算子（`t` + `mm`）是相同的

## 第四步：从 dispatcher 到 native 实现

### addmm 的 CPU 实现

```cpp
// aten/src/ATen/native/LinearAlgebra.cpp (简化)
// 版本: v2.14.0

TORCH_IMPL_FUNC(addmm_out_cpu)(
    const Tensor& self,     // bias
    const Tensor& mat1,     // input
    const Tensor& mat2,     // weight^T
    const Scalar& beta,
    const Scalar& alpha,
    const Tensor& result
) {
  // 实际调用 BLAS
  // ...省略形状检查、内存布局处理
  
  at::native::cpublas::gemm(
      /* ... */
      mat1.data_ptr<float>(),
      mat2.data_ptr<float>(),
      result.data_ptr<float>()
  );
}
```

**这段代码的位置**：
- 文件：`aten/src/ATen/native/LinearAlgebra.cpp:789`
- 版本：v2.14.0
- 观察层次：第 4 层（Native 实现）

**这段代码做什么**：
- 调用 BLAS 的 `gemm`（通用矩阵乘）
- 处理 `beta * bias + alpha * (mat1 @ mat2)`

**这段代码不做什么**：
- 不分解算子（分解在上一层）
- 不处理 autograd（autograd 包装在 dispatcher 层）

### addmm 的 CUDA 实现

```cpp
// aten/src/ATen/native/cuda/Blas.cpp (简化)
// 版本: v2.14.0

Tensor& addmm_out_cuda_impl(
    Tensor& result,
    const Tensor& self,
    const Tensor& mat1,
    const Tensor& mat2,
    const Scalar& beta,
    const Scalar& alpha
) {
  // 调用 cuBLAS 或 cutlass
  at::cuda::blas::gemm<float>(
      /* ... */
      mat1.data_ptr<float>(),
      mat2.data_ptr<float>(),
      result.data_ptr<float>()
  );
  
  return result;
}
```

**CPU 和 CUDA 实现的共同点**：
- 都实现 `addmm` 的数学语义
- 都调用高度优化的 BLAS 库

**CPU 和 CUDA 实现的不同点**：
- 调用的库不同（CPU BLAS vs cuBLAS/cutlass）
- 内存布局处理不同
- CUDA 版本可能用不同精度或 Tensor Core

## 观察层次的对照表

| 层次 | 看到的名字 | 观察工具 | 能证明什么 | 不能证明什么 |
|---|---|---|---|---|
| Python API | `F.linear` | `help(F.linear)` | 函数签名、文档 | 实际调用路径 |
| Python binding | `THPVariable_linear` | 源码 grep | 参数解析 | 算子分解 |
| Dispatcher | `aten.t` + `aten.addmm` | `TorchDispatchMode` | 分解关系 | 实际 kernel |
| Native 实现 | `addmm_out_cpu` | 源码 + 断点 | 调用 BLAS | BLAS 内部实现 |
| Kernel | `sgemm_` (BLAS) | `perf` / `gdb` | 实际指令 | 微架构细节 |

**关键原则**（重复 M1）：
> 你在第 N 层看到的证据，只能证明第 N 层发生了什么。

## Mini 实现：最小的 dispatcher

我们自己实现一个最小的 dispatcher，理解分发逻辑：

```python
# labs/L2/mini_dispatcher.py
from typing import Callable, Dict, Any
from dataclasses import dataclass

@dataclass
class DispatchKey:
    """简化的 dispatch key"""
    name: str
    priority: int  # 数字越大优先级越高

# 预定义的 keys
CPU = DispatchKey("CPU", 1)
CUDA = DispatchKey("CUDA", 1)
AutogradCPU = DispatchKey("AutogradCPU", 10)
AutogradCUDA = DispatchKey("AutogradCUDA", 10)

class MiniDispatcher:
    """最小的算子 dispatcher"""
    
    def __init__(self, op_name: str):
        self.op_name = op_name
        self.impls: Dict[str, Callable] = {}
    
    def register(self, key: DispatchKey, impl: Callable):
        """注册一个实现"""
        self.impls[key.name] = impl
        print(f"  [注册] {self.op_name}.{key.name} → {impl.__name__}")
    
    def call(self, *args, dispatch_keys: list[DispatchKey], **kwargs):
        """根据 dispatch keys 选择实现"""
        # 按优先级排序
        sorted_keys = sorted(dispatch_keys, key=lambda k: k.priority, reverse=True)
        
        print(f"\n[调用] {self.op_name}")
        print(f"  keys: {[k.name for k in sorted_keys]}")
        
        # 选择第一个有实现的 key
        for key in sorted_keys:
            if key.name in self.impls:
                impl = self.impls[key.name]
                print(f"  → 选择 {key.name} 实现: {impl.__name__}")
                return impl(*args, **kwargs)
        
        raise RuntimeError(f"No implementation for {self.op_name} with keys {sorted_keys}")

# 示例：实现一个 addmm 算子
addmm_dispatcher = MiniDispatcher("addmm")

def addmm_cpu(mat1, mat2, bias):
    """CPU 实现（简化）"""
    print("    [执行] CPU GEMM")
    # 实际会调用 BLAS
    return "result_cpu"

def addmm_cuda(mat1, mat2, bias):
    """CUDA 实现（简化）"""
    print("    [执行] CUDA GEMM (cuBLAS)")
    return "result_cuda"

def addmm_autograd_wrapper(mat1, mat2, bias, base_key):
    """Autograd 包装"""
    print(f"    [包装] 记录 autograd 信息")
    # 调用下一层（redispatch）
    print(f"    [Redispatch] 到 {base_key.name}")
    result = addmm_dispatcher.call(mat1, mat2, bias, dispatch_keys=[base_key])
    print(f"    [包装] 注册反向函数")
    return result

# 注册实现
addmm_dispatcher.register(CPU, addmm_cpu)
addmm_dispatcher.register(CUDA, addmm_cuda)
addmm_dispatcher.register(
    AutogradCPU,
    lambda m1, m2, b: addmm_autograd_wrapper(m1, m2, b, CPU)
)
addmm_dispatcher.register(
    AutogradCUDA,
    lambda m1, m2, b: addmm_autograd_wrapper(m1, m2, b, CUDA)
)

# 测试
if __name__ == "__main__":
    print("=" * 60)
    print("场景 1: CPU, no grad")
    print("=" * 60)
    addmm_dispatcher.call("mat1", "mat2", "bias", dispatch_keys=[CPU])
    
    print("\n" + "=" * 60)
    print("场景 2: CPU, with grad")
    print("=" * 60)
    addmm_dispatcher.call("mat1", "mat2", "bias", dispatch_keys=[AutogradCPU, CPU])
    
    print("\n" + "=" * 60)
    print("场景 3: CUDA, with grad")
    print("=" * 60)
    addmm_dispatcher.call("mat1", "mat2", "bias", dispatch_keys=[AutogradCUDA, CUDA])
```

```

  [注册] addmm.AutogradCPU → <lambda>
```

## 常见陷阱

### 陷阱 1：从 hook 推断算子不存在

❌ **错误推理**：

```python
class OpTracer(torch.utils._python_dispatch.TorchDispatchMode):
    def __torch_dispatch__(self, func, types, args=(), kwargs=None):
        print(func)
        return func(*args, **(kwargs or {}))

with OpTracer():
    F.linear(x, w)
# 只看到 aten.t 和 aten.addmm
# 结论：没有 linear 算子 ❌
```

**为什么错**：
- `linear` 在 dispatcher 层被分解
- Hook 看到的是分解后的算子
- `linear` 确实存在，在 `native_functions.yaml` 中有定义

✅ **正确理解**：
- Hook 在第 3 层（dispatcher）
- `linear` 的注册在第 2-3 层之间
- 分解是设计选择，不是"不存在"

### 陷阱 2：把算子分解等同于 kernel 融合

❌ **错误推理**：

```python
with OpTracer():
    F.linear(x, w)
# 看到: aten.t + aten.addmm
# 结论：PyTorch 把 linear 融合成一个 kernel ❌
```

**为什么错**：
- 分解发生在第 3 层（dispatcher）
- 融合发生在第 4-5 层（Inductor codegen / 实际 launch）
- 分解后的两个算子可能仍然是两个 kernel

✅ **验证融合**：
- 用 `torch.compile` 编译
- 用 nsys 数 launch 次数（第 4 层）
- 看生成的 Triton 或 CUDA 代码

### 陷阱 3：混淆 dtype 分支与 dispatcher key

❌ **错误推理**：

```python
x_fp32 = torch.randn(2, 3, dtype=torch.float32)
x_fp16 = torch.randn(2, 3, dtype=torch.float16)

# 结论：dtype 不同走不同 dispatch key ❌
```

**为什么错**：
- Dtype 在 native 实现内部处理（第 4 层）
- Dispatch key 在更高层（第 3 层）
- 同一个 `addmm_out_cpu` 可以处理多种 dtype

✅ **正确理解**：
- Dispatch key: `CPU` / `CUDA` / `Autograd*`
- Dtype 分支: 在 native 实现内部（模板特化或 if-else）

## 自测题

1. `F.linear` 在 dispatcher 层被分解成什么？用什么工具能看到？
2. `requires_grad=True` 改变了哪个 dispatch key？分解后的算子变了吗？
3. 如何验证 `addmm` 在 CPU 和 CUDA 上是不是同一个 kernel？

::: details 答案

1. **分解成 `aten.t` + `aten.addmm`**
   - 工具：`TorchDispatchMode` hook
   - 层次：第 3 层（dispatcher）
   - 证据：`labs/L2/trace_linear_dispatch.py` 的输出

2. **改变了 dispatch key，分解后的算子没变**
   - `requires_grad=False`: 只有 `CPU` 或 `CUDA` key
   - `requires_grad=True`: 额外有 `AutogradCPU` 或 `AutogradCUDA` key
   - 分解后仍然是 `t` + `addmm`，但 autograd 包装会记录反向信息

3. **看源码 + 动态验证**
   - 源码：`aten/src/ATen/native/LinearAlgebra.cpp` (CPU) vs `aten/src/ATen/native/cuda/Blas.cpp` (CUDA)
   - 它们不是同一个 kernel，一个调用 CPU BLAS，一个调用 cuBLAS
   - 动态验证：断点调试或 nsys 看实际调用的库函数

:::
