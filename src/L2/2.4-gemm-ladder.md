## 本章回答三个问题

1. GEMM 从 naive 推到接近硬件上限，**每一步各贡献多少倍**？哪一步最关键？
2. 为什么"加共享内存分块"这个教科书第一优化，在本机只带来 **1.2 倍**？
3. 我手写的 tensor core GEMM 只有 cuBLAS 的 41%。**差距在哪一件事上**？

GEMM 是通用矩阵乘法。以 C = A × B 为例，每个输出元素都要沿 K 维累加乘积。
优化的核心问题是：同一份 A、B 数据能在片上复用多少次，
以及线程如何分工才能减少搬运、同步和等待。
本章保留 fp32 和 bf16 两条实现路线，分别观察分块、寄存器和共享内存布局的作用。

## 机制拆解

### v0：算术强度 0.25，比 decode 还低

```cpp
__global__ void gemm_v0(const float* A, const float* B, float* C) {
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    float acc = 0.f;
    for (int k = 0; k < K; ++k) acc += A[row * K + k] * B[k * N + col];
    C[row * N + col] = acc;
}
```

每个输出元素要读 $2K$ 个数、做 $2K$ 次浮点运算：

$$\text{算术强度} = \frac{2K\ \text{FLOP}}{2K \times 4\ \text{byte}} = 0.25\ \text{FLOP/byte}$$

对照 L0.2 实测的机器平衡点 **153 FLOP/byte** —— 差了 612 倍。
**这个"计算密集"的算子，写成这样之后比 decode 还 memory-bound。**

实测 7.6 TFLOPS，只有 fp32 峰值的 **6.5%**。

### v1：共享内存分块只带来 1.2 倍 —— 为什么

教科书的第一优化：把 $BS \times BS$ 的一块 A 和 B 读进共享内存，
让整个 block 复用 $BS$ 次。理论上访存量降到 $1/BS = 1/32$。

实测：**7.6 → 9.1 TFLOPS，只有 1.2 倍。**

原因是 **L2 已经在替你做缓存了**。

A 和 B 各 64 MB，而本机 **L2 有 96 MB**（L1.1 实测）。
v0 里那些"重复读全局内存"的操作，绝大部分命中 L2 而不是显存——
L1.1 实测 L2 带宽 5.5 TB/s，是显存的 3.3 倍。

**共享内存分块真正的价值不是"省显存带宽"（L2 已经省了），
而是为下一步（寄存器分块）提供一个可控的数据布局。**
它本身不是目的。

::: note 这一条同样是"教科书结论过时了"
和 L2.3 的 warp shuffle 一样：那些优化写于 L2 只有 1–2 MB 的年代。
Blackwell 的 96 MB L2 改变了很多结论。

**判断方法**：算一下你的工作集与 L2 容量的关系。
如果工作集能装进 L2，"减少全局访存"的优化收益会大打折扣。
:::

### v2：5.1 倍 —— 整条阶梯上最关键的一步

```cpp
float acc[TM][TN] = {0.f};        // 每线程 8×8 = 64 个累加器（在寄存器里）
float regA[TM], regB[TN];

for (int k = 0; k < BK; ++k) {
    for (int i = 0; i < TM; ++i) regA[i] = sA[k][tRow * TM + i];   // 读 8 个
    for (int j = 0; j < TN; ++j) regB[j] = sB[k][tCol * TN + j];   // 读 8 个
    for (int i = 0; i < TM; ++i)
        for (int j = 0; j < TN; ++j) acc[i][j] += regA[i] * regB[j];  // 做 64 次
}
```

**读 8 + 8 = 16 个数，做 8 × 8 = 64 次乘加。** 这就是**外积累加**：
把 A 的一小列和 B 的一小行相乘，得到一个 $8\times8$ 的秩一更新。

算术强度从 1 提升到：

$$\frac{TM \times TN}{TM + TN} = \frac{64}{16} = 4$$

而且这 16 次读是从**共享内存**（6.5 周期，L1.1 实测）读的，不是显存（929 周期）。

实测：**9.1 → 46.7 TFLOPS，5.1 倍。**

代价是寄存器：`-Xptxas -v` 显示 v2 用了 **122 个寄存器**（v1 只有 38），
每 SM 只能驻留 537 个线程。但按 L2.1 的结论，**这完全够用**——
GEMM 是 compute-bound，靠 ILP 而不是占用率。

### v3：向量化只带来 1.13 倍

L2.3 里向量化是最关键的一步（2 倍），这里只有 1.13 倍（46.7 → 52.6）。

因为**瓶颈不同**：L2.3 的归约完全 memory-bound，向量化直接提高在途字节；
这里已经是 compute-bound，访存不是瓶颈，向量化只是顺带减少了指令数。

**同一个手段在不同瓶颈下的收益完全不同** —— 这是本站反复出现的主题。

### v5 → v6：bank 冲突值 62%

换成 bf16 + tensor core（WMMA API）：**89.2 TFLOPS**，
但只有 tensor core 峰值的 35.4%，也只有 cuBLAS bf16（218.6）的 **41%**。

差距在哪？先看**共享内存的布局**：

```cpp
__shared__ __nv_bfloat16 sA[BM * BK], sB[BK * BN];   // BK=32, BN=128
wmma::load_matrix_sync(fa, &sA[(wRow*WM + i*16) * BK + k], BK);   // 行距 = 32
```

行距是 **32 个 bf16 = 64 字节 = 16 个 bank**。
`load_matrix_sync` 要按 16×16 的块读，同一列的不同行地址相差 64 字节，
**每 2 行就撞回同一个 bank** —— 严重的 bank 冲突。

L1.1 实测：32 路 bank 冲突让共享内存访问慢 **10.1 倍**。

解法是 **padding**：把行距改成非 2 的幂：

```cpp
constexpr int LDA = BK + PAD, LDB = BN + PAD;        // PAD = 8
__shared__ __nv_bfloat16 sA[BM * LDA], sB[BK * LDB];
wmma::load_matrix_sync(fa, &sA[(wRow*WM + i*16) * LDA + k], LDA);
```

行距变成 40 个 bf16 = 80 字节 = 20 个 bank。相邻行的起始 bank 依次错开，
冲突被打散。

实测：**89.2 → 144.9 TFLOPS，1.62 倍。** 达到峰值的 57.5%、cuBLAS 的 66%。

::: note padding 只是最朴素的一种 swizzle
真正的高性能库用的是 **XOR swizzle**：地址的低位与高位异或，
让访问模式在任何 stride 下都均匀分布到 32 个 bank，而且**不浪费共享内存**
（padding 会浪费 $PAD/(BK+PAD) = 20\%$ 的空间）。

CUTLASS 的 `Swizzle<B, M, S>` 模板、以及 CuTe 的 layout algebra，
本质上就是在描述这类地址变换。L2.5 会看它们的写法。
:::

### 还差 cuBLAS 34%：剩下的是什么

v6 到 cuBLAS 之间还有 1.51 倍。已知的差距来源：

| 手段 | 本章实现 | 说明 |
|---|---|---|
| 双缓冲 / 软件流水 | ✗ | 用计算掩盖下一块的加载。CUTLASS 的 `x3`/`x4` 就是流水级数（L2.2 读过 kernel 名） |
| `cp.async` 异步拷贝 | ✗ | Ampere 起，全局→共享不占寄存器、不阻塞 |
| XOR swizzle | ✗（只用了 padding） | 不浪费空间且更彻底 |
| warp specialization | ✗ | 一部分 warp 专职搬数据，一部分专职算 |
| tile 尺寸 autotuning | ✗（写死 128×128×32） | cuBLAS 对每个形状选最优 tile |
| epilogue 融合 | ✗ | 写回时顺便做 scale/bias/激活 |

**这是一条可以继续走下去的路**，但每一步的收益递减而复杂度递增。
到 66% 已经足够理解机制；再往上就是 CUTLASS 的领域了（L2.5）。

### 一个意外的发现：v6 与 cuBLAS 逐位相同

误差列显示 v5/v6 相对 cuBLAS bf16 的误差是 **0.00e+00**。
这太整齐了，专门验证了一次（1024³）：

```
参考 RMS = 2.666367
自写 RMS = 2.666367
最大绝对差 = 0
不同的元素数 = 0 / 1048576
相对RMS误差 = 0.000e+00
```

**逐位相同。** 100 万个元素无一不同。

这个观察只说明该输入与配置下输出一致，不能反推出两者的累加顺序相同。
不同求和顺序也可能得到完全一样的浮点结果；输出舍入还可能掩盖中间差异。

fp32 的 v0–v3 与 cuBLAS SGEMM 存在 **1.19e-06** 的相对 RMS 差异。
分块与累加顺序是候选解释，但需要读取实际生成代码才能确认。
L4.2 将继续区分：一个样本输出一致、同一实现重复运行一致、
以及 batch 改变后仍一致。这是三种不同的要求。

## 工程实现 · 源码走读：真实 GEMM 里的这些手段

### 1. CUTLASS kernel 名里的每一段

L0.1 抓到的 vLLM bf16 GEMM：

```
cutlass_80_tensorop_bf16_s16816gemm_relu_bf16_128x64_64x3_nn_align8
                                              ^^^^^^  ^^ ^^      ^^^^^^
                                              block   BK 流水级  向量对齐
```

- `128x64_64` = block tile M×N，BK=64 —— 对照我们的 128×128×32
- `x3` = **3 段软件流水**（本章版本没有双缓冲）
- `align8` = 按 8 个元素（16 字节）对齐，可用 `LDG.128` —— 我们的 v6 也做了
- `s16816` = `m16n8k16` —— 和我们的 WMMA 底层是同一条指令

三段流水是可见的实现差异之一。要量化它对性能差距的贡献，仍需控制 tile、布局等变量做对照。

### 2. 为什么 tile 是 128×128 而不是别的

三个硬约束同时卡着：

**共享内存**（L1.1 实测每 block 上限 99 KB）：

$$\underbrace{128 \times 40}_{sA} + \underbrace{32 \times 136}_{sB} \times 2\ \text{B} = 18.9\ \text{KB}$$

`-Xptxas -v` 实测 v6 用了 **18944 bytes smem** —— 对得上。还有很大余量，
所以可以加双缓冲（×2 = 37.9 KB，仍在 99 KB 内）。

**寄存器**（每 SM 65536 个）：v6 实测 **128 个/线程**，
256 线程的 block 要 32768 个 → 每 SM 最多 2 个 block。

**累加器**：$WM \times WN / 32 = 64 \times 32/32 = 64$ 个 fp32 累加器/线程，
已经占了 64 个寄存器的一半。**tile 再大就要 spill**（L2.2 实测 spill 值 23 倍减速）。

**所以 tile 尺寸不是调出来的，是被这三个数卡出来的。**
这和 L1.1 里推 FlashAttention tile 的方法完全一样。

### 3. LLM 里的 GEMM 形状很特殊

L0.2 算过：Qwen3-1.7B 的 prefill 有 88% 的 FLOP 在线性层。但那些 GEMM 的形状是：

| 层 | M | N | K | 形状特点 |
|---|---|---|---|---|
| QKV 投影 (prefill, S=4096) | 4096 | 4096 | 2048 | 接近方阵 |
| FFN gate/up | 4096 | 6144 | 2048 | 瘦长 |
| **decode 的任何一层 (batch=1)** | **1** | 6144 | 2048 | **退化成 GEMV** |

最后一行是关键：**decode 的 M=batch，通常只有几十。**
本章的所有优化（寄存器分块、tensor core）**在 M=1 时全部失效**——
没有足够的行去填 tile。

这就是 L0.1 kernel trace 里 decode 阶段 45% 时间花在
`internal::gemvx::kernel` 而不是 GEMM kernel 的原因。
**GEMV 是另一个问题，属于 memory-bound，回到 L2.3 的方法论。**

## 工程实现 · 自己写一遍

四个必须做对的地方。

**(1) 共享内存里 A 要转置存**

```cpp
__shared__ float sA[BK][BM], sB[BK][BN];    // 注意 sA 的维度是 [BK][BM]
...
sA[c][r] = A[(cRow + r) * K + t + c];        // 转置写入
...
for (int i = 0; i < TM; ++i) regA[i] = sA[k][tRow * TM + i];   // 按行连续读
```

因为内循环要按**列**取 A（固定 k，遍历 m）。转置存之后这就变成按行连续读，
可以向量化，也不会 bank 冲突。

**(2) 累加器必须在寄存器里**

```cpp
float acc[TM][TN] = {0.f};      // 编译器会把它放进寄存器
```

只有当索引是**编译期常量**（靠 `#pragma unroll` 全展开）时，
编译器才能把数组放进寄存器。一旦有动态索引，它就会掉到 local memory（显存！）。

用 `-Xptxas -v` 检查：`stack frame` 必须是 0。

**(3) padding 的值要算，不能猜**

```cpp
constexpr int LDA = BK + PAD;    // PAD = 8
```

目标是让相邻行的起始 bank 错开。bf16 是 2 字节，一个 bank 4 字节：

$$\text{行距 bank 数} = \frac{LDA \times 2}{4} = \frac{40 \times 2}{4} = 20$$

20 与 32 的最大公约数是 4，并不互质。
只看行首地址时，步长 20 会遍历 8 个起始 bank；步长 16 只会遍历 2 个。
这能解释行首分布发生了什么变化，但 WMMA 的实际访存还取决于线程与元素映射，
不能仅凭行首地址宣布全部冲突消失。完整访问模式应结合生成指令和计数器检查。

**(4) 验证必须对着 cuBLAS，而且误差度量要选对**

第一版用逐元素相对误差，测出 9.47e-03，看着像出了大错。
实际上是 K=4096 的随机矩阵乘结果在 0 附近震荡，
**单点相对误差因为抵消（cancellation）而虚高**。

改成相对 RMS 误差 $\|got - ref\| / \|ref\|$ 后是 1.19e-06 —— 正常的 fp32 舍入。

**误差度量选错会让你去追一个不存在的 bug。**

### 消融建议

| 改什么 | 你应该看到什么 |
|---|---|
| v6 的 `PAD` 从 8 改成 0 | 退回 v5 的性能（89 TFLOPS）—— **亲手验证 bank 冲突值 62%** |
| `PAD` 改成 4 / 16 / 24 | 行距 bank 数分别是 18 / 24 / 28，与 32 的最大公约数不同，冲突程度不同 |

| 把 K 从 4096 改成 128 | 主循环只有 4 次迭代，启动与收尾开销占比激增 |

第一行是本章最值得亲手做的：一个常数改回 0，性能掉 38%。

例如，小整数的 `(1+2)+3` 与 `1+(2+3)` 在浮点数中也完全相等；
非结合性表示顺序变化可能改变结果，不是一定改变结果。

再检查实际计算路径，不把一个候选原因写成已经证明的原因。

**这个对照是 L4.2（确定性）的一个具体案例**：
"GPU 结果不可复现"不是必然的，它取决于分块策略是否固定。

<details markdown="1">
<summary>④ 第一版的误差度量为什么会误导</summary>

第一版用逐元素相对误差：

```cpp
double d = std::fabs(got[i] - ref[i]);
double s = std::fabs(ref[i]) + 1e-6;
maxrel = std::max(maxrel, d / s);
```

测出 **9.47e-03**，看着像 fp32 GEMM 出了大错。

实际原因：A、B 的元素取自 $[-0.5, 0.5]$，$K = 4096$ 项求和的结果
在 0 附近震荡（期望为 0，标准差约 $\sqrt{4096} \times 0.29 \approx 18$，
但**单个元素**可能非常接近 0）。当 `ref[i]` ≈ 0.001 而绝对误差是 1e-5 时，
相对误差就是 1e-2 —— 这是**抵消（cancellation）**，不是 bug。

改用相对 RMS：

```cpp
double d = (double)got[i] - ref[i];
se += d * d; sr += (double)ref[i] * ref[i];
return std::sqrt(se / (sr + 1e-30));
```

得到 **1.19e-06**，正是 fp32 累加 4096 项的预期舍入水平（约 $\sqrt{K} \times \epsilon_{fp32}$）。

**教训：验证数值 kernel 时，误差度量要匹配问题的数值性质。**
逐元素相对误差只适用于结果远离 0 的情况。
</details>

## 前沿

| 方向 | 内容 |
|---|---|
| **`cp.async` / TMA** | Ampere 的 `cp.async` 让全局→共享的拷贝异步进行、不占寄存器；Hopper 的 TMA 把整块搬运交给专用硬件。这是双缓冲能真正生效的前提（L2.2 里 cuBLAS 的 `tmaAB` kernel 名就是证据） |
| **warp specialization** | 一部分 warp 专职搬数据（producer），一部分专职算（consumer），用 named barrier 协调。Hopper/Blackwell 上高性能 GEMM 的标准结构 |
| **XOR swizzle** | 比 padding 更彻底且不浪费空间。CUTLASS 的 `Swizzle<B,M,S>`、CuTe 的 layout algebra（L2.5） |
| **split-K / stream-K** | K 很大而 M/N 很小时，把 K 切开并行再归约。stream-K 进一步做动态负载均衡，消灭尾效应（L2.1） |
| **`nvjet` 运行时 JIT** | L2.2 发现 cuBLASLt 对 sm_120 的 fp8 走运行时代码生成，针对具体形状生成专用 kernel |
| **DeepGEMM** | DeepSeek 为 MoE 的分组 GEMM 写的专用库，用 JIT + 极简代码达到超过 cuBLAS 的性能（L4.4） |
| **`kind::mxf8f6f4` 指令族** | L1.2 留下的开放问题。cuBLAS fp8 达到 1501 FLOP/clk/SM 而 `m16n8k32` 上限只有 1022 —— 本章仍未测<span class="unverified">未实测</span> |

## 陷阱

**1. 以为共享内存分块一定有大收益。** 本机只有 1.2 倍，因为 96 MB 的 L2 已经在缓存了。

**2. 忽略 bank 冲突。** 本章实测：一个 `PAD = 8` 值 **62%** 的性能。
判断方法：算行距对应多少个 bank，看它与 32 的最大公约数。

**3. 累加器数组用动态索引。** 会掉到 local memory（显存）。
必须 `#pragma unroll` 全展开，并用 `-Xptxas -v` 确认 `stack frame` 为 0。

**4. tile 开太大。** 累加器数量 = $TM \times TN$，直接吃寄存器。
16×16 就是 256 个累加器 → 必然 spill → L2.2 实测 23 倍减速。

**5. 用逐元素相对误差验证 GEMM。** 结果在 0 附近时会虚高，
让你去追不存在的 bug。用相对 RMS。

**6. 把 M=1 的 decode 当 GEMM 优化。** 那是 GEMV，是 memory-bound 问题，
本章的所有手段都不适用。

**7. 拿"纯计算峰值"当 GEMM 的分母。** 本章的 116 TFLOPS 来自 L2.1 的纯 FMA 循环，
不搬数据。cuBLAS SGEMM 也只到它的 59.6% —— 说明真实 GEMM 的可达上限更低。

## 自测题

<details markdown="1">
<summary>1. 我把 v2 的 tile 从 8×8 改成 16×16，期望算术强度翻倍。结果性能反而崩了。为什么？</summary>

因为**累加器数量是 $TM \times TN$**：

- 8×8 → 64 个 fp32 累加器 → 实测 122 个寄存器（含临时变量），不 spill
- 16×16 → **256 个累加器** → 远超每线程 255 个寄存器的硬上限 → **必然 spill**

L2.2 实测：2796 字节的 spill 带来 **23 倍**减速。
即使算术强度从 4 提升到 8，也远远补不回来。

**诊断方法**：`-Xptxas -v` 看 `spill stores`。不为 0 就说明 tile 太大了。

**正确的做法**是保持 8×8 的线程 tile，通过**增大 block tile**（比如 256×128）
来提高整体复用——那样每个线程的累加器数量不变，但一个 block 复用更多数据。
代价是共享内存和每 SM 驻留 block 数。
</details>

<details markdown="1">
<summary>2. 为什么 padding 用 8 而不是 1 或 16？给出计算过程。</summary>

目标：让**相邻行的起始 bank 错开**，且连续 32 行能覆盖全部 32 个 bank。

共享内存有 32 个 bank，每 bank 4 字节。bf16 是 2 字节，所以：

$$\text{行距占的 bank 数} = \frac{(BK + PAD) \times 2\ \text{字节}}{4\ \text{字节/bank}} = \frac{BK + PAD}{2}$$

代入 $BK = 32$：

| PAD | 行距(bf16) | 行距 bank 数 | gcd(bank数, 32) | 连续行能覆盖几个 bank |
|---|---|---|---|---|
| 0 | 32 | 16 | **16** | 只有 2 个 ← 灾难 |
| 4 | 36 | 18 | 2 | 16 个 |
| **8** | **40** | **20** | **4** | **8 个** |
| 16 | 48 | 24 | 8 | 4 个 |

严格说 PAD=4（gcd=2）比 PAD=8（gcd=4）更好。但还要考虑：

- **向量化对齐**：v6 用 `float4` 写共享内存（8 个 bf16 = 16 字节），
  要求行距是 8 的倍数。$32 + 8 = 40$ 满足，$32 + 4 = 36$ **不满足**。
- **空间浪费**：PAD 越大越浪费。

**所以 PAD=8 是"错开 bank"与"保持 16 字节对齐"的折中。**

这也说明为什么真正的库用 **XOR swizzle** 而不是 padding：
它能同时做到零浪费、完全错开、且保持对齐。
</details>

<details markdown="1">
<summary>3. v6 达到 cuBLAS 的 66%。如果只能再做一件事，你会做什么？为什么？</summary>

**双缓冲（软件流水）。**

理由：

1. **收益最大。** CUTLASS 的 kernel 名里 `x3` 表示 3 段流水
   （L2.2 走读过）。当前 v6 是"加载 → 同步 → 计算 → 同步"的严格串行，
   加载阶段 tensor core 完全空闲。双缓冲能把这两段重叠。
2. **资源允许。** `-Xptxas -v` 实测 v6 只用了 18944 B 共享内存，
   翻倍到 37.9 KB 仍远低于 99 KB 上限（L1.1）。寄存器 128 个也有余量。
3. **其他手段的收益更小或更复杂**：
   - XOR swizzle 比 padding 只强一点（padding 已经解决了大部分冲突）
   - warp specialization 需要重构整个 kernel
   - autotuning 需要一套框架

**做法**：开两份共享内存缓冲，计算第 $t$ 块的同时用 `cp.async`
预取第 $t+1$ 块。`cp.async` 的好处是异步且不占寄存器（L2.2 前沿提到）。

**预期收益**：如果加载占了 30% 的时间，完全隐藏能带来约 1.4 倍 ——
144.9 → 约 200 TFLOPS，达到 cuBLAS 的 92%。
</details>

<details markdown="1">
<summary>4. 本章的所有优化，在 decode 阶段（M=1）还有用吗？</summary>

**基本都没用。**

decode 时 $M = \text{batch}$，通常只有 1–64。此时：

- **寄存器分块失效**：$TM = 8$ 需要 8 行，M=1 时只有 1 行，7/8 的计算是浪费。
- **tensor core 部分失效**：`m16n8k16` 要求 M 维至少 16。M=1 时要 padding 到 16，
  **15/16 的算力被浪费**。
- **共享内存分块的价值下降**：A 只有 1 行（2048 个数，4 KB），本来就能装进寄存器。

这就是 L0.1 的 kernel trace 里 decode 阶段
**45% 的 GPU 时间在 `internal::gemvx::kernel`** 的原因——
cuBLAS 检测到 M 很小，切换到了专门的 GEMV kernel。

**GEMV 是 memory-bound 问题**（L0.2 算过算术强度只有 1.1），
方法论要回到 L2.3：向量化访存、对齐波长、足够的并行度。

**这正是 L5 里所有工程手段的出发点**：既然 decode 的算力用不上，
就想办法**提高 batch**（continuous batching）或**一次算多个 token**（投机解码），
把 M 从 1 拉大到能用上 tensor core 的区间。
</details>

<details markdown="1">
<summary>5. v6 与 cuBLAS 逐位相同，但 v2/v3 与 cuBLAS SGEMM 有 1.19e-06 的误差。这对生产系统意味着什么？</summary>

意味着**数值可复现性取决于分块策略是否固定**，而不是"GPU 天生不确定"。

**具体到 LLM 推理**：

同一个 prompt，在 batch=1 和 batch=32 时可能得到**不同的输出**。原因链条：

1. batch 变了 → GEMM 的 M 维变了
2. cuBLAS/引擎为不同的 M 选择**不同的 kernel 或不同的分块**（autotuning）
3. K 方向的累加顺序变了
4. 浮点结果有微小差异（~1e-6）
5. 经过 28 层放大，最终 logits 的差异可能足以改变 argmax
6. **输出的 token 不同**

这就是 **batch-invariance** 问题。它的后果是：
- 用户反馈"同样的问题两次回答不一样"（即使 temperature=0）
- 复现线上问题困难
- A/B 测试的对照组不干净

**解法**（都有代价，L4.2 会展开）：
- 固定 batch size（浪费算力）
- 用确定性的 kernel（禁用 split-K 等动态策略，牺牲性能）
- 提高数值精度（fp32 累加已经是标配，再往上代价很大）

**本章的实测给了这个问题一个具体的锚点**：
分块一致时可以做到逐位相同，所以这是**工程可解**的，不是物理限制。
</details>
