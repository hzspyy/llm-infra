## 本章回答三个问题

1. 现代 kernel DSL 声称"几十行 Python 拿到接近 cuBLAS 的性能"。**是真的吗**？
2. 它们各自的代价是什么？代码量、编译时间、可控性怎么权衡？
3. 这些 DSL 到底**生成了什么**？相比基础手写实现补充了哪些关键优化？

DSL 是领域专用语言。这里的几种 DSL 都用于描述 GPU 计算，
但把不同的决策交给了编译器：有的要求你指定 tile 和流水，
有的还会自动搜索这些参数。本章用同一个 GEMM 比较这些分工，
并检查生成代码。表中的表现只代表列出的实现和配置，不是语言本身的固定排名。

## 机制拆解

### 实测结果

| 实现 | 耗时 ms | TFLOPS | 占上限 | kernel 行数 | 首次编译 s | 相对误差 |
|---|---|---|---|---|---|---|
| `torch.matmul`（cuBLAS） | 0.628 | **218.9** | 86.9% | 1 | 0 | 0 |
| **Helion** | 0.632 | **217.3** | 86.3% | **12** | **492.8** | 0 |
| `torch.compile`（Inductor） | 0.633 | 217.3 | 86.2% | 1 | 0.1* | 0 |
| **TileLang** | 0.669 | **205.4** | 81.5% | **18** | ~1 | 0 |
| Triton（手调 tile） | 0.770 | 178.4 | 70.8% | 34 | 0.5 | 0 |
| **手写 CUDA v6**（L2.4） | 0.948 | **144.9** | 57.5% | **~400 行 C++** | — | 0 |

\* 命中了上一次运行的编译缓存

这张表是 bf16、每个实现用自己挑的配置，回答"哪条路线更省事"；
CuTe-DSL 的官方例程只提供 fp16 路径，所以它不出现在这里，
而在后面的受控 tile 对照中与另外三条一起排。两个契约不可混读。

**结论很明确：三种 DSL 实测性能均优于基础手写的 CUDA v6，性能最优的 Helion 提升达 50%。**

这次输出中的相对误差为 **0**，说明所用比较方法在该样本上没有发现差异。
这不等于已经确认所有实现使用相同的累加顺序，也不保证换输入后仍然一致。
区分输出观察与实现机制的方法见 L2.4。

### 为什么 DSL 能赢：看它生成了什么

L2.4 的 v6 尚未实现以下优化：

> | 手段 | 本章实现 |
> |---|---|
> | 双缓冲 / 软件流水 | ✗ |
> | `cp.async` 异步拷贝 | ✗ |
> | XOR swizzle | ✗（只用了 padding） |
> | tile 尺寸 autotuning | ✗（写死 128×128×32） |

去看 Helion 生成的 PTX（Triton 缓存目录里）：

```
=== 里面的 tensor core 指令
     64 mma.sync.aligned.m16n8k16.row.col.f32.bf16.bf16.f32

=== 异步拷贝与同步
      4 cp.async.bulk.tensor.2d.shared      ← TMA！
      2 cp.async.bulk.commit_group
      2 cp.async.bulk.wait_group.read
      2 barrier.arrive.expect_tx.shared     ← mbarrier 异步同步
      1 barrier.init.shared
      1 barrier.try_wait.parity.shared
```

**`cp.async.bulk.tensor.2d.shared` 就是 TMA**（Tensor Memory Accelerator）：
把整块 2D tile 的搬运交给专用硬件，不占寄存器、不阻塞计算。
配合 `barrier.arrive.expect_tx` 这套 mbarrier 机制做异步流水。

这里看到了与手写版本相同的 mma 指令类型，以及不同的数据搬运与同步安排。
这说明搬运和流水值得优先检查，但仅凭指令列表不能把全部性能差距归到它们。
还要考虑 tile、寄存器、调度和编译配置的差异。

### 从 12 行 Python 到 857 行 PTX

Helion 的 kernel 只有 12 行：

```python
@helion.kernel(static_shapes=True)
def helion_gemm(x: torch.Tensor, y: torch.Tensor) -> torch.Tensor:
    m, k = x.size()
    k2, n = y.size()
    out = torch.empty([m, n], dtype=torch.promote_types(x.dtype, y.dtype),
                      device=x.device)
    for tile_m, tile_n in hl.tile([m, n]):          # ← 只声明"要分块"
        acc = hl.zeros([tile_m, tile_n], dtype=torch.float32)
        for tile_k in hl.tile(k):
            acc = torch.addmm(acc, x[tile_m, tile_k], y[tile_k, tile_n])
        out[tile_m, tile_n] = acc.to(out.dtype)
    return out
```

注意它**没有说 tile 多大**——`hl.tile` 只表达"这一维要分块"，
具体尺寸、流水级数、warp 数、索引方式全部交给自动调优器搜索。

生成的产物逐级展开：

```
_helion_helion_gemm.source     19 041 B   Triton 源码（Helion 生成的）
_helion_helion_gemm.ttir       108 行     Triton IR
_helion_helion_gemm.ttgir      148 行     TritonGPU IR（带 layout）
_helion_helion_gemm.llir     1 047 行     LLVM IR
_helion_helion_gemm.ptx        857 行     PTX
_helion_helion_gemm.cubin   52 400 B     SASS
```

**12 行 Python → 857 行 PTX。** 中间隔着两个编译器（Helion→Triton，Triton→LLVM→PTX）。

### 代价一：编译时间差三个数量级

| DSL | 首次编译 | 做了什么 |
|---|---|---|
| Triton（手指定 tile） | **0.5 s** | 只编译你给的那一组参数 |
| TileLang | ~1 s | 同上，但多一层 TVM 风格的调度变换 |
| **Helion** | **492.8 s** | **自动调优 752 个配置**，遗传算法搜索 |

Helion 的调优日志（原文）：

```
[306s] Fitting surrogate: 752 points, 752 targets
[306s] Copy 3 finish because of no improvement
[307s] Generation 10 starting: 53 neighbors, 3 active search path(s)
Generation 10: precompiling 100% ━━━━━━━━━━━ 55/55  15.3 configs/s
```

它在搜的参数包括（从日志里摘的）：

```
block_sizes, range_num_stages, range_multi_buffers, range_flattens,
load_eviction_policies, num_warps, num_stages,
indexing = ['pointer', 'tensor_descriptor', 'tensor_descriptor'],
pid_type = 'flat', epilogue_subtile = 2
```

**`indexing = 'tensor_descriptor'` 就是选择用 TMA**（tensor descriptor 是 TMA 的 API）。
这个选择是**搜出来的**，不是人写的。

::: warning 8 分钟的编译时间意味着什么
对**离线的、形状固定的**场景（比如一个固定尺寸的模型层），
调一次用一年，8 分钟完全可以接受，而且结果缓存下来。

对**在线服务**就是灾难：LLM 推理的 GEMM 形状随 batch 变化，
每个新形状都要重调 8 分钟，服务根本起不来。

**所以生产引擎的做法是**：
- 预先离线调好一批常见形状，把配置固化进代码（vLLM 的 `configs/*.json` 就是）
- 或者用 cuBLAS 这种运行时启发式选择（快但未必最优）
- 或者像 cuBLASLt 那样用 `nvjet` 做轻量 JIT（L2.2 发现的）
:::

### 换个算子：RMSNorm 与分段 gather+reduce（补两类非 GEMM 对照）

GEMM 只是三类算子之一。用 2.3 的两类 memory-bound 算子再对一次
（`labs/L2/dsl_ops_extra.py`，RMSNorm `[512, 14336]` fp16；
分段 gather+reduce 512 段、段长 1..4096，fp32）：

| 算子 | 实现 | 冷编译 | 稳态 | 代码行数 | PTX 指令行 | max&#124;err&#124; |
|---|---|---:|---:|---:|---:|---:|
| RMSNorm | 手写 CUDA | 0.2 ms | 0.0207 ms | 28 | — | 1.95e-03 |
| RMSNorm | Triton | 249.9 ms | **0.0127 ms** | 31 | 159 | 1.95e-03 |
| RMSNorm | TileLang | 1064.3 ms | 0.1026 ms | 26 | — | 3.91e-03 |
| 分段归约 | 手写 CUDA | 1.6 ms | **0.0037 ms** | 21 | — | 7.63e-06 |
| 分段归约 | Triton | 33.7 ms | 0.0054 ms | — | — | 7.63e-06 |

读法与 GEMM 那组不同：

- **谁是稳态赢家取决于算子形状。** RMSNorm 上 Triton 比手写 CUDA 快 1.6×
  （0.0127 vs 0.0207 ms），分段归约上手写 CUDA 反而快 1.46×
  （0.0037 vs 0.0054 ms）。没有"某 DSL 全面更快"这回事。
- **代码行数量级相同（21–31 行），差距全在 lowering。** Triton 的 RMSNorm
  PTX 包含 159 条指令，手写 CUDA 的同样 28 行源码依靠手工推导的
  vectorize/裁剪，两者稳态差 1.6×。
- **冷编译差距是 2–3 个数量级**：手写 CUDA 的扩展一旦建好是 0.2 ms，
  Triton 249.9 ms，TileLang 1064.3 ms。这印证了"编译时间与迭代速度"
  是选型轴上的一根独立坐标。

TileLang 的 RMSNorm 这一组还给出了两条真实警告，值得原样保留：

```
Warning: Data race detected: `ss(0,)` is written by multiple threads in loop (i,)
Warning: T.vectorized loop over `vec` with extent 8 is lowered as a serial loop
         because TileLang could not find a valid vectorization plan.
```

**共享累加器 `ss` 的数据竞争没有被消除**，稳态 0.1026 ms 比 CUDA/Triton 慢
5–8 倍，误差也比另外两个大一个 fp16 ulp（3.91e-03 对 1.95e-03）。
这不是"DSL 不可用"，而是**同一份数学用不同抽象写出来，编译器给出的诊断与
最终质量差别很大** —— 这也是选型时要一起看的：出问题时你能不能看懂它的报错。

### CuTe-DSL：从"跑不起来"到实测 211 TFLOPS

早前记录的现象是 `cute.compile` 无法把 `torch.cuda.Stream` 适配成参数。真正的原因有两层，
都不在 kernel 里：

1. **`@cute.jit` 的 host 函数不该接收 stream。** CuTe-DSL 的 launch 走当前流：
   `kernel(...).launch(grid=..., block=...)`。传 `torch.cuda.current_stream()` 进去，
   反而触发参数适配失败（原文见原始现场④）。
2. **`CUDA_TOOLKIT_PATH` 必须指向 CUDA 安装根。** 不设时 IR 能生成，
   但 libNVVM 报 `backend compilation failed`（后端找不到），
   看起来像 kernel 写错，实际是环境变量缺失。

两点修好后，CUTLASS 官方 sm_120 例程
（`examples/python/CuTeDSL/cute/blackwell_geforce/kernel/dense_gemm/dense_gemm.py`，
TMA 多级流水 + persistent tile scheduler + `mma.sync`）在 4096³ fp16 上跑通：
受控 tile 128×128×64 稳态 **651.7 µs = 210.8 TFLOPS**，是上限的 83.7%、
cuBLAS fp16（216.3）的 97.5%。

生成物揭示了它的抽象落点（`CUTE_DSL_KEEP=ir,ptx,cubin` + `sass_census.py`）：

```
clean MLIR 222 KB   cute.gemm(...) : (!mma_f16_f16_f32_16x8x16, !memref_rmem_f32, ...)
                    nvvm.setmaxregister increase 232
PTX                 mma.sync.aligned.m16n8k16 × 256    cp.async.bulk.tensor × 55
SASS（sm_120a）      HMMA 256   UTMA 23   LDSM 96   STSM 32   本地访存 0
资源                REG:209  STACK:0
```

三点：

- **累加器在寄存器里**（MLIR 里是 `memref_rmem_f32`），不是 TMEM —— sm_120 上
  根本没有 TMEM 这条路径（L2.4 的门控实测）。
- **PTX 与 SASS 的 mma 条数一一对应**（256 ↔ 256）：这条路上没有二次展开或合并，
  "看 PTX 猜最终指令"在这里是成立的。
- **TMA 被生成为 `nvvm.cp.async.bulk`**，与手写 kernel 里的 `cp.async` 不是同一层机制。

本章没有为 RMSNorm 与分段归约写 CuTe-DSL 版本（那两类只有 CUDA/Triton/TileLang 三条路线），
这是本章剩余的缺口；GEMM 这一类的结论已经可以给实测数字。

### 受控 tile 对照：把 dtype、tile 与输出精度全部固定

上面那张横评是"每个实现用自己挑的配置"，它回答"哪条路线更省事"，
回答不了"同一个 tile 下谁快"。任务 B 要的是后者，所以另做一组：

**契约**：4096³，输入 fp16，累加 fp32，输出 fp32，tile 固定 128×128×64。
四条路线（手写 CUDA、Triton、TileLang、CuTe-DSL 官方例程），
前三条与 cuBLAS 用同一组张量，误差统一对 FP64 matmul 参照。

| 实现 | 稳态 ms | TFLOPS | 占上限 | 寄存器 | 溢出 | smem B | PTX 行 | 冷编译 s | 二次调用 s | 相对 RMS |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 手写 CUDA（WMMA） | 0.784 | 175.2 | 69.6% | 126 | 0 | 35840 | — | — | — | 0* |
| Triton | 0.726 | 189.4 | 75.2% | 166 | 0 | 65536 | 1235 | 0.21 | 0.0008 | 4.87e-06 |
| TileLang | 0.679 | 202.5 | 80.4% | — | — | — | — | 0.01 | 0.0009 | 4.87e-06 |
| CuTe-DSL（官方例程） | **0.652** | **210.8** | **83.7%** | 209 | 0 | — | — | — | — | —† |
| — cuBLAS fp16 | 0.635 | 216.3 | 85.9% | — | — | — | — | — | — | — |

\* 手写 CUDA 与 cuBLAS 在这组输入上逐位相同（16777216 个元素，不同的 0 个），
所以它的"相对 RMS"按 cuBLAS 的口径记 0；把它换算到 FP64 尺子上与 cuBLAS 同值。
† CuTe-DSL 例程的输出是 fp16、参照检查走 CPU einsum，误差口径与前三条不同，
因此不并列比较。

四点读法：

1. **受控 tile 上手写 CUDA 垫底（69.6%）。** 它缺的正是 2.4 没实现的那几项：
   `cp.async`/TMA 的多级流水与 XOR swizzle。这不是"手写不如 DSL"的证明，
   而是"这一份手写实现只做到 2.4 的 v6 阶梯"。换成 2.4 的 v6 配置
   （128×128×**32**）同机实测 154.8 TFLOPS，同一个 tile 换 BK 就值 13%。
2. **Triton 的"各自 tile"在 fp16→fp32 契约下反而更慢**：128×256×64 只有 176.0，
   比受控 tile 的 189.4 低 7%。上一节"猜错 tile 的代价是 23%"来自
   bf16→bf16 的契约与 Inductor 的 autotune 日志，**不能跨契约外推**：
   同一组 tile 在 fp16、fp32 输出下排名可以翻转。
3. **TileLang 在本机只能开到受控 tile。** 128×256×64 + 3 级流水需要 144 KB
   动态共享内存，直接失败（原文见原始现场②）；Triton 的同一形状用 98 KB 就够。
   两者的 shared 预算算法不同，这是"谁能开大 tile"的实际差别。
4. **编译时间必须与稳态分开记。** Triton 冷编译 0.21 s、TileLang 0.01 s，
   而 CuTe-DSL 冷/热两次墙钟只差 0.02 s（1.95 vs 1.97 s）—— 那 ~2 s 是
   Python 端与 DSL 运行时的固定启动成本，不是 kernel 编译。把它算进"编译时间"
   会把 CuTe-DSL 描述成"编译两秒"，而实测的边际编译成本小到测不出来。
5. **输出精度比累加精度更值钱。** 同一个乘积对 FP64 参照的相对 RMS：
   fp32 输出（Triton/TileLang）4.87e-06；把 cuBLAS 的输出改成 fp16
   （PyTorch 的 `matmul` 输出 dtype 跟随输入，拿不到 fp32 输出），
   相对 RMS 变成 **2.08e-04**，最大绝对差 0.126。**fp16 输出的一次舍入
   比整条 K 方向累加的误差大 40 倍**，所以比较误差前先确认输出 dtype。

### 改一个布局、加一个融合需求（任务 C）

任务 C 要求记录"改一个布局和一个融合需求"时各条路线要动什么。
受控 tile 上做两处改动：

**布局：B 从 K-major 换成 N-major（转置存放）。**

| 路线 | 要改的代码 | 稳态变化 | 说明 |
|---|---|---|---|
| Triton | 核函数里 B 的指针表达式加一个 `B_TRANS` 分支；host 侧改传 `b.t().contiguous()` 的 stride | 189.4 → 191.5 TFLOPS | PTX 从 1235 行降到 1203 行，寄存器 166 → 154 |
| TileLang | `Bs` 的 shared 形状从 `(BK, BN)` 改成 `(BN, BK)`，`T.gemm(..., transpose_B=True)` | 202.5 → 202.2 TFLOPS | 改错形状立刻报 `T.gemm K shape check failed: K_A = 64, K_B = 128` |
| CuTe-DSL | **用户代码不动**，例程自带 `--b_major n` | 651.7 → 651.7 µs | layout 由 layout 代数与 TMA 描述符吸收 |
| 手写 CUDA | 需要改 smem 的写入索引与 `load_matrix_sync` 的 row/col major 标记 | 未做 | — |

最危险的一点：**这类改动只改 host 侧的 stride 顺序，写反了不会报错。**
把 N-major 的两个 stride 按未转置的顺序传下去，编译通过、计时正常、
结果是错的（实测相对 RMS 1.41）。只有对拍能发现——这是"改布局"与"改 tile"
在风险上的本质区别。

**融合：epilogue 加 bias + ReLU。**

| 路线 | 要改的代码 | 稳态变化 | 代价 |
|---|---|---|---|
| Triton | 加 3 行：`tl.load(bias + offs_n)`、`acc + bv`、`tl.maximum(..., 0)` | 189.4 → 194.2 TFLOPS | PTX 从 1235 涨到 1412 行；寄存器 166 → 158 |
| TileLang | 加一个 `T.Parallel` 循环写 `Cf[i,j] = T.max(Cl[i,j] + Bias[...], 0)` | 202.5 → 202.2 TFLOPS | 稳态几乎不变 |
| CuTe-DSL | 例程的 epilogue 段没有暴露融合钩子，要改源码里的 epilogue 阶段 | 未做 | 这是"抽象高"的反面：融合需求触到 DSL 的边界 |

两处改动都没有引入新的 barrier：epilogue 在 shared→global 写出之前，
累加器已经在寄存器/fragment 里，加 bias 与 ReLU 是纯元素级操作。
**需要引入同步的是"融合进 mainloop"的改动**（比如把 RMSNorm 折进 GEMM 的
归约），那要等 tile 的 K 维累加结束，属于另一个层次的改动。

### 代价二：Triton 手调 tile 只有 70.8%

Triton 的 34 行里**写死了** tile：

```python
BM, BN, BK, GROUP = 128, 256, 64, 8
...
num_stages=3, num_warps=8
```

结果 178.4 TFLOPS，只有 70.8%。

而 `torch.compile` 用的**也是 Triton**，但它跑了 autotune，实测日志：

```
triton_mm_9  0.6221 ms 100.0%  BLOCK_M=64,  BLOCK_N=128, BLOCK_K=32, num_stages=3, num_warps=4
triton_mm_11 0.6226 ms  99.9%  BLOCK_M=64,  BLOCK_N=128, BLOCK_K=64, num_stages=3, num_warps=4
mm           0.6308 ms  98.6%  ← ATen 的 cuBLAS 后端
triton_mm_16 0.6649 ms  93.6%  BLOCK_M=128, BLOCK_N=128, BLOCK_K=32, num_stages=3, num_warps=4
```

**最优是 `64×128×32, num_warps=4`，而直觉预期的 `128×256×64, num_warps=8` 差距显著。**
直觉误判的代价是 23%。

而且注意：**autotune 选出的 Triton kernel（0.6221 ms）比 cuBLAS（0.6308）快 1.4%。**
这是 Inductor 默认会同时评估 ATen 与 Triton 两条路的原因。

**Triton 不是"比 cuBLAS 慢"，是"不调参就比 cuBLAS 慢"。**

但这句话有边界：上面这组数字是 **bf16、输出 bf16** 的契约。
换成 fp16、输出 fp32 的受控对照，同一个手写 tile（128×256×64）只比
128×128×64 慢 7%（176.0 对 189.4），排名甚至与 Inductor 的 autotune 结论相反
（见前面的受控 tile 对照）。**"最优 tile"是契约的函数，不是常数。**

### 四种 DSL 的抽象层次

| DSL | 你要写什么 | 编译器负责什么 | 抽象层次 |
|---|---|---|---|
| **CUDA C++** | 线程索引、共享内存布局、同步、指令选择 | 寄存器分配、指令调度 | 最低 |
| **CUTLASS / CuTe-DSL** | tile 层次结构、layout 代数 | 布局变换、指令选择、流水 | 低（但抽象好） |
| **Triton** | block 级的张量操作、显式 tile 尺寸 | 线程映射、smem 布局、同步、swizzle | 中 |
| **TileLang** | tile 操作 + 显式流水级数 | 同上 + 自动 layout 推导 | 中高 |
| **Helion** | **只说"这一维要分块"** | 全部，包括 tile 尺寸搜索 | 最高 |

**抽象越高，写得越少、越容易接近最优，但你越不知道它做了什么，也越难在它做错时干预。**

TileLang 的 18 行正好在中间：

```python
with T.Kernel(T.ceildiv(N, BN), T.ceildiv(M, BM), threads=threads) as (bx, by):
    As = T.alloc_shared((BM, BK), "bfloat16")
    Bs = T.alloc_shared((BK, BN), "bfloat16")
    Cl = T.alloc_fragment((BM, BN), "float")       # fragment = 寄存器块
    T.clear(Cl)
    for k in T.Pipelined(T.ceildiv(K, BK), num_stages=stages):   # ← 显式流水
        T.copy(A[by * BM, k * BK], As)             # 自动生成 cp.async
        T.copy(B[k * BK, bx * BN], Bs)
        T.gemm(As, Bs, Cl)                         # 自动选 mma 与布局
    T.copy(Cl, C[by * BM, bx * BN])
```

它**明确区分了 shared / fragment 两种存储**（对应 L1.1 的共享内存与寄存器），
**显式写出流水级数**（`T.Pipelined(..., num_stages=3)`），
但把 layout 推导、swizzle、指令选择交给编译器。

**这个抽象层次和在 L2.4 手写时的思考层次是对齐的**——
因而最直观地展现了编译器在底层自动完成的变换与优化。

## 工程实现 · 源码解析：真实项目怎么选

### 1. vLLM：Triton + CUDA 混用

L0.1 的 kernel trace 里能看到两类 kernel 共存：

```
_penalties_kernel                                  ← Triton（L0.1 原始现场 ⑥ 反汇编过）
vllm::rms_norm_kernel<c10::BFloat16, 8, 3, true>   ← 手写 CUDA
vllm::reshape_and_cache_flash_kernel<...>          ← 手写 CUDA
flash::flash_fwd_splitkv_kernel<...>               ← CUTLASS/CUTE
cutlass_80_tensorop_bf16_s16816gemm_...            ← CUTLASS
```

选择规律很清楚：

- **形状多变、逻辑复杂、性能不极端**（采样惩罚、各种 mask）→ **Triton**
- **热路径、形状固定、要榨干性能**（RMSNorm、KV 写入）→ **手写 CUDA**
- **GEMM / attention** → **CUTLASS 或专用库**

### 2. DeepSeek 用 TileLang

TileLang 在近期的 DeepSeek 开源里被使用。原因可以从本章的数据推测：
**18 行拿到 81.5%，编译只要 1 秒**——对需要为大量 MoE 形状生成 kernel 的场景，
这个"性能/开发成本/编译时间"组合很划算。

### 3. FlashAttention-4 用 CuTe-DSL

FA4 完全用嵌入 Python 的 CuTe-DSL 写，没有 C++ 部分。
它的卖点是**编译比 C++ CUTLASS 模板快 20–30×**——
对照 L2.2 实测的"预处理膨胀 1761 倍"，这个提速的来源就清楚了：
**跳过整个 C++ 前端**。

::: note 本章的 CuTe-DSL 用的是官方例程，不是自己写的
`nvidia-cutlass-dsl 4.6.2` 已装在本机。要**从零写**一个 CuTe-DSL GEMM
需要理解 layout algebra（`Layout`、`Tiler`、`TiledMma` 等概念），
代码量与学习曲线都远超其他三家，所以本章用的是 CUTLASS 自带的
sm_120 例程（`blackwell_geforce/kernel/dense_gemm`），把它当作
"这条路线在受控 tile 下能跑到多少"的参照。

自己写的部分是 host 侧的适配（见前面的 CuTe-DSL 小节）与生成物普查。
它通过 Python 接口表达底层布局与流水，
适合要完全控制流水和布局的场景（例如手动安排 FA4 中的 exp() 近似计算）。
L3.2 讲 FlashAttention-4 时会回到它。
:::

## 工程实现 · 自己写一遍

三个 DSL 的关键差异，浓缩成各自最核心的几行。

**Triton：你管 tile，编译器管线程**

```python
acc = tl.zeros((BM, BN), dtype=tl.float32)      # 累加器必须 fp32（L4.2）
for k in range(0, tl.cdiv(K, BK)):
    am = tl.load(a_ptr, mask=offs_k[None, :] < K - k * BK, other=0.0)
    bm = tl.load(b_ptr, mask=offs_k[:, None] < K - k * BK, other=0.0)
    acc = tl.dot(am, bm, acc)                   # ← 一行就是 tensor core
    a_ptr += BK * sak
    b_ptr += BK * sbk
```

`tl.dot` 一行就展开成 64 条 `mma.sync`（实测 PTX 里数出来的）。
你**看不到**共享内存、看不到 `__syncthreads`、看不到 warp 映射——
那些是编译器的事。

但你**必须**自己写 `mask`（边界处理）和指针递增，
还有那段 L2 友好的 block 重排（`GROUP` 那几行）。

**TileLang：显式区分 shared / fragment，显式写流水**

```python
As = T.alloc_shared((BM, BK), "bfloat16")     # 共享内存
Cl = T.alloc_fragment((BM, BN), "float")      # 寄存器（fragment）
for k in T.Pipelined(T.ceildiv(K, BK), num_stages=3):    # 3 段流水
    T.copy(A[by * BM, k * BK], As)
    T.gemm(As, Bs, Cl)
```

`T.Pipelined(..., num_stages=3)` 对应 L2.4 中讨论的异步双缓冲流水线，
对应 CUTLASS kernel 名里的 `x3`（L2.2 解析过）。**一个参数替代几十行手写代码。**

**Helion：连 tile 尺寸都不写**

```python
for tile_m, tile_n in hl.tile([m, n]):        # 不说多大
    acc = hl.zeros([tile_m, tile_n], dtype=torch.float32)
    for tile_k in hl.tile(k):
        acc = torch.addmm(acc, x[tile_m, tile_k], y[tile_k, tile_n])
```

注意内层直接用了 **`torch.addmm`** —— Helion 的 kernel 体里可以写普通的 PyTorch 算子，
它会被翻译成 tile 级的操作。这是它 12 行的原因。

**一个实操坑**：Helion 要求 kernel 引用的名字是**全局**的，不能是闭包变量。
将 `import helion.language as hl` 放在函数内会报错：

```
ClosuresNotSupported: A closure (('hl',)) was found in the kernel.
```

把 import 和 kernel 定义都提到模块级才能用。

## 前沿

| DSL | 定位与现状 |
|---|---|
| **Triton** | 事实标准。PyTorch Inductor 的后端，vLLM/SGLang 大量使用。跨 NVIDIA/AMD。弱点是对新硬件特性（TMA、wgmma、tcgen05）的支持滞后于 CUTLASS |
| **CuTe-DSL** | NVIDIA 官方，CUTLASS 4.x 的 Python 前端。**FlashAttention-4 完全用它写**，编译比 C++ 模板快 20–30×，保留寄存器分配与流水调度的控制权。只支持 NVIDIA |
| **TileLang** | TVM 血统，本章实测 18 行 81.5%。近期 DeepSeek 的开源里在用。跨后端（LLVM/MLIR） |
| **Helion** | PyTorch 官方的更高层 DSL，编译到 Triton。本章实测 12 行 86.3%，但要 8 分钟自动调优 |
| **ThunderKittens** | 2.0 于 2026-01 发布，支持 Blackwell + MXFP8/NVFP4。以 16×16 tile 为基本单位。**本机未装**<span class="unverified">未实测</span> |
| **cuda.compute (CCCL)** | NVIDIA 的 Python 并行原语库，2026 登顶过 GPU MODE 排行榜 |
| **AI 写 kernel 的现状** | KernelBench 上前沿模型对 Triton 的 pass@1 尚可，但对 TileLang 低于 20%、ThunderKittens 低于 2% —— 因为公开语料太少（不足 100 万 token）<span class="unverified">未实测</span> |

最后一行对你有直接意义：**越新的 DSL，能问 AI 的东西越少，越要读官方 example**。

## 陷阱

**1. 拿"不调参的 Triton"跟 cuBLAS 比。** 本章实测差 23%。
Triton 的性能高度依赖 tile 参数，必须 autotune。

**2. 以为高层 DSL 一定慢。** 12 行 Helion 打过 400 行手写 CUDA 50%。

**3. 忽略编译时间。** Helion 493 秒。对形状多变的在线服务是致命的。

**4. Helion 的 kernel 里用闭包变量。** 报 `ClosuresNotSupported`。
import 和 kernel 定义都要在模块级。

**5. 只看性能不看生成的代码。** 本章最有价值的一步是去 PTX 里
数 `cp.async.bulk.tensor` 和 `mma.sync` —— **那才知道它凭什么快**。

**6. 以为 DSL 免除了硬件知识。** 恰恰相反：TileLang 要你写 `num_stages`，
Triton 要你选 `BLOCK_M/N/K` 和 `num_warps`。
**不懂 L1/L2 那些硬件事实，你连参数该往哪调都不知道。**

**7. 用方阵 GEMM 的结论去推 decode。** M=1 时全部失效（L2.4 自测题 4）。

**8. 把"受控 tile"和"各自配置"混在一张表里读。**
同一个 tile 在不同 dtype 与输出精度下排名会翻转：Triton 的手写 tile
在 bf16→bf16 下比 autotune 最优慢 23%，在 fp16→fp32 下只比受控 tile 慢 7%。
比较前先把 dtype、累加类型、输出精度、tile 四件事写清楚。

**9. 改布局只改 host 侧的 stride，不写对拍。**
N-major B 的 stride 顺序写反不会报错，实测相对 RMS 1.41 —— 编译通过、
计时正常、结果是错的。布局改动必须配一组数值对拍。

**10. 把框架的"共享内存上限"当成硬件常数。**
同机实测：Triton 报的上限是 101376 B（99 KB，未申请 opt-in），
而 sm_120 通过 opt-in 可以到 227 KB。TileLang 的 144 KB 请求直接失败。
"这个 tile 能不能开"取决于框架有没有去申请额度，不是芯片的固定属性。

**11. 把 Python 端的固定启动成本算成编译时间。**
CuTe-DSL 的冷/热两次墙钟只差 0.02 s（1.95 vs 1.97 s），
剩下的约 2 s 是解释器与 DSL 运行时的启动；真正的边际编译成本在这台机器上测不出来。

**12. 以为 CuTe-DSL 连不上 torch 流。** 是 host 函数**不该**接收 stream 参数；
再加上 `CUDA_TOOLKIT_PATH` 没设会让 libNVVM 报后端失败。两处都不是 kernel 的问题。

## 自测题

<details markdown="1">
<summary>1. 我的项目要给 20 种不同形状的 GEMM 写 kernel，形状在编译期已知。选哪个 DSL？</summary>

**TileLang 或 Helion，取决于你有多少调优时间预算。**

- **形状编译期已知** → 可以离线调优，Helion 的 493 秒 × 20 = 2.7 小时，一次性成本，可接受。
- **要求当天出结果** → TileLang：18 行、1 秒编译、81.5% 性能，够用。
- **不要选手写 CUDA**：本章实测它反而最慢，而且 20 种形状 × 400 行 = 8000 行要维护。

**关键判断**：调优是**一次性成本**还是**每次部署都要付**？
前者选高抽象 + 自动调优，后者选中抽象 + 手工参数。

**还有一个选项**：先用 `torch.compile(mode="max-autotune")` 试一下。
本章实测它 0.633 ms（86.2%），而且你一行 kernel 都不用写。
**在决定手写之前，先确认自动方案确实不够。**
</details>

<details markdown="1">
<summary>2. Helion 生成的 PTX 里有 TMA（<code>cp.async.bulk.tensor</code>），但 L1.2 说 sm_120 不支持 Hopper 的特性。矛盾吗？</summary>

**不矛盾。TMA 与 `wgmma`/`tcgen05` 是不同的特性，支持范围不同。**

L1.2 实测确认 sm_120 **不支持**：
- `wgmma.mma_async`（Hopper 的 warp-group MMA）
- `tcgen05.mma` + TMEM（数据中心 Blackwell）

但 **TMA（`cp.async.bulk.tensor`）在 sm_120 上是支持的** ——
本章的 PTX 就是证据（`.target sm_120a` 且含 4 条 `cp.async.bulk.tensor.2d.shared`，
而且这个 kernel 确实跑出了 217 TFLOPS）。

**一般教训：不要把一代架构的特性当成一个整体。**
「Blackwell 有什么」这个问题必须逐条问，而且要以**编译器/实测**为准，
不是以宣传材料为准。L1.2 的 `tcgen05_probe.cu` 就是这类判决性实验的模板。
</details>

<details markdown="1">
<summary>3. 我的 Triton kernel 只有 cuBLAS 的 70%。在调 tile 之前，我应该先检查什么？</summary>

按顺序：

**(1) 累加器是不是 fp32。** `tl.zeros((BM, BN), dtype=tl.float32)`。
如果写成 bf16，精度会崩（L2.3 实测 float 在 $2^{24}$ 处就失效，bf16 在 $2^8$）。

**(2) 有没有 L2 友好的 block 重排（`GROUP_M`）。** 默认的行主序 block 编号
会让同时执行的 block 读完全不同的 A 行和 B 列，L2 命中率很低。
本章的 Triton 版有这段（`GROUP = 8`），Inductor 选的也是 `GROUP_M=8`。

**(3) `num_stages` 是不是 ≥ 3。** 这决定软件流水的深度，对应 L2.4 讨论的异步双缓冲。
Inductor 的最优配置是 `num_stages=3`。

**(4) 然后才是 tile 尺寸。** 而且**不要猜，要扫**：

```python
@triton.autotune(configs=[
    triton.Config({'BM':64,'BN':128,'BK':32}, num_stages=3, num_warps=4),
    triton.Config({'BM':128,'BN':64,'BK':32}, num_stages=3, num_warps=4),
    ...
], key=['M','N','K'])
```

**(5) 最后去看生成的 PTX**：`grep mma.sync` 确认真的用了 tensor core，
`grep cp.async` 确认真的异步搬运了。
本章实测：这一步能直接告诉你"编译器有没有做到你以为它做的事"。
</details>

<details markdown="1">
<summary>4. 既然 DSL 这么好，为什么 vLLM 里还有那么多手写 CUDA kernel？</summary>

三个原因，L0.1 的 kernel trace 里都能看到证据。

**(1) 有些算子不是"张量运算"。**
`reshape_and_cache_flash_kernel` 要按 slot mapping 把 K/V **散写**到非连续的物理块里
（L5.2 的 PagedAttention）。这是**指针操作**，不是 Triton/TileLang 擅长表达的
block 级张量代数。

**(2) 极端热路径值得手工。**
`rms_norm_kernel` 在 decode 每步调用 952 次（L0.1 实测）。
即使只快 10%，累计也可观。而且它的形状固定（hidden=2048），
手工调一次用很久。

**(3) 依赖与编译时间。**
Triton 的 JIT 首次运行要编译（L0.1 实测一次 `LLM.generate` 产生 41 个 cubin）。
生产环境不希望冷启动时编译几十个 kernel。手写 CUDA 是 AOT 编译进 `.so` 的。

**趋势是在变的**：vLLM 里 Triton kernel 的比例在增加，
新的算子（采样惩罚、各种 mask）基本都用 Triton 写。
**但"全部用 DSL"短期内不会发生。**
</details>

<details markdown="1">
<summary>5. 本章所有实现的误差都是 0（与 cuBLAS 逐位相同）。这可信吗？我该怎么验证不是测量出了 bug？</summary>

需要核对测量范围，下面给出实测对照。

L2.4 里对手写 WMMA 版做过专门验证（1024³，逐元素比对）：

```
参考 RMS = 2.666367
自写 RMS = 2.666367
最大绝对差 = 0
不同的元素数 = 0 / 1048576
```

**100 万个元素，一个都不差。** 所以"误差 0"是真的。

应继续验证输出比较本身：确认读取的是本次结果、参考与结果不是同一缓冲、
比较没有先经过低精度转换，并记录最大绝对误差与不同元素数。
然后改变输入分布、K 长度和归约路径，检查一致性是否仍成立。
这些改变可能引入数值差异，但不能保证每个样本一定出现差异。
不要因为 bf16 输入在一次比较中相等，就认定 fp32 累加总能精确表示所有中间和。

**最后一条是最好的对照**：同样的验证代码，fp32 路径能测出非零误差，
说明测量方法本身是有效的，bf16 的 0 是真结果。
</details>

<details markdown="1">
<summary>6. 受控 tile 下 CuTe-DSL（210.8）比手写 CUDA（175.2）快 20%，是因为它生成了更好的指令吗？</summary>

不能这么归因，因为两者的**实现层次不同**，不只是指令选择的差别：

- 手写 CUDA 那一份是 L2.4 的 v6 阶梯：共享内存分块 + 寄存器分块 + padding，
  **没有** `cp.async`/TMA 的多级流水，也**没有** XOR swizzle。
- CuTe-DSL 的例程用 TMA 装载、多级流水、persistent tile scheduler。
  它的 PTX 是 `cp.async.bulk.tensor × 29`，SASS 里 23 条 `UTMA*` 与 256 条 `HMMA`。

两者的 mma 指令其实是同一族（`m16n8k16` 对应 SASS 的 `HMMA.16816`），
差距来自**搬运与流水**，不是计算指令。要判断"同一条流水下指令选择是否有差别"，
需要把两边都固定到同样的流水结构——本章没有做到这一步，
所以只能给出"这份实现比那份实现快"的结论，不能给出"DSL 的指令选择更好"的结论。
</details>

<details markdown="1">
<summary>7. TileLang 在本机开不到 128×256，而 Triton 可以，谁的上限说法是对的？</summary>

两个都不"错"，它们报的是**各自框架申请到的额度**：

- Triton 报 `Hardware limit: 101376`（99 KB）—— 这是未申请 opt-in 时的默认上限，
  它据此判断 458752 B 超限并拒绝编译。
- TileLang 在设置 `cudaFuncAttributeMaxDynamicSharedMemorySize` 时失败于 147456 B
  —— 说明它请求的额度低于 144 KB。

sm_120 通过 opt-in 实际可以到 227 KB（L1.1 的每 block 上限口径）。
所以"能不能开大 tile"是**框架有没有去申请**的函数。
要验证这一点，可以在同一个形状上显式调用
`cudaFuncSetAttribute(..., cudaFuncAttributeMaxDynamicSharedMemorySize, ...)`
再编译，看两个框架的上限是否都能提高。
</details>
