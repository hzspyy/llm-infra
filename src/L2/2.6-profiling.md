## 本章回答三个问题

1. 「这个 kernel 慢」——这句话要**翻译成哪个具体计数器**才算一个可回答的问题？
2. 为什么 `nsys` 能跑而 `ncu` 报 `ERR_NVGPUCTRPERM`？这两个工具读的是**不同性质的东西**，
   而那个差别是一条安全边界。
3. profiler 会带来多少额外开销？怎样避免把工具造成的延迟当成原程序的延迟？

L1.1、L2.3 和 L2.4 中的时间差提出了几个需要进一步核对的问题：跨步访问是否增加 bank conflict，向量化是否改变内存事务，GEMM 是否执行了 Tensor Core 指令。

本章结合时间线、反汇编和计数器检查这些问题。记录中的 crater 与 worldvln 缺少硬件计数器权限，spark 可采集 ncu 数据；容器身份本身不是能否采集的判据。没有计数器时可以先检查指令与时间线，但不能把推断当作直接观测；跨机器计数也不能替代原机器的时间归因。

先分清三类材料：时间线告诉你什么时候执行，计数器记录执行期间发生了多少事件，
反汇编展示程序里有哪些指令。它们回答的问题不同，需要结合使用。
本章会用计数器补充前面的计时解释，并保留哪些判断仍需要进一步验证。

## 机制拆解

### 一、`ERR_NVGPUCTRPERM`：完整诊断

这是 GPU profiling 最常撞的一堵墙。本机上 ncu 的原文：

```
==PROF== Connected to process 2355858 (/scratch/learn/results/prof/_smoke)
==ERROR== ERR_NVGPUCTRPERM - The user does not have permission to access
          NVIDIA GPU Performance Counters on the target device 0.
==PROF== Disconnected from process 2355858
```

**能不能读性能计数器，由两件事决定，任一满足即可**：

$$\text{允许} \iff \texttt{RmProfilingAdminOnly}=0 \;\lor\; (\text{有 CAP\_SYS\_ADMIN} \land \text{在宿主 user namespace})$$

所以要查三条证据。本机实测：

| 证据 | crater（容器） | worldvln（容器） | spark（裸机，改前） | spark（改后） |
|---|---|---|---|---|
| `RmProfilingAdminOnly` | 1 | 1 | 1 | **0** |
| `CapEff` 里的 `CAP_SYS_ADMIN` | **✗ 没有** | ✓ 有 | ✗（普通用户） | ✗ |
| `/proc/self/uid_map` | `0 0 4294967295`（未移位） | **`0 1000000 1000000000`（移位）** | 未移位 | 未移位 |
| 结果 | 拒绝 | 拒绝 | 拒绝 | **✓ 通过** |

**三台机器，同一个错误，三个不同的原因**：

- **crater**：就在宿主 namespace 里，但容器没给 `CAP_SYS_ADMIN`。
- **worldvln**：有 `CAP_SYS_ADMIN`，但处在 **UID 移位的 user namespace**
  （`uid_map` 第二列是 1000000）。容器里的 root 在宿主看来是 uid 1000000，
  这个 capability 只在容器自己的 namespace 里成立，**驱动按宿主 namespace 判定**，
  所以不算数。旁证：`/dev/nvidiactl` 的属主显示成 `nobody`。
- **spark**：裸机、未移位，但当前是普通用户 `smc`，`CapEff` 全 0。

::: warning 为什么驱动要锁这个
NVIDIA 从 2019 年起默认 `RmProfilingAdminOnly=1`，起因是 **CVE-2018-6260**：
SM 性能计数器是**全芯片共享**的资源，一个进程读它们能间接推断出**同时在跑的
其他进程**的访存模式——在多租户 GPU 上这是侧信道。
所以这不是"NVIDIA 懒得配"，是一个有意的安全边界。

**这也解释了为什么 nsys 不受影响**：CUPTI activity 只记录**你自己进程**的
kernel 起止时间戳，不读共享计数器。两个工具的权限差异，直接来自它们读的东西不同。
:::

**裸机上的权限配置示例**（spark 的已有配置）：

```bash
echo 'options nvidia NVreg_RestrictProfilingToAdminUsers=0' | sudo tee /etc/modprobe.d/nvidia-profiling.conf
sudo update-initramfs -u        # Ubuntu 上 nvidia 模块在 initramfs 里，不更新就不生效
sudo reboot
```

重启后 `awk '/RmProfilingAdminOnly/{print $2}' /proc/driver/nvidia/params` 应该是 `0`。
**这条 `update-initramfs` 很容易漏**——只写 modprobe.d 然后重启，会发现值还是 1。

**容器里没有对应解法**：`--privileged` 只解决 capability，
如果同时开了 user namespace 重映射（worldvln 那种），还得加 `--userns=host`。
两者都是宿主管理员的事。

### 二、profiler 怎么工作：两条完全不同的路径

**CUPTI Activity API**（nsys、torch.profiler 都走这条）：

驱动内部在每个 kernel 的 launch / begin / end 处写一条 activity record 到一个环形缓冲区，
应用退出或缓冲区满时批量回传。所以：

- 开销是**每条记录**的，不是每周期的 → kernel 越小越密，相对开销越大
- GPU 时间戳描述被观测运行中的执行区间，但采集也可能改变调度、重叠和运行状态
- 会拉长 launch 路径 → **CPU 侧和间隙会被放大**

这两条性质合起来就是本章最重要的方法论：
用 profiler 定位执行区间，再用不带 profiler 的运行测整体耗时。
不要默认两次运行的 GPU 忙时相同，也不要把两者相减直接视作真实空闲率。

**硬件性能计数器**（ncu）：

ncu 会把 kernel **重放多次**（replay），每次配置一组不同的计数器，
因为 SM 上能同时激活的计数器数量有限。所以 ncu 报告里的一次「kernel 执行」
其实是十几次真实执行的拼接。这带来两个后果：

- **很慢**（`--set full` 一个 kernel 要几秒）
- 默认每次 replay 前**刷 cache**（`--cache-control all`），所以它测的是**冷缓存**性能，
  和你在稳态循环里量到的数字**不是一回事**

### 三、观测者效应：量化

同一个 profiler，两种负载，本机实测：

| profiler 配置 | GEMM 主导 | 小 kernel 洪流 |
|---|---|---|
| 无 | 1.3729 ms | 0.3932 ms |
| `CUDA only` | 1.3774 ms  (1.00×) | 0.5517 ms  (**1.40×**) |
| `CPU+CUDA` | 1.3808 ms  (1.01×) | 0.6126 ms  (**1.56×**) |
| `+record_shapes` | 1.3809 ms  (1.01×) | 0.6256 ms  (1.59×) |
| `+with_stack +profile_memory` | 1.3832 ms  (1.01×) | 0.6592 ms  (**1.68×**) |

GEMM 负载 10 次迭代只有 30 个 kernel，每个几百微秒——profiler 的开销淹没在噪声里。
小 kernel 洪流是 120 个各几微秒的 kernel，**开销涨到 68%**。

**LLM decode 正是后者**：L0.1 实测 vLLM 一步 444 个 kernel。
所以在 decode 路径上用 profiler 读绝对延迟，会系统性地高估。

**观测工具带来的自指偏差。** 基于 trace 记录计算 GPU 空闲率：

```
[GEMM 主导]     40 个 GPU 事件, 跨度 13.708 ms, 忙 13.646 ms, 空闲  0.5%
[小 kernel 洪流] 360 个 GPU 事件, 跨度  1.924 ms, 忙  0.308 ms, 空闲 84.0%
```

需要注意的是，84.0% 是在启用 profiler 时的统计值。若将未开启 profiler 时的纯净墙钟时间作为基准进行推算：

```
推算修正：GPU 净忙时 0.103 ms/次（假设 kernel 本身计算耗时不变）
          纯净墙钟时间 0.394 ms/次  ->  推算空闲率 74.0%
```

推算值（74.0%）与带 profiler 实测值（84.0%）相差达 10 个百分点。这一差异直观展示了 profiler 自身开销对空闲率指标的拉伸效应。在评估小 kernel 密集场景的真实空闲水平时，必须对观测工具带来的时间线失真保持警惕。

### 四、静态分析能回答什么、不能回答什么

`cuobjdump -sass` 不用跑、不用特权，直接数指令。对 L2.3 的归约阶梯：

| kernel | 总指令 | LDG | LDS | STS | RED | SHFL | BAR | NOP |
|---|---|---|---|---|---|---|---|---|
| `red_v0` | 32 | 1 | 0 | 0 | 1 | 0 | 0 | 14 |
| `red_v1` | 56 | 1 | 3 | 2 | 1 | 0 | 2 | 13 |
| `red_v2` | 64 | 1 | 4 | 2 | 1 | **5** | 2 | 10 |
| `red_v3` | 72 | 1 | **1** | **1** | 1 | **10** | 1 | 13 |
| `red_v4` | 72 | 1 | 1 | 1 | 1 | 10 | 1 | 10 |
| `red_v5` | 88 | 1 | 1 | 1 | 1 | 10 | 1 | 11 |
| `red_v6` | 136 | **5** | 1 | 1 | 1 | 10 | 1 | 14 |

**阶梯的故事全在这张表里**：

- v1 引入共享内存树形归约 → `LDS` 3 / `STS` 2 / `BAR` 2
- v2 最后一个 warp 换 shuffle → `SHFL` 出现 5 条
- v3 全程 shuffle → `SHFL` 涨到 10，**`LDS` 从 4 掉到 1**（共享内存几乎不用了）
- v6 四个独立累加器 → **`LDG` 从 1 变成 5**（四路独立取数 + 一路）

**但这张表也标出了静态分析的边界。**
注意每一级都恰好只有 **1 条 `RED`**（全局原子加，SASS 里叫 `REDG.E.ADD.F32.FTZ.RN`）。
可是 v0 是**每个线程各执行一次**（6700 万次），
v1 及以后是**每个 block 只有 0 号线程执行一次**（26 万次）——差 256 倍。

**静态指令数是"这段代码里有几条指令"，不是"这次运行执行了几条指令"。**
后者只有动态 profiler（ncu 的 `smsp__inst_executed`）能给。

这条边界是本章的核心：**知道每把尺子量不到什么，和知道它能量什么一样重要。**

（顺带：v0 的 32 条指令里有 **14 条 `NOP`**。这是 SASS 的指令对齐填充，
Blackwell 的取指要求特定边界。所以「总指令数」这个量本身就要打折看。）

## 用计数器检查候选解释

以下全部在 **spark（GB10, sm_121, 裸机）** 上用 ncu 实测。
注意换了机器——GB10 是 Grace-Blackwell 的**统一内存**架构，绝对时间和 crater 不可比，
但**机制层面的计数器是可比的**，而机制正是要验的东西。

::: warning GB10 上没有 `dram__*` 计数器
`ncu --query-metrics | grep -c '^dram__'` 返回 **0**。

因为 GB10 的 GPU 和 CPU 共用一片 LPDDR5X，**没有独立的 GPU 显存分区**，
也就没有对应的显存控制器计数器。访存流量只能在 **L2（`lts__`）** 这一层看，
或者用综合指标 `gpu__compute_memory_throughput`。

**在讨论"显存带宽利用率"之前，先确认这块卡上存不存在"显存"这个东西。**
:::

### 推断一：bank conflict —— 从「慢 10 倍」到「冲突了 6,094,848 次」

在 L1.1 中对比两个不同跨步的 kernel（跨步 32 vs 跨步 33）时，测得 10.1× 的时间差异，
并将其归因为 bank conflict。然而**延迟恶化可能有多种硬件诱因**，仅凭耗时差异只能做出推断。

现在做一个只有下标算式不同的三元对照，读硬件计数器：

```cuda
__global__ void probe_stride1 (float* o) { probe_body<1> (o); }   // 相邻线程相邻 bank
__global__ void probe_stride32(float* o) { probe_body<32>(o); }   // 32 个线程全撞 bank 0
__global__ void probe_stride33(float* o) { probe_body<33>(o); }   // 错开一位
```

每个 kernel：48 block × 256 线程 × 64 轮 × 8 次共享内存读 = **6,291,456 次读**，
即 $6291456 / 32 = 196{,}608$ 次 warp 级请求。

| kernel | 耗时 ns | **bank 冲突** | smem 读 wavefront | **wavefront/请求** |
|---|---|---|---|---|
| `probe_stride1` | 7,392 | **0** | 196,608 | **1.00** |
| `probe_stride32` | 72,640 | **6,094,848** | 6,291,456 | **32.00** |
| `probe_stride33` | 9,280 | **0** | 196,608 | **1.00** |

**判据不是时间，是 `wavefront/请求` 这个比值。**
共享内存一次请求如果没有冲突，硬件用**一个 wavefront** 就能服务完；
$N$ 路冲突就要拆成 $N$ 个 wavefront 串行发。

- `stride32` 测出 **32.00**——教科书上的 32 路冲突，精确到小数点后两位
- 冲突次数 6,094,848 = $196{,}608 \times 31$（每个请求多出 31 个 wavefront）——**分毫不差**
- 跨步改成 33 之后回到 **1.00**，冲突归零

时间比 $72640/7392 = \mathbf{9.83\times}$，和 L1.1 纯靠计时得到的 10.1× 吻合。

**推断一：成立。** 而且现在它不再是推断——是一个能用算术核对的观测量。

### 推断二：向量化改善访存合并 —— 从 4 sector/请求 到 16

L2.3 的归约阶梯，全部七级的计数器：

| kernel | 耗时 ns | **全局读请求** | **sector/请求** | L2 sector | 占用率% | **动态指令(warp)** |
|---|---|---|---|---|---|---|
| `red_v0` | 104,313,248 | 2,097,152 | 4 | **75,685,621** | 78.88 | 35,651,584 |
| `red_v1` | 1,682,464 | 2,097,152 | 4 | 8,655,091 | 86.91 | **236,716,032** |
| `red_v2` | 1,704,416 | 2,097,152 | 4 | 8,655,011 | 80.63 | 101,187,584 |
| `red_v3` | 1,406,208 | 2,097,152 | 4 | 8,654,967 | 75.22 | 81,264,640 |
| `red_v4` | 1,319,936 | **524,288** | **16** | 8,458,439 | 93.96 | 21,889,024 |
| `red_v5` | 1,154,528 | 524,288 | 16 | 8,393,115 | 98.52 | 6,394,560 |
| `red_v6` | **1,102,816** | 524,288 | 16 | 8,391,856 | **100.00** | **4,466,112** |

从 v3 改为 v4 的 `float4` 访问后，两列计数发生变化：

- 全局读请求 2,097,152 → **524,288**（正好 $\div 4$）
- 每次请求覆盖的 sector 数 4 → **16**（一个 warp 一次拿 32×16B = 512 B = 16 个 32 B sector）

$2097152 = 67108864 / 32$，即**每个 warp 一次请求**；改成 `float4` 后
每个 warp 一次请求就取回四倍的数据。这就是「向量化」在硬件上的确切含义。

**注意 v0–v3 的 sector/请求 也是 4，不是更差的值。** 也就是说这几级**访存本来就是完美合并的**
（一个 warp 的 32 个连续 float = 128 B = 4 个 sector，一个都不浪费）。
所以 v0 慢，**根本不是合并的问题**——

**看 `L2 sector` 那一列**：v0 是 75,685,621，其余六级都是 ~8.4M。**9 倍的 L2 流量。**
那多出来的就是 6700 万次全局 `atomicAdd` 打在同一个地址上的读-改-写。

**推断二成立。** 而且计数器还**排除了一个竞争解释**：

L2.3 把 v0 的慢归因于「所有线程争抢同一个地址导致串行化」。
这个说法本身是对的，但当时无法排除另一种可能——v0 的访存模式是不是也有问题？
`sector/请求 = 4` 回答了这个问题：**v0 的读取是完美合并的，一个 sector 都没浪费。**

剩下的观察是 v0 有 9 倍的额外 L2 流量，与「大量原子操作打在同一地址」的解释一致。
需要说明的是，这几个计数器**支持**这个解释，但没有把全部运行时间量化地归到这一项上；
要做到那一步，需要 `--set full` 的 warp stall 分解（见原始现场 ⑦，
red_v0 的 `Issue Slots Busy` 只有 0.08%，说明 warp 几乎发不出指令）。

### 推断三：动态指令数 —— 静态表看不见的那一列

同一张表最右边一列，回答了上一节留下的问题：

```
red_v1  236,716,032        ← 共享内存树形归约，指令最多
red_v2  101,187,584
red_v3   81,264,640        ← 换成 shuffle
red_v4   21,889,024        ← float4
red_v5    6,394,560        ← grid-stride
red_v6    4,466,112        ← 独立累加器
```

**v1 → v6 少了 53 倍的指令。** 而静态 SASS 表里 v1 是 56 条、v6 是 136 条——
**静态看 v6 是 v1 的 2.4 倍，动态看 v6 是 v1 的 1/53。**

这是本章那条边界的最直接证据。静态指令数完全无法预测这个方向。

（`red_v0` 的 35,651,584 = $67108864/32 \times 17$：每个 warp 执行 17 条有效指令，
32 条静态指令里减掉 NOP 和被谓词关掉的部分。`smsp__inst_executed` 数的是
**warp 级**指令，不是线程级。）

### 推断四（L2.4）：tensor core 与 bank conflict

GEMM 阶梯的计数器：

| kernel | 耗时 ns | **HMMA 指令** | **bank 冲突** | 寄存器 | smem/blk | SM吞吐% | 占用率% |
|---|---|---|---|---|---|---|---|
| `gemm_v0` | 120,429,408 | 0 | 0 | 40 | 0 | 69.52 | **99.84** |
| `gemm_v1` | 83,651,136 | 0 | 0 | 38 | 8,192 | 68.96 | 66.66 |
| `gemm_v2` | 12,265,536 | 0 | **268,435,469** | 122 | 8,192 | 52.33 | 32.61 |
| `gemm_v3` | 10,752,064 | 0 | **269,766,172** | 109 | 8,192 | 57.19 | 32.81 |
| `gemm_v5` | 8,048,192 | **33,554,432** | **218,263,980** | 128 | 16,384 | 33.07 | 32.38 |
| `gemm_v6` | **4,884,832** | 33,554,432 | **10,515** | 128 | 18,944 | 32.46 | 32.50 |

**三个结论，全部是观测而非推断：**

**(1) tensor core 确实只在 v5/v6 用上了。** `HMMA 指令` 从 0 跳到 33,554,432。
$4096^3 / (16\times8\times16) = 33{,}554{,}432$——**正好是 `mma.m16n8k16` 所需的指令数**，
一条不多一条不少。L2.4 说"用上了 tensor core"，现在这句话有了确切的量。

**(2) v6 相对 v5 的 1.65× 加速，确实来自 padding 消除 bank conflict。**
bank 冲突 218,263,980 → **10,515**，降了 **两万倍**。
v6 与 v5 的唯一差别就是 `constexpr int LDA = BK + PAD`（`PAD=8`）。
**单变量，效果直接可见。**

**(3) v2/v3 有 2.7 亿次 bank 冲突，而且 v3 比 v2 还多一点。**
这是 L2.4 里**没说清楚**的地方：v3 做的是**全局访存**的 `float4` 向量化，
它压根没动共享内存的布局——所以共享内存冲突原封不动地留着。
如果当时就有计数器，v3 之后立刻加 padding 会是更好的下一步。

**(4) 占用率和性能反着走。** `gemm_v0` 占用率 **99.84%**，是全场最高，
也是全场最慢（比 v6 慢 **24.7 倍**）；`gemm_v6` 占用率只有 32.50%，最快。
`SM吞吐%` 也一样：v0 是 69.52%，v6 只有 32.46%。

**因为 v0 的 SM 忙着做无用功。** 占用率衡量的是"有多少 warp 在飞"，
不是"这些 warp 在干有价值的事"。v0 每个输出元素要重复读 4096 次 A 和 B，
SM 一直很忙，忙的全是重复访存。

::: warning 占用率不是优化目标
这张表是最干净的反例：**最高占用率 = 最慢**。

占用率只是**掩盖延迟的手段之一**。另一条路是提高每个线程的指令级并行
（ILP）——v6 的每线程 8×8 寄存器分块正是这么做的，代价是寄存器涨到 128、
占用率掉到 32%，但**总吞吐赢了 24.7 倍**。

要优化的是 `gpu__time_duration`，不是占用率。
:::

## 工程实现 · 源码解析：chrome trace 里到底有什么

`prof.export_chrome_trace()` 出来的 JSON，大多数人只是拖进 `chrome://tracing` 看看。
**打开它。** 顶层结构：

```json
{
  "schemaVersion": ..., "deviceProperties": [...],
  "cuda_driver_version": ..., "cuda_runtime_version": ..., "cupti_version": ...,
  "baseTimeNanoseconds": ..., "traceEvents": [ ... ]
}
```

326 个事件按 `cat` 分类：

```
ac2g            102     ← async CPU-to-GPU 流程箭头（把 launch 连到 kernel）
<无 cat>         60
cpu_op           60     ← aten 算子
cuda_runtime     42     ← cudaLaunchKernel 等 runtime 调用
kernel           40     ← 真正的 GPU kernel
cuda_driver      20     ← cuLaunchKernel
overhead          1     ← profiler 自己的开销，它诚实地记了一条
Trace             1
```

**单条 kernel 事件的 `args` 是个宝库**——这是一条原文：

```json
{
  "ph": "X", "cat": "kernel",
  "name": "void cutlass::Kernel2<cutlass_80_tensorop_bf16_s16816gemm_relu_bf16_128x64_64x3_nn_align8>(...)",
  "ts": 6043715623156.92, "dur": 633.534,
  "args": {
    "registers per thread": 154,
    "shared memory": 73728,
    "grid": [512, 8, 1], "block": [128, 1, 1],
    "occupancy": {
      "limitingFactors": "SMEM",
      "blockLimitRegs": 3, "blockLimitSharedMem": 0,
      "blockLimitWarps": 12, "blockLimitBlocks": 24,
      "allocatedRegistersPerBlock": 20480,
      "allocatedSharedMemPerBlock": 74752
    }
  }
}
```

下面区分三个问题：

**(1) `limitingFactors: "SMEM"`** —— torch.profiler 的导出字段提供了该 kernel 的占用率约束估计。
不需要 ncu。大多数人从来没打开过这个字段。

**(2) kernel 名字本身是完整的规格说明**：
`cutlass_80_tensorop_bf16_s16816gemm_relu_bf16_128x64_64x3_nn_align8`

| 片段 | 含义 |
|---|---|
| `cutlass_80` | 为 **sm_80（Ampere）** 编译的 CUTLASS kernel |
| `tensorop` | 走 tensor core |
| `s16816` | 用的是 `mma.m16n8k16`（L1.2 讲的 Ampere 那代指令）|
| `128x64_64x3` | threadblock tile 128×64，K-tile 64，**3 级流水**（`cp.async` 双/三缓冲）|
| `nn_align8` | 两个矩阵都不转置，8 元素对齐 |

**这个 kernel 是给 Ampere 编的，跑在 Blackwell（sm_120）上。**
它当然能跑（PTX 向前兼容），但它不会用 sm_120 的新指令。
这正是 L2.4 里「cuBLAS 218 TFLOPS 而纯发射上限 251」的一部分来源——
你用的往往不是为你这代卡专门调过的 kernel。

**(3) `"est. achieved occupancy %": 0` 与 `activeBlocksPerMultiprocessor: 0`
是错的**（`blockLimitSharedMem: 0` 也是）。PyTorch 的占用率模型里没有 sm_120 的
表项（100 KiB smem/SM），算出了 0。**原始字段（寄存器数、smem 字节、grid/block）是准的，
派生字段在全新架构上不可信。** 又一条：新卡上要分清哪些是测的、哪些是算的。

还有一个经典陷阱在 `key_averages()` 的表里：

```
                       Name    Self CPU %      Self CPU   ...
      cudaDeviceSynchronize        92.70%      13.407ms   ...
```

**排第一的「CPU 开销」是 `cudaDeviceSynchronize`，占 92.7%。**
它不是开销，它是**在等 GPU**。按 Self CPU 排序几乎总会把它排到第一，
然后你就会去优化一个根本不存在的问题。

### 引擎侧怎么 profile

**vLLM** 内置了 profiler 支持（`VLLM_TORCH_PROFILER_DIR` 环境变量），
因为 EngineCore 在**独立进程**里（L0.1 陷阱 5：在父进程开 profiler 抓不到任何 GPU 工作）。
设了这个变量之后，可以通过 `/start_profile`、`/stop_profile` 两个 HTTP 端点控制。

**SGLang** 同理，`SGLANG_TORCH_PROFILER_DIR` + `/start_profile`。

nsys 侧对应的开关是 `--target-processes all`——否则它只跟踪你直接启动的那个进程。
再配合 `--capture-range=cudaProfilerApi`，可以只抓 `torch.cuda.profiler.start()`
到 `stop()` 之间那一段，避开模型加载和 warm-up。

## 工程实现 · 自己写一遍：造一把尺子，然后拿 ncu 校准它

ncu 报告最核心的三个数字，不用任何特权都能自己算出来。
更重要的是：**造完之后要验它**——而 spark 上正好有 ncu 可以当标准件。

关键是两个特殊寄存器：

```cuda
__device__ __forceinline__ unsigned sm_id() {
    unsigned r; asm volatile("mov.u32 %0, %%smid;" : "=r"(r)); return r;
}
__device__ __forceinline__ unsigned long long gtimer() {
    unsigned long long r; asm volatile("mov.u64 %0, %%globaltimer;" : "=l"(r)); return r;
}
```

::: warning 必须用 `%globaltimer`，不能用 `clock64()`
`clock64()` 是**每个 SM 自己的**周期计数器。不同 SM 的计数器起点不同、
频率还会各自变。跨 SM 比较 `clock64()` 的值没有意义。

`%globaltimer` 是全芯片统一的**纳秒**计时器，正是为这种用途准备的。
（在 L1.1 中使用 `clock64()` 测量微架构延迟是有效的，因为那是同一个 SM 内同一线程的时间差值。）
:::

探针只让 0 号线程记录，代价是两条指令加一次 16 字节写：

```cuda
#define PROBE_BEGIN() \
    unsigned long long _t0 = gtimer(); unsigned _sm = sm_id();
#define PROBE_END(rec) \
    if (threadIdx.x == 0) { \
        BlockRec r; r.smid = _sm; r.block = blockIdx.x; \
        r.t_begin = _t0; r.t_end = gtimer(); (rec)[blockIdx.x] = r; }
```

拿到每个 block 的 `(SM, 起, 止)` 之后，**achieved occupancy 就是定义式本身**：
把每个 block 拆成 `(时刻, ±1)` 事件，按 SM 分组扫描，求时间加权的平均并发数。

```cpp
double area = 0;                 // ∫ 并发数 dt
for (每个 SM s) {
    sort(ev[s]);
    int cur = 0; auto prev = ev[s][0].first;
    for (auto& e : ev[s]) {
        area += double(cur) * double(e.first - prev);   // 上一段区间的贡献
        prev = e.first;
        cur += e.second;                                 // ±1
    }
}
achieved_blocks_per_sm = area / 总跨度 / 用到的 SM 数;
```

理论值这边直接问驱动，也不需要特权：

```cpp
cudaOccupancyMaxActiveBlocksPerMultiprocessor(&max_blocks, kernel, block_size, 0);
```

**实测结果（crater, 170 SM, 每 SM 48 warp, 100 KiB smem）**：

| 场景 | 理论 blocks/SM | 实测(时间加权) | 峰值观测 | 耗时 |
|---|---|---|---|---|
| balanced (grid=1360) | 6 (100%) | 4.18 (70%) | **6** | 0.149 ms |
| skewed (1/8 的 block 干 8 倍活) | 6 (100%) | 3.87 (65%) | 6 | 0.282 ms |
| smem_heavy (32 KiB/block) | **3 (50%)** | 2.65 (44%) | **3** | 0.144 ms |

**峰值观测精确等于理论值**（6 / 6 / 3）——自制的尺子和驱动的模型对上了。
而时间加权平均低于理论，差的就是启动爬坡和收尾的长尾。

`smem_heavy` 这一行是最干净的因果：唯一的变量是每个 block 申请 32 KiB 共享内存，
$\lfloor 100 / 32 \rfloor = 3$，占用率被砍到 50%——**和 L2.1 用 smem 调占用率的实验完全一致**。

### 用 ncu 校准自制的软件尺子

同样三个 kernel，在 spark 上分别用**自制软件探针**和 **ncu 的硬件计数器**测 achieved occupancy：

| kernel | 自制（`%smid`+`%globaltimer` 积分） | **ncu**（`sm__warps_active`） | 差 |
|---|---|---|---|
| `k_balanced` | 70% | **72.08%** | 2.1 pt |
| `k_skewed` | 65% | **65.99%** | 1.0 pt |
| `k_smem_heavy` | 44% | **44.11%** | **0.1 pt** |

**两种完全独立的方法，差不到 2 个百分点。**

- 自制探针方法：每个 block 记下 `(SM, 起, 止)`，在**软件层面**通过积分还原并发曲线
- ncu 硬件方法：直接读取 SM 内部的 `sm__warps_active` **硬件累加器**

它们唯一的共同点是被测对象。**这就是仪器校准。**
两者的微小差异源于软件探针仅在 block 首尾记录时间戳，无法捕获 block 内部各 warp 异步退出的细微时序。

ncu 还顺手给出了占用率**被谁卡住**：

```
k_balanced     限制: smem 16 / reg 16 / warp 6
k_smem_heavy   限制: smem  3 / reg 16 / warp 6      ← smem 成为瓶颈
```

`launch__occupancy_limit_warps = 6` 是因为每 SM 48 warp ÷ 每 block 8 warp = 6；
`k_smem_heavy` 的 `limit_shared_mem` 掉到 3，**smem 取代 warp 数成了绑定约束**。
和自制尺子测到的"理论 3 / 实测峰值 3"完全一致。

### 尾效应：多一个 block 的代价

用同一把尺子做一个单变量实验。一个满波 = 6 blocks/SM × 170 SM = **1020 blocks**。

| grid | 耗时 | SM 忙碌时间 最大/最小 | 末 10% 的并发度 |
|---|---|---|---|
| 1020（整波） | 0.109 ms | 1.01 | 25% |
| **1021（多一个）** | **0.126 ms** | **1.21** | **0%** |

**多一个 block，慢 16%。**

因为第 1021 个 block 必须等某个 SM 空出槽位才能开始，
而它一个人跑的时候，另外 169 个 SM **全在空转**——
所以末 10% 的并发度直接掉到 0，SM 之间的忙碌时间也从均衡（1.01）裂成 1.21。

这就是 L1.1 提到的 wave quantization，现在它被自制的 profiler 直接量出来了。

### 一个负面结果：块级负载倾斜，硬件自己扛住了

`skewed` 那一行让 1/8 的 block 干 8 倍的活，总工作量变成 $\frac{1}{8}\times 8 + \frac{7}{8} = 1.875$ 倍。
实测耗时 0.149 → 0.282 ms，正好 **1.89 倍**。而 SM 忙碌时间的最大/最小只有 **1.02**。

**GPU 的块调度器把重块摊得几乎完美。** 只要 block 数远多于槽位数，
块级的负载倾斜基本不需要你操心——这和 CPU 上的静态分区完全不同。
（真正会出问题的是 **warp 内**的分支发散，那是 L2.1 的话题；
以及 block 数少于槽位数时——那就退化成上面的尾效应。）

<summary>⑧ 一个负面结果：<code>--cache-control</code> 在流式 kernel 上没有区别</summary>

ncu 默认 `--cache-control all`（每次 replay 前刷 cache），
所以常被提醒"它测的是冷缓存"。实测：

```
    --cache-control=all   red_v6 耗时    1,062,528 ns   L2 sector      8,395,076
    --cache-control=none  red_v6 耗时    1,071,136 ns   L2 sector      8,394,661
```

**差 0.8%，在噪声里。**

因为 `red_v6` 要读 256 MB，远超任何一级 cache——刷不刷都一样，
每个 sector 反正都得从内存来一次（L2 sector 数几乎完全相同，佐证了这一点）。

**所以这条"陷阱"是有条件的**：它只在**工作集能装进 cache** 的 kernel 上才咬人
（比如小矩阵 GEMM、attention 的单个 tile、embedding 查表）。
流式的 memory-bound kernel 不受影响。

**把一条听来的注意事项在自己的负载上验一遍，才知道它对你适不适用。**

## 陷阱

**1. 按 `Self CPU` 排序读 `key_averages()`。**
`cudaDeviceSynchronize` 会稳居第一（本机 92.7%），但它是在等 GPU，不是开销。
**按 `Self CUDA` 排。**

**2. 拿 profiler 里的 wall-clock 当性能结论。**
小 kernel 密集的负载上，profiler 本身就是 1.4–1.68× 的税（本机实测）。
**GPU busy 时间可信，墙钟和空闲率要用干净计时校正。**

**3. 在父进程开 profiler 去抓 vLLM。**
EngineCore 在独立进程里，抓到 0 个 kernel（L0.1 陷阱 5）。
要么 `VLLM_ENABLE_V1_MULTIPROCESSING=0`，要么用 `VLLM_TORCH_PROFILER_DIR` +
`nsys --target-processes all`。

**4. 相信新架构上的派生字段。**
本机 `est. achieved occupancy % = 0`、`blockLimitSharedMem = 0` 都是错的，
因为 PyTorch 的占用率模型没有 sm_120 的表项。**原始字段准，派生字段要交叉验证。**

**5. 把 ncu 的数字直接和稳态循环里的数字比。**
ncu 默认 `--cache-control all`，每次 replay 前刷 cache，测的是**冷缓存**。
要比就加 `--cache-control none`，并且用 `--clock-control base` 锁频
（否则 boost 频率漂移会污染跨 kernel 的比较——L1.2 踩过）。
**但先验一下这条对你的负载成不成立**：本章实测流式 kernel 上两者只差 0.8%（见原始现场 ⑧）。

**5b. 把占用率当优化目标。**
本章 GEMM 阶梯里**占用率最高的 v0 是最慢的**（99.84%，比 32.5% 的 v6 慢 24.7 倍）。
占用率只是掩盖延迟的手段之一，另一条路是提高 ILP，而它和占用率此消彼长。
**要优化的是耗时。**

**6. 用 `clock64()` 做跨 SM 的时间比较。**
它是每个 SM 自己的计数器。要跨 SM 就用 `%globaltimer`。

**7. 把静态指令数当动态执行次数。**
本章的 SASS 表里每一级都只有 1 条 `RED`，但 v0 执行了 6700 万次、v1 执行了 26 万次。
**静态分析回答「有什么」，不回答「跑了多少次」。**

**8. 忘了先查正确性。**
很多「性能问题」其实是越界写或竞态导致的重算/重试。
`compute-sanitizer` 零特权、几秒钟，**应该排在 profiler 前面。**

**9. 假设每块卡都有 `dram__*` 计数器。**
GB10（Grace-Blackwell 统一内存）上 `ncu --query-metrics | grep -c '^dram__'` 返回 **0**——
它根本没有独立的 GPU 显存分区。**先查 metric 存不存在，再写脚本**，
否则 ncu 会安静地返回 `n/a`，你还以为是 0。

**10. 用 `--launch-count N` 想抓齐所有 kernel。**
它按 **launch 顺序**抓前 N 次，而不是每种 kernel 各一次。
一个跑七级阶梯的程序，`-c 7` 抓到的可能全是第一级的七次重复。
要按 kernel 抓就 `-k "regex:^名字$" -c 1` 逐个来（`ncu_ladder.sh` 的 `collect()` 就是这么写的）。
顺带：模板实例在 `--kernel-name-base function` 下都显示成 `probe<...>`，
正则分不开，**得给它们不同的函数名**。

## 自测题

<details markdown="1">
<summary>1. 同事说「我在容器里跑 ncu 报 ERR_NVGPUCTRPERM，加 --privileged 就好了吧？」——对吗？</summary>

**不一定，要看是哪个原因。** 判据是：

$$\text{允许} \iff \texttt{RmProfilingAdminOnly}=0 \;\lor\; (\text{CAP\_SYS\_ADMIN} \land \text{宿主 user namespace})$$

`--privileged` 给的是 **capability**，解决的是第二项的前半。
但如果容器同时启用了 **user namespace 重映射**（`/proc/self/uid_map`
第二列非 0），那么这个 capability 只在容器内部成立，驱动按宿主 namespace 判定，
**加了 `--privileged` 依然被拒**。

本章的两台机器恰好是两种情况：

| | crater | worldvln |
|---|---|---|
| `CAP_SYS_ADMIN` | ✗ | **✓** |
| `uid_map` 移位 | ✗ | **✓** |
| 加 `--privileged` 能解决吗 | **能** | **不能**，还要 `--userns=host` |

**三条都要查**：`grep RmProfilingAdminOnly /proc/driver/nvidia/params`、
`grep CapEff /proc/self/status`、`cat /proc/self/uid_map`。
</details>

<details markdown="1">
<summary>2. 我的 trace 显示 GPU 空闲 84%。可以直接汇报「这是 launch-bound」吗？</summary>

**结论方向对，但那个数字不能直接汇报。**

这个 84% 是**在 profiler 底下**测的，而 profiler 对小 kernel 洪流有 1.4–1.68× 的开销
（本机实测）。开销全部落在 CPU 侧的 launch 路径上——**恰好就是产生这些缝的地方**。

正确的做法是用一个不受 profiler 影响的量做校正：**GPU busy 时间**。
kernel 在 GPU 上跑多久不因为被观测而改变。

```
profiler 下：跨度 1.924 ms, GPU 忙 0.308 ms  →  空闲 84.0%
干净墙钟：  0.394 ms/次, GPU 忙 0.103 ms/次 →  空闲 74.0%
```

**汇报 74%。** 结论不变（重度 launch-bound，该上 CUDA Graph），
但你没有把自己的观测开销算进被观测对象的账上。

**推广**：任何用 profiler 时间轴算出来的「比例」，
都要问一句这个比例的分母有没有被 profiler 撑大。
</details>

<details markdown="1">
<summary>3. 我只能拿到 <code>cuobjdump -sass</code>，能判断两个 kernel 谁更快吗？</summary>

**基本不能。** 静态指令数回答「代码里有什么」，不回答「执行了多少次」。

本章的表就是反例：`red_v0` 只有 32 条指令，`red_v6` 有 136 条——
但 v0 慢 **521 倍**。因为：

- v0 的那 1 条 `REDG`（全局原子加）被 **6700 万个线程各执行一次**
- v6 的 136 条指令被每个线程执行一次，但只有 26 万个 block 各做一次原子加

**静态分析能可靠回答的是「有没有」类的问题**：

- 有没有用上 tensor core（找 `HMMA` / `IMMA`）
- 有没有向量化访存（`LDG.E.128` vs `LDG.E`）
- 有没有寄存器溢出（找 `LDL` / `STL`，local memory 的读写）
- 用了共享内存还是 shuffle（`LDS`/`STS` vs `SHFL`）
- 谓词化了还是真分支（`@P0` 前缀 vs `BRA`）

**要比快慢，还是得跑。** 而且要注意 SASS 里的 `NOP`——
本例 v0 的 32 条里有 14 条是对齐填充，占 44%。

本章的 ncu 实测给了这条边界最直接的证据：

| | 静态指令数 | **动态执行指令数** |
|---|---|---|
| `red_v1` | 56 | **236,716,032** |
| `red_v6` | 136 | **4,466,112** |

**静态看 v6 是 v1 的 2.4 倍，动态看 v6 是 v1 的 1/53。方向完全相反。**
</details>

<details markdown="1">
<summary>3b. 怎么判断共享内存的访问模式有几路 bank conflict？看哪个指标？</summary>

**看 `wavefront / request` 的比值**，不是看时间。

```
l1tex__data_pipe_lsu_wavefronts_mem_shared_op_ld.sum   ÷  请求数
```

共享内存一次 warp 级请求，如果 32 个 lane 落在 32 个不同 bank 上，
硬件用**一个 wavefront** 就能服务完。有 $N$ 路冲突就要拆成 $N$ 个 wavefront 串行发。
**所以这个比值直接就是冲突路数。**

本章实测（6,291,456 次读 = 196,608 次请求）：

| 跨步 | wavefront | **比值** | `bank_conflicts` 计数器 |
|---|---|---|---|
| 1 | 196,608 | **1.00** | 0 |
| 32 | 6,291,456 | **32.00** | 6,094,848 |
| 33 | 196,608 | **1.00** | 0 |

两个指标是自洽的：$6{,}094{,}848 = 196{,}608 \times 31$
（冲突计数器数的是**额外**的 wavefront 数，所以是 $N-1$ 倍）。

**为什么跨步 33 就没事**：共享内存有 32 个 bank，
地址 $a$ 落在 bank $(a / 4) \bmod 32$。跨步 32 时线程 $i$ 访问
$32i$，$\text{bank} = 32i \bmod 32 = 0$——**全撞在 bank 0**。
跨步 33 时 $\text{bank} = 33i \bmod 32 = i \bmod 32$——**正好每个 bank 一个**。

**判据：跨步只要是 32 的倍数就全冲突；只要与 32 互质就完全无冲突。**
所以 padding 加 1 就够，加 8（如 `gemm_v6`）是为了同时照顾 128 位向量访问的对齐。
</details>

<details markdown="1">
<summary>4. 我要给一个 4096 tokens 的 prefill 做 profiling，从哪一步开始？</summary>

**按分辨率从粗到细，每一层先排除掉再往下走。**

**第 0 步：先查正确性。** `compute-sanitizer --tool memcheck`，几秒钟。
越界写会导致重算和奇怪的性能表现。

**第 1 步：分相位。** prefill 和 decode 的瓶颈完全不同（L5.1）。
先用自己的埋点确认时间花在哪个相位，别一上来就 profile 整个请求。

**第 2 步：算 roofline 下界。** 用 L0.2 的账本算出这个 prefill 的
FLOP 和访存量，得到理论下界。**如果实测已经在下界的 80%，profiling 到此为止**——
剩下的空间要靠换算法（量化、稀疏），不是靠调 kernel。

**第 3 步：kernel 成分表。** `torch.profiler`，按 `Self CUDA` 排序。
prefill 应该是 GEMM 主导（本机 MLP 实测 94.9% 在 GEMM 上）。
如果不是，说明有非预期的开销。

**第 4 步：看时间轴的缝。** 算 GPU 空闲率（记得做第 2 题的校正）。
prefill 的 kernel 都很大，空闲率应该在个位数。
高了就是 launch-bound，上 CUDA Graph。

**第 5 步（要 ncu）：单 kernel 深挖。** 只有走到这一步才需要特权。
而且到这时候你已经知道该挖哪一个 kernel 了——
**这正是前四步的价值：把「慢」收敛成一个具体到能用计数器回答的问题。**

顺带：`args.occupancy.limitingFactors` 在第 3 步就能免费拿到，
很多占用率问题不用等到第 5 步。
</details>

<details markdown="1">
<summary>5. 为什么 nsys 能跑而 ncu 不能？这个差异说明了什么更一般的事？</summary>

**因为它们读的是两种不同性质的东西。**

- **nsys / torch.profiler** 走 CUPTI Activity：驱动在你自己进程的每个 kernel
  起止处打时间戳，事后批量回传。**只涉及你自己的事件**，所以不需要特权。
- **ncu** 直接读 SM 上的硬件性能计数器。这些计数器是**全芯片共享**的，
  一个进程读它们能间接推断出**同时在跑的其他进程**的访存模式。
  这是 CVE-2018-6260 报告的侧信道，所以 2019 年起驱动默认锁死。

硬件计数器还受到系统安全策略的限制。

同样的模式在别处反复出现：

- Linux 的 `perf_event_paranoid`：读 CPU PMU 计数器同样是侧信道，同样默认限制
- 浏览器把 `performance.now()` 的精度从纳秒降到 100 µs：Spectre 之后的缓解
- 云上的 GPU 实例通常不开性能计数器：多租户

在多租户或容器环境中，应先确认计数器权限，再设计实验。`profile_ladder.sh` 第 0 节提供了相应诊断。
</details>

<details markdown="1">
<summary>6. 我的 kernel 占用率只有 32%，同事说太低了要调。该听吗？</summary>

**先问：耗时是多少？占用率不是优化目标。**

GEMM 阶梯中的对照如下：

| | 占用率 | SM 吞吐 | **耗时** |
|---|---|---|---|
| `gemm_v0`（naive） | **99.84%** | 69.52% | 120.4 ms |
| `gemm_v6`（最优） | **32.50%** | 32.46% | **4.88 ms** |

**占用率最高的那个慢 24.7 倍**，而且 `SM 吞吐` 也是它更高——
因为它的 SM 忙着做无用功（每个输出元素重复读 4096 次 A 和 B）。

**占用率的作用是掩盖延迟**：一个 warp 卡在等访存时，
换另一个 warp 上来发指令。但这不是唯一的办法——
**提高单线程的指令级并行（ILP）同样能掩盖延迟**，而且更便宜。

`gemm_v6` 走的就是 ILP 路线：每线程算 8×8 个输出，
手里同时有 64 个独立的累加，一条访存指令的延迟被 64 条乘加盖住了。
代价是寄存器涨到 128、每 SM 装不下那么多 block、占用率掉到 32%。
**这是有意的取舍，不是缺陷。**

**该调占用率的信号**是：ncu 的 `Warp State Statistics` 显示大量
`stalled_long_scoreboard`（等访存）**并且**每个 warp 的 ILP 已经榨干了。
光看占用率数字本身，什么都说明不了。

（`gemm_v0` 还给了另一个警示：`SM 吞吐 69.52%` 看起来很健康。
**吞吐率高只说明流水线在动，不说明它在做有用的事。**）
</details>
