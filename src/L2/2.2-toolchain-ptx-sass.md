## 本章回答三个问题

1. `nvcc a.cu -o a` 这一行命令，实际调用了**哪些程序**、产生了**哪些中间文件**？
2. PTX 和 SASS 到底差在哪？`sm_120` / `sm_120a` / `sm_120f` 三个目标有什么区别？
3. **`__launch_bounds__` 能让占用率翻 4 倍——但代价是多少？**

本章跟踪一份 CUDA 源文件如何成为可执行程序。
PTX 是面向虚拟指令集的中间表示，SASS 是针对具体 GPU 的机器指令。
编译器还负责把变量分配到有限的寄存器；放不下时，一部分变量可能转存到内存。
后面的例子会展示这种寄存器溢出（spill），以及为什么占用率提高后程序反而可能变慢。

## 机制拆解

### 八个程序在接力

`nvcc --dryrun` 会打印它准备执行的每一条命令而不真的执行。抓出来是：

```
gcc -E        预处理（宿主代码路径）
cudafe++      把 .cu 拆成"宿主部分"与"设备部分"
gcc -E        预处理（设备代码路径）
cicc          NVVM 编译器：设备代码 → PTX      ← 属于 nvidia-nvvm 包
ptxas         PTX → SASS（cubin）              ← 属于 nvidia-cuda-nvcc 包
fatbinary     把多个架构的 cubin + PTX 打包成 fatbin
gcc           把 fatbin 嵌进宿主目标文件
```

**`cicc` 与 `ptxas` 属于两个不同的 pip 包** —— 这正是 L0.1 陷阱一节里那个
`Unsupported .version 9.3` 的根源：只钉 `nvidia-cuda-nvcc` 换掉了 ptxas，
`cicc` 还是旧版本，产出的 PTX ISA 版本对不上。

### 中间产物：源码 810 字节，预处理后 1.43 MB

`--keep` 会保留所有中间文件：

| 文件 | 大小 | 是什么 |
|---|---|---|
| `demo.cu` | 810 B | 你写的源码 |
| `demo.cpp1.ii` | **1 426 606 B** | 预处理后（**膨胀 1761 倍**） |
| `demo.cudafe1.gpu` | 8 074 B | 拆分出的设备代码 |
| `demo.ptx` | 3 165 B | 虚拟 ISA，文本 |
| `demo.sm_120.cubin` | 7 248 B | 真实机器码 ELF |
| `demo.fatbin` | 8 192 B | cubin + PTX 打包 |
| `demo.o` | 13 680 B | 最终目标文件 |

预处理后体积增加 **1761 倍**，说明头文件处理是编译成本的一项：一个 `#include <cuda_runtime.h>`
带进来 1.4 MB 的头文件，每个 `.cu` 都要重新处理一遍。
这也是 CuTe-DSL 宣称"编译比 C++ CUTLASS 模板快 20–30×"的部分原因（L2.5）——
它跳过了整个 C++ 前端。

### PTX：虚拟 ISA，无限寄存器

```ptx
//
// Generated by NVIDIA NVVM Compiler
// Cuda compilation tools, release 13.0, V13.0.88
// Based on NVVM 20.0.0
//
.version 9.0
.target sm_120
.address_size 64

	// .globl	_Z11reduce_tileILi256EEvPKfPfi
// _ZZ11reduce_tileILi256EEvPKfPfiE1s has been demoted

.visible .entry _Z11reduce_tileILi256EEvPKfPfi(
	.param .u64 .ptr .align 1 _Z11reduce_tileILi256EEvPKfPfi_param_0,
	...
```

四点值得看：

- **`.version 9.0`** 是 **PTX ISA 版本**，`.target sm_120` 是目标架构。两者独立。
  L0.1 的失败就是 `.version` 不匹配（9.3 的 PTX 喂给只认 9.0 的 ptxas）。
- **`_Z11reduce_tileILi256EEvPKfPfi`** 是 C++ name mangling。`c++filt` 还原：
  `void reduce_tile<256>(float const*, float*, int)`。
  **模板参数被编码进符号名** —— 所以 L0.1 里能从 kernel 名读出
  `Flash_fwd_kernel_traits<128, 64, 128, 4>` 的全部 tile 尺寸。
- **`has been demoted`** 说的是共享内存变量被降级为局部符号。
- PTX 用的是**无限虚拟寄存器**（`%r1`, `%r2`, …）。真正的寄存器分配是 ptxas 干的。

归约循环在 PTX 里长这样：

```ptx
46:	st.shared.f32 	[%r4], %f29;
47:	bar.sync 	0;
50:	ld.shared.f32 	%f4, [%r4+512];
51:	ld.shared.f32 	%f5, [%r4];
52:	add.f32 	%f6, %f4, %f5;
53:	st.shared.f32 	[%r4], %f6;
```

清晰对应源码里的 `s[t] += s[t + stride]; __syncthreads();`。

### SASS：真实机器码

同一段在 SASS 里：

```
/*0000*/  LDC R1, c[0x0][0x37c] ;                   /* 0x0000df00ff017b82 */
/*0010*/  S2R R6, SR_TID.X ;                        /* 0x0000000000067919 */
/*0020*/  LDCU UR4, c[0x0][0x390] ;                 /* 0x00007200ff0477ac */
/*0030*/  HFMA2 R0, -RZ, RZ, 0, 0 ;                 /* 0x00000000ff007431 */
/*0040*/  S2R R9, SR_CTAID.X ;                      /* 0x0000000000097919 */
/*0060*/  LEA R5, R9, R6, 0x8 ;                     /* 0x0000000609057211 */
/*0070*/  ISETP.GE.AND P0, PT, R5, UR4, PT ;        /* 0x0000000405007c0c */
/*0080*/  @!P0 LDC.64 R2, c[0x0][0x380] ;           /* 0x0000e000ff028b82 */
/*00a0*/  @!P0 LDG.E.CONSTANT R0, desc[UR6][R2.64] ;/* 0x0000000602008981 */
/*0110*/  STS [R5], R0 ;                            /* 0x0000000005007388 */
```

指令统计（本 kernel 共 80 条）：

```
17 LDS    共享内存读     ← 归约循环的主体
 9 STS    共享内存写
 9 ISETP  整数比较置谓词
 9 BAR    barrier（__syncthreads）
 8 NOP
 8 FADD   浮点加         ← 真正的"计算"只有 8 条
 3 LDC / 2 S2R / 2 LEA / 2 LDCU
```

**一个"归约" kernel 里，真正的算术只有 8 条 `FADD`，而访存与同步有 35 条。**
这些静态指令计数展示了访存与同步结构，但不能单独判定运行时瓶颈——L2.3 会专门优化它。

几个 SASS 特有的东西（PTX 里没有）：

- **`@!P0`**：谓词执行。L2.1 讲的 predication，在这里是实物。
- **`UR4` / `URZ`**：uniform register（Turing 起引入）。整个 warp 共享同一个值时用它，
  省下常规寄存器和指令带宽。
- **`.reuse` 标志**：告诉硬件这个操作数下一条指令还要用，留在 operand reuse cache 里。
- **`c[0x0][0x37c]`**：constant bank 0。kernel 参数、grid 维度都放在这里，
  由 driver 在 launch 时填好——这是 L1.4 那 2.68 µs launch 开销的一部分去处。
- **右边的 `/* 0x... */`** 是指令的二进制编码。

### `sm_120` / `sm_120a` / `sm_120f`：三个目标

| 目标 | 含义 | 目标文件大小 | 能在哪跑 |
|---|---|---|---|
| `sm_120` | 只用通用指令 | 13 704 B | sm_120 及未来兼容架构 |
| `sm_120a` | **architecture-specific**，允许该架构独有指令 | 14 536 B | **只有 sm_120** |
| `sm_120f` | **family-specific**，sm_12x 全家族 | 14 536 B | sm_120 / 121 / … |

L0.1 原始现场 ⑤ 里，Triton 生成的 PTX 是 `.target sm_120a`（架构专属），
而 FlashInfer 的 JIT 缓存目录叫 `120f`（家族兼容）。
**库作者要在"用尽硬件"与"一份二进制覆盖更多卡"之间选。**

多架构 fatbin（同时装 sm_80 / sm_89 / sm_120）：

```
多架构 fatbin: 22 872 字节（单架构 14 536）
  含 cubin: sm_80 sm_89 sm_120
```

这就是 PyTorch 的 `.so` 动辄几百 MB 的原因——每个 kernel 都要为
Volta 到 Blackwell 的每一代各编一份。

### `-O` 级别：主要影响的是指令数

| `-O` | 寄存器 | SASS 指令数 | smem |
|---|---|---|---|
| `-O0` | 16 | **176** | 1024 |
| `-O1` | 12 | **88** | 1024 |
| `-O2` | 12 | 80 | 1024 |
| `-O3` | 12 | 80 | 1024 |

**`-O0` → `-O1` 指令数减半**，之后基本饱和。注意 `nvcc -O3` 只控制宿主代码，
设备代码要用 `-Xptxas -O3` 才生效（本实验两个都给了）。

### `__launch_bounds__`：寄存器预算与运行时间

`__launch_bounds__(N)` 告诉编译器"这个 kernel 最多用 N 个线程/block"，
ptxas 会据此**限制寄存器用量**，使得 $N$ 个线程能同时驻留：

$$\text{每线程寄存器上限} = \frac{65536}{N}$$

用一个刻意制造寄存器压力的 kernel（160 个交叉依赖的活跃变量）实测：

```
kernel                          寄存器    栈帧B  spill存B  spill取B  每SM线程上限
heavy<64,  256>                   80        0        0        0        819
heavy<128, 256>                  254        0        0        0        258
heavy<128, 512>                  128      248      396      412        512   ← 开始溢出
heavy<128, 1024>                  64     1264     2796     2920       1024   ← 大量溢出
heavy<200, 1024>                  64     1672     4680     4848       1024
```

同一个 kernel（N=128），只改 `__launch_bounds__`：
- `256` → 254 个寄存器，**不溢出**
- `512` → 128 个寄存器，溢出 396 字节
- `1024` → 64 个寄存器，**溢出 2796 字节**

然后测实际耗时（**三者都用 256 线程启动，工作量完全相同**）：

| `__launch_bounds__` | 寄存器 | spill | 驻留 block/SM | 耗时 |
|---|---|---|---|---|
| 256 | 254 | 0 B | 1 | **0.012 ms** |
| 512 | 128 | 396 B | 2 | 0.025 ms（1.98×） |
| 1024 | 64 | 2796 B | 4 | **0.286 ms（23.03×）** |

**占用率提高 4 倍，实际速度慢了 23 倍。**

溢出的变量可能存入 local memory。它由设备内存支持，但访问也可能命中缓存，
不能给每次访问都套用 L1.1 的显存延迟。应先检查 spill 指令是否位于热循环，
再结合缓存与访存计数器判断代价。

::: warning 不要只按占用率选择参数
L2.1 说"占用率是手段不是目标"，本章给出了量化：
**为了占用率牺牲寄存器，可能换来 23 倍的减速。**

`__launch_bounds__` 的正确用途是**告诉编译器你确实需要那个 block 大小**
（比如 kernel 里有 `__syncthreads` 且逻辑依赖 1024 线程），
它也可以用于调优，但需要同时检查寄存器溢出与总运行时间，
不能把占用率变高本身当成优化成功。

诊断方法：`-Xptxas -v` 里 `spill stores` 一旦不为 0 就要警惕，
超过几百字节且在内循环里，基本可以断定是灾难。
:::

## 工程实现 · 源码走读：真实世界的两种代码生成

### 1. 静态 fatbin：CUTLASS 的路子

L0.1 的 trace 显示 vLLM 的 bf16 GEMM 是
`cutlass_80_tensorop_bf16_s16816gemm_relu_bf16_128x64_64x3_nn_align8`。
这是**编译期实例化**的模板，静态打进 `.so` 的 fatbin 里。

从名字能读出全部配置：`80`=sm_80 血统，`s16816`=`m16n8k16` 指令，
`128x64_64`=tile 尺寸，`x3`=3 段流水，`nn`=两个矩阵都不转置，`align8`=8 元素对齐。

代价是**组合爆炸**：每种 dtype × tile × 布局 × 架构都要单独实例化。
`libcublasLt.so` 里光 sm_120 就有 **1596 个 cubin**（实测 `cuobjdump -lelf`）：

```
1596 sm_120
1376 sm_90a
1187 sm_100
 482 sm_80
 247 sm_89
```

### 2. 运行时 JIT：`nvjet` 的路子

同一次 profile 里，**fp8** GEMM 的 kernel 名是：

```
nvjet_sm120_qqtst_mma_64x256x64_4_64x64x64_tmaAB_bz_TNNN
```

`nvjet` 是 cuBLASLt 的 **JIT 引擎**。用 `cuobjdump` 在 `.so` 里找这个符号：

```
$ strings libcublasLt.so.13 | grep -c "nvjet_sm120"
0
$ cuobjdump -sass -fun nvjet_sm120_qqtst_... libcublasLt.so.13
cuobjdump warning : Function listed in --function '...' not found
```

**它根本不在 `.so` 里 —— 是运行时生成的。**

这解释了 L1.2 留下的开放问题：我测的 `mma.sync.m16n8k32` 只有 1022 FLOP/clk/SM，
而 cuBLAS 的 fp8 达到 1501。因为 cuBLAS 走的是 `nvjet` 生成的、
用了 **TMA**（名字里的 `tmaAB`）的另一条路径，而不是我手写的那条。

::: note 名字里的信息量
`nvjet_sm120_qqtst_mma_64x256x64_4_64x64x64_tmaAB_bz_TNNN` 拆开：
`sm120` 架构 · `qq` 输入都是 quarter precision(fp8) · `tst` 输出/累加类型 ·
`64x256x64` 线程块 tile · `4` 流水级数 · `64x64x64` warp tile ·
`tmaAB` A 和 B 都用 TMA 搬运 · `bz` 沿 K 分块 · `TNNN` 转置组合。

**C++ 模板实例化名与 JIT kernel 名，都是最省事的性能线索。**
不用读源码就能知道 tile 尺寸、精度、搬运方式。
:::

### 3. Triton：第三种路子

L0.1 原始现场 ⑧ 展示过 Triton 的缓存目录：源码哈希 → 一个目录，
里面有 `.ttir/.ttgir/.llir/.ptx/.cubin` 五份产物。
它既不是静态 fatbin，也不是 cuBLAS 那种闭源 JIT，
而是**用户可见的、每一跳都落盘的 JIT**。L2.5 会对比这三条路。

## 工程实现 · 自己写一遍

`labs/L2/toolchain_tour.sh` 把每一跳都留下产物。三个要点：

**(1) `--dryrun` 看流水线，`--keep` 留产物**

```bash
nvcc -arch=sm_120 -O3 -c demo.cu -o demo.o --dryrun        # 只打印不执行
nvcc -arch=sm_120 -O3 -c demo.cu -o demo.o --keep --keep-dir .
```

**(2) `-Xptxas -v` 的四个数字要成表看**

`labs/L2/parse_ptxas.py` 把它解析成表并自动算出每 SM 线程上限：

```python
REG_FILE = 65536          # 每 SM 的 32 位寄存器数（Blackwell 消费级）

for b in re.split(r"ptxas info\s+: Compiling entry function ", txt)[1:]:
    reg = re.search(r"Used (\d+) registers", b)
    ss  = re.search(r"(\d+) bytes spill stores", b)
    warn = "   ← 溢出到 local memory（显存！）" if ss and int(ss.group(1)) > 0 else ""
    print(..., REG_FILE // int(reg.group(1)), warn)
```

**这个脚本应该成为你每次写 kernel 的标配。** spill 不为 0 就停下来查。

**(3) 逼出寄存器压力要制造交叉依赖**

第一版实验用 `a[k] = fmaf(a[k], b, c)`（每个元素独立），
编译器把循环融合掉了：每个 `a[k]` 载入、算完、丢弃，**从不同时活跃 160 个**，
所以怎么调 `__launch_bounds__` 都不溢出。

改成交叉依赖后才逼出来：

```cpp
for (int k = 0; k < N; ++k)
    a[k] = fmaf(a[k], 1.0001f, a[(k + 7) % N]);   // ← 依赖另一个元素
```

**"我造不出这个现象"往往说明我对编译器的能力估计不足**，
而不是这个现象不存在。

```
/*0010*/  S2R R6, SR_TID.X ;                          ← threadIdx.x
/*0040*/  S2R R9, SR_CTAID.X ;                        ← blockIdx.x
/*0060*/  LEA R5, R9, R6, 0x8 ;                       ← blockIdx*256 + threadIdx
/*0070*/  ISETP.GE.AND P0, PT, R5, UR4, PT ;          ← i < n ?
/*0080*/  @!P0 LDC.64 R2, c[0x0][0x380] ;             ← 谓词执行：只有 i<n 的线程做
/*00a0*/  @!P0 LDG.E.CONSTANT R0, desc[UR6][R2.64] ;  ← 全局内存读（只读缓存路径）

/*0110*/  STS [R5], R0 ;                              ← 写共享内存
```

`LDG.E.CONSTANT` 里的 `.CONSTANT` 是因为源码写了 `const float* __restrict__` ——

`S2UR UR5, SR_CgaCtaId` 出现在这里有点意外：`Cga` = Cooperative Grid Array（cluster）。
即使源码里没用 cluster，编译器也会读它来算共享内存的基址——
说明 Blackwell 的共享内存寻址已经是 cluster-aware 的。

|---|---|
| **cuBLASLt 的 nvjet JIT** | 本章实测发现的运行时代码生成路径。它能针对具体的 M/N/K 和布局生成专用 kernel，避开模板组合爆炸 |

## 陷阱

**1. 以为 `nvcc -O3` 优化了设备代码。** 它只管宿主代码，设备代码要 `-Xptxas -O3`。

**2. 忽略 `-Xptxas -v` 里的 spill。** 本章实测：2796 字节的 spill 带来 **23 倍**减速，
而且**不会有任何报错或警告**。

**3. 用 `__launch_bounds__` 提高占用率。** 它是用 spill 换占用率。
只在你**确实需要**那个 block 大小时用。

**4. 混淆 `.version` 与 `.target`。** 前者是 PTX ISA 版本（由 cicc 决定），
后者是目标架构（由 `-arch` 决定）。L0.1 的失败是前者不匹配。

**5. 以为 `cicc` 和 `ptxas` 是同一个包。** 它们分属 `nvidia-nvvm` 与 `nvidia-cuda-nvcc`，
必须一起钉版本。

**6. 只编译一个架构然后到处部署。** 缺 cubin 时驱动会 JIT PTX——首次 launch 会很慢，
而且如果 PTX ISA 版本高于驱动支持范围，会直接失败。

**7. 造不出某个现象就以为它不存在。** 本章第一版逼不出 spill，
是因为编译器把循环融合了，不是因为 spill 不会发生。

## 自测题

<details markdown="1">
<summary>1. 我的 kernel 编译时 <code>-Xptxas -v</code> 报 <code>Used 255 registers</code>。这是好事还是坏事？</summary>

**看情况，但 255 是个特殊数字——它是硬件上限。**

SASS 的寄存器编号是 8 位，`R255` 是 `RZ`（零寄存器），所以实际可用是 **254 个**。
报 255 通常意味着 ptxas 已经用满，**再复杂一点就要 spill**。

判断步骤：

1. **看 spill 是否为 0。** 如果是 0，说明刚好装下，**这是最优状态**——
   254 个寄存器意味着每 SM 只能驻留 258 个线程（1 个 256 线程的 block）。
   按本章和 L2.1 的实测，只要不是 memory-bound 到极限，1 block/SM 通常够用。
2. **如果 spill 不为 0**，必须处理：减小 tile、拆分 kernel、
   或者把部分数据放共享内存（smem 延迟 6.5 周期 vs local memory 929 周期）。

**不要**为了"降低寄存器用量"去加 `__launch_bounds__`——本章实测那会慢 23 倍。
</details>

<details markdown="1">
<summary>2. 为什么一个 810 字节的 .cu 预处理后会变成 1.43 MB？这对我有什么实际影响？</summary>

因为 `#include <cuda_runtime.h>` 递归带进来上千个头文件，
包含全部的 CUDA API 声明、内建函数、类型定义、内联实现。

**实际影响有三个**：

1. **编译慢。** 每个 `.cu` 都要重新处理这 1.4 MB。CUTLASS 这类重模板库
   编译一个 kernel 要几十秒到几分钟。
2. **这是 CuTe-DSL / Triton 快的原因之一。** 它们用 Python 描述 kernel，
   直接生成 IR，完全跳过 C++ 前端。
3. **增量编译很重要。** 改一行 CUDA 代码要重编整个翻译单元。
   把 kernel 拆到独立的 `.cu` 文件能显著改善迭代速度。
</details>

<details markdown="1">
<summary>3. 我看到某个 kernel 叫 <code>cutlass_80_tensorop_bf16_s16816gemm_relu_bf16_128x64_64x3_nn_align8</code>。不读源码，能推出什么？</summary>

几乎全部关键配置：

| 片段 | 含义 |
|---|---|
| `cutlass_80` | CUTLASS 库，**sm_80（Ampere）血统**的模板 |
| `tensorop` | 用 tensor core（对照 `simt` = 用 CUDA core） |
| `bf16` | 输入数据类型 |
| `s16816` | mma 指令形状 **m16n8k16**（L1.2 讲过） |
| `gemm_relu` | GEMM 融合了 ReLU epilogue |
| `bf16`（第二个） | 输出类型 |
| `128x64_64` | 线程块 tile：M=128, N=64, K=64 |
| `x3` | **3 段软件流水**（多级 double buffering） |
| `nn` | 两个矩阵都不转置（Non-transposed × Non-transposed） |
| `align8` | 按 8 个元素对齐（=16 字节，可用 `LDG.128`） |

**能推出的事**：这个 kernel 跑在 sm_120 上但用的是 Ampere 世代的指令
（因为 sm_120 没有 tcgen05，L1.2）；tile 是 128×64，可以据此估算 smem 用量
$\approx (128 + 64) \times 64 \times 2\ \text{B} \times 3\ \text{段} = 72$ KB，
接近 99 KB 上限（L1.1）。

**读 kernel 名是最省事的性能诊断手段。** 不用 profiler、不用读源码。
</details>

<details markdown="1">
<summary>4. 我把 kernel 编译成 <code>sm_90</code>（Hopper）却在 5090（sm_120）上运行。会发生什么？</summary>

**取决于 fatbin 里有没有 PTX。**

- **有 PTX**（`-gencode=arch=compute_90,code=compute_90`）：
  驱动在首次 launch 时把 PTX **JIT 编译**成 sm_120 的 SASS。
  能跑，但首次 launch 会有明显延迟（L1.4 实测首个 kernel 15.1 ms，
  含 JIT 的话会更久），而且用不上 sm_120 的专属指令。
- **只有 sm_90 的 cubin、没有 PTX**：直接失败，
  报 `no kernel image is available for execution on the device`。

**更隐蔽的情况**：如果你写 `-arch=sm_89` 编译，5090 上照样能跑（有 PTX 兜底），
**没有任何警告**，只是可能慢。这就是 L1.2 陷阱 3 说的"最隐蔽的性能坑"。

**判断方法**：`cuobjdump -lelf your.so | grep -oE "sm_[0-9]+"` 看有没有你的架构。
</details>

<details markdown="1">
<summary>5. 本章发现 cuBLAS 的 fp8 kernel 是 JIT 生成的、不在 .so 里。如果要彻底查清它用了哪条 mma 指令，你会怎么做？</summary>

按可行性排序：

**(a) ncu 的指令计数器。** `ncu --metrics sm__inst_executed_pipe_tensor.sum`
给出该 kernel 执行了多少条 tensor 指令。用总 FLOP 除以它，
就得到"每条指令多少 FLOP"，直接判定指令宽度。
**本机没有 ncu**（L2.1 原始现场 ③ 记录了工具清单），需要用 NVIDIA 官方安装包装。

**(b) 运行时 dump cubin。** 设置 `CUDA_ENABLE_CUBIN_DUMP=1` 或
`CUDA_DEVICE_MAX_CONNECTIONS` 相关的调试环境变量（具体名称随版本变），
让驱动把 JIT 产物落盘，再 `nvdisasm`。**本机可试**。

**(c) 反推。** 从名字 `qqtst_mma_64x256x64_4_64x64x64_tmaAB` 里，
`tmaAB` 说明用了 TMA。而 TMA 在 sm_120 上的支持范围、
以及配套的 mma 指令族（`kind::mxf8f6f4`，L1.2 探测到可编译），
可以缩小到几个候选，再逐个手写 benchmark 比对 FLOP/clk/SM。

**(d) 直接写一个用 `kind::mxf8f6f4.block_scale` 的 kernel 测吞吐**（L1.2 的建议）。
如果它达到 1501 FLOP/clk/SM，就基本确认了。

**(a) 最直接，(d) 最不依赖工具。** L2.4 会走 (d)。
</details>
