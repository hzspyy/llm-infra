## 本章回答三个问题

前面六章各自拆了一个部件。这一章把它们装到一起：**一个能收 HTTP 请求、
能同时服务多条请求、能复用前缀、能被取消的引擎，最少需要哪些状态？**

1. 四家引擎（vLLM V1 / SGLang / TensorRT-LLM / llama.cpp）在进程模型、调度、
   显存、执行、扩展点上分别做了什么选择？分歧在哪？
2. 自己从零写一个，六次迭代各增加什么能力？每一次能测出什么？
3. 一条请求在引擎内部的完整状态是什么？怎么证明它被完整地收回来了？

本章的 nanoserve 复用 4.1 那份手写 Qwen3 前向，只往上加服务层。
它跑出来的 token **与 `transformers.generate` 的贪心解码逐个相同**，
所以后面所有关于调度和显存的数字都建立在一个正确的模型之上。

## 机制拆解：并发上限从哪来

四家引擎在最上层其实只分成两派，判据是**"最多同时跑几条请求"这个数是怎么定的**。

**一派把它写死在启动参数里。** llama.cpp 的 server 开 `n_parallel` 个 slot，
每个 slot 是一个独立的状态机，启动时就把 KV 按 slot 切好：

```cpp
// tools/server/server-context.cpp:152
if (params.n_parallel < 0) {
    SRV_TRC("%s", "n_parallel is set to auto, using n_parallel = 4 and kv_unified = true\n");
    params.n_parallel = 4;
}
...
params.n_ctx = params.n_parallel * params.kv_unified_per_slot;
```

TensorRT-LLM 也有同一个东西，叫 sequence slot
（`tensorrt_llm/_torch/pyexecutor/seq_slot_manager.py:6`）：

```python
class SeqSlotManager(BaseResourceManager):
    def __init__(self, max_num_sequences: int):
        self.slot_manager = SlotManager(max_num_sequences)
```

**另一派让它由剩余块数决定。** vLLM 和 SGLang 没有 slot：请求要几块给几块，
块用完了就不再收新请求（本章 nanoserve 走的是这条）。
`max_num_seqs` 存在，但它是上界，不是预留。

这个分歧解释了后面很多差异：

- 有 slot 的引擎**容量是确定的**，一条超长请求不会挤掉别人，代价是短请求也占着一整个 slot 的额度。
- 无 slot 的引擎**容量随负载浮动**，显存利用率高，代价是必须处理"块不够了"这件事——
  于是就有了抢占、换出和重算（5.3、5.8）。

llama.cpp 的做法很能说明代价：块不够时它在 `update_slots()` 里**退回去用更小的 batch 重试**：

```
// tools/server/server-context.cpp:3733
failed to find free space in the KV cache, retrying with smaller batch size, off = %d, n_batch = %d, ret = %d
```

### 四家逐层对比

固定版本：vLLM 0.29.0、SGLang 0.5.19（均为 crater 上安装的 wheel），
llama.cpp `df03399b`、TensorRT-LLM `7bbf99e5`（2026-09-10 浅克隆到
`/scratch/learn/opt/src/`，只读源码，未编译未运行）。

| | vLLM V1 | SGLang | TensorRT-LLM (PyExecutor) | llama.cpp server |
|---|---|---|---|---|
| **进程模型** | HTTP 进程 + 独立的 `EngineCoreProc`（`v1/engine/core.py:1027`），ZMQ 通信；`VLLM_ENABLE_V1_MULTIPROCESSING` 默认 1（`envs.py:155`） | tokenizer / scheduler / detokenizer 三个 `mp.Process`（`srt/entrypoints/engine.py:885` 起） | 单进程，Python executor 驱动 C++ `batch_manager` | 单进程，HTTP 线程 + 一个推理线程，中间一个带锁的任务队列（`tools/server/server-queue.cpp`） |
| **调度** | 一个 scheduler，token 预算 + chunked prefill | 一个 scheduler，`ScheduleBatch` + 基数树 | **两级**：`CapacityScheduler` 决定谁装得下，`MicroBatchScheduler` 决定这一拍谁上（`scheduler/scheduler.py:412`、`:474`、`:531`） | `update_slots()`（`server-context.cpp:2793`）扫一遍所有 slot |
| **并发上限** | 剩余块数（`max_num_seqs` 是上界） | 剩余块数 | `max_num_sequences` 个 seq slot | `n_parallel` 个 slot，启动时定 |
| **KV 组织** | 块池 + 哈希表（5.2） | 基数树（5.2） | `KVCacheManager`，`tokens_per_block`（`resource_manager.py:352`） | 每 slot 一段；`kv_unified` 时共用一个池 |
| **前缀复用** | 块哈希表 | 基数树前缀匹配 | block reuse | `slot_prompt_similarity`：挑与新 prompt 最长公共前缀的 slot（`server-context.cpp:1561`） |
| **执行** | `gpu_model_runner` + CUDA Graph（2.6b、5.4） | 同上 | TensorRT engine / PyTorch 后端 | ggml 计算图 + 多后端 |
| **扩展点** | platform / attention backend / structured output backend 注册表 | `srt/constrained/` 等一组 backend 基类 | `connectors/`、`guided_decoder.py` | ggml backend 接口 |

三点值得单独说：

- **只有 llama.cpp 把"复用"做在 slot 粒度上**：它不切块，而是找一个"上次跑过相似 prompt"的 slot 接着用。
  这在 `n_parallel` 很小、请求高度相似时非常划算，而且实现极简；
  代价是复用是全或无的，两条只共享一半前缀的请求分不到好处。
- **只有 TensorRT-LLM 把调度拆成两级。** 「装不装得下」和「这一拍谁上」是两个问题：
  前者关心显存，后者关心 batch 形状与 in-flight 的微批。vLLM 把两件事揉在一个函数里。
- **进程边界的位置决定了故障边界。** vLLM 与 SGLang 把引擎放进独立进程，
  HTTP 侧崩了引擎还在；llama.cpp 与 TRT-LLM 是一个进程，一起生一起死。5.8 会用到这条。

::: warning 这张表的证据强度不一样
vLLM 与 SGLang 是 crater 上**实际安装并跑过**的版本（本章及 5.1–5.6 的实验都在其上）。
llama.cpp 与 TensorRT-LLM **只读了源码，没有编译、没有运行、没有任何性能数字**。
表里关于它们的每一格都可以在上面给出的 `file:line` 处核对，但
「它们实际跑起来什么样」本章 `UNVERIFIED`。
要补的话：llama.cpp 需要在 crater 上编译（CUDA 后端），
TensorRT-LLM 需要与本机 CUDA 13.0 匹配的构建，两者本轮都没做。
:::

## 工程实现 · 自己写一遍：nanoserve 的六次迭代

每一次迭代只加一件事，并且加完之后立刻能测出点什么。
代码在 `labs/L5/nanoserve/`，一次跑完六个阶段：

```bash
ssh crater 'bash /scratch/learn/work/labs/L5/nanoserve/run_all.sh'
```

模型层复用 4.1 的手写 Qwen3，只把 KV 换成块池寻址：

{{srcfold:labs/L5/nanoserve/model.py}}

::: warning 这不是 paged attention kernel
`forward()` 先按 `gather_idx` 把 KV **收集成连续张量**再交给 SDPA，
分页只体现在寻址上，不体现在 kernel 内部。3.3 量过这条路的代价上界。
本章所有耗时数字都带着这个前提，不能拿去和真实引擎比。

### 迭代 1 · 一条请求走完全程

引擎最小的样子：一个 `step()`，一条请求，四个状态。
把预算压到 8 个 token，中间态就现形了（`s1_trajectory`）：

| step | state | num_computed | block_table | kv_len | 本步 prefill / decode |
|---:|---|---:|---|---:|---|
| — | waiting | 0 | `[]` | 0 | — |
| 0 | prefill | 8 | `[0, 1]` | 8 | 8 / 0 |
| 1 | prefill | 16 | `[0, 1]` | 16 | 8 / 0 |
| 2 | decode | 17 | `[0, 1]` | 17 | 1 / 0 |
| 3 | decode | 17 | `[0, 1]` | 18 | 0 / 1 |
| 4 | finished | 17 | `[]` | 19 | 0 / 1 |

17 个 prompt token 分成 3 个 chunk；结束时 `block_table` 变回空 —— **块归还是状态的一部分**。

这里有一个必须踩对的坑：**最新采样出来的那个 token 还没有 KV**。

```python
# labs/L5/nanoserve/engine.py
@property
def kv_len(self) -> int:
    if not self.output_ids:
        return self.num_computed
    return self.num_computed + len(self.output_ids) - 1
```

它要等下一步被喂进模型时才写进块池。少减这个 1，位置就整体串一格，
模型照样跑、照样出 token，只是全错。第一版就是这么错的，症状是
`all_ids[kv_len]` 越界。

**怎么检查这个最小实现**：同一条 prompt、同样贪心，和 `transformers.generate` 逐 token 比：

```json
{"kind": "s1_crosscheck", "reference": "transformers.generate greedy",
 "compared": 24, "identical": true, "first_divergence": null,
 "ref_text": "Three prime numbers are:\n\n1. 2  \n2. 3  \n3. 5  \n\nThese are the first"}
```

24 个 token 全同。**分页寻址、chunked prefill、块回收都不改变输出**——
这是后面所有实验的前提。

### 迭代 2 · 连续批处理

只加一件事：新请求可以中途上车。对照组是"静态批"——攒着，
等引擎彻底跑空才把攒下的一起放进去。**两组用同一份错峰到达序列**
（每 2 步来一条，每条生成 24 token），3 次重复取中位数：

| 并发请求数 | 模式 | 平均延迟 | 最大延迟 | 吞吐 | step 数 |
|---:|---|---:|---:|---:|---:|
| 4 | 连续 | **289.6 ms** | **313.2 ms** | **240.7 tok/s** | 30 |
| 4 | 静态 | 416.1 ms | 510.9 ms | 170.4 tok/s | 48 |
| 8 | 连续 | **310.4 ms** | **363.1 ms** | 337.2 tok/s | 38 |
| 8 | 静态 | 408.3 ms | 520.7 ms | 323.3 tok/s | 48 |
| 16 | 连续 | **341.4 ms** | **422.8 ms** | 439.1 tok/s | 52 |
| 16 | 静态 | 389.6 ms | 523.6 ms | 417.8 tok/s | 72 |

**平均延迟三档都赢（1.44× / 1.31× / 1.14×），最大延迟也都赢。
吞吐只在 n=4 明显赢（1.41×），n=8/16 几乎持平（1.04× / 1.05×）。**

吞吐持平不是意外：5.1 和 5.5 都测过，这个规模的 decode 是带宽受限的，
batch 从 1 涨到 16 每步几乎不变贵。所以**连续批处理在这里买到的主要是延迟，
不是吞吐**——它省掉的是"排队等上一批跑完"的时间，而不是把 GPU 喂得更满。

而 n=4 那一档吞吐也赢，是因为静态批多花了 18 个 step（48 vs 30）：
它有大段时间在跑只有一条请求的批。

step 序列直接印证了"中途上车"：

```
step 0  prefill=[q0]                    decode=[]
step 1  prefill=[]                      decode=[q0]
step 2  prefill=[q1]                    decode=[q0]
step 3  prefill=[]                      decode=[q0, q1]
step 4  prefill=[q2]                    decode=[q0, q1]
step 5  prefill=[]                      decode=[q0, q1, q2]
```

### 迭代 3 · 分页 KV

两条请求交替分块，逻辑上各自连续，物理上互不相邻：

```json
{"kind": "s3_tables", "step": 1,
 "A": {"state": "decode", "blocks": [0, 1, 2], "kv": 41},
 "B": {"state": "decode", "blocks": [3, 4, 5], "kv": 40}, "pool_free": 58}
```

`block_table[p / 16] * 16 + p % 16` 就是全部的寻址逻辑，逐条打出来：

| 逻辑位置 | 落在第几块 | 物理槽位 |
|---:|---:|---:|
| 0 | 0 | 0 |
| 15 | 0 | 15 |
| 16 | **1** | 16 |
| 31 | 1 | 31 |
| 32 | **2** | 32 |

这张表在 `model.py` 里就是 `slot_mapping`（写）和 `gather_idx`（读），
名字和 vLLM 一致。**块的物理编号可以任意打乱，寻址逻辑不变**——
这正是分页的全部意义。

块池的账：Qwen3-1.7B 每 token 的 KV 是

$$2 \times 28\,\text{层} \times 8\,\text{KV头} \times 128 \times 2\,\text{B} = 114\,688\ \text{B} = 112\ \text{KiB}$$

256 块 × 16 token = 4096 token，池子实测占 469 762 048 B = 448 MiB，与账本一致（0.2）。

### 迭代 4 · 前缀复用

四条请求共享同一段 system prompt。先**预测**再测：
公共前缀 105 个 token，块大小 16，所以可复用 $\lfloor 105/16 \rfloor = 6$ 块。

| 请求 | prompt token | 命中块 | 实际要算的 prefill token | TTFT |
|---|---:|---:|---:|---:|
| p0（第一条） | 121 | 0 | 121 | 13.79 ms |
| p1 | 121 | **6** | **25** | 11.61 ms |
| p2 | 118 | **6** | **22** | 11.51 ms |
| p3 | 120 | **6** | **24** | 11.51 ms |

**预测的 6 块和实测的 6 块逐点相符**（5.2 的公式在这里被第二次验证）。
prefill 计算量降到 1/5，但 TTFT 只降了 17%——因为这个规模下
121 个 token 的 prefill 本来就只要十几毫秒，固定开销占了大头。

关掉前缀缓存重跑，同一批请求分配了 32 块；开着只分配 14 块、复用 18 次。
**省的是块，不只是算力。**

复用有一条边界必须画对：**复用来的块是只读共享的，所以只能停在块边界上**。
如果整段 prompt 都命中，得退掉最后一块重算：

```python
# labs/L5/nanoserve/engine.py
if hit and hit * self.block_size >= len(req.prompt_ids):
    self.pool.release(req.block_table.pop())
    hit -= 1
```

否则这一步没有任何 token 需要前向，采样就拿不到 logits。

### 迭代 5 · chunked prefill 与 token 预算

一条 1201 token 的长 prompt 插进 3 条正在 decode 的请求里。
稳态每步 11.6 ms，扫 `max_batched_tokens`：

| token 预算 | prefill 分几块 | 插入期间最慢一步 | 相对稳态 | 长 prompt 占用的 step 数 |
|---:|---:|---:|---:|---:|
| 64 | **20** | 24.6 ms | 2.1× | 20 |
| 256 | 5 | 29.0 ms | 2.5× | 5 |
| 1024 | **2** | **54.8 ms** | **4.7×** | 2 |

**这是一条干净的单调取舍**：预算越大，长 prompt 越快算完（20 步 → 2 步），
但同批 decode 的那一步越慢（24.6 ms → 54.8 ms）。

它对应的是真实系统里的 TPOT 抖动：一条长 prompt 进来，
正在聊天的用户会看到吐字卡一下。卡多久由 `max_batched_tokens` 决定。
5.1 讲过为什么两相不能用一套参数——这里是那句话的可测版本。

::: warning 这条曲线的形状取决于本实现
nanoserve 一步里跑**两次前向**（一次 prefill 组、一次 decode 组），
共用一个 token 预算。真实引擎（vLLM）把两者拼进**同一次** varlen 前向，
所以它们的绝对开销更低。本章测到的是"预算怎么切"这个取舍的形状，
不是 vLLM 的实际数字。
:::

最后一层：裸 asyncio 的 HTTP，`text/event-stream` 逐 token 推。
用裸 socket 而不是框架，是因为下一章要看断连——
框架会把"客户端走了"包装掉，这里它就是 `writer.drain()` 抛异常。

| 场景 | TTFT | token 间隔（前 7 个） | 结果 |
|---|---:|---|---|
| A 单条流式 | 228.18 ms | 30.7 / 30.3 / 32.2 / 31.0 / 30.3 / 30.4 / 30.7 ms | 24 token，`[DONE]` |
| B 三条并发 | 36.53 / 36.54 / 36.55 ms | 三条**逐拍相同**（34.6 / 34.4 / 34.9 …） | 各 24 token |
| C 读 5 个就关 socket | — | — | 服务端 abort，块归还 |

- **A 的 228 ms 里绝大部分是第一次 CUDA 调用的预热**，B 的三条同样长度只要 36.5 ms。
  报 TTFT 一定要说清是不是冷启动。
- **B 三条的 token 间隔在毫秒级上完全一致**，因为它们被调度进了同一步。
  这是"同一批"在客户端侧看得见的样子。

客户端读到第 8 个 token 之后间隔掉到 0.0x ms —— 那不是引擎变快了，
是**这些 token 早就发出来了，堆在内核缓冲区里**。
端到端量到的 token 间隔是"网络与缓冲之后的节奏"，不是引擎的 TPOT。

### 迭代之外：一条取消路径（5.8 的入口）

三条请求跑到一半取消中间那条：

```json

 "held_blocks": [5, 6, 7, 8, 9],
 "pool_before": {"free": 113, "refcounts": {"0":1,...,"14":1}},
 "pool_after":  {"free": 118, "refcounts": {"0":1,"1":1,"2":1,"3":1,"4":1,"10":1,...,"14":1}},
 "freed": 5}
```

**它占的 5 块，一块不多一块不少地回到池子**，另外两条的引用计数没被碰。
HTTP 那条路上也验了同一件事：客户端读了 5 个 token 就关掉 socket，
服务端日志

## 设计取舍

### 1. 状态放在哪里，决定了取消有多难写

nanoserve 里一条请求的状态分布在三处：队列（它在 waiting 还是 running）、
自己的 `block_table`、以及 HTTP 协程里的那个 `asyncio.Queue`。
`abort()` 必须同时处理前两处，第三处由 `finally` 兜底。

四家引擎的做法差别就在**这三处离得有多远**：

- llama.cpp 把它们放进同一个 `server_slot` 结构体（`server-context.cpp:239`），
  一个 slot 就是请求的全部状态。取消 = 把 slot 打回 `SLOT_STATE_IDLE`。
  简单，但也意味着**状态和资源绑死**：slot 空着也占着 KV。
- vLLM 把请求状态放在 scheduler 进程里，输出通道在另一个进程。
  取消要跨进程传递（这也是它有 `RequestStatus.FINISHED_ABORTED` 这类显式状态的原因）。
  换来的是 HTTP 侧崩溃不影响正在跑的请求。

**可带走的判断：状态的分布决定了失败路径的复杂度。
状态越集中越好写，越分散越能隔离故障。这两件事不可兼得。**

### 2. 块池的引用计数是唯一的真相来源

nanoserve 有意不维护"某条请求用了几块"这个派生字段——
要知道就去数 `block_table`，要知道块是不是自由就看 `ref_count`。
`leak_check()` 因此只需要一句断言：结束之后不应该有任何 `ref_count > 0`。

反例是很容易写出来的：如果同时维护 `num_free` 计数器和 free 链表，
两者就会在某条罕见路径上分叉，而且分叉之后系统还能跑很久才暴露。
5.2 里 vLLM 的块池也是同一个选择：空闲链表就是空闲状态本身。

**不变量应该由一份数据承担；派生字段只能是缓存，不能是真相。**

### 3. 预算是唯一的调度旋钮

`_schedule()` 一共只有一个数：`max_batched_tokens`。
decode 先占（它们已经拿着块了），剩下的给 prefill。

这个顺序不是随便定的。反过来（prefill 优先）会导致
**长 prompt 到达时所有 decode 停摆**——迭代 5 那张表里 54.8 ms 那一格
就是"prefill 一次吃掉 1021 个预算"的后果，只不过 decode 还占着 3 个名额。
如果 decode 不优先，那一步就是纯 prefill，正在聊天的用户直接卡住一整步。

vLLM 的调度器同样把"已经在跑的"排在"新来的"前面（5.3）。
**这是一条通用规则：已经消耗过资源的请求优先，否则系统会在高负载下
把算力浪费在反复启动新请求上。**

### 4. 加一个后端要改哪些地方

nanoserve 的模型层与引擎层之间只有一个接口：`forward(input_ids, positions,
slot_mapping, gather_idx, ctx_lens)`。换模型只需要换 `model.py`，
`engine.py` 一行不动——只要新模型愿意接受"KV 写到我指定的槽位"这个约定。

四家引擎的扩展点都落在同一处，因为这是唯一必须约定的东西：

- vLLM 的 attention backend 接口要的就是 `slot_mapping` 与 `block_table`；
- SGLang 同理；
- llama.cpp 的 ggml backend 接口在更低一层（算子），所以换后端不涉及 KV 布局，
  但也因此**换 KV 组织方式要改的地方更多**。

**扩展点的位置 = 你允许别人替换的那一层的边界。放低了灵活但改动大，
放高了好接但能做的事少。**

## 前沿

- **调度拆成两级。** TensorRT-LLM 的 `CapacityScheduler` / `MicroBatchScheduler`
  把"装得下吗"和"这一拍谁上"分开。当引擎要同时处理 PD 分离、多微批、
  encoder 请求时，揉在一起的调度函数会迅速失控。L6.4 会回到这里。
- **进程边界继续外移。** vLLM 把 EngineCore 拆成独立进程之后，
  下一步是把 tokenizer、detokenizer、结构化输出的语法编译都挪出关键路径
  （5.6 测到语法填 mask 现在还在调度器里串行）。
- **slot 与 block 的融合。** llama.cpp 的 `kv_unified` 是从"每 slot 一段"
  往"共用一个池"挪的中间形态。两派在收敛。
- **nanoserve 缺的最大一块是抢占。** 现在块不够就抛异常。
  真实引擎要么换出到 CPU，要么丢弃重算（5.3），这决定了系统在过载下
  是优雅降级还是直接拒绝。5.8 补这一段。

## 陷阱

1. **最新采样的 token 还没有 KV。** `kv_len = num_computed + len(output) - 1`。
   少减这个 1 会让位置整体串一格，模型照样出 token，只是全错。
2. **"跑完了"不等于"资源回来了"。** 每条路径结束后都要断言块池回到初始状态。
   nanoserve 的 `leak_check()` 在六个阶段都跑，全部为 0。
3. **复用来的块是只读共享的**，复用只能停在块边界。整段 prompt 命中时
   必须退掉最后一块重算，否则这一步没有 token 要前向。
4. **TTFT 要区分冷热。** 本章第一条 228 ms、之后 36.5 ms，差 6 倍全是预热。
5. **端到端量的 token 间隔不是 TPOT。** 内核缓冲会把多个 token 一起交付
   （本章前 7 个约 30 ms，之后掉到 0.0x ms）。
6. **连续批处理主要买延迟，不一定买吞吐。** 本章 n=8/16 时吞吐只差 4–5%，
   因为 decode 在这个规模上是带宽受限的（5.1）。
7. **有 slot 的引擎容量确定但利用率低，无 slot 的相反。** 选哪个取决于
   你更怕"容量不确定"还是"显存浪费"。
8. **框架层的分页不等于 paged attention kernel。** nanoserve 先 gather 再 SDPA，
   它证明的是寻址正确，不是 kernel 代价。

## 自测题

<details markdown="1">
<summary>1. 一条请求被取消时，需要动哪些状态？漏掉任何一处会怎样？</summary>

nanoserve 里一条请求的状态在三处：

1. **它在哪个队列里**（`waiting` 还是 `running`）——漏掉它，调度器下一步还会调度它。
2. **它的 `block_table`**——漏掉它，那些块的 `ref_count` 永远不归零，
   池子会慢慢饿死。这是最难发现的一种：系统跑几小时之后开始拒绝新请求，
   但没有任何一条报错。
3. **输出通道**（HTTP 协程里的 `asyncio.Queue`）——漏掉它，协程永远等不到
   `None`，连接挂着不释放。

本章的做法是让 `abort()` 处理前两处，`finally` 兜底第三处，
再用 `leak_check()` 对第 2 处做事后断言：结束之后不应有任何 `ref_count > 0`。

**只测"输出对不对"发现不了其中任何一种。**
</details>

<details markdown="1">
<summary>2. 为什么连续批处理在本章的吞吐上几乎没赢，延迟却赢了 1.14–1.44 倍？</summary>

因为这个规模的 decode 是**带宽受限**的（5.1、5.5 都测过）：
batch 从 1 涨到 16，每步耗时几乎不变。所以"把 GPU 喂得更满"这件事
在这里换不来多少吞吐——n=8 和 n=16 时吞吐比只有 1.04× 和 1.05×。

延迟赢的是另一件事：**静态批让后到的请求干等上一批跑完**。
本章实测最大延迟 313 vs 511 ms（n=4）、363 vs 521 ms（n=8）、423 vs 524 ms（n=16）。

n=4 那一档吞吐也赢了 1.41×，原因不同：静态批多花了 18 个 step（48 vs 30），
其中大段时间在跑只有一条请求的批。

**推论：报连续批处理的收益必须说明看的是延迟还是吞吐，以及负载有多重。**
</details>

<details markdown="1">
<summary>3. 把 <code>max_batched_tokens</code> 从 64 调到 1024，谁变好谁变坏？</summary>

本章实测（一条 1201 token 的长 prompt 插进 3 条 decode）：

| 预算 | prefill 分几块 | 插入期间最慢一步 |
|---:|---:|---:|
| 64 | 20 | 24.6 ms |
| 256 | 5 | 29.0 ms |
| 1024 | 2 | 54.8 ms |

稳态一步是 11.6 ms。所以：

- **变好的**：长 prompt 算完得更快（20 步 → 2 步）。
- **变坏的**：同批 decode 那一步从 2.1× 慢到 4.7×，正在聊天的用户看到卡顿。

这就是 chunked prefill 存在的理由：把 TTFT 和 TPOT 之间的取舍变成一个**可调的旋钮**，
而不是一个由 prompt 长度决定的意外。
</details>

<details markdown="1">
<summary>4. llama.cpp 的 slot 和 vLLM 的 block，本质区别是什么？</summary>

**"最多同时跑几条"这个数是怎么定的。**

- llama.cpp：启动时定死 `n_parallel` 个 slot（`server-context.cpp:152`，
  auto 时是 4），KV 按 slot 切好。TensorRT-LLM 的 `SeqSlotManager` 是同一个东西。
- vLLM / SGLang：没有 slot，请求要几块给几块，块用完了就不收新的。

代价对称：

- 有 slot → 容量确定，一条超长请求不会挤掉别人；但短请求也占着一整个 slot 的额度，
  显存利用率低。
- 无 slot → 显存利用率高；但必须处理"块不够了"，于是有了抢占、换出与重算（5.3、5.8）。

llama.cpp 遇到块不够时的做法很能说明问题：**退回去用更小的 batch 重试**
（`server-context.cpp:3733` 那条日志）。这是有 slot 一派的典型处理方式——
因为容量本来就是确定的，不够只可能是这一拍要得太多。
</details>

<details markdown="1">
<summary>5. nanoserve 的分页和真实的 PagedAttention 差在哪？本章的耗时数字能拿去比吗？</summary>

**寻址一样，kernel 不一样，所以耗时不能比。**

一样的部分：`slot_mapping`（写 KV 到哪个槽）、`block_table` / `gather_idx`
（读 KV 收集哪些槽）、`table[p/16]*16 + p%16` 这个翻译。名字都和 vLLM 一致，
本章把 pos 0/15/16/31/32 的槽位逐个打出来验过。

不一样的部分：nanoserve **先把 KV 收集成一个连续张量再调 SDPA**。
真实的 paged attention kernel 在 kernel 内部按块寻址，不做这次拷贝。
3.3 量过"显式 gather"这条路的代价，它是分页代价的**上界**。

所以本章的 11.6 ms/步、54.8 ms 峰值这些数字只能用来看**取舍的形状**
（预算大→峰值高），不能和 vLLM 的绝对值比。
</details>
