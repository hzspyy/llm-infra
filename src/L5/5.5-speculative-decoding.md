## 本章回答三个问题

3.3 和 5.1 反复证明了同一件事：**decode 是带宽受限的，算力大把闲着。**
投机解码就是去花那些闲算力——先猜 $k$ 个 token，
再用**一次前向并行验证**它们；猜对多少就一次前进多少步。

1. 收益到底由什么决定？
2. 为什么它在高并发下会失效？
3. 有哪些草稿方法？现在主流是哪一种？

---

## 一 · 收益由「任务 × 草稿方法」决定，不是引擎的属性

用 `ngram`（prompt lookup）：在 prompt + 已生成文本里找与当前后缀匹配的 n-gram，
把它后面几个 token 拿来当草稿。不需要任何额外权重。

同一个引擎、同一份配置、同样 $k=4$，两个任务：

| 任务 | 无投机 | 投机 k=4 | 加速 | **接受率** |
|---|---:|---:|---:|---:|
| 抄写（输出大量复述输入） | 217.0 tok/s | 893.9 | **4.12×** | **95.7%** (314/328) |
| 自由创作（要求不重复） | 221.0 tok/s | 324.3 | 1.47× | **37.0%** (296/800) |

**加速比差 2.8 倍，接受率差 2.6 倍——它们是同一件事。**

ngram 只会"抄"，所以在输出复述输入的任务上几乎全中（95.7%），
在要求原创的任务上大半落空（37.0%）。

::: warning 「我们的引擎支持投机解码，快 4 倍」这句话没有信息量
本章两行数据来自**同一个引擎、同一份配置**，差别只在 prompt。

报投机解码的收益必须同时说明：**什么草稿方法、什么任务分布、什么并发**。
少任何一项，那个数字都无法复现。
:::

## 二 · 加速比随并发下降

投机花的是"闲算力"。5.1 算过：decode 在 batch < 72 时带宽受限，
算力闲着；batch 一大，算力不闲了，就没得花。

抄写任务，batch 扫描：

| batch | 无投机 tok/s | 投机 tok/s | 加速 |
|---:|---:|---:|---:|
| 1 | 219.9 | 847.8 | **3.86×** |
| 4 | 835.6 | 3100.9 | 3.71× |
| 16 | 2808.4 | 7959.9 | 2.83× |
| 64 | 7289.8 | 11792.7 | **1.62×** |

**单调下降，从 3.86× 掉到 1.62×。**

这是投机解码最重要的一条性质：**它在低并发、要低延迟的场景最有价值，
高并发下收益迅速缩水**（而且验证多算的那些位置开始真的占算力）。

含义很实际：
- **本地单用户 / 交互式 agent**（batch≈1）→ 投机是最划算的优化之一
- **高吞吐批处理服务**（batch 几十上百）→ 收益有限，还要付草稿的复杂度
- 所以很多引擎把投机做成**按负载动态开关**的

## 三 · 猜几个

$k$ 越大，猜中时赚得越多，猜不中时浪费越多。抄写任务上扫 $k$：

| k | tok/s | 加速 |
|---:|---:|---:|
| 1 | 388.3 | 1.81× |
| 2 | 567.7 | 2.64× |
| 4 | 898.0 | 4.18× |
| **8** | **1444.4** | **6.72×** |

**一路涨到 k=8 还没饱和。** 因为这个任务的接受率高达 95.7%，
草稿几乎全中，猜多少赚多少。

### 用第四节的模型对一下

设每个草稿 token 的接受概率为 $p$（近似独立），一次投机迭代期望前进：

$$E[\text{前进}] = \frac{1 - p^{k+1}}{1 - p}$$

代入实测的 $p = 0.957$、$k = 8$：

$$E[\text{前进}] = \frac{1 - 0.957^{9}}{1 - 0.957} = \frac{1 - 0.673}{0.043} = 7.60$$

而**实测加速比是 6.72×**。两者的比值

$$c = \frac{7.60}{6.72} = 1.13$$

就是"验证一步相对普通 decode 一步的耗时倍数"。

**1.13 这个数很说明问题**：一次验证要算 9 个位置的前向，
却只比算 1 个位置贵 13%——**因为 decode 是带宽受限的，
权重只读一遍，多算 8 个位置几乎不额外花时间**（3.3 §一）。

**这就是投机解码能成立的根本原因**，也是它和 batch 之间此消彼长的原因：
batch 大了之后算力不再闲，$c$ 会显著上升，第二节那条下降曲线就是它的表现。

## 四 · 草稿方法的谱系

`vllm/config/speculative.py` 里的类型定义（源码事实）：

```
SpeculativeMethod（顶层）= ['ngram', 'medusa', 'mlp_speculator',
                            'draft_model', 'suffix', 'custom_class']

EagleModelTypes（3 项）  ['eagle', 'eagle3', 'extract_hidden_states']
MTPModelTypes（26 项）   ['deepseek_mtp', 'dots3_note_mtp', 'mimo_mtp',
                          'glm4_moe_mtp', 'ernie_mtp', 'qwen3_next_mtp',
                          'kimi_k3_mtp', 'gemma4_mtp', 'minimax_m3_mtp', ...]
NgramGPUTypes  ['ngram_gpu']   DSparkModelTypes ['dspark']   DFlashModelTypes ['dflash']
```

按**草稿从哪来**分成四类：

| 类 | 草稿来源 | 草稿成本 | 接受率 | 需要什么 |
|---|---|---|---|---|
| **ngram / suffix** | 在文本里查 n-gram | 极低（查表） | 强烈依赖任务（本章 37%–96%） | 什么都不要 |
| **draft model** | 一个独立的小模型 | 高（跑一遍小模型） | 中高，与小模型质量相关 | 另一份权重 |
| **Medusa / MLP speculator** | 在目标模型上加几个预测头 | 低（共享主干） | 中 | 额外训练的头 |
| **EAGLE / EAGLE3** | 用目标模型的**隐藏状态**做自回归草稿 | 低（共享主干） | 高 | 额外训练的草稿模块 |
| **MTP** | 模型**训练时就带**的多 token 预测头 | 低（共享主干） | 高（与主干联合训练） | 模型自带 |

### MTP 是现在的主流

那 26 个 `*_mtp` 类型说明了问题：**DeepSeek、GLM、Qwen3-Next、Kimi、
Ernie、MiniMax、Gemma4、Nemotron…… 新模型普遍自带 MTP 头。**

MTP 与前几类的关键区别是**它不是事后加的**：
多 token 预测头在**预训练阶段就和主干一起训练**（原本是作为训练目标提出的，
用来给主干更密的监督信号），推理时顺便拿来当草稿。所以：

- 草稿几乎免费（共享主干的隐藏状态，只多几个小头）
- 接受率高（草稿头见过和主干一样的数据，分布天然对齐）
- 不需要额外维护一份草稿模型的版本 / 量化 / 部署

还有一个工程细节值得注意：**vLLM 把 `MTPModelTypes` 归在 `EagleModelTypes` 下**。
也就是说在运行时它走的是 EAGLE 那条路径——
**区别在草稿权重从哪来，不在验证机制**。验证永远是同一件事：
把 $k+1$ 个位置一次前向，逐位比对，接受最长的匹配前缀。

::: warning 本章只实测了 ngram
MTP / EAGLE / Medusa 都需要带草稿头的模型权重。
带 MTP 的模型（DeepSeek-V3 类）这张 32 GB 的卡装不下，本轮**没有实测**。

所以本章关于 MTP 的陈述**全部来自源码与文档层面**，
接受率、加速比这些数字我一个都没测过，不要引用。

要补的话：`Qwen3-Next` 系列带 `qwen3_next_mtp`，规模上可能塞得进——
这是本章最值得补的一个实验。
:::

## 五 · 设计取舍

### 5.1 为什么"验证"必须是并行的

投机的收益完全建立在"验证 $k+1$ 个位置几乎和验证 1 个一样快"上。
本章实测这个倍数 $c = 1.13$。

如果 decode 是**算力**受限的，$c$ 会接近 $k+1$，
那么 $E[\text{前进}]/c \le (k+1)/(k+1) = 1$——**投机永远不划算**。

所以投机解码不是一个通用优化，它是**专门针对"带宽受限 + 算力闲置"这个特定失衡**
设计的。这个失衡是 decode 的结构性质（3.3：算术强度恒为 1），
不是某个实现的缺陷——所以这个机会是稳定存在的。

**可带走的判断：一个优化能不能成立，往往取决于系统里存在某个稳定的资源失衡。
先找失衡，再设计怎么花那份闲置资源。**

### 5.2 精确性：投机解码不改变输出分布

这一点常被误解。用**拒绝采样**做验证时，投机解码给出的 token 分布
与不投机时**完全一致**（贪心解码下则是逐 token 相同）。

它和 3.1 的分块 attention 是同一类优化：**精确的重排，不是近似**。
这也是它能被迅速采用的原因（3.1 §7.1 讲过这条判据：
精确的优化不需要任何人重新评估质量）。

代价只在**性能的不确定性**上：接受率随输入变化，
所以每步的耗时不再稳定——这对 TPOT 的 P99 是个新问题（5.1 §三）。

### 5.3 草稿方法的演化方向：把草稿并进主干

看第四节那张表的成本列，演化方向很清楚：

```
独立草稿模型（跑两个模型）
  → Medusa/EAGLE（共享主干 + 事后训练的头）
    → MTP（共享主干 + 预训练时就一起训的头）
```

每一步都在**减少草稿的边际成本**并**提高草稿与主干的分布一致性**。
MTP 走到了终点：草稿头是模型的一部分，不需要额外训练、额外部署、额外对齐。

代价是**它必须在预训练时就决定**——一个没有 MTP 头的开源模型，
事后只能退回 EAGLE 那条路。这是一个"能力必须在早期注入"的例子，
和 3.4 §5.3 说的 attention sink（训练涌现出来、事后只能适应）形态相反
但含义相通：**有些性质由训练阶段决定，推理侧只能接受。**

## 七 · 陷阱

1. **"投机解码快 N 倍"没有信息量。** 必须说明草稿方法、任务、并发。
   本章同一配置下 1.47×–4.12×。
2. **高并发下收益迅速缩水**（本章 batch=64 只剩 1.62×）。
3. **`disable_log_stats=True` 时 vLLM 根本不产生接受率统计**，
   读到的永远是 `None`。要测接受率必须打开它。
4. **接受率统计每步被消费掉**，`make_stats()` 里读不到；要包住
   `make_spec_decoding_stats` 自己累加。
5. **MTP 不是"另一种投机"，它是草稿头的来源不同**；
   在 vLLM 里它走 EAGLE 的运行时路径。
6. **投机不改变输出分布**（拒绝采样保证），但**会让每步耗时变得不稳定**。
7. **最优 $k$ 取决于接受率**，没有普适值。低接受率下猜多是净亏。

## 八 · 自测题

<details markdown="1">
<summary>1. 为什么投机解码在 decode 上有效，在 prefill 上没有意义？</summary>

投机的全部收益来自"验证 $k+1$ 个位置几乎和验证 1 个一样快"。
本章实测这个倍数 $c = 1.13$——因为 decode 是**带宽受限**的（3.3：算术强度恒为 1），
权重只读一遍，多算几个位置几乎不额外花时间。

prefill 本来就一次处理成百上千个 token，而且是**算力受限**的（5.1：
算术强度 2048）。那里没有闲置算力，也没有"串行步数"可省——
prefill 本身就是并行的。

一般化：投机解码是针对"带宽受限 + 算力闲置"这个**特定失衡**设计的。
没有失衡就没有收益。
</details>

<details markdown="1">
<summary>2. 同一个引擎，用户 A 报 4 倍加速、用户 B 报 1.5 倍。谁错了？</summary>

**都没错。** 本章实测同一引擎、同一配置、同样 $k=4$：
抄写任务 4.12×（接受率 95.7%），自由创作 1.47×（接受率 37.0%）。

ngram 只会从上下文里"抄"，所以：
- 文档问答、代码补全、格式化输出、翻译 → 输出大量复述输入 → 接受率高
- 创作、开放对话、推理链 → 输出是新内容 → 接受率低

再加上并发的影响（本章 batch 1→64 使加速从 3.86× 降到 1.62×），
两个数字可以差得更远。

**报投机收益必须带上：草稿方法 + 任务分布 + 并发。**
</details>

<details markdown="1">
<summary>3. 接受率 95.7%、k=8，理论上能前进多少步？实测 6.72 倍，差的那部分是什么？</summary>

$$E[\text{前进}] = \frac{1-p^{k+1}}{1-p} = \frac{1-0.957^9}{1-0.957} = 7.60$$

实测加速 6.72×，比值 $c = 7.60/6.72 = 1.13$。

$c$ 是**验证一步相对普通 decode 一步的耗时倍数**。它包含：
- 一次前向要算 9 个位置而不是 1 个（因为带宽受限，只贵 13%）
- ngram 查表的成本（很小）
- 逐位比对与回退的开销

$c = 1.13$ 说明这笔交易极其划算。反过来，如果 batch 很大、
算力不再闲置，$c$ 会向 $k+1$ 靠拢，收益就没了——
这正是第二节那条下降曲线。
</details>

<details markdown="1">
<summary>4. MTP 和 EAGLE、draft model 的本质区别是什么？</summary>

**区别在草稿权重从哪来，不在验证机制。** 验证永远一样：
$k+1$ 个位置一次前向，逐位比对，接受最长匹配前缀。
（vLLM 干脆把 `MTPModelTypes` 归在 `EagleModelTypes` 下，走同一条运行时路径。）

- **draft model**：一个独立的小模型。要单独训练、量化、部署、对齐版本，
  而且跑它本身就要钱。
- **EAGLE / Medusa**：在目标模型上**事后**加训练的草稿头，共享主干，草稿便宜。
- **MTP**：多 token 预测头在**预训练时就和主干一起训**，模型自带。
  草稿几乎免费，分布天然对齐。

演化方向是把草稿不断并进主干，减少边际成本、提高分布一致性。
MTP 走到了终点，代价是**必须在预训练时决定**——
没有 MTP 头的开源模型事后只能退回 EAGLE。
</details>
