## 本章回答三个问题

投机解码先生成候选 token，再让目标模型并行验证，减少生成同样长度所需的串行迭代。它是否更快，取决于接受长度能否抵消草稿、验证与状态管理的成本。

1. 一次验证可以提交多少 token，收益怎样计算？
2. 贪心验证与随机采样的验证有何不同，怎样保持目标分布？
3. 草稿长度、任务与并发怎样影响收益，已有实验能支持哪些判断？

## 机制拆解与推导

### 1. 接受前缀长度决定每轮进展

设一次提出 k 个草稿，连续接受的长度为 A。忽略 EOS 和输出长度截断，一轮通常前进 A+1 个 token：首个拒绝位置生成修正 token；全接受时生成额外的目标 token。

令第 i 个草稿在前 i−1 个都通过的条件下被接受的概率为 a_i，则

$$E[N]=1+\sum_{i=1}^{k}\Pr(A\ge i)
=1+\sum_{i=1}^{k}\prod_{j=1}^{i}a_j.$$

只有把各位置条件接受概率近似为同一个 p，才能简化为

$$E[N]=\sum_{i=0}^{k}p^i=\frac{1-p^{k+1}}{1-p},\quad p\ne1.$$

p=1 时取 k+1。**日志中的“接受 token 总数 / 草稿 token 总数”不是这组条件概率的直接替代品。** 变长草稿、位置相关性和末尾截断都会影响二者的关系。

### 2. 一轮成本必须包含草稿与状态处理

令普通 decode 单步耗时为 T_d，投机一轮的平均总耗时为 T_s。在相同负载、忽略启动与 prefill 差异的稳态模型中，

$$\text{speedup}\approx\frac{E[N]T_d}{T_s}=\frac{E[N]}{c},\qquad c=T_s/T_d.$$

T_s 包括草稿生成、目标前向、接受判定、KV 回退和调度。小 batch 下，多个验证位置可以复用权重读取，因此 T_s 未必随 k+1 线性增长；这只是收益机会，不是“验证几乎免费”的保证。

例如**假设** p=0.957、k=8，则 E[N]≈7.60。这个计算不能用来解释后面的 6.72× 实测：95.7% 来自另一组 k=4 的聚合统计，k=8 实验没有记录逐位置接受概率，也没有单独计时验证阶段。由 7.60/6.72 得到的 1.13 不是实测验证成本。

### 3. 随机验证需要拒绝采样，而不只是逐 token 比对

在贪心解码下，逐个比较草稿与目标 argmax，接受最长匹配前缀即可。随机采样时，设同一前缀下目标分布为 P、草稿分布为 Q，对草稿 x 按下式接受：

$$\alpha(x)=\min\left(1,\frac{P(x)}{Q(x)}\right).$$

拒绝后，从归一化的残差分布采样：

$$R(x)=\frac{\max(P(x)-Q(x),0)}{\sum_y\max(P(y)-Q(y),0)}.$$

接受分支给 x 的概率质量是 min(P(x),Q(x))，拒绝分支补回 max(P(x)−Q(x),0)，相加为 P(x)。若 P=Q，拒绝概率为零，不需要计算全零残差的归一化。

这是理想算术下的分布保证，前提是使用正确的条件分布、接受规则和残差采样。它不保证相同 seed 下产生相同 token 序列；实际低精度计算、停止规则与缓存回退还需单独测试。本章的性能实验使用 temperature=0，不能作为随机采样分布正确性的实验证据。

### 具体 checkpoint 的 MTP 产物核对（Qwen3.5-4B）

模型族声明支持多 token 预测，不等于手上这个 checkpoint 带 MTP 权重。逐项核对
`Qwen/Qwen3.5-4B`（snapshot `851bf6e8`，`labs/L5/mtp_weight_audit.py`，只读 safetensors
header、不加载权重）：

| 项 | 值 |
|---|---|
| `text_config.num_hidden_layers` | 32（主干层号 0–31，权重清单 738 个张量） |
| `layer_types` | 24 × `linear_attention` + 8 × `full_attention`（`full_attention_interval=4`） |
| `text_config.mtp_num_hidden_layers` | 1 |
| `text_config.mtp_use_dedicated_embeddings` | False（复用主干 embedding，无独立 embedding 张量） |
| `mtp.*` 张量 | 15 个，全部 BF16 |

MTP 层是一个标准 attention+MLP 块，外加两条输入归一化与一个融合投影：

| 张量 | 形状 | 作用 |
|---|---|---|
| `mtp.pre_fc_norm_embedding.weight` / `mtp.pre_fc_norm_hidden.weight` | [2560] | 两条输入各自的 RMSNorm |
| `mtp.fc.weight` | [2560, 5120] | 把 embedding(2560) 与 hidden(2560) 拼接后投影回 2560 |
| `mtp.layers.0.self_attn.q_proj.weight` | [8192, 2560] | 16 head × 256 × 2（`attn_output_gate=True`） |
| `mtp.layers.0.self_attn.{k,v}_proj.weight` | [1024, 2560] | 4 个 KV head × 256 |
| `mtp.layers.0.self_attn.o_proj.weight` | [2560, 4096] | 16 head × 256 |
| `mtp.layers.0.mlp.{gate,up,down}_proj.weight` | [9216, 2560] / [9216, 2560] / [2560, 9216] | SwiGLU |
| `mtp.norm.weight` | [2560] | 输出归一化 |

三点结论：

1. **MTP 是第 33 个块，不在主干层号里**（主干 0–31）。它的输入是主干最后一个 hidden 与
   当前 token 的 embedding 拼接，必须与目标模型出自同一次发布、同 revision。
2. **`mtp_use_dedicated_embeddings=False` 表示草稿复用主干的 embedding 与 lm_head**。
   base 权重或量化方式更新时两者要一起换；只替换主干而不换 MTP 会得到不匹配的草稿。
3. **声明与产物逐项对应**：`mtp_num_hidden_layers=1` 恰好对应 15 个张量
   （每层 12 个块内张量 + `fc` + 2 个 pre-norm + `norm`）。

SGLang 0.5.19 有独立的 `models/qwen3_5_mtp.py`，`qwen3_5.py` 里也带 `is_nextn` 分支，
说明该版本声明支持这条路线；**权重存在与实现存在都不等于本机加载与接受长度已通过**，
实测部分见下面的 lab 与陷阱。

### 引擎侧能观测到什么

引擎自己暴露了两个观测点，不需要插桩：

| 位置 | 内容 |
|---|---|
| `vllm/v1/spec_decode/metrics.py:41` | `SpecDecodingStats.observe_draft(num_draft_tokens, num_accepted_tokens)`，每个请求每步调用一次 |
| `vllm/v1/spec_decode/metrics.py:46-49` | 两个逐位置计数按前缀累加：`num_accepted_tokens_per_pos[i]` 是「至少接受到第 i+1 个」的步数，`num_draft_tokens_per_pos[i]` 是「至少提出到第 i+1 个」的步数 |
| `vllm/v1/core/sched/scheduler.py:1906` | `num_accepted = max(len(generated_token_ids) - num_sampled, 0)`：接受数就是本步提交的 token 数减一 |
| `vllm/v1/core/sched/scheduler.py:2722` | `if not self.log_stats or not num_draft_tokens: return None`：没有草稿调度的步不进入统计 |
| `vllm/v1/worker/gpu/async_utils.py:48` | `StepTimingCollector`：用 CUDA event 分别量 `forward_ms` 与 `drafter_ms`；默认只在自适应验证的标定里打开 |

一个容易读错的地方：两个逐位置计数之比的分母是「至少提出到第 i+1 个」的步数，
所以它是**生存函数** $s_i=\Pr(A\ge i+1)$，不是条件概率。
条件概率要再除前一项：$a_i=s_i/s_{i-1}$。
两种写法给出的期望前进长度相同（$E[N]=1+\sum_i s_i=1+\sum_i\prod_{j\le i}a_j$），
但把 $s_i$ 当 $a_i$ 再连乘，或者把聚合接受率直接当 $p$ 代入几何公式，都会系统性低估 $E[N]$。

本版本的 ngram 路线会回退到 V1 model runner，引擎日志原文是
`Model Runner V2 does not yet support ngram/ngram_speculative decoding; using the V1 model runner instead`。
如果要让「有投机」与「无投机」的阶段计时同源，就要显式固定 `VLLM_USE_V2_MODEL_RUNNER=0`，
并把这个开关写进实验记录。

### 设计取舍

- **状态归属。** 调度器持有请求进度；目标与草稿执行路径各自维护所需缓存。接受后，二者必须对同一个已提交前缀达成一致。
- **不变量。** 未验证的后缀不能泄漏到输出；回退后的有效 KV 长度必须与下一轮输入位置匹配。复用内存块之前还要确认引用已释放。
- **草稿长度。** 增大 k 同时增加潜在进展与验证工作量。应在目标并发和上下文下扫描，不能只按平均接受率选择。
- **共享隐藏状态与独立模型。** 前者可减少重复计算，但绑定目标架构与训练产物；后者更容易独立替换，却增加权重、KV 和前向成本。不存在由方法名称决定的固定性能排序。
- **增加后端。** 不只增加一个配置枚举，还要实现提案输入、位置与 mask 布局、随机验证、接受长度回传、缓存回退及停止处理。参数兼容性在初始化检查，前缀和缓存一致性在每轮检查。

上述取舍为机制分析，不代表上游正式否决了某种替代方案。

## 工程实现 · mini 实现

先用一个三分类分布检查拒绝采样的概率质量，不需要 GPU。下列实现枚举所有分支，验证一次提案最终返回的分布，而不是用少量随机样本近似它：

```python
def corrected_distribution(target, draft):
    assert len(target) == len(draft) and target
    assert all(p >= 0 for p in target + draft)
    assert abs(sum(target) - 1) < 1e-12
    assert abs(sum(draft) - 1) < 1e-12
    accepted = [min(p, q) for p, q in zip(target, draft)]
    residual = [max(p - q, 0) for p, q in zip(target, draft)]
    rejected_mass = 1 - sum(accepted)
    if rejected_mass < 1e-12:
        return accepted
    normalizer = sum(residual)
    return [a + rejected_mass * r / normalizer
            for a, r in zip(accepted, residual)]

p = [0.5, 0.3, 0.2]
q = [0.2, 0.5, 0.3]
assert all(abs(a - b) < 1e-12
           for a, b in zip(corrected_distribution(p, q), p))
assert corrected_distribution(p, p) == p
```

把拒绝后的残差改成直接从 P 重采样，再枚举一次，结果通常不再等于 P。

完整的多 token 参照实现在 `labs/L5/speculative_reference.py`：小词表 Markov 链上实现 γ 步提案、
逐位置验证、`max(0, p−q)` 残差采样与 EOS 吸收，再把长度 4 的全部 625 条序列枚举出来对拍。
参照实现的序列级总变差 0.0221，与「直接用目标分布采样」的噪声地板 0.0217 同量级；
条件前缀的 185 个组合里最大 $|z|=3.19$；回滚的提交长度不变量在 9,226 个轮次上 0 违例。
三个错误变体（全部接受、拒绝后抽 $p$、拒绝后抽 $q$）都能给出正确的单位置边际，
但序列级总变差 0.16–0.32、最大 $|z|$ 38–52——**边际正确不足以说明分布正确**。
输出见 `results/local/5.5/speculative-reference-20260913/`。

k=8 是所测点中的最快值，不是已经找到的全局最优值。此组未记录各 k 的接受率，也没有重复测量分布。

### 逐位置接受统计与阶段计时

对同一份引擎，用上表的观测点扫 k=1/2/4/8/15，两种输入各一遍（batch=1，贪心，返回 200 token）。
$s_i$ 是引擎的两个逐位置计数之比（生存函数），`E[N]` 取 $1+\sum_i s_i$；
「聚合几何」是把 $\sum\text{accepted}/\sum\text{draft}$ 当 $p$ 代入 $(1-p^{k+1})/(1-p)$：

| 输入 | k | $s_i$ | E[N] | 聚合几何 | 相对差 |
|---|---:|---|---:|---:|---:|
| 抄写 | 1 | 0.970 | 1.970 | 1.970 | +0.0% |
| 抄写 | 2 | 0.971, 0.956 | 2.926 | 2.891 | −1.2% |
| 抄写 | 4 | 0.976, 0.951, 0.951, 0.951 | 4.829 | 4.591 | −4.9% |
| 抄写 | 8 | 0.917×7, 0.875 | 8.292 | 6.391 | −22.9% |
| 抄写 | 15 | 1.000×4, 0.933×2, 0.800×9 | 14.067 | 6.906 | −50.9% |
| 自由创作 | 1 | 0.640 | 1.640 | 1.640 | +0.0% |
| 自由创作 | 2 | 0.684, 0.491 | 2.175 | 1.933 | −11.1% |
| 自由创作 | 4 | 0.740, 0.380, 0.180, 0.180 | 2.480 | 1.576 | −36.4% |
| 自由创作 | 8 | 0.632, 0.395, 0.237×3, 0.184×3 | 3.289 | 1.401 | −57.4% |
| 自由创作 | 15 | 0.676, 0.441, 0.176×3, 0.118×3, 0.121×3, 0.125×4 | 3.864 | 1.238 | −68.0% |

两个结论：**逐位置口径与聚合口径在 k 变大时差距迅速扩大**（本组最大 −68%），
所以「接受率 31% 所以 E[N] 只有 1.3」这类推算不成立；**位置越靠后接受率越低**，
`k=15` 的抄写任务前四个位置是 1.000，第九个之后掉到 0.800。

同一份统计还能给出接受长度分布，并与 $s_i$ 推出的 $P(A=i)$ 对齐
（$P(A=0)=1-s_0$，$P(A=i)=s_{i-1}-s_i$，$P(A=k)=s_{k-1}$）：

| 输入（k=4） | 有草稿的步 | 接受长度分布 | P(A=i) 预测 = 实测 |
|---|---:|---|---|
| 抄写 | 41 | 0:1, 1:1, 4:39 | 0.024, 0.024, 0, 0, 0.951 |
| 自由创作 | 50 | 0:13, 1:18, 2:10, 4:9 | 0.260, 0.360, 0.200, 0, 0.180 |

阶段计时（`execute_model` 前后各一个 CUDA event；草稿用包住 `drafter.propose` 的墙钟）：

| 输入 | 无投机：步数 / 每步前向 | 投机 k=4：步数 / 每步前向 | 前向比值 | 草稿 ms/步 | 端到端加速 |
|---|---:|---:|---:|---:|---:|
| 抄写 | 201 / 4.463 ms | 41 / 4.754 ms | 1.07× | 0.028 | 4.15× |
| 自由创作 | 201 / 4.449 ms | 50 / 4.632 ms | 1.04× | 0.029 | 1.46× |

验证一次要算 k+1 个位置，但**每步前向只贵 4–7%**：decode 是权重带宽受限的，
多算的几个位置复用同一次权重读取。ngram 的草稿是 CPU 查表，0.03 ms/步，
相对 4.7 ms 的前向可以忽略。这条数字对「草稿模型」不成立——它的草稿本身就要一次前向。

提交与回滚用两条判据检查。第一条是统计口径的自洽：由
`num_accepted = len(generated) − num_sampled`，$\sum(\text{accepted}+1)$ 应当只覆盖
**有草稿的步**；实测三轮都是「生成 160 token、35 次前向、33 个有草稿的步、
$\sum(\text{accepted}+1)=158$、未计入统计的 token = 1」，差值正好是没有草稿的步数，
不会为负。第二条是输出一致：同一 prompt、同一贪心设置下，投机与不投机的
token 序列逐位相同（各 160 个）。被拒位置的草稿不进入输出，KV 有效长度按接受数截断，
这两条一起覆盖了提交/回滚路径。

|---|---:|---:|---:|---|---|

四点：

1. **k 有明确下界。** DFlash 在 k=1/2 时比普通 decode **更慢**（191.8/288.2 对
   345.8 tok/s）：草稿与验证的固定成本还没被多 token 前进摊平；k=4 才转正（1.32×），
   k=8 到 2.13×。这与机制一节"一轮成本必须包含草稿"一致，但只有实测能给出这个下界
   落在 k=3–4 之间。
2. **任务决定哪种草稿划算。** 抄写任务上 ngram k=8 比 DFlash k=8 快（896.3 对
   735.2 tok/s），因为要抄的内容就在上下文里；GSM8K 这类自由推理上 ngram 只涨 18%
   （92.2 → 108.9），EAGLE3 涨到 1.94×。**同一目标模型内，草稿方法的排名随任务翻转。**
3. **batch 放大收益但不改变顺序。** DFlash k=8 相对基线的倍数在 B=1 是 2.13×、B=16
   降到 1.55×：批次本身已经把权重读取摊薄，投机的边际收益随之变小。
4. **token 一致性不是自动成立的。** DFlash 一侧七个配置的输出 sha1 全部相同；EAGLE3
   一侧 k=1/k=2 的 B=1 档与基线不同（`a942e735cfb6` 对 `7c68ee6773ce`，前 8 个 token
   相同），k=4 又回到基线。贪心 + 拒绝采样在理论上保持分布，**实现中的浮点与归约顺序
   仍可能翻转近似并列的 argmax**；换草稿版本或目标 revision 后必须做逐 token 对拍，
   不能只看接受率。

GSM8K 的分数在这组预算下只有 0–1/24：B=1 档每条输出长度恰好等于 `max_tokens=192`，
**推理被截断**。分数只能说明两侧用了同一判据，不能当质量结论；质量对照需要把预算提到
模型能写完推理的长度再比。

抄写任务上：

| 路径 | B=1 tok/s | B=4 tok/s | 平均前进 | 输出 sha1（B=1 / B=4） |
|---|---:|---:|---:|---|
| 普通 decode | 104.7 | 386.4 | — | 456600e3ce11 / 4e75d6ff419a |
| MTP k=1 | 176.5 | 630.0 | 1.96 | 同上 |
| MTP k=2 | 226.0 | 690.3 | 2.82 | 同上 |

**MTP 从 k=1 就转正**（1.63–1.69×），不像 DFlash 要等到 k=4：它的输入只是主干最后一个
hidden 与当前 token embedding 的拼接，草稿本身只有一个块，草稿成本比独立模型低。
四个配置的输出 sha1 与基线逐位相同，这条路径在本机通过了 token 级一致性检查。

### 消融与补测

1. 向 k=12、16 扩展扫描，比较草稿时间、验证时间及端到端吞吐，而不只比较接受率；
   注意 k 越大、每轮步数越少，$s_i$ 的抽样噪声会让生存函数出现轻微非单调（本节 k=15、34 步的
   自由创作已出现 $-0.004$ 的 $P(A=i)$）。
2. 把阶段计时换成 `StepTimingCollector`（在支持的 runner 上），核对自装 CUDA event 的读数。
3. 对同一输入验证普通与投机的贪心 token 序列；随机模式另做分布检查，不能要求同 seed 的序列逐位相同。
4. **SGLang 侧的草稿路线对照未做**：本章的 DFlash/EAGLE3/MTP 实测都在 vLLM 0.29.0 上；SGLang 0.5.19 有 `models/qwen3_5_mtp.py` 与对应的 speculative 入口，需在同一负载下补测。容量要按主干、草稿、KV、激活与 workspace 一起算——Qwen3-8B + EAGLE3 在 `gpu_memory_utilization=0.55` 下 KV 只剩 0.01 GiB、引擎起不来，本章用 0.9 才跑通。

## 前沿

后续可比较动态草稿长度、树形候选和目标/草稿共享状态。它们改变的分别是每轮预算、验证形状和重复计算，不能仅按草稿方法名称推断收益。本章已实测 EAGLE3、DFlash 与内置 MTP（同一负载下的接受长度与时间见 lab），**Medusa 与 suffix、以及 SGLang 侧的草稿路线仍是 `UNVERIFIED`**，需要兼容权重、固定版本源码与同负载记录。

## 陷阱

1. **把聚合接受率当作各位置条件接受概率。** 几何级数模型需要额外假设。
2. **跨实验反推验证成本。** k=4 的统计不能直接解释 k=8 的耗时。
3. **随机验证只比较 token 是否相同。** 保持分布需要正确的接受与残差规则。
4. **只回退输出，不回退缓存。** 下一轮会读到不属于已提交前缀的状态。
5. **只报“快几倍”。** 同时报告模型、草稿方法、输入、并发、长度、计时与停止规则。
6. **把类型枚举当作性能证据。** 声明支持不等于当前硬件上已经运行。

## 自测题

<details markdown="1"><summary>1. k=4，所有草稿都接受时，一轮最多前进多少 token？</summary>

通常是 5 个：4 个草稿与 1 个目标模型额外 token。EOS、最大输出长度及具体接口的提交边界可能使其少于 5。
</details>

<details markdown="1"><summary>2. p=0.957、k=8 时得到 E[N]≈7.60，能否据 6.72× 算出验证只贵 13%？</summary>

不能。这要求 p 是同一实验的适当条件接受概率，且加速比来自相同稳态口径。本章的 95.7% 来自 k=4 的聚合计数；k=8 没有这些统计。总迭代成本也不等于目标验证前向成本。
</details>

<details markdown="1"><summary>3. 拒绝后为什么不能简单地从目标分布再抽一次？</summary>

接受分支已经贡献 min(P,Q) 的概率质量。拒绝分支应补回剩余的正差，而不是再按 P 增加一份，否则最终分布一般不等于 P。可用 mini 实现枚举验证。
</details>

<details markdown="1"><summary>4. batch=64 的收益低于 batch=1，是否应该关闭投机？</summary>

不一定。本组仍有 1.62× 吞吐收益。还要检查目标 SLO 下的延迟分布、草稿资源及并发容量，再决定是否动态关闭。
</details>

<details markdown="1"><summary>5. 模型自带 MTP 头，是否意味着草稿没有成本？</summary>

不是。预测模块仍需执行，也可能持有独立缓存；验证、状态传递与回退也有成本。是否更省取决于具体架构、实现和输入分布。
</details>
