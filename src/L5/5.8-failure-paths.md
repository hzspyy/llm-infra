## 本章回答三个问题

正常请求跑得快只是一半。另一半是：**出事的时候，谁负责把资源收回来？**

1. 客户端断连之后，那条请求的 KV 块什么时候被释放？怎么证明它真的被释放了？
2. 队列积压时靠什么反压？不反压会怎样，反压过头又会怎样？
3. 块池不够用时会发生什么？抢占要付多少代价？

本章在 5.7 的 nanoserve 上补四条路径（抢占、超时、背压、泄漏），
再拿真实 vLLM 对照。**最重要的一条结论：泄漏不会报错。**
把 `abort()` 写错一行，引擎不崩、日志干净、输出正确，
只是从第 16 条请求开始**再也不产出任何 token**。

## 机制拆解

### 取消的清理内容取决于请求当时在哪

同一条 `abort()`，让受害者分别停在三种状态（`labs/L5/nanoserve/run_failures.py` case 1）：

| 取消时的状态 | 在等待队列 | 在运行集 | 持有的块 | 空闲块 | 归还 | 旁边那条请求的引用计数 |
|---|---|---|---|---|---|---|
| waiting | 是 | 否 | `[]` | 48 → 48 | **0** | 未变 |
| prefill | 否 | 是 | `[5,6,7,8,9]` | 38 → 43 | **5** | 未变 |
| decode | 否 | 是 | `[5,6,7,8,9]` | 38 → 43 | **5** | 未变 |

三点：

- **waiting 状态下取消不需要还块**，因为块是在准入那一刻才分配的。
  一个只处理"运行中取消"的实现，在这条路径上会静默地什么都不做——**看起来是对的**。
- **prefill 和 decode 归还的块数一样**，因为 nanoserve 在准入时就按整段 prompt 分好了块表。
  换成"边算边分"的实现，这两格就会不同。
- **旁边那条请求的引用计数一格没动**。这是最容易写错的地方：
  取消时把别人共享的前缀块也释放掉，症状是另一条请求的 KV 被后来者覆盖，
  输出变成乱码，而且只在有前缀复用时才出现。

三条路径跑完都做泄漏检查，全部 `leaked: 0`。

### 断连：引擎跑在客户端前面

在 HTTP 完整链路上执行断连测试（`labs/L5/nanoserve/drive_server.py` 的 C 场景）。
客户端读到第 5 个 token 就关掉 socket，服务端日志：

```json
{"kind": "disconnect", "req": "C1", "aborted": true, "blocks_freed": 2, "sent_tokens": 18}
{"kind": "close", "req": "C1", "state": "aborted", "finish_reason": "client-disconnect", "free_blocks": 512}
```

**客户端收到 5 个，服务端已经发出 18 个。** 中间 13 个 token 是白算的：
引擎按自己的节奏推进，SSE 的写入先进内核缓冲区，客户端还没读到就走了。

这解释了为什么"断连要尽快传下去"是有价值的：晚一步，就多浪费一步的算力。
也解释了为什么不能靠 `writer.drain()` 单独发现断连——
缓冲区没满时 `drain()` 立刻返回，什么都察觉不到。nanoserve 的做法是
**同时挂一个 `reader.read(1)`**，对端半关时它先醒：

```python
# labs/L5/nanoserve/server.py
watcher = asyncio.create_task(reader.read(1))
...
done, _ = await asyncio.wait({get, watcher}, return_when=asyncio.FIRST_COMPLETED)
if watcher in done:
    get.cancel()
    raise ConnectionResetError("client closed")
```

断连之后 `/health` 报 `free_blocks: 512`，与启动时一致。

### 超时：队列里超时和运行中超时是两件事

给两条请求各挂一个 deadline，一条注定在队列里等到超时，一条在 decode 中途超时：

```json
{"kind": "timeout", "req": "queued", "from_state": "waiting", "waited_ms": 53.48}
{"kind": "abort",   "req": "queued", "from_state": "waiting", "blocks_returned": 0, "free": 60}
{"kind": "timeout", "req": "slow",   "from_state": "decode",  "waited_ms": 254.57}
{"kind": "abort",   "req": "slow",   "from_state": "decode",  "blocks_returned": 5, "free": 64}
```

`queued` 一个 token 都没产出就被砍了，归还 0 块；
`slow` 已经吐了 25 个 token，归还 5 块。

**"超时"这个词在两种情况下含义完全不同**：前者是"我们根本没开始服务你"，
后者是"我们服务到一半放弃了"。对上游来说，第一种应该重试，第二种重试大概率还会超时。
只回一个 504 的 API 把这两件事混在了一起。

### 抢占：块不够时踢谁，丢什么

nanoserve 把块池压到 24 块（384 个 token 的 KV），塞 6 条各要 104 token 的请求，
显然装不下。开与不开抢占：

| | 抢占开 | 抢占关（5.7 的行为） |
|---|---:|---:|
| 结果 | 6 条全部完成 | **`OutOfBlocks` 崩在第 26 步** |
| 产出 token | 384 | 150（然后崩） |
| step 数 | 128 | 26 |
| 墙钟 | 1.51 s | 0.29 s |
| 抢占次数 | 4 | 0 |
| **丢弃并重算的 KV token** | **279** | 0 |
| 结束后块池 | `leaked: 0` | **24 块全部卡死** |

**代价是 279 / 384 = 73% 的重算。** 这不是小数目：
为了不崩，系统多算了将近一倍的 token。

抢占的具体动作（`labs/L5/nanoserve/failure.py`）：

```python
victim = max(victims, key=lambda r: r.arrival)   # 踢最新来的
self._free(victim)                                # 块全部归还
victim.num_computed = 0
victim.output_ids.clear()                         # 已生成的 token 一并丢弃
self.waiting.appendleft(victim)
```

如果抢占后仍允许新请求立即进入，资源不足可能反复发生：
刚腾出来的块在同一个 step 里被 `_schedule()` 的准入立刻吃掉，
下一步照样不够，最后还是崩了（`preempted: 2` 之后 `crashed: 块池空了`）。
因此，准入还需要检查剩余资源水位：

```python
def _grow_block_table(self, req, upto):
    if req.state is State.WAITING:            # 只拦准入路径
        need = ceil(upto / block_size) - len(req.block_table)
        if self.pool.num_free - need < self._running_reserve():
            raise OutOfBlocks("watermark：要给正在跑的请求留块")
    super()._grow_block_table(req, upto)
```

**「腾出资源」和「不让新请求立刻抢走」必须成对出现**，否则前者是无效功。

### 背压：都慢，还是一部分被拒

24 条请求同时到达，`max_num_seqs=4`。等待队列设不设上限：

| 队列上限 | 接受 | 拒绝 | 接受者的 p50 延迟 | 最大延迟 | step 数 |
|---:|---:|---:|---:|---:|---:|
| 不设 | 24 | 0 | 734.1 ms | 1100.1 ms | 96 |
| 12 | 12 | 12 | 366.1 ms | 548.9 ms | 48 |
| 4 | 4 | 20 | 183.0 ms | 183.0 ms | 16 |

**延迟几乎与队列长度成正比**（734 / 366 / 183 ms，比值 4 : 2 : 1），
这是排队论最朴素的形态：队列只会把延迟往后推，不会让系统变快。

所以"不设上限"不是更友好，而是**把拒绝换成了超时**——
排在第 24 位的用户等 1.1 秒，如果他的客户端设了 500 ms 超时，
他既没拿到结果，还占了引擎 1.1 秒的算力。**显式拒绝至少是快的、可重试的、
不浪费算力的。**

队列上限该设多少，取决于你能接受的 p99：
本章的负载下，队列 12 对应 p50 366 ms、最大 549 ms。

### 泄漏：唯一一条不报错的失败路径

把 `abort()` 写错——请求从队列里摘掉了，块表清空了，但引用计数没减：

```python
target.block_table = []            # 表清空了，引用计数没减
```

反复"接一条、跑三步、取消"，20 次：

| 第几条请求 | 0 | … | 15 | **16** | 17 | 18 | 19 |
|---|---:|---|---:|---:|---:|---:|---:|
| 取消后的空闲块（32 块池） | 30 | … | 0 | 0 | 0 | 0 | 0 |
| 产出 token | 3 | … | 3 | **0** | 0 | 0 | 0 |

**每次取消漏 2 块，第 16 条把池子抽干。从第 16 条开始，
每条请求产出 0 个 token——而引擎没有抛任何异常。**

原因是准入路径上的 `OutOfBlocks` 被 `_schedule()` 捕获了（那是设计如此：
块不够就先不收），于是请求永远停在 waiting，引擎每步都在空转。
日志干净，`/health` 也返回 200。

对照组（正确的 abort）：20 条全部产出 3 个 token，每次取消后空闲块都回到 32。

这就是为什么 nanoserve 每条路径结束都跑一次 `leak_check()`：

```python
def leak_check(self):
    held = {b.block_id: b.ref_count for b in self.pool.blocks if b.ref_count}
    return {"held_blocks": held, "free": self.pool.num_free,
            "total": len(self.pool.blocks), "leaked": len(held)}
```

**泄漏检查不是测试的装饰，它是这条失败路径唯一的探测器。**

## 工程实现 · 源码解析：真实 vLLM 怎么做

固定版本 vLLM 0.29.0。把 KV 预算压到 `gpu_memory_utilization=0.15`
（实测 460 块 × 16 = 7360 个 token 的 KV），塞 48 条各生成 512 token 的请求，
需要的 KV 约 25 000 个 token —— 装不下三倍多。

### A. 抢占：踢最新的，全部重算

`v1/core/sched/scheduler.py:705`，非优先级模式下就一行：

```python
else:
    preempted_req = self.running.pop()
```

`self.running` 按加入顺序排，`pop()` 取最后一个——**踢最新加入的**。
nanoserve 的 `max(victims, key=lambda r: r.arrival)` 是同一个策略。

被抢占的请求做什么（`scheduler.py:1405` 的 `_preempt_request`）：

```python
self._free_request_blocks(request)
self.encoder_cache_manager.free(request)
self._inflight_prefills.discard(request)
request.status = RequestStatus.PREEMPTED
request.num_computed_tokens = 0
```

**`num_computed_tokens = 0`：已经算过的全部作废，重来。**
和 nanoserve 一样，vLLM 选的是"丢弃重算"而不是"换出到 CPU"。

实测（把 `_preempt_request` 包一层数出来）：

| | 实测值 |
|---|---:|
| KV 块 | 460 × 16 = 7360 token |
| 请求 | 48 条 × 512 token |
| **抢占次数** | **55** |
| 被抢占过的请求数 | 35 / 48 |
| **被丢弃的已算 token** | **13 437** |
| 实际产出 token | 24 576 |
| 墙钟 | 5.94 s |
| finish_reason | 全部 `length` |

**13437 / 24576 = 55% 的重算开销**，和 nanoserve 那 73% 同一个量级。
48 条请求里有 35 条至少被踢过一次，其中 7 条被踢了不止一次（55 次 / 35 条）。

被踢的顺序是 47、46、45、44、43……**严格从最新往回踢**，与源码一致。

::: warning vLLM 不打抢占日志
本次运行把 `vllm` logger 调到 DEBUG，抓到的 393 行日志里
**匹配 preempt / swap / recompute 的行数是 0**。
抢占只进 `SchedulerStats`（`v1/metrics/stats.py:122` 的 `preempted_requests`），
不写日志。

含义很实际：**线上服务被抢占打得半死时，日志里看不出来**。
必须去看 metrics，或者像本章一样自己包一层。
:::

### B. 取消：块确实回来了

对一条正在跑的请求调 `abort_request`，前后读块池：

```json
{"kind": "B_abort",
 "before": {"unfinished": 1, "free_blocks": 457},
 "after":  {"unfinished": 0, "free_blocks": 459},
 "has_unfinished": false}
```

**归还 2 块**（该请求 prompt 约 20 个 token，占 2 块），未完成请求数 1 → 0。
调用链是 `LLMEngine.abort_request`（`v1/engine/llm_engine.py:212`）：

```python
request_ids = self.output_processor.abort_requests(request_ids, internal)
self.engine_core.abort_requests(request_ids)
```

**两处都要动**：`output_processor` 管输出通道（对应 nanoserve 的 `Stream`），
`engine_core` 管调度器与块池。少动一处就是前面那两类 bug 之一。

### C. 预算太小时的失败：连块都分不出来

第一次实验用 `gpu_memory_utilization=0.12` 直接起不来：

```
ValueError: No available memory for the cache blocks. Try increasing
`gpu_memory_utilization` when initializing the engine ...
```

`v1/core/kv_cache_utils.py:859` 的 `_check_enough_kv_cache_memory`。
0.12 × 31.4 GiB = 3.77 GiB，而权重加激活约 4.0 GiB，剩给 KV 的是负数。

**这是唯一一条在启动时就报错的失败路径，因此也是最好处理的一条。**
其余几条（抢占、泄漏、断连）全都在运行时静默发生。

## 设计取舍

### 1. 丢弃重算 vs 换出到 CPU

两家都选了丢弃重算。代价一目了然：本章实测 55%（vLLM）与 73%（nanoserve）的重算。

换出（swap）把 KV 拷到主机内存，恢复时拷回来。账很好算（0.2、1.3）：
Qwen3-1.7B 每 token 的 KV 是 112 KiB，一条 512 token 的请求是 56 MiB。
PCIe 4.0 x16 单向约 25 GB/s，来回 112 MiB ≈ 4.5 ms；
而重算 512 个 token 的 prefill 在本机是几十毫秒的量级。**换出看起来更划算。**

那为什么两家都不默认换出？源码给了线索：`_preempt_request` 只做了
`num_computed_tokens = 0` 和释放块，没有任何拷贝路径的状态。
加上换出意味着：块池要区分"在 GPU"和"在 CPU"，恢复时要等拷贝完成才能调度，
调度器要处理"拷了一半"的中间态，PD 分离时还要和 KV 传输抢 PCIe。
**换出把一个同步的状态机变成了异步的。**

**设计原则：重算是"用算力换实现简单"。当算力便宜而复杂度昂贵时，
这笔交易是划算的——尤其是抢占本来就是异常路径，不该为它引入常态复杂度。**

（本段的换出耗时是按带宽推算的，**本章没有实测换出路径**。）

### 2. 有界队列以拒绝率换取延迟约束

背压那张表说明了一件反直觉的事：**不设队列上限并不更友好**。
24 条请求下，不设上限的 p50 是 734 ms、最大 1100 ms；
上限 12 时是 366 / 549 ms。多出来的那 12 条并没有"被服务"，
它们只是在队列里把所有人的延迟推高了一倍。

如果客户端有超时（真实系统总是有的），排在后面的请求最终**既拿不到结果、
又已经消耗了引擎的资源**——这是最糟的一种结局。显式拒绝可避免继续消耗模型计算，但入口处理、重试和负载恢复仍有成本。

**这条判断在 8.2/8.4 会再出现：任何没有上限的队列都是一个把延迟藏起来的地方。**

### 3. 资源不变量需要可执行的断言与告警

本章五条路径里，四条会以某种方式暴露自己：崩溃、超时、拒绝、日志。
只有泄漏不会。它的症状是"引擎慢慢停止接客"，
而且**从症状到原因之间隔着任意长的时间**。

nanoserve 在块池中统一保存引用计数（5.7 §2），由 `leak_check()` 检查请求结束后是否仍有占用。
代价是每条测试路径末尾都得记得调它——本章和 5.7 一共 14 处。

反过来说，如果块的归属信息分散在请求对象、调度器和池子三处，
这个断言就写不出来，泄漏也就无从检测。
集中管理状态后，资源回收条件更容易检查。

### 4. 抢占与准入必须成对

抢占之后还需要限制新请求进入，否则
腾出来的资源会被立刻消耗掉，抢占退化成纯粹的浪费（丢了 128 个 token 的 KV，
系统照样崩）。

vLLM 用 watermark 做同一件事。这条规律在别处也成立：
**任何"回收资源"的机制都要配一个"暂缓分配"的机制，
否则回收只是给新的分配让路。**

## 前沿

- **抢占之外的第三条路：把 KV 存到别处。** 8.6 会讲 KV 分层存储
  （GPU → CPU → 远端）。抢占时不丢也不换出，而是降级到更慢的一层。
  代价是恢复时的延迟不确定。
- **优先级调度。** vLLM 已经有 `SchedulingPolicy.PRIORITY`
  （`scheduler.py:670`），抢占时按 `(priority, arrival_time)` 选受害者。
  一旦引入优先级，"谁被牺牲"就成了产品决策而不是工程决策（8.8 租户隔离）。
- **把断连传得更快。** 现在的链条是 socket → 协程 → engine.abort。
  在多进程引擎里这还要跨一次进程边界。本章实测断连时已经浪费了 13 个 token，
  额外通信可能增加取消延迟，但需测量，不能直接按跳数推算多生成的 token 数。
- **崩溃恢复。** 本章没有涉及 worker 进程崩溃。
  vLLM 把引擎放在独立进程里（5.7），所以 HTTP 侧崩了引擎还在；
  反过来引擎崩了，所有在跑的请求一起丢——**本章尚未验证 worker 崩溃后的请求恢复**，
  恢复方案需要重算、检查点或外部状态副本；不同实现的支持范围需分别核对。

## 陷阱

1. **泄漏不报错。** 本章实测：每次取消漏 2 块，第 16 条请求开始产出 0 token，
   引擎不崩、日志干净、`/health` 返回 200。只有块池断言能发现。
2. **"取消"在三种状态下清理的东西不同。** 只处理"运行中取消"的实现，
   在 waiting 状态下静默无操作，看起来是对的。
3. **取消要同时动输出通道和块池。** vLLM 的 `abort_request` 两处都动
   （`llm_engine.py:212`），少一处就是泄漏或者悬挂的连接。
4. **不能靠 `drain()` 发现断连。** 缓冲区没满时它立刻返回。要另挂一个读任务。
5. **抢占必须配准入闸。** 只抢占不拦准入，腾出来的块会被同一步的准入吃掉，
   该错误配置丢弃了 128 个 token 的 KV 后，仍因块不足而失败。
6. **抢占的代价是重算，而且不小。** 实测 vLLM 55%、nanoserve 73%。
7. **vLLM 不打抢占日志**，只进 metrics。线上要自己观测。
8. **无上限的队列不是更友好**，它把拒绝换成了超时，而且浪费算力。
9. **两种超时含义不同**：队列里超时（从未被服务，可重试）vs 运行中超时
   （服务到一半放弃，重试大概率还超时）。只回 504 把两者混为一谈。
10. **`gpu_memory_utilization` 太小时是启动期报错**，反而是最好处理的失败。

## 自测题

<details markdown="1">
<summary>1. 客户端断连后，那条请求的 KV 块什么时候被释放？怎么证明？</summary>

链条有五步（本章实测走通）：

1. 客户端关 socket → 服务端挂着的 `reader.read(1)` 返回 EOF；
2. HTTP 协程抛 `ConnectionResetError`；
3. `except` 里调 `engine.abort(rid, "client-disconnect")`；
4. `abort` 把请求从运行集摘掉，遍历它的 `block_table` 逐块 `release()`，引用计数归零的块回到空闲链；
5. `finally` 里清掉输出通道的 `Stream`。

**块是在第 4 步释放的**，实测这条请求归还 2 块，之后 `/health` 报
`free_blocks: 512`，与启动时一致。

请求结束后，使用断言检查块池是否回到初始状态：
`leak_check()` 要求结束后没有任何 `ref_count > 0`。
本章和 5.7 一共 14 处这样的断言。

顺带一个实测细节：客户端只收到 5 个 token，服务端已经发出 18 个——
**中间 13 个的算力白花了**。断连传得越快，浪费越少。
</details>

<details markdown="1">
<summary>2. 队列积压时靠什么反压？不反压会怎样？</summary>

靠**给等待队列设上限，满了就直接拒绝**（HTTP 503），而不是让请求排着。

本章实测，24 条请求同时到达、`max_num_seqs=4`：

| 队列上限 | 接受 / 拒绝 | p50 | 最大 |
|---:|---|---:|---:|
| 不设 | 24 / 0 | 734 ms | 1100 ms |
| 12 | 12 / 12 | 366 ms | 549 ms |
| 4 | 4 / 20 | 183 ms | 183 ms |

延迟几乎与队列长度成正比（4 : 2 : 1）。**队列只会把延迟往后推，不会让系统变快。**

不反压的后果不是"大家都慢一点"，而是：客户端有超时，排在后面的请求
**既拿不到结果，又已经消耗了引擎的算力**。显式拒绝可减少无效计算；重试仍需退避、期限和次数限制，避免进一步放大过载。

上限设多少取决于能接受的 p99，得测——本章负载下队列 12 对应最大 549 ms。
</details>

<details markdown="1">
<summary>3. 块池不够用时会发生什么？为什么"只抢占"不够？</summary>

不处理就是 `OutOfBlocks` 崩掉：本章实测在第 26 步崩，24 块全部卡死，0 条请求完成。

处理方式是**抢占**：踢掉最新加入的请求，把它的块全部归还，
`num_computed = 0`、已生成的 token 一并丢弃，放回队列重算。
vLLM 做的是同一件事（`scheduler.py:705` 的 `self.running.pop()` +
`_preempt_request` 里的 `num_computed_tokens = 0`）。

**只抢占不够**，因为腾出来的块会在同一个 step 里被 `_schedule()` 的准入吃掉——
该错误配置中抢占了 2 次、丢弃了 128 个 token 的 KV，最终仍然失败。
必须再加一道 watermark：准入时要留够正在跑的请求下一步要用的块。

代价是重算：nanoserve 实测 279 / 384 = 73%，真实 vLLM 实测 13437 / 24576 = 55%。
</details>

<details markdown="1">
<summary>4. 为什么两家引擎都选"丢弃重算"而不是"换出到 CPU"？</summary>

按带宽推算，换出**看起来**更划算：Qwen3-1.7B 每 token 的 KV 是 112 KiB，
512 token 的请求是 56 MiB，PCIe 4.0 x16 来回约 4.5 ms；
而重算 512 个 token 的 prefill 是几十毫秒量级。

但看 `_preempt_request` 的实现就明白代价在哪：它现在只做两件事
（释放块、`num_computed_tokens = 0`），是一个**同步**操作。
换出会引入：块池要区分在 GPU / 在 CPU，恢复要等拷贝完成才能调度，
调度器要处理"拷了一半"的中间态，PD 分离时还要和 KV 传输抢 PCIe。

**换出把一个同步的状态机变成了异步的**，而抢占本来就是异常路径，
不值得为它在常态代码里引入这份复杂度。

这是"用算力换实现简单"的典型交易。
（本段的 4.5 ms 是按带宽推算的，本章**没有实测换出路径**。）
</details>

<details markdown="1">
<summary>5. 一个引擎跑了几小时之后开始拒绝所有新请求，日志干净，没有报错。先查什么？</summary>

**先查块池的引用计数，而不是查日志。**

本章复现过这个症状：把 `abort()` 写错一行（请求摘掉了、块表清空了，
但引用计数没减），每次取消漏 2 块。32 块的池子在第 16 条请求上被抽干，
之后每条请求产出 0 个 token，**引擎没有抛任何异常**——
因为准入路径上的 `OutOfBlocks` 被调度器捕获了（设计如此：块不够就先不收），
请求永远停在 waiting，引擎每步空转。

诊断方法就是本章的 `leak_check()`：

```python
held = {b.block_id: b.ref_count for b in self.pool.blocks if b.ref_count}
```

结束（或空闲）时不应该有任何 `ref_count > 0`。如果有，看看它们属于谁——
本章的泄漏模式下，32 块全部 `ref_count = 1`，而 running 和 waiting 都是空的。
**"没有请求在跑，却没有空闲块"就是泄漏的签名。**

一般化：把这个断言做成周期性的监控，就是从"事后排查几小时"变成"几分钟内告警"。
</details>
