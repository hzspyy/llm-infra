## 本章回答三个问题

3.1 和 3.3 分别从 attention 的角度看过 prefill 和 decode。这一章换成整个引擎的视角，
回答三个问题：

1. 两相分别落在 roofline 的哪一侧，判据是什么？
2. 加大 batch 对两相的影响为什么相反，什么时候开始反过来？
3. 一个请求的时间花在哪几段，首个输出 token 由哪一次前向产生？

答案不是"prefill 算力受限、decode 带宽受限"这一句话：这取决于实际的 shape、batch 与后端，
所以本章把每一步调度的 token 数、KV 长度、时间戳都留下原始记录，再由账本解释它。

两类工作共用一次前向：一步里同时有未算完 prompt 的请求和已经进入 decode 的请求时，
调度器把两者放进同一个 batch——这就是**混合批**。8 条 decode 各出 1 个 token、
再加一条 8192 token 的 prompt，一个 step 的调度量是 $8+8184$（见本章 lab 的分块记录）。

长 prefill 会占满这一步的预算，期间所有 decode 都停住。**chunked prefill** 把长 prompt
切成多块插进连续的 step 里：单步时间变短，代价是长请求自己的首 token 变晚。两者之间的
取舍是本章实测最清楚的一条曲线。

## 机制拆解与推导

### 算术强度把两相分到 roofline 两侧

Qwen3-1.7B，权重 bf16 = 3.20 GiB，按 0.3 的实测算力 232000 GFLOP/s 与带宽 1608.6 GB/s，
简化权重模型的平衡点是 $232000/1608.6\approx144.2$ FLOP/byte：

| 相 | batch | 序列 | FLOP | 权重字节 | 算术强度 | 落在哪一侧 |
|---|---:|---:|---:|---:|---:|---|
| prefill | 1 | 2048 | 7.047e12 | 3.441e9 | **2048.0** | 算力 |
| prefill | 1 | 4096 | 1.409e13 | 3.441e9 | **4096.0** | 算力 |
| decode | 1 | 1 | 3.441e9 | 3.441e9 | **1.0** | 带宽 |
| decode | 8 | 1 | 2.753e10 | 3.441e9 | 8.0 | 带宽 |
| decode | 64 | 1 | 2.202e11 | 3.441e9 | 64.0 | 带宽 |
| decode | 256 | 1 | 8.809e11 | 3.441e9 | 256.0 | 算力 |

这张表由 `labs/L5/mini_phase_ledger.py` 生成。它把参与矩阵乘的权重都算进来，
并假设一批共享一次读取，于是 $I\approx BS$；embedding 查表、只算末位置的 lm_head、
KV 和中间张量都要另算（较细的账见 L0.2）。**144 是简化模型的平衡点，不是实测的瓶颈切换点**——
实测的切换要看下面两节的 step 账。

### 一个 step 的真实形状与读写账

把 mini 账本用在真实调度记录上：prompt 64 token、batch 1、层数 28、16 个 query head、
8 个 KV head、head_dim 128。

| step | 阶段 | 本步 token | Q（每层） | K/V 读取（每层） | 权重读 B | KV 读 B | KV 写 B | FLOP | 算术强度 |
|---:|---|---:|---|---|---:|---:|---:|---:|---:|
| 0 | prefill-last | 64 | [1,16,64,128] | [1,8,64,128] | 3.441e9 | 7.34e6 | 7.34e6 | 2.202e11 | 63.86 |
| 1 | decode | 1 | [1,16,1,128] | [1,8,65,128] | 3.441e9 | 7.45e6 | 1.15e5 | 3.441e9 | 0.998 |
| 2 | decode | 1 | [1,16,1,128] | [1,8,66,128] | 3.441e9 | 7.57e6 | 1.15e5 | 3.441e9 | 0.998 |
| 3 | decode | 1 | [1,16,1,128] | [1,8,67,128] | 3.441e9 | 7.68e6 | 1.15e5 | 3.441e9 | 0.998 |

`results/crater/5.1/walk-20260921/walk.txt` 同时记了这四步的 device 时间：5.12 / 3.14 / 3.14 / 3.14 ms。
第一步多出的约 2 ms 就是 64 倍计算量的代价——但注意它的算术强度只有 63.9，还没有越过 144，
所以**短 prompt 的 prefill 并未处于算力墙**。这也解释了 B 扫描里 prefill 加 batch 收益有限：
它不在"加 batch 也吃不饱"的极端，而在中间地带。

### 阶段判定不靠调用耗时差

不要用两次 `generate()` 的耗时相减来"分离 prefill 与 decode"：请求处理、排队、采样、
后端调度都在里面。本组实验用引擎自己的四个时间戳：

| 段 | 定义 |
|---|---|
| 排队 | `scheduled_ts − queued_ts` |
| prefill | `first_token_ts − scheduled_ts` |
| decode | `last_token_ts − first_token_ts` |
| 完整 | `last_token_ts − queued_ts` |

并用逐 step 记录回答"首个输出由哪一次 forward 产生"：在 `labs/L5/serve_protocol.py` 里，
每次 `schedule()` 的返回值携带 `num_scheduled_tokens`，请求对象的 `num_computed_tokens`
给出 before/after。核对结果是确定的：

```
首输出归属核对：35 次运行 / 635 条请求，异常 0 条；
  首次覆盖整段 prompt 的那次 forward 与被发出的 step 相差 {1: 635}（step）
```

635 条请求全部满足：产生首输出的那一步就是覆盖完整 prompt 的 prefill，采样发生在下一步之前。
`labs/L5/mini_phase_ledger.py` 用独立的实现复核了同一批工件的 114095 个 (step, 请求) 条目：
阶段判定不一致 0；每个 decode 步的调度 token 数都是 1；875/890 条请求满足
「各步调度 token 之和 = prompt + 生成 − 1」（少掉的那个 1 正是首 token 由 prefill 产生），
其余 15 条多出的量等于一次完整的 prompt+生成 —— 它们是被抢占后重算的请求。

### 逐 step 的 kernel 与形状账对齐

调度计数给出阶段，但"这一步真正发射了什么"要另取证据。`labs/L5/step_kernel_align.py`
在每个引擎 step 上挂 NVTX range 与 `torch.profiler.record_function`，并在 range 内
`torch.cuda.synchronize()`；导出 chrome trace 后按时间区间把 `cpu_op`（带 `Input Dims`）
与 CUDA kernel 归到 step。账本预测的是「本步参与矩阵乘的激活行数 = 本步调度 token 数」，
prompt 64 的实测（`results/crater/5.1/step-kernel-20260922/eager_p64/`）：

| step | 阶段 | 本步 token | device ms | kernel 数 | kernel 总 ms | CPU op ms | 激活行数实测 | 命中账本 |
|---|---:|---:|---:|---:|---:|---:|---|---|
| 0 | prefill-last | 64 | 8.73 | 417 | 3.24 | 9.41 | [1, 64] | 是 |
| 1 | decode | 1 | 7.52 | 385 | 2.93 | 9.60 | [1] | 是 |
| 2 | decode | 1 | 7.35 | 385 | 2.93 | 9.51 | [1] | 是 |
| 3 | decode | 1 | 7.56 | 383 | 2.92 | 9.93 | [1] | 是 |

`CPU op ms` 是逐条 `cpu_op` 事件的 dur 之和，嵌套调用（`aten::linear` 里再调 `aten::mm`）
会各自计时，绝对值偏大，它只用来定位某一步的宿主侧开销落在哪一类算子上。四条读法：

1. **账本在 kernel 层对得上。** 每一步都出现以本步 token 数为 M 的矩阵乘：prefill-last
   的 `aten::linear` 输入是 `[64, 2048]`，decode 的每一条是 `[1, 2048]`。矩阵乘调用
   339 条 = 113 个真实调用 × 3（同一调用在 trace 里被记为 `linear`、`matmul`、`mm`
   三条）；113 = 28 层 × 4 组投影（qkv、o、gate_up、down）+ 1 个 lm_head。
2. **prefill 与 decode 落在不同 kernel 族。** prompt 64 的 prefill-last 步里
   `cutlass_80_tensorop_bf16_s16816gemm_relu_bf16_128x64_64x3` 与
   `cutlass_80_tensorop_bf16_s16816gemm_relu_bf16_64x64_64x6` 各 28 次；decode 步里换成
   `internal::gemvx::kernel` 85 次（1.88 ms，占该步 device 时间的一半以上）加
   `cutlass_80_wmma_tensorop_bf16_s161616gemm_bf16_16x16_128x1` 28 次——85 + 28 = 113，
   正好是同一组矩阵乘。把 prompt 换成 2048，prefill 的 GEMM 变成
   `..._64x256_32x4` 56 次、合计 20.6 ms。**同一个算子在不同 M 下由 cuBLASLt 换档**，
   这就是"prefill 算力受限、decode 权重带宽受限"在 kernel 层的形态。
3. **注意力 kernel 随 KV 长度换路径。** prompt 64 的 decode 步用
   `flash_fwd_splitkv_kernel<128, 64, 64, 4>`；prompt 2048 之后第一次 decode（历史 2049）
   改用 `<128, 64, 128, 4>` 并多出 `flash_fwd_splitkv_combine_kernel` 28 次——KV 变长后
   FA2 走了 split-KV 归约路径。该步 device 时间 50.8 ms 而 kernel 总时间只有 3.18 ms，
   差值对应 CPU 侧 `_vllm_fa2_C::varlen_fwd` 的 41.5 ms：**换路径的首次调用成本集中在
   这一个 step**，8 步档的后 6 步稳定在 7.5–8.1 ms。
4. **device 跨度不是 kernel 时间。** 每步的 device 时间都比 kernel 总时间大 1.3–2.5 倍
   （8.73 对 3.24 ms）：step 里还有采样、块表收集、Python 侧调度与提交。这与 2.6 的
   "CPU 提交受限"判据一致——只看 kernel 之和会漏掉这段时间。

CUDA Graph 打开后，账本的原子形状看不见了：`graph_p64` 档每步只剩 3 条 `aten::mm`
（lm_head 的 `[1, 2048] × [2048, 151936]`），模型主体的调用被编译进图；kernel 数仍可
逐 step 归属（prefill-last 359、decode 382–384）。**图执行把 aten 级形状账藏进图里，
要看图内节点必须换工具**（5.4 用 nsys `--cuda-graph-trace=node`）。

nsys 侧在这里有自己的边界。按同一次运行采集后
（`results/crater/5.1/step-kernel-20260922/nsys_step_align.txt`）：

- `NVTX_EVENTS` 的 step 区间在 16.281–16.300 s，而 `CUPTI_ACTIVITY_KIND_RUNTIME` 在
  4.215–14.723 s、`CUPTI_ACTIVITY_KIND_KERNEL` 在 6.520–14.725 s，**两套时间戳的末端
  相差 1.575 s**；按区间比较或按 `correlationId` 关联都归到 0 个 kernel。
- `nsys stats --report nvtx_kern_sum` 与 `nvtx_gpu_proj_sum` 都没有把 `step*` range
  投影到 kernel；`--capture-range=nvtx --nvtx-capture=stepK` 采到 0 个事件。

因此本章的逐 step 归属由 profiler 口径（NVTX 标注 + CUDA event）承担，nsys 用于不依赖
NVTX 的独立核对：本次默认配置下 51 382 个 kernel 全部 `graphId IS NULL`（没有走 CUDA
Graph 重放），图内/图外的区分与图池账见 5.4。

## 工程实现 · 源码解析

### 调度器用两个计数判定阶段

vLLM 0.29.0 的 `Scheduler.schedule()`（`v1/core/sched/scheduler.py:501`）先算预算，再逐请求
决定本轮推进多少 token。对已经在跑的请求：

```python
num_new_tokens = (
    request.num_tokens_with_spec
    + request.num_output_placeholders
    - request.num_computed_tokens
)
if 0 < self.scheduler_config.long_prefill_token_threshold < num_new_tokens:
    num_new_tokens = self.scheduler_config.long_prefill_token_threshold
num_new_tokens = min(num_new_tokens, token_budget, input_budget - draft_slots)
```

（`v1/core/sched/scheduler.py:585-594`）此时 `num_new_tokens` 就是这一轮要补算的位置数：
未算完 prompt 的请求得到的是"剩余 prompt"的截断，已经算完的请求 `num_tokens_with_spec`
只比 `num_computed_tokens` 多一个（新生成的 token），于是自然得到 1。**decode 每步 1 个 token
不是特判，而是同一个式子的结果。**

`long_prefill_token_threshold`（`config/scheduler.py:70`，默认 0）是把长 prefill 主动切块的开关；
`input_budget = max_num_batched_tokens`（`v1/core/sched/scheduler.py:524`）才是每轮的总预算。
本章 lab 扫的正是后者：预算 128 时，8192 token 的 prompt 被切成 68 块。

KV 不够时调度器抢占请求，`_preempt_request`（`v1/core/sched/scheduler.py:1405`）把请求放回
等待队列并释放块；被抢占的请求 `num_computed_tokens` 归零，下次重新 prefill——这就是上面 15 条
请求"调度 token 之和超出下界"的来源。抢占的代价与换出对照见 5.8。

### 设计取舍

- **两相的最优配置是冲突的。** prefill 想要方阵形状（2.7 §六：cuBLAS 方阵到 92% 峰值），
  decode 想要大 batch 摊薄权重；prefill 写 KV，decode 读 KV；一个看 TTFT，一个看 TPOT。
- **混合批是折中，不是最优。** 同一个 step 里既做 prefill 又做 decode 时，GEMM 的 M 维被
  两类工作拼在一起，取值介于两者之间。本组实测中混合批只在 B≥8 出现，B=64 时中位 17 个 step
  是混合的（`serve_b.txt`）。
- **chunked prefill 的取舍可量化。** 预算越小，单步越短、decode 抖动越小，但长请求的
  TTFT 越长：128 → 8192 时 LONG 的首 token 从 511.4 ms 降到 172.6 ms，而 decode 的最大
  单次间隔从 9.1 ms 涨到 158.0 ms。没有免费的一侧。
- **分离处理要付协调成本。** 把两相放到不同机器（PD 分离）要求 KV 跨机传输；本机实测的
  跨机带宽上限 3.1 GB/s（1.5），而一条 4096 上下文请求的 KV 是 448 MiB（3.3），
  单向传输约 152 ms，比 prefill 本身（75 ms）还久。L6.4 展开这条路线。
- **增加后端时先核对阶段的定义。** SGLang 不暴露 vLLM 的四个时间戳，但
  `ScheduleBatch` 的 prefix/seq/extend 三个计数足以复现同一套阶段判据；两引擎的差别
  落在"哪一步发现请求结束"（SGLang 的 Σextend 比 vLLM 多 1），不核对就会把一次多余的
  forward 当成调度或算子差异。

## 工程实现 · mini 实现

`labs/L5/mini_phase_ledger.py` 只做两件事：判定阶段、算一步的账。

```python
def classify(before, after, prompt):
    if after < prompt and before == 0:
        return "prefill"
    if after < prompt:
        return "prefill-chunk"
    if before < prompt <= after:
        return "prefill-last"          # 首输出由这一前向产生
    return "decode"

def step_ledger(phase, n_sched, hist, cfg):
    flops = 2 * params(cfg) * n_sched
    kv_read = hist * kv_bytes_per_token(cfg)
    return dict(q_shape=(1, cfg["heads"], n_sched, cfg["head_dim"]),
                kv_shape=(1, cfg["kv_heads"], hist, cfg["head_dim"]),
                weight_bytes=weight_bytes(cfg), kv_read_bytes=kv_read,
                flops=flops, intensity=flops / (weight_bytes(cfg) + kv_read))
```

跑一遍会得到本章第一节的 roofline 表、第二节的 step 账，以及对真实工件的三条不变量核对
（阶段判定、decode 步长、调度 token 之和）。把 `params()` 换成别的模型即可复用到其他配置。

### 加 batch：prefill 与 decode 的收益差一个数量级

$S=2048$、输出 128、5 轮中位数（`results/crater/5.1/serve-b-20260921/serve_b.txt`）：

| 配置 | B | steps | 混合步 | 排队 ms | prefill ms | TPOT ms | 墙钟 ms | 输出 tok/s | 峰值 run | 峰值排队 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| S2048_B1 | 1 | 129 | 0 | 0.03 | 36.01 | 3.228 | 446.4 | 286.7 | 1 | 0 |
| S2048_B2 | 2 | 129 | 0 | 0.09 | 68.31 | 4.006 | 577.8 | 443.0 | 2 | 0 |
| S2048_B4 | 4 | 129 | 0 | 0.15 | 129.58 | 4.287 | 675.0 | 758.6 | 4 | 0 |
| S2048_B8 | 8 | 131 | 2 | 2.43 | 192.64 | 5.380 | 884.8 | 1157.3 | 8 | 4 |
| S2048_B16 | 16 | 133 | 4 | 69.38 | 259.82 | 7.146 | 1310.4 | 1562.9 | 16 | 12 |
| S2048_B32 | 32 | 137 | 8 | 330.74 | 266.11 | 11.050 | 2086.2 | 1963.4 | 32 | 28 |
| S2048_B64 | 64 | 260 | 17 | 870.68 | 270.75 | 20.289 | 4394.6 | 1864.1 | 58 | 60 |

三条读法：

1. **prefill 阶段从 36.01 涨到 270.75 ms（7.5×），但这是排队与分块的结果，不是"每条变慢"。**
   B=64 时真正在算了 64 条请求的 prefill，总工作量是 B=1 的 64 倍；把 prefill 时间除以请求数，
   每条从 36.0 ms 降到 4.2 ms。吞吐从 286.7 涨到 1963.4 tok/s，只涨 6.8×。
2. **decode 的 TPOT 从 3.228 涨到 20.289 ms（6.3×），但每步服务了 64 倍的请求。**
   聚合输出吞吐只涨 6.5×（286.7 → 1864.1 tok/s）：B=64 的 64 条 2048 token prompt
   装不进单批预算，分成了两批（260 步而不是 129 步），多出的那一批把增益吃了回去。
   吞吐在 B=32 附近见顶（1963.4 tok/s）。
3. **排队开始主导 TTFT。** B=8 时排队 2.43 ms，B=32 时 330.7 ms，B=64 时 870.7 ms；
   此时 prefill 本身只有 270 ms。要诊断 TTFT，就必须把这两段分开记，否则会把排队算进 prefill。

### 行长扫长度：同一总 token 量下，长 prompt 更贵

| 配置 | B | 排队 ms | prefill ms | TPOT ms | 墙钟 ms | 输出 tok/s | 混合步 |
|---|---:|---:|---:|---:|---:|---:|---:|
| S128_B1 | 1 | 0.02 | 5.24 | 3.136 | 404.0 | 316.8 | 0 |
| S2048_B1 | 1 | 0.02 | 35.81 | 3.228 | 446.0 | 287.0 | 0 |
| S8192_B1 | 1 | 0.05 | 161.49 | 3.847 | 650.4 | 196.8 | 0 |
| S128_B8 | 8 | 0.17 | 18.66 | 3.771 | 498.4 | 2054.5 | 0 |
| S2048_B8 | 8 | 2.43 | 192.59 | 5.369 | 883.0 | 1159.7 | 2 |
| S8192_B8 | 8 | 408.88 | 493.48 | 11.294 | 2358.3 | 434.2 | 8 |

B=1 的三档长度比为 64×，而 prefill 时间只涨 30.8×（5.24 → 161.49 ms）：**短 prompt 的单位
token 成本更高**，固定开销（提交、采样、图重放）摊在更少的 token 上。这与 step 账里
prompt 64 那一步只有 63.9 强度、还没到算力墙是一致的。
B=8 的 S8192 一档出现了 408.9 ms 排队：8×8192=65536 token 超过单批预算 8192，后面的请求
要等前面的 prefill 分块跑完。

### 相同 token 总量的等长与长短混批

`--scan mix` 让每档的总 prompt token 数都是 16384，只改长度分布：

| 配置 | 请求数与长度 | 排队 ms | prefill ms | TPOT ms | 墙钟 ms | 混合步 |
|---|---|---:|---:|---:|---:|---:|
| equal_8x1024 | 8 × 1024 | 0.03 | 124.41 | 4.299 | 671.2 | 0 |
| mixed_6144_2x1024 | 6144 + 2 × 1024 | 0.04 | 145.16 | 4.376 | 701.8 | 0 |
| equal_8x2048 | 8 × 2048 | 0.03 | 192.62 | 5.364 | 882.6 | 2 |
| mixed_8192_4x2048 | 8192 + 4 × 2048 | 0.05 | 291.17 | 5.293 | 972.8 | 2 |

同样是 16384 个 prompt token：8 条等长 2048 用 882.6 ms，一条 8192 加四条 2048 用 972.8 ms
（+10.2%），而 prefill 阶段 291.17 对 192.62 ms（+51%）。**token 总量相同不代表工作相同**——
长请求要等 8192 个位置分块跑完才能出首 token，这段等待被算进它的 TTFT。

### chunked prefill：单步时长与长请求 TTFT 的取舍

8 条 prompt 64、生成 64 的 decode 先跑到稳态，再插入一条 8192 token 的 prompt。
扫 `max_num_batched_tokens`，每档 3 次重复（`results/crater/5.3/budget-20260921/chunked_budget.txt`）：

| 预算 | 长 prompt 分块数 | LONG 首 token ms | decode 最大间隔 ms | 最慢 step ms | 长请求完成 ms |
|---:|---:|---:|---:|---:|---:|
| 128 | 68 | 511.4 | 9.1 | 10.5 | 508.3 |
| 256 | 34 | 307.5 | 11.7 | 11.7 | 370.2 |
| 512 | 17 | 215.0 | 15.1 | 15.1 | 344.3 |
| 2048 | 5 | 187.9 | 52.8 | 52.8 | 360.7 |
| 8192 | 2 | 172.6 | 158.0 | 158.0 | 355.5 |

三档重复的极差都小于 2 ms（如 128 档 [511.4, 511.5]）。**这条曲线两端都是代价**：
分块越细，decode 的最大停顿越小（158.0 → 9.1 ms，17×），但长请求自己的首 token 越晚
（172.6 → 511.4 ms，3.0×）；长请求的完成时间几乎不变（344–371 ms），说明总工作量没变，
变的只是排队顺序。实际分块大小 = 预算 − 8 条 decode 的 1 个 token（128 → 每块 120，
256 → 248，2048 → 2040）。

### 两引擎同一网格

同一模型、同一 prompt 集（`S=2048`、输出 128）在 SGLang 0.5.19（`page_size=16`，
`chunked_prefill_size=8192`）上的整批墙钟（`results/crater2/5.1/sglang-grid-20260921/`）：

| B | vLLM 墙钟 ms | SGLang 墙钟 ms | vLLM tok/s | SGLang tok/s |
|---:|---:|---:|---:|---:|
| 1 | 446.4 | 451.8 | 286.7 | 283.3 |
| 8 | 884.8 | 872.6 | 1157.3 | 1173.6 |
| 32 | 2086.2 | 2096.3 | 1963.4 | 1953.9 |
| 64 | 4394.6 | 4257.5 | 1864.1 | 1924.1 |

两个引擎在同一台机器的同一代 GPU 上、同一负载下的整批吞吐相差在 3% 以内；它们内部结构不同
（vLLM 的分块哈希表对 SGLang 的基数树，见 5.2），但在这一组形状上没有可测的整批差异。
**引擎各自的默认预算不同**，跨引擎比较必须先固定 `max_num_batched_tokens` 与
`chunked_prefill_size`，否则量到的是配置差而不是实现差。

### SGLang 侧的逐 step 阶段归属

vLLM 侧靠 rebind `EngineCore.step_fn` 取逐 step 事件；SGLang 是另一套结构：
`sgl.Engine` 强制 `spawn` 启动 scheduler 子进程，父进程的 monkeypatch 不会被继承。
`labs/L5/sglang_phase_ledger.py` 用 spawn 的导入语义解决这一点——子进程会以
`__mp_main__` 重新导入入口脚本，放在模块顶层（`if __name__` 之外）的 patch 于是在
调度进程内同样生效——在 `run_batch` 与 `process_batch_result` 上记录 `ScheduleBatch`
的成员与计数，阶段判定复用同一套判据。prompt 64、输出 4
（`results/crater2/5.1/sglang-phase-ledger-20260922/`）：

| step | forward_mode | 本步 token | before | after | 阶段 | 本步产出 | 墙钟 ms |
|---:|---|---:|---:|---:|---|---:|---:|
| 0 | EXTEND | 64 | 0 | 64 | prefill-last | 1 | 23.31 |
| 1 | DECODE | 1 | 64 | 65 | decode | 2 | 3.71 |
| 2 | DECODE | 1 | 65 | 66 | decode | 3 | 0.45 |
| 3 | DECODE | 1 | 66 | 67 | decode | 4 | 0.39 |
| 4 | DECODE | 1 | 67 | 68 | decode | 4 | 0.38 |

三条读法：

1. **阶段边界与 vLLM 一致。** 首输出在第 0 步（prefill-last）产生，与 vLLM 的"首 token
   由覆盖完整 prompt 的前向产生"相同；`本步产出` 列给出直接证据——步 0 产出第 1 个
   token，随后每步加 1。
2. **chunked prefill 的分块可直接读出。** prompt 2048、`chunked_prefill_size=512` 得到
   4 个 EXTEND 块（prefill 512 / prefill-chunk 512 / 512 / prefill-last 512，墙钟
   23.4 / 8.5 / 10.6 / 10.9 ms），首输出落在最后一块（步 3）。
3. **找"结束"的位置与 vLLM 不同。** 生成满 `max_new_tokens` 后 SGLang 仍多跑一次
   decode：各请求「各步 extend 之和 − (prompt + 实际生成 − 1)」恒为 +1（单请求 68 对
   67、B=4 每请求 +1、chunked 档 2052 对 2051），而该步产出的 token 数不再增加。
   vLLM 的口径是 Σsched = prompt + 生成 − 1。

这是两引擎第一组可直接并排的逐 step 口径：**阶段判定一致，差别落在"哪一步发现请求
结束"这类记账位置**。不做这一步核对，就会把一次多余的 forward 当成调度或算子差异。

**建议的消融**

1. 把 B 扫到 128/256，看聚合吞吐在哪个 batch 见顶，并记录峰值排队——本组在 B=32 附近已见顶。
2. 把 `S=8192` 档的输出长度从 8 加到 128，观察长上下文下的 TPOT 是否随 KV 增长上升（3.3）。
3. 打开前缀缓存重跑 B 扫描，比较共享 system prompt 场景下的 TTFT（5.2 提供命中读数）。
4. 在 SGLang 上改 `chunked_prefill_size` 重做预算扫描，比较两引擎的分块边界是否一致。

## 前沿

**PD 分离**把两相拆到不同的机器：prefill 集群配算力强的卡，decode 集群配带宽大、显存大的卡。
它成立的条件可以直接用本章的量算出来：

- 收益：prefill 与 decode 各自使用最适合自己的 batch 与形状，不再互相等待。本章预算扫描量到
  这种等待的上界——一条 8192 token 的 prefill 在预算 8192 时会让 8 条 decode 停 158 ms。
- 成本：prefill 算出的 KV 必须送到 decode 机器。一条 4096 上下文请求的 KV 为 448 MiB（3.3），
  按 1.5 实测的跨机 3.1 GB/s 估计，单向传输约 152 ms，比 prefill 本身（75 ms）还久。
- 因此 PD 分离只在互联足够快时成立。vLLM 0.29.0 通过 `kv_transfer_config` 接入 KV 连接器，
  SGLang 有对应的分离部署模式，两者都把"KV 怎么走"交给具体传输后端（NIXL、Mooncake、
  LMCache 等）。本机没有 RDMA（1.5），这条路线在本课程中的实测范围见 L6.4。

沿同一问题还有两条机制值得追踪，它们的判据都落在本章的账上：

- **批次内重排**：把混合批里 prefill 与 decode 的 GEMM 拆成两个形状更好的调用，代价是权重
  读两遍。是否划算取决于两者的 token 数比例——用 `step_ledger` 直接算两次调用的
  weight_bytes 与 FLOP 即可判断，不需要先上硬件。
- **预算预测**：用历史长度预测下一步要多少 token，据此决定分块大小。预测误差的代价同样可以
  用本章的预算扫描外推：把预测的 step 时间当作约束，误差 ±25%/50% 对应到实际单步的偏离量，
  5.3 会把它做成可运行的调度器对照。

## 陷阱

1. **只报一个"吞吐"会同时掩盖 TTFT 和 TPOT。** 必须分相位报，并说明排队段是否计入。
2. **本组 prefill 加 batch 的收益只有 6.8×，而 decode 的 TPOT 涨幅与它相抵。** 短 prompt 或
   其他形状不能沿用这一结论。
3. **`generate()` 两次调用相减不是阶段计时。** 请求处理、排队、采样都在差值里；
   用引擎的 `queued/scheduled/first_token/last_token` 四个时间戳。
4. **token 总量相同不代表工作相同。** 16384 个 prompt token，8 条等长 2048 用 882.6 ms，
   一条 8192 加四条 2048 用 972.8 ms。
5. **chunked prefill 不是纯收益。** 它买的是 decode 的抖动（158.0 → 9.1 ms），
   付的是长请求的首 token（172.6 → 511.4 ms）。
6. **共享机器上不要写死 `gpu_memory_utilization`。** 按空闲量算并留余量；
   同一进程里反复建引擎会留下显存残留，档间比较要每档一个进程并固定 util。
7. **PD 分离要先量 KV 传输成本。** 按 3.1 GB/s 传输 448 MiB 约 152 ms，比 prefill 还久。
8. **两引擎的逐 step 记账不完全等价。** SGLang 在生成满 `max_new_tokens` 后多跑一次
   decode，`Σextend` 比 vLLM 的 `Σsched` 多 1；跨引擎比较 forward 数或调度 token 总量
   时先统一这个口径。
9. **device 跨度里有非 kernel 时间。** 本组每步的 kernel 之和只有 device 时间的
   40%–75%，另有换路径时的首次调用成本（一次 41.5 ms）落在单步上；用 kernel 和代替
   step 时间会同时漏掉这两项。

## 自测题

<details markdown="1">
<summary>1. 为什么 prefill 加 batch 的收益远小于 decode？用本章的强度表解释。</summary>

prefill 一次处理 $S$ 个 token，算术强度 $\approx S$。$S=2048$ 时强度 2048，
已经越过平衡点 144，加 batch 只是把更多工作排进同一侧；decode 一次处理 1 个 token，
强度 = batch，batch=1 时是 1，加 batch 直接把权重读取分摊掉。

本组实测：decode 聚合吞吐从 286.7 涨到 1963.4 tok/s，而 prefill 阶段的时间涨幅
主要由排队与分块解释（B=64 时排队 870.7 ms，prefill 本身 270.8 ms）。
</details>

<details markdown="1">
<summary>2. 服务的 p99 TTFT 很差但吞吐很高，可能是哪两件事？怎么区分？</summary>

一是**排队**：调度器优先把 decode 批凑大，新请求要等当前批跑完才能 prefill。
二是**长 prompt 阻塞**：一条 8192 token 的 prefill 会让所有 decode 停 158 ms（预算 8192），
新请求的首 token 也被推后。

区分方法就是本章的两个读数：`scheduled_ts − queued_ts` 是排队，`first_token_ts − scheduled_ts`
是 prefill。B=64 时前者 870.7 ms、后者 270.8 ms，瓶颈在排队不在计算。
</details>

<details markdown="1">
<summary>3. 把 chunked prefill 的预算从 8192 调到 128，你会看到什么变化？谁受损？</summary>

单步最慢从 158.0 ms 降到 10.5 ms，8 条 decode 的最大输出间隔从 158.0 降到 9.1 ms；
代价是长 prompt 被切成 68 块，它自己的首 token 从 172.6 ms 涨到 511.4 ms（3.0×）。
总工作量不变：长请求的完成时间 344–371 ms 只有 128 档的 508.3 ms 例外，
因为它开始分块时 decode 也在跑。

受损的是长请求的 TTFT；受益的是已经在 decode 的请求。这是交互式服务里最常见的取舍方向。
</details>

<details markdown="1">
<summary>4. 首 token 由哪一次前向产生？为什么它决定了"调度 token 之和 = prompt + 生成 − 1"？</summary>

由覆盖完整 prompt 的那次 prefill 前向产生：它的 logits 直接采样出第一个输出 token，
不需要额外一次 decode 前向。所以一条请求消耗的前向位置数是
`prompt + (生成 − 1)`，而不是 `prompt + 生成`。

本章 890 条请求里 875 条精确满足这个等式，其余 15 条多出的量等于一次完整的
prompt+生成——它们被抢占后重算了一遍（`v1/core/sched/scheduler.py:1405`）。
</details>

<details markdown="1">
<summary>5. PD 分离在什么条件下是负收益？用本章与 1.5、3.3 的量算一遍。</summary>

当 KV 跨机传输的时间超过它省下的时间时。一条 4096 上下文请求的 KV 为 448 MiB（3.3），
按 1.5 实测的 3.1 GB/s 估计，单向传输约 152 ms；而这条请求的 prefill 只要 75 ms。
传输比计算还贵，所以在普通以太网上做 PD 分离等于给每个请求加一段比 prefill 更长的延迟。

判据是通用的：**分离的收益必须大于协调成本，而协调成本要实测。**
</details>
