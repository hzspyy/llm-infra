## 本章回答三个问题

3.1 和 3.3 分别从 attention 的角度看过 prefill 和 decode。
这一章从**整个引擎**的角度看：这两相对硬件的要求是**相反的**，
于是引擎的每一个调度决策都要在它们之间做取舍。

1. 两相分别落在 roofline 的哪一侧？
2. 加 batch 对它们的影响为什么完全不同？
3. 一个请求的时间花在哪里？该用什么指标衡量？

---

## 一 · 两相在 roofline 上的位置

Qwen3-1.7B，权重 bf16 = 3.20 GiB，机器平衡点 144.2 FLOP/byte：

| 相 | batch | 序列 | FLOP | 权重字节 | 算术强度 | 落在哪一侧 |
|---|---:|---:|---:|---:|---:|---|
| prefill | 1 | 2048 | 7.05e12 | 3.44e9 | **2048.0** | 算力 |
| prefill | 1 | 4096 | 1.41e13 | 3.44e9 | **4096.0** | 算力 |
| decode | 1 | 1 | 3.44e9 | 3.44e9 | **1.0** | 带宽 |
| decode | 8 | 1 | 2.75e10 | 3.44e9 | 8.0 | 带宽 |
| decode | 64 | 1 | 2.20e11 | 3.44e9 | 64.0 | 带宽 |
| decode | 256 | 1 | 8.81e11 | 3.44e9 | 256.0 | 算力 |

关键在**权重字节那一列是常数**：无论 batch 多大、序列多长，
每一步都要把全部权重读一遍，**只读一遍**。

- **prefill** 一次处理 $S$ 个 token，$S=2048$ 就有 2048 的算术强度——
  天然在算力一侧。
- **decode** 一次只处理 1 个 token，算术强度就是 batch 大小。
  batch≈72 时才越过平衡点。

这就是全部：**prefill 靠序列长度自带算术强度，decode 只能靠 batch 去买。**

（这里只算权重。KV 的读取**不随 batch 摊薄**——每条请求有自己的 KV，
所以 batch 越大 KV 读取越多。3.3 那本账是另一半。）

## 二 · batch 对两相的影响完全不同

同一个引擎、同一台机器、同样的 batch 扫描：

**prefill**（每条 1024 token，只生成 1 个）

| batch | 总耗时 ms | 每条 ms | prompt tok/s | 相对 batch=1 |
|---:|---:|---:|---:|---:|
| 1 | 20.0 | 20.0 | 51177 | 1.00× |
| 2 | 35.0 | 17.5 | 58454 | 1.14× |
| 8 | 130.8 | 16.3 | 62632 | 1.22× |
| 32 | 514.6 | 16.1 | 63679 | **1.24×** |

**decode**（每条 prompt 128 token，生成 64）

| batch | 每步 ms | output tok/s | 相对 batch=1 |
|---:|---:|---:|---:|
| 1 | 4.496 | 222 | 1.00× |
| 4 | 4.531 | 883 | 3.97× |
| 16 | 4.752 | 3367 | 15.14× |
| 32 | 4.791 | 6679 | 30.03× |
| 64 | 5.134 | 12467 | **56.05×** |

**batch 从 1 到 32：prefill 吞吐只涨 1.24×，decode 涨 30×。**

原因就是第一节那张表：prefill 在 batch=1 时就已经算力受限，
加 batch 只是把更多工作排队，单位时间做的事没变多。
decode 的每步时间从 4.496 涨到 5.134 ms（**只涨 14%**），
却同时服务了 64 倍的请求——**权重读取被 64 条请求分摊了**。

::: note 这两张表是引擎所有调度决策的出发点
**prefill 不需要凑批，decode 极其需要凑批。**

推论一串：
- 调度器应该优先把 decode 的批凑大（5.3 的 continuous batching）
- prefill 可以切碎了插空（chunked prefill）而不损失什么
- 两相甚至可以放到不同的机器上（PD 分离，L6.4）
- 评估引擎不能只报一个"吞吐"（0.3 §陷阱 1）
:::

## 三 · TTFT 与 TPOT

| prompt 长度 | 生成 | TTFT ms | TPOT ms | 总时长 ms | TTFT 占比 |
|---:|---:|---:|---:|---:|---:|
| 128 | 64 | 5.67 | 4.489 | 293.0 | 1.9% |
| 512 | 64 | 11.03 | 4.430 | 294.5 | 3.7% |
| 2048 | 64 | 37.04 | 4.515 | 326.0 | 11.4% |
| 4096 | 64 | 75.54 | 4.493 | 363.1 | **20.8%** |

- **TTFT 随 prompt 长度线性增长**（5.67 → 75.54 ms，prompt 涨 32 倍，
  TTFT 涨 13 倍——不是严格线性，因为有固定开销）。
- **TPOT 基本不变**（4.43–4.52 ms）。这里 KV 还很小，
  按 3.3 的账，KV 长了 TPOT 才会涨。

所以**负载形态决定了该看哪个指标**：

| 负载 | 主导指标 | 例子 |
|---|---|---|
| 长 prompt + 短输出 | TTFT | 文档问答、代码补全、分类 |
| 短 prompt + 长输出 | TPOT | 对话、创作、推理链 |
| 两者都长 | 都要看 | Agent、长文摘要 |

**只报"吞吐"会同时掩盖这两个。** 一个把 TTFT 做到很差、
靠大批把吞吐堆上去的引擎，在交互场景里是不能用的。

## 四 · 长度不齐的浪费

16 条请求，两种输出长度分布：

```
长度一致（都生成 64）
  实际生成 1024 token，耗时 333.3 ms，吞吐 3073 tok/s
  最长 64，若静态批处理要按最长算：1024 个 step 的位置
  利用率 = 1024 / 1024 = 100.0%

长度不齐（1..128 均匀）
  实际生成 949 token，耗时 551.9 ms，吞吐 1720 tok/s
  最长 114，若静态批处理要按最长算：1824 个 step 的位置
  利用率 = 949 / 1824 = 52.0%
```

**静态批处理在长度不齐时只能拿到 52% 的利用率**——
一批一起开始、一起结束，最长的那条决定整批时长，
先结束的请求占着位置什么也不干。

::: warning 但第二行的吞吐也掉了一半，而 vLLM 已经是连续批处理
这两件事要分开：

1. **52% 是静态批处理会浪费的比例。**
2. **吞吐从 3073 掉到 1720，是因为这里没有排队的新请求可以补位。**
   批在跑的过程中不断有请求结束，活跃数从 16 一路掉到 1，
   最后几步是在按 batch=1 的速度跑（第二节：batch=1 只有 222 tok/s）。

**连续批处理消除的是「等最慢的那条」，不是「没活干」。**
:::

给它一个队列，收益就出来了：

```
一次提交 64 条（长度同样 1..128 不齐）
  实际生成 4162 token，耗时 748.1 ms，吞吐 5563 tok/s
```

对照 16 条不齐时的 1720 tok/s——**3.2×**。
早结束的请求空出的位置立刻被后面的补上，批一直是满的。

**这也说明闭环测试（一次提交固定一批，等全部结束）会低估连续批处理。**
要看真实收益必须开环压测（持续按到达率发请求），这是 L8.3 的方法。

## 五 · 设计取舍

### 5.1 为什么不能用一套参数同时优化两相

两相的最优配置是冲突的：

| | prefill | decode |
|---|---|---|
| 想要的 batch | 小（已经算力受限，大批只增加延迟） | 大（越大越摊薄权重） |
| 想要的 kernel 形状 | 方阵（2.7 §六：cuBLAS 在这里到 92% 峰值） | 瘦长（M 很小） |
| 对 KV 的操作 | 写入 | 读取 |
| 瓶颈 | 算力 | 带宽 |
| 延迟指标 | TTFT | TPOT |

一个引擎在同一个 step 里既做 prefill 又做 decode（混合批），
就必须在这两组要求之间折中。**chunked prefill**（把长 prompt 切成小块
插进 decode 批里）就是这个折中的具体形态：
它牺牲一点 prefill 的效率，换 decode 批不被长 prefill 打断。

### 5.2 PD 分离的动机与代价

既然两相要求相反，最彻底的解法是**放到不同的机器上**：
prefill 集群配算力强的卡，decode 集群配带宽大、显存大的卡。

代价是 **KV 要跨机传输**——prefill 算出的 KV 必须送到 decode 机器。
1.5 实测本机跨机带宽上限只有 3.1 GB/s，而 3.3 算过
一条 4096 上下文的请求 KV 是 448 MB。传一次要 145 ms，
比 prefill 本身（75 ms）还久。

**所以 PD 分离在慢网络上是负收益。** 它需要高速互联才成立——
这也是为什么它先出现在有 NVLink/InfiniBand 的集群上。L6.4 会展开。

### 5.3 一个可带走的判断

本章的形态在系统里反复出现：**当一个系统里存在两种性质相反的工作时，
"统一处理"和"分开处理"之间的选择，取决于分开的协调成本。**

- 协调成本低（同一进程内切换）→ 混合批 + chunked prefill
- 协调成本高（跨机传 KV）→ 只有在互联足够快时才分离

判据不是"哪种更先进"，而是**量出协调成本**再比。
3.3 §四 的分页、4.3 §五 的 KV 量化，我都在这一点上栽过——
框架层的模拟会把协调成本量错。

## 七 · 陷阱

1. **只报一个"吞吐"会同时掩盖 TTFT 和 TPOT。** 必须分相位报。
2. **prefill 加 batch 几乎没有收益**（本章 1.24×）。为 prefill 凑批是白等。
3. **decode 的 batch 收益接近线性**（本章 56×），但要 KV 显存装得下。
4. **闭环测试低估连续批处理。** 没有队列时批会drain，
   最后几步退化成 batch=1（本章 3073 → 1720 tok/s）。
5. **共享机器上不要写死 `gpu_memory_utilization`。** 按空闲量算并留余量。
6. **TPOT 在短上下文下几乎不变**，别用短测试外推长上下文的 TPOT（3.3）。
7. **PD 分离要先量 KV 传输成本。** 本机跨机 3.1 GB/s 下传 448 MB 要 145 ms，
   比 prefill 本身还久。

## 八 · 自测题

<details markdown="1">
<summary>1. 为什么 prefill 加 batch 几乎没收益，而 decode 有 56 倍？</summary>

看算术强度。权重字节是常数（每步读一遍全部权重），FLOP 正比于处理的 token 数。

- prefill 一次处理 $S$ 个 token，算术强度 $\approx S$。$S=1024$ 时已经是 1024，
  远超平衡点 144，**已经算力受限**。加 batch 只是排更多队。
- decode 一次处理 1 个 token，算术强度 = batch。batch=1 时是 1，
  **严重带宽受限**。加 batch 直接把权重读取分摊掉。

本章实测：decode 每步时间从 4.496 只涨到 5.134 ms（14%），
却服务了 64 倍的请求。
</details>

<details markdown="1">
<summary>2. 你的服务 P99 TTFT 很差但吞吐很高，可能是什么原因？</summary>

最可能是**调度偏向 decode**：为了把 decode 批凑大，
新到的请求要等当前批跑完才能 prefill，排队时间全算进 TTFT。

或者**长 prompt 阻塞**：一条 4096 token 的 prefill 要 75 ms（本章实测），
这段时间所有 decode 都停着，其它请求的 TTFT 和 TPOT 都被拖长。

chunked prefill 就是针对后者：把长 prefill 切成小块插进 decode 批，
让每一步的时间可控。代价是 prefill 的效率略降（切碎了不如整块）。

诊断：分别记录排队时间和 prefill 时间，看 TTFT 主要花在哪一段。
</details>

<details markdown="1">
<summary>3. 一次提交 16 条 vs 64 条，同样的长度分布，为什么吞吐差 3.2 倍？</summary>

因为**有没有请求可以补位**。

16 条时，随着短请求结束，活跃数从 16 掉到 1，最后几步在按 batch=1 跑
（222 tok/s，第二节实测）。整段的平均吞吐被这个尾巴拉低。

64 条时，早结束的位置立刻被后面排队的补上，批一直接近满载。

**这说明连续批处理的收益取决于队列深度。** 没有队列时它退化成
"提前释放资源"，对吞吐帮助有限。

也说明**闭环测试（提交固定一批等结束）会低估它**——
必须用开环压测（按到达率持续发请求）才能测到真实收益。
</details>

<details markdown="1">
<summary>4. PD 分离听起来很合理，什么情况下它是负收益？</summary>

当 **KV 跨机传输的时间超过它省下的时间**时。

按本书的实测：一条 4096 上下文请求的 KV 是 448 MB（3.3），
本机跨机带宽上限 3.1 GB/s（1.5）——传一次要 **145 ms**，
而 prefill 本身只要 75 ms（本章）。**传输比计算还贵。**

所以 PD 分离要求高速互联（NVLink/InfiniBand/RDMA）。
在普通以太网上做，等于给每个请求加一段比 prefill 还长的延迟。

这也是一个通用判据：**分离的收益必须大于协调成本，
而协调成本要实测，不能假设"网络很快"。**
</details>
