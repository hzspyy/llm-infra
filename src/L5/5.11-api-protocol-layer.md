## 本章回答三个问题

本章介绍推理引擎的 API 层：HTTP 请求如何进入调度器，生成的 token 如何以流式响应返回客户端。

1. 一个 HTTP 请求到进入 scheduler，中间经过哪些层？每层花多少时间？
2. streaming 的每个 chunk 是怎么产生和推出去的？一个 token 对应几个字节？
3. tokenization 在高并发下会不会成为瓶颈？

API 层的工作量通常小于模型前向，但共享事件循环中的阻塞仍会影响其他请求。本章实测 24 token 的流式请求：客户端墙钟
77.75 ms，其中引擎推理 76.32 ms，进程内前端 0.79 ms、进程外 0.63 ms，非推理部分合计 1.84%。
但把 tokenizer 放回事件循环，一个 16k token 的请求会让**所有**在跑的请求停顿 11.4 ms——
与该请求的编码耗时接近。

## 机制拆解与推导

### 1. 请求在 HTTP 层要过四道门

ASGI 服务器的调用栈是嵌套的：每个中间件包住下游，请求自外向内穿过，响应自内向外回来。
vLLM 注册中间件的顺序（`entrypoints/serve/middleware/register.py:19-75`）是
CORS → 鉴权 → request-id → 扩缩容状态，最后才是用户通过 `--middleware` 传入的。
Starlette 的 `add_middleware` 是**后加的先执行**，所以列表顺序和实际执行顺序相反。
中间件越多，每个请求的固定开销越大，而且**流式响应同样会经历整条中间件链**——返回
`StreamingResponse` 并不代表能够绕过中间件。

### 2. SSE 是叠在 chunked 上的第二层分帧

一个流式响应在 HTTP/1.1 上同时有两层分帧。外层是传输层的 chunked：
`长度(十六进制) CRLF 负载 CRLF`，最后以 `0 CRLF CRLF` 结束。内层是 SSE 的事件：
字段行加一个空行构成一个事件。

两层都有「一个逻辑单元可能被拆到多次 `recv`」的问题。本章实测的 24 token 响应里，
25 个 chunked 帧恰好被 25 次 `recv` 读到——这是**偶然**，不是保证。
客户端必须按字节流处理：先把 chunked 还原成 body，再把 body 喂给 SSE 解析器。
`labs/L5/mini_sse.py` 的 `SSEDecoder` 只吃 body 字节，就是为了让这两层解耦。

SSE 的规范细节容易漏的有四条，都在 `mini_sse.py` 里做了自检：

- 行分隔符 CR、LF、CRLF 都算，而 CRLF 可能被拆在两次读之间；
- 冒号后**紧跟的一个**空格被吃掉，多出来的属于数据；
- 以冒号开头的行是注释，客户端必须忽略——vLLM 的 keep-alive 就走这条路；
- EOF 不是事件结束符，没等到空行就结束的半个事件要丢掉。

### 3. 引擎指标能拆出前端段和运行段

vLLM 的请求时延指标（`v1/metrics/stats.py:218-245`）在 engine core 里盖章，
`arrival_time` 则在前端进程、**tokenization 之前**打上（`v1/engine/input_processor.py:321-322`）。
于是：

| 段 | 算法 | 内容 |
|---|---|---|
| 前端段 | `e2e − inference − queue` | tokenization + 序列化 + 送进 core |
| 排队段 | `queue` | WAITING 状态 |
| 运行段 | `inference = prefill + decode` | core 里的前向与采样 |
| 回程段 | `客户端墙钟 − e2e` | 增量 detokenize + SSE 编码 + 回写 |

这个减法能成立，靠的是「各时间戳盖在哪个进程」这一件事。换个引擎、换个版本，
时间戳位置变了，减法就不再成立——**先读代码确认戳在哪，再做减法**。

### 4. 一个 token 不一定对应一个 SSE 事件

engine core 每步吐出的是 token id，推给客户端的是**文本增量**。中间隔着增量 detokenizer：
vLLM 的 `FastIncrementalDetokenizer` 用 tokenizers 库的 `DecodeStream.step()` 解码单个 token，
而 `DecodeStream` 会把**不完整的 UTF-8 前缀扣住**，等下一个 token 到了再一起吐
（`v1/engine/detokenizer.py:211-248`）。扣住的那一步返回空串，前端就不发事件。

所以「生成 24 个 token」不等于「收到 24 条 `data:`」。本章这次实测正好相等：
24 个 delta 事件 + 1 个 `[DONE]`，没有空 delta。相等是常见情况，不是不变量——
多字节字符被切开、或 BPE 合并跨 token 时就会不等。

### 5. tokenization 的成本不在总量，在它跑在哪

先看绝对量级。Qwen3-1.7B 的 tokenizer 在 crater 的 CPU 上：

| 输入字符 | token 数 | 编码中位耗时 |
|---:|---:|---:|
| 69 | 17 | 0.021 ms |
| 552 | 129 | 0.091 ms |
| 4 416 | 1 025 | 0.616 ms |
| 17 664 | 4 097 | 2.468 ms |
| 70 656 | 16 385 | 9.941 ms |

约 **0.6 µs/token**。16k token 的长上下文请求编码一次只要 9.9 ms，
而同一台机器上 1.7B 模型一个 decode step 是 20.6 ms。**从吞吐看，tokenizer 不是瓶颈。**

但从延迟看，它是。Python 的 `async def` 里直接调 `tok.encode()` 会占住事件循环：
这段时间里所有协程都不推进，包括正在给别的请求推 token 的那个。
这就是本章要复现的失败模式——它的危害不来自耗时总量，来自**位置**。

修法有两个层次，可以叠加：

1. **挪出去。** `await asyncio.to_thread(tok.encode, ...)` 或 `run_in_executor`，
   把阻塞调用放到线程池。vLLM 对 raw prompt 走的就是这条路，注释写得很直白：
   「Raw prompts require tokenization and possibly multimodal processing,
   which must not block the event loop.」（`v1/engine/async_llm.py:440-441`）
2. **合起来。** 挪出去之后每次调用仍是一次独立编码，N 个并发请求就是 N 次。
   SGLang 的 `AsyncDynamicbatchTokenizer` 把这两件事一起做：请求进队列，
   后台任务在 2 ms 窗口内攒到最多 32 条，**一次** `tokenizer(...)` 批量编码，
   再按 future 分回各请求（`managers/async_dynamic_batch_tokenizer.py:58-152`）。

代价也要说清：挪出去要多一次线程往返，而线程的结果只能在事件循环空闲时投递。
本章实测同一份 16k token 输入，in-loop 编码 11.0 ms，`to_thread` 后服务端侧变成 31.7 ms——
多出来的部分是「等事件循环腾出手」。**保护了别人，自己变慢。**

### 6. 代理缓冲、慢读者与断连：分帧在哪一层被改掉

前面几节讲的是引擎自己怎么分帧。真实部署里客户端和引擎之间还有一层代理，
而**代理可以对分帧做任何事**。用一条最小链路把它测出来
（`labs/L5/proxy_stream_audit.py`，纯 stdlib，不占 GPU；
`results/local/5.11/proxy-stream-20260914/`）：

```
client ──▶ proxy ──▶ backend(SSE：20 个事件，每 50 ms 一个，整段约 1.07 s)
```

| 用例 | 客户端块数 | 收到事件 | 代理转发首包 | 后端送完 | 墙钟 |
|---|---:|---:|---:|---:|---:|
| baseline（stream 直通） | 22 | 20 | 0.0004 s | 1.0712 s | 6.07 s |
| **代理缓冲（buffer）** | **2** | 20 | **1.0684 s** | 1.0675 s | 6.07 s |
| keep-alive 头关掉 | 22 | 20 | 0.0014 s | 1.0662 s | 6.07 s |
| 慢读者（16 B/事件） | 5 | 20 | 0.0007 s | 1.0638 s | 6.77 s |
| 慢读者（64 KiB/事件） | 22 | 20 | 0.0008 s | 1.0640 s | **12.76 s** |
| **客户端中途断连** | 3 | **1** | 0.0011 s | — | 0.054 s |

四条可以直接引用的结论：

1. **缓冲把"逐 token 到达"变成"结束时刻一次性到达"。** buffer 模式下代理的
   转发首包发生在 **1.0684 s**，与后端送完的 1.0675 s 只差 0.9 ms；
   客户端看到的块数从 22 塌到 **2**（响应头 + 455 B 全量 body）。
   客户端侧的"首包时间"因此完全失去意义——它量到的是**整段生成时间**。
2. **断连的取消确实传到了后端，但有时延。** 客户端在第 3 个块后关闭（0.054 s），
   后端在 **0.2129 s** 观测到对端关闭，**传播 0.159 s**；
   后端没有继续补完剩下的事件（自然结束是 1.07 s）。
   这一条是"取消传播"的可测形式：不是看客户端有没有断，而是看**生成侧多久停**。
3. **慢读者不会把压力传回生成侧。** 事件负载从 16 B 放大到 64 KiB（整段约 1.3 MB）后，
   后端两次都在约 1.06 s 送完，墙钟从 6.77 s 涨到 12.76 s——
   多出来的时间全部来自客户端自己的读取节奏与链路缓冲。
   **在本例的数据量级上，慢客户端只慢自己**；要观察到对生成侧的回压，
   需要更大的流或更小的发送缓冲。
4. **keep-alive 在本机回环上不是瓶颈。** 单独量建连成本：新建连接中位
   1069.657 ms、复用 1068.688 ms（两者都包含整段约 1.07 s 的流），
   差值 **0.969 ms/请求** 就是 keep-alive 每请求能省下的上限。
   对照组（把 `Connection` 头改成 close）因此量不出差异——
   而且那一组**只改了请求头，代理自身没有连接池**，所以它测的不是"连接复用"，
   这一点必须写清楚，不能拿它当 keep-alive 的结论。
   跨网络或高连接数下这个数会变大，那才是 keep-alive 的收益区间。

**HTTP/2 这一格后来补上了（用 h2c，明文）。** 之前记"本机缺 `h2`"是对的，
但缺的是 **Python 客户端**；服务端其实早就支持：SGLang 0.5.19 有
`--enable-http2`（server_args 里还有 `http2_max_concurrent_streams` 等参数），
而本机 curl 7.81 带 nghttp2。所以这一格不用装依赖也能测
（`labs/L5/http2_audit.py` + `run_http2_audit.sh`，
`results/crater/sglang/http2-20260914/`）：

| 协议 | 单请求 `%{http_version}` | 单请求总时长 | 流式事件数 | **并发 32 墙钟** | 逐请求中位 |
|---|---|---:|---:|---:|---:|
| HTTP/1.1（基线） | `1.1` | 27.7 ms | 17 | **0.086 s** | **0.083 s** |
| h2c（prior knowledge） | **`2`** | 26.5 ms | 17 | **0.058 s** | **0.055 s** |

1. **协议协商有直接证据**：同一个服务、同一端口，`--http1.1` 报 `1.1`、
   `--http2-prior-knowledge` 报 **`2`**。不是"应该支持"，是协商到了。
2. **SSE 在两种协议下都通**：同一条流式请求两边都收到 **17 个 `data:` 事件**。
   HTTP/2 只是把同样的事件装进 DATA 帧，本章前面讲的"三层分帧"再多一层。
3. **并发 32 条时 h2c 墙钟 0.058 s 对 HTTP/1.1 0.086 s（−33%）**，
   逐请求中位 0.055 对 0.083 s。机制是多路复用：h2 在**一条连接**上跑完 32 条，
   HTTP/1.1 要开多条连接。但这个差值里也含**客户端**因素——
   curl 在 HTTP/1.1 下要多管一批连接——所以它是"协议 + 客户端"的合计，
   **不能整笔算给协议本身**。单请求耗时两边基本相同（27.7 对 26.5 ms），
   说明协议本身的开销差异可以忽略。

**仍未测**：HTTP/3（本机 curl 没有 HTTP3 feature）、真实代理（NGINX/Envoy）
在 h2 下的行为，以及 h2 的流控窗口对长流式输出的影响。

### 7. 多 worker / 多 tokenizer 进程：前端能不能吃满并发

本章前面所有数字都来自**单进程前端**。两个引擎各有把前端并行的旋钮：
vLLM 的 `--api-server-count N`（N 个 API server 共享同一个 EngineCore）、
SGLang 的 `--tokenizer-worker-num` / `--detokenizer-worker-num`。
负载设计成"前端有活干"：**513 token 的 prompt、并发 32、每条生成 16 token**，
每档 3 轮取中位（`labs/L5/multiworker_audit.py` + `run_multiworker_audit.sh`、
`run_vllm_apiserver_audit.sh`，`results/crater/api/multiworker-20260915/`）。

| 引擎 / 旋钮 | TTFT p50 | TTFT p99 | 整批墙钟 | 单请求 p50 |
|---|---:|---:|---:|---:|
| SGLang tokenizer/detokenizer worker = 1 / 1 | 152.4 ms | 247.5 ms | 444.1 ms | 418.1 ms |
| SGLang worker = 4 / 4 | **143.6 ms**（−5.8%） | **225.0 ms**（−9.1%） | 470.7 ms（+6.1%） | 415.5 ms |
| vLLM api-server-count = 1 | 174.2 ms | 267.0 ms | 342.6 ms | 322.8 ms |
| vLLM api-server-count = 4 | 174.0 ms | 267.6 ms | 342.6 ms | 322.3 ms |

**SGLang 这一格有可测的小幅改善**：把 tokenizer/detokenizer 的 worker 从 1 提到 4，
TTFT 中位降 5.8%、p99 降 9.1%，而**整批墙钟反而涨 6.1%**——
这是"把分词的排队摊到多个进程"换来的：前端阶段更不容易串行等待，
但多进程之间多了协调与传输。单请求总时长几乎不动（418 → 415 ms），
说明它影响的是**排队**而不是**单条的处理速度**。

**进程级复核的结论是：这一档里根本不存在第二个前端。** 两档都在服务运行期间抓了
进程表与监听套接字（`results/crater/5.11/mw-confirm-20260921/processes-*.txt`）：

```
=== ps 里 VLLM::APIServer / EngineCore（vllm_api4）

=== APIServer 计数
1
=== 监听 8180 的进程
LISTEN 0 2048 0.0.0.0:8180 0.0.0.0:* users:(("python",pid=3261420,fd=25))
```

`--api-server-count 4` 那一档与 count=1 完全同构：一个 `VLLM::EngineCore` 子进程，
监听 8180 的只有父进程（pid 3261420），没有额外的 `APIServer` 子进程。
源码也支持这个观察：`--api-server-count` 在 vLLM 0.29.0 里只被用于
数据并行的默认值推导（`entrypoints/cli/serve.py:104-114`）、多模态处理器缓存的
容量公式（`config/multimodal.py:158`）与一条指标告警
（`v1/metrics/loggers.py:1341`：`api_server_count more than 1` 时关闭统计日志以避免
不完整统计），**没有任何路径按它 fork 出额外的 HTTP 前端**。

所以上一轮"多前端无收益"的正确读法是：**没有多前端可对照。** 这也解释了
513-token prompt 那一档的数值为何逐项重合（TTFT p50 174.2 对 174.0 ms）。
本轮补的形状 B（9-token prompt、并发 128）同样没有差别：

| 负载 | count=1 TTFT p50 / 整批 | count=4 TTFT p50 / 整批 |
|---|---|---|
| 513 token × 32 并发 | 173.5 ms / 346.1 ms | 176.1 ms / 345.2 ms |
| 9 token × 128 并发 | 27.9 ms / 147.3 ms | 27.9 ms / 146.5 ms |

短 prompt 那一档的 TTFT p50 只有 27.9 ms、整批 147 ms，说明前端（HTTP + 分词）
在这台机器上远没有成为瓶颈——即便真起了 4 个前端，能省下的也只是这 27.9 ms 里
属于协议与分词的那一小段。

**要在本版本横向扩前端，得换成"多个服务进程 + 外部负载均衡"**（8.1 的网关形态）：
让每个进程各带一个 EngineCore 分片，而不是指望一个进程内的线程/子进程分担。
`--api-server-count` 不是那个开关。

**SGLang 侧的进程结构已在本轮复核**（`labs/L5/run_sglang_worker_probe.sh`，
`results/crater2/5.11/sglang-worker-20260922/`）。同一条 513 token × 32 并发负载、
两次启动只改 worker 数，服务运行期间按线程名统计：

| 启动参数 | `sglang::tokeniz` 线程 | `sglang::detoken` 线程 | `sglang::schedul` 线程 | 主进程线程数 |
|---|---:|---:|---:|---:|
| `--tokenizer-worker-num 1` | 0（未出现） | 25 | 26 | 89 |
| `--tokenizer-worker-num 4` | **68** | 29 | 26 | 71 |

`--tokenizer-worker-num 4` 确实改变了进程内的线程结构（tokenizer 线程从 0 涨到 68），
但**它不是子进程**：两组都只有 `sglang.launch_server` 一个主进程，worker 是该进程内的
线程组。这与 vLLM 的 `--api-server-count` 形成对照——后者在本版本连线程都不加。

对应负载上的数字几乎不动（同一脚本、3 轮中位）：

| 配置 | TTFT p50 | TTFT p99 | 整批墙钟 | 单请求 p50 |
|---|---:|---:|---:|---:|
| worker = 1 / 1 | 171.4 ms | 260.2 ms | 368.0 ms | 358.9 ms |
| worker = 4 / 4 | 169.9 ms | 260.2 ms | 357.1 ms | 348.9 ms |

TTFT p50 差 −0.9%、墙钟 −2.9%，都落在运行间波动内。**进程结构变了、负载数字没变**，
两者一起说明：这条负载下前端（分词 + detokenize）没有形成排队，多开 worker 没有可
摊薄的等待；上一轮"影响排队而非单条处理速度"的读法由此获得进程级证据。

**仍待验证**：多进程前端与 prefix cache 共享的交互边界（缓存按进程本地、跨进程不复用，
需 8.6 的取回接口）；HTTP/3 与 h2 流控窗口；分词真正成为瓶颈的场景（更小模型或纯 CPU
前端），需要先把前端成本推到与本负载同一量级。

## 工程实现 · 源码解析

版本固定：vLLM 0.29.0、SGLang 0.5.19。行号取自 `site-packages` 里的安装源码。

### A. vLLM：应用怎么搭起来，中间件顺序是什么

`build_app()` 只做四件事（`entrypoints/launchers/app.py:19-56`）：建 `FastAPI`、
挂路由、挂异常处理、挂中间件。`api_server.py` 本身只有 59 行，是个薄壳。

{{srcfold:results/crater/api/20260912-0325/source/vllm/entrypoints/serve/middleware/register.py:19-54}}

注意 65–71 行的扩展点：`--middleware` 接的是 `模块路径.对象名`，类和协程函数都收。
这是给本章 lab 留的口子——要测某一层的耗时，不必改 vLLM。

### B. vLLM：路由函数把生成器交给 StreamingResponse

路由本身不生成 token，它只是把 handler 返回的对象分派成三种响应之一
（`entrypoints/openai/chat_completion/api_router.py:54-80`）：
错误走 `JSONResponse`，非流式走 `JSONResponse`，流式走 `StreamingResponse`。

{{srcfold:results/crater/api/20260912-0325/source/vllm/entrypoints/openai/chat_completion/api_router.py:75-80}}

真正的 SSE 字节在生成器里拼（`chat_completion/serving.py:505-506` 与 `910`）：

```
yield f"data: {data}\n\n"
...
yield "data: [DONE]\n\n"
```

`\n\n` 是 SSE 的事件分隔，不是 HTTP 的。**没有任何一层在这里加 `Content-Length`**，
所以响应必然是 chunked——这正是本章 lab 里 25 个 chunked 帧的来源。

### C. vLLM：keep-alive 注释与它绕开的 asyncio 陷阱

反向代理会在长时间没有字节时掐断连接。vLLM 的对策是发 SSE 注释行
（`entrypoints/openai/sse_keep_alive.py:36-65`）：

{{srcfold:results/crater/api/20260912-0325/source/vllm/entrypoints/openai/sse_keep_alive.py:36-65}}

这段代码处理了两个 asyncio 问题：

- `asyncio` 不允许对同一个异步生成器并发调用 `__anext__`，所以必须**保留一个 task**，
  不能每轮重新创建；
- `asyncio.wait_for` 超时会取消 task，把生成器卡在半推进状态。这里用
  `asyncio.wait(..., timeout=...)` 观察结果，超时就不管那个 task，继续等它。

`with_sse_keep_alive` 在间隔非正或非有限时原样返回生成器（31–33 行），
默认路径没有开销。间隔参数是**整秒**（`entrypoints/launchers/cli_args.py:140`）。

### D. vLLM：HTTP 层与 engine core 之间只有队列

这是本章最重要的一处结构。前端进程拿到请求后做两件事
（`v1/engine/async_llm.py:494-514`）：

{{srcfold:results/crater/api/20260912-0325/source/vllm/v1/engine/async_llm.py:494-514}}

`output_processor.add_request(...)` 在**本地**登记一个 per-request 队列，
`engine_core.add_request_async(request)` 把请求送进**另一个进程**。
反向由一条常驻协程负责（`v1/engine/async_llm.py:761-822`）：从 core 拉 `EngineCoreOutputs`，
按 `VLLM_V1_OUTPUT_PROC_CHUNK_SIZE` 切片处理，再推给各自的队列。

{{srcfold:results/crater/api/20260912-0325/source/vllm/v1/engine/async_llm.py:772-798}}

这里包含两个设计选择：切片是为了「不要一次占住事件循环太久」（注释原文），
每个切片之间 `await asyncio.sleep(0)` 让出；`reqs_to_abort` 是 core 反过来要求前端取消的请求。
**HTTP 层从不直接碰调度器**——它只会往队列里放和从队列里取。这条边界的代价是 IPC 和序列化，
收益是 HTTP 层的抖动不会传进调度，core 崩了前端还能报错而不是一起挂。

### E. vLLM：tokenization 在前端进程，且不许阻塞事件循环

`process_inputs_async` 在前端进程里跑 tokenizer，`arrival_time` 就在它入口处盖上
（`v1/engine/input_processor.py:321-322`）：

{{srcfold:results/crater/api/20260912-0325/source/vllm/v1/engine/input_processor.py:321-334}}

所以 tokenization 的耗时算在**前端段**里，不算在 `inference` 里。
这正是本章第 3 节那个减法能用的原因。

### F. SGLang：同一件事的另一种切法

SGLang 的 `/generate` 路由把 tokenizer manager 的异步生成器直接转成 SSE
（`srt/entrypoints/http_server.py:908-945`）：

```
async def stream_results() -> AsyncIterator[bytes]:
    async for out in _global_state.tokenizer_manager.generate_request(obj, request):
        yield b"data: " + dumps_json(out) + b"\n\n"
...
yield b"data: [DONE]\n\n"
return StreamingResponse(..., background=_global_state.tokenizer_manager.create_abort_task(obj))
```

与 vLLM 相比，有三处差异：

- 字节直接用 `dumps_json` 拼，不经过字符串再编码；
- 断连的清理挂在 `StreamingResponse(background=...)` 上，由 `create_abort_task` 负责，
  而不是像 vLLM 那样用 `with_cancellation` 装饰器包住路由函数；
- **detokenize 在另一个进程**。SGLang 有独立的 `DetokenizerManager`
  （`srt/managers/detokenizer_manager.py:102`），vLLM V1 则放在前端进程里。
  多一次 IPC，换前端更轻。

`AsyncDynamicbatchTokenizer.encode()` 把 `(prompt, kwargs, future)` 放进队列就返回
（`srt/managers/async_dynamic_batch_tokenizer.py:58-63`），后台循环负责攒批：

{{srcfold:results/crater/api/20260912-0325/source/sglang/srt/managers/async_dynamic_batch_tokenizer.py:65-113}}

动态批分词器开/关的前端对照（含逐档原始中位）：

{{srcfold:results/crater/api/sglang-frontend-20260913/dynamic_off/sglang_frontend.json}}

三个参数决定了它的行为：`max_batch_size=32`、`batch_wait_timeout_s=0.002`、
单线程 `ThreadPoolExecutor`。单线程是刻意的：源码注释写的是「保持事件循环响应」。
Rust tokenizer 默认不释放 GIL，多开线程预期不会并行——**这一点本章没有单独实测**，
只是解释源码为什么这样写。

同一份 token 序列分别以 `text` 和 `input_ids` 提交给同一个服务，
两者在服务端走同一段推理，差别只有前端要不要分词/后端要不要反分词。
该实验同时印证了一条核心接口契约：**SGLang 的 `/generate` 支持直接传入 `input_ids`，允许客户端整段绕过服务端的前端分词阶段。**

| 513 | 1 | 14.28 | 14.50 | −0.22 | 0.014 |
| 513 | 8 | 61.23 | 57.06 | +4.17 | 0.077 |
| 513 | 32 | 159.18 | 158.86 | +0.32 | 0.277 |

三条结论：

1. **4097 token 一档的前端成本是 2.0–3.0 ms/请求**，相对该档 101–1485 ms 的端到端

2. **33/513 两档的差值在 ±4 ms 内来回，出现负值**（ids 反而更慢），

3. **动态批分词器在这组负载下没有可测收益**：打开后 9 格里 5 格的差值反而变大，

   在 batch ≤ 32、prompt ≤ 4096 的组合里没有出现；2 ms 攒批窗口的代价
   在这个 batch 下也换不到批量收益——与上面「低并发下换不到收益」的推断一致，

**那就把它推到它针对的场景去测。** "攒批"要有收益，得同时满足"并发足够多"
和"每条足够短（分词本身便宜、但调用次数多）"。把并发提到 **64/128/256**、
prompt 压到 **8/32 token**，仍然用"同一份 token 内容分别以 text / input_ids 提交"
的办法分离前端成本（`run_sglang_frontend_highconc.sh`，

| 长度 | batch | **text 中位（关 → 开）** | ids 中位（关 → 开） | 差值（关 → 开） |
|---:|---:|---|---|---|
| 8 | 64 | 30.18 → **32.01 ms** | 28.61 → 30.05 | +1.57 → +1.97 |
| 8 | 128 | 36.58 → **41.30** | 38.80 → 35.39 | −2.22 → +5.91 |
| 8 | 256 | 50.32 → **50.08** | 49.51 → 43.80 | +0.81 → +6.28 |
| 32 | 64 | 70.31 → **81.20** | 77.22 → 83.98 | −6.92 → −2.78 |
| 32 | 128 | 120.96 → **122.24** | 93.81 → 97.15 | +27.14 → +25.09 |
| 32 | 256 | 153.12 → **182.53** | 147.15 → 160.44 | +5.97 → +22.09 |

**在它自己的目标场景里也没有收益，而且多半更慢。** 逐格比同一负载下的 text 中位：
打开后 6 格里 **5 格变慢**（+0.2 ~ +29 ms），只有 8/B=256 一格基本持平（−0.24 ms）；
批墙钟同向（0.054→0.057、0.083→0.087、0.141→0.145、0.097→0.104、0.171→0.182、

而且 +27/+25 ms 这两格在**开关两侧同时存在**——说明它们不是开关造成的，
而是这套"text 减 ids"代理在这个负载下的系统性偏差。所以**能引用的只有
"同一格内开关前后的 text 中位对比"**，不能引用差值列本身。

合并两轮结论：**在 batch 1–256、prompt 8–4096 的范围内，动态批分词器没有测到收益，
代价（2 ms 窗口）倒是稳定可测。** 这不等于"该开关无用"——它针对的是
分词任务本身成为瓶颈的场景（更小的模型、更长的分词器队列、或纯 CPU 前端），
本实验的 SGLang 前端在这些负载下都还不是瓶颈。

### H. 两边的增量 detokenize 都在处理同一个问题：半个字符

SGLang 的 `DecodeStatus` 带两个游标（`srt/managers/detokenizer_manager.py:75-81`）：
`surr_offset` 是「用来当上下文但不输出」的窗口，`read_offset` 是「已经输出到哪」。
每步把 `decode_ids[surr_offset:read_offset]` 解码一次当上下文，再把新的一段输出，
然后 `surr_offset = read_offset; read_offset = len(decode_ids)`（394–395 行）。

vLLM 用 tokenizers 库的 `DecodeStream` 达到同样效果。两边的共同点是：
**解码器需要回头看一眼已经吐出去的字符，才能决定新 token 的文本**。
这就是「一个 token 不一定产生一个事件」的根源。

## 设计取舍

**前端进程做多少事。** vLLM 把 tokenize、detokenize、SSE 编码都放在前端进程，
engine core 只管调度和前向；SGLang 把 detokenize 又拆了一个进程出去。
前端做得多，IPC 少、延迟低，但前端一卡全线卡；拆得越细，越能独立扩缩，
代价是每一段都要序列化，而且时间戳散在多个进程里，性能归因更难做。
本章的减法能成立，正是因为它建立在「戳在前端、推理在 core」这个具体切法上。

**流式响应的背压放在哪。** SSE 没有应用层流控，背压只能由 TCP 窗口传导。
`writer.drain()` 会等到对端把数据收走（`labs/L5/nanoserve/server.py:137`），
慢客户端因此把整个引擎拖住。要在应用层解决，就得给每个流加有界队列并定义丢弃策略——
这不是 HTTP 层能单独决定的事，它要和 5.3 的调度、5.8 的背压一起设计。

**keep-alive 注释是给中间设备看的，不是给客户端看的。** 客户端必须忽略它，
但它确实占带宽。间隔设小了，长连接的空闲期会持续产生注释；设大了，代理照样掐断。
默认 0 表示不产生，只有部署在会掐连接的代理后面才需要打开。

**取消由谁负责。** vLLM 用装饰器包路由，SGLang 用 `background` 任务。
前者要求「请求体已经被读完」，因为装饰器会消费掉后续消息来找断连
（`entrypoints/serve/utils/api_utils.py:51-71` 的注释明确写了这条前提）；
后者挂在响应对象上，天然知道流什么时候结束。两种都能用，
使用装饰器时必须满足上述前提，否则可能丢失尚未读取的请求体数据。


HTTP 客户端自己用 `socket` 写，因为要拿到**未经解析的字节**。用 `requests` 或
`httpx` 只能看到解完 chunked 之后的 body，看不到分帧。

### 2. 原始字节流：两层分帧各是多少

一次 24 token 的流式响应，从 socket 上收到的东西：

| 项 | 值 |
|---|---:|
| 响应头字节 | 168 |
| 总字节 | 6 211 |
| body 字节 | 5 888 |
| chunked 帧数 | 25 |
| 单帧负载最小 / 最大 | 14 / 292 字节 |
| `recv` 调用次数 | 25 |
| SSE 事件数 | 25（24 个 delta + 1 个 `[DONE]`） |
| 空 delta 事件数 | 0 |
| 平均每个 delta 事件字节 | 245.3 |
| 首个事件到达 | 17.6 ms |
| 末个事件到达 | 89.0 ms |
| 事件间隔中位 / 最大 | 3.13 ms / 17.56 ms |

响应头里是 `server: uvicorn`、`transfer-encoding: chunked`、`connection: close`。
**没有 `content-length`**：流式响应在生成完之前不知道总长，只能 chunked。

4 个 ASCII 字符的 token 编码成 JSON 后约 20 字节，加上 `data: ` 和两个 `\n`，
一条事件 27 字节左右；再套一层 chunked 的长度前缀和 CRLF，就是 245 字节/事件里
大部分的开销来源。**协议开销是有效载荷的十倍量级**——这不是缺陷，
但解释了为什么小模型的流式吞吐会被字节数而不是算力限制住。

最大间隔 17.6 ms 就是 TTFT，和引擎侧 `prefill` 均值 4.41 ms 的差是排队与 IPC。
中位间隔 3.13 ms 说明多个 token 常常被一次 `recv` 一起读到——
**客户端的读次数不等于服务端的写次数**，把 `recv` 次数当作「chunk 数」是错的。

### 3. 层间分解：非推理部分占 1.84%

12 条串行流式请求，引擎指标增量除以请求数：

| 段 | 均值 ms | 占客户端墙钟 |
|---|---:|---:|
| **客户端墙钟** | **77.75** | **100%** |
| 前端段（进程内：tokenization + 序列化 + IPC + core 准入） | 0.79 | 1.02% |
| 排队段 queue | 0.005 | 0.01% |
| 运行段 inference | 76.32 | 98.2% |
| ├ prefill | 4.41 | 5.7% |
| └ decode | 71.91 | 92.5% |
| 进程外段（入站解析与中间件 + 增量 detokenize + SSE 编码 + 回写） | 0.63 | 0.81% |

四段相加 `0.79 + 0.005 + 76.32 + 0.63 = 77.75`，与客户端墙钟 77.75 ms 完全吻合。
四段覆盖了从 `sendall` 到收到最后一个字节的时间，
没有重叠也没有遗漏。

结论：24 token 的短请求里，HTTP 与协议层合计 **1.84%**，推理占 98.2%。
`prefill` 只有 4.41 ms 而 `decode` 71.91 ms，说明 24 个 token 里绝大多数时间
花在逐 token 的 decode 上——**短输出请求的时延几乎完全由输出长度决定，
前门能优化的空间很小**。

做这种减法必须知道每个时间戳的起点：`e2e` 从「输入处理开始」算起，
客户端从 `sendall` 算起，两者的差是「入站解析 + 回程」；`e2e` 止于
「最后一个 token 在 core 里生成」，客户端止于最后一个字节到达，两者的差是回写。
把这一段叫做「回程」是不准确的——它同时包含入站和出站两侧。

### 4. 并发：客户端时延涨得比推理快

同一份负载，不同并发下的客户端侧数据：

| 并发 | 客户端均值 ms | p50 ms | p95 ms | TTFT 最大 ms | 吞吐 req/s |
|---:|---:|---:|---:|---:|---:|
| 1 | 79.13 | 79.13 | 79.13 | 7.5 | 12.6 |
| 8 | 96.81 | 96.86 | 97.10 | 12.6 | 81.7 |
| 32 | 104.91 | 105.55 | 106.72 | 28.7 | 288.9 |

引擎侧同批次的每请求均值，以及「客户端均值 − 引擎 e2e」得到的进程外段：

| 并发 | e2e ms | queue ms | inference ms | prefill ms | decode ms | 进程外 ms |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 78.28 | 0.016 | 76.89 | 5.12 | 71.77 | 0.85 |
| 8 | 95.18 | 0.009 | 91.28 | 6.47 | 84.81 | 1.63 |
| 32 | 100.76 | 0.013 | 94.17 | 10.69 | 83.48 | 4.15 |

三点读数：

- **排队时间始终接近 0。** vLLM 默认 `max_num_seqs` 远大于 32，请求可以直接进入执行，
  所以瓶颈不是准入，而是 batch 变大后每个 decode step 变长（71.77 → 84.81 ms）。
- **进程外段随并发上升：0.85 → 1.63 → 4.15 ms。** 32 条流同时在事件循环里做
  detokenize 和 SSE 编码，前端开销随之增加。它在低并发时不到 1 ms，
  所以只测单请求是看不到这一段的。
- **TTFT 最大从 7.5 ms 涨到 28.7 ms，比均值涨得猛。** 首 token 要等 prefill 排进一个
  iteration，而 iteration 的长度随 batch 增长；已开始执行的请求不再经历这段等待。

**前门的占比随负载上升。** 按「客户端均值 − inference」算，非推理部分从并发 1 的
2.8% 涨到并发 32 的 10.2%。这不是「HTTP 层变慢了」，而是推理段被 batch 摊薄、
而前端开销按请求数线性叠加。

并发 32 这一档此前记过：同一配置三次运行的客户端 p50 是 131.4 / 105.3 / 105.6 ms、
TTFT 最大 54.7 / 27.0 / 28.7 ms，差幅超 20%，**当时没有定位**。
按计划要求（"并发 32 的波动需交错重复、事件循环与连接重用记录解释"）
把它做成实验设计：**每一轮都跑 1/8/32 三档，共 6 轮交错**
（`labs/L5/concurrency_variance.py`，`results/crater/api/conc-variance-20260914/`）。

| 档 | p50 中位 | 区间 | 差幅 | **首轮** | 客户端 CPU / 墙钟 |
|---:|---:|---|---:|---:|---|
| 1 | 121.49 ms | 120.77–126.77 | 4.94% | 126.77 ms | 0.2–0.4% |
| 8 | 142.64 ms | 140.53–143.73 | **2.24%** | 140.53 ms | 2.1–3.2% |
| 32 | 162.97 ms | 159.94–**183.59** | **14.51%** | **183.59 ms** | 5.8–8.5% |

三份记录把这条波动拆开了：

1. **差幅几乎全部来自首轮，也就是预热/轮次效应。**
   并发 32 的首轮是 **183.59 ms**，之后 5 轮落在 159.9–167.6 ms，
   **后续轮之间的差幅只有约 4%**；而 8 档的首轮（140.53 ms）反而是它最快的一轮，
   说明这不是"轮次越靠前越慢"的普遍漂移，而是**第一次跑到 32 并发**那一下的代价
   （图捕获/内核自动调优/CPU 侧线程起速）。这与旧记录里
   "131.4 → 105.3 → 105.6" 的形状一致：如果每档只顺序跑一次，
   第一次 32 档就必然把预热算进去。
2. **引擎排队不是原因。** 三档的 `request_queue_time` 都在 **0.02 ms 以下**，
   32 档的 p50 比 8 档高出的约 20 ms 完全不在排队里。
3. **客户端也不是主因，但它在按并发放大。** 客户端 CPU 占墙钟的比例从
   1 档的 0.2–0.4% 涨到 32 档的 **5.8–8.5%**：32 个 Python 线程做 SSE 解析确实在吃 CPU，
   但它离"客户端自己成为瓶颈"（比值接近 1）还差一个量级。

顺带记一条**可比性边界**：这次的绝对值（32 档中位约 163 ms）高于旧记录的 105 ms，
因为服务配置与机器状态都不同（本次 `gpu_memory_utilization=0.28`，
且机器上另有一个占 18.5 GB 显存的服务在跑）。
**跨运行的绝对值不可比**，可比的是形状：档位方向（1 < 8 < 32）与首轮偏慢。

连接重用另测：回环上新建连接相对复用一条连接的成本约 **0.97 ms/请求**
（5.11 任务 C 的代理实验已量，见第 6 节），相对 100 ms 量级的时延约 1%，
所以它**不足以解释** 20% 的差幅——这一条在这里是用数据把可能性排除掉。

### 5. tokenization 曲线

| 输入字符 | token 数 | 中位耗时 ms | 单 token µs |
|---:|---:|---:|---:|
| 69 | 17 | 0.022 | 1.27 |
| 552 | 129 | 0.090 | 0.70 |
| 4 416 | 1 025 | 0.608 | 0.59 |
| 17 664 | 4 097 | 2.397 | 0.59 |
| 70 656 | 16 385 | 9.582 | 0.58 |

单 token 成本在 1k token 以上收敛到约 0.59 µs。**这条曲线是线性的**，
没有拐点，说明 HF 的 Rust tokenizer 在常见长度区间没有需要回避的复杂度。
把它和上表的 `prefill` 比：16k token 的编码 9.6 ms，同规模的 prefill 在 GPU 上
远快于此——**CPU 侧的 tokenization 确实是长上下文请求里 CPU 与 GPU 之间
最不匹配的一对**，但它的绝对量级（毫秒）还不足以成为吞吐瓶颈。

同一进程内顺序编码 16 段 256-token 文本共 9.78 ms，折合 **2.39 µs/token**；
而一次编码 4097 token 的长文本只要 2.397 ms，折合 **0.59 µs/token**。
**同样的 token 总量，合成一次调用比拆成 16 次便宜约 4 倍。**
这是下一节「合起来」那条路线的依据：合批省下的不是算法复杂度，
是每次调用的固定开销与短输入下 tokenizer 内部的低效。

### 6. 把 tokenizer 放回事件循环

单看耗时不能说明问题，得看它阻塞了谁。实验设计：先起一条流式请求 A，
等它稳定吐 token（稳态间隔约 20.6 ms，即一个 decode step）；
然后发请求 B，只测 B 到达那一刻 A 的间隔有没有多出来。

B 走一个**只做编码、不进引擎**的端点，这样「事件循环被占住」和
「引擎多了一条请求」是分开的两件事。B 的 prompt 长度用 `--b-reps` 控制，
用 4 段（65 token）当对照组。

| B 的规模 | 写法 | B 编码耗时 ms | A 在 B 到达前间隔最大 ms | B 到达后 A 间隔最大 ms | 多出来的部分 ms |
|---|---|---:|---:|---:|---:|
| 16 001 token | `tok.encode()` 直调 | 11.02 | 20.35 | **31.76** | **+11.4** |
| 16 001 token | `asyncio.to_thread` | 31.71 | 21.04 | 21.53 | +0.5 |
| 65 token | `tok.encode()` 直调 | 0.96 | 20.66 | 21.10 | +0.4 |
| 65 token | `asyncio.to_thread` | 1.13 | 21.25 | 21.40 | +0.2 |

读法：

- **in-loop 组多出来的 11.4 ms，等于 B 自己的编码耗时 11.0 ms。** 事件循环被占多久，
  别人就等多久，一一对应。
- **对照组（65 token）几乎不动**，说明这个尖峰来自 tokenization，不是「B 到达」这件事本身。
- **`to_thread` 组没有尖峰**，尽管它的编码耗时反而更长（31.7 ms）。它保护了别人，
  自己却多等了 20 ms——多出来的正是「线程干完了，但事件循环还在忙」的那一段。

当同一个负载执行完整的端到端生成路径（B 也是一条真实请求，prompt 同样是 16k token）时，
A 的最大间隔在两种写法下分别是 373.4 ms 和 373.9 ms，**没有区别**。
因为 B 的 prefill 要占 47 个 chunked prefill 步，引擎侧的负载才是主导，
tokenization 的 11 ms 被淹没了。**这条对照说明：只有当引擎侧的扰动小于 tokenization
的耗时时，这个实验才测得出东西。** 在小模型、短输出、单请求的场景下，
in-loop tokenization 的代价才显现；大模型长输出的生产负载里，它通常不是第一瓶颈。

### 7. keep-alive 注释：一次真实的样本

`--sse-keep-alive-interval` 是**整秒**，所以注释只在流空闲超过 1 秒时出现。
把 `--max-num-seqs` 压到 1、并发发 20 条请求，排队时间拉到均值 732 ms、
TTFT 最大 1 483 ms，20 条流里有 7 条各收到一条注释。

字节流里它的样子（`data-keepalive2/conc20-slowest.bin`）：

```
e\r\n: keep-alive\n\n\r\nf0\r\ndata: {"id":"cmpl-922d22fce1e26002",...
```

`e` 是十六进制的 14——**注释自成 14 字节的 chunked 帧**，正好等于
`: keep-alive` 12 字节加两个 `\n`。紧随其后的 `f0` 帧（240 字节）才是下一个 token。
它落在两次 `data:` 之间，SSE 客户端必须跳过；但代理的读超时会把它算成流量，
这正是它的作用。

### 8. 消融与未测范围

建议消融，每种配置另存结果：

- 把 `--b-reps` 在 100 到 3000 之间扫描，找出「in-loop 尖峰」从什么时候开始
  超过稳态间隔的一半；
- **（已做）`--enable-dynamic-batch-tokenizer` 的开关对照**：见 G 节实测。
  下一步是把并发推到 batch ≥ 128、prompt ≤ 64 的小请求场景，
  那里才可能出现攒批收益；同时把 2 ms 窗口扫到 0/1/4 ms。
- 把 `--sse-keep-alive-interval` 设为 1 秒并把 `--max-num-seqs` 压到 1，
  观察排队流的注释频率与代理行为；
- 用 `--middleware` 挂一个计时中间件，把 ASGI 解析与路由的耗时单独量出来。
- **（已做）代理的 buffer / 慢读者 / 断连对照**：见机制拆解第 6 节。
  下一步是给代理加真正的连接池再测 keep-alive，以及装 `h2` 补 HTTP/2 基线。

未测：

- **SGLang 端的完整对照只补了前端这一段。** 前端分词与动态批分词器已实测（G 节），
  但高并发（batch ≥ 128 的小请求）下攒批收益、以及 SGLang 的排队/尖峰
  仍未对照，那部分保持 `UNVERIFIED`。
- **keep-alive 的间隔与代理行为只补了一半。** 注释频率与排队时长的定量关系、
  以及真实反向代理（NGINX `proxy_read_timeout`、Cloudflare Tunnel）的行为差异都没有测；
  代理的 buffer/慢读者/断连已用自建最小代理测过（第 6 节），但没有连接池，
  也没有 HTTP/2（Python 侧缺 `h2`；服务端与 curl 侧另有 h2c 实测）。
- **HTTP/2 已补 h2c 一段，HTTP/3 未测。** h2c 的协商（`%{http_version}` 报 `2`）、
  SSE（两边都 17 个事件）与 32 并发已实测，见前面那一节；
  HTTP/3 本机 curl 没有 HTTP3 feature。HTTP/2 没有 chunked 这一层，
  SSE 直接走 DATA 帧；**多路复用对前端排队行为的影响没有单独测**。
- **两个引擎的"多前端"旋钮在进程结构上不同，且都没有收益。** vLLM 的
  `--api-server-count 4` 与 1 完全同构（一个 EngineCore 子进程 + 父进程持有唯一监听
  套接字，源码里该参数只用于 DP 默认值、多模态缓存容量与一条指标告警）；
  SGLang 的 `--tokenizer-worker-num 4` 确实多出 68 个 `sglang::tokeniz` 线程，
  但仍是同一个主进程内的线程组，负载数字在波动内（p50 171.4 → 169.9 ms）。
  前端横向扩展在本版本等于"多开服务进程 + 外部负载均衡"（8.1），
  代价是 prefix cache 变成进程本地（8.6 的取回接口）。
- **`empty_delta_events` 在这次运行里是 0**，所以「token 数 ≠ 事件数」
  只有源码依据，没有本章的实测样本。

## 前沿

沿本章机制继续扩展，而不是只调参数：

- **前端与 core 的边界往哪挪。** 本章的减法依赖「tokenize 在前端、推理在 core」。
  把 tokenize 挪进 core（或再拆一个 tokenizer 进程）会改变这条边界，
  也随之改变哪些时延指标可比。值得系统测量的是**挪动边界对尾延迟的影响**，
  而不是某一次的平均值。
- **应用层背压。** SSE 把流控完全交给 TCP，慢客户端会把引擎拖住。
  有界队列 + 丢弃/降级策略需要在 HTTP 层和调度层之间定义一个接口，
  这个接口目前没有标准形态。
- **协议升级。** HTTP/2 的 DATA 帧、HTTP/3 的流、以及 gRPC 双向流，
  都会改变本章的三层分帧。哪些结论能保住、哪些要重做，需要实测。
- **tokenizer 的并行度。** SGLang 用单线程执行器，源码说明的理由是「保持事件循环响应」。
  Rust tokenizer 默认不释放 GIL，因此多开线程预期不会并行——**本章没有单独实测多线程编码，
  这一条是推断，不是测量结果**。真正的加速方向是**批内合并**（SGLang 的做法）或换实现
  （如 tiktoken 风格的分词），两者都需要在自己的负载上测，不能只看单次编码耗时。

## 陷阱

1. 把 `recv` 次数当成服务端写的 chunk 数。本章 25 个 chunked 帧恰好对应 25 次
   `recv`，这是偶然；TCP 合并是常态。
2. 用 `requests` / `httpx` 抓 SSE 再谈分帧——它们只给你解完 chunked 的 body。
3. 把 `e2e_request_latency` 当成客户端感知的时延。它从输入处理开始、到最后一个 token
   在 core 里生成为止，**不含 detokenize 与回写**。
4. 拿不同引擎的指标直接相减。时间戳盖在哪个进程、包不包括 detokenize，
   各引擎不同。
5. 以为「生成 N 个 token」就一定有 N 个 SSE 事件。增量 detokenizer 会扣住
   不完整的 UTF-8 前缀。
6. 误以为返回 `StreamingResponse` 就能绕过中间件。它同样需要逐层经过整条中间件处理链。
7. 只测 tokenization 的单次耗时，不看它阻塞了谁。0.6 µs/token 看起来很便宜，
   放在事件循环里就变成了别人的延迟。
8. 把 keep-alive 注释当成数据。它是注释，客户端必须忽略，但它占带宽。
9. 以为 SSE 有应用层流控。没有，背压只能靠 TCP 窗口传导。

## 自测题

1. 一条流式响应在 HTTP/1.1 上有哪两层分帧？为什么客户端必须按字节流处理？
2. `e2e_request_latency_seconds` 与客户端墙钟的差包含什么？为什么会有正有负？
3. 引擎的 `queue` 时间是 0.005 ms，但并发 32 时客户端 p50 比并发 1 高了 26 ms。
   这 26 ms 花在哪？
4. 同一个 16k token 的输入，`to_thread` 后服务端侧耗时从 11.0 ms 涨到 31.7 ms。
   为什么还要这么做？
5. 一个 token 编码成 4 个 ASCII 字符，为什么一条 SSE 事件要 245 字节？
6. 为什么本章要关掉 prefix caching？

::: fold 答案
1. 外层 HTTP/1.1 chunked（长度 + CRLF + 负载 + CRLF），内层 SSE（字段行 + 空行）。
   两层都可能把一个逻辑单元拆到多次 `recv`，所以只能按字节流增量解析，
   不能假定一次读到一个完整帧。
2. 差 = 请求从 `sendall` 到「输入处理开始」的时间（网络 + ASGI 解析 + 中间件）
   减去回程（detokenize + SSE 编码 + 回写）。本章并发 1 时客户端墙钟 77.75 ms
   比 e2e 77.12 ms 大 0.63 ms（进程外段为正）；并发 32 时这个差涨到 4.15 ms。
   正负取决于入站与出站两侧各占多少，而两侧都随负载变化。
3. 不在排队（`queue` 始终约 0.01 ms），而在两处：batch 变大后每个 decode step
   变长（decode 71.77 → 84.81 ms），以及 32 条流同时在事件循环里做
   detokenize 与 SSE 编码，进程外段从 0.85 ms 涨到 4.15 ms。
   两项相加仍解释不了全部差值，剩下的落在 prefill（5.12 → 10.69 ms）与统计口径差异上。
4. 因为成本是**自己的**，收益是**别人的**。in-loop 时这 11 ms 会加到所有在跑的
   请求的 token 间隔上；`to_thread` 后尖峰消失，代价只是发起方多等一次线程往返。
   多租户下这笔交易成立。
5. 4 个 ASCII 字符的 token 编码成 JSON 是 `{"token": 1234}` 这类形式，约 20 字节；
   加 `data: ` 前缀和两个 `\n`，一条事件约 27 字节；再套 chunked 的长度前缀、
   CRLF 和响应头摊销。协议开销是有效载荷的十倍量级。
6. 本章所有请求用同一条 prompt。开着前缀复用，第一条之后的 `prefill` 会塌到接近 0，
   运行段的构成就失真了；`prefill`/`decode` 的对照和前端段的减法都会失去意义。
:::
