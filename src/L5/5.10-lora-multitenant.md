## 本章回答三个问题

多 LoRA 服务让请求共享基础模型，并分别使用各自的 adapter。引擎需要将请求、GPU 权重槽位和 token 行对应起来，在槽位不足时安排等待或换入。

1. 一个 batch 混入不同 adapter，怎样实现共享 base GEMM 与逐行低秩增量？
2. adapter 的逻辑身份、CPU 缓存、GPU 槽位和 KV cache 怎样保持一致？
3. adapter 数量从 1 增到 64 时，吞吐下降来自 kernel，还是调度容量？

本章用随机生成的 adapter 验证系统机制，不评价微调质量。实测的核心结论是：**固定 8 个 GPU adapter 槽位时，8→9 个 adapter 让这组等长请求从一轮拆成两轮，端到端耗时接近翻倍。** 这里限制并行执行的是配置的槽位数。

## 心智模型

adapter 是附加在 base 模型上的小权重集合。请求携带逻辑 ID；worker 把它映射到可复用的物理槽位。低秩 kernel 读取的是槽位，不应拿外部 ID 直接当数组下标。

## 机制拆解与推导

### 1. 低秩更新避免为每个租户复制完整模型

设 base 权重 $W\in\mathbb{R}^{O\times H}$，adapter 的 $A\in\mathbb{R}^{r\times H}$、$B\in\mathbb{R}^{O\times r}$。r 是 rank，即低秩中间维度。普通 LoRA 的缩放 $s=\alpha/r$，一行输入满足：

$$y=xW^T+s(xA^T)B^T.$$

先算 $xA^T$ 把 H 维压成 r 维，称为 shrink；再乘 $B^T$ 展开到 O 维，称为 expand。它们是两次矩阵乘法，不是把 A、B 逐元素加到 W。

共有 M 行输入时，base 计算量约为 $2MHO$ FLOPs；低秩分支约为 $2Mr(H+O)$ FLOPs。BF16 adapter 权重字节数为：

$$D_{adapter}=2r(H+O).$$

本章 Qwen3-1.7B 的 q_proj 使用 H=O=2048、28 层、r=8，因此全部层的 q_proj adapter 张量共 $2\times8\times(2048+2048)\times28=1835008$ 字节，即 1.75 MiB。这是张量净数据，不包括 safetensors 文件头、CPU 对象、GPU padding 和其他被包装层的预分配空间。

单个 q_proj 的理论额外 FLOPs 比例为 $r(H+O)/(HO)=0.0078125$。**0.78125% 的 FLOPs 不等于 0.78125% 的时延。** 小 GEMM、metadata 整理、额外 kernel 发射、槽位复制和中间 buffer 都不在这个比例中。

### 2. 混批要求逐行选择权重

令 $a(i)$ 是 token 行 i 的 adapter ID，$s_{a(i)}$ 是对应缩放：

$$Y_i=X_iW^T+s_{a(i)}(X_iA_{a(i)}^T)B_{a(i)}^T.$$

base 的 $XW^T$ 仍能对整个 batch 做一次 GEMM。低秩部分按 adapter 分组：取属于同一 adapter 的行，做两次小 GEMM，再写回原行号。实现可以只排序行号并间接寻址，不必物理搬动整个 X。

不能把 $\sum_jB_jA_j$ 合并进一份 W 供所有请求使用，那会把每个租户的更新同时应用到所有请求。逐 adapter 合并成 $W_j=W+s_jB_jA_j$ 在代数上可行，但会重新承担多份 dense 权重的存储和分组执行成本。

### 3. 三种容量不能混为一谈

| 容量 | 本次扫描配置 | 限制的对象 |
|---|---:|---|
| 提交请求数 | 64 | 一次离线 generate 的请求集合 |
| `max_cpu_loras` | 64 | worker 保留的 adapter 缓存数量 |
| `max_loras` | 8 | 同一步可用的 GPU adapter 槽位数量 |

64 个请求只用一个 adapter 时，一个槽位足够。64 个请求各用一个不同 adapter 时，即使模型和 KV 显存有余量，也不能在这套配置下把 64 种 adapter 同时装进 8 个槽位。

驻留选择还会影响 KV 容量。粗略预算为：

$$M_{GPU}=M_{base}+M_{adapter\ slots}+M_{KV}+M_{activation}+M_{workspace}.$$

增大槽位数可能减少换入或调度分轮，但会增加预分配、metadata 和潜在的图捕获组合；不能只按磁盘上的 adapter 文件大小估算 GPU 成本。

### 4. 换入成本应分层测量

文件解析、CPU 缓存命中、CPU→GPU 复制、目标槽位清零、mapping 更新是不同阶段。若 CPU 权重已经存在，传输部分可用 $D/B_{H2D}$ 作理想化预测，但实测的整个 `activate_adapter` 还包括 Python 调度与多层小复制，不能反过来当成 PCIe 峰值带宽。

是否驻留可按预期复用次数分析：若保留该 adapter 节省的累计换入时间大于其挤占 KV 或其他 adapter 所增加的等待代价，保留才有意义。这是设计分析；本章没有拟合线上到达过程，也没有得出通用驻留阈值。

## 工程实现 · 源码解析

以下行号均对应本地保存的安装版本快照，具体 revision 与校验值见 manifest。vLLM 实验为 **0.29.0**，模型为 **Qwen3-1.7B**。SGLang 对照来自既有 0.5.19 环境，不把其 kernel 小实验当作整套引擎性能。

### A. 调度器先保证这一轮容得下所有 adapter

`vllm/v1/core/sched/scheduler.py:817–830` 在接纳 waiting 请求前检查 `scheduled_loras`。达到槽位上限后，使用新 adapter 的请求被暂时跳过；使用已选 adapter 的请求仍有机会进入本轮。

{{src:results/crater/lora/20260912-0010/data/source/scheduler.py:817-830}}

这解释了为什么同样 64 个请求会拆成不同波次。不能把 `max_num_seqs=64` 解读为“所有请求必定同时执行”。

### B. CPU 缓存和 GPU 槽位分别管理

`vllm/lora/worker_manager.py:293–314` 先加载并验证新 adapter，再驱逐旧 CPU 缓存项。这样无效文件不会先把正常缓存赶走。CPU 命中后仍需要激活对应 GPU 槽位。

{{src:results/crater/lora/20260911-1110/source/vllm/worker_manager.py:293-314}}

GPU manager 的 `model_manager.py:315–351` 选择空槽，将 ID 记入 `lora_index_to_id`，再逐层设置权重。通用 linear 层在 `base_linear.py:174–184` 先 reset，再复制有效 rank 区域：

{{src:results/crater/lora/20260911-1110/source/vllm/layers/base_linear.py:174-184}}

清零不是多余操作。rank 较大的旧 adapter 被 rank 较小的新 adapter 替换时，未覆盖的尾部不能继续参与计算。QKV 与 merged linear 覆盖了具体的 `set_lora` 实现；通用 linear 的这段分析不能代替所有 packed 布局的实现细节。

### C. 逻辑 ID 先转槽位，再整理分组 metadata

`punica_wrapper/utils.py:91–111` 建立反向表。正 ID 映射到 GPU slot；base 请求映射到内部哨兵 -1。入口处的 0 与 kernel 中的 -1 不是同一层接口。

{{src:results/crater/lora/20260911-1110/source/vllm/punica_wrapper/utils.py:91-111}}

`ops/triton_ops/lora_kernel_metadata.py:135–151` 对 slot ID 稳定排序，保存原 token 行号，并统计每个 slot 的行数。`164–168` 对计数求前缀和，得到分段起点。

{{src:results/crater/lora/20260911-1110/source/vllm/ops/triton_ops/lora_kernel_metadata.py:135-151}}

必须同时维护四项：行→slot、按 slot 排序的原行号、每组行数、每组起点。只把 ID 排序而不保存原行号，会把不同请求的输出写错位置。

### D. Punica wrapper 调用 shrink 与 expand

`punica_gpu.py:245–267` 为低秩中间量创建 FP32 buffer，shape 是 `[output_slices, token_rows, rank]`。shrink 填入中间量，expand 加到输出的相应 slice。

{{src:results/crater/lora/20260911-1110/source/vllm/punica_wrapper/punica_gpu.py:245-267}}

在 `max_loras=2, max_lora_rank=16` 配置下，真实 QKV 入口张量形态实测如下：

| 字段 | prefill | decode |
|---|---|---|
| X shape / stride | `[80,2048]` / `[2048,1]` | `[8,2048]` / `[2048,1]` |
| Y shape | `[80,4096]` | `[8,4096]` |
| A 的三个 slice | 各 `[2,1,16,2048]` | 相同 |
| B 的三个 slice | `[2,1,2048,16]`、两个 `[2,1,1024,16]` | 相同 |
| output_slices | `[2048,1024,1024]` | 相同 |

需要注意该组参数对应双槽位配置（不同于后文基准测试中的 8 槽位、rank 上限 8）。q_proj adapter 文件中的 `[8,2048]` 也不等于 GPU packed QKV 所有预分配张量的物理 shape。完整插桩保留了其他被包装的 linear 层，不能仅凭存在包装就断定每一层都包含非零 adapter 权重。

### E. SGLang 显式描述分段与每槽 rank

SGLang `srt/lora/backend/triton_backend.py:74–98` 调用真实 `sgemm_lora_a_fwd` / `sgemm_lora_b_fwd`。`LoRABatchInfo` 带有分段边界、权重槽位、每槽 rank、scaling 和可选 permutation。

{{src:results/crater/lora/20260911-1110/source/sglang/backend/triton_backend.py:74-98}}

本章 probe 的 6 行输入分为 `[0,2)`、`[2,3)`、`[3,6)`，metadata 为：

```text
seg_indptr  = [0, 2, 3, 6]
weight_indices = [1, 0, 2]
lora_ranks = [0, 8, 16]
X = [6, 64]; A = [3, 16, 64]; B = [3, 48, 16]
low = [6, 16]; Y = [6, 48]
```

rank 数组按槽位索引，不按 segment 序号索引。因此第一段用 slot 1 的 rank 8；第二段用 slot 0 的 rank 0，增量应为零。与 FP32 dense 参照的最大绝对误差为 `2.5033950805664062e-05`，base 行确实为零。输入权重为 FP16；这不是逐位相等，也不是 vLLM 与 SGLang 的端到端对照验证。

### F. adapter 身份还进入 prefix cache key

本版本 vLLM 的 `v1/core/kv_cache_utils.py:542–554` 返回 `lora_name` 作为额外 hash key，并非 `lora_int_id`：

{{src:results/crater/lora/20260911-1110/source/vllm/kv_cache_utils.py:542-554}}

相同 prompt 在不同 adapter 下可能产生不同隐藏状态，不能无条件共用 KV。服务设计还需要让名称与权重版本保持一致，或在更新时可靠失效缓存。本章性能实验显式关闭 prefix caching。

同名热更新测试（`lora_kv_invalidation_test.py`）使用相同 `lora_name="test"` 和相同 prompt，分四步生成：v1 权重首次、v1 权重第二次、v2 权重（同名覆盖）、v1 权重第三次。观察到：

- v1 的三次输出完全一致（24 个点）
- v2 输出与 v1 不同（`"? the ...? is . "`）

**这个方向不成立，正文在此改正。** 旧实验每步都在换 `lora_int_id`，又没有记录缓存命中，
所以它无法区分"权重生效"与"缓存复用"。重做的实验
（`labs/L5/lora_cache_identity_test.py`，`results/crater/lora/cache-identity-20260914/`）
把 name / id / path / 权重内容四个量分开动，并在每步读 `llm.get_metrics()`
里的 prefix cache 计数——**判据是命中计数，不是文本比对**：

| 步 | name / id / path | 输出 | `prefix_cache_hits` 增量 |
|---|---|---|---|
| S1 | A / 1 / P1（v1） | v1 token | **0**（queries 101） |
| S2 | A / 1 / P1（v1）再发一次 | v1 token | **96** |
| S3 | A / 1 / P1，**把 P1 的权重原地换成 v2** | **v1 token** | **96** |
| S4 | A / 1 / P2（v2 的副本） | **v1 token** | **96** |
| S5 | B / 2 / P1（此时权重已是 v2） | **v2 token** | **0** |
| R1 | 同 S4，但**关闭** prefix caching | v2 token | — |
| S6 | 同 S4，但换成**新引擎** | v2 token | — |

三条结论：

1. **同名热更新的旧值来自 adapter 权重缓存，不是前缀缓存。** S3 的输出与命中增量跟 S2
   一模一样（96 hits）。把两处成因分开的实验（同一脚本 `--mode split`）在同一批 adapter
   上跑三种引擎配置（`results/crater/lora/hot-split-20260922/`）：

   | 配置 | 前缀缓存 | adapter 槽 | 更新前先挤掉 | S3 输出 | S3 命中增量 |
   |---|---|---|---|---|---|
   | `cache_on_cpu3` | 开 | `max_loras=2` / `max_cpu_loras=3` | 否 | **v1 token** | 96 |
   | `cache_off_cpu3` | **关** | `max_loras=2` / `max_cpu_loras=3` | 否 | **v1 token** | 0 |
   | `cache_on_cpu1_evict` | 开 | `max_loras=1` / `max_cpu_loras=1` | 是（先加载另一个 adapter） | **v2 token** | 96 |

   **关掉前缀缓存后仍返回 v1**（命中 0）：旧值不需要前缀缓存来解释。
   **挤掉 adapter 槽后返回 v2**（命中仍是 96）：前缀缓存命中 96 个 token 也没有拦住新权重
   生效。两者合起来说明——**权重缓存按 name/id 常驻，才是"同名热更新无效"的主因**；
   前缀缓存只是复用 KV，不决定输出是哪一版。

2. **换 path 不换 name 时，输出仍由 adapter 缓存决定。** S4 换成 v2 的副本路径、
   `lora_name` 仍是 `A`，请求仍然命中缓存里的旧权重（输出 v1、前缀缓存 96 hits）；
   同一请求在**新引擎**（S6）下得到 v2。这与上一条一致：**换 name 才能换到新 KV，
   换 name/id 或清空缓存才能换到新权重。**
3. **`lora_int_id` 不是缓存身份。** S5 只把 name 换成 `B`（id 同时换成 2），
   命中立刻变成 0、输出立刻变成 v2——而它读的路径 P1 本来就是已经更新过的权重。
   与源码一致：进入 hash key 的是 `lora_name`（`v1/core/kv_cache_utils.py:542–554`），
   **权重版本不在里面**。

**给服务设计的结论要反过来读**：同名热更新不仅不会自动失效旧 KV，
在权重已经换掉之后，**同名的请求会继续命中旧 KV**。生产上必须用版本化名称
（如 `modelA-v2`），或在更新时显式清掉该名称的全部 KV。

### G. 公开产物里到底有什么：adapter→loader→kernel 逐层核对

换一个 base 快照去加载，只能验证"能不能加载、输出是否合理"，不能声称复现原始训练结果。

**第三条：训练侧元信息读不出来。** `training_args.bin` 是 pickle 且引用训练侧库
（本机没有 `trl`），缺库时用占位类顶住可以绕过类解析，但随即撞上

保留未知"一致：**训练数据与超参不在可移植的产物里**。

**张量清单与 rank 核对。** 144 个张量 = 36 层 × 2 模块 × (A, B)，
共 2 949 120 个元素、11 796 480 字节（存的是 **F32**，基座是 bf16），
观测 rank 一律 8，覆盖 0–35 全部 36 层：

```
base_model.model.model.layers.0.self_attn.q_proj.lora_A.weight  [8, 2560]
base_model.model.model.layers.0.self_attn.q_proj.lora_B.weight  [4096, 8]
base_model.model.model.layers.0.self_attn.v_proj.lora_A.weight  [8, 2560]
base_model.model.model.layers.0.self_attn.v_proj.lora_B.weight  [1024, 8]
```

注意 `q_proj` 的 B 是 `[4096, 8]`、`v_proj` 的 B 是 `[1024, 8]`——
基座 32 个 query head × 128 head_dim = 4096，而 **8 个 KV head** × 128 = 1024。
**同一个 rank 在 q 与 v 上的输出宽度差 4 倍**（GQA），这正是 k/v 分段要写对的原因。

**两个引擎怎么读同一个产物。**

| 引擎 | 解析路径 | 结果 |
|---|---|---|
| vLLM 0.29.0 | `vllm/lora/peft_helper.py` 的 `PEFTHelper.from_local_dir` | `r=8`、`lora_alpha=8`、`target_modules=["q_proj","v_proj"]`、`bias="none"`、`use_rslora=False`、`use_dora=False`、`vllm_lora_scaling_factor=1.0`、`vllm_max_position_embeddings=40960`，缩放 `alpha/r = 1.0` |
| SGLang 0.5.19 | `srt/lora/utils.py` 的 `get_normalized_target_modules` | 把 `["q_proj","v_proj"]` 归一成 **`["qkv_proj"]`**，缩放同样取 `lora_alpha/r`（`srt/lora/lora.py:71`） |

同一个产物，**vLLM 保持 q/v 两个独立模块名，SGLang 归一到合并的 `qkv_proj`**。
这不是命名偏好：合并之后 kernel 必须把宽度 4096 与 1024 的两段拼进同一个
`qkv_proj` 的低秩更新里，切片位置由基座布局决定，写错不会报错、只会算错。
两边的缩放公式一致（`alpha/r = 1.0`），所以这一例里数值差异不会来自缩放。

### H. 把公开 adapter 挂上真实服务：能测出什么、测不出什么

上一节只在 CPU 上看产物。这一节把它挂到 vLLM 0.29.0 上跑
（`labs/L5/lora_public_adapter_audit.py`，
`results/crater/lora/public-adapter-20260914/`）：基座 `Qwen/Qwen3-4B`、
adapter `trl-lib/Qwen3-4B-LoRA`、贪心 64 token、4 条固定 prompt、
**四组配置交错重复 3 轮**（`base`＝开 LoRA 但不用 adapter / `adapter` /
`other_name`＝同权重换 `lora_name` / `alpha16`＝把 alpha 从 8 改成 16）。
交错是为了不让"跑的先后"混进耗时差。

**运行间抖动：默认配置不可复现，固定 batch 不变性后可以。**

默认配置（`VLLM_BATCH_INVARIANT` 未设）下，同一台引擎、同一配置、同一 prompt
重复跑三轮就会出现 1–4 条 token 序列不同（`results/crater/lora/public-adapter-20260914/`）：

| 配置 | 轮间不同的 prompt 条数（4 条/轮，两两比较） |
|---|---|
| base | 1 / 3 / 4 |
| adapter | 1 / 1 / 0 |
| 换 lora_name | 0 / 3 / 3 |
| alpha=16 | 2 / 0 / 2 |

原因与 4.2 同类：batch 组成改变归约顺序，贪心在近似并列处就会翻。
**这种抖动会让"换 lora_name 是否改变输出"无法判定**——它每轮有 0–3 条不同，
正好落在抖动带里。

4.2 给出的开关在这里直接有效：把 `VLLM_BATCH_INVARIANT=1` 与 `seed=0` 一起设置后，
同一组对照重复 4 轮（`results/crater/5.10/lora-rng-20260921/`）：

| 对照 | 每轮不同的 prompt 条数 | 结论 |
|---|---|---|
| 同配置跨轮（base / adapter / 换名 / alpha16 各 3 次轮间比较） | **全部 0/4** | 抖动被消除，可以判定 |
| base vs adapter | 4/4，首个分岔 [9, 4, 3, 28] | adapter 结构性生效 |
| adapter vs **换 lora_name**（同权重） | **0/4** | **只换名称不改变任何输出** |
| adapter vs alpha=16 | 4/4，首个分岔 [5, 4, 15, 16] | `lora_alpha` 进入 kernel |
| base（开 LoRA 不用） vs 关 LoRA | 0/4 | 启用 LoRA 本身不改变未走 adapter 的输出 |

上一轮"换名后 1–3 条不同"因此有了确定答案：**那是抖动，不是名称的效应。**
名称只进缓存键（5.2 的块哈希把 `lora_name` 放进 `extra_keys`），不进计算路径。
这也把 5.10 里"同名热更新不使旧 KV 失效"的机制补齐了：
名称相同 → 键相同 → 旧 KV 被复用；名称不同 → 键不同 → 必然重算。

**能站住的结论是"效应量远大于抖动"，而不是"逐 token 一致"。**

| 对比 | 每轮不同的 prompt 条数 | 首个分岔位置（三轮） |
|---|---|---|
| base vs adapter | 4/4、4/4、4/4 | **[9, 4, 7, 28]**（三轮完全相同） |
| adapter vs alpha=16 | 4/4、4/4、4/4 | **[5, 4, 3, 16]**（三轮完全相同） |

两条都**每轮全中、且分岔位置三轮一模一样**：adapter 的作用是结构性的，
不是抖动。alpha 从 8 改到 16（缩放 1.0 → 2.0）同样稳定地改变输出，
说明产物里的 `lora_alpha` **确实进入了 kernel**，不是被忽略的元数据。
这正好补上"随机 adapter 只能证明调度、公开 adapter 才能证明功能"这一层。

**耗时（3 轮交错，中位 [区间]，4 条 prompt × 64 token）：**

| 配置 | 墙钟中位 | 区间 |
|---|---:|---|
| base（开 LoRA 但不用） | 0.592 s | 0.586–0.610 |
| adapter | 1.056 s | 1.049–1.112 |
| 换 lora_name | 1.119 s | 1.044–1.145 |
| alpha=16 | 1.081 s | 1.025–1.130 |

**走 adapter 的路径约为 base 的 1.8 倍**，四组之间的差别（1.03–1.15 s）
小于 base 与 adapter 之间的差别，说明这里的主项是"低秩分支本身"，
而不是 name 或 alpha。这仍是单进程单机的数字，不能外推成服务吞吐比。

### H0. SGLang 侧 top-k logprob 的取法

跨引擎对照 logprob 时先要读对字段——两边的形状完全不同：

| 引擎 | 怎么请求 | 怎么读 |
|---|---|---|
| vLLM（OpenAI 兼容） | `logprobs=k`（或 `prompt_logprobs`） | `choices[0].logprobs.top_logprobs` 是 **`[{token 文本: logprob}, …]`** |
| SGLang（`/generate`） | **顶层**字段 `return_logprob=True`、`top_logprobs_num=k` | `meta_info.output_token_logprobs` 每位置 `[logprob, token_id, None]`；top-k 在**另一个键** `output_top_logprobs` 里，每位置 `[[logprob, token_id], …]` |

`labs/L5/sglang_topk_logprob.py` 对着真实服务读了一遍
（`results/crater2/5.10/sglang-logprob-20260921/`，`top_logprobs_num=5`、输出 16 token）：

```
meta_info 键：cached_tokens, …, input_token_logprobs, input_top_logprobs, …,
              output_token_logprobs, output_token_logprobs_length, output_top_logprobs, …
output_token_logprobs: 16 个位置，输出 token 16 个；top-k 尺寸 [5]；top-1 与实际 token 相同的位置 16
首元素：len=3: [logprob=-1.1711, token_id=4891, third=None]
  位置 token=4891  logprob=-1.1711  topk_ids=[4891, 220, 24562]
  位置 token=231   logprob=-0.0095  topk_ids=[231, 98, 223]
  位置 token=235   logprob=-0.0     topk_ids=[235, 103, 107]
```

三个容易踩的坑，都在这次的实测里对上了：

1. **`return_logprob`/`top_logprobs_num` 是 `GenerateReqInput` 的顶层字段**
   （`srt/managers/io_struct.py:226/231`），放进 `sampling_params` 会被服务端拒绝
   （HTTP 500）——第一次请求就是这样失败的。
2. **top-k 不在逐位置元素的第三个槽里**：`output_token_logprobs[i]` 只有
   `[logprob, token_id, None]`，真正的候选列表在 `output_top_logprobs[i]`。
   按第三个槽取值会得到"top-k 尺寸为空"的假结论。
3. **SGLang 返回的是 `[logprob, token_id]` 数对，vLLM 返回的是 `{token 文本: logprob}`**。
   后者要小心文本匹配（`yes`/`Yes`/`YES` 是不同 token，见 5.12 的 rerank 对照），
   SGLang 侧用 token_id 就没有这个问题。

**一致性核对**：16 个位置全部满足"top-1 == 该位置实际采到的 token"，
长度也与输出 token 数相等——字段读对之后，这两条是最低限度的一致性检查。

### H1. SGLang 的 unload 是「驱逐」，不是「移除」

源码先把语义摆清楚（`sglang 0.5.19`）：

- `/unload_lora_adapter`（`srt/entrypoints/http_server.py:1574`）要求请求体带
  **`lora_name`**（`srt/managers/tokenizer_control_mixin.py:768-771` 断言），
  最终由 `LoRAManager._unload_lora_adapter`（`srt/lora/lora_manager.py:332`）
  按 `lora_id` 从内存池、`configs`、`loras`、`lora_refs` 里删除；而请求带的是
  **`lora_path`**，两者不是同一个键。
- 每个带 `lora_path` 的请求都会先走 `_resolve_lora_path`
  （`srt/managers/tokenizer_manager.py:3344`）：它向注册表问"哪些路径已不在注册表里"
  （`lora_registry.get_unregistered_loras`），然后从 `lora_ref_cache` **隐式重新加载**
  它们（日志 `Reloading evicted adapter`，`:3364-3378`），再 `acquire` 拿 id。

`labs/L5/sglang_lora_unload_semantics.py` 用五个动作把这条语义跑出来
（Qwen3-4B + `trl-lib/Qwen3-4B-LoRA`，`results/crater2/5.10/sglang-unload-20260921/`）：

| 动作 | 结果 |
|---|---|
| A 装载 `pub` | HTTP 200，`loaded_adapters={"pub": …}` |
| A' 用 `lora_path=pub` 生成 | HTTP 200，输出 token `[4891, 231, 235, 103630, …]` |
| B 卸载 `pub` | HTTP 200，`loaded_adapters={}`（内存池里确实没了） |
| **C 再请求同一路径** | **HTTP 200，输出与 A' 逐 token 相同**；服务端日志出现 `Reloading evicted adapter: pub` |
| D 请求从未装载的路径 | HTTP 400 `Got LoRA adapter that has never been loaded: … All loaded adapters: dict_keys(['pub'])` |
| E 卸载不存在的名字 | HTTP 400 `LoRA with name no-such-name does not exist. Loaded LoRAs: odict_keys(…)` |

三条结论：

1. **`unload` 只保证"此刻不占槽位"，不保证"之后不会被装回来"。**
   C 步的输出与 A' 逐 token 相同、且日志里出现了隐式重载，说明卸载后可观测状态
   取决于**之后有没有请求点到同一个路径**——这正是"卸载行为看起来不一致"的成因。
2. **D 步的报错正好是第 1 条的镜像**：隐式重载把 `pub` 重新注册回了注册表，
   所以"已装载列表"里又能看到它；而一个真正从未装载过的路径会被明确拒绝。
3. **两个键不能混用**：请求用 `lora_path`、卸载用 `lora_name`。
   按名字卸载、按路径重载，中间靠 `lora_ref_cache` 的路径做桥。

要把适配器真正从服务里移除，得同时断开重载路径（把 `lora_ref_cache` 里的条目也清掉，
或让请求不再指向该路径）；`max_loaded_loras` 的 LRU 驱逐走的是同一条隐式重载路径，
所以"被驱逐"同样只是暂时状态。

### H2. `qkv_proj` 的切片对齐：v 落在哪几行

SGLang 把适配器的 q/k/v 三个模块归一成一条融合模块 `qkv_proj`
（`srt/lora/lora.py:264 normalize_qkv_proj`）：**按 [q, k, v] 的顺序拼接**，
适配器没有 k_proj 时用 `zeros_like(v)` 补零；融合输出维由 `get_hidden_dim`
（`srt/lora/utils.py:175`）给出 `head_dim × (num_attention_heads + 2 × num_key_value_heads)`。

`labs/L5/lora_qkv_slice_alignment.py` 在 CPU 上只读第 0 层的 q/k/v 与适配器对应张量
（`results/crater/5.10/qkv-align-20260921/`）：

| 量 | 值 |
|---|---|
| 基座权重 | q (4096, 2560)、k (1024, 2560)、v (1024, 2560) |
| 公式核对 | $128 \times (32 + 2\times 8) = 6144 = 4096 + 1024 + 1024$ ✓ |
| 归一化后的 B | (6144, 8) = [q; **k 全零**; v]，v 的行区间 **[5120, 6144)** |
| 归一化后的 A | (24, 2560) = [A_q; A_k 全零; A_v] |
| 只拼 [q; v] 的负例 | B (5120, 8)，v 的行区间变成 [4096, 5120) —— **相差 1024 行** |
| 数值对拍（融合 vs 分别合并） | q 段 max\|Δ\| **0**，v 段 max\|Δ\| **0** |
| 错位写入（v 写到 [4096, 5120)） | v 段 max\|Δ\| **6.10e-04**（正好是 LoRA 增量本身的量级） |

两条结论：

1. **"v 紧跟在 q 后面"是错的，中间必须留出 k 的 1024 行。**
   这里 1024 = `num_key_value_heads × head_dim`，不是常数——换模型就变。
   错位不会报错：形状仍然合法（5120 + 1024 行也能拼出来），只是注意力的
   K 与 V 段被写乱，误差量级与"少加一次 LoRA"相同。
2. **适配器不带 k_proj 时，k 段必须是精确的零块**（实测 True）。
   没有这一步，SGLang 的 [q;k;v] 行序就无从与基座的融合权重对齐。

### I. merged dense 与服务侧 unmerged：合并误差与低秩分支的代价

任务 D 的另一半是 merged/unmerged 对照。用 PEFT 的 `merge_and_unload()`
把公开 adapter 合并进 `Qwen/Qwen3-4B`，再把 merged 与 unmerged（base + adapter）
分别交给同一个 vLLM 跑同一批 prompt
（`labs/L5/lora_merge_reference.py`，`results/crater/lora/merge-20260914/`）。

**先验证合并本身。** 直接把 `merged − base` 与 `B @ A` 相减会得到一个吓人的数
（3.54e-04），但那是**消去误差**：base 权重的量级是 **0.59**，bf16 在该量级上一个 ulp 是
**2.32e-03**，而 LoRA 增量本身只有 **4.92e-04**——增量还不到 base 的 0.2 个 ulp，
两个 bf16 数相减根本分辨不出来。把 bf16 存储的舍入也算进去再比就干净了：

| 模块 | `bf16(base + B@A)` 与落盘 merged 的最大差 | base 量级 | 增量量级 |
|---|---:|---:|---:|
| `q_proj` | **0.0**（逐位相同） | 0.594 | 4.92e-04 |
| `v_proj` | **2.33e-10**（float32 舍入） | 0.171 | 6.10e-04 |

**服务侧对照（同一批 prompt、贪心 32 token、取首 token 的 top-20 logprob）：**

| prompt | top-20 重叠 | 首 token 最大 \|Δlogprob\| | argmax 相同 | 生成序列首个分岔 |
|---|---:|---:|---|---:|
| 0 | 19 | 6.49e-02 | 是 | 第 18 个 token |
| 1 | 19 | 6.61e-02 | 是 | 第 4 个 |
| 2 | 20 | 9.40e-02 | 是 | 第 3 个 |
| 3 | 19 | 1.17e-01 | 是 | **无**（32 个全同） |

三条结论：

1. **合并是对的**：落盘权重与 `bf16(base + B@A)` 逐位一致（q_proj 为 0.0）。
2. **merged 与 unmerged 的首 token 分布在 6.5e-02 ~ 1.2e-01 之间**，四个 prompt 的
   argmax 全相同；生成序列在 4 个里有 3 个中途分岔——这与本节前面测到的
   "同一配置重复运行之间也会分岔"是同一类现象，**所以不能用文本是否相同来判断合并对不对**，
   要比的是同一上下文下的分布差。
3. **低秩分支的代价可以量化**：4 条 prompt × 32 token，merged 0.271 s、unmerged 0.597 s，
   **merged 快 2.2 倍**（省掉 shrink/expand 两个 kernel）。
   代价是每份合并权重占 **7.6 GB**（单个 safetensors），而 adapter 本体只有 11.8 MB——
   这就是"每租户一份 dense 模型"与"共享 base + 低秩"之间的实际交换比。

**本节没有做的**：没有在 SGLang 上跑同一组对照；没有固定 RNG 去消除运行间抖动；
merged 侧的显存占用没有单独测（只记了磁盘体积）。同 checkpoint 的固定 RNG 复现、
`qkv_proj` 切片对齐与 unload 语义见后文 I/K 两节的补测。

### J. 另一侧的执行路径：SGLang 的 CUDA Graph 开关

任务 D 还要求「在两引擎对齐完整路径，比较 eager/graph」。vLLM 侧的图模式在 5.4
量过（FULL_AND_PIECEWISE、51 个捕获尺寸、padding 表），这里补 SGLang 一侧：
同一个 Qwen3-1.7B、同一批请求，**只切 decode 的图后端**
（`--cuda-graph-backend-decode full` 默认 / `disabled`），
用流式接口按到达时刻量 TTFT 与**逐 token 间隔**
（`labs/L5/sglang_graph_audit.py` + `run_sglang_graph.sh`，
`results/crater/sglang/graph-20260914/`）。每格 3 次重复取中位，96 个生成 token。

| batch | 配置 | TTFT 中位 | **逐 token 间隔中位** | 间隔最大 | 整请求中位 |
|---:|---|---:|---:|---:|---:|
| 1 | 图开 | 6.92 ms | **2.885 ms** | 3.52 ms | 281.4 ms |
| 1 | 图关 | 9.56 ms | **4.693 ms** | 5.72 ms | 458.5 ms |
| 8 | 图开 | 10.84 ms | **3.582 ms** | 7.22 ms | 352.2 ms |
| 8 | 图关 | 12.50 ms | **4.761 ms** | 15.35 ms | 468.8 ms |
| 32 | 图开 | 12.93 ms | **5.035 ms** | 25.41 ms | 507.1 ms |
| 32 | 图关 | 12.99 ms | **5.044 ms** | 28.65 ms | 505.9 ms |

**图模式的收益随 batch 单调衰减，到 32 已经归零：**

- batch 1：逐 token 间隔 **2.885 → 4.693 ms（+62.7%）**，整请求 281 → 459 ms；
- batch 8：3.582 → 4.761 ms（+32.9%），整请求 352 → 469 ms；
- batch 32：5.035 → 5.044 ms（**+0.2%**），整请求 507 → 506 ms。

原因是清楚的：图省下的是**每次前向的启动开销**，它是常数；
batch 越大，每步的真实计算越长，常数占比越小，到 batch 32 时已被完全淹没
（两边的"间隔最大"都在 25–29 ms，说明这一步的瓶颈已经是调度抖动而不是启动）。

两条边界要一起记：

1. **本对照只关了 decode 的图**。SGLang 的 prefill 图仍然是开的
   （服务端日志里仍有 `Capture target prefill CUDA graph … backend=breakable`，
   捕获了 4–2048 共 42 档 token 桶，耗时 2.35 s、占 0.36 GB），
   所以 TTFT 那一列不是"prefill 图 vs 无图"的对照；
   日志里 `cuda graph: True/False` 的计数可以逐配置核对（图开 39/9，图关 27/23）。
2. **SGLang 的图后端是可分的**：`--cuda-graph-backend-{decode,prefill}`
   各自有 `full/breakable/tc_piecewise/disabled` 四档，
   这比"开/关图"的二值说法更贴近实际部署的调参面。

**三档扫描与一个真实缺陷。** 本轮把 decode 后端从两档（开/关）扩到三档
（`labs/L5/run_sglang_graph_backends.sh`，`results/crater2/5.10/sglang-graph-backends-20260922/`）：

| decode 后端 | batch 1 间隔中位 | batch 8 | batch 32 | batch 1 整请求 |
|---|---:|---:|---:|---:|
| `full`（默认） | **2.922 ms** | **3.596 ms** | **5.263 ms** | 284.6 ms |
| `disabled` | 5.001 ms | 5.052 ms | 5.434 ms | 485.2 ms |

### K. SGLang 侧挂同一个 adapter：两引擎的对照补齐

§H 在 vLLM 上量了 base vs adapter，这里在 **SGLang** 上做同一件事，
让"两引擎对齐完整路径"两侧都有数据。同一 Qwen3-1.7B、同一份 rank-8 adapter
（`q_proj` + `v_proj`、28 层），SGLang 用
`--enable-lora --max-lora-rank 8 --lora-paths pub=<dir>` 起服务，
请求里把 `lora_path` 放在 **`/generate` 的顶层**
（放进 `sampling_params` 会 500：`TypeError: Unexpected keyword argument 'lora_path'`），
三轮交错重复（`labs/L5/sglang_lora_serving_audit.py` + `run_sglang_lora_serving.sh`，
`results/crater/sglang/lora-serving-20260914/`）：

| 轮 | base 首 token（4 条 prompt） | adapter 首 token | base≠adapter | 首个分岔 |
|---|---|---|---|---|
| 0 | 84648 / 576 / 7281 / 576 | 50750 / 53617 / 50750 / 28245 | **4/4** | **全部在第 0 个 token** |
| 1 | 同上（逐位相同） | 同上 | 4/4 | 0 |
| 2 | 同上（逐位相同） | 同上 | 4/4 | 0 |

三条结论：

1. **SGLang 的低秩路径确实在起作用，而且作用很大**：4 条 prompt 的**第一个 token**
   就全部改变，三轮完全一致。§H 在 vLLM 上看到的是首个分岔在 `[9,4,7,28]`，
   这里更早——因为 adapter 是随机权重的，模型/负载也不同，
   **两次实验的"分岔位置"不可互比**，但"adapter 改变输出"这一点两侧一致。
2. **在这个配置下 base 是可复现的**：§H 里 vLLM 上"同一配置重复三轮会差 1–4 条"，
   这里三轮 base 逐位相同、adapter 也逐位相同。
   差别可能来自模型规模（1.7B 对 4B）、`--disable-radix-cache` 与负载大小，
   所以**不能据此说 SGLang 更确定**，只能说这条实验里的噪声比 §H 那组小。
3. **低秩开销在这条负载上很小**：4 条 × 24 token，base 中位 0.081 s、
   adapter 0.084 s（+3 ms，约 +4%）。§H 在 4B 上看到的是 base 的 1.8 倍——
   量级差得多，原因是那边的负载与模型都不同，**这两个倍数不能并列引用**。

服务端日志还记下了 SGLang 选了哪个 LoRA 后端与有没有调优过的 kernel 配置：
`Using csgmv as backend of LoRA kernels`、`LoRA shrink (K=2048, R=8): no tuned config,
using defaults {'BLOCK_N': 16, 'BLOCK_K': 256}`、`LoRA expand (K=4096, R=8): no tuned
config, using defaults {'BLOCK_N': 64, 'BLOCK_K': 16}`——也就是说这次跑的是
**默认参数、没有 autotune 缓存**的 csgmv 路径。

**本节没有做的**：SGLang 侧的 **top-k logprob 没取到**
（`output_top_logprobs` 解析为空，`top_logprobs_num` 已按顶层字段传入），
所以这里的判据是 token 身份而不是 logprob 分布；adapter 是随机权重，
只证明路径生效、不证明质量。

### L. SGLang 的 LoRA 异常路径：非法请求之后还能不能服务

任务 C 要求在 HTTP 服务上测「非法 rank 后合法请求」「请求执行中卸载/替换」，
并把「重启恢复与同进程恢复分开」。vLLM 侧已有 `lora_recovery_test.py`，
SGLang 侧这次补上（`labs/L5/sglang_lora_recovery_test.py` + `run_sglang_lora_recovery.sh`，
`results/crater/sglang/lora-recovery-20260914/`）。服务只注册一个合法 rank-8 adapter，
然后按顺序打六种请求：

| 步 | 请求 | 结果 |
|---|---|---|
| S1 | 合法 `lora_path=pub` | 200，16 token |
| S2 | 未知名字 | **400** `Got LoRA adapter that has never been loaded: no-such-adapter` |
| S3 | `lora_path` 指向 rank=16 的**目录路径** | **400**，同样是"never been loaded" |
| S4 | 目录里 `adapter_config.json` 缺失/权重损坏 | **400**，同理 |
| S5 | 合法 `pub` 再来一次 | 200，16 token，**与 S1 逐位相同** |
| S6 | 合法 `pub` 流式，收到若干 chunk 后**断开连接** | HTTP 正常返回 |
| S7 | 中断之后再发一次合法请求 | **200，16 token** |

**同进程不受影响**：三种非法请求之后、以及一次流式中断之后，
合法请求都照常返回，且输出与第一次逐位相同，
所以"打过异常请求就得重启引擎"在 SGLang 的这条路径上不成立。

**但 rank 超限的失败方式不一样，这是本节真正的发现。** S3 用的是"路径"，
被 400 挡在门外——原因不是 rank，而是**路径没注册**。要真正触发 rank 校验，
得在启动时把它注册进去：把 rank=16 的 adapter 写进
`--lora-paths pub=<valid> big=<rank16>`，服务**启动并没有拒绝**；
直到第一次真正发到 `lora_path=big` 的请求，才在加载权重时炸：

```
AssertionError: LoRA buffer shape torch.Size([24, 2048]) does not match
weight shape torch.Size([48, 2048]).
```

位置在 `sglang/srt/lora/mem_pool.py:1226` 的 `load_lora_weight_to_buffer`，
客户端看到的是 **curl 的"Empty reply from server"（HTTP 000）**——
也就是**连接被打断，而不是干净的 4xx**。

结论有三条：

1. **校验点太晚**：`--max-lora-rank 8` 只在真正加载权重时生效，
   启动注册阶段不校验，所以一个配置错误能进到线上并炸在一次真实请求上。
   对照 vLLM：那边 `lora_recovery_test.py` 记录的也是"rank 超限后同引擎继续失败、
   重建引擎才恢复"——**两个引擎在这一点上都不能靠启动校验兜住**。
2. **失败形态不同**：SGLang 这里是连接中断（000），不是带错误信息的 400；
   前三种非法（名字/路径/坏目录）都是 400 + 明确文案。
   对客户端来说，"缺少 LoRA 配置"与"服务端崩了"是两种完全不同的故障，
   而它们在这里看起来只差一个 HTTP 状态码的有无。
3. **同进程恢复仍然成立**：这次 rank-16 的失败发生在**另一个**服务实例上
   （第三配置），所以它没有污染 S1–S7 那一轮；
   也就是说"注册了超限 adapter 的服务会崩在第一次用到它时"与
   "正常服务能扛住非法请求"是两件独立的事实，不要混在一起说。

**本节没有做的**：没有测"同名不同版本热更新"在 SGLang 侧的表现
（§F 那套命中计数只在 vLLM 上做过）；没有测运行中的 adapter 卸载/替换 API。

### M. SGLang 的管理接口：同名替换被拒，卸载报告成功但请求仍生效

上一节留下的两个缺口一起补：SGLang 的同名热更新与**运行中卸载/替换**。
它有两个管理接口（`srt/entrypoints/http_server.py:1551` / `:1574`）：
`POST /load_lora_adapter {lora_name, lora_path, pinned}` 与
`POST /unload_lora_adapter {lora_name}`。实验用**三份参照**说话
（`labs/L5/sglang_lora_admin_test.py` + `run_sglang_lora_admin.sh`，
`results/crater/sglang/lora-admin-20260914/`）：base（不带 adapter）、
C1（启动时注册为 `pub`）、C2（用另一个名字 `pub2` 注册）——

| 步 | 操作 | 结果 | 输出首 6 个 token |
|---|---|---|---|
| S0 | 不带 adapter | 200 | `84648 6500 374 264 …`（base 参照） |
| S1 | `lora_path=pub`（C1） | 200 | `23297 ×6`（C1 参照） |
| A1 | load `pub2`=C2 | **200 success** | — |
| S2 | `lora_path=pub2`（C2） | 200 | `53930×4 99712×2`（C2 参照） |
| A2 | **同名把 `pub` 重载成 C2** | **400** `Failed to load LoRA adapter pub because it is already loaded` | — |
| S3 | `lora_path=pub` | 200 | `23297 ×6`（**仍是 C1**） |
| A3 | **unload `pub`** | **200 success**，`loaded_adapters` 只剩 `pub2` | — |
| S4 | `lora_path=pub` | 200 | `23297 ×6`（**仍是 C1**） |
| A4 | 重新 load `pub`=C1 | **400** `already loaded` | — |
| S6 | 生成中途 unload 后再请求 | 200 | `23297 ×6`（仍是 C1） |

三份参照把每条判断都钉死了（base、C1、C2 三者互不相同，
所以"等于谁"是有信息量的，不是文本比对碰运气）：

1. **同名替换被显式拒绝，而不是静默沿用。** A2 返回 400 且写明
   `because it is already loaded`；S3 的输出与 C1 逐位相同。
   这与 §F 在 vLLM 上测得的行为**不同**：vLLM 那边同名热更新没有报错、
   只是继续用旧 KV/旧权重（静默），SGLang 这边直接拒绝。
   两条都说明"热更新不会被自动感知"，但**失败形态一个是静默、一个是报错**，
   后者的可运维性好得多。
2. **`unload` 之后请求仍然成功，但原因不是"卸载没生效"，而是"按需隐式重载"。**
   A3 返回 `success:true` 且 `loaded_adapters` 里已经没有 `pub`；
   紧接着 S4 带 `lora_path=pub` 的请求仍然 200，输出与 C1 **逐位相同**
   （且不等于 base）。**这一格最初的解读是错的**——把它当成"卸载没生效/账本不一致"。
   读源码可以看到真正发生的事：`tokenizer_manager._resolve_lora_path()`
   （`srt/managers/tokenizer_manager.py:3344`）在请求进来时先查
   `lora_registry.get_unregistered_loras(...)`，对**已被卸载的名字会从
   `lora_ref_cache` 自动隐式重载**，并打日志 `Reloading evicted adapter: <名字>`；
   只有它不在 cache 里才报 `Got LoRA adapter that has never been loaded`。
   服务端日志里紧接着那次 unload 就有 `Reloading evicted adapter: pub`——
   证据本来就在工件里。
3. **把两种顺序分开跑，就能把这件事钉死**（`labs/L5/sglang_lora_unload_probe.py`
   + `run_sglang_lora_unload_probe.sh`，`results/crater/sglang/unload-probe-20260914/`）：

   | 顺序 | 结果 |
   |---|---|
   | A：unload → **不请求** → 显式 load 同名 | **200 成功**（说明注册表真的空了） |
   | B：unload → **请求一次** → 显式 load 同名 | 请求 200；显式 load **400** `because it is already loaded` |

   B 里的 400 是那次请求把名字**装回来**造成的，不是账本自相矛盾；
   而 B 的请求输出与参照**逐位相同**（`implicit_reload_same_weights: true`），
   说明隐式重载装回的是同一份权重。服务端日志里 `Reloading evicted adapter`
   恰好出现一次——就是 B 的请求触发的。

**所以 SGLang 的语义应该这样读**：`unload` 把 adapter 从注册表移除、释放运行时占用，
但 `lora_ref_cache` 保留引用，**下一个同名请求会把它按需装回来**。
它是"卸载即按需重载"（unload-on-idle + reload-on-demand），
而不是"卸载后不可再用"。运维上要真正让一个 adapter 消失，
还必须清掉它的缓存引用——这一点接口没有直接提供。

**本节没有做的**：没有测"先前已有的请求还在生成时替换权重"（S6 只测了卸载）；
没有测 `max_loaded_loras` 触发的 LRU 驱逐与隐式重载的交互。

## 设计取舍

**核心不变量：一个 token 行的请求身份、adapter 版本、GPU slot 和输出位置必须一致。** 从调度完成到该步 kernel 完成，slot 不能被另一 adapter 覆盖；rank padding 不得残留；base 行不得误加增量。

状态归属分为四层：入口管理名称、版本与授权；scheduler 管可接纳请求；worker 管 CPU 缓存和 GPU 槽位；kernel 只消费本步 metadata。prefix cache 则必须带上足以区分有效权重的身份。把所有状态压到一个全局“当前 adapter”变量中，单请求测试可能正常，混批必然不可靠。

| 路线 | 收益 | 代价及本章验证范围 |
|---|---|---|
| 每 adapter 合并一份 dense 模型 | 推理不再走低秩分支（**实测快 2.2×**） | 每份合并权重占 **7.6 GB** 磁盘/显存；仅 mini 代数参照与服务侧首 token 对照 |
| Python 逐行 LoRA | 状态清楚、便于对照验证 | 小调用多；本章 mini 不代表 GPU kernel 性能 |
| vLLM 分组索引＋shrink/expand | base 共享，混批低秩运算在 GPU 执行 | metadata、padding、槽位上限；本章有端到端与 GPU trace |
| SGLang 分段 backend | 显式传递边界、rank、缩放与 permutation | 分段整理及 backend 约束；本章仅真实 kernel 对照验证 |

提高 GPU 槽位容量，可能减少波次，却会挤占其他显存用途。按 adapter 重排请求，可能提高局部复用，却改变公平性和尾延迟。本章只测等长突发请求，没有评估这些替代策略的线上收益；这张表是分析，不是上游否决方案的记录。

新增后端至少涉及层的布局与 TP slice、metadata 契约、rank/缩放语义、base 哨兵、输出累加、dtype，以及 graph capture 的地址和形状稳定性。错误应尽早发现：rank、target module、base revision 在加载前验证；槽位数量在调度时验证；shape、stride、输出误差在 kernel 测试中验证。租户授权与文件来源仍须由服务入口检查，LoRA 数值路径本身不是权限隔离机制。

结构运行与计时分开。下表把 `set_adapter_mapping` 调用按实际 token 行数归类；每次生成 16 token，对应一个 prefill 加 15 个 decode 执行步。

| adapter 数 | mapping 调用 | prefill 行数 | decode 行数 | GPU 槽位变更次数 |
|---:|---:|---|---|---:|
| 1 | 16 | 640×1 | 64×15 | 0 |
| 8 | 16 | 640×1 | 64×15 | 0 |
| 9 | 32 | 570×1、70×1 | 57×15、7×15 | 9 |
| 16 | 32 | 320×2 | 32×30 | 16 |
| 64 | 128 | 80×8 | 8×120 | 64 |

9 档先处理 adapter 1–8 的 57 个请求，再处理 adapter 9 的 7 个请求。64 档每轮仅 8 个请求。**本次拐点有源码和执行形状共同支持：槽位上限导致分轮，较小的活跃 batch 降低了共享 base 执行的摊销效率，同时增加换入。** 还没有把每个因素的毫秒数完全拆开，不能把总差值全部归因于复制。

1/4/7/8 的那点差异**用已有的交错重复就能判定是噪声，不要当趋势引用**。
`timings.json` 里 rep 是外层循环，所以同一档有 5 轮交错重复；
把相邻档做**配对比较**（每轮内相减，看符号是否换边，`labs/L5/lora_timing_stability.py`，
`results/local/lora-timing-stability-20260914/`）：

| 1 | 219.4 ms | 215.2–222.6 | 3.35 |
| 4 | 222.2 ms | 219.2–225.1 | 2.66 |
| 7 | 220.6 ms | 218.8–228.2 | 4.26 |
| 8 | 221.5 ms | 217.6–228.7 | 5.01 |
| 9 | 439.0 ms | 428.7–446.8 | 4.12 |

| 64 | 1729.0 ms | 1715.8–1760.4 | 2.58 |

| 相邻档 | 5 轮同号 | 中位差 | 档内离散 | 判定 |
|---|---:|---:|---:|---|
| 1→4 | 3/5 | +0.99 ms（0.45%） | 7.36 ms | **噪声内，读作持平** |
| 4→7 | 4/5 | +0.99 ms（0.44%） | 9.39 ms | **噪声内，读作持平** |
| 7→8 | 3/5 | +0.70 ms（0.32%） | 11.09 ms | **噪声内，读作持平** |

所以 1–8 档应该读成**约 220 ms 的平台**，而不是"有上有下的小趋势"；
真正稳定的只有两处：跨过 8 个槽位的 **8→9（+96%）**，以及 **16→64（+283%）**。

顺带量到一个此前没记录的时间相关因素：把每一轮各档的均值排开，
5 轮是 **497.0 / 501.0 / 502.2 / 502.8 / 504.3 ms**，也就是**会话内约 1.5% 的上漂**。
它与 1/4/7/8 之间那点差异同量级——这正是那些差异不该被引用的原因。
漂移的成因（频率、温度、其他占用）本实验没有记录，**不作归因**；
要归因需要同时采频率/功耗。7 与 9 档的请求分布并非完全均匀，具体计数保存在每个样本中。

### 3. 槽位命中与换入不是同一条路径

结构运行在 `activate_adapter` 前后显式同步。16 档有 16 次槽位变更，变更路径中位数为 `1.5484909527003765` ms；240 次不变路径中位数为 `0.0028796494007110596` ms。64 档对应 64 次变更，变更路径中位数为 `1.5424108132719994` ms。

这些是带同步插桩的调用耗时，包含逐层设置与复制，不是纯 H2D 时间，不能乘以次数后从普通计时中扣除。CPU adapter 已在预热中缓存；这个对照不包含首次磁盘读入。warm-up 也不意味着所有 adapter 都在 GPU：64 个 CPU cache 项仍只能轮流占用 8 个 GPU slot。

### 4. GPU trace 确认真正执行低秩 kernel

8 档在单独 profiler 运行中采集原始 Chrome trace。按 CUDA device event 汇总，避免把 CPU 父算子与子 kernel 重复计数：

| CUDA kernel | 调用数 | 累计时间 μs |
|---|---:|---:|
| `_lora_shrink_kernel` | 1808 | 10632.033999999321 |
| `_lora_expand_kernel` | 1824 | 17917.164999999706 |

两者合计 `28549.198999999026` μs；所有 CUDA device event 累计 `93234.68699999717` μs。这是 profiler 中的事件时间之和，不是端到端墙钟占比，不包含排队、CPU 空隙，也不能替代未插桩的 `221.47243656218052` ms。

分析脚本重新读取原始 trace，核对 LoRA kernel 名称和调用次数一致。shrink 与 expand 相差 16 次的具体来源未定位；不据此推断“每层正好一对”，需进一步按层标记和调用关联。旧目录名 `trace/` 只保存 Python 插桩；新增 `mixed8.trace.json` 才是 GPU profiler trace。

### 5. 旧混批对照验证与失败路径

既有 8 请求×24 输出 token 实验在 `max_loras=2,max_cpu_loras=3,max_lora_rank=16` 下验证零 B adapter 与 base 的 greedy token 一致，并记录混批与分开运行的结果。随机非零 adapter 是否改变输出只能按该输入判断，不能用来评价训练效果。

其三档中位耗时为 base `178.892` ms、单 adapter `318.707` ms、双 adapter `317.972` ms，数字来自旧 `derived.json`。base 档仍是已启用 LoRA 的同一个引擎，不是另建未启用 LoRA 的服务。该实验包含 logprobs，batch、长度和 rank 上限也与新增扫描不同，不能横向计算统一加速比。

注入 rank 32 的 adapter 后，loader 抛出 `LoRA rank 32 is greater than max_lora_rank 16.`。捕获异常后再发合法请求，旧离线运行仍失败，退出码 1。**异常被捕获不等于引擎状态已恢复。**

专门的恢复测试（`lora_recovery_tests.sh`）确认了两个结论：

1. **同一引擎内继续使用失败。** rank 超限后，即使后续请求的 adapter 是有效的（rank 8 < max 16），仍报同样的 `LoRA rank 32 is greater than max_lora_rank 16.` 错误。异常被捕获并不意味着引擎的 LoRA 请求队列、adapter mapping 或内部状态已回滚到干净状态。
2. **销毁引擎并创建新引擎可恢复。** 调用 `del llm_engine` 后重新构造同配置引擎，有效 adapter 能正常工作。这说明状态污染留在引擎实例内，进程本身未损坏。

HTTP 服务的行为未测：连接池、异步调度和全局状态可能与离线 `LLMEngine` 不同。建议在真实部署前用非法请求 + 后续合法请求序列验证服务恢复路径，并记录是否需要重启进程或只需中止该请求。

建议消融：把 `max_loras` 改为 4/16 并重新核算显存，观察拐点是否随容量移动；固定槽位后扫描 rank；比较请求按 adapter 聚集与交错；打开 prefix cache 并使用版本化名称；单独测冷文件加载与 pinned H2D。每种配置必须另存结果，不能覆盖本章基线。

## 前沿与待验证路线

沿本章机制继续扩展，而不是只增加 adapter 数量：

- **统一分页与异构 rank。** 把 adapter 和 KV 的容量管理一起考虑，减少固定最大 rank padding 的浪费；应比较碎片、寻址和搬运成本。S-LoRA、Punica 是相关系统路线的阅读入口，不代表本章复现了它们的全部设计。
- **计算与加载重叠。** 当前快照含辅助 stream、overlap loader 等代码；没有运行本章负载的开关对照，收益为 `UNVERIFIED`，尤其要检查 slot 生命周期与 stream 依赖。
- **图捕获与量化组合。** eager 结果不能预测 CUDA Graph、量化 base、FP8 LoRA 或 MoE adapter 的表现；需要专门的 shape、dtype、误差和图缓存测试。
- **线上公平性。** adapter-aware batching 可能改善吞吐，但长尾租户、取消、deadline 与权限需要独立测试。SGLang 全引擎、TensorRT-LLM 和其他服务实现的端到端对照为 `UNVERIFIED`；未配置对应服务与本章负载。

## 陷阱

1. 只测单 adapter，掩盖混批 mapping 和容量边界。
2. 把逻辑 ID 当 GPU slot，忽略槽位复用与 base 哨兵。
3. 以为 alpha/r 必须在 kernel 中乘；loader 可以预先折进权重，重复缩放会出错。
4. 从 q_proj 文件净字节推断所有 GPU 预分配，遗漏 packed slice、rank padding 和其他层。
5. 把 64 个已缓存 adapter 当作 64 个 GPU 常驻 adapter。
6. 把带同步插桩的换入调用耗时当成 PCIe 传输基准。
7. 把 profiler kernel 时间之和写成端到端占比。
8. 同名替换 adapter 却默认旧 KV 仍正确；只捕获 loader 异常却假定请求状态已经回滚。

## 自测题

1. 给定 H=4096、O=4096、r=16、BF16，一个 linear adapter 的净字节数是多少？
2. token ID 映射 `[7,9,7,0]`、GPU slot 表 `[9,7]` 应转换为什么？
3. 为什么 64 请求、9 个 adapter、8 个 GPU slot 不一定只比 8 个 adapter 慢一点？
4. “只有 0.8% 额外 FLOPs，所以只慢 0.8%”缺了哪些开销？
5. 应怎样证明非法 rank 请求没有破坏后续服务？

::: fold 答案
1. `2×16×(4096+4096)=262144` 字节，即 256 KiB；未计文件头与运行时 padding。
2. `[1,0,1,-1]`。7 在 slot 1，9 在 slot 0，base 用内部哨兵 -1。
3. 请求接纳受不同 adapter 数限制。本章等长突发负载从 16 个执行步变为 32 个，后轮还伴随换入和较小 batch；9 不是硬件阈值。
4. metadata、分组、额外发射、小 GEMM 利用率、读写低秩 buffer、槽位加载与排队。FLOPs 不能单独决定 wall time。
5. 除检查错误类型外，还必须继续发起后续合法请求，严格校验其执行完成状态、文本输出、调度请求表、KV 缓存及槽位生命周期账本。若后续请求未能正确完成，则不能判定异常已安全恢复。
:::
