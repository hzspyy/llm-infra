## 本章回答三个问题

调度器决定每轮处理哪些请求、每条请求处理多少 token，并协调 KV 分配。长 prefill 与
正在生成的请求共用 GPU 时，调度预算同时影响首 token 延迟、输出间隔和吞吐。

1. 一次 step 的请求状态与 token 预算怎样对应？
2. 插入长 prompt 后，怎样区分 step 变慢与请求没有被调度？
3. 长 prompt 与正在生成的请求争用时，不同策略把代价推给谁？

## 机制拆解与推导

### token 数比请求数更接近本轮工作量

普通 decode 每条请求通常新增一个位置；prefill 可能新增数千个位置。仅限制请求条数，
无法区分两类工作的规模。设本轮请求 i 被分配 $n_i$ 个新 token、总预算为 $M$，则

$$\sum_i n_i\le M.$$

这只是调度约束。相同新增 token 数，在历史长度、模型架构、投机配置或 attention 后端
不同的情况下，耗时仍可能不同（5.1 的 step 账给了同一个模型内的例子）。

chunked prefill 将长 prompt 分成多个轮次处理。它能限制单轮新增位置数，让 decode 有机会
在轮次之间推进；代价包括重复调度、较小的 GEMM 形状和历史 KV 读取。**分块不保证吞吐不变**，
下面 lab 的预算扫描给出两端的具体代价。

### step 时间与逐请求输出间隔不同

step 变长时，该轮完成的输出通常更晚返回。但仅记录 `step()` 调用耗时，不能判断这一步
是否给某条请求生成了 token。要区分"仍在推进，只是每步更慢"和"没有被调度"，必须同时
保存每请求的调度 token 数及输出。

`running` 和 `waiting` 的长度也不是调度器的全部状态。请求还包含已计算长度、待处理输入、
停止条件、优先级、块引用和可能的抢占状态。5.7 和 5.8 会把这些状态展开。

### 预测单步耗时为什么容易错

按 token 数分配预算的前提是"这一步大概要跑多久"。用本章预算扫描的 885 个 step 拟合
一个最简模型 $t = c + b\cdot n$，结果分两段：

| 步的类型 | 样本数 | 模型 |
|---|---:|---|
| 纯 decode 步（8 条 decode） | 507 | 中位 3.36 ms，与 token 数无关 |
| 含 prefill 的步 | 378 | $t = 9.92 + 0.00114n$，残差极差 [−15.0, +148.0] ms |

**一个线性式跨不了三个数量级的分块大小。** 含 prefill 的步从 128 token 到 8184 token，
固定开销、GEMM 效率与 attention 的 $O(n^2)$ 项在不同区间各占一段，单一斜率必然在某一端失真。
用它预测 mini 调度器的计数轨迹，长请求 TTFT 的偏差在 −83% 到 +34% 之间
（`results/local/5.3/schedule-prediction/schedule_prediction.txt`）。

结论不是"模型没用"，而是**预测式策略必须带误差范围**：控制器按估计的斜率选分块时，
斜率低估 50% 会把真实单步推到目标的 1.30 倍，高估 50% 会把分块切到 229 token，
长请求多等 36 个 step。误差的代价是双向的。

## 工程实现 · 源码解析

### 预算从哪里来、阶段怎么判

vLLM 0.29.0 的 `Scheduler.schedule()`（`v1/core/sched/scheduler.py:501`）先取两个数：
`token_budget = self.max_num_scheduled_tokens`（`:521`）与
`input_budget = self.scheduler_config.max_num_batched_tokens`（`:524`）。
然后逐请求决定本轮推进多少 token（`:585-594`）：

```python
num_new_tokens = (
    request.num_tokens_with_spec
    + request.num_output_placeholders
    - request.num_computed_tokens
)
if 0 < self.scheduler_config.long_prefill_token_threshold < num_new_tokens:
    num_new_tokens = self.scheduler_config.long_prefill_token_threshold
num_new_tokens = min(num_new_tokens, token_budget, input_budget - draft_slots)
```

已经算完 prompt 的请求 `num_tokens_with_spec` 只比 `num_computed_tokens` 多一个，
于是自然得到 1——**decode 每步一个 token 不是特判，而是同一个式子的结果**。
`long_prefill_token_threshold`（`config/scheduler.py:70`，默认 0）是主动切长 prefill 的开关；
本章 lab 扫的是总预算 `max_num_batched_tokens`。

KV 不够时 `_preempt_request`（`v1/core/sched/scheduler.py:1405`）把请求放回等待队列并释放块，
被抢占的请求 `num_computed_tokens` 归零，下次重新 prefill。换出与重算的对照见 5.8。

### 设计取舍

- **不变量。** 分配的 token 数不超预算；写入 KV 前已有对应物理槽位；完成、取消或
  被抢占的请求不再被调度。
- **状态归属。** 调度器管理请求进度与块引用；执行器按本轮计划构造张量。执行结果必须
  更新同一请求，不能仅用 batch 位置标识请求身份。
- **准入顺序就是策略。** vLLM 的 `waiting` 是 FIFO 队列，running 请求先被调度；
  想让优先级生效，可以在 `_schedule` 里换顺序，也可以在 `add()` 时排序——5.7 的
  nanoserve 实测显示这两者的差别在于抢占路径会把请求 `appendleft` 回队列，绕过入队时的排序。
- **预算大小。** 小预算限制单轮工作量，也减少并发推进数；大预算提高组合自由度，
  却可能让长 prefill 拉长一轮。两端都有代价，下一节的曲线给出具体数值。

## 工程实现 · mini 实现

`labs/L5/mini_scheduler.py` 把预算 mini 扩成一个离散事件调度器：请求带 arrival、
computed/output token、KV 块、deadline 与取消状态；三种策略共用同一条轨迹。

```python
def candidates(self):
    if self.policy == "fcfs":
        return sorted(self.running + self.waiting, key=lambda r: (r.arrival, r.rid))
    if self.policy == "decode_priority":
        in_decode = [r for r in self.running if r.computed >= r.prompt]
        rest = [r for r in self.running if r.computed < r.prompt] + self.waiting
        return in_decode + sorted(rest, key=lambda r: (r.arrival, r.rid))
    # round_robin：waiting 队列用游标轮转
    ...
```

每个 step 的顺序是：新到达 → deadline 取消 → 按策略与预算切分工作量（KV 不够就按策略
抢占）→ 执行并更新状态。每一步都检查四条不变量：本步 token 不超预算、块使用不超容量、
已结束请求不占块、请求的块装得下已计算长度。

```bash
python labs/L5/mini_scheduler.py --out <dir>
```

**同一轨迹、三种策略**（A/B 各剩 2/8 个 token，C 在 t=2 到达，预算 1）：

| 策略 | 步数 | 最大 TTFT | 完成顺序 |
|---|---:|---:|---|
| FCFS | 17 | 13 | A, B, C |
| decode 优先 | 17 | 13 | A, B, C |
| 轮转 | 17 | 15 | A, C, B |

轮转把等待最久的 C 提前，代价是 B 多等两步。FCFS 与 decode 优先在这条轨迹上一致——
因为所有请求都是 prefill，两者的排序相同；它们真正分开需要"某个已在 decode 的请求
比另一个正在 prefill 的请求到达更早"的场合，即没有 head-of-line 阻塞的轨迹。

**长 prompt 插入 + 到达过程**（8 条 decode 生成 64，t=8 插入 8192；以及
prompt 256、生成 64、预算 64、KV 40 块下的到达扫描）：

```
=== 轨迹 3：prompt 256、生成 64，预算 64，KV 40 块 = 640 token；SLO：TTFT ≤ 30 步 ===
      到达率策略                 完成   取消  SLO内     最长排队    最大TTFT      最大完成步    抢占   重算token
      0.1fcfs               18   22     2      195       201        631   210     53760
      0.1decode_priority    18   22     2      195       201        631   210     53760
      0.1round_robin        18   22     5      180       204        645   170     44300
      0.2round_robin        14   26     4      192       171        494   196     50934
      0.4round_robin        12   28     5      199       195        432   150     39050
```

三件事同时可读：**过载**（40 条请求只完成 10–18 条）、**饥饿**（FCFS 的 TTFT 中位 193 步，
轮转 81 步）、**抢占成本**（FCFS 210 次抢占、53760 个重算 token，轮转 170 次、44300 个）。
轮转在 SLO 内多留下 1–3 条请求，代价是最大完成步略高。

### B：预算扫描（真实引擎）

8 条 prompt 64、生成 64 的请求先跑到稳态，再插入一条 8192 token 的 prompt，
扫 `max_num_batched_tokens`，每档 3 次重复、每次一个独立进程：

```bash
python labs/L5/chunked_prefill_scan.py --out <dir> --single 512:0   # 由 run_chunked_budget.sh 驱动
python labs/L5/chunked_prefill_scan.py --out <dir> --merge
```

| 预算 | 长 prompt 分块数 | LONG 首 token ms | decode 最大间隔 ms | 最慢 step ms | 长请求完成 ms |
|---:|---:|---:|---:|---:|---:|
| 128 | 68 | 511.4 | 9.1 | 10.5 | 508.3 |
| 256 | 34 | 307.5 | 11.7 | 11.7 | 370.2 |
| 512 | 17 | 215.0 | 15.1 | 15.1 | 344.3 |
| 2048 | 5 | 187.9 | 52.8 | 52.8 | 360.7 |
| 8192 | 2 | 172.6 | 158.0 | 158.0 | 355.5 |

每一档三次重复的 TTFT 极差都小于 2 ms（如 128 档 [511.4, 511.5]）。
实际分块大小 = 预算 − 8 条 decode 的 1 个 token（128 → 每块 120，2048 → 2040）。
**长请求完成时间几乎不变（344–371 ms）**，说明总工作量没变，变的只是排队顺序：
分块越细，decode 的停顿越小（158.0 → 9.1 ms，17×），长请求的首 token 越晚
（172.6 → 511.4 ms，3.0×）。

### C：预测模型与误差注入（不需要 GPU）

```bash
python labs/L5/schedule_prediction.py --results <预算扫描目录> --out <dir>
```

用预算扫描的逐 step 记录拟合、再用 mini 的计数轨迹预测，结果见"机制拆解"的最后一节。
核心是三条：

1. 纯 decode 步约 3.36 ms，与 token 数无关；含 prefill 的步从 10.5 ms 涨到 157.9 ms。
2. 单一线性模型跨不了这个范围，长请求 TTFT 的预测偏差在 −83% 到 +34% 之间。
3. 斜率误差 ±50% 时，按"单步 15 ms"选出的分块在真实曲线上落在 11.5–19.5 ms
   （0.76×–1.30×），分块数 12–36 个。**低估伤尾延迟，高估伤 TTFT。**

### 建议的消融

1. 把预算扫到 64 与 16384，看两侧极端的单步与 TTFT 各到哪里。
2. 在 mini 调度器里把抢占受害者从"最新"改成"最老"，对照重算 token 与最长等待。
3. 给 mini 的 deadline 收紧到 50 步，观察取消率随到达率的变化。
4. 打开真实引擎的前缀缓存重跑预算扫描，看长 prompt 的首 token 是否随命中下降（5.2）。

### D：ARRIVAL 协议下的过载拐点（两引擎真实服务）

预算扫描是固定负载下的对照；真实服务还要回答"到达率超过容量时会怎样"。
按统一协议（同一模型、同一 prompt 2048 / 输出 128、关闭前缀缓存、泊松到达、
到达率为闭环基线的 0.3/0.6/0.9/1.1 倍、每档 3 个 120 秒窗口）：

```bash
# 服务已在 8100 端口就绪；扫描期间每 2 s 抓一次 /metrics（SGLang 需 --enable-metrics）
python labs/L5/arrival_scan.py --engine vllm  --base-url http://127.0.0.1:8100 --out <dir>
python labs/L5/arrival_scan.py --engine sglang --base-url http://127.0.0.1:8100 --out <dir>
```

两台同型号机器上各跑一个引擎（vLLM 0.29.0 在 crater、SGLang 0.5.19 在 crater2）：

| 引擎 | 闭环基线 QPS | 基线 TTFT p50 ms | 0.3× goodput | 0.9× goodput | 1.1× goodput | 1.1× SLO 内 |
|---|---:|---:|---:|---:|---:|---:|
| vLLM | 15.30 | 1096.6 | 4.79 | 14.26 | 17.37 | 0.181 |
| SGLang | 16.03 | 1404.8 | 5.02 | 14.92 | 18.10 | 0.158 |

| 倍率 | TTFT p50 ms（vLLM / SGLang） | TTFT p99 ms（vLLM / SGLang） | TPOT p50 ms（vLLM / SGLang） |
|---:|---|---|---|
| 0.3 | 46.1 / 46.5 | 144.6 / 105.4 | 5.11 / 5.31 |
| 0.6 | 50.3 / 50.0 | 146.1 / 143.3 | 7.30 / 8.70 |
| 0.9 | 95.7 / 127.7 | 1064.1 / 1253.8 | 15.83 / 20.45 |
| 1.1 | 8636.0 / 8669.4 | 15631.7 / 16704.1 | 20.54 / 20.50 |

四条读法：

1. **0.3 到 0.9 倍之间，goodput 与到达率同步上涨**（vLLM 4.79 → 14.26、SGLang 5.02 → 14.92 QPS），
   TTFT p50 在 0.3–0.6 倍上稳定在 46–50 ms——这一段排队是线性的。
2. **0.9 倍的 p99 先跳两个数量级**（vLLM 146 → 1064 ms，SGLang 143 → 1254 ms），
   而 p50 只涨到 96/128 ms。服务还没垮，尾延迟先垮。
3. **1.1 倍时 goodput 只比各自基线高 13%**（17.37 对 15.30、18.10 对 16.03 QPS），
   TTFT p50 却到 8.6 s；SLO 内比例从 1.000 掉到 0.18/0.16。超发的那一部分全部堆成队列。
4. **TPOT 在 0.9 与 1.1 倍上几乎一样**（vLLM 15.83/20.54、SGLang 20.45/20.50 ms）：
   饱和之后 decode 每步的成本由批大小决定，与到达率无关——这是"准入控制买的是
   被接收请求的尾延迟，不是吞吐"的实测依据。

两个引擎在这条曲线上的差别小于 5%（容量 15.30 对 16.03 QPS；过载区 p50 8636 对 8669 ms）。
低倍率下 vLLM 的 p99 略高（0.3 倍 144.6 对 105.4 ms），三次窗口极差分别是 [106, 243] 与
[103, 109]——vLLM 那一档的窗口间波动更大，单看一个窗口会得出更强的结论。

样本量：vLLM 合计 5512 条、SGLang 合计 5753 条，**都不足 10000 条**，
p99 只作同口径排序（窗口极差已在原始汇总里列出）。

### 过载区的准入：抢占次数才是两引擎真正的差别

客户端曲线在两引擎上几乎重合，但"过载时牺牲谁"要看服务端计数。把
`labs/L5/arrival_scan.py` 扩成在每档窗口内每 2 秒抓一次 `/metrics`，1.1× 与 1.3× 的结果：

| 引擎 | 倍率 | 到达 QPS | 样本 | 超时 | goodput | SLO 内 | TTFT p50 ms | 溢出计数 | 等待峰值 | 运行峰值 | KV 峰值 |
|---|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| vLLM | 1.1 | 16.83 | 2051 | 0 | 17.09 | 0.147 | 7470 | **抢占 75.5** | 201.5 | 44.0 | 1.000 |
| vLLM | 1.3 | 19.89 | 2390 | 0 | 19.91 | 0.066 | 18444 | **抢占 81.0** | 214.0 | 44.0 | 0.9996 |
| SGLang | 1.1 | 17.63 | 2132 | 0 | 17.77 | 0.130 | 7979 | **retract 0** | 217.0 | 46.5 | 0.995 |
| SGLang | 1.3 | 20.83 | 2489 | 0 | 20.74 | 0.063 | 18745 | **retract 0** | 232.0 | 45.5 | 0.995 |
| SGLang | 2.0 | 31.91 | 3771 | **2660** | 9.26 | 0.024 | 17689 | **retract 0** | 256.0 | 54.0 | 1.000 |

四点：

1. **1.1×/1.3× 的客户端指标几乎逐格相同**（TTFT p50 差 <3%、p99 差 <2%、TPOT 都在
   20–21 ms），但引擎内部走了两条路：vLLM 分别抢占 75.5 与 81.0 次——被抢占的请求
   释放 KV、`num_computed_tokens` 归零，下一轮从头重算（5.8 的 `_preempt_request`）；
   SGLang 的 retract 计数始终为 0，请求停在等待队列里等 KV 自然释放。
2. **两者的等待与运行峰值也接近**（等待 201–232、运行 44–46），KV 都到 0.995–1.000：
   池子都被打满。差别不在"谁更满"，而在满的时候是**牺牲在跑的请求**还是**让新请求排队**。
3. **SGLang 推到 2.0× 仍不 retract**，代价转成超时：3771 条里 2660 条在 120 s 窗口内没
   完成，goodput 掉到 9.26 QPS，等待峰值顶到 256（队列上限），TTFT p50 17.7 s、
   p99 51.1 s。**准入策略改变的是"谁被牺牲"，不是"能否撑住"。**
4. **要判断一台引擎在过载下会牺牲谁，必须读引擎侧计数。** 只报 TTFT 与 goodput 时，
   两种完全不同的准入实现可以给出同一条曲线。

采集口径本身有一个坑：vLLM 的 `vllm:num_preemptions_total` 是 Counter，取窗口首末差；
SGLang 只导出 `sglang:num_retracted_reqs` 这一个 **Gauge**，每次上报后复位，取首末差
恒为 0，必须按采样点累加。两侧的原始 `/metrics` 各存了一份
（`results/crater/5.3/arrival-overload-20260922/vllm/*/metrics_end.txt`）。

## 前沿

调度预算可以进一步结合历史 KV 长度、预测 step 时长和请求期限，而不只按新增 token 数分配。
三条正在被使用的路线：

- **按轮调度（iteration-level scheduling）**：Orca 把"一个请求一个 batch"改成"每轮重组 batch"，
  本章的 continuous batching 就是它的当代形态；代价是每轮都要重算成员与 KV 归属。
- **按预测的 step 时长分配预算**：先估计这一步要跑多久，再决定放多少 token 进去。
  本章的误差注入给出了这条路线的前提：斜率估计必须带误差界，否则两端都会付代价。
- **任务级优先级与准入**：把优先级从"serving 请求"提到"任务图"上（Autellix、Parrot 等），
  在 agent 负载里按剩余任务价值排序。这一层由 [9.7](../L9/9.7-agent-workflow-scheduling.html) 承担，
  它复用本章的引擎接口与预算语义。

上表中除本章实测外的机制来自各自论文与源码，**加速比尚未在本机复现**<span class="unverified">未实测</span>。

## 陷阱

1. **把 step 耗时当作每请求输出记录。** 是否推进必须看实际调度与输出。
2. **用固定观察窗口代替请求生命周期。** 长请求没跑完时的"总时间"只是窗口时间，
   本章的预算扫描一直跑到所有请求结束。
3. **用预算代替真实产出。** prefill 消耗 token 预算，却未必产生输出 token。
4. **把 token 预算当作延迟保证。** 上下文长度和后端改变每 token 成本；
   同样的分块大小在训练与推理、不同 attention 后端下的耗时不同。
5. **只测边界一侧。** 扫描需覆盖预算低于、等于和高于实际需求的情况。
6. **拿一个超参数式预测 step 时间。** 纯 decode 步与含 prefill 的步不落在同一条直线上；
   只用最慢步拟合会把截距抬高 2.6 倍。
7. **假设"切得更细更安全"。** 低估斜率时细切确实压住尾延迟，但长请求的 TTFT
   从 172.6 ms 涨到 511.4 ms；预算选择取决于服务更在意哪一端。
8. **把 gauge 当 counter 读。** SGLang 的 `sglang:num_retracted_reqs` 是 Gauge，
   每次上报后复位，窗口首末差恒为 0；只有按采样点累加才能看到窗口内的事件数。
   直接相减会得出"引擎从不回收 KV"的错误结论。
9. **用客户端指标推断准入策略。** 抢占与排队可以让 TTFT/goodput 曲线重合；
   要判断"过载时牺牲谁"，必须同时读引擎侧的抢占/retract 计数与运行/等待峰值。

## 自测题

<details markdown="1"><summary>1. 预算 512，8 条普通 decode 都获调度，最多还能安排多少 prefill token？</summary>

在不考虑其他约束时为 504。实测里每块是 504 而不是 512：`max_num_batched_tokens=512`
要减去 8 条 decode 各占的 1 个 token。还需确认块池、请求长度和后端是否允许这份混合批。
</details>

<details markdown="1"><summary>2. 连续五步变慢，是否说明这五步 decode 全部停止？</summary>

不能。它们可能是混合批，仍在生成输出。需要逐请求调度与输出记录才能区分。
本章的采集器把每步每请求的调度 token 数与产出都存了下来，可以逐条核对。
</details>

<details markdown="1"><summary>3. 三档预算下长请求的完成时间几乎相同，能否证明分块没有代价？</summary>

不能。完成时间不变只说明**总工作量**没变。代价在两端：预算 128 时长请求的首 token
是 8192 档的 3.0 倍（511.4 对 172.6 ms），而预算 8192 时 8 条 decode 的最大停顿
是 128 档的 17 倍（158.0 对 9.1 ms）。分块改变的是代价在谁身上。
</details>

<details markdown="1"><summary>4. 为什么纯 decode 步的时间与 token 数无关，而含 prefill 的步强烈相关？</summary>

纯 decode 步每条请求只新增 1 个位置，本轮工作量由权重读取主导——权重字节是常数，
batch 从 8 变到 9 只让 GEMM 的 M 维动一格。含 prefill 的步新增的位置从 128 到 8184，
既要读长度成正比的历史 KV，attention 还有 $O(n^2)$ 项，所以时间随分块大小快速增长。

本章实测：纯 decode 步 507 个样本中位 3.36 ms；含 prefill 的步从 10.5 涨到 157.9 ms。
</details>

<details markdown="1"><summary>5. 如果 step 时间预测的斜率低估了 50%，调度器会犯什么错？怎么发现？</summary>

它会以为一个 686 token 的分块只要 15 ms，实际要 19.5 ms（1.30 倍），于是 decode 的
停顿被拉长到目标之上；反之高估 50% 会把分块切到 229 token，长请求多等 36 个 step。

发现方法：同时记录**预测的单步时长**与**实际墙钟**，按分块大小分桶看残差。
只报平均值会把两个方向的误差抵消掉——本章的残差极差是 [−15.0, +148.0] ms。
</details>
