## 本章回答三个问题

调度器决定每轮处理哪些请求、每条请求处理多少 token，并协调 KV 分配。长 prefill 与正在生成的请求共用 GPU 时，调度预算同时影响首 token 延迟、输出间隔和吞吐。

1. 一次 step 的请求状态与 token 预算怎样对应？
2. 插入长 prompt 后，怎样区分 step 变慢与请求没有被调度？
3. `max_num_batched_tokens` 在什么区间限制工作量，已有实验测到了什么？

## 机制拆解与推导

### token 数比请求数更接近本轮工作量

普通 decode 每条请求通常新增一个位置；prefill 可能新增数千个位置。仅限制请求条数，无法区分两类工作的规模。设本轮请求 i 被分配 n_i 个新 token、总预算为 M，则

$$\sum_i n_i\le M.$$

这只是调度约束。相同新增 token 数，在历史长度、模型架构、投机配置或 attention 后端不同的情况下，耗时仍可能不同。

chunked prefill 将长 prompt 分成多个轮次处理。它能限制单轮新增位置数，让 decode 有机会在轮次之间推进；代价包括重复调度、较小的 GEMM 形状和历史 KV 读取。分块不保证吞吐不变。

### step 时间与逐请求输出间隔不同

step 变长时，该轮完成的输出通常更晚返回。但仅记录 `step()` 调用耗时，不能判断这一步是否给某条请求生成了 token。要区分“仍在推进，只是每步更慢”和“没有被调度”，必须同时保存每请求的调度 token 数及输出。

`running` 和 `waiting` 的长度也不是调度器的全部状态。请求还包含已计算长度、待处理输入、停止条件、优先级、块引用和可能的抢占状态。5.7 和 5.8 会把这些状态展开。

### 设计取舍

- **不变量。** 分配的 token 数不超预算，写入 KV 前已有对应物理槽位，完成或取消的请求不再被调度。
- **状态归属。** 调度器管理请求进度与块引用；执行器按本轮计划构造张量。执行结果必须更新同一请求，不能仅用 batch 位置标识请求身份。
- **优先级。** 优先推进 running 请求可以减少重复工作，但过度偏向它们会增加新请求等待时间。需要同时观察 TTFT、输出间隔和公平性。
- **预算大小。** 小预算限制单轮工作量，也可能减少并发推进数；大预算提高组合自由度，却可能让长 prefill 拉长一轮。
- **增加后端。** 应明确其支持的混合批、长度布局、KV 容量和返回状态；不能只替换模型调用而保留不适用的预算假设。

这些是依据接口和实验代码作出的设计分析。vLLM/SGLang 同负载下的公平性与调度开销对照为 `UNVERIFIED`。

## 工程实现 · mini 实现

下面实现一个仅用于理解预算的分配器。真实系统还需处理抢占、前缀缓存、块粒度及失败清理。

```python
def allocate(budget, decode_ids, prefill_remaining):
    if budget < 0:
        raise ValueError("budget must be nonnegative")
    assigned = {}
    for rid in decode_ids:
        if budget == 0:
            break
        assigned[rid] = 1
        budget -= 1
    for rid, remaining in prefill_remaining:
        if rid in assigned or remaining < 0:
            raise ValueError("invalid request state")
        n = min(remaining, budget)
        if n:
            assigned[rid] = n
            budget -= n
    return assigned

plan = allocate(512, [f"d{i}" for i in range(8)], [("long", 8192)])
assert sum(plan.values()) == 512
assert plan["long"] == 504
```

将预算改为 4，只能推进前四条 decode。每轮保持相同顺序会造成饥饿；可以加入轮转游标，再检查各请求的最大等待轮数。

### 插入长 prompt 的时间尖峰

8 条短请求进入生成阶段后，插入 8192-token prompt。原始记录：

- 稳态 step 中位数：4.735 ms。
- 最慢 step：53.326 ms，为稳态的 11.3×。
- 超过稳态两倍的 step：5 / 40。
- 前 12 步：`[4.76, 31.38, 41.02, 47.18, 53.33, 49.86, 5.39, 4.9, 4.81, 5.03, 4.77, 4.9]`。

这表明该负载出现了连续慢轮次。没有逐请求输出记录，不能据此恢复每条请求的 TPOT 分布。

### token 预算影响最长 step

| token 预算 | 稳态 ms | 最慢 step ms | 尖峰倍数 | 插入后观察窗口耗时 ms |
|---:|---:|---:|---:|---:|
| 16384 | 4.607 | 165.852 | 36.0× | 529.5 |
| 2048 | 4.679 | 53.624 | 11.5× | 539.6 |
| 512 | 4.651 | 15.926 | 3.4× | 514.6 |

所测点上，预算减小伴随最长 step 缩短。最后一列覆盖固定的最多 80 步，不是长请求独立耗时，也不是等工作量吞吐比较；缺少重复样本，不能宣称三档“差异都在噪声内”。

### 预算跨越并发数的扫描

| token 预算 | step 中位数 ms | 原脚本估计 tok/s | 相对最高估计值 |
|---:|---:|---:|---:|
| 16 | 4.387 | 3647 | 0.26× |
| 32 | 4.436 | 7214 | 0.52× |
| 64 | 4.574 | 13993 | 1.00× |
| 128 | 5.247 | 12197 | 0.87× |
| 512 | 5.178 | 12361 | 0.88× |
| 8192 | 5.162 | 12399 | 0.89× |

普通纯 decode 的理论预算需求为每条请求一个 token，因此 M=64 是一个值得覆盖的边界。但原脚本没有核对观察区间是否全部为纯 decode，也没有保存真实输出计数。64 以上的数据还相差约一成，不能写成“完全不变”。**这条趋势未解释，不要引用**为真实吞吐的稳定规律。

### 建议的消融

1. 在每步同时记录 scheduled token、请求 ID、已计算长度和新增输出；以这些字段区分 prefill、decode 与混合批。
2. 单独记录长请求从准入到首 token、完成的时间；另用持续到达负载测总吞吐和延迟分布。
3. 在 16/32/64/128/256/512 等预算上重复运行，确认预热结束和纯 decode 区间；用实际输出计数计算吞吐。
4. 固定负载，对照 running 优先、轮转与优先级策略，检查最大等待时间及抢占重算量。

## 前沿

调度预算可以进一步结合历史 KV 长度、预测 step 时长和请求期限，而不只按新增 token 数分配。其收益需要在持续到达的负载下检查，特别是预测误差、饥饿与过载后的行为。相关策略及 SGLang 对照在本章均为 `UNVERIFIED`。

## 陷阱

1. **把 step 耗时当作每请求输出记录。** 是否推进必须看实际调度与输出。
2. **把固定 80 步计时称为 prefill 总时长。** 观察窗口与请求生命周期不同。
3. **用预算代替真实产出。** prefill 消耗 token 预算，却未必产生输出 token。
4. **把 token 预算当作延迟保证。** 上下文长度和后端改变每 token 成本。
5. **只测边界一侧。** 扫描需覆盖预算低于、等于和高于实际需求的情况。
6. **把单次差异归为噪声。** 先保存重复样本，再报告区间。

<details markdown="1"><summary>2. 连续五步变慢，是否说明这五步 decode 全部停止？</summary>

不能。它们可能是混合批，仍在生成输出。需要逐请求调度与输出记录才能区分。
</details>

<details markdown="1"><summary>3. 三档预算的 80 步总时间接近，能否证明分块没有吞吐代价？</summary>

不能。相同步数不保证相同有效工作量；观察窗口也没有精确覆盖长请求的生命周期。应以实际处理和产出的 token 数计量，并做重复对照。
</details>

<details markdown="1"><summary>4. 为什么纯 decode 时预算超过并发数仍可能改变实测时间？</summary>

它不再直接限制每轮新增 token 数，但配置可能影响其他执行选择；实验也可能包含 prefill 或状态差异。应先确认工作量和实际路径，不能将所有变化归为噪声。
</details>
