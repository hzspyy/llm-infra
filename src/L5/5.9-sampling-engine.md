## 本章回答三个问题

采样引擎把一行 logits 变成一个 token。它还负责惩罚重复、裁剪候选、管理随机数，并按请求返回 logprobs。即使参数名称相同，处理顺序和边界条件不同也会改变结果。

1. temperature、top-k、top-p、min-p 和三种重复惩罚分别改了什么，怎样自己实现？
2. vLLM 与 SGLang 的处理顺序、并列值和返回概率有何差异？
3. 采样与 logprobs 在 GPU 和真实生成请求中分别花多少时间？

实验覆盖采样函数、SGLang 的 CPU/GPU 路径及 vLLM 端到端生成。大 batch 下，Triton 过滤与排序参照仍有一个候选 token 的差异，原因尚未确定。

## 心智模型

logits 是模型为词表中每个 token 输出的分数。概率分布由这些分数计算得到；修改分数或候选集合，都会改变采样分布。

下图是本版本 vLLM 中随机采样的主线。左侧的 raw logprobs 从处理前的 logits 计算，右侧才是真正参与采样的分布。temperature 为 0 时走 greedy 分支，直接从惩罚后的 logits 选 argmax，不执行右侧随机过滤链。

## 机制拆解

### 1. temperature 改变分布的尖锐程度

对 temperature $T>0$，

$$p_i=\frac{\exp(z_i/T)}{\sum_j\exp(z_j/T)}.$$

降低 T 会放大分数差距；增大 T 会让概率更接近。实际实现先减去最大值以避免 exp 溢出。T=0 应走 argmax，不能直接除以零。

greedy 只在**给定 logits**上确定。模型计算可能因 batch、数值精度和 kernel 路径变化而产生不同 logits；temperature 为 0 不能证明整个系统逐位确定。

### 2. 三种惩罚不是同一个开关

设 token i 的原始 logit 为 $z_i$，已生成次数为 $c_i$，repetition penalty 为 $r>0$。本版本 vLLM 对 prompt 或 output 中出现过的 token 做：

$$z_i^{(r)}=\begin{cases}z_i/r,&z_i>0,\\z_i r,&z_i\le0.\end{cases}$$

当 r>1 时，两种符号的分数都下降。把负数也除以 r，反而会提高它。

frequency penalty 按生成次数扣分，presence penalty 只看生成过没有：

$$z'_i=z_i^{(r)}-\alpha c_i-\beta\mathbf{1}[c_i>0].$$

这里 frequency/presence 的计数来自 output，repetition 的出现集合则包含 prompt 与 output。三种操作需要按各自定义构造历史计数或出现标记。

可核对的小例子：原始 logits 为 `[-1, 2, 1, 0.5]`，prompt ids 为 `[0,1]`，output ids 为 `[3,3,1]`，r=1.5、α=0.25、β=0.5。token 3 的计算是 `0.5/1.5 − 2×0.25 − 0.5`。完整向量与真实 GPU penalty 操作的结果在原始日志中。

### 3. top-k、top-p、min-p

**top-k** 保留分数最高的候选。遇到第 k 名并列时，按“阈值”保留可能多于 k 个，按“位置”保留则恰好 k 个；本章确实测到了两种做法。

**top-p** 又叫 nucleus sampling：按概率从大到小累积，保留覆盖指定概率质量 p 的前缀，至少留下一个候选。计算累计概率前是否先做 top-k 并归一化，会改变结果。

**min-p** 按最大概率的比例设阈值，保留满足 $p_i\ge m p_{\max}$ 的 token。它不是“保留概率大于 m 的 token”。对同一 softmax 分布，该条件可写成：

$$z_i\ge z_{\max}+\log m.$$

这里的 z 是已经除以 temperature 的分数。m=0 表示禁用 min-p，不应计算 log 0 后继续一般参数路径。

这些操作通常通过把丢弃位置设为负无穷实现。下一次 softmax 中这些位置概率为零。过滤后的合法集合必须非空；NaN、全负无穷和越界 token id 都应作为错误处理。

### 4. 顺序改变候选集合

取概率 `[0.5,0.3,0.15,0.05]`，k=2、p=0.6。先 top-k 后归一化，前两项成为 `[0.625,0.375]`，top-p 只需第一项。若在原概率上同时求 top-k 与 top-p，第一项只有 0.5，需要保留第二项。

本地安装版本的函数对照如下。数字是 token id，输入与输出向量完整保存在 `filters.json`。

| 用例 | 参数 | vLLM PyTorch 路径的非零候选 | SGLang PyTorch 路径的非零候选 |
|---|---|---|---|
| top-k / top-p 顺序 | k=2，p=0.6 | `[0]` | `[0,1]` |
| min-p 顺序 | 输入 `[0.4,0.3,0.2,0.1]`；m=0.6，p=0.55 | `[0]` | `[0,1]` |
| top-k 并列 | 三项同分，k=2 | `[0,1,2]` | `[0,1]` |

不能把右列当成 SGLang 所有后端的保证。它的实际 GPU 路径在无 min-p 时使用 FlashInfer 的 `joint` 过滤；有 min-p 时先调用 top-k/top-p renorm，再执行 min-p。我们也运行了这条 GPU 调用链：三个用例各抽样 8192 次，计数见原始现场。**并列用例在 GPU 路径抽到了三个 token，和 PyTorch fallback 不同。**

### 5. 从概率分布抽一个 token

标准库 mini 实现用累计概率与均匀随机数比较。vLLM 的 native 路径则使用指数噪声：对每个 token 生成独立 $q_i\sim\mathrm{Exp}(1)$，选择使 $p_i/q_i$ 最大的项。

原因是 $q_i/p_i$ 服从速率为 $p_i$ 的指数分布。其成为最小值的概率为：

$$\int_0^\infty p_i e^{-p_i t}\prod_{j\ne i}e^{-p_jt}\,dt=\frac{p_i}{\sum_jp_j}.$$

因此它与 categorical sampling 具有相同的理想分布，但随机数消耗顺序可以不同。相同 seed 不足以保证换后端后得到同一串 token；应分别测试分布正确性和同一路径的重复性。

## 设计取舍

**不变量**是参数、history、随机状态和 logits 必须属于同一请求、同一步、同一词表。输出 token 必须来自规定的候选集合；返回的 logprobs 必须注明来自处理前还是处理后分布。

引擎持有请求的历史与采样配置，sampler 接收整理后的 batch metadata，GPU kernel 执行张量变换。按请求保存 generator 可以减少其他请求对随机序列的影响，但本版本 vLLM 的 FlashInfer 路径遇到 per-request generator 时会回退 native。可复现性要求会影响执行路径。

增加一个采样后端，至少要处理调度选择、过滤顺序、并列值、数值精度、随机状态和返回字段。验证不仅包括“能抽到 token”，还包括 mask 边界与 logprobs 的语义。错误也应分层发现：非法参数在入口检查；全非法 logits、越界 id 和 kernel 输出异常在执行路径检查。

| 设计选择 | 收益 | 代价或适用边界 |
|---|---|---|
| 完整排序后过滤 | 参照实现直观，便于检查每个边界 | 生成排序值、索引与累计概率；大词表代价可观 |
| pivot / rejection sampling | 可以避免完整排序 | 数值边界、并列值及随机路径更难核对 |
| 先算并返回 raw logprobs | 原始模型分数与采样策略分离 | 它不是最终选词分布；仍需完整行归一化 |
| 返回 processed logprobs | 可以解释实际过滤后的概率 | 本版本会关闭 FlashInfer 快路径，增加计算与中间结果 |
| 单独保存每请求 RNG | 更清楚的请求级随机状态归属 | 可能失去批量采样快路径；跨后端仍不保证同 token |

上述比较是基于源码与测量的设计分析，不是上游方案评审记录。

## 前沿

高效采样不一定先完整排序。FlashInfer 将多轮 rejection sampling 放进 GPU kernel，并提供 `top_k_first` 与 `joint` 两种过滤方式；选择时要同时看性能与分布语义。[FlashInfer 官方文档](https://docs.flashinfer.ai/generated/flashinfer.sampling.top_k_top_p_sampling_from_logits.html)

本地 vLLM 的 Triton 文件注明采用 Qrita 的 pivot-based 思路。该方向把选择问题转化为阈值搜索，减少完整排序，但边界值仍需与参照核对。本章已经发现未解释的候选差异，因此不引用论文速度作为本实现的正确性或性能保证。[Qrita](https://arxiv.org/abs/2602.01518)

训练与推理需要一致的概率定义时，raw/processed、temperature、过滤顺序和精度都必须固定。SGLang 源码为部分 RL 路径单独计算 log-softmax，也说明“生成的 token 相同”和“训练所需 logprob 相同”是两项检查。

## 陷阱

1. **把负 logit 也除以 repetition penalty。** r>1 时这会奖励而非惩罚负分 token。
2. **只对齐参数名。** top-p 归一化位置、min-p 顺序和 ties 都能改变候选集。
3. **把 `logprobs=0` 当成关闭。** 它仍返回 sampled token 的 logprob；关闭用 None。
4. **把 raw logprob 当成实际采样概率。** top-k=1 时实际选择可为必然，raw 分数仍小于 0。
5. **把同 seed 当成跨引擎相同输出。** 随机算法、请求位置与随机数消耗方式都可能不同。
6. **只测 batch 1 或只测大 batch。** 会错过实现切换；本章在 7→8 两侧测量。
7. **丢掉正确性失败，继续只报速度。** 本章保留了 batch 64/256 的候选差异，尚不能声称等价。
8. **把 beam search 写成不存在。** 本版本有明确实现，但本章未运行其性能对照。

## 自测题

<details><summary>1. top-k=2 是否一定只剩两个 token？</summary>

不一定。按第 k 名的值作阈值，可能保留所有同分项；按排序位置裁剪才会只保留 k 个。本章还测到同一引擎的 CPU/GPU 路径对此行为不同。
</details>

<details><summary>2. 输入概率为 [0.5,0.3,0.15,0.05]，为什么 k=2、p=0.6 有时只留下 token 0？</summary>

top-k 后归一化得到 [0.625,0.375]，第一项已经超过 p。若 top-p 使用原始分布，则需要保留第二项。先确定顺序，再谈参数是否相同。
</details>

<details><summary>3. 选出的 token 概率为 1，返回 logprob 却是负数，是否一定有错？</summary>

不是。若返回的是 raw logprob，它来自过滤前的原始分布。应先检查 logprobs_mode；本章的实际 Sampler 分别返回 -0.6931471824645996 与 0.0。
</details>

<details><summary>4. 采样函数比另一个快，但候选集合相差一个 token，能直接替换吗？</summary>

不能把它称为等价替换。先核对预期语义、数值边界、ties 与终止条件，再决定差异是否可接受；不能用速度抵消未解释的正确性差异。
</details>

<details><summary>5. logprobs 从 5 增到 20，GPU 时间几乎不变，是否可以忽略成本？</summary>

不可以。GPU 仍有全行计算和选择；返回记录数、CPU 处理和序列化体积还会变化。应同时测 GPU 工作和真实请求，而不是从一个独立计时概括整个服务。
</details>
