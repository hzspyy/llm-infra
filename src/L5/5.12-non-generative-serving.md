## 本章回答三个问题

全书到目前为止默认「模型 = 自回归生成」。embedding、rerank、classifier 不是：
本章关注其中一次前向返回向量或分数的服务路径，没有自回归 decode 阶段。这一章补上这个盲区。

1. 没有 decode 的模型，瓶颈在哪一侧？
2. 为什么 embedding 服务能用大得多的 batch？
3. 变长输入的 padding 浪费在这里为什么更严重？

结论先给：

- 本章把一次前向返回向量的 pooling 服务与自回归生成对照。pooling 不需要跨 decode 步保留 KV；前向内部仍有 Q/K/V，具体引擎也可能分配缓存或临时 buffer。
- 大 batch 的容量取决于权重、激活、workspace 与持久状态。权重读取的摊薄影响吞吐，不能直接决定显存容量。
- 既有框架计时支持比较所测形状的耗时。roofline 的 FLOP 与字节均为公式估计；图中位置不能单独证明实际瓶颈。旧容量实验存在执行范围和对象释放问题，不能用于两类服务的容量比值。
- 本批补齐容量公式与 meta 参数对拍；rerank、classifier 和 SGLang 真实链路仍为 `UNVERIFIED`，不标整章验收完成。

## 机制拆解与推导

### 1. 算术强度决定了落在哪一侧

用 0.2 那套账本，把一次前向的成本拆成 FLOP 与字节两项：

```text
权重 FLOP   = 2 · N_body · tokens
attention   = causal:  2 · d · n_l · L² · B      （只有一半的 L² 被算）
              双向:    4 · d · n_l · L² · B
decode attn = 4 · d · n_l · C · B                （1 个 query 对 C 个 key）
权重字节    = N_body · dtype_bytes
KV 读取     = 2 · n_l · n_kv_head · d_head · dtype_bytes · C · B
```

`N_body` 是不含词嵌入与 lm_head 的参数量。算术强度 = FLOP / 字节：

- **decode**：分子里 `2·N_body·B`，分母里 `N_body·dtype_bytes`。B 很小时分子分母同阶，
  强度趋近 2/dtype_bytes——bf16 下就是 **1**。批量上去之后分子随 B 线性增长、
  分母的权重项不变，强度才慢慢爬。
- **编码**：分子是 `2·N_body·(B·L)`，分母还是那一个 `N_body·dtype_bytes`。
  强度正比于总 token 数，轻松上到几千。

crater 上 BF16 GEMM 峰值 232.0 TFLOP/s、纯读带宽 1608.6 GB/s（`hw_crater_5090.json`），
脊点落在 **144 FLOP/byte**。这是简化模型的分类边界，不是实测瓶颈判据。字节式未计入全部激活读写、缓存复用及 kernel 中间量；需用目标形状的 profiler 证据确认瓶颈。

### 2. 没有 KV，就没有随上下文增长的状态

一次完成的 encoder 前向不保留跨步 KV；这里容量账本的持久 KV 项为 0。这不是「省了一点显存」，而是**状态空间变了**：

| | 生成 | 编码 |
|---|---|---|
| 每请求的常驻状态 | KV cache，随上下文线性增长 | 无 |
| 显存随 batch 增长的部分 | 权重 + KV + 激活 | 权重 + 激活 |
| 请求之间能否共享一次前向 | 只有同一 iteration 里的请求 | 同一 batch 的全部请求 |

KV 项的缺失减少了随 `B × C` 增长的持久状态。容量上限由各项占用之和决定；权重搬运的摊薄属于时间模型。两种模型不能互相替代。

### 3. pooling 的 batch 是拼出来的，不是 padding 出来的

vLLM 的 pooling 路径里，hidden states 是一条**扁平**的 `[total_tokens, hidden]` 张量，
每条序列的位置由 `query_start_loc` 给出（`v1/worker/gpu/pool/pooling_runner.py:137-149`）：

{{srcfold:results/crater/pooling/20260912-0400/source/vllm/v1/worker/gpu/pool/pooling_runner.py:131-158}}

这段代码说明池化入口按有效 token 数切片，并通过 cursor 读取各段。它不能单独证明此前所有 kernel 都没有对齐 padding，也不能消除客户端已经传入的 pad token。

### 4. 三种池化各自的索引语义

序列池化有三种（`config/pooler.py:16`），区别在于取行或归约：

{{srcfold:results/crater/pooling/20260912-0400/source/vllm/model_executor/layers/pooler/seqwise/methods.py:37-58}}

- `CLS` 取每段的第一行，`LAST` 取最后一行——索引数量为 O(B)，实际复制向量涉及 O(BH) 个元素，H 为 hidden size。
- `MEAN` 要把每段所有行加起来（`methods.py:60-105`）：用 `repeat_interleave` 把
  `prompt_lens` 展开成 `segment_ids`，再 `index_add_` 分段累加。为了不让中间张量炸掉，
  它按 `_MEAN_POOL_ACCUMULATION_CHUNK_BYTES = 16 MiB` 分块累加。

这里有一个约束值得记住：**`CLS` 和 `MEAN` 都显式拒绝 partial prefill**
（`methods.py:44` 与 `67`，直接抛 `RuntimeError`）。这是该实现的约束。双向 attention 的 CLS 依赖整段上下文；MEAN 要求全部位置或额外维护分段累加状态。不能推广成所有模型的部分序列都无法池化。

### 5. 「chunked」在两个语境里不是一回事

同一个词在两个地方指两件不同的事，混起来会得出错误结论。

**生成侧的 chunked prefill**：一条请求被拆到多个 iteration 里算，KV 逐段累积，
请求始终是同一条。它让「32k 的 prompt」在 512 token 的预算下也能跑。

**embedding 侧的 chunked processing**：一条**超长输入**被拆成多条**独立请求**，
各自算完 embedding，再按权重平均（`entrypoints/pooling/embed/io_processor.py:121-169`，
开关是 `enable_chunked_processing`，默认 `False`）。这里没有 KV，没有状态跨段传递。

而 pooling 请求本身，**默认不会被 chunk**。调度器里写得很直接
（`v1/core/sched/scheduler.py:988-996`）：

```python
# chunked prefill has to be enabled explicitly to allow
# pooling requests to be chunked
if (
    not self.scheduler_config.enable_chunked_prefill
    and num_new_tokens > request_token_budget
):
    break
```

后果是：**`max_num_batched_tokens` 成了 pooling 模型序列长度的硬上限。**
vLLM 在启动时就拒绝非法组合——同一组参数用在生成模型上没问题，用在 pooling 模型上直接退出：

```
max_num_batched_tokens (256) is smaller than max_model_len (512).
This effectively limits the maximum sequence length to max_num_batched_tokens
and makes vLLM reject longer sequences.
```

### 6. padding 的代价为什么在这里更贵

padding 让一部分 token 位置是空的，但前向照样算它们。浪费比例是
`L_max / mean(L)`。生成服务里这份浪费被摊薄了：prefill 只占整条请求的一小段，
后面还有 N 个 decode 步。embedding 服务里**没有后面**——一次前向就是全部成本。

而且这个浪费是**二次的**：attention 的 FLOP 正比于 `L²`，把批内最长的那条序列
当作所有序列的长度，attention 部分按 `L_max²` 计费，而真正需要的是 `mean(L²)`。

## 工程实现 · 源码走读

版本固定：vLLM 0.29.0。行号取自 `site-packages` 里的安装源码，快照见「原始现场」。

### A. 路由：`/v1/embeddings` 不产生流式响应

embedding 的路由比 chat completions 短得多（`entrypoints/pooling/embed/api_router.py:28-43`）：

{{srcfold:results/crater/pooling/20260912-0400/source/vllm/entrypoints/pooling/embed/api_router.py:28-43}}

没有 `StreamingResponse`、`[DONE]` 或 SSE keep-alive 注释（HTTP 持久连接是另一层机制）——**一次请求一个响应**。
`@with_cancellation` 还在（断连仍然要清理），但 5.11 讲的那整套 SSE 机制在这里
不适用。HTTP、取消、输入校验和序列化仍然存在。

### B. 调度：pooling 请求默认不被 chunk

见上一节。这一条同时解释了为什么 embedding 服务的 `max_num_batched_tokens`
要设得**不小于** `max_model_len`：它不是吞吐旋钮，而是长度上限。

### C. runner：扁平张量 + pooling cursor

`PoolingRunner.pool()` 拿到的是扁平 hidden states，`build_pooling_cursor` 把
`num_scheduled_tokens`、`seq_lens` 和 `query_start_loc` 三者绑成一个游标对象，
池化层靠它定位每一段。第 142 行有一句注释：

```python
# Pooling has no speculative tokens, so this CPU upper bound is exact.
```

「没有投机 token，所以这个上界是精确的」——生成侧为了省一次同步只能用
`seq_lens` 的上界估计，pooling 侧因为一次算完，可以精确知道每段有多长。
这里的精确性仅指该注释描述的 token 数上界，不能推广到全部元数据。

### D. 池化层：取行、求和、分块

见机制第 4 节。三种池化都很短，但 `MEAN` 的分块累加值得注意：它把
「一次 `index_add_`」换成了「按 16 MiB 分块多次 `index_add_`」，
用一点循环开销换中间张量的内存上限。这是把 OOM 风险换成常数开销的典型做法。

### E. 超长输入：拆成多条独立请求再加权平均

`enable_chunked_processing` 打开后，超长输入按 `max_model_len` 切段，
每段变成一条独立的引擎请求，id 形如 `{request_id}-prompt-{i}-chunk-{j}`，
最后在线聚合。默认关闭——所以默认行为是**截断或拒绝**，不是自动处理。

## 设计取舍

**状态归属与不变量。** scheduler 管 token 预算，runner 提供扁平 hidden states 与 cursor，pooler 按序列取值。cursor 的分段边界必须与有效 token 一致。`CLS`/`MEAN` 的 partial-prefill 错误在 pooler 内发现；预算与最大长度不兼容则在启动配置校验中发现。

**分块需要匹配语义。** 双向 encoder 的早期位置依赖后续 token，不能直接照搬因果模型的 KV 递推。MEAN 的分段累加还需要状态与计数。独立切段再平均是另一种输入处理策略，不保证与整段 embedding 等价。

**响应与容量。** 当前 embeddings 路由一次返回完整向量。响应时间还包含排队、输入处理和序列化。容量账本把持久 KV 与单次激活区分开；两类前向都可能受 workspace 限制。

**增加实现对照。** 新后端需核对 tokenizer、mask、输出维度、归一化、cursor 和取消回收，随后再比较性能。只有池化公式相同不足以保证 embedding 相同。SGLang 端到端及 rerank/classifier 对照待实现。

**时延差值的边界。** 客户端均值与引擎直方图均值的差涵盖客户端线程调度、建连、网络、前后处理和指标窗口差异。它是待分解的残差，不能全部计入 HTTP 服务端。

## 工程实现 · 最小池化批处理

`mini_pooling.py` 只用标准库，做两件事：把变长序列**打包**成扁平数组并用
`query_start_loc` 寻址，以及把同样的序列**padding** 成矩形。两者的池化结果必须相同，
代价必须不同。

{{src:labs/L5/mini_pooling.py:22-53}}

自检覆盖三件事：

- **等价性**：200 组随机长度（1–40、每批 1–12 条），`MEAN` / `CLS` / `LAST` 三种池化，
  打包与 padding 的输出逐元素相同（1e-9 内）。
- **浪费比**：同一批数据下，padding 让算的 token 数变成中位数 **1.64 倍**
  （最坏 3.33 倍）。
- **分桶**：256 条长度 4–512 的输入，按批内最长补齐是 **2.11 倍**，
  按长度分 8 条一桶降到 **1.03 倍**，32 条一桶 1.12 倍。

### 3. padding 实验：减少 token 不保证同比例加速

同一份长度分布包含 128 条序列、16 679 个真实 token，最长 482：

| 批法 | 算的 token 数 | 与真实 token 之比 | 耗时 ms |
|---|---:|---:|---:|
| 一次 padding 到批内最长 | 61 696 | 3.699 | 31.955 |
| 按长度排序后 8 条一桶 | 18 528 | 1.111 | 29.305 |

分桶值是 16 个桶各自计时中位数之和，不是整轮墙钟中位数。原脚本分桶还重新采样 token，并对包含 padding 的 hidden states 直接求均值；这只用于执行成本观察，未验证 embedding 等价。

分桶改变了前向次数和 GEMM shape。BERT 权重小于 L2，不能把 16 次前向直接换算成 16 次完整 DRAM 权重读取。**这条趋势未解释，不要引用**作带宽归因；需要同输入、正确 masked pooling、整轮计时和缓存/launch 证据。

### 4. batch 扫描：吞吐涨 7.6 倍，引擎时间几乎不动

bge-small，目标长度参数 128（字符近似构造；实际每请求 102 token），每个并发档跑 3 次取中位数：

| 并发 | 请求/秒 | token/秒 | 客户端均值 ms | 客户端 p95 ms | 引擎 e2e ms | 引擎 inference ms | 排队 ms |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 232.5 | 23 711 | 4.19 | 4.19 | 3.029 | 2.015 | 0.009 |
| 8 | 1 027.3 | 104 783 | 6.61 | 7.25 | 3.145 | 1.608 | 0.010 |
| 32 | 1 518.1 | 154 846 | 14.11 | 17.58 | 4.249 | 1.099 | 0.004 |
| 128 | 1 726.1 | 176 063 | 37.52 | 59.95 | 4.389 | 0.983 | 0.003 |
| 256 | 1 768.1 | 180 342 | 64.89 | 115.25 | 4.286 | 0.968 | 0.003 |

表中是每档三次运行的统计中位数。吞吐随提交请求数增加，但客户端并发不等于引擎 batch。引擎 inference 是请求时间指标，不能解释成把一次 GPU 时间除以 batch 后得到的摊销成本。

并发 256 的客户端均值减引擎均值得到约 60.61 ms；两项分别取中位数，差值也不等于逐请求残差中位数。缺少分段插桩，不能得出“93% 的时间在 HTTP 层”的结论。

把同一个 1.5B 因果 backbone 用 `--runner pooling --convert embed` 当 embedding 服务
（目标长度参数 256，实际每请求 193 token）：

| 并发 | 请求/秒 | token/秒 | 客户端均值 ms | 引擎 e2e ms | 引擎 inference ms | 客户端 − 引擎 ms |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 47.8 | 9 235 | 20.70 | 17.453 | 15.370 | 3.25 |
| 8 | 440.1 | 84 943 | 15.88 | 8.517 | 4.406 | 7.36 |
| 32 | 1 065.4 | 205 623 | 23.12 | 9.630 | 4.299 | 13.49 |
| 128 | 1 131.6 | 218 391 | 57.59 | 10.958 | 4.194 | 46.63 |

两个服务使用不同模型、tokenizer 和输入长度，token/s 不可作为等量工作的速度比较。较大的模型在该负载上返回更多 token/s，只是这组配置的观测，不能证明“小模型省显存不省时间”。

### 5. 变长输入：引擎不吃这份浪费

同一台服务，长度取自对数正态分布（上限 512）：

| 并发 | 固定长度 req/s | 变长 req/s | 固定长度 token/秒 | 变长 token/秒 | 变长引擎 inference ms |
|---:|---:|---:|---:|---:|---:|
| 1 | 232.5 | 345.9 | 23 711 | 17 989 | 1.266 |
| 8 | 1 027.3 | 1 066.0 | 104 783 | 114 048 | 1.582 |
| 32 | 1 518.1 | 1 752.9 | 154 846 | 191 697 | 1.217 |
| 128 | 1 726.1 | 1 751.7 | 176 063 | 154 609 | 1.016 |
| 256 | 1 768.1 | 1 712.6 | 180 342 | 165 355 | 1.015 |

两组请求的 token 总数和长度分布不同，当前表不能隔离 padding 的影响。打包机制的依据是源码的 cursor 寻址；相近的时延不足以证明所有 kernel 都消除了 padding。需要相同总 token 数、同一组内容和可控 batch 的对照。

### 6. token 预算边界：同一组参数，生成能起、pooling 起不来

A/B 对照，三个服务端，其余参数完全相同：

| 服务端 | 模型 | `--max-model-len` | `--max-num-batched-tokens` | 结果 |
|---|---|---:|---:|---|
| 生成 | Qwen2.5-1.5B-Instruct | 2 048 | 256 | **启动成功** |
| pooling | bge-small-en-v1.5 | 512 | 256 | **进程退出** |
| pooling | bge-small-en-v1.5 | 512 | 512 | 启动成功，512 token 请求通过 |

第二个服务端的报错原文：

```text
Value error, max_num_batched_tokens (256) is smaller than max_model_len (512).
This effectively limits the maximum sequence length to max_num_batched_tokens
and makes vLLM reject longer sequences.
```

生成模型能接受这组参数，是因为 chunked prefill 把「预算」和「长度」解耦了：
32k 的 prompt 可以拆成 512 token 一段慢慢算。pooling 请求默认不被 chunk
（`scheduler.py:988-996`），于是 `max_num_batched_tokens` 直接变成长度上限，
vLLM 索性在启动时拦住。

**这条约束的实践含义**：给 embedding 服务调 `max_num_batched_tokens` 时，
它不是一个可以随便压小的吞吐旋钮——压到 `max_model_len` 以下，服务根本起不来。

### 7. batch 上限：修正账本与实验边界

旧 [batch_limit.json](../../results/crater/pooling/20260912-0400/data/batch_limit.json) 保留不变。旧公式重复计算 Q/O 投影，把 BERT FFN 当成三投影 gated MLP，又增加不存在的 LM head。新公式按 GQA 的 Q/K/V/O、两种 FFN、bias、norm、词嵌入及共享 head 分别计数，并与 transformers 5.17.0 meta 模型对拍：

| 模型 | 固定 revision | 完整参数量 | BF16 权重字节 |
|---|---|---:|---:|
| bge-small-en-v1.5 | `5c38ec7c405ec4b44b94cc5a9bb96e735b38267a` | 33 360 000 | 66 720 000 |
| Qwen2.5-1.5B-Instruct | `989aa7980e4cf806f80c7fef2b1adb7bc71aa306` | 1 543 714 304 | 3 087 428 608 |

以 **30 GiB = 32 212 254 720 byte** 为预算，激活暂估 `16 × d × dtype_bytes × tokens`，修正后的公式上限为 decode C=1024 时 990、C=4096 时 247，encoder L=512 时 5109。这仍是未标定的公式预测，不是可用服务容量。

{{srcfold:results/crater/pooling/20260912-ledger-audit/ledger-meta.json}}

旧实验记录 decode 最后成功档 256、首次 OOM 档 512；encoder 到 4096 未 OOM。但 decode 分支先执行完整 1024-token prefill，OOM 阶段未记录；encoder 分支只删除 `llm`，局部 `body` 仍持有 Qwen 权重。因此它们不是独立的稳态容量测量，**撤回“编码容量至少为 decode 的 16 倍”及差值来自 workspace 的归因**。

### 8. rerank 真实链路：Qwen3-Reranker-0.6B

**模型与版本。** `Qwen/Qwen3-Reranker-0.6B`，revision `e61197ed`，0.6B 因果 LM（`Qwen3ForCausalLM`，28 层，hidden 1024，1.6B 词嵌入共享，完整参数量 595,776,512）。vLLM 0.29.0，crater，RTX 5090 D。HF 前向峰值显存 1,242,823,680 bytes（约 1.16 GiB，bf16 加载）。

**路由注册机制。** vLLM 对因果 LM 的 reranker 识别任务为 `score`，经 `pooling/factories.py` 只挂 `/score` 和 `/rerank` 路由。`/classify` 仅在 `pooling_task == "classify"` 时注册，Qwen3-Reranker 不属于该路径，所以对它发 `/classify` 会返回 404——这是预期行为，不是错误。

**合约核对结果。**

| 检查项 | 结果 |
|---|---|
| `/score` 返回 200 | 通过 |
| `/rerank` 返回 200 | 通过 |
| 不等长对拒绝（queries:2 documents:3）→ 400 | 通过 |
| 文档数 1/4/16/64 扫描全 200 | 通过 |
| `/classify` 返回 404（预期，非 `classify` 任务） | 记录，符合路由注册机制 |

**文档数与时延（中位数，预热 2 次后 3 次）。**

| 文档数 | 客户端中位数 ms | prompt_tokens |
|---:|---:|---:|
| 1 | 6.72 | 26 |
| 4 | 6.06 | 94 |
| 16 | 8.22 | 372 |
| 64 | 16.78 | 1 484 |

时延随文档数增加，但增幅较小，说明多文档在同一批次内完成打分。token 数与文档数线性增长，约 23 token/doc（本实验的 query+doc 对）。

**HF reference 与 vLLM `/score` 的数值对照。**

vLLM `/score` 返回的分数（0.77–0.88，分布紧凑）与 HF reference `sigmoid(yes_logit − no_logit)`（0.0001–0.9987，分布极宽）不匹配，二者对同一组文档给出不同排序（HF reference 排第一的是 doc 0「Prefix caching...」，vLLM 排第一的是 doc 4「A prefix cache lookup...」）。根因未确认：vLLM 走 `CrossEncoderIOProcessor` → pooler 路径，而 HF reference 是手动提取 LM head 的 `yes`/`no` 两行（token id 9693/2152）计算 sigmoid(logit 差），两条路径并不等价。`1_LogitScore/config.json` 里只含 `true_token_id`/`false_token_id`，未见 `logit_mean`/`logit_sigma` 仿射标定参数。**vLLM 与 HF 两条路径的 score 不应直接比较，需确认两者的完整计算链才能做数值对照。** 两者的排序差异也保留为未解释结论。

实验前后 GPU 均为 1 MiB、0% 利用率，计算进程列表为空；vLLM 服务端退出码 0；HF 前向退出码 0；在线阶段因 `/classify` 404 导致合约脚本以退出码 1 结束，原始响应均已保留。

### 9. 消融与未测范围

建议消融，每种配置另存结果：

- 把 bge-small 换成 `--dtype float32` 跑一遍，看权重字节翻倍后 roofline 点怎么移动；
- 打开 `--enable-chunked-processing`，给超过 512 token 的输入，量拆段与聚合的开销；
- 用 `MEAN` / `CLS` / `LAST` 三种池化各跑一次同样的 batch 扫描，看池化本身是否可测；
- 打开 chunked prefill 后重跑第 6 节，验证 pooling 请求是否真的被 chunk、以及
  `CLS`/`MEAN` 是否如源码所示直接抛错；
- 给 batch 上限的账本加一个标定步：先实测一个点，用实测/账本的比值修正后再外推。

未测：

- **SGLang / TensorRT-LLM 的 pooling 路径未对照。** 只走了 vLLM 0.29.0。
- **`max_num_batched_tokens` 边界只测了启动行为**，没有测「启动成功之后，
  接近上限的请求会怎样排队」。
- **生成侧在 256 token 预算下跑长 prompt 没有实测。** 第 6 节第一个服务端只记录了
  「启动成功」；用它跑 1024 token 的 prompt 需要另起一次服务并用 chat 接口，

- **batch 上限的实测用的是 transformers 前向，不是 vLLM 服务**，两者对激活的

## 前沿

沿本章机制继续扩展，而不是只调参数：

- **Matryoshka 与维度截断。** `pooler_config.dimensions` 支持把 1536 维输出截成 512 维。
  这会改变返回字节数与下游存储成本，但**不改变前向的计算量**——前向仍要算完整维度。
  收益在哪一侧需要单独测。
- **late interaction（ColBERT 一类）。** 输出从「每序列一个向量」变成「每 token 一个向量」，
  返回数据量涨 `L` 倍，池化从 `MEAN` 变成 `ALL`。这会把瓶颈从计算推向序列化与带宽。
- **rerank 与 classifier。** cross-encoder 打分是「一次前向、一个标量」，
  形状比 embedding 更极端；classifier 通常带分类 head；具体分数变换需按模型核对。两者的 batch 行为都没有实测。
- **多向量与多模态。** 图像/视频 embedding 的输入不再是变长 token 序列，
  打包策略要重做。
- **数据并行部署。** pooling 没有 KV，请求之间完全独立，是最适合做 DP 的负载；
  但每个副本都要装一份权重，收益取决于模型大小。

## 陷阱

1. 把 decode 的调优结论套到 embedding 上。`max_num_seqs`、chunked prefill、
   KV 容量、prefix caching 在这里**要么不适用，要么含义完全不同**。
2. 把 `max_num_batched_tokens` 当成吞吐旋钮压小。对 pooling 模型它等于长度上限，
   压到 `max_model_len` 以下服务直接起不来。
3. 把两种 chunked 混为一谈。生成的 chunked prefill 是「一条请求分多步」，
   embedding 的 chunked processing 是「一条输入拆成多条请求」。
4. 以为引擎会 padding。vLLM 的 pooling 路径是打包寻址，pad token 是客户端造出来的。
5. 用 `CLS` 或 `MEAN` 池化还打开 chunked prefill。源码里这两种池化直接拒绝
   partial prefill。
6. 拿 roofline 上的 TFLOP/s 当作 kernel 上限。本章测的是框架级前向，
   本章的 47–50% 是估计 FLOP 除以框架时间，再相对 GEMM 基准归一化；原因尚未定位。
7. 用 embedding 的 batch 上限去规划生成服务，或反过来。
8. 只看吞吐不看客户端时延。本章并发 256 时引擎时间几乎没变，客户端时延涨了 15 倍。

## 自测题

1. 为什么单序列 decode 的算术强度接近 1，而编码能到几千？
2. bge-small 在并发 1→256 之间吞吐涨 7.6 倍，但引擎侧单请求时间几乎不变。
   这两件事为什么不矛盾？
3. 变长输入的吞吐和固定长度几乎一样。这说明引擎做了什么？
4. `--max-num-batched-tokens 256 --max-model-len 512` 用在生成模型上没问题，
   用在 pooling 模型上直接退出。为什么？
5. `CLS` 和 `MEAN` 池化为什么拒绝 partial prefill，而 `LAST` 不拒绝？
6. 256 条长度 4–512 的输入，按批内最长补齐的浪费是 2.11 倍，
   按长度分 8 条一桶是 1.03 倍。为什么分桶能省这么多？

::: fold 答案
1. decode 每一步只处理 1 个 token，却要把 `N_body` 的权重全部读一遍：
   分子 `2·N_body·B`、分母 `N_body·dtype_bytes`，B=1 时强度趋近 `2/dtype_bytes`（bf16 下为 1）。
   编码的分子是 `2·N_body·(B·L)`，分母还是那一个权重字节数，强度正比于总 token 数。
2. 客户端提交请求数、调度器 batch 和每请求时间是不同指标；需要实际 batch 轨迹才能解释吞吐变化。现有数据不能证明 inference 下降来自权重摊销。
3. 相近吞吐不能证明实现机制。打包应核对 cursor、有效 token 与实际执行 shape，同时控制输入长度和总工作量。
4. 生成模型默认开启 chunked prefill，一条长 prompt 可以拆到多个 iteration，
   所以 token 预算与序列长度解耦。pooling 请求默认不被 chunk
   （`scheduler.py:988-996`），预算直接成为长度上限，vLLM 在启动时拦住非法组合。
5. 该版本 CLS/MEAN 显式拒绝 partial prefill。双向 CLS 依赖整段上下文，MEAN 需要完整归约或额外状态。LAST 没有同样的检查不代表可以提前返回正确的最终序列向量；还需核对调度和输出完成条件。
6. 按批内最长补齐时，每条序列都被补到 512，而真实长度均匀分布在 4–512，
   平均只有 258，浪费比例接近 2。按长度排序后分桶，桶内长度接近，
   每条只需要补到桶内最长，浪费降到 3%。
:::
