## 本章回答三个问题

这一层要回答的不是「agent 能不能用」，而是「agent 负载长什么样」。一次 agent 任务不是一次补全：它是若干轮模型调用、穿插工具等待、每轮把上一轮的全部上下文重新送回引擎的会话。轮次结构、长度结构、前缀结构和等待结构共同决定了后面五章能优化什么、不能优化什么。

1. 真实执行产生怎样的轮次和长度分布？
2. 工具等待怎样改变并发与缓存？
3. 合成分布能检验什么假设、不能检验什么？

## 机制拆解与推导

### 1. 任务 harness 与事件模型

三类任务各 100 个，由固定 seed 确定性生成（`labs/L9/agent_tasks.py`）：

| 任务类 | 工具 | 判定方式 | 说明 |
|---|---|---|---|
| `compute` | `calculate(expression)` | `FINAL` 的整数与本地 AST 白名单求值结果精确相等 | 表达式深度 ≤3，含 `+ - * // % **`，防止心算 |
| `retrieval` | `search_corpus(query, k)` | `FINAL` 引用的 `MED-*` 文档出现在 NFCorpus `test.tsv` 的 qrels 中 | 纯 Python BM25，语料 3 633 篇、查询 323 条，取 100 条有标注的 |
| `codefix` | `list_files` / `read_file` / `edit_file` / `write_file` / `run_tests` | 隔离副本上 14 项 `unittest` 全绿 | 固定小仓库 3 模块 14 函数，注入单点变异（104 个候选全部经自检可被测试捕获） |

`codefix` 的沙箱是任务级目录，测试目录对模型只读：`edit_file`/`write_file` 遇到 `tests/` 直接拒绝并计入 `rejected_writes`，所以「改测试骗过判分」这条路被堵住。

每次模型调用记一条事件，每个会话记一条结果。事件里这些字段支撑了后面所有结论：

```json
{"session_id": "codefix-071-c16-ad10daea", "task_class": "codefix", "turn": 5,
 "t_global_ms": 3503.3, "prompt_tokens": 1861, "cached_tokens": 1408,
 "completion_tokens": 44, "reasoning_tokens": 0, "ttft_ms": 233.1, "e2e_ms": 661.1,
 "tool_names": ["edit_file"], "tool_wait_ms": 0.27, "common_prefix_chars": 1229}
```

三点约定写进采集器，避免后面几章拿错数：

1. `cached_tokens` 是**引擎自报**的命中量（`usage.prompt_tokens_details.cached_tokens`），不是客户端估算；
2. `common_prefix_chars` 是相邻两轮 prompt 文本的公共前缀字符数，与 token 无关，只作结构指标；
3. **失败会话不删**：得分 0 的会话照样入库，`error_sessions` 单独计数。

#### 统一因果事件模型（`labs/L9/agent_trace_spans.py`）

上面那条「一轮一条事件」的记录够画分布，但不够画**任务图**：它没有准入时刻、没有工具的开始/结束、也无法把一次调用和它的重试、它的工具子节点对上。9.1-A 把标识与时间点收敛到一套 span 模型，9.2–9.8 共用同一套字段：

| 类别 | 字段 | 说明 |
|---|---|---|
| 标识链 | `session_id` → `task_id` → `node_id`（`<task>#tN`）→ `parent_node_id` → `attempt` → `tool_call_id`（`<node>/toolK`）→ `engine_call_id`（模型给的 `call_*`）→ `engine_request_id`（SSE 的 `chatcmpl-*`） | 缺任何一级都会把「重试」「并行工具」「跨轮复用」混成一件事 |
| 任务时间点 | `task_arrive` → `task_admit` → `task_start` → `node_ready` → `task_end` | `arrive` 由**独立到达器**在绝对时刻打点，`admit` 才是拿到并发槽；两者之差就是排队 |
| 模型时间点 | `model_start` → `model_first_reasoning` / `model_first_final` / `model_first_tool` → `model_end` | 三个「首输出」分开记，`model_end` 落 `finish_reason`、`chunk_count`、`delta_chunks`、`missing_delta` |
| 工具时间点 | `tool_start` / `tool_end`（每个 `tool_call_id` 一对） | 带 `parallel`（是否只读并行批）、`duration_ms`、`result_chars`、`ok` |

四条口径写死在这一层，后面几章不再各自定义：

1. **首输出三选一，不是 TTFT 一个数。** 首 reasoning delta、首 final delta、首 tool delta 分别记时；`ttft_ms` 只是「三者中最早出现的那个」的别名。实测 1 386 次调用里 `first_reasoning` 有 201 次、`first_final` 359 次、`first_tool` 1 123 次——**只按 content 定义首输出会丢掉 74% 的调用**（工具轮的 token 全在 `delta.tool_calls` 里，`content_chars` 为 0）。三者都没有的调用记 `missing_delta=1` 并照样进入分母。
2. **TTFT 不是 prefill，`e2e − ttft` 也不是 GPU decode。** 没有引擎阶段事件时，客户端只观测到「请求发出 → 首个 delta」与「首个 delta → 流结束」。后者含服务端排队、逐 token 解码、客户端调度与 SSE 分帧，本实验把它记作 `stream_tail_ms`，不折算成 GPU 时间。本次 `stream_tail_ms` p50 179.6 ms、p95 2 383.4 ms——p95 已经是 p50 的 13 倍，把它当 decode 会得出完全错误的阶段账。
3. **到达与准入解耦。** 到达时刻先在独立循环里按绝对时钟打点落盘，任务随后才竞争 `asyncio.Semaphore`。因此注入慢工具或队列拥塞后，全部逻辑到达仍然在记录里（本次慢工具档 `all_arrivals_recorded=true`）。
4. **工具分两批执行。** 只读工具（`calculate`/`search_corpus`/`list_files`/`read_file`）同轮并行（fork），有副作用的工具（`write_file`/`edit_file`/`run_tests`）按模型给出的顺序串行；回填进上下文的消息顺序始终按模型调用顺序（join），所以后续轮次的输入仍然可复现。本次 300 个会话里只有 2 个出现同轮并行只读工具——这个负载的图深度主要来自轮次串行，不来自工具扇出，不能按「多 agent 并行」去理解它。

### 2. 轮次与长度的联合分布

一次采集：3×100 个会话，1 372 次模型调用，共 66.4 s 墙钟（并发 16，`--max-turns 12`）。

| 任务类 | 会话 | 得分 | 轮次均值 | p50 | p90 | 触顶(12) | 每轮 prompt p50 | 每轮输出 p50 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| compute | 100 | 0.98 | 2.02 | 2 | 2 | — | 330 | 261 |
| retrieval | 100 | 0.43 | 2.58 | 2 | 4 | — | 914 | 26 |
| codefix | 100 | 0.35 | 9.12 | 8 | 12 | 37 | 1 946 | 23 |

四个直接可用的结论：

1. **轮次不是常数。** `codefix` 的轮次从 5 到 12 全谱分布，p50 8、均值 9.12；37% 的会话把 12 轮预算用完仍没修好。把「agent 请求」当成固定 3 轮的模板，会同时低估长尾和缓存价值。
2. **输出长度与轮次无关，prompt 长度与轮次强相关。** `codefix` 每轮输出 p50 只有 23 token（几乎全是工具调用与一句结论），但 prompt 从 721 涨到 4 940（p0→p100）。这类负载的成本在 prefill，不在 decode。
3. **首轮输出长度不能预测会话长度。** `codefix` 的首轮输出恒为 16 token（一次 `list_files()` 调用），方差为 0，与总会话轮次的相关系数无法定义（实测 `None`）；`compute` 的首轮输出与轮次相关系数 0.37，`retrieval` 只有 0.14。用「第一个回答多长」来预判任务规模没有依据。
4. **thinking 会改变输出的性质。** `compute` 类开启 thinking：输出 p50 261 token，其中 reasoning token p50 233——**89% 的输出花在思考上**；同一个模型在另外两类关闭 thinking 后，reasoning token 恒为 0。

### 3. 前缀命中：多轮负载里最值钱的一项

同一批轨迹里的前缀命中（引擎自报）：

| 任务类 | 命中率均值 | 命中率 p50 | 每轮命中 token 均值 | 每轮 prompt token 均值 | 相邻轮字符前缀占比均值 |
|---|---:|---:|---:|---:|---:|
| compute | 0.835 | 0.835 | 276 | 331 | 0.448 |
| retrieval | 0.613 | 0.608 | 486 | 845 | 0.176 |
| codefix | 0.851 | 0.876 | 1 719 | 1 987 | 0.701 |

`codefix` 的命中率最高，因为它的每一轮都在上一轮的基础上追加，会话内前缀几乎完全保留；`retrieval` 命中率最低，因为工具结果被插到 prompt 中段时，后续文本对不齐，前缀到此断裂——这与 5.2 的结论一致：**前缀复用的前提是「从头开始逐字相同」，中段注入不改变这一点，但它把共同前缀截短了。**

`corr_cached_vs_prompt` 给出这三类的相关强度：compute 0.889、retrieval 0.864、codefix 0.977。**prompt 越长，能命中的绝对量越大**——因为长 prompt 来自更长的历史，而历史正是可复用的部分。这条相关性是「会话亲和」在实际系统里值钱的原因，也是 9.3 整章要算的账。

### 4. 块粒度的命中模型：4 个已知条件就够了

前缀命中不是黑箱。vLLM v1 的规则可以完整写下来：

1. 缓存以**块**为单位，默认块大小 16 token（`vllm/config/cache.py:79` `DEFAULT_BLOCK_SIZE: ClassVar[int] = 16`，未显式指定时在 `:317` 取默认值）；
2. 只有**满块**参与哈希，且哈希链住父块（`vllm/v1/core/kv_cache_utils.py:621` `hash_block_tokens(hash_function, parent_block_hash, curr_block_token_ids, extra_keys)`），所以命中是从第 0 块起的一段连续深度；
3. 查询命中时返回 `(blocks, num_computed_tokens, shared_prefix_boundary)`（`vllm/v1/core/kv_cache_manager.py:228` `get_computed_blocks`）；
4. 缓存有容量上限。本实验的引擎自报 `GPU KV cache size: 41,008 tokens`（`--gpu-memory-utilization 0.45`，Qwen3-4B bf16），41 008 = 2 563 × 16，正好是 2 563 个块；同一条日志还给出 `Maximum concurrency for 8,192 tokens per request: 5.01x`。

把 1–4 写成一个 Python LRU（`labs/L9/mini_prefix_accounting.py`，见下面「mini 实现」），在**真实到达顺序**上逐请求预测 `cached_tokens`，再与引擎自报值逐条对拍：

| 变体 | 命中量精确相等 | 相差 ≤1 块 | 预测命中总量 | 引擎命中总量 |
|---|---:|---:|---:|---:|
| 按块 LRU，容量 2 563 块 | 1 363 / 1 372（99.34%） | 1 368（99.71%） | 1 741 744 | 1 741 536 |
| 按块前缀，容量无限 | 1 337 / 1 372（97.45%） | 1 347（98.18%） | 1 741 744 | 1 741 536 |

分任务类看总量（容量 2 563 块）：`retrieval` 预测 121 664 对引擎 121 664（逐条全中）；`codefix` 1 564 192 对 1 564 032（+160 token，0.01%）；`compute` 55 888 对 55 840（+48 token，0.09%）。

两件事同时被验证：

- **容量是真的在起作用。** 把容量限制去掉，`delta_min` 从 −32 掉到 −432，也就是说有请求本来能命中更深的块，但因为缓存被别的会话挤掉而没有命中。**「命中率」不是模型属性，是「前缀结构 × 容量 × 并发」三者共同的结果。** 这与 5.2 的块哈希是同一机制，只是在 agent 负载下容量压力显著更大：本实验的 KV 容量按 8 192 上下文只够 5 个并发请求。
- **剩下的 9 条不一致是块对齐与共享前缀边界的效应**，最大偏差 2 块；这正是 `get_computed_blocks` 里 `shared_prefix_boundary` 要处理的情形（密集 attention 的命中深度与稀疏保留组可能不一致）。

**渲染口径要写清楚。** 用 `apply_chat_template(messages, tools=..., add_generation_prompt=True)` 重新分词，只有 14.4%（198/1 372）与引擎 `prompt_tokens` 完全相同，其余主要是**恒定差 4 token**（337/400 的样本），另有 7 条差 23。恒定偏移只整体平移块边界，不改变命中深度，所以上表仍能对到 99.3%；但要做 token 级精确对拍，必须用引擎自己的分词路径，不能拿本地渲染直接当输入。

### 5. 工具等待在时间轴上占多少

工具是本地执行（计算器、BM25、文件操作），但它们的等待时间在会话时间轴上的位置决定了「并发请求数」怎么变化：

| 任务类 | 工具等待 p50 | p90 | p99 | 每轮平均模型时间 | 工具/模型 |
|---|---:|---:|---:|---:|---:|
| compute | 0.03 ms | 0.04 ms | 0.05 ms | 2 788 ms | ~0 |
| retrieval | 4.1 ms | 7.3 ms | 9.7 ms | 116 ms | 3.5% |
| codefix | 0.18 ms | 21.3 ms | 27.0 ms | 143 ms | 0.1%（p90 达 15%） |

三类任务的工具都不重，但含义不同：

- `compute` 的工具等待完全可忽略，但它**拉长了会话**：一次工具调用把「一次长输出」切成两段 prefill + 两段 decode，第二段还要重放第一段全部上下文（命中 83.5%）。
- `retrieval` 的工具是 BM25，p50 4.1 ms、p99 9.7 ms，占单轮模型时间的 3.5%；它把 43% 的会话延长到 3 轮以上。
- `codefix` 的 `run_tests` 是子进程 + 解释器启动，p90 21.3 ms，均值被少数长尾拉高；**在 12 轮预算里它出现 2–3 次，是会话墙钟里除模型之外最大的一项**。

结论不是「工具很慢」，而是：**工具等待不占 GPU，却占会话时间**。它把同一会话的请求在时间上摊开，从而改变缓存驻留：等待越长的会话，其中间状态越容易被其他会话挤出缓存——这正是 9.3 里「轮间等待 = 0/1/10/60 s」实验要量化的东西。

### 6. 合成负载：均值匹配与分布匹配差在哪

「合成一个 agent 负载」常见的做法是抽长度分布：轮次按均值抽、prompt 按均值抽、输出按均值抽，然后独立拼成会话。这批真实轨迹可以直接检验这种做法的代价——两种合成都用**同一批真实请求**，各轮边际完全相同，唯一差别是会话内联合结构：

| 方案 | 构造方式 | 请求数 | 相邻轮字符前缀占比(均值/p50) | 连续轮公共字符 p50 |
|---|---|---:|---:|---:|
| `session` | 整会话有放回重采样 | 1 268 | 0.547 / 0.724 | 2 495 |
| `independent` | 同一批轮次请求按轮打散重排 | 1 372 | 0.103 / 0.052 | 346 |

在线重放（同一引擎、并发 16、同一 max_tokens、`--max-num-seqs 64`）的结果见下表；几行的唯一区别是请求之间的**配对关系**：

| 方案 | 缓存命中率均值 | TTFT p50 | TTFT p95 | 墙钟 | 吞吐 |
|---|---:|---:|---:|---:|---:|
| `original`（原轨迹顺序） | 0.805 | 1 763.8 ms | 4 062.0 ms | 64.4 s | 21.3 req/s |
| `session`（整会话重采样） | 0.816 | 1 649.6 ms | 3 972.5 ms | 64.7 s | 19.6 req/s |
| `independent`（按轮打散） | 0.588 | 1 672.7 ms | 6 343.2 ms | 107.1 s | 12.8 req/s |

（prompt token 总量：`original` 与 `independent` 都是 2 096 928，`session` 1 792 063；`session` 因重采样出的会话长度不同，请求数少 7.6%，所以对比看的是比率与分位数，不是总量。）

结论可以说得很硬：**边际分布相同、联合结构不同，p95 TTFT 涨 1.56 倍、吞吐掉 40%、缓存命中率差 22 个百分点。** 独立抽样长度再拼成会话，产生的请求清单在 token 总量上与真实负载一致，在服务行为上不是同一个负载。这是 9.1 对后面五章最重要的一条约束：**比较优化方案时，负载的联合结构必须一起固定。**

`session` 与 `original` 几乎重合（命中率 0.816 对 0.805、吞吐 19.6 对 21.3），说明整会话有放回重采样是足够好的近似——它保留了会话内前缀链，代价只是复制了部分会话并让「热门会话」多出现几次。

**惩罚的幅度取决于调度配置，方向不变。** 同一台机器换 `--max-num-seqs 8` 再跑一遍：`original` 13.6 req/s、TTFT p95 3 912.9 ms，`independent` 10.4 req/s、TTFT p95 5 478.4 ms——吞吐差从 40% 缩到 23%，p95 差从 1.56 倍缩到 1.40 倍。批得越小，队列本身越长，负载结构造成的差异被排队噪声淹没一部分；**报这类结论必须同时给出调度配置。**

### 7. 重放一致性：请求能重放，到达过程不能

把原轨迹的 1 372 条请求原样送回同一引擎（`replay-original-c16`），与采集时逐条对比：

| 指标 | 采集（原轨迹） | 重放 | 说明 |
|---|---:|---:|---|
| prompt token 精确相同 | — | 1 372 / 1 372 | 连同 tools schema 一起重放，渲染完全一致 |
| `cached_tokens` p50 / p90 | 896 / 2 720 | 896 / 2 720 | 命中量分位完全一致 |
| `cached_tokens` 均值 | 1 269.3 | 1 270.1 | 差 0.06% |
| 输出 token p50 / 均值 | 23 / 61.8 | 23 / 61.6 | 贪心解码下分布吻合 |
| TTFT p50 | 143.7 ms | 1 763.8 ms | **差 12 倍** |

**请求本身可重放，服务时延不可重放。** 原因是采集时每个会话在轮次之间要等工具执行（客户端本地算完才发下一轮），GPU 在这段时间是空的；重放把 1 372 条请求按并发 16 连续打出去，队列结构完全不同。这条对后面几章都是硬约束：**要还原真实服务的排队行为，必须把工具执行时间一起重放**（9.5 的运行时要把这段等待建模成有状态的服务步骤），只重放请求清单只能还原 token 账与缓存账。

四条结论：

1. **4B 模型在 BFCL 多轮上的绝对水平很低（8%），但这正是基准存在的意义。** 关键不在这个数，而在于它是**同一套公开题、官方评分器与官方环境**下得到的，可与公开榜单对照；本项目自造的教学任务不能替代它。
2. **失败的主力是状态不一致（25/46），而不是格式错误。** 模型经常能发出语法正确的调用（213 次调用几乎没有解析失败），但**顺序与前置条件**出错——对照第 1 节的例子：任务要求先 `cd` 进目录再 `mkdir`，模型直接 `mkdir`，于是后续所有状态都偏了。**多轮任务的失败是"链式"的：一个前置动作错了，后面每一步都在错的状态上执行。**
3. **`execution_response_mismatch` 与 `instance_state_mismatch` 必须分开报。** 前者说明模型走到了正确的状态但调用方式与标准答案不同（例如用不同的参数顺序完成了同一件事），后者说明状态本身就错了。只看一个总数会把"能做事但不符合参考实现"和"根本没做对"混为一谈。
4. **公开题的负载形状与教学任务不同。** 这里平均 3.18 轮、每轮中位 1 次调用、单次会话 prompt 累计约 20k token（1 028 430 / 50）；而教学任务里的 codefix 会话可以长到 12 轮。**"轮次少、每轮调用少"的公开题不能代表 agent 的真实负载形状**，两者的分布要分别报（本节与第 2 节的分布并列，不做合并）。

两个流程性结论也记下来：

* **BFCL 的数据随 wheel 一起分发**（15 MB 包内含题目、标准答案与工具文档），**不需要访问 Hub**。本机 pip 默认镜像里没有该包，必须显式 `--index-url https://pypi.org/simple`；依赖装不全时 `bfcl_eval` 的导入会在 `tree_sitter`（需 `==0.21.3`，新版 API 不兼容）或 `filelock`/`mpmath` 处失败——**这些缺件会让部分题目"执行失败"，如果只看准确率会把它误读成模型不会做**（本轮首次运行时 11 题因缺 `mpmath` 而执行失败，装上后才得到干净结果）。
* **`TwitterAPI` 的工具文档文件名是 `posting_api.json`**，类名到文件名不是大小写变换，必须用 BFCL 自己的 `MULTI_TURN_FUNC_DOC_FILE_MAPPING`。

## 工程实现：一次 agent 请求在 vLLM 里经过什么

### 源码解析：从消息到 `cached_tokens`

**第一步：模板与工具。** 客户端发来 `messages` + `tools`，服务端用模型自己的 chat template 渲染成 prompt，工具 schema 进入模板（Qwen3 的 Hermes 风格 tool 段落）。工具调用在输出侧由工具解析器还原：`vllm/tool_parsers/hermes_tool_parser.py:70` `extract_tool_calls` 做一次性解析，`:204` `extract_tool_calls_streaming` 做增量解析。`compute` 类的 thinking 由 `vllm/reasoning/qwen3_engine_reasoning_parser.py` 从输出中分离，与最终回答分开返回。

**思考文本的 SSE 字段是 `reasoning`，不是 `reasoning_content`。** 服务端 `vllm/entrypoints/openai/chat_completion/protocol.py:71` 声明 `reasoning: str | None = None`，`:530-531` 的注释写明「Renames the deprecated `reasoning_content` field to `reasoning` so downstream code only needs to check one field」，`:544-546` 的兼容代码只处理**请求侧**输入的旧字段。原始字节里 `delta` 的键是 `["content", "reasoning", "role", "tool_calls"]`，`reasoning_content` 不出现。

客户端按 `reasoning_content` 取名不会报错，只会拿到恒为 `None` 的思考文本：同一批 `usage` 里 `reasoning_tokens` 非零（`compute` 类合计 51 251 个），而按字符累计的思考长度是 0。采集器因此同时读两种拼法，并把命中的那个写进 `reasoning_field`（本次 201 次全部命中 `reasoning`），让「读了一个不存在的字段」变成可检查的字段而不是静默的零。


**第二步：前缀查询。** 调度前，`KVCacheManager.get_computed_blocks`（`vllm/v1/core/kv_cache_manager.py:228`）返回复用块、已算 token 数与共享前缀边界。命中量按块计，块哈希是 `(父块哈希, 本块 token)` 的链式哈希（`vllm/v1/core/kv_cache_utils.py:621`）。

**第三步：计数与上报。** prefill 结束后，引擎把本次 prefill 的统计写进请求状态：`vllm/v1/engine/output_processor.py:676` 处 `req_state.num_cached_tokens = engine_core_output.prefill_stats.num_cached_tokens`。HTTP 层把它装进 `prompt_tokens_details`：`vllm/entrypoints/openai/chat_completion/serving.py:92` 的 `_make_prompt_tokens_details` 组装，`:527` 从引擎结果取值，`:1138` 写进最终 usage。

```python
# vllm/entrypoints/openai/chat_completion/serving.py:100-107（节选）
    if not enable_prompt_tokens_details:
        return None
    ...
    return PromptTokenUsageInfo(
        cached_tokens=num_cached_tokens,
        created_cache_tokens=num_cache_creation_tokens,
        multimodal_tokens=mm_token_counts or None,
    )
```

**`prompt_tokens_details` 默认不返回。** 本次采集在服务端显式开启 `--enable-prompt-tokens-details`；不开启时 `cached_tokens` 为 `None`。第一次 smoke 测试就踩到这个：事件里 47 条 `cached_tokens` 全是 `null`，看起来像「没有命中」，实际是字段没开。**把「字段缺失」读成「命中为零」会让整章的结论反过来。**

**第四步：指标。** 引擎侧同时有 Prometheus 计数 `vllm:prefix_cache_queries` / `vllm:prefix_cache_hits`（`vllm/v1/metrics/loggers.py:584`、`:595`），并在 `:212` 处按调度统计刷新 `prefix_caching_metrics`。它们是跨请求聚合口径；本实验逐请求的账走 usage，两者不要混用。

### 设计取舍

- **逐请求记账 vs 引擎聚合指标。** 逐请求的 `cached_tokens` 能算出「哪一类任务命中多少、第几轮开始命中」，代价是每个请求多一次 usage 解析；聚合指标便宜，但会把长尾抹平。9.1 需要分布，所以选前者。
- **端到端墙钟 vs 分段计时。** 工具等待与模型时间必须分开，否则「agent 慢」会被错误归因到模型。本实验把 `tool_wait_ms` 记在事件里；模型侧只报客户端观测到的三个首输出时刻与 `stream_tail_ms`，**不把 `e2e_ms − ttft_ms` 当 GPU decode**——它含排队、逐 token 解码与 SSE 分帧，没有引擎阶段事件时无法拆开，只能用 `cached_tokens` 与 prompt 长度解释方向。
- **流式 vs 非流式。** 只有流式才能测 TTFT，也才能看到工具调用参数是逐步到达的（9.2 要用）。代价是要自己拼增量、处理空 delta。
- **工具在客户端执行。** 这让 harness 必须自己维护会话状态与重试；好处是每个工具调用都可记录、可替换（9.5 会把它升级成带 deadline 与幂等账本的运行时）。

## 工程实现：mini 实现——按块预测前缀命中

下面这段是 `labs/L9/mini_prefix_accounting.py` 的核心。它只依赖上面 4 条规则，就能把每个请求的命中量预测到 99.3% 精确：

```python
class BlockCache:
    """按块计价的 LRU 前缀缓存；键是 (父块哈希, 本块 token 元组)。"""

    def __init__(self, block_size, capacity_blocks):
        self.block_size = block_size
        self.capacity = capacity_blocks
        self.alive = OrderedDict()

    def lookup_and_insert(self, tokens):
        n_full = len(tokens) // self.block_size
        parent, hit_blocks = None, 0
        for b in range(n_full):                      # 从第 0 块起连续命中
            block = tuple(tokens[b * self.block_size:(b + 1) * self.block_size])
            key = (parent, block)
            if key not in self.alive:
                break
            hit_blocks += 1
            self.alive.move_to_end(key)
            parent = key
        parent = None
        for b in range(n_full):                      # prefill 后填充缓存
            block = tuple(tokens[b * self.block_size:(b + 1) * self.block_size])
            key = (parent, block)
            if key in self.alive:
                self.alive.move_to_end(key)
            else:
                self.alive[key] = None
            parent = key
        while len(self.alive) > self.capacity:       # 容量外的 LRU 驱逐
            self.alive.popitem(last=False)
        return hit_blocks * self.block_size
```

三点实现说明：

1. **不满一块的尾部永远命不中**：`n_full = len(tokens) // block_size`。这就是「命中量总是 16 的倍数」的原因，也是 9.3 里判断「多轮之间能不能接上」的第一道门槛。
2. **键必须包含父块哈希**：只哈希块内容会让不同位置上的相同块错误共享，这与 5.2 的块哈希契约一致。
3. **容量口径是上界**：真实引擎还要区分「被运行中请求占用」与「可驱逐」，本模型不区分，所以预测只会偏乐观——表里 `delta_min = -432` 的无限容量变体正是这个偏乐观的极端。

## 前沿

**Agent 负载的测量已经从「平均轮次」转向「会话状态的可复用性」。** 本章的实测显示：同一批请求，只把会话内配对关系打散，p95 TTFT 就涨 1.56 倍、吞吐掉 40%。这说明在 agent 场景下，**负载生成器（load generator）本身就是一个需要被验证的组件**——一个均值正确的合成器可以给出完全错误的 SLO 结论。

**缓存账正在从「命中率」转向「命中深度 × 容量 × 亲和」。** 现代引擎（vLLM v1 的块哈希、SGLang 的 radix tree、LMCache 的多级存储）都把前缀复用做成了跨请求的一等公民。本章的对拍表明：只要知道块大小、链式哈希与容量，命中量就是可以逐条预测的——这意味着服务容量规划可以从「测出来的经验曲线」变成「可计算的账」，9.3 与 9.6 都在这个方向上前进一步。

**长思维链把输出侧重新变重。** 本章里 `compute` 类 89% 的输出是 thinking，9.4 会把这个比例当成变量：预算、并发和状态架构共同决定「每个正确答案的成本」。这也是 agent 负载与经典 chat 负载的分水岭——前者的输入几乎全部可复用，后者不一定。

## 陷阱

1. **把字段缺失读成命中为零。** 不开 `--enable-prompt-tokens-details` 时 `cached_tokens` 是 `null`，不是 0。
2. **用平均轮次代替轮次分布。** `codefix` 均值 9.12，但 37% 在 12 轮触顶；截断的会话会在均值里消失，看起来像「任务都完成了」。
3. **把失败会话从统计里删掉。** 本章 `retrieval` 成功率 0.43、`codefix` 0.35；删掉失败会话后，平均轮次、平均长度、缓存命中率会全部上移，得到的是「成功的任务」而不是「这个负载」。
4. **用均值匹配的合成负载做 SLO 结论。** 边际相同、联合不同的两份清单，p95 TTFT 从 4 062 ms 涨到 6 343 ms、吞吐掉 40%。
5. **假设所有轮次的前缀都能命中。** 命中量永远是块大小的整数倍，且受容量与跨会话竞争限制；本实验的 KV 容量按 8 192 上下文只够 5 个并发请求。
6. **把工具等待归因给模型。** `codefix` 的 `run_tests` p90 是 21 ms 的子进程时间，它不出现在 GPU 上，但出现在会话墙钟里。
7. **用首轮输出长度预测任务规模。** `codefix` 首轮输出恒为 16 token，方差为零。
8. **把 `prompt_tokens` 当成本章模型的输入。** 本地渲染与引擎渲染差一个恒定 4 token 的偏移，token 级对拍必须用引擎路径。
9. **把命中率当成可迁移的模型属性。** 换容量、换并发、换路由策略，命中率都会变；`router.json` 里单引擎 0.831、会话亲和 0.773、最少负载 0.165、轮转 0 是同一批请求的四种结果。
10. **一次会话代表总体。** 本章每条结论都基于 100 会话/类；单会话的时间线只能用来解释机制。
11. **按字段名猜服务端 schema。** vLLM 0.29.0 的思考文本在 SSE 的 `delta.reasoning` 里，`reasoning_content` 是已弃用的旧名（只在请求侧兼容）。读错名字不会报错，只会让 `reasoning_chars` 恒为 0；接入新引擎或新版本时必须先用原始字节审计字段。
12. **把客户端观测的时间当引擎阶段时间。** `ttft_ms` 与 `e2e_ms − ttft_ms` 都含排队与 SSE 分帧；没有引擎阶段事件时它们只能解释方向。本章 `stream_tail_ms` p95 是 p50 的 13 倍，把差值当 decode 会得出完全错误的阶段账。
13. **用请求级重放给「新策略的闭环成功率」打分。** 依赖驱动重放固定了请求内容，只能做系统变量对照；推理策略改变轨迹后必须重新执行任务并重新评分。

## 自测题

1. 为什么 `codefix` 的缓存命中率（0.851）高于 `retrieval`（0.613）？
2. 命中量为什么总是 16 的倍数？在什么情况下会看到不是 16 的倍数的 `cached_tokens`？
3. 本章的按块预测器为什么在「无限容量」下反而对得更差？
4. 工具等待不占 GPU，为什么它会影响缓存命中率？
5. 一份合成负载的各轮长度均值与真实负载完全相同，为什么 p95 TTFT 会从 4.1 s 涨到 6.3 s？
6. `compute` 类的 TTFT 达到 2.8 s，能说「thinking 让 prefill 变慢」吗？

::: fold 答案

1. `codefix` 每一轮都在上一轮文本尾部追加，会话内前缀几乎完整保留（相邻轮字符前缀占比 0.701）；`retrieval` 把检索结果插进 prompt，共同前缀被截到注入点之前（0.176）。
2. 因为 vLLM v1 只对**满块**做哈希与复用（`kv_cache_utils.py:621` 要求满块，默认块 16 token）。看到非 16 倍数的值，说明统计口径不同：例如开启 KV connector 时本地命中与外部搬运的记账方式不同，或不同引擎的块大小/口径不同（本篇实验里 `cached_tokens` 全部是 16 的倍数）。
3. 无限容量时模型认为「前几天出现过的块都还在」，但真实引擎的 2 563 块容量早就把它们驱逐了；容量受限的模型反而更接近真实。这说明容量不是可忽略的细节，`delta_min` 从 −32 掉到 −432 就是被高估的那部分。
4. 等待把同一会话的相邻轮次在时间上拉开，中间这段时间里其他会话会占用缓存块，触发 LRU 驱逐；会话的中间前缀因此可能在下一轮到来前就没了。等待越长、并发越高，损失越大。
5. 独立抽样破坏了会话内的前缀链：同一会话的相邻轮次不再共享长前缀，缓存命中率从 0.805 掉到 0.588，prefill 量上升，排队变长，p95 TTFT 从 4 062 ms 涨到 6 343 ms、吞吐从 21.3 掉到 12.8 req/s。边际相同只保证了「一共多少 token」，不保证「这些 token 怎么排列」。
6. 不能。那次会话的 prompt 只有 293/332 token，TTFT 的主要成分是并发 16 下的排队（同批次里 `codefix` 的长 prefill 在跑）。要归因给 thinking，需要单请求、固定并发的对照，这正是 9.4-B 的做法。
