## 本章回答三个问题

工具执行环境决定「代码在哪里跑、能碰什么、出错后留下什么」。它与 L8 的模型 worker 是两套资源：

1. 目录、进程、容器、gVisor 与 microVM 分别隔离什么？
2. 冷启动、预热池与快照如何影响启动时间与常驻成本？
3. 取消、崩溃与复用之后，怎样**证明**进程与任务状态已经回收？

## 机制拆解与推导

### 1. 先核验：这台机器能提供哪几层

隔离不是配置项，而是内核与权限的函数。同一份实验代码在三种环境下能做的完全不同，所以第一步是**把可用原语问清楚**（`labs/L9/sandbox_capability_probe.py`）：

| 能力 | 本机结果 | 判定依据 |
|---|---|---|
| capabilities | `CapEff = CapPrm = CapBnd = 0x00000000a80465fb`，**无 `CAP_SYS_ADMIN` / `CAP_SYS_RESOURCE`** | `capsh --print` 逐项对照 |
| seccomp | `Seccomp: 0`（无过滤器） | 限制来自 capabilities，不来自 seccomp |
| cgroup v2 | 已挂载（含 `cpu memory pids` controller），但 `/sys/fs/cgroup` **只读** | 建目录返回 `Read-only file system` |
| PID / mount 命名空间 | **不可创建** | `unshare --pid` 返回 `Operation not permitted` |
| user / net / uts / ipc 命名空间 | **可创建** | `unshare --user --map-root-user` 后 `id -u` = 0；netns 里只有 `lo` |
| rlimit | `RLIMIT_AS` / `RLIMIT_FSIZE` / `RLIMIT_CPU` **被强制执行** | 见第 4 节的注入结果 |
| 进程数限制 | `RLIMIT_NPROC` **未被强制执行**（限 4 仍 fork 出 8 个子进程） | 同一子进程内的实测 |
| 容器 / gVisor / microVM | docker、podman、runc、crun、bwrap、runsc、firecracker **均未安装**；`/dev/kvm` 不存在 | `shutil.which` 与 `/dev/kvm` |

**这张表就是本章的验收范围声明**：进程组、rlimit、user/net 命名空间与工作区快照可以在本机实测；容器隔离、cgroup 限制、gVisor 与 microVM 只做源码与生命周期分析，标 `UNVERIFIED`（补测条件：可写 cgroup + 容器运行时 + `/dev/kvm`）。把边界先写死，比事后解释"为什么没测容器"有用得多。

一个容易混淆的点：`Seccomp: 0` 让人误以为"没有限制"，实际限制全部来自 capabilities。**判断一个环境能做什么，要看 `CapEff` 而不是看有没有 seccomp 过滤器。**

### 2. 状态机：为什么 READY 必须经过健康探测

池的状态机只有六个状态，但每个迁移都有可观测的判据：

```text
NEW ──► STARTING ──► READY ──► BUSY ──► DRAINING ──► DESTROYED
                        ▲        │            │
                        └────────┘            └──► READY（探测通过）
```

* `STARTING`：建工作区、写工具源码与输入（实测仅 **0.05 ms**——真正贵的是解释器与依赖启动）；
* `READY`：**必须跑通一条最短命令**才算就绪。进程存活不代表可执行：解释器缺失、动态库找不到、工作区权限不对，进程都不会"死"，但工具跑不起来；
* `BUSY`：一次任务占用一个槽位，带租约与 fencing token；
* `DRAINING`：回收子进程、清工作区，**再次探测**；通过才回 `READY`，否则 `DESTROYED`。

Python 版实测一条完整迁移链（`pool.json` 的 `state_transitions`）：`NEW→STARTING→READY→BUSY→DRAINING→READY` 循环四次，四个任务全部回到 `READY`，`running_after=0`。

### 3. 有界池与预热：省下的是哪一段

预热槽位 `warm ∈ {0,1,4}` × 并发 `∈ {1,4,16}`，每格 12 个任务，`max_slots=4`（`labs/L9/sandbox_lifecycle_bench.py`）：

| 配置 | 首次申请→首个结果 p50 | 命中路径排队 p50 | 冷启动路径排队 p50（miss 数） | 预热耗时 | 溢出未获槽 |
|---|---:|---:|---:|---:|---:|
| warm=0 c=1 | 71.7 ms | 0.008 ms | **64.5 ms**（1） | — | 0 |
| warm=0 c=4 | 76.1 ms | 0.005 ms | **57.9 ms**（4） | — | 0 |
| warm=0 c=16 | 72.3 ms | — | 59.4 ms（4） | — | **8** |
| warm=1 c=1 | 75.4 ms | 0.008 ms | —（0） | 66.9 ms | 0 |
| warm=1 c=4 | 74.8 ms | 0.005 ms | 62.6 ms（3） | 63.4 ms | 0 |
| warm=4 c=4 | 73.1 ms | 0.004 ms | —（0） | 224.1 ms | 0 |
| warm=4 c=16 | 76.9 ms | 0.005 ms | —（0） | 249.5 ms | **8** |

四条结论：

1. **预热带走的是"槽位启动"这段固定成本。** 冷启动路径的排队 p50 是 57.9–64.5 ms，命中路径只有 0.005–0.008 ms。`warm=4` 时 c=1/c=4 两格的 miss 数都归零，那 60 ms 被移出任务路径；代价是启动时先付 224–250 ms。
2. **单次「申请→首个结果」p50 稳定在 71–77 ms，与预热无关。** 分解（`warm=4 c=1`）：依赖复制 1.4 ms、依赖装载 9.7 ms、工具子进程 64.5 ms。**当任务本身就要 60 ms 时，池化省下的 60 ms 只在第一次出现**；预热的收益随任务数摊薄，只有高频短任务才把它变成持续收益。
3. **`max_slots` 是硬上界，溢出直接拒绝而不是排队。** c=16 时 8 个任务拿到 `acquired=false`（`not_acquired=8`），池内槽位数始终 ≤ 4。拒绝还是排队是策略选择：拒绝把压力推给上层任务调度（9.7），排队则把等待藏在池里、让超时更难归因。
4. **就绪槽位的常驻占用可以量。** 工作区 8 MiB（依赖 payload）+ 工具源码；RSS 在就绪态为 0（槽位不保留常驻进程，只在 `BUSY` 时拉起）。**"池化"不等于"常驻进程池"**：本实现常驻的是目录与元数据，进程按任务起停。

### 4. 资源限制：四种注入，各自的证据

`labs/L9/sandbox_failure_cases.py` 逐个注入，每个用例都给回收证据而不只报失败：

| 注入 | 观测 | 证据 |
|---|---|---|
| 输出 4 MiB，上限 64 KiB | `truncated=true`，保留 65 536 B | 父进程 RSS 只涨 936 KiB（上限 64 KiB 的结果被真正截断，不是攒在内存里） |
| 申请 900 MiB，`RLIMIT_AS` 512 MiB | `exit_reason=as_limit`，退出码 1 | 子进程 `MemoryError` traceback；宿主不受影响 |
| 写 8 MiB，`RLIMIT_FSIZE` 2 MiB | `exit_reason=fsize_limit` | 文件停在 2 097 152 B（正好一个块边界），且被工作区回收清掉 |
| 派生 3 个子进程后卡住，取消 | `group_peak=4`，`running_after=0` | 进程组存活数回零 |
| 子进程 `setsid` 逃逸后取消 | **逃逸进程仍在 `S` 状态** | 反例：按进程组回收抓不到它 |
| `sleep 60`，wall-time 3 s | `exit_reason=wall_timeout`，实测 3 272 ms | 整组回收、槽位回到 `READY` |
| 租约 1 s，持有 1.4 s | `expired=true`，槽位 `DESTROYED` | 过期租约的槽位不复用 |

三条实现上的硬要求：

1. **必须用非阻塞读。** 第一版实现用 `proc.stdout.read(4096)` 收输出，结果一个 `sleep 60` 的工具跑满 **60 022 ms** 才结束——`read` 阻塞时 wall-time 检查永远轮不到。改成 `selectors` + `os.set_blocking` 之后，同一个工具在 3 272 ms 被整组杀掉。**"超时没生效"最常见的成因不是超时算错，而是主循环被一次阻塞读卡住。**
2. **进程数限制不能依赖 `RLIMIT_NPROC`。** 本机实测限 4 仍 fork 出 8 个；`RLIMIT_NPROC` 的判定与 uid 的全局进程数、capabilities 相关。可用做法是监督进程组存活成员数（本 lab 的做法：遍历 `/proc/*/stat` 的 pgrp 字段），超限即整组回收；更可靠的做法是 cgroup v2 的 `pids.max`——本机 cgroup 只读，该路径 `UNVERIFIED`。
3. **`killpg` 只覆盖同一进程组。** 只要工具派生的子进程调用 `setsid` 就会脱离进程组，`killpg` 之后它照常运行。要覆盖这种情况必须按进程树追踪（父链递归）或给每个任务打标记（如独立 cgroup、独立 user 命名空间），并在回收后复核。

### 5. 输出上限与「stdout 截断不等于进程终止」

输出截断解决的是**运行时内存**，不是**工具行为**：4 MiB 输出的工具在我们的实现里被读干后正常退出（`exit_reason=ok`）。如果一个工具无限输出，截断只保证父进程不被撑爆，工具本身仍要由 wall-time 或输出字节数阈值终止。两条独立机制缺一不可：

* 上限（本 lab 64 KiB）保护**监督进程的 RSS**；
* wall-time（本 lab 3 s）终止**工具本身**。

把两者混为一谈，就会出现"内存没炸但任务永远不结束"或者"任务结束了但内存已经炸了"。

### 6. 复用环境时先重置状态

槽位回 `READY` 之前经过 `DRAINING`：杀进程组 → 清工作区（保留工具源码）→ 重新健康探测。实测每次 `reclaim_removed` 包含 `blob.bin`、`input.json` 等本次任务的产物，`remaining` 只剩 `tool.py`。**复用不是"什么都没做"**：如果不清工作区，上一个任务写的文件会被下一个任务读到，这类串号在 `read_file` / `search_corpus` 一类工具上不会报错，只会给出错误答案。

## 工程实现：源码解析

### OpenHands 的 Docker 工作区：容器版的状态机

`software-agent-sdk` 的 `openhands-workspace/openhands/workspace/docker/workspace.py` 提供了容器路线的一个完整实现，可以逐项对照本章的池：

| 位置 | 机制 | 对照 |
|---|---|---|
| `DockerWorkspace(RemoteWorkspace)` | 字段 `working_dir="/workspace"`、`server_image`、`host_port`、`volumes`、`platform="linux/amd64"`、`enable_gpu`、`network`、`health_check_timeout=120.0` | 本章池的「工作区 + 上界 + 超时」三个字段同构 |
| `find_available_tcp_port(min_port=30000, max_port=39999, max_attempts=50)` | 随机探测可用端口 | 池化必须解决「端口/路径等命名资源」的并发分配 |
| `_start_container()` | `docker version` 预检 → 组装 `-e`（`forward_env`）、`-v`（`volumes`）、`-p`、`--gpus all`、`--network` → `docker run -d --rm --ulimit nofile=65536:65536 --name agent-server-<uuid>` | **唯一的资源限制是 `nofile`**：内存、CPU、进程数、输出都没有设 |
| `_wait_for_health()` | 轮询 `GET /health` 直到 2xx，同时用 `docker inspect -f {{.State.Running}}` 检查容器是否还活着；死了就带日志抛错 | 与本章的 `health_probe` 同一意图：**就绪由可执行性判定，不由进程存活判定** |
| `cleanup()` | `docker stop`（容器带 `--rm` 自动删除），可选 `docker rmi -f` 删除镜像 | 「回收」包含镜像层，属于常驻成本的一部分 |
| `pause()` / `resume()` | `docker pause` / `unpause` 冻结与恢复，恢复后**重新做健康检查** | 冻结是省常驻成本的手段，但恢复必须重新探测 |
| `_stream_docker_logs()` | 后台线程 `docker logs -f` | 工具日志是事后取证的主要来源 |

三点可以直接迁移到本章的实现：

1. **容器里唯一的资源限制是打开文件数。** CPU、内存、进程数与输出上限在容器路线里同样要另外提供（cgroup、`--pids-limit`、输出重定向）；"用了容器"不等于"资源被限制了"。
2. **健康检查是"能干活"而不是"还活着"。** `docker inspect` 的 `Running` 只用于判断是否异常退出，真正的就绪判据是 `/health` 返回 2xx。
3. **`mount_dir` 已被移除，改用 `volumes=['/host/dir:/workspace']`**（`_reject_removed_mount_dir` 校验器会直接报错）。挂载点的生命周期是容器回收的一部分：宿主目录不会随容器 `--rm` 消失，需要单独清理。

### gVisor 与 microVM：文档给出的边界

本机 `runsc` 与 `firecracker` 都未安装、也没有 `/dev/kvm`，因此这两条路线只按官方文档描述机制，**不在本机结果之列**：

* **gVisor** 在应用与宿主内核之间放一个用户态内核（Sentry），应用的 syscall 由 Sentry 实现，只有它自己发起的少量宿主 syscall 到达宿主内核。因此隔离面比容器大（不共享宿主内核的系统调用实现），代价是 syscall 路径变长、部分 syscall 语义与性能特征不同。它的 checkpoint/restore 保存的是 Sentry 侧的进程与内存状态，用来做「启动慢的工具环境」的快照。
* **Firecracker** 用 KVM 起 microVM，guest 有自己的内核；snapshot 保存 guest 内存与设备状态，恢复时**首次触页**的成本会体现在恢复后的第一次访问上（文件映射的写时复制语义决定哪些页要重新读）。

两者的共同点：**快照恢复的是"环境"，不是"任务的业务状态"**。外部已经发生的副作用（写出去的请求、提交的订单）不会被快照撤销——这部分只能靠 9.5 的幂等键与补偿。

## 工程实现：mini 实现——池的取用与回收

核心只有两个函数。取用：优先复用 `READY`，否则在 `max_slots` 内现起，超出就拒绝。

```python
def acquire(self, task: dict) -> tuple[Slot | None, float]:
    """取一个 READY 槽位；没有就现起（受 max_slots 限制）。返回 (槽位, 等待毫秒)。"""
    t0 = now_ms()
    for s in self.slots:
        if s.state == "READY":
            self.hits += 1
            s.begin_busy(task)
            return s, round(now_ms() - t0, 3)
    if len(self.slots) >= self.max_slots:
        self.overflows += 1                      # 有界：拒绝，不排队
        return None, round(now_ms() - t0, 3)
    self.misses += 1
    slot = self._new_slot()
    return (slot, round(now_ms() - t0, 3)) if slot.start()["ok"] else (None, round(now_ms() - t0, 3))
```

回收：整组杀 → 清工作区 → 重新探测，通过才回 `READY`。

```python
def drain(self, cleanup: dict) -> bool:
    self.to("DRAINING", **cleanup)
    healthy = self.health_probe()          # 真的跑一条最短命令
    if healthy["ok"]:
        return True
    self.destroy("drain_probe_failed")
    return False
```

两条不变量贯穿全部实现：

1. **状态迁移只在判据成立时发生**：`READY` 之前必有成功的健康探测，`DESTROYED` 一定带 `reason`；
2. **每个任务结束都清一次工作区并复核进程组存活数为 0**，回收是可检查的事实而不是承诺。

| 预热从 4 降到 0 | 冷启动路径的排队 p50 应回到 58–65 ms；任务数越多，摊薄后差异越小 |
| 把 `RLIMIT_AS` 从 512 MiB 调到 128 MiB | 工具自己都起不来（Python 解释器 + 依赖 > 128 MiB），`health_probe` 会让槽位直接 `DESTROYED`——限制过紧要能自证 |
| 把输出上限从 64 KiB 降到 1 KiB | 截断更早，但工具仍要跑完；父进程 RSS 不变，说明两者是独立机制 |
| 在 `DRAINING` 里跳过工作区清理 | 下一个任务的 `list_files` 能看到上一个任务的产物——复用串号，必须靠重置避免 |
| 给逃逸用例加上按进程树追踪 | `escaped_state` 应不再是 `S`；这是"进程组回收"与"进程树回收"的分界 |

## 前沿

**隔离层的选择正在从"容器 or 不用"变成按任务风险分级。** 本章的核验表说明一件事：可用原语是分层的，而每层能挡住的攻击面不同。生产系统因此按任务来源分级——只读检索用进程组 + rlimit，代码执行用容器 + cgroup，不可信代码用 gVisor 或 microVM。分级的前提是**每层都有自己的证据**：进程组要能证明整组回收，容器要能证明文件系统与 cgroup 边界，microVM 要能证明 guest 内核独立。

**快照把"启动成本"变成"存储成本"。** 预热池省下的是每次冷启动的几十毫秒到几百毫秒；快照把「依赖装载完成、进程已启动」的状态固化下来，恢复时省掉解释器与依赖装载，代价是快照文件的常驻存储与恢复后的首次触页。gVisor 的 checkpoint/restore 与 Firecracker 的 snapshot 是这条路线上的两个代表；**它们恢复的都是环境，不是业务状态**，外部副作用仍需幂等键与补偿。

**工具执行的日志与状态正在被当作一等证据。** 本章每个用例都要求「回收的证据」：进程组存活数、工作区文件清单、fd 数、租约状态。这比"任务返回 0"更接近可运维的系统——9.5 的事务账本、9.7 的任务级 SLO 都依赖同一类证据才能判断真实状态。

## 陷阱

1. **把进程存活当成就绪。** 解释器缺失或权限错误时进程不会"死"，但工具跑不起来；`READY` 必须经过一次真实执行。
2. **用阻塞读收输出。** `stdout.read()` 阻塞时 wall-time 检查永远轮不到——本 lab 第一版因此让一个 60 s 的工具跑满 60 s。
3. **依赖 `RLIMIT_NPROC` 限制进程数。** 本机实测限 4 仍 fork 出 8 个；应改为监督进程组成员或使用 cgroup `pids.max`。
4. **只按进程组回收。** 子进程 `setsid` 后脱离进程组，`killpg` 之后照常运行；必须按进程树追踪或给任务独立命名空间/控制组。
5. **把输出截断当成进程终止。** 截断保护的是监督进程的内存，工具本身要靠 wall-time 或其他阈值停下。
6. **复用槽位不清工作区。** 上一个任务的产物会被下一个任务读到，且通常不报错，只给出错误答案。
7. **把"目录副本 + 子进程"称为沙箱。** 它不隔离内核、不隔离身份、不限制资源（除 rlimit 外），只能算"工作区隔离"。
8. **把容器当 microVM。** 容器共享宿主内核，容器逃逸影响宿主；microVM 才有独立 guest 内核，两者在威胁模型上不同层。
9. **以为快照能撤销副作用。** 快照恢复的是环境状态，已发出的外部请求不会被回滚。
10. **在有界池里用排队掩盖压力。** 拒绝把压力交给上层任务调度、排队把等待藏进池里；两种都行，但必须明确选择并让超时可归因。
11. **把 seccomp 状态当成权限判据。** 本机 `Seccomp: 0` 但限制来自 capabilities；判断能力要看 `CapEff`。

## 自测题

1. 本机的 `Seccomp` 是 0，为什么仍然不能创建 PID 命名空间？
2. 一个工具进程被 `killpg` 杀掉，但 3 秒后 `ps` 仍能看到它。可能的原因是什么？如何区分"没死"与"已死未回收"？
3. 预热 4 个槽位相比不预热，省下了哪一段？为什么「申请→首个结果」的 p50 几乎没有变化？
4. 池里 `max_slots=4`、并发 16 时，8 个任务拿不到槽位。把这 8 个任务改成排队等待，会带来什么新的归因困难？
5. `RLIMIT_AS` 设成 128 MiB 时，为什么槽位可能直接进入 `DESTROYED` 而不是任务失败？

7. 快照恢复一个 gVisor checkpoint 之后，任务之前发出的 HTTP 请求会被撤销吗？为什么这决定了幂等键必须存在？

<summary>参考答案</summary>

1. seccomp 只决定"哪些系统调用被过滤"，不授予权限。创建 PID 命名空间需要 `CAP_SYS_ADMIN`，本机 `CapEff` 里没有这一位，所以内核直接返回 `EPERM`，与 seccomp 是否有过滤器无关。判断环境能力要看 capability 集合。
2. 最常见的原因是进程已被杀死但尚未被回收（僵尸，`/proc/<pid>/stat` 的第 3 个字段是 `Z`）。`kill(pid, 0)` 对僵尸也返回成功，所以只看它会把僵尸算成存活。区分方法是读 `/proc/<pid>/stat` 的进程状态：`R/S/D` 是活着，`Z` 是僵尸；本 lab 的对照里 `killpg` 后正是"无运行中进程 + 1 个僵尸"。
3. 省下的是槽位冷启动那一段（实测 57.9–64.5 ms，包含工作区准备、解释器启动与首次健康探测）。`first_result_ms` 的 p50 没变，是因为它主要由每次任务都要付的部分构成：依赖复制 1.4 ms + 依赖装载 9.7 ms + 工具子进程 64.5 ms。预热的收益只在"任务本身很便宜"或"任务数很多"时才显现为持续的 p50 改善。
4. 排队会把等待留在池内部，于是"任务变慢"既可能来自工具本身，也可能来自池的排队，而池的排队又受上层任务并发影响；超时归因需要在事件里区分「申请排队」与「执行」两段。本 lab 选择拒绝（`overflow`），让压力显式回到上层调度（9.7 的准入），代价是上层必须处理拒绝并重试。
5. 因为就绪判定要真的跑一条命令：128 MiB 的地址空间不足以让 Python 解释器加依赖启动，健康探测失败，槽位从未进入 `READY`，于是按 `drain_probe_failed`/`health_probe_failed` 被销毁。这说明**限制过紧时的失败表现是"环境起不来"而不是"任务失败"**，池必须能自证这一点，否则会表现为持续的槽位创建失败。
6. `RLIMIT_FSIZE`（2 MiB）由内核在写文件时强制，拦住的是**磁盘写入量**，超出时得到 `File too large`；输出上限（64 KiB）由监督进程在读管道时实施，拦住的是**父进程为工具输出分配的内存**。前者对子进程生效、后者对父进程生效；工具把日志写到文件还是 stdout 是两条不同的路径，所以不能互相替代。本 lab 里 fsize 用例的文件正好停在 2 097 152 B，输出用例保留 65 536 B 而父进程 RSS 只涨 936 KiB。
7. 不会。快照恢复的是执行环境（进程与内存状态），已经离开进程边界的副作用——HTTP 请求、写出去的文件、提交的事务——都在环境之外。因此恢复后重放任务会再次发出请求，必须靠业务幂等键让第二次执行收敛到同一结果，或者用补偿记录标注已经发生的事实。
