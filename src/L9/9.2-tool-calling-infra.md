## 本章回答三个问题

工具调用看起来只是一段 JSON，但它在系统里有三条不同的路径：**模板**决定模型看见什么工具，**约束**决定它能吐出哪些 token，**解析**决定这些 token 如何变回一次函数调用。三条路径各自有成本，而且它们的效果不能互相推断。

1. tool choice 在哪里约束输出？
2. 增量 parser 怎样维护多调用状态？
3. 约束与投机如何共同影响成本？

## 机制拆解与推导

### 1. tool choice 在哪里约束输出

`tool_choice` 不是一个开关，而是四种不同的施加点。用同一句 prompt（「请调用工具查询珠穆朗玛峰海拔，只调用一次」）在同一台服务上扫 4 种模式 × 4 种工具数（1/4/16/64），每格 2 次：

| mode | 1 个工具 | 4 个工具 | 16 个工具 | 64 个工具 | 实际选中的工具（≥4 工具时） |
|---|---|---|---|---|---|
| `none` | 不调用 | 不调用 | 不调用 | 不调用 | —（8/8 次都没有 tool_calls） |
| `auto` | **不调用**（0/2） | 调用 | 调用 | 调用 | `search_corpus` |
| `required` | 调用 `calculate` | 调用 | 调用 | 调用 | `search_corpus` |
| `named=calculate` | 调用 `calculate` | 调用 `calculate` | 调用 `calculate` | 调用 `calculate` | 恒为 `calculate` |

四列读出来的东西不一样：

1. **`none` 是硬约束**：模型仍然会回答，但不会产生 tool_calls。它不改变模型"知不知道"工具，只是不允许它调用。
2. **`required` 与 `named` 是"必须调用"**：两者都会产生调用，区别在 `named` 把函数名锁死。`required` + 只有 `calculate` 可用时，模型被迫调用一个与问题无关的工具。
3. **`auto` 是判断权交给模型**：声明 1 个工具（`calculate`）时它拒绝调用，直接给出文字答案；声明 ≥4 个工具时它选了 `search_corpus`——语义上正确的那个。**同一个 `auto`，工具集合不同，行为就不同**；只测单工具的 auto 会得到"模型不爱调用"的错误结论。
4. **四种模式的语法有效性都是 100%**：8/8 格都返回合法 JSON，参数也都能解析。**"语法有效"在这批请求上无法区分模式**，区分它们的是"有没有调用"和"调用得对不对"。

模板成本随工具数线性上升（每格 prompt token 是全批次里引擎自报的中位数）：

| 工具数 | prompt token | 相对 1 个工具 | 每次调用 e2e 中位数 |
|---:|---:|---:|---:|
| 1 | 186 | 1.00× | 137–389 ms |
| 4 | 393 | 2.11× | 189–223 ms |
| 16 | 1 335 | 7.18× | 203–259 ms |
| 64 | 5 127 | 27.6× | 204–319 ms |

平均每多一个工具约 **+79 token**。这些 token 每一轮都要重新 prefill——在 9.1 的 `codefix` 会话里，12 轮就是 12 次；工具库越大，第 ① 层越贵。注意 e2e 中位数并没有随工具数明显上升（137→319 ms 里还混着首请求的编译与预热），**模板 token 的增长主要落在 prefill 与缓存账上，不是每次调用的固定开销**。

#### 约束与 mask 的施加点：`tool_choice` 不改 prompt，也不建语法

把四种模式在 vLLM 0.29.0 里逐条追到底，它们在服务端只影响**两件事**，而且都不在解码 mask 上：

| 位置 | 代码 | 作用 |
|---|---|---|
| `chat_completion/serving.py:989-993` | `is_named_tool_choice = type(request.tool_choice) is ChatCompletionNamedToolChoiceParam`；`is_required_tool_choice = request.tool_choice == "required"` | 把 `required` 与 `named` 识别出来 |
| `:1006-1014` | `elif is_named_tool_choice or is_required_tool_choice:` → 无条件从解析结果构造 `tool_calls` | 这两种模式**强制走工具解析**，即使模型输出里没有工具段也会给出空调用 |
| `:1017-1021` | `elif not request.tool_choice or request.tool_choice == "none":` → 只取 `content` | `none` 只关闭解析，不改变输入 |
| `:1030+` | `auto` 分支：解析出 `tool_calls` 就回填，否则退回纯文本 | `auto` 是"解析成功与否"的分支 |

**`tool_choice` 没有参与语法或 mask 的构造。** 在 `chat_completion/` 目录里搜索 `tool_choice` 与 `structured/guided/grammar/mask` 的交集为空——解码侧约束必须由 `structured_outputs`（或 `guided_*`）单独请求。这也解释了本轮实测：四种模式下参数都是合法 JSON，但那是模板与训练的结果，不是 grammar 在解码时施加 bitmask。

**`none` 能不能把工具从 prompt 里去掉，取决于一个本版本没暴露的开关。** `entrypoints/launchers/cli_args.py:108` 定义了 `exclude_tools_when_tool_choice_none: bool = False`，它在 `responses/utils.py:388-390` 的 `construct_tool_dicts` 里生效：

```python
def construct_tool_dicts(tools, tool_choice, exclude_tools_when_tool_choice_none=False):
    if not tools or (tool_choice == "none" and exclude_tools_when_tool_choice_none):
        return None
```

但 `chat_completion/serving.py:167` 只是把这个字段存下来、**全文再没有读它**，而该字段在本版本的 CLI 里也没有对应的命令行开关（全包搜索 `--exclude-tools` 无结果）。于是走 OpenAI chat completions 接口时，`tool_choice=none` 无法让工具从 prompt 里消失——这正是实测 `none` 的 prompt token（186/393/1 335/5 127）与 `auto`/`required` 完全相同的原因；而 SGLang 的 `none` 只有 33 token，是它自己的渲染路径默认就这么做。**跨引擎对照前必须确认这类"字段存在但未接线"的差异**，否则会把渲染差异当成模型行为差异。

#### 同一套模式在两个引擎上的渲染路径不同

把同一份 4 模式 × 4 工具数矩阵搬到 SGLang 0.5.19（`--tool-call-parser qwen25`，transformers 5.12.1）对照 vLLM 0.29.0：

| mode | vLLM prompt token（1/4/16/64） | SGLang prompt token（1/4/16/64） | 差异 |
|---|---|---|---|
| `none` | 186 / 393 / 1 335 / 5 127 | **33 / 33 / 33 / 33** | vLLM 仍把工具渲染进 prompt；SGLang 完全不渲染 |
| `auto` | 186 / 393 / 1 335 / 5 127 | 196 / 433 / 1 495 / 5 767 | 同量级，SGLang 模板多 5%–13% |
| `required` | 186 / 393 / 1 335 / 5 127 | 196 / 433 / 1 495 / 5 767 | 同上 |
| `named=calculate` | 186 / 393 / 1 335 / 5 127 | **196 / 196 / 196 / 196** | SGLang 只渲染被指定的那个工具 |

两个可迁移的事实：

1. **`tool_choice` 的"约束"发生在两处不同的地方：** 一处是 prompt 渲染（把哪些工具写进上下文），一处是输出侧解析（允不允许产生 tool_calls）。SGLang 在 `named` 下把渲染收敛到单个工具，`none` 下直接不渲染；vLLM 保持全量渲染，靠输出侧约束生效。**"prompt 一样"不是跨引擎对照的前提**，工具集 token 账必须分引擎记。
2. **四种模式在两个引擎上都被支持，本批请求没有出现拒绝路径。** 两边的语法有效性、调用判定与工具选择一致（`auto`+1 工具都是 0/2 次调用，`named` 都锁定 `calculate`，`required` 都产生调用），差异只在 prompt 的构造。

#### 工具 schema 的前缀是增量可复用的

同一请求连发两次，第二次的前缀必然命中：

| 工具数 | prompt token | 第 1 次未命中 token | 第 1 次 TTFT | 第 2 次未命中 token | 第 2 次 TTFT |
|---:|---:|---:|---:|---:|---:|
| 1 | 186 | 186 | 158.3 ms | **10** | 14.2 ms |
| 4 | 393 | 297（96 已命中） | 70.3 ms | **9** | 63.5 ms |
| 16 | 1 335 | 1 031（304 已命中） | 99.7 ms | **7** | 65.7 ms |
| 64 | 5 127 | 3 879（1 248 已命中） | 247.1 ms | **7** | 77.2 ms |

两点要分开说：

- **工具集是包含关系，前缀可以跨请求复用。** 4 个工具的第 1 次请求已经命中 96 token——那是 1 工具请求留下的 `calculate` 块；16/64 个工具同理（304/1 248）。把工具集从 1 扩到 64，增量是"新增工具的那几段"，不是整块重算。
- **缓存热了之后，5 127 token 的工具集只剩 7 个未命中 token 要算。** 所以"工具越多越贵"的准确说法是：**冷前缀的一次性成本随工具数增长（186→5 127），稳态成本几乎是常数（7–10 token）**。容量压力落在缓存而不是每次 prefill 上——这与 9.3 的会话驻留是同一个池子。

#### 完整工具集 vs 按需发现

给模型 64 个工具，其中只有 `lookup_37` 能回答问题。两种做法各跑 2 次：

| 做法 | 模型往返 | 声明的工具数 | prompt token 合计 | TTFT 合计 | e2e 合计 | 最终选中 |
|---|---:|---|---:|---:|---:|---|
| 完整工具集 | 1 | 64 | 5 128（5 088 命中） | 89.1 ms | 206.8 ms | `lookup_37` ✓ |
| 按需发现 | 2 | 1 → 2 | **584**（160 → 576 命中） | 147.9 ms | 330.4 ms | `lookup_37` ✓ |

按需发现把 prompt token 压到 **1/8.8**（584 vs 5 128），代价是**多一次模型往返、e2e 变成 1.6 倍**（330 vs 207 ms），并且两次都没有漏选（最终工具选择正确）。**这就是"按需发现同时报告漏选与额外往返"的具体形态**：省下的是上下文，付出的是往返；在本实验里往返更贵，所以只有当工具集大到让冷前缀成本压过一次往返时，按需发现才划算。阈值可以直接从这两列算：完整集冷前缀 5 128 token ≈ 一次 89 ms 的 prefill，而一次额外往返 ≈ 330−207 = 123 ms，因此工具集需要再大一些（或前缀频繁被驱逐）才会翻转。

### 2. 约束解码作用在哪一段

`tool_choice` 与"参数形状约束"是两件事。前者限制**能不能调用、调用哪个**，后者限制**参数长什么样**。在进程内 LLM 上对四种内容做 `structured_outputs(json=schema)` 对照（每格 3 次，贪心解码，thinking 关闭）：

| 内容类型 | 约束 | JSON 合法 | 参数正确 | 输出 token | ms/token |
|---|---|---:|---:|---:|---:|
| 结构固定（两字段可枚举） | 无 | 3/3 | 3/3 | 18 | 10.3 |
| 结构固定 | guided_json | 3/3 | 3/3 | 18 | 15.7 |
| 参数自由（自拟 query） | 无 | 3/3 | 3/3 | 8 | 10.2 |
| 参数自由 | guided_json | 3/3 | 3/3 | 8 | 18.6 |
| 长数字（39 位整数原样抄） | 无 | 3/3 | 3/3 | 46 | 9.4 |
| 长数字 | guided_json | 3/3 | 3/3 | 46 | 9.5 |
| 长文本（76 token 原样抄） | 无 | 3/3 | 3/3 | 80 | 8.9 |
| 长文本 | guided_json | 3/3 | 3/3 | 80 | 10.3 |

这四类内容在本模型上**不加约束也能 100% 合法**——因为任务简单、输出短、模板已经把格式交代清楚。这不是"约束无用"，而是说明：**约束解码的收益只在模型本来会写错格式时才能看到**。这里能看到的只有代价：

- 结构固定与参数自由的 `ms/token` 从 10.2–10.3 涨到 15.7–18.6 ms（**+53%~+82%**），因为每一步都要与自动机求交、生成 bitmask 并施加到 logits 上（5.6 已给出这条路径的源码与掩码形状）。
- 长数字与长文本两格几乎无差别（9.4→9.5、8.9→10.3 ms/token）：这两类内容本来就是"抄"，语法约束在这里没什么可排除的。

### 3. 增量 parser：状态比语法难

工具调用的流式解析核心难点在于：客户端契约要求按数据块增量输出新解析的片段，而网络传输给到解析器的是任意切分的字节流。`labs/L9/incremental_tool_parser.py` 实现的状态机将其解耦为四段显式状态：

| 状态 | 做什么 | 为什么需要 |
|---|---|---|
| `SEEK` | 固定窗口找 `<tool_call>` | 标记可能跨片段，窗口只需 len(marker) |
| `BODY` | 有界头部缓冲找 `"name"` 与 `"arguments"` 键 | 头部长度有限，不必缓存整个调用体 |
| `VALUE` | 维护字符串/转义/`\uXXXX`/括号深度，判断值何时结束 | 决定 arguments 的边界；外层对象的 `}` 不能混进来 |
| `AFTER` | 只找 `</tool_call>` | 值结束后的结构字符不属于参数 |

再加一条：**尾部扣留 len(`</tool_call>`) = 11 个字符**。扣留是必需的——若不扣留，`</tool_call>` 的前缀会先作为参数 delta 发给客户端，等标记读完才发现该收回；扣留窗口让"发出"与"确认不是标记"同时完成。

六个构造用例的对拍结果（CPU，无 GPU）：

| 用例 | 片段数 | 结果 | 与一次性解析对拍 |
|---|---:|---|---|
| 单调用短参数 | 3 | 1 个调用 | 逐字段相同 |
| 转义字符串（`\"`、`\\`、`\n`） | 5 | 1 个调用 | 逐字段相同 |
| Unicode 转义被逐字符切开（91 片段） | 91 | 1 个调用 | 逐字段相同 |
| 并行两个调用 | 5 | 2 个调用 | 逐字段相同 |
| 不完整 JSON（流在 JSON 中途结束） | 4 | 1 个调用，标 `incomplete_json` | 两边都判错（错误信息可不同） |
| 流中途取消 | 6 | 0 个调用（丢弃在途） | 取消是客户端语义，参照实现看不到 |

还验证了一条流式协议的核心不变量：**每步发出的 delta 拼接起来必须等于最终 `arguments_raw`**（六个用例全部成立）。这条不变量一旦破坏，客户端就会拿到与最终解析结果不一致的参数。

### 4. 重扫的代价是二次的

一个"简单实现"是每收到一个片段就把累计文本整体重新解析一次。它的语义与增量实现相同，代价不同。用固定 8 字符片段喂入同一条调用，参数 payload 从 256 B 扫到 64 KiB：

| payload | 片段数 | 单遍扫描字符 | 逐片段重扫字符 | 扫描倍数 | 单遍墙钟 | 重扫墙钟 | 时间倍数 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 256 B | 33 | 262 | 4 486 | 17.1× | 0.15 ms | 0.09 ms | 0.62× |
| 1 KiB | 129 | 1 030 | 67 078 | 65.1× | 0.60 ms | 0.37 ms | 0.62× |
| 4 KiB | 513 | 4 102 | 1 054 726 | 257.1× | 2.37 ms | 2.17 ms | 0.92× |
| 16 KiB | 2 049 | 16 390 | 16 801 798 | 1 025.1× | 9.08 ms | 18.58 ms | 2.05× |
| 64 KiB | 8 193 | 65 542 | 268 533 766 | 4 097.1× | 73.5 ms | 204.0 ms | 2.77× |

两点必须一起说：

- **扫描量是确定的二次增长**：片段数与长度成正比，逐片段重扫的总量 ≈ L·k/2，所以倍数随长度线性上升（每个 4 倍长度让倍数再乘 4）。
- **墙钟不是**。前三行重扫反而更快，因为 Python 的字符串拼接与小 JSON 解析有固定成本，而增量实现每字符都要走状态机分支；到 16 KiB 才反超，64 KiB 是 2.77 倍。**"二次复杂度"是复杂度事实，"慢多少"要在目标语言与目标长度上实测**——本实验里 4 KiB 以下两种实现一样快。

**多调用长参数不会让缓冲累加。** 把 payload 拆到 1/2/4 个调用里（总量仍是 256 B/4 KiB/64 KiB），单遍状态机的峰值缓冲稳定在 **62 字符**：

| 总 payload | 调用数 | 片段数 | 扫描倍数 | 单遍峰值缓冲 | 重扫峰值缓冲 |
|---:|---:|---:|---:|---:|---:|
| 256 B | 1 / 2 / 4 | 33 / 34 / 44 | 17.1 / 17.7 / 22.8 | 62 / 62 / 62 | 262 / 269 / 347 |
| 4 KiB | 1 / 2 / 4 | 513 / 514 / 516 | 257.1 / 257.7 / 258.8 | 62 / 62 / 62 | 4 102 / 4 109 / 4 123 |
| 64 KiB | 1 / 2 / 4 | 8 193 / 8 194 / 8 196 | 4 097.1 / 4 097.7 / 4 098.8 | 62 / 62 / 62 | 65 542 / 65 549 / 65 563 |

原因是每个调用结束时它的 arguments 就被交出去，常驻的只有头部窗口与尾部扣留窗口；**缓冲与"流里同时有多少调用"无关，只与单个调用的头部长度有关**。逐片段重扫的峰值则随总字节数线性增长。

**常驻缓冲是第三个、也是唯一随长度不变的量。** 单遍状态机的缓冲只有三部分：找 `<tool_call>` 的滑窗（≤11 字符）、有界的头部缓冲（≤256 字符）、arguments 区的尾部扣留窗口（≤12 字符）。实测峰值稳定在 **62 字符**，与 payload 无关；逐片段重扫的峰值就是累计文本本身（64 KiB 档 65 542 字符，相差 1 057 倍）。三者一起看才完整：扫描量差 4 097 倍、墙钟差 2.68 倍、缓冲差 1 057 倍，**决定能不能在长流上跑的是第三个**。

### 5. 提交闸门：闭合、允许表与 schema 三道

解析出参数不等于可以执行。把「一次调用可以派发」定义成三步全部通过，10 个用例逐项断言：

| 用例 | 解析出的调用 | 派发 | 拒绝原因 |
|---|---:|---:|---|
| 单调用 / 转义串 / Unicode 转义跨片段 / 逐字符转义 | 1 | 1 | — |
| 两个并行调用 | 2 | 2 | — |
| 交错三调用（末个截断） | 3 | 2 | `incomplete_json` |
| JSON 未闭合 | 1 | 0 | `incomplete_json` |
| 闭合但 `expression` 传了整数 | 1 | 0 | `schema: 'expression' should be string, got int` |
| 闭合但工具不在允许表 | 1 | 0 | `not_in_allowlist` |
| 客户端中途取消 | 0 | 0 | （在途调用被丢弃） |

三点设计后果：

1. **schema 校验必须在服务端做，且要在派发之前。** 客户端解析器只保证 JSON 语法；类型错误在参数闭合后才暴露，此时派发已经太晚。
2. **允许表是客户端的第一道闸，不是唯一一道。** 客户端拦下未授权工具能省掉一次往返，但服务端仍需独立校验——两者都不能靠提示词或工具注解。
3. **截断与取消都不会派发。** 未闭合的调用在 `finish()` 里被标成 `incomplete_json` 并保持 `dispatched=False`；取消丢弃在途调用、保留已完成的调用。这条不变量是 9.5「不重复副作用」在客户端侧的前提。

### 6. 约束与投机：接受长度看内容，不看模板

DFlash 草稿（`z-lab/Qwen3-4B-DFlash-b16`，8 个投机 token）与普通解码在同一批 8 格上对拍：

| 内容类型 | 接受率（无约束） | 接受率（约束） | 墙钟 无草稿 | 墙钟 DFlash | 加速 |
|---|---:|---:|---:|---:|---:|
| 结构固定 | 1.000 | 1.000 | 186–282 ms | 45–174 ms | 1.6–4.2× |
| 参数自由 | 0.125 | 0.222 | 82–149 ms | 69–135 ms | 1.1–1.2× |
| 长数字（抄 prompt 里的 39 位整数） | 0.594 | 0.844 | 434 ms | 109–110 ms | 4.0× |
| 长文本（抄 prompt 里的 76 token） | 0.796 | 0.921 | 716–821 ms | 144–171 ms | 4.5–5.0× |

四个可迁移的结论：

1. **结构固定时接受率 1.0**，但绝对收益有限——这类输出本来就只有 18 个 token，草稿一次就猜完，省下的是每请求的固定开销。
2. **参数自由时接受率掉到 0.13–0.22**，加速只有 1.1–1.2×。参数内容由模型自己决定，草稿猜不中。
3. **"抄 prompt"是草稿最喜欢的内容**：长文本 0.80/0.92、长数字 0.59/0.84，墙钟降到 1/4 上下。
4. **约束解码会抬高接受率**（自由 0.125→0.222、长数字 0.594→0.844、长文本 0.796→0.921）：语法把候选压到更小的集合里，草稿与目标的分布更接近。**但接受率是"草稿猜中多少"，与"输出是否正确"没有关系**——8 格 × 3 次的参数正确率都是 100%，两种解码方式没有区别。

这里有一个与直觉相反的结果要保留：**"长数字没人猜得中"只对 prompt 里没有的数字成立。** 本实验的 39 位整数就写在 prompt 里，草稿能看到 prompt，于是接受率 0.59–0.84。要检验"高熵数字"假设，必须用不在上下文里的数字。

### 7. 协议边界：谁提供幂等，谁提供取消

模型 token 走到真正执行要跨四道边界，每道边界的保证不同：

| 边界 | 谁在管 | 提供什么保证 | 不提供什么 |
|---|---|---|---|
| 工具解析器 | 引擎（Hermes parser） | 把 delta 还原成 `tool_calls`；参数闭合前不提交 | 不校验业务语义，不保证参数已授权 |
| schema 校验 | 服务端框架（pydantic 等） | 必填/类型/枚举检查，失败给出结构化错误 | 不理解权限与租户；schema 变更会让缓存 schema 的调用方失败 |
| JSON-RPC / 传输 | MCP 客户端与服务端 | 请求-响应配对、会话、取消通知、SSE/JSON 两种回包 | **不提供 exactly-once**：重试就是重新执行，除非服务端按业务键去重 |
| 业务执行 | 工具实现 | 副作用、幂等键、事务边界、允许表 | 协议层无法替你回滚已验证的副作用 |

这张表解释了失败矩阵里的每一行：不带幂等键重试产生 2 条副作用，是因为第三层只保证「一次尝试的结果可见」；「执行成功但响应丢失」窗口只能靠第四层的幂等键收口；`session_idle_timeout` 属于第三层的会话状态，它失效时客户端要做的是重建会话，而不是重试同一请求。

**取消也在第三层。** MCP 的取消通知是「尽力而为」：服务端可以忽略，副作用也不会因为收到取消而回滚。要真正做到可回收，需要在工具实现里传播取消（进程组、deadline），并让业务侧用幂等键区分「重试」与「新动作」——这部分留给 9.5 的持久执行与 9.8 的沙箱回收。

## 工程实现：vLLM 的工具调用路径

### 源码解析

**模板与工具注入。** 服务端把 `tools` 交给 tokenizer 的 chat template 渲染成 prompt。实测的模板成本可以直接从 usage 读出：1/4/16/64 个工具对应 186/393/1 335/5 127 token。

**工具解析器。** `vllm/tool_parsers/hermes_tool_parser.py:70` `extract_tool_calls` 做一次性解析；`:204` `extract_tool_calls_streaming` 做增量解析，输入是"累计文本 + 本步增量"，输出是"本步该发给客户端的 delta"。本次实测里一次典型调用被切成 12–15 个参数片段。

**约束解码。** `structured_outputs` 在 0.29 里必须是 `StructuredOutputsParams` 对象（`vllm/sampling_params.py` 的 dataclass 字段为 `json/regex/choice/grammar/...`）；直接传 dict 会在 `input_processor.py` 的参数校验处报 `'dict' object has no attribute '_backend'`。这条错误在本轮实验中真实出现过，保留在 `content.log` 的失败版本里。

**reasoning 与 tool 的分离。** `--reasoning-parser qwen3` 把 `thinking` 段从输出中拆出来（`vllm/reasoning/qwen3_engine_reasoning_parser.py`）。这直接改变工具任务的行为：本实验里若开着 thinking，模型会先写 256 token 的思考再输出 JSON，甚至在 `max_tokens` 用尽时根本不给答案——本轮 9.2 的对照组因此显式 `enable_thinking=False`。

### 设计取舍

- **在模板里塞工具 vs 在系统提示里描述工具。** 前者用引擎的 tool parser 自动还原调用、可以被约束解码加持；后者要靠正则自己解析、拿不到语法保证。代价是模板 token 随工具数线性增长，64 个工具就是 5 127 token/轮。
- **`tool_choice=required` vs `named`。** `required` 保留模型的选择自由（本实验里它选了语义正确的 `search_corpus`），`named` 把选择权拿走（恒为 `calculate`）。要求"必须产生一次调用"而工具集又很大时，两者对任务成功率的影响完全不同：本实验里 named + 只有一个 `calculate` 会得到一次语义无关的调用。
- **流式 delta vs 一次性返回。** 流式让客户端早看到参数、能提前取消，代价是解析器要维护状态、尾部要扣留窗口。一次性返回实现简单，但客户端必须等整段生成完。
- **约束解码 vs 提示词约束。** 约束是硬保证，但每一步都要与自动机求交（本实验里 `ms/token` 涨 53%–82%）；提示词约束没有运行时成本，但只是概率倾向。**先问"模型本来会不会写错"**，再决定要不要付这个代价。

## 工程实现：mini 实现——有状态增量解析器

核心是"值何时结束"的判断。下面这段来自 `labs/L9/incremental_tool_parser.py`：

```python
def _consume_args(self, text):
    flushed, ended = [], False
    for ch in text:
        if self._value_done:                     # 值已完整，只等 </tool_call>
            self._staging = (self._staging + ch)[-len(CLOSE):]
            if self._staging == CLOSE:
                self._staging = ""               # 结束标记不属于 arguments
                self._end_call(); ended = True; break
            continue
        if self._value_kind is None and ch.isspace():
            continue                             # 值前的空白不进 delta
        if self._value_kind is None:
            self._value_kind = ("object" if ch == "{" else "array" if ch == "["
                                else "string" if ch == '"' else "literal")
        self._staging += ch
        self._track(ch)                          # 字符串/转义/\uXXXX/括号深度
        if self._value_complete():               # 对象深度归零、字符串闭合…
            self._value_done = True
            if self._staging:
                self._cur["arguments_raw"] += self._staging
            flushed.append(self._staging); self._staging = ""
            continue
        if len(self._staging) > len(CLOSE):      # 扣留窗口之外的部分立刻发出
            ready = self._staging[:-len(CLOSE)]
            self._staging = self._staging[-len(CLOSE):]
            self._cur["arguments_raw"] += ready
            flushed.append(ready)
    return ended, "".join(flushed)
```

三处容易写错的地方：

1. **结束标记的扣留**：不扣留就会把标记前缀当参数发出去；扣留窗口只需要 11 个字符。
2. **值的边界不等于调用体的边界**：`{"name": "...", "arguments": {...}}` 里外层对象的 `}` 紧跟在内层 `}` 之后，若"从 arguments 键之后一路收到底"，参数里就会多一个 `}`，`json.loads` 报 `Extra data`。
3. **字符串内的标记不结束调用**：`_track` 维护的 `_in_string` 必须与扣留窗口配合，否则 `{"q": "</tool_call>"}` 会提前收尾。

### 工具调用三条路径：协议层比工具本身贵得多

同一个 `calculate` 工具（返回 66–69 字节的 JSON）、同一批参数，四条路径各 9 个采样点（并发 1/8/32 × 注入延迟 0/10/1000 ms，每格 64 次调用，全部校验返回值、0 错误 0 不匹配）：

| 路径 | 连接建立 | 单次总耗时 p50（延迟 0，并发 1/8/32） | 传输段 p50（并发 1/8/32） |
|---|---:|---|---|
| 直接调用 | — | 0.0036 / 0.0035 / 0.0035 ms | 0.002 / 0.002 / 0.002 ms |
| stdio MCP | **275.6 ms**（拉子进程 + initialize） | 0.28 / 2.39 / **8.41** ms | 0.27 / 2.39 / **8.41** ms |
| Streamable HTTP（JSON 回包） | 14.6 ms | 0.79 / 4.46 / **17.28** ms | 0.78 / 4.46 / 17.28 ms |
| Streamable HTTP（SSE 回包） | 4.5 ms | 1.14 / 7.27 / **27.85** ms | 1.14 / 7.26 / 27.84 ms |

三点直接可用的结论：

1. **协议开销在并发下超线性增长。** 64 次调用的平均单次耗时从并发 1 的 0.28 ms 升到并发 32 的 8.41 ms（stdio）、0.79→17.28 ms（HTTP JSON）、1.14→27.85 ms（SSE）。工具本身只花 0.005 ms，增长全部来自帧编解码与单管道/单连接的串行化。**把工具调用拆成 MCP 服务不能只看功能，要看这条曲线的斜率。**
2. **SSE 与 JSON 的差价约 1.4–1.6 倍**，且随并发放大；一次工具调用的结果只有 69 字节，差价不是带宽而是分帧与事件解析。
3. **冷连接代价压倒热路径。** 每次调用重建连接时（8 次调用），stdio 单次 330 ms、HTTP 4.9 ms；热连接下分别是 0.28 ms 与 0.79 ms——**stdio 冷热差约 1 000 倍**。池化连接的收益不在吞吐，在把这条 275 ms 的固定成本从关键路径上拿掉。

`next-turn` 那一档把工具结果按 96 B / 4 KiB / 24 KiB 回填给模型，测下一轮首 token：TTFT 11.4–20.2 ms，prompt token 95/126/286，`cached_tokens` 分别命中 80/112/272。**注意填充物是空格**，字节数增长远快于 token 数增长，所以这一档只能说明「回填体积对首 token 的影响小于协议自身的抖动」，不能用来估计真实大结果（如整份文件）的 prefill 代价。

### 失败矩阵：协议不给 exactly-once

10 个用例在独立进程里各跑一遍（避免一个会话的取消作用域污染下一个），副作用由服务端账本逐条数出：

| 用例 | 观测结果 | 说明了什么 |
|---|---|---|
| 不带幂等键重试 | 账本 **2** 条副作用 | 协议层重试就是第二次执行 |
| 带幂等键重试 | 账本 **1** 条，第二次 `dedup_hit=true` | 去重必须由服务端在同一提交边界完成 |
| 客户端超时 + 晚到结果 | 首次超时；执行于 3 s 后完成（账本 1 条）；同键重试 `dedup_hit=true` | 断开不停止执行，晚到回包被丢弃 |
| 副作用已提交后进程被杀 | 客户端报错，账本 **1** 条，同键重试 `dedup_hit=true`、总数仍 1 | 「执行成功但响应丢失」窗口的真实代价与唯一解法 |
| 副作用提交前进程被杀 | 客户端报错，账本 **0** 条 | 另一种断连窗口：确实没执行 |
| schema 变更 | v2 必填 `[expression, mode]`；旧调用被 pydantic 校验拒绝（`Field required`）；重新 `tools/list` 后成功 | 缓存 schema 的调用方在参数校验处失败，退路是重新列出工具 |
| 会话失效 | 配置的 `session_idle_timeout=2 s` 在等待 6 s 后仍未过期（负结果）；服务重启后新会话可继续 | 超时未生效按事实记录；重建会话是恢复路径 |
| HTTP 鉴权 | 无 token **401**、有 token 200；工具侧看到 `Authorization: Bearer l9-secr...` | 传输层鉴权与工具授权是两层 |
| 客户端 allowlist | 未授权工具在发出前被拒，账本 **0** 条 | 允许表要在客户端先拦一道，服务端仍需独立校验 |
| Tasks 扩展 | 见下一小节：能力可协商，但规范路径（任务增强 `tools/call`）被本机 SDK 服务端判为 invalid result | 依赖版本的实际支持范围，不能按规范文本假定 |

协商结果本身也是一条要记的事实：钉住的规范版本是 MCP 2025-11-25，python-sdk 2.2.0 的握手版本上限相同（`negotiated_protocol_version = 2025-11-25`），但该 SDK 同时认识 2026-07-28 的「现代」版本；换 SDK 大版本必须重新记录协商值，否则协议行为不可比。

### Tasks 扩展：能力能协商，规范路径走不通

上一轮只测到「服务端没声明 `capabilities.tasks`」。本轮显式声明了一个完整的 Tasks 能力块（`list` / `cancel` / `requests.tools.call`），并用 SDK 自己的 lowlevel 服务端实现 `tasks/get`、`tasks/cancel`、`tasks/result`，客户端则用同一份 SDK 的 `send_request` 发原始请求。结果分三层：

| 层次 | 观测 | 结论 |
|---|---|---|
| 能力协商 | 客户端 `initialize` 收到 `tasks: {list, cancel, requests: {tools: {call}}}` | 能力块可以声明并被解析，协商本身没问题 |
| 规范路径：任务增强 `tools/call` | 客户端收到 `MCPError: Handler returned an invalid result` | **规范语义走不通**：SDK 的 `tools/call` 结果面只接受 `CallToolResult`（`SERVER_RESULTS[("tools/call","2025-11-25")]`），服务端把 `CreateTaskResult` 当非法结果（`mcp/server/runner.py:385`） |
| 显式建任务后的轮询/取结果/取消 | `tasks/get` 7 次轮询 `working→…→completed`；`tasks/result` 返回 `_meta`；`tasks/cancel` 把状态改成 `cancelled` | 这三条方法可以走通，但载荷类型 `GetTaskPayloadResult` 只有 `meta` 字段，工具结果内容无法按类型带回 |

SDK 的支持范围可以直接在源码里对上：`mcp_types/methods.py` 的方法表在 2025-11-25 一行明确写着 `tasks/* deliberately absent`（第 101 行）与 `tasks/status deliberately absent`（第 146 行）——类型定义齐全（`GetTaskRequest`、`CreateTaskResult`、`ServerTasksCapability` 都在），但方法表刻意不收；`mcp/server/extension.py:59` 又把 `tasks/get` 举为「扩展可新增的方法」的例子。也就是说，**要跑通 Tasks，得把它当扩展自己提供方法，而不能期待 SDK 按规范文本自动接上**。这正是任务书说的"Tasks 为实验性且必须报告 SDK 支持范围"。

### 取消通知不保证副作用回滚，两种实现都要数账本

`tasks/cancel` 与 `notifications/cancelled` 都不构成回滚。用一个会写账本的工具做对照（`commit=first`：先写账本再等待；`commit=last`：等待后再写）：

| 场景 | `commit=last`（可协作取消） | `commit=first`（已提交） |
|---|---|---|
| 任务运行中 `tasks/cancel` | — | 状态先变 `cancelled`，worker 跑完后账本 **2 条**记录仍在，任务记录被 worker 覆盖为 `completed` |
| 客户端放弃在飞请求（SDK 自动发 `notifications/cancelled`） | 服务端收到取消通知，账本 **0 条**——取消在提交前生效 | 服务端收到取消通知，账本 **1 条**——**已发生的副作用不因取消而消失** |

服务端确实收到了取消通知（账本中留了两条 `notifications/cancelled` 记录，request id 17/18）。SDK 的默认取消模式是 `interrupt`（`mcp/shared/jsonrpc_dispatcher.py:81`：取消处理器的执行作用域；另一种 `signal` 只置位 `ctx.cancel_requested`），且**被取消的请求一律不回包**。所以「取消」在协议层的含义是「不再等待」，不是「撤销已经发生的事」；要撤销只能靠补偿或业务幂等键，这与 9.5-B 的结论一致。

## 前沿

**工具调用的瓶颈正在从"能不能解析"转向"选得对不对"。** 本章实测里四种模式、四种工具数下的语法有效性都是 100%，真正分化的是语义选择：同一个模型在只有 `calculate` 可用时拒绝调用，在有 `search_corpus` 时选它。这意味着 infra 侧能提供的帮助不是"更强的语法"，而是**工具集合的组织方式**——工具的命名、描述与分组直接改变选择结果。

**约束解码与投机解码的关系刚开始被利用。** 本章实测显示约束会把接受率推高 8–25 个百分点（长数字 0.594→0.844、长文本 0.796→0.921），因为语法给了草稿模型一个更小的目标分布。把 grammar 状态喂给草稿模型、或在约束下重排草稿候选，是 5.5 与 5.6 交汇处的一个开放方向。

**增量解析的复杂度正在被工程化解决。** 现代引擎的流式解析器都把"每字符只扫一次"当作硬要求，因为工具参数的 payload 由模型自己决定、可以任意长；本章的 64 KiB 档说明二次实现的时间倍数虽然只有 2.77×，扫描量已经差 4 097 倍——在更长参数或更弱 CPU 上，这个差距会变成延迟问题。

## 陷阱

1. **把所有工具调用等同于 grammar。** `none`/`auto`/`required` 三种模式里，模型输出的语法约束来自模板与训练，不来自 grammar；只有显式 `structured_outputs` 或服务端配置的语法才在解码时施加 bitmask。
2. **只测单工具。** `auto` + 1 工具下模型 0/2 不调用；扩展到 4 个工具就 100% 调用。工具集大小是自变量。
3. **用"调用率"当成功率。** `required` + 单工具时调用率 100%，但调用的是与问题无关的工具。
4. **JSON 能解析就认为执行正确。** 第 ④ 层只管语法；选错工具、参数语义错误都发生在第 ②③ 层。
5. **从模板可预测性推断参数也可预测。** 结构固定时接受率 1.0，参数自由时掉到 0.13；同一份模板下两者可以差 8 倍。
6. **认为"长数字一定难猜"。** 数字若在 prompt 里，草稿能抄，接受率 0.59–0.84；要用上下文里没有的数字做这个实验。
7. **忘了 thinking 也在 `max_tokens` 里。** 开着 thinking 时 256 token 预算会被思考吃光，JSON 一个字符都出不来；本轮对照因此关闭 thinking。
8. **把"约束解码更慢"当普遍结论。** 本实验里 `ms/token` 涨 53%–82%，但长数字/长文本两格几乎无差别——代价与"约束真的排除了多少 token"有关。
9. **低估重扫的复杂度、高估它的即时代价。** 64 KiB 时扫描量差 4 097 倍，墙钟只差 2.83 倍；两个数字都要报。
10. **直接用 dict 传 `structured_outputs`。** 0.29 要 `StructuredOutputsParams` 对象，否则在参数校验处报 `_backend` 属性错误。
11. **把 MCP 当成 exactly-once 通道。** 协议只保证一次尝试的结果可见；重试就是第二次执行，去重必须由服务端按业务键在同一提交边界完成。
12. **忽略协议开销随并发的斜率。** 工具本身 0.005 ms，stdio 在并发 32 下每次 8.41 ms、HTTP SSE 27.85 ms；不测这条曲线会把「工具很快」当成端到端结论。
13. **每次调用重建连接。** stdio 冷连接 330 ms 对热路径 0.28 ms，差约 1 000 倍；连接池化的收益在固定成本，不在带宽。
14. **把传输层鉴权当工具授权。** 401 只说明没有凭据；工具注解、合法 JSON 与「模型想调用」都不构成执行权限，allowlist 与服务端校验要各做一遍。
15. **用字节数估计回填代价。** 本实验的 24 KiB 填充是空格，token 只从 95 涨到 286；真实大结果（整份文件）的 prefill 代价必须用真实内容测。
16. **假定两个引擎的 prompt 相同。** `named` 下 SGLang 只渲染被指定的工具（prompt 恒 196 token），vLLM 渲染全量（186→5 127）；`none` 下 SGLang 完全不渲染（33），vLLM 仍渲染。跨引擎对照必须先核对工具集的 token 账。
17. **以为 `tool_choice` 会施加语法或 mask。** 在 0.29.0 里它只决定"是否走工具解析"（`serving.py:989-1011`），语法/mask 要另外用 `structured_outputs` 请求；参数是合法 JSON 不能反推启用了 grammar。
18. **以为字段存在就等于生效。** `exclude_tools_when_tool_choice_none` 在 `cli_args.py:108` 有定义、在 responses 渲染路径里生效，但 chat completions 路径存下不用、CLI 也没暴露；因此 `none` 在本版本不会把工具移出 prompt。
19. **用冷前缀成本推稳态。** 工具 schema 热了之后 5 127 token 只剩 7 个未命中；把一次冷请求的成本乘以轮数会高估到几十倍。
18. **假定配置的会话超时会生效。** 本 SDK 下 `session_idle_timeout=2 s` 等待 6 s 仍未过期，这是负结果，不是「会话很长寿」的结论。

## 自测题

1. `tool_choice=none` 时模型还能不能"知道"工具？它受什么约束？
2. 为什么 `auto` 在只有 1 个工具时不调用，在 4 个工具时却调用？
3. 增量解析器为什么要扣留尾部 11 个字符？不扣留会发生什么？
4. 为什么"从 arguments 键之后一路收到底"会多出一个 `}`？
5. 本章 64 KiB payload 上扫描量差 4 097 倍，为什么墙钟只差 2.77 倍？
6. 约束解码为什么能提高草稿接受率？这能说明输出质量更高吗？

::: fold 答案

1. 能——工具 schema 仍然在模板里，模型"看得见"。约束的是**输出侧**：服务端不接受它产生 tool_calls，模型只能给文字答案。
2. 因为 `auto` 把"用不用工具、用哪个"交给模型判断。只有 `calculate` 时，模型判断没有合适的工具可用，于是直接回答；有 `search_corpus` 等工具时存在语义匹配的选项，于是调用。工具集本身是选择行为的一部分。
3. 因为 `</tool_call>` 有 11 个字符，而片段可以切在任意位置。不扣留的话，标记的前缀（如 `</tool_`）会先被当成参数内容发给客户端，等识别出标记再收回已经来不及——客户端已经拼进参数了。扣留窗口保证"发出"与"确认不是标记"同时发生。
4. 调用体的 JSON 是 `{"name": ..., "arguments": {...}}`。arguments 键之后的内容包含内层对象的 `}` 与外层对象的 `}`；从键后收到底会把两个 `}` 都收进来，`json.loads` 就会报 `Extra data`。正确做法是跟踪值的边界（对象深度归零或字符串闭合）。
5. 因为复杂度只描述增长趋势，绝对值还有常数项。前几档里 Python 的字符串拼接与小 JSON 解析的固定成本占主导，增量状态机的每字符分支反而更贵；到 16–64 KiB 时二次项才压过常数项。
6. 约束把下一步的合法 token 集合缩小，草稿模型与目标模型的候选分布因此更接近，猜中率上升（本实验长数字 0.594→0.844）。这只是"猜得准"，与输出是否正确无关——本实验里两种解码方式的参数正确率都是 48/48。

:::
