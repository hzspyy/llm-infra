## 本章回答三个问题

一次 agent 调用的失败面比一次补全大得多：模型在等、工具在跑、工具跑完但结果没被确认、下一轮 prefill 还没开始——这四个位置上断掉，系统需要做的事完全不同。运行时的工作就是把"哪些步骤已经确定发生"变成可查询、可恢复的事实。

1. 多轮任务如何持有状态？
2. 取消怎样跨工具和模型传播？
3. 重试怎样与幂等和持久恢复配合？

## 机制拆解与推导

### 1. 状态机与事件模型

运行时把一次会话拆成四种持久事件，全部追加写进 `events.jsonl`：

| 事件 | 关键字段 | 用途 |
|---|---|---|
| `session_start` | `model`、`adapter`、`model_rev`、`tool_schema_hash` | 恢复前的版本校验 |
| `turn_start` / `model_call` | `turn`、`call_id`、`prompt_tokens`、`cached_tokens` | 轮次边界与模型侧证据 |
| `tool_call` / `tool_result` | `call_id`、`tool`、`args`、`idem_key`、`committed` | 幂等账本的唯一依据 |
| `turn_done` / `session_done` / `session_cancelled` | `turn`、`side_effects` | 恢复时的起点 |

三条不变量：

1. **每个会话、每一轮、每次工具调用都有唯一 ID**（`sess-*`、`m{turn}-*`、`t{turn}-*`）；
2. **只有写进 `tool_result` 且 `committed=true` 的结果才算"已发生"**；`tool_call` 存在但没有结果，说明工具可能跑过也可能没跑——恢复时按"没跑"处理并用同一个幂等键重试；
3. **恢复起点 = `max(turn_done)+1`**，不做任何"猜测性推进"。

### 2. 正常路径

| 事件 | 第 1 轮 | 第 2 轮 | 第 3 轮 |
|---|---|---|---|
| 工具 | `calculate` | `task_ledger_append(key-1)` | `task_ledger_append(key-2)` |
| 结果 | 57 | `committed:step1=57` | `committed:step2=14` |
| 轮次确认 | ✓ | ✓ | ✓ |

会话结束时 `status=done`、`turns=3`、`side_effects=2`。这份 `events.jsonl` 可以逐步重放出同一串状态迁移——**正常路径的可重放性不是"能再跑一次"，而是"只靠日志就能说清每一步确认了什么"。**

工具选择在这一步是**强制**的（`tool_choice` 指向具体函数）。原因不是"模型不听话"，而是**幂等与恢复路径只有在副作用确实发生时才被检验**：本轮第一次实现里模型在第 2/3 轮都只调用了 `calculate`，整个账本机制一次都没被触发，矩阵里的"重复副作用"当然全是 0。

### 3. 故障矩阵：四个位置 × 三条路径

每个格子都真的起一次进程、注入一次崩溃，然后再跑一次恢复。`crash_turn=2`（第 2 轮才有账本写入）：

| 注入点 | restart | resume | abort |
|---|---|---|---|
| `model_wait` | done（key-1, key-2，重复 0） | done（key-1, key-2，重复 0） | 停在 1 轮，无新副作用 |
| `tool_running` | done（重复 0） | done（重复 0） | 停在 1 轮 |
| `tool_done_unacked` | done（**key-1 ×2**，重复 1） | done（key-1, key-2，重复 0） | 停在 1 轮，key-1 保留 |
| `next_prefill` | done（重复 0） | done（重复 0） | 停在 1 轮 |

读法：

- **只有 `tool_done_unacked` 上三条路径产生差异。** 原因很直接：只有这个位置"副作用已经发生、但系统还没记录自己确认过"。前两个位置崩溃时账本还是空的，重启与恢复没有区别；第四个位置上一轮已经完整确认，恢复只是继续。
- **`restart` 的重复副作用是真实存在的**：`key-1` 在外部账本里出现两次。这就是"进程重启后盲目重放所有工具"的代价——**副作用发生在系统之外，进程重启不会把它抹掉**。
- **`resume` 在四个位置都恢复到 `done` 且重复 0**：靠的是"同幂等键查账本，命中就复用结果"，而不是靠"猜上次做到哪了"。
- **`abort` 不等于回滚**：`tool_done_unacked` 的 abort 格子停在 1 轮，但外部账本里已经留下的 `key-1` 不会消失。**运行时能保证的是"不再产生新的副作用"和"不谎报完成"，不是"什么都没发生"。**

一个必须写清的边界：**幂等只能覆盖有幂等键的接口。** 本轮的工具是项目内账本（自带 `idem_key`），所以能保证"同键只写一次"；对没有幂等能力的外部接口（如真实支付、真实文件写入），`resume` 最多做到"不重复已知已提交的调用"，无法提供通用 exactly-once。

### 4. 持久任务存储：把状态搬进事务边界

上一节的运行时把状态放在进程内的字典与追加日志里。真实系统还要回答：**进程被 `kill -9` 之后，哪些状态必须保留、哪些可以重算**。`labs/L9/durable_task_store.py` 用一个 SQLite 存储把这件事做成可检查的：

| 表 | 内容 | 关键约束 |
|---|---|---|
| `tasks` | 任务图节点 `(session, node)` | `state`/`attempt`/`result`，节点唯一 |
| `effects` | 副作用结果 | `idem_key` 主键，重复调用直接复用 |
| `leases` | worker 租约 | `fencing_token` 单调递增，过期后新 worker 接管 |
| `events` | 状态迁移流水 | 追加写，供事后取证 |

**核心不变量：副作用与"我知道副作用发生了"必须在同一个事务里提交。** 把它拆成两次提交就会出现一个窗口，本轮用一个三节点任务图（`fetch → compute → commit`）把两种写法都跑出来：

| 模式 | 崩溃后已提交的副作用 | 恢复后副作用数 | 重复 | 说明 |
|---|---:|---:|---:|---|
| 单事务（默认） | **0** | 3 | 0 | 崩溃时副作用与节点状态一起回滚 |
| 两事务（反例） | **1** | 3 | 0 | 副作用已提交、状态未提交；恢复靠幂等键复用，不重复执行 |

崩溃用 `os._exit(137)` 注入（不是抛异常），恢复由另一个进程执行，两个进程通过磁盘上的库交互。运行脚本对每个后果都写了断言，本轮 10 项全过：

| 检查 | 结果 |
|---|---|
| 正常路径三节点全部 `done`、无重复副作用 | ✅ |
| 崩溃退出码为 137（强制退出而非异常） | ✅ |
| 单事务模式崩溃时副作用为 0（一起回滚） | ✅ |
| 两事务模式崩溃时副作用为 1（窗口存在） | ✅ |
| 恢复后副作用总数 3、重复 0（幂等键复用） | ✅ |
| **过期 worker 的迟到提交被拒绝** | ✅ |
| 接管时 `fencing_token` 递增 | ✅ |

租约与 fencing 的机制值得单独说清楚：worker A 用 token=1 提交了副作用，租约过期后 worker B 用 token=2 接管并提交；此时 A 拿着 token=1 的迟到提交会被 `_commit_node_state` 拒绝（`PermissionError: stale fencing token`）。**这解决的是"两个 worker 同时以为自己拥有任务"的问题**：没有 fencing，A 的迟到写入会覆盖 B 的结果。

#### 4a. 进程级故障矩阵：五种注入，21 项断言

把 kill/restart、租约过期、checkpoint 失败、重复/乱序完成与版本不兼容放在同一个新输出目录里跑一遍，判定全部来自账本、退出码与结构化结果：

| 注入 | 观测 | 结论 |
|---|---|---|
| `kill -9`（单事务） | 退出码 **137**，副作用 0 条、节点仍 `pending` | 未提交的事务整体回滚 |
| `kill -9`（两事务反例） | 退出码 137，副作用 **1** 条、状态未提交 | 拆开提交就留下"副作用已完成但运行时不知道"的窗口 |
| 租约过期 | 旧 worker 的迟到提交被 `stale fencing token` 拒绝，token 1→2 | 只有带有效租约的写入能提交 |
| checkpoint 写失败 | 副作用 0 条、节点 `pending`；重试后 1 条、节点 `done` | 副作用与状态同事务，checkpoint 失败不会留下半个结果 |
| 同一幂等键重复完成 | 1 条副作用、`duplicate_effects=0`；第二次返回首次结果 | 唯一约束把重复收敛成复用 |
| 换键重试（客户端换了业务键） | **2** 条副作用 | 去重只对同一业务键生效 |
| 乱序完成 | 依赖未满足时在**产生副作用之前**拒绝（`effects_after_refusal=0`） | 依赖是准入门槛，不是事后检查 |
| 重复完成同一节点 | 幂等 no-op（`idempotent=true`） | 重复回包不会推进状态机 |
| 工具 schema 版本不一致 | `resume_decision=refused`（`tool schema changed`） | 版本变更必须显式表达 |

四条判据设计上的要求在这里都落实了：**正常任务与失败恢复共用同一组断言**（`summary.json` 把两类合在一个 `checks` 字典里）；**从退出码与结构化字段判定**（每个注入点自己给出 `ok` 并据此返回退出码，`kill` 的 137 也是证据的一部分）；**不看 stdout 最后一行**；**重复与乱序各自有独立用例**，不会被"结果看起来对"掩盖。

#### 4b. 与 LangGraph 的持久执行模型对照

同一个「节点已产生副作用、运行时还没记下它」的窗口，两套模型的答案不同。三节点图（`plan → tool → finish`）用 LangGraph 1.2.12 + `langgraph-checkpoint-sqlite` 3.1.1 跑，工具节点在写完外部账本之后抛异常：

| 档位 | 首次运行（异常前） | 从 checkpoint 恢复后 | 结论 |
|---|---:|---:|---|
| 工具不去重（`naive`） | 1 条副作用 | **2 条** | LangGraph 的恢复语义是**重放未完成节点**，副作用会再执行一次 |
| 工具按业务键去重 | 1 条副作用 | **1 条** | 幂等键把重放收敛成复用 |
| 自写存储（副作用与状态同事务） | — | 崩溃提交前 → **0 条** | 未提交等于没发生，代价是已做的工作要重算 |

checkpoint 的结构本身就是证据：这次运行留下 3 个 checkpoint、9 条 writes，最新一个的 `next` 是 `["tool"]`，且该 task 上记着 `Boom('node failed after producing the side effect')`——**恢复点是"哪个节点待执行"，不是"哪条副作用已完成"**。这就是两套模型的分工：

| 问题 | LangGraph 的答案 | 自写存储的答案 |
|---|---|---|
| 进程死掉后从哪继续 | 从上一个 checkpoint 重放未完成的节点 | 从事务里读已提交节点，未提交的重跑 |
| 副作用会不会重复 | **会**，除非节点自身幂等 | 不会重复，但可能丢失已做的工作 |
| 谁来保证幂等 | 应用（节点代码） | 存储的唯一约束 + 业务幂等键 |
| 「有 tool_call 无 tool_result」 | task 的 writes 为空即未提交 | 事务未提交即未发生 |

**可恢复不等于副作用只执行一次**，反过来，**不重复也不等于可恢复**（单事务模型在提交前崩溃时要重算）。生产系统两者都要：存储提供原子提交与幂等键约束，应用提供业务语义上的去重键；只要缺一个，上面的表就会从"1 条"变成"2 条"或"0 条"。

### 5. 取消：跨模型与工具的传播

在第 2 轮发出取消：

| 时刻 | 已完成轮次 | 副作用 | 说明 |
|---|---|---|---|
| 取消瞬间 | 1 | 0 条 | 第 2 轮在 `turn_start` 前被拦下，模型与工具都没跑 |
| 恢复之后 | 1、2、3 | key-1、key-2 各一次，重复 0 | 从第 2 轮继续，不重放已完成轮次 |

取消在这里是**在状态边界检查的令牌**：模型流读取与工具调用之间各有一个检查点。这样做的意义不是"省一次调用"，而是**让"哪些轮次已经确认"保持单调**——取消后的会话不会把半途的轮次算进 `turn_done`，恢复时也就不会跳过未完成的轮次。

真实系统里更复杂的一层是"取消只断了客户端连接、工具还在跑"（5.8 的失败路径）。本运行时的做法是把取消令牌同时传给工具调用边界，并在恢复时对"有 `tool_call` 无 `tool_result`"的调用按未执行处理——**外部是否真的停下，取决于工具自己是否支持取消，运行时只能保证自己不再推进。**

#### 取消的四个位置：各自该回收什么

取消不是一个动作，而是四个位置上的四种处理。用一条 `plan → fork 两个子任务 → join` 的最小任务图逐个注入，判定只看事件日志、账本、子进程存活与退出码：

| 取消位置 | 当时在途的东西 | 期望终态 | 观测 |
|---|---|---|---|
| `queued` | 只等准入槽 | 0 副作用、无残留进程 | 0 副作用，`alive=[]` |
| `streaming` | 模型流 + 一个已发出但未返回的终止帧 | 晚到回包按 epoch 拒收 | 2 个终止帧事件，1 个 `accepted=false` |
| `tool_running` | 工具子进程（独立进程组） | 杀整个进程组、兄弟子任务一并停、0 新副作用 | `alive=[]`，副作用 0 |
| `tool_committed_unacked` | 副作用已提交、结果未回填 | 保留已提交副作用，按业务键取回、不重放 | 副作用保留、`recovered` 非空、`replay=0` |

四条处理共同构成一条不变量：**取消后不再产生新的副作用，但已经提交的副作用不会被撤销**。第三行和第四行的区别正是这条不变量的两侧——前者只能在提交前拦下，后者只能靠幂等键取回。

取消向 fork/join 兄弟子任务传播是必须显式做的：只给被取消的那一支发信号，兄弟分支会继续跑完并提交副作用。本实验把检查点放在「工具等待的每一轮循环开头」与「提交之前」，两处都检查 epoch/取消标志，因此 `tool_running` 档的副作用是 0 而不是 1。

#### 总 deadline 不能被重试重新起算

子调用有各自的超时与有界退避（0.05 s 起、每轮翻倍），但**总 deadline 是任务级的**。把子超时设为 0.3 s、允许 5 次重试、总时限 1.2 s：

| 量 | 值 |
|---|---|
| 总时限 | 1.2 s |
| 实测总耗时 | 1.202 s |
| 实际尝试次数 | 4 |
| 是否在总时限内 | 是 |

如果每轮都重新分配全额超时，5 次重试最坏会跑到 1.5 s 以上并把总时限撑开。**"每轮重新分配 timeout"和"总 deadline"是两个不同的契约**：前者约束单次调用，后者约束任务。运行时必须在每次发起子调用前用剩余预算取 `min(子超时, 剩余)`，这也是 9.7 的任务级 SLO 能成立的前提。

#### 客户端断开之后，引擎还在算吗：两个引擎给出不同答案

上面四个位置里的 `streaming` 用带延迟的 stub 流验证了状态机语义。但任务书要求「真实引擎侧的流式取消」，因为**客户端停止读取与引擎停止执行是两件事**，而这件事只能用引擎自己的指标判定。用同一条请求（Qwen3-4B、`max_tokens=1024`、`ignore_eos`、流式）在两个引擎上各做「读到 8 个 chunk 就关闭连接」，随后按 0.1 s 采样 `num_requests_running` 与 KV 占用：

| 观察量 | vLLM 0.29.0 | SGLang 0.5.19 |
|---|---:|---:|
| 断开时已收到的 chunk | 8 | 8 |
| 断开后第一次采样 `running` | 0 | 1（上一次采样可能仍读到 0，见下） |
| `running` 回到 0 的时刻 | 断开后约 0.22 s（其中两次采样是判定条件本身要求） | **约 6.1 s**（与同一请求完整生成 1024 token 的自然完成时长一致） |
| 断开后仍生成的 token | 约 9 个（随即中止） | 未直接读数：请求 6.1 s 后才结束，期间 KV 一直在涨 |
| KV 占用峰值 / 最终 | 0.00 / 0.00 | 0.04 / 0.00（生成期间一直占着） |
| 显式中止入口 | 无 | `POST /abort_request`，中止后 0.22 s 回到 0 |

**同一句「客户端断开」在两个引擎上是两种语义。** vLLM 的 OpenAI 服务端用 `with_cancellation`（`vllm/entrypoints/serve/utils/api_utils.py:51`）把路由处理器与「HTTP 断开消息」绑在一起，断开即取消请求、释放块；SGLang 0.5.19 在本例中**继续把请求算完**：客户端 72 ms 就关闭了连接，`num_running_reqs` 仍为 1，`token_usage` 从 0 涨到 0.04 并在 6.1 s 后才归零（该时长与同一请求完整生成 1024 token 的耗时一致；被放弃后计数器不再增加，因此 token 数只有时间与 KV 两条间接证据，已在工件里写清）。这一档不能用「客户端不再报错」当作执行停止的证据——它恰恰是反例：**不读结果的客户端不会让引擎少算一个 token**，除非有显式中止或引擎自己实现断开检测。

还有三个必须先解决的测量陷阱，否则读数会指向错误结论：

1. **思考文本的 delta 字段两引擎不同**（vLLM `reasoning`、SGLang `reasoning_content`）。只数 `delta.content` 时两边都得到「收到 0 个 chunk」，断开就发生在流自然结束之后，测的其实是完整请求——第一版脚本正是这样得到「SGLang 也立即停」的假象。
2. **断开后的第一次采样不可信**：调度器尚未把请求加入 running 集合时读到的 0 与「已中止」无法区分，必须按时间序列判据（连续采样 + KV 同向变化）。
3. **计数器的记账口径也要分别核对**：vLLM 中止的请求不进入 `vllm:request_success_total`（`finished_reason="abort"` 恒为 0，本次实验中始终为 0），SGLang 在被客户端放弃的请求完成后 `sglang:generation_tokens_total` 也不增加（8.0 → 8.0）。**引擎自报的 token 账在断开路径上会少记**，成本核算要用 GPU 时间或显式的执行窗口，不能只信这两个计数器。

## 工程实现：最小运行时的三个组件

### 源码解析：状态、账本与检查点

本轮实现（`labs/L9/agent_runtime.py`）刻意保持小，只包含三件真实系统里也必须有的东西：

```python
# 1) 幂等账本：先查已提交结果，命中就复用（不重复写外部副作用）
def side_effect(self, idem_key: str, entry: str) -> str:
    if idem_key in self.ledger["tool_results"]:
        return "reused:" + str(self.ledger["tool_results"][idem_key]["result"])
    self.side_fh.write(json.dumps({"idem_key": idem_key, "entry": entry}) + "\n")
    return f"committed:{entry}"

# 2) 恢复起点：只承认显式确认过的轮次
def _rebuild_state(self) -> str:
    return "TURN_DONE" if self.ledger["done_turns"] else "CREATED"
start_turn = max(self.ledger["done_turns"], default=0) + 1

# 3) 幂等键的唯一性由调用方给定（工具参数里的 idem_key），运行时不做内容哈希
result = self.side_effect(key, str(args.get("entry", "")))
```

**为什么幂等键由调用方给而不是运行时生成？** 运行时生成的键（比如 `call_id`）在进程重启后就不一样了——那等于没有幂等。键必须来自"跨重启稳定"的东西：业务键、请求 ID、或者像本轮这样的显式 `idem_key` 字段。

`agent_failure_matrix.py` 负责注入与比对：注入用真实的 `raise`/进程退出（不是模拟标记），恢复用独立的子进程调用 `recover`，两者通过磁盘上的账本与副作用日志交互。

### 设计取舍

- **事件日志 vs 状态快照。** 日志追加写、崩溃安全、可审计；快照读取快但要处理"写一半"的问题。本实现只用日志，牺牲恢复速度换简单与可检查。
- **恢复粒度是"轮"还是"步"。** 本轮以轮为单位（一轮里可能多次工具调用）。粒度越细，重复副作用窗口越小，但日志与幂等键的复杂度越高。
- **取消令牌 vs 强制杀进程。** 令牌让系统有机会记账（哪些轮次确认了）；杀进程最彻底但丢掉未落盘的状态。真实系统通常两者都要。
- **拒绝恢复 vs 尽力恢复。** schema/模型/adapter 变更时选择拒绝：宁可要求人工判断，也不产生"错位但成功"的会话。

## 前沿

**运行时的核心资产正在从"调度器"变成"账本"。** 本章的矩阵说明：四个注入点里只有一个会产生重复副作用，而处理它的能力不来自更聪明的调度，而来自"幂等键 + 持久事件"这两件朴素的东西。真实系统（veRL 的 AgentLoop、各家 agent 平台）都在把会话状态、工具调用与幂等键显式建模，而不是隐含在进程内存里。

**取消与恢复正在成为同一条协议。** 取消要求"不再推进未确认的轮次"，恢复要求"只补做未提交的步骤"——它们共用同一份事件日志与同一套确认语义。把两者分开实现，就一定会出现"取消了但账本写了"或"恢复了但状态错了"。

**版本与身份正在进入恢复路径。** 模型、adapter、量化配置、工具 schema 的任何变更都会让"上一轮的结论是否还成立"变成未知；本章用拒绝恢复处理它。9.3 的缓存身份和 9.5 的恢复校验是同一个问题的两面。

## 陷阱

1. **把"调用率"当"幂等被验证"。** 第一次实现里模型三轮都只调 `calculate`，账本一次没触发，矩阵里所有格子都"没有重复"——那是没测到，不是通过了。
2. **用运行时生成的 ID 当幂等键。** 重启后 ID 改变，等于没有幂等；键必须跨重启稳定。
3. **假设重启会回滚副作用。** 副作用发生在外部系统，进程重启只丢自己的账本。`restart` 格子里的 `key-1 ×2` 就是这么来的。
4. **把 abort 当回滚。** abort 只保证"不再产生新副作用"和"不谎报完成"，已经写进外部账本的内容不会消失。
5. **取消只断连接。** 断开客户端不等于工具停下；运行时要在状态边界检查取消令牌，并按"有调用无结果 = 未执行"处理。
6. **恢复时不校验版本。** 工具 schema 变了还继续用旧结果，会产生"成功但错位"的会话。
7. **以为幂等能覆盖任意接口。** 没有幂等键的外部接口上，最多做到"不重复已知已提交的调用"，不能宣称通用 exactly-once。
8. **把"事件日志存在"当"可重放"。** 可重放要求日志记录足够的状态迁移（轮次边界、提交与否），只记请求与响应是不够的。
9. **把取消后的旧结果带进新一轮。** 4.11 的 epoch 协议解决的就是这件事：打断后旧音频/旧工具结果必须按 epoch 作废，否则会"复活"。
10. **恢复起点靠猜。** `max(turn_done)+1` 是唯一安全的起点；"大概做到第 3 轮了"这种推断在故障下必然出错。
11. **把副作用与状态分成两次提交。** 中间崩溃会留下"副作用做了、运行时不知道"的窗口（本轮两事务模式实测：崩溃后已提交副作用 1 条、状态仍是 pending）；正确做法是同一事务提交。
12. **不检查 fencing token。** 租约过期后旧 worker 的迟到写入会覆盖新 worker 的结果；本轮实测旧 token 的提交被拒绝，`fencing_token` 从 1 增到 2。

## 自测题

1. 四个注入点里，哪一个会让 restart 与 resume 产生差异？为什么其他三个不会？
2. 为什么幂等键必须由调用方给出，而不能用运行时生成的调用 ID？
3. `abort` 之后，外部账本里已经写入的内容会怎样？
4. 取消在第 2 轮发生后，为什么恢复时不需要重放第 1 轮？
5. 工具 schema 在会话中断期间升级了，为什么选择拒绝恢复而不是尽力继续？
6. 本章的幂等保证在什么条件下不成立？
7. 为什么"副作用提交"和"节点状态提交"必须放在同一个事务里？用一个可观察的差别说明。
8. worker 租约过期后，旧 worker 拿着过期 token 提交会发生什么？为什么必须有这一层？

::: fold 答案

1. `tool_done_unacked`：此时副作用已经写进外部账本，但运行时还没确认这一轮。另外三个位置崩溃时账本里还没有任何提交，restart 与 resume 面对的是同一个空状态，因此结果相同。
2. 因为幂等键必须在**跨进程重启**后仍然指代同一个操作。运行时生成的 ID（如 `call_id`）在重启后会变，第二次执行会被当成新的操作，导致重复副作用。稳定键只能来自业务语义（业务键、请求 ID、显式字段）。
3. 会保留。abort 停止的是运行时的推进，不是外部系统已经发生的事实；它保证的是"不再产生新的副作用"与"不声称任务完成"。
4. 因为第 1 轮在取消前已经 `turn_done`，事件日志里它是显式确认过的；恢复起点是 `max(turn_done)+1 = 2`，第 1 轮不在补做范围内。
5. schema 变更意味着"上一轮工具结果的语义"与"这一轮工具调用的语义"可能不一致；继续恢复会产生看起来成功、实际错位的会话，而且错误很难在事后发现。拒绝恢复把判断交回给人。
6. 只在"接口支持幂等键"时成立。对没有幂等能力的外部副作用（真实支付、无条件写入等），运行时最多避免重复提交"已知已提交"的调用，无法保证外部系统对同一逻辑操作只执行一次。
7. 因为拆成两次提交就会出现一个窗口：第一次提交之后、第二次提交之前崩溃，副作用已经发生但运行时不知道（本轮两事务模式实测崩溃后已提交副作用 1 条、节点仍是 pending；单事务模式是 0 条）。同一事务提交让"做了"和"知道做了"同时成立，恢复时只需读状态。
8. 被拒绝（`PermissionError: stale fencing token`）。因为租约过期意味着"任务已经交给别人"，旧 worker 的写入可能覆盖新 worker 的结果、或者把已经前进的状态写回去。fencing token 单调递增，让"谁是最新的持有者"可以被存储层直接判断。
