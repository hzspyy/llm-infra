## 本章回答三个问题

多轮会话把前缀缓存从"一个请求内的优化"变成了"一条会话跨请求的状态问题"。同样的 token 会被反复 prefill，但"能复用多少"取决于历史怎么组织、"什么时候"下一轮才来、以及下一轮落在哪台机器上。

1. 跨轮哪些 token 真正保持共同前缀？
2. 驻留、驱逐、取回和重算怎样选择？
3. 会话迁移怎样影响收益？

## 机制拆解与推导

### 1. 预测命中块，再与引擎对拍

9.1 的按块模型给出了一条可检验的规则：**命中 = 从第 0 块起、连续存在的整块前缀**（块大小 16，块哈希链住父块）。把三种历史组织方式各跑 2/4/8 轮（每轮含一次工具调用），每种配置开局都清空引擎缓存，预测值与引擎自报 `cached_tokens` 逐轮对拍：

| 历史组织 | 观测轮次 | 预测=实测 | 相差 ≤1 块 | 命中率均值 | 需重算 token 均值 |
|---|---:|---:|---:|---:|---:|
| `append`（追加） | 28 | 28 | 28 | 0.634 | 129.9 |
| `mid_insert`（插入 system 段） | 28 | 28 | 28 | 0.064 | 458.4 |
| `trim_thinking`（裁剪历史 thinking） | 28 | 28 | 28 | 0.556 | 170.5 |

**84 次观测全部精确相等**，不需要容差。三行读出来的就是"共同前缀能走多深"：

- `append` 每轮只在末尾追加，前缀几乎完全保留（0.634）；
- `mid_insert` 把新证据插进 system 段，**共同前缀立刻退到 system 之前**（0.064），从第 2 轮起每轮都要重算 400+ token；
- `trim_thinking` 在第一条 assistant 消息处断开，命中率落在两者之间（0.556）——**裁剪历史的收益（更短的 prompt）与代价（丢掉 assistant 段之后的所有前缀）必须一起算**。

这条对 9.5 的运行时是直接的约束：**任何"改写历史"的操作（裁剪、摘要、重排）都会让后续轮次的前缀复用归零**，而"只追加"能保住它。

### 2. 驻留、间隔与驱逐

4 轮 `append` 会话，轮间插入等待与压力（24 条互不相同的约 1 500 token 长前缀请求）：

| 轮间等待 | 压力 | 命中率均值 | 需重算 token | e2e 均值 |
|---:|---:|---:|---:|---:|
| 0 s | 无 | 0.958 | 15.5 | 269.6 ms |
| 1 s | 无 | 0.958 | 15.5 | 234.5 ms |
| 10 s | 无 | 0.958 | 15.5 | 235.9 ms |
| 60 s | 无 | 0.958 | 15.5 | 240.2 ms |
| 0 s | 24 条 | 0.000 | 391.5 | 244.8 ms |
| 1 s | 24 条 | 0.000 | 391.5 | 245.8 ms |
| 10 s | 24 条 | 0.000 | 391.5 | 245.9 ms |
| 60 s | 24 条 | 0.000 | 391.5 | 254.2 ms |
| 参照：关闭前缀缓存 | — | 0.000 | 391.5 | 288.0 / 245.9 ms |

三条结论：

1. **等待时间本身不驱逐缓存。** 从上到下四个"无压力"行完全一样（0.958 / 15.5 token），60 秒不来的会话和立刻回来的会话得到同样的命中。vLLM 的前缀缓存是**按容量淘汰**的，没有基于时间的过期策略。
2. **容量压力才是驱逐的原因。** 只要在轮间插入 24 条长前缀请求，所有间隔档的命中率都掉到 0，重算量涨到 391.5 token——**与"关掉前缀缓存"的 token 账完全相同**。本引擎在 `--gpu-memory-utilization 0.45` 下的 KV 容量是 41 008 token，24×1 500 的填充足以把它冲一遍。
3. **e2e 几乎不动（235–288 ms），但 token 账差 25 倍（15.5 对 391.5）。** 这些会话的 prompt 只有几百 token，重算的绝对时间被每请求固定开销掩盖。**判断"该不该保留缓存"必须看 token 与容量，不能只看这几个毫秒。**

四条路线的取舍因此写成条件式：

| 策略 | 什么时候划算 | 代价 |
|---|---|---|
| 常驻（不驱逐） | 会话马上要来下一轮、且容量有余 | 挤占其他会话的 KV；容量是硬上限 |
| 容量淘汰（本实验默认） | 大部分会话在几十秒内继续 | 压力下退化为全量重算（命中 0） |
| 重算 | 会话很长但只来一次；容量紧张 | 每轮付 391.5 token 的 prefill |
| CPU/远端取回 | 容量紧张但会话还会回来 | **本章未实测**：需要 8.6 的两级存储与取回接口，本机没有该路径 |

#### 三条路线的代价可以直接算：保留、换出、重算

上面那张表给的是方向，这一节把它算成数。输入全部来自实测：KV 每 token 147 456 B（Qwen3-4B，9.4 已核对）、换出聚合带宽 36 GB/s（5.8）、以及本轮在同一台机器上量到的单请求 prefill 时间（关掉前缀缓存）：

| 前缀长度 | prompt token | 重算（关缓存，稳态中位） | 命中（缓存开，稳态） | 命中/重算 |
|---:|---:|---:|---:|---:|
| 515 | 515 | 52.2 ms | 20.9 ms | 0.40× |
| 4 022 | 4 022 | 373.5 ms | 36.8 ms | 0.10× |
| 8 028 | 8 028 | 856.8 ms | 56.1 ms | 0.065× |

折算 prefill 吞吐约 9.4–11.5 k token/s（515/52.2、4 022/373.5、8 028/856.8），三段一致。据此算三种处理的成本：

| 上下文 | 单会话 KV | 重算 | 换出+取回（2×B ÷ 36 GB/s） | 换出/重算 | 保留 1 s 的占用积分 |
|---:|---:|---:|---:|---:|---:|
| 512 | 75.5 MB | 206.6 ms | 4.19 ms | 0.020 | 75.5 MB·s |
| 4 096 | 604.0 MB | 347.5 ms | 33.6 ms | **0.097** | 604.0 MB·s |
| 8 192 | 1 152.0 MB | 856.3 ms | 67.1 ms | **0.078** | 1 152.0 MB·s |

**换出比重算便宜一个量级**（0.078–0.097），所以「保留还是重算」这个二选一其实问错了：只要会话还会回来、且换出通道可用，换出几乎总是比重算划算。

真正的分界在**保留与换出之间**。保留不消耗任何搬运带宽，代价是占着 KV 池：设池子总量 $M$、会话 KV 为 $B$、工具间隔 $g$，占用可以写成「池·秒」$g\cdot B/M$。换出要搬 $2B$（出去再回来），代价是 $2B/v$ 的带宽秒。把这两种资源按同一尺度计价（**这是一个明确的建模假设**：池·秒与带宽·秒同价），令两者相等：

$$g^\*\cdot\frac{B}{M}=\frac{2B}{v}\;\Rightarrow\;g^\*=\frac{2M}{v}$$

代入 $M=12$ GiB、$v=36$ GB/s 得 $g^\*\approx 0.72$ s。两点读法：

1. **临界间隔与上下文长度无关**（两边都正比于 $B$），但**与池子大小成正比**：池子越大，越值得为长间隔保留。
2. 这个数只在 $M$ 与 $v$ 的口径确定后才有意义；换一套计价尺度（例如把池·秒按更高权重计价）会把它推向更小的值。**结论是条件式的，不是常数。**

把它套到 9.1 采集到的真实工具时延上：1 086 次工具调用里 `p50 = 0.8 ms`、`p90 = 21.6 ms`、`p99 = 27.4 ms`、最大 607 ms。**本地工具的间隔比 0.72 s 低两三个数量级**，所以本章负载上「原地保留」是对的；只有极少数长尾（下载、装依赖、跑测试，最大 607 ms）接近这条线。这也解释了为什么前面的驻留扫描里等待 0/1/10/60 s 的命中完全相同——那些等待都远小于容量淘汰的时间尺度，而容量压力一到就全部失效。

#### 容量约束是「同时在等工具的会话数」

驻留的容量约束不是累计占用积分，而是**任一时刻同时在等工具的会话数 × 单会话 KV**。同一份 9.1 轨迹里的等待区间与 12 GiB KV 预算：

| 上下文 | 单会话 KV | 12 GiB 能装下 | 实测最大并发等待 | 工具时延 ×1.5 后 | 是否装得下 |
|---:|---:|---:|---:|---:|---|
| 512 | 75.5 MB | 170 | 6 | 8 | 是 |
| 4 096 | 604.0 MB | **21** | 6 | 8 | 是（余量 2.6×） |
| 8 192 | 1 152.0 MB | **10** | 6 | 8 | 是（余量 1.25×） |

两点必须一起报：

1. **上下文越长，能同时驻留的会话数越少**：4 096 token 只装得下 21 个会话，8 192 token 只装得下 10 个，而 12 GiB 是 `--gpu-memory-utilization 0.45` 这一档的一个假定预算。这条账是硬的，与调度策略无关。
2. **工具变慢会让等待区间拉长、重叠数上升。** 时延 ×1.5 后并发等待从 6 升到 8，8 192 档的余量从 1.67× 掉到 1.25×。容量预留要按最坏情况放大（本实验里占用积分的最坏/名义比正好是 1.5），而不是按观测均值。

### 3. 会话迁移：收益归零，输出还可能变

同一段 4 轮会话，两种投递方式：

| 策略 | 第 1 轮 | 第 2 轮 | 第 3 轮 | 第 4 轮 | 命中率均值 | 输出逐字相同 |
|---|---:|---:|---:|---:|---:|---:|
| 固定副本 | 0 | 0.725 | 0.781 | 0.814 | 0.580 | 3/4 轮 |
| 每轮迁移 | 0 | 0 | 0 | 0 | 0.000 | — |

- **迁移把逐轮复用全部抹掉**：第 2 轮起每一轮都命中 0，等于把 `append` 会话退化成"每次都从头 prefill"。这正是 8.1 会话亲和（session-aware routing）要解决的问题：**路由到一个没有该会话前缀的副本，收益不是"少一点"，而是"没有"。**
- **另一件必须记录的事**：固定副本与迁移两种投递下，4 轮里有 1 轮的输出文本不同（贪心解码、`temperature=0`）。原因是数值路径不同——命中缓存的 prefill 与全量 prefill 走的 kernel/批次组合不一样，浮点结果因此有微小差异。**KV 复用是性能优化，不是数值等价变换**；要断言"输出一致"，必须逐条比对而不是假定。
- 本次迁移用 `/reset_prefix_cache` 在同一引擎上模拟"落到空副本"。**它不是多实例路由实测**：真实跨实例路径（8.6 的两级存储/传输）本机没有落地，这一项保持 `UNVERIFIED`。

### 3c. 两台真实 worker：迁移、重算与跨实例搬运

前面几节都在单个引擎里。这一节把会话真正搬到另一台机器上：crater（A）与 crater2（B）在同一子网，各起一个 Qwen3-4B 引擎（开前缀缓存），会话 4 轮、前缀约 5 400 token。三种投递方式各用**互不相同的前缀**（否则会命中上一次实验在 B 上留下的缓存）：

| 轮次与目标 worker | 固定副本（全在 A） | 迁移后重算（1–2 在 A，3–4 在 B） | 迁移 + 搬运 KV（同左） |
|---|---|---|---|
| r1 @A | 5 408 / 5 420 = **0.998** | 16 / 5 421 = 0.003 | 16 / 5 292 = 0.003 |
| r2 @A | 5 408 / 5 454 = 0.992 | 5 408 / 5 455 = **0.991** | 5 280 / 5 326 = **0.991** |
| r3 @B | 5 440 / 5 488 = 0.991 | 16 / 5 489 = **0.003** | 16 / 5 360 = **0.003** |
| r4 @B | 5 472 / 5 522 = 0.991 | 5 472 / 5 523 = **0.991** | 5 344 / 5 394 = **0.991** |

（表中"命中 token / prompt token = 复用率"。**复用率不会是 0**：块粒度下总有一个 16 token 的模板公共块命中，所以判据必须用比例。）

四条结论：

1. **迁移把复用率从 0.99 打到 0.003。** B 第一次处理该前缀时只能重算，TTFT 从 A 的命中态 **20.7 ms** 涨到 **264.8 ms**（12.8×）。第二轮起 B 自己建立缓存，复用率回到 0.99——**迁移不必永久失去后续复用**，代价是每个新副本上的"第一次"。
2. **搬运了 799 MB，B 仍然 0.003。** 跨实例传输实测 **799 211 520 B / 6.77 s = 118.0 MB/s**（接收端独立测得 117.7 MB/s，两侧一致）。但 vLLM 0.29.0 没有把外部 KV 块注入前缀缓存的公开接口，所以「搬运 + 注入后能恢复多少复用」保持 `UNVERIFIED`——这不是推断，是把缺口写成可检查的字段（`injection_gap.engine_has_public_kv_import_api=false`）。
3. **重算与搬运不能相加成"取回总成本"。** 264.8 ms 是 B 上的真实重算时间，6.77 s 是真实搬运时间；但缺注入接口时两者不是同一条路径上的两段，只能分别报告。若按本机 118 MB/s 折算，搬运 799 MB 的时间（6.77 s）比 B 上重算（0.26 s）**贵 26 倍**——所以在这个前缀长度与这条链路上，"搬 KV"不如"直接重算"；只有当重算成本超过搬运成本（更长前缀、更慢的卡、更快的链路）时搬运才划算，而那条路径本机无法验证。
4. **模板身份差异只影响分叉点之后。** 同一批消息切换 `enable_thinking`：prompt token 5 162 对 5 158（差 4），但开 thinking 的那次复用了关闭档留下的 **5 152** token 前缀——分叉在尾部，公共前缀照常复用。**"身份不同"不等于"前缀全部失效"**，失效范围要按分叉位置算。

这一节的三个实现约定值得单独记下，它们都直接影响结论有效性：

* **每次实验必须用新的前缀标记。** B 上的前缀缓存会跨实验保留（容量允许时）；复用标记会让"B 首次见到该前缀"这个前提不成立，测出来的复用率虚高到 0.99。
* **引擎的缓存单位是块，不是 token。** 判据用复用率而不是"cached 是否为 0"，否则每个用例都会被那 16 token 的模板公共块判成"有命中"。
* **启动脚本用 pidfile 互斥，不要用 `pkill -f`。** 模式匹配会命中发起启动的那条 ssh 命令自身，把 shell 一起杀掉，表现为"命令没有输出、输出目录没建"。

### 4. 上下文压缩：省下的 token 与丢掉的正确率一起报

多轮会话越长，"哪些历史留在上下文里"就越成为一个策略选择。用同一批多轮任务（每轮给一个整数、要求累加到当前值）比较四种策略，任务本身要求"知道全部历史才能算对"，所以质量与成本可以同时测：

| 策略 | 每轮 prompt token | 缓存命中率 | TTFT p50 | 逐轮正确率 | 额外调用 |
|---|---:|---:|---:|---:|---|
| `full`（完整历史） | 427.3 | 0.885 | 14.3 ms | **0.958（92/96）** | — |
| `window`（只留最近 2 轮） | 401.6 | 0.840 | 15.1 ms | **0.958（92/96）** | — |
| `summary`（丢历史、模型摘要替换） | 356.0 | 0.851 | 14.2 ms | **0.469（45/96）** | 84 次摘要请求 |
| `external`（历史外置、按需 `recall_history` 取回） | 377.3 | 0.835 | 14.3 ms | **0.146（14/96）** | 模型仅 32/96 轮主动取回 |

四条结论：

1. **"省 token"与"保正确率"在这里是两笔独立的账。** `summary` 把 prompt 从 427 压到 356（−17%），正确率从 0.958 掉到 0.469（−51%）；`external` 只省了 12% 的 prompt，正确率掉到 0.146。**只报 prompt 长度会把这两条策略都写成"改进"。**
2. **压缩的代价还落在请求数上。** `summary` 每轮都要生成一次摘要（本轮 84 次额外请求），端到端均值从 65 ms 涨到 98 ms。这里的实现是"每轮把全部被丢弃历史重新压一遍"，本身是 O(T²) 成本——**增量摘要才是工程上正确的做法**，本轮把它作为实现缺陷记录。
3. **`window` 在本任务上不掉质量，但这不能外推。** 因为累加任务只需要"上一轮的累计值"这一个状态，最近 2 轮里就有；换成长依赖任务（多跳问答、跨轮引用工具结果）时窗口会直接丢掉必需信息。**"窗口够用"是任务性质的结果，不是压缩的普遍结论。**
4. **"按需取回"把正确性押在模型行为上。** `external` 策略下模型只有 32/96 轮主动调用了取回工具，其余轮次凭残缺上下文作答；**接口存在不等于模型会用它**——这类策略需要配合强制的状态检查，而不是"需要时可调用"。

### 5. 缓存身份包含 adapter

LoRA 服务把"同一个 base 模型 + 不同 adapter"放进同一个引擎。缓存身份如果不含 adapter，就会出现**用 A 的 KV 回答 B 的请求**。跨 adapter 序列实测（同一段 prompt，依次换 adapter，不重置缓存）：

| 步骤 | 使用的 adapter | prompt token | 命中 token | 命中率 |
|---:|---|---:|---:|---:|
| 0 | `rev_a`（首次） | 272 | 0 | 0.000 |
| 1 | `rev_b`（紧接着） | 272 | 0 | 0.000 |
| 2 | `rev_a`（再次） | 272 | 256 | 0.941 |
| 3 | `rev_b`（再次） | 272 | 256 | 0.941 |
| 4 | base（无 adapter） | 272 | 0 | 0.000 |

`rev_b` 是 `rev_a` 的**同一份权重的拷贝**，只是注册名不同。第 1 步命中 0 说明：**缓存身份按 adapter 的注册标识区分，不按权重内容**——这对"不把旧版本缓存接到新模型"是保守而正确的一侧。量化配置、位置规则的变更同理：它们改变的是同一段文本对应的 KV，引擎把它们当不同身份，因此不会串用。

代价也要说清楚：**adapter 名一改，缓存立刻全部失效**。版本化 adapter 的部署如果每次发布都换名字，就等于每次发布都把缓存清空；要保持复用，应当让"语义未变"的版本沿用同一个注册名。

### 6. 分支、写时复制与引用计数

一条会话分叉成两条（Best-of-N、MCTS、多 agent 并行探索）时，两条分支共享同一段前缀。共享的代价落在引用计数上，收益落在命中上。用与引擎同构的块模型跑一条固定调度：父序列 P 建 4 个满块 → fork 出 B1、B2 → B1 改写自己的第 3 块 → 各分支陆续结束。

| 不变量 | 观测值 |
|---|---|
| fork 只加引用计数 | 第 1 次 fork 后首块引用计数 2（P+B1），第 2 次后 3（P+B1+B2） |
| 改写共享块必须写时复制 | 1 次 COW，新块引用计数 1，旧块计数降到 2 |
| 兄弟分支内容不被污染 | B1 第 3 块 = `1032…`，B2 第 3 块 = `32…`（原内容），两者不同 |
| 一支退出不释放共享前缀 | P 退出后 `free=0`、`live=5` |
| 不做 COW 会静默污染 | B2 第 3 块被改写成 `1032…`，与 B1 相同且不再是原内容 |

最后一行是这一节的重点：**没有引用计数的缓存不会报错，只会让兄弟分支读到别人的内容**。这类错误与浮点波动有本质区别——它是可复现的内容不一致，检测方式是对块内容做哈希对拍，而不是"重复运行看数值是否漂移"。反过来，正确实现下同一调度重跑应当逐比特一致，数值漂移只能来自浮点归约顺序。

扇出宽度决定可回收容量。共享前缀让每条分支都命中同样多的 token，但这些块在**所有**分支结束前都不可驱逐：

| 扇出 | fork 后首块引用计数 | 退掉除最后一条外全部分支后 | 仍在用的块 | 可驱逐块 | 每条分支命中 |
|---:|---:|---:|---:|---:|---:|
| 1 | 2 | 1 | 4 | 0 | 64 |
| 2 | 3 | 1 | 4 | 0 | 64 |
| 4 | 5 | 1 | 4 | 0 | 64 |
| 8 | 9 | 1 | 4 | 0 | 64 |

四条读法：

1. **命中收益与分支数无关**：每条分支都命中 64 token，扇出不会摊薄命中。
2. **容量占用与分支寿命绑定**：只要还有一条分支活着，共享前缀就一个块都回收不了。**并行探索的宽度直接换成 KV 压力**，这与 8.4 的混部容量是同一笔账。
3. **引用计数归零才是回收条件**，时间与优先级都不参与；这也是"取消一条分支"在 9.5 里必须传播到块释放的原因——不释放就只是把占用留给别人。
4. **写时复制只在改写共享块时发生**。满块在追加时不会被改写（新块一定新分配），所以 COW 的触发点是"往共享的未满块或分叉点之后追加"，不是每一次 append。

## 工程实现：vLLM 的前缀缓存与 dev 接口

### 源码解析

- **块粒度与链式哈希**：`vllm/config/cache.py:79` `DEFAULT_BLOCK_SIZE = 16`；`vllm/v1/core/kv_cache_utils.py:621` `hash_block_tokens(hash_function, parent_block_hash, curr_block_token_ids, extra_keys)` 要求满块，且把父块哈希链进去——这解释了为什么"插入 system 段"会让命中率归零，而"尾部追加"几乎不受影响。
- **命中查询**：`vllm/v1/core/kv_cache_manager.py:228` `get_computed_blocks` 返回 `(blocks, num_computed_tokens, shared_prefix_boundary)`。
- **清空缓存（dev 路由）**：`vllm/entrypoints/serve/dev/cache/api_router.py:20` 的 `POST /reset_prefix_cache`。**它默认不挂载**：需要启动时设 `VLLM_SERVER_DEV_MODE=1`，否则该路径返回 404。本轮实验第一次跑就踩到这个（`[warn] reset_prefix_cache status=404`），预测因此与引擎状态对不上；打开 dev 模式后 84/84 条精确相等。
- **容量口径**：同一份日志里的 `GPU KV cache size: 41,008 tokens`（util 0.45）与 `63,840 tokens`（util 0.55）是两个不同预算下的实测值——它们既是"能装多少会话"的上限，也是"压力多大才会驱逐"的门槛。

### 设计取舍

- **会话亲和 vs 无状态路由。** 亲和能把命中率稳定在 0.58–0.96（视历史组织方式），代价是负载不均与故障域绑定；无状态路由天然均衡，但**每一轮都要重算整个历史**。本实验的量级是"每轮多付 300–400 token 的 prefill"，会话越长差距越大。
- **按容量淘汰 vs 按时间淘汰。** 本引擎只有前者。按时间过期看起来"公平"，但会主动丢掉本来还能命中的 KV（§2 的 60 s 无压力行证明这些 KV 完全可用）。
- **迁移后重算 vs 迁移前搬运。** 搬运（8.6 的 CPU/远端层级）在网络与序列化上有成本，但比重算整个会话便宜——前提是有真实接口；没有接口时，"迁移"只能退化成重算。
- **adapter 身份按名字 vs 按内容。** 按内容更"聪明"（同一份权重的两个注册名可以共享），但要求逐字节比较权重、成本高且对量化/布局敏感；按名字保守但安全。本实验证明 vLLM 选了后者。

## 前沿

**会话亲和正在从"优化"变成"必需"。** 本实验里迁移一次就把逐轮复用从 0.58 打到 0；在 9.1 的 `codefix` 负载上，这意味着每轮多 300–400 token 的 prefill，12 轮会话就是 4 000 token 量级的重复计算。8.1 的路由器与 8.6 的存储层级因此不是"锦上添花"，而是让多轮负载可服务的前提。

**"缓存身份"的边界正在被版本化组件撑开。** 本章证明 adapter 的注册名参与身份；量化配置、位置规则、甚至工具 schema 的变更同理。这带来一个新的工程要求：**部署系统要能表达"哪些改动不改变 KV 语义"**，否则每次发布都要为清空缓存付一次全量重算。

**近似复用（片段级拼接与选择性重算）是下一个突破口。** 精确前缀复用要求"从头逐字相同"，而真实 RAG 每次注入的片段都不同。CacheBlend 一类方案尝试只重算被拼接位置的 KV；本章没有该接口的实测条件，保持 `UNVERIFIED`——它需要引擎暴露片段级 KV 的读写与重算入口。

## 陷阱

1. **以为"间隔久了缓存就没了"。** 本实验 60 s 无压力下命中率仍是 0.958；驱逐只由容量触发。
2. **把"有压力"当"压力够大"。** 压力是否致命取决于它相对 KV 容量的比例（本实验 24×1 500 对 41 008 token）。
3. **只报命中率不报 token 账。** 命中 0.958 对 0.000 背后是 15.5 对 391.5 的重算 token，而 e2e 只差几十毫秒——只看时间会得出"无所谓"。
4. **改写历史还想保住前缀。** 插入 system 段把命中率打到 0.064；裁剪 thinking 打到 0.556。任何中段修改都会截断共同前缀。
5. **拿 session ID 当 KV 等价的证据。** 同一个 session 的两轮请求，只要中间内容变了，前缀就断了；要预测命中，必须比 token 而不是比 ID。
6. **假设迁移只是"慢一点"。** 逐轮迁移把命中率打到 0，收益不是变少而是消失。
7. **假设 KV 复用是数值等价变换。** 同一请求命中缓存与全量 prefill 的贪心输出在 4 轮里有 1 轮不同。
8. **忘记 `/reset_prefix_cache` 需要 dev 模式。** 默认 404，代码不检查状态码就会"以为清了、其实没清"，预测与引擎状态立刻错位。
9. **把 adapter 名当无关细节。** 换名字等于清空缓存；同名换内容则会让身份失去保护。
10. **在没有取回接口时宣称做到了"CPU 取回"。** 本章的"取回"档位没有实测，只有"重算"与"驱逐后重算"两种真实数据。
11. **只比 prompt 长度就宣布压缩有效。** 本轮 `summary` 省 17% prompt 却丢掉一半正确率、还多出 84 次摘要请求。
12. **把"按需取回"当自动生效。** 状态外置后模型只有 32/96 轮主动取回；接口存在不等于模型会用。

## 自测题

1. 为什么"轮间等待 60 s"没有让缓存失效，而"插 24 条长请求"让它全部失效？
2. `append`、`mid_insert`、`trim_thinking` 三种历史的命中率分别是多少？差异来自哪一段文本？
3. 命中率 0.958 与 0.000 的 e2e 只差几十毫秒，为什么还不能说"缓存没用"？
4. 迁移一次为什么把命中率从 0.58 打到 0？
5. 为什么 `rev_b`（`rev_a` 的同一份权重拷贝）拿不到 `rev_a` 的缓存？这样设计的好处与代价是什么？
6. 同一请求"命中缓存"与"全量 prefill"为什么会输出不同 token？

::: fold 答案

1. 因为驱逐由容量触发而不是时间触发。vLLM 的前缀缓存按块管理并在容量满时 LRU 淘汰，没有 TTL；60 s 不来的会话只要没被挤掉就仍然命中。24 条各约 1 500 token 的请求把 41 008 token 的 KV 容量冲了一遍，于是所有会话的前缀都没了。
2. 0.634 / 0.064 / 0.556。`append` 只在尾部追加，共同前缀几乎全保留；`mid_insert` 把新证据写进 system 段，共同前缀退到 system 之前（只够一个块左右）；`trim_thinking` 改写历史里的 assistant 消息，在第一条 assistant 处断开，介于两者之间。
3. 因为这几毫秒只是本批会话（prompt 几百 token）的表象。真正的差别是每轮 15.5 对 391.5 token 的 prefill：会话越长、并发越高，这些 token 会直接变成 TTFT 与吞吐。判断缓存价值要看 token 与容量，并按 9.1 的方法放到真实负载上折价。
4. 前缀复用要求"这段前缀在这台机器上存在过"。迁移动把下一轮发到没有该会话前缀的副本，该副本必须从第 0 个 token 重新 prefill；一旦某轮不在原副本，后续轮次也不会自动恢复——命中率因此是 0 而不是下降一点。
5. 因为缓存身份包含 adapter 的注册标识，而不是权重内容。好处是不会把 A 的 KV 误用到 B 上（正确性优先）；代价是权重完全相同、只是改名/新版本也会让缓存全部失效，部署时需要刻意沿用注册名来保留复用。
6. 因为两条路径的数值计算不同：命中缓存的 prefill 只算新增部分、KV 从缓存读出，全量 prefill 一次算完整段；不同的 kernel、批次形状与累加顺序会带来微小浮点差异，贪心解码在边界情况下会把它放大成不同的 token。
