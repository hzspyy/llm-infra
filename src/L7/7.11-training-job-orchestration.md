## 心智模型：完成计算不等于提交进度

**关键要点**：

- 提交点由 checkpoint 协议定义，不由"进程还在跑"或"已经算完一批"定义。
- MFU 的分母是共同 step 窗口。每个 rank 的局部活动跨度只是诊断量。
- 准入策略的差别体现在同一作业集合的 makespan、空闲卡时与重放卡时上，需要一起报告。

本章使用真实本机子进程检查 watchdog、ACK 和提交协议，用离散事件模拟比较准入策略，用已有实测插桩事件检验时间线口径。worker 内只计算确定性标量状态；不把该协议实验当作 NN 训练、NCCL 故障恢复或生产调度器测量。

## 机制拆解与推导

### 作业与数据进度的状态归属

作业声明至少固定代码/环境版本、rank 拓扑、资源、数据版本、恢复入口、重试上限与超时策略。整组准入（gang admission）要让同步训练所需的 worker 一起满足资源条件；单个 rank 已启动而其它 rank 长期等待，通常不能形成有效训练进度。

| 状态 | owner | 提交/恢复原则 |
|---|---|---|
| PID、连接、进度时钟 | coordinator | 重启后重新建立，不从旧 PID 推断存活 |
| 正在处理的 sample IDs | worker / 数据分配器 | ACK 前后都可能失败，不能直接充当恢复游标 |
| 参数、optimizer、scheduler、scaler | learner | 必须属于同一逻辑更新点 |
| 已提交游标与样本计数 | checkpoint 协议 | 与模型状态一同发布 |
| rollout/teacher 请求 ID 和版本 | 对应服务协议 | 超时、重复回包与过期结果分别处理 |

普通 torchrun/Elastic 能启动和重启 worker，应用仍负责 checkpoint 和数据一致性。Kueue/JobSet 这类编排组件负责的是配额、队列与整组准入，不是训练状态：它们能让"整组一起启动"成立，但不会替你保证 optimizer、RNG 和已消费数据已经恢复。

### 三种准入策略的代价

在固定的 8 卡与作业集合上，三种策略给出不同的 makespan 与卡时账。作业集合是声明的合成假设：`J1-long-6cards`（6 卡、600 s、优先级 1、checkpoint 间隔 300 s）、`J2-low-4cards`（4 卡、300 s、优先级 0、间隔 100 s）、`J3-small-2cards`（2 卡、150 s、优先级 0、间隔 50 s，t=10 s 到达）、`J4-high-4cards`（4 卡、300 s、优先级 2、间隔 100 s，t=200 s 到达）。

| 策略 | makespan | 忙碌卡时 | 重放卡时 | 空闲卡时 | 利用率 | 高优先级作业排队 |
|---|---:|---:|---:|---:|---:|---:|
| FIFO 顺序准入 | 1050 s | 6300 | 0 | 2100 | 0.750 | 550 s |
| 整组准入 + 保守回填 | 900 s | 6300 | 0 | 900 | 0.875 | 400 s |
| 优先级抢占 | 1100 s | 7500 | 1200 | 1300 | 0.852 | 0 s |

FIFO 让 2 卡的空闲容量一直等到长作业结束；保守回填把 J3 放进这 2 张卡，makespan 从 1050 s 降到 900 s。抢占把 J4 的排队时间压到 0，代价是 J1 在 t=200 s 被抢占时丢掉 200 s 工作（6 卡 × 200 s = 1200 卡秒），makespan 反而增长到 1100 s。抢占是否值得取决于高优先级作业的价值与 checkpoint 间隔：若 J1 的间隔是 100 s 而不是 300 s，同样在 t=200 s 被抢占时损失为 0。

### 失败重放与 goodput

设窗口中处理了 $n_{physical}$ 个样本，新增提交 $n_{commit}$ 个有效样本，墙钟时间为 $T$：

$$throughput_{physical}=n_{physical}/T,\qquad goodput=n_{commit}/T.$$

失败前完成但尚未提交的工作可能再次执行，因此 $n_{physical}>n_{commit}$ 是合法现象。两个计数都应保留。这里的 goodput 是已提交处理进度，不自动代表模型质量提升；数据重复、错误 mask、scaler 跳步或退化训练都可能让"忙碌"与有效学习脱节。

本章协议先把完整候选 JSON 写入 `.pending`，通过同一文件系统的 rename 发布，再原子替换 latest 指针。coordinator 必须先收齐所有当前步 ACK。该实验验证进程故障下的可见性和重放，不验证掉电持久性、分布式文件系统的原子语义或 DCP 的内部协议。

### 时间线：共同 step 窗口与活动区间并集

同一 rank 的事件区间为 $I_i=[s_i,e_i]$：

$$T_{span}=\max_i e_i-\min_i s_i,\qquad T_{covered}=\left|\bigcup_i I_i\right|.$$

compute=[0,10] ms、comm=[5,15] ms 时两类事件各 10 ms，但并集是 15 ms：把两者相加会把重叠的 5 ms 算两次。没有被事件覆盖的区间只能叫"未归因"，不能自动叫 dataloader 气泡。

多 rank 时还要区分三个量。**共同 step 窗口** $T_{window}$ 由协调者时钟的步边界定义，是同步训练真正的墙钟分母；**活动区间并集** $T_{covered}$ 是各 rank 真正在工作的区间；**最长局部跨度** $T_{local\_max}$ 只是单 rank 的诊断值。两个 rank 的活动错位时，"每个 rank 各自忙 100 ms"并不等于"这一步 100 ms"——本机构造的两 rank fixture 里，共同窗口是 190 ms，而最长局部跨度只有 100 ms，用后者当分母会把 MFU 从 6.54% 高估到 12.42%（1.9 倍）。所以分析器在缺少共同窗口时直接输出 `null`，不自行补一个分母。

### MFU 的公式与限制

给定同一窗口内模型工作量的估计 $F_{model}$、设备数 $N$、对应 dtype/稀疏设置的单设备峰值 $P_{peak}$ 和共同 step 窗口 $T_{window}$：

$$MFU=\frac{F_{model}}{NP_{peak}T_{window}}.$$

稠密 Transformer 常用 $6P\times tokens$ 估计训练 FLOPs，全重算有时用额外 $2P\times tokens$ 估计。它们省略部分 attention、embedding、非线性与具体重算结构，不能直接充当硬件计数器读数。HFU 若用估计的执行 FLOPs，必须标为估算；若声称实测硬件利用率，则需要对应计数器。

padding token 参与计算但不一定参与 loss；teacher/critic、rollout 和 checkpoint 可能属于完整作业成本，却不在 learner 的 $6P$ 分子里。当设备峰值、FLOP 模型或共同窗口任一缺失时，本章分析器不输出 MFU 数值。

### 从进程 API 到可检查协议

`training_job_simulator.py` 的 `ProcessCoordinator.start` 调用 `multiprocessing.get_context('spawn').Process.start()`，worker 首条 ready 消息返回真实 PID。`execute` 收集 progress/ACK，监控进程存活与 0.5 秒进度 deadline；`stop` 先发送 stop，再 join，必要时 terminate/kill，并确认所有创建过的子进程已退出。它不会扫描并终止其它作业的进程。

{{src:labs/L7/training_job_simulator.py:62-103}}

发布协议只写 `.pending`、rename 到正式文件、原子替换 latest 指针三步；失败注入在 rename 之前抛出，保证未完成的 checkpoint 不会被 latest 选中。

### 分析器的时间窗口契约

`training_trace_analysis.py` 的 `analyze_events` 先校验输入来源类型与时间有限性，再逐 rank 计算跨度、并集与未归因区间。只有当输入提供 `step_window`（协调者时钟的 `start_ms`/`end_ms`）时，才用它作 MFU 分母；事件落在窗口之外、窗口短于任何 rank 的局部活动跨度都会直接报错。

{{src:labs/L7/training_trace_analysis.py:239-296}}

### 设计取舍

父进程集中提交容易检查一致性，但父进程自身的高可用是另一项任务。短 deadline 能快速发现无进展，也容易把正常慢步骤当故障，应按实际工作分布设定。同步全组恢复降低状态组合复杂度，却会重复计算已完成但未提交的工作。把"最长局部跨度"当全局窗口会让 MFU 好看而失去意义，因此宁可返回 `null`。异步 teacher/reward 服务还需独立的请求去重与版本协议；本章的超时用子进程内延迟模拟，没有调用真实远程服务。

## 工程实现：小进程与分析器

`training_job_simulator.py` 的 worker 将收到的 sample IDs 求和加入标量状态；两 rank 每步各处理两个 ID，共两步。第二步注入一次故障，随后从 latest 恢复重试。检查器断言最终 committed IDs 为 0–7、rank states 为 `[10,18]`，并保留所有 physical IDs。

`training_job_manifest.py` 声明合法作业（6 节点 × 8 卡 = 48 rank）并推导 rank → 环境变量映射，同时用五个反例检查非法配置。`training_scheduling_budget.py` 输出准入策略对照与公开配方预算账。`training_trace_analysis.py` 必须显式选择 `--input`、`--cross-rank-demo` 或 `--synthetic-demo` 之一。

### 作业清单与环境契约

合法清单一次完整流转：`PENDING → ADMITTED → INITIALIZING → RUNNING → FAILED_TRANSIENT → RESTARTING → RESUMING → RUNNING → COMPLETED`，world_size=48，rank 0 与 rank 47 的环境分别是 `RANK=0/LOCAL_RANK=0` 与 `RANK=47/LOCAL_RANK=7`。五个反例各自停在校验阶段并给出具体原因：节点数为 0、每节点 3 卡、未知 rendezvous 后端、缺恢复目录、`--nproc_per_node` 与资源声明不一致。

### 进程故障实测

| 注入 | 恢复次数 | physical ID 数 | 重复数 | 最终提交 | 存活子进程 |
|---|---:|---:|---:|---|---|
| 子进程 exit(17) | 1 | 10 | 2 | 0–7 | 无 |
| rank 无进展超时 | 1 | 10 | 2 | 0–7 | 无 |
| 非法 batch | 1 | 10 | 2 | 0–7 | 无 |
| checkpoint 发布前中断 | 1 | 12 | 4 | 0–7 | 无 |
| mock reward 超时 | 1 | 10 | 2 | 0–7 | 无 |
| mock teacher 超时 | 1 | 10 | 2 | 0–7 | 无 |

发布中断时所有 worker 已 ACK，所以两个 rank 的未提交工作都会重放，重复数为 4；其它故障只重放已 ACK 的部分。未 ACK 的真实计算不能凭空恢复计数，因此 physical 字段的观测边界也需明确。

### 真实事件与假设预算分开

RTX 5090 D、SmolLM2-360M、FP32 第二次更新的插桩事件跨度为 **134.8905 ms**（forward 41.5728 ms、backward/unscale 62.6010 ms、diagnostics/optimizer 30.7167 ms），三个区间在该采集协议下相邻，并集等于跨度、未归因为 0 ms。这份输入没有共同 step 窗口，也没有设备峰值，因此 MFU 输出 `null`，不做任何分母假设。

`--synthetic-demo` 的 3B、64 设备、阶段时长都是预算假设，例中 1285 ms 与 MFU=46.41% 来自这些常量的算式，不是 64 张 H100 的运行结果。`--cross-rank-demo` 是专门暴露口径错误的构造：局部跨度 100 ms、共同窗口 190 ms、并集 180 ms、窗口内未归因 10 ms。

## 完整教学项目：把实际成本汇总起来（7.11-I）

I 任务要求把各教学项目从数据准备到部署的实际时间、峰值与存储汇总，并用 pilot 预测与实际预算对照。`labs/L7/teaching_cost_report.py` 读各阶段的 `run.json` 与目录字节，输出一张表；GPU 小时按单卡墙钟折算，不把 CPU 数据准备混进去。

| 阶段 | step | 有效 token | 墙钟 s | GPU 小时 | 峰值 MiB | checkpoint 字节 |
|---|---:|---:|---:|---:|---:|---:|
| 预训练（6000 步） | 6000 | 98,112,000 | 486.6 | 0.1352 | 8633 | 2,163,400,150 |
| SFT（900 步） | 900 | 5,823,900 | 62.4 | 0.0173 | 4351 | 1,888,057,472 |
| pilot（预算测算） | 200 | 3,270,400 | 17.5 | 0.0049 | 8633 | 1,612,719,406 |
| **合计** | | | **566.5** | **0.1574** | | **5,664,177,028** |

三件事只有分开记才看得见：

1. **"有效 token"必须按阶段换分母。** 预训练报的是 next-token target（98,112,000），SFT 报的是回答 token（5,823,900）；把 SFT 的 3.87M 输入 token 当分母会虚高约 1.7 倍。
2. **峰值由常驻状态决定，不随阶段线性变化。** 预训练 8633 MiB 几乎全程恒定；SFT 只有 4351 MiB，因为模型相同而序列更短、batch 更小。按"训练越长显存越高"估算会估错方向。
3. **checkpoint 字节和计算量不是一回事。** 预训练 6000 步产生 2.16 GB（`last.pt` 786.7 MB + `best.pt` 275.3 MB + 4 个快照），SFT 900 步产生 1.89 GB——步数少 6.7 倍，字节只少 13%，因为每个 checkpoint 的大小由参数量决定。

预算对照：pilot 用 200 步预测 98.3M token 的主运行约 8.2 分钟，实际 8.11 分钟，误差 1.1%；两阶段合计 0.1525 GPU 小时，只有规划上限 12 小时的 1.3%。**这不是"预算定得太松"，而是教学项目的规模本来就让预算剩很多**：共同任务把文本预训练定在 20M–100M token，6000 步正好落在上沿；剩下的额度按计划留给后训练分支（LoRA/DPO、蒸馏、RL）与视觉适配，各自的预算单列。

数据侧：7.8-I 的两份产品共 182,743,762 B（171 MB），其中预训练分片 171 MB、SFT 张量 11.5 MB；准备时间 CPU 约 2 分钟 + 14 秒。检查点 5.66 GB 全部留在学习盘，进仓库的只有 `manifest.json`、`run.json`、`metrics.jsonl` 与生成样例（合计约 1.5 MB）。

还有一项没有计入：被 `SIGKILL` 打断的那次运行（[7.4-H](7.4-data-ckpt-fault.html)）耗掉 15 s、恢复后重放约 54 步。它的 `run.json` 只记录恢复进程的 55.98 s，被杀进程的 15 s 不在其中——**按 `run.json` 求和会漏掉失败重跑的成本**，这正是为什么表里单独列 pilot 而把失败重跑写在正文。

## 前沿与规模决策

### SmolLM3 配方的预算账

三份 Nanotron YAML 都写 `micro_batch_size=3`、`batch_accumulation_per_replica=1`、`sequence_length=4096`、`train_steps=4,720,000`、`checkpoint_interval=2000`；DP/TP 不在 YAML 里，由 run 名的 48 节点 × 8 卡与 TP=2 推出 DP=192，于是全局 batch 为 576 个样本、11.14 T token（4,720,000 × 576 × 4096）。阶段区间按 YAML 的 `start_training_step` 切分（stage3 那份同时给出 stage2 与 decay 起点）：stable 1–3,450,000 步 = 8.14 T token，stage2 3,450,001–4,198,000 步 = 1.77 T token，decay 4,198,001–4,720,000 步 = 1.23 T token。

在声明的设备假设下（3 B 参数、384 张卡、989 TFLOP/s 单卡峰值 BF16、40% MFU），$6P$ 估计给出 2.004e23 FLOPs：墙钟约 366.5 小时（15.3 天），合计约 14.07 万 GPU 小时。checkpoint 每 2000 步一次共 2360 次，按 bf16 参数 + fp32 master + Adam m/v 估计每次 42 GB，整轮写入约 99.1 TB。

| 项 | 值（声明假设下） |
|---|---:|
| 全局 batch | 576 样本（3 × 1 × 192） |
| 总 token / 总 FLOPs（6P） | 1.114e13 / 2.004e23 |
| 墙钟 / GPU 小时 | 366.5 h / 140,747 GPU·h |
| checkpoint 次数 / 单次 / 合计 | 2360 / 42 GB / 99.1 TB |
| 单次故障平均重放（间隔 2000 步） | 1000 步 = 2.36e9 token = 29.8 GPU·h |

两个可计算的决策：

- **checkpoint 间隔**。间隔从 2000 步加到 4000 步，写入量减半（99.1 → 49.6 TB），单次故障平均重放从 29.8 增到 59.6 GPU·h。若故障率是每 10 万步一次，整轮 4.72M 步约 47 次故障，多付约 1.41 千 GPU·h（约为 14.07 万 GPU·h 预算的 1.0%）。所以这个决定取决于存储带宽与故障分布，而不是"越频繁越安全"。
- **准入策略**。碎片化容量（本机例中 2 张空闲卡）用保守回填消化，makespan 从 1050 s 降到 900 s；抢占留给真正有优先级价值的作业，并把可被抢占作业的 checkpoint 间隔压到小于其被抢占的典型时长，让重放损失接近 0。

### 另三条公开流程的字段账（7.11-G）

SmolLM3 之所以能算出墙钟，是因为它公布了三份训练 YAML 与启动规模。另外三条流程没有公布作者机器的迭代时间或训练日志，**能复算的只有配置里写死的量**：token 预算、可训练参数组、checkpoint 次数、奖励调用量与公开程度。`labs/L7/training_scheduling_budget.py --section public-flows` 只读仓库内的配置快照（Cosmos SFT 的 TOML、SpecForge 的 Eagle3/DFlash 配方与草稿 config、CosyVoice2 GRPO 的 `run.sh`），输出下面三张表，不产生任何 GPU 小时估计。

Cosmos3-Edge 的两条 SFT 配方分别是生成分支（`task=vfm`）与 Reasoner 分支（`task=vlm`）：

| 项 | vision_sft_edge（生成） | videophy2_sft_edge（Reasoner） |
|---|---|---|
| 优化器覆盖的参数组 | `moe_gen`、`time_embedder`、`vae2llm`、`llm2vae`、`k_norm_und_for_gen` | 未指定，Optimizer 覆盖全部参数 |
| lr / weight decay | $1\times10^{-4}$ / 0 | $1\times10^{-6}$ / 0.1 |
| 每 micro-batch 预算 | 45,056 打包 token | 1 样本 × 16,000 序列长度 |
| grad accum / max_iter | 2 / 500 | 8 / 50 |
| 整轮 token 上界（每 rank） | 45.06 M | 6.4 M |
| 精度 / 激活重算 / compile / EMA | bf16 / full / 开 / 开 | bf16 / full / 关 / 关 |
| save_iter / 整轮 checkpoint 次数 | 100 / 5 | 100 / 1（只在最后） |

生成分支只把生成路径与两个 connector、时间嵌入放进优化器，Reasoner 分支没有参数组限制——"同一个模型的两条 SFT 配方更新对象不同"在配置里是显式的，不需要从 loss 反推。Reasoner 分支的 `max_iter=50` 小于它的 `save_iter=100`，中途不落盘；作者没有公布单迭代时间，因此"更密保存的收益"在本材料里无法定量。

SpecForge 的 Eagle3 配方（Qwen3-8B target + 单层草稿）：

| 项 | 值 |
|---|---|
| target / 草稿结构 | `Qwen/Qwen3-8B`（词表 151,936）/ 1 层、hidden 4096、草稿词表 32,000 |
| epochs / max_steps / batch / max_length | 10 / 10,000 / 1 / 4096 |
| 目标模型 token 预算 | 40.96 M（10,000 × 1 × 4096） |
| 每 epoch 样本量（隐含） | 1,000 |
| save_interval / checkpoint 次数 | 1000 / 10 |
| 部署模式 / trainer rank | disaggregated / 1 节点 1 进程 |

batch=1、length 4096 意味着每个 step 触发一次目标模型前向；同一份数据训 10 个 epoch，把特征离线预生成一次即可复用，目标前向从 10,000 次降到 1,000 次（省 90%）。这是本章第二个可计算的决策，代价写在"陷阱"里：缓存身份（模型 revision、模板、层号）一变就要重跑目标模型。

CosyVoice2 的 GRPO 配方：

| 项 | 值 |
|---|---|
| 训练样本 / epoch | 80,000 / 1 |
| GPU / micro batch / train batch | 8 / 4 / 32 |
| rollout n / prompt / response 长度 | 4 / 1024 / 512 |
| 采样总数（含 n 与 epoch） | 320,000 |
| 奖励服务 | Triton 上的 token2wav + SenseVoice ASR 串联，独立占 8 个设备 |
| save_freq / test_freq | 100 / 100 |

奖励服务单独占 8 个设备，等于训练集群的 100%——这条配方把三分之一以上的机器预算花在打分上，而奖励又来自第三方 codec/ASR。奖励调用量是 80,000 × 4 × 1 = 320,000 次；把它缩容或与训练共置可以省设备，代价是拉长奖励等待、放大策略陈旧度。作者没有公布奖励服务时延与训练曲线，这条只能作为配置层面的取舍。

三条流程的公开程度需要与数字一起读：Cosmos、SpecForge、CosyVoice 都公开了配置与（部分）权重，但都没有公布作者机器的迭代墙钟与完整训练日志；SpecForge 的 Qwen3-8B 草稿权重是公开发布物，Cosmos3-Edge 的权重可下载，CosyVoice2 GRPO 只有配方、基础权重与奖励实现。**因此本节的数字是字段账，不是成本账**；教学项目的成本来自上文 7.11-I 的实测，两者不能混记。

## 陷阱

- **用最长局部跨度当全局窗口**。同步训练的墙钟由共同 step 边界决定；本机构造里两者差 1.9 倍。缺少窗口时应输出 `null`，而不是挑一个更好看的分母。
- **把不同 YAML 相加**。三份 SmolLM3 配置的 `train_steps` 都是 4,720,000，它们描述同一次训练的不同阶段，相加会得到 3 倍 token 预算。
- **把类别时间相加**。重叠区间只能取并集，未被覆盖的部分叫未归因。
- **把"spawn 日志"当进程证据**。必须有真实 PID 与退出码；"checkpoint 文件存在"也不等于它可恢复。
- **把高 GPU 使用率当有效进度**。要看已提交更新与 goodput，而不是利用率或队列长度。
- **把配额调度当状态恢复**。Kueue/JobSet/torchrun 能保证整组启动与重启，但 optimizer、RNG、数据游标仍由应用负责。

诊断顺序：loss 异常查 mask 与数值；step 慢查未插桩基准与时间线；rank 卡住查 collective 顺序与进程状态；恢复不一致查已提交游标与 optimizer。证据不足时保留未归因，不把预算常量改名为测量。

## 自测题

1. 一批数据被处理两次，为什么最终提交计数仍可能正确？

::: details 答案

第一次处理可能发生在尚未提交的失败区间。恢复后重放该区间，只有与合法模型状态共同提交的 IDs 计入有效进度。本章保留 physical 重复与 committed 无重复两个字段：注入发布前中断时 physical 重复数为 4，committed 仍是 0–7。

:::

2. 两个 rank 各忙 100 ms、活动错开，这一步的 MFU 分母应该取多少？

::: details 答案

取协调者时钟定义共同 step 窗口。本机 fixture 中窗口是 190 ms，活动并集 180 ms，窗口内还有 10 ms 未归因；用最长局部跨度 100 ms 会把 MFU 高估 1.9 倍。没有窗口时分析器输出 `null`。

:::

3. compute 0–10 ms 与 comm 5–15 ms，总步长是多少？

::: details 答案

只覆盖这两个区间时跨度与并集均为 15 ms，类别时间之和为 20 ms。不能把重叠的 5 ms 再加到总耗时。

:::

4. 6P、8P 和一段 trace 足够证明硬件 HFU 吗？

::: details 答案

不够。6P/8P 是模型/重算 FLOP 近似，trace 是时间材料；只有匹配设备峰值与任务口径才能给出估算，硬件计数仍需要独立采集。MFU 也不衡量任务质量。

:::

5. 抢占一个 checkpoint 间隔 300 s、已运行 200 s 的作业会丢多少工作？怎样把损失压到接近 0？

::: details 答案

已保存的检查点进度是 0，损失 200 s，按 6 卡计是 1200 卡秒。把间隔压到 100 s 后，同一时刻已保存 200 s，损失为 0。代价是 checkpoint 次数增加，需要与写入带宽和存储预算一起权衡。

:::
