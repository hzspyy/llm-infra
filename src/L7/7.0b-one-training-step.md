前一章把反向传播拆到了 Node 和 Edge 的粒度。这一章往上走一层：一个 batch 从样本 ID 出发，怎样变成一个可求导的标量，再怎样落成一次可以被恢复的参数更新。

loss 是个有限数并不说明训练语义正确。同一份 batch 在三种常见写法下会得到三个不同的优化目标，而它们的 loss 数值只差 0.4%。

## 机制拆解与推导

### 对齐只做一次

因果语言模型用位置 $t$ 的输出预测位置 $t+1$ 的 token。HF 风格的 labels 与 input 同位置，位移在 loss 内部完成；调用方若已经手工移过一位，就不能再交给会自己移位的接口。

transformers 的做法是给 labels 右补一个 `ignore_index` 再整体左移，logits 不切片：

```python
labels = F.pad(labels, (0, 1), value=-100)
shift_labels = labels[..., 1:]
```

于是一条 $n$ 个 token 的序列贡献 $n-1$ 个 target：最后一个 token 只当输入，没有"下一个"可预测。TinyLM 上三条长度 5/3/6 的样本给出 $4+2+5=11$ 个 target；把 labels 预先移一位再送进同一接口，目标整体错一位，有效数掉到 7，loss 从 3.0658 变成 3.0973——一个完全看不出异常的数。

`torch.nn.functional.cross_entropy` 本身不做任何 shift，它只认 `ignore_index`。

### 可见范围与监督范围是两件事

attention mask 决定哪些位置进入 softmax，loss mask 决定哪些预测计入目标。两者取值可以完全不同，也必须分开检查。

右 padding 的因果模型有一个容易误导的性质：pad 在序列右侧，因果 mask 本来就挡住了它们，缺 attention mask 对有效位置的 logits **没有影响**（实测最大差 0.000e+00）。同一段序列改成左 padding，不传 attention mask 时有效位置的 logits 最大差 2.51——pad 在左边，因果 mask 挡不住。

SFT 屏蔽 prompt 只改监督范围。屏蔽 s2 的前 3 个 prompt 位置后 $N$ 从 11 降到 9，但**位置 2 仍然在监督范围内**：它的 shift 目标是第一个 answer token。prompt 的最后一个位置是"用最后一段 prompt 预测第一个回答 token"，屏蔽必须止于它之前。

### 分母是目标的一部分

等 token 权重的目标是

$$L=\frac{1}{N}\sum_{i=1}^{N}\ell_i,\qquad N=\#\{\text{loss mask 为真的 shift 位置}\}.$$

连续目标共用同一套接口，只是有效元素换成坐标或帧：

$$L=\frac{1}{N_{\text{coord}}}\sum m\,\lVert v_\theta(x_t,t)-u\rVert^2 .$$

二维 flow matching 的小例里，9 个有效帧对应 18 个有效坐标，按坐标平均得 1.9029，按帧平均得 3.8058，正好差一个坐标数。换分母等价于把学习率乘上坐标数：梯度方向不变，步长变。同一 batch 的 token CE 是 3.0658 nats/token，与这两个 MSE 没有可比性——它们只共享"Σ 目标项 / 有效元素数"这套系统接口。

$N=0$ 是一个必须显式处理的状态。`cross_entropy(reduction='mean')` 在全屏蔽时返回 `nan`，一次 backward 就会把全部梯度污染掉；正确写法是先算 Σ 和 $N$，再按整步协议决定跳过还是参与归约。

### 累积：三条路径，两个目标

把全局 batch 切成 $M$ 份 microbatch，第 $m$ 份的有效数为 $N_m$、目标项之和为 $S_m$。正确的等 token 权重目标是

$$L=\frac{\sum_m S_m}{\sum_m N_m},$$

对应的实现是每份 backward 前除以同一个 $N_{\text{total}}$。而另一种常见写法是把每份自己的均值等权相加：

$$\tilde L=\frac{1}{M}\sum_m \frac{S_m}{N_m}.$$

两者给每个 target token 的权重分别是 $1/N_{\text{total}}$ 和 $1/(M N_m)$。TinyLM 上四份有效数为 6/4/3/5 时：

| microbatch | $N_m$ | 等 token 权重 $1/N_{\text{total}}$ | 每份等权 $1/(M N_m)$ |
|---|---:|---:|---:|
| 0 | 6 | 0.05556 | 0.04167 |
| 1 | 4 | 0.05556 | 0.06250 |
| 2 | 3 | 0.05556 | 0.08333 |
| 3 | 5 | 0.05556 | 0.05000 |

短 microbatch 里的每个 token 被放大。实测三条路径：直接大 batch 与全局分母累积的梯度最大差 $2.8\times10^{-16}$（FP64 噪声），与每份等权的梯度最大差 $1.28\times10^{-1}$。把四份长度改成相同，后者立刻与前者重合。

**等价条件只有一个**：所有 $N_m$ 相等。定长打包的预训练天然满足，变长 SFT、多模态和 packing 边界都不满足。

### 顺序不能换的三处

**dropout 与 RNG。** 分母只管权重。同一批数据切成四份前向，抽到的 dropout 掩码和一次大 batch 不同：实测在分母完全正确的前提下，梯度最大差仍有 1.66；关掉 dropout 后回到 $2.8\times10^{-16}$。

**clip 的位置。** 窗口末尾一次 global clip 量到的 total_norm 是 2.6775；改成每份 microbatch 各 clip 一次，得到四个 1.12/1.52/1.25/2.21，最终梯度差 $6.0\times10^{-2}$。逐份裁剪改的是各 microbatch 的相对权重，窗口末尾的全局范数不再是被裁剪的对象。

**scheduler 的时钟。** 同样 3 次 optimizer 更新，按 optimizer step 推进得到 LR 0.00730，按 microbatch 推进得到 0.00100（`last_epoch` 3 对 12）。accumulation 数一变学习率曲线就跟着变。

### 从梯度到参数

顺序是：清梯度 → 按目标累积梯度 → 必要的跨 rank 归约与 unscale → finite 检查 → global clip → `optimizer.step()` → 推进 scheduler 与 scaler。

`clip_grad_norm_` 先把各参数梯度的二范数拼成一个向量再取二范数，然后乘上 $\min(1,\ \text{max\_norm}/(\text{total}+10^{-6}))$。TinyLM 上手算与 PyTorch 返回逐位相同（2.7970997585），系数 0.3575。

AdamW 的 decoupled weight decay 直接乘在参数上，不进 $m$、$v$：

$$p \leftarrow p(1-\eta\lambda),\quad
m\leftarrow\beta_1 m+(1-\beta_1)g,\quad
v\leftarrow\beta_2 v+(1-\beta_2)g^2,\quad
p\leftarrow p-\frac{\eta}{1-\beta_1^k}\cdot\frac{m}{\sqrt{v}/\sqrt{1-\beta_2^k}+\epsilon}.$$

按这个公式手写，两次更新后与 `torch.optim.AdamW` 的参数最大差 $1.7\times10^{-16}$、$m$ 差 $1.7\times10^{-17}$；改用 PyTorch 的 `lerp_`/`addcdiv_` 顺序则逐位相同（差 0）。数学等价与浮点顺序一致是两件事，FP64 上差 $10^{-17}$，BF16 上不会这么小（见 [7.9](7.9-optimizer-mixed-precision.html)）。

把同样的 `weight_decay` 交给 `torch.optim.Adam`，一次更新后参数最大差 $2.0\times10^{-2}$：L2 正则把 $\lambda p$ 加进梯度，随后被 $\sqrt{v}$ 缩放，有效衰减强度随梯度历史变化，不是同一个目标。

### 起点、接续与"一致"的定义

五种启动方式共用同一条流水线，区别只在参数来源、`requires_grad` 划分和监督定义：

| 启动方式 | 参数来源 | 可训练 / 总参数 | optimizer 参数组 | 首次 step 后有状态的张量 |
|---|---|---:|---:|---:|
| 从零训练 | 按初始化分布采样 | 664 / 664 | 8 | 8 |
| 加载权重 | 已有 checkpoint 的权重 | 664 / 664 | 8 | 8 |
| 冻结主干 | 同上，只解冻 projector | 136 / 664 | 2 | 2 |
| LoRA | base 全冻结，新增 A/B | 64 / 728 | 2 | 2 |
| teacher/student | 学生取已有权重，teacher 另一份且只前向 | 664 / 664 | 8 | 8 |

optimizer 状态在第一次 `step()` 时按参数组现场创建；冻结的参数既不产生梯度也不占状态。LoRA 的 $B$ 初始化为 0，第一次更新只有 `qkv.B` 变化——$A$ 的梯度正比于 $B$，此时为 0。

严格恢复要求把**参数、m/v/step、scheduler 计数、RNG、数据游标**一起还原。逐项移除一个，第一个被破坏的不变量各不相同：

| 移除项 | 第一个不一致的量 | 差值 |
|---|---|---|
| 数据游标 | 第 2 步的样本 ID（b1 → b0） | — |
| RNG | 第 2 步的 loss | 1.980e-01 |
| scheduler | 第 3 步的 lr | 8.889e-05 |
| m/v/step | 第 2 步的参数 | 7.230e-03 |

顺序是固定的：游标错了在样本 ID 上就能看见；RNG 错了要到 loss 才暴露；scheduler 错了 loss、梯度和当前 LR 都正确，下一步的 LR 才偏；optimizer 状态错了前四项全部正确，第一次参数写回才出现差异。**只比一次 forward loss 的恢复检查正好漏掉最后一类。**

学习率本身存在 `optimizer.state_dict()['param_groups']` 里，scheduler 的 `state_dict` 只有 `last_epoch` 一类计数，两者缺一都还原不出 LR 曲线。

FP16 训练还有第六项：`GradScaler` 的当前 scale 与连续成功计数。这份 CPU FP32 参照里不存在这个状态，它的恢复语义与跳步判据在 [7.9](7.9-optimizer-mixed-precision.html)。

只加载权重是完全合法的 fine-tuning 初始化，但它不满足上面任何一项：样本从头取、LR 回到调度起点、$m$ 从 0 起步。把它当成 resume 不会报任何错。

## 工程实现：源码解析

### 同一个 batch，三个框架三种分母

**transformers v5.17.0** 用 `num_items_in_batch` 是否给出来切换 reduction：

{{src:results/local/7.0b/20260915-one-step/source/transformers/src/transformers/loss/loss_utils.py:32-46}}

直接调用 `model(input_ids=..., labels=...)` 不会带这个参数，拿到的就是**这一次调用内部**的均值。HF `Trainer` 在累积窗口开始时统计整窗口的有效 token 数并逐次传入，才把分母变成全局的。`ForCausalLMLoss:61-64` 是前面那两行 pad-then-shift。

**Nanotron** 的语言模型 loss 固定按本 microbatch 的 `label_mask` 求均值：

{{src:results/local/7.0b/20260915-one-step/source/nanotron/src/nanotron/models/qwen.py:853-873}}

累积窗口的归一化在 pipeline engine 里，是对 microbatch 个数的等权平均：

{{src:results/local/7.0b/20260915-one-step/source/nanotron/src/nanotron/parallel/pipeline_parallel/engine.py:53-55}}

两处合起来正是 $\tilde L=\frac{1}{M}\sum_m S_m/N_m$。SmolLM3 的预训练配方用定长 4096 打包，各 microbatch 的 `label_mask.sum()` 相等，这条路径与等 token 权重重合；换到变长样本就不再重合。

**TorchTitan** 走另一条路：先把整个累积窗口的 `num_valid_tokens` 取完并跨 DP 求和，再用这个全局计数归一化。

{{src:results/local/7.3/20260914-review-fixes/additional-source/torchtitan/torchtitan/trainer.py:883-912}}

| 框架 | 默认分母 | 与等 token 权重一致的条件 |
|---|---|---|
| transformers 直接调用 `forward` | 本次调用的有效 token 数 | 只有一个 microbatch，或各 microbatch 有效数相同 |
| transformers `Trainer` | 窗口内全局有效 token 数（显式传入） | 总是一致 |
| Nanotron Qwen2 | 本 microbatch 有效数，再对 $M$ 等权平均 | 各 microbatch 有效数相同 |
| TorchTitan | 窗口内、跨 DP 的全局有效 token 数 | 总是一致 |

这不是"谁对谁错"：按样本等权也是一种合法目标。要求只有一条——分母必须是被声明过的目标的一部分，而不是实现细节的副产品。

### 一次更新真正涉及的状态

SmolLM3 的配方写着 `dtype: bfloat16` 和 `accumulate_grad_in_fp32: true`。后者在 Nanotron 里展开成一份 FP32 参数副本加一份 FP32 梯度缓冲：

{{src:results/local/7.0b/20260915-one-step/source/nanotron/src/nanotron/optim/gradient_accumulator.py:214-239}}

半精度参数的 `.grad` 累加进 FP32 缓冲后立即置 `None`（`:226`），optimizer 拿到的是挂在 FP32 副本上的梯度（`:239`）。于是每个参数的常驻训练状态是 bf16 参数 2 B + FP32 master 4 B + FP32 梯度缓冲 4 B + `exp_avg` 4 B + `exp_avg_sq` 4 B = 18 B。3.075 B 参数对应 51.55 GiB，`zero_stage: 0` 意味着这份状态在 192 个 DP rank 上完整复制，只按 `tp: 2` 切一半，每 rank 25.78 GiB。

### 设计取舍

**按 token 平均 vs 按样本平均。** 前者让每个监督位置等权，代价是必须把有效数纳入通信与流水（TorchTitan 为此多做一次跨 DP 求和，并刻意把计数留在设备上避免 CPU 同步）。后者实现简单、无需额外归约，但长样本里的每个 token 被系统性地降权。选哪个都行，写清楚即可。

**累积 vs 更大的 microbatch。** 累积用更多次前向/反向和调度开销，换更小的激活工作集；它不减少参数与 optimizer 状态，也不改变 scheduler 的时钟。流水并行同样在调度 microbatch，两者可以共存。

**保存多少状态。** 参数是最小集合，能让模型可用；加上 m/v/step 才能接续同一条优化轨迹；再加 RNG 与数据游标才能逐元素复现。每往上一级都增加容量与 I/O，收益要和"重放这段训练要花多少钱"一起算。分布式保存、异步暂存与原子提交在 [7.4](7.4-data-ckpt-fault.html)。

## 前沿

分母的定义正在随训练形态变复杂。packing 把多篇文档拼进同一条序列后，"有效元素"要同时扣掉文档边界和 padding，`cu_seqlens` 与 loss mask 必须来自同一份切分（[7.8](7.8-training-data-engineering.html)）。多模态联合训练里，文本 token、图像 patch、音频帧和动作步的"一个有效元素"根本不是同一个单位，多 loss 加权前必须各自归一化（[7.10](7.10-multimodal-training-orchestration.html)）。RL 的 token 级与序列级平均对应不同的策略梯度估计（[7.6](7.6-rl-infra-rollout.html)）。

状态一侧同样在扩张：FP8/FP4 训练额外引入 amax 与 scale 需要保存（[7.9](7.9-optimizer-mixed-precision.html)），FSDP2 与 DCP 把"一份 optimizer 状态"变成跨 rank 的分片集合（[7.2](7.2-training-parallelism.html)、[7.4](7.4-data-ckpt-fault.html)）。这两条线都不改变本章的判据：分母是目标的一部分，一致 checkpoint 是"同一次更新之后的那一整组状态"。

## 陷阱

### 陷阱 1：shift 做了两次

labels 预先移位后又交给会自己移位的接口，整条序列错一位，$N$ 少一个，loss 仍然是有限数。判据是打印逐位置的 `(input_id, shift 目标)` 对，而不是看 loss 是否"合理"。

### 陷阱 2：把 loss mask 和 attention mask 当成一件事

右 padding 的因果模型会掩盖这个错误——缺 attention mask 时有效位置的 logits 一点不变。换成左 padding 或双向编码器就会暴露。

### 陷阱 3：用 pad token ID 屏蔽 labels

很多 tokenizer 把 `pad_token` 设成 `eos_token`。用 token ID 匹配来生成 loss mask 会顺手把序列真正的 EOS 也屏蔽掉，模型学不会停。按 `attention_mask == 0` 生成。

### 陷阱 4：把每份 microbatch 的 mean 再平均

只有各份有效数相同才等价。定长预训练看不出问题，一换到变长 SFT 就在优化另一个目标，而且没有任何报错。

### 陷阱 5：把参数差当作等价判据

Adam 首步更新约等于 $\eta\cdot\mathrm{sign}(g)$，梯度差 1e-5 和差 1e-1 会给出同一量级的参数差。比较两条路径要比梯度。

### 陷阱 6：`N == 0` 直接相除

`reduction='mean'` 在全屏蔽时返回 `nan`；分布式下还要求各 rank 对"这一步跳过"取得一致，否则后续 collective 次序就对不上。

### 陷阱 7：用一次 forward loss 验证恢复

loss 相同只能排除参数、RNG 和数据游标出错。optimizer 状态丢失要到第一次参数写回才暴露，scheduler 丢失要到下一步的 LR 才暴露。

## 自测题

1. labels 与 input 同位置时，shift 应该在哪里做？做两次会怎样？

::: fold
只做一次：模型的 causal loss 内部，或调用方明确手工执行。`F.cross_entropy` 不会自动 shift。做两次的后果是目标整体错一位、有效数减少，但 loss 仍是有限数——只能靠打印逐位置的目标发现。
:::

2. 什么条件下"每份 microbatch 的 mean 再平均"与"全局有效数平均"等价？

::: fold
所有 microbatch 的有效元素数相同。前者给每个 token 的权重是 $1/(M N_m)$，后者是 $1/\sum_m N_m$；$N_m$ 全相等时两式相同。定长打包的预训练满足，变长 SFT 不满足。
:::

3. 一次 forward 的 loss 与参照完全一致，能否说明恢复完整？

::: fold
不能。loss 只依赖参数、当前输入和 RNG。optimizer 的 m/v/step 缺失时 loss 完全正确，差异要到这一步的参数写回才出现；scheduler 缺失时连这一步的 LR 都对，下一步才偏。要按样本 ID、loss、梯度、LR、参数、m/v 逐项比较。
:::

4. SmolLM3 的三个预训练阶段与两个长上下文阶段，每步的 token 数都是 2,359,296，但 `mbs×accum×dp` 从 576 条降到 36 条。这说明了什么？

::: fold
全局 batch 在这份配方里是按 token 固定的，不是按序列条数固定的。序列长度涨 16 倍时同比例减少序列条数，才能让每步的监督量、学习率曲线和 token 预算保持同一口径。这只有在 loss 分母按 token 计时才成立。
:::

5. 发布的 `config.json` 里 `rope_theta=5000000.0`，能否据此说明整个预训练都用这个值？

::: fold
不能。发布 config 记录的是最后一个训练阶段的配置。SmolLM3 的 stage1–3（约 11T token）用的是 50000，4k→32k 阶段改成 2000000，32k→64k 阶段才是 5000000。同理，发布权重不带 optimizer/RNG，它能 warm start 但不能接续原来那条轨迹。
:::
