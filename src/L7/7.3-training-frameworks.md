一份训练配方是一堆字段，一次训练是一个状态机。框架的工作就是把前者变成后者：决定哪个对象拥有参数、谁负责归约、loss 的分母从哪里来、什么时候允许更新、以及保存下来的东西够不够接着训。

这一章用 SmolLM3 的八份真实配方作为贯穿线——五份 Nanotron 预训练、三份 alignment-handbook 后训练——先把字段解析成一份可检查的契约，再沿 FSDP2、DeepSpeed、Megatron Core 和 TorchTitan 四条路线的源码追同一条调用链，最后回到公开的阶段权重，核对"哪个 checkpoint 能做什么"。

判据只有一条：**配置能解析、静态检查通过、框架接受它，是三件不同的事。**

## 机制拆解与推导

### 五份预训练配方：同一条训练的五段

用只读检查器把五份 Nanotron YAML 规范化之后，阶段结构一眼就能看出来：

| 配方 | micro × accum × dp | seq | GBS | token/step | LR | 调度 | 接续 |
|---|---|---:|---:|---:|---:|---|---|
| stage1_8T | 3 × 1 × 192 | 4096 | 576 | 2,359,296 | 2e-4 | linear，从 step 4,198,001 起 522,000 步 | 载入 optimizer 与 scheduler |
| stage2_8T_9T | 3 × 1 × 192 | 4096 | 576 | 2,359,296 | 2e-4 | 同上 | 载入 optimizer 与 scheduler |
| stage3_9T_11T | 3 × 1 × 192 | 4096 | 576 | 2,359,296 | 2e-4 | 同上 | 载入 optimizer 与 scheduler |
| long_context_4k_to_32k | 1 × 6 × 12 | 32768 | 72 | 2,359,296 | 2e-5 | cosine，warmup 1000 | 载入 optimizer 与 scheduler |
| long_context_32k_to_64 | 1 × 3 × 12 | 65536 | 36 | 2,359,296 | 2e-5 | cosine，warmup 1000 | **不载入 optimizer 与 scheduler** |

三件事从这张表里直接读出来：

**每步的 token 预算是常量。** 五份配方的 `micro × accum × dp × seq` 全都等于 **2,359,296**。序列从 4k 拉到 64k 时，GBS 从 576 降到 36，乘积保持不变——模型卡上公布的 "GBS in tokens = 2,359,296" 与配置算术逐位吻合。这也是"batch 大小"必须说清单位的原因：样本数变了 16 倍，token 数一个没变。

**三份预训练配方是同一条训练的三段。** 它们的 `train_steps` 都是 4,720,000，LR 调度参数完全相同，只是 `resume_checkpoint_path` 指向不同的 S3 位置，`data_stages` 依次多出一段。stage2 在 step 3,450,001 切换数据混合（41 → 46 个源），stage3 在 step 4,198,001 再切一次（→ 56 个源）并进入 LR 衰减。**数据阶段的切换点和 LR 衰减的起点是同一个 step**——这是 WSD 式训练里"退火阶段换数据"的具体实现。

**最后一份配方换了训练身份。** `long_context_32k_to_64` 把 `load_optimizer` 与 `load_lr_scheduler` 都设成 `False`，其余四份都是 `True`。前者是"用上一阶段的权重冷启动一段新训练"，后者是"接着上一次训练继续跑"。两者在文件层面只差两个布尔值，在语义上是完全不同的事——[7.4](7.4-data-ckpt-fault.html) 把这条边界展开。

优化器一侧五份完全一致：AdamW、betas (0.9, 0.95)、eps 1e-8、weight_decay 0.1 且 `weight_decay_exclude_named_params: ['.*token_embedding.*']`、`clip_grad: 1.0`、`torch_adam_is_fused: true`、`accumulate_grad_in_fp32: true`、`zero_stage: 0`、模型 `dtype: bfloat16`、`tie_word_embeddings: true`。注意排除衰减的只有 token embedding，不是常见的"norm 与 bias 一律排除"。

### 三份后训练配方：模型身份就是接续关系

| 配方 | base 与 revision | 目标 | max_length | LR | 其它 |
|---|---|---|---:|---:|---|
| mid.yaml | `SmolLM3-3B-Base` @ main | SFT CE | 32768 | 2e-5 | packing、`average_tokens_across_devices: true`、5 epoch |
| sft.yaml | `SmolLM3-3B-checkpoints` @ **it-mid-training** | SFT CE | 65536 | 2e-5 | packing、按 epoch 保存、5 epoch |
| apo.yaml | `SmolLM3-3B-checkpoints` @ **it-SFT** | `apo_zero`，beta 0.05 | 24576 | 1e-6 | padding_free、1 epoch |

后训练阶段之间不靠文件路径接续，而是靠**模型仓库的 revision**：SFT 从 `it-mid-training` 开始，APO 从 `it-SFT` 开始。这三份 YAML 都不声明 world size，所以 `global_batch = micro × accum × dp` 里的 dp 只有启动命令才知道——检查器在这里只能给出"GBS 未定"，而不能假装算出一个数。

`average_tokens_across_devices: true` 是这组配方里最容易被忽略的一行：它决定 loss 的分母是全局有效 token 还是每 rank 各自的，正是 [7.2](7.2-training-parallelism.html) 里那条分母契约在 TRL 侧的开关。

### 四条路线的同一条调用链

把四条路线放在同一张表上，差别集中在"谁拥有状态"和"谁定义时钟"：

| 环节 | FSDP2（并行 API） | DeepSpeed（Engine） | Megatron Core | TorchTitan（应用） |
|---|---|---|---|---|
| 入口 | `fully_shard(module)` | `deepspeed.initialize(...)` 返回 engine | `pretrain()` / `setup_model_and_optimizer()` | `config.build()` → `Trainer` |
| 并行描述 | 由调用方给 `DeviceMesh` | JSON 配置里的 `zero_optimization` 等 | `parallel_state` 的全局进程组 | `ParallelDims` + `parallel_dims.get_mesh("batch")` |
| 模型构建 | 调用方自己建好再包 | 调用方建好交给 engine | `model_provider_func` + `get_model()` | meta device 上 build，再 apply converter |
| 取 batch | 不参与 | 调用方 | `forward_step_func` + `data_iterator` | `Trainer.train_step` 自己取并统计 token |
| loss 分母 | 不参与 | 调用方（`backward(scale_wrt_gas=True)` 按累积步数缩放） | `forward_step_func` 返回 loss 与统计量 | 应用层 all-reduce 出 `global_valid_tokens` |
| 反向 | autograd + 自己的 hook | `engine.backward(loss)` | `forward_backward_func`（流水 schedule） | `forward_backward_step`，PP 时走 schedule |
| 梯度归约 | post-backward 的 reduce-scatter | ZeRO optimizer 内部 | `finalize_model_grads_func` | 交给 FSDP2/DDP |
| 更新时钟 | 不参与 | `engine.step()`：clip → step → 查 `optimizer.overflow` → 决定是否推进 scheduler | `optimizer.step()` 返回 `update_successful`、`grad_norm` | 全局 finite 检查 → `optimizers.step()` → `lr_schedulers.step()` |
| 保存 | 提供分片张量（DTensor） | `engine.save_checkpoint` | `save_checkpoint` | `checkpointer`（DCP，含异步 staging） |

**FSDP2 只在第一行和倒数第三行出现。** 它不知道 batch、loss、scheduler 和 checkpoint 时机，这正是"并行 API"与"训练应用"的分界：FSDP2 管张量归属与通信插入点，其余全由调用方决定。TorchTitan 是使用这些 API 的应用，所以它要自己处理分母、时钟和保存。

**跳步协议三家三样。** DeepSpeed 在 `_take_model_step` 里读 `optimizer.overflow`，溢出就累加 `skipped_steps` 并**不推进 lr_scheduler**；Megatron 的 `optimizer.step()` 返回 `update_successful` 让调用方决定；TorchTitan 则先把 `loss_is_finite` 按 MIN 在 dp 与 pp 两个 mesh 上 all-reduce，再用 `torch._assert_async` **直接让训练停下来**，而不是跳过这一步。三种协议对应三种运维假设：容忍偶发溢出、把决定权交给上层、宁可停下来查。

### 配置验证发生在什么时候

TorchTitan 在 `Trainer.__init__` 里就把序列长度的整除条件挡在前面：

规则是 `num_tokens_per_microbatch` 必须能被 `tp（启用 SP 时）× 2cp` 整除——CP 要除以 2 是因为因果 mask 下常把序列切成两段来均衡负载，这与 [7.2](7.2-training-parallelism.html) 的配置检查器用的是同一条规则。它还在 `apply_overrides` 之后重新跑一遍 `__post_init__`：覆盖项可能改掉任何字段，验证必须在最终配置上做一次。

### 加一个模型或一个目标要改什么

四条路线对"新模型 / 新目标"的接口要求差别很大：

| 需求 | FSDP2 | DeepSpeed | Megatron Core | TorchTitan |
|---|---|---|---|---|
| 新模型结构 | 只要是 `nn.Module` 即可；按模块边界选 `fully_shard` 的粒度 | 同样只要是 `nn.Module` | 需要实现 Megatron 的层接口与并行切分（TP 切分方式写在层里） | 注册 `ModelSpec`，提供 `model_config.build()` 与 `preprocess_inputs` |
| 冻结 projector | `requires_grad_(False)` 即可，但被冻结模块若仍在 `fully_shard` 单元里，仍会参与 all-gather | 需要在 param group 与 ZeRO 分片中排除 | 需要保证各 PP stage 的可训练参数集合一致 | 由 optimizer 构建器决定参数组 |
| LoRA 等 adapter | 不感知 adapter；分片单位仍是模块 | 支持，但 ZeRO-3 下 adapter 也会被分片 | 需要适配层接口 | 通过 converter 机制改配置树 |
| 新 loss | 不感知 | 调用方算好传给 `backward` | `forward_step_func` 返回 loss 与统计量 | `loss_fn` + 分母由 `global_valid_tokens` 统一 |
| 新 optimizer | 不感知 | 需要能被 ZeRO 包住 | 需要接 distributed optimizer 的分片约定 | 由 optimizer 构建器提供 |

一个共同的最小适配接口可以概括成五个问题：**这个模块的参数归谁分片、它的梯度往哪归约、它的 loss 用哪个分母、它的状态怎么进 checkpoint、它在多大粒度上被编译或重算。** [7.2](7.2-training-parallelism.html) 的两 rank 小例已经给出这五项的可运行参照，本章不再重复实现。

### 公开阶段权重能支持什么

`HuggingFaceTB/SmolLM3-3B-checkpoints` 用 **133 个 git 分支**发布中间权重：

| 分支族 | 数量 | 覆盖范围 |
|---|---:|---|
| stage1-step-* | 86 | step 40,000 → 3,440,000，每 40,000 步一个（≈94.4B token） |
| stage2-step-* | 19 | step 3,450,000 → 4,200,000 |
| stage3-step-* | 13 | step 4,200,000 → 4,720,000 |
| lc-4k-to-32k-step-* | 5 | 长上下文第一段，每 4,000 步一个（≈9.4B token） |
| lc-32k-to-64k-step-* | 5 | 长上下文第二段 |
| it-mid-training / it-SFT / it-soup-APO / it-LC-expert | 各 1 | 后训练每个阶段的产物 |

评测侧的对应关系写在 smollm 仓库的评测目录里：base 模型跑 `smollm3_base.txt`（hellaswag/arc/mmlu/mmlu_pro/boolq/commonsenseqa/winogrande/openbookqa/piqa 的 cf 变体、gsm8k 5-shot、math_cot 4-shot、belebele 八个语种），instruct 模型跑 `smollm3_instruct.txt`（aime25、gpqa:diamond、ifeval、lcb codegeneration、五个语种的 global_mmlu_instruct、gsm_plus、mixeval_hard），全部 0-shot，用 lighteval 的 vllm 后端、TP=2、在 2×H100 上运行。**base 和 instruct 的任务清单几乎没有交集**：前者测基础能力用对数似然式任务，后者测指令跟随与推理用生成式任务，两条清单不能互换着报分。

这些分支发布的是 Transformers 格式的权重——仓库主分支只有 README 和 `.gitattributes`，每个分支带的是模型文件。因此：

- 可以做的：从任意中间步做**冷启动**（继续预训练、微调、蒸馏），对比不同训练进度的能力曲线，复现评测分数。
- 不能做的：**严格恢复那次训练**。optimizer 状态、scheduler 位置、RNG 和数据游标都不在发布内容里；原始训练的 `resume_checkpoint_path` 指向的是作者的 S3 路径。Nanotron 的训练态 checkpoint 与这里的 Transformers 导出是两种东西，[7.4](7.4-data-ckpt-fault.html) 会把这两类文件的字段差异摊开。

README 还写了一个可以直接核对的换算：`nb_tokens = nb_step × GBS`，GBS = 2,359,296 token。这与本章从 YAML 算出的数字一致——**公开配方、公开权重和官方说明三者能互相验证，这本身就是评估一份材料是否完整的判据。**

阶段边界要按来源分别核对：README 说 stage3 从 step 4,200,000 开始，而 stage3 的 YAML 里数据阶段 `decay stage` 的起点是 4,198,001、LR 衰减起点也是 4,198,001。两个数字差 1,999 步，分别来自叙述与配置，不要合成一个"新配方"。

## 工程实现：源码解析

### 只读检查器的三层

配方检查器的价值在于它**只做静态判断**：解析成功不代表框架会接受，静态检查通过也不代表训练语义正确。三层分工是：

1. **类型与取值**：`micro_batch_size`、`accumulation`、`dp`、`tp`、`pp`、`cp` 必须是正整数。字符串 `"8"`、浮点 `1.5`、`0` 和 `-1` 在这一层就被挡住。
2. **一致性**：`global_batch = micro × accum × dp`；注意力头能被 tp 整除、能被 KV 头整除；hidden 能被头数整除；层数能被 pp 整除；数据源数量与权重数量一致且权重非负。
3. **契约**：loss 分母等于有效 target 数；严格恢复所需的状态齐全；adapter target 在模型模块名里存在；显存预算没有漏项且不超限。

反例套件注入 12 种错误，12 种全部被拒绝：

| 注入的错误 | 检查器输出 |
|---|---|
| microbatch 为 0 | `micro_batch_size 必须为正：0` |
| accumulation 为 −1 | `accumulation 必须为正：-1` |
| dp 为 1.5 | `dp 不是整数：1.5` |
| dp 写成字符串 | `dp 不是数值：'8'` |
| global batch 与三项乘积不符 | `global batch 60 ≠ micro×accum×dp=64` |
| tp 不能整除注意力头 | `注意力头 32 不能被 tp=5 整除` |
| pp 不能整除层数 | `层数 32 不能被 pp=5 整除` |
| loss 分母写成 batch 内 token 总数 | `loss 分母 2048 ≠ 有效 target 数 1792` |
| 恢复缺 data_cursor 与 rng | `严格恢复缺状态：data_cursor, rng` |
| adapter target 模型里没有 | `adapter target 在模型里不存在：gate_proj` |
| 预算漏掉 activation | `预算漏项：activation` |
| 预算超限 | `预算超限：32 > 24` |

第四行值得单独说：`dp="8"` 时如果不先做类型检查，`micro × accum × dp` 会走 Python 的字符串乘法得到 `'88888888'`，然后与整数比较得出"不相等"——错误确实被发现了，但报出来的原因完全误导。**类型检查要在算术之前。**

### 设计取舍

**"能解析"离"能跑"还有两层。** 检查器不导入任何 Python 配置代码，因此它对 TorchTitan 这类用 Python 描述配置的框架只能检查其导出的规范化结果。这是刻意的：执行未知配置代码等于把检查器变成一个任意代码执行入口。

**分母属于应用层，不属于并行层。** FSDP2 完全不知道 loss 怎么算，TorchTitan 必须自己 all-reduce token 数，TRL 用 `average_tokens_across_devices` 开关表达同一件事。移植配方时，这一项是最容易丢的语义。

**跳步 vs 停机。** DeepSpeed 的"溢出就跳过并不推进 scheduler"适合长跑的大作业；TorchTitan 的"任一 rank 非有限就 assert 停机"适合可以快速重启、且更在意静默错误的场景。两者不是实现质量差异，而是运维假设不同。

### 把教学循环接到 FSDP2：同一契约、不同归约顺序

`labs/L7/teaching_framework_path.py` 用同一份数据、同一条窗口顺序、同一个全局 micro-batch（32）× 序列长度（512）× lr（$5\times10^{-4}$，余弦到 10%）、同一个 clip，在 worldvln 的 L40S 上跑两条路径各 300 步：`plain` 是单卡循环，`fsdp2` 用 `torchrun --nproc_per_node=2` 启动、`fully_shard` 包装并配 `MixedPrecisionPolicy`。

| 项 | plain（1 rank） | fsdp2（2 ranks） |
|---|---:|---:|
| 全局 micro-batch / 每 rank | 32 / 32 | 32 / 16 |
| 全局 token（300 步） | 4,915,200 | 4,915,200 |
| 墙钟 | 40.9 s | 30.3 s |
| 全局吞吐 | 3.86M tok/s | 3.89M tok/s |
| 单卡峰值显存 | 8,584 MiB | 4,470 MiB（每 rank） |
| 末步 loss | 5.3032 | 5.3369 |
| 300 步内最大 loss 偏差 | — | 0.0676（第 151 步） |
| 参数平方和相对差 | — | 0.054% |
| 保存 | `torch.save` 全量 state_dict | DCP：`.metadata` + 每 rank 一个 `.distcp` |
| 集合通信（3 个采样步内） | 0 | `all_gather` 12、`reduce_scatter` 3（NCCL 后端） |

四条判读：

**框架路径确实跑起来了，而且通信真的发生。** 3 个采样步里 12 次 `FSDP::all_gather`（每步约 4 次）与 3 次 `_reduce_scatter_base`（每步 1 次），来源是 `fully_shard` 的前向 unshard 与反向梯度归约；单卡路径同一区间为 0。保存也换了接口：DCP 写的是分片元数据加每 rank 一个数据文件，重新 `dcp.load` 能装回同一份状态。

**损失轨迹不是逐位相同，而是同量级的漂移。** 两条路径在第 1 个记录点就出现 $>10^{-3}$ 的差，300 步内最大 0.0676、末步 0.0337（相对 1.3%），参数平方和相对差 0.054%。差异来自归约顺序、FSDP 的 fp32 梯度归约与 bf16 参数 unshard，而不是目标函数不同。这与 [7.2](7.2-training-parallelism.html) 的结论一致：**换并行配置后"同一份配方"只在浮点容差内相等，别把逐位相同当验收判据**。

**小模型上 FSDP2 省的是单卡显存，不是总显存。** 单卡峰值从 8,584 MiB 降到每 rank 4,470 MiB（52%），但两 rank 合计约 8.9 GiB，比单卡还多一点：64M 参数下 all-gather 缓冲与分片元数据的固定开销占比高，而优化器状态本来就只占几百 MiB。这正是"小模型暂未暴露的瓶颈"——**它没暴露通信带宽压力，反而先暴露了并行框架的常数开销**。

**吞吐在两条路径上持平。** 3.86M 与 3.89M tok/s 的差落在 run 间波动内：64M 模型 + 512 序列长度下计算通信比高，2 卡 all-gather 的等待被计算掩盖。要到 7.2/6.1 那种 8B 级模型与长序列，通信才会变成可测的瓶颈。

## 前沿

四条路线的能力差异正在收敛到"谁先支持新的并行维度与新的低精度格式"。TorchTitan 把 FP8/MXFP8/NVFP4 做成配置层的 converter（见 [7.9](7.9-optimizer-mixed-precision.html) 的门槛表），Megatron Core 把它们做进层实现，DeepSpeed 则通过 engine 配置暴露。选型时可比的不是"支持不支持"，而是**支持的粒度**：能不能只对部分模块启用、能不能与 activation checkpointing 和 compile 叠加、状态是否进 checkpoint。

本章的所有框架结论都来自固定版本的源码与官方文档——DeepSpeed、Megatron Core 与 TorchTitan 在本项目环境中**都没有安装运行**，四框架的实际吞吐、收敛与大模型训练结果保持 `UNVERIFIED`。可运行的两 rank 更新参照在 [7.2](7.2-training-parallelism.html)，它验证的是语义而不是性能。

## 陷阱

### 陷阱 1：把 "batch size" 当成一个数

SmolLM3 的五个阶段 GBS 从 576 变到 36，每步 token 数一直是 2,359,296。比较两次训练前先确认比的是样本数、token 数还是更新次数。

### 陷阱 2：把 `load_optimizer: false` 当成一个小开关

它把"继续同一次训练"变成"用权重冷启动一段新训练"。LR 从头开始、m/v 清零、数据游标复位，训练轨迹与前一阶段不再连续。

### 陷阱 3：以为配置解析成功就等于配置合法

解析、静态检查、框架接受是三件事。检查器能发现 `dp=1.5`，但发现不了"这个 checkpoint 里没有 optimizer 状态"。

### 陷阱 4：把类型检查放在算术之后

`dp="8"` 会让 `micro × accum × dp` 变成字符串重复，得到一个荒谬的数字和一条误导的报错。

### 陷阱 5：以为 FSDP2 能替代一个训练框架

FSDP2 不管 batch、loss、分母、scheduler、checkpoint。把它换进来只解决状态归属，训练应用那一层还得自己写或者用 TorchTitan。

### 陷阱 6：拿 base 的评测清单去评 instruct 模型

两份清单几乎没有交集：base 用对数似然式任务，instruct 用生成式任务。跨清单比较的分数没有意义。

### 陷阱 7：把公开的阶段权重当成可恢复的训练 checkpoint

它们是 Transformers 导出，只有权重。能冷启动，不能严格恢复。

## 自测题

1. SmolLM3 的长上下文阶段把 GBS 从 576 降到 36，是不是意味着训练规模缩小了 16 倍？

::: fold
不是。序列长度同时从 4096 涨到 65536，`GBS × seq` 保持 2,359,296 token 不变。每步的 token 预算是常量，变的只是这些 token 怎么被切成样本。模型卡给出的换算 `nb_tokens = nb_step × 2,359,296` 与配置算术完全吻合。
:::

2. 同样是"把 loss 除以有效 token 数"，TorchTitan、TRL 和 FSDP2 各自在哪一层实现？

::: fold
TorchTitan 在应用层：`train_step` 自己累计 `local_valid_tokens`，用 dp mesh all-reduce 出全局值，并把它同时用于主 loss 和辅助 loss。TRL 用 `average_tokens_across_devices` 这个配方字段表达同一件事。FSDP2 完全不参与——它只管张量归属与通信插入点。移植配方时最容易丢的就是这一项。
:::

3. 检查器对 `long_context_32k_to_64.yaml` 补上 `load_optimizer: true` 之后不会报错，这说明了什么？

::: fold
静态检查只能核对配置内部的一致性，无法知道目标 checkpoint 里到底有没有 optimizer 状态。要确认这一点得去读 checkpoint 的 manifest 或试着加载。这条边界正是把"解析成功""静态合法""运行时可行"分成三层的原因。
:::

4. 为什么 TorchTitan 把 `loss_is_finite` 做成 `int32` 并按 MIN 归约，而不是在每个 rank 上各自判断？

::: fold
一个 rank 上的非有限值会通过梯度归约传播到所有 rank，因此"是否更新"必须是全局一致的决定；各自判断会让部分 rank 更新、部分不更新，参数从此发散。用 int32 是因为 NCCL 的归约不支持 bool，按 MIN 归约表示"任一 rank 不有限则全体不有限"。它还用 `torch._assert_async` 保持设备端顺序，避免每步一次主机同步。
:::
