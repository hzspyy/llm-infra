训练数据工程是最容易被压缩成一句"清洗一下就好"的环节，也是最容易在半年后再也说不清的环节。这一章沿着一条样本跑通整条链路：它带着什么身份进来，被哪些规则删掉或改写，怎样进 batch，怎样从存储被取出来，以及中断之后从哪里接着读。

判据只有一条：**任何一个数字都要能追回到具体的样本 ID、规则版本和单位**。

## 本章回答的三个问题

1. 一条原始样本要带哪些字段才能被追溯、拆分和恢复？不同模态的这些字段分别长什么样？
2. "50% 的数据来自某个源"到底是 50% 的什么？混合权重、packing 和分母之间怎么换算？
3. 存储布局、worker 与预取怎样决定供数的关键路径？坏样本和中断怎样影响已消费与已提交的边界？

## 心智模型：四组字段，三个边界

一条样本身上有四组用途完全不同的字段：**model** 决定梯度，**audit** 决定能不能复现和能不能用，**partition** 决定 train/val 怎么切，**resume** 决定中断后从哪继续。把它们压成一个扁平的 `input_ids` 之后，后三组就再也找不回来了。

这条链上有三个必须显式声明的边界：过滤规则的版本、混合权重的单位、packing 后的文档边界。

## 机制拆解与推导

### schema 先描述任务，再描述张量

上游真实的数据结构已经把这四组字段分开了。datatrove 的 `Document` 只有四个字段：`text`、`id`、`media`、`metadata`——过滤器把判定结果写回 `metadata`，于是"为什么被删"跟着样本一起流动，而不是散在日志里。`Media` 再拆出 `id / type / url / path / offset / length / media_bytes / metadata`，把"引用哪个媒体、在文件的哪一段"独立出来。

各模态的对应物在字段名上完全不同，职责却一一对上：

| 类别 | 送进前向 | 审计 | 拆分单元 | 恢复 | 字段依据 |
|---|---|---|---|---|---|
| 文本文档 | `input_ids` / `labels` / 文档边界 | 来源、许可、质量分、规则版本 | document id | shard + 偏移 | datatrove `Document.metadata` |
| 图文样本 | `pixel_values` / grid / `loss_mask` | caption 来源、`min_pixels`/`max_pixels` | 图像或相册 id | annotation 文件 + 行号 | Qwen3-VL `data_processor` |
| 音频 utterance | 16 kHz 单声道波形 / `labels` | 转写来源、语言前缀、信噪比 | speaker、session | JSONL 行号 | Qwen3-ASR collator |
| 视频 clip | 帧序列 / `start_frame..end_frame` | caption 生成模型与提示词版本、fps | video `uuid` + clip 序号 | 行号 + window 序号 | Cosmos3 `dataset_jsonl` |
| 机器人轨迹 | 观测 / proprio / action / mask | 机器人配置、normalizer 统计版本 | episode key | episode 内 step 区间 | openpi DROID |
| 偏好对 | prompt / chosen / rejected + 各自 mask | 标注来源、一致性、模板版本 | 归一化后的 prompt 身份 | JSONL 行号 | TRL / handbook 的 DPO 列 |
| 教师生成 | student 输入 / teacher logits 或 hidden | teacher revision、温度、topk、层 | 原始 prompt 身份 | 特征块 id + 偏移 | SpecForge / Cosmos caption |

最后一行不是补充：Cosmos3 的视频 SFT 数据集里，`caption` 是用 Qwen3-VL-8B-Instruct-FP8 经 vLLM 现场生成的。**一条视频样本同时是一条教师生成记录**，teacher 的身份必须和视频 uuid 一起存，否则换了 captioner 之后没人能解释训练结果的变化。

### 拆分单元不是样本，是独立单元

同一个说话人、同一段视频、同一个 episode 的相邻片段高度相关。按样本随机切分会让 val 集里几乎每一条的"上下文"都在 train 里出现过。40 个说话人 × 25 条的合成集合上，随机 9:1 切分得到的 100 条 val 里，**100 条的说话人都在 train 出现过**；按说话人分组切分后泄漏为 0。

文本 hash 去重查不出这类泄漏——两条录音的字面内容可以完全不同，模型却已经见过这个音色。DROID 把 episode 身份定义成 `{recording_folderpath}--{file_path}`，这也是唯一合法的拆分单元。

### MinHash 近似的是什么

把规范化文本切成 shingle 集合 $A$、$B$，Jaccard 相似度 $J=|A\cap B|/|A\cup B|$。理想随机置换下两个集合最小哈希相同的概率等于 $J$，用 $K$ 个签名估计：

$$\hat J=\frac1K\sum_{k=1}^{K}\mathbf 1[h_k(A)=h_k(B)].$$

生产实现不会两两比较。datatrove 用 banding LSH：`num_buckets=14`、`hashes_per_bucket=8`（共 112 个签名），只要有**任意一个桶**的 8 个签名全部相同就成为候选对。于是被判为候选的概率是

$$P(J)=1-\left(1-J^{r}\right)^{b},\qquad b=14,\ r=8,$$

隐含阈值 $(1/b)^{1/r}=(1/14)^{1/8}=0.719$。这是一条 S 形曲线而不是硬阈值：

| 真实 $J$ | 0.60 | 0.72 | 0.80 | 0.90 |
|---|---:|---:|---:|---:|
| 成为候选对的概率 | 0.211 | 0.650 | 0.924 | 0.9996 |

0.8 的相似度也有 7.6% 的概率被漏掉，0.6 的相似度也有 21% 的概率被判为重复。调 $b$ 和 $r$ 就是在调这条曲线的位置和陡度。

### packing 的两条边界

两篇文档 `[1,2]` 与 `[3,4]` 拼成 `[1,2,3,4]` 后，整段 causal shift 会用位置 1 的 logit 去预测 token 3。**block-diagonal attention 只限制"看见谁"，不会取消这个跨文档 target。** 与逐篇独立 shift 等价的处理是同时改两处：

```text
input_ids    = [  1, 2,    3, 4]
labels       = [-100, 2, -100, 4]     # 每篇第一项屏蔽 → 只剩 target 2 和 4
position_ids = [  0, 1,    0, 1]      # 每篇重新计位置
cu_seqlens   = [  0, 2,    4]         # 交给真正消费它的 varlen backend
```

`cu_seqlens` 放进 batch 却没传给算子不会产生任何隔离。position reset 是否影响结果取决于位置编码，它也不能替代 attention mask。

等 token 权重的分母是 shift 之后的有效 label 数：

$$N=\sum_{b,t}\mathbf 1\left[\text{labels}_{b,t+1}\ne-100\right].$$

多 rank 用全局有效数时还要补偿 DDP 默认的梯度平均，见 [7.2](7.2-training-parallelism.html)；连续坐标、音频帧的分母另有定义，见 [7.0b](7.0b-one-training-step.html)。

### 混合权重的单位

设源 $i$ 每次被抽中的概率为 $p_i$、平均长度 $L_i$，长期 token 占比约为 $p_iL_i/\sum_j p_jL_j$。这个公式只在"长度与是否被抽中独立"时成立，而且它给出的是期望，不是任何一次实际采样的结果。

关键在于配方里写的权重作用在哪个单位上。对预分词成等长序列的语料，样本数与 token 数成固定比例，权重就是 token 占比；同一份权重作用在变长文档上立刻变成文档占比。两者可以差一个数量级。

### 供数的关键路径

存储布局决定"取一条随机样本要读多少字节"。Parquet 的最小读取单位是 row group，tar 没有目录结构、必须另建索引，预分词 mmap 用定宽 token 换来 O(1) 定位但放弃了变长字段和原文。

worker 与预取把读取藏进上一步的计算里，代价是内存里多驻留 `workers × prefetch × batch` 条样本，以及**每个 epoch 一次的 worker 启动成本**。后者在 spawn 平台上是秒级，必须与稳态吞吐分开计时，否则短 epoch 的墙钟对照会把"多 worker"误判成更慢。

已读取（consumed）与已提交（acknowledged）是两个不同的游标。预取跑在更新前面，checkpoint 只能记后者。

### 预训练：过滤、双层去重与按文档划分

流程是"流式扫描 → 长度与字符过滤 → 整文件 reservoir 采样 → 复读/精确/近似三层去重 → 内容哈希划分 → 编码并打包"。reservoir 的作用是让入选文档均匀来自整个文件，而不是取前多少 MB——按文件顺序截断会让语料来源随文件排列偏斜。

同一份 1,270,238 条文档上的计数（[manifest](../../results/crater/7.8/20260922-teaching-data/data-pretrain/manifest.json)）：

| 阶段 | 计数 |
|---|---:|
| 扫描文档 | 1,270,238 |
| 短于 64 字符 | 10,848 |
| 含 U+FFFD 替换符 | 148 |
| 含控制字符 | 141 |
| 5-gram 唯一率低于 0.75（复读/模板） | 1,541 |
| 精确重复 | 42 |
| 近似重复（b=14，r=8） | 1,204 |
| reservoir 入选 | 600,000 |
| 去重后保留 | 597,213 |
| 填满预算实际使用 | 366,455 |
| 编码后不足 16 token | 16 |

划分按规范化文本的内容哈希分桶（val 2.5%、test 2.5%），所以三份的文档互不重叠，且与扫描顺序无关；这不是上游的原始划分，换一份语料要重新生成。同一份 reservoir 上的产物：

| split | 文档 | token | 512 窗口 | 跨文档窗口 | 文档 token p50 / p90 / p99 |
|---|---:|---:|---:|---:|---|
| train | 348,920 | 80,000,044 | 156,250 | 156,200（99.968%） | 212 / 421 / 512 |
| val | 8,824 | 2,000,119 | 3,906 | 3,906（100%） | 207 / 415 / 512 |
| test | 8,711 | 2,000,159 | 3,906 | 3,906（100%） | 212 / 423 / 512 |

磁盘上是 `train.bin` 160,000,088 B、`val.bin` 4,000,238 B、`test.bin` 4,000,318 B，加三份边界偏移共约 2.93 MB，合计约 171 MB；1.24 GB 的原始 jsonl 到 171 MB 的定宽分片，代价是失去原文（`offsets.npy` 只保留文档边界，不保留文档身份）。准备这一步是 CPU 工作，整轮约 2 分钟，不占 GPU。

### LSH 的 b 和 r 决定"近重复"是什么

同一份 reservoir、同一批 5-gram 哈希，只改 (b, r)：

| (b, r) | 隐含阈值 $(1/b)^{1/r}$ | 判为近重复 | 去重后保留 |
|---|---:|---:|---:|
| 14, 8（datatrove 默认） | 0.719 | 1,204 | 597,213 |
| 8, 1 | 0.125 | 32,626 | 565,791 |

两次运行的删重数量差 27 倍——**"近重复比例"不是语料的属性，而是参数与语料的联合属性**。r=1 时任一 band 的最小哈希相等就判重，碰撞概率 $1-(1-J)^b$，J=0.5 的一对文档也有 99.6% 的概率被删；这不是"更严格的去重"，而是换了一个问题。本项目的产物用 (14, 8)，并在 manifest 里记下隐含阈值；换参数就必须换一份产物、换一条学习曲线，不能只改一个数字继续比较。

### SFT：模板确定化，只监督 assistant 段

SFT 产物把每条会话渲染成对话模板，再用上游同一套规则定位监督区间：`<bos>assistant\n` 到 `<eos>\n` 之间的 token 置 label，其余为 -100。两处与上游默认不同，都写进 manifest：**不再按概率随机注入 system prompt**，**确定性地删除空 `<think>\n\n</think>\n\n`**。上游这两个选择带随机性，同一份原始数据准备两次会得到不同的监督 token 数；教学项目需要可重复的产物与可比较的曲线，所以在数据准备阶段就固定下来，而不是在训练脚本里设种子。

| 阶段 | 计数 |
|---|---:|
| 扫描会话 | 905,718 |
| reservoir | 12,000 |
| 截断到 768 | 612 |
| 监督不足 4 token 丢弃 | 10 |
| train | 8,000 条 / 3,231,598 回答 token / 640,567 prompt token |
| val | 621 条 / 245,429 / 48,399 |
| test | 592 条 / 241,140 / 48,085 |

回答 token 是 prompt token 的约 5 倍，因为上游会话里 assistant 段普遍较长（含 `<think>` 推理段）。这个比例决定了 SFT 的有效吞吐分母：按样本数报"每秒多少条"会把长短样本平均掉，按回答 token 报才和梯度对齐。数据预览（原始模板尾部与解码后的监督开头）在 `preview.jsonl`，用来核对 mask 是否落在正确位置。

### 跨文档窗口不是例外，是默认

seq_len 512、文档 p50 只有 212 token，于是 **99.968% 的预训练窗口至少跨一个文档边界**（156,250 个窗口里有 156,200 个；窗口内边界总数 348,245）。这不是配置失误，而是这份语料长度分布的必然结果。它意味着三件事：

1. 整段 causal shift 会用上一篇文章的最后一个 token 去预测下一篇文章的第一个 token。目标仍然是"预测下一个 token"，但监督里混进了跨文档的边界对。
2. 想严格隔离，需要 block-diagonal/cu_seqlens 加"每篇首项屏蔽 + 位置重置"三件套。7.8 的 packing 小例验证了改这三处的等价性；本项目没有改，因为代价要按实际 kernel 算，而收益在这份语料上不可测。
3. 因为边界普遍存在，"某一步的 loss 更低"不能归因于模型学到了更长的依赖——它也可能来自更好预测的文档开头。

manifest 因此把 `window_cross_doc_fraction` 和 `cross_doc_boundaries` 一起记下来；换语料或换 seq_len 时，这个数字会先变，然后才轮到 loss。

## 工程实现：源码解析

### datatrove 的四步去重

{{src:results/local/7.8/20260915-data-engineering/source/datatrove/src/datatrove/pipeline/dedup/minhash.py:29-60}}

上游把阈值公式直接写进了模块注释。四个 `PipelineStep` 子类各管一步：`MinhashDedupSignature`（算签名并按桶落盘）、`MinhashDedupBuckets`（在桶内找候选对）、`MinhashDedupCluster`（并查集聚类，每个簇留一个）、`MinhashDedupFilter`（按聚类结果过滤，可选把被删的样本写进 `exclusion_writer`）。

拆成四个阶段不是为了好看：签名可以按分片并行、桶可以按 bucket 并行、聚类要全局做一次。**被删样本单独落盘**这一点尤其重要——没有它，"删掉了什么"就只剩一个计数。

### 同一份权重，两种单位

Nanotron 消费 `dataset_weights` 的位置把单位说得很清楚：

{{src:results/local/7.8/20260915-data-engineering/source/nanotron/src/nanotron/data/tokenized_bytes.py:571-597}}

权重先归一化（`:576-579`），再用 `int((train_steps - it) * global_batch_size * w_i)` 换成**样本数**，最后乘 `sequence_length` 得 token 数（`:589-590`）。SmolLM3 的这批数据已经预分词成等长序列，所以样本占比就等于 token 占比。

Qwen3-VL 走的是另一条路。数据集名后面的 `%NN` 被解析成采样率：

{{src:results/local/7.8/20260915-data-engineering/source/Qwen3-VL/qwen-vl-finetune/qwenvl/data/__init__.py:38-57}}

消费点是 `data_processor.py:277-280` 的 `random.sample(annotations, int(len(annotations) * rate))`——对 **annotation 条目**取样。一条 annotation 可能带一张图，也可能带一整段视频，所以 50% 的条目既不是 50% 的图像数，也不是 50% 的视觉 token 数。

### 多模态的 loss mask 是同一份契约

Qwen3-ASR 的 collator 把音频统一重采样到 16 kHz 单声道（`qwen3_asr_sft.py:84-85`），然后分别构造 prompt-only 与完整输入，用 `-100` 屏蔽 prompt 前缀（`:146`）和 padding（`:150`）。除了输入侧多了一步重采样，它与纯文本 SFT 是同一套 loss mask 契约。

openpi 的 DROID 过滤则把"哪些帧可以训练"写成三个常量加一个判据：连续 idle 超过 `min_idle_len=7` 帧就切断，保留的区间至少 `min_non_idle_len=16` 帧，每段末尾再去掉 `filter_last_n_in_ranges=10` 帧；idle 的判据是全部关节的速度变化都小于 `1e-3`。

{{src:results/local/7.8/20260915-data-engineering/source/openpi/examples/droid/compute_droid_nonidle_ranges.py:1-14}}

注释里写清了为什么是 7：多数 DROID 动作分块策略每次执行生成的前 8 个动作，容忍 7 帧以内的停顿才不会让策略学会"卡住不动"。**这是一条把下游推理行为写进数据过滤规则的例子。**

### 设计取舍

**padding vs packing。** padding 简化 shape 和静态内存布局；packing 减少无效槽位，代价是文档映射、mask 和变长 kernel 约束。packed batch 也可以按总 token 数分桶，不能断言它一律无法使用 CUDA Graph。真实收益取决于打包成本、padding 比例、backend 和完整训练步，本章只验证数值与槽位。

**存储布局。** Parquet 用列存和 row group 换压缩率与投影下推，代价是随机取一条要解一整个 row group；tar 顺序友好、和对象存储契合，但需要外部索引；预分词 mmap 定位最快、体积最小，代价是丢掉原文与一切变长字段，换 tokenizer 就要全部重做。这三者不是优劣关系，而是"随机读 / 顺序读 / 预处理一次性成本"的三角。

**过滤的严格程度。** 阈值调高漏删增多，调低误删增多，而两类错误都只能在有 ground truth 的小集合上估计。生产上的做法是保留被删样本、保留规则版本，让结论可以在换阈值之后重算，而不是追求一次调对。

`persistent_workers=False` 的每个 epoch 都要重新 spawn 并 `import torch`，在这台 CPU-only 的机器上让同一段循环从 1.5 s 涨到 12 s。这是本机的 spawn 行为，Linux 上 fork 的代价不同，但"启动与稳态必须分开计时"这条判据不变。

**坏样本与两个游标**（同上）：

```

  policy=placeholder: 产出 10 个 batch，形状 [(8, 8)]，rejected 3 条

  rank 0: 分到 40 条，跳过 0 条 → 5 个完整 batch
  rank 1: 分到 40 条，跳过 3 条 → 4 个完整 batch（余 5）

  step 5: 已读取到样本 96，已提交到样本 32，在途 64

```

worker 里抛出的异常会被重新包装后抛回主进程（`RuntimeError: Caught RuntimeError in DataLoader worker process 1`，末行是原始的 `sample 13: decode_error`），整个 epoch 终止。DataLoader 没有"忽略坏样本"的开关，想跳过必须在 `__getitem__` 里显式处理。

**改一条规则的影响**（[schema.txt](../../results/local/7.8/20260915-data-engineering/schema.txt)，按 openpi 的规则在一条 600 帧合成 episode 上重放）：

| `min_idle_len` | `filter_last_n` | 区间数 | 保留帧 | 保留比例 |
|---:|---:|---:|---:|---:|
| 7（上游默认） | 10 | 4 | 496 | 82.7% |
| 7 | 0 | 4 | 536 | 89.3% |
| 3 | 10 | 8 | 415 | 69.2% |
| 15 | 10 | 3 | 522 | 87.0% |

把 `min_idle_len` 从 7 调到 3，同一条 episode 被切成更多更短的区间，保留帧从 82.7% 降到 69.2%。这不是超参数微调，而是换了一个训练集。相应地：

| 规则 | 直接改变 | 指标口径的影响 | 缓存与 checkpoint |
|---|---|---|---|
| 过滤/去重阈值 | 训练集组成 | 评测污染结论、混合比例 | tokenized shard 全部作废 |
| packing 最大长度 | 每步有效 token 数 | loss 分母与学习率的有效标度 | batch 边界变了，游标不可复用 |
| 图像 `min/max_pixels` | 视觉 token 数 | 上下文长度与显存峰值 | 预计算的视觉特征作废 |
| 音频重采样率 | 编码器输入长度 | 每秒的监督量 | 预抽特征与 codec token 作废 |
| action 归一化统计 | 回归目标的量纲 | 动作误差不可跨版本比较 | 导出的 normalizer 必须同版本 |
| teacher revision | 监督信号本身 | 学生质量结论只对该 teacher 成立 | 特征 store 整体失效 |

## 前沿

流式 packing、多模态时长分桶和 `StatefulDataLoader` 把数据布局与 checkpoint 更紧地绑在一起：数据侧的状态从"读到第几条"变成"读到哪个 shard 的哪个 row group 的第几行、当前 pack 里还剩多少空位"。合成数据与教师生成把 teacher 的身份变成数据版本的一部分，Cosmos3 的 caption 流程已经是这个形态。

本章的所有测量都在一台 CPU-only 的机器上完成。真实语料规模下的 MinHash 分桶 I/O、对象存储的随机读、跨节点 worker 的 straggler 分布都保持 `UNVERIFIED`，补测条件是一套带真实分片的共享存储。

## 陷阱

### 陷阱 1：只做一半的 packing 隔离

只设 loss mask 不会隔离跨文档 attention，只设 block mask 不会屏蔽跨文档 shift target。`cu_seqlens` 放进 batch 但没传给算子，等于没做。

### 陷阱 2：把"50%"当成一个确定的量

50% 的文档、50% 的样本、50% 的 token、50% 的音频小时是四个不同的配比。本章的例子里它们能差到 10.4% 对 76.7%。

### 陷阱 3：按样本随机切 train/val

说话人、episode、视频源是拆分单元。随机切分下 val 的每一条都可能"见过"，而文本 hash 去重完全查不出来。

### 陷阱 4：把阈值筛查当成纯净证明

保留数说明不了任何事。四个植入的近重复里三个被保留，而且它们的真实 Jaccard 本来就低于阈值——误删与漏删要分别估计，被删样本要保留。

### 陷阱 5：用短 epoch 的墙钟对比 worker 数

worker 启动是每个 epoch 一次的固定成本，spawn 平台上是秒级。不分开计时会得出"多 worker 更慢"的相反结论。

### 陷阱 6：把 prefetch 指针写进 checkpoint

预取跑在更新前面。把它当作已提交位置会漏掉在途样本；把在途样本算作"已训练"则会多算数据消耗。

### 陷阱 7：让各 rank 自行跳过坏样本

某个 rank 静默 `continue` 会让它比别的 rank 少一次 collective，先跑完的 rank 会卡在下一个集合通信上直到超时。坏样本要在全局层面统一处理。

## 自测题

1. `[1,2]`、`[3,4]` packing 之后为什么要把第二篇的第一项 label 屏蔽？

::: fold
整段 shift 会让第一篇的末位置去预测第二篇的首 token。attention mask 不会取消这个 loss 项——它只决定谁能被看见。屏蔽每篇的第一项 label 才与逐篇独立 shift 相符，本章的梯度对拍在三个 seed 下差为 0。
:::

2. datatrove 默认的 `num_buckets=14`、`hashes_per_bucket=8` 意味着什么阈值？$J=0.8$ 的一对文档一定会被检出吗？

::: fold
隐含阈值是 $(1/14)^{1/8}\approx0.719$，但这是 S 曲线的拐点而不是硬阈值。$J=0.8$ 被判为候选对的概率是 $1-(1-0.8^8)^{14}=0.924$，即仍有 7.6% 的概率漏掉；$J=0.6$ 也有 21% 的概率被判为重复。
:::

3. 配方里写 `dataset_weights: [0.5, 0.25, 0.25]`，怎样确定这三个数的单位？

::: fold
看消费它的加载器。Nanotron 在 `tokenized_bytes.py:576-590` 把权重归一化后乘 `global_batch_size` 得样本数、再乘 `sequence_length` 得 token 数；因为这批数据预分词成等长序列，样本占比等于 token 占比。Qwen3-VL 的 `%50` 则是 `random.sample` 对 annotation 条目取样，与 token 数无关。同一组数字作用在变长文档上就是文档占比。
:::

4. 为什么"取一条随机样本读了多少字节"比读取耗时更适合用来比较存储布局？

::: fold
耗时同时包含页缓存状态、文件系统、设备带宽和 CPU 解码，在一台笔记本上量出来的主要是最后一项。而"要读多少字节、要解多少行、需要哪些外部索引"是布局本身的性质：Parquet 的最小单位是 row group（本例解 256 行读 243 KB 才拿到一条 542 字节的样本），mmap 是精确的字节区间。带宽结论要在目标存储上单独测。
:::

5. 训练中断重启后，数据侧要从哪个位置继续？

::: fold
从 acknowledged（已完成 optimizer 更新对应的样本位置）继续，不是 consumed（预取已读到的位置）。两者之间的样本会被重新消费——本章的例子里是 64 条。把 prefetch 指针写进 checkpoint 会直接漏掉这批样本，而把它们计入"已训练"则会高估数据消耗。
:::
