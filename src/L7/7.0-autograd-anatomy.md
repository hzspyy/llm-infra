**关键要点**：

- 反向图的边就是 `Node.next_edges`，每条边带一个 `input_nr`，指明梯度落在这个节点的第几个输入上。
- 引擎先数入边得到依赖计数，再把计数归零的节点放进就绪队列；节点本身只执行一次。
- 同一输出被多次消费时，多份梯度在 InputBuffer 里按 `output_nr` 就地相加，这是"共享参数梯度累加"的机制来源。
- 保存值在节点执行后释放；原地修改把版本计数推进，反向读取时用版本号发现不一致。

## 机制拆解与推导

### Node、Edge 与 apply 的返回契约

前向每执行一个算子，就创建一个 `Node`，并把该算子输入的 `Edge` 记进 `next_edges`。反向时引擎把收集到的梯度交给 `Node.apply()`，`apply()` 返回一个梯度列表，长度等于 `next_edges` 的条数：第 i 个梯度沿着第 i 条边进入下一个节点。

这条契约解释了两个常见困惑。其一，一个节点有多个输出时（例如 `torch.split`、`torch.unbind`），它的 `apply()` 会收到多份输出梯度，但调用一次；节点内部把多份梯度按自己的数学关系合并。其二，一个节点的某个输入不需要梯度时，对应位置返回未定义值，边被跳过。

### 依赖计数：数的是入边，不是执行次数

引擎需要知道"一个节点还要等几份梯度才能开始算"。算法是：从 root 出发遍历 `next_edges`，每遇到一条指向节点 N 的边就把 N 的计数加一，同时把尚未展开的 N 放进待遍历队列。于是计数等于该节点在反向图中的入边数量。

`MmBackward0` 的入边可以为 2：若 `h = x @ W.t()` 之后 h 同时被 `relu` 和另一个 `mul` 使用，relu 的反向节点和 mul 的反向节点各向 h 的节点贡献一份梯度，必须都到齐才能对 `x` 和 `W` 求导。这正是"梯度汇合"的定义。

### InputBuffer：按 output_nr 就地相加

引擎为每个待执行节点准备一个 InputBuffer，按该节点的输出编号存梯度。当同一个输出被两条路径消费时，两份梯度落到同一个槽位。第二份到达时就地与第一份相加，而不是排队两次。这就使"一个节点执行一次、但收到多路贡献"成为可能。

### 叶子累积与 zero_grad

`AccumulateGrad` 是叶子的终点。它把收到的梯度写进 `tensor.grad`，并且**跨调用累积**：不清零就再次 `backward()`，梯度相加。`zero_grad(set_to_none=False)` 把已有张量填零，保留同一块存储；`set_to_none=True` 把 `.grad` 置为 `None`，下一次反向会分配新张量。两者数值等价，但前者保留存储、后者让后续 `backward` 少一次写零。

### 保存值何时释放

前向用 `save_for_backward` 记录反向需要的张量与当时的版本号；反向执行完一个节点后，只要图不需要保留，引擎立刻调用 `release_variables()` 释放该节点的保存值。因此第二次 `backward()` 会同时踩到两件事：图结构仍在（Python 对象还在），但保存值已经空了。`retain_graph=True` 跳过的正是这次释放。

引擎把一次调用的中间梯度放进任务级 InputBuffer，只有叶子 `.grad` 承担跨调用累积。这样同一套机制同时支持"多输出汇合"和"多次 forward 累积"，也让 `forward` 与 `backward` 的调度解耦。代价是引擎必须额外维护依赖计数、就绪队列与保存值生命周期——这些状态在 mini 实现里可以看得很清楚，但线程队列、reentrant backward 与跨流依赖仍是 mini 不覆盖的部分。

## 前沿

PyTorch 近几个版本把 autograd 从"运行时解释执行"推向"可捕获、可编译"：

- **AOTAutograd 与功能化**。`torch.compile` 在 `torch._functorch/_aot_autograd/` 里把前向与反向一起捕获成图，并要求先做 functionalization——原地修改被改写成"新张量 + 拷贝"，从图上消除版本计数这类运行时状态。本章的原地修改报错正是这套改写要规避的问题。
- **compiled autograd**。`torch._dynamo.compiled_autograd` 把整张反向图交给编译器，减少 Python 与 C++ 引擎的往返；它保留了本章的图语义，但把逐节点调度换成了编译产物。
- **非重入 checkpoint 成为默认**。2.14 的 `torch.utils.checkpoint` 在未显式指定时使用非重入路径，并通过 saved tensors hooks 实现保存值的按需重算；`early_stop=True` 是它的默认行为。
- **CUDA Graph 与反向**。把反向放进 CUDA Graph 要求固定 shape、固定地址，并且梯度消费必须与捕获流正确同步——本章 [B]/[C] 的对照就是这条约束的最小版本。

这些是上游文档与本地源码可核对的方向；本章未在本机验证 AOTAutograd 与 compiled autograd 的产物，相关结论留给 2.6b/2.7。

## 陷阱

### 陷阱 1：把依赖计数当成执行次数

入边越多不代表节点执行越多次。`dependencies[next]` 是"还等几份梯度"，节点本身仍只执行一次。想验证执行次数，可以用 `grad_fn.register_hook` 数触发次数，而不是数 `next_functions`。

### 陷阱 2：忘记清零梯度，或清零方式不一致

不清零就再次 `backward()`，叶子 `.grad` 会累加。`zero_grad(set_to_none=True)` 与 `set_to_none=False` 数值等价，但后者保留同一块存储；如果代码依赖 `data_ptr` 不变（例如已被 CUDA Graph 捕获的缓冲区），两者不能互换。

### 陷阱 3：原地修改的三个阶段

叶子参数的原地写在前向调用处就报错；中间张量的原地写不报错，但会把版本号推进，等到反向读取保存值时才对不上；不需要保存值的算子（例如 `AddBackward`）在输出上原地写则完全合法。定位问题时先看报错发生在哪个阶段。

### 陷阱 4：`retain_graph` 与 `create_graph` 混用

`retain_graph=True` 只是不在反向结束时释放保存值，让同一张图可以再次求导；要得到能继续求导的梯度（高阶梯度），需要 `create_graph=True`。前者不产生二阶梯度，后者不会自动避免内存泄漏。

### 陷阱 5：把 `no_grad` 与 `inference_mode` 当同义词

两者都不记录图，但 `inference_mode` 产出的张量带 inference 标记，被需要梯度的算子保存时会直接报错，`no_grad` 不会。要一段前向只省图、还想让结果参与后续 autograd，用 `no_grad`；完全确定不参与训练时才用 `inference_mode`。

### 陷阱 6：冻结权重就不需要保存激活

冻结 encoder 参数只让权重没有梯度。如果 encoder 的输入仍需要梯度（例如前面是可训练的 embedding），反向仍要穿过 encoder，激活照旧保存——`frozen_branches.py` 的 V2/V3 对照里 saved tensors 从 2 变 0 靠的是 `no_grad`，不是冻结。反过来，只要输入不需要梯度、encoder 又在 `no_grad` 内，则整段都可以不保存。

### 陷阱 7：CPU 返回就认为梯度可用

CUDA 上 `loss.backward()` 返回只说明 CPU 提交完成。在另一条流上读梯度而不等待反向流的事件，实测 18/20 轮读到与参照不同的值。正确做法是在反向流上记录 event，消费流 `wait_event`；`.to("cpu")` 之所以看起来没问题，是因为阻塞式 `cudaMemcpy` 把设备工作串行化了。

## 自测题

1. 一条边上的 `input_nr` 表示什么？为什么 `Node.apply()` 返回的列表长度等于 `next_edges` 条数，而不是 `num_outputs`？
2. 同一个中间张量被三个下游算子消费时，它的反向节点会被执行几次？三份梯度在哪里相加？
3. `retain_graph=True` 与 `create_graph=True` 分别解决什么问题？各自不解决什么问题？
4. 为什么"冻结 encoder 权重"之后，encoder 仍可能持有大量被保存的激活？
5. 在 CUDA 上把 `loss.backward()` 的结果立刻拷回 CPU 为什么可能是错的？两种正确的同步写法是什么？

::: details 答案

1. `input_nr` 指明梯度落到目标节点的第几个输入上（对应 `next_edges` 的下标）。`apply()` 的返回契约是"每条输入边一个梯度"，输出侧的合并发生在节点内部：多输出节点收到多份输出梯度，但只调用一次 `apply()`。
2. 执行一次。三份梯度都落在该节点输出编号对应的 InputBuffer 槽位，第二、三份就地与前一份相加，之后计数减到 0 才入队。
3. `retain_graph=True` 让反向结束后不释放保存值，用于对同一张图再次求导；`create_graph=True` 让求导过程本身被记录，从而能对梯度再求导。前者不产生二阶能力，后者不自动防止引用环导致的内存泄漏。
4. 梯度是否需要穿过 encoder 由输入是否 `requires_grad` 决定，与参数是否冻结无关。输入仍需梯度时，反向要计算"对输入的梯度"，于是需要保存前向激活；要同时省掉激活，得对这段前向使用 `no_grad`（或让输入不需要梯度）。
5. 因为 `backward()` 返回时设备工作可能还没结束，另一条流或阻塞拷贝可能读到尚未写完的梯度缓冲。正确写法是在反向流上 `ev.record(stream)`，消费侧 `stream.wait_event(ev)`；跨流读取时还应保证被读张量的存储生命周期覆盖消费侧使用（`record_stream`）。阻塞式 `.to("cpu")` 依赖同步 `cudaMemcpy` 串行化设备工作，不应作为跨流同步手段。

:::
