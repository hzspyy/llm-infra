## 本章回答三个问题

前面几章把「一张卡怎么跑模型」「多张卡怎么切模型」讲完了。PD 分离换了一个问法：**prefill 和 decode 是两种性质完全不同的负载，为什么要把它们绑在同一张卡上？** prefill 是算力受限的大矩阵乘，decode 是权重带宽受限的逐 token 小步长；合在一起调度，两边互相拖。

分离的代价也很直白：KV cache 必须从 P 实例搬到 D 实例。这一章要回答的就是这笔搬运值不值。

1. KV 交接的所有权怎样转移？接收方凭什么相信这份 KV 是自己的？
2. 传输和两侧排队怎样共同影响收益？
3. 取消和重复交接怎样回收资源？

## 机制拆解与推导

### 1. 交接描述符：接收方凭什么相信这份 KV

KV cache 是一块没有自描述信息的裸张量。接收方拿到 224 MiB 的字节之后，必须能回答：这是哪个请求的？哪个模型版本？多少 token？什么布局？如果答不上来，它就无法判断该不该把这份 KV 接进自己的分页缓存。

所以交接的第一步不是传数据，是**交换描述符并校验**。本机实测的描述符包含 15 个字段，其中 10 项被强制要求一致：

| 字段 | 作用 | 不一致时的实测行为 |
|---|---|---|
| `request_id` / `session_id` | 这是哪个请求、哪个会话 | 拒绝 |
| `model_revision` | 权重与层结构版本 | 拒绝 |
| `prompt_sha256` | 前缀内容校验 | 拒绝（与 token 数一起用） |
| `num_tokens` | KV 覆盖的 token 数 | 拒绝 |
| `dtype` / `kv_scale` | 数值格式与量化尺度 | 拒绝 |
| `tp_size` / `tp_rank` | **TP 布局**：这一份是哪一片 | 拒绝 |
| `num_layers` / `num_kv_heads` / `head_dim` | 形状自校验 | 拒绝 |
| `block_size` / `block_ids` / `block_table` | 分页身份与物理块映射 | 拒绝 |

实测 10 类非法交接（逐个字段改错 + block 表错）**全部被拒绝，没有一次静默接受**。其中 `tp_rank`/`tp_size` 与 `block_table` 这两项是分离场景特有的：同一个请求在 P 侧可能按 TP=2 切成两份，D 侧如果按 TP=1 接手，就不能把某一 rank 的 KV 当成完整的 KV 用——这正是任务书里「异构 TP 仅在支持的布局转换下运行」的意思。

### 2. 为什么这次交接过得去：逐位对拍

正确性的判据不能只是「没报错」。本机的做法是：以 prefill 之后立刻取的 CPU 快照为唯一真值，两个分支各自从同一份快照重建 cache，再比较后续解码。

| 检查项 | 结果 |
|---|---|
| KV 往返（GPU→CPU→GPU，同设备）最大绝对差 | 0.0 |
| KV 跨设备拷贝最大绝对差 | 0.0 |
| 首 token 与后续 8 步 token 序列 | 完全相同 |
| 每步 logits 最大绝对差 | **0.0** |

logits 逐位相同说明这份交接没有引入任何数值变化——这不是「足够接近」，是同一条计算路径。能做到这一点的前提是快照取自同一个 prefill，两侧用的是同一份 bf16 权重。

### 3. 搬运的两条参照与一档慢状态

| 路径 | 时间（224 MiB） | 速率 | 说明 |
|---|---:|---:|---|
| GPU→CPU→GPU（D2H + H2D 暂存） | 175.71 ms | 1.34 GB/s | 每 rank 都要过一次主机内存 |
| GPU→GPU（P2P 直连，56 个拷贝） | 21.59 ms | 10.88 GB/s | 每操作 0.385 ms |

**0.385 ms/操作与 98.9 ms/操作是同一台机器的两档状态。** 1.3 在驱动层量 PCIe P2P 时记录过这个现象：同一个二进制连跑两次，一次全慢一次全快，成因未定位。本章第一次跑 task A 时拿到的就是慢状态（5346 ms / 224 MiB ≈ 每操作 98.9 ms），重跑同一条命令落回快状态。所以搬运时间**必须在运行前确认机器处在哪一档**，否则同一个实验会得到差 25 倍的结论。

CPU 暂存路线的 1.34 GB/s 是一个关键瓶颈点：它反映的并非 PCIe 的物理带宽能力（6.1 测到单向 24 GB/s），而是「D2H + H2D 两次拷贝 + Python 逐层循环」的合成开销。真实实现不会这样搬——它们用 RDMA 直接写对端显存，或者把 KV 注册成可远端寻址的对称窗口。

### 4. 分离相对并置多付了多少

并置基线用 vLLM 0.29.0 实测（Qwen3-1.7B、BF16、关 prefix caching 与 CUDA Graph、贪心解码），输入 × 输出共 9 个组合：

| S | out | 并置 TTFT | TPOT | goodput | 峰值 |
|---:|---:|---:|---:|---:|---:|
| 128 | 32 | 28.70 ms | 12.025 ms | 79.7 tok/s | 26.57 GiB |
| 128 | 1024 | 22.47 ms | 10.924 ms | 91.4 tok/s | 26.57 GiB |
| 2048 | 32 | 37.94 ms | 10.623 ms | 87.1 tok/s | 26.57 GiB |
| 2048 | 1024 | 39.39 ms | 10.963 ms | 91.0 tok/s | 26.57 GiB |
| 8192 | 32 | 178.73 ms | 10.673 ms | 62.8 tok/s | 26.57 GiB |
| 8192 | 1024 | 178.79 ms | 11.028 ms | 89.3 tok/s | 26.57 GiB |

把实测的搬运时间加到并置 TTFT 上，就得到分离的单请求 TTFT：

| S | 搬运 | 分离 TTFT（并置 + 搬运） | 搬运占 TTFT | 搬运占整个请求（out=32） |
|---:|---:|---:|---:|---:|
| 128 | 3.40 ms | 25.4 – 32.1 ms | 10.6% – 13.4% | 0.8% |
| 2048 | 33.66 ms | 69.6 – 73.1 ms | **46.1% – 48.4%** | 9.2% |
| 8192 | 127.44 ms | 305.7 – 306.2 ms | 41.6% | **25.0%** |

**在 S=2048 与 8192 上，搬运吃掉了分离后 TTFT 的四成以上。** 短输入（S=128）时搬运只占一成，因为 KV 本身很小（3.4 ms）；输入一长，KV 线性增长而搬运速率不变，占比就封顶在 40% 附近（封顶是因为 prefill 时间本身也随 S 线性增长）。

### 5. 分离要赚回来，只能靠跨请求重叠

上面的账是**单请求**的：分离让 TTFT 变长，多出来的正好是搬运时间。单请求视角下 PD 分离永远是亏的。

它的收益在系统层面：并置时 P 的 prefill 会把 D 的 decode 挡在后面（同一条 GPU 队列），分离之后两者在不同的 GPU 上并行。于是收益条件是

```text
（被重叠掉的 prefill 时间）× 每单位时间的请求数  >  每次请求的搬运时间
```

用实测数代入，看单请求那条时间线的两个量：

| S | prefill（并置 TTFT 的绝大部分） | 搬运 | 重叠空间 |
|---:|---:|---:|---|
| 128 | 22–29 ms | 3.40 ms | 充足 |
| 2048 | 36–39 ms | 33.66 ms | **几乎相等，收益最脆弱** |
| 8192 | 178 ms | 127.44 ms | 最大 |

S=8192 时 prefill 178 ms 远大于搬运 127 ms，只要 D 侧有排队，重叠就能把搬运赚回来；S=2048 时两者几乎相等，**分离的收益完全取决于能不能做到接近满重叠**——任何一侧的排队或拷贝串行化都会把这点微薄的空间吃掉。

这也解释了为什么真实系统把 PD 分离和高并发绑在一起用：单请求不划算，只有 D 侧持续有 decode 工作可做，重叠才有东西可叠。

### 6. 失败与取消：两侧都要收干净

交接是两阶段提交式的：发送方持有 block，接收方 ACK 之后发送方才释放；接收方用完自己的那份再释放。任何一个时点取消，都必须把两侧状态收回基线。实测五个时点：

| 时点 | 已发出 token | refcount 干净 | staging 干净 | 显存回到基线 |
|---|---|---:|---:|---:|
| 注册之后、传输之前 | 0 | ✓ | ✓ | +0.0 MiB |
| 传输中 | 0 | ✓ | ✓ | +0.0 MiB |
| 接收之后、decode 之前 | 0 | ✓ | ✓ | +0.0 MiB |
| decode 中 | 1 | ✓ | ✓ | +0.0 MiB |
| 正常完成 | 4 | ✓ | ✓ | +1.2 MiB |

四条读法：

**取消路径要主动释放，不能指望 GC。** 第一版实现里取消路径只回收了 staging、没有释放发送方持有的 block，五个时点全部报「refcount 不干净」。这不是系统缺陷，而是实现里少了「未完成 ACK 的交接由发送方自己释放」这条规则。补上之后四个取消时点都回到 0.0 MiB。

**「decode 中取消」只发出 1 个 token 是对的。** 取消发生在第一层 decode 之后，已经产生的那个 token 不能撤回，也不该重复提交。

**重复 ACK 必须被拒绝。** 接收方对同一个 block 再 ACK 一次，实测报 `consumer: block 0 释放次数超过持有次数`。若静默接受，refcount 会变成负数，后续的块分配会把还在用的块复用出去。

**失败之后实例要能继续服务。** 五个时点跑完，同一个实例仍能用同一份 prefill 正常解码出 4 个 token，说明状态没有被污染。

### 7. 连接器：本机跑不了生产路径

| 连接器 | 依赖 | 完成接口 | 本机 |
|---|---|---|---|
| NIXL | `nixl`、RDMA 或 POSIX 后端 | `get_finished` / `wait_for_save` | ✗ 未安装 |
| Mooncake | `mooncake.engine.TransferEngine`、RDMA | `get_finished` / `wait_for_save` | ✗ 未安装 |
| LMCache | `lmcache` | `get_finished` / `wait_for_save` | ✗ 未安装 |
| ExampleConnector | 无 | 同左 | ✓ 共享目录落盘，**可用但未接入服务栈** |
| DecodeBenchConnector | 无 | 同左 | ✓ 但只**模拟**填充 KV，不是真实交接 |

三个生产连接器的完成接口形状是统一的：`get_finished(finished_req_ids)` 返回 `(finished_sending, finished_recving)` 两个集合，配合 `wait_for_save()`。**这个统一形状是 PD 分离能被多种后端替换的基础**——调度器只依赖「哪些请求的 KV 已经传完」。

NIXL 还带一份异构 TP 布局转换（`tp_mapping.py:69 compute_tp_mapping`）：当 `tp_size < remote_tp_size` 时按 kv head 建立 `head_to_slot` 映射做 GQA 去重（`:101-132`），`is_mla` 或 `tp_size >= remote_tp_size` 时走直通分支（`:87`）。也就是说**跨不同 TP 度的交接只在特定关系下被定义**，超出范围必须拒绝而不是猜。

### 设计取舍

**为什么把完成接口做成集合而不是回调。** `get_finished` 返回两个 request id 集合，调度器每一轮去查。这让连接器可以是推送式（P 主动发）也可以是拉取式（D 主动取），调度器都不用改——NIXL 的 Pull/Push 两个连接器共用同一套完成接口就是证据。代价是完成信息有轮询延迟，调度器要按步对齐。

**为什么要 block 级 refcount 而不是请求级。** 一个请求的 KV 跨多个 block，交接过程中接收方可能只拿到一部分；block 级计数才能表达「这部分已经归你了，那部分还在路上」。取消时也要按 block 回收，否则会漏掉半传的块。

**为什么描述符要带去重后的指纹。** 每次交接都逐字段比 15 项开销不小，实际实现会先比一个短指纹，只有不匹配才逐项报错。本章的实现直接逐项比并给出差异字段，是为了让「错在哪一项」可读。

**为什么 RDMA 是生产路径的前提。** CPU 暂存路线在本机只有 1.34 GB/s，而 KV 在 S=2048 时是 224 MiB。用 RDMA 直接写对端显存可以跳过两次主机内存拷贝，这也是 NIXL/Mooncake 都要 RDMA 的原因。本机没有 `/dev/infiniband`，这条路线只能做源码分析。

### 命令

```bash
# 任务 A：交接协议、搬运参照与逐位对拍
python labs/L6/kv_handoff.py A --model <qwen3-1.7b> --seq 2048 --tokens 8 \
    --out results/worldvln/6.4/run/A

# 任务 C：五个取消时点与重复 ACK

    --out results/worldvln/6.4/run/C

# 任务 B：并置基线与 1P1D
python labs/L6/pd_serving_bench.py colocated --model <qwen3-1.7b> \
    --out results/worldvln/6.4/run/B --full
python labs/L6/pd_serving_bench.py 1p1d --model <qwen3-1.7b> \
    --out results/worldvln/6.4/run/B --full
```

跑之前先确认 P2P 处在哪一档：同一台机器上 224 MiB 的 GPU→GPU 拷贝见过 21.59 ms 与 5346 ms 两种结果，差 25 倍。

### 实测数字

- **KV 体量**：Qwen3-1.7B 每 token 114688 B（28 层 × 8 kv_head × 128 × 2 × 2B），S=2048 共 224.0 MiB。
- **搬运速率**：GPU→CPU→GPU 1.34 GB/s；GPU→GPU P2P 10.88 GB/s（每操作 0.385 ms，快档）。
- **对拍**：首 token 与后续 8 步 token 序列相同，每步 logits 最大绝对差 **0.0**。
- **拒绝**：10 类非法交接（含 TP 布局与 block 表）全部拒绝，0 次静默接受。
- **取消回收**：5 个时点全部 refcount 干净、staging 干净、显存回到基线（最长路径 +1.2 MiB 分配器残差）。
- **并置基线**：TTFT 22.5–178.8 ms、TPOT 10.6–12.0 ms、goodput 62.8–91.4 tok/s、峰值 26.57 GiB。
- **分离的额外成本**：搬运占 TTFT 的 10.6%（S=128）、46–48%（S=2048）、41.6%（S=8192）；S=8192、out=32 时占整个请求的 25.0%。

### 消融建议

1. 把 `kv_to_cpu` 换成直接 GPU→GPU，重跑 task A 的搬运段，确认 CPU 暂存路线的 1.34 GB/s 里各有多少来自两次拷贝与逐层循环。
2. 在 task A 里把 `seq` 从 2048 扫到 128/8192，画出「KV 字节 vs 搬运时间」的直线，确认是否线性、斜率是否等于实测速率。
3. 在 task C 里去掉「未完成 ACK 由发送方释放」这条规则，观察五个时点是否全部报 refcount 泄漏——用来确认这条规则是必需的而不是冗余的。
4. 把描述符里的 `tp_size` 改成 2、同时把 KV 按 head 切成两半，尝试实现 head_to_slot 式布局转换并与并置对拍——这是接 NIXL `tp_mapping` 的入口。

## 前沿

**把 KV 放进独立的数据平面。** 本章把 KV 当成「一次性交接的资产」。更进一步的路线是让 KV 常驻在一个共享存储/内存层（Mooncake Store、LMCache），P 写一次、多个 D 复用，前缀命中直接跳过 prefill。这条路线把「搬运」变成「寻址」，收益模型也从带宽问题变成命中率问题。

**对称内存与 RDMA 直写。** 6.1 里 NCCL 在本机注册了 48 GB 对称虚拟地址空间，但 NVLS 不可用。真正的 PD 数据平面依赖「对端显存可直接寻址」——NIXL 的 POSIX/RDMA 后端、Mooncake 的 TransferEngine 都是这条路。本机没有 `/dev/infiniband`，保持 `UNVERIFIED`。

**调度与分离的耦合。** 分离只是把 P 和 D 拆开，谁给谁派活是另一层问题（Dynamo 的 disaggregated serving 文档给的是一套 router + planner）。本章没有触及调度策略，只量了单条链路的成本结构。

**异构 TP 的交接。** NIXL 的 `compute_tp_mapping` 只在 `is_mla` 或 `tp_size >= remote_tp_size` 时走直通，否则做 GQA 去重。P 侧 TP=2、D 侧 TP=1 这类组合需要真实的 head 级重排，本章只做了源码分析，没有实测这条转换路径。

## 陷阱

**1. 以为交接只要把字节搬过去。** 没有描述符校验，接收方无法判断这 224 MiB 是不是自己要的。实测 10 类错配都必须在接入分页缓存之前就被拒绝。

**2. 不确认 P2P 状态就报搬运时间。** 同一台机器上 224 MiB 的 GPU→GPU 拷贝见过 21.59 ms 与 5346 ms 两种结果（每操作 0.385 ms vs 98.9 ms），差 25 倍。1.3 已经记录过这个慢状态；每次多卡实验前都要先测一次。

**3. 把 CPU 暂存的 1.34 GB/s 当成链路能力。** 它是 D2H + H2D + 逐层 Python 循环的合成结果，而 6.1 测到的单向链路是 24 GB/s。两者不是一回事。

**4. 用单请求 TTFT 论证分离的收益。** 单请求视角下分离永远亏——多出来的正好是搬运时间（S=2048 时占 46%–48%）。收益只在跨请求重叠里，而且要求重叠接近满格。

**5. 认为 S 越大越划算。** 搬运占 TTFT 的比例在 S=2048 已到 46%，S=8192 反而略降到 41.6%（prefill 涨得更快）。真正的判据是「prefill 时间 vs 搬运时间」的比值，不是输入长度本身。

**6. 取消路径只回收缓冲、不释放 block。** 第一版实现就是这样，五个时点全部报 refcount 泄漏。未完成 ACK 的交接必须由发送方释放自己持有的 block。

**7. 静默接受重复 ACK。** refcount 会变负，之后块分配会把还在用的块复用出去。实测的正确行为是直接报错。

**8. 把 DecodeBenchConnector 的结果当成 PD 收益。** 它的自述是「emulates prefill-decode disaggregation」——用哑值填 KV，只测 decode 侧在大 ISL 下的表现。它能回答「D 侧要花多久」，不能回答「分离比并置好多少」。

**9. 跨 TP 度直接接手 KV。** 同一次 prefill 在 TP=2 下被切成两份，TP=1 的接收方拿到其中一份不能当完整 KV 用。布局转换只在特定关系下被定义（NIXL 的 `tp_mapping.py:87`），范围外必须拒绝。

## 自测题

::: fold 1. Qwen3-1.7B 在 S=2048 时 KV cache 有多大？怎么算出来的？
224.0 MiB。每 token = 2（K 和 V）× 28 层 × 8 个 kv_head × 128 head_dim × 2 字节（bf16）= 114688 B；乘以 2048 得 234881024 B = 224.0 MiB。
:::

::: fold 2. 交接描述符里为什么必须有 `tp_size`/`tp_rank`？
因为同一份 KV 在不同 TP 度下是不同的分片。P 侧 TP=2 时每个 rank 只持有自己那半 head 的 KV；D 侧按 TP=1 接手就必须做 head 级重排，否则会把半份当成完整的。实测把 `tp_size` 改错会被直接拒绝，这是防止静默错位的必要字段。
:::

::: fold 3. 分离之后单请求 TTFT 变长了多少？这笔成本能靠什么赚回来？
变长的部分正好等于搬运时间：S=128 加 3.40 ms（占 TTFT 10.6%–13.4%），S=2048 加 33.66 ms（46%–48%），S=8192 加 127.44 ms（41.6%）。单请求永远亏，只能靠「P 的 prefill 不再阻塞 D 的 decode」这层跨请求重叠赚回来；S=2048 时 prefill 与搬运几乎相等，重叠空间最脆弱。
:::

::: fold 4. 为什么 task C 的第一版实现里五个时点全部报 refcount 泄漏？
因为取消路径只回收了 staging buffer，没有释放发送方持有的 block 引用。交接是两阶段提交式的：发送方持有 block，收到接收方 ACK 之后才释放。取消意味着 ACK 永远不会来，所以必须由发送方在取消路径上自己释放。补上这条规则后四个取消时点都回到 0.0 MiB。
:::

::: fold 5. 「decode 中取消」发出 1 个 token，这算不算重复提交？
不算。取消发生在第一层 decode 完成之后，那个 token 已经真实产生，既不能撤回也不该被撤销；要检查的是它没有被提交第二次。实测该时点的 token 列表长度为 1、无重复。
:::

::: fold 6. 为什么不能拿 DecodeBenchConnector 的结果说「PD 分离提升了 X%」？
它用哑值填充 KV cache，目的是让 decode 实例在受限环境里也能测大 ISL 下的解码性能，自述为 emulates prefill-decode disaggregation。它不含任何真实交接，因此测得到 D 侧成本，测不到分离相对并置的净收益。
:::

::: fold 7. 同一台机器上同一个拷贝操作，为什么两次运行能差 25 倍？
worldvln 的 PCIe P2P 存在两档状态：快档每操作约 0.385 ms、慢档约 98.9 ms。1.3 在驱动层测 PCIe 时记录过同一现象（同一二进制连跑两次，一次全慢一次全快），成因未定位。所以多卡实验前要先测一次搬运，把状态记进本轮 manifest，否则同一个实验会给出差 25 倍的结论。
:::
