## 本章回答三个问题

一张卡跑得动的模型，搬到多卡上第一步不是改模型，而是先回答三个问题：数据在谁手里、谁和谁配对、什么时候算真的交换完了。这三个问题的答案与设备数量无关，与后端实现强相关。答错的代价不是慢一点，而是**某个 rank 拿到一个看起来像结果的错值**，或者整个作业在没有任何人报错的情况下挂到超时。

1. rank 怎样持有数据？全局张量和局部片段是什么关系？
2. 集合通信靠什么匹配？op 名字相同就一定会配上吗？
3. API 返回、stream 完成、buffer 可以复用，这三件事有什么区别？

后面的 6.0b 到 6.5 都建立在这一层的语义之上：并行策略只是在决定「哪个 rank 持有什么」，通信库只是在执行「谁和谁换哪块内存」。这一章把这两个动作的口径固定下来。

::: warning 实验范围
集合通信的数值对拍是精确的（整数、容差 0），失败注入是可复现的。但**设备完成时间**只在 worldvln 的两张 L40S 上测过，跨机链路、NVLink 和 RDMA 的语义不在本章范围内。凡是没有对应硬件或权限的结论，正文都标 `UNVERIFIED`。
:::

## 机制拆解与推导

### 1. rank 是组内编号，不是设备编号

`init_process_group(rank, world_size)` 建立的是 **world** 这个进程组。rank 是这个组里的位置编号，与它用哪张卡、哪个 host 完全解耦。`labs/L6/distributed_basics.py` 里写作 `cuda:{rank}` 只是一种省事的约定；把 rank 1 放到 `cuda:3` 上，集合通信一样成立。

从 world 里再切出子组，得到的是另一层编号：

```python
pair_handles = [dist.new_group(p) for p in ([0, 1], [2, 3])]
even = dist.new_group([0, 2])
```

`new_group` 本身是一次集合操作：**所有 rank 必须以完全相同的顺序调用它**。上面这段代码的列表推导在四个 rank 上执行时，两次 `new_group` 的次序和参数都一致，所以安全。把 `new_group` 放进 `if rank == 0:` 里，就是在给自己埋一次初始化阶段的死锁。

组建好之后，两次编号要分清：`dist.get_process_group_ranks(group)` 给的是**全局 rank 列表**（`[0, 2]`），`dist.get_rank(group)` 给的是**组内序号**（even 组里 rank 2 的组内序号是 1）。本章的记录器保存的是前者，因为重建全局视图时只有全局 rank 才能和缓冲区位置对上。

同一个 `all_reduce` 在不同进程组上是三次完全独立的配对。world=4、子组为 `pairs = {0,1}/{2,3}` 与 `even = {0,2}` 时，三个调用给出三个不同的结果：

| 进程组 | 组内 rank | 输出（四个 rank 各自看到的值） |
|---|---|---|
| world `[0,1,2,3]` | 0–3 | `[16, 20, 17, 14]` |
| pairs `[0,1]` | 0–1 | `[10, 11, 6, 10]` |
| even `[0,2]` | 0–1 | `[9, 12, 7, 6]` |

全局视图里，同一次调用的四个局部片段必须靠 `(step, op, group, group_members)` 四元组才能对齐。只靠 `op` 名对齐，会把上面三个 `all_reduce` 混成一条记录——这正是第三节要讲的错配来源。

### 2. 匹配靠的是序号、字节数和通信子，不是 op 名字

集合通信没有消息头，亦无显式对端寻址字段。两端配对完全由底层实现约定：

- **Gloo** 用 tag（等同于调用序号）匹配，并在传输层校验字节数。
- **NCCL** 用通信子内的 `seqNum` 匹配，**不校验 numel**。

op 名字只出现在 API 和 profiler 里，不参与匹配。下面两张表是同一组注入在两种后端上的实测结局。

**Gloo（本地 macOS，2 进程，torch 2.14.0）**

| 注入 | wall | 退出码 | 现场 |
|---|---:|---|---|
| op 次序错配 | 21.0 s | `[1, 1]` | `gloo/transport/uv/unbound_buffer.cc:65`：recv 等 20000 ms 超时 |
| shape 错配 | 0.8 s | `[-6, -6]` | `gloo/transport/uv/pair.cc:253`：`op.nread == op.preamble.nbytes` 断言失败，进程 SIGABRT |
| 单 rank 提前退出 | 21.0 s | `[7, 1]` | rank0 主动退出；rank1 `unbound_buffer.cc:101`：send 等 20000 ms 超时 |
| 组错配 | 21.0 s | `[0, 1]` | rank0 在自己的 size=1 子组里成功返回；rank1 在 world 上等到超时 |
| P2P 两端都先发后收 | 0.8 s | `[0, 0]` | **完成**，Gloo 按 tag 匹配，容忍这个次序 |

**NCCL（worldvln 2×L40S，torch 2.13.0+cu130）**

| 注入 | wall | 退出码 | 现场 |
|---|---:|---|---|
| op 次序错配 | 90.0 s | `[-9, -9]` | watchdog 在 20 s 报 `SeqNum=1, OpType=ALLREDUCE`（rank0）/ `BROADCAST`（rank1）；进程没有自行退出，由父进程超时强杀 |
| shape 错配 | 84.0 s | `[0, -6]` | **rank0 正常返回**，rank1 SIGABRT |
| 单 rank 提前退出 | 83.5 s | `[7, -6]` | rank0 退出码 7；rank1 在 `AllReduce` 上被 watchdog 判定超时后中止 |
| 组错配 | 3.0 s | `[0, 1]` | rank1 在建立 NCCL 通信子阶段就失败：从 TCPStore 取 `ncclUniqueId` 超时 |
| P2P 两端都先发后收 | 83.5 s | `[-6, -6]` | 两端 `SeqNum=2, OpType=RECV` 同时超时 |

shape 错配这一行值得单独看。NCCL 这侧 **rank0 的调用成功返回了**，它拿到的输出是：

```text
rank0 输入 x = [1, 2, 3, 4]        （numel=4）
rank1 输入 x = [1, 2, 3, 4, 5, 6, 7, 8]  （numel=8）
rank0 得到的输出 = [2, 4, 8, 10]
```

`[2, 4, 8, 10] − [1, 2, 3, 4] = [1, 2, 5, 6]`——对端贡献的是它的第 1、2、5、6 个元素。这不是任何一次合法 `all_reduce` 的结果，但它看起来完全像一个归约结果：量级正常、每个位置都有值、没有任何异常。Shape 错配在 NCCL 上不会当场失败，只会给出一份错数据，然后在对端超时崩溃。**这是多卡调试里最贵的一类 bug。**

同一类注入在 Gloo 上的表现完全相反：0.8 秒、断言、SIGABRT、非零退出码，错误现场直接指到字节数校验那一行。结论不是「Gloo 更好」，而是**两个后端对同一份非法程序给出的失败形态不同，而可观测性决定了排查成本**。

### 3. 三步完成语义

`dist.all_reduce(t, async_op=True)` 返回一个 `Work`。从获得 `Work` 对象到「结果真正写入显存目标张量并对后续计算全局可见」之间有三道语义门槛。

**第一道：CPU 侧返回。** 这只说明调用已经入队。实测里它花 0.052–0.065 ms。

**第二道：stream 可见结果。** 对 NCCL，`WorkNCCL::wait()` 把**当前 CUDA 流**阻塞在 NCCL 的结束事件上，但默认不阻塞 CPU：

```cpp
// torch/csrc/distributed/c10d/ProcessGroupNCCL.cpp:820-825（v2.13.0）
void ProcessGroupNCCL::WorkNCCL::synchronizeStream() {
  auto currentStream = at::cuda::getCurrentCUDAStream(device_.index());
  // Block the current stream on the NCCL stream
  ncclEndEvent_->block(currentStream);
  ...
}
```

```cpp
// torch/csrc/distributed/c10d/ProcessGroupNCCL.cpp:850-851（v2.13.0）
  // In case of blockingWait or a timeout value is specified by the user, we
  // block the CPU thread until the work is completed or timed out.
  if (blockingWait_ || timeout != kNoTimeout) {
```

`blockingWait_` 的默认值取自环境变量 `TORCH_NCCL_BLOCKING_WAIT`，默认 `false`（同文件 `:951`）。所以「`work.wait()` 返回了」在 NCCL 上的准确含义是：**调用流上后续的 kernel 会排在通信之后**，而不是「CPU 现在能安全读这块内存」。

对 Gloo，语义相反：`Work::wait` 直接卡在条件变量上，CPU 返回即代表完成。

```cpp
// torch/csrc/distributed/c10d/Work.cpp:121-126（v2.14.0）
bool Work::wait(std::chrono::milliseconds timeout) {
  std::unique_lock<std::mutex> lock(mutex_);
  if (timeout == kNoTimeout) {
    // This waits without a timeout.
    cv_.wait(lock, [&] { return completed_; });
```

**第三道：buffer 可复用。** 这一道最容易被前两道掩盖。通信还没读完输入缓冲区时改写它，结果是错的；通信还在写输出缓冲区时把它还给分配器，结果是读到脏数据（2.0c 从分配器一侧讲过同一件事）。

把这三道拆开，就得到五种写法。worldvln 2×L40S、64 MiB `all_reduce`、期望值 3.0，每种变体 20 次 × 2 rank：

| 变体 | 读时正确 | 全同步后正确 | 读到的值 | 说明 |
|---|---:|---:|---|---|
| `cpu_return_only`：只等 CPU 返回就在默认流上读 | 1/40 | 40/40 | `1.0 / 2.0 / 3.0` | 默认流与通信流无依赖，读到的是本 rank 的旧值 |
| `event_without_wait`：在入队点记事件，计算流等这个事件 | 0/40 | 40/40 | `1.0 / 2.0` | 事件只代表「调用已入队」，不代表通信完成 |
| `premature_overwrite`：不等完成，在第三条流上改写 buffer | 0/40 | **0/40** | `0.0 / 1.0 / 2.0` | 输入被覆盖，通信结果本身就是错的，事后同步也救不回来 |
| `event_after_wait`：先 `wait()` 让通信流挂上结束事件，再记事件 | 40/40 | 40/40 | `3.0` | 正确做法之一 |
| `wait_correct`：同一流上 `wait()` 之后直接读 | 40/40 | 40/40 | `3.0` | 正确做法之二 |

`event_without_wait` 是这张表里最有信息量的一行：它的写法看起来非常标准（记事件、跨流等待），但它只是把「入队点」传播到计算流。事件必须在 `work.wait()` **之后**记录，才携带完成信息。这一点无法从「记一个 event」这个动作本身看出来，只能从实现里读出来。

**同一套写法换到跨机 transport 上，分类结论完全一样。** 把同一份代码放到 crater ↔ crater2（各 1×RTX 5090，`NET/Socket`，链路条件见 6.1 第 7 节），同样 64 MiB、期望值 3.0、每变体 20 次 × 2 rank：

| 变体 | 读时正确 | 全同步后正确 | CPU 返回中位 | 设备完成中位 |
|---|---:|---:|---:|---:|
| `cpu_return_only` | 0/40 | 40/40 | 0.0747 ms | 593.59 ms |
| `event_without_wait` | 0/40 | 40/40 | 0.0722 ms | 593.59 ms |
| `premature_overwrite` | 0/40 | **0/40** | 0.0707 ms | 594.60 ms |
| `event_after_wait` | 40/40 | 40/40 | 0.0706 ms | 594.35 ms |
| `wait_correct` | 40/40 | 40/40 | 0.0697 ms | 593.71 ms |

逐行的判定与单机档一致，三种错误写法的错误形态也一致（`premature_overwrite` 同样救不回来，读到的都是 `0.0`）。变的是量级：**CPU 返回仍是 0.07 ms 量级，设备完成从单机档的 4.72 ms 涨到 593.6 ms，两者的比值从 90 倍变成 8000 倍。** 错误写法的暴露窗口被拉长——跨机时 `cpu_return_only` 读到旧值的比例从 39/40 变成 40/40，「碰巧读对」这一支被链路延迟彻底挤掉。

换到另一条网卡（容器 overlay `eth0`）复跑同一组，五个变体的读数分类与设备完成时间（593.6–594.6 ms）都与 `net1` 一致。**这组结论只依赖「传输在 CPU 侧代理线程上完成」，不依赖具体网卡。**

但跨机档的「设备完成」这一列本身要换工具：它由 CPU 侧墙钟（`torch.cuda.synchronize()` 包住整轮）测得，不是 device event。跨机搬数据的是代理线程，device event 只包住 GPU 上那一小段 kernel，直接读会得到小一个数量级的数字（6.1 第 7 节给了同一现象的定量对照：4 KiB broadcast 不隔离 0.017 ms、隔离后 0.062 ms）。**完成语义的定义没变，测量它的工具必须跟着传输路径变。**

### 4. P2P 的配对：一对 rank 一个通信子，按序号配对

`send`/`recv` 与集合通信的匹配规则不同。NCCL 后端给未批量化的 P2P 单独建通信子，键按有序对归一化：

```cpp
// torch/csrc/distributed/c10d/ProcessGroupNCCL.cpp:151-157（v2.13.0）
std::string getKeySendRecv(int myRank, int peer) {
  int lowRank = myRank < peer ? myRank : peer;
  int highRank = myRank < peer ? peer : myRank;
  std::string sendRecvPair =
      std::to_string(lowRank) + ":" + std::to_string(highRank);
  return sendRecvPair;
}
```

rank 0 发给 1 和 rank 0 收自 1，算出来的键都是 `"0:1"`：**两个方向共用同一个 2-rank 通信子**。同一通信子上再按 `seqNum` 配对，于是：

- rank0 `isend`(seq0) ↔ rank1 `irecv`(seq0)：正确配对
- rank0 `isend`(seq0) 与 rank1 `isend`(seq0)：两个 send 对上了

实测就是这样：两端都「先 `isend` 再 `irecv`」时，两端的 `SeqNum=2, OpType=RECV` 同时超时。把两端的次序改成相反（一端先发后收、另一端先收后发），或者直接用 `dist.batch_isend_irecv` 成对提交，都能完成。本章的 `all_reduce`/`all_gather`/`reduce_scatter`/`send_recv` 对拍里，NCCL 一路走 `batch_isend_irecv`，Gloo 一路走未批量化的 `isend`/`irecv`，两者数值都与单进程参照逐元素相等。

批量化路径在跨机 transport 上又暴露了一层差异。crater ↔ crater2 各一张 RTX 5090、8 MiB 载荷、30 轮、`NET/Socket`：

| 写法 | 结果 | 设备完成中位 | CPU 入队中位 |
|---|---|---:|---:|
| `async_isend_irecv`：两条都先入队、再逐个 `wait()` | **两端都失败** | — | — |
| `batch_isend_irecv`：`P2POp` 列表一次提交 | 两端各 30/30 正确 | 71.57 ms | 0.068 ms |
| `coalescing_async`：`_coalescing_manager(async_ops=True)` + `cm.wait()` | 两端各 30/30 正确 | 71.61 ms | 0.140 ms |
| `coalescing_sync`：`_coalescing_manager(async_ops=False)` | 两端各 30/30 正确 | 71.61 ms | 0.126 ms |

三行成功的写法给出同一条链路时间（71.54–71.62 ms，离散 0.1%），起点也一致：8 MiB ÷ 0.1176 GB/s = 71.3 ms，与 6.1 量到的跨机链路速率吻合。**区别只在 CPU 侧：批量化把每轮入队压到 0.068 ms，两条 coalescing 路径是 0.126–0.140 ms**，而设备完成时间完全一样——批量化省的是提交开销，不是传输时间。

失败那一行值得单独记：`async_isend_irecv` 在单机档是「逐条路径的正确形式」，跨机档却两端同时报

```text
ncclSocketInit: connecting to address  with family 1 is neither AF_INET(2) nor AF_INET6(10)
```

——未批量化的 `isend`/`irecv` 在延迟建链时要给新通信子提供对端地址，而 Socket transport 上这次建链没有携带可用地址，于是直接失败（rank0 报 family 1、rank1 报 family 0，同一原因的两侧表现）。**在单机上被证明正确的写法，换 transport 后必须重测**，这条比任何性能数字都重要。

最后一个变体 `sync_send_recv_ring`（两条阻塞 `send`/`recv` 顺序调用）在跨机档触发 `CUDA error: an illegal memory access was encountered`，rank 进程在写出结果文件前就被 watchdog 终止（工件留在 `results/crater/6.0/20260922-p2p-batching`）。因此正式那一档用 `--variants` 显式排除了它，并把这次失败按原样留在结果目录里——**失败变体不能靠「反正会崩」跳过，它的崩溃形态本身就是结论的一部分。**

Gloo 在同一场景下用 tag 匹配，不区分方向，所以同样的错误次序照样完成。**「P2P 一定要求两端次序相反」不是通信的普遍规律，而是 NCCL 未批量化 P2P 的实现约束。**

::: fold 为什么 NCCL 要给每对 rank 单独建通信子
源码注释给出了两条理由（`ProcessGroupNCCL.cpp:4164-4170`）：一条通信子只对应一条流，如果多个未批量化 P2P 复用同一条通信子，会被序列化到同一条流上；而 NCCL 不允许同一条通信子上跨流发多个 P2P。把「每条流一个通信子」这条不变量守住，代价是每次 P2P 都要新参与一次通信子建立。
:::

## 工程实现 · 源码解析

### 设计取舍

**为什么 NCCL 的 `wait()` 默认不阻塞 CPU。** 多卡训练里，通信常常要和计算重叠：CPU 提交完通信后应该立刻去准备下一个 batch，而不是停在原地。把同步语义放在**流**上而不是 CPU 上，是让重叠自然发生的前提。代价是「`wait()` 返回」这件事不再蕴含「数据可用」，调用方必须自己维护流之间的依赖。

**为什么 Gloo 与 NCCL 对非法程序的反应差这么多。** Gloo 在传输层逐 op 校验字节数（`pair.cc:253`），把错误变成立即的断言；NCCL 的 kernel 按通信子里的 `seqNum` 和本地 numel 推进，对端的 numel 不参与判定，于是错配表现为「一端算完、一端超时」。可观测性上的取舍很明确：立即失败更容易定位，而宽松检查在合法程序里省掉了一次同步。

**为什么通信子要按进程组划分。** 不同子组是不同通信子，意味着组间没有共享状态，也意味着同一对 rank 在不同组里是两次独立的配对。这让「一个 rank 同时属于多个组」变得可行（张量并行组、数据并行组、流水线组），代价是每组都要独立建链，组数多的时候初始化时间和显存开销都需要算。

**为什么 P2P 要批量化。** `batch_isend_irecv` 把多个 P2P 操作放进同一个通信子、同一批提交，避免每个操作各建一次通信子，也让配对关系显式化。代价是调用方要一次性列出本 rank 所有的 P2P 操作，不能边算边发。

## 前沿

**对称内存（symmetric memory）。** NCCL 的对称内存把各 rank 的缓冲区注册成彼此可寻址的窗口，NVLS 让归约在交换机一侧完成，SHARP 把聚合下沉到网卡。它们改变的是「归约在哪里发生」，不改变本章的三步完成语义——`wait()` 之后的依赖关系仍然要靠流和事件维护。worldvln 无 NVLink、无 RDMA 设备，这条路线在本项目里保持 `UNVERIFIED`，6.1 会给出硬件/驱动/权限矩阵。

**超时取证。** PyTorch 的 FlightRecorder 与 `TORCH_NCCL_DUMP_ON_TIMEOUT` 会在 watchdog 判定超时后 dump 出每个 rank 最后入队与最后完成的操作序号。本章的 NCCL 现场就来自这条路径（`ProcessGroupNCCL.cpp:730/1964/2372`）。它解决的是「挂住了但不知道挂在哪一步」，不解决「为什么配不上」。

**设备发起的通信。** IBGDA 与 NVSHMEM 让 GPU 侧直接发起通信，CPU 不再逐次提交。这会改变第一步（API 返回）的形态——提交动作本身下沉到 kernel 里——但第二步和第三步的语义仍然成立。6.3 会按抽象层次比较 NCCL、NVSHMEM、DeepEP 与 UCCL。

**弹性与成员变更。** 本节所有结论都假设进程组在一次作业内不变。弹性训练（TorchFT 等）要在 rank 集合变化后重建通信子，重建期间旧的 `Work` 句柄与缓冲区归属需要显式作废。本章没有覆盖这条路径。

## 陷阱

**1. 把 CPU 返回当完成。** `all_reduce(..., async_op=True)` 之后不建立任何流依赖就去读结果，实测 40 次里只有 1 次侥幸正确。默认流与通信流之间没有任何顺序关系，通过率不构成正确性证据。

**2. 用 op 名字判断配对。** `all_reduce` 这个名字在不同进程组、不同 step 上是互不相干的配对。重建全局视图必须带 `(step, op, group, group_members)`，少了任何一项都会把两批数据混在一起。

**3. 把 `ev.record(stream)` 当完成标记。** 事件标记的是它在流上的**位置**。在 `work.wait()` 之前记录，事件只代表「调用已入队」；实测 40 次全错。正确顺序是 `wait()` → `record()` → 跨流 `wait_event()`。

**4. 在子组里假定 shape 一致。** 子组的 rank 数决定了 `reduce_scatter` 的输入长度和 `all_gather` 的输出长度。world=4 与 pair 组（size=2）上同一个 op 的 shape 不同，写死 shape 会在切换并行度时立刻出错。

**5. 假定错配一定会报错。** NCCL 上 shape 错配的 rank0 正常返回了一个 `[2, 4, 8, 10]` 的错值；它不崩溃、不警告，直到对端超时。跨 rank 校验 shape（或在测试里加一次 `all_gather_object` 的元数据对拍）是唯一可靠的防线。

**6. 假定 P2P 通信两端可任意独立定序。** NCCL 未批量化 P2P 在同一对 rank 上共用一个 2-rank 通信子，按序号配对；两端同序会配错。用 `batch_isend_irecv` 成对提交，或者显式约定两端的操作次序。

**7. 把 Gloo 的结论外推到 NCCL。** 两者的匹配规则、超时行为、失败形态都不同：同一个「先发后收」的次序，Gloo 完成、NCCL 死锁。跨后端复用代码时，P2P 次序和 shape 校验要单独检查。

**8. 把单机上验证过的写法直接搬到跨机。** 未批量化的 `isend`/`irecv`（先入队再逐个 `wait()`）在单机上是正确形式，跨机 `NET/Socket` 上两端同时报 `ncclSocketInit` 地址族错误。传输层变了，通信子的建立路径也变了，正确性要重测。

## 自测题

::: fold 1. world_size=4，每个 rank 的输入是 `[rank, rank, rank, rank]`。`all_reduce(SUM)` 之后，rank 2 的张量是什么？
`[6, 6, 6, 6]`（0+1+2+3 = 6）。所有 rank 的输出相同，这也是 `all_reduce` 与 `reduce` 的区别：后者只有目标 rank 拿到结果。
:::

::: fold 2. 两个 rank 各自调用 `all_reduce`，一个用 world 组，一个用 size=1 的子组。会发生什么？
Gloo 上 size=1 子组的那一侧立即返回（自己和自己归约），另一侧等 20 s 超时（实测 `group_mismatch`，退出码 `[0, 1]`）。NCCL 上更早失败：等待方在建立通信子阶段就取不到 `ncclUniqueId`（实测 3.0 s，退出码 `[0, 1]`）。
:::

::: fold 3. `work.wait()` 返回之后，CPU 能立刻安全地读这块 CUDA 张量吗？
不能。NCCL 的 `wait()` 默认只把**当前流**阻塞在 NCCL 结束事件上，`blockingWait_` 默认 `false`。要 CPU 侧安全读，需要 `torch.cuda.synchronize()`，或把读操作放进那个已经被阻塞的流里（实测 `wait_correct` 就是后者，40/40 正确）。
:::

::: fold 4. 为什么 `ev.record(s_comm)` 写在 `all_reduce(async_op=True)` 之后、`work.wait()` 之前，跨流等待这个事件仍然会读到旧值？
事件记录的是流上的位置。此时 `s_comm` 还没有和 NCCL 的结束事件建立依赖，事件覆盖的范围只到「调用已入队」。`work.wait()` 的作用正是把 `ncclEndEvent_` 阻塞到当前流上（`ProcessGroupNCCL.cpp:820-825`），之后记录的事件才代表通信完成。
:::

::: fold 5. 一段两 rank 的 P2P 代码在 Gloo 上跑通，切到 NCCL 后卡死。最可能的原因是什么？
两端对 `isend`/`irecv` 的调用次序相同。NCCL 为这对 rank 建一个共用的 2-rank 通信子并按序号配对，两端的 seq0 都是 send，谁也没在 seq0 上 recv，于是两端的 `RECV` 同时超时。改成 `batch_isend_irecv` 成对提交，或让两端次序相反。
:::

::: fold 6. 为什么本章的对拍用整数而不是浮点？
集合通信的语义是「把数据搬到该在的位置」，与数值精度无关。整数让容差为 0，任何位置错位、元素数错配都会立刻暴露；用浮点则需要先确定一个与后端无关的容差，反而把「搬错了位置」和「累加顺序不同」两类问题混在一起。
:::

::: fold 7. 同一份完成语义代码，单机档设备完成中位 4.72 ms、跨机档 593.6 ms，而 CPU 返回都是 0.07 ms 量级。这说明了什么？
说明三个「完成」门槛里，只有第一道与传输路径无关：CPU 返回始终是入队时间（微秒级），第二、三道的时间由链路上的字节决定（相差 126 倍，与 6.1 的链路速率一致），但它们的**语义**没变——跨机档里 `cpu_return_only` 读旧值、`premature_overwrite` 事后也救不回来，分类与单机档逐行相同。所以换传输路径要重测的是「暴露概率」和「计时工具」，不是判据本身。
:::

::: fold 8. 跨机档为什么不能直接用 device event 报「设备完成」？
跨机时数据由 CPU 侧的代理线程经 TCP 送出，device event 只包住 GPU 上的那一小段 kernel，kernel 返回不代表字节已经上链路。实测同一配置下 4 KiB broadcast 不隔离时 0.017 ms、逐轮隔离后 0.062 ms，差 3.6 倍。跨机档统一用 `torch.cuda.synchronize()` 的 CPU 墙钟，并与裸 TCP（16 MiB 上 0.1176 GB/s）对照过一次。
:::
