## 本章回答三个问题

6.0 讲清了通信怎么配对、什么时候算完成；这一章讲它有多贵。集合通信的成本模型看起来简单——启动开销加传输时间——但真正难的是口径：同一句「all-reduce 带宽 14.8 GB/s」，在不同文献里可能指每 rank 输入字节、单向链路上的字节，或者双向聚合字节，三者相差 1.5 到 2 倍。口径不统一，跨论文、跨集群的数字就没法比。

1. 算法和协议在什么条件下切换？切换由谁决定？
2. 带宽口径怎样统一？算法带宽与总线带宽分别是什么？
3. 拓扑与消息尺寸怎样共同决定成本？

这一章有套测量，边界完全不同，数字不能互相代入：

| 档 | 机器与链路 | 传输路径 | 覆盖内容 |
|---|---|---|---|
| 单机（主体） | worldvln，2×/4× L40S，PCIe Gen4×16，无 NVLink | `SHM/direct/direct`，不经网络栈 | 口径、α/β、算法与协议、强制组合、重叠 |
| 跨机 | crater ↔ crater2，各 1×RTX 5090，`net1` 1 GbE | `NET/Socket`（两机均无 `/dev/infiniband`） | 链路 β 上限、字节主导区间、裸 TCP 参照、跨传输的完成语义 |

单机档的结论是「PCIe 与 NVLink 的量级差异」，跨机档的结论是「网卡与 1 GbE 是硬上限」。跨机档用的是消费级 RTX 5090 与千兆网卡，不代表生产集群的 RDMA 或 NVLink 域，两者都只在自己的条件下成立。

## 机制拆解与推导

### 1. 成本公式来自 NCCL 自己的步数定义

不用猜 ring 怎么走。NCCL 的调优代码把每种 collective 的步数写死在一个表达式里（`src/graph/tuning.cc:269-271`，v2.29.7-1）：

```cpp
    int nsteps = coll == ncclFuncAllReduce ? 2*(nRanks-1) :
      coll == ncclFuncReduceScatter || coll == ncclFuncAllGather ? nRanks-1 :
      nRanks;
```

每次传输的数据量是 `M/nRanks`。把这两件事乘起来，就是每个 rank 需要收发的字节数：

| collective | 步数 | 每 rank 过链字节 | 时间模型 | busbw |
|---|---|---|---|---|
| ring all-reduce | 2(N−1) | 2M(N−1)/N | 2(N−1)α + 2M(N−1)/(Nβ) | 2(N−1)/N × M/t |
| all-gather | N−1 | M(N−1)/N | (N−1)α + M(N−1)/(Nβ) | (N−1)/N × M/t |
| reduce-scatter | N−1 | M(N−1)/N | (N−1)α + M(N−1)/(Nβ) | (N−1)/N × M/t |
| broadcast | N−1 | M（root 发出） | (N−1)α + M/β | M/t |

`α` 是每步的启动/同步开销，`β` 是链路速率。这张表和公式是本章所有数字的口径基准：**`M` 始终指每 rank 输入字节**，`N` 单独标出，两者不混用。

测出来的 α 和 β（最小二乘拟合，只用 ≥1 MiB 的点）：

| collective | N=2 近（α / β） | N=2 远（α / β） | N=4（α / β） |
|---|---|---|---|
| all_reduce | 16.02 µs / 14.82 GB/s | 15.85 µs / 14.56 GB/s | 73.38 µs / 6.53 GB/s |
| all_gather | 13.90 µs / 12.74 GB/s | 13.79 µs / 12.71 GB/s | 86.59 µs / 3.16 GB/s |
| reduce_scatter | 13.36 µs / 12.81 GB/s | 14.15 µs / 12.79 GB/s | 20.13 µs / 3.01 GB/s |
| broadcast | 13.16 µs / 24.18 GB/s | 14.09 µs / 23.83 GB/s | 16.94 µs / 11.65 GB/s |
| sendrecv（环） | 51.78 µs / 14.66 GB/s | 48.66 µs / 14.44 GB/s | 57.48 µs / 7.81 GB/s |

两条读法：

**β 随 N 下降**。all_reduce 的单向链路速率从 N=2 的 14.82 GB/s 掉到 N=4 的 6.53 GB/s。注意这里的 β 是「每 rank 每方向速率」，N 变大时总端口带宽被更多 rank 分走，而 busbw 已经把 N 的因子折算进去了（N=4 时 all_reduce 的 busbw = 9.79 GB/s，比 β 大 1.5 倍，这个 1.5 就是 2(N−1)/N）。

**β 与 collective 有关**。同一块链路，broadcast 的 β 是 all_gather 的 1.9 倍。原因不是链路有差别，而是流量形态不同：broadcast 是纯单向流，all_gather 是双向同时收发。把 all_gather 的 β（12.74 GB/s）按两个方向算聚合是 25.5 GB/s，与 broadcast 单向的 24.18 GB/s 同量级——**链路的聚合带宽是 ~25–30 GB/s，单向流可以吃满 24 GB/s，双向流每方向只能拿到一半。**

### 2. 单一 α/β 模型覆盖不了 5 个数量级

把 4 KiB 到 256 MiB 的全部点拿去拟合，最大相对误差是 22%–56%；只用 ≥1 MiB 的点，误差降到 2%–18%：

| collective | 全区间最大相对误差 | ≥1 MiB 最大相对误差 |
|---|---:|---:|
| all_reduce | 0.352 | 0.069 |
| all_gather | 0.479 | 0.031 |
| reduce_scatter | 0.389 | 0.032 |
| broadcast | 0.386 | 0.022 |
| sendrecv | 0.259 | 0.158 |

小消息段支配时间的不再是传输，而是每步的同步与内核启动；用一个大消息段的 α 去预测 4 KiB 会高估一个数量级。这不是模型错了，而是**两段机制**：小消息看延迟，大消息看带宽。做容量规划时先确认目标消息落在哪一段，再选公式。

### 3. 算法与协议由 NCCL 的调优表决定

NCCL 在初始化时打印自己的候选成本表，并在每次 collective 时打印最终选择。这两个都是可解析的证据，不需要由「带宽接近某个值」反推算法：

```text
NCCL INFO AllReduce: 1048576 Bytes -> Algo RING proto SIMPLE channel{Lo..Hi}={0..1}
NCCL INFO AllReduce: 4096 Bytes -> Algo RING proto LL channel{Lo..Hi}={0..0}
```

实测的自动选择（2×L40S）：

| 消息大小 | 算法 | 协议 | 通道数 |
|---|---|---|---|
| 4 KiB – 256 KiB | RING | LL | 1→2（16 KiB 起） |
| 1 MiB – 256 MiB | RING | SIMPLE | 2 |

切换点在 256 KiB 与 1 MiB 之间：LL 协议为小消息优化，SIMPLE 从 1 MiB 起接管。强制指定算法/协议后选择随之改变（`Algo TREE proto SIMPLE`），说明日志里的选择确实来自调优，而不是解析错位。

**哪些强制组合是合法的，源码里写得清清楚楚**（`src/graph/tuning.cc:272-275`）：

```cpp
      if ((coll == ncclFuncBroadcast || coll == ncclFuncReduce) && a != NCCL_ALGO_RING) continue;
      if ((coll == ncclFuncReduceScatter || coll == ncclFuncAllGather)
          && a != NCCL_ALGO_PAT && a != NCCL_ALGO_RING
          && a != NCCL_ALGO_NVLS && a != NCCL_ALGO_COLLNET_DIRECT) continue;
      if (coll == ncclFuncAllReduce && a == NCCL_ALGO_PAT) continue;
```

强制 `NCCL_ALGO=Tree` 的实测结果与这段代码完全对应：

| collective | auto | Ring | Tree |
|---|---|---|---|
| all_reduce | OK | OK | OK |
| all_gather | OK | OK | **FAIL** |
| reduce_scatter | OK | OK | **FAIL** |
| broadcast | OK | OK | **FAIL** |

失败不是静默回退，而是直接报错：

```text
Error : no algorithm/protocol available for function AllGather with datatype ncclInt8.
NCCL_ALGO was set to Tree. NCCL_PROTO was set to Simple.
```

协议侧没有这种硬性限制：1 MiB 的 all_reduce 在 auto / Simple / LL / LL128 四种设置下都能跑，只是性能不同（见下）。

### 4. 强制算法与协议的性能对照

同一个 all_reduce，256 MiB，2×L40S：

| 配置 | 时间 | busbw | 实际选择 |
|---|---:|---:|---|
| auto | 18.135 ms | 14.80 GB/s | RING / SIMPLE |
| 强制 Ring / Simple | 18.538 ms | 14.48 GB/s | RING / SIMPLE |
| 强制 Ring / LL128 | 30.843 ms | 8.70 GB/s | RING / LL128 |
| 强制 Tree / Simple | 17.723 ms | 15.15 GB/s | TREE / SIMPLE |

auto 与强制 Ring/Simple 差 2.2%，说明 1 MiB 以上 auto 选的就是 Ring/Simple，日志与实测互证。LL128 在大消息上比 Simple 慢 40%——LL128 的 128 字节粒度在这条 PCIe 链路上没有优势。

4 卡时反过来：

| 配置（N=4，256 MiB all_reduce） | 时间 | busbw |
|---|---:|---:|
| auto | 41.138 ms | 9.79 GB/s |
| 强制 Tree / Simple | 34.717 ms | 11.60 GB/s |

**Tree 比 auto 选的 Ring 快 18.5%。** 这台机器上 `libnccl-tuner.so` 不存在，用的是默认拓扑模型；模型对这套「三卡在同一 PCIe host bridge、第四卡跨 NUMA」的非对称拓扑估计不准。这是「先量再调」的直接理由：默认不是最优，而最优随拓扑变化。

### 5. 近拓扑与远拓扑

同一对 GPU 之间的差异：

| 组合 | 位置 | all_reduce β | broadcast β |
|---|---|---:|---:|
| GPU0–GPU1 | 同 NUMA，PCIe host bridge（NODE / PHB） | 14.82 GB/s | 24.18 GB/s |
| GPU0–GPU3 | 跨 NUMA（SYS，经 UPI） | 14.56 GB/s | 23.83 GB/s |

差 1.8% 和 1.4%。跨 NUMA 几乎没有代价，原因是两段都还在 PCIe 上、UPI 的带宽高于实测速率；NCCL 日志显示通道走的是 `via SHM/direct/direct`，即 GPU 之间的直接 P2P 映射，没有落到主机内存中转。

**这个结论只对 PCIe 成立。** 有 NVLink 的平台上，近/远会变成 NVLink 与 PCIe 的差别，量级完全不同；跨机时决定成本的是网卡与 RDMA 路径，不是 UPI。1.3 已经从驱动层测过这台机器的 PCIe 单向能力（x16 22.67 GB/s），这里的 24.18 GB/s 是集合通信视角下的同一量级。

### 6. 通信与计算的重叠

GEMM 取 8192³ bf16（1099.5 GFLOP），通信取 64 MiB all_reduce，2×L40S：

| 配置 | 时间 | 折算 |
|---|---:|---|
| 通信单独 | 4.655 ms | 14.42 GB/s |
| 计算单独 | 4.645 ms | 236.7 TFLOP/s |
| 串行（计算等通信） | 9.751 ms | 4.655 + 4.645 = 9.300 ms，吻合 |
| 独立重叠（正确依赖） | 5.259 ms | 比串行快 46.1% |
| 理论上限 | 4.645 ms | 达成 97% |

重叠的代价是资源竞争：重叠期间 GEMM 只有 209.1 TFLOP/s（单独时的 88.4%），通信有效速率 12.76 GB/s（单独时的 88.5%）。**两个方向各掉约 11.6%**，但总时间仍然接近理论上限——这就是重叠的价值：牺牲 12% 的单项效率，换回 46% 的端到端时间。

还有一条必须单独说的：把「等待通信流」这一步漏掉，时间看起来一样快，但结果是错的。同一个重叠写法，正确版本 20 次读到的 buffer 值全部是 2.0；漏掉 `wait_stream` 的版本读到 `{1.0, 2.0}` 两种值——32 MiB 的 all_reduce 还没写完，D2H 就把半成品拷走了。**重叠的收益与正确性是两件事，必须分开验。**

### 7. 跨机 transport：一条千兆链路把成本模型压成纯字节

前六节的边界是「单机、PCIe」。同一套采集脚本可以放到两台互通的机器上（crater 与 crater2，各一张 RTX 5090，走 `net1` 的 1 GbE，`NCCL_SOCKET_IFNAME=net1`、`NCCL_IB_DISABLE=1`），此时 NCCL 的通道路径从 `SHM/direct/direct` 换成 `NET/Socket`。**换的不只是带宽数字，还有三件事：可用的字节区间、算法与协议的切换点、以及「什么时候能计时」。**

先看链路本身。两台机器的 `net1` 协商速率都是 1000 Mb/s（`/sys/class/net/net1/speed`）。用裸 TCP 单向流（不经 NCCL、不经 GPU）反复发 16 MiB 并等对端回执，**中位 142.683 ms，即 0.1176 GB/s**——1 GbE 线速 0.125 GB/s 的 94.1%。

再看 NCCL 在同一对链路上的选择与耗时（隔离计时，见下）：

| 消息 | 算法/协议/通道 | all_reduce t | all_reduce busbw | all_gather busbw |
|---|---|---:|---:|---:|
| 4 KiB | RING / LL / 1 | 0.166 ms | 0.025 GB/s | 0.015 GB/s |
| 64 KiB | RING / SIMPLE / 2 | 0.670 ms | 0.098 GB/s | 0.049 GB/s |
| 1 MiB | RING / SIMPLE / 2 | 9.052 ms | 0.116 GB/s | 0.058 GB/s |
| 4 MiB | RING / SIMPLE / 2 | 35.879 ms | 0.117 GB/s | 0.058 GB/s |
| 16 MiB | RING / SIMPLE / 2 | 143.256 ms | 0.117 GB/s | 0.059 GB/s |
| 64 MiB | RING / SIMPLE / 2 | 571.853 ms | 0.117 GB/s | 0.059 GB/s |
| 256 MiB | RING / SIMPLE / 2 | 2286.445 ms | 0.117 GB/s | 0.059 GB/s |

16 MiB 这一格值得单独看：**裸 TCP 0.1176 GB/s、NCCL all_reduce 0.1171 GB/s、NCCL broadcast 0.1175 GB/s，三个数字在 0.4% 以内。** 集合通信没有给链路增加可观的开销，它只是把这条链路跑满了；千兆链路上各 collective 的差别被链路吞掉，只有 4 KiB 那一档还能看出 op 之间的差异（0.015–0.066 GB/s，全被启动开销支配）。

与单机 PCIe 档对照（同为 64 MiB）：

| 指标 | 单机 2×L40S（PCIe） | 跨机 2×5090（1 GbE） | 比值 |
|---|---:|---:|---:|
| broadcast 单向 β | 24.154 GB/s | 0.118 GB/s | 205× |
| all_reduce busbw | 14.847 GB/s | 0.117 GB/s | 126× |
| all_gather busbw | 6.364 GB/s | 0.059 GB/s | 108× |
| 起始段（4 KiB broadcast） | 0.100 GB/s | 0.066 GB/s | 1.5× |

**小消息的差距只有 1.5 倍，大消息是 100–200 倍**，这正是「启动开销」与「字节速率」的分离：4 KiB 的耗时由每跳的固定成本支配，两台机器之间多一次 TCP 往返并不比 PCIe 上的 launch 与同步贵多少；一旦进入字节主导区间，1 GbE 与 PCIe Gen4×16 的差距就完整暴露出来。单机档第 2 节那张「单一 α/β 模型覆盖不了 5 个数量级」的表在跨机档里依然成立，但原因换了：跨机档的斜率由网卡决定，而且从 1 MiB 起就完全平坦。

换一条网卡也一样。同一个 `/24` 上另有容器 overlay `eth0`（`/sys/class/net/eth0/speed` 报 10000，MTU 1450），跨机扫描给出 all_reduce 0.113 GB/s、broadcast 0.114 GB/s，与 `net1` 相差 3.5%。**「网卡自报 10 GbE」与「两个容器之间实际能跑多少」是两件事**，这里只有把裸 TCP 参照一起测出来才能判定瓶颈在哪一段。

**跨机计时必须换口径。** 本节所有跨机数字都用 `dist.barrier()` 逐轮隔离后再记 device event。原因是 NCCL 跨机时真正搬数据的是 CPU 侧的 proxy 线程：device event 只包住 GPU 上的 kernel，kernel 返回并不等于字节已经上链路。不隔离时，64 MiB broadcast 是 570.371 ms（隔离 570.564 ms）看不出问题，但**4 KiB broadcast 只有 0.017 ms（隔离后 0.062 ms）、64 KiB 只有 0.022 ms（隔离后 0.595 ms）**——前一轮的网络传输还没结束，下一轮就已经「计时完成」了。跨机小消息用 device event 直接读会得到小一个数量级的结果。

**这一档没有覆盖的东西。** 两台机器都无 RDMA（无 `/dev/infiniband`、无 IB 设备），走的是 `NET/Socket`；跨机侧的强制算法对照、通信与计算重叠、超过 2 个 rank 的拓扑，以及 NVLS/GIN 都没有做。生产集群跨节点走 RDMA/RoCE 时链路速率与协议栈都与这里的 1 GbE + 内核 TCP 不同，**本节任何数字都不能代入**。

### 设计取舍

**为什么把算法选择放在调优表里而不是运行时试跑。** 每次 collective 都试跑不可行，NCCL 的做法是用一张「拓扑 → 每算法每协议的带宽/延迟」表在初始化时算一次代价，之后按消息大小查表。代价是表的质量取决于拓扑探测的准确度——本章第 4 节测到的「Tree 比 auto 快的 18.5%」就是模型失准的结果。NCCL 提供 `libnccl-tuner.so` 插件接口让用户替换这张表，本机没有该插件。

**为什么小消息和大消息用不同协议。** LL 用 8 字节粒度、开销小但只适合小消息；SIMPLE 用大块流水，带宽高但启动成本大；LL128 折中。三者不是「新旧替代」关系，而是按消息大小分工，切换点由调优表决定。

**为什么广播只允许 Ring。** 树形广播在单机内没有优势（树的每一跳都要经过同一批 PCIe 链路，而 ring 的流量分布更均匀），而实现树形广播会引入额外的记账与同步。这条限制写在 `tuning.cc` 里，强制违反会直接报错。

**为什么 CPU 与 GPU 的路径不同。** 本机没有可用的 RDMA 设备，NCCL 的 IB 插件找不到设备（`NET/IB : No device found.`），退到 Socket transport；而单机内 GPU 之间走 `SHM/direct/direct`，完全不经过网络栈。跨机时这两条路径的差别会成为主导项。

### 实测数字

- **单向链路上限**：broadcast β = 24.18 GB/s（PCIe Gen4×16，编码后理论 31.5 GB/s 的 76.8%）。
- **双向 collective**：all_reduce 14.82、sendrecv 14.66、reduce_scatter 12.81、all_gather 12.74 GB/s（每方向）。
- **N=4 缩放**：all_reduce 的每方向速率 14.82 → 6.53 GB/s，busbw 9.79 GB/s。
- **近/远拓扑**：14.82 vs 14.56 GB/s，差 1.8%。
- **重叠**：46.1% 端到端收益，达成理论上限的 97%，两个方向各掉约 11.6% 效率。
- **rank 间离散**：256 MiB 各 collective 的 max/min rank 差值都在 0.4% 以内（表内 `t_s_spread`）。

- **跨机 vs 单机**：64 MiB 上 broadcast 差 205×、all_reduce 126×、all_gather 108×；4 KiB broadcast 只差 1.5×。
- **跨机第二条网卡**：`eth0`（自报 10 GbE）0.113–0.114 GB/s，比 `net1` 低 3.5%。

### 消融建议

1. 把 `--gpus 0,1,2,3` 换成 `0,1,3,4`（两两跨 NUMA 的对称配置），看 Tree 与 Ring 的排序是否反转——这是检验「默认 tuner 失准」是否与拓扑非对称有关的最快方式。
2. 把 LL128 强制配置的扫描扩到 64 KiB 以下，找到 LL128 相对 Simple 的交叉点。
3. 把重叠用例里的 GEMM 换成半长（`--gemm-n 4096`），此时计算短于通信，观察收益是否从「接近通信时间」变成「接近计算时间」，以及竞争比例如何变化。
4. 把 `overlap_missing_wait` 的小 GEMM 换回大 GEMM，看错误值是否消失——用来确认「竞态是否可见取决于计算与通信的相对长度」，而不是写法本身。

## 前沿

**对称内存与 NVLS。** NCCL 2.29 在这台机器上注册了 48 GB 的对称虚拟地址空间（`Symmetric VA size=48GB`），但 `NVLS multicast support is not available on dev 0 (NVLS_NCHANNELS 0)`——NVLS 需要 NVSwitch 或支持组播的 NVLink 域，PCIe 平台没有。对称内存本身是可用的（窗口注册不需要 NVLink），它改变的是「谁可以直接读写谁的缓冲区」，不改变本章的步数与口径。这条路线在本项目里保持 `UNVERIFIED`。

**设备发起的通信。** 本机 `libnccl-gin.so` 缺失、IB 设备不可用，GIN 路径不具备运行条件。GIN 与 IBGDA 把提交动作下沉到 kernel 里，能去掉每步的 CPU 参与，从而压低 α；本章测到的 α（13–86 µs）里有多少是 CPU 提交造成的，需要在实际支持 GIN 的平台上重测才能回答。跨机档测到的是「链路已经饱和」的形态，GIN 在这种链路上不会带来收益；它的价值出现在有 RDMA 的集群里。

**调优器插件。** `libnccl-tuner.so` 缺失意味着用的是拓扑模型推算的默认表。自定义 tuner 可以用实测数据覆盖这张表——本章第 4 节测到的 18.5% 差距就是这类插件的目标场景。NCCL 也支持用 `NCCL_ALGO` 按 collective 分别覆盖（`tuning.cc:44-46` 给了写法示例），适合在固定拓扑上做一次性调优。

**跨机 transport 的现实形态。** 本章跨机档量到的是**没有 RDMA 时的下界形态**：1 GbE 内核 TCP，94.1% 线速，NCCL 与裸 socket 无差别，代价是比单机 PCIe 慢两个数量级。生产集群跨节点走的是 RDMA/RoCE 与 GPU Direct RDMA（本机日志里的 `GPU Direct RDMA Disabled for HCA 0` 就是缺这一段），链路速率高一个数量级、协议栈也从内核里搬到了网卡上；本章给出的「NCCL 不额外增加开销」这条结论可以迁移，具体速率不能。

## 陷阱

**1. 混用三种带宽口径。** 同一个 256 MiB all_gather，algbw 是 12.7 GB/s、busbw 是 6.36 GB/s，差一倍；换个 collective 又变成 24 GB/s。写数字时必须同时给出 M 的定义、N 和折算因子。

**2. 用 rank 数变化前后的数字直接比。** all_reduce 的 busbw 从 N=2 的 14.80 GB/s 到 N=4 的 9.79 GB/s，这个下降里既有链路竞争也有折算因子的变化。要分离两者只能看 β（每方向链路速率），它从 14.82 掉到 6.53。

**3. 用小消息段的 α 去预测大消息。** 全区间拟合的最大相对误差 22%–56%，分段后降到 2%–18%。4 KiB 的 44 µs 里几乎全是启动开销。

**4. 由「带宽接近 24 GB/s」推断用了 ring。** 算法选择要从 NCCL 的 `-> Algo ... proto ...` 行读，不能反推。本章就是靠这条日志确认 auto 在 1 MiB 以上选了 RING/SIMPLE，而不是因为测出来像 ring。

**5. 认为强制算法一定合法。** `NCCL_ALGO=Tree` 在 AllGather/ReduceScatter/Broadcast 上直接报错，因为 `tuning.cc` 的合法性表不允许这些组合。设置环境变量前先查表。

**6. 假定默认调优就是最优。** 4 卡上强制 Tree 比 auto 的 Ring 快 18.5%。默认表来自拓扑模型，不是实测。

**7. 把重叠的收益当成「免费」。** 重叠期间计算掉到 88.4%、通信掉到 88.5% 的单项效率；总时间变好是因为两者本来串行。而且漏掉一个 `wait_stream` 就能让时间一样漂亮、结果全错。

**8. 把单机 PCIe 的结论外推到 NVLink 或跨机。** 单机档的前置条件是「单机、PCIe、无 NVLink、无 RDMA」。近/远拓扑差 1.8% 这个结论尤其不能外推——那是因为两段都在 PCIe 上。跨机档的 0.1176 GB/s 是 1 GbE 内核 TCP 的上限，不是「跨机 collective 的普遍速率」。

**9. 跨机小消息照搬 device event 计时。** 跨机搬数据的是 CPU 侧 proxy 线程，device event 只包住 GPU kernel。不逐轮隔离时 4 KiB broadcast 会报 0.017 ms，隔离后是 0.062 ms——差了 3.6 倍，而且方向是「看起来更快」。任何跨机计时都必须说明是否逐轮隔离，并与裸 TCP 或 CPU 墙钟对照一次。

**10. 拿网卡自报的速率当可达带宽。** `eth0` 自报 10000 Mb/s、`net1` 自报 1000 Mb/s，实测两条都是 0.113–0.118 GB/s。判定链路能力要用「两台机器之间的裸流吞吐」，不是 `/sys/class/net/*/speed`。

## 自测题

::: fold 1. M 是每 rank 输入 256 MiB，N=4，测得 all_reduce 耗时 41.138 ms。algbw 和 busbw 各是多少？
algbw = M/t = 268.435456 MB / 0.041138 s = 6.53 GB/s。busbw = 2(N−1)/N × M/t = 1.5 × 6.53 = 9.79 GB/s。两者相差 1.5 倍，这个倍数完全来自 N：N=2 时 2(N−1)/N = 1，algbw 与 busbw 相等。所以跨 N 比较只能看 β，不能直接比 algbw。
:::

::: fold 2. 为什么 broadcast 的 β 是 all_gather 的 1.9 倍？
broadcast 是纯单向流，每个 rank 只发不收（除 root 外只收不发），可以吃满链路的单向有效载荷 24.18 GB/s。all_gather 每个 rank 同时收发，PCIe 是双向链路，聚合带宽有限，每方向只能拿到约一半（12.74 GB/s），两边加起来约 25.5 GB/s，与单向上限同量级。
:::

::: fold 3. 强制 `NCCL_ALGO=Tree` 后 all_gather 报错，为什么不是回退到 Ring？
NCCL 的合法性表明确排除了 (AllGather, Tree) 这个组合（`src/graph/tuning.cc:273-275`）。强制指定后候选集为空，NCCL 直接报 `no algorithm/protocol available for function AllGather`。回退会让用户以为设置生效了，而实际跑的是另一个算法。
:::

::: fold 4. 全区间拟合的 α 是 28 µs，≥1 MiB 拟合的 α 是 16 µs，哪个更可信？
取决于要预测什么。预测 256 MiB 用后者（误差 6.9%），预测 4 KiB 两个都不可信——小消息段的时间由启动与同步支配，与二分段的线性模型不是同一个机制。报告 α 时必须同时说明拟合区间。
:::

::: fold 5. 重叠把串行 9.751 ms 降到 5.259 ms，理论上限是 4.645 ms。剩下的 0.614 ms 去哪了？
来自资源竞争：重叠期间 GEMM 从 236.7 掉到 209.1 TFLOP/s，通信从 14.42 掉到 12.76 GB/s，两者各损失约 11.6% 的效率。这部分不可能靠更好的重叠写法消除，只能靠减少通信量或换更宽的链路。
:::

::: fold 6. 为什么收集各 rank 的测量结果不能用 `all_gather_object`？
它内部会发起一次 `ncclAllGather(int8)`。在 `NCCL_ALGO=Tree` 的配置下这次 AllGather 不在合法组合里，直接报错，把测量进程带崩——本该只影响结果汇总的一步，污染了整个实验。测量代码里任何额外的集合通信都要先确认它在被测配置下合法。
:::

::: fold 7. 近拓扑与远拓扑只差 1.8%，能否推断「NUMA 位置对多卡通信不重要」？
不能。这只说明在这台机器上、这两条路径都由 PCIe 承载，UPI 带宽高于实测速率，所以瓶颈不在这里。换成 NVLink + PCIe 的混合拓扑，或跨机走网卡，位置的影响会变成数量级差异。
:::

::: fold 8. 跨机档里 4 KiB 只比单机慢 1.5 倍，而 64 MiB 慢 126 倍，这两个数字矛盾吗？
不矛盾，它们分别落在成本模型的两端。4 KiB 的耗时由每跳的固定成本支配（单机 41 µs、跨机 166 µs 的往返与同步），字节项可以忽略；64 MiB 的时间几乎全部是字节传输，PCIe 与 1 GbE 的速率差 126 倍就完整暴露。判据是：只要把消息改成 16 MiB，跨机档立刻落到 0.117 GB/s 的平坦段，与裸 TCP 的 0.1176 GB/s 一致。
:::

::: fold 9. 跨机 all_reduce 与裸 TCP 在 16 MiB 上都是 0.117 GB/s，能说「NCCL 已经优化到极限」吗？
只能说「这条链路已经跑满」，不能说 NCCL 已经优化到极限。两者一致（差 0.4%）证明 NCCL 没有在小消息之外引入额外开销，但瓶颈是 1 GbE 而不是 NCCL 的实现；换到 100 GbE RDMA 上，NCCL 的协议、通道数与 GPU Direct 路径才会重新成为变量。
:::
