## 比较 GPU 之前，先固定要做的工作

“哪张 GPU 跑模型更快”缺少几个条件：什么模型，输入多长，一次处理多少请求，
比较首个输出还是后续生成。不同条件下，模型需要的计算量与数据量不同，
两张卡的差距也可能改变。

本章基于 Qwen3-1.7B 在相同模型快照下的实测表现，对比 RTX 5090 D 与 L40S 两款 GPU。测试统一采用 vLLM 的 eager 路径并关闭前缀缓存，以严格控制变量。

## 两台机器的硬件差异

下面列出与本次分析直接相关的核心规格。显存容量为标称规格，带宽与 GEMM 吞吐来自微基准实测值（非端到端请求吞吐）：

| 项目 | crater：RTX 5090 D | worldvln：L40S |
|---|---:|---:|
| 架构标识 | sm_120 | sm_89 |
| 显存容量标称 | 32 GB | 48 GB |
| copy 带宽记录 | 1519.3 GB/s | 649.7 GB/s |
| bf16 GEMM 吞吐记录 | 232.0 TFLOP/s | 256.0 TFLOP/s |
| eager 微基准均摊提交/执行时间 | 2.68 µs | 5.03 µs |

两台机器的 bf16 GEMM 理论参照值相近，而显存带宽参照值相差悬殊（超过 2.3 倍）。按 L0.2 建立的分析模型：若工作负载主要受算力限制，两者的性能差距会较小；若主要受访存带宽制约，差距将显著放大。

## 脚本的计时范围

prefill 部分调用离线 `LLM.generate()`，要求只生成一个输出 token，
再记录整个调用耗时。它包含 prompt 前向、采样和请求处理，
不是只对 attention 或某个 GPU kernel 计时，也不是从 HTTP 客户端测到的 TTFT。

decode 部分使用差分。对于同一 batch 大小和初始上下文长度，
分别测“生成一个 token”和“生成 33 个 token”的调用耗时，
用差值除以 32，估算额外生成步骤的平均耗时：

$$T_{step,estimate}=\frac{T_{33\ outputs}-T_{1\ output}}{32}$$

两个调用使用独立生成的随机 prompt。关闭前缀缓存是为了避免后一调用
因命中前缀而少算一部分输入，但这并不消除所有运行差异。
另外，生成过程中上下文逐步变长，所以这个差分是多步的平均估计，
不是固定上下文长度处某一步的直接时间戳。

## 结果一：处理 prompt 的调用耗时

下表汇总了单请求下不同 prompt 长度的耗时（单位：毫秒）：

| prompt 长度 | RTX 5090 D | L40S |
|---:|---:|---:|
| 512 token | 10.85 | 12.80 |
| 1024 token | 19.83 | 19.75 |
| 2048 token | 36.64 | 38.85 |
| 4096 token | 76.91 | 79.54 |

在这些点上，两台机器的耗时较接近。4096-token 点约相差 3.4%。
这与前面“bf16 GEMM 参照值接近”的观察相容，但还不能证明整段 prefill
只受 GEMM 算力限制。归一化、attention、KV 写入和 CPU 处理也在该调用中。

prompt 从 512 增加到 4096 时，耗时并没有简单按八倍增长。
一个原因是固定开销不会随长度等比例增长；另一方面，
attention 计算量、矩阵形状和后端选择也可能变化。
要进一步解释，需要结合 L0.1 的 trace，而不是只看这一张总时间表。

## 结果二：后续生成步骤的平均耗时估计

这一组的初始上下文长度为 1024 token，每条请求额外生成 32 个 token。
这里的 batch 表示一起处理的请求数量。

| batch | RTX 5090 D，ms/步 | L40S，ms/步 | L40S 时间 / 5090 D 时间 |
|---:|---:|---:|---:|
| 1 | 4.483 | 11.127 | 约 2.48 |
| 4 | 4.680 | 11.411 | 约 2.44 |
| 16 | 5.850 | 11.949 | 约 2.04 |
| 32 | 6.798 | 12.624 | 约 1.86 |

先看 batch=1：这一配置下，L40S 每步平均估计耗时约为 5090 D 的 2.48 倍。
再看 batch=32：两台机器的每步时间都增加了，但每轮同时为更多请求生成 token，
所以总吞吐也提高了。

例如，5090 D 在 batch=32 时，一轮约 6.798 ms，为 32 条请求各生成一个 token。
总吞吐约为 4707 token/s。这个数字不是单条请求的生成速度，
也不能用它倒数来表示该请求等待一个 token 的时间。

batch 增大后，时间比从 2.48 缩小到 1.86。
这说明不能把 batch=1 的比值直接用于所有并发规模。
L0.2 的权重与 KV 公式可以帮助解释这种变化，
但具体比例仍要依赖实际执行数据。

## 带宽能解释到哪一步

两台机器的 copy 带宽之比约为：

$$1519.3/649.7\approx2.34$$

它与小 batch decode 的时间比 2.48 接近。因此，
“数据搬运是这个配置下的重要限制”是值得继续检验的解释。

但不能再往前跳一步，写成“94% 的差异由显存带宽造成，剩余 6% 来自 launch”。
这两个比值之间的接近程度不是原因的占比。
完整调用包含多种工作，CPU 提交与 GPU 执行还可能重叠，
不满足把总时间按带宽缩放、再把余量分配给另一个因素的简单假设。

更有帮助的下一步，是把候选解释与检查方法对应起来：

| 候选解释 | 需要检查什么 |
|---|---|
| 主要差异来自权重或 KV 读取 | 实际流量、缓存命中，以及改变上下文后的变化 |
| CPU 提交限制了执行 | 同一运行的 CPU/GPU 时间线与等待区间 |
| 两台机器用了不同实现 | attention backend、GEMM kernel 与编译目标 |
| 频率或功耗状态不同 | 覆盖被测区间的设备状态记录 |

上述诊断尚未完成，因此这里只列出候选原因与验证方法。

## 如何读代码里的硬件适配

相同的 Python 调用不保证两张卡运行完全相同的机器码。
库可能依据 GPU 架构、dtype、head_dim、可用后端及编译配置选择实现。
因此需要区分三层身份：上层算子名称、实际 kernel 符号、最终编译目标。

先在配置与启动日志中找后端选择，再在 trace 中找 kernel 名，
最后在编译产物中确认目标。kernel 名和缓存目录名能提供线索，
但不能仅凭一个名字就断言指令、调度和全部执行路径都相同。

这一阅读方法也适用于环境错误。例如 PTX ISA 版本不被 ptxas 接受时，
要比较前端生成了哪个版本、后端支持哪个版本，
而不是笼统地说“CUDA 版本不对”。

本章原有工具链记录可以作为样本，但修复命令必须按当前独立学习环境重新确认。
不要修改共享系统的驱动或工具链，也不要为了复现一个数字清理他人的缓存。

### 已经观察到的两处差别

把上面的方法用在这两台机器上，得到两个具体结果。

**后端身份：符号与缓存目标需要分别核对。**
vLLM 的 `v1/attention/selector.py` 按 compute capability、head_dim、dtype
以及 FlashInfer 是否可用来选后端。两台机器上都看到了
`flash::flash_fwd_splitkv_kernel`，符号名相同；但编译目标不同，
FlashInfer 的 JIT 缓存目录名把这一点显示了出来：

```
crater:    /scratch/learn/.cache/flashinfer/0.6.18/120f/cached_ops/sampling
worldvln:  /root/.cache/flashinfer/0.6.18/89/cached_ops/sampling
                                          ^^^^   ^^
```

`120f` 指 `sm_120f`（family-specific），`89` 指 `sm_89`。
但这里列出的是 sampling 缓存，不能据此确认 attention 的编译目标；还需对应 kernel 的编译记录。

**GEMM kernel：5090 上跑的是 sm_80 世代的 kernel。**
L0.1 的 trace 在 5090 上看到的是 `cutlass_80_tensorop_bf16_s16816gemm_*`。
消费级 Blackwell（sm_120）没有 `tcgen05` 与 Tensor Memory，
它的 tensor core 编程模型仍是 Ampere 血统的 `mma.sync`；
L40S（sm_89，Ada）同样走 `mma.sync`。

这些线索表明两台机器都可能使用 `mma.sync` 指令族，但不能证明 GEMM 的模板、tile 或最终机器码相同，也不足以解释 prefill 耗时接近。确认具体路径需要同次运行的 kernel 符号与编译目标；性能归因还需要对应时间线。

sm_120 缺少 `tcgen05` 这一条本身是可验证的：L1.2 用一个只含该指令的探针，
在 `sm_100a` 上编译通过、在 `sm_120a` 上被 ptxas 拒绝。
真正需要 tcgen05、TMEM 与 FP4 的路径，见 L1.2 与 L4.3。

## 读这组结果时容易出错的地方

**1. 只报一个"吞吐"数字。** 吞吐是 prefill 与 decode 的混合结果，
两者在这两台机器上的表现方向不同。不说明输入长度、batch 与阶段构成的吞吐，
无法比较。

**2. 用厂商标称参数做归因。** L40S 标称带宽 864 GB/s，本章实测 649.7 GB/s，
约为标称的 75%。用标称值做分母，会把归因算错。

**3. 把"达标率高"当成"性能好"。** 在 batch=32 上，L40S 达到约 88% 的 roofline 参照，
5090 D 约 70%，但 5090 D 的每步时间仍然更短。
达标率衡量的是"离自己的上限有多远"，不是"比别人快多少"。

**4. 忽略持续负载下的降频。** L40S 在 8192 的 GEMM 上比 4096 慢约 22%。
如果基准只跑一个尺寸、且跑得很短，可能测不到这一项。

**5. 忘了两台机器的软件栈可能不同。** 本章两台都是 vLLM 0.29.0 + torch 2.13.0+cu130，
这是刻意对齐的结果，不是默认状态。跨机比较前应先记录并核对版本。

**6. 在共享机器上不查占用就开跑。** 显存被别人占用时，引擎可能直接启动失败，
也可能以更小的 KV 池启动而不报错——后一种情况会安静地改变你的测量条件。

## 如何把结果用于选择配置

这组数据支持比较“当前小模型、当前长度与 batch 下”的表现，
不支持直接给 GPU 做采购排名。
更多显存可能允许更大模型或更多缓存，但并不自动意味着更低的请求延迟；
某个小 batch 更快，也不自动意味着特定 SLO 下的服务成本更低。

如果考虑 PD 分离，把 prefill 和 decode 放到不同节点，
还要加入 KV 传输、排队和路由成本。单机两个阶段各自较快，
不能保证拆开之后端到端更快。L6.4 应把这些成本一起测量。

## 自测与练习

<details markdown="1">
<summary>两张卡在 4096-token prefill 上相差 3.4%，能否宣布性能相同？</summary>

不能。这里报告的是已有中位数，缺少完整样本和预先确定的等价范围。
可以说“这组记录中的耗时接近”，但不能由此证明等价。
</details>

<details markdown="1">
<summary>batch=32 的总吞吐很高，为什么单条请求仍可能更慢？</summary>

一轮同时产出的 token 更多，但该轮本身也可能更长。
总吞吐除以请求数之后才与单请求平均生成速率有关；
实际服务中还要考虑排队及请求长度不一致。
</details>

<details markdown="1">
<summary>改变 prefix cache 开关后速度提高，是否说明 kernel 更快？</summary>

不一定。缓存命中可能使模型少处理一些输入 token，
这是工作量减少，不是同样工作量下 kernel 变快。
必须同时记录命中量和实际处理的 token 数。
</details>

只用已有 JSON 也能做一个练习：逐行算出两台机器的时间比，
再算 batch 增大时各自的吞吐变化。为每个结论写出适用的模型、长度和执行配置。
比较结果仅适用于所记录的模型、输入与配置。
