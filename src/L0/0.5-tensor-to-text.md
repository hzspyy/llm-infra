## 本章回答三个具体问题

1. temperature、top-k/top-p/min-p 与三种惩罚各自改变了分布的什么？这些步骤为什么不能换顺序？
2. 流式输出为什么不能逐 token decode？停止条件在哪一层判断，两个条件同时满足时谁优先？
3. 一次流式响应里，token 数、文本 delta 数与 SSE event 数为什么不是同一个数？

L0.4 解析了「文本 → 张量」。本章是另一半：模型吐出 151,936 个实数之后，经过哪些步骤变成屏幕上的字，以及这条链上每一层各自负责什么。

分布的演算在一个 4 分类玩具上做——词表只有 4 个 token、logits 含负值、全程 FP64，每一步的向量都能手算核对。检验实现是否正确则回到真实引擎：增量解码与 vLLM 实际使用的 `DecodeStream` 逐步对拍，停止条件与流式分帧直接读真实响应的原始字节。

## 机制拆解

### 一、真实 logits 长什么样

一次真实前向（原样）：

```
prompt '中国的首都是' -> 3 个 token [105538, 59975, 100132]
logits 形状 (1, 3, 151936)，取最后一个位置 -> (151936,)
量级：min -4.44  max 22.12  mean 3.50  std 2.35

  排名       id token              logit      prob   logprob
   0    68990 '北京'             22.1250  0.554616   -0.5895
   1   101314 '哪里'             20.1250  0.075059   -2.5895
   2     2130 '____'           19.6250  0.045526   -3.0895
   3    99245 '什么'             19.1250  0.027613   -3.5895
   4   104673 '哪个'             19.0000  0.024368   -3.7145
   5    99459 '哪'              19.0000  0.024368   -3.7145
   6     9909 '（'              18.8750  0.021505   -3.8395
   7    58695 '中国'             18.2500  0.011511   -4.4645
```

三件事：

- **`'中国的首都是'` 只切成 3 个 token**。Qwen3 的词表里「中国」「的首都」「是」各是一个 token（L0.4）。
- 最高分 `'北京'` 的概率是 **0.5546** 而不是接近 1，模型还给「把这句当填空题」留了一半概率。
- 排名 4 和 5 的 logit **完全相同**。bf16 只有 8 位尾数，19.0 附近的可表示值间隔是 0.125，两个不同的实数落到了同一个值上。这个并列在后面的 top-k 一节会再出现。

### 二、logits、logprob、prob

$$p_i = \frac{e^{z_i}}{\sum_j e^{z_j}},\qquad \ell_i = \log p_i = z_i - \log\sum_j e^{z_j}$$

`logits` 是模型直接输出的实数，没有归一化。**给所有 logit 加同一个常数不改变分布**——分子分母的 $e^c$ 约掉。三条验证：

```
验证 1：给所有 logit 加 100，softmax 不变   最大绝对差 5.274e-16
验证 2：exp(logprob) == prob                最大绝对差 7.451e-09
验证 3：概率之和                            1.000024
```

::: note 概率之和不是 1.000000
实测 **1.000024**，差 $2.4\times10^{-5}$。bf16 logits 先转成 fp32 再 softmax，对 151,936 个数求和的舍入误差累积到这个量级（对照 L2.3 的归约精度实验）。4 个数的玩具分布上则看不到误差：本章 FP64 小例的概率和是 1.000000000000。

**工程含义**：不要写 `assert probs.sum() == 1.0`；容差要随词表大小放宽。
:::

**为什么 API 返回 logprob 而不是 prob。** 序列的联合概率是各步概率的乘积，很快小到 fp32 存不下：

```
例：连续采 10 个概率各 0.5546 的 token，
    联合概率 = 2.754e-03，而 logprob 相加 = -5.89
```

10 步到 $10^{-3}$，100 步是 $10^{-26}$，1000 步直接下溢成 0。取对数之后乘法变加法，数值范围完全没问题。凡是涉及**序列打分**的地方——beam search、投机解码的验证（L5.5）、RL 里算 ratio（L7.6）——用的都是 logprob。

### 三、一个能手算的 4 分类分布

后面几节的演算都在这个玩具上做：词表 `[A, B, C, D]`，logits `[2.0, 0.5, -1.0, -3.0]`，FP64。

```
token               A            B            C            D
logits       2.000000     0.500000    -1.000000    -3.000000
exp(z)       7.389056     1.648721     0.367879     0.049787
prob         0.781461     0.174367     0.038907     0.005265
logprob     -0.246591    -1.746591    -3.246591    -5.246591

手算核对：exp(2)=7.389056，sum=9.455444，p(A)=7.389056/9.455444=0.781461
```

**logits 含负值不是特例**，真实前向里同样有（上面那次实测的最小值是 −4.44）。下一节的 repetition penalty 对正负 logit 的处理方向相反，正是要靠这个才能看清楚。

### 四、temperature

$$p_i = \operatorname{softmax}(z_i / T)$$

$T$ 只是在 softmax 之前除一下：$T<1$ 把差距拉大，分布更尖；$T>1$ 压缩差距，分布更平。玩具分布上的逐步向量：

| $T$ | 缩放后 logits | 概率 | 熵 | $e^{\text{熵}}$ |
|---|---|---|---|---|
| 0.2 | `10.00, 2.50, -5.00, -15.00` | `0.999447, 0.000553, 0.000000, 0.000000` | 0.0047 | 1.00 |
| 0.5 | `4.00, 1.00, -2.00, -6.00` | `0.950289, 0.047312, 0.002356, 0.000043` | 0.2075 | 1.23 |
| 1.0 | `2.00, 0.50, -1.00, -3.00` | `0.781461, 0.174367, 0.038907, 0.005265` | 0.6512 | 1.92 |
| 1.5 | `1.33, 0.33, -0.67, -2.00` | `0.649820, 0.239055, 0.087944, 0.023182` | 0.9233 | 2.52 |
| 3.0 | `0.67, 0.17, -0.33, -1.00` | `0.462260, 0.280375, 0.170056, 0.087310` | 1.2274 | 3.41 |

$e^{\text{熵}}$ 是「有效候选数」：词表只有 4 个时，$T=3$ 已经涨到 3.41，接近均匀分布。同一指标在真实前向上是 $T=1$ 时 13.9、$T=3$ 时 86,190（词表 151,936）。

**$T=0$ 不是除以 0。** vLLM 把温度小于 $10^{-5}$ 的请求替换成 1.0 再走 argmax 分支（`v1/sample/sampler.py:235`），采样分支的结果最后被 argmax 的结果覆盖。自己写采样器时必须同样特判，否则得到 `inf`/`nan`。

### 五、top-k、top-p 与 min-p

三者都是**截断**：把不要的候选的 logit 置成 $-\infty$，softmax 之后自然是 0。区别在于阈值怎么来。

```
原始概率  0.781461  0.174367  0.038907  0.005265   累计 0.781461 0.955828 0.994735 1.000000

策略        候选数   过滤后 logits                     归一化概率
top_k=1        1    2.0000  -inf    -inf    -inf     1.000000 0.000000 0.000000 0.000000
top_k=2        2    2.0000  0.5000  -inf    -inf     0.817574 0.182426 0.000000 0.000000
top_p=0.78     1    2.0000  -inf    -inf    -inf     1.000000 0.000000 0.000000 0.000000
top_p=0.80     2    2.0000  0.5000  -inf    -inf     0.817574 0.182426 0.000000 0.000000
top_p=0.96     3    2.0000  0.5000  -1.0000 -inf     0.785597 0.175290 0.039113 0.000000
min_p=0.04     3    2.0000  0.5000  -1.0000 -inf     0.785597 0.175290 0.039113 0.000000
min_p=0.05     2    2.0000  0.5000  -inf    -inf     0.817574 0.182426 0.000000 0.000000
min_p=0.30     1    2.0000  -inf    -inf    -inf     1.000000 0.000000 0.000000 0.000000
```

- **top-k** 只保留最大的 $k$ 个，与概率大小无关。
- **top-p**（核采样）按概率从大到小累加，**跨过阈值的那一个要保留**。`top_p=0.78` 只留 1 个，因为 A 一个就占 0.7815；`top_p=0.80` 留 2 个。如果把跨界的那个也丢掉，$p$ 小于最大概率时会一个候选都不剩，softmax 出来全是 `nan`。
- **min-p** 的阈值是 $\max_i p_i \times \text{min\_p}$，随分布走。`min_p=0.04` 时阈值 0.031258，C（0.038907）留下；`min_p=0.05` 时阈值 0.039073，C 恰好低于它被丢掉。**模型越确定，min-p 的阈值越高、候选越少**，所以它比 top-p 更贴着模型的确定程度走。

vLLM 的 min-p 实现是同一个公式：先 softmax、取每行最大值乘 `min_p`、低于阈值的 `masked_fill_(-inf)`（`v1/sample/logits_processor/builtin.py:102-116`）。本章实现与它的候选集逐位相同。

真实模型上的同一组截断（词表 151,936）：

```
策略                    候选数       覆盖概率
原始                 151936     1.0000
top_k=5                 6     0.7515      ← 留下 6 个
top_k=50               52     0.9075      ← 留下 52 个
top_p=0.9              46     0.9008
top_p=0.99            146     0.9900
```

`top_k=5` 留下 6 个是**并列**所致：排名 4 和 5 的 logit 都是 19.0000，本章实现用 `logits < kth` 做掩码，等于第 $k$ 大值的全部保留。这不是 bug，是一种策略选择，下一节给出两种策略的分布差异。

### 六、三种惩罚：repetition 对正负 logits 的方向相反

设 prompt 里出现过 B，已生成 `[A, A, C]`：

| 设置 | logits | 概率 |
|---|---|---|
| 无惩罚 | `2.0000, 0.5000, -1.0000, -3.0000` | `0.781461, 0.174367, 0.038907, 0.005265` |
| repetition=1.2 | `1.6667, 0.4167, -1.2000, -3.0000` | `0.739209, 0.211787, 0.042052, 0.006951` |
| frequency=0.5 | `1.0000, 0.5000, -1.5000, -3.0000` | `0.585847, 0.355334, 0.048089, 0.010730` |
| presence=0.3 | `1.7000, 0.5000, -1.3000, -3.0000` | `0.735253, 0.221454, 0.036606, 0.006687` |
| 三者同时 | `0.3667, 0.4167, -2.0000, -3.0000` | `0.458806, 0.482330, 0.043033, 0.015831` |

三条规则各不相同：

- **repetition penalty 是乘性的，且按符号分支**：logit 为正时除以 penalty，为负时乘以 penalty。A 从 $+2.0$ 变成 $+1.6667$，C 从 $-1.0$ 变成 $-1.2$。两支都让概率下降，**如果写成「一律乘 $1/\text{penalty}$」，负 logit 反而会被奖励**。vLLM 的实现就是这个分支（`_custom_ops.py:377-390` 的 `apply_repetition_penalties_torch`，CUDA 路径是同一语义的 kernel）。
- **frequency penalty 是加性的，按出现次数线性扣**：A 出现 2 次，扣 $2\times0.5=1.0$。
- **presence penalty 也是加性的，只看出现与否**：A 出现过就扣 0.3，不管几次。

作用范围也不同：**repetition 看 prompt ∪ 已生成**，frequency/presence 只看已生成。B 只在 prompt 里，所以 repetition 罚到它（0.5 → 0.4167），frequency/presence 不动它。D 从未出现，三种惩罚都不碰。这一段对应 `model_executor/layers/utils.py:80-88`：先 repetition，再减 frequency×次数，再减 presence×出现掩码。

### 七、顺序不可交换——以及一个可交换的例外

同样的参数，换个顺序就是另一套行为。玩具分布上的三组对照：

```
T=0.5 与 top_p=0.8
  先温度再截断   候选 1    1.000000 0.000000 0.000000 0.000000
  先截断再温度   候选 2    0.952574 0.047426 0.000000 0.000000

T=0.5 与 min_p=0.1
  先温度再 min_p  候选 1    1.000000 0.000000 0.000000 0.000000
  先 min_p 再温度  候选 2    0.952574 0.047426 0.000000 0.000000

T=0.5 与 frequency=0.5
  先温度再惩罚    3.0000 1.0000 -2.5000 -6.0000    0.877543 0.118763 0.003586 0.000108
  先惩罚再温度    2.0000 1.0000 -3.0000 -6.0000    0.727298 0.267558 0.004900 0.000244
```

- **温度在前，候选集只剩 1 个**：分布被拉尖，A 一个就超过了 0.8。先截断则按原分布留 2 个，再降温只是把这 2 个的比例拉开。min-p 同理，因为它的阈值挂在最大概率上，而温度会改变最大概率。
- **加性惩罚与温度不可交换**：先惩罚再除以 $T$，惩罚力度被整体放大 $1/T$ 倍（实测两者最大差 1.0000）。同样写 `frequency_penalty=0.5`，两种实现的实际强度差一倍。

**唯一可交换的是 repetition penalty**：实测两种顺序的 logits 最大差 `0.000e+00`。原因是它按符号分支做乘法，而除以正的 $T$ 不改变符号，缩放与缩放可交换。这条例外说明「顺序重要」不能当口号用——哪一对可交换，要按算子的性质判断。

vLLM 0.29.0 的固定顺序写在 `v1/sample/sampler.py` 里：

```
forward(:73)  → 先按原始 logits 算 raw logprobs（:80-95 的注释说明这是与 V0 的差别）
              → logits.to(float32)（:97）
              → apply_logits_processors(:99) 内部：allowed_token_ids → bad_words
                 → 非 argmax 不变的 processor → 惩罚（:405）
sample(:244)  → greedy_sample 取 argmax（:261，此时温度还没除）
              → apply_temperature（:277）
              → argmax 不变的 processor，min-p 在这里（:283）
              → topk_topp_sampler（:287）
```

两个容易被忽略的事实：**greedy 取的是「惩罚之后、温度之前」的 argmax**——温度对贪心解码没有影响，但惩罚有；**返回给客户端的 logprobs 默认是惩罚与温度之前的原始分布**，所以 API 返回的 logprob 与实际采样用的分布不是同一个。

### 八、并列与两种「正确」

并列时截断策略的分歧是实打实的分布差异。玩具分布 `[2.0, 2.0, 0.5, -1.0]`，`top_k=1`：

```
保留全部并列   候选 2    0.500000 0.500000 0.000000 0.000000
严格留 k 个    候选 1    1.000000 0.000000 0.000000 0.000000
torch.argmax 的返回：[0, 0, 0, 0, 0]（取下标最小的，确定但任意）
```

一个给出两个等概率候选，另一个给出确定的 A。真实 logits 出现精确并列并不罕见——第一节那次前向里排名 4 和 5 就完全相同。

由此引出两种不同的正确性判据：

- **greedy 的判据是 id 精确相等。** 它是确定性函数，同样的输入必须给同样的 id；并列时结果取决于 argmax 的实现约定（PyTorch 返回下标最小的），这一点在跨引擎对比时要单独确认。
- **随机采样的判据是分布检验。** 本章用 top-k=3 后的分布抽 200,000 次，3 个 seed 的结果：

```
seed=0  频率 0.785375 0.175410 0.039215    max|Δ|=0.00022  χ²=0.083  通过
seed=1  频率 0.785215 0.175190 0.039595    max|Δ|=0.00048  χ²=1.239  通过
seed=2  频率 0.786620 0.175445 0.037935    max|Δ|=0.00118  χ²=7.384  超过临界值
```

自由度 2、$\alpha=0.05$ 的临界值是 5.991，**第三个 seed 超了**。这不是实现错误：$\alpha=0.05$ 的含义就是正确的实现也有 5% 的单次运行会被判为不通过，跑 3 个 seed 至少出现一次的概率约 14%。统计涨落的量级是 $1/\sqrt{N}=0.00224$，与实测 `max|Δ|` 同量级。

**所以「同 seed 必须出同 token」是一个错误的验收标准。** 不同引擎的 RNG 状态、抽样 kernel 和批次构成都不同，能要求的是：贪心下 id 序列一致，采样下分布一致。

### 九、增量 detokenize：与引擎逐步对拍

先看一个**恰好没出问题**的例子：

```
'风吹过山谷' -> 3 个 token
  i       id      单独 decode 字节
  0   109520           '风吹' e9 a3 8e e5 90 b9
  1    38182            '过' e8 bf 87
  2   113599           '山谷' e5 b1 b1 e8 b0 b7
```

这三个 token 各自都落在字符边界上，逐个 decode 碰巧正确。换一个词表里没有的罕见字就不行了：

```
'𩸽' (4 字节) -> 3 个 token
  i       id  字节          单独 decode   手写缓冲吐出   引擎 DecodeStream 吐出
  0   103914  f0 a9         '�'          ''            ''
  1      116  b8            '�'          ''            ''
  2      121  bd            '�'          '𩸽'          '𩸽'
  逐 token 拼接 '���'      手写缓冲 '𩸽'      引擎 '𩸽'
```

`𩸽` 不在词表里，退回字节级，4 个字节被切成 3 个 token。**每个 token 单独 decode 都得到替换符 U+FFFD**，因为它们都不是完整的 UTF-8 序列。ZWJ emoji 更密集：`👨‍👩‍👧‍👦` 切成 10 个 token，三个零宽连接符各自被拆成 `e2 80` + `8d` 两个 token，逐 token decode 得到 `'👨��👩��👧��👦'`。

**正确做法是维护字节缓冲**：凑不齐完整 UTF-8 序列就先不吐字。6 个构造用例里，逐 token decode 有 4 个出错，手写缓冲与引擎实际使用的 `tokenizers.DecodeStream` 有 5 个**逐步完全相同**。

剩下那一个用例暴露了另一件事。`'答案是 𩸽 和 👍🏽。'` 中间有一个 token 的字节是 `20 f0 9f 91`（一个空格 + 👍 的前三个字节）：

```
  i       id  字节          手写缓冲吐出   引擎 DecodeStream 吐出
  7    61804  20 f0 9f 91   ' '           ''
  8      235  8d            '👍'          ' 👍'
```

手写实现先把能解的空格吐出去，引擎把空格一起压到下一步。**两者最终文本完全相同，但某一步的 delta 不同**——落到流式接口上就是「这一步客户端收到的内容为空」。这不是故障。

还有一个用例（`café` 的分解形）三种做法都与原文不同：tokenizer 的 normalizer 在**编码**阶段就把 NFD 改写成了 NFC（L0.4 的 L1 层），与 detokenizer 无关。对拍时先确认输入侧有没有被规范化，否则会把上一段的行为记到这一段头上。

::: warning 取 token 的原始字节本身就是个坑
用 `tok.convert_tokens_to_string(...).encode("utf-8")` 取字节，不完整的字符已经被替换成 U+FFFD，拿到的是 `ef bf bd`，不是原始字节。必须反查字节级映射表（L0.4 的 `Ġ` 那套）。
:::

### 十、停止条件：三条路径，各自的层与优先级

| 条件 | 判断对象 | 在哪一层 |
|---|---|---|
| **eos token** | token id | 采样之后、detokenize 之前（引擎调度层） |
| **stop string** | 文本 | detokenize 之后（需要跨 token） |
| **max_tokens** | 计数 | 任意层，**唯一保证会终止的一条** |

基线：同一 prompt 贪心生成到自然结束，**18 个 token**，`finish_reason=stop`，文本 `'风是空气的流动现象，通常由温度差异或气压差异引起。'`。

**停止串必须在文本上判断。** 从基线输出里取一个横跨两个 token 的串：第 4、5 个 token 是 `'流动'` 和 `'现象'`，拼起来的 `'流动现象'` 不等于任何单个 token 的文本。用它作停止串：

```
stop-span-exclude      6 token  finish=stop  stop_reason='流动现象'  文本 '风是空气的'
stop-span-include      6 token  finish=stop  stop_reason='流动现象'  文本 '风是空气的流动现象'
```

两者的 token 数相同（都是 6），**文本差 4 个字符**：`include_stop_str_in_output=False` 时引擎把最后一个 token 整个跳过解码，再按字符位置截断（`v1/engine/detokenizer.py:107-113`）。所以「输出里没有停止串」不代表模型没生成它，**计费和 KV 占用按 token 算，那部分 token 是实打实产生了的**。

**EOS 与 max_tokens 同时满足时，EOS 优先**：

```
max_tokens=17 (n-1)  实际 17 token  finish_reason=length  文本 '风是空气的流动现象，通常由温度差异或气压差异引起。'
max_tokens=18 (n)    实际 18 token  finish_reason=stop
max_tokens=19 (n+1)  实际 18 token  finish_reason=stop
```

注意第一行：**`finish_reason=length` 而文本是完整的**。第 18 个 token 是 EOS，本身不产生文本，所以砍掉它不改变可见输出，只改变结束原因。把 `finish_reason` 当作「输出是否被截断」的判据会误判。

`token_ids` 里含 EOS（151645），文本里没有 `<|im_end|>`——`SamplingParams` 默认 `skip_special_tokens=True`。手写增量 detokenizer 与引擎输出逐字节对拍时这件事必须先对齐：

```
引擎文本            75 字节
手写（全部 token）  85 字节   相同：False
手写（跳过特殊）    75 字节   相同：True     ← 差的正是 eos 的 10 字节
```

**min_tokens 会同时屏蔽停止串和 EOS**：设 `min_tokens=40` 再跑同一个停止串，输出变成 44 个 token，文本里出现了两遍完整句子和两个 `</think>`。停止串只在 `num_output_tokens > min_tokens` 之后才检查（`detokenizer.py:130`），EOS 同样被压住，于是模型越过自然结束点继续写。

### 十一、token、文本 delta 与 SSE event 是三种计数

流式响应里这三个数都不相等。同一个服务（vLLM 0.29.0，`--reasoning-parser qwen3 --enable-auto-tool-choice --tool-call-parser hermes`）上的三次请求：

| 请求 | completion_tokens | 文本 delta | SSE event | HTTP chunk | socket 收到次数 |
|---|---:|---:|---:|---:|---:|
| 纯文本 | 18 | 17 | 21 | 22 | 19 |
| 带 reasoning | 159 | 156 | 160 | 161 | 159 |
| tool call | 20 | 7 | 11 | 12 | 10 |

每一层的差额都有确定的来源：

- **SSE event 比文本 delta 多 4 个**，三次请求都一样：一个只带 `role` 的首事件、一个只带 `finish_reason` 的末事件、一个只带 `usage` 的事件（`stream_options.include_usage`）、以及 `data: [DONE]`。**这四个事件的 delta 里没有文本，但它们都不是失败。**
- **token 比文本 delta 多**：纯文本请求的第 18 个 token 是 EOS，不产生任何文本。
- **HTTP chunk 比 SSE event 多 1**：chunked 编码最后要发一个长度为 0 的终止块（L5.11 详细分析过这两层分帧）。
- **socket 收到的次数又是另一个数**：TCP 可能把多个 chunk 合进一次 `recv`，19 < 22。**不能用「收到几次」推断服务端发了几次。**

tool call 那一行的差距最大：20 个 token 只对应 7 个 delta。原因是 parser 在中间做了聚合——模型实际生成的是一串带标签的文本，hermes parser 把它解析成结构化的 `tool_calls` 增量：

```
#1  {"tool_calls": [{"id": "chatcmpl-tool-…", "type": "function", "index": 0,
                     "function": {"name": "get_weather"}}]}
#2  {"tool_calls": [{"index": 0, "function": {"arguments": "{\""}}]}
#3  {"tool_calls": [{"index": 0, "function": {"arguments": "city"}}]}
…
拼接结果 {"city": "北京"}
```

函数名单独一个事件，参数按片段续传，客户端要自己拼。**`content` 字段在这几个事件里是 `null`**——按 `content` 是否为空判断「生成是否正常」，在 tool call 场景下必然误判。

reasoning 的分段同理：159 个 token 里有 151 个 delta 落在 `reasoning` 字段、5 个落在 `content`，第一个 `content` delta 出现在第 152 个 data 事件。**分界不是模型输出的一个特殊 token 位置，而是 parser 在文本上找到 `</think>` 之后切开的**。字段名也要注意：vLLM 0.29.0 发的是 `reasoning`，而不少客户端按 OpenAI 的 `reasoning_content` 读，读不到就会显示成空。

**detokenizer 与 parser 的职责必须分开看**：detokenizer 只管 id → 文本、维护跨 token 的字节缓冲；parser 在已经成形的文本上做结构化切分，认识 `<think>`、`<tool_call>` 这类标签。前者的状态是几个字节，后者的状态是一台小型状态机。

## 工程实现 · 源码解析

采样放在 CPU 还是 GPU，决定每步要传多少数据。朴素做法是把 logits 拷回 CPU 采样：logits 是 $[B, V]$，$V=151936$，$B=64$ 时就是 $64 \times 151936 \times 4\ \text{B} \approx 39$ MB。每步拷 39 MB 过 PCIe，按 L1.3 实测的 ~25 GB/s 是 1.5 ms，而一步 decode 本身可能才 5 ms。

vLLM 因此把整条采样链放在 GPU 上，只回传 token id。这条设计也解释了 L2.6b 的另一件事：**热路径里不能有 `.item()`**。采样结果留在 GPU 上就地拼回序列，整步可以不做同步；一旦 `.item()` 判断「是不是 eos」就会强制同步（L1.4 实测 4.76 µs），打断 CPU 提前提交下一步的流水。

本章用到的入口（vLLM 0.29.0）：

| 位置 | 符号 | 职责 |
|---|---|---|
| `v1/sample/sampler.py:73` | `Sampler.forward` | 原始 logprobs → fp32 → logits processors → sample |
| `v1/sample/sampler.py:229` | `apply_temperature` | `T<1e-5` 换成 1.0，避免除零 |
| `v1/sample/sampler.py:241` | `greedy_sample` | 惩罚之后、温度之前取 argmax |
| `v1/sample/sampler.py:405` | `apply_penalties` | 调 `apply_all_penalties` |

| `_custom_ops.py:377` | `apply_repetition_penalties_torch` | 正的除、负的乘 |
| `v1/sample/logits_processor/builtin.py:102` | `MinPLogitsProcessor.apply` | 阈值 = 最大概率 × min_p |
| `v1/engine/detokenizer.py:31/69/168` | `IncrementalDetokenizer` 三层 | 基类 / 停止串 / DecodeStream 快路径 |

`stop_buffer_length` 是流式接口里空 delta 的另一个来源：

```python
# v1/engine/detokenizer.py:86-90
if self.stop and not self.include_stop_str_in_output:
    self.stop_buffer_length = max(len(s) for s in self.stop) - 1
else:
    self.stop_buffer_length = 0
```

设了停止串且不含在输出里时，引擎每一步都要**扣住最后 $L-1$ 个字符不发**——否则停止串的前半截已经发送给客户端，后续已无法截断或召回。代价是流式输出的尾部延迟稍有增加，而且某些 step 的 delta 会是空的。

### 设计取舍

**不变量**：采样链的顺序是模型无关的协议的一部分。同样的 `temperature=0.7, top_p=0.9`，在哪个引擎上都应该指同一件事；一旦某个实现把惩罚放到温度之后，同样的参数就变成了另一种强度（第七节实测差 1 倍）。

**状态归属**：跨 token 的字节缓冲属于 detokenizer，每个请求一份；语法/标签状态属于 parser，也是每请求一份；而 RNG 状态属于引擎的采样器，与请求的 `seed` 只是弱绑定。这解释了为什么「同 seed 跨引擎同输出」做不到——三份状态里没有一份是协议规定的。

**错误发现位置**：输出乱码先看是不是逐 token decode（第九节）；输出被截断先看 `finish_reason` 与 `token_ids` 是否含 EOS（第十节）；客户端「收不到内容」先数三种计数（第十一节），再看是不是把 `reasoning`/`tool_calls` 当成了 `content`。

**加一条新的过滤规则要改什么**：在 vLLM 里是实现一个 `LogitsProcessor` 并声明它是否 argmax 不变——不变的（如 min-p）挂在温度之后，会改变 argmax 的（如惩罚、bad words）必须挂在 `greedy_sample` 之前。放错位置不会报错，只会让贪心解码的结果与预期不同。

**把 detokenize 放在哪**：它是字符串处理——查 15 万条目的词表、反查字节映射、维护跨步骤缓冲、UTF-8 变长解码，全是不规则控制流，数据量却只有每步几个 id。vLLM 因此把 detokenizer 放在与 EngineCore 不同的进程里（L0.1），好处是 Python 开销不占 GPU 调度线程，代价是多一次进程间通信。高并发下 detokenize 会成为吞吐瓶颈而不是延迟瓶颈，对策是加进程或让客户端自己解码（只回传 token id）。

## 前沿

| 方向 | 改变了什么 | 代价 | 章节 |
|---|---|---|---|
| **min-p 取代 top-p** | 阈值挂在最大概率上，模型确定时自动收紧 | 对温度顺序敏感，跨实现要对齐 | 本章第五节 |
| **重复惩罚的变体** | DRY、no-repeat-ngram 等按 n-gram 而不是单 token 惩罚 | 状态更大，长上下文下开销明显 | — |
| **约束解码** | 用语法/正则把非法 token 置 $-\infty$，保证输出可解析 | 每步要算合法集合，且要处理同一字符串的多种 token 化 | L5.6 |
| **投机解码** | 小模型先猜几个 token，大模型一次验证；验证要比较两个分布 | 接受率不高时反而更慢 | L5.5 |
| **GPU 上的 top-p kernel** | 避免每步拷 39 MB logits 回 CPU | 需要排序，是非平凡 kernel | L5.3、L5.9 |
| **结构化流式输出** | reasoning/tool_call 由 parser 在文本上切分 | 与 detokenizer 的边界要划清，字段名各家不一致 | 本章第十一节、L5.6 |
| **logprob 的返回** | API 返回 top-n logprob 供下游打分 | 额外拷回 CPU；且默认返回的是惩罚与温度之前的原始分布 | L5.9 |

## 陷阱

**1. `assert probs.sum() == 1.0`。** 真实词表上实测 1.000024，要用容差，且容差随词表放宽。

**2. 以为 $T=0$ 就是 `logits / 0`。** 必须特判成 argmax，否则 `inf`/`nan`。

**3. 以为所有过滤步骤都不可交换。** 加性惩罚与温度确实不可交换（实测差 1.0000），但 repetition penalty 与温度**可以**交换（差 0.000e+00）——按算子性质判断，别当口号背。

**4. 把 repetition penalty 写成一律乘 $1/\text{penalty}$。** 负 logit 会被奖励，方向反了。正的除、负的乘。

**5. 以为 API 返回的 logprob 就是采样用的分布。** vLLM 默认返回惩罚与温度之前的原始 logprobs（`sampler.py:80-95`）。

**6. 用「同 seed 同 token」验收跨引擎一致性。** RNG 状态、抽样 kernel、批次构成都不同。贪心比 id，采样比分布。

**7. 流式输出逐 token decode。** 6 个构造用例里有 4 个会吐出 `�`。必须维护字节缓冲。

**8. 把空 delta 判为生成失败。** 每次流式响应固定有 4 个不带文本的事件（role、finish_reason、usage、`[DONE]`），加上停止串的 hold-back 和 flush 时机差异。

**9. 按 `content` 字段判断有没有输出。** tool call 场景下 `content` 是 `null`，内容在 `tool_calls` 里；reasoning 段在 `reasoning` 字段（vLLM 0.29.0 的字段名，不是 `reasoning_content`）。

**10. 把 `finish_reason=length` 当成「被截断」。** 实测 `max_tokens=17` 时文本完整，被砍掉的是不产生文本的 EOS。

**11. 以为 stop string 没进输出就没花钱。** 两种 `include_stop_str_in_output` 的 token 数相同，只是文本被截断。

**12. 在热路径里 `.item()` 判断 eos。** 强制 CPU-GPU 同步（L1.4 实测 4.76 µs），打断流水。

## 自测题

<details markdown="1">
<summary>1. <code>temperature=0.7</code>、<code>top_p=0.9</code>、<code>frequency_penalty=0.5</code> 三个参数，引擎按什么顺序应用？换顺序会怎样？</summary>

**vLLM 0.29.0 的顺序是：惩罚 → 温度 → min-p → top-k/top-p。**

对应 `v1/sample/sampler.py`：惩罚在 `:405`（`apply_logits_processors` 内），温度在 `:277`，argmax 不变的 processor（含 min-p）在 `:283`，top-k/top-p 在 `:287`。

**换顺序的后果分两类：**

**(1) 加性惩罚与温度不可交换。** 本章玩具分布实测：

```
先温度再惩罚   3.0000 1.0000 -2.5000 -6.0000   p = 0.877543 0.118763 …
先惩罚再温度   2.0000 1.0000 -3.0000 -6.0000   p = 0.727298 0.267558 …
```

差 1.0000。先惩罚再除以 $T$，等价于惩罚力度被放大 $1/T$ 倍——同样写 `frequency_penalty=0.5`，两种实现的实际强度差一倍。

**(2) 截断与温度不可交换。** `T=0.5` + `top_p=0.8`：先温度候选集只剩 1 个，先截断留 2 个。因为截断用的是哪个分布决定了留多少。

**一个反直觉的例外**：repetition penalty 与温度**可以**交换，实测差 `0.000e+00`。它是按符号分支的乘法，而除以正的 $T$ 不改变符号。

**还有一点容易忽略**：温度对 `temperature=0` 的贪心路径没有影响，但惩罚有——`greedy_sample` 取的是惩罚之后、温度之前的 argmax（`sampler.py:261`）。所以「设 T=0 就能屏蔽所有采样参数」是错的。
</details>

<details markdown="1">
<summary>2. 同样的 prompt、同样的 seed，在两个引擎上结果不同。怎样判断这是 bug 还是正常现象？</summary>

**先分清两种正确性判据。**

**greedy（T=0）的判据是 id 精确相等。** 这时如果结果不同，是真问题，按顺序排查：

1. **输入不同。** 打印两边最终的 token id 序列逐位对比——chat template、`add_special_tokens`、是否加 BOS 都可能不同（L0.4 实测过这些差异）。
2. **惩罚位置不同。** 贪心受惩罚影响但不受温度影响；如果一边把惩罚放在了 argmax 之后，结果就会分叉。
3. **并列。** 本章实测真实前向里排名 4 和 5 的 logit 完全相同（bf16 间隔 0.125）。两边的 argmax 约定不同（PyTorch 返回下标最小的）就会选出不同的 token。
4. **数值差异。** kernel 不同、batch 构成不同都会让累加顺序不同，**一个 ULP 就足以让并列的两个互换**。

**随机采样的判据是分布检验，不是逐次相等。** 本章用 20 万次抽样做 χ² 检验，3 个 seed 得到 0.083 / 1.239 / 7.384，临界值 5.991——**第三个超了，但实现是对的**。$\alpha=0.05$ 意味着正确实现也有 5% 的运行被判不通过；跑 3 次至少出现一次的概率约 14%。

所以采样场景下「同 seed 出不同 token」不是 bug：RNG 状态、抽样 kernel、批次构成三份状态都不受协议约束。**能要求的是：贪心下 id 一致，采样下分布一致。**
</details>

<details markdown="1">
<summary>3. 客户端流式接收时，某一步的 delta 是空字符串。有哪几种可能？怎样区分？</summary>

**至少五种，全都是正常现象：**

1. **首事件只带 role。** `{"role": "assistant", "content": ""}`，每次响应固定有一个。
2. **末事件只带 finish_reason。** delta 为空，`finish_reason` 有值。
3. **usage 事件。** 开了 `stream_options.include_usage` 时多一条，`choices` 是空数组。
4. **`[DONE]`。** 不是 JSON，是字面量。
5. **字节还没凑齐或被 hold back。** 多字节字符跨 token 时这一步解不出字符（本章实测 `'答案是 𩸽…'` 那个用例）；设了停止串且不含在输出里时，引擎每步要扣住 $L-1$ 个字符（`detokenizer.py:86-90`）。

前四种的实测证据是三种计数的固定差额：纯文本请求 17 个文本 delta 对 21 个 SSE 事件，差的正是这 4 个。

**区分方法**：看事件里除了 `content` 还有什么。有 `role` 是第 1 种，有 `finish_reason` 是第 2 种，`choices` 为空且有 `usage` 是第 3 种，不是 JSON 是第 4 种；四种都不是，就是第 5 种——继续等下一个事件即可。

**还有一种不是空 delta 但同样会被误判的情况**：`content` 是 `null`，内容在 `tool_calls` 或 `reasoning` 字段里。本章 tool call 请求的 7 个 delta 全部如此。
</details>

<details markdown="1">
<summary>4. 请求设了 <code>max_tokens=200</code> 和 <code>stop=["\n\n"]</code>，返回 <code>finish_reason=length</code>。能得出「输出被截断」的结论吗？</summary>

**不能直接得出。** 需要看两件事。

**第一，`finish_reason=length` 不代表文本不完整。** 本章实测：自然结束需要 18 个 token，其中第 18 个是 EOS。把 `max_tokens` 设成 17，得到的是

```
max_tokens=17  实际 17 token  finish_reason=length  文本 '风是空气的流动现象，通常由温度差异或气压差异引起。'
```

文本一字不差，被砍掉的是不产生任何文本的 EOS。**判据应该是 `token_ids` 的最后一个是不是 EOS**，而不是 `finish_reason`。

**第二，200 个 token 用完确实说明停止串没出现。** 这时要怀疑停止串本身：

- 它可能被 `min_tokens` 屏蔽了——停止串只在 `num_output_tokens > min_tokens` 之后才检查（`detokenizer.py:130`）。本章实测 `min_tokens=40` 时，原本 6 个 token 就该停的请求跑到了 44 个，中间输出了两遍完整句子。
- 它可能永远不会出现。**`max_tokens` 是唯一保证终止的条件**，停止串只是可选的提前终止。

**反过来的情形也要注意**：`finish_reason=stop` 且 `stop_reason` 有值时，那部分 token 是实打实生成了的——两种 `include_stop_str_in_output` 的 token 数相同（本章实测都是 6），只是文本被截断。计费与 KV 占用按 token 算。
</details>

<details markdown="1">
<summary>5. 为什么 detokenize 不能放在 GPU 上？它会成为瓶颈吗？</summary>

**因为它是带状态的字符串处理，不是数值计算。** 具体要做四件事：

1. 按 token id 查 15 万条目的词表；
2. 反查字节映射（L0.4 的 `Ġ` 那套）；
3. 维护跨步骤的字节缓冲（本章第九节的核心）；
4. UTF-8 变长解码。

全是不规则控制流与内存访问，而数据量极小：每步每个请求只有 1 个 token id。

**引擎的分层是：**

| 层 | 在哪 | 处理什么 |
|---|---|---|
| 模型前向 + 采样 | GPU | $[B, V]$ 的 logits → $B$ 个 token id |
| token id 回传 | PCIe | 几百字节，可忽略 |
| detokenize | CPU（独立进程） | id → 文本 |
| parser | CPU | 文本 → reasoning / tool_call 分段 |

vLLM 把 detokenizer 放在与 EngineCore 不同的进程里（L0.1），Python 开销不占 GPU 调度线程，代价是多一次进程间通信。

**会不会成为瓶颈：** 单步只有 1 个 token，开销与 GPU 那 2 ms 相比可以忽略；但它随 $B \times$ 步数线性增长，所以影响的是**吞吐上限**而不是单步延迟。高并发时对策是加 detokenizer 进程，或者让客户端只收 token id 自己解码。

**parser 的开销要单独算**：它在文本上做匹配，状态比 detokenizer 大，且 tool call 场景下要累积完整片段才能解析。本章实测 tool call 请求 20 个 token 只产生 7 个事件，就是 parser 聚合的结果。
</details>

<details markdown="1">
<summary>6. 一次请求生成 500 个 token。这 500 步里 CPU 和 GPU 各做了什么？瓶颈在哪？</summary>

| 步骤 | 在哪 | 数据量 | 性质 |
|---|---|---|---|
| 模型前向 | GPU | 读整个模型权重（1.7B bf16 ≈ 3.4 GB） | **带宽瓶颈** |
| 采样（惩罚/温度/截断/抽样） | GPU | $[B, 151936]$ | 需要排序，非平凡 |
| token id 回传 | PCIe | $B$ 个 int32 | 可忽略 |
| eos 检查 | GPU 上算 mask | 1 个比较 | 用 `.item()` 会强制同步 |
| detokenize | CPU | 1 个 token | 字符串处理，有跨步状态 |
| 发送给客户端 | 网络 | 几十字节 | 有 syscall 开销 |

**瓶颈在模型前向的显存带宽。** 生成一个 token 要把整个模型权重读一遍：$3.4\ \text{GB} / 1519\ \text{GB/s} \approx 2.2$ ms（L0.3 实测带宽）。而这一步只做 $2\times1.7\times10^9 \approx 3.4$ GFLOP，在 232 TFLOP/s 的卡上只要 0.015 ms——**算力用了不到 1%**。

**三个推论：**

1. **batch 越大越划算。** 权重只读一次，可以同时服务 $B$ 个请求；$B$ 从 1 涨到 64，延迟几乎不变、吞吐涨几十倍。这是 continuous batching 的全部动机（L5.3）。
2. **500 步总时间约 1.1 秒**，与 prompt 长度基本无关（KV cache 的读取随长度增长，但相对权重小得多）。
3. **CPU 侧每一项都要避免同步。** 单步只有 2 ms 预算，一次 `.item()` 是 4.76 µs（0.24%），但它打断的是 CPU 提前提交下一步的流水，实际影响远大于这个数（L1.4、L2.1）。

**什么时候瓶颈会转移**：$B$ 到几百时，$[B, V]$ 的排序和 detokenize/parser 的 CPU 开销开始显现。对策是 GPU 上的 top-p kernel 优化（L5.9）与 detokenize 多进程。
</details>
