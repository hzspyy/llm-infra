## 本章回答三个问题

1. 一个请求跨过哪些进程与状态边界？
2. Python 里的一个算子，对应 GPU 上的什么工作？
3. 不同观察层（HTTP、日志、调度、profiler、机器码）怎样关联到同一个请求？

你向模型发送一条消息，最后收到一段逐字出现的回答。两端都像是在处理文字，
但 GPU 并不直接读取聊天消息。服务器需要先把文字变成模型的输入，
安排一次或多次计算，再把计算结果变回文字。

本章沿一次真实请求贯通整条调用链。三个核心角色首先明确界定：

- **API 服务**接收请求、检查参数，并把输出发回客户端。
- **调度器**管理等待中和执行中的请求，决定下一轮处理谁。
- **模型执行器**准备张量、调用模型，并把工作提交给 GPU。

这三个角色不一定各占一个进程。同一个进程可以承担多个角色，
一个角色也可以由多个 worker 承担。读源码时先分清职责，再看进程划分，
比先记住「某引擎有几个进程」更有用。

本章的主线是普通文本生成。图片、投机解码和多机部署会增加步骤，
不能把这里的流程当成所有配置的完整调用栈。

## 机制拆解

### 一、请求跨过的是进程边界，不只是函数边界

先看真实结构。启动一个 Qwen3-1.7B 的服务后，从 `/proc` 读它的进程树：

**vLLM 0.29.0：两个干活的进程。**

| 进程 | 线程数 | 线程名（去重） | 职责 |
|---|---:|---|---|
| API 进程 | 125 | `python`、`ZMQbg/IO/0`、`ZMQbg/IO/1`、`ZMQbg/Reaper`、`iou-sqp`、`cuda00001800007` | HTTP、模板、分词、输出处理 |
| `VLLM::EngineCore` | 153 | `VLLM::EngineCor`、`ZMQbg/IO/0`、`cuda-EvtHandlr`、`pt_nccl_watchdg`、`pt_nccl_heartbt`、`gloo_tcp_loop`、`python` | 调度、KV 管理、前向、采样 |
| `resource_tracker` | 1 | `python` | 清理共享内存等资源 |

**SGLang 0.5.19：同样的模型和请求，切成三个。** 用同一个脚本、同一份 prompt 量到：

| 进程 | 线程数 | 线程名（去重） | 职责 |
|---|---:|---|---|
| HTTP 进程 | 97 | `python`、`ZMQbg/IO/0`、`ZMQbg/IO/1`、`ZMQbg/Reaper`、`iou-sqp`、`cuda00001400006` | HTTP、分词（TokenizerManager） |
| `sglang::scheduler` | 94 | `sglang::schedul`、`ZMQbg/IO/*`、`cuda-EvtHandlr`、`pt_nccl_watchdg`、`pt_tcpstore_uv`、`gloo_tcp_loop` | 调度、KV 管理、前向、采样 |
| `sglang::detokenizer` | 67 | `sglang::detoken`、`ZMQbg/IO/*`、`python` | 增量解码 |
| `resource_tracker` | 1 | `python` | 清理共享内存等资源 |

**差别在解码放在哪里。** vLLM 把增量解码留在 API 进程，SGLang 单独给它一个进程。
职责是同一套，进程数不同——这正是开头那句「先分清职责，再看进程划分」的意思。
两边都用 ZeroMQ 传消息（两侧都有 `ZMQbg/*` 线程），也都带一个 `resource_tracker`。

三件事值得记住：

**1. 这是两个进程，不是两个线程。** 两侧都出现 `ZMQbg/*` 线程，说明它们之间走 ZeroMQ 消息，
而不是共享 Python 对象。一个请求从 API 进程进入引擎进程时，必须被序列化再发送。

**2. 线程数远多于「worker 数」。** 153 个线程里绝大多数不是干活的，
是 CUDA 事件处理、NCCL 看门狗、心跳这类后台线程。用线程数推断并行度会得出错的结论。

**3. 这种切分是强制的，不是配置。** vLLM 0.29.0 的客户端工厂里直接拒绝了
「异步模式 + 单进程」这种组合：

{{src:results/crater/0.1/20260913-lifecycle/vllm-core-client.py:89-108}}

所以在线服务这条路径上，你无法把引擎塞回 API 进程里观察。
本章后面的逐 step 记录因此改用同步 `LLM`——它走 `InprocClient`，
所有层落在同一个进程，但也就不再有跨进程边界可看。
**两种配置各自回答一部分问题，不能互相替代。**

### 二、同一个 id 怎样贯穿各层

请求在不同层有不同的名字，但前缀一路保留。实测一次请求的完整链条：

| 观察层 | 看到的标识 | 从哪里读 |
|---|---|---|
| HTTP 请求头 | `l01-trace-0001` | 客户端自己设置的 `X-Request-Id` |
| 响应 JSON | `cmpl-l01-trace-0001` | `id` 字段 |
| 服务端日志 | `cmpl-l01-trace-0001-0` | `request_logger.py:63` 的 `Received request` |
| 引擎内部 | `cmpl-l01-trace-0001-0-ad7beb1d` | `async_llm.py:514` 的 `Added request` |

两次加后缀各有用途：`-0` 区分同一请求的第 $n$ 个候选（`n>1` 时会有 `-1`、`-2`），
末尾的随机段保证引擎内部 id 不会因为客户端重复使用同一个 id 而冲突。

同一规律在单进程配置下也成立：那次运行里前端拿到的 id 是 `0`，
引擎内部各层记录的是 `0-b33284cf`。**在 vLLM 上排查时按前缀匹配，不要按完整字符串相等匹配。**

**换成 SGLang，这条链断了。** 同一个客户端、同一个 `X-Request-Id`，
SGLang 返回的 `id` 是 `76d32d5dd8a345438ef5b2c9d9e47594`——一个与请求头无关的随机串，
在服务端日志里搜客户端的 id 得到 **0 行**。

| 引擎 | 客户端设的 id | 响应 id | 日志里能按客户端 id 搜到 |
|---|---|---|---|
| vLLM 0.29.0 | `l01-trace-0001` | `cmpl-l01-trace-0001` | 能（2 行） |
| SGLang 0.5.19 | `l01-trace-0001` | `76d32d5d…e47594` | **不能（0 行）** |

这条差异直接决定排查方式：在 vLLM 上可以让客户端带上自己的 id 再去 grep 日志；
在 SGLang 上必须先从响应里取回它生成的 id，再用那个 id 去找。
**换引擎时这类「外部可观测性」的约定往往不迁移**，不能假设一套排查手法通用。

### 三、一次 step 到底调度了什么

「引擎跑了几步」是可以直接读出来的。在单进程配置下给三个边界打点，
一次 `max_tokens=3` 的请求留下这样的记录：

| 事件 | step | 记录到的内容 | waiting | running |
|---|---:|---|---|---|
| `LLMEngine.add_request` | — | 请求 id `0` | — | — |
| `Scheduler.schedule` | 1 | `{'0-b33284cf': 11}`，`scheduled_new_reqs` 非空 → **prefill** | 1 → 0 | 0 → 1 |
| `Worker.execute_model` | 1 | 同一批 11 个 token | | |
| `Scheduler.schedule` | 2 | `{'0-b33284cf': 1}` → **decode** | 0 → 0 | 1 → 1 |
| `OutputProcessor.process_outputs` | 2 | 新 token `[362]` | | |
| `Scheduler.schedule` | 3 | `{'0-b33284cf': 1}` → **decode** | 0 → 0 | 1 → 1 |
| `OutputProcessor.process_outputs` | 3 | 新 token `[84648]`，随后 `[6500]` 并 `finished` | | |

后两列是调度器两个队列的深度，在每次 `schedule` 前后各读一次。
**请求的状态变化就发生在 prefill 那一步**：它从 `waiting` 队列被取走（1→0）、
进入 `running` 集合（0→1），此后两个 decode 步都只是在 `running` 里继续。
从 `add_request` 到第一次被调度中间隔了 **4.11 ms**，这段是排队与准入，
不属于任何一个模型算子——L0.2 的时延账里它要单列。

本次还记录到 **1 次空调度**：引擎循环转了一圈但没有可调度的请求，
`num_scheduled_tokens` 为空。统计「每步耗时」时这类迭代要区分开，
否则平均值会被拉低。

读这张表要注意三点：

**prefill 一次吃掉整个 prompt。** 11 个 token 一步算完，
并且**第一个输出 token 就来自这一步**，不需要额外再跑一次 decode。
之后每个输出 token 各占一步，每步只调度 1 个 token。
`num_scheduled_tokens` 是区分两个阶段最直接的字段，比看耗时可靠。

**输出比调度晚一拍。** step 1 调度完成后，第一个 token 的输出在 step 2 才被处理。
引擎把「取上一步结果」和「提交这一步」重叠了起来，
所以按时间戳配对 step 与 token 会错位一格。

**引擎启动时还跑过 4 次 `execute_model`。** 那是 warmup，请求 id 形如 `_warmup_N_`，
不属于任何用户请求。统计 kernel 次数或平均耗时时，这些必须排除。

### 四、从 Python 算子到 GPU kernel

把一次前向放进 profiler，就能把每个 Python 算子和它发起的 kernel 对上。
对应关系靠 trace 里的 `correlation` 编号：一次 runtime 调用和它启动的 kernel 共享同一个编号。

实测一次 profiler 采样（2 步、5,846 个 CPU 算子、1,189 次 runtime 调用、
745 个 kernel、31 种不同 kernel、设备合计 6,438.6 µs），
沿 attention 层的三个算子往下看：

先看调用链本身：

| 算子（prefill 步） | 输入形状 | runtime 调用 | 设备 kernel |
|---|---|---|---|
| `aten::linear`（QKV 投影） | `[11,2048] × [4096,2048]` | `cuLaunchKernel` | `cutlass_80_wmma_tensorop_bf16_s161616gemm` |
| `_C_cache_ops::reshape_and_cache_flash` | `[11,8,128]` → `[2229,16,8,128]` | `cudaLaunchKernel` | `vllm::reshape_and_cache_flash_kernel` |
| `vllm::unified_attention_with_output` | Q `[11,16,128]`，K/V `[11,8,128]` | `cudaLaunchKernel` | `flash::flash_fwd_splitkv_kernel` |

再看各自的耗时与资源：

| 算子（prefill 步） | CPU µs | runtime µs | 设备 µs | grid / block | 寄存器 | 共享内存 |
|---|---:|---:|---:|---|---:|---:|
| QKV 投影 | 48.50 | 3.4 | 13.2 | `[8,32,1]` / `[32,1,1]` | 124 | 16,896 B |
| 写 KV cache | 8.17 | 3.8 | 1.6 | `[11,1,1]` / `[512,1,1]` | 48 | 0 |
| attention | 86.51 | 3.9 | 6.8 | `[1,1,16]` / `[128,1,1]` | 254 | 81,920 B |

几处能直接读出的结构信息：

- **QKV 是一次融合投影。** 权重 `[4096, 2048]` 对应 Q 的 16 头 × 128 加上 K、V 各 8 头 × 128，
  一次 GEMM 同时产出三份，与 L0.0 讲的合并 QKV 一致。
- **写 KV 是独立算子。** `[2229, 16, 8, 128]` 是分页 KV cache 的形状：2,229 个块、
  每块 16 个槽位、8 个 KV 头、head_dim 128。attention 之前要先把本轮 K/V 写进去，
  这一步不属于 attention kernel。L5.2 展开分页管理。
- **attention 的 grid 是 `[1,1,16]`。** 第三维是 16 个 Q 头，
  说明这次划分按头并行；`splitkv` 表示它还可能沿 KV 维再切。

同一批算子在 decode 步的形状完全不同：

| 算子（decode 步） | 输入形状 | CPU µs | 设备 kernel | 设备 µs | grid |
|---|---|---:|---|---:|---|
| `_C_cache_ops::reshape_and_cache_flash` | `[1,8,128]` | 4.35 | 同上 | 1.4 | `[1,1,1]` |
| `vllm::unified_attention_with_output` | Q `[1,16,128]` | 63.42 | `flash_fwd_splitkv_kernel`（另一组模板参数） | 4.2 | `[1,1,8]` |
| `aten::linear`（lm_head） | `[1,2048] × [151936,2048]` | 10.17 | `internal::gemvx::kernel` | **383.1** | `[37984,1,1]` |

最后一行是这次采样里最贵的单个 kernel。它是 lm_head：词表 151,936，
decode 时只有 1 个位置，矩阵乘退化成矩阵向量乘，框架也相应换成了 `gemvx` 而不是 GEMM。
**383 µs 里几乎全是把 `151936 × 2048` 的权重从显存读一遍的时间**，
算术强度极低——这正是 L0.2 要算的账、L5.1 要处理的问题。

**不要期待算子和 kernel 一一对应。** 这次采样里 5,846 个 CPU 算子只产生 745 个 kernel：
大量算子是纯 CPU 的形状计算、元数据构造和 Python 开销，根本不发起 GPU 工作；
反过来一个算子也可能发起多个 kernel。层数、算子数、kernel 数是三个不同的量。

### 五、提交返回不等于计算完成

同一份 trace 里，每个 kernel 都有两组时间：主机发起调用的区间，和设备执行的区间。
把它们分开看：

| 算子（prefill 步） | runtime 调用耗时 | 提交到设备开始 | 主机返回后设备还要跑 |
|---|---:|---:|---:|
| QKV 投影 | 3.4 µs | 10.5 µs | 20.2 µs |
| 写 KV cache | 3.8 µs | 6.0 µs | 3.7 µs |
| attention | 3.9 µs | 5.7 µs | 8.6 µs |

`cudaLaunchKernel` 三四微秒就返回了，但设备要再过五到十微秒才真正开始，
并在主机调用返回之后才结束。这就是**异步提交**：主机只是把工作放进流里。

由此得到两条排查纪律：

1. **在主机侧计时得到的「kernel 耗时」是假的**，它测的是提交动作。
   要测设备时间必须用 CUDA event 或 profiler，L0.3 与 M2 展开这件事。
2. **主机侧看起来空闲，不代表 GPU 空闲**，反之亦然。
   本例 prefill 步的 attention，Python 侧 86.5 µs 而 kernel 只有 6.8 µs，
   瓶颈明确在主机；这类情形正是 CUDA Graph（L2.6b）要解决的。

### 六、再往下一层：fatbin 里装的是什么

kernel 名字之下还有机器码。把这三个 kernel 所在的动态库拆开看，
结果分成两类：

| 构建 | 带 SASS 的架构 | 带 PTX 的架构 | 本机 sm_120 |
|---|---|---|---|
| vLLM 自编 kernel（`_C_stable_libtorch.abi3.so`） | sm_75 / 80 / 86 / 89 / 90 / 90a / 100 / **120** | sm_80 / 89 / 90 | 原生可跑 |
| vLLM 自带 FlashAttention-2（`vllm_flash_attn/_vllm_fa2_C.abi3.so`） | 仅 sm_80 | 仅 sm_80 | **需 JIT** |
| vLLM 自带 FlashAttention-3（`vllm_flash_attn/_vllm_fa3_C.abi3.so`） | 仅 sm_90a | 无 | **跑不了** |
| 上游 `flash-attn` 2.8.3（cu13torch2.9 wheel） | sm_80 / 90 / 100 / **120** | 无 | 原生可跑 |

本机是 RTX 5090 D（sm_120）。架构对照表明，**同一个算法的四份构建，覆盖范围截然不同**：

- vLLM 自己编译的那批 kernel 带 sm_120 机器码，装上直接跑。
- **本次实际用到的 FlashAttention-2 只带 sm_80**，在 sm_120 上只能由驱动从 PTX
  即时编译（JIT）出机器码——换新卡后首次运行某个 kernel 特别慢，常常就是这一步。
- 自带的 FlashAttention-3 只有 sm_90a 且**不带 PTX**，在 sm_120 上没有可用路径，
  这也解释了引擎为什么在本机选了 FA2 而不是 FA3。
- **上游 `flash-attn` 2.8.3 的 wheel 反而带 sm_120 原生 SASS**，覆盖 sm_80/90/100/120。

也就是说，「FlashAttention 在这张卡上要不要 JIT」取决于**你用的是哪一份构建**，
而不是取决于算法本身。这里用到的是**随 vLLM 分发的 `vllm.vllm_flash_attn`**，
环境里并没有单独安装上游 `flash-attn`；服务日志 `cuda.py:492` 选中 `FLASH_ATTN`、
`flash_attn.py:897` 打印 `Using FlashAttention version 2`，与 trace 里 `flash::` 命名空间的 kernel 对得上。
libtorch 里还有第三份同名 kernel，命名空间是 `pytorch_flash::`，按名字搜索极易混淆。

上游 wheel 的架构清单是直接从下载到的 `.so` 读出来的，**没有安装、也没有导入**：
它针对 torch 2.9 构建，而本机是 torch 2.13，能否在此加载运行属于另一个问题，
本章不作结论。

### 真的把机器码取出来

`cuobjdump` 不能直接反汇编共享库里的 kernel，要分三步：把 fatbin 里的 cubin 抽出来
（`cuobjdump -xelf`），挑出目标架构的那些，再用 `nvdisasm -c` 反汇编并截出这个函数。
三个算子的结果各不相同，正好覆盖了三种情况：

| 算子 | 结果 |
|---|---|
| 写 KV cache | 在 `_C_stable_libtorch.abi3.so` 的 **sm_120 cubin** 里找到，**4,984 条指令** |
| attention | sm_80 的 cubin 只声明符号、没有函数体——**机器码不在 wheel 里** |
| QKV 投影 | 符号没在所搜索的库里找到，见下文 |

写 KV cache 的 SASS 指令分布是 `FFMA` 1,012、`MOV` 830、`IMAD` 329、`BRA` 299——
以浮点乘加、搬运和地址计算为主，没有矩阵指令，符合「做 dtype 转换再写进分页缓存」这件事。

attention 那一行才是有意思的：既然 wheel 里没有 sm_120 的机器码，
驱动在加载时就得自己编。**这一步可以用同一套工具链离线复现**：
把定义该 kernel 的 PTX 模块抽出来（`cuobjdump -xptx`，模块 6.4 MB、23.6 万行，
`.target sm_80`），用 `ptxas -arch=sm_120` 编译，再反汇编：

```
ptxas -arch=sm_120 -o jit.cubin <module>.ptx   →  4.7 MB cubin
nvdisasm -c jit.cubin                          →  该 kernel 3,856 条指令
```

得到的指令分布与上一个 kernel 截然不同：`HMMA` 384、`LDSM` 216、`IMAD` 328、`FMUL` 204。
`HMMA` 是 tensor core 的矩阵乘累加，`LDSM` 是给它喂数的共享内存矩阵加载——
**这两个助记符基本就是 FlashAttention 这类 kernel 的签名**。
换句话说：同一次前向里，一个 kernel 的机器码是装好就有的，另一个是运行时现编的，
而现编出来的东西可以在本机精确复现。

QKV 投影那个 cutlass GEMM 的符号没能在搜索范围（vLLM、torch、flash、nvidia 四类库）
里定位到，因此**这一个 kernel 的反汇编仍标 `UNVERIFIED`**；
它大概率经由 cuBLASLt 分派，kernel 未以独立符号暴露。
指令集、寄存器分配与 PTX→SASS 的完整下降链在 L2.2 展开，本章到此为止。

### 设计取舍

**把引擎拆成独立进程，买到的是 GIL 隔离，付出的是序列化与调试成本。**
API 进程要跑 HTTP、模板渲染、分词和增量解码，这些都是 Python 密集工作；
和引擎循环放同一个进程会互相抢 GIL。代价是每个请求都要跨进程传一次，
而且你无法在一个进程里同时给两侧打断点——本章做逐 step 记录时只能换成同步配置。
vLLM 直接在 `make_client` 里禁掉了「异步 + 单进程」，把这个取舍固化成了约束。

**请求 id 加后缀，换来的是各层可独立生成 id。** 若各层共用同一个字符串，
客户端重复使用一个 id 就会让引擎内部状态冲突；若各层独立编号，
跨层排查就要维护映射表。加后缀保留前缀是折中：日志可按前缀 grep，
内部仍然唯一。代价是不能用字符串相等去匹配。

**两个引擎在这件事上选择不同，代价也不同。** vLLM 把客户端的 id 带进响应和日志，
外部可观测性好，但也意味着客户端能影响服务端的日志键；
SGLang 自己生成一个随机 id，服务端完全自洽，代价是客户端手上的 id
在服务端一行都搜不到，排查必须先回读响应。**这类约定不随「都实现了 OpenAI 协议」而统一**，
是选型时要单独确认的一项。

**后端选择放在 `selector` 加一层缓存，是为了让形状无关的决策只做一次。**
`get_attn_backend` 的结果对同一组配置是固定的，每层都重算属于浪费；
但缓存也意味着**运行中换后端不会生效**，要改就得在引擎启动前改。
替换 attention 后端的改动范围因此很清楚：实现一个后端类，
让平台的 `get_attn_backend_cls` 能返回它，其余各层不用动。

**采样器与 logits 处理器分开，是为了让「改概率」和「怎么抽」互不影响。**
惩罚项、约束解码都在 logits 上做文章，走 `build_logitsprocs` 注册；
真正的抽样只在 `Sampler.forward`。想加一种新的约束不必碰采样实现，
想换采样算法也不必重写惩罚项。L5.6 与 L5.9 分别展开这两侧。

## 前沿

本章测的是最简单的配置：单卡、batch 1、eager 模式、无前缀缓存。
真实部署在这条链上会加入下面这些，每一项都改变某一层的观察方式：

| 加进来的东西 | 改变了什么 | 章节 |
|---|---|---|
| 连续批处理 | 一步里 `num_scheduled_tokens` 同时含多条请求 | L5.3 |
| 前缀缓存 | prefill 调度的 token 数少于 prompt 长度 | L5.2 |
| CUDA Graph | 多个 kernel 合成一次重放，runtime 调用数骤降 | L2.6b |
| 张量并行 | 引擎侧变成多个 worker 进程，多一层通信 | L6.2 |
| 投机解码 | 一步可能接受多个 token，step 数不再等于输出 token 数 | L5.5 |
| PD 分离 | prefill 与 decode 落在不同实例，id 要跨机器串 | L6.4 |

## 陷阱

**1. 把静态调用图当执行证据。** 调用地图说明「可能经过谁」；
某个 hook 没出现不代表没执行，一张图也不能证明某次请求确实走过它。
要执行证据就打点或看 trace。

**2. 用字符串相等去匹配请求 id。** vLLM 各层的 id 带不同后缀，按前缀匹配才对；
SGLang 干脆不透传客户端 id，得先从响应里取回它生成的那个。

**3. 把客户端时延当模型耗时。** 本例客户端看到 23.7 ms，
其中包含排队、跨进程传递、分词、推理和回传。分解方法见 L5.11。

**4. 在主机侧给 kernel 计时。** `cudaLaunchKernel` 三四微秒就返回，
测到的是提交而不是计算。设备时间要用 event 或 profiler，见 M2。

**5. 把算子数、kernel 数和层数混用。** 本章采样里 5,846 个算子只发起 745 个 kernel。
统计前先确认区间，并排除 warmup。

**6. 用线程数推断并行度。** 引擎进程 153 个线程里大多数是 CUDA 事件、
NCCL 看门狗一类的后台线程。

**7. 假设 wheel 里有你这张卡的机器码。** 同一个 FlashAttention-2，
vLLM 自带的那份只有 sm_80（sm_120 要 JIT），上游 wheel 却带 sm_120 原生 SASS。
首次运行慢未必是代码问题，先查你用的那份构建的架构清单。
「FlashAttention」也不止一份实现：vLLM 的 vendored 版本、上游 `flash-attn` 包、
libtorch 内置的 `pytorch_flash` 各是各的，比较前先确认用的是哪一份。

**8. 以为取消是瞬间的。** 它要跨进程传递、从队列摘除、再释放 KV 块，
这期间请求可能已经进入下一步。L5.8 量化了这段过程。

**9. 把排队时间算进模型耗时。** 本章实测从 `add_request` 到第一次被调度有 4.11 ms，
这段只是排队与准入。看「每步耗时」时还要把空调度的迭代排除掉。

## 自测题

<details markdown="1">
<summary>1. 模型输出了 token id，为什么客户端还没有收到文字？</summary>

模型计算结束不等于响应发送完成。服务端还要把结果拷回主机、
执行增量解码（detokenize）、判定停止条件，最后写回网络响应通道。
这些步骤在 vLLM 里发生在**另一个进程**：前向在 EngineCore 进程，
输出处理与流式回写在 API 进程，中间隔着一次 ZMQ 传递。

排查延迟时要把这些步骤逐一拆开，不能把耗时都归给模型前向。
本章的实测是客户端 23.7 ms、prompt 11 token、输出 3 token；
L5.11 把这条链分解成前端、排队、推理、进程外四段。
</details>

<details markdown="1">
<summary>2. 一份 trace 显示 745 次 kernel 调用，能否说模型有 745 层？</summary>

不能，本章的 745 次就是反例。这次采样覆盖 2 个 step，模型 28 层。

三个量各不相同：

- **层数**由模型结构决定（28）。
- **算子数**由框架实现决定（本次 5,846 个 CPU 算子，多数是纯 CPU 工作）。
- **kernel 数**由后端实现与融合程度决定（745 个，31 种）。

判断方法是看 `top_kernels` 里每种 kernel 的次数：
`reshape_and_cache_flash` 出现 56 次 = 28 层 × 2 步，这类才是「每层一次」；
而 `rms_norm_kernel` 出现 112 次 = 28 × 2 × 2，因为每层有两个归一化。
统计前还要排除 warmup。
</details>

<details markdown="1">
<summary>3. 使用 CUDA Graph 后只提交一次，GPU 是否就只执行一个 kernel？</summary>

不是。一张图可以包含多个 kernel 节点。图重放减少的是**提交次数**，
不是 kernel 数量；算子融合才可能减少独立 kernel 的数量。

本章的数据说明为什么这件事有意义：prefill 步的 attention，
Python 侧 86.5 µs 而 kernel 只有 6.8 µs。主机侧的算子调度、
参数打包和 launch 开销远大于设备计算，这正是图重放要省掉的部分。

两种方法可以组合，但要分别观察：图模式下数 runtime 调用，
融合与否看 kernel 名字和数量。L2.6b 展开。
</details>

<details markdown="1">
<summary>4. 一个请求在服务端「卡住」了，先看哪一层？</summary>

**按边界从外往里排除，每一层都有对应的观察手段。**

| 怀疑 | 怎么确认 | 如果是它 |
|---|---|---|
| 根本没进来 | API 进程日志有没有 `Received request <id>`（SGLang 要用响应里的 id） | 看 HTTP 层、反向代理、参数校验 |
| 进来了没被调度 | 引擎日志有没有 `Added request`；调度统计里排队数 | 看并发上限、KV 块是否耗尽（L5.3） |
| 调度了但很慢 | 逐 step 的 `num_scheduled_tokens` 与 step 耗时 | 看 batch 组成、序列长度（L5.1） |
| 算完了没发出来 | 输出处理与流式回写这一侧 | 看增量解码、缓冲与连接（L5.11） |

关键是**先确定请求停在哪个边界**，再选观察层。
反过来先上 profiler，往往测了一段与问题无关的区间。

**改动位置**：要在自己的服务里补这条链，最小的做法就是本章的四个打点——
前端入口、调度、执行、输出处理，每处记 `request_id`、时间戳、
进程与线程号。四个时间戳之间的差值直接指出是哪一段慢。
</details>

<details markdown="1">
<summary>5. 要把 attention 换成自己实现的后端，改哪里？会影响到哪些层？</summary>

**vLLM 0.29.0 的改动范围：**

1. 实现后端类（提供 metadata 构造与 forward）。
2. 让 `vllm/platforms/cuda.py` 的 `CudaPlatformBase.get_attn_backend_cls`
   在你的名字下返回它。
3. 启动时通过配置选中；`vllm/v1/attention/selector.py:102` 的 `get_attn_backend`
   会解析一次，结果被 `:195` 的 `_cached_get_attn_backend` 缓存。

**会受影响的层**：调度器不受影响（它只管 token 数和块）；
执行器受影响，因为 attention metadata 的字段由后端定义；
KV cache 的**布局**可能受影响——本章 trace 里 `[2229, 16, 8, 128]`
这个形状就是后端与块大小共同决定的，换后端要同步确认写入路径
`reshape_and_cache_flash` 是否仍然适用。

**不会生效的做法**：运行中替换。选择结果被缓存，必须在引擎启动前设置。

**SGLang 对应的位置**是 `model_runner.py:993` 的 `init_attention_backends`
与 `:1408` 的 `_get_attention_backend`，结构类似但注册方式不同。
两边都要改时，先确认各自的 metadata 契约，不要假设字段同名同义。
</details>

<details markdown="1">
<summary>6. 客户端断开连接后，服务端立刻就不算了吗？</summary>

**不是，它要跨过几层才停下来。**

1. API 进程先察觉断连（`api_utils.py:51` 的 `with_cancellation`）。
2. 前端调用 `AsyncLLM.abort`，经 `MPClient` 把消息发到引擎进程。
3. 引擎的 `EngineCore.abort_requests` 把它从在跑的集合里去掉。
4. 调度器 `Scheduler.finish_requests` 把 KV 块还给块池。

这几步之间请求可能已经被调度进了下一个 step，
所以取消后通常还会多算一两步。**显存也不是在断连瞬间释放的**，
要等第 4 步执行完。

SGLang 的对应路径是 `TokenizerManager.abort_request` → `Scheduler.abort_request`，
层数更少但同样跨进程。

真实的取消时延、资源回收与并发下的表现在 L5.8 有实测。
</details>
