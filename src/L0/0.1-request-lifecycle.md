## 一次请求，先看谁在做什么

你向模型发送一条消息，最后收到一段逐字出现的回答。两端都像是在处理文字，
但 GPU 并不直接读取聊天消息。服务器需要先把文字变成模型的输入，
安排一次或多次计算，再把计算结果变回文字。

这一章沿着这个过程介绍推理引擎。先记住三个参与者：

- API 服务接收请求、检查参数，并把输出发回客户端。
- 调度器管理等待中和执行中的请求，决定下一轮处理谁。
- 模型执行器准备张量、调用模型，并把工作提交给 GPU。

这三个角色不一定各占一个进程。同一个进程可以承担多个角色，
一个角色也可以由多个 worker 承担。读源码时，先分清职责，再看进程划分，
比先记住“某引擎有几个进程”更有用。

本章的主线是普通文本生成。图片、投机解码和多机部署会增加步骤，
不能把这里的流程当成所有配置的完整调用栈。

## 从聊天消息变成模型输入

假设请求中的消息是“请用一句话解释显存带宽”。API 首先解析 HTTP 请求中的 JSON，
确认消息格式、模型名称和生成参数是否合法。这时处理的仍是普通应用数据。

接下来，服务将消息交给 chat template。模板会加入角色标记、消息分隔符，
也可能加入模型约定的生成提示。相同的问题套用不同模板后，得到的字符串可能不同。
因此模板不是显示格式，而是模型输入的一部分。

tokenizer 再把字符串分成 token，并为每个 token 找到词表中的整数编号。
模型接收的是这些编号，不是 Python 字符串。这里要分别检查三份东西：
原始 messages、模板展开后的文本、最终 token id。只检查最初的消息，
很容易漏掉模板或特殊 token 的差异。

已有采集文件保存了真实词条和模板。展开后，先找到普通词条与特殊 token，
再看完整模板，不必从第一行一路读到最后一行。

{{srcfold:results/crater/raw/13_tokenizer.txt}}

词条中的 `Ġ` 常表示前导空格。“带空格的词片”和“不带空格的词片”可能是不同 token。
但末尾多一个空格不一定使整个前缀失效；应直接比较实际 token 序列。

## 请求为什么要先进入调度器

服务器可能同时收到多个请求。它们的输入长度不同，已经生成的长度也不同，
有些刚到达，有些只差一步就会结束。调度器的任务是把这些状态组织成下一轮计算。

它需要同时考虑两类限制：本轮可以处理多少 token，以及显存是否足以保存所需状态。
因此，“请求已经进入服务器”不等于“GPU 已经开始计算它”。排队时间属于请求延迟，
但不属于某个模型算子的执行时间。

对于使用前缀缓存的请求，还需要查询已有缓存。KV cache 保存历史位置的
key 和 value 张量；如果缓存与当前输入的前缀兼容，就可能少算一部分输入。
分页管理与前缀查找是两件事：前者决定 KV 存放位置，后者决定已有 KV 能否复用。
L5.2 会单独展开这两个问题。

vLLM 的块哈希把前面的上下文带入身份计算；SGLang 的基数树显式保存前缀分叉。
这两种表示方式各有取舍，但不能从数据结构名称直接推出哪一个更快，
也不能说块哈希原则上无法提供前缀感知调度需要的信息。

## 调度结果怎样变成 GPU 工作

调度器的决定通常还是 CPU 上的数据结构。执行器需要把它整理成 GPU 能读取的张量。
其中几项在后面的章节会反复出现：

| 输入 | 含义 | 为什么需要 |
|---|---|---|
| token id | 本轮各位置对应的词表编号 | 查 embedding，开始模型计算 |
| position | 这些位置在序列中的位置 | 进行位置相关的变换 |
| slot mapping | 新 K/V 应写入的槽位 | 把新状态放入正确的缓存位置 |
| block table | 逻辑块对应的物理块编号 | 找到历史 K/V |
| attention metadata | 长度、偏移等辅助信息 | 让 kernel 正确处理不同序列 |

这个步骤是在把一份执行安排翻译成张量。当模型很小或每轮计算很短时，
CPU 构造和搬运这些数据的时间也值得检查，不能把它当作没有成本的准备工作。

GPU 随后执行模型。一次前向通常包含矩阵乘、归一化、位置变换、
attention 和激活函数等多个操作。框架可能把其中一些操作融合，
也可能为一个操作调用多个 kernel。因此，模型层数、算子数和 kernel 数不能混用。

## 首个输出与后续输出有什么不同

在普通自回归生成中，第一次前向处理 prompt，通常称为 prefill。
末位置的隐藏状态经过 lm_head 得到 logits，采样器据此选择第一个输出 token。
**第一个输出来自这次 prompt 前向，不需要先额外执行一次 decode 前向。**

为了生成第二个输出，模型再处理上一步选出的 token，并读取历史 KV。
这时新增输入通常只有一个 token，而历史上下文已经较长。这类后续步骤称为 decode。
如果一个 batch 中有多条请求，每条请求都可能贡献自己的新 token。

同一模型在两个阶段会出现不同形状的矩阵计算：prefill 的线性层一次处理较多位置，
小 batch decode 一次处理的位置较少。L0.2 将据此估算计算量和数据量，
L0.3 再比较硬件上的表现。

拿到 token id 后，服务还要执行增量解码，把编号转换成可发送的文本，
检查停止条件，并通过流式响应返回。一次网络事件未必恰好对应一个 token：
缓冲策略、解码器和接口协议都可能影响发送时机。

## 自测：能否把几个边界分开

<details markdown="1">
<summary>模型输出了 token id，为什么客户端还没有收到文字？</summary>

模型计算结束并不等于响应发送结束。服务仍可能需要传回设备结果、
进行增量解码、检查停止条件，再写入响应通道。应分别查看这些步骤的时间，
而不是把所有延迟都算到模型前向上。
</details>

<details markdown="1">
<summary>一份 trace 显示 400 次 kernel 调用，能否说模型有 400 层？</summary>

不能。一层可能调用多个 kernel，同一个 kernel 也可能被多层复用。
先确认统计区间，再根据符号、次数和对应代码判断这些调用属于哪些操作。
</details>

<details markdown="1">
<summary>使用 CUDA Graph 后只提交一次，GPU 是否就只执行一个 kernel？</summary>

不是。一张图可以包含多个 kernel 节点。图重放减少重复提交工作，
算子融合才可能减少独立 kernel 的数量。两种方法可以组合，但应分别观察。
</details>
