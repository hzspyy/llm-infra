## 本章回答三个问题

1. 为什么一个中文字常常是 2~3 个 token？这个说法在什么条件下成立？
2. chat template 到底往序列里插了什么？
3. 一个 batch 里长短不一的句子，padding 之后 `attention_mask` 和 `position_ids` 分别应该是什么？

L0.0 的模型直接从 token id 开始。这一章补上前面那一段：
从你敲进去的那串字符，到模型真正收到的那个整数张量。

本章分两条线：**先手写一个 BPE**（不用任何分词库，每一轮合并都打印出来），

## 机制拆解

### 一、字符在内存里是字节

先把最底下那一层弄清楚。Python 里的 `str` 是 Unicode 码点序列，
但它落到磁盘、网络、模型输入之前，必须编码成字节。现在的事实标准是 UTF-8：

```
'风' 的 Unicode 码点：U+98CE
UTF-8 编码：[233, 163, 142]  = e9 a3 8e  （3 个字节）

'a'    U+00061  1 字节  61
'é'    U+000E9  2 字节  c3 a9
'风'   U+098CE  3 字节  e9 a3 8e
'🌊'   U+1F30A  4 字节  f0 9f 8c 8a
```

UTF-8 是**变长**的：ASCII 占 1 字节，多数汉字 3 字节，emoji 4 字节。
这个事实会在本章和 L0.5 里反复出现，包括一个真实的乱码 bug。

### 二、为什么从字节开始，而不是从字符

一个自然的想法是：词表就是所有字符。问题有两个：

- Unicode 有十几万个码点，词表会非常大；
- 永远会遇到没见过的字符（生僻字、新增 emoji），需要一个 `<UNK>` 兜底，
  而 `<UNK>` 是不可逆的——解码时你不知道原来是什么。

**字节级 BPE 的做法**：初始词表固定是 0–255 这 256 个字节。
任何输入都能表示，**永远不会 OOV**，而且编解码无损。
代价是一个汉字起手就是 3 个 token，要靠后续合并把它压回来。

### 三、BPE 就是「反复合并最高频的相邻对」

算法只有三行：

1. 统计当前序列里所有相邻符号对的出现次数；
2. 把出现次数最高的那一对合并成一个新符号，分配一个新 id；
3. 回到第 1 步，重复 $N$ 次。

本站手写实现在一段两千字的中英混合语料上跑，前 12 轮（**原样输出**）：

```
初始：256 个字节 token，语料切成 209 段，共 1213 个符号
  轮                   合并的对     次数   新 id 新符号                 剩余符号数
  0              ' ' + 't'     29    256 ' t'                 1184
  1              'h' + 'e'     27    257 'he'                 1157
  2            ' t' + 'he'     26    258 ' the'               1131
  3            <ef> + <bc>     21    259 <ef bc>              1110
  4         <ef bc> + <8c>     21    260 '，'                  1089
  5            <e4> + <b8>     17    261 <e4 b8>              1072
  6            <e3> + <80>     15    262 <e3 80>              1057
  7         <e3 80> + <82>     15    263 '。'                  1042
```

三件事从这里就能看清：

- **第 2 轮合成了 `' the'`**，先有 `' t'` 再有 `' the'`——
  这就是词表里为什么满是带前导空格的 token。
- **第 3、4 轮**分两步把中文逗号 `，`（3 字节 `ef bc 8c`）拼了出来：
  先 `ef bc`，再加 `8c`。**汉字必须经过至少两次合并才能变成一个 token。**
- 尖括号 `<ef bc>` 表示这个 token 不是完整的 UTF-8 序列——它是半个字符。
  这类 token 在真实词表里大量存在，也是 L0.5 那个乱码 bug 的根源。

### 四、merges 表是有序的，顺序就是算法

训练产出两样东西：词表（id → 字节串）和 **merges 表**（有序的合并规则）。

编码一段新文本时，必须**按 merges 的顺序**反复尝试合并：

```python
rank = {pair: i for i, pair in enumerate(merges)}
while len(ids) >= 2:
    pairs = set(zip(ids, ids[1:]))
    best = min(pairs, key=lambda p: rank.get(p, float("inf")))   # rank 最小 = 最早学到
    if best not in rank:
        break
    ids = merge_pair([ids], best, 256 + rank[best])[0]
```

顺序不能变。换个顺序会切出不同的结果，模型就认不出来了。
**所以 merges 表和权重一样，是模型文件的一部分**——L4.0 会在真实 checkpoint 里看到它。

### 五、预切分：BPE 不知道什么是词

BPE 只看「相邻」。不加限制的话，它会把跨越空格、甚至跨越标点的组合也合并掉。
本章实测（同一语料，同样 120 轮）：

```
不预切分时，学到的 token 里有 25 个内部含空格，例如：
  'e ' ' the ' 's ' 'nd ' ' the s' 'es '
也就是说 25/120 = 21% 的词表预算
花在了「某个词 + 它后面那个空格」这种依赖上下文的组合上。
```

::: note 预切分在小语料上的对照结果
这组小语料实验没有显示预切分带来压缩优势：

```
在训练语料里出现过的句子上，不预切分反而更省 token：
  不预切分： 8 个 token   （'the wind comes from the sea'）
  预切分：   9 个 token
换成没见过的句子：
  不预切分：25 个 token   （'a bird sings near the old bridge'）
  预切分：  25 个 token
```

**两者一样。** 在这个语料规模上，预切分没有压缩优势，不能硬说它更省 token。

预切分真正的理由是**词表预算**：那 25 个含空格的 token 各占一个词表槽，
只在特定上下文里有用。真实词表有 15 万个槽、语料几百 GB 时这类浪费会累积。
另一个理由是**可控性**：预切分保证 token 不跨越数字、标点与文字的边界，
这对约束解码（L5.6）和数字处理很重要。
:::

真实模型的预切分是一条正则。Qwen3 的 `tokenizer.json` 里原样写着：

```
(?i:'s|'t|'re|'ve|'m|'ll|'d)|[^\r\n\p{L}\p{N}]?\p{L}+|\p{N}| ?[^\s\p{L}\p{N}]+[\r\n]*|\s*[\r\n]+|\s+(?!\S)|\s+
```

逐段读：

| 片段 | 匹配什么 |
|---|---|
| `(?i:'s\|'t\|'re\|'ve\|'m\|'ll\|'d)` | 英文缩写，单独成块 |
| `[^\r\n\p{L}\p{N}]?\p{L}+` | 可选的一个非字母非数字前缀（通常是空格）+ 一串字母 |
| **`\p{N}`** | **单个**数字——注意没有 `+`，每个数字自成一块 |
| ` ?[^\s\p{L}\p{N}]+[\r\n]*` | 可选空格 + 一串标点 |
| `\s*[\r\n]+` / `\s+(?!\S)` / `\s+` | 各种空白 |

**`\p{N}` 没有加 `+`，这是有意的**：每个数字单独成一个块，
BPE 无法把 `3.14` 里的 `14` 合并成一个 token。
后面的实测会看到这个设计的直接后果。

### 六、真实 tokenizer 的文件

Qwen3-1.7B 的分词器相关文件（本章实测）：

```
config.json                                 726 字节
generation_config.json                      239 字节
merges.txt                            1,671,853 字节
tokenizer.json                       11,422,654 字节
tokenizer_config.json                     9,732 字节
vocab.json                            2,776,833 字节
```

`tokenizer.json` 是主文件，11.4 MB，自包含。它的顶层结构：

```
version                '1.0'
added_tokens           list，26 项
normalizer             dict，键 = ['type']            -> {"type": "NFC"}
pre_tokenizer          dict，键 = ['type', 'pretokenizers']
post_processor         dict
decoder                dict
model                  dict，键 = ['type', 'dropout', 'unk_token', ...]
```

`model` 里放词表和 merges。词表大小 **151,643**，merges **151,387** 条。
两者相差 256，正好是初始的字节表——**和手写版的结构完全一致**。

词表片段（原样）：

```
      id  token（repr）              字节
       0  '!'                      21
     100  '§'                      c2 a7
    1000  'atus'                   61 74 75 73
    5000  'Ġdifficult'             c4 a0 64 69 66 66 69 63 75 6c 74
   50000  'RESET'                  52 45 53 45 54
  100000  'ä¹Łæĺ¯'                 c3 a4 c2 b9 c5 81 ...
```

`Ġdifficult` 和 `ä¹Łæĺ¯` 看起来像乱码，其实是**字节到可打印字符的映射**。
JSON 存不下任意字节，所以 GPT-2 定义了一张表：

- 本来就可打印的字节映射到自己（`!` 到 `~`、`¡` 到 `¬`、`®` 到 `ÿ`）；
- 其余 68 个（控制字符、空格等）依次映射到 U+0100 往后。

于是空格 `0x20` → U+0120 `Ġ`，换行 `0x0A` → U+010A `Ċ`。
`ä¹Łæĺ¯` 是「也是」两个汉字的 6 个字节各自映射后的样子。

merges 表的前 8 条（原样）：

```
       0  Ġ Ġ
       1  ĠĠ ĠĠ
       2  i n
       3  Ġ t
       4  ĠĠĠĠ ĠĠĠĠ
       5  e r
       6  ĠĠ Ġ
       7  o n
```

**前几条几乎全是空格。** 因为训练语料里有大量代码，
而代码的缩进是连续空格——4 个空格、8 个空格是最高频的相邻对。
`ĠĠĠĠ ĠĠĠĠ` 就是 8 个空格合成一个 token。

### 七、特殊 token 不是学出来的

```
added_tokens 共 26 个：
  151643  '<|endoftext|>'          special=True
  151644  '<|im_start|>'           special=True
  151645  '<|im_end|>'             special=True
  151652  '<|vision_start|>'       special=True
  151655  '<|image_pad|>'          special=True
  ...

tok.eos_token = '<|im_end|>' (id 151645)
tok.pad_token = '<|endoftext|>' (id 151643)
```

它们的 id 都在 151643 之后，即**排在 BPE 学到的词表后面**——
是训练前硬加进去的。`<|vision_start|>` 这类给多模态用（L4.7），
`<|im_start|>` / `<|im_end|>` 给对话格式用。

### 八、chat template 就是字符串拼接

`tokenizer_config.json` 里有一个 4168 字符的 Jinja 模板。展开一次：

```
<|im_start|>system
你是一个助手。<|im_end|>
<|im_start|>user
风是什么？<|im_end|>
<|im_start|>assistant
```

92 个字符，编码成 20 个 token。前几个（原样）：

```
    0  id=151644   '<|im_start|>'
    1  id=8948     'system'
    2  id=198      'Ċ'           ← 换行
    3  id=56568    'ä½ł'          ← '你'
    4  id=101909   'æĺ¯ä¸Ģä¸ª'    ← '是一个'
    5  id=110498   'åĬ©æīĭ'       ← '助手'
    6  id=1773     'ãĢĤ'          ← '。'
    7  id=151645   '<|im_end|>'
```

**模板做的事只有三件**：插入角色标记、把多轮消息串起来、
在末尾放上「轮到模型说话了」的提示。

最后那个 `<|im_start|>assistant\n` 就是 `add_generation_prompt=True` 的产物，
本章实测它是 **22 个字符**。没有它，模型不知道该接话，
可能会继续扮演 user 或者直接输出 `<|im_end|>`。

::: warning 模板不匹配是一类静默故障
每个模型的模板都不同。用 A 模型的模板喂 B 模型，不会报错，
但模型看到的是没见过的格式，输出质量会明显下降，而且很难归因。

所以推理引擎从 `tokenizer_config.json` 读模板，而不是自己硬编码。
L0.1 走读过 vLLM 的这一段。
:::

### 九、padding、mask 与 position

普通 padded batch 会把不同长度的句子补齐成矩形张量；packed 输入是另一种组织方式。本章实测（两条中文）：

```
padding_side = right
  样本 0  len=9
    input_ids      [99208, 102021, 11319, 151643, 151643, 151643, 151643, 151643, 151643]
    attention_mask [1, 1, 1, 0, 0, 0, 0, 0, 0]
  样本 1  len=9
    input_ids      [99718, 110936, 111926, 101036, 11319, 14880, 100700, 66394, 1773]
    attention_mask [1, 1, 1, 1, 1, 1, 1, 1, 1]
  样本 0 的 position_ids: [0, 1, 2, 0, 0, 0, 0, 0, 0]
```

三个张量各自的职责：

- `input_ids`：补上 `pad_token_id`（这里是 `<|endoftext|>` 151643）。
  填充值必须是合法词表 ID；mask 和 loss 屏蔽仍需分别正确设置。
- `attention_mask`：1 表示真实 token，0 表示 padding。
  注意力会把 0 的位置屏蔽掉，所以真实 token **看不到** padding。
- `position_ids`：按 mask 累加得到。padding 位置的值不重要（这里填 0）。

对直接取 `logits[:, -1, :]` 的批量生成接口，使用 left padding 可让每条序列的最后一列都是有效 token。right padding 下必须按各自有效长度选择 logits，并正确维护 mask 与 position。使用 packed/ragged 输入的引擎可以不补齐；left padding 不是 decoder-only 架构本身的强制要求。

训练时用右 padding 没问题，因为 loss 会用 mask 把 padding 位置排除（L0.0b、L7.0b）。

## 工程实现 · 源码走读

手写版和真实实现的对应关系：

| 手写版（`bpe_from_scratch.py`） | 真实实现 | 位置 |
|---|---|---|
| `pre_tokenize()` 按字符类别分组 | 一条 `\p{L}`/`\p{N}` 正则 | `tokenizer.json` 的 `pre_tokenizer.pretokenizers[0].pattern.Regex` |
| `merges` 有序列表 | `model.merges`，151,387 条 | `tokenizer.json` |
| `vocab: id -> bytes` | `model.vocab`，字节经映射后存成字符串 | `tokenizer.json` |
| 无 | `normalizer: {"type": "NFC"}` | Unicode 规范化，手写版跳过了 |
| 无 | `added_tokens`，26 个特殊 token | 硬加，不参与 BPE |

真实实现是 Rust 写的（`tokenizers` 库），Python 侧只是绑定。
所以 `tokenizer.json` 是**跨语言的**：Python、Rust、C++、JS 的实现读同一个文件。
这也是为什么推理引擎（vLLM/SGLang）能直接用它，不需要 transformers。

## 前沿

| 方向 | 内容 |
|---|---|
| **词表大小的取舍** | 词表大 → 序列短（省算力、省 KV cache）但 embedding 与 lm_head 变大。Qwen3 15 万 / Llama 3 12.8 万 / GPT-2 5 万，趋势是变大 |
| **多语言与公平性** | 同样的意思，某些语言要 3–5 倍的 token，按 token 计费时成本直接差几倍。这是分词层面的公平性问题 |
| **数字的处理** | 单数字切分（Qwen3、Llama 3）vs 三位一组（部分模型）vs 从右往左分组。对算术能力有实测影响 |
| **tokenizer-free** | ByT5、MegaByte、以及 2024 年之后的 BLT（Byte Latent Transformer）尝试直接在字节上建模，用动态分块替代固定词表。代价是序列变长，需要额外的层次结构 |
| **词表扩展** | 给已训练模型加新语言的 token：新 embedding 行怎么初始化、要不要继续预训练。L7.5 会碰到 |
| **多模态占位 token** | `<|image_pad|>` 这类 token 在分词阶段只是占位，进模型前被替换成视觉特征（L4.7） |

## 陷阱

**1. 以为 tokenizer 是「按词切分」。** 它是在字节上做频率合并，
和语言学意义上的词没有必然关系。`' the'` 是一个 token，`the` 可能不是。

**2. 用 A 模型的 chat template 喂 B 模型。** 不会报错，输出质量静默下降。
永远从模型自己的 `tokenizer_config.json` 读。

**3. 忘了 `add_generation_prompt`。** 少了末尾那 22 个字符，
模型不知道轮到自己说话，可能继续扮演 user。

**4. 生成时用右 padding。** 模型会从 `<pad>` 后面开始写。
decoder-only 生成必须 left padding。

**5. 用没见过的文本之外的数据评价 tokenizer。**
重复单一句子的语料曾得到压缩比 36；这反映样本重复性，不能代表自然文本的压缩率。

**6. 假设 token 边界 = 字符边界。** 大量 token 是不完整的 UTF-8 序列。
L0.5 会给出一个真实的乱码案例。

**7. 按字符数估算 token 数。** 中文约 1.5 字符/token（Qwen3），
英文约 4 字符/token，代码和数字差异更大。要估就实际 encode 一遍。

## 自测题

<details markdown="1">
<summary>1. 为什么 merges 表的前几条几乎全是空格（<code>Ġ Ġ</code>、<code>ĠĠĠĠ ĠĠĠĠ</code>）？</summary>

**因为 BPE 合并的是训练语料里最高频的相邻对，而训练语料里有大量代码。**

逐步推：

1. BPE 第一轮统计所有相邻字节对的频率。
2. 代码文件里，缩进是连续空格。一个 4 空格缩进的 Python 文件，
   每一行开头都贡献若干个 `(空格, 空格)` 对。
3. 现代 LLM 的预训练语料里代码占比很高（通常 10–20%），
   所以 `(Ġ, Ġ)` 轻易成为全语料最高频的相邻对。
4. 合并出 `ĠĠ` 之后，`(ĠĠ, ĠĠ)` 又成了最高频 → 得到 `ĠĠĠĠ`（4 空格）。
5. 再一轮得到 8 空格。

**实际收益**：本章实测 `"a" + " "*20 + "b"` 只用 3 个 token，
7.33 字节/token，是所有样本里最高的。一个 4 空格缩进只花 1 个 token，
否则要花 4 个。对代码任务这是很大的节省。

**推论**：merges 表的开头部分基本反映了训练语料的构成。
一个中文占比高的 tokenizer，前几十条里会出现中文字节对。
</details>

<details markdown="1">
<summary>2. 同一个词 <code>the</code>，为什么句首和句中切法不同？这会带来什么问题？</summary>

**因为预切分把空格并入了后面那一块。**

`"the wind"` 预切分成 `['the', ' wind']`——注意第二块带前导空格。
训练时语料里绝大多数 `the` 都出现在句中，前面有空格，
所以 BPE 学到的是 `' the'`（带空格）这个 token。

句首的 `the` 没有前导空格，`' the'` 匹配不上，只能退回更碎的切法。
本章实测：

```
'the wind blows' -> 't' | 'he' | ' wind' | ' ' | 'b' | 'l' | 'ows'
```

**带来的问题有三个**：

1. **prompt 末尾有没有空格会改变切分。** `"翻译：the"` 和 `"翻译： the"`
   给模型的 token 序列不同，输出可能差别很大。这是 prompt 调试时的一个常见困惑源。
2. **前缀缓存的命中率。** 两个只差一个空格的 prompt，token 序列从那里开始就不同了，
   后面的块全部无法复用（L5.2）。
3. **约束解码。** 如果要求模型输出必须匹配某个语法，
   需要考虑同一个字符串有多种 token 化方式（L5.6）。

**工程上的应对**：有些 tokenizer 提供 `add_prefix_space` 选项，
在文本开头自动补一个空格。Qwen3 的 `tokenizer.json` 里
`"add_prefix_space": false`——它不这么做。
</details>

<details markdown="1">
<summary>3. 我要给一个英文为主的模型加中文能力，从分词器角度看要做什么、代价是什么？</summary>

**先量清楚问题有多大。** 本章实测 GPT-2 的中文效率是 1.29 字节/token，
Qwen3 是 4.50。也就是说同一段中文，GPT-2 要用 **3.5 倍**的 token。

后果是连锁的：

- 上下文窗口按 token 算，实际能装的中文内容少 3.5 倍；
- 按 token 计费时成本高 3.5 倍；
- 生成同样长度的中文，要走 3.5 倍的 decode 步数——而 decode 是带宽瓶颈（L0.0b 自测题 5），
  所以延迟也大致差 3.5 倍。

**做法是词表扩展**：

1. 在中文语料上训练一批新的 merges，挑出高频的中文 token；
2. 把它们追加到词表末尾（id 从原词表大小往后排）；
3. `tok_emb` 和 `lm_head` 各加对应的行。

**代价有三项，都要预算**：

| 代价 | 说明 |
|---|---|
| 新 embedding 行的初始化 | 随机初始化会让这些 token 一开始输出乱码。常见做法是用它拆开后各子 token 的 embedding 平均值初始化 |
| 必须继续预训练 | 新 token 的 embedding 需要在中文语料上训练才有意义。这不是「改个配置」能完成的 |
| 词表变大 | 15 万词表、$d=4096$ 时，embedding + lm_head 各 1.2 GB（bf16）。加 3 万个 token 要多约 0.5 GB |

**还有一个容易忽略的**：所有已有的 checkpoint、KV cache、
以及任何缓存了 token id 的东西全部作废，因为 id 空间变了。

**所以现在的主流做法是**：训练之初就用多语言语料训练分词器，而不是事后扩展。
</details>

<details markdown="1">
<summary>4. Qwen3 把每个数字切成单独的 token（1.00 字节/token），这看起来很浪费。为什么这么设计？</summary>

**为了让数字的切分与它出现的上下文无关。**

考虑不做这个约束的情况。BPE 会按频率合并数字：
`2024` 很常见，可能成为一个 token；`2025` 也常见；但 `2027` 可能被切成 `20 | 27`，
而 `1234` 可能被切成 `123 | 4`。

**同一个数字在不同上下文里的切分不一致**，会带来几个问题：

1. **算术**。做加法时模型需要按位对齐。如果 `456` 是一个 token 而 `457` 是 `4|57`，
   模型很难学到「个位相加」这种规则。
2. **数值比较**。`1000` 和 `999` 如果 token 数不同、切分方式不同，
   模型判断大小时用到的表示就不对齐。
3. **泛化**。训练时见过 `2024` 这个 token，推理时遇到 `2087` 只能拆开——
   两者的表示完全不同。

**代价**：数字确实变贵了，1.00 字节/token 意味着 16 位数字要 16 个 token。
本章实测 `"3.14159265358979"`：Qwen3 用 16 个 token，GPT-2 用 8 个。

**这是一个明确的取舍**：牺牲数字的压缩率，换取切分的一致性。
Llama 3 也采用了单数字切分。有些模型用三位一组（从右往左），
是另一种权衡——保留了一定压缩率，同时保持分组规则固定。

**验证方法**：`tok.encode("12345")` 和 `tok.encode("2345")`，
看后者是不是前者的后缀。单数字切分下必然是；按频率合并时通常不是。
</details>

<details markdown="1">
<summary>5. 一个 batch 里两条 prompt 长度是 10 和 100，padding 到 100。这次前向浪费了多少计算？有什么办法？</summary>

**先算浪费。** 前向的计算量大致与序列长度成正比（attention 部分是平方，先忽略）。

- 有效 token：$10 + 100 = 110$
- 实际计算：$2 \times 100 = 200$
- **浪费 45%**

如果 batch 里有 8 条长度分别是 10、10、10、10、10、10、10、100，
有效 70 + 100 = 170，实际 $8\times100=800$，**浪费 79%**。

attention 部分更糟，因为它是 $O(T^2)$：
$100^2$ vs $10^2$ 差 100 倍，padding 的代价被放大。

**办法一：按长度分桶（bucketing）。**
把长度接近的请求放进同一个 batch，padding 浪费就小了。
代价是要等——凑不齐一个桶就得等，尾延迟变差。

**办法二：不 padding。** 把所有序列首尾相接拼成一个长序列，
再用一个「每条序列从哪里开始」的索引数组告诉 attention 不要跨序列。
这叫 **packing** 或 varlen，是现在推理引擎的标准做法：

- FlashAttention 的 `varlen` 接口接受 `cu_seqlens`（累计长度前缀和）
- vLLM 的 batch 里根本没有 padding 概念，token 是连续排布的

**浪费降到 0**，代价是 attention kernel 更复杂（L3.2、L5.3）。

**办法三（训练侧）：sample packing。**
把多条短样本拼成一条固定长度的训练样本，用 mask 隔开。
注意 loss 的分母要按有效 token 数算（L7.0b）。

**所以「padding」主要是 transformers 这类通用库的做法**，
生产推理引擎基本都用 varlen。这也是 L0.1 里 vLLM 的输入张量
和 transformers 形状完全不同的原因。
