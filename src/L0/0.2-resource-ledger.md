## 为什么先算资源需求

读性能报告时，我们常看到“某模型每秒生成多少 token”，却不知道这个数字是否合理。
一个比较直接的起点是：先算模型要读取多少数据、执行多少运算，
再看机器完成这些工作大约需要多久。

本章用 Qwen3-1.7B 做例子，依次计算权重、KV cache 和主要矩阵运算的规模。
这些计算是一份简化模型，不是 GPU 执行轨迹。
它的作用是帮助你提出问题，例如“为什么显存增加了这么多”或“为什么 batch 增大后吞吐提高”，
而不是只靠配置文件就精确预测延迟。

先约定单位。GB 使用十进制，1 GB 等于十亿字节；GiB 使用二进制，
1 GiB 等于 2 的 30 次方字节。bf16 的每个元素占 2 字节。
后面的容量计算都先保留字节数，再换算显示，避免把 GB 和 GiB 混在一起。

## 第一步：从配置中找到维度

配置文件给出模型结构所需的数字。先读下面这份真实文件，
然后在表中找到各字段的作用：

{{srcfold:results/crater/raw/11_config.json}}

| 记号 | 配置字段 | 本例取值 | 含义 |
|---|---|---:|---|
| L | num_hidden_layers | 28 | Transformer 层数 |
| d | hidden_size | 2048 | 每个位置的隐藏向量维度 |
| h | num_attention_heads | 16 | query head 数量 |
| g | num_key_value_heads | 8 | key/value head 数量 |
| q | head_dim | 128 | 每个 head 的维度 |
| f | intermediate_size | 6144 | FFN 中间维度 |
| V | vocab_size | 151936 | embedding / 输出词表维度 |

这里的 query head 数与 KV head 数不同。GQA 让多组 query 共享较少的 K/V head，
所以计算 KV 时要用 g，而不是 h。这个区别既影响投影参数量，也影响缓存大小。

先不要把这些数字当作一张必须背下来的表。你需要学会的是：
看到一项矩阵操作，能从配置中找出输入维度和输出维度。

## 第二步：算一层要保存多少权重

对于一个没有 bias 的线性变换，输入维度为 a、输出维度为 b，
权重矩阵就有 a × b 个元素。先按这个规则计算 attention 的四个投影：

| 投影 | 输入维度 | 输出维度 | 参数个数 |
|---|---:|---:|---:|
| Q | d | hq | d × hq |
| K | d | gq | d × gq |
| V | d | gq | d × gq |
| O | hq | d | hq × d |

因此，一层的投影参数数为：

$$P_{attn}=2dhq+2dgq$$

本例代入 d=2048、h=16、g=8、q=128，可以分别检查 Q/O 与 K/V 的大小。
这一步只数投影矩阵，不把归一化等小参数算进去。

SwiGLU FFN 包含 gate、up、down 三个矩阵。前两个把维度从 d 提到 f，
最后一个从 f 降回 d，因此：

$$P_{ffn}=3df$$

把每层相加，再乘层数，就得到主干线性层的参数量。
embedding 有 Vd 个元素；如果 lm_head 与 embedding 共享权重，
计算独立参数时不应把它们重复算两次。

已有脚本给出的主要矩阵统计如下。它省略了一些归一化等小项，
所以应称为结构估算，不能代替完整的参数清单：

| 部分 | 估算参数个数 |
|---|---:|
| 28 层 attention 投影 | 352,321,536 |
| 28 层 FFN | 1,056,964,608 |
| 共享 embedding / lm_head | 311,164,928 |
| 合计 | 1,720,451,072 |

按 bf16 存储，以上主要权重约占 3.44 GB。这里约六成参数属于 FFN。
因此，即使你的优化目标是 attention，也不能忽略 FFN 对权重读取量的影响。

权重文件大小与加载后的显存占用还不是同一个量：重复存储、权重共享、
量化辅助数据、运行时 workspace 都可能改变两者的关系。
要确认共享，应同时看加载代码和加载后的张量，而不只看参数名。

## 第三步：算 KV cache 为什么越生成越大

权重通常由一批请求共享；KV cache 则描述某条请求已经处理过的上下文。
两个请求没有可复用前缀时，不能仅因它们使用同一模型就共用全部 KV。

对本例普通 GQA attention，一个 token 在一层需要保存：
g 个 K head，以及 g 个 V head，每个 head 有 q 个元素。
设每个元素占 s 字节，则所有层的缓存量为：

$$K_{token}=2L g q s$$

代入 28 层、8 个 KV head、每 head 128 个元素、每元素 2 字节：

$$K_{token}=2\times28\times8\times128\times2=114688\text{ bytes}$$

这等于 112 KiB，也约为 114.69 KB。一个长度为 4096 的上下文因此需要：

$$4096\times114688=469762048\text{ bytes}$$

也就是 448 MiB，约 0.47 GB。它只是一条请求的 KV。
如果 32 条请求都具有这么长的上下文，且不共享缓存，KV 总量约为 15.03 GB。

实际分页缓存会按块分配，末块还可能没有填满；引擎也可能提前预留缓存池。
所以“按 token 算出的有效数据量”“已经分配的块容量”和“GPU 总显存占用”
是三个不同的量。L5.2 会把它们与 block table、空闲块和引用计数联系起来。

这条公式不是所有架构的通用公式。量化 KV、滑动窗口、MLA 或其他状态表示，
都需要按实际存储布局重新推导，不能只把模型名字换掉继续使用。

## 第四步：算一次前向做多少运算

一个 M×K 矩阵乘 K×N 矩阵，要得到 M×N 个输出。
每个输出沿 K 维累加乘积。按一次乘法和一次加法各计一个 FLOP 的惯例，
主要运算量约为 2MKN。

设主干线性层参数量为 P_body，输出层参数量为 P_head，
prompt 长度为 S。只需生成一个首 token、也不请求 prompt logprobs 时，
可以按以下方式估算线性层计算：

$$F_{linear,prefill}\approx2SP_{body}+2P_{head}$$

第一项处理 prompt 的各个位置；第二项只为末位置计算输出 logits。
这是当前估算采用的执行需求。训练或需要其他位置 logits 的任务，必须另算。

attention 还要形成 Q 与 K 的匹配，并用这些权重汇总 V。
在普通 causal attention 的粗略模型中，计算量随 S 的平方增长。
这里用：

$$F_{attention,prefill}\approx2L S^2 hq$$

它省略了 softmax 等操作，也没有描述具体 kernel 的 tile、padding 和访存。
因此应把它读作数量级与主要项估算，而不是实际执行的精确指令数。

decode 则不同：每条请求本轮只处理一个新位置，仍需访问历史 K/V。
如果有 B 条等长请求，历史长度为 C，主要运算量可写成：

$$F_{decode}\approx2B(P_{body}+P_{head})+4L B C hq$$

这说明 batch 与上下文长度都会影响 decode，但影响的是不同部分：
batch 增大会增加本轮的新位置数，上下文变长则增加 attention 需要读取和处理的历史。

## 第五步：把运算量与读取量放在一起

算术强度（arithmetic intensity）是运算量除以数据搬运量，单位是 FLOP/byte。
它描述平均每搬一个字节，进行了多少运算。

在一个理想化的 decode 模型中，可以先把每步读取量估为：

$$D_{decode}\approx W+BCK_{token}$$

W 是本轮涉及的权重字节数，后一项是历史 KV 字节数。
这里假设一批请求能共享一次主要权重读取；实际缓存命中、重复读取和中间张量
还会改变真实流量，因此这个式子不是硬件计数器的替代品。

由此可以理解 batch 的作用。B 从 1 增加时，权重项不必按请求数等比例增长，
每份权重能参与更多位置的计算；但 KV 项仍随请求数增长。
所以 batch 可以提高总吞吐，却不会让收益无限线性增长。

也不要把总吞吐与单请求速度混淆。一次花 10 ms 为 32 条请求各生成一个 token，
总吞吐是 3200 token/s；单条请求仍要等这一轮约 10 ms，而不是 1/3200 秒。

## Roofline 给的是参照，不是完整延迟预测

假设机器的计算吞吐参照为 R FLOP/s，内存带宽参照为 BW byte/s。
完成 F 次运算和 D 字节搬运，分别需要的理想时间为 F/R 与 D/BW。
若把二者视为可以充分重叠，可用较大者作为时间下限的模型：

$$T_{model}=\max(F/R,\;D/BW)$$

这就是 roofline 分析的基本想法。若数据搬运项更大，优先检查访存；
若计算项更大，优先检查计算路径。但真实请求还包含调度、同步、通信及其他操作，
它们没有自动包含在这两个除法里。

本章的 R 和 BW 来自微基准，而非对所有工作负载都成立的物理上限。
因此更准确的叫法是“基于这些参照值的估计下限”。
如果后来出现更高的有效带宽，应先检查流量口径、缓存和参照测试，
不要马上认定硬件超过了物理极限。

## 引擎自己怎么算这本账

上面是解析模型。vLLM 启动时算同一本账，但有两处差别值得单独看，
因为它们正好是解析式估算算不出来的部分。

**第一处：一个 KV 页实际占多少字节。** `v1/kv_cache_interface.py:419`：

```python
@property
def unpadded_page_size_bytes(self) -> int:
    return self.num_heads * self.num_states * self.state_content_size_bytes

@property
def page_size_bytes(self) -> int:
    if self.page_size_padded is not None:
        assert self.page_size_padded >= self.unpadded_page_size_bytes
        return self.page_size_padded
    return self.unpadded_page_size_bytes
```

`num_states` 对普通 full attention 是 2（K 和 V），这和我们的公式一致。
但 `page_size_padded` 是一个逃生口：某些 attention 后端（例如需要特定对齐的
FlashInfer 或 MLA）要求页大小按硬件对齐补齐，**实际占用因此可能大于理论值**。
补齐量取决于后端实现，公式里没有这一项。

同文件 439 行的 `AttentionSpec` 派生出 `FullAttentionSpec`；
滑动窗口、Mamba 状态、跨层共享各有自己的子类。换句话说，
「KV cache」在当前引擎里不是一种结构，而是一族结构。L3.4 会展开。

**第二处：非 KV 的显存不是估的，是量出来的。**
`labs/L0/ledger.py` 里我们写了一个固定的 `overhead = 1.5e9`。
vLLM 的做法在 `v1/worker/gpu_worker.py:513`：

```python
self.available_kv_cache_memory_bytes = (
    self.requested_memory
    - profile_result.non_kv_cache_memory
    - cudagraph_memory_estimate_applied
)
```

`non_kv_cache_memory` 来自同文件 553 行的 `memory_profiling(...)`：
启动时真的按最大规模跑一遍 dummy forward，测出激活峰值。
之所以要测，是因为激活峰值取决于 batch 形状、attention 后端实现和算子融合情况，
没有闭式解。

第三项 `cudagraph_memory_estimate_applied` 是 CUDA Graph 捕获需要预留的显存池。
**开启 CUDA Graph 会占掉一部分本来可以给 KV 的显存**，
也就是用并发度换取更低的提交开销。L5.4 会回到这个取舍。

这一节可以概括成一句可复用的判断：解析模型给数量级和方向，
实测给出当前实现下的真值。两者都需要，因为只有模型会漏掉实现细节，
只有实测则说不出为什么。

## 广度对照：SGLang 把同一本账拆得更细

vLLM 用一个 `KVCacheSpec` 描述「一个 KV 页多大」。
SGLang 把同一件事放在 `model_executor/pool_configurator.py`，
需要处理的情况明显更多：

```python
class DefaultPoolConfigurator(MemoryPoolConfigurator):
    """Configurator for standard models: MHA, MLA, DSA, FP4.
       coeff = cell_size (bytes per token across all layers)"""

    def __init__(self, kvc: KVCacheConfigurator):
        # 1) 混合架构：Mamba 层不产生 KV，只有 full-attention 层算进 cell_size
        if mambaish := mambaish_config(kvc.model_config):
            effective_layer_ids = [i for i in mambaish.full_attention_layer_ids
                                   if kvc.layer_info.start_layer <= i < kvc.layer_info.end_layer]
            num_layers = len(effective_layer_ids)
        else:
            num_layers = kvc.layer_info.num_effective_layers

        self._cell_size = self._compute_cell_size(kvc, num_layers)

        # 2) 投机解码：draft 模型自己也要 KV，要把 cell_size 按比例放大
        if (kvc.spec_algorithm.is_eagle() or kvc.spec_algorithm.is_standalone()) \
                and not kvc.is_draft_worker:
            eagle_draft_num_layers = kvc.spec_aux_config.eagle_draft_num_layers
            ...
            # 3) DeepSeek DSA：稀疏 attention 的 indexer 也占显存，
            #    要先从 cell_size 里减掉再按 draft 层数缩放
            if is_deepseek_dsa(kvc.model_config.hf_config):
                target_indexer_size = self._compute_dsa_indexer_cell_size(...)
                target_kv_size = self._cell_size - target_indexer_size
```

我们那个一行的 `kv_bytes_per_token()`，在真实引擎里对应这一串条件分支。
原因是「每 token 的 KV 字节」已经不是一个常数：

| 情况 | 这本账怎么变 |
|---|---|
| Mamba / 线性 attention 混合层（L3.4） | 那些层不产生 KV，`num_layers` 要按 full-attention 层数算 |
| 滑动窗口层 | KV 有上界，不随上下文线性增长（SGLang 另有 `swa_max_total_num_tokens`） |
| 投机解码 EAGLE（L5.5） | draft 模型也要一份 KV，`cell_size` 要放大 |
| DeepSeek DSA 稀疏 attention | 除 KV 外还有 indexer 的显存 |
| MLA | K/V 压成一个低秩隐向量，`cell_size` 的结构不同 |
| pipeline 并行 | 有些层的 KV 在别的 PP stage 上，本地 `cell_size` 可能是 0 |

对照两家实现的用处在这里：一个公式足以应付常见情况，
读第二份实现才能看到边界条件长什么样，以及它们为什么存在。
L3.4、L5.5、L6.2 会分别回到表中的几行。

## 读这本账时容易出错的地方

**1. 拿厂商标称带宽当分母。** 标称与实测可能差 15%（L40S 标称 864 GB/s，
实测 649.7 GB/s）。判断「我的 kernel 达到了 78% 还是 92% 带宽」时，
这 15% 会改变你要不要继续优化的结论。分母应该用自己测的值。

**2. 把「AI TOPS」当算力。** 厂商宣传数字通常是稀疏（2:4）后的、
最低精度的理论峰值，与 bf16 稠密 GEMM 实际能到的数字可能差 4 倍以上。

**3. 忘了 KV 按 token 计费，不按序列。** 「支持 128 并发」这句话缺少条件，
必须同时说明上下文长度：在同样的显存下，54 条 4K 序列与 6 条 32K 序列大致相当。

**4. 以为 decode 慢是因为算力不够。** 用账本里的数字：crater 的机器平衡点是
152.7 FLOP/byte，而 4096 上下文的 decode 算术强度 batch=1 时是 1.12、
batch=32 时是 8.21，分别约为平衡点的 **0.7%** 和 **5.4%**。
这个配置离算力上限很远，加算力不改变它，除非同时增加带宽。
（这几个数在 `results/crater/ledger_qwen3_1.7b_ctx4096.json` 的
`arithmetic_intensity` 与 `machine_balance_flops_per_byte` 字段。）

## 自测：这些数字能说明什么

<details markdown="1">
<summary>模型权重能放进显存，为什么请求仍可能 OOM？</summary>

还需要 KV、激活、workspace、图捕获等空间。权重只是显存需求的一项。
应先判断是加载时失败，还是随着请求数或上下文增长才失败，
再分别检查固定开销与随请求增长的开销。
</details>

<details markdown="1">
<summary>把 KV 元素字节数减半，是否意味着每步延迟减半？</summary>

不意味着。只有 KV 相关的数据量在该模型中减半；权重、其他操作和转换开销仍然存在。
先估算 KV 在总量中的比例，再检查低精度路径需要哪些额外计算。
</details>

<details markdown="1">
<summary>一次 decode 的算术强度很低，是否所有 kernel 都是 memory-bound？</summary>

不是。整步汇总值把不同操作混在一起了。某些 kernel 可能受计算、同步或提交开销限制。
需要结合 L0.1 的 kernel 记录，再按操作拆分分析。
</details>

## 接下来读什么

L0.3 保持模型不变，比较两种 GPU。
重点不是记住谁快多少，而是练习把工作量、机器能力和真实调用时间放在同一张表里，
同时说清楚哪些差异已经观察到，哪些原因还没有被证明。
