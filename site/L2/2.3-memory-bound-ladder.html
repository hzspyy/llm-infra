优化阶梯 I：memory-bound 算子

逐步实现连续归约，比较原子操作、分块、向量化与数值累加的代价。

实测机器 crater (RTX 5090 D, sm_120) · CUDA 13.0.88 · torch 2.13.0前置 L1.1（带宽与 Little's Law）· L2.1（占用率与尾效应）

本章回答三个问题

  1. 一个归约 kernel 从 naive 到打满带宽，每一步各贡献多少？
  2. 教科书上的经典优化（warp shuffle、减少 barrier）在现代 GPU 上还有用吗？
  3. 手写 kernel 能打过 PyTorch 吗？

归约（reduction）是将张量元素按特定算子（如求和、求最大值）聚合成标量或低维结果的核心操作，也是典型的访存密集型（memory-bound）计算范式。本章以大规模连续 fp32 数组求和为例，从最原始的全局原子操作出发，沿经典优化阶梯逐级重构。我们将深入剖析不同优化手段在现代 GPU 架构下的真实增量与瓶颈迁移，并测定手写专用 kernel 对比框架通用算子的性能边界。

心智模型：把大量局部和逐级合并

机制拆解

v0：全局原子竞争同时影响性能与数值

__global__ void red_v0(const float* in, float* out, size_t n) {
    size_t i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) atomicAdd(out, in[i]);       // 6700 万个线程抢同一个地址
}

实测：82.897 ms，3.2 GB/s，只有带宽上限的 0.2%。

慢的原因是所有线程争抢同一个地址，硬件必须把 6700 万次加法串行化。

硬件性能计数器的交叉验证

单凭宏观耗时增加，尚无法严格区分究竟是「全局原子锁冲突」还是「全局访存未合并」导致的性能劣化。

在 L2.6 中，我们通过底层硬件性能分析器（NCU）直接采集了该 kernel 的底层计数器：v0 的 sector/request 恒等于 4（即 32 个连续 float 严格合并为 128 字节单次全局内存事务），证实访存合并处于完美状态；而 v0 的 L2 缓存访问事务数是其余版本的 9 倍，直接印证了数千万次原子“读-改-写”指令在 L2 缓存控制器端口严重拥塞串行的物理事实。同时，其指令发射利用率（Issue Slots Busy）仅有 0.08%，说明几乎所有 warp 都阻塞在等待原子更新的完成队列中。

该实现还存在数值错误：

✗ 结果 16777216，应为 67108864（相对误差 75.0%）

16777216=224。float 的尾数只有 24 位（含隐含位）， 累加器一旦到达 224，再加 1.0 就完全丢失—— 因为 224+1 在 float 里舍入回 224。

又慢又错，而且是同一个根因：串行累加。 并行化不只是为了快，它把误差从 O(N) 降到 O(logN)。

对照 v6（分层归约）的精度：

CPU fp64 参考       67108864.0
GPU v6 (fp32 分层)   67108864.0   相对误差 0.00e+00

分层归约天然是"成对求和"（pairwise summation）—— 每线程算局部和 → warp 内归约 → block 内归约 → 全局。 每一层的加数量级相近，误差不累积。

v1：253 倍提升，来自消除竞争

extern __shared__ float s[];
s[t] = (i < n) ? in[i] : 0.0f;
__syncthreads();
for (int stride = blockDim.x / 2; stride > 0; stride >>= 1) {
    if (t < stride) s[t] += s[t + stride];
    __syncthreads();
}
if (t == 0) atomicAdd(out, s[0]);        // 全局原子从 N 次降到 N/256 次

82.897 → 0.328 ms，253 倍。到达带宽上限的 49%。

v2 / v3：所测配置未显示额外收益

经典的《CUDA 归约优化》教程会告诉你接下来该做两件事：

  1. 最后一个 warp 用 shuffle：warp 内天然同步，不需要 __syncthreads
  2. 全程用 shuffle：barrier 从 log2(256)=8 次降到 1 次

实测：

版本 耗时 带宽 相对 v1
v1 共享内存树形 0.328 ms 819.6 GB/s —
v2 末 warp shuffle 0.327 ms 822.0 GB/s 1.00×
v3 全程 shuffle 0.327 ms 821.0 GB/s 1.00×

在这组测量中，三者的耗时差异很小。

原因：这个 kernel 是 memory-bound，卡在 49% 的带宽上。 barrier 和共享内存访问的时间被访存延迟完全掩盖了—— warp 在等 LDG 返回的时候，那点同步开销根本不在关键路径上。

经典教程的时代背景

NVIDIA 那份著名的归约优化 slides 写于 Fermi（2010）时代： 当时共享内存带宽相对显存带宽的优势没这么大，barrier 也更贵， 而且没有 __shfl_sync（Kepler 才引入）。

在那个硬件上，v1→v3 确实有明显收益。在 Blackwell 上没有。

这不是说 shuffle 没用——它在 compute-bound 或 归约维度很小 （比如 RMSNorm 里对 2048 个元素归约）的场景下仍然重要。 但对"扫一大块显存"这种任务，它优化的不是瓶颈。

应根据测量确定主要开销，再选择优化方向。

v4：每次访存指令读取更多元素

__global__ void red_v4(const float4* in, float* out, size_t n4) {
    ...
    if (i < n4) { float4 x = in[i]; v = x.x + x.y + x.z + x.w; }
    ...
}

只改了一件事：每线程读 16 字节（float4）而不是 4 字节。

0.327 → 0.166 ms，2 倍，直接冲到 96.3%。

为什么？回到 L1.1 的 Little's Law：

在途字节数=带宽×延迟=1674 GB/s×320 ns=536 KB

  • float 版：一个 warp 的 32 个线程各读 4 B → 合并成 128 B 一次事务。 要凑够 536 KB 需要 4288 个 warp 同时有未完成的 load。
  • float4 版：一个 warp 读 32 × 16 = 512 B（4 个 128 B 事务）。 只要 1072 个 warp。

而且更关键的是每条指令的收益：循环里的索引计算、边界检查、 累加，这些开销在 float4 版被摊薄了 4 倍。

这就是为什么 L1.1 的自测题 1 说"向量化访存是所有 memory-bound kernel 的第一步优化"。 本章给出了实测：2 倍。

在 SASS 层面，这一步把 LDG.E 变成了 LDG.E.128。

v5 / v6：最后的 4%

v5：grid-stride + 对齐波长

int bps = 0;
cudaOccupancyMaxActiveBlocksPerMultiprocessor(&bps, red_v5, 256, 0);
int wave = SMS * bps;                    // 实测 170 × 6 = 1020
red_v5<<<wave, 256>>>(...);              // 固定一个波，内部 grid-stride 循环

0.166 → 0.160 ms，+4%，达到 100.1%。

收益来自消灭尾效应（L2.1 实测：多 1 个 block 慢 17%）。 v4 用的是 grid = ceil(n4 / 256) = 65536 个 block = 64.3 个波， 最后那 0.3 个波是浪费。

v6：每线程 4 个独立累加器

0.160 → 0.160 ms，+0.2%（在噪声内）。

ILP 在这里没用，因为已经完全 memory-bound—— FADD 的延迟早就被访存延迟掩盖了。这组对照未观察到收益： L2.1 里 ILP 对 compute-bound kernel 很关键，这里没用。

在所测连续归约上比较 PyTorch 与专用实现

实现 耗时 带宽 占上限 结果
我们的 v6 0.160 ms 1679 GB/s 100.3% 67108864 ✓
torch.sum 0.188 ms 1431 GB/s 85.5% 67108864 ✓
torch.linalg.vector_norm 0.188 ms 1431 GB/s 85.5% 8192 ✓
x.mean() 0.187 ms 1433 GB/s 85.6% 1.0 ✓
torch.sum(dtype=float64) 0.890 ms 301 GB/s 18.0% 67108864 ✓

手写 60 行比 PyTorch 快 17%。 为什么？

因为 torch.sum 是通用的：要处理任意 shape、任意 stride、任意 dtype、 沿任意维度归约、还要支持 autograd。这些通用性在 kernel 里表现为 额外的索引计算和分支。本章版本只支持连续 fp32 全归约。

专用实现可以利用固定的输入条件减少通用处理开销。 比较时应同时列出它不支持的情况；本例不能推出手写 kernel 普遍快于框架算子。

最后一行显示，fp64 累加慢 4.7 倍（301 vs 1431 GB/s）。 读的字节数完全一样，但消费级 GPU 的 fp64 算力只有 fp32 的 1/64， 这提示高精度累加可能改变主要成本；确定瓶颈仍需结合相应指令吞吐和计数器。精度不是免费的（L4.2 会展开）。

工程实现 · 源码解析：LLM 里的归约在哪

1. RMSNorm 就是一个归约 + 逐元素

L0.1 的这段 kernel trace 中，累计有 952 次 rms_norm_kernel 调用 （28 层 × 2 个 norm × 17 步）。RMSNorm 的定义：

yi=xi1d∑jxj2+ϵ·wi

分母就是一个沿 hidden 维（2048）的归约。

但注意它和本章的归约规模完全不同：本章是 6700 万个元素归约成 1 个， RMSNorm 是每行 2048 个元素归约成 1 个，有 batch×seq 行。

规模不同，最优策略也不同： - 本章（超大单归约）：瓶颈是显存带宽，向量化是关键 - RMSNorm（大量小归约）：每行 2048 个元素正好一个 block 能装下， warp shuffle 在这里是有用的（归约树只有 log2(2048/32)=6 层）

vLLM 的 kernel 签名（L0.1 trace 原文）：

void vllm::rms_norm_kernel<c10::BFloat16, 8, 3, true>(
    c10::BFloat16*, c10::BFloat16 const*, ...)

模板参数 <dtype, 8, 3, true> 里的 8 很可能是向量化宽度 （8 个 bf16 = 16 字节 = LDG.128）——和本章 v4 是同一个手段。

2. fused_add_rms_norm：融合掉一次往返

trace 里还有 _C::fused_add_rms_norm（952 次）。它把 residual = residual + x; y = rmsnorm(residual) 合成一个 kernel。

收益是省掉一次显存往返：不融合的话，residual + x 要写回显存（4 MB）， rmsnorm 再读回来（4 MB）。融合后中间结果留在寄存器里。

按 L1.1 的带宽算，每次省 8 MB / 1674 GB/s ≈ 4.8 µs， 952 次就是 4.5 ms —— 但注意那是 17 步的总和，每步约 0.27 ms。 对照 decode 每步 4.3 ms 的墙钟，融合省下约 6%。

这就是 L2.7（算子融合）的基本盘。

3. attention 里的 online softmax 也是归约

FlashAttention 的核心是把 softmax 的两次归约（求 max、求 sum） 变成单遍在线更新，避免把 S×S 的中间矩阵写回显存。 那是 L3.1 的主题，但机制和本章同源：归约的代价在访存，不在算术。

工程实现 · 自己写一遍

阶梯的关键是每一步只改一件事，否则增量无法归因。

warp shuffle 的标准写法（v2 起复用）：

__device__ __forceinline__ float warp_reduce(float v) {
    #pragma unroll
    for (int off = 16; off > 0; off >>= 1)
        v += __shfl_down_sync(0xffffffff, v, off);
    return v;
}

__shfl_down_sync 直接在寄存器之间搬数据，不碰共享内存。 0xffffffff 是参与的线程掩码（全部 32 个）。 Volta 之后必须用带 _sync 后缀的版本——因为独立线程调度让 "warp 内隐式同步"不再成立。

两级归约的骨架（v3 起）：

__shared__ float warp_sums[32];
int lane = t & 31, wid = t >> 5;
float v = /* 本线程的局部值 */;
v = warp_reduce(v);                        // 第一级：warp 内
if (lane == 0) warp_sums[wid] = v;
__syncthreads();                           // 唯一的一次 barrier
if (wid == 0) {                            // 第二级：第 0 个 warp 归约各 warp 的结果
    v = (lane < (blockDim.x >> 5)) ? warp_sums[lane] : 0.0f;
    v = warp_reduce(v);
    if (lane == 0) atomicAdd(out, v);
}

这个骨架在几乎所有 LLM kernel 里都能见到（RMSNorm、softmax、LayerNorm）。 后续可用同样的结构分析这些归约算子。

验证不能省。本实验每个版本跑完都检查结果：

bool ok = std::fabs(got - (float)n) / (float)n < 0.01f;
if (!ok) snprintf(note, ..., "✗ 结果 %.0f，应为 %zu（相对误差 %.1f%%）", ...);

正是这个检查抓出了 v0 的精度灾难。只测速度不验结果的 benchmark 一文不值。

消融建议

改什么 你应该看到什么
把数据量从 256 MB 降到 1 MB 全部落进 L2（L1.1 实测 L2 带宽 5.5 TB/s），排名会变——小数据的最优实现和大数据不同
把 float4 改成 float2 带宽应该落在 v3 与 v4 之间，验证"向量宽度 → 在途字节"的线性关系
v5 的 grid 故意设成 wave + 1 应该看到 L2.1 那个 17% 的台阶
把 v6 的 4 个累加器改成 8 个 仍然没有提升（已 memory-bound），但寄存器用量会涨，用 -Xptxas -v 看
把 fp32 改成 bf16 输入 字节减半 → 理论上快 2 倍。但要注意 bf16 累加的精度（L4.2）
用 compute-sanitizer --tool racecheck 跑一遍 检查共享内存竞态。本机已装

第一项实验改变输入规模，检查最优 kernel 是否随之变化。这也是 autotuning 需要针对不同形状搜索的原因，见 L2.7。

③ v0 为什么算出 2²⁴：float 精度的硬边界

IEEE 754 单精度：1 位符号 + 8 位指数 + 23 位尾数（+1 位隐含）= 24 位有效精度。

当累加器达到 224=16777216 时，能表示的最小间隔（ULP）变成 224−23=2。 此时 224+1 舍入回 224 —— 加 1.0 不再产生任何效果。

所以 v0 的累加器卡死在 16777216，剩下的 5000 万次加法全部丢失。

验证（可以在任何 Python 里跑）：

>>> import numpy as np
>>> x = np.float32(2**24)
>>> x + np.float32(1) == x
True

这不是 GPU 的问题，也不是并发的问题，是 float 的固有限制。 分层归约之所以精确，是因为它让每次加法的两个操作数量级相近 （成对求和，误差 O(logN) 而非 O(N)）。

L4.2（数值系统）会展开讲：这正是为什么 LLM 的 norm 层要在 fp32 里算 （即使输入输出都是 bf16），以及为什么 attention 的累加必须是 fp32。

前沿

方向 内容
算子融合 归约往往夹在逐元素操作中间（RMSNorm = 归约 + 缩放）。融合能省掉整趟显存往返。vLLM 的 fused_add_rms_norm、torch.compile 的 Inductor 都在做（L2.7）
持久化 kernel + 单次 launch 多归约 把很多小归约合并成一个 kernel，减少 launch 次数（L1.4 实测每次 2.68 µs）。CUB 的 DeviceSegmentedReduce 是这条路
确定性归约 浮点加法不满足结合律，所以并行归约的结果依赖于线程调度。要位级可复现就要固定归约顺序，代价是性能。这是 batch-invariance 问题的一部分（L4.2）
在线归约（online softmax） 把"两遍扫描（求 max、求 sum）"变成单遍在线更新，是 FlashAttention 的数学基础（L3.1）
低精度累加的边界 bf16 只有 8 位尾数，28=256 个数就会开始丢精度。所以所有归约的累加器都用 fp32（L4.2）
CUB / Thrust 的通用实现 本章手写打过 torch.sum 17%，但 CUB 的 DeviceReduce 做了更激进的调优。值得作为下一个对照 未实测

陷阱

1. 照搬 2010 年的优化教程。 v1→v3 那三步在 Fermi 上有效， 在 Blackwell 上增量为零。硬件变了，瓶颈也变了。

2. 不验证结果只测速度。 v0 快不了也就算了，它结果还是错的， 而且错得很隐蔽（75% 相对误差，但看起来是个合法的数）。

3. 用串行累加求大数组的和。 float 在 224 处失效， double 在 253 处失效。任何超过百万元素的求和都要用分层归约。

4. 忘了向量化。 本章唯一有效的一步就是它，2 倍。 判断标准：每线程一次读的字节数是不是 16（float4 / LDG.128）。

5. 用 ceil(n/block) 当 grid。 会产生零点几个波的浪费。 用 cudaOccupancyMaxActiveBlocksPerMultiprocessor 算出波长再对齐。

6. 以为 ILP 总有用。 本章 v6 的多累加器增量是 0.2%（噪声内）， 因为已经完全 memory-bound。ILP 只在 compute-bound 时有意义（L2.1）。

7. 随手加 dtype=float64 提精度。 实测慢 4.7 倍。 消费级卡的 fp64 算力只有 fp32 的 1/64。要精度应该用 fp32 累加 + 分层归约， 或者 Kahan 求和。

自测题

1. 我的归约达到了 819 GB/s，占带宽上限 49%。下一步该做什么？

先算每线程读多少字节。 如果是 4 字节（float）， 那答案就是向量化——本章实测这一步值 2 倍。

判断方法：

每 warp 在途字节=32×每线程字节

对照 L1.1 的带宽-延迟积 536 KB，算出需要多少 warp：

  • 每线程 4 B → 每 warp 128 B → 需要 4288 个 warp
  • 每线程 16 B → 每 warp 512 B → 需要 1072 个 warp

全卡最多常驻 8160 个 warp（170 SM × 48）。4288 看似够， 但实际上不是每个 warp 时刻都有未完成的 load（还要算索引、做累加）， 所以边际上不足。向量化把需求降到 1/4，就宽裕了。

不要去优化 barrier 或 shuffle —— 本章实测那些增量为零。

2. 为什么 warp shuffle 在本章没用，但在 RMSNorm 里有用？

因为归约的规模不同。

  • 本章：6700 万个元素 → 1 个。绝大部分时间在扫显存， 归约树本身只占极小比例。优化它等于优化一个不到 1% 的部分。
  • RMSNorm：每行 2048 个元素 → 1 个，有 batch×seq 行。 2048 个元素只有 8 KB，一个 block 一次就读完了， 之后的归约树反而是主要成本。此时 shuffle（省掉 barrier）就有意义。

一般规律：

归约树的开销扫数据的开销∝log(每 block 元素数)每 block 元素数

每 block 处理的元素越少，归约树占比越高，shuffle 越重要。

这也是"最优 kernel 依赖于问题规模"的一个实例—— 所以 cuBLAS/cuDNN 要为不同规模准备不同的 kernel 并做 autotuning。

3. 我需要位级可复现的归约结果（同样输入永远同样输出）。本章的 v6 能做到吗？

不能，严格说来。

v6 的结果依赖于： - 每个 block 处理哪些元素（由 gridDim 决定，而 grid 又依赖占用率） - 各 block 的 atomicAdd 到达顺序（由调度决定，不确定）

浮点加法不满足结合律：(a+b)+c≠a+(b+c)。所以顺序变了结果就可能变。

本章实测 v6 结果精确等于 67108864，是因为输入全是 1.0（特殊情况）。 换成随机数就会看到抖动。

要位级可复现，有三条路： 1. 固定归约顺序：不用 atomicAdd，改成两阶段 kernel—— 第一阶段每个 block 写自己的部分和到固定位置，第二阶段按固定顺序求和。 代价是多一次 kernel launch。 2. 用整数或定点累加：整数加法满足结合律。 3. Kahan / 补偿求和：减小误差但不保证位级一致。

这个问题在 LLM 推理里很实际：同样的 prompt 在不同 batch 里 可能得到不同的输出，因为归约顺序变了。这就是 batch-invariance 问题，L4.2 会展开。

4. 手写打过 torch.sum 17%。这是不是意味着 PyTorch 的实现很差？

不是。 这是通用性的代价，是有意的设计取舍。

torch.sum 必须处理：任意 shape、非连续 stride、任意 dtype（含复数）、 沿任意维度子集归约、keepdim、autograd 反向、以及各种边界情况。 这些在 kernel 里表现为额外的索引计算、分支、和更保守的向量化判断 （不能假设 16 字节对齐）。

我们的 v6 只做一件事：连续 fp32 全归约，还假设了对齐。

这正是专用 kernel 存在的价值： - FlashAttention 之所以快，是因为它只做 attention，不做通用矩阵乘 - DeepGEMM 之所以快，是因为它只做 fp8 分组 GEMM - vLLM 的 rms_norm_kernel 之所以快，是因为它只做 RMSNorm

代价是维护成本：每个专用 kernel 都要为每种 dtype、每种架构单独写和调优 （L2.2 实测 libcublasLt.so 里有 5000+ 个 cubin）。 这就是 Triton / TileLang 这类 DSL 试图解决的问题（L2.5）。

5. 如果输入是 bf16 而不是 fp32，本章的结论要怎么改？

两处要改，一处不变。

(1) 理论下界减半。 同样的元素数，字节数减半 → 时间下界减半。 所以 256 MB 的 bf16 数组（1.34 亿个元素）下界仍是 0.160 ms， 但如果是同样 6700 万个元素的 bf16（128 MB），下界就是 0.080 ms。

(2) 向量宽度要重算。 float4 是 16 字节。bf16 要装满 16 字节需要 8 个元素——所以用 int4 或自定义的 bfloat16x8。 L0.1 trace 里 vLLM 的 rms_norm_kernel<c10::BFloat16, 8, 3, true> 那个 8 很可能就是这个宽度。

(3) 累加器必须仍是 fp32。 bf16 只有 8 位尾数， 28=256 个数就开始丢精度——比 fp32 的 224 早了 65536 倍。 读用 bf16，算用 fp32，这是所有 LLM kernel 的铁律（L4.2）。

不变的是：向量化仍然是最重要的一步，barrier/shuffle 优化仍然没用。
