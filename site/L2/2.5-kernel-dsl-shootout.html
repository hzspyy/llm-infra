现代 kernel 编写栈横评

对照 CUDA、Triton 与其他 kernel 编写栈，区分已测结果、编程接口和未验证路线。

实测机器 crater (RTX 5090 D, sm_120) · Triton 3.7.1 · TileLang 0.1.12 · Helion 1.4.0 · CUTLASS-DSL 4.6.2数据日期 2026-09-10前置 L2.4（手写 CUDA 的 GEMM 阶梯）· L2.2（编译工具链）

本章回答三个问题

  1. 现代 kernel DSL 声称"几十行 Python 拿到接近 cuBLAS 的性能"。是真的吗？
  2. 它们各自的代价是什么？代码量、编译时间、可控性怎么权衡？
  3. 这些 DSL 到底生成了什么？它们做对了我手写时没做的哪件事？

DSL 是领域专用语言。这里的几种 DSL 都用于描述 GPU 计算， 但把不同的决策交给了编译器：有的要求你指定 tile 和流水， 有的还会自动搜索这些参数。本章用同一个 GEMM 比较这些分工， 并检查生成代码。表中的表现只代表列出的实现和配置，不是语言本身的固定排名。

心智模型：三个轴上的取舍

为什么 DSL 能赢：看它生成了什么

L2.4 的 v6 尚未实现以下优化：

手段 本章实现
双缓冲 / 软件流水 ✗
cp.async 异步拷贝 ✗
XOR swizzle ✗（只用了 padding）
tile 尺寸 autotuning ✗（写死 128×128×32）

去看 Helion 生成的 PTX（Triton 缓存目录里）：

=== 里面的 tensor core 指令
     64 mma.sync.aligned.m16n8k16.row.col.f32.bf16.bf16.f32

=== 异步拷贝与同步
      4 cp.async.bulk.tensor.2d.shared      ← TMA！
      2 cp.async.bulk.commit_group
      2 cp.async.bulk.wait_group.read
      2 barrier.arrive.expect_tx.shared     ← mbarrier 异步同步
      1 barrier.init.shared
      1 barrier.try_wait.parity.shared

cp.async.bulk.tensor.2d.shared 就是 TMA（Tensor Memory Accelerator）： 把整块 2D tile 的搬运交给专用硬件，不占寄存器、不阻塞计算。 配合 barrier.arrive.expect_tx 这套 mbarrier 机制做异步流水。

这里看到了与手写版本相同的 mma 指令类型，以及不同的数据搬运与同步安排。 这说明搬运和流水值得优先检查，但仅凭指令列表不能把全部性能差距归到它们。 还要考虑 tile、寄存器、调度和编译配置的差异。

从 12 行 Python 到 857 行 PTX

Helion 的 kernel 只有 12 行：

@helion.kernel(static_shapes=True)
def helion_gemm(x: torch.Tensor, y: torch.Tensor) -> torch.Tensor:
    m, k = x.size()
    k2, n = y.size()
    out = torch.empty([m, n], dtype=torch.promote_types(x.dtype, y.dtype),
                      device=x.device)
    for tile_m, tile_n in hl.tile([m, n]):          # ← 只声明"要分块"
        acc = hl.zeros([tile_m, tile_n], dtype=torch.float32)
        for tile_k in hl.tile(k):
            acc = torch.addmm(acc, x[tile_m, tile_k], y[tile_k, tile_n])
        out[tile_m, tile_n] = acc.to(out.dtype)
    return out

注意它没有说 tile 多大——hl.tile 只表达"这一维要分块"， 具体尺寸、流水级数、warp 数、索引方式全部交给自动调优器搜索。

生成的产物逐级展开：

_helion_helion_gemm.source     19 041 B   Triton 源码（Helion 生成的）
_helion_helion_gemm.ttir       108 行     Triton IR
_helion_helion_gemm.ttgir      148 行     TritonGPU IR（带 layout）
_helion_helion_gemm.llir     1 047 行     LLVM IR
_helion_helion_gemm.ptx        857 行     PTX
_helion_helion_gemm.cubin   52 400 B     SASS

12 行 Python → 857 行 PTX。 中间隔着两个编译器（Helion→Triton，Triton→LLVM→PTX）。

代价一：编译时间差三个数量级

DSL 首次编译 做了什么
Triton（手指定 tile） 0.5 s 只编译你给的那一组参数
TileLang ~1 s 同上，但多一层 TVM 风格的调度变换
Helion 492.8 s 自动调优 752 个配置，遗传算法搜索

Helion 的调优日志（原文）：

[306s] Fitting surrogate: 752 points, 752 targets
[306s] Copy 3 finish because of no improvement
[307s] Generation 10 starting: 53 neighbors, 3 active search path(s)
Generation 10: precompiling 100% ━━━━━━━━━━━ 55/55  15.3 configs/s

它在搜的参数包括（从日志里摘的）：

block_sizes, range_num_stages, range_multi_buffers, range_flattens,
load_eviction_policies, num_warps, num_stages,
indexing = ['pointer', 'tensor_descriptor', 'tensor_descriptor'],
pid_type = 'flat', epilogue_subtile = 2

indexing = 'tensor_descriptor' 就是选择用 TMA（tensor descriptor 是 TMA 的 API）。 这个选择是搜出来的，不是人写的。

8 分钟的编译时间意味着什么

对离线的、形状固定的场景（比如一个固定尺寸的模型层）， 调一次用一年，8 分钟完全可以接受，而且结果缓存下来。

对在线服务就是灾难：LLM 推理的 GEMM 形状随 batch 变化， 每个新形状都要重调 8 分钟，服务根本起不来。

所以生产引擎的做法是： - 预先离线调好一批常见形状，把配置固化进代码（vLLM 的 configs/*.json 就是） - 或者用 cuBLAS 这种运行时启发式选择（快但未必最优） - 或者像 cuBLASLt 那样用 nvjet 做轻量 JIT（L2.2 发现的）

代价二：Triton 手调 tile 只有 70.8%

Triton 的 34 行里我写死了 tile：

BM, BN, BK, GROUP = 128, 256, 64, 8
...
num_stages=3, num_warps=8

结果 178.4 TFLOPS，只有 70.8%。

而 torch.compile 用的也是 Triton，但它跑了 autotune，实测日志：

triton_mm_9  0.6221 ms 100.0%  BLOCK_M=64,  BLOCK_N=128, BLOCK_K=32, num_stages=3, num_warps=4
triton_mm_11 0.6226 ms  99.9%  BLOCK_M=64,  BLOCK_N=128, BLOCK_K=64, num_stages=3, num_warps=4
mm           0.6308 ms  98.6%  ← ATen 的 cuBLAS 后端
triton_mm_16 0.6649 ms  93.6%  BLOCK_M=128, BLOCK_N=128, BLOCK_K=32, num_stages=3, num_warps=4

最优是 64×128×32, num_warps=4，而我猜的是 128×256×64, num_warps=8。 猜错的代价是 23%。

而且注意：autotune 选出的 Triton kernel（0.6221 ms）比 cuBLAS（0.6308）快 1.4%。 这是 Inductor 默认会同时评估 ATen 与 Triton 两条路的原因。

Triton 不是"比 cuBLAS 慢"，是"不调参就比 cuBLAS 慢"。

四种 DSL 的抽象层次

DSL 你要写什么 编译器负责什么 抽象层次
CUDA C++ 线程索引、共享内存布局、同步、指令选择 寄存器分配、指令调度 最低
CUTLASS / CuTe-DSL tile 层次结构、layout 代数 布局变换、指令选择、流水 低（但抽象好）
Triton block 级的张量操作、显式 tile 尺寸 线程映射、smem 布局、同步、swizzle 中
TileLang tile 操作 + 显式流水级数 同上 + 自动 layout 推导 中高
Helion 只说"这一维要分块" 全部，包括 tile 尺寸搜索 最高

抽象越高，写得越少、越容易接近最优，但你越不知道它做了什么，也越难在它做错时干预。

TileLang 的 18 行正好在中间：

with T.Kernel(T.ceildiv(N, BN), T.ceildiv(M, BM), threads=threads) as (bx, by):
    As = T.alloc_shared((BM, BK), "bfloat16")
    Bs = T.alloc_shared((BK, BN), "bfloat16")
    Cl = T.alloc_fragment((BM, BN), "float")       # fragment = 寄存器块
    T.clear(Cl)
    for k in T.Pipelined(T.ceildiv(K, BK), num_stages=stages):   # ← 显式流水
        T.copy(A[by * BM, k * BK], As)             # 自动生成 cp.async
        T.copy(B[k * BK, bx * BN], Bs)
        T.gemm(As, Bs, Cl)                         # 自动选 mma 与布局
    T.copy(Cl, C[by * BM, bx * BN])

它明确区分了 shared / fragment 两种存储（对应 L1.1 的共享内存与寄存器）， 显式写出流水级数（T.Pipelined(..., num_stages=3)）， 但把 layout 推导、swizzle、指令选择交给编译器。

这个抽象层次和你在 L2.4 手写时的思考层次是对齐的—— 所以它最容易理解"编译器替我做了什么"。

工程实现 · 源码走读：真实项目怎么选

1. vLLM：Triton + CUDA 混用

L0.1 的 kernel trace 里能看到两类 kernel 共存：

_penalties_kernel                                  ← Triton（L0.1 原始现场 ⑥ 反汇编过）
vllm::rms_norm_kernel<c10::BFloat16, 8, 3, true>   ← 手写 CUDA
vllm::reshape_and_cache_flash_kernel<...>          ← 手写 CUDA
flash::flash_fwd_splitkv_kernel<...>               ← CUTLASS/CUTE
cutlass_80_tensorop_bf16_s16816gemm_...            ← CUTLASS

选择规律很清楚：

  • 形状多变、逻辑复杂、性能不极端（采样惩罚、各种 mask）→ Triton
  • 热路径、形状固定、要榨干性能（RMSNorm、KV 写入）→ 手写 CUDA
  • GEMM / attention → CUTLASS 或专用库

2. DeepSeek 用 TileLang

TileLang 在近期的 DeepSeek 开源里被使用。原因可以从本章的数据推测： 18 行拿到 81.5%，编译只要 1 秒——对需要为大量 MoE 形状生成 kernel 的场景， 这个"性能/开发成本/编译时间"组合很划算。

3. FlashAttention-4 用 CuTe-DSL

FA4 完全用嵌入 Python 的 CuTe-DSL 写，没有 C++ 部分。 它的卖点是编译比 C++ CUTLASS 模板快 20–30×—— 对照 L2.2 实测的"预处理膨胀 1761 倍"，这个提速的来源就清楚了： 跳过整个 C++ 前端。

本章没有测 CuTe-DSL

nvidia-cutlass-dsl 4.6.2 已装在本机，但写一个完整的 CuTe-DSL GEMM 需要理解 layout algebra（Layout、Tiler、TiledMma 等概念）， 代码量和学习曲线都远超其他三家。

本站把它标为待补未实测。 它的定位很清楚：最接近 CUTLASS C++ 的表达力 + Python 的迭代速度， 适合要完全控制流水和布局的场景（比如 FA4 那种要手动做 exp() 软件仿真的）。 L3.2 讲 FlashAttention-4 时会回到它。

工程实现 · 自己写一遍

三个 DSL 的关键差异，浓缩成各自最核心的几行。

Triton：你管 tile，编译器管线程

acc = tl.zeros((BM, BN), dtype=tl.float32)      # 累加器必须 fp32（L4.2）
for k in range(0, tl.cdiv(K, BK)):
    am = tl.load(a_ptr, mask=offs_k[None, :] < K - k * BK, other=0.0)
    bm = tl.load(b_ptr, mask=offs_k[:, None] < K - k * BK, other=0.0)
    acc = tl.dot(am, bm, acc)                   # ← 一行就是 tensor core
    a_ptr += BK * sak
    b_ptr += BK * sbk

tl.dot 一行就展开成 64 条 mma.sync（实测 PTX 里数出来的）。 你看不到共享内存、看不到 __syncthreads、看不到 warp 映射—— 那些是编译器的事。

但你必须自己写 mask（边界处理）和指针递增， 还有那段 L2 友好的 block 重排（GROUP 那几行）。

TileLang：显式区分 shared / fragment，显式写流水

As = T.alloc_shared((BM, BK), "bfloat16")     # 共享内存
Cl = T.alloc_fragment((BM, BN), "float")      # 寄存器（fragment）
for k in T.Pipelined(T.ceildiv(K, BK), num_stages=3):    # 3 段流水
    T.copy(A[by * BM, k * BK], As)
    T.gemm(As, Bs, Cl)

T.Pipelined(..., num_stages=3) 对应 L2.4 里我没做的"双缓冲"， 对应 CUTLASS kernel 名里的 x3（L2.2 走读过）。一个参数替代几十行手写代码。

Helion：连 tile 尺寸都不写

for tile_m, tile_n in hl.tile([m, n]):        # 不说多大
    acc = hl.zeros([tile_m, tile_n], dtype=torch.float32)
    for tile_k in hl.tile(k):
        acc = torch.addmm(acc, x[tile_m, tile_k], y[tile_k, tile_n])

注意内层直接用了 torch.addmm —— Helion 的 kernel 体里可以写普通的 PyTorch 算子， 它会被翻译成 tile 级的操作。这是它 12 行的原因。

一个实操坑：Helion 要求 kernel 引用的名字是全局的，不能是闭包变量。 本实验第一版把 import helion.language as hl 放在函数里，报：

ClosuresNotSupported: A closure (('hl',)) was found in the kernel.

把 import 和 kernel 定义都提到模块级才能用。

消融建议

改什么 你应该看到什么
Triton 的 BM,BN,BK 改成 64,128,32（Inductor 选的最优） 应该从 178 涨到接近 218 —— 验证"猜 tile 的代价是 23%"
Triton 的 num_stages 从 3 改成 1 流水消失，性能应该明显下降（回到接近 L2.4 v6 的水平）
改成非方阵（如 M=1, N=6144, K=2048，模拟 decode） 所有 DSL 的优势会缩小——GEMV 是另一个问题（L2.4 自测题 4）
用 HELION_AUTOTUNE=0 或指定 config 跳过调优 编译从 493 s 降到几秒，但性能会掉多少？
对比各 DSL 生成的 .ttgir 里的 layout 标注 看它们对同一个问题选了什么 layout（L0.1 原始现场 ⑥ 解释过 #blocked）

四点：

  1. 最优是 64×128×32, num_warps=4，而我在 Triton 版里猜的是 128×256×64, num_warps=8 —— 猜错的代价 23%。
  2. 最优的 Triton kernel（0.6221）比 cuBLAS（0.6308）快 1.4%。 所以 Inductor 默认同时评估两条路是有意义的。
  3. 最差与最好只差 7.7%（0.6697 vs 0.6221）。tile 参数在合理范围内不敏感， 但"合理范围"要靠搜索找到。
  4. ALLOW_TF32=False：因为输入已经是 bf16，不涉及 TF32。
③ Helion 生成的 PTX 里有什么 
PTX 头部：
    .version 9.1
    .target sm_120a                        ← 架构专属（L2.2 讲过 a/f/裸的区别）

tensor core 指令：
     64 mma.sync.aligned.m16n8k16.row.col.f32.bf16.bf16.f32
        ↑ 和 L2.4 手写的完全一样

异步搬运与同步：
      4 cp.async.bulk.tensor.2d.shared     ← TMA（我手写时没有）
      2 cp.async.bulk.commit_group
      2 cp.async.bulk.wait_group.read
      2 barrier.arrive.expect_tx.shared    ← mbarrier 事务计数
      1 barrier.init.shared
      1 barrier.inval.shared
      1 barrier.try_wait.parity.shared
      4 barrier

cp.async.bulk.tensor.2d.shared 是 TMA 指令：一条指令搬一整块 2D tile， 由专用硬件（TMA engine）执行，不占 CUDA core、不占寄存器。

barrier.arrive.expect_tx.shared 是 mbarrier：不是普通的 __syncthreads， 而是带"事务计数"的异步屏障——等的是"这块数据搬完了"而不是"所有线程到齐了"。 这套机制才让真正的异步流水成为可能。

这正是 L2.4 结尾我列的两个缺口。 DSL 自动生成了它们。

前沿

DSL 定位与现状
Triton 事实标准。PyTorch Inductor 的后端，vLLM/SGLang 大量使用。跨 NVIDIA/AMD。弱点是对新硬件特性（TMA、wgmma、tcgen05）的支持滞后于 CUTLASS
CuTe-DSL NVIDIA 官方，CUTLASS 4.x 的 Python 前端。FlashAttention-4 完全用它写，编译比 C++ 模板快 20–30×，保留寄存器分配与流水调度的控制权。只支持 NVIDIA
TileLang TVM 血统，本章实测 18 行 81.5%。近期 DeepSeek 的开源里在用。跨后端（LLVM/MLIR）
Helion PyTorch 官方的更高层 DSL，编译到 Triton。本章实测 12 行 86.3%，但要 8 分钟自动调优
ThunderKittens 2.0 于 2026-01 发布，支持 Blackwell + MXFP8/NVFP4。以 16×16 tile 为基本单位。本机未装未实测
cuda.compute (CCCL) NVIDIA 的 Python 并行原语库，2026 登顶过 GPU MODE 排行榜
AI 写 kernel 的现状 KernelBench 上前沿模型对 Triton 的 pass@1 尚可，但对 TileLang 低于 20%、ThunderKittens 低于 2% —— 因为公开语料太少（不足 100 万 token）未实测

最后一行对你有直接意义：越新的 DSL，能问 AI 的东西越少，越要读官方 example。

陷阱

1. 拿"不调参的 Triton"跟 cuBLAS 比。 本章实测差 23%。 Triton 的性能高度依赖 tile 参数，必须 autotune。

2. 以为高层 DSL 一定慢。 12 行 Helion 打过 400 行手写 CUDA 50%。

3. 忽略编译时间。 Helion 493 秒。对形状多变的在线服务是致命的。

4. Helion 的 kernel 里用闭包变量。 报 ClosuresNotSupported。 import 和 kernel 定义都要在模块级。

5. 只看性能不看生成的代码。 本章最有价值的一步是去 PTX 里 数 cp.async.bulk.tensor 和 mma.sync —— 那才知道它凭什么快。

6. 以为 DSL 免除了硬件知识。 恰恰相反：TileLang 要你写 num_stages， Triton 要你选 BLOCK_M/N/K 和 num_warps。 不懂 L1/L2 那些硬件事实，你连参数该往哪调都不知道。

7. 用方阵 GEMM 的结论去推 decode。 M=1 时全部失效（L2.4 自测题 4）。

自测题

1. 我的项目要给 20 种不同形状的 GEMM 写 kernel，形状在编译期已知。选哪个 DSL？

TileLang 或 Helion，取决于你有多少调优时间预算。

  • 形状编译期已知 → 可以离线调优，Helion 的 493 秒 × 20 = 2.7 小时，一次性成本，可接受。
  • 要求当天出结果 → TileLang：18 行、1 秒编译、81.5% 性能，够用。
  • 不要选手写 CUDA：本章实测它反而最慢，而且 20 种形状 × 400 行 = 8000 行要维护。

关键判断：调优是一次性成本还是每次部署都要付？ 前者选高抽象 + 自动调优，后者选中抽象 + 手工参数。

还有一个选项：先用 torch.compile(mode="max-autotune") 试一下。 本章实测它 0.633 ms（86.2%），而且你一行 kernel 都不用写。 在决定手写之前，先确认自动方案确实不够。

2. Helion 生成的 PTX 里有 TMA（cp.async.bulk.tensor），但 L1.2 说 sm_120 不支持 Hopper 的特性。矛盾吗？

不矛盾。TMA 与 wgmma/tcgen05 是不同的特性，支持范围不同。

L1.2 实测确认 sm_120 不支持： - wgmma.mma_async（Hopper 的 warp-group MMA） - tcgen05.mma + TMEM（数据中心 Blackwell）

但 TMA（cp.async.bulk.tensor）在 sm_120 上是支持的 —— 本章的 PTX 就是证据（.target sm_120a 且含 4 条 cp.async.bulk.tensor.2d.shared， 而且这个 kernel 确实跑出了 217 TFLOPS）。

一般教训：不要把一代架构的特性当成一个整体。 「Blackwell 有什么」这个问题必须逐条问，而且要以编译器/实测为准， 不是以宣传材料为准。L1.2 的 tcgen05_probe.cu 就是这类判决性实验的模板。

3. 我的 Triton kernel 只有 cuBLAS 的 70%。在调 tile 之前，我应该先检查什么？

按顺序：

(1) 累加器是不是 fp32。 tl.zeros((BM, BN), dtype=tl.float32)。 如果写成 bf16，精度会崩（L2.3 实测 float 在 224 处就失效，bf16 在 28）。

(2) 有没有 L2 友好的 block 重排（GROUP_M）。 默认的行主序 block 编号 会让同时执行的 block 读完全不同的 A 行和 B 列，L2 命中率很低。 本章的 Triton 版有这段（GROUP = 8），Inductor 选的也是 GROUP_M=8。

(3) num_stages 是不是 ≥ 3。 这决定软件流水的深度，对应 L2.4 里我缺的双缓冲。 Inductor 的最优配置是 num_stages=3。

(4) 然后才是 tile 尺寸。 而且不要猜，要扫：

@triton.autotune(configs=[
    triton.Config({'BM':64,'BN':128,'BK':32}, num_stages=3, num_warps=4),
    triton.Config({'BM':128,'BN':64,'BK':32}, num_stages=3, num_warps=4),
    ...
], key=['M','N','K'])

(5) 最后去看生成的 PTX：grep mma.sync 确认真的用了 tensor core， grep cp.async 确认真的异步搬运了。 本章实测：这一步能直接告诉你"编译器有没有做到你以为它做的事"。

4. 既然 DSL 这么好，为什么 vLLM 里还有那么多手写 CUDA kernel？

三个原因，L0.1 的 kernel trace 里都能看到证据。

(1) 有些算子不是"张量运算"。 reshape_and_cache_flash_kernel 要按 slot mapping 把 K/V 散写到非连续的物理块里 （L5.2 的 PagedAttention）。这是指针操作，不是 Triton/TileLang 擅长表达的 block 级张量代数。

(2) 极端热路径值得手工。 rms_norm_kernel 在 decode 每步调用 952 次（L0.1 实测）。 即使只快 10%，累计也可观。而且它的形状固定（hidden=2048）， 手工调一次用很久。

(3) 依赖与编译时间。 Triton 的 JIT 首次运行要编译（L0.1 实测一次 LLM.generate 产生 41 个 cubin）。 生产环境不希望冷启动时编译几十个 kernel。手写 CUDA 是 AOT 编译进 .so 的。

趋势是在变的：vLLM 里 Triton kernel 的比例在增加， 新的算子（采样惩罚、各种 mask）基本都用 Triton 写。 但"全部用 DSL"短期内不会发生。

5. 本章所有实现的误差都是 0（与 cuBLAS 逐位相同）。这可信吗？我该怎么验证不是测量出了 bug？

应该怀疑，而且本站验证过。

L2.4 里对手写 WMMA 版做过专门验证（1024³，逐元素比对）：

参考 RMS = 2.666367
自写 RMS = 2.666367
最大绝对差 = 0
不同的元素数 = 0 / 1048576

100 万个元素，一个都不差。 所以"误差 0"是真的。

应继续验证输出比较本身：确认读取的是本次结果、参考与结果不是同一缓冲、 比较没有先经过低精度转换，并记录最大绝对误差与不同元素数。 然后改变输入分布、K 长度和归约路径，检查一致性是否仍成立。 这些改变可能引入数值差异，但不能保证每个样本一定出现差异。 不要因为 bf16 输入在一次比较中相等，就认定 fp32 累加总能精确表示所有中间和。

最后一条是最好的对照：同样的验证代码，fp32 路径能测出非零误差， 说明测量方法本身是有效的，bf16 的 0 是真结果。
