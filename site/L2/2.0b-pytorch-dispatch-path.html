PyTorch 算子调用：从 Python 到 dispatcher 与 kernel

沿同一算子贯通 Python binding、schema、代码生成、dispatch key、redispatch、ATen native 实现与 kernel；解释注册、分解和实际执行的观察层次。

2.0b PyTorch 算子调用：从 Python 到 dispatcher 与 kernel

核心问题
一次 Python 算子调用如何找到实际实现？dispatch key、线程局部状态与 redispatch 如何共同决定路径？同一操作在 hook、export 图和 GPU trace 中为什么可能具有不同名字与粒度？

dispatcher 根据运行状态选择实现

当你在 Python 中调用 torch.nn.functional.linear(x, w, b) 时：

import torch
x = torch.randn(2, 4, device='cuda')
w = torch.randn(8, 4, device='cuda')
b = torch.randn(8, device='cuda')
y = torch.nn.functional.linear(x, w, b)

这一行代码会触发： - Python binding 解析参数 - Dispatcher 根据 tensor 的 device、dtype、layout、是否需要梯度等属性选择实现 - 可能经过 autograd、autocast、profiler 等 hook - 最终调用 ATen 的 native 实现或 CUDA kernel

选择实现时，还需要考虑以下功能： - 多种 device（CPU、CUDA、MPS、XLA） - 自动求导（autograd） - 混合精度（autocast） - 量化（quantization） - 编译器（torch.compile） - profiling 和 hook

这些功能需要在运行时根据 tensor 的属性和当前线程状态动态选择实现路径。

观察层次

同一个操作 linear 在不同观察点可能呈现不同的名字和粒度：

层次 工具 看到什么 示例
Python API print(op) 用户调用的函数 torch.nn.functional.linear
Torch dispatch torch.library.impl_abstract ATen schema aten::linear
Autograd hook register_hook grad_fn 节点 LinearBackward0
Export 图 torch.export FX 图节点 aten.addmm.default 或 aten.linear.default
CUDA trace nsys 实际 kernel ampere_sgemm_128x64_tn
Profiler torch.profiler 算子边界 aten::mm, aten::add

某个节点未出现在 hook 记录中，并不说明相应计算不存在。可能的原因包括： - 在 export 前被分解（decompose） - 在编译时被融合（fuse） - 在 dispatcher 中走了不同的注册路径

Schema 与注册

native_functions.yaml

PyTorch 的算子定义在 aten/src/ATen/native/native_functions.yaml：

- func: linear(Tensor input, Tensor weight, Tensor? bias=None) -> Tensor
  python_module: nn
  variants: function
  dispatch:
    CPU: linear_cpu
    CUDA: linear_cuda
    CompositeImplicitAutograd: linear_impl

字段含义： - func：算子签名（名称、参数、返回值） - python_module：Python 模块（torch.nn.functional.linear） - variants：function 或 method（支持 tensor.linear(...) 吗？） - dispatch：每个 dispatch key 对应的实现函数

代码生成

torchgen 工具会根据 yaml 生成： - Python binding：torch/csrc/autograd/generated/python_nn_functions.cpp - Dispatcher 注册表：build/aten/src/ATen/RegisterCPU.cpp - schema：build/aten/src/ATen/Operators_0.cpp

生成的 Python binding（简化）：

// torch/csrc/autograd/generated/python_nn_functions.cpp
static PyObject* THPVariable_linear(
    PyObject* self, PyObject* args, PyObject* kwargs) {
  HANDLE_TH_ERRORS
  // 解析参数
  ParsedArgs<3> parsed_args;
  auto r = parser.parse(args, kwargs, parsed_args);

  // 调用 dispatcher
  return wrap(dispatch_linear(
      r.tensor(0),  // input
      r.tensor(1),  // weight
      r.optionalTensor(2)  // bias
  ));
  END_HANDLE_TH_ERRORS
}

生成的 dispatcher 注册（简化）：

// build/aten/src/ATen/RegisterCPU.cpp
TORCH_LIBRARY_IMPL(aten, CPU, m) {
  m.impl("linear", TORCH_FN(linear_cpu));
}

Dispatcher 核心：DispatchKeySet

DispatchKey 列表

c10/core/DispatchKey.h 定义了所有 dispatch key（简化）：

enum class DispatchKey : uint16_t {
  // Backend keys
  CPU,
  CUDA,
  XLA,
  MPS,

  // Functionality keys (ordered by priority)
  AutogradCPU,
  AutogradCUDA,
  Autocast,
  Profiler,
  Tracer,

  // Backend keys
  CompositeImplicitAutograd,  // 实现自动支持 autograd
  CompositeExplicitAutograd,  // 需要显式 autograd 实现
};

DispatchKeySet

每个 tensor 携带一个 DispatchKeySet，表示它支持的所有 dispatch key：

// c10/core/DispatchKeySet.h
class DispatchKeySet {
  uint64_t repr_;  // 每个 bit 对应一个 DispatchKey

  bool has(DispatchKey k) const {
    return repr_ & (1ULL << static_cast<uint8_t>(k));
  }
};

示例：CUDA tensor 且需要梯度

x = torch.randn(2, 4, device='cuda', requires_grad=True)
# x 的 DispatchKeySet 包含：
# - CUDA
# - AutogradCUDA
# - (可能) Autocast（如果在 autocast 上下文中）

Dispatcher 查找

c10/core/impl/LocalDispatchKeySet.h 维护线程局部的 dispatch key：

// 线程局部状态
thread_local DispatchKeySet g_included_keys;
thread_local DispatchKeySet g_excluded_keys;

// 计算有效的 dispatch key set
DispatchKeySet effective_keys = 
    (tensor_keys | g_included_keys) & ~g_excluded_keys;

// 选择优先级最高的 key
DispatchKey key = effective_keys.highestPriorityTypeId();

优先级顺序（从高到低）： 1. Autograd（AutogradCPU、AutogradCUDA） 2. Autocast 3. Profiler 4. Backend（CPU、CUDA） 5. CompositeImplicitAutograd

调用路径：linear 案例

路径 1：CUDA + autograd

x = torch.randn(2, 4, device='cuda', requires_grad=True)
w = torch.randn(8, 4, device='cuda', requires_grad=True)
y = torch.nn.functional.linear(x, w)

调用栈（简化）：

1. Python: torch.nn.functional.linear(x, w)
2. C++ binding: THPVariable_linear
3. Dispatcher: at::linear(x, w, bias)
   - 计算 DispatchKeySet: {CUDA, AutogradCUDA}
   - 选择最高优先级: AutogradCUDA
4. Autograd: autograd::VariableType::linear
   - 创建 LinearBackward0 节点
   - 保存 input, weight（用于反向）
   - redispatch 到下一层
5. Dispatcher (redispatch): 
   - 排除 AutogradCUDA
   - 选择: CUDA
6. Backend: at::native::linear_cuda
   - 调用 at::addmm(bias, input, weight.t())
7. CUDA kernel: cublasSgemm

关键点： - Autograd 层不实现算子，它只记录计算图，然后 redispatch - Redispatch 通过修改线程局部的 g_excluded_keys 排除已处理的 key - 最终调用到 backend 实现

路径 2：CPU + no autograd

with torch.no_grad():
    x = torch.randn(2, 4)
    w = torch.randn(8, 4)
    y = torch.nn.functional.linear(x, w)

调用栈：

1. Python: torch.nn.functional.linear(x, w)
2. C++ binding: THPVariable_linear
3. Dispatcher: at::linear(x, w, bias)
   - DispatchKeySet: {CPU}  # 无 AutogradCPU
   - 选择: CPU
4. Backend: at::native::linear_cpu
   - 调用 at::addmm(bias, input, weight.t())
5. CPU kernel: BLAS sgemm

无 autograd 层，直接到 backend。

路径 3：Export 图

import torch
from torch.export import export

def f(x, w):
    return torch.nn.functional.linear(x, w)

x = torch.randn(2, 4)
w = torch.randn(8, 4)
exported = export(f, (x, w))
print(exported.graph_module.code)

输出：

def forward(self, x, w):
    t = torch.ops.aten.t.default(w)
    addmm = torch.ops.aten.addmm.default(None, x, t)
    return addmm

关键认知： - Export 时，linear 被分解为 t + addmm - 这是因为 linear 在 yaml 中有 CompositeImplicitAutograd 实现：

// aten/src/ATen/native/Linear.cpp
Tensor linear_impl(const Tensor& input, const Tensor& weight, 
                   const optional<Tensor>& bias) {
  auto output = at::matmul(input, weight.t());
  if (bias.has_value()) {
    output.add_(bias.value());
  }
  return output;
}
  • Export 会调用这个"composite"实现，将高层算子分解为基础算子

分解 vs 融合

常见混淆：把算子分解等同于 kernel 融合。

  • 分解（Decomposition）：高层算子 → 基础算子（编译时或 dispatcher 层）
  • 示例：linear → addmm → mm + add
  • 发生在：export、Inductor 编译
  • 融合（Fusion）：多个 kernel → 单个 kernel（CUDA 图、编译器优化）
  • 示例：mm + add + relu → 单个 fused kernel
  • 发生在：torch.compile、CUDA Graph、手写 kernel

示例：

# 源码
y = F.linear(x, w, b)
z = F.relu(y)

# Export 后（分解）
t1 = aten.t(w)
t2 = aten.addmm(b, x, t1)  # linear 分解
z = aten.relu(t2)

# Inductor 编译后（融合）
# 单个 Triton kernel: fused_addmm_relu

Redispatch 机制

为什么需要 redispatch

Autograd、Autocast 等功能层不实现算子，它们只是： 1. 记录信息（计算图、类型转换） 2. 修改线程局部状态 3. 再次调用 dispatcher，让下一层处理

实现

// torch/csrc/autograd/VariableTypeManual.cpp
Tensor VariableType::linear(
    const Tensor& input, const Tensor& weight, 
    const optional<Tensor>& bias) {
  // 1. 创建反向节点并保存输入
  auto grad_fn = std::make_shared<LinearBackward0>();
  grad_fn->set_next_edges(collect_next_edges(input, weight, bias));
  grad_fn->save_for_backward({input, weight});

  // 2. 排除 Autograd 键，向下 redispatch
  at::AutoDispatchBelowAutograd guard;
  return at::redispatch::linear(
      c10::DispatchKeySet(c10::DispatchKey::AutogradCUDA),
      input, weight, bias);
}

小结

  1. 分发机制的核心是位图运算：通过 (tensor_keys | g_included_keys) & ~g_excluded_keys 动态计算有效键集，按优先级取最高位。
  2. 中间功能层通过 redispatch 串联：Autograd、Autocast 在执行自身逻辑后，排除当前键并再次进入 dispatcher，最终落入具体后端（CPU / CUDA / Meta）。
  3. 观察粒度决定呈现形态：Python API 层面单一的 linear，在 export 图中会分解为 t 与 addmm，而在编译优化后又可能被融合为单个 Triton kernel。区分“分解”与“融合”是理解算子执行路径的关键。
