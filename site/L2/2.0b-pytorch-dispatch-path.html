PyTorch 算子调用：从 Python 到 dispatcher 与 kernel

沿同一算子贯通 Python binding、schema、代码生成、dispatch key、redispatch、ATen native 实现与 kernel；解释注册、分解和实际执行的观察层次。

实测机器 本地 CPU（torch 2.14.0，无 GPU）；CUDA 分支在 crater（torch 2.13.0+cu130）复采前置 2.0（张量、storage 与 dispatcher 位图）· 2.1（CUDA 执行模型）· 2.8（自定义算子接入）

本章回答三个问题

torch.nn.functional.linear(x, w, b) 这一行在 Python 里只是一个函数名，在设备上却是一串 kernel。中间那段「按运行时状态选择实现」的机制就是 dispatcher。

  1. 一次 Python 调用如何找到实际实现？调用链上有哪些固定环节？
  2. dispatch key 与 dtype 分支有什么区别？同一条链为什么在 CPU 和 CUDA 上分叉？
  3. redispatch 如何避免重复包装？为什么它需要一个线程局部的「排除集」？

证据范围

本章结论在本地 CPU（torch 2.14.0）与 crater（torch 2.13.0+cu130，RTX 5090 D）上取得， 原始输出在 results/local/2.0b/ 与 results/crater/2.0b/20260913-cuda-branch/。 源码引用固定到 commit 08187d9e（pytorch/pytorch），快照、SHA256 与下载命令在 results/local/2.0b/20260913-lineage/source/manifest.json。

RegisterCPU_*.cpp、RegisterCUDA_*.cpp、VariableType_*.cpp 这类文件是构建期生成的， 不在仓库里，也不在 wheel 的 Python 包内；它们的路径与行号来自运行时的 torch._C._dispatch_dump_table，是「这份 wheel 当时注册在哪」的直接记录。

两个 wheel 的版本不同（本地 2.14.0、crater 2.13.0），生成文件的行号会整体位移 （例如 aten::linear 的复合实现是 5216 对 5218），所以行号只在同一版本内可比， 跨版本要比的是"指向哪个文件、是不是后端专属 kernel"。

心智模型：位图选键，排除集向下

三条不变量决定了整条链的行为：

  1. 选键看优先级，不看注册顺序。 每个张量带一个 DispatchKeySet 位图；dispatcher 取其中优先级最高、且有实现的键。功能键（Autograd、Autocast…）的位比后端键高，所以包装层永远先于计算层。
  2. 每个包装层都向下 redispatch，并把自己排除掉。 排除集是线程局部的，不是张量上的字段；它保证「Autograd 处理过的算子不会再被 Autograd 处理」。
  3. 复合算子没有后端 kernel。 它在前向就被拆成别的算子，dispatch mode 里根本看不到它的名字；而结构化算子有一个由模板生成的 CPU/CUDA kernel。

一 · 机制：位图、优先级与排除集

1.1 优先级由枚举顺序定义

c10/core/DispatchKey.h 里 DispatchKey 的枚举顺序就是优先级顺序， DispatchKeySet::highestPriorityTypeId() 取的是其中最高的位。与本章相关的几段：

ADInplaceOrView,                     // :289
AutogradOther,                       // :315
AutogradFunctionality,
AutogradNestedTensor,
Tracer,                              // :329

// TODO: make Autocast a functionality key
// Autocasting precedes VariableTypeId, to ensure casts are autograd-exposed
// and inputs are saved for backward in the post-autocast type.
AutocastCPU,                         // :334
...
AutocastCUDA,                        // :344

这一段注释直接回答了「Autocast 和 Autograd 谁先」：Autocast 先， 所以转换后的张量才会被 autograd 保存下来，反向拿到的是 autocast 的类型。 实测印证：

autocast 下 y = x @ w（x、w 为 float32 且 requires_grad）
  y.dtype = torch.bfloat16  grad_fn = MmBackward0
  反向保存的张量：(bfloat16, (4,4)), (bfloat16, (4,4))
  x.grad.dtype = torch.float32

1.2 redispatch 与线程局部排除集

aten/src/ATen/core/dispatch/Dispatcher.h:190 的注释把用法写死了：

  // Like call, but intended for use in a redispatch in kernels that have
  // already been dispatched to. ... redispatch treats the inputted
  // DispatchKeySet *as is*, and does NOT mask ...
  Return redispatch(

实现在同一个文件 :843：

inline Return Dispatcher::redispatch(
    const OperatorHandle& op, DispatchKeySet currentDispatchKeySet, Args... args) {
  // do not use RecordFunction on redispatch

而「不再命中原键」不是靠 redispatch 自己，是靠调用方在进入前用 at::AutoDispatchBelowAutograd 之类的 guard 把键塞进排除集。 排除集可以从 Python 直接读出来：

普通上下文   DispatchKeySet(AutocastCPU, AutocastMTIA, ..., AutocastCUDA, AutocastPrivateUse1)
no_grad      DispatchKeySet(AutocastCPU, AutocastMTIA, ..., AutocastCUDA, AutocastPrivateUse1)
autocast     DispatchKeySet(AutocastMTIA, ..., AutocastCUDA, AutocastPrivateUse1)

两件事同时成立：

  • no_grad 不改变排除集。它翻的是 GradMode 这个 TLS 布尔（2.0 已核对）； Autograd 键照样被分发到，只是它查到 GradMode 关着就不建反向节点。
  • 默认状态下 Autocast* 就在排除集里（autocast 默认关闭）， with autocast() 做的是把 AutocastCPU 从排除集里拿掉。

1.3 dtype 分支不在 dispatcher 层

dtype 不参与选键。同一个 aten::linear 在 float32 与 bfloat16 上的 DispatchKeySet 完全一样（2.0 的实测表：bf16 与 fp32 的 keyset 相同）。 dtype 的分派发生在 kernel 内部：

// 结构化算子的统一模板，注册进 RegisterCPU_*.cpp
AT_DISPATCH_ALL_TYPES_AND2(kBFloat16, kHalf, result.scalar_type(), "...", [&] {

dispatch key 决定「谁来算」（后端、功能层），dtype 决定「按哪种类型算」。 把两者混在一起，就会写出「CUDA 上 dtype 不支持时在 dispatcher 里找不到实现」 这类错误推断。

二 · 源码解析：两条真实调用链

2.1 链一：F.linear → aten::linear → addmm

第一步：Python 名字其实是一个 C++ 绑定。

torch.nn.functional.linear           = <built-in function linear>
type                                 = builtin_function_or_method
__module__ / __name__                = torch._C._nn / linear
F.linear is torch._C._nn.linear      = True

绑定生成到哪个命名空间，由 native_functions.yaml 的 python_module 决定。 生成器是 tools/autograd/gen_python_functions.py（:241 判断 f.python_module == "nn"，:316 把结果写进 python_nn_functions.cpp）。

第二步：schema 与注册表。 运行时读出的 schema：

aten::linear(Tensor input, Tensor weight, Tensor? bias=None) -> Tensor

它的 native_functions.yaml 声明（commit 08187d9e，:3337）：

- func: linear(Tensor input, Tensor weight, Tensor? bias=None) -> Tensor
  python_module: nn
  dispatch:
    CompositeImplicitAutograd: linear
    NestedTensorCPU, NestedTensorHPU, NestedTensorCUDA, NestedTensorXPU: nested_linear
    MPS: _mps_linear

没有 CPU: / CUDA: 行。 这是本章最关键的一条事实。运行时的注册表 （129 个注册点）里，CPU、CUDA、Meta、QuantizedCPU 等 99 个键全部指向 同一个复合实现，种类标为 math kernel：

CPU      build/aten/src/ATen/RegisterCompositeImplicitAutograd_0.cpp:5216  math kernel
CUDA     build/aten/src/ATen/RegisterCompositeImplicitAutograd_0.cpp:5216  math kernel
Meta     build/aten/src/ATen/RegisterCompositeImplicitAutograd_0.cpp:5216  math kernel

即：这些后端键上没有任何后端专属实现。运行 A1–A3 小节时脚本会直接统计 「指向 RegisterCPU_* / RegisterCUDA_* 的注册点数」，这里是 0。

第三步：复合实现落到哪。 aten/src/ATen/native/Linear.cpp:85：

Tensor linear(const Tensor& input, const Tensor& weight, const std::optional<Tensor>& bias_opt) {
  ...
  if (input_dim == 2 && bias->defined()) {
    // Fused op is marginally faster.
    return at::addmm(*bias, input, weight.t());
  }

高维输入走 _flatten_nd_linear（:68）后同样落到 at::addmm。

第四步：addmm 是结构化算子。 它的声明在 native_functions.yaml:7073：

- func: addmm(Tensor self, Tensor mat1, Tensor mat2, *, Scalar beta=1, Scalar alpha=1) -> Tensor
  structured_delegate: addmm.out

CPU 实现挂在 addmm.out 上（:7060 CPU: addmm_out_cpu）， 函数体在 LinearAlgebra.cpp:1609 的 TORCH_IMPL_FUNC(addmm_out_cpu)， 核心数值在 addmm_impl_cpu_（:1392），最终调 BLAS。

第五步：Autograd 与 Autocast 的注册。 两者都不是后端 kernel：

torch/csrc/autograd/generated/VariableType_5.cpp:8739      Autograd[alias]
aten/src/ATen/autocast_mode.cpp:338                        AutocastCPU
aten/src/ATen/autocast_mode.cpp:181                        AutocastCUDA

Autograd 那一条由 tools/autograd/derivatives.yaml:2387 的规则生成：

- name: linear(Tensor input, Tensor weight, Tensor? bias=None) -> Tensor
  input, weight, bias: "grad.defined() ? linear_backward(input, grad, weight, grad_input_mask) : ..."

Autocast 那一条对应 autocast_mode.cpp:353 的 KERNEL_CPU(linear, lower_precision_fp)。

2.2 链二：x + y → aten::add.Tensor → TensorIterator

# native_functions.yaml:542
- func: add.Tensor(Tensor self, Tensor other, *, Scalar alpha=1) -> Tensor
  device_check: NoCheck   # TensorIterator
  structured_delegate: add.out
  variants: function, method
  dispatch:
    SparseCPU, SparseCUDA, SparseMPS, SparseMeta, SparseXPU: add_sparse

add.Tensor 自己只注册了稀疏、Mkldnn、ZeroTensor 等特化实现； 稠密路径由 structured_delegate: add.out 交给 add.out（:565）， 后者声明成 structured: True + structured_inherits: TensorIteratorBase， 并给出 ufunc_inner_loop 的逐元素函数。运行时的落点是：

aten::add.Tensor  CPU  build/aten/src/ATen/RegisterCPU_0.cpp:1307  kernel
aten::add.out     CPU  build/aten/src/ATen/RegisterCPU_0.cpp:1307  kernel

同一个 RegisterCPU_0.cpp:1307：结构化算子的 CPU kernel 是模板实例化出来的， 不是手写的 add_cpu() 函数。2.0 里 TensorIterator 的维度重排、合并 （TensorIterator.cpp:231）就发生在这一层。

2.3 两条链的差别

linear add
schema 数 1（linear） 2（add.Tensor + add.out）
后端 kernel 无（CPU 与 CUDA 都指向同一复合实现） 有（CPU RegisterCPU_0.cpp:1297、CUDA RegisterCUDA_0.cpp:2396，模板生成）
前向形态 分发时拆成 t + addmm 一个 TensorIterator kernel
autograd 生成 LinearBackward0（derivatives.yaml） AddBackward0
加一张卡要动哪 复合实现内部（addmm 已有后端） add.out 的模板实例化

分水岭是 CompositeImplicitAutograd 与 structured 两种声明方式： 前者用「拼装已有算子」换取零后端维护成本，后者用「共享迭代器模板」换取 逐元素算子的统一实现与向量化。

2.4 CUDA 侧复采：同一条链在带 CUDA 的 wheel 上

本地是 CPU-only wheel，_dispatch_dump_table 里根本没有 CUDA 键。 在 crater（torch 2.13.0+cu130）上用同一套解析复采 （labs/L2/dispatch_cuda_branch.py）：

算子 CUDA 键的落点 是不是后端专属 kernel
aten::linear RegisterCompositeImplicitAutograd_0.cpp:5218（math kernel） 否 —— 与 CPU 指向同一行
aten::addmm RegisterCUDA_0.cpp:22696 是
aten::addmm.out RegisterCUDA_0.cpp:22696 是（与 addmm 同点，结构化委托）
aten::add.Tensor RegisterCUDA_0.cpp:2396 是
aten::add.out RegisterCUDA_0.cpp:2396 是（同点）
aten::mm RegisterCUDA_0.cpp:15178 是
aten::relu RegisterCUDA_0.cpp:17006 是

结构结论在 CUDA 上完全一致：linear 的 CUDA 键和 CPU 键落在同一行—— 那个复合实现的 math kernel；而 add/addmm/mm/relu 各自有后端专属 kernel。 "多个键指向同一实现"在带 CUDA 的 wheel 上同样成立（aten::linear 129 个注册点、 CUDA 键 1 个、后端专属 0 个）。

注册点只说"谁来接这个调用"，profiler 才说"最后跑了什么"。同一台机器上跑一次 fp32 前向（F.linear + relu(y+1) + x@w+b）：

     128.2 µs  ×1   cutlass::Kernel2<cutlass_80_simt_sgemm_256x128_8x4_tn_align1>
      69.3 µs  ×1   cutlass::Kernel2<cutlass_80_simt_sgemm_128x64_8x5_nn_align1>
       3.3 µs  ×1   at::native::elementwise_kernel<... CUDAFunctor_add<float> ...>
       2.3 µs  ×1   at::native::vectorized_elementwise_kernel<4, CUDAFunctorOnSelf_add<float> ...>
       2.0 µs  ×1   at::native::vectorized_elementwise_kernel<4, ... launch_clamp_scalar ...>

两处核心机制要点：

  1. 两次 linear/mm 都落到 cuBLAS，而 cuBLAS 在 sm_120 上选了 SIMT 的 cutlass_80_simt_sgemm，不是 tensor core kernel。fp32 输入、且默认不允许 TF32 （allow_tf32=False）时，cuBLAS 走 SIMT sgemm —— 与 L1.2/2.4 里 "bf16 才会用上 tensor core"一致。
  2. add/relu 落到 vectorized_elementwise_kernel，正是 RegisterCUDA_0.cpp:2396 那条结构化模板实例化的产物； 而 linear 没有自己的 kernel，profiler 里也就看不到 linear 这个名字 （只有 addmm 之后的 cuBLAS kernel）—— 与 CPU 侧观察到的现象同源。

设计取舍

为什么让 linear 做复合算子，而不是给每个后端写一个 kernel？

linear 的语义完整地由 addmm + t 决定，没有后端专属的数值细节。 写成复合算子后：加一个新后端不需要碰 linear；反向由 derivatives.yaml 一条规则生成；代价是每次调用多两次分发（t、addmm）， 以及在 dispatch mode 里再也看不到 linear 这个名字。

为什么用「排除集 + 向下 redispatch」，而不是函数调用链？

如果 Autograd 直接调用 linear_cpu()，那么「Autograd 之上还有没有别的层」 就变成编译期固定的顺序：autocast 想插在 autograd 之上就必须改 Autograd 代码。 排除集把顺序交给优先级位图运行时决定，于是 Autocast 可以在 DispatchKey.h 里只挪一次位置，就获得「先改输入再被 autograd 记录」的语义。 代价是每次包装都要重新查一次表，以及一个容易写错的点： redispatch 时忘了排除自己就是死循环（见 4.2 的反例）。

为什么 profiler 看到的名字和 dispatch mode 不一样？

dispatcher 入口是唯一的「所有算子都经过」的位置，所以 profiler 在那里打点； 而 dispatch mode 挂在 ATen 层，看到的是实际被分发的算子。 复合算子有入口但不再往下分发，于是出现「profiler 有 aten::linear、 dispatch mode 没有」的现象。这不是矛盾，是观察点不同（见 3.1）。

三 · 观察层次：同一程序，三种粒度

3.1 三个层次各自看到什么

程序统一为 relu(linear(x, w, b))，本地 CPU，torch 2.14.0：

层次 工具 看到的名字
ATen 分发 TorchDispatchMode aten.t → aten.addmm → aten.relu
导出图 torch.export.export linear.default → relu.default（未分解）
导出图再过分解 pass ep.run_decompositions() permute.default → addmm.default → relu.default
执行采样 torch.profiler aten::linear 与它的子调用 aten::t、aten::addmm 同时出现

四个读数放在一起，三条结论就出来了：

  1. 分解不是 export 干的，是一个独立的 pass。 导出图保留 aten.linear.default，run_decompositions() 之后才变成 permute + addmm。 说「export 会把 linear 拆成 t + addmm」不准确。
  2. dispatch mode 看不到复合名字。 它看到的是真正被分发的算子序列。
  3. profiler 既记录父算子又记录子算子，逐行相加会重复计数。 实测 aten::linear 的 self 是 0.014 ms、total 是 0.050 ms， 后者把子调用的时间算了进来。比较算子开销要看 self，或只看叶子算子。

3.2 换成一个不可分解的算子

用 torch.library 定义 l2b_obs::fused_linear_relu（一个 schema、 一个 CPU 实现、一个 register_fake），同一程序变成：

层次 看到的名字
ATen 分发 l2b_obs.fused_linear_relu.default（1 个）
导出图 fused_linear_relu.default（1 个节点）
分解 pass 之后 fused_linear_relu.default（不变，没有分解规则）
profiler l2b_obs::fused_linear_relu 与它的 Python 实现内部的 aten::linear、aten::addmm 同时在表里

profiler 看执行，不看图的边界。 自定义算子在图里是一个不透明节点， 但它的 Python 实现在执行时调用了哪些 aten 算子，profiler 一清二楚。 「opaque 边界」是图层面的概念，不是执行层面的。

数值对拍：两者输出逐位相同（max |diff| = 0.0）。

3.3 没有 fake 实现就进不了图

同一个自定义算子如果只有 CPU 实现、没有 register_fake， dispatch mode 里能正常跑，export 却会失败，错误链是：

[UnsupportedOperatorException] l2b_obs.no_fake.default
[NotImplementedError] l2b_obs::no_fake: attempted to run this operator with Meta tensors,
                      but there was no fake impl or Meta kernel

原因与 2.0 里那条 Meta 注册在 Python 文件（torch/_meta_registrations.py） 的事实同源：图模式靠 fake/meta 实现推导形状，不执行真实 kernel。 2.8 会把这条要求写成自定义算子的交付契约。

七 · 前沿：这一层在推理引擎里长什么样

  • 引擎把自写 kernel 变成一等算子。 0.1 已经看到 vLLM 把自写 kernel 编进 _C_stable_libtorch.abi3.so；这些 kernel 要在 Python 侧作为算子可见， 必须经过 schema、实现与形状推导三层注册。本章只核对了框架自身的注册路径， vLLM 的具体注册点与命名约定保持 UNVERIFIED，在 2.8 的自定义算子 章节逐条核对。
  • 图模式需要 fake 实现，这决定了引擎的切分点。 5.4 的 piecewise CUDA Graph 把 attention 标成 splitting op：图需要在不执行的情况下 推导形状，任何缺少 Meta/fake 实现的算子都必须被挡在图外， 或补齐推导函数。
  • Autocast 的位置决定了混合精度的数值路径。 本章实测「保存值在 autocast 类型上」是 DispatchKey.h:332 的直接后果；引擎选择 bf16/fp8 时，哪些张量被保存、反向按什么精度累加，都由这条优先级决定。
  • torch.library 是给引擎补算子的标准接口，而不是改 ATen 源码。 2.8 的任务就是把本章的机制用在一个真实算子上（fused add+RMSNorm）， 并交付 schema、fake、autograd 与部署改动的完整清单。

八 · 陷阱

  1. hook 里没有某个算子，不等于它没执行。 复合算子在 dispatch mode 里本来就看不到名字；要判断某次调用路径，得同时看 dispatch mode、 导出图与 profiler 三个层次。
  2. 算子分解不是 kernel 融合。 分解是「一个名字变成几个名字」， 融合是「几个 kernel 变成一个 kernel」。export 图上的节点数与 设备上执行的 kernel 数没有固定关系。
  3. dtype 分支与 dispatch key 是两件事。 dtype 不参与选键； 说「bf16 在 dispatcher 里走了另一条注册」是错的。
  4. redispatch 不自动排除当前键。 每个包装 kernel 必须自己加 guard； 忘了就是 RecursionError（mini 版是深度上限报错）。
  5. profiler 的父子事件不能相加。 aten::linear 与它的子调用 同时出现，total 已经包含子调用时间。
  6. export 图保留复合算子，不代表执行时也保留。 图是 pre-dispatch 的 函数式表示，分解发生在后续 pass；两者相差一个 run_decompositions()。
  7. 没有 fake/Meta 实现的算子会挡住图模式。 它能在 eager 下正确运行， 但 export/compile 会在形状推导处失败，错误链的根因是 NotImplementedError: no fake impl or Meta kernel。

九 · 自测题

1. `aten::linear` 的注册表里 CPU、CUDA 两个键都存在，为什么说它「没有后端 kernel」？ 因为这两个键指向的是同一条复合实现 （`RegisterCompositeImplicitAutograd_0.cpp:5216`，种类 `math kernel`）， 而不是 `RegisterCPU_*` / `RegisterCUDA_*` 里的后端专属实现。 脚本对「指向 RegisterCPU/RegisterCUDA 的注册点」计数为 0。 判据：**一个算子是不是复合的，看它的后端键是否指向通用复合实现， 而不是看后端键在不在表里。**
2. `with autocast(): y = x @ w`，x、w 是 float32 且 requires_grad，反向保存的张量是什么类型？为什么？ bfloat16。`c10/core/DispatchKey.h:332` 明确写了 「Autocasting precedes VariableTypeId, to ensure casts are autograd-exposed and inputs are saved for backward in the post-autocast type」—— Autocast 的优先级高于 Autograd，所以输入先被转换，autograd 记录到的 是转换后的算子，保存值也就是 bfloat16。 叶子的梯度仍是 float32，因为累积按叶子自身的 dtype 进行。
3. `no_grad()` 会改变线程局部排除集吗？ 不会。实测 `no_grad` 内外的 `_dispatch_tls_local_exclude_set()` 完全相同， 默认就装着全部 `Autocast*`。 `no_grad` 翻的是 `GradMode` 布尔；`with autocast()` 才是把 `AutocastCPU` 从排除集里拿掉。
4. 一个自定义算子只有 CPU 实现和 `register_fake`，它在 dispatch mode、export 图和 profiler 里分别是什么样？ - dispatch mode：一个算子 `l2b_obs.fused_linear_relu.default`。 - export 图：一个不透明节点 `fused_linear_relu.default`； 过分解 pass 后仍然是一个节点（没有分解规则）。 - profiler：自定义算子本身与它 Python 实现内部的 `aten::linear`、 `aten::addmm` 同时出现 —— profiler 记录执行，不认图的边界。 去掉 `register_fake` 后，前两者中的 export 会失败： `NotImplementedError: ... no fake impl or Meta kernel`。
5. 一个包装 kernel 里写 `return at::redispatch::linear(keyset, x, w, b)` 却忘了加 guard，会发生什么？ 它会重新选中自己。真实框架里表现为 `RecursionError: maximum recursion depth exceeded`（Python 实现的重入），mini 版本则由深度上限拦下并 报「redispatch 时没有排除自己的键」。 正确写法是进入前用 `at::AutoDispatchBelowAutograd`（或对应功能的 guard） 把当前键放进线程局部排除集，再 redispatch。
