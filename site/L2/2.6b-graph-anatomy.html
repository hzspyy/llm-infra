2.6b

算子图：FX、AOTAutograd 与 Inductor 生成代码

阅读 FX 图与 Inductor 生成代码，理解图捕获、分图、融合和 CUDA Graph 重放的区别。

实测机器 crater (RTX 5090 D, sm_120) · torch 2.13.0+cu130前置 L2.3（融合的收益从哪来）· L2.5（Triton）

本章回答三个问题

算子图是表示程序计算过程的数据结构： 节点表示输入、操作或输出，边表示某个操作使用了另一个操作产生的值。 本章把同一个小函数交给编译器，逐步查看图的文本表示、反向图和生成的 kernel。 先理解每一步的输入输出，再读完整打印结果，不需要一次记住所有节点名。

  1. 「torch.compile 会捕获计算图」——那个图到底长什么样？能打印出来吗？
  2. 融合 7 个逐元素算子，实际收益是多少？从哪里来？
  3. 反向图长什么样？为什么它比前向图大？

本章的原则：凡是能打印的，一律打印。不用比喻。

心智模型：四跳，四种表示

机制拆解

第一阶段：Dynamo 捕获 FX 图

被编译的源码只有 4 行：

def rmsnorm_like(x: torch.Tensor, w: torch.Tensor) -> torch.Tensor:
    v = x.float()
    s = v.pow(2).mean(-1, keepdim=True)
    return (v * torch.rsqrt(s + 1e-6)).to(x.dtype) * w

Dynamo 捕获出来的 FX 图（原样打印）：

class GraphModule(torch.nn.Module):
    def forward(self, L_x_: "bf16[4096, 2048]", L_w_: "bf16[2048]"):
        l_x_ = L_x_
        l_w_ = L_w_

        # code: v = x.float()
        v: "f32[4096, 2048]" = l_x_.float();  l_x_ = None

        # code: s = v.pow(2).mean(-1, keepdim=True)
        pow_1: "f32[4096, 2048]" = v.pow(2)
        s: "f32[4096, 1]" = pow_1.mean(-1, keepdim = True);  pow_1 = None

        # code: return (v * torch.rsqrt(s + 1e-6)).to(x.dtype) * w
        add: "f32[4096, 1]" = s + 1e-06;  s = None
        rsqrt: "f32[4096, 1]" = torch.rsqrt(add);  add = None
        mul: "f32[4096, 2048]" = v * rsqrt;  v = rsqrt = None
        to: "bf16[4096, 2048]" = mul.to(torch.bfloat16);  mul = None
        mul_1: "bf16[4096, 2048]" = to * l_w_;  to = l_w_ = None
        return (mul_1,)

这份图的文本表示是一个 Python 类，变量附有 shape 和 dtype 标注。 这份输出反映了三个特点：

  1. 每一行都标了形状与类型（"f32[4096, 2048]"）。 这是后续所有优化的前提——不知道形状就无法决定 tile 和融合边界。
  2. ; x = None 释放生成 Python 代码中的一个引用。 是否能释放或复用底层存储，还要看其他引用、alias、反向保存值和编译器的内存分析， 不能只从这条赋值判断显存已经归还。
  3. 注释保留了原始源码行。所以报错和 profile 能指回你写的那一行。

节点层面（11 个）：

placeholder      L_x_
placeholder      L_w_
call_method      float          args=(l_x_,)
call_method      pow            args=(v, 2)
call_method      mean           args=(pow_1, -1)
call_function    add            args=(s, 1e-06)
call_function    rsqrt          args=(add,)
call_function    mul            args=(v, rsqrt)
call_method      to             args=(mul, torch.bfloat16)
call_function    mul            args=(to, l_w_)
output           output

这个样例出现了四种 op：placeholder、call_function、call_method 和 output。 FX 还支持 get_attr 和 call_module，不能把样例里出现的类型当成全部类型。 完整定义见 PyTorch 2.13 FX 文档。

第二阶段：AOTAutograd 构建前向与反向图

如果需要梯度，AOTAutograd 会生成前向图 + 反向图。实测节点数：

图 节点数
forward 11
backward 25

先看前向图的最后一行——它揭示了整个机制：

def forward(self, primals_1: "f32[1024, 512]", primals_2: "f32[512]"):
    pow_1:  "f32[1024, 512]" = aten.pow.Tensor_Scalar(primals_1, 2)
    mean:   "f32[1024, 1]"   = aten.mean.dim(pow_1, [-1], True);  pow_1 = None
    add:    "f32[1024, 1]"   = aten.add.Tensor(mean, 1e-06);  mean = None
    rsqrt:  "f32[1024, 1]"   = aten.rsqrt.default(add);  add = None
    detach: "f32[1024, 1]"   = aten.detach.default(rsqrt)
    mul:    "f32[1024, 512]" = aten.mul.Tensor(primals_1, rsqrt)
    mul_1:  "f32[1024, 512]" = aten.mul.Tensor(mul, primals_2)
    sum_1:  "f32[]"          = aten.sum.default(mul_1);  mul_1 = None
    return (sum_1, primals_1, primals_2, rsqrt, detach, mul)
    #       ↑真正的输出  ↑—————— 这五个是留给反向的 ——————↑

前向图返回了 6 个值，但函数只有 1 个输出。 后面五个是 AOTAutograd 为反向计算保留的中间张量，因此也列在前向图的返回值中。

（pow_1、mean、add、mul_1 后面跟着 = None，说明它们不需要保存， 可以立刻释放。编译器精确知道哪些能扔。）

反向图（原样，25 个节点）：

def forward(self, primals_1: "f32[1024, 512]", primals_2: "f32[512]",
            rsqrt: "f32[1024, 1]", detach: "f32[1024, 1]",
            mul: "f32[1024, 512]", tangents_1: "f32[]"):
    expand:   "f32[1024, 512]" = aten.expand.default(tangents_1, [1024, 512])
    mul_2:    "f32[1024, 512]" = aten.mul.Tensor(expand, mul)
    mul_3:    "f32[1024, 512]" = aten.mul.Tensor(expand, primals_2)
    sum_2:    "f32[1, 512]"    = aten.sum.dim_IntList(mul_2, [0], True)   # → dL/dw
    view:     "f32[512]"       = aten.view.default(sum_2, [512])
    mul_4:    "f32[1024, 512]" = aten.mul.Tensor(mul_3, primals_1)
    mul_5:    "f32[1024, 512]" = aten.mul.Tensor(mul_3, rsqrt)            # 路径 A
    sum_3:    "f32[1024, 1]"   = aten.sum.dim_IntList(mul_4, [1], True)
    detach_1: "f32[1024, 1]"   = aten.detach.default(detach)
    pow_2:    "f32[1024, 1]"   = aten.pow.Tensor_Scalar(detach_1, 3)      # rsqrt′
    mul_6:    "f32[1024, 1]"   = aten.mul.Scalar(sum_3, -0.5)             # rsqrt′
    mul_7:    "f32[1024, 1]"   = aten.mul.Tensor(mul_6, pow_2)
    expand_1: "f32[1024, 512]" = aten.expand.default(mul_7, [1024, 512])
    div:      "f32[1024, 512]" = aten.div.Scalar(expand_1, 512)           # mean′
    pow_3:    "f32[1024, 512]" = aten.pow.Tensor_Scalar(primals_1, 1.0)   # pow(2)′
    mul_8:    "f32[1024, 512]" = aten.mul.Scalar(pow_3, 2.0)              # pow(2)′
    mul_9:    "f32[1024, 512]" = aten.mul.Tensor(div, mul_8)              # 路径 B
    add_1:    "f32[1024, 512]" = aten.add.Tensor(mul_5, mul_9)            # A + B 汇合
    return (add_1, view)
    #       dL/dx  dL/dw

每一步都能对应到链式法则的一项：

  • pow_2 = detach^3 与 mul_6 = sum_3 × (-0.5)：这是 ddxx−1/2=−12x−3/2
  • div(..., 512)：mean 的反向是把梯度均摊到 512 个元素
  • mul_8 = pow_3 × 2.0：ddxx2=2x
  • add_1 = mul_5 + mul_9：因为 v 在前向里被用了两次 （一次算 s，一次乘 rsqrt），所以反向要把两条路径的梯度相加

最后一条是理解反向图的关键：前向图里一个值被用了 N 次，反向图里就有 N 条梯度路径要汇合。 这也是反向图更大的直接原因。

再数一遍保存的东西：primals_1（输入 x，2 MB）、primals_2（权重 w）、 rsqrt（1024 个 fp32）、detach（rsqrt 的 view，不额外占显存）、 mul（1024×512 fp32，2 MB）。

关键的是 mul —— 它是前向算出的归一化结果， 一个和输入等大的张量，必须一路活到反向结束。 一层就 2 MB，L 层的模型乘 L 倍。这就是训练显存的大头 （activation memory，L7.1 会算这笔账；★7.0 会把整个反向过程再拆一遍）。

第三阶段：Inductor 生成 Triton kernel

7 个算子 → 1 个 kernel。生成的函数名本身就是清单：

@triton.jit
def triton_red_fused__to_copy_add_mean_mul_pow_rsqrt_0(
        in_ptr0, in_ptr1, out_ptr1, xnumel, r0_numel,
        XBLOCK: tl.constexpr, R0_BLOCK: tl.constexpr):

triton_ + red（reduction）+ fused_ + 被吞掉的算子名依次排列： _to_copy、add、mean、mul、pow、rsqrt。

kernel 体是标准的两遍归约结构（对照 L2.3 的方法论）：

    # 第一遍：算平方和
    _tmp4 = tl.full([XBLOCK, R0_BLOCK], 0, tl.float32)      # 累加器 fp32
    for r0_offset in tl.range(0, r0_numel, R0_BLOCK):
        tmp0 = tl.load(in_ptr0 + (r0_1 + 2048*x0), r0_mask,
                       eviction_policy='evict_last', other=0.0).to(tl.float32)
        tmp2 = tmp1 * tmp1
        _tmp4 = tl.where(r0_mask, _tmp4 + tmp3, _tmp4)
    tmp4 = tl.sum(_tmp4, 1)[:, None]

    # 第二遍：归一化并写回
    for r0_offset in tl.range(0, r0_numel, R0_BLOCK):
        tmp6  = tl.load(in_ptr0 + (r0_1 + 2048*x0), r0_mask,
                        eviction_policy='evict_first', other=0.0).to(tl.float32)
        tmp15 = tl.load(in_ptr1 + (r0_1), r0_mask, eviction_policy='evict_last', ...)
        tmp9  = (tmp4 / tmp8)                    # mean
        tmp11 = tmp9 + tmp10                     # + eps
        tmp12 = libdevice.rsqrt(tmp11)           # rsqrt
        tmp16 = (tmp7 * tmp12).to(tl.float32) * tmp15
        tl.store(out_ptr1 + (r0_1 + 2048*x0), tmp16, r0_mask)

下面分别解释三个细节：

(1) 累加器是 tl.float32，即使输入输出都是 bf16。 这正是 L2.3 自测题 5 说的铁律：读用 bf16，算用 fp32。 Inductor 自动做对了。

(2) eviction_policy='evict_last' / 'evict_first' —— 这是 L2 缓存驱逐提示： - 第一遍读 in_ptr0 时标 evict_last（"这份数据第二遍还要用，别急着踢"） - 第二遍读同一块时标 evict_first（"用完就可以丢了"） - 权重 in_ptr1（2048 个元素，所有行共用）标 evict_last

编译器在管 L2 缓存。 这是 L1.1 提到的"L2 驻留控制"的一种实际用法。

(3) in_ptr0 被读了两遍。 这是"两遍归约"的固有代价—— 要先知道均值才能归一化。所以理论访存量是 2×读+1×写， 而不是朴素以为的 1 读 1 写。

融合的收益：3.68 倍

kernel 数 耗时 有效带宽
eager 8 0.0858 ms 391 GB/s
compiled 1 0.0233 ms 1440 GB/s
3.68× 占上限 86%

（带宽按"读 x + 写 out"两趟算；实际因为两遍归约还多读一趟， 所以真实带宽利用率比 86% 更高。）

收益的来源：eager 的 8 个 kernel 里，每个都要 「从显存读中间结果 → 算 → 写回显存」。7 个中间张量（v、pow_1、s、add、 rsqrt、mul、to）里有 4 个是 [4096, 2048] 的大张量，每个 32 MB（fp32）。

融合后这些中间值全部留在寄存器里，一次都不落显存。

这和 L2.3 解析的 vLLM fused_add_rms_norm 是完全同一件事—— 只不过那个是手写的，这个是编译器自动做的。

图断裂：一句 .item() 的代价

def has_break(x_):
    y = x_ * 2
    if y.sum().item() > 0:          # ← 这里断图
        y = y + 1
    return y.relu()

实测：

图数量        2
断裂次数      1
断裂原因      "GraphCompileReason(reason='Unsupported Tensor.item() call with capture...'"

为什么必须断？因为 .item() 要把 GPU 上的值拿到 CPU才能判断 > 0。 Dynamo 是编译期工作的，它不知道运行时那个值是多少， 所以无法把 if 的两个分支都编进一张图。

后果有三层：

  1. 两张图，中间要回到 Python 解释器。
  2. 强制同步：L1.4 实测 .item() 要 4.76 µs，且会打断 CPU-GPU 流水。
  3. 融合边界：断裂点两侧的算子不能互相融合。

这就是为什么推理引擎的热路径里绝不写 .item()（L1.4 陷阱 4）。 vLLM 的采样全在 GPU 上完成，结果通过异步拷贝 + 事件回传。

工程实现 · 源码解析：vLLM 的 piecewise 图

先区分两件事：编译器分图决定哪些算子一起优化，CUDA Graph 捕获决定哪些设备操作 可以作为一个执行序列重放。二者有关联，但不是同一个过程。

vLLM 0.29.0 的 CUDAGraphMode（vllm/config/compilation.py:53）有五个取值：

class CUDAGraphMode(enum.Enum):
    NONE = 0
    PIECEWISE = 1
    FULL = 2
    FULL_DECODE_ONLY = (FULL, NONE)
    FULL_AND_PIECEWISE = (FULL, PIECEWISE)
  • PIECEWISE：分段捕获，把与 CUDA Graph 不兼容的算子（部分 attention）留在捕获范围外。
  • FULL：后端满足要求时整图捕获。
  • 后两个是复合值：元组的两项分别用于 decode 与 mixed 两类 batch （decode_mode() / mixed_mode()，同文件 65–69 行）。

v1 的默认值是 FULL_AND_PIECEWISE（同文件 615 行的文档字符串标注 (v1 default)）， 不是 PIECEWISE。也就是说默认配置下，decode 走整图捕获，混合 batch 走分段捕获。

还要注意 splitting_ops（517 行）是编译分图的配置，与 cudagraph_mode（607 行） 的图捕获是两个独立开关，不要混为一谈。

运行时还会考虑 attention backend 能力、batch 描述和已有捕获尺寸， 必要时选择其他模式或 eager 路径。变长输入不意味着每步都必须重新捕获， 也不意味着 attention 必须永远留在图外。 参见 该版本的 CUDA Graph 设计。

L0.1 使用 enforce_eager=True，不能从该 trace 断言开启 graph 后的具体路径。 而且一次 graph launch 仍可能执行多个 kernel；在支持节点级跟踪的 profiler 中， 这些 kernel 仍然可见。图重放减少提交次数，算子融合减少 kernel 数，二者要分开看。

三种图模式的提交与 kernel 计数

上面那句「二者要分开看」现在有数了。同一份 decode 负载 （Qwen3-1.7B，bs=4，每条生成 32 token，关掉 prefix caching）， 用 nsys 只统计 generate 那一段（--capture-range=cudaProfilerApi）：

模式 CPU 侧 launch 调用 GPU 侧 kernel 数 GPU 忙 (ms)
NONE（enforce_eager） 14,003 14,003 137.76
PIECEWISE 6,071（0.434×） 12,147（0.867×） 132.87
FULL_AND_PIECEWISE（默认） 863（0.062×） 12,147（0.867×） 133.37

三件事：

  1. CPU 侧的提交次数掉了 16.2 倍（14,003 → 863）。这是图的全部收益。
  2. GPU 侧执行的 kernel 数在两种图模式下一模一样：12,147。 图没有让 GPU 少算任何东西。
  3. GPU 忙时基本不变（137.8 / 132.9 / 133.4 ms，相差 4% 以内）。 在这个负载上 GPU 根本不是瓶颈——省下来的是 CPU 提交时间， 这正是 L0.1 里「decode 每步 444 次 launch 占墙钟 27%」的那一项。

NONE 的 14,003 比图模式的 12,147 多出 1,856 个 kernel。 这 1,856 个不是图省掉的，是编译省掉的：enforce_eager=True 连 torch.compile 一起关了，所以没有 Inductor 融合。这正好演示了那句 「图重放减少提交次数，算子融合减少 kernel 数」——两个数字来自两个机制。

launch 类 API 的明细能看出图的形状：

--- PIECEWISE ---
  cudaLaunchKernel_v7000                           4,684
  cudaGraphLaunch_v10000                             899
  cuLaunchKernel                                     257
  cuLaunchKernelEx                                   231

--- FULL_AND_PIECEWISE ---
  cudaLaunchKernel_v7000                             344
  cuLaunchKernel                                     257
  cuLaunchKernelEx                                   231
  cudaGraphLaunch_v10000                              31

31 与 899 不是随便的数：本次共 31 个 decode step， Qwen3-1.7B 有 28 层。

  • FULL_AND_PIECEWISE：31 次 graph launch = 每步整模型一张图。
  • PIECEWISE：899 = 29 × 31，即每步 29 段（28 层各一段，加上收尾一段）。

分段模式把图切在 attention 处，所以每层都要单独提交一次。 两种模式跑的是同一批 kernel，区别只在提交的粒度。

CUDA Graph 的统计粒度影响 kernel 计数

nsys 的 --cuda-graph-trace 默认值是 graph，它把整张图记成一个单位， 于是 CUPTI_ACTIVITY_KIND_KERNEL 表里只剩非图的 kernel。 使用默认粒度时，得到的三行计数为 14,003 / 5,172 / 832—— GPU kernel 数恰好等于 CPU launch 数，看起来像「图让 GPU 少跑了 17 倍的 kernel」。 那是假象。加上 --cuda-graph-trace=node 之后才是上表。

识别信号很直接：三种模式下 GPU kernel 数都精确等于 CPU launch 数。 一个恒等式在三个不同配置下都成立，通常说明你在用两种方式数同一个东西。

工程实现 · 自己写一遍

关键是怎么把图拿出来。三种方式，各有用途。

(1) 自定义 backend：拿到 Dynamo 的原始 FX 图

def capture_fx(fn, *args):
    graphs = []
    def backend(gm: torch.fx.GraphModule, example_inputs):
        graphs.append(gm)
        return gm.forward           # 原样返回，不做任何编译
    torch.compile(fn, backend=backend, dynamic=False)(*args)
    return "\n\n".join(g.print_readable(print_output=False) for g in graphs), graphs

print_readable() 输出的就是上面那段带 shape 标注的 Python 代码。

(2) aot_module_simplified：拿到前向/反向图

from functorch.compile import aot_module_simplified

def backend(gm, inputs):
    def fw(g, i): joint.append(("forward", g));  return g.forward
    def bw(g, i): joint.append(("backward", g)); return g.forward
    return aot_module_simplified(gm, inputs, fw_compiler=fw, bw_compiler=bw)

(3) 环境变量：让 Inductor 把生成的代码落盘

TORCHINDUCTOR_CACHE_DIR=./cache python your_script.py
# 或者更直接：
TORCH_LOGS="output_code" python your_script.py       # 直接打印 Inductor 输出

        XBLOCK : tl.constexpr, R0_BLOCK : tl.constexpr):

    r0_numel = 2048
    RBLOCK: tl.constexpr = R0_BLOCK
    xoffset = tl.program_id(0) * XBLOCK
    xindex = xoffset + tl.arange(0, XBLOCK)[:, None]
    xmask = tl.full([XBLOCK], True, tl.int1)[:, None]
    r0_base = tl.arange(0, R0_BLOCK)[None, :]
    x0 = xindex

    # ---- 第一遍：平方和 ----
    _tmp4 = tl.full([XBLOCK, R0_BLOCK], 0, tl.float32)
    for r0_offset in tl.range(0, r0_numel, R0_BLOCK):
        r0_index = r0_offset + r0_base
        r0_mask = r0_index < r0_numel
        r0_1 = r0_index

                       eviction_policy='evict_last', other=0.0).to(tl.float32)

        tmp2 = tmp1 * tmp1
        tmp3 = tl.broadcast_to(tmp2, [XBLOCK, R0_BLOCK])
        tmp5 = _tmp4 + tmp3

前沿

方向 内容
regional compilation 不编整个模型，只编重复出现的层（如一个 Transformer block），编一次复用 N 层。大幅降低编译时间
torch.compile 与 CUDA Graph 的组合 mode="reduce-overhead" 自动套 graph。vLLM 的 piecewise graph 是更细粒度的手工版（L5.4）
动态形状 LLM 推理的形状每步都变。Dynamo 的符号形状（s0、s1）让一张图覆盖多个形状，代价是生成的 kernel 多一层判断
自定义算子与图 torch.library 让你把手写 CUDA kernel 注册成 aten 算子，从而能出现在图里并参与融合边界的决策
Inductor 的融合规则 目前主要融合逐元素与归约。GEMM 通常不融合（除了 epilogue）。融合决策的启发式是 L2.7 的主题
图级别的量化与重写 把 fp32 图重写成 fp8/int8 图，插入量化/反量化节点。torch.ao 与 llm-compressor 走的都是这条路（L4.3）

陷阱

1. 以为"图"是个抽象概念。 它是一个能打印、能读、带完整 shape 标注的 Python 类。 先导出图节点与边，再判断捕获、分图和融合分别发生在哪里。

2. 在热路径里写 .item() / print(tensor) / if tensor > 0。 会断图，融合机会全没，还有 4.76 µs 的同步（L1.4 实测）。

3. 不看 graph_count 就调优。 图被切成十几段时， 任何融合优化都是白费——先消除断裂。

4. 以为反向图和前向图一样大。 实测 2.3 倍。 而且它需要保存前向的中间值，那是训练显存的大头。

5. 忘了融合会改变数值。 融合后中间值留在寄存器（fp32）， 不融合时可能被写回 bf16 再读出——结果会有微小差异（L4.2）。

6. 以为 Inductor 会融合一切。 它主要融合逐元素与归约。 GEMM 之间不融合，跨 graph break 不融合，有副作用的算子不融合。

自测题

1. 我的模型用了 torch.compile 但只快了 5%。第一步该查什么？

查 graph_count。

expl = torch._dynamo.explain(model)(*example_inputs)
print(expl.graph_count, expl.graph_break_count)
for r in expl.break_reasons:
    print(r)

如果 graph_count 是几十，说明图被切碎了，每段之间不能融合， 而且每段之间都要回到 Python 解释器。融合收益（本章实测 3.68×）基本拿不到。

常见的断裂原因（按频率）： 1. .item() / .tolist() / bool(tensor) —— 需要 GPU→CPU 同步 2. print(tensor) / 日志里带张量 3. 数据依赖的控制流（if tensor.max() > threshold） 4. 不支持的 Python 特性（某些闭包、生成器、第三方库调用）

修断裂比调任何编译参数都重要。

2. 为什么 Inductor 生成的 kernel 里累加器是 fp32，而输入输出都是 bf16？

因为归约的累加必须提精度。

L2.3 实测过：fp32 累加 6700 万个 1.0，在 224 处就完全失效（算出 2²⁴ 而非 2²⁶）。 bf16 只有 8 位尾数，28=256 个数就开始丢——比 fp32 早 65536 倍。

本例是对 2048 个元素求平方和。用 bf16 累加的话： 平方值量级约 1，累加到 256 之后再加 1 就基本无效， 后面 1792 个元素的贡献会大部分丢失。

Inductor 自动做对了这件事（tl.full([XBLOCK, R0_BLOCK], 0, tl.float32)）。

这也是所有 LLM kernel 的铁律：存用低精度，算用高精度。 attention 的 softmax 累加、GEMM 的 K 方向累加，全都是 fp32（L2.4 实测 cuBLAS 也是）。

3. 反向图的签名里有 rsqrt、detach、mul 三个参数。它们是什么？为什么重要？

它们是前向保存给反向用的中间值（saved tensors）。

反向要算 ∂L∂x，需要用到前向的中间结果。 比如 mul_5 = mul_3 × rsqrt 这一步就要用到前向算出的 rsqrt。

为什么重要：这些张量必须在整个前向-反向期间驻留显存。 一个 L 层的模型，每层保存 k 个中间值，显存占用就是 L×k× 张量大小。

对 Qwen3-1.7B、batch=8、seq=2048： 每层保存的激活约 8×2048×2048×2 B≈67 MB， 28 层就是 1.9 GB——而权重才 3.44 GB（L0.2 实测）。

这就是 activation checkpointing 的动机：不保存中间值， 反向时重新前向算一遍。用大约 33% 的额外计算换取大幅的显存节省（L7.1 会实测）。

从图上看，checkpointing 就是把前向图的一段标记为"不保存输出、反向时重跑"。

4. 融合后带宽达到 1440 GB/s（上限的 86%）。还能更快吗？

理论上还有空间，但不多，而且要改算法。

当前的访存量是：读 x 两遍 + 读 w 一遍 + 写 out 一遍。 两遍读 x 是因为"两遍归约"：必须先扫一遍算出均值，才能第二遍归一化。

访存=2×32 MB(读)+32 MB(写)=96 MB

（bf16 输入 16 MB，但转 fp32 后中间量是 32 MB；实际以 bf16 读写。）

改进方向：单遍（online）归约。 用 Welford 算法或类似的在线更新， 一遍扫完同时得到均值和归一化结果——但 RMSNorm 需要先有完整的均值 才能归一化，所以单遍做不到，除非：

  • 把 x 缓存在共享内存/寄存器里：2048 个 bf16 = 4 KB， 一个 block 完全装得下！这样第二遍从 smem 读（L1.1 实测 6.5 周期）而不是显存。 这正是 vLLM 手写 rms_norm_kernel 做的事，也是它能比 Inductor 快的原因。

所以 86% 已经很好，但手写仍有约 1.3 倍的空间—— 代价是失去通用性（要求 hidden 维能装进 smem）。

这呼应 L2.3 的结论：专用打得过通用。
