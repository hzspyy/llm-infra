2.8

把一个算子接进 PyTorch：注册、分发、backward 与 compile

为自定义 kernel 注册 schema、fake 实现和梯度，使其支持 autograd 与 torch.compile。

实测机器 crater (RTX 5090 D, sm_120) · torch 2.13.0+cu130 · CUDA 13.0前置 2.0（dispatcher 与 DispatchKeySet）· 2.2（工具链）· 2.6b / 2.7（编译器栈）

本章回答三个问题

L2 到这里已经会写 kernel（2.1–2.5）、会看编译器（2.6b、2.7）、 会读 dispatcher（2.0）。这一章把它们接起来：把一个自己写的 CUDA kernel 变成 PyTorch 里的一等公民——能求导、能被 torch.compile 捕获、 能在别人的模型里当作普通算子使用。

  1. torch.compile 遇到一个它不认识的算子会怎么办？
  2. 自定义算子怎么参与反向？fake（meta）函数是干什么的？
  3. 注册之后它能被融合吗？为什么？

本章用的算子：

out[i]=∑jrelu(x[i,j]·w[j])

反向（后面会用 gradcheck 验）：

∂L∂x[i,j]=g[i]·w[j]·1[xijwj>0],∂L∂w[j]=∑ig[i]·x[i,j]·1[xijwj>0]

选它是因为：它含一个归约（复用 2.3 的两段式归约结构）、 有两个需要求导的输入、而且反向里有一个很容易忘掉的 relu 掩码—— 后面会故意忘一次，看 gradcheck 能不能抓住。

一 · 裸 kernel 调用不自动具备框架语义

先用 load_inline 编出来，确认它是对的：

前向对不对: max|err| = 5.684e-14
返回类型: <class 'torch.Tensor'>  shape=(64,)

数值没问题。但它在 PyTorch 眼里什么也不是：

l28::fused_scale_sum         **不存在**
aten::add.Tensor             存在

dispatcher 里没有它——它只是一个 pybind 出来的 python 可调用对象。 后果有两个。

第一，没有反向：

out.requires_grad = False   grad_fn = None

autograd 根本不知道发生过这次计算。把它放进模型里，反向传播会在这里断掉， 而且不报错。

第二，torch.compile 装作没看见。 这一条有个陷阱：

explain(): 图数量 1   图断裂 0   捕获算子 1

看起来一切正常。但把捕获到的图打印出来：

def forward(self, L_stack0_ : torch.Tensor):
    l_stack0_ = L_stack0_
    mul = l_stack0_ * 2;  l_stack0_ = None
    return (mul,)

kernel 调用根本不在图里。 图的入参 L_stack0_ 是"栈上第 0 号槽"—— 也就是已经算好的结果。Dynamo 在图外 eager 执行了这次调用， 只从它的返回值开始捕获，于是图里只剩一个 * 2。

设置 fullgraph=True，让未完整捕获的情况显式报错：

Unsupported: Attempted to call function marked as skipped

explain() 报 0 次断裂，不等于全部被捕获

断裂计数只统计捕获过程中被打断的次数； 如果不支持的调用恰好在区域开头，Dynamo 直接从它之后开始， 计数是 0，但你的算子完全在编译范围之外。

判据有两个，都比 explain 的计数可靠： 把图打印出来看有没有你的算子；或者直接上 fullgraph=True。

Dynamo 自己也给了提示（运行时的 UserWarning）：

Dynamo does not know how to trace the builtin `l28_fss...fss_forward`.
This function is either a Python builtin ... or a third-party C/C++ Python
extension (perhaps created with pybind). ... please either wrap it into a
PyTorch-understood custom operator ... or, if it is traceable, use
`torch.compiler.allow_in_graph`.

二 · 注册成一个真正的算子

@torch.library.custom_op("l28::fused_scale_sum", mutates_args=())
def fused_scale_sum(x: torch.Tensor, w: torch.Tensor) -> torch.Tensor:
    return m.fss_forward(x, w)

mutates_args=() 是在告诉框架"这个算子不改写任何输入"。 这不是可选的礼貌信息——functionalization 和内存规划都依赖它， 写错会导致难查的错误。

注册之后 dispatcher 里就有它了：

name: l28::fused_scale_sum
schema: l28::fused_scale_sum(Tensor x, Tensor w) -> Tensor
debug: registered at .../torch/_library/custom_ops.py:1104
alias analysis kind: FROM_SCHEMA
Meta: registered at .../custom_ops.py:1104 :: (none) [ boxed ]
Autograd[alias]: registered at .../custom_ops.py:1104 :: (none) [ boxed ]
CompositeExplicitAutograd[alias]: registered at .../custom_ops.py:1104 :: (none) [ boxed ]

对照 2.0 里 aten::add.Tensor 那张 97 行的表，这里只有三行。注意它落在哪个键上：

key 有 kernel
CUDA False
CPU False
Meta True
Autograd True
CompositeExplicitAutograd True

CUDA 和 CPU 都是 False，而 CompositeExplicitAutograd 是 True： torch.library.custom_op 默认注册的是与后端无关的实现， 由这个别名键覆盖所有后端。（想按设备分别注册，用 custom_op(..., device_types="cuda") 或 register_kernel。）

Meta 和 Autograd 虽然显示 True，注册的是占位实现—— 调用时会报错提示你还没写。接下来两节就是补这两个。

三 · fake（meta）函数：不执行也要知道形状

torch.compile 在追踪时不执行真实计算，而是用 FakeTensor 进行符号推导， 只关心形状和 dtype（2.0 §3.3 里 Meta 键上注册了 1614 个算子，比 CUDA 还多）。 若自定义算子缺少 meta 实现，追踪过程便会直接报错：

TorchRuntimeError
  RuntimeError when making fake tensor call
    Explanation: Dynamo failed to run FX node with fake tensors:
      call_function l28.no_fake.default(*(FakeTensor(..., device='cuda:0', size=(64, 512)), ...

补上：

@no_fake.register_fake
def _(x, w):
    torch._check(x.dim() == 2, lambda: "x 必须是二维")
    torch._check(w.dim() == 1, lambda: "w 必须是一维")
    return x.new_empty(x.shape[0])

它只描述形状与 dtype，不做任何真实计算。 new_empty 分配的是 FakeTensor（追踪时）或真实空张量（不追踪时），里面的值从不被读取。 torch._check 是给符号形状用的断言——它会变成约束求解器的一条约束， 而不是普通的 assert（普通 assert 在动态形状下会强制特化）。

补上之后编译成功，图里的样子：

def forward(self, L_a_ : torch.Tensor, L_b_ : torch.Tensor):
    l_a_ = L_a_
    l_b_ = L_b_
    no_fake_default = torch.ops.l28.no_fake.default(l_a_, l_b_);  l_a_ = l_b_ = None
    mul = no_fake_default * 2;  no_fake_default = None
    return (mul,)

和第一节那个图对比：现在 torch.ops.l28.no_fake.default 在图里， 两个输入也都是真正的图输入（L_a_、L_b_），不再是"栈上算好的值"。

它是图里的一个不透明节点：Inductor 知道它的形状、知道要在这里调用它， 但不知道它内部在算什么。这一点决定了第五节的融合结论。

四 · 反向：注册 + gradcheck

def setup_context(ctx, inputs, output):
    x, w = inputs
    ctx.save_for_backward(x, w)

def backward(ctx, grad):
    x, w = ctx.saved_tensors
    gx, gw = m.fss_backward(grad, x, w)
    return gx, gw

with_grad.register_autograd(backward, setup_context=setup_context)

setup_context 与 backward 分开，是因为前向可能在 no_grad 下运行—— 那时根本不需要保存任何东西。这个拆分让框架可以跳过保存。 （这正是 0.0b 里"前向要为反向存中间量"的那一步， 以及 2.6b 里 AOTAutograd 前向返回 6 个值、其中 5 个给反向的原因。）

gradcheck 通过

Autograd key 现在有 kernel 了: True
gradcheck 通过: True

dx max|err| = 0.000e+00
dw max|err| = 0.000e+00

gradcheck 用有限差分逐元素扰动输入，比较数值雅可比与解析雅可比。 必须用 float64——float32 的舍入误差比差分信号还大。 （本章的 kernel 用 AT_DISPATCH_FLOATING_TYPES 同时支持 float 和 double， 就是为了能跑 gradcheck。这也是真实算子的标准做法。）

失败现场：反向写错，前向完全正确

故意把 relu 的掩码忘掉：

def bad_backward(ctx, grad):
    x, w = ctx.saved_tensors
    gx = grad.unsqueeze(1) * w.unsqueeze(0)      # 少了 1[x*w>0]
    gw = (grad.unsqueeze(1) * x).sum(0)
    return gx, gw

前向仍然正确: max|err| = 0.000e+00
gradcheck 抓到了:
  Jacobian mismatch for output 0 with respect to input 0,
  numerical:tensor([[ 0.5888,  0.0000,  0.0000,  ...,
  analytical:tensor([[ 0.5888,  0.0000,  0.0000,  ...

前向误差精确为 0，反向是错的。 这类 bug 在训练里的表现是 "loss 下降得有点慢"或"某个配置下不收敛"——没有任何一处会报错。 0.0b 里那个"损失曲线看不出问题"的教训，在这里是同一件事的另一面。

gradcheck 是唯一能在写完当场抓住它的工具。写反向就要写 gradcheck， 成本是三行代码。

五 · 不透明算子形成融合边界

不能。自定义算子在 Inductor 眼里是不透明的。

同一个表达式 (op(x, w) * 2).relu() + 1，两种写法：

自定义算子 + 后续逐元素
  Inductor 生成 triton kernel: 1
  图里对外部算子的调用: [..., 'torch.ops.l28.fusible_probe']

等价的纯 torch 写法
  Inductor 生成 triton kernel: 1
  图里对外部算子的调用: [...]（没有外部算子）

自定义算子那条路上，GPU 上实际跑的是我的 kernel + 1 个 Inductor kernel； 纯 torch 那条路上，Inductor 把归约和后续逐元素一起生成了。

时间（4096×4096 fp32，crater）：

写法 时间
纯 torch（编译后） 0.013 ms
我的 kernel（裸调，不含后续算子） 0.018 ms
自定义算子（编译后，含后续算子） 0.027 ms
纯 torch（eager） 0.138 ms

三件事：

  1. 我手写的 kernel（0.018）比 Inductor 生成的整段代码（0.013）还慢， 而且 Inductor 那 0.013 里还包含了后面的 *2、relu、+1。
  2. 包成自定义算子之后是 0.027，比裸调多 0.009 ms：多了一次不透明边界， 后续的逐元素算子只能另起一个 kernel。
  3. 编译相对 eager 有 10.6×，但那个收益纯 torch 就拿到了， 和我写不写 kernel 无关。

六 · 设计取舍

6.1 不透明边界的可组合性与优化限制

Inductor 要融合两个算子，前提是它知道两者在算什么—— 知道循环结构、访存模式、哪些维度可以合并。对一个只有 schema (Tensor x, Tensor w) -> Tensor 的黑盒，这些全都不知道。

可选的设计：

方案 代价
A. 不透明节点（PyTorch 的选择） 无法融合；但注册成本极低，任何语言写的 kernel 都能接
B. 要求提供循环结构描述 能融合；但注册门槛变成"用编译器的 IR 重写一遍"
C. 只允许用 Triton/框架 DSL 写 能融合、能重排；但排除了 CUDA/汇编/闭源库

真实生态里三种都存在：cuBLAS / FlashAttention 走 A； Inductor 自己生成的走 C；torch.library.triton_op 是一条中间路， 让 Inductor 知道这是个 Triton kernel 从而能做一部分处理。

判据是边界划在哪。A 把边界划在"函数调用"这个最小公约数上， 换来的是任何东西都能接进来。这是一个有意识的取舍，不是能力不足。

6.2 自定义算子的功能与性能目标

本章的测量给出了一个直接的判据：若目标是加速，需要你的 kernel 比编译器生成的快， 而且快出的部分能覆盖不透明边界的代价。

本章 kernel 未达到这一目标。一个待核对的实现差异是：一个 block 归约一行（4096 个元素）， grid 只有 4096 个 block，且每行只有一个 block 在做归约—— 2.3 里讲的两段式切分我只做了 block 内那一段。Inductor 生成的版本 按 size_hints={'x': 512, 'r0_': 8192} 两级切分（2.7 §3），并行度更高。

自定义 kernel 通常用于以下情况： 编译器表达不出来的算法（FlashAttention 的在线 softmax + 分块）、 特殊指令（tcgen05、FP4，L1.2）、 融合了编译器不会跨越的边界（PagedAttention 跨 block table 的 gather）。 是否更快仍需与现有实现比较。

6.3 schema、fake 与 autograd 各自负责不同契约

custom_op → register_fake → register_autograd， 对应三个不同的 dispatch key：CompositeExplicitAutograd → Meta → Autograd。 缺哪个就在哪一层失败，而且失败方式不同：

缺什么 什么时候炸 表现
全都没有（裸 pybind） 追踪时 不报错，悄悄留在图外（第一节）
缺 fake torch.compile 时 RuntimeError when making fake tensor call
缺 autograd .backward() 时 报错说算子不支持 autograd
autograd 写错 可能不报错 用 gradcheck、解析梯度与多输入对照检查

最危险的是第一行和最后一行——它们都不报错。 这就是 2.0 §4.6 说的"错误在第几层被发现"： 注册的价值一半在功能，一半在把静默失败变成显式失败。

建议的消融

  1. 把 kernel 改成 2.3 那样的两段式归约（先分块归约到临时数组，再归约一次）， 看能不能追上 Inductor 的 0.013 ms。这是本章唯一没做的实验， 也是判断"值不值得手写"的关键一步。
  2. 去掉 mutates_args=()，改成声明它会改写 x，看 functionalization 在图里插入了什么（会多出一次拷贝）。
  3. 用 torch.library.opcheck(op, (x, w)) 跑一遍完整的注册自检—— 它会同时检查 schema、fake、autograd 与 functionalization 的一致性， 比只跑 gradcheck 覆盖面大。
  4. 把 register_fake 里的 x.new_empty(x.shape[0]) 故意写成 x.new_empty(x.shape[0] + 1)，看错误在哪一层被发现—— 注意 eager 完全正常，编译路径才会报错。

八 · 陷阱

  1. explain() 报 0 次断裂不等于全部被捕获。 不支持的调用如果在区域开头， Dynamo 直接从它之后开始，计数是 0 而你的算子在图外。 用 fullgraph=True 或把图打出来。
  2. 裸 pybind 函数没有反向，且不报错。 requires_grad=True 的输入进去， 出来的张量 grad_fn=None，反向在这里静默断掉。
  3. custom_op 默认注册到 CompositeExplicitAutograd，不是 CUDA。 查 _dispatch_has_kernel_for_dispatch_key(name, "CUDA") 会得到 False， 这不是注册失败。
  4. gradcheck 必须用 float64。 float32 的舍入误差比有限差分的信号还大， 会给出假的失败或假的通过。
  5. 反向写错前向不受影响。 本章实测前向 max|err| = 0.000e+00， 反向完全错。写反向就写 gradcheck。
  6. mutates_args 写错会导致难查的错误，因为 functionalization 和内存规划都信任这个声明。
  7. fake 函数里不要做真实计算，也不要读输入张量的值——追踪时那是 FakeTensor， 没有数据。要断言形状关系用 torch._check，不要用 assert （后者在动态形状下会强制特化）。
  8. 自定义算子是融合边界。 包一层的代价在本章是 0.009 ms， 小算子上可能比 kernel 本身还贵。

九 · 自测题

1. 你把一个 pybind 出来的 kernel 直接用在模型里，训练能跑、loss 也在降，但精度始终差一截。最可能是什么？

那个 kernel 没有注册成算子，所以它没有反向。经过它的那条路径上， autograd 图是断的——它前面的所有参数收不到梯度。

loss 仍然会降，因为其它路径（比如残差分支、后面的层）照常更新。 这就是它难查的原因：没有任何报错，只是一部分参数从未被训练过。

判据：拿一个 requires_grad=True 的输入过一遍，检查输出的 grad_fn 是不是 None；或者 .backward() 之后检查上游参数的 .grad 是不是 None。

2. fake 函数为什么不能直接调用真实实现来得到输出形状？

因为追踪时传进来的是 FakeTensor：它有形状、dtype、device， 但没有数据，底层也没有真实显存。真实 kernel 会去读 data_ptr， 那里什么都没有。

而且在动态形状下，x.shape[0] 可能是一个符号量 s0 而不是具体整数， 真实 kernel 也没法拿它去启动 grid。

fake 函数的职责就是从"输入的形状"算出"输出的形状"， 这是一个纯符号运算，不碰任何数据。

3. 注册之后 torch.compile 不再图断裂了，为什么性能反而可能变差？

因为自定义算子是不透明节点。Inductor 不能把它前后的算子融进它， 也不能拆开重排。

本章实测：等价的纯 torch 写法编译后 0.013 ms（归约和后续逐元素融在一起）， 自定义算子那条路 0.027 ms（我的 kernel + 另起一个 kernel 做后续逐元素）。 慢了一倍多，尽管两者数值完全一致。

所以注册解决的是正确性和可组合性（有反向、能进图、别人能用）， 不自动带来性能。性能要单独量。

4. 什么情况下写自定义算子是划算的？给出一个可操作的判据。

判据：你的 kernel 的时间 + 不透明边界的代价 < 编译器为同一段表达式生成的时间。

三个量都要实测： 1. 你的 kernel 裸调的时间； 2. 包成自定义算子后、连同上下游算子一起编译的时间； 3. 等价纯 torch 写法编译后的时间。

本章这个例子里三个数是 0.018 / 0.027 / 0.013——不划算， 因为我的归约只做了 block 内那一段，并行度不如 Inductor 的两级切分。

真正划算的场景通常是编译器表达不出来的算法（FlashAttention 的 在线 softmax 分块）、需要特殊指令（FP4、tcgen05）， 或者要跨越编译器不会跨越的边界（PagedAttention 的 block table gather）。

5. 缺 fake、缺 autograd、autograd 写错，这三种情况分别在什么时候暴露？哪个最危险？
  • 缺 fake：torch.compile 时报 RuntimeError when making fake tensor call。eager 正常。
  • 缺 autograd：.backward() 时报错说算子不支持 autograd。前向正常。
  • autograd 写错：可能不报错；前向正确不保证梯度正确，需要独立检查反向。

最危险的是第三种，其次是完全不注册（第一节那种：悄悄留在图外，也不报错）。

一般规律：一个失败越晚被发现、越不产生显式信号，就越贵。 完整的注册和检查有助于尽早发现这些不一致。
