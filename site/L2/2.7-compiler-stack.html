2.7

PyTorch 编译器：捕获、分图与代码生成

介绍编译守卫、重编译、动态形状和 autotune，比较不同编译后端的行为。

实测机器 crater (RTX 5090 D, sm_120) · torch 2.13.0+cu130 · CUDA 13.0前置 2.6b（三段式的产物长什么样）· 2.0（DispatchKeySet）· 2.3（访存阶梯）

本章回答三个问题

2.6b 已经把 Dynamo 的 FX 图、AOTAutograd 的联合图、Inductor 生成的 Triton 源码逐字打印过了。那一章问的是"编译产物长什么样"。这一章问的是别的：

  1. 编译好的代码凭什么可以复用？Dynamo 每次调用到底检查什么？
  2. 什么时候这份代码失效？失效之后会发生什么——报错，还是悄悄变慢？
  3. mode="max-autotune" 真的更快吗？Inductor 在哪些形状上打不过 cuBLAS？

这一章有三个负面结果

本章测出来的三件事都和常见说法相反：max-autotune 在测过的三种形状上全部更慢； 动态形状让一个归约慢 5300 倍；"撑爆编译缓存会退回 eager"这个说法不准确。 每一条都给了判据和复现命令。原始输出在 results/crater/compile/27_compiler_stack.txt。

一 · 守卫：编译结果的有效期

torch.compile 不是"把函数编译一次然后一直用"。它编译的是 某一类输入下的这个函数，并把"哪一类"写成一串检查，叫守卫（guard）。 每次调用先跑守卫，全过才用编译好的代码。

对这个函数：

def f(x, alpha):
    return (x * alpha).relu().sum()

Dynamo 装了 15 行守卫。原文（节选，完整的在 lab 输出里）：

TREE_GUARD_MANAGER:
+- RootGuardManager
| +- GLOBAL_STATE: ___check_global_state() against {"allow_bf16_reduce":0,"allow_fp16_reduce":0,"allow_tf32":f
| +- TORCH_FUNCTION_MODE_STACK: ___check_torch_function_mode_stack()
| +- DEFAULT_DEVICE: utils_device.CURRENT_DEVICE == None
| +- GuardManager: source=L['x'], accessed_by=FrameLocalsGuardAccessor(key='x', framelocals_idx=0)
| | +- TENSOR_MATCH: check_tensor(L['x'], Tensor, DispatchKeySet(CUDA, BackendSelect, ADInplaceOrView, Autogra
| | +- DIMENSION_DYNAMIC_MARKING_GUARD: hasattr(L['x'], '_dynamo_dynamic_indices') == False
| +- GuardManager: source=L['alpha'], accessed_by=FrameLocalsGuardAccessor(key='alpha', framelocals_idx=1)
| | +- EQUALS_MATCH: L['alpha'] == 2.0

以下三处分别说明：

  • TENSOR_MATCH 里出现了 DispatchKeySet(CUDA, BackendSelect, ADInplaceOrView, Autograd…)。 这正是 2.0 里那个 64 位位图。守卫检查的不只是形状和 dtype， 还包括这个张量会分发到哪条路径上——因为分发路径变了，生成的代码就不对了。
  • EQUALS_MATCH: L['alpha'] == 2.0。 浮点参数 alpha 被当成编译期常量 折进了代码里。传 3.0 进来这份代码就不能用。
  • GLOBAL_STATE 检查的是 allow_tf32、allow_bf16_reduce 这类全局开关。 在编译之后改 torch.backends.cuda.matmul.allow_tf32，守卫会失败。

守卫每次调用都要跑一遍，所以它本身是运行时开销。 这也解释了为什么 torch.compile 对极小的函数可能是负收益。

二 · 什么会让编译结果失效

同一个函数，依次喂不同的东西，看累计编译次数：

调用 累计编译次数 本次新增
基准 (8,8) f32 cuda 1 1
同形状同 dtype 再来一次 1 0
换形状 (16,16) 2 1
再换形状 (32,32) 2 0
换 dtype bf16 3 1
换维数 (8,8,8) 4 1
换 device cpu 5 1
非连续（转置） 6 1

第 3 行和第 4 行是这张表的重点：第一次换形状会重编译，第二次不会。 Dynamo 第一次把形状特化成常量；发现形状会变之后， 它把这一维改成符号量重编译一次，之后所有形状复用同一份代码。 这个机制叫 automatic dynamic。

最后一行中，转置触发了重编译。因为 stride 变了， 生成的访存代码不一样——2.0 里那条 stride 公式，在这里表现为一次重编译。

标量参数也会自动去特化

该版本对这些 Python int 输入没有逐值生成新代码：

k = 0..11 时累计编译次数: [1, 2, 2, 2, 2, 2, 2, 2, 2, 2, 2, 2]

只编译了 2 次，和形状是同一个机制。不要假设标量一定会特化。

rank 变化会触发新的特化

维数（rank）没法做成动态——张量有几维决定了循环有几层。 用维数去撑：

   维数       累计编译  说明
    1          1
    2          2
   ...
    8          8  <- 卡在 cache_size_limit
    9          8  <- 卡在 cache_size_limit
   12          8  <- 卡在 cache_size_limit

cache_size_limit 默认 8（accumulated_cache_size_limit 是 256）。 到了上限，Dynamo 打印一条警告然后不再为这个函数编译：

torch._dynamo hit config.recompile_limit (8)
   function: 'probe' (<stdin>:3)
   last reason: 0/7: tensor 't' rank mismatch. expected 7, actual 8

「撑爆缓存就会退回 eager」——这个说法不准确

我按这个说法做了测量，数字对不上，于是把它拆开测：

撑爆，但 big 那条缓存还在（rank 2..13）      0.019 ms   编译数=8
撑爆，且 big 那条被挤掉（rank 1..12）       80.100 ms   编译数=8
纯 eager 参照                            0.025 ms

第一行说明撑爆缓存本身不贵：只要还有一条守卫对得上， 照样用编译好的代码，Dynamo 连编译器都不进（frames 计数器增量为 0）。

第二行那 80 ms 也不是"退回 eager"——eager 只要 0.025 ms， 退回 eager 应该是 0.025 而不是 80。慢了 3200 倍，方向都不对。

真正的原因在下一节。这里先记一个方法上的教训： 当一个解释预测的是"变慢一点"而你测到"慢三千倍"时，那个解释是错的， 不是"程度上有出入"。

三 · 动态形状的真实代价

上一节那 80 ms 的来源：rank 1 的缓存被一个 2 元素的张量顶掉， 触发 automatic dynamic，于是那个归约变成了动态形状版本。

直接对照静态与动态（4M 元素 = 16 MiB，crater）：

表达式 eager 静态 动态 动态/静态
归约 (t*2).relu().sum() 0.025 ms 0.015 ms 80.096 ms 5342.6×
逐元素 (t*2).relu()*1.5 0.025 ms 0.012 ms 0.015 ms 1.2×

差别在生成的 kernel 上，size_hints 一眼看出来：

归约   静态 size_hints ["size_hints={'x': 512, 'r0_': 8192}", "size_hints={'x': 1, 'r0_': 512}"]
归约   动态 size_hints ["size_hints={'x': 1, 'r0_': 2}"]

逐元素 静态 size_hints ["size_hints={'x': 4194304}"]
逐元素 动态 size_hints ["size_hints={'x': 4194304}"]
  • 逐元素不受影响。 kernel 本来就是一维网格，元素个数当运行时参数传进去， grid 大小在启动时算。形状是不是编译期已知，不改变并行结构。
  • 归约塌了。 静态版是 {'x': 512, 'r0_': 8192}：512 个 block， 每个块归约 8192 个元素，再来第二个 kernel 归约那 512 个部分和—— 这就是 2.3 里那个两段式归约。动态版只有 {'x': 1}： 形状未知时 Inductor 无法决定怎么切分归约维，退化成 一个 block 顺序扫完整个张量。

并行度从 512 掉到 1。这不是"少了一点常量折叠"，是并行结构没了。 按带宽算：80 ms 搬 32 MiB（读+写）约等于 0.4 GB/s， 而这张卡的 DRAM 上限是 1519 GB/s（L1.1）。

这条对服务的直接含义

变长输入是推理服务的常态。一旦某个含归约的函数被 automatic dynamic 转成动态版， 它可能在不报任何错的情况下慢几千倍。 LayerNorm、softmax、sum、mean、max 全是归约。

可操作的做法： 1. 用 torch._logging 打开 recompiles，观察哪些函数在反复重编译。 2. 对确实变长的维度用 mark_dynamic 显式声明，而不是让它自动发生—— 至少你知道哪些 kernel 是动态版。 3. 更常见的工程解法是分桶：把长度补齐到有限几档，让每一档都是静态形状。 vLLM 捕获若干个固定 batch 尺寸的 CUDA Graph（2.6b），正是这个思路。 4. 关键路径上直接量一遍：静态与动态各跑一次，比值不该超过个位数。

这一条的边界

测的是 torch 2.13.0 + Inductor 在 sm_120 上的行为，工作负载是一维归约。 更高维的归约（例如 LayerNorm 沿最后一维）通常只有最后一维参与归约， 而那一维往往是静态的（hidden_size），塌陷程度可能完全不同。 不要把 5342× 这个数字外推到别的算子上，要外推的是那个方法： 比 size_hints，看并行度有没有掉。

四 · 融合边界：Inductor 在哪里停下来

4M 元素、fp32，数生成了几个 Triton kernel：

表达式 triton kernel 数 eager ms compiled ms 加速
5 个逐元素算子 1 0.440 0.116 3.78×
逐元素 + 一个归约 2 0.289 0.084 3.43×
归约之后再逐元素 2 0.193 0.084 2.30×
两个独立归约 4 0.157 0.090 1.74×
中间要写出去（转置后再归约） 2 0.287 0.045 6.36×

读法：

  • 连续的逐元素算子全部融进一个 kernel。 5 个算子 1 个 kernel， 中间结果不落显存——这就是 2.3 讲的那个收益，3.78×。
  • 归约是一道边界。 逐元素可以融进归约的前面（第 2 行： *2、+、relu、*1.5 都并进了归约 kernel）， 但归约的结果要等所有块都算完，所以后面的算子进不去同一个 kernel。
  • 两个独立归约给了 4 个 kernel，因为每个归约都是两段式。

图断裂是另一回事：它发生在捕获阶段，不是代码生成阶段。

图数量 2  断裂 1
原因: Unsupported Tensor.item() call with capture_scalar_outputs=False

.item() 要把值搬回 host 才能参与 python 的 if， Dynamo 只能在这里把图切开、交回 python、再从下一句重新开始捕获。 这和 2.0 里那个".item() 会强制一次同步"是同一件事的两个侧面： 它既是运行时的同步点，也是编译期的边界。

五 · 设计取舍

5.1 守卫为什么是一棵树，而不是一个哈希

最省事的设计是把输入特征拼成一个 key 去查哈希表。Dynamo 没这么做， 它生成的是一棵 TREE_GUARD_MANAGER。原因可以从上面那份原文读出来：

守卫要检查的东西不在一个层级上。 有全局状态（allow_tf32）、 有线程局部状态（torch function mode stack）、有每个参数的属性、 还有参数的参数（L['x'].__class__）。哈希 key 要求你先把所有特征取出来， 而树可以短路——第一层不过就不必再去访问后面的字段。 考虑到守卫在每次调用的热路径上，这个差别是实打实的。

代价是：守卫的失败原因变成一条路径而不是一个值， 所以诊断要靠 TORCH_LOGS=recompiles 打出"哪一条守卫在第几号缓存上失败了"。 上面那条 last reason: 0/7: tensor 't' rank mismatch. expected 7, actual 8 就是这个格式：0/7 是第 0 号 code、第 7 号缓存项。

5.2 automatic dynamic：把猜错的代价推迟到第二次

设计空间里有三个选择：

方案 做法 代价
A. 一律静态 每个形状编一份 形状一多就爆缓存
B. 一律动态 从不特化 每个 kernel 都放弃形状信息——本章测到归约慢 5342×
C. 先静态，被打脸再转动态 automatic dynamic 第一次遇到新形状要多编译一次

PyTorch 选 C。这个选择的假设是"大多数程序的大多数张量形状是固定的"， 对训练基本成立。但推理服务恰恰是反例：序列长度天生变长。

于是就有了本章第三节那个坑：C 的失败模式比 B 更隐蔽—— B 至少是一致地慢，C 是平时很快、某次输入之后突然慢几千倍， 而且触发条件（第二次见到不同形状）在测试里很容易碰不到。

这是一个具有普遍意义的工程判断：当一个系统用"先猜、猜错再改"来降低成本时， 要问的是"猜错之后的状态有多差"，而不只是"猜错的概率有多大"。

5.3 为什么 vLLM 不把整个模型交给 Inductor

下一节的测量会显示 Inductor 在 GEMM 上打不过 cuBLAS。 结合 2.6b 看到的 splitting_ops：vLLM 的做法是 让 Inductor 做它擅长的（逐元素融合、layout），把 GEMM 和 attention 留给专用库，再用 CUDA Graph 收掉提交开销。 三件事由三种机制分别负责，而不是指望一个编译器全包。

六 · autotune 的收益与适用形状

三种形状，都是 bf16。方阵代表 prefill，瘦长的两个代表 decode：

方阵 4096×4096×4096

mode 编译 s 运行 ms TFLOP/s 相对 eager
eager (cuBLAS) — 0.6446 213.2 1.00×
default 0.3 0.6367 215.8 1.01×
max-autotune 0.0 0.6976 197.0 0.92×

瘦长 8×4096×4096（decode 形状）

mode 编译 s 运行 ms GB/s 相对 eager
eager (cuBLAS) — 0.0230 1465.9 1.00×
default 0.2 0.0232 1454.1 0.99×
max-autotune 1.5 0.0360 935.2 0.64×

瘦长 1×4096×11008（decode + FFN）

mode 编译 s 运行 ms GB/s 相对 eager
eager (cuBLAS) — 0.0325 2775.1 1.00×
default 0.1 0.0614 1468.0 0.53×
max-autotune 0.8 0.1523 592.5 0.21×

在测过的三种形状上，max-autotune 全部比 eager 慢， 而且越是 decode 形状越慢。原因是 max-autotune 会用 Inductor 自己的 Triton GEMM 模板去替换 aten::mm（也就是 cuBLAS）， 然后在候选配置里挑最好的——但"一组候选里的最好"不等于"比 cuBLAS 好"。 default 模式保留 cuBLAS，所以基本打平。

方阵那一行还能交叉验证：cuBLAS 的 213.2 TFLOP/s 对上 L1.1 实测的 bf16 上限 232 TFLOP/s，是 92%。已经没多少可赢的了。

2775 GB/s 又一次超过了 DRAM 上限

第三个形状里 eager 报 2775.1 GB/s，而这张卡 DRAM 上限是 1519 GB/s。 和 2.0 里那次一样：权重 4096×11008×bf16 = 86 MiB，装得进 96 MiB 的 L2。 所以这是 L2 带宽，不是 DRAM 带宽。 反复出现同一个陷阱，说明「先算工作集、再和 roofline 比」应该是条件反射。

七 · 广度：几条不同的编译路线

8 层 Block、batch=1、bf16——这是 launch 开销占比最高的区间（L1.4）。 两种计时都报：紧凑循环（CPU 提交能和 GPU 重叠）与每次同步 （服务里逐 token 返回时看到的那种）。

路线 紧凑循环 ms 加速 每次同步 ms 加速
eager 0.2074 1.00× 0.2193 1.00×
compile/aot_eager 0.2199 0.94× 0.2400 0.91×
compile/inductor 0.1842 1.13× 0.2130 1.03×
compile/reduce-overhead 0.1522 1.36× 0.1947 1.13×
compile/max-autotune 0.1728 1.20× 0.2143 1.02×
  • aot_eager 比 eager 还慢。 它只做图捕获与 AOTAutograd，不生成代码， 是给编译器开发者用的调试后端。出现在这张表里是为了说明 "接了 torch.compile" 不等于"变快了"。
  • reduce-overhead 赢得最多（1.36×），因为它在 Inductor 之上加了 CUDA Graph。 这个区间的瓶颈就是提交次数——和 2.6b 测到的"图把 CPU 侧 launch 从 14,003 降到 863"是同一件事。
  • 两列计时不一样。 紧凑循环里 CPU 提交能藏在 GPU 执行后面， 加速看起来更大；每次同步则暴露真实的单次延迟。 报加速比时必须说明是哪一种，否则同一份代码可以报出 1.36× 或 1.13×。

torch.export：另一条路

导出成功：90 个节点，40 个 call_function
  aten.linear.default                              16
  aten.layer_norm.default                          8
  aten.gelu.default                                8
  aten.add.Tensor                                  8

8 层 × 2 个 linear = 16 个 aten.linear，逐项对得上。

torch.export 与 torch.compile 的关键区别不是快慢，是图里还有没有 python。 compile 生成的代码仍然活在 python 进程里，靠守卫决定走哪条路； export 产出一个不含 python 控制流的完整图，可以交给 AOTInductor 编成 .so 脱离 python 运行时部署。代价是它要求整个模型可以被完整捕获—— 任何一处 .item()、任何数据相关的控制流都会让它失败，而不是像 compile 那样退回 python 继续跑。

尚未实测的后端与复现条件

torch._dynamo.list_backends() 在这台机器上还有两项本章没用：

  • cudagraphs —— 只做 CUDA Graph 捕获，不做 codegen。 它和上表的 reduce-overhead 目标相同（都是压 launch 开销）， 但 reduce-overhead 是 Inductor 之上再加图，两件事都做，所以更快。 vLLM 则自行管理图的捕获时机、 捕获哪些 batch size、padding 到哪一档，并根据请求的形状分布调整配置（见 5.3、5.4）。
  • openxla —— 走 XLA，主要面向 TPU 和 XLA 生态。 本书的硬件底座全是 NVIDIA GPU，这条路线不在范围内，也没有测。

未实测的编译后端

TensorRT 与 ONNX Runtime 这两条路线没有测——crater 的学习环境里没装， 而在共用 vLLM venv 里装它们会动到别的实验的依赖。 所以本章的"广度"只覆盖了 PyTorch 自己的几个后端。

补充对照时，应在单独的虚拟环境中 装 onnxruntime-gpu 与 torch-tensorrt，用同一个 Stack 模块导出对照， 比较三件事——图节点数、算子融合结果、同一批形状下的每次同步延迟。 两条路线的性能仍为 UNVERIFIED。

八 · 陷阱

  1. 以为标量参数一定会特化。 实测 python int 和形状一样走 automatic dynamic， 0..11 只编译了 2 次。
  2. 以为撑爆 cache_size_limit 就是退回 eager。 只要还有守卫对得上， 照样用编译好的代码；对不上时的慢也不是 eager 的慢。
  3. 动态形状 + 归约 = 并行度塌成 1。 本章实测 5342×。 比 size_hints 是最快的判据。
  4. max-autotune 不保证更快。 本章三种形状全部更慢，decode 形状最差 0.21×。 它换掉的是 cuBLAS，而 cuBLAS 在方阵上已经到 92% 峰值。
  5. aot_eager 不是"更快的 eager"，它是调试后端，比 eager 慢。
  6. 报加速比不说计时方式。 同一份代码紧凑循环 1.36×、每次同步 1.13×。
  7. 忘了算工作集是否超过 L2。 本章又一次测出 2775 GB/s > DRAM 上限 1519 GB/s。
  8. 改全局开关会让守卫失效。 编译之后再改 allow_tf32 会触发重编译， GLOBAL_STATE 守卫就是干这个的。

十 · 自测题

1. 一个函数在测试里 `torch.compile` 后快 2 倍，上线后吞吐反而下降。列出三个可能原因和各自的判据。
  • 反复重编译：线上输入的形状/dtype/rank 比测试里多。 判据：TORCH_LOGS=recompiles，或读 torch._dynamo.utils.counters["stats"]["unique_graphs"]。
  • automatic dynamic 把含归约的 kernel 转成了动态版：本章实测可以慢几千倍。 判据：比静态与动态两次编译的 size_hints，看并行度有没有掉。
  • 计时方式不同：测试用紧凑循环（CPU 提交与 GPU 重叠）， 线上是每个 token 同步一次。本章同一份代码两种计时分别是 1.36× 和 1.13×。 判据：用每次同步的方式重测。

还有一个常见但本章没测的：编译发生在第一次请求上，冷启动延迟被算进了 P99。

2. 为什么 `.item()` 会造成图断裂，而 `.sum()` 不会？

.sum() 的结果仍是一个 GPU 上的张量，可以继续作为图里的节点参与后续算子， Dynamo 不需要知道它的值。

.item() 要把值搬回 host 变成一个 python 数，通常是为了参与 python 的 if/while。Dynamo 在追踪时并不执行真实计算，拿不到这个值， 也就无法决定走哪个分支，只能把图切开、交回 python 执行、再从下一句重新捕获。

（capture_scalar_outputs=True 可以让它用未定符号继续追踪， 代价是后续所有依赖这个值的形状都变成 unbacked symint，约束求解会更难。）

3. 你的模型里有一个 `LayerNorm`，输入形状是 `(B, S, 4096)`，B 和 S 都变长。哪一维动态是危险的？

LayerNorm 沿最后一维（4096，hidden_size）归约，这一维是静态的。 B 和 S 只是"有多少行要各自归约一次"，对应 kernel 的 x 维（并行维）， 形状未知不影响归约维的切分策略。

所以这个例子里 B、S 动态大概率是安全的，危险的是归约维本身动态—— 例如对变长序列做 x.sum(dim=1)（沿序列长度归约）。

这一解释尚待验证。可以比较 size_hints： 把 B、S 换几个值编译，看归约那一维的 hint 有没有从具体数字变成 1。 自测题 9.1 就是让你去做这件事。

4. `max-autotune` 花了 1.5 秒编译，结果比 eager 慢 36%。它做错了什么？

这组结果只说明选中的编译路径在当前基准下慢于 eager。max-autotune 的候选后端由版本与配置决定，可能包括 ATen/cuBLAS 和 Triton 等实现；不能仅凭时间断言候选集排除了 cuBLAS。

应保留 autotune 日志、实际生成代码和计时口径，检查调优阶段与正式测量是否一致。一组候选中的最快值也不保证在所有调用方式下最快。

5. 守卫为什么要检查 DispatchKeySet？形状和 dtype 不够吗？

不够。同样形状、同样 dtype 的张量，可能是稠密的也可能是稀疏的， 可能在 CUDA 上也可能在 meta 上，可能带 autograd 也可能被 functorch 包着。 这些差别决定了 a + b 最终分发到哪个 kernel（2.0 那张 97 行的分发表）。

Inductor 生成的代码是针对某一条分发路径的。路径变了，代码就不适用。 所以守卫直接检查那个 64 位位图——它正是"这个张量会走哪条路"的完整编码。
