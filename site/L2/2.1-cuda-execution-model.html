2.1

CUDA 执行模型与 CUDA Graph

通过分支、驻留资源、多流和线程块扫描，理解 CUDA 执行与并行度约束。

实测机器 crater (RTX 5090 D, sm_120) · CUDA 13.0.88 · driver 580.95.05前置 L1.1（内存层次与 Little's Law）· L1.4（launch 路径）

本章回答三个问题

  1. warp 分支发散的代价是不是"N 路发散就慢 N 倍"？实测和理论差多少，为什么？
  2. 占用率（occupancy）越高越快吗？memory-bound 与 compute-bound 的答案一样吗？
  3. 为什么 grid = 1021 会比 grid = 1020 慢 17%？

CUDA 用三个层次组织工作：线程执行代码，线程组成 block，多个 block 组成 grid。 GPU 的 SM 接收并执行 block；资源允许时，一个 SM 可以同时容纳多个 block。 occupancy（占用率）描述常驻 warp 数相对于硬件上限的比例， 并不直接表示 GPU 有多忙，也不直接表示程序有多快。

心智模型：三层调度，每层都有自己的"整数倍"

机制拆解

分支发散：实测 6.02×，理论 8×

在 SIMT 执行模型中，同一 warp 的 32 个线程由同一个 warp 调度器驱动。当遇到条件分支且线程走向不同分支路径时，硬件必须依次执行各分支路径，并通过活跃线程掩码（active mask）或谓词寄存器屏蔽非目标线程。现代 Volta 及更新架构引入了独立线程调度（Independent Thread Scheduling），使线程具备各自的调用栈与程序计数器，但底层执行单元依然遵循锁步发射原理。

实验：让每条分支做完全相同的工作量（一条 fmaf），唯一的区别是有几条路：

int branch = (threadIdx.x % 32) % ways;      // ways=1 时全 warp 走同一条
for (int it = 0; it < iters; ++it) {
    switch (branch) {
        case 0: acc = fmaf(acc, 1.0001f, 0.1f); break;
        case 1: acc = fmaf(acc, 1.0002f, 0.2f); break;
        ...
    }
}

实测：

发散路数 耗时 ms 相对 1 路 理论
1 3.912 1.00× 1×
2 5.653 1.45× 2×
4 12.838 3.28× 4×
8 23.544 6.02× 8×

实测始终低于理论。 原因是编译器把短分支转成了谓词执行（predication）： 不跳转，两条路的指令都发，用谓词寄存器决定哪些线程的结果生效。

这样省掉了分支指令与流水线冲刷，但算力照付——所以还是慢，只是没那么慢。 L0.1 的 SASS 原始现场里那 273 条 FSEL（条件选择）和 225 条 ISETP（置谓词）， 就是谓词执行的实物。

什么时候真的会跳转

分支体足够长时，编译器会判断"两边都算"不划算，改用真正的跳转 + 掩码 （SASS 里是 BSSY/BSYNC 配对）。这时代价才接近 N 倍。

一般规律：短分支 ≈ 谓词执行（算力惩罚），长分支 ≈ 真发散（时间惩罚）。 两种都要避免，但前者温和得多。

占用率：1 → 2 有用，2 → 6 无用

「提高占用率」是最常被误当成目标的指标。用共享内存做旋钮 （只改占用率、算法完全不变）实测：

smem/block 驻留 block/SM memory-bound (GB/s) compute-bound (TFLOPS)
96 KB（动态） 1 1545.0 —
64 KB（动态） 1 1546.1 —
48 KB 2 1678.8 115.5
32 KB 3 1687.3 115.6
16 KB 5 1694.5 115.9
8 KB 6 1699.3 116.4
1 KB 6 1685.1 116.2

两个结论：

(1) 1 → 2 block/SM 涨 9%，2 → 6 完全不涨。 这精确复现了 L1.1 的 Little's Law 结果：带宽-延迟积是 536 KB， 2 block/SM（2720 warp × 512 B 在途）就已经超过它。再多的 warp 无处可用。

(2) compute-bound 对占用率几乎完全不敏感（115.5 → 116.4，差 0.8%）。

因为它靠的不是线程级并行，而是指令级并行（ILP）——kernel 里写了 4 条独立的 FMA 链：

float x0 = a, x1 = a + 1, x2 = a + 2, x3 = a + 3;   // 4 条独立链填流水
for (int i = 0; i < iters; ++i) {
    x0 = fmaf(x0, b, c); x1 = fmaf(x1, b, c);
    x2 = fmaf(x2, b, c); x3 = fmaf(x3, b, c);
}

一个 warp 自己就能填满 FMA 流水线，不需要别的 warp 来接力。

顺带一个数字：116 TFLOPS 是 CUDA core 的 FP32 吞吐。 对照 L1.2 测出的 tensor core bf16 251.9 TFLOPS —— tensor core 快 2.2 倍。 核算一下：170 SM×128 FP32 单元×2 FLOP×2.9 GHz=126 TFLOPS， 实测 116 = 92%，对得上。

「提高占用率」不是目标

占用率是掩盖延迟的手段。一旦延迟已经被掩盖住（本机 2 block/SM 就够了）， 再提高它只会挤占寄存器和共享内存，反而伤害每线程的工作效率。

L1.1 的自测题 4 讲过同一件事：GEMM 的 tile 从 128×128 缩到 64×64 能让占用率翻倍， 但数据复用率减半，净效果是变慢。唯一的目标是墙钟时间。

多流并发：只有 kernel 占不满 GPU 时才有意义

用一个只占 24% SM 的小 kernel（42 blocks / 170 SM）：

并发 kernel 数 同一条流 各自一条流 重叠倍数
1 0.316 ms 0.330 ms 0.96×（略亏）
2 0.627 ms 0.322 ms 1.95×
4 1.254 ms 0.333 ms 3.77×

1 个 kernel 时多流是净亏损（多一次流切换开销）。 2 个和 4 个时接近线性加速——因为 4 × 24% = 96%，正好把 GPU 填满。

这直接对应推理里的场景：decode 每步有 444 个 kernel（L0.1 实测）， 其中 RMSNorm、RoPE、SwiGLU 这些小算子在 batch=1 时根本占不满 GPU。 理论上可以多流并发，但实际上它们之间有数据依赖（层与层串行）， 所以真正的解法是融合（L2.7）而不是并发。

多流真正有用的地方是无依赖的工作：H2D 传输与计算重叠（L1.3）、 不同请求的 prefill 与 decode 重叠、以及 CPU 侧调度与 GPU 执行重叠（L5.4）。

尾效应：耗时是阶梯，不是斜线

这是本章最实用的一个结论。

一"波"能同时驻留的 block 数 = SM 数 × 每 SM 可驻留 block 数。 本机对这个 kernel 是 170×6=1020。扫描 grid 大小：

每 SM 可驻留 6 个 block ⇒ 一波 = 1020 个 block
blocks    波数    耗时 ms    每 block 摊销 µs
510       0.50      0.611        1.20
1018      1.00      1.074        1.05
1019      1.00      1.075        1.06
1020      1.00      1.080        1.06
1021      1.00      1.263        1.24    ← 跨过波次边界，跳了一台阶
1022      1.00      1.265        1.24
2039      2.00      2.096        1.03
2040      2.00      2.096        1.03
2041      2.00      2.264        1.11    ← 又一个台阶
3060      3.00      3.100        1.01
3061      3.00      3.271        1.07    ← 又一个

1020 → 1021 仅仅增加了 1 个 block，整体耗时却跳增了 17%。 在硬件调度中，当首批 1020 个 block 刚好占满全卡 170 个 SM 时，第 1021 个 block 必须等待某个 SM 执行完毕并释放资源后才能被调度。此时全卡 170 个 SM 中只有 1 个 SM 在忙碌，其余 169 个 SM 全部处于闲置空等状态——这正是 GPU 计算中经典的尾效应（tail effect）。

而在同一波次内部（如 1018 → 1020），由于未饱和的 SM 拥有空闲并发槽位，增加少量 block 可以被并发吞吐完全吸收，耗时几乎保持水平（1.074 ms vs 1.080 ms）。这一现象揭示了网格规模（grid size）设计的核心准则：尽量让总 block 数接近或整除单波容量，避免因为多出几个零散 block 而拖累整批执行的尾延迟。

这解释了三件事：

  1. grid 要按「SM 数 × 每 SM 可驻留 block 数」对齐。 多一个 block 的代价可能是整整一波。
  2. persistent kernel 的动机：固定开一波 block，内部循环取任务。 这样永远只有一波，没有尾效应。FlashAttention-4 的 "longest-processing-time-first tile scheduler" 就是在做这件事（L3.2）。
  3. 小 batch 推理为什么效率低：batch=1 时很多 kernel 的 grid 远小于一波， GPU 大部分 SM 空着。这是 L0.2 里"算力利用率不到 6%"的另一个侧面。

映射：一个 block 只落在一个 SM 上

把 blockIdx、threadIdx 和 %smid 一起打印出来（3 个 block × 48 线程）：

      block 0：48 个线程全在 SM 0（同 SM: 是）  尾 warp 活跃线程 = 16
      block 1：48 个线程全在 SM 1（同 SM: 是）  尾 warp 活跃线程 = 16
      block 2：48 个线程全在 SM 2（同 SM: 是）  尾 warp 活跃线程 = 16

两条可以直接用于估算的事实：

  • block 是 SM 的调度单位，不会被拆到两个 SM。 所以一个 block 内的线程可以 用共享内存和 __syncthreads() 通信；跨 block 就不行（见下一节的屏障作用域）。
  • block 内按 32 线程切 warp，48 线程 = 1 个满 warp + 1 个只有 16 个线程的尾 warp。 尾 warp 的 16 个线程照样占一个 warp 槽位、照样按 32 lane 发指令 —— "48 个线程"实际消耗的资源和一个 64 线程 block 的 warp 数相同。

尾元素：31/32/33 与 127/128/129 都要对上

尾 warp 与尾 block 的存在使"越界判断"成为正确性的一部分。用 block=128、 grid=ceil(n/128) 的逐元素 kernel，对 16 个边界尺寸与 CPU 参照逐元素比较：

n grid 逐元素一致 不一致个数
1 / 31 / 32 / 33 1 是 0
63 / 64 / 65 1 是 0
127 / 128 1 是 0
129 / 255 / 256 2 是 0
257 3 是 0
1023 / 1024 8 是 0
1025 9 是 0

if (i < n) 这一行覆盖了尾 warp 的 16 个 lane 与尾 block 的 127 个线程。 去掉它，结果在数值上看不出任何异常（越界写落在分配之外，读回来的前 n 个元素 仍然正确），只有 compute-sanitizer 会报出来 —— 这正是下一节要展示的。

元素数的台阶不只出现在 block 数上，也直接体现在一波的边界上。 block=256、每个 block 固定工作量、grid=ceil(n/256)：

      n          grid         波数   耗时 ms    相对一波
      261119     1020         1.00     1.087        1.00x
      261120     1020         1.00     1.087        1.00x
      261121     1021         2.00     1.266        1.17x   <- 多一波
      261376     1021         2.00     1.267        1.17x
      261377     1022         2.00     1.266        1.17x

元素数只多 1，grid 多 1 个 block，就跨进第二波。 第二波里只有那 1 个 block 在跑，另外 169 个 SM 空等 —— 这就是 [E] 那个 17% 台阶在"元素数"坐标下的样子。 所以对齐判据不只是"grid 是 SM 的整数倍"，而是 grid ≤ SM 数 × 每 SM 可驻留 block 数。

共享内存 producer/consumer 的失败现场

四类失败各有一个"错"版本与一个"对"版本，跑同一份输入。判据是数值与 工具两条线：

案例 数值证据（20 次重复） 工具证据 修复后
缺 __syncthreads 的跨 warp 读写 不一致 0/20（把第 0 个 warp 的写入延后放大窗口后仍是 0/20） racecheck 报 40 hazards 加 __syncthreads() 后 racecheck 0 hazards
shuffle 掩码写错（16 个 lane 执行却声明 32 个参与） 与掩码语义不符 20/20 synccheck 对这类不报（它查的是屏障） 改成全 warp 执行 shuffle 后 0/20
去掉 if (i < n) 的越界访问 不一致 0（前 n 个元素完全正确） memcheck 报 139 errors 加回判断后 0
两条流之间缺事件依赖 20 次里 1–2 次读到未完成的数据 这类跨 kernel 顺序问题不在 racecheck 覆盖面内 加 cudaStreamWaitEvent 后 0/20

第一行是最值得记住的：数值一致不能证明没有竞态。 20 次全对，racecheck 依然指出 40 处共享内存冒险 —— 它只是在等一个不同的调度时机。

第三行说明越界写为什么危险：被越界写坏的是别人的内存，自己的结果看起来完全正确。

第四行的 1–2/20 表明：竞态并非确定性每次触发，因此"单次运行未报错"绝非正确性证据； racecheck 这类工具的作用正是把概率性竞态转化为确定性违规报告。

关于屏障的作用域：

  • __syncthreads() 是 block 级屏障，只对同一个 block 内的线程有效， 不会等其它 block。
  • __syncwarp() 是 warp 级的；掩码必须精确描述参与的 lane， 且调用点必须被掩码内的所有 lane 共同执行。
  • block 之间没有廉价屏障。需要跨 block 同步时，要么拆成两个 kernel （用 kernel 边界同步，5.4 的图执行就是这么做的），要么用 cooperative groups 的 grid 同步（要求 kernel 能整卡驻留，见 5.4 的 persistent 讨论）。

发散屏障（只有一半线程执行 __syncthreads()）在 CUDA 里是未定义行为。 本章实测里它既没有报错、也没有产生错误数值，synccheck 也报 0 errors —— 未定义行为的典型表现就是"什么都没发生"。 这不能作为可以这么写的依据。

CUDA Graph：捕获把什么固定下来

一次捕获、多次 replay 的成本与限制（crater 实测）：

    捕获 0.100 ms   实例化 0.067 ms   节点数 1
    首次 launch 0.0203 ms   热 replay 0.0021 ms（100 次平均）
    显存 free 变化 -2.0 MB

捕获与实例化是一次性成本；热 replay 比首次 launch 快约一个量级。 真正的约束在"捕获冻结了什么"，逐个变量试一遍：

改什么 结果 结论
输入的值（同一块内存） 与新输入的不一致元素 = 0 合法。图固定的是地址，不是内容
输入指针（换成另一块显存） 结果仍写在旧地址；新地址 0 字节被写 非法。host 侧换个变量没有任何效果
元素数（shape） 前 100000 个元素正确，[100000, 200000) 全为 0 非法。grid 与 n 都被冻结在捕获时的值
释放后重新分配 图仍指旧地址，memcheck 报非法访问 非法。内存池复用只是让错误变得随机
把 n 放进设备内存 同一张图跑 n=1000/100000/200000/1048576，全部 0 不匹配 合法。这是动态尺寸的正解

改 shape 有两条合法修法，实测都得到 0 不匹配：

  1. 重新捕获并实例化（新 n 一张新图）；
  2. cudaGraphExecKernelNodeSetParams 就地改节点参数（同一张图， 只改 grid 与 n，不重新实例化）。

链式 kernel 的成本对照（10 个 kernel）：

    CPU 侧提交：逐个 launch 0.023 ms   一次 replay 0.006 ms   (4.05 ×)
    GPU 侧执行：逐个 launch 0.023 ms   一次 replay 0.010 ms   (2.22 ×)

replay 省下的是 CPU 侧的提交次数。GPU 时间也跟着降，是因为逐个 launch 之间存在 CPU 提交间隙、GPU 在等命令；图把这些间隙填上了。这仍然不代表计算量减少 —— 图里该跑的 10 个 kernel 一个不少。2.6b 在真实引擎（vLLM + Qwen3-1.7B）上用 nsys 数过同一件事：三种图模式下 GPU 上的 kernel 数几乎不变（14,003 → 12,147）， 变的只是 CPU 侧 launch 调用（14,003 → 863）。

工程实现 · 源码解析：引擎在哪里对齐 grid

1. vLLM 的 reshape_and_cache_flash

L0.1 的 trace 里这个 kernel 每步调用 28 次（每层一次）。 它的 grid 是按 token 数决定的：batch=1 时只有 1 个 block， 170 个 SM 里 169 个闲着。

这就是为什么小算子在 decode 阶段的绝对时间很小（0.8% 的 GPU 时间）， 但launch 次数却是大头（L1.4 测出 444 次 × 2.68 µs = 1.19 ms）。 问题不在 kernel 慢，在 kernel 太多太小。

2. FlashAttention 的 tile scheduler

L1.1 解析过 Flash_fwd_kernel_traits<128, 64, 128, 4>。 grid 维度是 (ceil(seqlen_q / 64), batch, heads)。

对 Qwen3-1.7B、seqlen=1024、batch=1：⌈1024/64⌉×1×16=256 个 block。 不能用前一个测试 kernel 的 1020-block 容量评估这个 attention kernel。 每个 kernel 的寄存器、共享内存和 block 大小不同，需要单独计算可驻留 block 数。

而 flash_fwd_splitkv_kernel（L0.1 trace 里 decode 用的那个）之所以要 split-K， 正是因为 decode 时 seqlen_q=1，不 split 的话 grid 只有 1 × batch × heads， 远远填不满 GPU。split-K 是在制造并行度（L3.3）。

3. cudaOccupancyMaxActiveBlocksPerMultiprocessor

本章的实验和引擎都用同一个 API 来问"一个 SM 能塞几个 block"：

int blocks_per_sm = 0;
cudaOccupancyMaxActiveBlocksPerMultiprocessor(&blocks_per_sm, kernel, 256, smem_bytes);
int grid = SMS * blocks_per_sm;         // 正好一波

这是写 persistent kernel 的标准起手式。不要硬编码 grid 大小—— 它依赖于 kernel 的寄存器用量，而寄存器用量会随编译器版本变化。

工程实现 · 自己写一遍

三个实验设计上的要点。

(1) 测发散要让每条路工作量相同。

否则你测的是"工作量不同"而不是"发散本身"。本实验每条分支都是一条 fmaf， 只是常数不同（避免编译器合并它们）。

(2) 用共享内存当占用率旋钮，而不是改 block 大小。

改 block 大小会同时改变很多东西（每 block 的工作量、访存模式、尾效应）。 共享内存是唯一一个只影响驻留 block 数的旋钮：

template <int SMEM_KB>
__global__ void occupancy_mem_kernel(...) {
    __shared__ char pad[SMEM_KB * 1024];
    pad[threadIdx.x] = (char)threadIdx.x;      // 防止 smem 被优化掉
    ...
}

那行 pad[threadIdx.x] = ... 是必需的——不写的话编译器发现 pad 没被用， 直接把 __shared__ 声明删掉，占用率根本不会变。

(3) 突破 48 KB 静态上限要显式 opt-in。

静态 __shared__ 最多 48 KB。想压到 1 block/SM 必须用动态共享内存：

extern __shared__ char dpad[];              // 动态
...
CK(cudaFuncSetAttribute(occ_mem_dyn,
       cudaFuncAttributeMaxDynamicSharedMemorySize, 96 * 1024));
occ_mem_dyn<<<grid, 256, kb * 1024>>>(...);  // 第三个参数是动态 smem 字节数

这就是 L1.1 里讲的 sharedMemPerBlockOptin —— 所有现代 attention/GEMM kernel 都要调这个 API，忘了调会在启动时报 invalid argument。

(4) 波长要现场问，不能算。

int bps = 0;
cudaOccupancyMaxActiveBlocksPerMultiprocessor(&bps, tail_kernel, 256, 0);
int wave = SMS * bps;                       // 一"波"

本机这个 kernel 是 6 block/SM，但换个 kernel（寄存器多一点）可能就是 4。 更换 kernel 或编译器后，应重新计算该配置的可驻留 block 数。

四个字段，每个都直接决定性能：

  • Used N registers：每线程用了多少寄存器。每 SM 的寄存器文件是 64K 个 32 位寄存器， 所以最多能驻留 65536/N 个线程。本例只用 12–16 个，不是瓶颈。
  • bytes smem：静态共享内存。本例属于实验中受控注入的负载旋钮。
  • stack frame / spill stores / spill loads：寄存器溢出。 全为 0 说明没溢出。一旦不为 0，说明寄存器不够用，变量被踢到 local memory （其实在显存里，延迟 929 周期——L1.1 实测），性能会断崖式下跌。

写 kernel 时第一件事就是看这四行。 尤其是 spill： 它不会报错，只会让你的 kernel 莫名其妙慢 3 倍。L2.4 优化 GEMM 时会反复用到。

前沿

方向 内容
Thread Block Cluster（Hopper 起） 在 grid 与 block 之间新增一层"cluster"，同 cluster 的 block 可以访问彼此的共享内存（DSMEM）。等于把本章的"一波"概念显式化，并让 tile 可以更大。sm_120 不支持（L1.2）
Cluster Launch Control（Blackwell） 让 kernel 在运行时动态获取下一批 tile，硬件层面的 persistent kernel。L1.2 前沿提到的 sm_120 NVFP4 GEMM 达到 80% 效率就用了它
persistent kernel + 软件流水 固定开一波，内部循环取任务，彻底消灭尾效应。FA4 的 LPT（最长处理时间优先）tile 调度器是这条路线的代表（L3.2）
warp specialization 同一个 block 里不同 warp 干不同的活（一组搬数据、一组算），用 __syncthreads 或 named barrier 协调。这是 Hopper/Blackwell 上高性能 kernel 的标准结构（L2.4、L3.2）
CUDA Graph 条件节点 图里能带分支与循环，减少"形状一变就要重新捕获"。vLLM 目前用 piecewise graph 折中（L5.4）
绿色上下文 / MPS 分区 把 SM 划分给不同的上下文，让本章的"占不满 GPU"问题在多租户下有解（L8.2）

除本章实测外的内容来自各自文档，尚未复现未实测。

陷阱

1. 把占用率当目标。 本机 2 block/SM 就打满带宽，再高无用。 占用率是手段，墙钟时间才是目标。

2. 忘了防优化。 共享内存不被读就会被删掉，占用率实验会完全失效。 compute-bound 的累加值不被使用，整个循环会被删掉。

3. 用改 block 大小来调占用率。 它同时改变了太多变量，实验不干净。 共享内存预留可用于控制驻留数，但还应检查 carveout 和额外访问是否引入其他影响。

4. 硬编码 grid 大小。 波长取决于 kernel 的寄存器用量， 换个编译器版本就变了。用 cudaOccupancyMaxActiveBlocksPerMultiprocessor 现场问。

5. 以为多流总是有用。 单个 kernel 已经占满 GPU 时，多流是净亏损（实测 0.96×）。

6. 忽略 -Xptxas -v 里的 spill。 寄存器溢出不报错，只会让 kernel 悄悄慢几倍。

7. 以为发散一定慢 N 倍。 短分支会被转成谓词执行，实测 8 路只慢 6.02×。 但这不代表分支发散的影响可被忽略——6 倍的延迟退化依然是显著的性能瓶颈。

8. 拿"跑了几次都对"当竞态不存在。 缺 __syncthreads 的跨 warp 读写 20 次全部通过数值检查，racecheck 仍报 40 处冒险。竞态只是还没等到那个调度时机。

9. 以为越界写会让自己的结果出错。 实测越界 127 个线程，前 n 个元素全部正确。 坏掉的是别人的内存，只有 memcheck 会告诉你。

10. 捕获后的 CUDA Graph 不允许直接更改输入指针或形状参数。 图固定的是地址与 launch 配置： 换指针 → 结果写进旧地址；换 shape → 新元素根本没人处理。 合法修法只有重新捕获或 cudaGraphExecKernelNodeSetParams。

11. 发散执行 __syncthreads() 可能"什么都没发生"。 本章实测它既没报错 也没有错误数值，synccheck 也报 0 errors。未定义行为不等于必然崩溃。

12. 工具报 0 不等于没有问题。 synccheck 不管屏障之外的同步原语， racecheck 不管跨 kernel 的顺序。用哪个工具取决于你要证明什么。

自测题

1. 我的 kernel 用了 64 个寄存器，block 是 256 线程，没有共享内存。每 SM 能驻留几个 block？

每 SM 的寄存器文件是 65536 个 32 位寄存器（Blackwell 消费级）。

每 block 需要：256 线程×64 寄存器=16384 个。

65536/16384=4 个 block

但还要检查另外两个上限： - 每 SM 最大线程 1536 → 1536/256=6 个 block - 每 SM 最大 block 数（通常 16–32）

取三者最小值 = 4 个 block/SM，对应 4×256/32=32 个 warp， 占用率 32/48=67%。

但请注意：本章实测显示 2 block/SM 就够打满带宽了。 所以 67% 的占用率完全够用，不必为了提高它去砍寄存器—— 砍寄存器很可能触发 spill，那才是灾难。

（实际写代码时不用手算，直接调 cudaOccupancyMaxActiveBlocksPerMultiprocessor。）

2. 我把 grid 从 1020 改成 1024（凑成 2 的幂，看起来更整齐）。会发生什么？

会慢 17%。 因为一波是 1020，1024 要开第二波来跑那 4 个 block， 而那 4 个 block 独占一整波的时间。

本章实测：1020 → 1.080 ms，1021 → 1.263 ms。1024 会在同一个台阶上。

"凑成 2 的幂"在 GPU 上是个坏习惯。 该对齐的是 SM 数 × 每 SM 可驻留 block 数，本机是 170×6=1020 —— 一个既不是 2 的幂也不好看的数。

先用 occupancy API 计算资源约束，再测实际执行时间。

3. 为什么 compute-bound kernel 对占用率不敏感，而 memory-bound 从 1 到 2 block/SM 会涨 9%？

因为两者掩盖延迟的方式不同。

memory-bound：延迟是访存的 929 周期（L1.1 实测）， 必须靠足够多的在途请求掩盖。按 Little's Law，需要 536 KB 在途。 1 block/SM 时只有 1360 warp × 512 B = 0.70 MB —— 看起来够， 但考虑到不是所有 warp 时刻都有未完成的 load，边际上不足，所以掉到 1546 GB/s。 2 block/SM 时富余，打满 1690 GB/s。

compute-bound：延迟是 FMA 的几个周期，而 kernel 里写了 4 条独立的 FMA 链， 一个 warp 自己就能填满流水线（ILP）。不需要别的 warp 来接力，所以占用率无关。

推论：如果把那 4 条链改成 1 条（纯依赖链），ILP 消失， compute-bound 就会变得和 memory-bound 一样依赖占用率。 这正是本章建议你做的消融之一。

4. decode 每步有 444 个 kernel，很多都很小、占不满 GPU。既然多流能重叠 3.77×，为什么引擎不用多流跑它们？

因为它们之间有数据依赖。

Transformer 的一层是严格串行的： RMSNorm → QKV投影 → RoPE → attention → O投影 → 残差 → RMSNorm → SwiGLU。 每一步的输入是上一步的输出，没有并发空间。

本章的多流实验之所以能重叠 3.77×，是因为那 4 个 kernel 完全独立。

真正的解法是融合（L2.7）：把 RMSNorm + 残差加合成一个 kernel （L0.1 trace 里的 fused_add_rms_norm 就是），把 SwiGLU 的 silu 与 mul 合成一个 （act_and_mul_kernel）。融合同时减少 launch 次数和访存往返。

多流在推理里真正有用的地方是无依赖的工作： - H2D 权重加载与计算重叠（L1.3） - 不同请求的 prefill 与 decode 重叠（chunked prefill，L5.3） - CPU 调度与 GPU 执行重叠（L5.4）

5. 编译一个 attention kernel 时，-Xptxas -v 显示 Used 168 registers, 48 bytes spill stores。该如何处理？

先确认 spill 有多严重，再决定。

48 字节的 spill 很少（大约 12 个寄存器），可能只在某个冷路径上。 但 spill 写的是 local memory，物理上在显存里（L1.1 实测延迟 929 周期）， 如果它在内循环里，代价是灾难性的。

诊断顺序：

  1. 看 spill 在哪：用 -Xptxas -v --generate-line-info 加上 SASS 反汇编 （nvdisasm，本机可用），找 LDL/STL（local load/store）指令在哪一行。
  2. 如果在内循环：必须消除。手段是减少活跃变量—— 比如把 accumulator 分块、把常量移出循环、或者缩小 tile。
  3. 如果在冷路径（初始化、收尾）：可以忽略。

不要用 __launch_bounds__ 强行限制寄存器来"解决"它—— 那只会让编译器 spill 得更多。__launch_bounds__ 是告诉编译器 指定特定占用率目标，编译器会为此牺牲寄存器，即以 local memory spill 为代价换取更高占用率。 按本章的结论，本机 2 block/SM 就够了，没必要为占用率牺牲寄存器。

6. 一个 block 内的相邻访问 kernel 忘了写 __syncthreads()，跑 20 次数值全对，能上生产吗？

不能。本章实测这正是 racecheck 报 40 hazards 的那个 kernel：数值 0/20 不一致， 工具报 40 处共享内存冒险。竞态是否触发取决于 warp 调度时机， "这次没撞上"和"不会撞上"是两件事。

修法是进入读阶段前加一次 __syncthreads()，改完 racecheck 报 0 hazards。 注意 __syncthreads() 是 block 级屏障：它保证同一 block 内所有线程都已写完后 才继续，不会等其它 block；跨 block 的同步只能靠 kernel 边界或 cooperative groups。

7. 一张捕获好的 CUDA Graph，哪些变化可以直接用，哪些必须重新捕获或更新？

可以直接用：同一块内存里的值（图固定的是地址，不是内容）。

必须重新捕获或用 cudaGraphExecKernelNodeSetParams 更新：shape / launch 配置（grid、n）。

必须重新捕获：指针本身变了（另一块显存、重新分配）。本章实测换指针后 结果仍然写进旧地址，新地址一个字节都没被写——不会报错，只会算错。

想在不重捕获的前提下支持动态尺寸，正解是把尺寸放进设备内存、kernel 在设备端读： 实测同一张图跑 n=1000/100000/200000/1048576 全部正确。

8. 一个 48 线程的 block，尾 warp 有几个活跃线程？这个 block 会不会跨两个 SM？为什么这决定了能用什么同步原语？

尾 warp 有 48 − 32 = 16 个活跃线程（它仍然占一个 warp 槽位）。 block 不会跨 SM：实测 3 个 block × 48 线程时，每个 block 的线程 %smid 完全相同。

这决定了同步原语的选择：block 内可以用共享内存 + __syncthreads()； warp 内用 __syncwarp(mask)，掩码必须精确描述参与的 lane； block 之间没有廉价屏障，需要跨 block 就拆 kernel（用 kernel 边界同步）。
