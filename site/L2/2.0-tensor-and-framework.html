框架内部：storage、stride、view 与 dispatcher

从 storage、offset 和 stride 推导张量寻址，再介绍算子分发、内存分配和跨流使用。

实测机器 crater (RTX 5090 D, sm_120) · torch 2.13.0+cu130 · CUDA 13.0；对象身份、Module 状态与别名三组机制实验在本地 CPU（torch 2.14.0）前置 0.0（最小模型的前向）· 2.1（CUDA 执行模型）· 2.3（访存阶梯）

本章回答三个问题

L0.0 中的 Q/K/V 经 transpose(1,2) 后不再连续，但底层数据并未搬动。本章从这个例子出发，解释 Tensor 如何描述内存，以及框架如何选择和调用 kernel。

张量布局、算子分发和内存生命周期分别连接模型代码与 GPU 执行。理解这三层，才能判断一次转置是否需要拷贝、一个操作实际走了哪条路径，以及显存何时可以复用。

  1. x.t() 之后底层字节动了吗？.contiguous() 什么时候真的拷贝？
  2. a + b 从 Python 到某个 CUDA kernel，中间经过哪几次分发？
  3. del x 之后显存还给驱动了吗？一次 OOM 报文里的 reserved 和 allocated 差在哪？

本章的所有数字

带宽、allocator 与跨流实验在 crater（RTX 5090 D，32 GiB，L2 96 MiB，实测 DRAM 上限 1519 GB/s）上跑出来，原始输出在 results/crater/tensor/。对象身份与逐字节寻址、 Module 状态归属、别名与 functionalization 三组实验不依赖 GPU， 在本地 CPU（torch 2.14.0）完成，原始输出在 results/local/2.0/。

心智模型：一块字节，很多副眼镜

理解 PyTorch 张量需要看三个部分：storage 保存数据；offset、sizes、strides 和 dtype 描述数据的读取方式；dispatch key set 参与选择执行的 kernel。本章分别介绍这三部分。

一 · 六元组与 stride 算术

PyTorch 里一个 Tensor 对象背后是 TensorImpl。它的数据成员在 c10/core/TensorImpl.h 里（行号来自机器上装的那份头文件）：

行 成员 是什么
2876 Storage storage_; 指向那段裸字节
2911 c10::impl::SizesAndStrides sizes_and_strides_; 形状与步长
2913 int64_t storage_offset_ = 0; 从 storage 第几个元素开始
2918 int64_t numel_ = 1; 缓存的元素总数
2922 caffe2::TypeMeta data_type_; dtype
2965 bool is_contiguous_ : 1; 缓存的一个 bit
3056 DispatchKeySet key_set_; 决定分发去哪

注意两件事。第一，没有任何一个成员指向"数据"本身 —— 数据在 Storage 里， TensorImpl 只持有一个指针。第二，is_contiguous_ 是一个缓存的 bit， 不是每次调用重算；这个选择后面会再提。

唯一的公式

逻辑索引到 storage 元素号，只有一条式子：

elem(i0,…,in−1)=offset+∑d=0n−1id·strided

字节地址就是 elem × itemsize。整章剩下的东西都是这条式子的推论。

拿 x = torch.arange(12).reshape(3,4) 验证。48 字节的 storage 原文：

  0000  00 00 00 00 00 00 80 3f 00 00 00 40 00 00 40 40
  0010  00 00 80 40 00 00 a0 40 00 00 c0 40 00 00 e0 40
  0020  00 00 00 41 00 00 10 41 00 00 20 41 00 00 30 41

（这是 ctypes 按 storage.data_ptr() 直接读进程内存读出来的， 不是格式化打印 —— 小端 float32，00 00 80 3f = 1.0。）

x.t() 的 stride 是 (1, 4)，代进公式：elem(0,1) = 0 + 0×1 + 1×4 = 4， 字节 16..19，也就是 00 00 80 40 = 4.0。实测逐格对上：

x.t()   shape=(4, 3) stride=(1, 4) offset=0 itemsize=4B storage=48B
  逻辑索引            元素号         字节区间  原始字节         值
  [0, 0]            0     0..3      00 00 00 00  0.0
  [0, 1]            4    16..19     00 00 80 40  4.0
  [0, 2]            8    32..35     00 00 00 41  8.0
  [1, 0]            1     4..7      00 00 80 3f  1.0
  [1, 1]            5    20..23     00 00 a0 40  5.0
  ...

八个 view 的对照表 —— 全部共用同一块 storage，只有 flip 不是：

表达式                          shape          stride           off         data_ptr  同源   连续
----------------------------------------------------------------------------------------------------
x                              (3, 4)         (4, 1)             0       0x3692ee80   是     是
x.t()                          (4, 3)         (1, 4)             0       0x3692ee80   是     否
x[1]                           (4,)           (1,)               4       0x3692ee90   是     是
x[:, 1]                        (3,)           (4,)               1       0x3692ee84   是     否
x[1:, 2:]                      (2, 2)         (4, 1)             6       0x3692ee98   是     否
x.view(2, 6)                   (2, 6)         (6, 1)             0       0x3692ee80   是     是
x[:, :1].expand(3, 4)          (3, 4)         (4, 0)             0       0x3692ee80   是     否
x.flip(0)   <-- 不是 view      (3, 4)         (4, 1)             0       0x36020600   否     是

x[1] 的 data_ptr 比 x 大 0x10 = 16 字节 = offset(4) × itemsize(4)。 data_ptr() 返回的是 storage 起点 + offset，所以两个 view 的 data_ptr 可以 不同却仍然同源；判断是否共享要看 untyped_storage().data_ptr()。

改一个 view，所有 view 一起变：

改之前  x[0,0]=0.0  y[0,0]=0.0
y[0,0]=999 之后  x[0,0]=999.0
storage 前 4 字节： 00 c0 79 44

stride = 0 就是广播

expand 不复制任何东西，它把长度为 1 的那一维的 stride 设成 0：

x[:, :1].expand(3, 4)   shape=(3, 4) stride=(4, 0)
  [0, 0] -> 元素 0 -> 字节 0..3   -> 0.0
  [0, 1] -> 元素 0 -> 字节 0..3   -> 0.0
  [0, 2] -> 元素 0 -> 字节 0..3   -> 0.0
  [0, 3] -> 元素 0 -> 字节 0..3   -> 0.0
  [1, 0] -> 元素 4 -> 字节 16..19 -> 4.0
  ...
storage 还是 48 字节，一个字节都没有多。

对照 repeat：值一样，但 storage 也是 48 字节？不 —— 这里 x[:, :1] 只有 3 个元素， repeat(1,4) 产生 12 个元素的新 storage（48 B），而 expand 复用的是原来那 12 个元素的 storage，其中只有 3 个会被读到。两者 nbytes 恰好相同是巧合，看 stride 才清楚：

expand: storage=  48B  stride=(4, 0)  contiguous=False
repeat: storage=  48B  stride=(4, 1)  contiguous=True
值完全一样： True

在 a + b 中，b 的广播可表示为：

b  shape=(1, 3) stride=(3, 1)
b.expand(4,3) stride=(0, 1)
a+b 与 a+b.expand(4,3) 相等： True

这解释了一个在 L2.3 会用到的账：广播加法里 b 只被从 DRAM 读一次， 之后都在 cache 里，所以算带宽时不能把 b 按 4×3 计。

as_strided：把眼镜直接摘下来自己配

as_strided 让你手写 sizes 和 strides。滑动窗口就是 stride 全填 1：

v = [0..9]，storage 40 字节
w = torch.as_strided(v, size=(8, 3), stride=(1, 1))
tensor([[0., 1., 2.],
        [1., 2., 3.],
        [2., 3., 4.],
        ...
        [7., 8., 9.]])
逻辑上 8×3=24 个元素，实际只有 10 个 —— 每个元素平均被读 2.4 次

拿它做 3 点滑动平均就是一次 matmul，没有 im2col 的那次拷贝： (w @ k).tolist() → [1.0, 2.0, ..., 8.0]。卷积的 im2col、 FlashAttention 的分块、vLLM 的 KV block table，本质上都是在配眼镜。

代价是它绕过所有边界检查：

head = v[:4] = [0.0, 1.0, 2.0, 3.0]   （它的 shape 只有 4）
as_strided(head, (10,), (1,)) = [0.0, 1.0, ..., 9.0]

head 逻辑上只有 4 个元素，as_strided 照样读到了第 10 个。它只认 storage， 不认 shape。越过 storage 的边界就是越界读，不报错，读到别人的显存。

对象、存储、数值是三个正交的问题

「两个张量是不是同一个」在工程上其实是三个问题：Python 对象是不是同一个、 底层字节是不是同一块、数值是不是相等。它们可以任意组合，混用会写出 「以为共享、实际拷贝」或「以为独立、实际互相覆盖」的代码。

基础张量 x = arange(24, int32).reshape(2,3,4) 的 96 字节 storage 上取一组 view：

表达式 shape stride offset numel storage 元素 同源 连续
x (2,3,4) (12,4,1) 0 24 24 是 是
x.transpose(1,2) (2,4,3) (12,1,4) 0 24 24 是 否
x[1] (3,4) (4,1) 12 12 24 是 是
x[..., 1:3] (2,3,2) (12,4,1) 1 12 24 是 否
x[:, 1:3, ::2] (2,2,2) (12,4,2) 4 8 24 是 否
x[0,:,:1].expand(2,3,4) (2,3,4) (0,4,0) 0 24 24 是 否
x.unfold(2,3,1) (2,3,2,3) (12,4,1,1) 0 36 24 是 否
x.as_strided((4,4),(1,1)) (4,4) (1,1) 0 16 24 是 否
x.flip(2) (2,3,4) (12,4,1) 0 24 24 否 是
x.transpose(1,2).reshape(-1) (24,) (1,) 0 24 24 否 是
x.clone() (2,3,4) (12,4,1) 0 24 24 否 是

「同源」指 untyped_storage().data_ptr() 相同。numel 与 storage 元素 两列 刻意分开：unfold 的逻辑元素比实际字节多 50%，expand 的 24 个逻辑元素只落在 少数几个地址上，逻辑大小不是占用大小。

三个问题各自的判据：

比较对象 同一对象 同一 storage 同 storage 指针 同 numel 展平后逐元素相等
x, x 是 是 是 是 是
x, x.reshape(6,4) 否 是 是 是 是
x, x.transpose(1,2).reshape(-1) 否 否 否 是 否
x, x.clone() 否 否 否 是 是
x, x[0,:,:1].expand(2,3,4) 否 是 是 是 否
x, x[0] 否 是 是 否 —

两行值得单独读：

  • x.reshape(6,4) 与 x 不是同一对象、形状也不同，但 storage 指针相同 —— 它是 view。 用 is 或 shape 判共享都会判错。
  • x.transpose(1,2).reshape(-1) 与 x 连数值都不相等：它展平的是转置后的顺序。 这里的拷贝不只是开销问题，它同时改变了元素次序。

已知索引的逐字节对拍

判断寻址是否理解正确，不能只看 stride() 打印出来对不对，要把逻辑索引 一路算到字节，再和真实读到的字节比。做法是独立写一遍索引算术：

def ref_elem(idx, stride, offset):
    acc = offset
    for i, s in zip(idx, stride):
        acc += i * s
    return acc

然后对每个 view 的全部逻辑索引做三件事：算出元素号 → 按 元素号 × itemsize 取 storage 的原始字节 → 用 struct.unpack_from 解码， 与张量自己的 t[idx] 比较。x 的 10 个 view 共 204 个逻辑索引，全部一致； data_ptr() - storage_ptr() 也逐项等于 offset × itemsize。

重叠 view 会连续命中同一段字节，这正好验证了 stride=0 与重叠窗口的语义：

x[0, :, :1].expand(2, 3, 4)   shape=(2, 3, 4) stride=(0, 4, 0) offset=0
  逻辑索引      算出的元素号   字节区间    原始字节       按字节解码  张量读数
  [0, 0, 0]            0     0..3      00 00 00 00          0        0
  [0, 0, 1]            0     0..3      00 00 00 00          0        0
  [0, 0, 2]            0     0..3      00 00 00 00          0        0
  [0, 0, 3]            0     0..3      00 00 00 00          0        0
  [0, 1, 0]            4    16..19     04 00 00 00          4        4
  逐索引核对 24 个，字节解码与张量读数不一致 0 个

mini_tensor.py 是这套算术的第二条独立实现。同一组 view 上，两边算出的元素号 与读出的值逐项相同，连续性判定也一致 —— 寻址这件事的全部内容就是 offset + Σ index_d × stride_d，没有别的隐藏规则。

版本计数不是引用计数

每个张量还带一个版本计数，它在原地修改时递增，是 autograd 判断 所需底层数据是否依然有效的依据。三条要点：

初始          x._version=0  view._version=0  clone._version=0
x 与 view 同一 storage: True；x 与 clone 同一 storage: False
view 的 _base is x: True
改写 view 后  x._version=1  view._version=1  clone._version=0
改写 clone 后 x._version=1  clone._version=1
  1. view 与 base 共享同一个版本计数，改 view 等于改 base，两者一起 +1。
  2. 拷贝不共享，改 clone 不动原张量。
  3. 版本计数与 Python 引用计数无关：del x 既不改变版本计数，也不代表显存被回收 （后者是 2.0c 的内容）。

代价写在 c10/core/TensorImpl.h:329 的 VariableVersion 里 —— 版本是一个 std::atomic<uint32_t>（:333），bump() 就是一次原子自增（:391）：

struct C10_API VariableVersion {
 private:
  struct VersionCounter : intrusive_ptr_target {
    VersionCounter(uint32_t version) : version_(version) {}
    std::atomic<uint32_t> version_;
  };
  ...
  void bump() {
    TORCH_CHECK(version_counter_ || InferenceMode::is_enabled(), ...);
    if (version_counter_) {
      ++version_counter_->version_;
    }
  }

用原子变量是因为反向可能在别的线程读它；用 intrusive_ptr 是因为 view 要共享它。 :347 还留了一条注释：SavedVariable 会在自己的构造函数里换掉版本计数 —— 保存值记录的是「保存那一刻的版本号」，反向时再比一次。

二 · contiguous 的精确定义

「连续」不是一个感觉，它有 25 行代码的定义。全文在 c10/core/Contiguity.h:15（这份文件就在机器上）：

template <typename T>
bool _compute_contiguous(ArrayRef<T> sizes, ArrayRef<T> strides, T numel) {
  if (numel == 0) {
    return true;
  }

  T expected_stride = 1;
  // NB: make sure we do signed arithmetic
  for (int64_t d = int64_t(sizes.size()) - 1; d >= 0; d--) {
    const auto& size_d = sizes[d];
    if (size_d == 1) {
      continue;
    }

    if (strides[d] != expected_stride) {
      return false;
    }
    expected_stride *= size_d;
  }
  return true;
}

读法：从最后一维往前，期望 stride 依次是 1, s[n-1], s[n-1]·s[n-2], …。 拿 x.t()：sizes (4,3)，strides (1,4)。d=1：期望 1，实际 4 → 立刻 false。 拿 x：sizes (3,4)，strides (4,1)。d=1：期望 1 实际 1 ✓，期望变 4； d=0：期望 4 实际 4 ✓ → true。

长度为 1 的维度被直接跳过

if (size_d == 1) continue; 这一行意味着：长度 1 的维度的 stride 是多少都不影响连续性。 sizes=(3,1,4), strides=(4,999,1) 是连续的。 配套的简易实现同样体现了这一行为。这也是为什么两个"看起来一样"的张量 stride 可能不同却都 contiguous —— 写 kernel 时不能靠 stride 相等来判断布局相同。

3.1 TensorIterator：为什么转置的逐元素算子不掉速

aten/src/ATen/TensorIterator.cpp:231（v2.13.0 tag）：

void TensorIteratorBase::reorder_dimensions() {
  // Sort the dimensions based on strides in ascending order with reduced dims
  // at the front. NOTE: that this inverts the order of C-contiguous tensors.
  // strides[0] is the fastest moving dimension instead of strides[ndim - 1].

以及 ATen/TensorIterator.h:640 那段设计说明（它把意图讲得比任何转述都清楚）：

/// Records the "computation" shape of the output tensor. The computation
/// shape is different from the regular shape in a few ways:
///
///   - The shape may be permuted (via permute_dimensions) so that we
///     process the dimensions in the most computationally efficient order
///     (rather than the logical order given to us by the users.)
///   - The shape may have adjacent dimensions collapsed (via
///     coalesce_dimensions) so that we minimize the number of
///     dimensions we have to explicitly iterate over.  For example,
///     a pointwise operation on a contiguous tensor "computationally"
///     consists of only a single dimension.

具体而言，TensorIterator 不接受"用户给的维度顺序"，它按 stride 升序重排维度， 再把相邻可合并的维度合并掉。对 g.t()*2 来说，重排之后迭代顺序就变回了 物理连续顺序，于是它退化成一个一维的、完全合并的 kernel。代价是输出的 stride 不再是行主序 —— 上面那个 (1, 8192) 就是账单。

生命周期写在同一段注释里：compute_shape() → reorder_dimensions() → coalesce_dimensions()。

3.6 functionalization：把原地算子换成函数式算子

torch.func.functionalize 是一个 mode：进入后，每个原地算子都被替换成 「出参版本 + 在离开 mode 时把结果 copy_ 回原输入」。同一个程序的算子序列：

eager
  aten.add.Tensor !aten.mul_.Tensor aten.t.default !aten.add_.Tensor
  !aten.add_.Tensor aten.sum.default

functionalize(remove='mutations')
  aten.add.Tensor aten.mul.Tensor aten.t.default aten.t.default aten.add.Tensor
  aten.t.default aten.t.default aten.add.Tensor aten.sum.default !aten.copy_.default

functionalize(remove='mutations_and_views')
  ... aten.t_copy.default ... （transpose 也变成拷贝版本）

（! 标记原地算子。）三件事可以直接读出来：

  1. mul_ / add_ 变成了 mul / add，程序里一次原地修改都不剩。
  2. 代价是算子数从 6 个涨到 10 个：每个被修改的张量要额外物化一份新的、 还要在边界补一次 copy_ 把改动写回输入。这就是「函数式化」的账单。
  3. remove 参数决定改写力度：'mutations' 只处理原地与 out= 算子， 'mutations_and_views' 连 view/t/reshape 也换成 *_copy 版本 —— 后者把所有共享存储的可能都切断了，代价是额外的拷贝。

关键收益在 saved_variable.cpp 那次版本比较上。同一段「原地修改打断保存值」 的程序，三条路径的处置完全不同：

路径 前向 反向 结果
eager OK 报错 RuntimeError，版本不匹配
functionalize('mutations') OK OK 无报错，grad = 8.0
compile(backend='eager') OK 报错 同 eager
compile(backend='aot_eager') 报错 — BackendCompilerFailed 包着同一个 autograd 错误
compile(backend='inductor') 报错 — 同上

函数式化之后保存的 y 不再被原地修改，反向拿到的是修改前那份， 于是它算出了 eager 拒绝算的那个梯度。这不是"修复"，而是说 「原地修改打断保存值」这个错误的判定依赖执行路径：同一段代码在 eager 里是错误，在函数式化后的图里是合法的、有确定含义的计算。

torch.compile 走的是 AOTAutograd 内嵌的函数式化，它把这个冲突提前到编译期 暴露，所以前向就失败了。同一段程序在三条路径下的可见行为不同， 这是 2.6b/2.7 讨论编译器边界时的起点。

3.7 Module 的注册表：状态归属由谁决定

nn.Module 用三张表区分「什么样的张量算什么状态」，源码在 torch/nn/modules/module.py：_parameters（:592 的 register_parameter）、 _buffers（:528 的 register_buffer）、_modules。三种写法放进同一个模型：

self.lin = nn.Linear(4, 4)                            # 子模块 -> _modules
self.p = nn.Parameter(torch.ones(3))                  # -> _parameters
self.plain = torch.ones(4)                            # 普通属性，三张表都不进
self.register_buffer("run", torch.zeros(3))           # -> _buffers
self.register_buffer("tmp", torch.ones(3), persistent=False)

实测三张表与 state_dict()：

self._parameters : ['p']
self._buffers    : ['run', 'tmp']
self._modules    : ['lin']

named_parameters(): ['p', 'lin.weight', 'lin.bias']
named_buffers()   : ['run', 'tmp']
state_dict() 键   : ['lin.bias', 'lin.weight', 'p', 'run']
  • 普通 tensor 属性可以参与前向，但不进任何注册表，因此不会被保存、不会被迁移、 不会被 optimizer 看到。
  • persistent=False 的 buffer 在 named_buffers() 里，但不在 state_dict() 里： 它需要跟着模型迁移设备，但不属于需要存档的状态。

to() 的遍历范围由 _apply（:930）决定，它只走 _parameters（:960） 与 _buffers（:1034）。实测结果与源码完全对应：

to(torch.float64) 之后：
  lin.weight dtype : torch.float64   （对象 id 保持: True）
  p (Parameter)    : torch.float64
  run (buffer)     : torch.float64   （对象 id 保持: False）
  tmp (non-persist): torch.float64
  plain (普通属性)  : torch.float32   <- 没被迁移

参数走 param.data = param_applied（:991），对象不换、只换内部张量， 所以 optimizer 里存的引用、以及外部持有的 Parameter 都不受影响。 buffer 走 self._buffers[key] = fn(buf)（:1036），换成了新对象。 plain 从头到尾没被碰过 —— 把一张常量表写成普通属性、再 .to("cuda")， 就是一次 device mismatch 报错：

RuntimeError: Tensor on device cpu is not on the expected device meta!

4.1 dispatcher 为什么是位图，不是虚函数表

最直觉的做法是给 Tensor 一个虚函数表，add 是个虚方法，CUDA 子类覆盖它。 PyTorch 没这么干，理由写在 c10/core/DispatchKeySet.h:60 的注释里：

// First: why do we have this distinction, and why not map every dispatch key
// directly to a bit? This is mostly because we have several types of
// functionalities that different backends would like to customize. For example,
// we have:
// - "Dense":     CPU, CUDA, XLA, ... (~12 keys)
// - "Sparse":    SparseCPU, SparseCUDA, ...
// - "SparseCsr": SparseCsrCPU, SparseCsrCUDA, ...
// - "Quantized": QuantizedCPU, QuantizedCUDA, QuantizedXLA, ...
// - "Autograd":  AutogradCPU, AutogradCUDA, Autograd XLA, ...
// The problem is that total number of keys grows quadratically with [#
// backends] x [# functionalities], making it very difficult to map each key
// directly to a bit in a bitset without dramatically increasing the size of the
// bitset over time.

关键判据是"加一个后端要动几处"。 这里真正的需求不是"多个后端"， 而是「后端」×「功能」的笛卡尔积：12 个后端 × 5 类功能。 虚函数表方案下，加一个后端要写 5 个类；加一个功能要改 12 个类 —— 二次增长。

PyTorch 的解法是把位图拆成两半：后端位（CPUBit、CUDABit…）和功能位 （Dense、Sparse、Autograd…），运行时键由两者组合而成：

//     auto dense_cpu_ks = DispatchKeySet({DispatchKey::CPUBit,
//     DispatchKey::Dense});
//     // The keyset has the runtime dense-cpu key.
//     dense_cpu_ks.has(DispatchKey::CPU);

于是位数从 O(后端×功能) 降到 O(后端+功能)。这就是所谓"正交扩展"： 让两个独立变化的维度在表示层就独立。

源码还注明了实现限制：

// Not every backend and not every functionality counts as a "building block
// key". This is mostly to give us more levers to pull in the design space.

即：不把所有东西都做成正交的。全正交要为每个组合在每个算子表里留一个槽， 代价是内存和查表时间。他们选择只对真正需要的组合付这个税。

设计“多个 A × 多个 B”的组合结构时，应先确认哪些组合实际需要支持， 再决定是做成两个正交维度还是做成一个枚举。做成枚举的那一刻，增长就是二次的。

4.2 TensorIterator：重排，而不是要求连续

面对"输入不连续"，有三种设计：

方案 做法 代价
A. 要求调用者保证 kernel 只接受 contiguous，不满足就报错 用户到处写 .contiguous()，多一遍全量读写
B. 框架自动 contiguous 进 kernel 前偷偷拷贝 正确但慢，且开销不可见

PyTorch 选 C。在 labs/L2/tensor_anatomy.py 的 [E] 节中，对比了自写 kernel 与框架实现的实测表现（8192×8192 float32 = 256 MiB，超出 L2 缓存容量）：

4.3 caching allocator：为什么不还给驱动

cudaMalloc / cudaFree 是同步调用 —— 它们会等待设备上所有工作完成。 在一个每步都要分配释放几十个中间张量的训练循环里，这等于每步同步几十次， GPU 直接被打成串行。所以 PyTorch 自己做了一层缓存分配器：向驱动整段要， 自己切；del 只是把块挂回空闲链表。

代价是显存账变成两本：allocated（你要的）和 reserved（向驱动要的）。 所有关于"显存去哪了"的困惑都来自这两本账的差。

尺寸常量在 c10/core/AllocatorConfig.h:16，注释就在旁边：

4.4 碎片：代价不是崩溃，是一次隐藏的停顿

直觉上常认为内存碎片会直接导致 OOM 崩溃，但实测结果展现了更为复杂的运行机制。

把 32 GiB 全部吃满（123 × 256 MiB），再隔一块释放一块， 留下 62 个 256 MiB 的洞、分属 62 个不同 segment，然后要一块 512 MiB：

请求一块 512 MiB（比任何一个洞都大）：
  >>> 成功，耗时 39.3 ms
  num_alloc_retries 1 -> 2   num_ooms 1 -> 1
  reserved 31488 -> 16128 MiB   (掉了 15360 MiB = 被 cudaFree 还给驱动的缓存)

  对照：干净堆上同样要 512 MiB，耗时 0.9 ms

发生的事：allocator 内部先 OOM 了（num_ooms 涨了 1）， 然后走重试路径 —— 把整个缓存 cudaFree 掉，再向驱动重新要。所以：

  • 结果是成功，不是异常；
  • 代价是 39.3 ms vs 0.9 ms，慢 44 倍，而且这 39 ms 里包含大量同步的 cudaFree/cudaMalloc，会把整条流水线卡住；
  • 副作用是 15 GiB 的缓存被清空，之后每次分配都要重新向驱动要。

碎片还可能表现为偶发的长尾延迟，而非直接报错。可结合 num_alloc_retries 检查是否发生了分配重试。

真正的 OOM 长这样（请求 40 GiB）：

31.36 GiB of which 30.86 GiB is free. Including non-PyTorch memory, this process

读这条报文的顺序：total capacity 是卡的物理容量；free 是驱动此刻的空闲； this process has X in use 含 CUDA context（这里 498 MiB）； allocated by PyTorch 是你真正持有的； reserved but unallocated 才是碎片。这四个数分开看，才知道该减 batch、 该 empty_cache()、还是该换分配策略。

4.5 expandable_segments 换的是什么

在上述“满载并构造等大空闲空洞”的极端场景下进行 A/B 测试：

默认段：            成功，耗时 39.3 ms
expandable_segments: 成功，耗时 50.0 ms

延迟没有下降，反而略有增加。 这是因为显存被彻底耗尽，两种策略最终都必须将已缓存内存交还驱动，无法体现虚拟内存管理的优势。

expandable_segments 真正针对的是变长负载：反复分配大小各不相同的 activation， 缓存里攒下一堆"尺寸不对"的块，reserved 一路涨而 allocated 不涨。 指标应该是 reserved/allocated，不是单次延迟。重做（600 次 4–384 MiB 的随机分配， 活跃集控制在 8 GiB）：

默认段 expandable_segments:True
allocated 8088 MiB 8088 MiB
reserved 14008 MiB 10800 MiB
reserved/allocated 1.73× 1.34×
浪费 5920 MiB 2712 MiB
segment 数 58 1

浪费砍掉 54%。机制在最后一行：58 个段 → 1 个段。 它用 CUDA 的虚拟内存 API 预留一大段连续地址空间，按需往里映射物理页； 释放时解映射，物理页可以补到这段地址空间的任何位置。 所以"洞"在物理层被消除了，而不是在逻辑层被绕过。

代价：多一层虚拟内存映射；与某些需要固定物理地址的路径（IPC、部分 RDMA 注册） 不兼容 —— 这也是它至今没成为默认值的原因。

比较分配策略前，需要区分碎片问题和实际容量不足。如果两种配置都耗尽显存，实验就无法反映碎片处理方式的差异。

4.6 反面：as_strided 的边界

as_strided 是这一层里唯一一个故意不做检查的接口。它不验证 offset + Σ(size_d-1)·stride_d 是否落在 storage 内，前面的实验里 一个 shape 为 4 的张量读到了第 10 个元素。

这一接口允许表达底层布局，也将部分边界检查责任交给调用方： 任何检查都会限制它的表达力（比如重叠窗口就是"越界"的合法用法）。 与其做一层挡不住的检查，不如把它明确定位成低层原语， 让 view/reshape/unfold 这些带检查的接口建在它上面。

判据是「错误在第几层被发现」：view 在自己那一层就报错并给出可读信息 （上面那条 "spans across two contiguous subspaces"）， as_strided 把这个责任显式交给调用者。危险的原语 + 安全的封装， 比"一个又想安全又想万能的接口"要好。

4.7 为什么参数、buffer、普通属性要分三张表

一个自然的简化是「模块里的张量都登记成参数」。PyTorch 分了三张表，因为三种张量 在四个操作上的正确答案各不相同：

操作 Parameter buffer 普通属性
state_dict() 保存 是 是（persistent=False 除外） 否
optimizer 更新 是 否 否
.to(device/dtype) 迁移 是（换 data，保对象） 是（换对象） 否
反向产生梯度 是 由 requires_grad 决定 由 requires_grad 决定

把常量表当参数：.to("cuda") 会把它搬走（好事），但 optimizer 会为它建一份 momentum/exp_avg 状态（浪费显存），state_dict 里多出一份永远相同的键（污染存档）。 把常量表当普通属性：省了后两项，但迁移时要自己处理。 这张表就是「状态归属」的判据 —— 先问「谁保存、谁更新、谁迁移」， 再决定用哪张表。

共享参数是这张表的一个边界情况。同一个 Parameter 对象挂两个名字时， 实测：

named_parameters()                -> ['emb.weight']
named_parameters(remove_duplicate=False) -> ['emb.weight', 'head.weight']
state_dict() 的键                -> ['emb.weight', 'head.weight']（两个键、同一块存储）

去重只发生在 named_parameters/named_buffers 上（module.py:2650 的 _named_members 按对象 id 去重），state_dict() 不去重，所以绑定权重在存档里 占两个键。这两点合起来解释了那个经典 bug：

去重后一步的参数变化  = 6.371428   （= lr × |g|1）
不去重一步的参数变化  = 12.742855  （= 2 × lr × |g|1）
警告原文： optimizer contains a parameter group with duplicate parameters;
          in future, this will cause an error

optimizer = SGD(model.parameters()) 是对的（默认去重）； SGD([p for _, p in model.named_parameters(remove_duplicate=False)]) 会让同一个 参数在优化器里出现两次，等效学习率翻倍，而且不报错，只有一条 UserWarning。 同理，load_state_dict 时两个键写同一块存储：

sd 里 emb.weight 全 1、head.weight 全 2，加载后 emb.weight 全 2: True
共享关系仍然成立: True

后写的键覆盖先写的，绑定关系不受影响，但存档里两个键的值不一致时不会报错， 结果取决于字典顺序。这是「共享状态必须显式声明」的一个具体代价。

4.8 原地修改的三种处置，各自交换了什么

面对「原地修改会打断保存值」，有三种可选设计：

方案 做法 收益 代价
A. 运行时检测 保存版本号，反向时比对，不匹配就报错 维护和比较版本计数；错误位置可追踪 报错发生在反向，此时前向的计算与显存都已付出
B. 函数式化 把原地算子换成出参版本 + 边界 copy_ 默认保留 view；去除 view 需 mutations_and_views，反向仍受支持范围约束 算子数与中间张量增加（实测 6 → 10）；写回拷贝可能被忽略的带宽
C. 改写程序 禁止原地修改，全部用新张量 语义最清晰 用户代码要改；add_ 这类原地算子在大 tensor 上省下的那次分配是真的

torch.func.functionalize(remove="mutations") 只移除中间变更；remove="mutations_and_views" 进一步把 view 改为非别名操作。输入写回、全局状态、autograd 和不支持的算子仍有各自边界，不能仅由函数式化成功推断任意反向都可执行。

PyTorch 三条路都在用：eager 用 A，torch.func/AOTAutograd 用 B，文档建议用 C。 选择判据是错误发生的时机：A 把错误推到反向（离犯错点最远）， B 把它推到编译期（BackendCompilerFailed 包着 autograd 的错误原文）， C 让它压根不会发生。

A 的关键设计是「报错而不猜」。运行时其实能看出「保存值被改过」， 但无法知道改动是不是语义需要的，于是它拒绝继续算：

eager:                      前向 OK，反向 RuntimeError
functionalize('mutations'): 前向 OK，反向 OK，grad = 8.0
compile(aot_eager):         前向 BackendCompilerFailed

同一段程序，三条路径给出「报错 / 算出结果 / 编译失败」三种可见行为。 这正是 2.7 要讨论的问题：编译路径改变了错误的边界，也会改变数值结果。

 56         return self.offset + sum(i * s for i, s in zip(idx, self.strides))

 88     def transpose(self, dim0, dim1):
 89         """交换两个维度 —— 只换 sizes/strides，不动数据。"""

 93         strides[dim0], strides[dim1] = strides[dim1], strides[dim0]

 96     def reshape(self, *sizes):
 97         """能 view 就 view，不能就拷贝 —— 与 torch.reshape 同一策略。
 98 
 99         PyTorch 在个别不连续但形状仍可表达的场合会返回 view；这里只实现
100         “连续则 view、否则拷贝”这条主干，差异在正文说明。

103             sizes = tuple(sizes[0])

105             raise ValueError(f"reshape 不能改变元素数: {self.sizes} -> {sizes}")

124     def expand(self, *sizes):
125         """把长度为 1 的维度的 stride 改成 0 —— 广播的全部实现。"""
126         assert len(sizes) == len(self.sizes)
127         strides = []
128         for want, have, st in zip(sizes, self.sizes, self.strides):
129             if have == want:

141     # ---- contiguous：PyTorch 的定义，逐字照抄 -----------------------
142     def is_contiguous(self) -> bool:
143         """c10/core/Contiguity.h:15 _compute_contiguous 的 Python 版。"""
144         if self.numel() == 0:
145             return True
146         expected = 1
147         for d in range(len(self.sizes) - 1, -1, -1):
148             if self.sizes[d] == 1:        # 长度 1 的维度 stride 是什么都无所谓
149                 continue

151                 return False

153         return True

157             return self                   # 已经连续 -> 原样返回，零成本

161             out[idx] = self[idx]

204 def broadcast_shape(a, b):
205     """广播在**左边**补 1，不是右边。补错方向 (2,3)+(3,) 就会假报不兼容。"""
206     n = max(len(a), len(b))

213         else:

215     return tuple(out)

广播维度的对齐方向约定

broadcast_shape 实现时若在右边补 1，会导致 (2,3) + (3,) 报"形状不兼容"。 标准的广播规则是在左边对齐补 1。 这一实现细节表明：广播的对齐方向是框架规范的工程约定，而非纯粹由数学公理推导得出，在不同 DSL 或执行引擎中需要核对对齐约定。

 94                     continue
 95                 if remove_duplicate:
 96                     if id(b) in seen:
 97                         continue
 98                     seen.add(id(b))
 99                 yield pre + name, b
100             if recurse:
101                 for mname, child in mod._modules.items():
102                     yield from walk(child, pre + mname + ".")
103 
104         yield from walk(self, prefix)
105 
106     def parameters(self, **kw):
107         return [p for _, p in self.named_parameters(**kw)]
108 
109     def buffers(self, **kw):
110         return [b for _, b in self.named_buffers(**kw)]
111 
112     def modules(self):
113         yield self
114         for child in self._modules.values():
115             yield from child.modules()
116 
117     # ---- 序列化 ----------------------------------------------------
118     def state_dict(self, prefix=""):
119         """先本层参数，再本层 buffer，然后递归子模块 —— 与 PyTorch 同序。"""
120         out = {}
121         for name, p in self._parameters.items():
122             if p is not None:
123                 out[prefix + name] = p.data
124         for name, b in self._buffers.items():
125             if b is not None and name not in self._non_persistent:
126                 out[prefix + name] = b
127         for mname, child in self._modules.items():
128             out.update(child.state_dict(prefix + mname + "."))
129         return out
130 
131     def load_state_dict(self, sd, strict=True):
132         local = self.state_dict()
133         missing = [k for k in local if k not in sd]
134         unexpected = [k for k in sd if k not in local]
135         for k in local:
136             if k in sd:
137                 local[k].copy_(sd[k])
138         if strict and (missing or unexpected):
139             raise RuntimeError(
140                 f"Error(s) in loading state_dict: missing={missing} "
141                 f"unexpected={unexpected}")
142         return missing, unexpected
143 
144     # ---- 迁移 ------------------------------------------------------
145     def to(self, dtype):
146         """参数与 buffer 都迁，普通 tensor 属性不迁 —— 与 nn.Module._apply 一致。"""
147         for p in self._parameters.values():
148             if p is not None:
149                 p.data = p.data.to(dtype)
150         for name, b in self._buffers.items():
151             if b is not None:
152                 self._buffers[name] = b.to(dtype)
153                 object.__setattr__(self, name, self._buffers[name])
154         for child in self._modules.values():
155             child.to(dtype)
156         return self

7.1 一个 torch 进程什么都不干要多少显存

--- 0. CUDA context 本身要多少显存 ---
  1) torch.cuda 尚未初始化        nvidia-smi 已用 =     4 MiB
  2) torch.cuda.init() 之后       nvidia-smi 已用 =     4 MiB   (+0)
  3) cudaDeviceSynchronize 之后   nvidia-smi 已用 =   508 MiB   (+504)
  4) 第一次 torch.empty(1) 之后   nvidia-smi 已用 =   510 MiB   (+2)

三件事：

  • torch.cuda.init() 是惰性的，它没有建 context（+0 MiB）。 名字很误导。context 在第一次真正碰 GPU 时才建。
  • context 本身要 504 MiB，一个字节的权重都还没有。 这就是 OOM 报文里 "Including non-PyTorch memory, this process has 498.00 MiB memory in use" 的那一项。
  • 之后 allocator 的第一个 segment 只占 2 MiB（= kSmallBuffer）。

测量前调用 CUDA API 可能提前创建 context

用 torch.cuda.mem_get_info() 取"初始化前"的空闲值 —— 但 mem_get_info() 自己就会建 context，于是测出"context 开销 ≈ 2 MiB"。 必须从进程外面看（nvidia-smi 查询驱动记录的显存用量）才测得到。 凡是测"初始化开销"的，都要检查你的测量手段是不是本身就触发了初始化。

7.4 跨流不同步的真实竞态

--- 2. 跨流不同步 —— 真的会读到旧值吗 ---

不是理论风险，是 6 次里错 5 次。做法是：默认流上跑 20 次 4096² matmul 写进 x， 然后在 side stream 上读 x.sum()，中间不加 s2.wait_stream(...)。 加上那一行，6 次全对。

隐式同步掩盖跨流竞态

.item() 将数据拷贝回 Host 侧时会在当前流触发阻塞式同步， 跨流的时序竞争常被此类隐式同步偶然掩盖。 一旦为优化性能移除同步（例如换用异步拷贝与 CUDA 事件），竞态条件便会立即暴露。 隐式掩盖不等于并发安全。

八 · 前沿：这一层在推理引擎里长什么样

  • vLLM 的 KV cache 就是一个巨大的 as_strided。 一块连续显存 + 一张 block table，逻辑上的"每个序列一段连续 KV"完全是靠索引算术造出来的 （L5.2 拆过 block table 的内容）。它把"连续性"这个不变量从物理层搬到了逻辑层 —— 和本章第 4.6 节说的"危险原语 + 安全封装"是同一个套路。
  • expandable_segments:True 是 vLLM / TorchTitan 的常见配置。 现在你知道它换的是什么：把 N 个物理段变成 1 个虚拟段，代价是与 IPC/RDMA 注册的兼容性。
  • torch.compile 的 fake tensor 走 Meta 键。 本章看到 Meta 上注册了 1614 个算子、比 CUDA 还多，且可以由 Python 覆盖 —— 2.6b 里 Dynamo 能在 不执行任何 kernel 的情况下推出所有中间形状，靠的就是这张表。2.8 会自己往上注册一个。
  • torch.compile 生成的 Inductor kernel 直接吃 stride，不做 .contiguous()。 2.6b 里那份 176 行 Triton 源码里的 xindex // ynumel 之类的算术， 就是本章那条 stride 公式的展开。

九 · 陷阱

  1. reshape 静默拷贝。想确认有没有拷贝就比 data_ptr()。 attention 里连着几个 reshape 很容易翻倍峰值显存。
  2. data_ptr() 不同不代表不同源。它含 storage_offset。 判断共享要用 untyped_storage().data_ptr()。
  3. 长度 1 的维度的 stride 不影响 is_contiguous()。 不要用 stride 相等来判断两个张量布局相同。
  4. 自写 kernel 只收到指针，看不见 stride。收到非 contiguous 输入 会算出错误结果且不报错（本章 max|err| = 12.0 的那一段）。 自写算子的入口必须显式 TORCH_CHECK(x.is_contiguous()) 或者老实吃 stride。
  5. torch.cuda.init() 不建 context。测初始化开销要从进程外面看。
  6. mem_get_info() 自己会建 context，用它测"初始化前"必然测错。
  7. del 不还显存给驱动，empty_cache() 才还。 但 empty_cache() 会同步且清空缓存，在训练循环里调用是自伤。
  8. 碎片通常不表现为 OOM，而表现为几十毫秒的偶发停顿。 用 num_alloc_retries 监控它，不要等 OOM。
  9. 跨流用张量必须 wait_stream / record_stream。 .item() 会掩盖这个 bug，去掉同步后它才现形。
  10. as_strided 不做边界检查，能读到 storage 外面。
  11. 测带宽时先算工作集有没有超过 L2。本章 64 MiB 的那次测出 1886 GB/s， 超过 DRAM 上限 1519 GB/s —— 因为整个 buffer 在 96 MiB 的 L2 里。
  12. 绑定权重不能靠 state_dict 恢复共享关系。两个键写同一块存储， 值不一致时不报错，谁后写谁生效；named_parameters() 默认去重， state_dict() 不去重。
  13. 普通 tensor 属性不随 .to() 迁移，也不会进 state_dict()。 常量表、位置编码缓存这类东西要么 register_buffer，要么自己处理迁移。
  14. optimizer 拿到重复参数会把更新做两遍，等效学习率翻倍且只有一条警告。 传入前先确认没有同一个 Parameter 出现两次。
  15. eval() 不关 autograd，它只把 training 改成 False。 实测 model.eval() 后中间张量照样有 grad_fn；停止建图要靠 no_grad()。

十 · 自测题

1. `sizes=(2,3,4)`、`strides=(1,8,2)`、`offset=5`，float32。逻辑索引 `[1,2,3]` 读第几个字节？这个张量连续吗？ `elem = 5 + 1×1 + 2×8 + 3×2 = 5 + 1 + 16 + 6 = 28`，字节 `112..115`。 连续性：从最后一维往前，期望 stride = 1，实际 `strides[2] = 2` → **不连续**。 （顺带：它也不是 non-overlapping-and-dense，因为 dim2 步长 2、dim0 步长 1， `[0,0,1]`（elem 2）和 `[1,0,0]`（elem 1）之间的元素 1 被 dim0 读到， 布局是交错的。）
2. 为什么 `g.t().contiguous()` 只有 455 GB/s，而 `g.t() * 2` 有 1530 GB/s？ `contiguous()` 必须产生**行主序**的输出，所以读或写里必有一边是跨大步长的， 在 8192 列 bf16 上步长是 16 KB，每个 128 B 的 sector 只用上 2 字节。 `g.t() * 2` 没有这个约束：TensorIterator 按 stride 升序重排维度， 让迭代顺序回到物理连续顺序，输出的 stride 就跟着变成 `(1, 8192)`。 它从来没有真的"按转置顺序"访问过内存。 代价是输出不是行主序 —— 如果下一步你需要行主序，那次拷贝只是被推迟了。
3. `no_grad()` 是把 Autograd 这个 dispatch key 从 key set 里摘掉了吗？ 不是。实测 `no_grad` 内外的 `_dispatch_tls_local_exclude_set()` **完全相同**， tensor 的 key set 也一直带着 `AutogradCUDA`。 `no_grad` 翻的是 `GradMode` 这个 TLS 布尔。Autograd kernel 照样被分发到， 只是它查到 `GradMode` 关着就不建反向节点、不保存中间量。 （历史上确实有过 `AutoNonVariableTypeMode` 是改 exclude set 的， 现在的机制不是这个。）
4. 一次 OOM 报文里 `reserved` 和 `allocated` 差 8 GiB，说明什么？该怎么办？ 说明 8 GiB 被 PyTorch 向驱动要来了、但没有分给任何张量 —— 它们躺在 allocator 的空闲链表里，形状不对，装不下当前这次请求。这就是碎片。 按代价从小到大： 1. 先看 `num_alloc_retries`。如果已经在涨，说明你早就在为碎片付停顿的钱了。 2. `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` —— 本章实测把 浪费从 5920 MiB 降到 2712 MiB，段数 58 → 1。注意它与 IPC/RDMA 注册可能冲突。 3. 让分配尺寸变规整（padding 到 2 的幂、固定 bucket），碎片的根因是尺寸多样性。 4. `empty_cache()` 是最后手段：它同步、清空全部缓存，之后每次分配都要重新 向驱动要。在训练循环里定期调用是自伤。
5. 你写了一个 CUDA kernel `out[i] = in[i] * 2`，测试全过，上线后偶发结果错误。最可能是什么？ 有人给你传了一个非 contiguous 的张量（`transpose`、`permute`、`slice`、 `expand` 之后都会）。你的 kernel 只收到一个 `float*`， 按 storage 线性顺序读，得到的是**另一个形状的数据**，而且不报错。 本章的实测：`naive(x.t())` 的 `max|err| = 12.0`，退出码 0。 两种修法及其代价（8192² fp32，256 MiB）： `.contiguous()` 后再喂 = 2.87× 基准；kernel 自己吃 stride = 1.99× 基准。 最省的是学 TensorIterator 重排迭代顺序（PyTorch 自己的 `bt*2` = 1.01×）。 最起码的自保：入口加 `TORCH_CHECK(x.is_contiguous(), "...")`。 让错误在第一层就被发现，而不是变成一个偶发的错误数字。
6. `x[:, :1].expand(3, 4)` 和 `x[:, :1].repeat(1, 4)` 值相同，为什么还要两个 API？ `expand` 只改 stride（改成 0），零拷贝、零新增显存，但结果**不连续**， 而且多个逻辑位置指向同一块内存 —— 往里写会互相覆盖，所以它是只读语义。 `repeat` 真的分配并拷贝，结果连续、可写。 选择判据：只是要参与一次广播运算 → `expand`（`a + b` 内部就是这么做的）； 需要把结果交给一个要求连续内存的 kernel、或者要往里写 → `repeat`。 本章实测里两者 `nbytes` 恰好都是 48 B，那是巧合（`expand` 复用的是 原始 12 元素的 storage，只读其中 3 个）；看 stride `(4,0)` vs `(4,1)` 才靠谱。
7. 两个模型都持有同一个 `Parameter` 对象，`state_dict()` 与 `named_parameters()` 会给出几个条目？ `named_parameters()` 给 **1 个**（默认 `remove_duplicate=True`，按对象 id 去重）； `named_parameters(remove_duplicate=False)` 给 2 个； `state_dict()` 给 **2 个键**，且两个键对应的张量是两个对象、同一块存储 （`is` 为 False，`data_ptr()` 相同）。 风险在于两个方向：把不去重的参数列表交给 optimizer，同一个参数会被更新两次 （实测一步的变化是去重时的 2.0000 倍）；把值不一致的两个键 `load_state_dict` 进去， 不报错，后写的覆盖先写的。
8. `model.eval()` 之后再前向，反向图还在吗？`model.to("cuda")` 会把 `self.mask = torch.ones(...)` 搬走吗？ 反向图还在。`eval()` 只把 `self.training` 置为 `False`，实测中间张量仍有 `grad_fn`，要停止建图得用 `torch.no_grad()`。 不会搬走。`to()` 只遍历 `_parameters`（`module.py:960`）与 `_buffers`（`:1034`）， 普通属性不在其中。实测 `.to("meta")` 后参数的 device 是 `meta`， 而普通属性的 device 仍是 `cpu`、dtype 仍是 `float32`。要迁移常量表， 用 `register_buffer`，或者自己处理。
9. 同一段「原地修改打断保存值」的程序，eager、`functionalize`、`compile` 分别是什么结果？ - eager：前向正常，**反向报错**（版本计数不匹配）。 - `functionalize('mutations')`：前向、反向都正常，`grad = 8.0` —— 原地修改被换成出参算子 + 边界 `copy_`，保存的 `y` 从未被改过。 - `compile(backend='aot_eager'/'inductor')`：**前向就失败**， `BackendCompilerFailed` 包着同一条 autograd 错误；`compile(backend='eager')` 则与 eager 一样在反向报错。 结论：错误的判定依赖执行路径。函数式化不是"修复"这个错误， 而是把它变成了一个有确定含义的合法计算 —— 这也是同一段代码在 eager 与编译路径下可能给出不同数值的原因（2.7 继续展开）。
