# L1.2 补测：FP8 指令吞吐差异诊断

## 问题陈述

`verify_gemm_ceiling.py` 在 crater (RTX 5090 D, sm_120) 上测得：

- **cuBLAS FP8 GEMM**: 1501 FLOP/clk/SM
- **纯发射基准** (`tensor_core.cu` mma.sync.m16n8k32.e4m3): 1022 FLOP/clk/SM

**cuBLAS 超出基准 47%**，这不可能——真实 GEMM 有访存开销，不应超过纯指令发射上限。

## 假设

1. **基准测错了**：`tensor_core.cu` 只测了 `mma.sync.m16n8k32.e4m3`，可能还有更宽的 FP8 指令（如 `mma.sync.m16n8k64` 或 `mxf8f6f4.block_scale`）
2. **cuBLAS 用了 f16 累加**：理论上 f16 累加可以达到 f32 累加的 2× 吞吐
3. **频率采样不准**：并发采样可能在 GPU 频率波动期采样，导致换算错误

## 实验设计

### 实验 A：扩展纯发射基准

**文件**: `tensor_core_fp8_variants.cu`  
**目标**: 测试所有可能的 FP8 tensor core 指令变体

测试项：
1. `mma.sync.m16n8k32.e4m3` f32 累加（已知基准，1022 FLOP/clk/SM）
2. `mma.sync.m16n8k32.e4m3` **f16 累加**（理论 2× 吞吐）
3. `mma.sync.mxf8f6f4.block_scale.m16n8k32`（如果编译通过）

**运行**：
```bash
# 在 spark (GB10, sm_121) 上编译并运行
cd /home/smc/learn/work/labs/L1
nvcc -O3 -std=c++17 -arch=sm_121a -o tensor_core_fp8_variants tensor_core_fp8_variants.cu
./tensor_core_fp8_variants > ../../out/12_fp8_variants.txt
```

**预期**：
- 如果 f16 累加达到 ~2000 FLOP/clk/SM，说明 cuBLAS 可能用了 f16 累加
- 如果 mxf8f6f4 达到 >1500 FLOP/clk/SM，说明这就是 cuBLAS 用的指令

---

### 实验 B：ncu 指令计数器采集

**文件**: `ncu_fp8_gemm.py`, `run_ncu_fp8.sh`  
**目标**: 用 Nsight Compute 采集 cuBLAS FP8 GEMM 的实际 tensor core 指令计数

关键指标：
- `sm__inst_executed_pipe_tensor.sum`: 总 tensor core 指令数
- `sm__inst_executed_pipe_tensor_op_hmma.sum`: warp 级 mma 指令数
- `gpu__time_duration.sum`: kernel 时间

**运行**：
```bash
# 本地同步到 spark
rsync -av labs/L1/ncu_fp8_gemm.py labs/L1/run_ncu_fp8.sh spark:/home/smc/learn/work/labs/L1/

# SSH 到 spark
ssh spark
cd /home/smc/learn
source env.sh
bash work/labs/L1/run_ncu_fp8.sh

# 拉回结果
rsync -av --ignore-existing spark:/home/smc/learn/work/out/ncu/12_fp8_cublas.* results/spark/ncu/
```

**分析**：
```bash
# 本地分析
python labs/L1/analyze_fp8_ncu.py results/spark/ncu/12_fp8_cublas.csv
```

**预期**：
- 从 `总 FLOP / tensor_inst` 推导出每条指令的 FLOP 数
- 如果是 8192 FLOP/inst → 标准 m16n8k32
- 如果是 16384 FLOP/inst → m16n8k64 或 mxf8f6f4
- 如果是 4096 FLOP/inst → 可能降级到 bf16 或有其他问题

---

### 实验 C：频率采样校验

**文件**: `verify_gemm_ceiling.py` (已存在)  
**目标**: 重新运行，确认频率采样的正确性

**检查点**：
1. 采样线程是否在 kernel 运行期间采样（不是 synchronize 之后）
2. 采样是否覆盖了频率稳态（丢掉前 30% 爬升期）
3. 功耗是否达到功耗墙（~575W for 5090）

---

## 验收标准

实验完成后，应该能回答：

1. **cuBLAS FP8 使用了哪条具体的 tensor core 指令？**
   - 从 ncu 的 FLOP/inst 推导
   - 从纯发射基准的覆盖范围确认

2. **1501 FLOP/clk/SM 是真实的还是测量错误？**
   - 如果是真实的，找到对应的指令变体
   - 如果是错误，定位频率采样或计算中的问题

3. **如何更新 1.2 正文？**
   - 补充完整的 FP8 指令变体表
   - 解释 cuBLAS 超出基准的真实原因
   - 更新"一个超过上限的数字"小节的结论
