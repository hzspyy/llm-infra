==============================================================================
[A] 接受率完全由任务决定
==============================================================================
  ngram（prompt lookup）的猜法：在已生成的文本 + prompt 里找
  和当前后缀匹配的 n-gram，把它后面的几个 token 拿来当草稿。
  所以它在**输出会抄输入**的任务上很准，在自由创作上基本没用。


  [无投机] 抄写任务        217.0 tok/s  (922 ms / 200 tok)

  [无投机] 自由创作        221.0 tok/s  (905 ms / 200 tok)

  [投机 k=4] 抄写任务        893.9 tok/s  加速 4.12×  接受率 95.7%（314/328）
  [投机 k=4] 自由创作        324.3 tok/s  加速 1.47×  接受率 37.0%（296/800）

  同一个引擎、同一份配置，两个任务的加速比可能相差很远 ——
  **投机解码的收益不是引擎的属性，是「任务 × 草稿方法」的属性。**

==============================================================================
[B] 加速比 vs batch：闲算力被吃掉之后就没得花了
==============================================================================
  5.1 实测：decode 在 batch<72 时带宽受限，算力闲着。
  投机就是花那些闲算力。batch 一大，算力不闲了，投机就无利可图。



  抄写任务，batch 扫描
   batch      无投机 tok/s      投机 tok/s       加速
       1          219.9         847.8    3.86×
       4          835.6        3100.9    3.71×
      16         2808.4        7959.9    2.83×
      64         7289.8       11792.7    1.62×

  加速比随 batch 下降 —— 这是投机解码最重要的一条性质。
  它在**低并发、要低延迟**的场景最有价值，高并发下反而是负担。

==============================================================================
[C] 猜几个：num_speculative_tokens 的取舍
==============================================================================
  猜 k 个：验证一次要算 k+1 个位置的前向。
  接受 a 个（0<=a<=k）就前进 a+1 步。
  k 越大，猜中时赚得越多，猜不中时浪费越多。


  基准（无投机）214.8 tok/s
     k      tok/s       加速

     1      388.3    1.81×

     2      567.7    2.64×

     4      898.0    4.18×

     8     1444.4    6.72×

  本任务上最好的 k = 8（1444.4 tok/s）。
  最优 k 取决于接受率：接受率高就该猜多点，低就该少猜。

==============================================================================
[D] 算一遍账：什么条件下投机才划算
==============================================================================
  记：
    p  = 每个草稿 token 的接受概率（近似独立）
    k  = 一次猜几个
    c  = 验证一步相对普通 decode 一步的耗时倍数（>=1）

  一次投机迭代期望前进的 token 数（几何级数）：
      E[前进] = (1 - p^(k+1)) / (1 - p)
  每次迭代的成本是 c 步普通 decode。所以
      加速比 = E[前进] / c

  c 为什么 >= 1：验证要一次算 k+1 个位置。decode 是带宽受限的，
  多算几个位置**几乎不额外花时间**（权重只读一遍）——
  这正是投机能成立的根本原因。但 c 不会恰好等于 1：
  草稿本身要花时间（ngram 查表便宜，草稿模型很贵），
  而且 batch 大时多算的位置会真的占算力（[B] 节）。

       p      k=1      k=2      k=4      k=8
     0.3     1.30     1.39     1.43     1.43
     0.5     1.50     1.75     1.94     2.00
     0.7     1.70     2.19     2.77     3.20
     0.8     1.80     2.44     3.36     4.33
     0.9     1.90     2.71     4.10     6.13
  （表里是 E[前进]，还要除以 c 才是加速比）

  读法：p=0.5 时猜 8 个只比猜 4 个好一点点（1.99 vs 1.94），
  但成本 c 随 k 上升 —— 所以低接受率下猜多是亏的。
  p=0.9 时猜 8 个能前进 5.7 步，值得。

  **临界条件：E[前进] > c。** 接受率太低时投机一定亏，
  因为 c>=1 而 E[前进] 最小是 1。

  两点值得注意：
  1. **MTP 有 26 个模型类型**（deepseek_mtp / qwen3_next_mtp / glm4_moe_mtp /
     kimi_k3_mtp / gemma4_mtp ...）—— 说明新模型普遍自带 MTP 头。
  2. **MTP 被归在 EagleModelTypes 里** —— 在 vLLM 里它走的是
     EAGLE 那条运行时路径，区别在权重从哪来，不在验证机制。

  本 lab 只实测了 ngram（不需要额外权重）。MTP/EAGLE 需要带草稿头的
  模型，这张卡装不下（DeepSeek-V3 类）—— 见正文「没测的部分」。
