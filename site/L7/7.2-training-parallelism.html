7.2

训练并行：ZeRO 到 zero-bubble

DP/ZeRO/FSDP2、TP/PP/SP/CP/EP 的训练状态、反向通信与更新语义；用小型两 rank 对拍和流水模拟分析四框架及规模取舍。

把训练摊到多张卡上，改变的从来不是"算得更快"这一件事。参数、梯度、optimizer 状态和激活这四块状态各自有各自的归属；通信插在前向、反向和更新之间的不同位置；而 loss 的分母一旦跨 rank，就变成一个必须显式约定的量。

这一章在两张 L40S 上把这三件事拆开测：同一个 109M 模型、同一批数据，分别用单进程、DDP、FSDP2 各做一次更新，比较每 rank 的字节、真实发出的 collective、以及更新结果与单进程参照的差；再用 CPU 事件模拟看流水调度的空泡与权重版本；最后复现三类只在多 rank 下才出现的失败。

判据只有一条：先证明更新语义没变，再谈省了多少、快了多少。

本章回答的三个问题

  1. 参数、梯度、optimizer 和激活分别归谁？DDP、ZeRO 各级与 FSDP2 的差别落在哪一项上？
  2. 两 rank 的有效 token 数不相等时，loss 分母、DDP 的默认平均和全局 clip 怎样才能与单进程一致？
  3. 流水调度的空泡、在途激活和权重版本是什么关系？多 rank 特有的失败长什么样？

心智模型：四块状态，三个通信位置

机制拆解与推导

实测环境：worldvln 的两张 L40S（sm_89，无 NVLink）、torch 2.13.0+cu130、NCCL；模型是 8 层、dim 1024、词表 4096 的 MiniLM，共 109,069,312 个 FP32 参数；输入 4 条 × 128 token，rank0 每条只留 8 个 target、rank1 每条留 64 个，全局有效 target 144。所有模式先做一次完整更新预热再记录。

状态归属：实测每 rank 的四块字节

模式 参数 梯度 optimizer 合计 全步峰值
单进程（全局 batch） 416.07 416.07 832.13 1664.27 2096.6
DDP（2 rank） 416.07 416.07 832.13 1664.27 2097.6
FSDP2（2 rank） 208.03 208.03 416.07 832.13 1072.4
FSDP2（不 reshard） 208.03 208.03 416.07 832.13 1271.4

单位 MiB。DDP 与单进程的常驻状态完全一样——DDP 复制的是全部状态，它只把 batch 拆开。FSDP2 把三项都按 dp 维切成两份，合计正好减半。

把这张表补成完整的方案谱系（ZeRO 各级为源码分析，本机未运行 DeepSpeed）：

方案 参数 梯度 optimizer 状态 通信位置
DDP 复制 复制（归约后每 rank 一份完整梯度） 复制 反向中的梯度 all-reduce
ZeRO-1 复制 复制 分片 梯度 all-reduce + 更新后参数 all-gather
ZeRO-2 复制 分片 分片 梯度 reduce-scatter + 参数 all-gather
ZeRO-3 / FSDP2 分片 分片 分片 前向/反向的参数 all-gather + 梯度 reduce-scatter

分级的顺序不是随意的：optimizer 状态最大（AdamW 下是参数的两倍）且只在 step 用到，所以先切它代价最小；参数要参与每一次前向和反向，切它就必须在用之前 all-gather，通信最贵。

通信时序：profiler 抓到的真实 collective

模式 all-reduce all-gather reduce-scatter broadcast
DDP 15 — — 2
FSDP2（reshard） 1 18 9 —
FSDP2（不 reshard） 1 9 9 —

窗口只覆盖前向与反向。DDP 的 15 次 all-reduce 里有 1 次是本 lab 用来汇总全局有效 token 数的计数，其余 14 次是梯度桶——416 MiB 的梯度按默认 25 MiB 分桶，正好落在这个量级；桶的作用是让归约与反向计算重叠。第一次迭代的分桶与稳态不同：DDP 要先观察一次梯度就绪顺序才重建桶，所以这组数字是在预热之后记录的。

FSDP2 的 9 次 reduce-scatter 对应 9 个 fully_shard 单元（8 个 block 加根模块）。all-gather 的次数则直接由 reshard_after_forward 决定：开启时前向 9 次、反向再 9 次，关闭时只有前向的 9 次。

reshard_after_forward 换的是什么

指标 reshard=True reshard=False
前向结束时 allocated 780.4 MiB 1196.4 MiB
反向结束时 allocated 848.4 MiB 850.3 MiB
全步峰值 1072.4 MiB 1271.4 MiB
all-gather 次数 18 9

差额 416 MiB 正好是一份完整参数。上游文档把这个取舍写得很直接：True 在前向后重新分片、反向再 all-gather 一次；False 保留展开的参数、省掉反向的 all-gather，并且建议根模块用 False，因为反向一开始就会立刻用到它。None 的默认行为正是"非根模块 True、根模块 False"。

不等有效数：分母必须是全局的

两 rank 的有效 target 分别是 16 和 128。四个环节必须同时对上，才能与单进程的全局 batch 等价：

  1. loss 用求和而不是平均：每 rank 算 ∑本 rankℓt。
  2. 分母取全局有效数：先 all-reduce 出 144。
  3. 补偿默认平均：DDP 与 FSDP2 的梯度归约都是取平均，所以每 rank 的 loss 要乘 world_size：lossr=W∑rℓtNglobal。归约后正好得到 ∑allℓtNglobal。
  4. clip 用全局范数：clip_grad_norm_ 在归约之后执行，FSDP2 下它作用在 DTensor 上，内部再做一次跨 rank 归约。

实测三种模式的全局梯度范数都是 4.16021729，与单进程参照逐位相同；梯度最大差 1.07e-07（相对最大梯度 5.14e-06）。

注意每 rank 打印出来的 loss 值（DDP 的 0.0542289）与单进程（0.68678945）完全不同，这是对的：它是"本 rank 的 loss 之和 × 2 / 144"，归约之后才等于全局值。用每 rank 的 loss 数字对比两次训练是常见的误判来源。

如果跳过第 3 步，梯度会整体差一个 world_size 倍；如果分母用每 rank 的本地有效数，rank0 的 16 个 token 会获得和 rank1 的 128 个 token 相同的权重——这不是数值误差，是训练目标被改了。

更新后的参数为什么差 2.7e-05

三种模式的梯度都与单进程一致到 1e-07，但更新后参数的最大差是 2.700e-05。这不是 bug：AdamW 首步的更新量约等于 ±η，与梯度大小无关，靠近零的分量只要符号被浮点误差扰动，整个更新就换方向。分布式实现的等价性判据是梯度，不是一步之后的参数；参数差的机制见 7.9。

流水调度：空泡、在途激活、权重版本

四设备、F 记 2 个单位、B 记 4 个单位的事件模拟（通信忽略）：

调度 m=4 总时长 平均空泡 峰值在途激活 m=8 总时长 平均空泡 峰值在途激活
GPipe 42 42.9% 4 66 27.3% 8
1F1B 42 42.9% 4 66 27.3% 4
interleaved（2 chunk） 33 27.3% 8 57 15.8% 11
ZB-V（拆 B/W） 36 33.3% 4 60 20.0% 4

三个结论：

GPipe 与 1F1B 的总时长完全相同。 它们的空泡结构一样，差别只在第一个设备要同时留多少份未回收的激活：GPipe 是 m 份，1F1B 是 stage 数那么多份。m=8 时是 8 对 4。1F1B 换来的是容量，不是时间。

interleaved 用通信换空泡。 每个设备持有 2 个虚拟 stage，块变小、预热变短，m=8 时空泡从 27.3% 降到 15.8%；代价是 stage 间通信次数翻倍（本模拟不计通信），而且在途激活从 4 涨到 11。

ZB-V 用拆分换空泡。 把 backward 拆成沿流水传播的 Bi（输入梯度）和只依赖本 stage 的 W（权重梯度），W 可以推迟到空闲时段。m=8 时最后一个 Bi 在 t=58 结束、最后一个 W 在 t=60 结束。能填空泡的是 W 的位置，不是它可以被跳过——optimizer 仍然要等全部 W。

权重版本是流水并行独有的记账项。 1F1B、m=4 时最后一个 B 在 t=42 结束，在此之前所有 stage 的所有 F 和 B 都用同一个权重版本 V0。哪个设备提前更新，它后续 microbatch 的 forward 就用上了 V1，而这些 microbatch 的 backward 对应的是 V0 的激活，梯度与产生它的前向不再匹配。in-flight 的 microbatch 天然跨越 forward 与 backward 两端，这就是为什么流水实现必须显式管理版本。

TP / SP / CP / EP 的合法性先于性能

多维并行的第一道关是整除条件。一个配置检查器就能挡住大部分非法组合：

配置 判定 原因
world=16，tp2 × pp2 → dp4 通过 —
tp=16 拒绝 world 不能被 tp×pp×cp=32 整除；KV 头数 8 不能被 16 整除
pp=5，32 层 拒绝 层数不能被 pp 整除，各 stage 不均
cp=3 拒绝 序列长度不能被 2×cp 整除（因果 mask 下常按两段分配以均衡负载）
ep=8，dp=4 拒绝 专家并行宽度不能超过可用的数据并行宽度
global batch 250，dp4 × micro 2 拒绝 不能整除，最后一个 batch 的有效数会与其它步不同

GQA 模型上最常见的越界是 KV 头数：注意力头 32 能被 tp=16 整除，KV 头只有 8，切不动。

合法之后再看状态归属。以 7B、BF16 权重 + FP32 master 与 m/v、16 卡 = tp2 × pp2 × dp4 为例：每张卡承担 1.75B 参数（tp 切宽、pp 切深，两者相乘），BF16 参数 3.26 GiB、FP32 master 6.52 GiB、m+v 13.04 GiB；dp 维默认只复制，要再切一次得靠 FSDP/ZeRO，那时三项分别降到 0.81 / 1.63 / 3.26 GiB。激活不随参数分片下降，它由 micro_bs、seq、cp 与重算策略决定。梯度归约组是 dp（与 cp 组合后是 dp×cp），TP 组内做的是激活的 all-reduce，两者的量、频率和所在阶段都不同，见 6.2 与 6.5。

三类只在多 rank 下出现的失败

分支不一致。 rank0 走分支 A、rank1 走分支 B，DDP 在第二次前向抛出：

RuntimeError: Expected to have finished reduction in the prior iteration before
starting a new one. This error indicates that your module has parameters that
were not used in producing loss.

DDP 假定每次迭代所有 requires_grad=True 的参数都参与，未参与的参数没有梯度可归约。find_unused_parameters=True 能救，代价是每步多一次图遍历。

teacher 忘了冻结。 teacher 在 no_grad 下只做前向，永远拿不到梯度；requires_grad 忘了关，它就进了 DDP 的归约集合，于是报同一个错。关掉之后两步正常完成，两 rank 的 student 梯度最大差 0.000e+00。

绕过 DDP 的 forward。 这一条最隐蔽：直接调用 model.module(x) 不会报任何错，但 DDP 的 hook 根本没被装上——实测两 rank 的 student 梯度最大差 1.482，两个进程从此各训各的。KD、多分支和自定义训练循环里很容易写出这种调用。

collective 次序不一致。 两 rank 交换 all-reduce 与 broadcast 的顺序，gloo 在超时后报错：Timed out waiting 15000ms for recv operation to complete。同名 collective 按调用顺序配对，条件分支里的 collective 必须保证所有 rank 都执行且顺序一致。

pre_forward 先 unshard 再 wait_for_unshard：参数必须在计算前聚齐。post_forward 调 reshard 并把自己记进 post_forward_order——这份顺序是反向预取的依据，反向按前向的逆序提前发起 all-gather。pre_backward 里的 unshard 注释写着"no-op if prefetched"，说明预取成功时这里不再产生等待。post_backward 负责 reduce-scatter，并且必须幂等：这个组可能根本没参与本次反向。

这四个钩子解释了实测的数字：9 个组各一次 pre_forward 的 all-gather，reshard=True 时反向再各一次，共 18 次；reduce-scatter 每组一次，共 9 次。

reshard_after_forward 的语义写在 fully_shard 的文档里：

bucket_cap_mb 默认 25 MiB，分桶是为了让归约与反向重叠；find_unused_parameters 的代价是"从输出遍历整张图"；gradient_as_bucket_view=True 让梯度直接是通信桶的视图，省掉一次拷贝，代价是不能对梯度调 detach_()。

DDP 的正确性依赖三个前提：所有 rank 执行相同的图、所有 requires_grad 参数都拿到梯度、归约按同一顺序发生。上面三类失败分别打破了其中一条。

DeepSpeed ZeRO 的对照

ZeRO 的分级在配置参数上就能看出边界（源码按固定 commit 阅读，本机未运行）：stage 1/2 的 reduce_bucket_size 默认 5e8、contiguous_gradients 默认开启，把梯度搬进连续缓冲再归约；partition_gradients 决定是 stage 1 还是 stage 2；single_partition_of_fp32_groups 就是每 rank 自己那一份 FP32 master 参数。stage 3 多出 prefetch_bucket_size、max_live_parameters、param_persistence_threshold 三个旋钮——它们管的是"同时有多少参数处于展开状态"，与 FSDP2 的 reshard_after_forward 解决同一个问题，但把控制粒度放在了字节阈值而不是模块边界上。

设计取舍

模块边界 vs 字节阈值。 FSDP2 的分片单位是 fully_shard 包住的模块，通信次数等于模块数，行为可预测、易对账；ZeRO-3 按参数字节阈值决定持久化与预取，旋钮更细，但"这一步会发几次通信"要从运行时推断。

DDP 的重复工作。 DDP 下每个 rank 都完整跑一遍 optimizer.step，等于把同一份计算做了 world_size 遍。参数规模小、卡数少时这点开销可以忽略；ZeRO-1 把它省掉的同时引入了更新后的参数 all-gather。

通信换容量是有上限的。 FSDP2 把常驻状态减半的同时，把 all-gather 次数从 0 提到 18。无 NVLink 的机器（例如本章的 worldvln）上，这条曲线更快触底；reshard_after_forward=False 就是在这种机器上的常见折中：多留 416 MiB，换掉 9 次反向 all-gather。

 37 class Block(nn.Module):
 38     def __init__(self, dim: int, heads: int):
 39         super().__init__()
 40         self.heads = heads
 41         self.norm1 = nn.RMSNorm(dim)
 42         self.qkv = nn.Linear(dim, 3 * dim, bias=False)
 43         self.proj = nn.Linear(dim, dim, bias=False)
 44         self.norm2 = nn.RMSNorm(dim)
 45         self.up = nn.Linear(dim, 4 * dim, bias=False)
 46         self.down = nn.Linear(4 * dim, dim, bias=False)
 47 
 48     def forward(self, x):
 49         b, t, d = x.shape
 50         h = self.norm1(x)
 51         q, k, v = self.qkv(h).chunk(3, dim=-1)
 52         shape = (b, t, self.heads, d // self.heads)
 53         q, k, v = (t_.view(shape).transpose(1, 2) for t_ in (q, k, v))
 54         attn = F.scaled_dot_product_attention(q, k, v, is_causal=True)
 55         x = x + self.proj(attn.transpose(1, 2).reshape(b, t, d))
 56         h = self.norm2(x)
 57         return x + self.down(F.silu(self.up(h)))

 61     """结构与真实 decoder 一致的小模型：固定 seed 初始化，各 rank 完全相同。"""

 63     def __init__(self):

 66         self.embed = nn.Embedding(VOCAB, DIM)
 67         self.blocks = nn.ModuleList([Block(DIM, HEADS) for _ in range(LAYERS)])
 68         self.norm = nn.RMSNorm(DIM)
 69         self.head = nn.Linear(DIM, VOCAB, bias=False)
 70 
 71     def forward(self, ids):
 72         x = self.embed(ids)
 73         for blk in self.blocks:
 74             x = blk(x)
 75         return self.head(self.norm(x))

 78 def make_shards():

 88 def loss_sum_and_count(model, ids, labels):
 89     logits = model(ids)
 90     target = F.pad(labels, (0, 1), value=IGNORE)[..., 1:]
 91     total = F.cross_entropy(logits.reshape(-1, VOCAB).float(), target.reshape(-1),
 92                             ignore_index=IGNORE, reduction="sum")
 93     return total, int((target != IGNORE).sum())

 96 def state_bytes(model, opt) -> dict:
 97     def nbytes(t):
 98         t = t.to_local() if hasattr(t, "to_local") else t

100 
101     params = sum(nbytes(p) for p in model.parameters())
102     grads = sum(nbytes(p.grad) for p in model.parameters() if p.grad is not None)
103     opt_bytes = sum(nbytes(t) for st in opt.state.values() for t in st.values()
104                     if torch.is_tensor(t))
105     return {"param_MiB": round(params / 2 ** 20, 2),
106             "grad_MiB": round(grads / 2 ** 20, 2),
107             "optimizer_MiB": round(opt_bytes / 2 ** 20, 2),
108             "sum_MiB": round((params + grads + opt_bytes) / 2 ** 20, 2)}

前沿

这一章测的是两 rank 的语义与状态。三条延伸方向本项目分别处理：通信原语本身的算法、拓扑与实测带宽见 6.1；TP/SP/CP/EP 的切分方式与推理侧对照见 6.2、6.3、6.5；框架层面的完整接口与状态归属比较（FSDP2、DeepSpeed、Megatron、TorchTitan 四条路线）见 7.3。

两项本章未做的验证：DeepSpeed 未在本机安装，ZeRO 各级的字节与通信只做了源码分析，实测保持 UNVERIFIED；流水调度只有 CPU 事件模拟，真实 torch.distributed.pipelining 的 schedule 与通信开销同样保持 UNVERIFIED。

陷阱

陷阱 1：把每 rank 打印的 loss 当训练 loss

分布式下每 rank 的 loss 是"本 rank 贡献 × world_size / 全局有效数"，实测 0.0542 对应的全局值是 0.6868。要比较训练曲线，得先明确打印的是哪一个。

陷阱 2：用本地有效数当分母

rank0 的 16 个 token 与 rank1 的 128 个 token 会被赋予相同权重。这不是精度问题，是优化目标被改了。

陷阱 3：忘了补偿默认的梯度平均

DDP 与 FSDP2 的归约都是 mean。用全局分母的 sum loss 时必须乘回 world_size，否则梯度整体小 world_size 倍。

陷阱 4：用一步之后的参数判断实现是否等价

梯度一致到 1e-07 的三种实现，更新后参数最大差 2.7e-05。判据要看梯度。

陷阱 5：以为 FSDP2 只是 DDP 换了个名字

DDP 的四块状态全部复制，FSDP2 把三块切开。实测每 rank 1664 MiB 对 832 MiB，all-gather 从 0 次变成 18 次。

陷阱 6：调用 model.module(...)

不会报错，梯度也不会同步。实测两 rank 的梯度差 1.482。

陷阱 7：把模拟的空泡当成真实加速比

流水模拟不计通信，interleaved 的通信次数按 chunk 数翻倍。模拟能回答"排程结构如何"，不能回答"快多少"。

自测题

  1. DDP 和单进程的每 rank 常驻状态完全相同（都是 1664 MiB），那 DDP 到底省了什么？
展开

什么状态都没省。DDP 省的是时间：把 global batch 拆成每 rank 一份，前向与反向的计算量按 rank 数下降，代价是每步一次梯度 all-reduce（实测 14 个桶）以及每个 rank 重复执行一遍 optimizer.step。要省状态得靠 ZeRO/FSDP 在 dp 维再切一次。

  1. FSDP2 打开 reshard_after_forward 之后 all-gather 次数从 9 变成 18，省下来的是什么？为什么上游建议根模块设成 False？
展开

省的是前向结束到反向开始之间的参数驻留：实测前向后 allocated 从 1196.4 降到 780.4 MiB，差额正好是一份完整参数（416 MiB），全步峰值从 1271.4 降到 1072.4 MiB。根模块建议 False，是因为反向一开始就要用到它，刚 reshard 完又立刻 all-gather 回来，这次通信换不到任何驻留时间。

  1. 两 rank 的有效 token 数是 16 和 128。写出与单进程全局 batch 等价的 loss 表达式，并说明每一项的作用。
展开

lossr=W·∑t∈rℓtNglobal，其中 W 是 world_size、Nglobal=144 由 all-reduce 得到。求和而不是平均，是为了让每个 token 权重相同；分母取全局，是为了让两 rank 合起来的分母正确；乘 W 是为了抵消 DDP/FSDP2 梯度归约的默认平均。实测这样做之后全局梯度范数与单进程逐位相同（4.16021729）。

  1. GPipe 与 1F1B 在本章模拟里总时长完全相同，那 1F1B 的价值是什么？
展开

在途激活。m=8 时 GPipe 的每个设备要同时留 8 份未回收的激活，1F1B 只留 stage 数那么多（第一个设备 4 份，往后递减）。空泡结构一样，省的是容量——这决定了同样的显存能塞下多大的 microbatch 数和多长的序列。
