7.11

训练作业调度、性能诊断与规模决策

训练作业的准入、rank/rendezvous、故障恢复、有效进度、训练 trace、MFU/内存/通信/I/O 诊断与资源预算。

实测机器 本地 CPU（torch 2.14.0）· 分析对象为 7.1 在 crater 采集的实测插桩事件前置 7.2（分片与并行）· 7.3（框架与配方）· 7.4（checkpoint 与容错）· 7.9（精度与优化器）

本章回答的三个问题

  1. worker 退出、慢 rank 或 checkpoint 未提交时，作业怎样恢复到一致的更新点？
  2. 真实事件时间线、合成预算、MFU 和有效训练进度分别说明什么，分母从哪里来？
  3. 怎样从数据、数值、并行与调度四个层次定位浪费，并做资源选择？

心智模型：完成计算不等于提交进度

worker 处理过样本、learner 完成更新、checkpoint 对外可见，是三个不同事件。恢复以已提交的一致状态为准；失败区间可以重放，但对外统计的已提交样本不能重复计数。

关键要点：

  • 提交点由 checkpoint 协议定义，不由"进程还在跑"或"已经算完一批"定义。
  • MFU 的分母是共同 step 窗口。每个 rank 的局部活动跨度只是诊断量。
  • 准入策略的差别体现在同一作业集合的 makespan、空闲卡时与重放卡时上，需要一起报告。

本章使用真实本机子进程检查 watchdog、ACK 和提交协议，用离散事件模拟比较准入策略，用已有实测插桩事件检验时间线口径。worker 内只计算确定性标量状态；不把该协议实验当作 NN 训练、NCCL 故障恢复或生产调度器测量。

机制拆解与推导

作业与数据进度的状态归属

作业声明至少固定代码/环境版本、rank 拓扑、资源、数据版本、恢复入口、重试上限与超时策略。整组准入（gang admission）要让同步训练所需的 worker 一起满足资源条件；单个 rank 已启动而其它 rank 长期等待，通常不能形成有效训练进度。

状态 owner 提交/恢复原则
PID、连接、进度时钟 coordinator 重启后重新建立，不从旧 PID 推断存活
正在处理的 sample IDs worker / 数据分配器 ACK 前后都可能失败，不能直接充当恢复游标
参数、optimizer、scheduler、scaler learner 必须属于同一逻辑更新点
已提交游标与样本计数 checkpoint 协议 与模型状态一同发布
rollout/teacher 请求 ID 和版本 对应服务协议 超时、重复回包与过期结果分别处理

普通 torchrun/Elastic 能启动和重启 worker，应用仍负责 checkpoint 和数据一致性。Kueue/JobSet 这类编排组件负责的是配额、队列与整组准入，不是训练状态：它们能让"整组一起启动"成立，但不会替你保证 optimizer、RNG 和已消费数据已经恢复。

三种准入策略的代价

在固定的 8 卡与作业集合上，三种策略给出不同的 makespan 与卡时账。作业集合是声明的合成假设：J1-long-6cards（6 卡、600 s、优先级 1、checkpoint 间隔 300 s）、J2-low-4cards（4 卡、300 s、优先级 0、间隔 100 s）、J3-small-2cards（2 卡、150 s、优先级 0、间隔 50 s，t=10 s 到达）、J4-high-4cards（4 卡、300 s、优先级 2、间隔 100 s，t=200 s 到达）。

策略 makespan 忙碌卡时 重放卡时 空闲卡时 利用率 高优先级作业排队
FIFO 顺序准入 1050 s 6300 0 2100 0.750 550 s
整组准入 + 保守回填 900 s 6300 0 900 0.875 400 s
优先级抢占 1100 s 7500 1200 1300 0.852 0 s

FIFO 让 2 卡的空闲容量一直等到长作业结束；保守回填把 J3 放进这 2 张卡，makespan 从 1050 s 降到 900 s。抢占把 J4 的排队时间压到 0，代价是 J1 在 t=200 s 被抢占时丢掉 200 s 工作（6 卡 × 200 s = 1200 卡秒），makespan 反而增长到 1100 s。抢占是否值得取决于高优先级作业的价值与 checkpoint 间隔：若 J1 的间隔是 100 s 而不是 300 s，同样在 t=200 s 被抢占时损失为 0。

失败重放与 goodput

设窗口中处理了 nphysical 个样本，新增提交 ncommit 个有效样本，墙钟时间为 T：

throughputphysical=nphysical/T,goodput=ncommit/T.

失败前完成但尚未提交的工作可能再次执行，因此 nphysical>ncommit 是合法现象。两个计数都应保留。这里的 goodput 是已提交处理进度，不自动代表模型质量提升；数据重复、错误 mask、scaler 跳步或退化训练都可能让"忙碌"与有效学习脱节。

本章协议先把完整候选 JSON 写入 .pending，通过同一文件系统的 rename 发布，再原子替换 latest 指针。coordinator 必须先收齐所有当前步 ACK。该实验验证进程故障下的可见性和重放，不验证掉电持久性、分布式文件系统的原子语义或 DCP 的内部协议。

时间线：共同 step 窗口与活动区间并集

同一 rank 的事件区间为 Ii=[si,ei]：

Tspan=maxiei−minisi,Tcovered=|⋃iIi|.

compute=[0,10] ms、comm=[5,15] ms 时两类事件各 10 ms，但并集是 15 ms：把两者相加会把重叠的 5 ms 算两次。没有被事件覆盖的区间只能叫"未归因"，不能自动叫 dataloader 气泡。

多 rank 时还要区分三个量。共同 step 窗口 Twindow 由协调者时钟的步边界定义，是同步训练真正的墙钟分母；活动区间并集 Tcovered 是各 rank 真正在工作的区间；最长局部跨度 Tlocal_max 只是单 rank 的诊断值。两个 rank 的活动错位时，"每个 rank 各自忙 100 ms"并不等于"这一步 100 ms"——本机构造的两 rank fixture 里，共同窗口是 190 ms，而最长局部跨度只有 100 ms，用后者当分母会把 MFU 从 6.54% 高估到 12.42%（1.9 倍）。所以分析器在缺少共同窗口时直接输出 null，不自行补一个分母。

MFU 的公式与限制

给定同一窗口内模型工作量的估计 Fmodel、设备数 N、对应 dtype/稀疏设置的单设备峰值 Ppeak 和共同 step 窗口 Twindow：

MFU=FmodelNPpeakTwindow.

稠密 Transformer 常用 6P×tokens 估计训练 FLOPs，全重算有时用额外 2P×tokens 估计。它们省略部分 attention、embedding、非线性与具体重算结构，不能直接充当硬件计数器读数。HFU 若用估计的执行 FLOPs，必须标为估算；若声称实测硬件利用率，则需要对应计数器。

padding token 参与计算但不一定参与 loss；teacher/critic、rollout 和 checkpoint 可能属于完整作业成本，却不在 learner 的 6P 分子里。当设备峰值、FLOP 模型或共同窗口任一缺失时，本章分析器不输出 MFU 数值。

设计取舍

父进程集中提交容易检查一致性，但父进程自身的高可用是另一项任务。短 deadline 能快速发现无进展，也容易把正常慢步骤当故障，应按实际工作分布设定。同步全组恢复降低状态组合复杂度，却会重复计算已完成但未提交的工作。把"最长局部跨度"当全局窗口会让 MFU 好看而失去意义，因此宁可返回 null。异步 teacher/reward 服务还需独立的请求去重与版本协议；本章的超时用子进程内延迟模拟，没有调用真实远程服务。

工程实现：小进程与分析器

training_job_simulator.py 的 worker 将收到的 sample IDs 求和加入标量状态；两 rank 每步各处理两个 ID，共两步。第二步注入一次故障，随后从 latest 恢复重试。检查器断言最终 committed IDs 为 0–7、rank states 为 [10,18]，并保留所有 physical IDs。

training_job_manifest.py 声明合法作业（6 节点 × 8 卡 = 48 rank）并推导 rank → 环境变量映射，同时用五个反例检查非法配置。training_scheduling_budget.py 输出准入策略对照与公开配方预算账。training_trace_analysis.py 必须显式选择 --input、--cross-rank-demo 或 --synthetic-demo 之一。

作业清单与环境契约

合法清单一次完整流转：PENDING → ADMITTED → INITIALIZING → RUNNING → FAILED_TRANSIENT → RESTARTING → RESUMING → RUNNING → COMPLETED，world_size=48，rank 0 与 rank 47 的环境分别是 RANK=0/LOCAL_RANK=0 与 RANK=47/LOCAL_RANK=7。五个反例各自停在校验阶段并给出具体原因：节点数为 0、每节点 3 卡、未知 rendezvous 后端、缺恢复目录、--nproc_per_node 与资源声明不一致。

真实事件与假设预算分开

RTX 5090 D、SmolLM2-360M、FP32 第二次更新的插桩事件跨度为 134.8905 ms（forward 41.5728 ms、backward/unscale 62.6010 ms、diagnostics/optimizer 30.7167 ms），三个区间在该采集协议下相邻，并集等于跨度、未归因为 0 ms。这份输入没有共同 step 窗口，也没有设备峰值，因此 MFU 输出 null，不做任何分母假设。

--synthetic-demo 的 3B、64 设备、阶段时长都是预算假设，例中 1285 ms 与 MFU=46.41% 来自这些常量的算式，不是 64 张 H100 的运行结果。--cross-rank-demo 是专门暴露口径错误的构造：局部跨度 100 ms、共同窗口 190 ms、并集 180 ms、窗口内未归因 10 ms。

三件事只有分开记才看得见：

  1. "有效 token"必须按阶段换分母。 预训练报的是 next-token target（98,112,000），SFT 报的是回答 token（5,823,900）；把 SFT 的 3.87M 输入 token 当分母会虚高约 1.7 倍。
  2. 峰值由常驻状态决定，不随阶段线性变化。 预训练 8633 MiB 几乎全程恒定；SFT 只有 4351 MiB，因为模型相同而序列更短、batch 更小。按"训练越长显存越高"估算会估错方向。
  3. checkpoint 字节和计算量不是一回事。 预训练 6000 步产生 2.16 GB（last.pt 786.7 MB + best.pt 275.3 MB + 4 个快照），SFT 900 步产生 1.89 GB——步数少 6.7 倍，字节只少 13%，因为每个 checkpoint 的大小由参数量决定。

预算对照：pilot 用 200 步预测 98.3M token 的主运行约 8.2 分钟，实际 8.11 分钟，误差 1.1%；两阶段合计 0.1525 GPU 小时，只有规划上限 12 小时的 1.3%。这不是"预算定得太松"，而是教学项目的规模本来就让预算剩很多：共同任务把文本预训练定在 20M–100M token，6000 步正好落在上沿；剩下的额度按计划留给后训练分支（LoRA/DPO、蒸馏、RL）与视觉适配，各自的预算单列。

数据侧：7.8-I 的两份产品共 182,743,762 B（171 MB），其中预训练分片 171 MB、SFT 张量 11.5 MB；准备时间 CPU 约 2 分钟 + 14 秒。检查点 5.66 GB 全部留在学习盘，进仓库的只有 manifest.json、run.json、metrics.jsonl 与生成样例（合计约 1.5 MB）。

 72 class TrainingTraceAnalyzer:
 73     """训练性能剖析器"""

 75     def __init__(self, workload: ModelWorkloadSpec, rank_traces: List[RankTraceTimeline]):
 76         self.workload = workload
 77         self.rank_traces = rank_traces
 78 
 79     def compute_metrics(self) -> Dict[str, Any]:
 80         # 各卡总耗时
 81         step_times = [t.total_step_time_ms for t in self.rank_traces]
 82         max_step_time_ms = max(step_times)
 83         min_step_time_ms = min(step_times)
 84         avg_step_time_ms = sum(step_times) / len(step_times)
 85 
 86         # 慢卡倾斜度 (Straggler Skew)
 87         straggler_skew_pct = (max_step_time_ms - min_step_time_ms) / min_step_time_ms * 100.0
 88 
 89         # FLOPs 计算
 90         # 标准无重算模型前反向 FLOPs = 6 * P * tokens
 91         p = self.workload.num_params
 92         tokens = self.workload.tokens_per_step
 93         model_flops_per_step = 6.0 * p * tokens
 94 
 95         # 近似执行 FLOPs 推演（不是硬件计数器）：全量重算按额外 2P 估算
 96         if self.workload.has_activation_recompute:
 97             hardware_flops_per_step = (6.0 + 2.0 * self.workload.recompute_ratio) * p * tokens
 98         else:
 99             hardware_flops_per_step = model_flops_per_step
100 
101         # 集群理论算力供给 (FLOPs / ms)
102         # peak_tflops * 10^12 FLOPs/s / 1000 ms/s = peak_tflops * 10^9 FLOPs/ms
103         cluster_peak_flops_per_ms = self.workload.num_gpus * (self.workload.gpu_peak_tflops_bf16 * 1e9)
104         cluster_peak_flops_per_step = cluster_peak_flops_per_ms * max_step_time_ms
105 
106         mfu = (model_flops_per_step / cluster_peak_flops_per_step) * 100.0
107         hfu = (hardware_flops_per_step / cluster_peak_flops_per_step) * 100.0
108 
109         # 各阶段耗时占比 (以最慢 Rank 为关键路径基准)
110         slowest_rank = max(self.rank_traces, key=lambda r: r.total_step_time_ms)
111         breakdown_pct = {
112             "data_loading": round((slowest_rank.data_loading_ms / max_step_time_ms) * 100.0, 2),
113             "forward_gemm": round((slowest_rank.forward_gemm_ms / max_step_time_ms) * 100.0, 2),
114             "forward_attn": round((slowest_rank.forward_attn_ms / max_step_time_ms) * 100.0, 2),
115             "recompute": round((slowest_rank.recompute_ms / max_step_time_ms) * 100.0, 2),
116             "backward_gemm": round((slowest_rank.backward_gemm_ms / max_step_time_ms) * 100.0, 2),
117             "backward_attn": round((slowest_rank.backward_attn_ms / max_step_time_ms) * 100.0, 2),
118             "comm_wait": round((slowest_rank.comm_wait_ms / max_step_time_ms) * 100.0, 2),
119             "optimizer": round((slowest_rank.optimizer_ms / max_step_time_ms) * 100.0, 2),
120             "ckpt_staging": round((slowest_rank.ckpt_staging_ms / max_step_time_ms) * 100.0, 2),
121         }
122 
123         # 瓶颈诊断
124         diagnoses = []
125         if breakdown_pct["comm_wait"] > 25.0:
126             diagnoses.append({
127                 "severity": "CRITICAL",
128                 "bottleneck": "COMMUNICATION_BOUND",
129                 "message": f"通信阻塞等待占比高达 {breakdown_pct['comm_wait']}%，可能存在跨交换机带宽不足、AllGather 通信与计算未重叠或通信拓扑未对齐",
130             })
131         if breakdown_pct["data_loading"] > 10.0:
132             diagnoses.append({
133                 "severity": "WARNING",
134                 "bottleneck": "INPUT_BOUND",
135                 "message": f"数据加载排队气泡占 {breakdown_pct['data_loading']}%，需增加 DataLoader workers 或启用共享内存与 pin_memory",
136             })
137         if straggler_skew_pct > 15.0:
138             diagnoses.append({
139                 "severity": "WARNING",
140                 "bottleneck": "STRAGGLER_SKEW",
141                 "message": f"卡间时延极差达 {straggler_skew_pct:.1f}%，存在慢卡拖累整体同步步频",
142             })
143 
144         return {
145             "workload": asdict(self.workload),
146             "timing_summary_ms": {
147                 "max_step_time": round(max_step_time_ms, 2),
148                 "min_step_time": round(min_step_time_ms, 2),
149                 "avg_step_time": round(avg_step_time_ms, 2),
150                 "straggler_skew_pct": round(straggler_skew_pct, 2),
151             },
152             "utilization_pct": {
153                 "mfu": round(mfu, 2),
154                 "hfu": round(hfu, 2),
155                 "recompute_overhead_ratio": round(hfu / mfu if mfu > 0 else 1.0, 3),
156             },
157             "breakdown_pct": breakdown_pct,
158             "diagnoses": diagnoses,

215 def interval_union(intervals):
216     intervals=sorted(intervals)
217     total=0.;right=None
218     for start,end in intervals:
219         if end<start:raise ValueError('event ends before it starts')
220         if right is None or start>=right:
221             total+=end-start
222             right=end
223         elif end>right:
224             total+=end-right
225             right=end
226     return total
227 
228 
229 def clip_intervals(intervals, window):
230     start, end = window
231     out = []
232     for a, b in intervals:
233         a2, b2 = max(a, start), min(b, end)
234         if b2 > a2:
235             out.append((a2, b2))
236     return out

239 def analyze_events(payload):
240     """按明确的共同 step 窗口分析事件；没有窗口时不给 MFU 分母。
241 
242     每个 rank 的局部跨度只作诊断：同步训练的全局关键路径由共同 step 边界
243     （或显式的跨 rank 观测窗口）决定，最长局部跨度会系统性低估它。
244     """
245     if payload.get('source_kind') not in ('measured','measured_instrumented','author_log','synthetic_fixture'):
246         raise ValueError('event input requires an explicit measured/author source kind')
247     events=payload['events']
248     if not events:raise ValueError('empty event list')
249     if any(not math.isfinite(e[k]) for e in events for k in ('start_ms','end_ms')):
250         raise ValueError('event times must be finite')
251 
252     ranks={}
253     for rank in sorted({e['rank'] for e in events}):
254         own=[e for e in events if e['rank']==rank]
255         span=max(e['end_ms'] for e in own)-min(e['start_ms'] for e in own)
256         busy=interval_union([(e['start_ms'],e['end_ms']) for e in own])
257         categories={key:interval_union([(e['start_ms'],e['end_ms']) for e in own if e['category']==key])
258                     for key in sorted({e['category'] for e in own})}
259         ranks[str(rank)]={'wall_span_ms':span,'union_covered_ms':busy,'unattributed_ms':span-busy,
260                           'category_union_ms':categories,'category_sums_may_overlap':True}
261 
262     max_local_span=max(r['wall_span_ms'] for r in ranks.values())
263     observed_start=min(e['start_ms'] for e in events)
264     observed_end=max(e['end_ms'] for e in events)
265     observed_span=observed_end-observed_start
266     covered_all=interval_union([(e['start_ms'],e['end_ms']) for e in events])
267 
268     window=payload.get('step_window')
269     window_ms=None
270     window_union=None
271     window_unattributed=None
272     if window is not None:
273         start,end=window['start_ms'],window['end_ms']
274         if not (math.isfinite(start) and math.isfinite(end)) or end<=start:
275             raise ValueError('step_window must be a finite increasing interval')
276         window_ms=end-start
277         if window_ms < max_local_span:
278             raise ValueError('provided step_window is shorter than a rank-local activity span')
279         outside=[e for e in events if e['start_ms']<start or e['end_ms']>end]
280         if outside:
281             raise ValueError('events fall outside the declared common step window')
282         window_union=interval_union(clip_intervals([(e['start_ms'],e['end_ms']) for e in events],(start,end)))
283         window_unattributed=window_ms-window_union
284 
285     flops=payload.get('model_flops_per_step_estimate')
286     peak=payload.get('peak_tflops_per_device')
287     devices=payload.get('num_devices')
288     inputs_present=all(x is not None for x in (flops,peak,devices))
289     if inputs_present:
290         if flops < 0 or peak <= 0 or devices <= 0:
291             raise ValueError('invalid FLOP, peak or device count')
292 
293     def mfu_for(denominator_ms):
294         if not inputs_present or denominator_ms is None or denominator_ms <= 0:
295             return None
296         return 100.0*flops/(peak*1e12*devices*denominator_ms/1000.0)
297 
298     mfu=mfu_for(window_ms)
299     if window_ms is None:
300         basis='no common step window in the input: MFU denominator unavailable'
301     elif not inputs_present:
302         basis='common step window present but model FLOP/peak/device inputs incomplete'
303     else:
304         basis='model FLOP estimate over the declared common step window; not a hardware counter'
305     return {'source_kind':payload['source_kind'],'source':payload.get('source'), 'ranks':ranks,
306             'step_window_ms':window_ms,'step_window_clock':(window or {}).get('clock'),
307             'window_union_covered_ms':window_union,'window_unattributed_ms':window_unattributed,
308             'observed_span_ms':observed_span,'covered_all_ranks_ms':covered_all,
309             'observed_unattributed_ms':observed_span-covered_all,
310             'max_rank_local_span_ms':max_local_span,
311             'max_local_span_is_not_global_window':True,
312             'mfu_estimate_pct':mfu,'mfu_basis':basis,
313             'mfu_wrong_basis_pct':mfu_for(max_local_span) if window_ms is not None else None,
314             'hardware_flops_measured':False,'quality_measured':False,
315             'note':payload.get('note')}

前沿与规模决策

SmolLM3 配方的预算账

三份 Nanotron YAML 都写 micro_batch_size=3、batch_accumulation_per_replica=1、sequence_length=4096、train_steps=4,720,000、checkpoint_interval=2000；DP/TP 不在 YAML 里，由 run 名的 48 节点 × 8 卡与 TP=2 推出 DP=192，于是全局 batch 为 576 个样本、11.14 T token（4,720,000 × 576 × 4096）。阶段区间按 YAML 的 start_training_step 切分（stage3 那份同时给出 stage2 与 decay 起点）：stable 1–3,450,000 步 = 8.14 T token，stage2 3,450,001–4,198,000 步 = 1.77 T token，decay 4,198,001–4,720,000 步 = 1.23 T token。

在声明的设备假设下（3 B 参数、384 张卡、989 TFLOP/s 单卡峰值 BF16、40% MFU），6P 估计给出 2.004e23 FLOPs：墙钟约 366.5 小时（15.3 天），合计约 14.07 万 GPU 小时。checkpoint 每 2000 步一次共 2360 次，按 bf16 参数 + fp32 master + Adam m/v 估计每次 42 GB，整轮写入约 99.1 TB。

项 值（声明假设下）
全局 batch 576 样本（3 × 1 × 192）
总 token / 总 FLOPs（6P） 1.114e13 / 2.004e23
墙钟 / GPU 小时 366.5 h / 140,747 GPU·h
checkpoint 次数 / 单次 / 合计 2360 / 42 GB / 99.1 TB
单次故障平均重放（间隔 2000 步） 1000 步 = 2.36e9 token = 29.8 GPU·h

两个可计算的决策：

  • checkpoint 间隔。间隔从 2000 步加到 4000 步，写入量减半（99.1 → 49.6 TB），单次故障平均重放从 29.8 增到 59.6 GPU·h。若故障率是每 10 万步一次，整轮 4.72M 步约 47 次故障，多付约 1.41 千 GPU·h（约为 14.07 万 GPU·h 预算的 1.0%）。所以这个决定取决于存储带宽与故障分布，而不是"越频繁越安全"。
  • 准入策略。碎片化容量（本机例中 2 张空闲卡）用保守回填消化，makespan 从 1050 s 降到 900 s；抢占留给真正有优先级价值的作业，并把可被抢占作业的 checkpoint 间隔压到小于其被抢占的典型时长，让重放损失接近 0。

另三条公开流程的字段账（7.11-G）

SmolLM3 之所以能算出墙钟，是因为它公布了三份训练 YAML 与启动规模。另外三条流程没有公布作者机器的迭代时间或训练日志，能复算的只有配置里写死的量：token 预算、可训练参数组、checkpoint 次数、奖励调用量与公开程度。labs/L7/training_scheduling_budget.py --section public-flows 只读仓库内的配置快照（Cosmos SFT 的 TOML、SpecForge 的 Eagle3/DFlash 配方与草稿 config、CosyVoice2 GRPO 的 run.sh），输出下面三张表，不产生任何 GPU 小时估计。

陷阱

  • 用最长局部跨度当全局窗口。同步训练的墙钟由共同 step 边界决定；本机构造里两者差 1.9 倍。缺少窗口时应输出 null，而不是挑一个更好看的分母。
  • 把不同 YAML 相加。三份 SmolLM3 配置的 train_steps 都是 4,720,000，它们描述同一次训练的不同阶段，相加会得到 3 倍 token 预算。
  • 把类别时间相加。重叠区间只能取并集，未被覆盖的部分叫未归因。
  • 把"spawn 日志"当进程证据。必须有真实 PID 与退出码；"checkpoint 文件存在"也不等于它可恢复。
  • 把高 GPU 使用率当有效进度。要看已提交更新与 goodput，而不是利用率或队列长度。
  • 把配额调度当状态恢复。Kueue/JobSet/torchrun 能保证整组启动与重启，但 optimizer、RNG、数据游标仍由应用负责。

诊断顺序：loss 异常查 mask 与数值；step 慢查未插桩基准与时间线；rank 卡住查 collective 顺序与进程状态；恢复不一致查已提交游标与 optimizer。证据不足时保留未归因，不把预算常量改名为测量。

自测题

  1. 一批数据被处理两次，为什么最终提交计数仍可能正确？

details 答案

第一次处理可能发生在尚未提交的失败区间。恢复后重放该区间，只有与合法模型状态共同提交的 IDs 计入有效进度。本章保留 physical 重复与 committed 无重复两个字段：注入发布前中断时 physical 重复数为 4，committed 仍是 0–7。

  1. 两个 rank 各忙 100 ms、活动错开，这一步的 MFU 分母应该取多少？

details 答案

取协调者时钟定义共同 step 窗口。本机 fixture 中窗口是 190 ms，活动并集 180 ms，窗口内还有 10 ms 未归因；用最长局部跨度 100 ms 会把 MFU 高估 1.9 倍。没有窗口时分析器输出 null。

  1. compute 0–10 ms 与 comm 5–15 ms，总步长是多少？

details 答案

只覆盖这两个区间时跨度与并集均为 15 ms，类别时间之和为 20 ms。不能把重叠的 5 ms 再加到总耗时。

  1. 6P、8P 和一段 trace 足够证明硬件 HFU 吗？

details 答案

不够。6P/8P 是模型/重算 FLOP 近似，trace 是时间材料；只有匹配设备峰值与任务口径才能给出估算，硬件计数仍需要独立采集。MFU 也不衡量任务质量。

  1. 抢占一个 checkpoint 间隔 300 s、已运行 200 s 的作业会丢多少工作？怎样把损失压到接近 0？

details 答案

已保存的检查点进度是 0，损失 200 s，按 6 卡计是 1200 卡秒。把间隔压到 100 s 后，同一时刻已保存 200 s，损失为 0。代价是 checkpoint 次数增加，需要与写入带宽和存储预算一起权衡。
