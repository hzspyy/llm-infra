7.1

训练循环的系统视角

训练供数、前反向、优化器与保存的关键路径；激活重算、累积、冻结/teacher 分支与混合精度的实际状态。

一次训练步里，数据路径、计算路径和 optimizer 时钟是三套各自独立的系统，它们每步只交汇一次。把这三套系统混在一个"每秒多少 token"的数字里，任何优化的效果都解释不清。

这一章在 SmolLM2-360M 上把一次真实更新拆开：每个阶段的 CPU 提交时间与 GPU 执行时间分开记，显存沿时间线分段记，重算开关做等价性与代价对照，四种训练循环各自列状态账，最后看编译把成本挪到了哪里。

判据只有一条：任何性能或容量结论都要写清它对应的分母和那一刻的状态。

本章回答的三个问题

  1. 一次更新由哪些阶段组成，时间和显存分别落在哪里，三种吞吐分母怎么换算？
  2. 重算、冻结、缓存分别改变了什么？哪些是等价变换，哪些悄悄改变了训练目标？
  3. 怎样区分数值失败、跳过的更新和"同样的训练工作真的更快了"？

心智模型：两套时钟，三种分母，一条显存曲线

机制拆解与推导

实测环境：RTX 5090 D、torch 2.13.0+cu130、transformers 5.17.0、SmolLM2-360M（FP32 权重，use_cache=False），序列 512、micro_batch 2、累积 2，记录前先跑 2 个完整更新做预热。

阶段时间：两套时钟分开记

阶段 GPU ms（重算关） CPU ms（重算关） GPU ms（重算开） CPU ms（重算开）
fetch 0.0 0.3 0.1 0.2
h2d 0.1 0.2 0.1 0.1
forward 55.8 30.7 55.7 37.7
backward 88.1 63.7 129.2 105.0
clip 2.8 14.9 2.9 14.8
optimizer 14.1 9.2 14.1 9.3
zero_grad 0.0 0.3 0.0 0.2
合计 161.0 119.3 202.0 167.4

两列的含义完全不同。CPU 列是 Python 侧提交这段工作花的时间，GPU 列是 CUDA event 之间真正执行的时间。forward 的 CPU 时间只有 GPU 的一半多，因为提交跑在执行前面；到 clip 这一步 CPU 反而比 GPU 长，是因为 clip_grad_norm_ 的返回值被读成 Python 数，这次读取会等前面所有 kernel 排空。把两列相加没有任何意义，把某一列当成"这个阶段的耗时"也会得到相反的结论。

fetch 只有零点几毫秒：64 条 × 512 token 的预分词分片完全驻留页缓存，2 个 worker 的预取足够把它藏进上一步。这既不是存储带宽测量，也不能说明真实语料下供数不是瓶颈——存储布局与背压的对照在 7.8。

显存是一条曲线

同一次更新的五个观测点（MiB，torch.cuda.memory_allocated 与该点为止的 max_allocated）：

观测点 allocated（重算关） max_allocated（重算关） allocated（重算开） max_allocated（重算开）
步开始 4265.4 4265.4 5801.5 5801.5
前向后 8102.0 8102.0 4740.9 6317.7
首次反向后 5907.0 8486.0 5862.4 6317.7
optimizer 后 5907.0 9936.3 5862.4 6569.9
zero_grad 后 4457.5 9936.3 4416.7 6569.9

三件事只有沿时间线才看得清楚：

  1. 步开始的 4265 MiB 是参数 1379 + m/v 2760，梯度已经被 zero_grad(set_to_none=True) 释放。第一次有效 step 之前 m/v 还没建立，这时的显存读数不是稳态容量。
  2. 前向后到反向中，激活在释放、梯度在生成，allocated 反而下降，而全步峰值 8486 MiB 出现在这两条曲线交叉的位置。
  3. optimizer 又抬起一个峰（8486 → 9936 MiB）：foreach 实现要为整组参数准备临时张量。按"参数+梯度+optimizer"算出的常驻值算不到这一段。

各项峰值不在同一时刻，因此不能把独立测得的 peak 相加：

Mpeak=maxt[Mparam(t)+Mgrad(t)+Mopt(t)+Mact(t)+Mworkspace(t)].

重算：一次等价变换，代价写在两处

对每一层开启 activation checkpointing，同一批数据、同一份初值：

指标 重算关 重算开
F.silu 实际调用次数 64 128
前向保存的字节 5024.01 MiB / 844 个张量 503.27 MiB / 42 个张量
全步峰值 8486.0 MiB 6317.7 MiB
backward GPU 时间 88.1 ms 129.2 ms
全步 GPU 时间 161.0 ms 202.0 ms
逐 microbatch loss 0.024588 / 0.017064 0.024588 / 0.017064
全局梯度范数 0.760076 0.760076

loss 与梯度范数逐位一致，说明这是一次等价变换——先验证等价，再谈代价。代价落在两处：保存值降到 1/10，全步峰值降 26%；反向多做一遍前向，backward 时间涨 47%，整步时间涨 25%。

保存值的张量个数从 844 降到 42，这个数字比字节更能说明机制：不开重算时每层的每个中间结果都被保存，开了之后每层只留一个入口张量。

显存省下来的不一定能直接换成 batch

重算把峰值从 8486 降到 6318 MiB，但 optimizer 阶段的第二个峰（6570 MiB）没有随之下降，因为它由参数量和 optimizer 实现决定，与激活无关。allocator 的 reserved 也不会自动跟随 allocated 回落：重算关那一次结束时 reserved 是 10076 MiB，比 allocated 高出 5.6 GB。判断"还能不能塞下更大的 batch"要看这两条曲线，而不是单一数字。

三种分母

同一次更新可以报成三个完全不同的吞吐：

配置 样本/秒 有效 token/秒 更新/秒
重算关 33.52 15018.3 8.381
重算开 23.90 10705.7 5.974

这三个数来自同一次运行的同一段墙钟，只是分母不同：4 个样本、1792 个有效 target、1 次 optimizer 更新。输入里有 2048 个 token，但前 1/8 的位置被 mask 成 prompt，所以有效 target 是 1792 而不是 2048。跳过的 step 不计入更新数，也不该计入吞吐：FP16 因为溢出跳步时，它少做了 optimizer 的工作，完成的训练工作和没跳步的运行不是同一件事。

四种训练循环的状态账

把 encoder → projector → head 这套结构分别按四种方式训练（CPU 教学模块，8×64×128 输入）：

循环 总参数 可训练 占比 保存值 MiB optimizer MiB
A 全参微调 263,424 263,424 100.0% 4.69 2.01
B LoRA 274,688 11,264 4.1% 3.32 0.09
C 冻结 encoder（no_grad） 263,424 197,376 74.9% 3.25 1.51
C' 冻结 encoder（未写 no_grad） 263,424 197,376 74.9% 3.25 1.51
D teacher/student 592,896 263,424 44.4% 5.19 2.01

三个容易搞反的结论：

LoRA 省的是 optimizer 状态，不是激活。 optimizer 从 2.01 降到 0.09 MiB（22×），保存值只从 4.69 降到 3.32 MiB。反向仍要穿过整个 base，激活该存还得存。

C 与 C' 的保存值完全相同。 输入和 encoder 参数都不要求梯度时，autograd 根本不会为这段前向建图，写不写 no_grad 在这个拓扑下只省图节点和 Python 开销。但换一个拓扑结论就反过来：把一个可训练的前置层放在冻结 encoder 之前，保存值从 3.25 涨到 4.75 MiB，因为梯度必须穿过冻结段。判据不是这个模块冻结了没有，而是它下游的梯度需不需要穿过它。

teacher 只前向，但它占显存也占时间。 D 行的 teacher 参数计入常驻，却没有梯度和 optimizer 状态；它的前向时间是每步成本的一部分，只统计 student 的 forward/backward 会低估一整块。

缓存的键必须包含所有变量

冻结一段前向之后，很自然想把它的输出缓存下来。缓存合法的前提是这段前向对本次训练是确定性的常量，缓存键要包含所有能改变它的东西：

  • 只换数据增强的 seed，特征就变了（实测最大差 0.065）。键里没有增强 seed，第二个 epoch 会命中第一个 epoch 的结果，等于悄悄关掉了数据增强。
  • encoder 参数被更新之后（哪怕只是某个阶段解冻），老键仍然命中，缓存值与重算值最大差 0.869。键里必须带参数版本。

混合精度在真实模型上的边界

同一个模型、同一份权重，三种精度配置各做两次尝试：

输入 配置 首次 loss logits dtype 两次梯度 finite 梯度范数 optimizer 调用
分片文本 FP32 0.09011 float32 是/是 1.8107 2
分片文本 BF16 autocast 0.09049 bfloat16 是/是 1.8081 2
分片文本 FP16 autocast + scaler 0.09011 float16 是/是 1.8117 2
随机 token FP32 12.33378 float32 是/是 13.9104 2
随机 token BF16 autocast 12.33349 bfloat16 是/是 13.8776 2
随机 token FP16 autocast + scaler 12.33375 float16 是/是 13.9057 2

三种配置在这两份输入上都完成了两次有效更新，FP16 没有溢出。溢出边界由 scale × 中间梯度量级决定，扫描初始 scale 立刻看得到：

初始 scale 梯度 finite 参数是否更新 update 后 scale 首个非有限张量
65536 True True 65536 —
1048576 False False 524288 model.embed_tokens.weight（22/47185920）
16777216 False False 8388608 model.embed_tokens.weight（1924711/47185920）
268435456 False False 134217728 model.embed_tokens.weight（2154434/47185920）

220 那一行只有 4700 万个元素里的 22 个越界，正好卡在边界上；再放大 16 倍就有 190 万个。scaler 每次把 scale 减半、跳过这一步，这正是它存在的理由。溢出不是 dtype 的固有属性，而是 dtype、scale、数据和当前权重共同决定的；精度机制本身见 7.9。

被记录下来的非有限梯度 dtype 是 FP32：梯度以 FP32 落盘不代表它是 FP32 算出来的，已经产生的 Inf 不会因为转成更宽的 dtype 而恢复。

编译把成本挪到了哪里

torch.compile 包住整个模型后：

情形 每步 ms
eager 稳态 88.79
compile 首次调用（冷 inductor 缓存） 20783.8
compile 首次调用（热缓存） 2339.7
compile 稳态 82.87

稳态只快了 6.7%，而冷缓存下的第一次调用要 20.8 秒。更贵的是形状变化：

输入形状 该次耗时 ms 新增编译帧
512 再来一次 82.7 0
384 39890.6 1
256 57.2 0
384 第二次 72.1 0

第二种形状触发了一次 39.9 秒的重编译，但之后 256 没有再编译——dynamo 在第二次见到新形状时把这一维标成动态，生成的 kernel 覆盖了后续长度。于是变长训练的编译代价集中在前两个形状上，而不是每种长度一次。

按这组数字算：冷启动共付 60.7 秒，稳态每步省 5.9 ms，要跑一万步以上才回本。这不是"编译没用"的结论，而是编译的收益必须按作业总步数摊销，短作业、频繁重启和形状高度多样的训练都会把它吃掉。

完整教学项目：从随机初始化到预算内预训练（7.1-F）

前面所有实验都在 SmolLM2-360M 的单步上做。F 任务要求换一个更小、可完全复现的载体，从随机权重出发完成一段真实预训练：数据来自 7.8 的产品，产物接 7.5 的 SFT。

载体与协议

模型用 MiniMind-3 的结构（源码固定 commit 1e6e909），参数随机初始化：hidden 768、8 层、8 个 query head / 4 个 KV head、head_dim 96、RoPE、SwiGLU、RMSNorm、词表 6400、tied embedding，共 63.91M 参数。分词器用同一仓库的 BPE（词表 6400，bos 1 / eos 2 / pad 0）。

项 值
数据 7.8-I 的 data-pretrain：train 80,000,044 token（348,920 文档）
序列与 batch seq 512、micro-batch 32、累积 1 → 16,384 token/step
优化器 AdamW，lr 5×10−4，lr·(0.1+0.45(1+cos(πs/S)))，无 warmup，clip 1.0
精度 BF16 autocast + FP32 master weight，allow_tf32=False
步数与调度 S=6000 步（98.3M 输入 token，约 1.23 个 epoch）
采样顺序 window_order.npy：固定排列（seed 42），恢复时复用同一文件
观测 每 10 步记 loss/grad/update/吞吐/峰值；每 250 步在 64 个固定 val 窗口上评测并保存
硬件 RTX 5090 D 32 GB（crater）

bash labs/L7/run_teaching_lm.sh pretrain     # 主运行
bash labs/L7/run_teaching_lm.sh eval-pretrain
bash labs/L7/run_teaching_lm.sh export

这解释了一个实测现象：forward 函数执行了两次，但 module forward hook 只触发一次。 一个四行的探针就能确认——checkpoint(m.__call__, x, use_reentrant=False) 之后立即计数是 {'fwd': 1, 'hook': 1}，backward 之后是 {'fwd': 2, 'hook': 1}。用 hook 统计重算次数会漏掉重算；本章因此改为统计 F.silu 的实际调用次数（64 → 128）。

check_recomputed_tensors_match 还会比对两次前向的张量元数据：如果这段前向不确定（例如带 RNG 的 dropout 没有被正确恢复），重算会在这里报错，而不是悄悄给出不同的梯度。

设计取舍

插桩与测量互相干扰。 本章的每个阶段都放了 CUDA event，clip 里还读了一次 Python 标量——这会强制同步，让 CPU 列失真。诊断运行回答"做了什么、在哪失败"，稳态基准必须去掉插桩、固定有效工作后另跑。两种运行的数字不能混进同一张表。

重算的粒度是可选的。 本章开的是每层重算，这是最省内存也最费时间的一端。选择性重算（只对 attention 或只对 MLP）介于两者之间；哪一种合适取决于该层的"保存字节 / 重算时间"比值。

编译的收益要摊销。 稳态 6.7% 的收益换 60.7 秒的一次性成本，还要承担形状变化的重编译。真实作业里的判断依据是总步数、形状分布和重启频率，不是单步时间。

前沿

这一章测的是单步机制。要把它接到真实作业上还差三件事，本项目分别记在别处：多 rank 的通信与分片改变的是同一条曲线上的哪一段，见 7.2；把活动区间并集当成完整 step 时长的错误，以及 MFU 的口径条件，见 7.11；供数侧的存储布局、背压与 straggler 见 7.8。

编译一侧还有两个未测方向：区域编译（只编译 decoder layer）能把首次编译成本压到多少，以及 mark_dynamic 手动声明动态维度能否避开第二次形状的全量重编译。本章只验证了自动动态形状在第二个形状之后生效，这两条保持 UNVERIFIED。

F 任务本身还剩三块没做，都属于"规模与生产"，不属于教学主线的必需项：真实冷存储下的供数对照（需要把数据放到对象存储或限速盘上）、多 rank 下同一条时间线的变化（接 7.2 与 7.11）、以及第二个 epoch 的重新洗牌（本次只跑 1.23 个 epoch，window_order.npy 在 epoch 间复用同一排列，重洗牌对结论的影响未测）。

陷阱

陷阱 1：把 CPU 时间和 GPU 时间相加

CPU 提交可以跑在 GPU 执行前面。本章 forward 的 CPU 时间是 GPU 的一半多，clip 的 CPU 时间是 GPU 的五倍——后者是因为读了一次 Python 标量触发同步。两套时钟各自成立，加起来没有意义。

陷阱 2：用模块 hook 统计重算次数

非重入 checkpoint 的重算会真的再跑一遍 forward 函数，但不会再触发 module forward hook。要观察重算，得在函数层面计数。

陷阱 3：把某一时刻的显存当稳态容量

第一次有效 step 之前 m/v 还没建立；zero_grad(set_to_none=True) 之后梯度也不在。这两个时刻的读数都比稳态低一大截。

陷阱 4：认为重算一定更快或一定更省

重算是等价变换，省的是激活、花的是一次额外前向。本章省 26% 峰值、多花 25% 时间。optimizer 阶段的第二个显存峰不随重算下降。

陷阱 5：冻结了就以为不用存激活

只要下游梯度需要穿过这段前向，它就必须建图并保存中间结果。可训练模块在冻结段之前时，保存值反而上升。

陷阱 6：缓存冻结段的输出却不记键

增强 seed 变了、encoder 参数变了，缓存都会给出过时的值，而且不会报错。能缓存的前提是这段前向在本次训练里是常量。

陷阱 7：拿 FP16 跳步当成加速

跳步意味着这一步没有做 optimizer 的工作。要比较速度，先确认两次运行完成了同样数量的有效更新。

自测题

  1. 同一次更新报出 33.52 样本/秒、15018 token/秒、8.381 次更新/秒，为什么这三个数不矛盾？
展开

它们共享同一段墙钟，只是分母不同：4 个样本、1792 个有效 target、1 次 optimizer 更新。输入里有 2048 个 token，前 1/8 被 mask 成 prompt，所以有效 target 是 1792。比较任何两次运行的吞吐前，必须先确认用的是同一个分母。

  1. 开启每层重算后 loss 与梯度范数逐位不变，这说明了什么？不能说明什么？
展开

说明这次重算是等价变换，没有改变训练目标——这是谈代价之前必须先过的一关。不能说明它更省或更快：本章实测峰值从 8486 降到 6318 MiB，但 backward 时间从 88.1 涨到 129.2 ms。也不能说明所有实现都等价：重算要求这段前向确定，带 RNG 的算子必须正确恢复随机状态，否则 check_recomputed_tensors_match 会报错。

  1. FP16 在 scale=65536 时两次更新都正常，把初始 scale 调到 220 后梯度出现 22 个非有限元素。这是 dtype 的问题吗？
展开

不是。溢出的判据是 scale × 中间梯度的量级是否超过 65504，scale 是可调的，梯度量级由数据和当前权重决定。scaler 的设计正是为此：越界就跳过这一步并把 scale 减半，逐步收敛到可用区间。

  1. torch.compile 稳态每步省了 5.9 ms，为什么不能直接说"编译让训练快了 6.7%"？
展开

因为还有一次性成本：冷缓存下首次编译 20.8 秒，第二种输入形状又触发 39.9 秒重编译，合计 60.7 秒，要一万步以上才摊销得回来。收益要按作业总步数、形状分布和重启频率算；形状多样或经常重启的作业可能永远不回本。
