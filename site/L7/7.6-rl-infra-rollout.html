7.6

RL infra：rollout、policy 版本与权重同步

从 policy gradient、PPO/GRPO、奖励与偏好数据到 rollout/learner/reference、策略版本、异步、权重同步和恢复，并分析视觉与语音 RL 流程。

本章回答的三个问题

  1. 奖励、GAE 和组内基线怎样形成一次合法的策略更新？
  2. PPO clipping 限制什么，为什么它不能作为异步策略滞后的硬安全边界？
  3. rollout、learner、reference、critic/reward 怎样交换带版本的状态？

心智模型：行为策略和当前策略分别记录

rollout 按行为策略生成动作；learner 可能已经持有较新的权重。一次训练样本需要保留 prompt/动作、有效 mask、行为 logprob、reward、终止状态和版本，才能解释当前 logprob 与行为 logprob 的比率。

机制拆解与推导

PPO clipping 的符号分支

对固定采样动作，令 r=exp(logπθ−logπold)、优势为 A。最小化的单项 loss 为：

ℓ(r,A)=−min[rA,clip(r,1−ϵ,1+ϵ)A].

当 A>0 时，上侧超过 1+ϵ 的继续增益被截平，但 r 本身不被约束；当 A<0 时，下侧低于 1−ϵ 的继续增益被截平，r 在上侧越大仍可能被强烈惩罚。取 ε=.2：

A r loss 对 r 的梯度
+1 .1 -.1 -1
+1 10 -1.2 0
-1 .1 .8 0
-1 10 10 +1

最后一行直接说明 clipping 不是“把所有有效比率锁在 [.8,1.2]”。共享参数、其它样本梯度与 optimizer 状态还可能改变某个已截平动作的概率。PPO-Clip 不保证新策略留在严格 trust region；KL 监控/early stopping、rollout correction 和过期样本拒绝是不同机制。

GAE 与真实终止

对 transition t，dt=1 表示真实终止，价值 bootstrap 为 Vt+1：

δt=rt+γ(1−dt)Vt+1−Vt,

At=δt+γλ(1−dt)At+1.

时间截断未必是环境终止；若任务仍可继续，末尾 bootstrap 不能无条件置零。GAE 的递推与显式展开应一致。本章用两组各四条、每条三步的轨迹检查正常终止和截断尾部。critic 不必与 policy 同等规模，具体容量由架构决定。

GRPO 与归约单位

对同一 prompt 的 G 个回答，用本章选定的 population std 归一化：

Ai=Ri−R¯1G∑j(Rj−R¯)2+ϵ.

它不需要单独拟合 value network，但多个 completion 的生成与打分仍有成本，不能直接换算为“总显存至少省一半”。不同实现可使用 sample std、不除 std 或不同 group 过滤；必须固定 recipe。

回答各自先按长度平均再跨回答平均，与全批有效 token 平均是两个目标。mask 必须对齐模型生成动作，prompt 作为条件参与前向但不一定作为策略梯度 target。组内奖励全相同且有稳定项时，优势为零；这只让该优势项的梯度为零，KL、entropy、weight decay 或已有动量仍可能使参数更新。

本章还对采样 logprob 上的 elogπref−logπ−(logπref−logπ)−1 求导。该 k3 形式在按当前策略采样等条件下与 KL 期望相连；固定旧轨迹上的数值项不能直接当作已精确计算完整分布 KL。

异步 lag 是运行时协议

learner_version - behavior_version 是版本差，不直接等于策略分布距离。运行时要保留行为 logprob、校验模型/模板版本、限制队列年龄、处理重复回包，并在需要时应用正确的 importance correction 或拒绝规则。仅设置 PPO 的 ε 无法提供这些保证。reward 服务返回及时也不证明 reward 与真实任务目标一致。

设计取舍

共置可复用 GPU，但推理 KV、训练激活/optimizer 与权重切换有峰值和等待；分离可重叠 rollout 与 learner，但增加权重发布、队列与陈旧度管理。两者的 MFU、空泡与同步成本依赖工作量配比，不能按“少于 32 卡用共置、千卡必然满载”直接判断。slime 与 OpenRLHF 的接口/时序需要分别核对，当前 veRL 源码分析不代替三框架验收。

 31 def compute_grpo_objective_analytical(
 32     logpi_new: torch.Tensor,  # shape [G]
 33     logpi_old: torch.Tensor,  # shape [G]
 34     rewards: torch.Tensor,    # shape [G]
 35     clip_eps: float = 0.2,
 36     kl_beta: float = 0.04,
 37     logpi_ref: Optional[torch.Tensor] = None,
 38 ) -> Tuple[torch.Tensor, torch.Tensor, torch.Tensor]:
 39     """
 40     计算标量 GRPO 损失以及关于 logpi_new 的解析梯度 (FP64)
 41     """
 42     G = rewards.shape[0]
 43     mean_r = rewards.mean()
 44     std_r = rewards.std(unbiased=False) + 1e-8
 45     advantages = (rewards - mean_r) / std_r
 46 
 47     ratios = torch.exp(logpi_new - logpi_old)
 48     ratios_clamped = torch.clamp(ratios, 1.0 - clip_eps, 1.0 + clip_eps)
 49 
 50     surr1 = ratios * advantages
 51     surr2 = ratios_clamped * advantages
 52 
 53     # PPO/GRPO 最小化代理目标: max E[min(surr1, surr2)] => min E[-min(surr1, surr2)]
 54     # 取 element-wise 最小值
 55     is_surr1_smaller = (surr1 < surr2)
 56     selected_surr = torch.where(is_surr1_smaller, surr1, surr2)
 57 
 58     # KL 惩罚项: D_KL(pi || ref) approx (exp(logref - lognew) - (logref - lognew) - 1) 或简单的反向 KL
 59     if logpi_ref is not None:
 60         kl_pen = torch.exp(logpi_ref - logpi_new) - (logpi_ref - logpi_new) - 1.0
 61     else:
 62         kl_pen = torch.zeros_like(logpi_new)
 63 
 64     loss_per_item = -selected_surr + kl_beta * kl_pen
 65     total_loss = loss_per_item.mean()
 66 
 67     # 解析梯度推导 d Loss / d logpi_new:
 68     # d ratio / d logpi_new = ratio
 69     # d surr1 / d logpi_new = ratio * adv
 70     # d surr2 / d logpi_new = 0 (当处于 clamp 边界之外时)
 71     # 因此若 surr1 < surr2 或处于 clamp 内部未饱和，导数为 ratio * adv；若饱和且被 clip，导数为 0
 72     in_unclipped_region = (ratios >= 1.0 - clip_eps) & (ratios <= 1.0 + clip_eps)
 73     active_grad_mask = is_surr1_smaller | in_unclipped_region
 74 
 75     grad_ratio = torch.where(active_grad_mask, ratios * advantages, torch.zeros_like(ratios))
 76     
 77     # KL 导数: d/d lognew [exp(ref - new) - (ref - new) - 1] = -exp(ref - new) + 1
 78     if logpi_ref is not None:
 79         grad_kl = kl_beta * (1.0 - torch.exp(logpi_ref - logpi_new))
 80     else:
 81         grad_kl = torch.zeros_like(logpi_new)
 82 
 83     analytical_grad = (-grad_ratio + grad_kl) / G
 84 
 85     return total_loss, analytical_grad, advantages

147 def gae(rewards, values, terminated, gamma=.99, lam=.95):
148     advantages=torch.zeros_like(rewards)
149     carry=torch.zeros_like(rewards[...,0])
150     for t in range(rewards.shape[-1]-1,-1,-1):
151         continuation=1-terminated[...,t]
152         delta=rewards[...,t]+gamma*values[...,t+1]*continuation-values[...,t]
153         carry=delta+gamma*lam*continuation*carry
154         advantages[...,t]=carry
155     return advantages

起点是 7.5 的 SFT 权重（768/8），任务在本地合成、答案在出题时已知，判分只做"从回复里取最终整数与 gold 比较"，不引入奖励模型。先用同一份 SFT 权重在验证集上量两类候选任务的基础成功率，再决定主任务：

任务 说明 easy medium hard
arith a+b，easy 一位、medium 两位、hard 三位加两位 0.030 0.000 0.000
count 统计 {A,B,C} 串里 A 的个数，长度随难度为 5/8/12 0.180 0.040 0.015

算术任务对 64M 教学模型整体超出能力范围，arith-easy 只有 3%，两位数起为 0——在这种起点上 GRPO 拿不到组内信号。计数任务在长度 5 时基础成功率 18%，是本题材下唯一有可用信号的一档。主任务因此定为 count/easy，题集 2,000/200/200 条 train/val/test，按题目内容独立生成，验证集与测试集不参与训练。

奖励三项：答对 +1.00、恰好一个 </think> 块 +0.25、总长在 20–800 字符 +0.25，再减去 3-gram 重复惩罚（上限 0.5）。另设一个把格式项权重置 0 的变体，用于把"解对题"与"守格式"从优势里分开。协议：组大小 G=8、每步 16 个 prompt、温度与 lr 分档对照、最多 192 个新 token、200 步，inner-epochs=1。

四条判读：

纯可验证奖励把留出正确率翻了一倍。 v2 的验证集正确率从 0.180 升到 0.305（第 125 步最高），留出测试集从 0.125 升到 0.235；同一权重末步在测试集上是 0.255。这是"规则奖励确实改变了任务行为"的证据，样本量是各 200 题，两个数字都远大于该样本量下 ±0.05 量级的波动。

奖励上涨可以完全不带动任务质量。 v1 的奖励从 0.066 升到 0.294，采样正确率却从 0.070 掉到 0.008，验证集在 50 步后归零。机制不在目标函数本身，而在信号密度：温度为 0.9 时采样正确率只有约 7%，8 条一组里"一条都没答对"的概率超过一半，这些组对正确性没有优势；剩下的差异全部来自格式、长度与重复惩罚，策略于是优化了它们。零方差组占比 0 在这里恰恰是危险信号——它说明每组都有优势可用，只是优势不是关于任务的。

温度决定可验证奖励能不能用起来。 v2 与 v3 只差温度：0.5 时采样正确率 9–17%、留出 0.235；0.9 时 7–13%、留出 0.170。采样温度越低，正确样本越容易落进组内，组内基线才有东西可比。这条与"温度只是采样多样性"的直觉相反，也解释了为什么把 v1 的失败归因于"奖励设计"并不完整。

本轮没有出现权重陈旧与裁剪。 inner-epochs=1 且 rollout 与 learner 是同一份权重，所以每一步的 ratio 恒为 1.000、clip_fraction 恒为 0，PPO 裁剪在本轮不生效；策略版本等于步数，不存在过期轨迹。裁剪的语义由 rl_objective_reference.py 的 FP64 参照与 veRL 源码材料覆盖，不能因为这里跑通就认为裁剪路径已验证。空输出比例为 0，无效输出没有成为本轮的变量。

单 arm 成本约 307 s（0.085 GPU 小时），峰值 15.1 GiB，其中大头是 128 条序列 × 222 位置 × 6,400 词表的 FP32 log_softmax。真实的多副本 rollout、异步 lag、分离式 learner 与 reward/teacher 服务按本节的前沿与 7.11 的材料分析，没有在本轮运行。

前沿

RLVR 使用代码测试、数学或形式化检查等规则奖励，但规则仍可能不完整，也可能被策略利用。Flow-GRPO、DanceGRPO 与语音 GRPO 要定义自己的随机动作、transition logprob、reward 与终止；确定性 ODE 输出不能未经转换就套文本 token 的概率比。此处没有运行图像、视频、语音或机器人 RL，相关质量、服务成本和非文本概率链保持 UNVERIFIED。

陷阱

current、behavior 和 reference 是三种角色，不能随意共用 logprob；零优势不保证所有参数静止；clip fraction 不等于过期轨迹比例；版本差为 1 也可能出现较大分布差异。成功生成、奖励上涨与目标任务质量提升分别需要证据。

自测题

  1. A=-1、r=10、ε=.2 时，标准 PPO-Clip 的 loss 和对 r 的梯度是多少？
展开

min(-10,-1.2)=-10，所以 loss=10、梯度=1；比率没有被硬限制为 1.2。

  1. 为什么 truncated 尾部与真实 terminated 不能用同一个无条件零 bootstrap？
展开

截断可能只是采集窗口结束，环境仍可继续，此时下一个状态价值仍属于 return 估计。真实终止才把后续项消去。

  1. GRPO 组内奖励相同，参数一定不更新吗？
展开

优势项可以为零，但 KL/entropy、optimizer 动量或 weight decay 仍可能产生变化。必须检查完整目标与 optimizer，而非只看优势向量。
