写作与证据要求

  1. 深度：每个机制推到能自己写一遍。源码走读给版本、真实 file:line 与代码原文，并说明设计取舍。
  2. 架构与品味：每个源码走读都要回答「为什么是这个结构」——不变量是什么、边界划在哪、谁拥有状态、扩展一个后端要动多少处、错误在第几层被发现。把被否掉的方案也写出来。看得懂代码只是起点，能判断一个设计好不好才是能力。
  3. 广度：同一层的多种实现围绕同一个问题并置对照（vLLM ⟷ SGLang，CUDA ⟷ Triton ⟷ TileLang，FSDP2 ⟷ Megatron，NCCL ⟷ NVSHMEM ⟷ DeepEP），而不是罗列项目名。
  4. 原始现场：关键机制必须有可检查的实体——config、词表片段、权重清单、图文本、PTX/SASS、真实报错。每组材料说明输入、采集命令、完整文件入口、该看哪些字段。
  5. 证据分层：源码事实、已有测量、模型预测、待验证解释四类分开标注。公式推算不等于实测；计时相近不等于等价；输出相同不能反推实现。没实测的写「待验证」并说明怎么验。

怎么读这套材料

顺序不是纯自底向上，也不是纯自顶向下。L0 先建立一本资源账本——一次请求的时间、字节、 FLOP 分别去了哪；它是后面每一章的挂载点。然后 L1–L5 自底向上打穿，每一层都在解决下一层 暴露出的约束。最后 L6–L8 横向展开，把单机的结论放大到多卡、训练与集群。

每个模块固定十段：本章回答的三个问题 → 心智模型 → 机制拆解 → 工程实现·源码走读 → 工程实现·自己写一遍 → 动手 lab（含实测数字）→ 原始现场 → 前沿 → 陷阱 → 自测题。

数字诚实性：站内每个数字都标注机器、日期与产生它的命令，原始输出留在 results/。没有实测的数字一律显式标注 未实测， 不会把别处 blog 的加速比当作已验证事实呈现。

L3

Attention 与序列核心整个系统里最重要的一个算子

Attention 同时是算法瓶颈和系统瓶颈，也是硬件与算法协同设计最激烈的战场。

  1. 3.1
    从 attention 数学到内存墙 有正文
    朴素实现要把 S×S 写进显存再读回来：S=8192 时峰值差 128 倍，S=16384 直接 OOM。算术强度的推导（朴素 D/3 与 S 无关，分块 S/2 随 S 增长）与实测吻合。online softmax 从「为什么减最大值」推到分块 attention，自写版本与 SDPA 对拍到 1e-7。
  2. 3.2
    FlashAttention 1 → 2 → 3 → 4 有正文
    每一代针对的具体硬件矛盾，只讲能测的。实测：kernel 在 B·H=1 时已达峰值 46%，证明它沿序列切分（FA1→FA2 的核心改动）；标定后 SFU exp = 16/clk/SM 对 tensor core 511 FLOP/clk/SM，一次 exp 抵 31 次浮点运算（FA4 的动机）。FA3/FA4 在 sm_120 上有硬性 cc 门槛，跑不了，正文明确标注未验证部分。
  3. 3.3
    Decode 侧 attention 有正文
    decode 是另一道题：算术强度恒为 1，与 S、D 都无关，永远在带宽侧。GQA 收益线性且可预测（相对 MHA 逐行跟住字节比）；B·H=8 就跑满 170 个 SM 的带宽，证明 split-K 存在。并置 SDPA 与 FlashInfer——后者 prefill 输、decode 赢 1.83 倍。
  4. 3.4
    稀疏、线性与混合架构 有正文
    从真实模型里把 attention sink 量出来（最后一层 73% 的注意力给了第一个 token），再讲滑动窗口为什么不能简单丢弃。滑动窗口 decode 耗时随上下文完全不变；线性 attention 的精确检索能力从 1.0000 掉到 0.2393；RoPE 频率表说明外推失败的确切机制。
L4

模型架构与数值模型不是黑盒，是一张 FLOP 与字节的账单

模型不是一段公式，是磁盘上的字节 + 一串张量运算。4.0 从字节讲起，4.1 解剖 Transformer，4.2–4.4 处理数值、量化与稀疏。VLM 拆成 4.5–4.8 四个可独立验收的单元：预处理、编码器与 connector、多模态序列与位置、服务侧缓存与视频流。

  1. 4.0
    模型文件到底是什么：safetensors 字节布局与加载路径 有正文
    三段结构、分片与 index、命名的三套翻译、mmap 的假带宽。三个实测发现：分片会把一层切开；config 写 tie=True 但文件里存了逐位相同的 lm_head（占 15.3%，两个独立例子）；量化模型的 embedding 根本没被量化（占 GPTQ 文件 41%），等效位宽 4.16 而非 4。
  2. 4.1
    Transformer 层解剖与从零实现 有正文
    直接从 safetensors 读权重、只用基本算子手写一遍 Qwen3，逐层与 HF 对齐：29 个对照点全部逐位相同，logits 也逐位相同。每个中间张量的 shape/dtype/stride 全打印。参数量解析模型与文件实际差 0；MLP 占每层 75%、attention 25%。
  3. 4.2
    数值系统与确定性 有正文
    bf16 与 fp32 指数位相同所以动态范围相同，只差分辨率；bf16 就是 fp32 的高 16 位。最重要的实测：同一条 prompt 只因同批次里有别人，logits 就差 0.25——不是 bug，也不是 use_deterministic_algorithms 能修的。温度 0 不等于可复现。
  4. 4.3
    量化工程 有正文
    手工解包 AWQ 的 qweight（nibble 顺序是 0,4,1,5,2,6,3,7）并自检；量化误差的绝对值均匀、相对值集中在小权重上，组间 scale 差 212 倍。实测：显存 2.7×、质量退化 2-4%，但 batch=64 小模型上 decode 反而慢 10% —— 量化最稳的收益是装得下，不是快。fp8 GEMM 1.50×。
  5. 4.4
    MoE：稀疏激活的系统代价 有正文
    用真实 MoE（OLMoE 64 专家/top-8）量三件事：稀疏的只有算力（5.8×），显存要按总参数量买（12.70 GiB 全驻留），带宽的稀疏性在 batch≥64 时完全消失。路由跨层聚合会抹掉不均衡（总体 CV 0.295 vs 逐层 1.0–1.2，每层都有专家拿 0.00%），逐层最热专家占 11.8% → 并行效率上界 13%。
  6. 4.5
    VLM（一）：图像与视频预处理 待写
    原图 → resize/crop/normalize → patch/grid → 视觉 token 数。把 processor 配置、实际裁剪结果和动态分辨率策略全部打印出来。VLM 拆成 4.5–4.8 四个可独立验收的单元。
  7. 4.6
    VLM（二）：视觉编码器与 connector 待写
    ViT 的前向、patch embedding 的实际张量、connector（MLP / resampler / cross-attn）把视觉特征投到语言维度的全过程；以及哪些模块被冻结、哪些参与训练。
  8. 4.7
    VLM（三）：多模态序列、位置编码与 mask 待写
    视觉 token 插进语言序列的确切位置、占位 token 的替换过程、多模态 rope（如 mrope）的位置分配、以及 mask 在图文交错与多图场景下的形状。
  9. 4.8
    VLM（四）：服务侧的 batching、缓存与视频流 待写
    多模态输入怎么进引擎：图像预处理放在哪一侧、视觉特征缓存与 KV 前缀缓存的关系、变分辨率带来的 batching 困难、视频流的分帧与丢帧策略。
L5

单机推理引擎把模型变成服务的那一层

这一层是 AI infra 的工程重头戏：调度、显存、批处理、图捕获的所有取舍都在这里交汇。5.8 补上失败路径：取消、超时、背压、断连、OOM 与资源回收——这是工程实现的一部分，不是运维附录。

  1. 5.1
    prefill 与 decode 的系统性质 有正文
    两相对硬件的要求相反：同一个 batch 扫描下 prefill 吞吐只涨 1.24×、decode 涨 56×。TTFT 随 prompt 线性增长而 TPOT 不变，所以负载形态决定该看哪个指标。静态批处理在长度不齐时只有 52% 利用率；但连续批处理的收益要有队列才看得到（1720 vs 5563 tok/s）。
  2. 5.2
    KV cache 管理：PagedAttention 与 prefix cache 有正文
    分页的动机与实现；vLLM PagedAttention 与 SGLang RadixAttention 并置：block table、allocator、碎片、copy-on-write、前缀树复用的不同取舍。
  3. 5.3
    调度：continuous batching 与 chunked prefill 有正文
    逐 step 计时看调度：一条 8192 token 的 prefill 让稳态 4.7ms 的步涨到 53ms，连续 5 步所有 decode 停摆。把块切到 512 后尖峰从 165.9 降到 15.9ms，而总时间不变——chunked prefill 在这个配置下近乎免费。max_num_batched_tokens 过了并发数就完全无效（拐点实测）。
  4. 5.4
    执行层：CUDA Graph 与流水重叠 有正文
    2.6b 量到图把 CPU launch 降 16.2 倍，这里量它值多少 tok/s：1.19–1.41×。最清楚的一条是开图后每步时间几乎与 batch 无关（3.16–3.86 ms）。代价：启动 5.5→9.5 s、捕获 51 个尺寸、KV 变小。prefill 上完全没有收益（1.00×）；padding 的代价在 CPU 受限区间量不出来。
  5. 5.5
    投机解码 有正文
    draft-verify 数学、方法谱系（ngram / suffix / draft model / Medusa / EAGLE / MTP，其中 MTP 有 26 个模型类型且走 EAGLE 运行时路径）、acceptance rate 与 batch-size cliff 实测。
  6. 5.6
    结构化输出与约束解码 有正文
    XGrammar / llguidance / outlines_core 三库逐位对照、FSM 与下推自动机、structural tag 与 function calling、tool-call 流式解析；并置 vLLM 与 SGLang 的约束解码路径。
  7. 5.7
    四家引擎架构对比 + 自建 nanoserve 有正文
    vLLM V1 / SGLang / TensorRT-LLM / llama.cpp 四家架构逐层对比（进程模型、并发上限、调度、KV 组织、执行、扩展点）；然后分六次迭代写出 nanoserve：单请求、连续批处理、分页 KV、前缀复用、chunked prefill 预算、HTTP/SSE。
  8. 5.8
    失败路径：取消、超时、背压、断连、OOM 与资源回收 有正文
