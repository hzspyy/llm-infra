最小完整模型（下）：链式法则与一次参数更新

沿同一个模型检查标签对齐、交叉熵、反向传播和参数更新，比较手算梯度与 autograd。

实测机器 本机 CPU（macOS, torch 2.14.0）数据日期 2026-09-10前置 L0.0（同一个模型）

本章回答三个问题

  1. loss 是一个标量，它怎么变成每个参数各一个数？
  2. 「更新一次参数」具体改了内存里的哪些字节？
  3. 为什么反向要保存前向算出的中间值？

L0.0 走完了一次生成。这一章用同一个模型走完一次训练： 样本怎么拼、loss 怎么算、梯度怎么回、参数怎么变。 L7 会把这套流程放大到真实规模，本章先在能手算的尺度上做一遍。

两个新词：

  • 梯度（gradient）：loss 对某个参数的偏导数。它和参数形状完全相同—— 每个参数一个数，表示「把这个参数调大一点，loss 会变大还是变小、变多少」。
  • 反向传播（backpropagation）：从 loss 出发，按链式法则逐层往回算梯度的过程。 它不是什么特殊算法，就是链式法则加上「把重复用到的中间结果存下来」。

心智模型：一个标量回到每个参数

机制拆解

一、训练样本：每个输入位置的标签是下一个 token

语言模型的训练目标是「预测下一个 token」。所以标签不需要人工标注， 对同一段 token 序列取 x=tokens[:-1]、y=tokens[1:]，使 y[t] 对应 x[t] 后面的 token：

原文  '风吹过山谷，云落在水面'  (11 个字符)
  位置     输入 x     标签 y   含义
   0        风        吹   看到 '风' 之后应当预测 '吹'
   1        吹        过   看到 '风吹' 之后应当预测 '过'
   2        过        山   看到 '风吹过' 之后应当预测 '山'
   …
   9        水        面   看到 '风吹过山谷，云落在水' 之后应当预测 '面'

一条长度 10 的样本同时提供了 10 个训练信号。这一点依赖 L0.0 讲的因果掩码： 位置 t 只能看到 ≤t，所以它预测 t+1 时不算作弊。 掩码没写对，模型就能看到答案——L0.0 自测题 4 讨论过这个问题。

训练时每一步喂进去的都是真实的前缀，而不是模型自己上一步生成的字符。 这叫 teacher forcing（教师强制）。它让训练可以并行—— 10 个位置一次算完，而不是像生成时那样必须一个一个来。

代价是训练与推理的分布不一致：训练时模型看到的前缀总是对的， 推理时前缀是它自己生成的，可能已经错了。这个差距叫 exposure bias， 是 RL 后训练要处理的问题之一（L7.6）。

二、从 logits 到一个标量

一次前向得到 logits: [1, 10, 18]——10 个位置，每个位置 18 个分数。 把它和标签对上，逐位置算交叉熵：

ℓt=−logpt[yt],pt=softmax(logitst)

ℓt 的含义是：模型给正确答案分配的概率越低，惩罚越大。 p=1 时 ℓ=0，p→0 时 ℓ→∞。

实测：

per_token_loss   (10,)   前6个: [+2.8736, +3.0997, +3.3885, +2.9945, +2.6051, +2.1830]
loss = per_token_loss.mean() = 2.995676

验证位置 0：正确字符 '吹'，p=0.056493，-log p=2.873633（脚本算出 2.873632）
未训练时模型接近均匀分布，预期 loss ≈ ln(V) = ln(18) = 2.8904，实测 2.9957

lnV 是一个有用的基准线。 均匀预测给每个字符 1/V 的概率，loss 为 lnV。随机初始化不保证输出严格均匀；偏离该值时应检查初始化尺度、数据分布和标签，而不能仅凭 loss 判定信息泄漏。

eloss 叫困惑度（perplexity），可以理解成「模型在多少个选项之间犹豫」。 lnV 对应的困惑度正好是 V。

最后一步是把 10 个数平均成 1 个：

loss = per_token_loss.mean()

mean() 的分母是 10，即有效 token 数。真实训练里一个 batch 内各条样本长度不同， 要 padding 对齐；padding 位置不能参与 loss，分母也只能数有效 token。 这件事写错的后果是 loss 被稀释、不同 batch 之间不可比。L7.0b 会展开。

三、梯度：一个标量怎么变成每个参数一个数

先在一个能手算的例子上把链式法则写清楚。取

f(a,b)=(ab+a)2,a=2, b=3

设 u=ab+a=a(b+1)，则 f=u2。链式法则说：

∂f∂a=∂f∂u·∂u∂a=2u·(b+1),∂f∂b=2u·a

代入 u=2×3+2=8：∂f/∂a=2×8×4=64， ∂f/∂b=2×8×2=32。

代入 u = 8.0:  手算 df/da = 64.0, df/db = 32.0
autograd:      df/da = 64.0, df/db = 32.0
一致：True

反向传播就是把这个过程自动化。 每个算子知道自己的局部导数， 框架按图的逆序把它们连乘起来。L2.6b 打印过完整的反向图。

回到模型。最靠近 loss 的是 logits，它的梯度有一个简洁形式：

∂L∂logitst=pt−onehot(yt)N

其中 N 是参与平均的 token 数。实测对拍：

手算与 autograd 的最大绝对差 = 7.451e-09
位置 0 的梯度前 6 个：手算   [+0.006362, +0.008880, +0.004424, +0.005823, +0.003122, +0.004670]
                    autograd [+0.006362, +0.008880, +0.004424, +0.005823, +0.003122, +0.004670]

这个式子值得读懂：

  • 对正确的那个字符，梯度是 (p−1)/N<0。 梯度为负意味着「增大这个 logit 会让 loss 变小」，所以更新时它会被推高。
  • 对其余字符，梯度是 p/N>0，会被压低。
  • p 越接近 1，(p−1) 越接近 0，梯度越小——已经答对的地方不再推动。

这里要与 attention 内部的 softmax 区分。softmax 与交叉熵合在一起后，logits 梯度为 (p−y)/N：只有预测分布接近正确标签时才趋近零；若模型自信地预测错误类别，相关分量仍可接近 ±1/N。不能从输出接近 one-hot 推出所有梯度消失。

四、反向需要前向的哪些中间值

反向不是「再跑一遍前向」。它需要前向算出来的一些张量。 以上面的式子为例：算 ∂L/∂logits 要用到 p， 而 p 是前向 softmax 的输出。

PyTorch 把这些值挂在计算图的节点上。从 loss 出发可以直接走这条链：

loss.grad_fn 链（前 6 跳）：
  NllLossBackward0 -> LogSoftmaxBackward0 -> ViewBackward0
  -> UnsafeViewBackward0 -> MmBackward0 -> ViewBackward0

每个 *Backward0 是一个反向节点，next_functions 指向它的上游。 这就是「计算图」在内存里的样子——L2.6b 把整张图打印过。

工程后果：这些中间值必须从前向一直活到反向结束。 本例里 logits 只有 10×18 个 fp32 = 720 字节，无所谓； 真实模型里这一项（activation memory）是训练显存的大头， 而且随 batch 和序列长度线性增长。L7.1 会算这笔账， 并介绍用重算换显存的做法（activation checkpointing）。

五、一次参数更新改了什么

梯度和参数形状完全相同：

lm_head.weight   (18, 32)   前4个: [-0.1212, -0.0809, +0.0522, -0.1445]
  .grad          (18, 32)   前4个: [+0.0017, -0.0146, +0.0118, -0.0236]
梯度范数 |g| = 1.765255

最朴素的 SGD 就是一行：

w←w−ηg

η 是学习率（learning rate）。实测（η=0.1）：

手算与 optimizer 的最大差 = 1.490e-08
w[0,0]: -0.121226 -> -0.121391  (变化 -0.000165 = -0.1 × +0.001655)

本章使用 AdamW 对照 SGD，它多维护两个和参数等大的状态：

状态键：['exp_avg', 'exp_avg_sq', 'step']
exp_avg          (18, 32)   前4个: [+0.0002, -0.0015, +0.0012, -0.0024]
exp_avg_sq       (18, 32)   前4个: [+0.0000, +0.0000, +0.0000, +0.0000]
w[0,0]: -0.121226 -> -0.221225
  • exp_avg（记作 m）是梯度的指数滑动平均，起平滑作用。 第一步时 m=(1−β1)g=0.1g，所以前 4 个数正好是梯度的 1/10。
  • exp_avg_sq（记作 v）是梯度平方的滑动平均。第一步 v=(1−β2)g2=0.001g2， 数量级是 10−6，所以按 4 位小数打印显示成 +0.0000——它不是零。

更新式（省略权重衰减）：

w←w−ηm^v^+ϵ,m^=m1−β1t, v^=v1−β2t

第一步时偏差修正后 m^≈g、v^≈|g|， 所以整个分式约等于 sign(g)。 实测 w[0,0] 变化正好是 −0.1=−η，与梯度大小无关——这与实测吻合。

这带来一笔明确的显存账：

参数 576 个 -> 权重 2304 B + 状态 4608 B = 6912 B

每个 fp32 参数占 4 B 权重 + 4 B 梯度 + 8 B 优化器状态 = 16 B，是权重的 4 倍。 一个 7B 模型光这三项就是 7×109×16 B=112 GB， 单卡放不下——这是 ZeRO / FSDP 存在的直接原因（L7.2）。

六、loss 真的会降

把上面这一步重复 200 次：

  step       loss      困惑度 exp(loss)
     0     2.9957             19.999
    40     0.0668              1.069
    80     0.0191              1.019
   120     0.0105              1.011
   160     0.0068              1.007
   200     0.0048              1.005

训练后从 '风吹' 续写：'风吹过山谷，云落在水'

困惑度从 20（约等于随机猜 18 个字符）降到 1.005（几乎确定）。 模型把这条语料背下来了。

只有一条训练数据时这叫过拟合，不能说明模型有泛化能力。 但它确实证明了梯度在起作用——这是训练代码的第一个可用性检查： 先让模型在一条数据上过拟合。 如果连这都做不到，说明梯度链路有 bug。

工程实现 · 源码走读

本章的训练循环就是四行，真实训练脚本的骨架与它相同：

loss = F.cross_entropy(model(x).view(-1, V), y.view(-1))
opt.zero_grad()      # 清掉上一步的梯度（PyTorch 的梯度是累加的）
loss.backward()      # 反向：填充每个参数的 .grad
opt.step()           # 用 .grad 更新参数

zero_grad() 容易被忽略但不能省：PyTorch 的 .grad 是累加的， 不清零就会把上一步的梯度加进来。这个设计是为了支持梯度累积—— 把一个大 batch 拆成几个小 batch，各自 backward() 之后再一次 step()。 L7.0b 会讲它与直接用大 batch 的区别（不完全等价，因为 BatchNorm 之类的算子会受影响）。

真实训练脚本在这四行之外还有：梯度裁剪、学习率调度、混合精度的 scaler、 分布式的梯度同步、checkpoint 保存。L7.1 逐项展开。

② 手算梯度与 autograd 的逐元素对比 
[2] 手算梯度 vs autograd
    先在一个两参数的函数上对拍，把链式法则写出来：
      f(a, b) = (a * b + a)^2，  取 a=2, b=3
      设 u = a*b + a = a(b+1)，f = u^2
      df/du = 2u
      du/da = b + 1,   du/db = a
      df/da = 2u(b+1), df/db = 2u·a
      代入 u = 8.0:  手算 df/da = 64.0, df/db = 32.0
      autograd:      df/da = 64.0, df/db = 32.0
      一致：True

    再看模型里最靠近 loss 的那一层：lm_head。
    交叉熵 + softmax 的梯度有一个简洁形式：dL/dlogits = (p - onehot(y)) / N
    其中 p 是 softmax 输出，N 是参与平均的 token 数（这里 N=10）。
    手算与 autograd 的最大绝对差 = 7.451e-09
    位置 0 的梯度前 6 个：手算 [+0.006362, +0.008880, +0.004424, +0.005823, +0.003122, +0.004670]
                              autograd [+0.006362, +0.008880, +0.004424, +0.005823, +0.003122, +0.004670]

该看哪个字段：7.451e-09 是 fp32 的舍入误差量级，不是 0。 两条路径做的浮点运算顺序不同，得到逐位相同才是意外。

注意这只验证了一个输入下的一致性，不能推广成「实现一定正确」。 torch.autograd.gradcheck 可用有限差分检查给定输入处的解析梯度。它不会自动替代多输入测试；调用方仍需准备随机样本、边界值和不同形状。L2.8 用它验证自定义算子。

下一步观察：把 f 换成 torch.sin(a*b)，手写它的导数再对拍。

⑤ detach 把梯度断在哪里 
[B] 失败案例：detach 把梯度断在哪里
    正常                       tok_emb.grad = 范数 0.126201 | lm_head.grad 范数 = 1.728341
    对 embedding 输出 detach    tok_emb.grad = None        | lm_head.grad 范数 = 1.728341

该看哪个字段：tok_emb.grad 从「范数 0.126」变成 None—— 不是变成 0，是从未被填充。而 lm_head.grad 的范数完全没变（1.728341）。

detach() 切断的是这条路径上的梯度回传， 它下游（更靠近 loss 的一侧）的参数照常拿到梯度。

这正是「冻结部分模块」的实现方式：

  • VLM 训练第一阶段冻结视觉编码器，只训 connector（L4.6）
  • LoRA 冻结整个主干，只训低秩旁路（L7.5）

冻结参数与切断计算图不同。requires_grad_(False) 不为该参数求梯度，但仍允许梯度穿过模块回传到需要训练的上游；detach() 会切断该张量之前的路径。LoRA 若在多个层插入可训练旁路，不能随意 detach 中间主干输出，否则前面旁路也收不到梯度。不把参数交给 optimizer 只是不更新它，不会自动停止梯度计算。

前沿

本章讲的是最基本的一步。它在真实训练里会被下面这些东西包住，各自解决一个具体问题：

加进来的东西 解决什么 代价 章节
混合精度（bf16 计算 + fp32 状态） 部分激活与通信字节减少；总显存需逐项核算 需要处理数值范围 L4.2 / L7.1
梯度裁剪 偶发的大梯度会毁掉训练 多一次全局归约 L7.1
学习率调度（warmup + 衰减） 开始时参数还没「对齐」，大步长会发散 多一个超参 L7.1
梯度累积 用小显存模拟大 batch 更新频率降低 L7.0b
activation checkpointing 不保存中间值，反向时重算 约 +33% 计算 L7.1
ZeRO / FSDP 把权重、梯度、优化器状态切到多卡 通信 L7.2
8-bit / paged 优化器 优化器状态从 8 B 降到 2 B 数值精度 L7.5

最后一行值得注意：本章算出「优化器状态是权重的 2 倍」， 这个比例正是那些优化器要攻击的目标。

陷阱

1. 忘记 zero_grad()。 PyTorch 的 .grad 是累加的。 不清零时等效学习率会逐步变大，训练往往不是立刻崩，而是过一阵才发散——很难查。

2. 用 loss 曲线判断训练是否正确。 本章的失败案例 [A] 里， 错误版本的 loss 曲线和正确版本几乎重合。 必须有一个不依赖 loss 的检查。

3. 混淆冻结参数与断开计算图。 detach() 切断当前路径，上游若无其他路径便收不到梯度；下游仍可训练。是否保存中间值取决于剩余梯度需求。no_grad() 也会阻断该区域的自动求导，不能用来包住需要向前面 LoRA 层回传梯度的计算。

4. 忽略 padding 位置的 loss。 分母数错会让 loss 被稀释， 不同长度的 batch 之间不可比。L7.0b 展开。

5. 把 exp_avg_sq 打印出的 0.0000 当成零。 它的量级是 10−6，只是打印精度不够。 调试数值问题时永远用科学计数法看。

6. 只在一条数据上验证训练代码就上大规模。 「能过拟合一条数据」是必要条件，不是充分条件。 它能发现部分明显错误，但不能排除全部梯度、数据管线、学习率或并行实现问题。

自测题

1. 一个 7B 模型用 AdamW 训练，纯 fp32，光「权重 + 梯度 + 优化器状态」要多少显存？

逐项算。 设参数量 N=7×109。

项 每参数字节 合计
权重 4 28 GB
梯度 4 28 GB
AdamW exp_avg 4 28 GB
AdamW exp_avg_sq 4 28 GB
合计 16 112 GB

112 GB，而 H100 是 80 GB。单卡放不下——而且这还没算 activation。

混合精度不会让它降到 1/4。 常见的 bf16 混合精度配方是： bf16 权重副本（2 B）+ bf16 梯度（2 B）+ fp32 主权重（4 B）+ fp32 优化器状态（8 B） = 16 B，和纯 fp32 一样。省下来的是激活值和通信量，不是这三项。

（有些实现把主权重与 exp_avg 合并或用 8-bit 优化器，那是另一回事，见 L7.5。）

这就是 ZeRO 的出发点：这三项在数据并行时每张卡都存了一份完全相同的副本， 纯属浪费。ZeRO-1/2/3 依次把优化器状态、梯度、权重切开分到各卡。L7.2 展开。

2. 我把学习率从 3e-3 改成 3e-1，loss 会「降得更快」吗？

不会，多半会发散。

先想清楚 AdamW 的更新量。前面推过，第一步时

|Δw|=η|m^v^+ϵ|≈η

也就是说，每个参数每一步的变化量大约就是 η，与梯度大小基本无关。

本章参数的初始值量级是多少？lm_head.weight 的前几个数是 −0.12,−0.08,+0.05,−0.14，量级约 0.1。

η=3×10−3 时，一步改动 0.003，是参数量级的 3%——合理。 η=0.3 时，一步改动 0.3，比参数本身还大 3 倍。 参数每一步都被推到一个和上一步几乎无关的位置，这不是优化，是随机游走。

实际会观察到：loss 先剧烈震荡，然后可能变成 nan （logits 爆炸 → softmax 溢出 → loss 为 inf → 梯度为 nan → 参数全部变 nan）。

判断学习率是否合理的一个经验法则： η 应当比参数的典型量级小 1–2 个数量级。 真实模型里 d 越大初始化越小（~1/d），所以大模型的学习率也更小。

warmup 的作用也在这里：训练最开始参数还是随机的，梯度方向不可靠， 先用很小的 η 走几百步，等 exp_avg_sq 积累出合理的尺度估计再放大。

3. 我删掉了 opt.zero_grad()，为什么模型不是立刻崩，而是训练一阵才出问题？

因为梯度是累加的，等效学习率是逐步变大的。

设第 t 步的真实梯度是 gt。不清零时，.grad 里的内容是

Gt=g1+g2+…+gt

早期（t 小）：各步梯度方向相近，Gt≈t·g¯， 相当于学习率被放大了 t 倍。t=2,3 时只是走得快一点，loss 甚至可能降得更快。

中期：等效学习率线性增长。到第 30 步时相当于 η 放大 30 倍， 按上一题的分析，参数开始被推到不合理的位置。

注意 AdamW 会掩盖这个问题一段时间。 因为它对梯度做了归一化：

Δw≈ηm^v^

Gt 整体放大 k 倍时，分子分母同时放大 k 倍，约掉了。 所以 AdamW 下这个 bug 比 SGD 下更隐蔽——真正出问题的是 Gt 里各步方向不一致带来的噪声累积，而不是尺度。

怎么查：在训练循环里打印 grad.norm()。 正常训练时它应当大致平稳或缓慢下降；单调线性增长就是没清零。

这个设计为什么存在：梯度累加是有意的，它让梯度累积（gradient accumulation） 成为可能——把一个大 batch 拆成 k 个小 batch， 各自 backward() 后再一次 step()。L7.0b 展开。

4. tok_emb 的梯度范数是 0.126，lm_head 是 1.728，差了 13 倍。这正常吗？

正常，而且方向可以预期。 有两个原因。

原因一：离 loss 的距离不同。 lm_head 直接产生 logits， 它的梯度就是 ∂L/∂logits 乘上输入——一步到位。 tok_emb 在最前面，梯度要穿过两层 attention + MLP + 若干 LayerNorm 才到达， 中间每一步都乘上一个雅可比矩阵，量级会衰减。

原因二：更新的稀疏性不同。 lm_head.weight 的每一行都参与了每个位置的计算 （因为要给所有 18 个字符打分），所以每行都有梯度。 tok_emb.weight 只有本次出现过的那几个 token 对应的行才有非零梯度—— 本例 10 个位置最多涉及 10 行，其余 8 行梯度是 0。

所以「梯度范数」这个量在跨层比较时要小心。 更有意义的比较是 相对量：‖g‖/‖w‖（梯度与参数的比值）， 它大致对应「这一步会把参数改变百分之多少」。

什么时候该担心：如果某一层的梯度范数比相邻层小几个数量级 （比如 10−8 vs 10−2），那才是梯度消失。 判断依据是层与层之间的比值，不是绝对值。

怎么看：训练时打印每一层的 ‖g‖/‖w‖，正常时各层应在同一数量级。 这也是残差连接与归一化层要保证的事情之一（L4.1）。

5. 训练时 10 个位置的预测一次算完，生成时却必须一个一个来。为什么不能反过来？

关键在于「下一步的输入是否已知」。

训练时，整条序列是已知的真实文本。位置 t 的输入是真实的第 t 个字符， 不依赖模型在位置 t−1 的输出。所以 10 个位置的计算互不依赖， 可以放进同一个矩阵乘一次算完（teacher forcing）。

生成时，位置 t 的输入是模型在位置 t−1 采样出来的字符。 不先算出 t−1，就不知道 t 该喂什么。这是一条串行的依赖链， 没法并行。

这个差别决定了两种负载的性质完全不同：

训练 / prefill 生成 / decode
一次处理的位置数 整条序列 1 个
矩阵乘的形状 T×d 乘 d×d 1×d 乘 d×d
瓶颈 算力 显存带宽
原因 矩阵够大，算术强度高 每个权重只被用一次就换下一个

decode 之所以是带宽瓶颈：为了算一个 token， 要把整个模型的权重从显存读一遍，而只做了 O(d2) 次乘加。 读 1.4 GB 权重、算 2×1.4×109 次浮点运算， 算术强度约 1 FLOP/字节——远低于 GPU 的平衡点（约 200+）。

这是本书 L0.2（资源账本）、L5.1（prefill/decode 性质）的核心， 也是投机解码（L5.5）的动机：既然带宽已经花了，不如一次多验证几个 token。
