异构对照：同一模型在两种 GPU 上

在相同模型和输入下，比较 RTX 5090 D 与 L40S 的 prefill 和后续生成时间。

实测机器 crater (RTX 5090 D, sm_120) 与 worldvln (L40S, sm_89) · vLLM 0.29.0 · PyTorch 2.13.0+cu130 · Qwen3-1.7B前置 L0.1（请求生命周期）· L0.2（资源账本与 roofline）

本章回答三个具体问题

  1. 相同模型（Qwen3-1.7B）与相同输入下，为什么在理论算力相近的两款 GPU 上，prefill 耗时相差仅 3.4%，而 decode 耗时却相差高达 2.48 倍？
  2. 两张卡的性能差异中，哪些来自底层硬件微架构（显存位宽、显存技术、时钟机制、PCIe 拓扑），哪些来自软件栈与 kernel 适配？
  3. 在集群与生产选型中，如何建立客观、可迁移的评估坐标系，避免落入“厂商标称参数陷阱”与“单一吞吐数字陷阱”？

“哪张卡跑大模型更快”是一个缺少前置条件的伪命题。模型的运行分为阶段不同的两个过程：前向填充（prefill）是大矩阵乘，主要受算力吞吐制约；逐字生成（decode）是向量与矩阵乘，主要受显存带宽制约。不同阶段、不同批处理大小下，系统的性能瓶颈在计算与访存之间动态转移。

本章固定相同的模型快照（Qwen/Qwen3-1.7B）、相同的分词输入和统一的软件栈（vLLM 0.29.0 + PyTorch 2.13.0+cu130），在客户端旗舰 RTX 5090 D 与数据中心主流推理卡 L40S 上展开端到端测量与分层对拍，拆解阶段分化的根本成因。

心智模型：两款 GPU 的两相工作点漂移

上图直观展示了两款硬件在不同阶段下的工作点分布： - 在 Decode 阶段（左侧低算术强度区）：生成单个 token 时，计算量极其有限（每字节权重仅贡献 1 次乘加运算），系统性能由显存带宽绝对主导。RTX 5090 D 凭借 512-bit GDDR7 带来的 1519.3 GB/s 超大带宽，压制了仅有 649.7 GB/s 带宽的 L40S，耗时缩短为后者的 40%（即 2.48 倍速）。 - 在 Prefill 阶段（右侧高算术强度区）：处理长提示词时，序列内所有 token 并行参与大 GEMM 运算，算术强度跨过硬件拐点。两张卡的实测密集 GEMM 算力均在 230~256 TFLOP/s 区间，因此执行耗时几乎完全重合。

机制拆解与推导：硬件瓶颈转移与相位分化

1. 理论 Roofline 模型的跨卡量化推导

在 0.2 中，已建立单请求推理的基础资源模型。设模型参数量为 P，前向计算所消耗的总浮点运算量为 FLOPs，设备访问显存的总字节量为 M。则算术强度定义为：

I=FLOPsM

系统的执行时间由访存时间与算力时间的瓶颈项共同决定（不考虑重叠时）：

T≈max(MBW,FLOPsPeakcompute)

将两台测试机器的真实硬件探针（微基准实测值）代入公式：

硬件维度 crater（RTX 5090 D） worldvln（L40S） 性能比值 (5090D / L40S)
架构代际与计算能力 sm_120（Blackwell 消费级） sm_89（Ada Lovelace 数据中心） —
显存类型与物理位宽 GDDR7 · 512-bit GDDR6 · 384-bit 1.33× 位宽
实测显存复制带宽（Copy BW） 1519.3 GB/s 649.7 GB/s 2.34×
实测只读规约带宽（Read-only BW） 1608.6 GB/s 734.4 GB/s 2.19×
实测稠密 BF16 GEMM 峰值 232.0 TFLOP/s 256.0 TFLOP/s 0.91×
理论平衡拐点 I*=PeakBW 152.7 FLOP/Byte 394.0 FLOP/Byte —
Eager 空 Kernel 下发开销 2.68 µs 5.03 µs 0.53×（快 1.88×）
PCIe 带宽（Pinned H2D） 47.5 GB/s（Gen5 x16） 25.0 GB/s（Gen4 x16） 1.90×

Decode 阶段推导（以 B=1,Sctx=1024 为例）

每生成一个 token，模型必须从显存中完整读取一次所有层权重（Mweight≈2×1.7×109≈3.40 GB），同时读取该请求已累积的 KV cache（Mkv=2×nlayers×2×nkv\_heads×dhead×Sctx×2≈11.7 MB）。 前向总浮点运算量为 2P≈3.4×109 FLOP。 算术强度计算如下：

Idecode=3.4×109 FLOP(3.40×109+0.0117×109) Byte≈0.997 FLOP/Byte≈1.03 FLOP/Byte

此时 I≪I*，两台设备均处于极深度的访存受限区。 - RTX 5090 D 理论下界：Tlower≈3.40 GB1519.3 GB/s+Tlaunch≈2.24 ms+0.10 ms≈2.34 ms。实测单步耗时为 4.483 ms（达到硬件理论下界的 52.3%）。 - L40S 理论下界：Tlower≈3.40 GB649.7 GB/s+Tlaunch≈5.23 ms+0.25 ms≈5.48 ms。实测单步耗时为 11.127 ms（达到硬件理论下界的 49.2%）。

理论下界比值为 5.48 ms2.34 ms=2.34×，实测单步耗时比值为 11.127 ms4.483 ms=2.48×。差距几乎 100% 由显存物理带宽的比值决定。

Prefill 阶段推导（以 B=1,S=4096 为例）

处理 4096 个提示词时，总计算量包含 Transformer 线性层 2×P×S≈13.47 TFLOP（注：单 token 采样时 lm_head 仅对末位 token 投影一次，见 L0.2 推导）。 权重搬运量仍为 3.40 GB，加上少量激活与 KV 写入，总数据交换量约为 3.5 GB。 算术强度跃升为：

Iprefill=13.47×1012 FLOP3.5×109 Byte≈3848 FLOP/Byte

这一数值远大于 5090 D 的拐点（152.7）和 L40S 的拐点（394.0），两张卡均进入水平算力平台。 - RTX 5090 D 理论下界：13.47 TFLOP232.0 TFLOP/s≈58.06 ms。实测耗时 76.91 ms（达到算力上限的 75.5%，有效算力 175.1 TFLOP/s）。 - L40S 理论下界：13.47 TFLOP256.0 TFLOP/s≈52.62 ms。实测耗时 79.54 ms（达到算力上限的 66.2%，有效算力 169.3 TFLOP/s）。

两者实测耗时比为 79.54 ms76.91 ms=1.034×。两张卡的实际大矩阵 GEMM 计算性能相差仅 3.4%。

2. 批处理扩大下的算术强度跃升与差距收窄

当并发请求数增大（B 从 1 扩展至 32），多条请求在同一时间步共享一次静态权重读取。此时总计算量随 B 线性扩展，而权重访存量保持固定：

FLOPs(B)=2·P·B,M(B)=Mweight+B·Mkv\_per\_req

算术强度随并发数的增长关系为：

I(B)=2P·BMweight+B·Mkv\_per\_req≈2P·B2P+B·Mkv\_per\_req

在 Qwen3-1.7B 模型上实测算术强度的演进： - B=1：I=1.03 FLOP/Byte - B=4：I=3.76 FLOP/Byte - B=16：I=11.06 FLOP/Byte - B=32：I=16.34 FLOP/Byte

随着算术强度向右上方爬升，计算开销在整体执行时间中的占比逐步增加，访存延迟所占的比例相对缩小。因此，两款显卡的性能差距从 B=1 时的 2.48×，平滑收窄至 B=32 时的 1.86×（6.80 ms vs 12.62 ms）。

3. 功耗墙、散热拓扑与长时降频机制

两款 GPU 在微基准测试中展现出显著不同的热力学行为，揭示了消费级显卡与数据中心显卡在设计哲学上的分歧：

RTX 5090 D (主动三风扇风冷 / 575W TDP 目标)
GEMM 4096: 218.1 TFLOP/s ───► GEMM 8192: 232.0 TFLOP/s (时钟稳定在 3090 MHz, 稳态算力充分释放)

L40S (机房被动风道风冷 / 350W TDP 限制)
GEMM 4096: 256.0 TFLOP/s ───► GEMM 8192: 199.9 TFLOP/s (下降 21.9%! 触发功耗墙与温控降频)
  1. L40S 的功耗节流（Power Capping）：L40S 是单槽/双槽被动散热卡，其整卡 TDP 被严格限制在 350W。当运行持续的大尺寸矩阵乘（N=8192）时，Tensor Core 全核满载导致瞬时功耗迅速触及 350W 上限，GPU 驱动与硬件温控被迫调降核心工作频率（从标称 Boost 2520 MHz 跌落），导致其纯算力产出从 256 TFLOP/s 骤降至 199.9 TFLOP/s。
  2. RTX 5090 D 的高功耗裕量：5090 D 具备高达 575W 的板卡功耗预算与庞大的均热板风冷组件，在 8192 GEMM 测试中能够维持 3090 MHz 的极限高频，其浮点吞吐不仅不降，反而随矩阵尺寸增大更充分地填满 SM，提升至 232.0 TFLOP/s。

工程实现：源码解析与设计取舍

1. 评测基准实现分析：差分计时与变量隔离 (labs/L0/bench_phases.py)

在评测大语言模型引擎时，常见的误区是直接使用一个端到端生成接口测量总耗时并除以生成的 token 数。这种粗糙测法混淆了 prefill 与 decode 两个异构阶段。

labs/L0/bench_phases.py 采用了严格的差分隔离测法：

# labs/L0/bench_phases.py: 核心计时与差分逻辑
def bench_decode(llm, prompts, steps=32):
    # 1. 测量生成 1 个 token 的基准时间（包含完整的 prompt prefill 阶段）
    sp_1 = SamplingParams(max_tokens=1, ignore_eos=True)
    t_prefill_plus_1 = time_median(lambda: llm.generate(prompts, sp_1))

    # 2. 测量生成 33 个 token 的累计时间（包含同样的 prefill + 32 步 decode）
    sp_33 = SamplingParams(max_tokens=steps + 1, ignore_eos=True)
    t_prefill_plus_33 = time_median(lambda: llm.generate(prompts, sp_33))

    # 3. 差分剥离：纯 decode 的单步平均耗时
    ms_per_step = (t_prefill_plus_33 - t_prefill_plus_1) / steps
    return ms_per_step

设计取舍（Design Tradeoffs）

  • 为什么使用独立生成的随机 prompt？：若多次调用复用相同的 prompt 字符串，引擎的前缀缓存（Prefix Caching）会将后续调用的 KV 块直接命中，从而跳过真实的 prefill 阶段，导致测量失真。因此测试显式指定 enable_prefix_caching=False，并在每一轮均重新生成无意义的随机 token 序列。
  • 为什么必须强制 enforce_eager=True？：CUDA Graph 可以消除 CPU launch 开销（见后文微基准对比），但不同 GPU 上的图捕获内存池与静态拓扑支持程度不一。在 L0 坐标系中，为了纯粹度量物理硬件（ALU 与 DRAM）的基础能力，必须先剔除 CUDA Graph 带来的软件优化增益。CUDA Graph 的加速收益将在 L5.4 单独量化。

2. 硬件微基准探测器实现分析 (labs/L0/probe_hw.py)

为了使 Roofline 分析具备科学基准，labs/L0/probe_hw.py 实现了设备底层的独立微基准探针：

# labs/L0/probe_hw.py: 设备事件同步与双向拷贝带宽探测
def probe_memory_bandwidth(mb: int = 512) -> dict:
    n_bytes = mb * 1024 * 1024
    t1 = torch.empty(n_bytes // 2, dtype=torch.float16, device="cuda")
    t2 = torch.empty_like(t1)

    # copy_ 算子：同时包含对 t1 的读与对 t2 的写，总物理吞吐量为 2 * n_bytes
    def run_copy():
        t2.copy_(t1)

    ms = time_cuda(run_copy, warmup=10, iters=50)
    # 计算有效传输速率：(2 * 字节数) / 耗时秒数
    gbps = (2.0 * n_bytes) / (ms * 1e-3) / 1e9
    return {"copy_gbps": round(gbps, 1), "buffer_mb": mb}

# labs/L0/probe_hw.py: 计时器基元定义
def time_cuda(fn, *, warmup: int = 10, iters: int = 50) -> float:
    for _ in range(warmup):
        fn()
    torch.cuda.synchronize()

    samples = []
    for _ in range(iters):
        start = torch.cuda.Event(enable_timing=True)
        end = torch.cuda.Event(enable_timing=True)
        start.record()
        fn()
        end.record()
        torch.cuda.synchronize()
        samples.append(start.elapsed_time(end))
    return statistics.median(samples)

设计取舍（Design Tradeoffs）

  • 计时器选型：CUDA Event vs Python time.perf_counter()：CUDA Kernel 的下发是异步非阻塞的。若使用 CPU 端时钟，测量到的仅仅是驱动层将指令推入环形队列（Ring Buffer）的时间，而非 GPU 核心执行 kernel 的真实时间。使用 torch.cuda.Event 搭配硬件时间戳，排除了 Host 操作系统调度扰动。
  • 只读规约 vs 双向拷贝：由于 LLM 的 decode 权重读取属于只读操作（无需回写），探针除了提供 copy_ 双向带宽外，还提供了只读规约（Reduction）带宽，使分析人员能够多视角校验显存控制器的吞吐极限。

工程实现：mini 异构性能对比器

以下自包含脚本 mini_gpu_comparator.py 实现了基于两机微基准参数的阶段性能预测，并与实测工件展开自动比对：

#!/usr/bin/env python3
"""mini_gpu_comparator.py · 异构 GPU 理论 Roofline 预测与实测对拍工具

用法：
    python mini_gpu_comparator.py
"""

from __future__ import annotations
from dataclasses import dataclass

@dataclass
class GPUSpec:
    name: str
    copy_bw_gbps: float
    bf16_tflops: float
    launch_us: float

@dataclass
class ModelSpec:
    name: str
    param_count: float       # 参数量 (单位: 个)
    weight_bytes: float      # BF16 权重字节数
    num_layers: int
    num_kv_heads: int
    head_dim: int

def predict_prefill_ms(gpu: GPUSpec, model: ModelSpec, prompt_len: int) -> float:
    # 浮点计算量: 注意 lm_head 仅在最后一个 token 执行投影
    flops = 2.0 * model.param_count * prompt_len
    # 算力主导阶段理论耗时 (ms)
    t_comp_ms = (flops / (gpu.bf16_tflops * 1e12)) * 1e3
    return t_comp_ms

def predict_decode_step_ms(gpu: GPUSpec, model: ModelSpec, batch: int, ctx_len: int) -> float:
    # 显存访存量: 静态权重 + KV cache 读取
    kv_bytes_per_token = 2 * model.num_layers * 2 * model.num_kv_heads * model.head_dim * 2
    total_bytes = model.weight_bytes + batch * ctx_len * kv_bytes_per_token
    # 访存主导阶段理论下界 (ms)
    t_mem_ms = (total_bytes / (gpu.copy_bw_gbps * 1e9)) * 1e3
    return t_mem_ms

def main():
    qwen3 = ModelSpec(
        name="Qwen3-1.7B",
        param_count=1.7e9,
        weight_bytes=3.4e9,
        num_layers=28,
        num_kv_heads=8,
        head_dim=128
    )

    rtx5090d = GPUSpec("RTX 5090 D", copy_bw_gbps=1519.3, bf16_tflops=232.0, launch_us=2.68)
    l40s = GPUSpec("L40S", copy_bw_gbps=649.7, bf16_tflops=256.0, launch_us=5.03)

    print("==========================================================================")
    print(f"模型: {qwen3.name} | 异构硬件 Roofline 理论预测 vs 实测对拍")
    print("==========================================================================")

    # 1. Decode 阶段对比 (ctx=1024)
    print("\n[Decode 阶段每步耗时 (ms/step) · ctx_len=1024]")
    print(f"{'Batch':<8}{'5090D 预测':<14}{'5090D 实测':<14}{'L40S 预测':<14}{'L40S 实测':<14}{'实测加速比':<10}")
    print("-" * 74)

    decode_actuals = {
        1:  (4.483, 11.127),
        4:  (4.680, 11.411),
        16: (5.850, 11.949),
        32: (6.798, 12.624),
    }
    for b in [1, 4, 16, 32]:
        p_5090 = predict_decode_step_ms(rtx5090d, qwen3, b, 1024)
        p_l40s = predict_decode_step_ms(l40s, qwen3, b, 1024)

前沿扩展：架构演进与现代算力卡格局

1. 消费级 Blackwell (sm_120) 与数据中心 Blackwell (sm_100) 的本质断层

初学者常因为 RTX 5090 D 采用 Blackwell 架构代号，便误认为它具备与 B200 相同的新一代编程模型。实际上，NVIDIA 对消费级与数据中心芯片做了极为彻底的功能切割：

  1. Tensor Memory (TMEM) 的缺失：数据中心级 Blackwell（sm_100 / sm_100a）引入了片上分布式的 TMEM 存储架构，并配有专用的 tcgen05 指令集，允许张量核心以非阻塞的流水线方式异步读取矩阵片。
  2. 5090 D 的指令集回归：sm_120 并不包含 tcgen05 与 TMEM 指令。其张量核心编程模型完全回退为与 Ampere (sm_80) / Ada (sm_89) 相同的同步 mma.sync 家族。这解释了为何 L0.1 在 5090 D 的执行轨迹中抓取到的 GEMM 仍然是 cutlass_80_tensorop_bf16_s16816gemm_*。
  3. GDDR7 的颠覆性收益：尽管 5090 D 在指令集上未获 TMEM 支持，但得益于 512-bit 物理位宽和 28 Gbps 的 GDDR7 颗粒，它实现了惊人的 1519 GB/s 实测显存带宽。在单卡 32 GB 容量容纳得下的小模型（如 1.7B~8B）或量化模型上，其 Decode 速度直接超越了多数昂贵的数据中心 GPU。

2. 数据中心推理卡的核心壁垒与选型权衡

既然 5090 D 的 Decode 表现如此优异，是否意味着企业应全面采用消费卡替代 L40S？答案必须回到系统工程的全生命周期考量：

选型决策树：
┌───────────────────────────────────────────────────────────────┐
│                      大模型推理服务选型                       │
└───────────────────────────────┬───────────────────────────────┘
                                │
        ┌───────────────────────┴───────────────────────┐
        ▼                                               ▼
[业务场景: 在线实时交互 / 低并发]               [业务场景: 批量离线吞吐 / 大并发]
- 首要指标: 单请求低 TPOT (Decode 敏感)         - 首要指标: 每美元并发吞吐 / 大上下文
- 推荐方案: 高带宽卡 (如 5090 D)                 - 推荐方案: 大显存容量卡 (如 L40S / H100)
- 优势: 1519 GB/s 带宽带来 2.48× 交互流速       - 优势: 48 GB 显存容纳 3.5× KV Cache 块
- 约束: 32 GB 显存上限，单卡仅能支撑有限并发   - 优势: 350W 机架高密度部署，数据中心 ECC 稳态
  1. 显存容量与并发容量上限（KV Pool Capacity）： - RTX 5090 D 拥有 32 GB 显存；扣除权重（3.4 GB）与运行时占用后，留给 KV cache 的可用显存约为 24 GB。 - L40S 拥有 48 GB 显存；扣除权重后，留给 KV cache 的空间高达约 40 GB（提升 1.67×）。 - 在长上下文（如 8k/16k）或数百并发请求涌入时，5090 D 将更早触碰 Out-of-Blocks 边界，导致排队堆积或请求被抢占（见 L5.8 抢占分析），而 L40S 凭借 48 GB 容量可以维持极高的稳态并发。
  2. 机房环境、ECC 容错与可维护性： - L40S 拥有全芯片端到端 ECC 纠错，专为 7×24 小时高可用服务设计，采用标准的双槽被动散热，适合 4U 8 卡高密度机架布置。 - 5090 D 不支持显存 ECC，尺寸巨大（多为 3.5~4 槽），采用下吹式主动风扇，无法装入标准高密度机柜服务器，且无 NVLink 支持，多卡并行时只能依赖有限的 PCIe 通信。

常见陷阱

1. 标称物理带宽直接代入理论分析

厂商产品规格书（Datasheet）中列出的显存带宽通常基于引脚速率（Pin Speed）计算的理想理论峰值。例如 L40S 标称带宽为 864 GB/s，而在实际平台通过优化后的微基准实测最大值为 649.7 GB/s（仅占标称值的 75.2%）。如果直接使用 864 GB/s 作为 Roofline 分母，推导得出的模型理论瓶颈将产生巨大偏差。做容量规划时，必须以实测物理微基准作为依据。

2. 混淆“硬件利用率高”与“绝对性能优异”

在批处理 B=32 时，L40S 的单步耗时为 12.624 ms，其 Roofline 达成率高达 87.8%（距离理论极限仅差 12%）；而 RTX 5090 D 的耗时为 6.798 ms，达成率仅为 69.7%。初学者常误以为 L40S 的表现更加优秀。实际上，达成率高仅说明 L40S 的硬件瓶颈已经被压榨得非常充分（显存通道已被彻底打满），但由于其物理带宽上限较低，其绝对执行速度仍然比 5090 D 慢了将近一半。

3. 用单一“平均端到端吞吐”掩盖阶段真实行为

报告类似于“某卡处理 Qwen-1.7B 吞吐为 800 tokens/s”的数字几乎没有参考价值。因为 Prefill（算力敏感）与 Decode（访存敏感）在这两款 GPU 上的表现呈现完全相反的走向。若测试集偏重长输入短输出，两款卡性能近乎打平；若测试集偏重短输入长生成，两款卡将拉开数倍差距。必须将 TTFT（Prefill）与 TPOT（Decode）分开度量。

4. 忽略持续高负载下的散热节流（Thermal Throttling）

在短时间跑 1~2 秒的 benchmark 时，被动散热卡（如 L40S）可能依靠短时热容维持在较高的核心频率；但若服务持续满载 10 分钟以上，核心温度触顶后会触发硬件级降频。在微基准测试中，L40S 的 GEMM 8192 吞吐直接暴跌 21.9%，正是由于散热节流所致。

自测题

1. 两张卡在 4096-token prefill 上实测耗时相差仅 3.4%（76.91 ms vs 79.54 ms），能否就此判定两台设备的大模型推理性能等价？为什么？

不能。 4096-token 的 prefill 是极度算力受限（Compute-bound）的操作，此时两款显卡的算术强度高达 3800+ FLOP/Byte，远超两者的平衡拐点，性能完全由两台显卡的 BF16 密集算力（232 vs 256 TFLOP/s）决定，因而耗时接近。 但在实际服务中，生成后续 token 的 Decode 阶段占用了总运行时间的大部分，而 Decode 处于极深度访存受限区（Memory-bound）。在 Decode 阶段，RTX 5090 D 凭借 2.34 倍的显存带宽优势，单步生成速度达到了 L40S 的 2.48 倍。因此，两台设备在大模型推理的两个主要阶段呈现完全分裂的性能特征，绝非性能等价。

2. 为什么在 batch=1 到 batch=32 的扩展过程中，RTX 5090 D 相对于 L40S 的加速比会从 2.48 倍逐渐回落至 1.86 倍？

因为随着 batch size 的增加，显卡在单步中处理的并发 token 数增大，静态模型权重在每个 step 中仅需从显存读取一次，但参与计算的浮点运算次数随 batch 线性放大 B 倍。 这使得单步执行的算术强度 I 从 B=1 时的 1.03 FLOP/Byte 提升至 B=32 时的 16.34 FLOP/Byte。系统工作点从最左侧的纯访存受限斜坡，开始逐步向右上方平移，计算时间在总耗时中的权重持续攀升。由于两张卡的算力相差无几，算力因素占比增大自然稀释了显存带宽优势对耗时比值的影响，导致加速比收窄。

3. 某在线交互式客服系统要求响应时延极为严苛（首字生成延迟 TTFT < 100 ms，单 token 流式生成时间 TPOT < 10 ms），且平均 prompt 长度为 2000 tokens。请根据本章数据评价 RTX 5090 D 与 L40S 是否满足要求，并给出选型建议。

指标校验分析： 1. TTFT 约束（Prefill 耗时）： - 对于 2000 tokens 输入，由本章表 1 可知两台显卡的耗时均在 36~39 ms 左右（5090 D 为 36.64 ms，L40S 为 38.85 ms），均大幅优于 100 ms 的门限要求。 2. TPOT 约束（Decode 耗时）： - 根据表 2 实测数据： - RTX 5090 D：在 B=1 时单步 4.48 ms，即便并发扩大至 B=32 时单步仅 6.80 ms，全区间均完全满足 TPOT < 10 ms 的严苛 SLA。 - L40S：在 B=1 单请求下单步耗时即为 11.127 ms，已经直接击穿了 TPOT < 10 ms 的 SLA 阈值；在任何 batch 大小下均无法满足该实时性约束。

选型结论： 对于要求严格流式交互速度（TPOT < 10 ms）的场景，由于单流 decode 受显存带宽硬约束，L40S 在硬件层面上物理不达标；必须选用拥有 1500+ GB/s 带宽的 RTX 5090 D 等高带宽硬件。若未来面临超长会话导致 32 GB 显存不足，应采取 Prefill-Decode 分离（PD 分离）架构，将高带宽卡专门作为 Decode 节点使用。
