文本输入：从 Unicode 到模型张量

介绍 Unicode、字节级 BPE、对话模板和 padding，说明文本如何转换成模型输入。

实测机器 本机 CPU（手写 BPE）+ crater（真实 tokenizer, Qwen3-1.7B / GPT-2）前置 L0.0（模型接受的是 token id）

本章回答三个问题

  1. 为什么一个中文字常常是 2~3 个 token？这个说法在什么条件下成立？
  2. chat template 到底往序列里插了什么？
  3. 一个 batch 里长短不一的句子，padding 之后 attention_mask 和 position_ids 分别应该是什么？

L0.0 从 token id 开始计算。本章介绍前面的文本处理过程：字符如何经过编码、分词和模板处理，转换为整数张量。

本章分两条线：先手写一个 BPE（不用任何分词库，每一轮合并都打印出来）， 再看真实 tokenizer 的文件，确认两者是同一件事。

机制拆解

一、字符在内存里是字节

先把最底下那一层弄清楚。Python 里的 str 是 Unicode 码点序列， 但它落到磁盘、网络、模型输入之前，必须编码成字节。现在的事实标准是 UTF-8：

'风' 的 Unicode 码点：U+98CE
UTF-8 编码：[233, 163, 142]  = e9 a3 8e  （3 个字节）

'a'    U+00061  1 字节  61
'é'    U+000E9  2 字节  c3 a9
'风'   U+098CE  3 字节  e9 a3 8e
'🌊'   U+1F30A  4 字节  f0 9f 8c 8a

UTF-8 是变长的：ASCII 占 1 字节，多数汉字 3 字节，emoji 4 字节。 这个事实会在本章和 L0.5 里反复出现，包括一个真实的乱码 bug。

二、为什么从字节开始，而不是从字符

一个自然的想法是：词表就是所有字符。问题有两个：

  • Unicode 有十几万个码点，词表会非常大；
  • 永远会遇到没见过的字符（生僻字、新增 emoji），需要一个 <UNK> 兜底， 而 <UNK> 是不可逆的——解码时你不知道原来是什么。

字节级 BPE 的做法：初始词表固定是 0–255 这 256 个字节。 任何输入都能表示，永远不会 OOV，而且编解码无损。 代价是一个汉字起手就是 3 个 token，要靠后续合并把它压回来。

三、BPE 逐轮合并高频相邻对

算法只有三行：

  1. 统计当前序列里所有相邻符号对的出现次数；
  2. 把出现次数最高的那一对合并成一个新符号，分配一个新 id；
  3. 回到第 1 步，重复 N 次。

本章的手写实现在一段两千字的中英混合语料上跑，前 12 轮（原样输出）：

初始：256 个字节 token，语料切成 209 段，共 1213 个符号
  轮                   合并的对     次数   新 id 新符号                 剩余符号数
  0              ' ' + 't'     29    256 ' t'                 1184
  1              'h' + 'e'     27    257 'he'                 1157
  2            ' t' + 'he'     26    258 ' the'               1131
  3            <ef> + <bc>     21    259 <ef bc>              1110
  4         <ef bc> + <8c>     21    260 '，'                  1089
  5            <e4> + <b8>     17    261 <e4 b8>              1072
  6            <e3> + <80>     15    262 <e3 80>              1057
  7         <e3 80> + <82>     15    263 '。'                  1042

三件事从这里就能看清：

  • 第 2 轮合成了 ' the'，先有 ' t' 再有 ' the'—— 这就是词表里为什么满是带前导空格的 token。
  • 第 3、4 轮分两步把中文逗号 ，（3 字节 ef bc 8c）拼了出来： 先 ef bc，再加 8c。汉字必须经过至少两次合并才能变成一个 token。
  • 尖括号 <ef bc> 表示这个 token 不是完整的 UTF-8 序列——它是半个字符。 这类 token 在真实词表里大量存在，也是 L0.5 那个乱码 bug 的根源。

四、merges 的顺序决定分词结果

训练产出两样东西：词表（id → 字节串）和 merges 表（有序的合并规则）。

编码一段新文本时，必须按 merges 的顺序反复尝试合并：

rank = {pair: i for i, pair in enumerate(merges)}
while len(ids) >= 2:
    pairs = set(zip(ids, ids[1:]))
    best = min(pairs, key=lambda p: rank.get(p, float("inf")))   # rank 最小 = 最早学到
    if best not in rank:
        break
    ids = merge_pair([ids], best, 256 + rank[best])[0]

顺序不能变。换个顺序会切出不同的结果，模型就认不出来了。 所以 merges 表和权重一样，是模型文件的一部分——L4.0 会在真实 checkpoint 里看到它。

五、预切分：BPE 不知道什么是词

BPE 只看「相邻」。不加限制的话，它会把跨越空格、甚至跨越标点的组合也合并掉。 本章实测（同一语料，同样 120 轮）：

不预切分时，学到的 token 里有 25 个内部含空格，例如：
  'e ' ' the ' 's ' 'nd ' ' the s' 'es '
也就是说 25/120 = 21% 的词表预算
花在了「某个词 + 它后面那个空格」这种依赖上下文的组合上。

预切分在小语料上的对照结果

这组小语料实验没有显示预切分带来压缩优势：

在训练语料里出现过的句子上，不预切分反而更省 token：
  不预切分： 8 个 token   （'the wind comes from the sea'）
  预切分：   9 个 token
换成没见过的句子：
  不预切分：25 个 token   （'a bird sings near the old bridge'）
  预切分：  25 个 token

在这个语料规模下，预切分并未直接降低 token 总数。预切分的核心价值在于合理分配词表预算：若不加限制，大量带空格的特化组合会占据宝贵的词表槽位，在真实工业规模（如数十万词表与海量预训练数据）中造成显著浪费。更关键的是它提供了边界可控性，防止 token 跨越数字、标点与自然文本的边界，这对于算术推理和受约束解码（L5.6）至关重要。

真实模型的预切分是一条正则。Qwen3 的 tokenizer.json 里原样写着：

(?i:'s|'t|'re|'ve|'m|'ll|'d)|[^\r\n\p{L}\p{N}]?\p{L}+|\p{N}| ?[^\s\p{L}\p{N}]+[\r\n]*|\s*[\r\n]+|\s+(?!\S)|\s+

逐段读：

片段 匹配什么
(?i:'s\|'t\|'re\|'ve\|'m\|'ll\|'d) 英文缩写，单独成块
[^\r\n\p{L}\p{N}]?\p{L}+ 可选的一个非字母非数字前缀（通常是空格）+ 一串字母
\p{N} 单个数字——注意没有 +，每个数字自成一块
?[^\s\p{L}\p{N}]+[\r\n]* 可选空格 + 一串标点
\s*[\r\n]+ / \s+(?!\S) / \s+ 各种空白

\p{N} 特意没有添加 + 量词：这确保了每个阿拉伯数字都被切分为独立块，BPE 因而无法把多位数字（如 3.14 中的 14）随意合并为一个 token。后文的对比实验将展现这一设计对数学运算带来的显著收益。

模板不匹配是一类静默故障

每个模型的模板都不同。用 A 模型的模板喂 B 模型，不会报错， 但模型看到的是没见过的格式，输出质量会明显下降，而且很难归因。

所以推理引擎从 tokenizer_config.json 读模板，而不是自己硬编码。 L0.1 分析过 vLLM 的这一段。

九、padding、mask 与 position

在常规批处理中，不同长度的序列通常需要补齐（padding）为矩形张量（现代推理系统也常用 packed 连续组织以消除 padding 浪费）。以下是两条不同长度中文样本的 padding 实测：

padding_side = right
  样本 0  len=9
    input_ids      [99208, 102021, 11319, 151643, 151643, 151643, 151643, 151643, 151643]
    attention_mask [1, 1, 1, 0, 0, 0, 0, 0, 0]
  样本 1  len=9
    input_ids      [99718, 110936, 111926, 101036, 11319, 14880, 100700, 66394, 1773]
    attention_mask [1, 1, 1, 1, 1, 1, 1, 1, 1]
  样本 0 的 position_ids: [0, 1, 2, 0, 0, 0, 0, 0, 0]

三个张量各自的职责：

  • input_ids：在空缺位置填入 pad_token_id（本例为 <|endoftext|> 151643）。填充值需为合法词表编号，且后续的 attention mask 与 loss 计算必须将其显式排除。
  • attention_mask：1 表示真实 token，0 表示 padding。注意力机制会将 0 所在位置填入 −∞，确保真实 token 完全屏蔽 padding 的干扰。
  • position_ids：按 mask 累加得到的位置序号。padding 位置的数值不参与有效计算（本例置 0）。

对于习惯直接取 logits[:, -1, :] 的自回归生成接口，采用左填充（left padding）能保证每条序列的最新预测点严格对齐在矩阵最后一列；若采用右填充（right padding），则必须根据每条样本各自的有效长度单独索引 logits。而在采用变长无填充（packed/ragged）的推理引擎中，多条序列紧密拼接，依靠元数据偏移寻址，无需进行 padding 操作。

模型训练阶段通常习惯使用右填充，因为反向传播直接利用 mask 屏蔽 padding 位置的损失（详见 L0.0b 与 L7.0b）。

手写 BPE 的完整实现。核心只有 get_pair_counts + merge_pair + 一个循环：

107 def get_pair_counts(seqs: list[list[int]]) -> collections.Counter:
108     """统计所有序列里相邻符号对的出现次数。"""
109     cnt: collections.Counter = collections.Counter()
110     for seq in seqs:
111         for a, b in zip(seq, seq[1:]):
112             cnt[(a, b)] += 1
113     return cnt
114 
115 
116 def merge_pair(seqs: list[list[int]], pair: tuple[int, int], new_id: int) -> list[list[int]]:
117     """把每个序列里所有出现的 pair 替换成 new_id。从左到右、不重叠。"""
118     out = []
119     for seq in seqs:
120         res, i = [], 0
121         while i < len(seq):
122             if i + 1 < len(seq) and (seq[i], seq[i + 1]) == pair:
123                 res.append(new_id)
124                 i += 2
125             else:
126                 res.append(seq[i])
127                 i += 1
128         out.append(res)
129     return out

 59 def pre_tokenize(text: str) -> list[str]:
 60     """把文本先切成若干「块」，BPE 只在块内部合并，不跨块。
 61 
 62     真实实现用一个正则（GPT-2 的那条最出名）：
 63         's|'t|'re|'ve|'m|'ll|'d| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+
 64     Python 标准库的 re 不支持 \p{L}，所以这里用字符类别手写一个等价物：
 65     按「字母 / 数字 / 空白 / 其他」分组，前导空格并入后面的块
 66     （这就是为什么真实词表里有大量以空格开头的 token，比如 ' the'）。
 67     """
 68     def kind(ch: str) -> str:
 69         if ch.isspace():
 70             return "s"
 71         if ch.isalpha():
 72             return "L"
 73         if ch.isdigit():
 74             return "N"
 75         return "P"
 76 
 77     chunks: list[str] = []
 78     cur, cur_kind = "", ""
 79     for ch in text:
 80         k = kind(ch)
 81         if k != cur_kind and cur:
 82             chunks.append(cur)
 83             cur = ""
 84         cur_kind = k
 85         cur += ch
 86     if cur:
 87         chunks.append(cur)
 88 
 89     # 把单独的空白块并到后一个块的前面： ['the',' ','wind'] -> ['the',' wind']
 90     merged: list[str] = []
 91     pending = ""
 92     for c in chunks:
 93         if c.isspace():
 94             pending += c
 95         else:
 96             merged.append(pending + c)
 97             pending = ""
 98     if pending:
 99         merged.append(pending)
100     return merged

107 def get_pair_counts(seqs: list[list[int]]) -> collections.Counter:
108     """统计所有序列里相邻符号对的出现次数。"""
109     cnt: collections.Counter = collections.Counter()
110     for seq in seqs:
111         for a, b in zip(seq, seq[1:]):
112             cnt[(a, b)] += 1
113     return cnt

116 def merge_pair(seqs: list[list[int]], pair: tuple[int, int], new_id: int) -> list[list[int]]:
117     """把每个序列里所有出现的 pair 替换成 new_id。从左到右、不重叠。"""
118     out = []
119     for seq in seqs:
120         res, i = [], 0
121         while i < len(seq):
122             if i + 1 < len(seq) and (seq[i], seq[i + 1]) == pair:
123                 res.append(new_id)
124                 i += 2
125             else:
126                 res.append(seq[i])
127                 i += 1
128         out.append(res)
129     return out

132 def train_bpe(text: str, n_merges: int, verbose_rounds: int = 12,
133               use_pretok: bool = True
134               ) -> tuple[list[tuple[int, int]], dict[int, bytes]]:
135     """返回 (merges 有序列表, id -> 字节串)。
136 
137     初始词表固定是 0..255 这 256 个字节。之后每合并一次就多一个 id。
138     use_pretok=False 时不做预切分，用来演示预切分为什么必要（见 [C]）。
139     """
140     chunks = pre_tokenize(text) if use_pretok else [text]
141     seqs = [list(c.encode("utf-8")) for c in chunks if c]
142 
143     vocab: dict[int, bytes] = {i: bytes([i]) for i in range(256)}
144     merges: list[tuple[int, int]] = []
145 
146     print(f"    初始：{len(vocab)} 个字节 token，语料切成 {len(seqs)} 段，"
147           f"共 {sum(len(s) for s in seqs)} 个符号")
148     print(f"    {'轮':>3s} {'合并的对':>22s} {'次数':>6s} {'新 id':>6s} "
149           f"{'新符号':<14s} {'剩余符号数':>10s}")
150 
151     for r in range(n_merges):
152         counts = get_pair_counts(seqs)
153         if not counts:
154             break
155         pair, freq = counts.most_common(1)[0]
156         if freq < 2:                       # 只出现一次的对，合并没有意义
157             print(f"    第 {r} 轮：最高频的对只出现 {freq} 次，停止")
158             break
159         new_id = 256 + len(merges)
160         vocab[new_id] = vocab[pair[0]] + vocab[pair[1]]
161         seqs = merge_pair(seqs, pair, new_id)
162         merges.append(pair)
163 
164         if r < verbose_rounds:
165             a, b = show_token(vocab[pair[0]]), show_token(vocab[pair[1]])
166             print(f"    {r:>3d} {a + ' + ' + b:>22s} {freq:>6d} {new_id:>6d} "
167                   f"{show_token(vocab[new_id]):<14s} {sum(len(s) for s in seqs):>10d}")
168         elif r == verbose_rounds:
169             print(f"    ... （后面 {n_merges - verbose_rounds} 轮省略）")
170 
171     return merges, vocab

174 def show_token(b: bytes) -> str:
175     """把一个 token 的字节串显示成可读形式。
176 
177     完整的 UTF-8 序列就显示成字符；不完整的（半个汉字）显示成十六进制。
178     这个区分本身就是本 lab 要讲的重点之一。
179     """
180     try:
181         s = b.decode("utf-8")
182         return repr(s)
183     except UnicodeDecodeError:
184         return "<" + " ".join(f"{x:02x}" for x in b) + ">"

191 def encode(text: str, merges: list[tuple[int, int]], trace: bool = False,
192            use_pretok: bool = True) -> list[int]:
193     """按 merges 的**顺序**反复合并。顺序不能变——它就是学到的那个算法。"""
194     if use_pretok:
195         out: list[int] = []
196         for chunk in pre_tokenize(text):
197             out.extend(_encode_chunk(chunk, merges, trace))
198         return out
199     return _encode_chunk(text, merges, trace)
200 
201 
202 def _encode_chunk(text: str, merges: list[tuple[int, int]], trace: bool = False) -> list[int]:
203     ids = list(text.encode("utf-8"))
204     rank = {pair: i for i, pair in enumerate(merges)}
205     step = 0
206     while len(ids) >= 2:
207         # 找当前序列里 rank 最小（即最早学到）的那个可合并对
208         pairs = set(zip(ids, ids[1:]))
209         best = min(pairs, key=lambda p: rank.get(p, float("inf")))
210         if best not in rank:
211             break
212         ids = merge_pair([ids], best, 256 + rank[best])[0]
213         step += 1
214         if trace and step <= 8:
215             print(f"      第 {step} 步：合并 {best} -> {256 + rank[best]}，"
216                   f"剩 {len(ids)} 个 token")
217     return ids
218

220 def decode(ids: list[int], vocab: dict[int, bytes]) -> str:
221     raw = b"".join(vocab[i] for i in ids)
222     return raw.decode("utf-8", errors="replace")

陷阱

1. 以为 tokenizer 是「按词切分」。 它是在字节上做频率合并， 和语言学意义上的词没有必然关系。' the' 是一个 token，the 可能不是。

2. 用 A 模型的 chat template 喂 B 模型。 不会报错，输出质量静默下降。 永远从模型自己的 tokenizer_config.json 读。

3. 忘了 add_generation_prompt。 少了末尾那 22 个字符， 模型不知道轮到自己说话，可能继续扮演 user。

4. 生成时用右 padding。 模型会从 <pad> 后面开始写。 decoder-only 生成必须 left padding。

5. 用没见过的文本之外的数据评价 tokenizer。 重复单一句子的语料曾得到压缩比 36；这反映样本重复性，不能代表自然文本的压缩率。

6. 假设 token 边界 = 字符边界。 大量 token 是不完整的 UTF-8 序列。 L0.5 会给出一个真实的乱码案例。

7. 按字符数估算 token 数。 中文约 1.5 字符/token（Qwen3）， 英文约 4 字符/token，代码和数字差异更大。要估就实际 encode 一遍。

自测题

1. 为什么 merges 表的前几条几乎全是空格（Ġ Ġ、ĠĠĠĠ ĠĠĠĠ）？

因为 BPE 合并的是训练语料里最高频的相邻对，而训练语料里有大量代码。

逐步推：

  1. BPE 第一轮统计所有相邻字节对的频率。
  2. 代码文件里，缩进是连续空格。一个 4 空格缩进的 Python 文件， 每一行开头都贡献若干个 (空格, 空格) 对。
  3. 现代 LLM 的预训练语料里代码占比很高（通常 10–20%）， 所以 (Ġ, Ġ) 轻易成为全语料最高频的相邻对。
  4. 合并出 ĠĠ 之后，(ĠĠ, ĠĠ) 又成了最高频 → 得到 ĠĠĠĠ（4 空格）。
  5. 再一轮得到 8 空格。

实际收益：本章实测 "a" + " "*20 + "b" 只用 3 个 token， 7.33 字节/token，是所有样本里最高的。一个 4 空格缩进只花 1 个 token， 否则要花 4 个。对代码任务这是很大的节省。

推论：merges 表的开头部分基本反映了训练语料的构成。 一个中文占比高的 tokenizer，前几十条里会出现中文字节对。

2. 同一个词 the，为什么句首和句中切法不同？这会带来什么问题？

因为预切分把空格并入了后面那一块。

"the wind" 预切分成 ['the', ' wind']——注意第二块带前导空格。 训练时语料里绝大多数 the 都出现在句中，前面有空格， 所以 BPE 学到的是 ' the'（带空格）这个 token。

句首的 the 没有前导空格，' the' 匹配不上，只能退回更碎的切法。 本章实测：

'the wind blows' -> 't' | 'he' | ' wind' | ' ' | 'b' | 'l' | 'ows'

带来的问题有三个：

  1. prompt 末尾有没有空格会改变切分。 "翻译：the" 和 "翻译： the" 给模型的 token 序列不同，输出可能差别很大。这是 prompt 调试时的一个常见困惑源。
  2. 前缀缓存的命中率。 两个只差一个空格的 prompt，token 序列从那里开始就不同了， 后面的块全部无法复用（L5.2）。
  3. 约束解码。 如果要求模型输出必须匹配某个语法， 需要考虑同一个字符串有多种 token 化方式（L5.6）。

工程上的应对：有些 tokenizer 提供 add_prefix_space 选项， 在文本开头自动补一个空格。Qwen3 的 tokenizer.json 里 "add_prefix_space": false——它不这么做。

3. 我要给一个英文为主的模型加中文能力，从分词器角度看要做什么、代价是什么？

本章实测 GPT-2 的中文效率是 1.29 字节/token， Qwen3 是 4.50。也就是说同一段中文，GPT-2 要用 3.5 倍的 token。

后果是连锁的：

  • 上下文窗口按 token 算，实际能装的中文内容少 3.5 倍；
  • 按 token 计费时成本高 3.5 倍；
  • 生成同样长度的中文，要走 3.5 倍的 decode 步数——而 decode 是带宽瓶颈（L0.0b 自测题 5）， 所以延迟也大致差 3.5 倍。

做法是词表扩展：

  1. 在中文语料上训练一批新的 merges，挑出高频的中文 token；
  2. 把它们追加到词表末尾（id 从原词表大小往后排）；
  3. tok_emb 和 lm_head 各加对应的行。

代价有三项，都要预算：

代价 说明
新 embedding 行的初始化 随机初始化会让这些 token 一开始输出乱码。常见做法是用它拆开后各子 token 的 embedding 平均值初始化
必须继续预训练 新 token 的 embedding 需要在中文语料上训练才有意义。这不是「改个配置」能完成的
词表变大 15 万词表、d=4096 时，embedding + lm_head 各 1.2 GB（bf16）。加 3 万个 token 要多约 0.5 GB

还有一个容易忽略的：所有已有的 checkpoint、KV cache、 以及任何缓存了 token id 的东西全部作废，因为 id 空间变了。

所以现在的主流做法是：训练之初就用多语言语料训练分词器，而不是事后扩展。

4. Qwen3 把每个数字切成单独的 token（1.00 字节/token），这看起来很浪费。为什么这么设计？

为了让数字的切分与它出现的上下文无关。

考虑不做这个约束的情况。BPE 会按频率合并数字： 2024 很常见，可能成为一个 token；2025 也常见；但 2027 可能被切成 20 | 27， 而 1234 可能被切成 123 | 4。

同一个数字在不同上下文里的切分不一致，会带来几个问题：

  1. 算术。做加法时模型需要按位对齐。如果 456 是一个 token 而 457 是 4|57， 模型很难学到「个位相加」这种规则。
  2. 数值比较。1000 和 999 如果 token 数不同、切分方式不同， 模型判断大小时用到的表示就不对齐。
  3. 泛化。训练时见过 2024 这个 token，推理时遇到 2087 只能拆开—— 两者的表示完全不同。

代价：数字确实变贵了，1.00 字节/token 意味着 16 位数字要 16 个 token。 本章实测 "3.14159265358979"：Qwen3 用 16 个 token，GPT-2 用 8 个。

这是一个明确的取舍：牺牲数字的压缩率，换取切分的一致性。 Llama 3 也采用了单数字切分。有些模型用三位一组（从右往左）， 是另一种权衡——保留了一定压缩率，同时保持分组规则固定。

验证方法：tok.encode("12345") 和 tok.encode("2345")， 看后者是不是前者的后缀。单数字切分下必然是；按频率合并时通常不是。

5. 一个 batch 里两条 prompt 长度是 10 和 100，padding 到 100。这次前向浪费了多少计算？有什么办法？

先算浪费。 前向的计算量大致与序列长度成正比（attention 部分是平方，先忽略）。

  • 有效 token：10+100=110
  • 实际计算：2×100=200
  • 浪费 45%

如果 batch 里有 8 条长度分别是 10、10、10、10、10、10、10、100， 有效 70 + 100 = 170，实际 8×100=800，浪费 79%。

attention 部分更糟，因为它是 O(T2)： 1002 vs 102 差 100 倍，padding 的代价被放大。

办法一：按长度分桶（bucketing）。 把长度接近的请求放进同一个 batch，padding 浪费就小了。 代价是要等——凑不齐一个桶就得等，尾延迟变差。

办法二：不 padding。 把所有序列首尾相接拼成一个长序列， 再用一个「每条序列从哪里开始」的索引数组告诉 attention 不要跨序列。 这叫 packing 或 varlen，是现在推理引擎的标准做法：

  • FlashAttention 的 varlen 接口接受 cu_seqlens（累计长度前缀和）
  • vLLM 的 batch 里根本没有 padding 概念，token 是连续排布的

浪费降到 0，代价是 attention kernel 更复杂（L3.2、L5.3）。

办法三（训练侧）：sample packing。 把多条短样本拼成一条固定长度的训练样本，用 mask 隔开。 注意 loss 的分母要按有效 token 数算（L7.0b）。

所以「padding」主要是 transformers 这类通用库的做法， 生产推理引擎基本都用 varlen。这也是 L0.1 里 vLLM 的输入张量 和 transformers 形状完全不同的原因。
