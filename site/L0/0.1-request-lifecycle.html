从 HTTP 到 SASS：一次请求的完整调用栈

跟踪一次文本请求经过的 API、调度器、模型执行和输出处理，学习如何从源码定位到实际调用。

实测机器 crater · RTX 5090 D · vLLM 0.29.0 · SGLang 0.5.19前置 可先读 L0.0；分词与采样的细节见 L0.4、L0.5

一次请求经过的组件

你向模型发送一条消息，最后收到一段逐字出现的回答。两端都像是在处理文字， 但 GPU 并不直接读取聊天消息。服务器需要先把文字变成模型的输入， 安排一次或多次计算，再把计算结果变回文字。

本章沿请求处理过程介绍推理引擎，先区分三个组件：

  • API 服务接收请求、检查参数，并把输出发回客户端。
  • 调度器管理等待中和执行中的请求，决定下一轮处理谁。
  • 模型执行器准备张量、调用模型，并把工作提交给 GPU。

这三个角色不一定各占一个进程。同一个进程可以承担多个角色， 一个角色也可以由多个 worker 承担。读源码时，先分清职责，再看进程划分， 比先记住“某引擎有几个进程”更有用。

本章的主线是普通文本生成。图片、投机解码和多机部署会增加步骤， 不能把这里的流程当成所有配置的完整调用栈。

从聊天消息变成模型输入

假设请求中的消息是“请用一句话解释显存带宽”。API 首先解析 HTTP 请求中的 JSON， 确认消息格式、模型名称和生成参数是否合法。这时处理的仍是普通应用数据。

接下来，服务将消息交给 chat template。模板会加入角色标记、消息分隔符， 也可能加入模型约定的生成提示。相同的问题套用不同模板后，得到的字符串可能不同。 模板内容会直接影响模型输入。

tokenizer 再把字符串分成 token，并为每个 token 找到词表中的整数编号。 模型接收的是这些编号，不是 Python 字符串。这里要分别检查三份东西： 原始 messages、模板展开后的文本、最终 token id。只检查最初的消息， 很容易漏掉模板或特殊 token 的差异。

调度器组织并发请求

服务器可能同时收到多个请求。它们的输入长度不同，已经生成的长度也不同， 有些刚到达，有些只差一步就会结束。调度器的任务是把这些状态组织成下一轮计算。

它需要同时考虑两类限制：本轮可以处理多少 token，以及显存是否足以保存所需状态。 因此，“请求已经进入服务器”不等于“GPU 已经开始计算它”。排队时间属于请求延迟， 但不属于某个模型算子的执行时间。

对于使用前缀缓存的请求，还需要查询已有缓存。KV cache 保存历史位置的 key 和 value 张量；如果缓存与当前输入的前缀兼容，就可能少算一部分输入。 分页管理与前缀查找是两件事：前者决定 KV 存放位置，后者决定已有 KV 能否复用。 L5.2 会单独展开这两个问题。

vLLM 的块哈希把前面的上下文带入身份计算；SGLang 的基数树显式保存前缀分叉。 这两种表示方式各有取舍，但不能从数据结构名称直接推出哪一个更快， 也不能说块哈希原则上无法提供前缀感知调度需要的信息。

执行器将调度结果整理成张量

调度器的决定通常还是 CPU 上的数据结构。执行器需要把它整理成 GPU 能读取的张量。 其中几项在后面的章节会反复出现：

输入 含义 为什么需要
token id 本轮各位置对应的词表编号 查 embedding，开始模型计算
position 当前 token 在序列中的位置序号 计算 RoPE 等位置编码变换
slot mapping 新 K/V 应写入的槽位 把新状态放入正确的缓存位置
block table 逻辑块对应的物理块编号 寻址历史 K/V
attention metadata 长度、偏移等辅助信息 让 attention kernel 正确处理变长序列

在小模型或短序列场景下，CPU 构造并向 GPU 传输这些元数据张量可能占据可观的时间。

GPU 随后执行模型。一次前向通常包含矩阵乘、归一化、位置变换、 attention 和激活函数等多个操作。框架可能把其中一些操作融合， 也可能为一个操作调用多个 kernel。因此，模型层数、算子数和 kernel 数不能混用。

首个输出来自 prefill，后续输出来自 decode

在普通自回归生成中，第一次前向处理 prompt，通常称为 prefill。 末位置的隐藏状态经过 lm_head 得到 logits，采样器据此选择第一个输出 token。 第一个输出来自这次 prompt 前向，不需要先额外执行一次 decode 前向。

为了生成第二个输出，模型再处理上一步选出的 token，并读取历史 KV。 这时新增输入通常只有一个 token，而历史上下文已经较长。这类后续步骤称为 decode。 如果一个 batch 中有多条请求，每条请求都可能贡献自己的新 token。

同一模型在两个阶段会出现不同形状的矩阵计算：prefill 的线性层一次处理较多位置， 小 batch decode 一次处理的位置较少。L0.2 将据此估算计算量和数据量， L0.3 再比较硬件上的表现。

拿到 token id 后，服务还要执行增量解码，把编号转换成可发送的文本， 检查停止条件，并通过流式响应返回。一次网络事件未必恰好对应一个 token： 缓冲策略、解码器和接口协议都可能影响发送时机。

43 **6. 跨进程 IPC**
44 - `vllm`：序列化后经 ZeroMQ 送到独立的 EngineCore 进程。拆进程是为了绕开 GIL：HTTP / 分词 / detokenize 不能和 GPU 调度抢同一个解释器。

48 - `vllm`：EngineCore 的 while True：收新请求 → step() → 把输出塞回 IPC。整个系统的心跳。
49 - `sglang`：Scheduler 的主循环。同文件还有 event_loop_overlap 变体：把 CPU 侧调度与 GPU 执行重叠起来（vLLM 的对应物是异步调度）。

51 **8. 一步 = 一次前向**
52 - `vllm`：step()：调度 → 执行 → 收结果。continuous batching 的「iteration-level」就是这个 step 的粒度：每一步都能换一批请求，不必等某个请求生成完。
53 - `sglang`：跑一个 batch。与 vLLM 的 step() 对应。
54 
55 **9. 调度器**
56 - `vllm`：本步跑哪些请求、每个跑几个 token。chunked prefill、抢占、优先级、token 预算都在这里。输出 SchedulerOutput——一份给 GPU 的施工图。
57 - `sglang`：选批策略。SGLang 把策略单独放在 managers/schedule_policy.py，支持 LPM（最长前缀优先）等对 radix cache 友好的排序——这是它和 vLLM 的关键差异之一。
58 
59 **10. 前缀复用查询**
60 - `vllm`：按**块哈希**查前缀有多少已算过。vLLM 用哈希表（O(1) 查一个块），命中的块直接引用，对应 token 不再进入 prefill。
61 - `sglang`：**RadixAttention**：前缀不是哈希表里的独立块，而是一棵基数树（radix tree）。match_prefix 沿树走最长公共前缀，天然支持共享分支与子树级淘汰。对照 vLLM 的哈希表方案：树能表达前缀间的包含关系，哈希表不能。
62 
63 **11. 显存分配**
64 - `vllm`：物理块分配器：free list + 块哈希表。PagedAttention 的「页」就是这里的 KVCacheBlock。
65 - `sglang`：按 LRU 从叶子往上淘汰整棵子树。同文件的 cache_finished_req / cache_unfinished_req 决定一个请求的 KV 何时进入共享树。
66 
67 **12. 执行/模型前向**
68 - `vllm`：组装输入张量（_prepare_inputs，同文件）→ 选 CUDA Graph 或 eager → 模型 forward。
69 - `sglang`：ModelRunner.forward。输入批信息在 model_executor/forward_batch_info.py 的 ForwardBatch 里（对照 vLLM 的 _prepare_inputs）。
70 
71 **13. 采样**
72 - `vllm`：logits → 惩罚 → 温度 → top-k/top-p → 采样。全在 GPU 上做，避免把 logits 拷回 CPU。
73 - `sglang`：采样。SGLang 默认走 FlashInfer 的采样 kernel。
74

143 def version_of(module: str, root: Path | None = None) -> str:
144     """先试导入；失败就从 root 旁边的 dist-info 目录名里读版本。

同一个符号可能执行多次，通常与层数、生成步数或分块有关。 分析调用频次时需先确认统计区间：是一次前向、多步生成的总和，还是通过差分估算的单步开销。不能把累计次数直接等同于“每步次数”。

此外，还需区分 GPU 执行时间与端到端墙钟时间。两者的差值包含了排队、CPU 调度、同步及工具开销。由于 CPU 提交与 GPU 执行存在流水线重叠，不能直接用“kernel 次数 × 单次 launch 开销”去粗暴分解请求总耗时。

 32 def summarize(prof, top: int = 25) -> dict:
 33     """把 profiler 事件汇总成「kernel 名 → 次数 / 总时长」。
 34 
 35     这里有个必须避开的坑：`key_averages()` 同时包含 **CPU 侧算子记录**和
 36     **GPU 侧 kernel 记录**。前者的 device_time 是它所有子事件的累加，
 37     所以 `aten::linear` / `aten::matmul` / `aten::mm` 三层嵌套会把同一段 GPU
 38     时间报三遍。直接求和会得到 3 倍虚高的总时长。
 39 
 40     正确做法是只保留 device_type == CUDA 的事件——那才是真正下发到 GPU 的 kernel。
 41     """
 42     from torch.autograd import DeviceType
 43 
 44     kernels = defaultdict(lambda: {"count": 0, "us": 0.0})
 45     total_us = 0.0
 46     for evt in prof.key_averages():
 47         if evt.device_type != DeviceType.CUDA:
 48             continue
 49         dev_us = getattr(evt, "device_time_total", 0.0) or 0.0
 50         if dev_us <= 0:
 51             continue
 52         kernels[evt.key]["count"] += evt.count
 53         kernels[evt.key]["us"] += dev_us
 54         total_us += dev_us
 55 
 56     ranked = sorted(kernels.items(), key=lambda kv: -kv[1]["us"])
 57     return {
 58         "total_device_us": round(total_us, 1),
 59         "distinct_kernels": len(kernels),
 60         "total_launches": sum(v["count"] for v in kernels.values()),
 61         "top": [
 62             {"kernel": k, "count": v["count"], "us": round(v["us"], 1),
 63              "share": round(v["us"] / total_us, 4) if total_us else 0}
 64             for k, v in ranked[:top]

 69 def clean_timing(llm, prompt, sp_cls, prompt_len: int, decode_steps: int,

 71     """不开 profiler 的干净计时。

 75     """

 77     import time
 78 
 79     def run(max_tokens: int) -> float:
 80         sp = sp_cls(max_tokens=max_tokens, temperature=0, ignore_eos=True)
 81         t0 = time.perf_counter()

 91         "prefill_plus_decode_ms": round(t_all, 2),
 92         "decode_ms_per_step": round((t_all - t_pf) / decode_steps, 3),
 93         "repeats": repeats, "prompt_len": prompt_len, "decode_steps": decode_steps,
 94         "note": "中位数；prefill 用 max_tokens=1，decode 用差分。未开 profiler。",
 95     }

 98 def dump_sass(match: str, out: Path) -> dict:
 99     """把**刚才真正跑过的**一个 Triton kernel 反汇编成 SASS。
100 
101     Triton 在 JIT 之后会把产物落到 TRITON_CACHE_DIR：同一个 kernel 会有
102     .ttir / .ttgir / .llir / .ptx / .cubin 五份，正好是完整的下降链路：
103         Triton IR → TritonGPU IR → LLVM IR → PTX（虚拟 ISA）→ cubin（真实机器码）
104     这条链在 L2.2 会展开讲。这里只取最后一跳：cubin → SASS。
105 
106     注意 PTX 与 SASS 的区别：PTX 是虚拟 ISA，向前兼容、可被驱动 JIT；
107     SASS 绑定具体架构（这里是 sm_120），是 GPU 真正执行的指令。
108     「装了新卡第一次跑特别慢」通常就是驱动在把 PTX 现场 JIT 成 SASS。
109     """
110     cache = Path(os.environ.get("TRITON_CACHE_DIR",
111                                 Path.home() / ".triton" / "cache"))
112     if not cache.exists():
113         return {"error": f"Triton 缓存目录不存在: {cache}"}
114 
115     cubins = sorted(cache.rglob("*.cubin"), key=lambda p: -p.stat().st_size)
116     if not cubins:
117         return {"error": f"{cache} 下没有 .cubin（本次运行可能没触发 Triton JIT）"}
118 
119     picked = next((c for c in cubins if match in c.stem), cubins[0])
120     stem_dir = picked.parent
121     stages = {ext: p.name for ext in ("ttir", "ttgir", "llir", "ptx", "json")
122               for p in stem_dir.glob(f"*.{ext}")}
123 
124     try:
125         sass = subprocess.run(["nvdisasm", "-c", str(picked)],
126                               capture_output=True, text=True, timeout=300).stdout
127     except FileNotFoundError:
128         return {"error": "nvdisasm 不在 PATH（需要 CUDA toolkit；见 env.sh 里的 CUDA_HOME）"}
129     if not sass.strip():
130         return {"error": f"nvdisasm 对 {picked.name} 没有输出"}
131     out.write_text(sass, encoding="utf-8")
132 
133     opcodes: dict[str, int] = defaultdict(int)
134     n_inst = 0
135     for ln in sass.splitlines():
136         s = ln.strip()
137         if not s.startswith("/*") or "*/" not in s:
138             continue
139         rest = s.split("*/", 1)[1].strip()
140         tok = rest.split()
141         if not tok:
142             continue
143         # SASS 里 `@!P6  BRA ...` 的第一个 token 是谓词寄存器（predicate），不是指令
144         if tok[0].startswith("@"):
145             tok = tok[1:]
146             if not tok:
147                 continue
148         op = tok[0].split(".")[0]
149         if not op or op[0] in "/.":
150             continue
151         opcodes[op] += 1
152         n_inst += 1
153 
154     return {
155         "cubin": str(picked),
156         "cubin_bytes": picked.stat().st_size,
157         "n_cubins_in_cache": len(cubins),
158         "compilation_stages_present": stages,
159         "sass_lines": len(sass.splitlines()),
160         "instruction_count": n_inst,
161         "top_opcodes": sorted(opcodes.items(), key=lambda kv: -kv[1])[:14],
162         "sass_file": str(out),
163     }

【5】这个格式为什么让加载变快
==============================================================================
  1. 张量在文件里是**连续的裸字节**，布局与内存中一致（row-major）。
     所以加载 = mmap 文件 + 按 offset 切片，**零反序列化、零拷贝**。
  2. 头部是纯 JSON，读它不需要读数据区 —— 可以先看 shape/dtype 再决定读不读，
     这就是 `safe_open(...).get_slice(name)` 能只读一个张量的原因。
  3. 没有 pickle，解析不执行任何代码（对照 torch.load 的 RCE 风险）。
  4. 代价：**没有对齐填充**。张量起点可能不是 64/128 字节对齐的，
     某些需要对齐的零拷贝路径（比如 GPUDirect Storage）要额外处理。

自测：能否把几个边界分开

模型输出了 token id，为什么客户端还没有收到文字？

模型计算结束并不等于响应发送完成。服务端仍需将结果拷贝回主机、 执行增量解码（detokenize）、判定停止条件，最后写回网络响应通道。排查延迟时应当将这些步骤逐一拆解， 不能把所有耗时都归咎于模型前向计算。

一份 trace 显示 400 次 kernel 调用，能否说模型有 400 层？

不能。一层可能调用多个 kernel，同一个 kernel 也可能被多层复用。 先确认统计区间，再根据符号、次数和对应代码判断这些调用属于哪些操作。

使用 CUDA Graph 后只提交一次，GPU 是否就只执行一个 kernel？

不是。一张图可以包含多个 kernel 节点。图重放减少重复提交工作， 算子融合才可能减少独立 kernel 的数量。两种方法可以组合，但应分别观察。
