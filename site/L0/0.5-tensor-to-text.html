文本输出：从 logits 到流式解码

从 logits 的过滤与采样开始，介绍流式解码和停止条件，解释 token 如何变成文本。

实测机器 crater（RTX 5090 D）· Qwen3-1.7B bf16 · torch 2.13.0+cu130前置 L0.4（文本 → 张量）· L0.0（模型输出 logits）

本章回答三个问题

  1. temperature 到底改变了分布的什么？top_p 的截断点怎么定？
  2. 为什么流式输出时不能每收到一个 token 就单独 decode？
  3. 生成什么时候停？停止条件有哪几种，分别在哪一层判断？

L0.4 解析了「文本 → 张量」的处理链路。本章剖析另一半： 模型吐出 151,936 个实数之后，到底经过哪些步骤才变成屏幕上的字。

本章所有数字都来自一次真实的前向：Qwen3-1.7B，prompt 是 '中国的首都是'。

心智模型：从分数到文本

机制拆解

一、logits 长什么样

一次真实前向（原样）：

prompt '中国的首都是' -> 3 个 token [105538, 59975, 100132]
logits 形状 (1, 3, 151936)，取最后一个位置 -> (151936,)
量级：min -4.44  max 22.12  mean 3.50  std 2.35

  排名       id token              logit      prob   logprob
   0    68990 '北京'             22.1250  0.554616   -0.5895
   1   101314 '哪里'             20.1250  0.075059   -2.5895
   2     2130 '____'           19.6250  0.045526   -3.0895
   3    99245 '什么'             19.1250  0.027613   -3.5895
   4   104673 '哪个'             19.0000  0.024368   -3.7145
   5    99459 '哪'              19.0000  0.024368   -3.7145
   6     9909 '（'              18.8750  0.021505   -3.8395
   7    58695 '中国'             18.2500  0.011511   -4.4645

这份输出包含三个现象：

  • '中国的首都是' 只切成 3 个 token，不是 6 个。 Qwen3 的词表里「中国」「的首都」「是」各是一个 token（L0.4）。
  • 最高分 '北京' 的概率是 0.5546，不是接近 1。 模型认为还有一半的可能性是别的（比如把这句话当成填空题，接 '哪里'）。
  • 排名 4 和 5 的 logit 完全相同（19.0000）。这是 bf16 的精度所致—— bf16 只有 8 位尾数，19.0 附近的间隔是 0.125，两个不同的实数落到了同一个可表示值上。

二、logits、logprob、prob

三者的关系：

pi=ezi∑jezj,ℓi=logpi=zi−log∑jezj

logits 是模型直接输出的实数，没有归一化。给所有 logit 加同一个常数不改变分布—— 分子分母中的 ec 可以约去。下面用同一组 logits 验证：

验证 1：给所有 logit 加 100，softmax 不变
  最大绝对差 = 5.274e-16
验证 2：exp(logprob) == prob
  最大绝对差 = 7.451e-09
验证 3：概率之和 = 1.000024

概率之和不是 1.000000

实测 1.000024，差了 2.4×10−5。

本次计算先将 bf16 logits 转成 fp32，再做 softmax。 对 151,936 个数求和，fp32 的舍入误差会累积到这个量级 （对照 L2.3 关于归约累加精度的实测）。

工程含义：不要写 assert probs.sum() == 1.0。 判断分布是否有效要用容差，而且容差要随词表大小放宽。

为什么 API 返回 logprob 而不是 prob。 序列的联合概率是各步概率的乘积， 很快就会小到 fp32 存不下：

例：连续采 10 个概率各 0.5546 的 token，
    联合概率 = 2.754e-03，而 logprob 相加 = -5.89

10 步就到了 10−3，100 步就是 10−26，1000 步直接下溢成 0。 取对数之后乘法变加法，数值范围完全没问题。

所以凡是涉及序列打分的地方——beam search、投机解码的验证（L5.5）、 RL 里算 ratio（L7.6）——用的都是 logprob。

三、temperature

pi=softmax(zi/T)

T 只是在进 softmax 之前除一下。T<1 把差距拉大，分布更尖； T>1 把差距压缩，分布更平。

本章实测：

T 最大概率 熵 e熵 top-3
0.0 1.0000 0.0000 1.0 argmax
0.2 1.0000 0.0006 1.0 北京, 哪里, ____
0.5 0.9659 0.2063 1.2 同上
1.0 0.5546 2.6288 13.9 同上
1.5 0.1283 7.3256 1518.6 同上
3.0 0.0022 11.3643 86190.6 同上

e熵 这一列叫「有效候选数」（perplexity 的另一种用法）， 可以理解成模型实际在多少个选项之间犹豫。词表 151,936， 均匀分布时这个值就是 151,936。

T=1 时是 13.9——模型基本在十几个词里选。 T=3 时涨到 86,190，已经接近乱采。

T=0 是特例：不是真的除以 0，而是直接取 argmax（贪心解码）。 实现上要单独判断，否则会得到 inf/nan。

四、top-k 与 top-p

两者都是截断：把不要的候选的 logit 置为 −∞，softmax 之后自然是 0。

  • top-k：只保留最大的 k 个。
  • top-p（核采样）：按概率从大到小累加，累计达到 p 之后的全部丢掉。

本章实测：

策略                    候选数       覆盖概率 候选
原始                 151936     1.0000   ['北京', '哪里', '____', '什么']
top_k=1                 1     0.5546   ['北京']
top_k=5                 6     0.7515   ['北京', '哪里', '____', '什么']
top_k=50               52     0.9075   ['北京', '哪里', '____', '什么']
top_p=0.5               1     0.5546   ['北京']
top_p=0.9              46     0.9008   ['北京', '哪里', '____', '什么']
top_p=0.99            146     0.9900   ['北京', '哪里', '____', '什么']

top_k=5 为什么留下了 6 个

因为并列。排名 4 和 5 的 logit 都是 19.0000（bf16 精度所致）， 本章实现用 logits < kth 做掩码，会把所有等于第 k 大值的都保留下来。 top_k=50 同理留下了 52 个。

不同引擎在这里的行为不一致：有的保留全部并列，有的按索引顺序截断到恰好 k 个。 这是一个真实的实现差异，会导致同样的种子在不同引擎上采到不同的 token。 做跨引擎复现时，这是要排查的地方之一。

top-k 与 top-p 的区别在模型确定时最明显。 上表里 top_p=0.5 只留 1 个（因为 '北京' 一个就占了 0.5546）， 而 top_k=50 仍然保留 52 个，包括一堆概率极低的。

反过来，模型不确定时 top-p 会自动放宽。所以 top-p 是自适应的， 这也是它更常用的原因。两者常一起用：先 top-k 砍掉长尾（限制计算量）， 再 top-p 动态收紧。

top-p 的实现有一个容易写错的边界：

53 def top_p_filter(logits: torch.Tensor, p: float) -> torch.Tensor:
54     """核采样：按概率从大到小累加，累计超过 p 之后的全部丢掉。
55 
56     注意边界：第一个使累计**达到或超过** p 的 token 要保留，
57     否则 p 很小时可能一个都不剩。
58     """
59     if p >= 1.0:
60         return logits
61     probs = F.softmax(logits, dim=-1)
62     sorted_probs, sorted_idx = torch.sort(probs, descending=True)
63     cum = torch.cumsum(sorted_probs, dim=-1)
64     # cum > p 的位置要丢；但把这个 mask 右移一位，保住第一个越界的那个
65     remove = cum > p
66     remove[1:] = remove[:-1].clone()
67     remove[0] = False
68     drop_idx = sorted_idx[remove]
69     return logits.index_fill(-1, drop_idx, float("-inf"))

问题在于「第一个使累计超过 p 的 token」要不要保留。 如果不保留，p 很小时可能一个候选都不剩。 本章实现是把 mask 右移一位；另一种等价写法是用「不含自己的累计」来判断。 两种写法本章都实现了并对照验证：

六、增量 detokenize：一个真实的流式乱码

先看一个表面上「看似正常」的例子：

'风吹过山谷' -> 3 个 token
  i       id      单独 decode 字节
  0   109520           '风吹' e9 a3 8e e5 90 b9
  1    38182            '过' e8 bf 87
  2   113599           '山谷' e5 b1 b1 e8 b0 b7

这三个 token 恰好各自对应完整的 UTF-8 字符边界，逐个 decode 碰巧不会报错。但若某个多字节字符被 BPE 切分到多个 token 中，逐个解码就会直接产生乱码故障：

'𩸽' (4 字节) -> 3 个 token
  i       id token         单独 decode
  0   103914 'ð©'                '�'
  1      116 '¸'                 '�'
  2      121 '½'                 '�'

  逐 token decode 再拼接 -> '���'   ← 三个替换符
  整体 decode            -> '𩸽'
  两者相同：False

𩸽 不在词表里，退回字节级，4 个字节被切成 3 个 token （f0 a9 是一个 token，b8、bd 各一个）。 每个 token 单独 decode 都得到替换符 U+FFFD，因为它们都不是完整的 UTF-8 序列。

流式接口增量返回文本，网络事件与 token 不一定一一对应。 如果每次都单独 decode，用户会先看到几个 �——而且永远看不到正确的字。

正确做法是维护一个字节缓冲。 本章实现：

104 class IncrementalDetokenizer:
105     """流式输出用的增量解码器：维护一个字节缓冲。
106 
107     直接对每个 token 调 decode 会在多字节字符被拆开时产生 U+FFFD 替换符。
108     正确做法是把字节攒起来，只吐出能构成完整字符的部分。
109     """
110 
111     def __init__(self) -> None:
112         self.buf = b""
113 
114     def push(self, token_bytes: bytes) -> str:
115         self.buf += token_bytes
116         # 从后往前找最长的可解码前缀；未完成的多字节序列留在缓冲里
117         for cut in range(len(self.buf), max(len(self.buf) - 4, -1), -1):
118             try:
119                 text = self.buf[:cut].decode("utf-8")
120             except UnicodeDecodeError:
121                 continue
122             self.buf = self.buf[cut:]
123             return text
124         return ""

取 token 的原始字节本身就是个坑

若用 tok.convert_tokens_to_string(...).encode("utf-8") 取字节，不完整的字符可能已被替换为 U+FFFD，得到的 ef bf bd 便不是原始 token 的字节。

必须反查字节级映射表（L0.4 讲的 Ġ 那套）才能拿到真实字节：

 72 def make_byte_decoder():
 73     """字节级 BPE 把 0..255 映射到可打印字符（Ġ Ĉ 之类），这里做反向表。
 74 
 75     没有这张表就拿不到 token 的**真实字节**——直接 decode 会在多字节字符
 76     被拆开时得到 U+FFFD，而 U+FFFD 的字节是 ef bf bd，和原始字节毫无关系。
 77 
 78     映射规则（GPT-2 定义，之后所有字节级 BPE 都沿用）：
 79       本来就可打印的字节（! 到 ~、¡ 到 ¬、® 到 ÿ）映射到自己；
 80       其余 68 个（控制字符、空格、以及几个空洞）依次映射到 U+0100 往后。

 88     for b in range(256):

七、停止条件：三条路径，三个层次

条件 判断对象 在哪一层
eos token token id 采样之后、detokenize 之前（引擎调度层）
stop string 文本 detokenize 之后（需要跨 token）
max_tokens 计数 任意层。唯一保证会终止的一条

stop string 必须在文本上判断，不能在 token 上判断—— 停止串可能横跨两个 token。比如停止串是 "\n\n"， 而模型采到的是一个内容为 "。\n\n好" 的 token，只看 token id 是发现不了的。

本章实测一次生成：

生成在 200-token 上限处停止。该配置开启思考模式， 先输出一大段 <think> 内容。这正说明 max_tokens 的必要性—— 没有它，一次请求可能跑很久。

停止原因：stop string '。' @ step 11
输出：'<think>\n嗯，用户让我用一句话说明风是什么。'

11 步就停了。

工程实现 · 源码解析

采样放在 CPU 还是 GPU，会影响每步需要传输的数据量。

朴素做法是把 logits 拷回 CPU，用 numpy/torch 在 CPU 上采样。 问题：logits 是 [B,V]，V=151936，B=64 时就是 64×151936×4 B≈39 MB。 每一步都拷 39 MB 过 PCIe，按 L1.3 实测的 ~25 GB/s 算就是 1.5 ms—— 而一步 decode 本身可能才 5 ms。

这使 GPU 采样成为减少传输量的一种选择。本章所用 vLLM 路径在 GPU 上处理 logits 和采样，再回传 token id；请求 logprobs 时还要返回额外数据。其他引擎可以在 CPU 上采样，不能把 vLLM 的做法推广为全部实现。5.9 对照具体版本中的处理顺序与返回字段。

这条设计也解释了 L2.6b 讲的另一件事： 热路径里不能有 .item()。采样结果如果在 GPU 上就地拼回序列， 整个 decode 步可以不做任何同步；一旦调用 .item() 判断「是不是 eos」， 就会强制同步，打断 CPU-GPU 流水（L1.4 实测 4.76 µs）。

vLLM 的做法是：把「是否遇到 eos」也在 GPU 上算成一个 mask， 异步拷回 CPU，下一步再检查——用一步的延迟换掉同步。

detokenize 可以与模型执行解耦，但仍影响客户端看到文本的时间： vLLM 的 detokenizer 跑在与 EngineCore 不同的进程里（L0.1 分析过）， GPU 只管产出 token id。

 36 def apply_temperature(logits: torch.Tensor, t: float) -> torch.Tensor:
 37     """t < 1 让分布更尖，t > 1 更平。t -> 0 等价于 argmax。"""
 38     if t <= 0:
 39         out = torch.full_like(logits, float("-inf"))
 40         out[logits.argmax()] = 0.0
 41         return out
 42     return logits / t

 45 def top_k_filter(logits: torch.Tensor, k: int) -> torch.Tensor:
 46     """只保留最大的 k 个，其余置为 -inf。"""
 47     if k <= 0 or k >= logits.numel():
 48         return logits
 49     kth = torch.topk(logits, k).values[-1]
 50     return logits.masked_fill(logits < kth, float("-inf"))

 53 def top_p_filter(logits: torch.Tensor, p: float) -> torch.Tensor:
 54     """核采样：按概率从大到小累加，累计超过 p 之后的全部丢掉。
 55 
 56     注意边界：第一个使累计**达到或超过** p 的 token 要保留，
 57     否则 p 很小时可能一个都不剩。
 58     """
 59     if p >= 1.0:
 60         return logits
 61     probs = F.softmax(logits, dim=-1)
 62     sorted_probs, sorted_idx = torch.sort(probs, descending=True)
 63     cum = torch.cumsum(sorted_probs, dim=-1)
 64     # cum > p 的位置要丢；但把这个 mask 右移一位，保住第一个越界的那个
 65     remove = cum > p
 66     remove[1:] = remove[:-1].clone()
 67     remove[0] = False
 68     drop_idx = sorted_idx[remove]
 69     return logits.index_fill(-1, drop_idx, float("-inf"))

 72 def make_byte_decoder():
 73     """字节级 BPE 把 0..255 映射到可打印字符（Ġ Ĉ 之类），这里做反向表。
 74 
 75     没有这张表就拿不到 token 的**真实字节**——直接 decode 会在多字节字符
 76     被拆开时得到 U+FFFD，而 U+FFFD 的字节是 ef bf bd，和原始字节毫无关系。
 77 
 78     映射规则（GPT-2 定义，之后所有字节级 BPE 都沿用）：
 79       本来就可打印的字节（! 到 ~、¡ 到 ¬、® 到 ÿ）映射到自己；
 80       其余 68 个（控制字符、空格、以及几个空洞）依次映射到 U+0100 往后。
 81       所以空格 0x20 -> U+0120 'Ġ'，换行 0x0A -> U+010A 'Ċ'。
 82     """
 83     printable = (list(range(ord("!"), ord("~") + 1))
 84                  + list(range(ord("¡"), ord("¬") + 1))
 85                  + list(range(ord("®"), ord("ÿ") + 1)))
 86     b2u = {b: chr(b) for b in printable}
 87     n = 0
 88     for b in range(256):
 89         if b not in b2u:
 90             b2u[b] = chr(256 + n)
 91             n += 1
 92     return {c: b for b, c in b2u.items()}

 95 def token_bytes(tok, tid: int, byte_dec: dict) -> bytes:
 96     """取一个 token 的原始字节。词表里存的是映射后的字符串。"""
 97     piece = tok.convert_ids_to_tokens([tid])[0]
 98     try:
 99         return bytes(byte_dec[ch] for ch in piece)
100     except KeyError:                     # 特殊 token（<|im_end|> 等）不走字节映射
101         return piece.encode("utf-8")

104 class IncrementalDetokenizer:
105     """流式输出用的增量解码器：维护一个字节缓冲。
106 
107     直接对每个 token 调 decode 会在多字节字符被拆开时产生 U+FFFD 替换符。
108     正确做法是把字节攒起来，只吐出能构成完整字符的部分。
109     """
110 
111     def __init__(self) -> None:
112         self.buf = b""
113 
114     def push(self, token_bytes: bytes) -> str:
115         self.buf += token_bytes
116         # 从后往前找最长的可解码前缀；未完成的多字节序列留在缓冲里
117         for cut in range(len(self.buf), max(len(self.buf) - 4, -1), -1):
118             try:
119                 text = self.buf[:cut].decode("utf-8")
120             except UnicodeDecodeError:
121                 continue
122             self.buf = self.buf[cut:]
123             return text
124         return ""

333         # 参照实现：排序 -> 累加 -> 右移一位 -> 丢弃

335         cum = sp.cumsum(-1)
336         mask = cum - sp > pp           # 另一种等价写法：用「不含自己的累计」
337         ref = logits.clone()
338         ref[si[mask]] = float("-inf")
339         same = torch.equal(torch.isfinite(mine), torch.isfinite(ref))
340         print(f"      top_p={pp}: 候选集相同 = {same}  "
341               f"(我的 {int(torch.isfinite(mine).sum())} 个 / 参照 {int(torch.isfinite(ref).sum())} 个)")
342     print("\n    两种写法在边界上的差别：一个用「含自己的累计 > p」再右移，")
343     print("    一个用「不含自己的累计 > p」。数学上等价，实现上容易写错一个位置——")
344     print("    差一个 token 在温度低时会显著改变输出。")

两种写法：

# 写法一（本站实现）：含自己的累计 > p，然后右移一位
remove = cum > p
remove[1:] = remove[:-1].clone()
remove[0] = False

# 写法二（常见参照实现）：不含自己的累计 > p
mask = cum - sorted_probs > p

数学上等价：cum[i] - p[i] 就是「前 i-1 个的累计」， 所以「不含自己的累计 > p」等价于「前一个位置的含自己累计 > p」， 正是右移一位。

为什么要写两遍再对照验证：这个边界差一位在温度低时会显著改变输出。 p=0.5、最大概率 0.5546 的情况下， 错误实现会留下 0 个候选（然后 softmax 全是 nan）。

这是本章唯一一处「自己实现 + 参照实现对照验证」的验证， 其余各节都只有观测，没有交叉验证。

陷阱

1. assert probs.sum() == 1.0。 本章实测是 1.000024。 词表越大误差越大，要用容差判断。

2. 以为 T=0 就是 logits / 0。 必须特判成 argmax，否则得到 inf/nan。

3. top-k 并列的处理方式不一致。 本章 top_k=5 留下 6 个。 不同引擎行为不同，跨引擎复现时要排查。

4. 流式输出逐 token decode。 遇到被拆开的多字节字符会吐出 �。 必须维护字节缓冲。

5. 从已经解码的文本恢复 token 字节。 convert_tokens_to_string(...).encode() 拿到的是替换符的字节。 必须反查字节级映射表。

6. stop string 在 token 上判断。 停止串可能横跨两个 token， 必须在 detokenize 之后的文本上判断。

7. 只设 stop string 不设 max_tokens。 stop string 可能永远不出现。 max_tokens 是唯一保证终止的条件。

8. 在热路径里 .item() 判断 eos。 会强制 CPU-GPU 同步（L1.4 实测 4.76 µs）。 引擎的做法是在 GPU 上算 mask、异步回传、下一步再检查。

自测题

1. temperature=0.7 和 top_p=0.9 一起用，先做哪个？顺序重要吗？

先 temperature，再 top-p。顺序重要。

设原始 logits 为 z。

正确顺序（先温度）： 1. z′=z/0.7 —— 差距被拉大 2. p′=softmax(z′) —— 分布更尖 3. 按 p′ 做 top-p 截断

错误顺序（先 top-p）： 1. p=softmax(z) 2. 按 p 截断 3. 再对剩下的除以 0.7

差别在于截断用的是哪个分布。

用本章的实测数据算：原始分布最大概率 0.5546。 - 先温度（T=0.7）：最大概率涨到约 0.72，top_p=0.9 大约留下 10 多个候选。 - 先 top-p：按原始分布截断，top_p=0.9 留下 46 个，然后再降温。

候选集差了 3 倍多。 温度越低差别越大：T→0 时正确顺序只留 1 个， 错误顺序仍然留 46 个再降温（虽然最终概率集中，但候选集里有 46 个非零项）。

约定是先温度。 HuggingFace 的 LogitsProcessorList、vLLM 的 sampler 都是这个顺序。写自己的采样器时要对齐，否则同样的参数会得到不同的行为。

2. 我用同样的 prompt、同样的 seed，在 transformers 和 vLLM 上跑，结果不一样。可能是哪些原因？

至少五个可能的来源，按排查顺序：

(1) 采样顺序或边界实现不同。 上一题讲的 temperature/top-p 顺序， 以及本章讲的 top-k 并列处理（本章 top_k=5 留下 6 个）。 排查方法：把 temperature 设成 0（贪心），如果这时结果一致， 问题就在采样阶段。

(2) 随机数生成器不同。 vLLM 在 GPU 上采样，用的是 CUDA 的 Philox 生成器；transformers 默认在 CPU 上采样。 即使种子相同，产生的随机数序列也完全不同。 若无法对齐随机数序列，可先用贪心解码排除抽样差异。

(3) 数值差异。 两个框架的 kernel 不同： transformers 用 PyTorch 的 SDPA，vLLM 用 FlashAttention 或自己的 paged kernel。 bf16 下累加顺序不同会带来最后几位的差异（L2.4 讨论过）。 本章实测的 logits 间隔是 0.125，一个 ULP 的差异就足以让排名 4 和 5 互换。

(4) batch 构成影响结果。 这一条最反直觉： vLLM 把多个请求拼成一个 batch，GEMM 的形状随 batch 变化， 不同形状可能走不同的 kernel 或不同的分块策略，累加顺序因此不同。 同一个请求在不同的 batch 里可能得到略微不同的 logits。

(5) 模板与特殊 token。 两边的 chat template 应用方式可能不同 （L0.4）。add_generation_prompt、是否加 BOS，都会改变输入。 排查方法：打印两边最终的 token id 序列做逐位对比。

实践上的建议：跨引擎对比只在 temperature=0 下做， 而且要先确认 token id 序列完全一致。即便如此， 数值差异仍可能在长生成中放大成完全不同的文本。

3. 流式接口每步都要把新 token 转成文本发给客户端。为什么这件事不能放在 GPU 上做？

因为 detokenize 是字符串处理，不是数值计算。

具体来说它需要：

  1. 按 token id 查词表（一个 15 万条目的哈希表）；
  2. 反查字节映射；
  3. 维护一个跨步骤的字节缓冲；
  4. UTF-8 解码（变长、带状态机）。

这些全是不规则的控制流与内存访问，正是 GPU 最不擅长的。 而且它的数据量极小：每步每个请求只有 1 个 token id。

所以引擎的做法是分层：

层 在哪 处理什么
模型前向 + 采样 GPU [B,V] 的 logits → B 个 token id
token id 回传 PCIe 几百字节，可忽略
detokenize CPU（甚至独立进程） id → 文本

vLLM 把 detokenizer 放在与 EngineCore 不同的进程里（L0.1 分析过）。 好处是 detokenize 的 Python 开销完全不占用 GPU 调度线程； 代价是多一次进程间通信。

一个推论：max_tokens=1 的请求和 max_tokens=1000 的请求， detokenize 的开销差 1000 倍，但这个开销不在 GPU 上， 所以它影响的是吞吐上限（CPU 成为瓶颈）而不是单步延迟。 高并发场景下 detokenize 确实会变成瓶颈，这时要么加进程， 要么让客户端自己 detokenize（只回传 token id）。

4. 我想让模型输出严格的 JSON。设 temperature=0 够吗？

不够。贪心解码只是「每步选概率最高的」，不保证结果合法。

反例很容易构造：模型在某一步的最高概率 token 是 " 而不是 }， 于是生成了一个未闭合的字符串；或者在数组里多写了一个逗号。 概率最高不等于语法正确。

正确做法是约束解码（constrained decoding）： 每一步先算出「在当前语法状态下哪些 token 是合法的」， 把非法 token 的 logit 置为 −∞，再采样。

实现上有几个真实困难：

  1. 合法集合要按语法状态维护。 JSON 的语法是上下文无关的， 需要一个下推自动机（或者编译成有限状态机）。
  2. token 与语法符号不对齐。 语法说的是「下一个字符必须是 }」， 但 token 可能是 "}"、"} "、"}\n"、"}}"…… 要把语法状态映射到 token 集合，这是预计算量很大的一步。
  3. 同一个字符串有多种 token 化。 L0.4 讲过 the 在句首句中切法不同。 约束解码必须接受所有合法的切分方式，否则会排除掉模型本来想走的路径。
  4. 性能。 每步都要算合法 token 集合。 现在的做法是把语法编译成 DFA，预计算每个状态的 token mask（bitmap）， 运行时只做一次位运算。

L5.6 将介绍约束解码，相关实现包括 Outlines、XGrammar、 以及 vLLM/SGLang 内置的 guided decoding。

约束解码可以与 temperature 同时使用。 约束保证合法，温度控制在合法候选里的多样性。 两者可以一起用。

5. 一次请求生成 500 个 token。从系统角度看，这 500 步里 CPU 和 GPU 各做了什么？瓶颈在哪？

先分层列出每一步做的事：

步骤 在哪 数据量 性质
模型前向 GPU 读整个模型权重（1.7B bf16 ≈ 3.4 GB） 带宽瓶颈
采样（温度/top-p/multinomial） GPU [B,151936] 需要排序，非平凡
token id 回传 PCIe B 个 int32 可忽略
eos 检查 CPU 或 GPU 1 个比较 若用 .item() 会强制同步
detokenize CPU 1 个 token 字符串处理
发送给客户端 网络 几十字节 有 syscall 开销

瓶颈在模型前向的显存带宽。 理由（L0.0b 自测题 5 推过）： 生成一个 token 要把整个模型权重读一遍， 3.4 GB/1674 GB/s≈2.0 ms（L1.1 实测带宽）。 而这一步只做了 2×1.7×109≈3.4 GFLOP， 在 232 TFLOPS 的卡上只需 0.015 ms。算力用了不到 1%。

这直接推出三件事：

  1. batch 越大越划算。 权重只读一次，可以同时服务 B 个请求。 B 从 1 涨到 64，延迟几乎不变，吞吐涨 64 倍—— 这就是 continuous batching 的全部动机（L5.3）。
  2. 500 步的总时间约 500 × 2 ms = 1 秒，与 prompt 长度基本无关 （KV cache 的读取随长度增长，但相对权重小得多）。
  3. CPU 侧的每一项都必须避免同步。 单步只有 2 ms 的预算， 一次 .item() 是 4.76 µs（0.24%），看起来不多， 但它打断的是 CPU 提前提交下一步的流水—— 实际影响远大于 4.76 µs（L1.4、L2.1）。

什么时候瓶颈会转移： B 很大时（几百），采样的 [B,V] 排序和 detokenize 的 CPU 开销 会开始显现。这时的对策是 GPU 上的 top-p kernel 优化和 detokenize 多进程。
