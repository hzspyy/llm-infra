资源账本：字节、FLOP 与 roofline

根据模型配置计算权重、KV cache 和计算量，用 roofline 估计性能上限。

实测机器 crater · RTX 5090 D 32 GB · Qwen3-1.7B前置 L0.0（矩阵乘与张量）；L0.1（从 HTTP 到 SASS）

本章回答三个问题

  1. 模型的权重容量、KV cache 与计算量如何直接从配置文件中推导？
  2. 为什么 prefill 阶段通常受算力限制，而 decode 阶段几乎必然撞上显存带宽墙？
  3. 静态的 Roofline 理论模型在哪些实际系统场景（动态批、长上下文、混合状态）下会失效？

心智模型：内存墙与 Roofline 双轴

在评估大模型推理性能时，只看“每秒生成多少 token”往往难以判断硬件是否物尽其用。一个可靠的工程基准是资源账本：先核算模型每一步需要读取多少字节数据、执行多少次浮点运算，再对比硬件的物理带宽与算力上界。

下图展示了基于 RTX 5090 D 实测参数绘制的 Roofline 模型。横轴为算术强度（每搬运 1 字节数据支持的浮点运算次数），纵轴为达到的计算吞吐。斜线代表显存带宽上限，水平线代表 Tensor Core 稠密算力上限，两者的交点即为机器平衡点（Machine Balance）：

机制拆解与推导

1. 从配置映射架构维度

模型的结构规模由 config.json 决定。以 Qwen3-1.7B 为例，关键架构超参数如下：

符号 配置字段 Qwen3-1.7B 取值 物理含义
L num_hidden_layers 28 Transformer 堆叠层数
d hidden_size 2048 隐藏层向量维度
h num_attention_heads 16 Query 注意力头数
g num_key_value_heads 8 Key/Value 注意力头数（GQA 分组）
q head_dim 128 每个注意力头的维度（满足 hq=d）
f intermediate_size 6144 SwiGLU FFN 中间层隐藏维度
V vocab_size 151936 词表大小

在 Grouped Query Attention（GQA）下，h≠g。多个 Query 头共享同一对 Key/Value 头，本例中每个 KV 头服务 h/g=2 个 Query 头。这一设计既削减了单层注意力投影的权重参数，也成倍降低了生成过程中的 KV cache 占用。

2. 逐层参数量与存储字节推导

对于无 bias 的线性层 Y=XW⊤（输入维度 a，输出维度 b），参数量为 a×b。

注意力层投影参数（Attention Projections）

注意力模块包含 Wq,Wk,Wv 三个输入投影与输出投影 Wo： - Wq：d→hq，参数量 d·hq - Wk：d→gq，参数量 d·gq（使用 KV 头数 g） - Wv：d→gq，参数量 d·gq - Wo：hq→d，参数量 hq·d

单层注意力权重参数总量为：

Pattn=2dhq+2dgq

代入数据：Pattn=2×2048×2048+2×2048×1024=8,388,608+4,194,304=12,582,912。

前馈网络参数（SwiGLU FFN）

现代 LLM 普遍采用 SwiGLU 激活，包含 Gate 投影、Up 投影与 Down 投影三个矩阵： - Gate 投影：d→f，参数量 df - Up 投影：d→f，参数量 df - Down 投影：f→d，参数量 fd

单层 FFN 参数总量为：

Pffn=3df

代入数据：Pffn=3×2048×6144=37,748,736。

词表嵌入与输出层（Embedding & lm_head）

词表投影矩阵维度为 V×d：

Pembed=V·d=151936×2048=311,164,928

当开启权重绑定（tie_word_embeddings: true）时，lm_head 与 embed_tokens 共享同一个底层物理内存对象；若未绑定，则需要各存一份，总量翻倍。

全模型主要线性参数核算

主干共有 L=28 层，主要矩阵参数总量为：

Ptotal=L·(Pattn+Pffn)+Pembed

Ptotal=28×(12,582,912+37,748,736)+311,164,928=1,720,451,072

在 BF16（每个元素 2 字节）精度下，基础权重显存占用为：

1,720,451,072×2 bytes=3,440,902,144 bytes≈3.20 GiB(3.44 GB)

其中 FFN 占主干参数的 37.75/(12.58+37.75)≈75.0%。因此即使针对 Attention 算子做了极致优化，整个模型的访存底色依然深度受制于 FFN 权重的搬运。

3. KV Cache 增长与容量天花板

在自回归生成中，每个已生成的 token 都必须保存其所有层的 Key 与 Value 状态供后续注意力检索。

每新增一个 token，所有 L 层累积保存的数据量为：

Ktoken=2·L·g·q·s

其中因子 2 代表 Key 与 Value 两份张量，s 为单元素字节数（BF16 为 2）。代入 Qwen3-1.7B：

Ktoken=2×28×8×128×2=114,688 bytes=112 KiB

若不采用 GQA（退化为标准 MHA，即 g=h=16），单 token 开销将翻倍至 224 KiB。

对于一条上下文长度为 C=4096 的请求，其单请求独占的 KV Cache 显存为：

4096×114,688 bytes=469,762,048 bytes≈448 MiB

若显存池分配 25.39 GB 空间给 KV Cache，在 C=4096 时最大物理并发序列数仅为：

⌊25,389,097,856/469,762,048⌋=54 条

这构成了系统级连续批处理并发度的物理硬上限。

4. 计算量（FLOP）与阶段非对称性

矩阵乘法 M×K 与 K×N 完成时，每次乘加累计计为 2 次浮点运算，总 FLOP 为 2MKN。

Prefill 阶段

输入序列长度为 S。引擎通常只需产出 prompt 末位 token 的分布并写入 KV Cache： - 主干网络线性层（S 个 token 全部参与前向）：

Flinear,body=2·S·Pbody=2×S×[28×(12,582,912+37,748,736)]

  • 输出层 lm_head（仅末位 1 个 token 参与前向）：

Flinear,head=2·1·Phead=2×1×(151936×2048)≈0.62 GFLOP

  • 因果自注意力（Causal Attention，受三角掩码约束，有效运算为全矩阵的一半）：

Fattn=L·2·(2·S2·h·q)×0.5=2LS2hq

当 S=4096 时，总计算量达到 13.47 TFLOP。此时 lm_head 计算量仅占 0.005%；若错误地将 lm_head 作用于全部 S 个 token，将凭空多算 2.55 TFLOP（高估 18% 计算量）。

Decode 阶段

在批大小为 B、上下文长度为 C 时，每步生成 1 个新 token： - 线性层计算：每条序列均需输出预测 logits，lm_head 作用于全部 B 个 token：

Flinear=2·B·(Pbody+Phead)

  • 注意力计算：新 Query 与历史 C 个 Key/Value 做点击与汇总：

Fattn=4·L·B·C·h·q

  • Decode 访存总量（权重 + 历史 KV）：

Ddecode≈Plinear,active·s+B·C·Ktoken

关键非对称性： - 权重搬运量与批大小 B 无关（批内所有请求共享同一份权重）； - KV Cache 搬运量与 B×C 严格成正比。

因此算术强度为：

AIdecode=FdecodeDdecode=2B(Pbody+Phead)+4LBChqPlinear,active·s+B·C·Ktoken

当 B=1,C=4096 时，AI≈1.12 FLOP/byte；即便提升至 B=32，AI 仅增长至 7.59 FLOP/byte，距离 RTX 5090 D 的机器平衡点（152.7 FLOP/byte）仍相差整整 20 倍。

工程实现：源码解析

在现代推理引擎中，显存预算并非由用户输入任意决定，而是在引擎初始化时通过静态参数与动态探针两道关卡划定。

1. 物理页块规格与动态探针（vLLM）

vLLM 将显存划分为离散的 Block。在 vllm/v1/kv_cache_interface.py:419 中定义了单页大小：

@property
def unpadded_page_size_bytes(self) -> int:
    return self.num_heads * self.num_states * self.state_content_size_bytes

@property
def page_size_bytes(self) -> int:
    if self.page_size_padded is not None:
        assert self.page_size_padded >= self.unpadded_page_size_bytes
        return self.page_size_padded
    return self.unpadded_page_size_bytes

对于全注意力模型，num_states = 2（分别对应 Key 与 Value）。但底层为了满足 Tensor Core 访存向量化对齐（如 16 字节对齐），实际申请的 page_size_padded 可能略大于理论计算值。

在 vllm/v1/worker/gpu_worker.py:513 中，剩余可分配给 KV Cache 的空间通过探针动态扣减：

self.available_kv_cache_memory_bytes = (
    self.requested_memory
    - profile_result.non_kv_cache_memory
    - cudagraph_memory_estimate_applied
)

其中： - requested_memory：由总显存乘以 --gpu-memory-utilization（默认 0.90）得出。 - non_kv_cache_memory：通过执行一次最大 batch/context 的虚拟前向（dummy forward）实测捕捉到的激活峰值、中间张量及 PyTorch 上下文常驻显存。 - cudagraph_memory_estimate_applied：为预录制 CUDA Graph 预分配的私有内存池。开启 CUDA Graph 会固定吃掉约 1~2 GB 显存，直接挤占可并发的 KV 块数。

2. 统一池配置器与架构分支（SGLang）

SGLang 在 sglang/srt/model_executor/pool_configurator.py 中集中管理不同架构的每 token 状态开销：

class DefaultPoolConfigurator(MemoryPoolConfigurator):
    def __init__(self, kvc: KVCacheConfigurator):
        # 1) 混合架构：仅全注意力层计入 KV 胞元
        if mambaish := mambaish_config(kvc.model_config):
            effective_layer_ids = [i for i in mambaish.full_attention_layer_ids
                                   if kvc.layer_info.start_layer <= i < kvc.layer_info.end_layer]
            num_layers = len(effective_layer_ids)
        else:
            num_layers = kvc.layer_info.num_effective_layers

        self._cell_size = self._compute_cell_size(kvc, num_layers)

        # 2) 投机解码：Draft 模型需要按比例扩充辅助 KV 缓冲
        if (kvc.spec_algorithm.is_eagle() or kvc.spec_algorithm.is_standalone()) \
                and not kvc.is_draft_worker:
            self._cell_size += self._compute_draft_cell_size(...)

设计取舍

  1. 静态解析 vs 动态探针：静态账本能提供理论下界与量级判断，但无法预测算子融合后的临时缓冲区（workspace）、内存分配器碎片（fragmentation）以及 CUDA Graph 私有显存池。现代引擎采用“理论算边界 + 探针定物理池”的组合策略。
  2. 增大 Batch 的边际递减：增大 Batch 可以在 Decode 阶段有效摊薄权重搬运成本，但在长上下文下，KV Cache 搬运量（B·C·Ktoken）迅速占据主导。当 B·C·Ktoken≫W 时，进一步加大 Batch 已无法提升算术强度，反而会引发显存耗尽导致排队或抢占换出。

工程实现：mini 资源账本

以下是一个纯 Python 实现的最小资源账本计算器，支持输入模型架构超参数，输出参数量分布、每 token KV 开销、特定负载下的 FLOP 与算术强度：

#!/usr/bin/env python3
"""mini_ledger.py · 最小模型资源账本计算器"""

def calculate_ledger(cfg: dict, ctx: int, batch: int, hw_bw_gbps: float, hw_tflops: float):
    d = cfg["hidden_size"]
    L = cfg["num_hidden_layers"]
    h = cfg["num_attention_heads"]
    g = cfg.get("num_key_value_heads", h)
    q = cfg.get("head_dim", d // h)
    f = cfg["intermediate_size"]
    V = cfg["vocab_size"]
    tied = cfg.get("tie_word_embeddings", False)

    # 1. 参数账
    p_attn_layer = 2 * d * (h * q) + 2 * d * (g * q)
    p_ffn_layer = 3 * d * f
    p_embed = V * d * (1 if tied else 2)
    p_total = L * (p_attn_layer + p_ffn_layer) + p_embed
    w_bytes = p_total * 2  # BF16

    # 2. KV Cache 账 (单 token)
    kv_bytes_per_tok = 2 * L * g * q * 2  # BF16
    kv_bytes_req = ctx * kv_bytes_per_tok

    # 3. Decode 单步计算量与访存
    flops_linear = 2 * (p_total) * batch
    flops_attn = 4 * L * batch * ctx * h * q
    flops_total = flops_linear + flops_attn
    bytes_moved = w_bytes + (batch * kv_bytes_req)
    ai = flops_total / bytes_moved

    # 4. Roofline 时间下界
    t_mem_ms = (bytes_moved / (hw_bw_gbps * 1e9)) * 1e3
    t_cmp_ms = (flops_total / (hw_tflops * 1e12)) * 1e3
    t_bound_ms = max(t_mem_ms, t_cmp_ms)

    return {
        "p_total_M": p_total / 1e6,
        "weight_GB": w_bytes / 1e9,
        "kv_tok_KB": kv_bytes_per_tok / 1e3,
        "kv_req_MB": kv_bytes_req / 1e6,
        "decode_flops_G": flops_total / 1e9,
        "decode_moved_GB": bytes_moved / 1e9,
        "arithmetic_intensity": ai,
        "bound": "memory" if t_mem_ms > t_cmp_ms else "compute",
        "t_lower_bound_ms": t_bound_ms,
    }

if __name__ == "__main__":
    qwen_cfg = {
        "hidden_size": 2048, "num_hidden_layers": 28,
        "num_attention_heads": 16, "num_key_value_heads": 8,
        "head_dim": 128, "intermediate_size": 6144,
        "vocab_size": 151936, "tie_word_embeddings": True
    }
    res = calculate_ledger(qwen_cfg, ctx=4096, batch=8, hw_bw_gbps=1519.3, hw_tflops=232.0)
    print(f"Qwen3-1.7B (B=8, C=4096):")
    print(f"  总参数量: {res['p_total_M']:.2f} M · 权重显存: {res['weight_GB']:.2f} GB")
    print(f"  每 token KV: {res['kv_tok_KB']:.2f} KB · 单序列 KV: {res['kv_req_MB']:.2f} MB")
    print(f"  算术强度: {res['arithmetic_intensity']:.2f} FLOP/byte · 瓶颈: {res['bound']}")
    print(f"  理论耗时下界: {res['t_lower_bound_ms']:.2f} ms")

3. 为什么实测耗时高于理论下界？

在 L0.1 中，实测 Decode 单步耗时（Batch=1）约为 4.2 ms，高于理论下界 2.57 ms。差距来源于： 1. GEMV 与非 GEMM 算子发射开销：单步 Decode 涉及 RMSNorm、RoPE、Sampling 等大量小算子，每个算子需经历主机发射与设备执行，在小 batch 下无法隐藏驱动调度延迟。 2. 显存未达峰值带宽：实测 1519.3 GB/s 为长连续块的 Copy 带宽，实际分页注意力检索存在非连续寻址与 Bank 冲突开销。 3. 输出层 lm_head 开销：虽然只生成 1 个 token，但仍需加载完整的 151936×2048 投影权重（占约 622 MB 访存）。

前沿：混合状态与 MoE 的资源账本

1. 混合状态架构（Hybrid State / SSM）

在以 RecurrentGemma-2B（L5.13）为代表的架构中，并非所有层都保存 Transformer 的 KV 张量： - 26 层中包含 18 层循环状态（Recurrent Layer）与 8 层全注意力层。 - 循环层状态固定为 360 KB/batch，不随序列长度增长；仅 8 层注意力保留标准 KV Cache（约 8 KB/token）。 - 在长上下文（如 32k）下，其总状态显存仅为传统 Transformer 的约 1/3，大幅推迟了显存见顶与带宽饱和的发生点。

2. 混合专家模型（MoE）

在 MoE 模型（如 DeepSeek、Mixtral，见 L4.4 / L6.3）中： - 存储容量按全部专家总参数计算（决定了能否装进卡内）； - 前向计算与有效搬运仅按被激活的 Top-K 专家计算。 - 在 Decode 阶段，若不同序列路由到不同的专家，激活的权重集合将产生联合扩散，使得批处理摊薄权重的收益显著降低。

陷阱

  1. 将参数文件大小直接等同于运行时显存：未计入运行时中间张量激活、优化器状态、CUDA 上下文常驻显存以及 PyTorch 内存池预留。
  2. Prefill 计算量高估 18%：错误地假设 lm_head 针对全部 S 个 token 计算输出。在线服务仅对末位 token 投影 logits。
  3. 盲目扩大 Batch 追求线性加速：在长上下文服务中，KV 搬运量迅速蚕食带宽优势；显存不足时更会触发块抢占甚至换出（Swap-out），导致时延雪崩。
  4. 微基准数字简单叠加：将单独测量的 Attention 延迟与 GEMM 延迟直接相加，忽略了流式异步发射、流水线掩盖与 CPU 提交排队效应。

自测题

1. 若将 Qwen3-1.7B 的 Key/Value 头数从 g=8 恢复为与 Query 头数相同的 h=16（即标准 MHA），在并发 B=32、上下文 C=8192 条件下，KV Cache 显存将增加多少？

解答： 原配置下，单 token 每层 KV 维度为 2×8×128=2048 个 BF16 元素（4096 字节），28 层总计 114,688 字节。 恢复为 g=16 后，每 token 状态翻倍至 229,376 字节。 在 B=32,C=8192 下： - 原总容量：32×8192×114,688 B≈30.06 GB - 恢复后容量：32×8192×229,376 B≈60.13 GB 显存需求净增约 30.07 GB，直接超出单张 RTX 5090 D（32 GB）的物理承载极限。

2. 为什么同样是矩阵乘法，Prefill 算术强度可达几百甚至上千，而单序列 Decode 仅有 1 左右？

解答： Prefill 阶段面对的是 GEMM（矩阵乘矩阵，维度 [S,d]×[d,d′]），每个读入片上的权重元素都会与输入序列中的 S 个 token 进行复用乘加，算术强度随序列长度 S 线性放大； Decode 阶段面对的是 GEMV（向量乘矩阵，维度 [1,d]×[d,d′]），每个权重元素从显存读入片上后仅与 1 个向量做点积即被丢弃，毫无时间局部性复用，算术强度退化至接近数据类型下界（约 1~2 FLOP/byte）。

3. 某服务为 Qwen3-1.7B 分配了 16 GB 的专属 KV Cache 显存池，要求必须支持 16 路并发，求单路请求允许的最大上下文长度？

解答： 已知 Qwen3-1.7B 单 token KV Cache 为 114,688 字节。 16 GB 显存池总字节数为 16×109 字节（若按二进制计算为 16×230≈17.18×109 字节）。 单路请求允许的最大 KV 预算为：

16×109/16=1.0×109 字节

最大上下文长度为：

Cmax=⌊1.0×109/114,688⌋≈8719 tokens

若按二进制 GiB 计算，则约为 9362 tokens。
