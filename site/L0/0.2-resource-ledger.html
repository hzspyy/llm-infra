资源账本：字节、FLOP 与 roofline

从模型配置计算权重、KV 与主要 FLOP，用 roofline 建立有明确假设的性能参照。

实测机器 历史记录：Qwen3-1.7B · crater RTX 5090 D数据日期 2026-09-09前置 L0.0（矩阵乘与张量）；L0.1（prefill 与 decode）

资源估算为性能测量提供参照

读性能报告时，我们常看到“某模型每秒生成多少 token”，却不知道这个数字是否合理。 一个比较直接的起点是：先算模型要读取多少数据、执行多少运算， 再看机器完成这些工作大约需要多久。

本章用 Qwen3-1.7B 做例子，依次计算权重、KV cache 和主要矩阵运算的规模。 这些计算是一份简化模型，不是 GPU 执行轨迹。 它的作用是帮助你提出问题，例如“为什么显存增加了这么多”或“为什么 batch 增大后吞吐提高”， 而不是只靠配置文件就精确预测延迟。

先约定单位。GB 使用十进制，1 GB 等于十亿字节；GiB 使用二进制， 1 GiB 等于 2 的 30 次方字节。bf16 的每个元素占 2 字节。 后面的容量计算都先保留字节数，再换算显示，避免把 GB 和 GiB 混在一起。

先不要把这些数字当作一张必须背下来的表。你需要学会的是： 看到一项矩阵操作，能从配置中找出输入维度和输出维度。

第二步：算一层要保存多少权重

对于一个没有 bias 的线性变换，输入维度为 a、输出维度为 b， 权重矩阵就有 a × b 个元素。先按这个规则计算 attention 的四个投影：

投影 输入维度 输出维度 参数个数
Q d hq d × hq
K d gq d × gq
V d gq d × gq
O hq d hq × d

因此，一层的投影参数数为：

Pattn=2dhq+2dgq

本例代入 d=2048、h=16、g=8、q=128，可以分别检查 Q/O 与 K/V 的大小。 这一步只数投影矩阵，不把归一化等小参数算进去。

SwiGLU FFN 包含 gate、up、down 三个矩阵。前两个把维度从 d 提到 f， 最后一个从 f 降回 d，因此：

Pffn=3df

把每层相加，再乘层数，就得到主干线性层的参数量。 embedding 有 Vd 个元素；如果 lm_head 与 embedding 共享权重， 计算独立参数时不应把它们重复算两次。

已有脚本给出的主要矩阵统计如下。它省略了一些归一化等小项， 所以应称为结构估算，不能代替完整的参数清单：

部分 估算参数个数
28 层 attention 投影 352,321,536
28 层 FFN 1,056,964,608
共享 embedding / lm_head 311,164,928
合计 1,720,451,072

按 bf16 存储，以上主要权重约占 3.44 GB。这里约六成参数属于 FFN。 因此，即使你的优化目标是 attention，也不能忽略 FFN 对权重读取量的影响。

权重文件大小与加载后的显存占用还不是同一个量：重复存储、权重共享、 量化辅助数据、运行时 workspace 都可能改变两者的关系。 要确认共享，应同时看加载代码和加载后的张量，而不只看参数名。

第三步：算 KV cache 为什么越生成越大

权重通常由一批请求共享；KV cache 则描述某条请求已经处理过的上下文。 两个请求没有可复用前缀时，不能仅因它们使用同一模型就共用全部 KV。

对本例普通 GQA attention，一个 token 在一层需要保存： g 个 K head，以及 g 个 V head，每个 head 有 q 个元素。 设每个元素占 s 字节，则所有层的缓存量为：

Ktoken=2Lgqs

代入 28 层、8 个 KV head、每 head 128 个元素、每元素 2 字节：

Ktoken=2×28×8×128×2=114688 bytes

这等于 112 KiB，也约为 114.69 KB。一个长度为 4096 的上下文因此需要：

4096×114688=469762048 bytes

也就是 448 MiB，约 0.47 GB。它只是一条请求的 KV。 如果 32 条请求都具有这么长的上下文，且不共享缓存，KV 总量约为 15.03 GB。

实际分页缓存会按块分配，末块还可能没有填满；引擎也可能提前预留缓存池。 所以“按 token 算出的有效数据量”“已经分配的块容量”和“GPU 总显存占用” 是三个不同的量。L5.2 会把它们与 block table、空闲块和引用计数联系起来。

这条公式不是所有架构的通用公式。量化 KV、滑动窗口、MLA 或其他状态表示， 都需要按实际存储布局重新推导，不能只把模型名字换掉继续使用。

第四步：算一次前向做多少运算

一个 M×K 矩阵乘 K×N 矩阵，要得到 M×N 个输出。 每个输出沿 K 维累加乘积。按一次乘法和一次加法各计一个 FLOP 的惯例， 主要运算量约为 2MKN。

设主干线性层参数量为 P_body，输出层参数量为 P_head， prompt 长度为 S。只需生成一个首 token、也不请求 prompt logprobs 时， 可以按以下方式估算线性层计算：

Flinear,prefill≈2SPbody+2Phead

第一项处理 prompt 的各个位置；第二项只为末位置计算输出 logits。 这是当前估算采用的执行需求。训练或需要其他位置 logits 的任务，必须另算。

attention 还要形成 Q 与 K 的匹配，并用这些权重汇总 V。 在普通 causal attention 的粗略模型中，计算量随 S 的平方增长。 这里用：

Fattention,prefill≈2LS2hq

它省略了 softmax 等操作，也没有描述具体 kernel 的 tile、padding 和访存。 因此应把它读作数量级与主要项估算，而不是实际执行的精确指令数。

decode 则不同：每条请求本轮只处理一个新位置，仍需访问历史 K/V。 如果有 B 条等长请求，历史长度为 C，主要运算量可写成：

Fdecode≈2B(Pbody+Phead)+4LBChq

这说明 batch 与上下文长度都会影响 decode，但影响的是不同部分： batch 增大会增加本轮的新位置数，上下文变长则增加 attention 需要读取和处理的历史。

第五步：把运算量与读取量放在一起

算术强度（arithmetic intensity）是运算量除以数据搬运量，单位是 FLOP/byte。 它描述平均每搬一个字节，进行了多少运算。

在一个理想化的 decode 模型中，可以先把每步读取量估为：

Ddecode≈W+BCKtoken

W 是本轮涉及的权重字节数，后一项是历史 KV 字节数。 这里假设一批请求能共享一次主要权重读取；实际缓存命中、重复读取和中间张量 还会改变真实流量，因此这个式子不是硬件计数器的替代品。

由此可以理解 batch 的作用。B 从 1 增加时，权重项不必按请求数等比例增长， 每份权重能参与更多位置的计算；但 KV 项仍随请求数增长。 所以 batch 可以提高总吞吐，却不会让收益无限线性增长。

也不要把总吞吐与单请求速度混淆。一次花 10 ms 为 32 条请求各生成一个 token， 总吞吐是 3200 token/s；单条请求仍要等这一轮约 10 ms，而不是 1/3200 秒。

Roofline 给的是参照，不是完整延迟预测

假设机器的计算吞吐参照为 R FLOP/s，内存带宽参照为 BW byte/s。 完成 F 次运算和 D 字节搬运，分别需要的理想时间为 F/R 与 D/BW。 若把二者视为可以充分重叠，可用较大者作为时间下限的模型：

Tmodel=max(F/R,D/BW)

这就是 roofline 分析的基本想法。若数据搬运项更大，优先检查访存； 若计算项更大，优先检查计算路径。但真实请求还包含调度、同步、通信及其他操作， 它们没有自动包含在这两个除法里。

本章的 R 和 BW 来自微基准，而非对所有工作负载都成立的物理上限。 因此更准确的叫法是“基于这些参照值的估计下限”。 如果后来出现更高的有效带宽，应先检查流量口径、缓存和参照测试， 不要马上认定硬件超过了物理极限。

怎样把公式与代码对应起来

先看 Arch.from_hf()：它从配置中取出哪些字段。 再看 p_attn_per_layer、p_ffn_per_layer 和 kv_bytes_per_token()， 检查它们是否就是前面推导的矩阵数与字节数。

最后看 prefill_flops() 和 decode_step()。 遇到某个假设时，在代码旁写出它针对哪种架构和输出需求。 这个脚本含有其他模型的分支，但没有因此获得对所有模型布局的验证。

100     def p_total(self) -> int:
101         per_layer = self.p_attn_per_layer + self.p_ffn_per_layer
102         return self.n_layer * per_layer + self.p_embed
103 
104     @property
105     def p_body(self) -> int:
106         """28 层主干里，每个 token 都要过一遍的线性层参数（不含 lm_head）。"""
107         return self.n_layer * (self.p_attn_per_layer + self.p_ffn_active_per_layer)
108 
109     @property
110     def p_head(self) -> int:
111         """lm_head：隐状态 → 词表 logits 的那个大矩阵。"""
112         return self.vocab * self.d_model
113 
114     @property
115     def p_linear_active(self) -> int:
116         """decode 一步要**读一遍**的线性层参数总量（主干 + lm_head）。
117 
118         注意这是「字节」口径：decode 每步都要把 lm_head 整个读进来。
119         FLOP 口径在 prefill 时不同——见 prefill_flops() 的注释。
120         """
121         return self.p_body + self.p_head
122 
123     # -- KV cache ----------------------------------------------------------
124 
125     def kv_bytes_per_token(self, kv_dtype: str = "bf16") -> float:
126         """K 和 V 各一份，所以有那个 2。这是 decode 阶段增长最快的一项。"""
127         return 2 * self.n_layer * self.n_kv_head * self.d_head * BYTES[kv_dtype]

132 def prefill_flops(a: Arch, seq: int) -> dict:
133     """一次 prefill 的 FLOP 拆分。
134 
135     这里有个容易高估 18% 的坑：**lm_head 只作用在最后一个 token 上**。
136     prefill 的目的是把 prompt 的 KV 填好并产出第一个 token，
137     中间那 S-1 个位置的 logits 没人要，引擎不会算（vLLM 只对
138     `logits_indices` 指定的位置做 lm_head）。
139     如果按 `p_linear_active * seq` 算，会把 lm_head 多算 S-1 倍——
140     对 Qwen3-1.7B、S=4096 来说，凭空多出 2.55 TFLOP（总量的 18%）。
141     """
142     linear_body = 2 * a.p_body * seq
143     linear_head = 2 * a.p_head * 1
144     # QK^T 与 AV 各一次：2 * S^2 * n_head * d_head * 2(乘加)，causal 掩掉一半
145     attn = a.n_layer * 2 * (2 * seq * seq * a.n_head * a.d_head) * 0.5
146     return {"linear": linear_body + linear_head, "linear_body": linear_body,
147             "linear_head": linear_head, "attention": attn,
148             "total": linear_body + linear_head + attn}
149

151 def decode_step(a: Arch, ctx: int, batch: int, *,
152                 w_dtype: str = "bf16", kv_dtype: str = "bf16") -> dict:
153     """decode 一步（每条序列出 1 个 token）的 FLOP 与字节。
154 
155     关键不对称：
156       - 权重字节与 batch **无关**（一整批共享同一份权重）
157       - KV 字节与 batch × 上下文长度 **成正比**
158     这个不对称正是 continuous batching 有效、而超长上下文又会把收益吃掉的原因。
159     """
160     # decode 时每条序列都要出 logits，所以 lm_head 对每个 batch 元素都算一次
161     flops_linear = 2 * (a.p_body + a.p_head) * batch
162     flops_attn = a.n_layer * 2 * (2 * ctx * a.n_head * a.d_head) * batch
163     flops = flops_linear + flops_attn
164 
165     bytes_w = a.p_linear_active * BYTES[w_dtype]
166     bytes_kv = batch * ctx * a.kv_bytes_per_token(kv_dtype)
167     total_bytes = bytes_w + bytes_kv
168 
169     return {
170         "flops": flops,
171         "bytes_weight": bytes_w,
172         "bytes_kv": bytes_kv,
173         "bytes_total": total_bytes,
174         "arithmetic_intensity": flops / total_bytes,
175     }

178 def roofline_tpot_ms(step: dict, hw: dict) -> dict:
179     """把字节数和 FLOP 数换算成时间下界。
180 
181     memory 时间 = 搬运字节 / 实测显存带宽
182     compute 时间 = FLOP / 实测稠密 GEMM 吞吐
183     实际耗时 >= max(两者)。取不到这个下界，说明有别的开销（launch、同步、
184     kernel 效率、CPU 调度），那就是要去 profile 的地方。
185     """
186     bw = hw["memory_bandwidth"]["copy_gbps"] * 1e9
187     tflops = hw["gemm"]["bf16"]["peak_tflops"] * 1e12
188     t_mem = step["bytes_total"] / bw
189     t_cmp = step["flops"] / tflops
190     return {
191         "t_memory_ms": t_mem * 1e3,
192         "t_compute_ms": t_cmp * 1e3,
193         "t_lower_bound_ms": max(t_mem, t_cmp) * 1e3,
194         "bound_by": "memory" if t_mem > t_cmp else "compute",
195         "machine_balance_flops_per_byte": tflops / bw,
196     }

 31 # 计时基元：用 CUDA event 而不是 time.time()。
 32 # CUDA kernel 是异步下发的，host 侧计时器测到的是「下发耗时」而非「执行耗时」。

 35 def time_cuda(fn, *, warmup: int = 10, iters: int = 50) -> float:
 36     """返回单次执行的中位耗时（毫秒）。"""
 37     for _ in range(warmup):
 38         fn()
 39     torch.cuda.synchronize()
 40 
 41     samples = []
 42     for _ in range(iters):
 43         start = torch.cuda.Event(enable_timing=True)
 44         end = torch.cuda.Event(enable_timing=True)
 45         start.record()
 46         fn()
 47         end.record()
 48         torch.cuda.synchronize()
 49         samples.append(start.elapsed_time(end))
 50     return statistics.median(samples)

 57 def probe_memory_bandwidth(mb: int = 512) -> dict:
 58     """用大块 copy 逼近显存带宽上限。
 59 
 60     copy_ 读一遍写一遍，所以搬运字节数 = 2 * size。
 61     选 512MB 是为了确保远超 L2（5090 约 96MB，L40S 约 96MB），
 62     否则测到的是 L2 带宽而不是显存带宽。
 63     """
 64     n = mb * 1024 * 1024 // 2  # fp16 元素数
 65     src = torch.empty(n, dtype=torch.float16, device="cuda")
 66     dst = torch.empty_like(src)
 67     src.normal_()
 68 
 69     ms = time_cuda(lambda: dst.copy_(src))
 70     moved_bytes = 2 * src.numel() * src.element_size()
 71     gbps = moved_bytes / (ms * 1e-3) / 1e9
 72 
 73     # 只读的场景（decode 读 KV cache 更接近这个）用 sum 近似
 74     ms_read = time_cuda(lambda: src.sum())
 75     read_gbps = src.numel() * src.element_size() / (ms_read * 1e-3) / 1e9
 76 
 77     return {
 78         "copy_gbps": round(gbps, 1),
 79         "readonly_gbps": round(read_gbps, 1),
 80         "buffer_mb": mb,
 81         "note": "copy_ 计入读+写两份流量；readonly 用 reduction 近似纯读",
 82     }

 89 def probe_gemm(sizes=(4096, 8192)) -> dict:
 90     """测 tensor core 实际能到的稠密 TFLOPS。
 91 
 92     GEMM 的 FLOP 数 = 2*M*N*K（一次乘 + 一次加）。
 93     用方阵 M=N=K，规模要够大才能摊薄启动与尾效应。
 94     """
 95     out: dict = {}
 96     for dtype, name in [(torch.bfloat16, "bf16"), (torch.float16, "fp16")]:
 97         best = 0.0
 98         detail = {}
 99         for s in sizes:
100             a = torch.randn(s, s, dtype=dtype, device="cuda")
101             b = torch.randn(s, s, dtype=dtype, device="cuda")
102             ms = time_cuda(lambda: torch.mm(a, b), warmup=5, iters=20)
103             tflops = 2 * s**3 / (ms * 1e-3) / 1e12
104             detail[f"{s}"] = round(tflops, 1)
105             best = max(best, tflops)
106             del a, b
107             torch.cuda.empty_cache()
108         out[name] = {"peak_tflops": round(best, 1), "by_size": detail}
109 
110     # FP8：Ada(sm_89) 与 Blackwell(sm_120) 都有 FP8 tensor core，
111     # 走 torch._scaled_mm（per-tensor scale）。
112     try:
113         s = 8192
114         a = torch.randn(s, s, device="cuda").to(torch.float8_e4m3fn)
115         b = torch.randn(s, s, device="cuda").to(torch.float8_e4m3fn).t().contiguous().t()
116         scale = torch.tensor(1.0, device="cuda")
117         ms = time_cuda(
118             lambda: torch._scaled_mm(a, b, scale_a=scale, scale_b=scale,
119                                      out_dtype=torch.bfloat16),
120             warmup=5, iters=20)
121         out["fp8_e4m3"] = {"peak_tflops": round(2 * s**3 / (ms * 1e-3) / 1e12, 1),
122                            "by_size": {str(s): round(2 * s**3 / (ms * 1e-3) / 1e12, 1)}}
123         del a, b
124         torch.cuda.empty_cache()
125     except Exception as exc:  # noqa: BLE001
126         out["fp8_e4m3"] = {"error": f"{type(exc).__name__}: {exc}"}
127 
128     return out

135 def probe_launch_overhead(n_kernels: int = 500) -> dict:
136     """一个「什么都不做」的小 kernel，重复下发，测每次的摊销成本。
137 
138     这是 CUDA Graph 存在的理由：decode 阶段每步要下发几百个小 kernel，
139     如果每个都要 CPU 走一遍 driver，CPU 就成了瓶颈。
140     """
141     x = torch.zeros(1, device="cuda")
142 
143     def burst():
144         for _ in range(n_kernels):
145             x.add_(1.0)
146 
147     ms_eager = time_cuda(burst, warmup=3, iters=10)
148 
149     # 同样的序列用 CUDA Graph 捕获后重放
150     g = torch.cuda.CUDAGraph()
151     torch.cuda.synchronize()
152     with torch.cuda.graph(g):
153         for _ in range(n_kernels):
154             x.add_(1.0)
155     ms_graph = time_cuda(g.replay, warmup=3, iters=10)
156 
157     return {
158         "n_kernels": n_kernels,
159         "eager_us_per_kernel": round(ms_eager * 1000 / n_kernels, 2),
160         "graph_us_per_kernel": round(ms_graph * 1000 / n_kernels, 2),
161         "graph_speedup": round(ms_eager / ms_graph, 2),
162     }

引擎自己怎么算这本账

上面是解析模型。vLLM 启动时算同一本账，但有两处差别值得单独看， 因为它们正好是解析式估算算不出来的部分。

第一处：一个 KV 页实际占多少字节。 v1/kv_cache_interface.py:419：

@property
def unpadded_page_size_bytes(self) -> int:
    return self.num_heads * self.num_states * self.state_content_size_bytes

@property
def page_size_bytes(self) -> int:
    if self.page_size_padded is not None:
        assert self.page_size_padded >= self.unpadded_page_size_bytes
        return self.page_size_padded
    return self.unpadded_page_size_bytes

num_states 对普通 full attention 是 2（K 和 V），这和我们的公式一致。 但 page_size_padded 用于描述补齐后的页容量：某些 attention 后端（例如需要特定对齐的 FlashInfer 或 MLA）要求页大小按硬件对齐补齐，实际占用因此可能大于理论值。 补齐量取决于后端实现，公式里没有这一项。

同文件 439 行的 AttentionSpec 派生出 FullAttentionSpec； 滑动窗口、Mamba 状态、跨层共享各有自己的子类。换句话说， 「KV cache」在当前引擎里不是一种结构，而是一族结构。L3.4 会展开。

第二处：非 KV 的显存不是估的，是量出来的。 labs/L0/ledger.py 里我们写了一个固定的 overhead = 1.5e9。 vLLM 的做法在 v1/worker/gpu_worker.py:513：

self.available_kv_cache_memory_bytes = (
    self.requested_memory
    - profile_result.non_kv_cache_memory
    - cudagraph_memory_estimate_applied
)

non_kv_cache_memory 来自同文件 553 行的 memory_profiling(...)： 启动时真的按最大规模跑一遍 dummy forward，测出激活峰值。 之所以要测，是因为激活峰值取决于 batch 形状、attention 后端实现和算子融合情况， 没有闭式解。

第三项 cudagraph_memory_estimate_applied 是 CUDA Graph 捕获需要预留的显存池。 开启 CUDA Graph 会占掉一部分本来可以给 KV 的显存， 也就是用并发度换取更低的提交开销。L5.4 会回到这个取舍。

这一节可以概括成一句可复用的判断：解析模型给数量级和方向， 实测给出当前实现下的真值。两者都需要，因为只有模型会漏掉实现细节， 只有实测则说不出为什么。

广度对照：SGLang 把同一本账拆得更细

vLLM 用一个 KVCacheSpec 描述「一个 KV 页多大」。 SGLang 把同一件事放在 model_executor/pool_configurator.py， 将容量计算集中在池配置器中，下面展示其处理的几类条件：

class DefaultPoolConfigurator(MemoryPoolConfigurator):
    """Configurator for standard models: MHA, MLA, DSA, FP4.
       coeff = cell_size (bytes per token across all layers)"""

    def __init__(self, kvc: KVCacheConfigurator):

        if mambaish := mambaish_config(kvc.model_config):

                                   if kvc.layer_info.start_layer <= i < kvc.layer_info.end_layer]

        else:

        if (kvc.spec_algorithm.is_eagle() or kvc.spec_algorithm.is_standalone()) \
                and not kvc.is_draft_worker:
            eagle_draft_num_layers = kvc.spec_aux_config.eagle_draft_num_layers
            ...
            # 3) DeepSeek DSA：稀疏 attention 的 indexer 也占显存，
            #    要先从 cell_size 里减掉再按 draft 层数缩放
            if is_deepseek_dsa(kvc.model_config.hf_config):
                target_indexer_size = self._compute_dsa_indexer_cell_size(...)
                target_kv_size = self._cell_size - target_indexer_size

简化版 kv_bytes_per_token()，在真实引擎里对应这一串条件分支。 原因是「每 token 的 KV 字节」已经不是一个常数：

情况 这本账怎么变
Mamba / 线性 attention 混合层（L3.4） 那些层不产生 KV，num_layers 要按 full-attention 层数算
滑动窗口层 KV 有上界，不随上下文线性增长（SGLang 另有 swa_max_total_num_tokens）
投机解码 EAGLE（L5.5） draft 模型也要一份 KV，cell_size 要放大
DeepSeek DSA 稀疏 attention 除 KV 外还有 indexer 的显存
MLA K/V 压成一个低秩隐向量，cell_size 的结构不同
pipeline 并行 有些层的 KV 在别的 PP stage 上，本地 cell_size 可能是 0

对照两家实现的用处在这里：一个公式足以应付常见情况， 读第二份实现才能看到边界条件长什么样，以及它们为什么存在。 L3.4、L5.5、L6.2 会分别回到表中的几行。

读这本账时容易出错的地方

1. 混用标称带宽与微基准参照。 本例 649.7/864≈75.2%，实测 copy 带宽比标称值低约 24.8%。报告利用率时注明分母及读写口径；微基准适合做当前环境的参照，但不是所有 kernel 的物理上限。

2. 把「AI TOPS」当算力。 厂商宣传数字通常是稀疏（2:4）后的、 最低精度的理论峰值，与 bf16 稠密 GEMM 实际能到的数字可能差 4 倍以上。

3. 忘了 KV 按 token 计费，不按序列。 「支持 128 并发」这句话缺少条件， 必须同时说明上下文长度：在同样的显存下，54 条 4K 序列与 6 条 32K 序列大致相当。

4. 以为 decode 慢是因为算力不够。 用账本里的数字：crater 的机器平衡点是 152.7 FLOP/byte，而 4096 上下文的 decode 算术强度 batch=1 时是 1.12、 batch=32 时是 8.21，分别约为平衡点的 0.7% 和 5.4%。 这个配置离算力上限很远，加算力不改变它，除非同时增加带宽。 （这几个数在 results/crater/ledger_qwen3_1.7b_ctx4096.json 的 arithmetic_intensity 与 machine_balance_flops_per_byte 字段。）

  1. 将上下文长度翻倍。检查 KV 大小、线性层 prefill FLOP 和 attention FLOP 分别如何变化。
  2. 将 batch 从 1 改为 8。检查权重项与 KV 项是否按同样比例变化。

自测：这些数字能说明什么

模型权重能放进显存，为什么请求仍可能 OOM？

还需要 KV、激活、workspace、图捕获等空间。权重只是显存需求的一项。 应先判断是加载时失败，还是随着请求数或上下文增长才失败， 再分别检查固定开销与随请求增长的开销。

把 KV 元素字节数减半，是否意味着每步延迟减半？

不意味着。只有 KV 相关的数据量在该模型中减半；权重、其他操作和转换开销仍然存在。 先估算 KV 在总量中的比例，再检查低精度路径需要哪些额外计算。

一次 decode 的算术强度很低，是否所有 kernel 都是 memory-bound？

不是。整步汇总值把不同操作混在一起了。某些 kernel 可能受计算、同步或提交开销限制。 需要结合 L0.1 的 kernel 记录，再按操作拆分分析。
