4.4

MoE：稀疏激活的系统代价

用真实 MoE（OLMoE 64 专家/top-8）量三件事：稀疏的只有算力（5.8×），显存要按总参数量买（12.70 GiB 全驻留），带宽的稀疏性在 batch≥64 时完全消失。路由**跨层聚合会抹掉不均衡**（总体 CV 0.295 vs 逐层 1.0–1.2，每层都有专家拿 0.00%），逐层最热专家占 11.8% → 并行效率上界 13%。

实测机器 crater (RTX 5090 D, sm_120) · OLMoE-1B-7B-0924-Instruct（64 专家 / top-8）数据日期 2026-09-11前置 4.1（参数量的账）· 3.3（decode 的带宽账）· 2.7（瘦长 GEMM 的效率）

本章回答三个问题

MoE 的宣传语是"7B 的模型，1B 的计算量"。这一章把这句话拆开： 稀疏的到底是哪一项？不稀疏的那一项要付什么代价？

  1. 参数量与激活量差多少？显存按哪个买？
  2. 路由是均衡的吗？不均衡对系统意味着什么？
  3. 把 token 按专家分组做 GEMM，分组本身要多少钱？

用的是 allenai/OLMoE-1B-7B-0924-Instruct：16 层、64 个专家、top-8、 hidden 2048、专家 intermediate 1024。

一 · 稀疏的是算力，不是显存

一个专家 = 3×2048×1024 = 6,291,456 参数
一层有 64 个专家 + 1 个 router(2048×64)

                          总参数       每 token 激活       比值
MoE 部分/层           402,784,256       50,462,720     8.0×
attention/层           16,777,216       16,777,216     1.0×
每层合计               419,561,472       67,239,936     6.2×
16 层 + embedding    6,816,006,144    1,178,861,568     5.8×

6.82B 总参数，每 token 只激活 1.18B（5.8×）。

MoE 那一层的比值恰好是 64/8=8.0×——因为每 token 只走 8 个专家。 attention 是 1.0×（每 token 都要走全部 attention 权重）， 所以整层被摊薄到 6.2×，全模型 5.8×。

但：

bf16 权重显存：全部 12.70 GiB，而每 token 只用到 2.20 GiB 的量
**但那 12.70 GiB 必须全部驻留显存** —— 你不知道下一个 token 会路由到谁。

这就是 MoE 的核心系统代价：按总参数量买显存，按激活量拿算力。

一个 6.8B 的 MoE 和一个 6.8B 的稠密模型占一样多的显存， 只是算得快一些。所以 MoE 不是"省显存的技术"，恰恰相反—— 它是"在显存够的前提下，用显存换质量"的技术。

二 · 路由有多不均衡

在 16 层的 router 上挂钩子，985 个 token 的真实文本：

总选择次数 126,080，理想每专家 1,970
实际 min=945  max=3511  中位数=1906
最热/最冷 = 3.7×
最热的专家拿了 2.78%（均匀应为 1.56%）
变异系数 CV = 0.295

看起来还行——最热的只比均匀多 78%。

但这是错的看法。 逐层看：

层 最热占比 最冷占比 最热/最冷 CV
0 9.51% 0.00% 749.0× 1.032
1 10.66% 0.20% 52.5× 1.145
2 11.37% 0.01% 896.0× 1.232
3 7.97% 0.00% 628.0× 0.996
13 8.17% 0.00% 644.0× 1.106
15 9.16% 0.00% 722.0× 1.206

每一层都有专家拿到 0.00%，最热/最冷动辄几百倍，CV 在 1.0 以上。

跨层求和会把不均衡抹掉

总体 CV 0.295 vs 逐层 CV 1.0–1.2，差了 3–4 倍。

原因：不同层的热专家不是同一批，加起来互相填平了。

而系统关心的是每一层——每层各做一次 grouped GEMM， 每层的最热专家各自决定那一层的关键路径。 看总体就是看错了对象。

这是一个很容易犯的统计错误：把需要分组看的量聚合起来看。 本书里 0.3 §陷阱 1（只报一个"吞吐"）、5.1 §三（只报吞吐掩盖 TTFT/TPOT） 都是同一个形态。

用逐层的数算系统含义：

每层 985 个 token × top-8 = 7880 次选择，均匀应为每专家 123 个
实测最热的专家拿到该层的 11.8%，即 933 个 token —— 是均匀值的 7.6 倍
grouped GEMM 若各段并行执行，总时间由最大的那一段决定，
所以并行效率的上界就是 1/7.6 = 13%。

13% 是上界。 在专家并行（EP，L6.3）里，这直接变成 某张卡在算、其它卡在等。这就是 MoE 服务最难的一件事。

（注意 router_aux_loss_coef = 0.01——训练时有负载均衡的辅助损失。 即使如此，推理时在具体文本上仍然这么不均。 辅助损失优化的是训练分布上的期望，不保证任意输入上的均衡。）

三 · 分组本身的代价

一步 4096 个 token、top-8，即 32768 次专家调用：

做法 ms TFLOP/s
grouped GEMM（含排序） 1.379 99.7
　其中只排序 0.255 — （占 18.5%）
同样 FLOP 的单个大 GEMM 0.627 219.3 ← 上界

分成 64 个小 GEMM 比一个大 GEMM 慢 2.2×。

原因是每个小 GEMM 的 M 只有约 512，远小于 tensor core 喜欢的形状—— 2.7 §六 量过瘦长 GEMM 的效率远低于方阵（那次是 cuBLAS 在 decode 形状上 只有 1465 GB/s 而方阵能到 213 TFLOP/s）。

而且排序就占了 18.5%——把 token 按专家重排是纯开销，不产生任何 FLOP。

这个 2.2× 是上界，不是真实实现的代价

我这里用 python 循环逐个专家做 GEMM，每个专家一次 kernel launch。 真实实现用专门的 grouped GEMM kernel：一次 launch 处理所有分段， 每个 block 根据自己的 block id 查表决定处理哪一段。

那样能省掉 64 次 launch（L1.4：每次 2.68 µs）和大部分调度开销。 本节量的是"用最朴素的方式实现会有多贵"， 它的用处是说明为什么必须写专门的 kernel。 （同 3.3 §四 分页那次的定位。）

不均衡会让情况更糟：

均匀              max=  575 min= 462 max/mean= 1.12×
倾斜（一个专家占 20%） max= 7061 min= 357 max/mean=13.79×

分段 GEMM 若并行执行，总时间由最大的那一段决定， max/mean 就是并行效率的直接上界——和第二节算出的 7.6× / 13% 是同一件事。

四 · 稀疏性在大 batch 下消失

decode 时 batch=1 只碰 8 个专家。但 batch 一大， 不同 token 路由到不同专家，读取量迅速逼近全部。

期望被碰到的专家数 =E[1−(1−K/E)B]：

batch 期望被碰到的专家数/层 读取量 MB 占全部
1 8.0 1536.0 12.5%
4 26.5 5085.0 41.4%
16 56.4 10837.2 88.2%
64 64.0 12285.6 100.0%
256 64.0 12288.0 100.0%

batch≥64 时每层所有 64 个专家都要读一遍。

所以：MoE 的稀疏性在大 batch 下从带宽角度基本消失， 只在算力上仍然稀疏（每 token 仍只算 8 个专家）。

结合 5.1 的账： - 小 batch decode（带宽受限）：MoE 读 12.5% 的权重，看似大赚—— 但小 batch 本来就没吃满带宽，收益打折 - 大 batch decode（越过平衡点后转算力受限）：权重全读， 带宽上没有优势；但算力上仍稀疏 8 倍——这才是 MoE 的主场 - prefill（算力受限）：同上，算力稀疏是真收益

MoE 适合算力受限的场景，在小 batch decode 上优势有限。 这和"MoE 让小模型跑得像大模型"的直觉相反。

五 · 设计取舍

5.1 MoE 稀疏化的是那 75%

4.1 实测：稠密 Transformer 每层 MLP 占 75%、attention 占 25% 的参数。 MoE 只把 MLP 换成专家，attention 一个字节都不动。

这个选择很精准： - MLP 是参数大头，稀疏化它收益最大 - attention 有 KV cache 的账（3.3），稀疏化它会破坏 KV 的规整性 - MLP 是逐 token 独立的，天然可以按 token 路由；attention 跨 token，不好切

本章实测的 8.0×（MoE 层）→ 6.2×（含 attention）→ 5.8×（含 embedding） 这条衰减链，就是"只稀疏化了一部分"的直接体现。

判据：稀疏化要挑那个「占比大 + 结构上可分」的部分。 两个条件缺一不可。

5.2 负载均衡是训练与推理的目标错配

训练时用 aux loss 惩罚不均衡（本模型 router_aux_loss_coef = 0.01）， 优化的是训练分布上的期望均衡。

但推理时面对的是某一个具体的 batch，而且 batch 越小方差越大。 本章实测：即使有 aux loss，单层最热专家仍拿到 11.8%（均匀 1.56%）。

这是一个结构性的错配：训练优化期望，推理承受方差。

工程上的应对都是在推理侧打补丁： - capacity factor（超出容量的 token 直接丢弃或走 residual）——牺牲质量 - 把热专家复制到多张卡——牺牲显存 - 动态重排专家到卡的映射——牺牲复杂度

没有一个是免费的，因为问题的根源在目标函数里。

5.3 "7B 的模型，1B 的计算量"这句话的正确读法

拆成三句：

维度 是不是稀疏的 本章实测
算力 是 5.8×（每 token 只算 1.18B）
显存 否 12.70 GiB 全部要驻留
带宽 取决于 batch batch=1 读 12.5%，batch≥64 读 100%

宣传语只说了第一行。第二行决定了你能不能部署， 第三行决定了它在你的负载上到底快不快。

可带走的判断：任何"稀疏"的说法，都要问清楚稀疏的是哪一种资源。 算力、显存、带宽三者可以完全解耦——本章就是一个三者各不相同的例子。

208def section_C():

223    x = torch.randn(T, H, device="cuda", dtype=torch.bfloat16)
224
225    # 均匀路由
226    torch.manual_seed(0)
227    assign = torch.randint(0, E, (T * K,), device="cuda")
228    xs = x.repeat_interleave(K, dim=0)
229
230    def dense_all():
231        """朴素：每个 token 都过所有专家（正确但浪费 E/K 倍）"""
232        return torch.einsum("th,ehi->tei", x, w)
233
234    def grouped():
235        """按专家排序后分段做 GEMM —— 这是真实实现的形态"""
236        order = assign.argsort()
237        xs_sorted = xs[order]
238        counts = torch.bincount(assign, minlength=E)
239        outs = []
240        off = 0
241        cpu_counts = counts.tolist()
242        for e in range(E):
243            n = cpu_counts[e]
244            if n:
245                outs.append(xs_sorted[off:off + n] @ w[e])
246            off += n
247        return torch.cat(outs) if outs else None
248
249    def sort_only():
250        order = assign.argsort()
251        return xs[order]
252
253    t_grp = timeit(grouped, n=10)
254    t_sort = timeit(sort_only, n=10)
255    flops = 2 * T * K * H * I
256    print(f"\n  {'做法':<34} {'ms':>9} {'TFLOP/s':>10}")
257    print(f"  {'grouped GEMM（含排序）':<30} {t_grp:>9.3f} "
258          f"{flops / t_grp / 1e9:>10.1f}")
259    print(f"  {'其中只排序':<32} {t_sort:>9.3f} "
260          f"{'—':>10}   占 {t_sort / t_grp:.1%}")
261    ref = torch.randn(T * K, H, device="cuda", dtype=torch.bfloat16)
262    w0 = w[0]
263    t_one = timeit(lambda: ref @ w0, n=10)
264    print(f"  {'同样 FLOP 的单个大 GEMM':<30} {t_one:>9.3f} "
265          f"{flops / t_one / 1e9:>10.1f}   <- 上界")
266    print(f"\n  分成 {E} 个小 GEMM 相对一个大 GEMM 慢 {t_grp / t_one:.1f}×。")
267    print("  原因：每个小 GEMM 的 M 只有 ~{:.0f}，远小于 tensor core 喜欢的形状"
268          .format(T * K / E))
269    print("  （2.7 §六 测过：瘦长 GEMM 的效率远低于方阵）。")
270    print("  真实实现用专门的 grouped GEMM kernel（一次 launch 处理所有分段），")
271    print("  比这里的 python 循环好得多 —— 这里量的是**上界**。")
272
273    sub("不均衡会让情况更糟")
274    for name, probs in [("均匀", None), ("倾斜（一个专家占 20%）", "skew")]:
275        if probs is None:

279            m = torch.rand(T * K, device="cuda") < 0.2

281        cnt = torch.bincount(a, minlength=E)
282        print(f"  {name:<22} max={cnt.max().item():>6} "
283              f"min={cnt.min().item():>5} max/mean={cnt.max().item() / cnt.float().mean().item():>5.2f}×")
284    print("  分段 GEMM 的总时间由最大的那一段决定（若并行执行），")
285    print("  所以 max/mean 就是并行效率的直接上界。")

七 · 陷阱

  1. MoE 不省显存。 全部专家必须驻留（本章 12.70 GiB），稀疏的只有算力。
  2. 跨层聚合路由统计会抹掉不均衡（本章总体 CV 0.295 vs 逐层 1.0–1.2）。 必须逐层看。
  3. 训练有 aux loss 不代表推理均衡。期望均衡 ≠ 每个 batch 均衡。
  4. 大 batch 下 MoE 的带宽优势消失（batch≥64 读 100% 的专家）。
  5. 框架层的 python 循环量不出真实 grouped GEMM 的代价（本章 2.2× 是上界）。
  6. 排序是纯开销，本章占 grouped GEMM 的 18.5%，不产生任何 FLOP。
  7. max/mean 才是并行效率的上界，不是 max/min，也不是 CV。

八 · 自测题

1. 一个 7B 的 MoE 和一个 7B 的稠密模型，部署时有什么区别？

显存一样，算力不同。

MoE 的全部专家都要驻留显存（本章实测 6.82B → 12.70 GiB bf16）， 因为你不知道下一个 token 路由到谁。所以显存按总参数量买。

算力上 MoE 每 token 只算 1.18B（5.8×），所以同样的算力预算能跑更大的"有效模型"。

另外 MoE 多了两项稠密模型没有的开销： - 路由 + 按专家排序（本章占 grouped GEMM 的 18.5%） - 负载不均导致的并行效率损失（本章上界 13%）

所以 MoE 的正确定位是：显存换质量，不是省资源。

2. 你测出 MoE 的路由「总体最热/最冷只有 3.7 倍」，能说明负载还算均衡吗？

不能——这是聚合错误。

本章实测：总体 3.7×、CV 0.295，看着不错；但逐层最热/最冷高达 896×， CV 1.0–1.2，而且每层都有专家拿到 0.00%。

原因是不同层的热专家不是同一批，求和时互相填平了。

而系统关心的是每一层：每层各做一次 grouped GEMM， 每层的最热专家各自决定那一层的关键路径。

正确的看法是逐层统计，而且指标要用 max/mean（并行效率的上界）， 不是 max/min（受最冷那个的噪声影响）也不是 CV（对长尾不敏感）。

3. MoE 在小 batch decode 上能省多少带宽？

理论上省很多（batch=1 只碰 8/64 = 12.5% 的专家），但实际收益有限， 因为小 batch decode 本来就没吃满带宽。

而且随 batch 上升，覆盖率迅速逼近 100%： 本章实测 batch=4 → 41.4%，batch=16 → 88.2%，batch=64 → 100%。

期望覆盖数 =E[1−(1−K/E)B]，这是个饱和很快的函数。

所以：MoE 的带宽优势只存在于极小 batch，而那个区间恰好是 整体利用率最低的区间。它真正的主场是算力受限的场景 （大 batch decode、prefill），那里 5.8× 的算力稀疏是实打实的。

4. 为什么 MoE 只稀疏化 MLP，不稀疏化 attention？

三个理由，前两个本书都量过：

  1. MLP 是参数大头：4.1 实测稠密层里 MLP 占 75%、attention 占 25%。 稀疏化 MLP 收益大得多。
  2. attention 有 KV cache 的账（3.3）。稀疏化 attention 头会让 KV 的形状不规整，而 KV 是 decode 的唯一瓶颈，破坏它得不偿失。
  3. MLP 是逐 token 独立的，天然可以按 token 路由； attention 要跨 token 交互，"这个 token 走专家 A、那个走专家 B" 在 attention 里没有对应的语义。

一般判据：稀疏化要挑「占比大 + 结构上可分」的部分，两个条件缺一不可。
