4.7

VLM（三）：多模态序列、位置编码与 mask

视觉 token 插进语言序列的确切位置、占位 token 的替换过程、多模态 rope（如 mrope）的位置分配、以及 mask 在图文交错与多图场景下的形状。 同时检查训练监督、packing 和模态位置契约。

实测机器 crater (RTX 5090 D, sm_120) · torch 2.13.0+cu130 · transformers 5.17.0 · Qwen3-VL-4B-Instruct前置 4.5（patch 与 grid）· 4.6（视觉塔与 merger）· 3.1（RoPE 与 attention）· 0.4（tokenizer）

本章回答的三个问题

4.5 把图变成 patch、4.6 把 patch 变成 300 个视觉 token。这一章问它们在序列里怎么排、位置怎么给、mask 怎么算：

  1. 占位符与 embedding 替换：模板里的 <|image_pad|> 有多少个？它们的位置上被换成什么？
  2. 位置数组：MRoPE 的三个分量（t/h/w）对文本、图像、视频分别怎么算？为什么长度等于"合并后的视觉 token 数"而不是 patch 数？
  3. 变体与失败：交换图像顺序、加 padding、改 fps、增量解码各改变什么？哪些错误会报错、哪些会静默出错？

心智模型：一条序列、三种分段、三个位置分量

机制拆解

序列与占位符

构造「文本—图1—文本—图2」的对话，apply_chat_template 之后的实测：

序列长度 403
分段游程（mm_token_type_ids）：[('text', 7), ('image', 80), ('text', 5), ('image', 300), ('text', 11)]
image_grid_thw [[1, 16, 20], [1, 30, 40]] → 视觉 token 380
<|image_pad|> 出现 380 次（与视觉 token 数逐项相等）

模板片段：

<|im_start|>user
第一张：<|vision_start|><|image_pad|>×80<|vision_end|>第二张：<|vision_start|><|image_pad|>×300<|vision_end|>它们分别写了什么？<|im_end|>

三件必须对齐的事：

  • 占位符数量 = 视觉 token 数 = grid 的 h·w·t / merge²。320×240 的图给出 80 个（grid [1,16,20]，16×20/4），640×480 给出 300 个（grid [1,30,40]）。
  • <|vision_start|>/<|vision_end|> 只出现一次，中间是连续的占位符；分段（mm_token_type_ids）据此产生一段连续的 image 类型。
  • embedding 替换发生在这 380 个位置上：视觉塔输出的 380 个向量按顺序写进这些位置，其余位置用文本 embedding。数量不匹配时会在形状上直接报错。

MRoPE 位置：三个分量怎么算

Qwen3VLModel.get_rope_index 的规则（源码见下节）：

  1. 用 mm_token_type_ids 把序列切成连续的同类段；
  2. 文本段：arange(len) + current_pos，三行（t/h/w）相同；current_pos += len；
  3. 图像/视频段：取该段对应的 grid，用网格坐标生成位置；current_pos += max(h, w) / merge；
  4. mrope_position_deltas = max(position) + 1 − 序列长度。

关键在"每个 LLM token 一个位置"：get_vision_position_ids 返回的长度是 hm·wm·t（合并之后的 token 数），与 <|image_pad|> 的数量一致，而不是 patch 数。

这一点是本章实现时踩到的第一个坑：按 patch 粒度算出 320 与 1200 个位置，与实际的 80 与 300 段长度对不上，赋值时立刻报

RuntimeError: shape mismatch: value tensor of shape [3, 1543] cannot be broadcast to indexing result of shape [3, 403]

独立实现对拍。 按上述规则重写一份（my_rope_index），在同一输入上比较：

官方 position_ids (3, 1, 403)，deltas [[-350]]
独立实现逐元素相同：True（最大差 0）

前几个位置（文本—图像交界处）：

   位置   token     类型    t    h    w
      0  151644      0    0    0    0
      ...
      6    <pad>      1    6    0    0     ← 图像段起点：t/h/w 都从 current_pos 起
      7    <pad>      1    6    0    1
     ...
    397   11319      0   47   47   47     ← 第二张图之后的文本：继续单调递增
    402     198      0   52   52   52

注意图像段的 h/w 只在各自 grid 内取值（第一张图 h∈[0,8)、w∈[0,10)），t 为 0；而文本段的三个分量相同且单调递增。"三维坐标不等于把一维位置复制三遍"：文本段是复制，图像段不是。

图像顺序、padding 与增量解码

图像顺序。 交换两张图，位置区间随之改变（第一张图的 h/w 取值域由它自己的 grid 决定）：

顺序 grid 视觉段（起, 止, h₀, w₀, w_末）
A,B [[1,16,20],[1,30,40]] (7, 87, 7, 7, 16) · (89, 389, 19, 19, 38)
B,A [[1,30,40],[1,16,20]] (7, 307, 7, 7, 26) · (309, 389, 29, 29, 38)

同一张图在不同位置时的起始 current_pos 不同（7 vs 7，但第二段从 89 变成 309），所以位置值不同——图像内容相同、序列位置不同，KV cache 不能跨位置复用。

padding。 双样本批（一个 91 token、一个 13 token）的实测：

padding=right 形状 (2, 91) 有效长度 [91, 13] deltas [-70, 0]
padding=left  形状 (2, 91) 有效长度 [91, 13] deltas [-70, 0]

get_rope_index 只在有效位置上写值，padding 位置保持 0；它们必须靠 attention_mask 屏蔽，位置值本身不参与计算。两个样本的 deltas 不同（−70 vs 0），因为 deltas 是"位置最大值 +1 − 序列长度"——短样本的有效长度小、位置最大值也小，两者的差不同。deltas 是逐样本的量，不是全局常量。

增量解码。 prefill 长度 93、末位列位置 [22,22,22]，解码一步后 cache 长度 94（期望 94）。cache_position 必须接着 prefill 的末尾，而不是从 0 开始——写成 0 会让新 token 的位置与历史重叠（4.1 的 KV cache 一节有同样的反例）。

视频：时间戳把视频切成多段

对 8 帧视频，video_grid_thw 报的是 [[2, 16, 20]]（temporal 折成 2），而 get_rope_index 里有一行很关键的处理：

video_grid_thw = torch.repeat_interleave(video_grid_thw, video_grid_thw[:, 0], dim=0)
video_grid_thw[:, 0] = 1        # 每帧变成独立的一段

源码注释写明了原因：Qwen3-VL 用时间戳分隔视频段（<t1> <vision_start> <frame1> <vision_end> <t2> …），所以每一帧都是一段独立的视频段，位置从帧自己的起点开始算。实测游程正是这个形状：

fps=2: 游程 [('text', 11), ('video', 80), ('text', 8), ('video', 80), ('text', 13)]  deltas [-140]
fps=4: 游程 [('text', 11), ('video', 80), ('text', 8), ('video', 80), ('text', 13)]  deltas [-140]

每两帧之间插一段文本（时间戳标记），这就是"文本时间戳"的载体。注意本章的 fps=2 与 fps=4 在该合成视频上得到相同的游程与 deltas——两种采帧口径在这个例子里落到了相同的帧数（都折成 2 个 temporal 组），差异没有在 token 层面体现出来；要观察 fps 的影响，需要更长的视频或不同的帧数设置。

失败输入的报错与静默

输入 结果
纯文本请求（无图） 正常，无视觉段
手写 <\|image_pad\|> 文本 StopIteration（视觉段的 grid 迭代器被耗尽——模板里的图像内容缺失）
谎报 image_grid_thw（t 从 1 改成 4） RuntimeError: The size of tensor a (320) must match the size of tensor b (1280)
交换 h/w 两个位置段 不报错，数值改变，只能靠位置数组对拍发现

前两条是"友好的失败"：形状/迭代器直接暴露不一致。后一条是本章最重要的反例——位置数组错了不会影响任何形状检查，模型照样前向，只是在空间方向上的注意力被转置。它与 4.1 的"RoPE 交错配对"、4.5 的"patch 内排布"是同一类错误：形状正确、语义错误。

时间定位的受控干预：基线命中之后

原设计（8 帧、纯色方块）连基线都不命中，无法做因果解释。重做后的任务设计：

  • 32 帧、标称 4 fps，绿色方块在第 20 帧（= 5.0 s）；
  • 每一帧的角落写着自己的时间戳（t=5.00s），所以画面本身携带时间信息；
  • 提问："绿色方块出现在第几秒？只回答一个数字（例如 5.0）"；
  • 三个条件，帧内容完全不变，每次只改一条通道：
条件 改什么 模型回答 读法
基线 不改（帧按 4 fps） 5.0 ✓ 基线命中，可以进入对照
只改文本时间戳 同一批帧按 8 fps 解释 → 文本时间戳减半 5.0 没有跟随文本（若跟随应给 2.5）
只打乱 temporal 位置 反转视频段的 t 分量 5.0 位置通道的扰动没有改变答案

三条结论：

  • 基线可用：模型给出了正确的 5.0（560 ms 生成），这是做干预的前提。
  • 这个任务里答案来自画面内容：把元数据时间戳减半它不动、把 temporal 位置反转它也不动——模型读的是帧里画着的那行字。
  • 设计上有一个必须说明的混淆：刺激把时间戳写进了像素，视觉通道与元数据通道冗余，所以本实验不能回答"模型用的是哪一种时间信息"。

去掉帧内文字之后（第二轮实验）：同一批 32 帧、同样三条条件，但帧里不再写任何文字（时间只能来自元数据时间戳）：

条件 模型回答
基线（帧按 4 fps） 0.2 ✗（正确 5.0）
只改文本时间戳（按 8 fps 解释） 0.2
只打乱 temporal 位置 0.2

基线不再命中，三种条件给出同一个错误答案。两轮合起来的结论是：

  • 帧内文字让基线可用，但让干预失效（答案来自画面，改元数据动不了它）；
  • 去掉文字后任务本身失效——模型没有用元数据时间戳去定位这个事件（否则基线至少能给出接近 5.0 的值）。

第三轮：换任务类型（事件先后）。 画面里不写任何文字，红色方块在第 4 帧（1.0 s）、蓝色在第 28 帧（7.0 s），问"哪个先出现？"：

条件 模型回答 预期
基线（fps=4） 红色 ✓ 正确（红在先）
只改文本时间戳（fps=8） 红色 顺序不变，应仍为红色（有效对照）
只反转 temporal 位置 红色 若答案由位置分量决定，应翻成蓝色

基线命中，但反转位置分量未翻转答案。 原因在于因果消融的不彻底：序列中 token 的先后物理排布本身就在编码事件先后——仅翻转 RoPE 的时间维度分量（t 坐标），帧在序列上下文中的排列顺序并未改变，红块的 token 依然先于蓝块进入自注意力。该消融设计未能解耦位置编码与物理序列顺序的混杂效应。

第四轮：让"帧序"与"帧内时间戳"互相矛盾（决定性设计）。 每帧写着自己的时间戳，红块在 t=1.00 帧、蓝块在 t=7.00 帧；然后交换这两帧的顺序，于是序列上蓝块先出现、而帧内时间戳仍说红块更早：

条件 模型回答
基线（原帧序） 红色 ✓
交换帧序（蓝块排在前面） 红色
交换帧序 + 时间戳减半 红色

交换帧序后模型仍然回答"红色"——实验表明模型优先依赖画面内显式呈现的时间戳语义，而非隐式的输入物理序列顺序。

四轮合起来的完整结论：

轮次 设计 结果 说明
C2 帧内有时间戳、改元数据时间戳 答案不动 元数据时间戳不是决定因素
C3 帧内无任何时间戳 基线失效 模型不会用元数据时间戳定位事件
C4 事件先后、反转 RoPE 的 t 分量 答案不动 token 顺序本身编码先后，干预过弱
C5 帧序与帧内时间戳矛盾 跟随帧内时间戳 决定因素是画面内容

也就是说：计划里要区分的两条通道（文本时间戳与交错频率分配/时间位置），在这个模型与这组合成任务上都不是答案的决定因素；模型依画面里能读到的信息判断时间。这不是"实验没做成"，而是一个可复现的、方向明确的结论——它同时提示：要让模型真正用上元数据时间轴，训练数据里的时间信息必须与画面内容解耦或互补，否则模型会走"读画面"这条捷径。

  • 帧内文字会主导答案：有文字时基线能命中，但干预改不动它（C2）；
  • 去掉文字后模型不用元数据时间戳定位事件：基线直接失效（C3）；
  • 只翻 RoPE 的 t 分量不足以测试位置通道：token 顺序仍然携带先后信息（C4）。要真正测试，必须重排视觉 token（打乱帧序）但保留与帧绑定的时间戳文本，让"序列顺序"与"时间戳"互相矛盾，才能看出模型信哪一个。这条留作后续实验。

两个容易被忽略的点：

  • current_pos 的增量是 max(h,w)/m，不是段长 h·w/m²。 视觉段占用 h·w/m² 个 token，但位置只推进 max(h,w)/m——位置空间比 token 空间"稀疏"。这解释了为什么 deltas 是负数（位置最大值远小于序列长度）。
  • 视频的 grid_t 被强制置 1。不这样做的话，一个 video 段会被当成"一帧内 t 个时间步"来处理，时间戳分隔的语义就丢了。

工程实现 · 自己写一遍

def my_vision_positions(grid_thw, merge=2):
    """每个合并后的视觉 token 一个 (t,h,w)；长度 = (h/m)(w/m)t。"""
    out = []
    for t, h, w in grid_thw.tolist():
        gh, gw = h // merge, w // merge
        hb = torch.arange(gh).view(-1, 1).expand(gh, gw).reshape(-1)
        wb = torch.arange(gw).view(1, -1).expand(gh, gw).reshape(-1)
        tb = torch.arange(t).repeat_interleave(gh * gw)
        out.append(torch.stack([tb, hb.repeat(t), wb.repeat(t)], dim=-1))
    return torch.cat(out, dim=0)

def my_rope_index(input_ids, mm_token_type_ids, image_grid_thw=None, ...):
    groups = [(k, len(list(g))) for k, g in itertools.groupby(tt.tolist())]
    cur, parts = 0, []
    for kind, length in groups:
        if kind == 0:                       # 文本段
            parts.append(torch.arange(length).view(1, -1).expand(3, -1) + cur)
            cur += length
        else:                               # 图像/视频段
            grid = next(img_it if kind == 1 else vid_it)
            vp = my_vision_positions(grid.view(1, 3), merge).t().contiguous()
            parts.append(vp + cur)
            cur += max(int(grid[1]), int(grid[2])) // merge
    return torch.cat(parts, dim=1)

 41 # ---------------------------------------------------------------- 独立实现
 42 def my_vision_positions(grid_thw, merge=2, include_temporal=True):
 43     """独立实现：每个**合并后的视觉 token** 一个 (t,h,w)。
 44 
 45     注意不是每个 patch 一个位置：merge m×m 把 m² 个 patch 合成一个 LLM token，
 46     所以位置数组的长度是 (h/m)·(w/m)·t，与 <|image_pad|> 的数量相等。
 47     """
 48     out = []
 49     for t, h, w in grid_thw.tolist():
 50         gh, gw = h // merge, w // merge
 51         hb = torch.arange(gh).view(-1, 1).expand(gh, gw).reshape(-1)
 52         wb = torch.arange(gw).view(1, -1).expand(gh, gw).reshape(-1)
 53         if include_temporal:
 54             tb = torch.arange(t).repeat_interleave(gh * gw)
 55             out.append(torch.stack([tb, hb.repeat(t), wb.repeat(t)], dim=-1))
 56         else:
 57             out.append(torch.stack([hb, wb], dim=-1).repeat(t, 1))
 58     return torch.cat(out, dim=0)

 61 def my_rope_index(input_ids, mm_token_type_ids, image_grid_thw=None,
 62                   video_grid_thw=None, attention_mask=None, merge=2,
 63                   swap_hw=False, shuffle_temporal=False):
 64     """独立实现的 get_rope_index：文本段 arange+current_pos，视觉段用网格位置+current_pos。"""
 65     import itertools
 66     if video_grid_thw is not None:
 67         video_grid_thw = torch.repeat_interleave(video_grid_thw, video_grid_thw[:, 0], dim=0)
 68         video_grid_thw[:, 0] = 1
 69     img_it = iter(image_grid_thw) if image_grid_thw is not None else None
 70     vid_it = iter(video_grid_thw) if video_grid_thw is not None else None
 71     pos = torch.zeros(3, input_ids.shape[0], input_ids.shape[1], dtype=torch.long)
 72     deltas = []
 73     for b in range(input_ids.shape[0]):
 74         tt = mm_token_type_ids[b]
 75         ids = input_ids[b]
 76         if attention_mask is not None:
 77             tt = tt[attention_mask[b].bool()]
 78             ids = ids[attention_mask[b].bool()]
 79         groups = [(k, len(list(g))) for k, g in itertools.groupby(tt.tolist())]
 80         cur, parts = 0, []
 81         for kind, length in groups:
 82             if kind == 0:
 83                 parts.append(torch.arange(length).view(1, -1).expand(3, -1) + cur)
 84                 cur += length
 85             else:
 86                 grid = next(img_it if kind == 1 else vid_it)
 87                 vp = my_vision_positions(grid.view(1, 3), merge)          # [N,3]
 88                 vp = vp.t().contiguous()                                   # [3,N]
 89                 if swap_hw:
 90                     vp = vp[[0, 2, 1]]
 91                 if shuffle_temporal:
 92                     vp = vp.clone()
 93                     vp[0] = vp[0].flip(0)
 94                 parts.append(vp + cur)
 95                 cur += max(int(grid[1]), int(grid[2])) // merge
 96         llm = torch.cat(parts, dim=1)
 97         if attention_mask is not None:
 98             pos[:, b, attention_mask[b].bool()] = llm
 99         else:
100             pos[:, b] = llm
101         deltas.append(llm.max() + 1 - len(ids))
102     return pos, torch.tensor(deltas).unsqueeze(1)

前沿

位置编码正在从"一维序号"变成"多轴坐标"，而轴的数量由模型自己定。 本章实测 Qwen3-VL 的位置数组是 3 行（t/h/w），图像段用网格坐标、文本段用序号；视觉段之后 current_pos 只推进 max(h,w)/m——位置空间与 token 空间不再一一对应。这套设计让"同一像素在不同时间/不同位置"天然拥有不同的旋转相位，代价是任何位置数组的错误都不会在形状上暴露（交换 h/w 不报错）。

视频的时间信息有两条独立通道：文本时间戳与时间轴位置。 前者写在序列里（模型要"读到"数字），后者写在 MRoPE 里（影响注意力的相位）。本章原计划用干预实验区分两者的因果作用，但基线未命中，没有得出结论。可行的重做路径：用更长的合成视频（64 帧以上）、把标记改成高对比且唯一的图案、把答案格式约束为固定字面量、每格至少 20 个样本；这也正是 4.9/4.10 里时间轴实验要遵守的协议。

多模态序列的"位置账"直接决定缓存设计。 同一张图在不同序列位置上的位置值不同（B1 的实测），所以 KV cache 不能跨位置复用同一份视觉 KV——除非把视觉段的位置也固定下来。4.8 的 feature cache 缓存的是视觉编码器的输出（位置无关），因此可以跨位置复用；但 KV 层面的复用需要额外的位置约束。

陷阱

  1. 位置数组按"合并后的视觉 token"计数，不是 patch 数：按 patch 算会得到 320/1200，实际段长是 80/300，赋值立刻报形状错。
  2. <|image_pad|> 的数量必须等于视觉 token 数（本章 380 = 80 + 300）。
  3. 文本段的三行位置相同，图像段不同；"三维位置 = 一维复制三遍"只对文本成立。
  4. current_pos 的增量是 max(h,w)/m，不是段长；所以 deltas 是负数。
  5. 交换 h/w 位置段不报错，只能靠位置数组对拍发现（本章的 my_rope_index 就是为此写的）。
  6. deltas 是逐样本量（−70 与 0），不是全局常量。
  7. padding 位置不写位置值，必须靠 attention_mask 屏蔽；去掉 mask 会让 padding 参与注意力。
  8. cache_position 必须接在 prefill 末尾；从 0 开始会让新旧 token 位置重叠。
  9. 视频的 grid_t 在算位置时被强制置 1（时间戳分段）；不这样做会丢掉时间戳语义。
  10. 手写 <|image_pad|> 而不给图 → StopIteration；谎报 grid_thw → 形状不匹配 RuntimeError。
  11. fps 与 num_frames 的差异不一定体现在游程上（本章 fps=2 与 4 完全相同）；要在更长的视频上验证。
  12. 基线未命中的任务不能做因果干预：三次输出相同且都错时，任何"干预无效"的说法都不成立。

自测题

1. 一张 640×480 的图在序列里占多少个位置？位置值是什么？

grid 是 [1, 30, 40]（4.5 的规则），merge 2：

位置个数=hm·wm·t=302×402×1=300

位置值是该合并 token 在网格里的坐标加上 current_pos：h 从 current_pos 到 current_pos+14，w 从 current_pos 到 current_pos+19，t 恒为 0（单帧）。之后 current_pos += max(30,40)/2 = 20。

注意不是 1200 个（那是 patch 数）：一个 (h/2, w/2) 坐标对应一个 LLM token，因为 2×2 个 patch 已经被 merger 合成一个向量。

2. 为什么 `mrope_position_deltas` 是负数？

因为它比较的是"位置空间"与"token 空间"：

deltas=max(position)+1−序列长度

图像段占 h·w/m² 个 token，但位置只推进 max(h,w)/m。对 grid [1,30,40]，段长 300、位置推进 20——位置空间比 token 空间稀疏 15 倍。所以位置的最大值远小于序列长度，差值为负。

本章实测：403 token 的序列（两图 + 文本）deltas = −350；93 token（单图 + 短文本）deltas = −70。

用途：deltas 记录"最后一个位置相对序列末尾偏了多少"，增量解码时用它把 cache_position 与位置数组对齐（否则新 token 的位置会与历史错开）。

3. 你交换了位置数组的 h 与 w 两行，模型不报错、输出也"看起来正常"。怎么发现？

只能靠与参考实现逐元素对拍，因为位置数组的错误不改变任何形状：

  • 本章的做法是写一份独立实现（my_rope_index），在同一输入上与 model.model.get_rope_index 比较，要求 max diff = 0；
  • 反例注入后（vp = vp[[0, 2, 1]]），两份实现的差会集中在图像段的 h/w 两行，文本段完全一致——差异的位置直接指向错误。

这也解释了为什么"跑通一条 prompt、输出像模像样"不能作为正确性证据：位置错了，注意力在空间方向被转置，模型仍然会输出流畅的文本，只是对空间关系的判断变差（在 OCR/计数这类任务上更明显）。

同类错误：4.1 的 RoPE 交错配对（形状不变、数值错）、4.5 的 patch 内排布（形状不变、数值错）。凡是"打包/展平/坐标"的代码，都要准备一个能逐元素对拍的参考实现。

4. 视频为什么要按时间戳切成多段？这对位置数组意味着什么？

Qwen3-VL 用文本时间戳把视频切成段（源码注释：<t1> <vision_start> <frame1> <vision_end> <t2> …），每段独立。因此 get_rope_index 在开头做：

video_grid_thw = torch.repeat_interleave(video_grid_thw, video_grid_thw[:, 0], dim=0)
video_grid_thw[:, 0] = 1          # 每个 temporal 组变成一段，t=1

对位置数组的影响：

  • 一个 video 段不再是一个整体，而是被拆成 grid_t 段，每段的位置从它自己的 current_pos 重新开始；
  • 每两段之间夹着一段文本（时间戳 token），文本段会推进 current_pos；
  • 于是同一帧在不同时间戳下的位置值不同——时间信息通过"位置重新起算 + 文本时间戳"两条通道进入模型。

实测游程正是这个形状：[('text',11), ('video',80), ('text',8), ('video',80), ('text',13)]。

5. 为什么"基线未命中的任务不能做因果干预"？

因果解释要求"干预 → 输出变化"的对照有意义，前提是基线在一个正确的行为上。本章的实测：

基线 '0.2'（正确 1.0，未命中）
干预一（改文本时间戳）'0.2'
干预二（打乱 temporal 位置）'0.2'

三次相同且都错。可能的解释至少有四种：任务太难（8 帧、纯色方块）；提问/答案格式与模型输出习惯不匹配；模型根本没在用时间信息；干预的对象不是决定答案的通道。在基线失败的情况下无法区分这些解释，所以任何"某通道无效"的结论都不成立。

正确做法：先把基线做到明显高于随机（例如 ≥80% 命中），再逐一干预；每次干预只改一个通道；样本量足够（每题至少 20 个样本，报告无效样本数）。这也是 4.9/4.10 的时间轴实验要先做的事。

6. 同一张图出现在序列的不同位置，位置数组会变吗？对缓存意味着什么？

会变。位置值 = 网格坐标 + current_pos，而 current_pos 取决于前面有多少 token。实测交换两张图的顺序后，第二段的起点从 89 变成 309。

对缓存的三点含义：

  1. 视觉编码器的输出与位置无关（它只看像素），所以 4.6 的 6.74 MiB 载荷可以跨位置复用，缓存键不需要序列位置；
  2. KV cache 与位置有关：同一张图在不同位置的视觉 token 会得到不同的 RoPE 相位，KV 值不同，不能直接用"图像哈希"复用 KV；
  3. 前缀复用（5.2）在多模态请求里要小心：如果历史前缀里的图像位置发生了变化（例如前面插入了一段文本），整段 KV 都不能复用。

这也是 4.8 要把三层缓存（processor / encoder / KV）分开记录的原因。
