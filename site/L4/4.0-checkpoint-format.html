模型文件到底是什么：safetensors 字节布局与加载路径

三段结构、分片与 index、命名的三套翻译、mmap 的假带宽。三个实测发现：分片会把一层切开；config 写 tie=True 但文件里存了逐位相同的 lm_head（占 15.3%，两个独立例子）；量化模型的 embedding 根本没被量化（占 GPTQ 文件 41%），等效位宽 4.16 而非 4。

实测机器 crater (RTX 5090 D, sm_120) · Qwen3-1.7B / Qwen3-8B / Qwen2.5-1.5B AWQ+GPTQ数据日期 2026-09-10前置 0.4（词表与 tokenizer 文件）· 1.5（存储路径与 mmap）· 2.0（storage 与 stride）

本章回答三个问题

"模型权重"这个词太抽象。这一章把它落到字节上：

  1. 一个 .safetensors 文件里到底有什么？一个张量怎么在 5 个文件里被找到？
  2. config.json 里写的东西和文件里实际有的东西，是一回事吗？
  3. "4 bit 量化模型"里，哪些部分真的是 4 bit？

本章有两个"文档说 A、文件里是 B"的实测发现

两个都是我先按教科书写法写好了叙述，然后被自己的实验输出打脸， 回去查证之后改过来的。它们比格式说明本身更值得记。

一 · 三段结构

.safetensors 的格式简单到可以手写解析器：

[0..8)      u64 小端       —— JSON 头部的字节长度 N
[8..8+N)    UTF-8 JSON     —— 每个张量的 dtype / shape / data_offsets
[8+N..)     裸字节         —— 所有张量的数据，紧挨着排，没有分隔符

没有魔数、没有版本号、没有压缩、没有 pickle。 "safe" 指的就是这个：解析它不需要执行任何代码， 而 PyTorch 的 .bin/.pth 是 pickle，加载等于执行任意代码。

逐字节的拆解在 B1 就做过（labs/L4/inspect_safetensors.py， 含手算 bf16 交叉验证）。本章补其余部分。

二 · 分片与 index

Qwen3-8B 的 5 个分片：

model-00001-of-00005.safetensors   3859.9 MB  头  10552 B    83 个张量
model-00002-of-00005.safetensors   3852.6 MB  头  12232 B    99 个张量
...
合计 15.26 GiB

model.safetensors.index.json 里的 weight_map 有 399 条， 形如 张量名 -> 哪个文件：

lm_head.weight                        -> model-00005-of-00005.safetensors
model.embed_tokens.weight             -> model-00001-of-00005.safetensors
model.layers.0.input_layernorm.weight -> model-00001-of-00005.safetensors

每个分片的层号范围：

model-00001-of-00005.safetensors   layers 0..7     另有 model.embed_tokens.weight
model-00002-of-00005.safetensors   layers 7..17
model-00003-of-00005.safetensors   layers 17..27
model-00004-of-00005.safetensors   layers 27..35   另有 model.norm.weight
model-00005-of-00005.safetensors   无 layer         另有 lm_head.weight

发现一：分片会把一层切开

我原本写的是"一层不会被切开，所以可以按层流式加载"。 但看那些范围——0..7 和 7..17 是重叠的。第 7 层在哪？

第 7 层的 11 个张量分布：{'2-of-00005.safetensors': 8, '1-of-00005.safetensors': 3}
  7.self_attn.q_proj.weight               1-of-00005.safetensors
  7.self_attn.k_proj.weight               1-of-00005.safetensors
  7.self_attn.v_proj.weight               1-of-00005.safetensors
  7.self_attn.o_proj.weight               2-of-00005.safetensors
  7.mlp.gate_proj.weight                  2-of-00005.safetensors
  ...

q/k/v_proj 在第 1 个文件，其余 8 个在第 2 个。 分片纯粹按字节大小切， 不管层的边界。所以"加载完一层就能开始算"需要跨文件协调，不是免费的。

（这也解释了为什么第 5 个分片只有 1 个张量：切到最后剩下 lm_head 就单独成片。）

定位一个具体张量

model.layers.20.self_attn.q_proj.weight
  文件      model-00003-of-00005.safetensors
  dtype     BF16   shape [4096, 4096]
  数据区偏移 [1317078528, 1350632960)  共 33554432 字节
  文件内绝对偏移 = 8 + 12824 + 1317078528 = 1317091360
  校验: 16777216 元素 × 2 字节(bf16) = 33554432 ✓

8 + 头长度 + data_offsets[0] 就是文件内的绝对位置。 拿这个数去 dd 或 xxd 一跳，就能看到那个张量的第一个字节。

三 · 命名：磁盘上的名字不是引擎里的名字

Qwen3-1.7B 第 0 层在磁盘上的 11 个张量：

model.layers.0.input_layernorm.weight            [2048]           BF16
model.layers.0.mlp.down_proj.weight              [2048, 6144]     BF16
model.layers.0.mlp.gate_proj.weight              [6144, 2048]     BF16
model.layers.0.mlp.up_proj.weight                [6144, 2048]     BF16
model.layers.0.post_attention_layernorm.weight   [2048]           BF16
model.layers.0.self_attn.k_norm.weight           [128]            BF16
model.layers.0.self_attn.k_proj.weight           [1024, 2048]     BF16
model.layers.0.self_attn.o_proj.weight           [2048, 2048]     BF16
model.layers.0.self_attn.q_norm.weight           [128]            BF16
model.layers.0.self_attn.q_proj.weight           [2048, 2048]     BF16
model.layers.0.self_attn.v_proj.weight           [1024, 2048]     BF16

几件能直接读出来的事：

  • q/k/v 是三个独立张量。但 0.0 里看到 vLLM 用的是融合的 QKVParallelLinear—— 加载时把三个拼成一个大矩阵，一次 GEMM 代替三次。 所以"权重名"在磁盘、HF 实现、推理引擎里是三套，加载器负责翻译。
  • k_proj 是 [1024, 2048] 而 q_proj 是 [2048, 2048]——正好一半。 16 个 query 头、8 个 KV 头，GQA g=2（3.3 那本账的来源）。
  • q_norm / k_norm 的 shape 是 [128]，不是 [2048]。 128 是 head_dim，说明这个 RMSNorm 作用在每个头内部，不是整个 hidden。 这是 Qwen3 相对 Qwen2 新增的 QK-Norm。 自己实现时漏掉它，模型能跑但输出是错的（4.1 会逐层对齐）。

非 layer 的只有两个：model.embed_tokens.weight [151936, 2048] 和 model.norm.weight [2048]。

四 · mmap：get_tensor 到底做了什么

文件 model-00001-of-00002.safetensors  3281.8 MB
张量 model.layers.0.mlp.down_proj.weight  shape (2048, 6144)  24.0 MB
  get_tensor()             0.223 ms  ->    112.6 GB/s
  之后完整读一遍           9.167 ms  ->      2.7 GB/s
  .to('cuda')              ...              （PCIe，见 L1.3）

112.6 GB/s 是假的。 get_tensor 只建了一个 mmap 视图，没有读盘。 真正的读发生在你第一次碰那些页的时候（缺页中断），那才是 2.7 GB/s。

L1.5 踩过这个坑，测出"104 GB/s 冷加载"。这里是同一个陷阱的复现—— 给一个只建映射的操作计时，量到的是映射的开销，不是 I/O。

判据：任何声称超过存储介质物理带宽的加载速度，一定是没有真的读。

五 · 发现二：config 说绑定，文件里存了两份

tie_word_embeddings=True 的意思是输出层复用 embedding 矩阵的转置。 教科书说法是"所以 checkpoint 里只存一份"。实测：

Qwen/Qwen3-1.7B
  config: tie_word_embeddings = True
  分片数 2，合计 3875.3 MB
  lm_head.weight                   在 model-00002-of-00002.safetensors
  model.embed_tokens.weight        在 model-00001-of-00002.safetensors
  两者 shape (151936, 2048)，逐位完全相同: True
  max|diff| = 0.0
  lm_head 那份 593.5 MB，占 checkpoint 的 15.3%

Qwen/Qwen3-8B
  config: tie_word_embeddings = False
  两者 shape (151936, 4096)，逐位完全相同: False
  max|diff| = 0.9637451171875
  lm_head 那份 1187.0 MB，占 checkpoint 的 7.6%

Qwen3-1.7B 声明了绑定，却存了一份逐位相同的独立副本，占 15.3%。 （8B 那行是对照：tie=False，两者确实不同，max|diff| = 0.96。）

按 tie=True 走绑定路径的加载器不会用到那 593.5 MB——它是纯冗余。 而且它单独占了第二个分片，也就是说下载这个模型时有一整个文件是白下的。

可带走的判据

config.json 描述的是模型结构，不是文件内容。 想知道文件里有什么，只能去读文件的头。

我原本按教科书写好了"tie=True 所以没有 lm_head"， 是自己的脚本输出 has lm_head: True 才发现不对。 如果当时把那行输出当成脚本写错了随手改掉，就会把一个错误结论写进正文。 输出和预期不一致时，先假设预期错了。

六 · 量化 checkpoint

同一个位置（第 0 层 q_proj），三种格式：

未量化（Qwen3-1.7B）

model.layers.0.self_attn.q_proj.weight    [2048, 2048]   BF16    8192.0 KB

AWQ（{"bits": 4, "group_size": 128, "quant_method": "awq", "zero_point": true, "version": "gemm"}）

q_proj.bias      [1536]        F16      3.0 KB
q_proj.qweight   [1536, 192]   I32   1152.0 KB
q_proj.qzeros    [12, 192]     I32      9.0 KB
q_proj.scales    [12, 1536]    F16     36.0 KB

GPTQ（{"bits": 4, "group_size": 128, "sym": true, "desc_act": false, ...}）

q_proj.bias      [1536]        F16      3.0 KB
q_proj.g_idx     [1536]        I32      6.0 KB     <- AWQ 没有
q_proj.qweight   [192, 1536]   I32   1152.0 KB     <- 注意 shape 转置了
q_proj.qzeros    [12, 192]     I32      9.0 KB
q_proj.scales    [12, 1536]    F16     36.0 KB

一个 bf16 矩阵被拆成三到四样东西：

张量 是什么
qweight 打包好的低位整数（8 个 4-bit 权重塞进一个 int32）
scales 每组一个缩放系数，组大小 = group_size
qzeros 每组一个零点（非对称量化才有）
g_idx GPTQ 的 act-order 分组索引（哪一列属于哪一组）

AWQ 的 qweight 是 [1536, 192]，GPTQ 的是 [192, 1536]——转置的。 同样是 4 bit、同样 group_size=128，打包方向不同。 这意味着两者的 kernel 不能互换，也解释了为什么推理框架要为每种格式 写一套单独的反量化路径（4.3 会看 kernel）。

真实等效位宽

"4 bit"只是 qweight 的位宽。把 scales 和 zeros 算进去：

每 group_size=128 个权重需要 128×4 位 qweight + 1 个 fp16 scale (16 位) + 1 个 4 位零点 =532 位，即

532128=4.16 bit/权重压缩比 164.16=3.85×

两种格式算出来一样。不是 4× 而是 3.85×——group_size 越小， scales 的开销占比越大。

发现三：embedding 根本没被量化

两个文件大小差 443 MB。查下去：

Qwen2.5-1.5B-Instruct-AWQ   tie=True   总 1539.7 MB
  dtype 分布 {'I32': 392, 'F16': 339}
  lm_head.weight              [151936, 1536]  F16   445.1 MB
  model.embed_tokens.weight   [151936, 1536]  F16   445.1 MB
  model.layers.0.mlp.down_proj.qweight [8960, 192]  I32   6.6 MB

Qwen2.5-1.5B-Instruct-GPTQ-Int4   tie=True   总 1096.5 MB
  dtype 分布 {'I32': 588, 'F16': 338}
  model.embed_tokens.weight   [151936, 1536]  F16   445.1 MB
  model.layers.0.mlp.down_proj.qweight [1120, 1536] I32  6.6 MB

两件事：

  1. AWQ 那份也多存了一个 lm_head.weight（445.1 MB），尽管 tie=True。 443 MB 的差额基本就是这一项。这和第五节 Qwen3-1.7B 是同一个模式—— 两个独立的例子，说明这不是个别打包失误。
  2. embedding 表根本没有被量化，两边都是 F16 的 445.1 MB。 GPTQ 文件 1096.5 MB 里它占 41%。

所以"4 bit 模型"这个说法只描述了线性层。 词表大、模型小的时候，未量化的那部分才是大头。 一个 1.5B 模型量化到 4 bit，文件只从约 3 GB 降到 1.1 GB，不是降到 0.75 GB， 差距全在这里。

七 · 设计取舍

7.1 safetensors 为什么故意做得这么简单

对比它替代的 pickle：pickle 能存任意 Python 对象，代价是加载即执行代码。 safetensors 只能存"张量的字典"，换来三件事：

  • 安全：解析器只做 JSON 解析 + 偏移计算，没有代码执行面。
  • 可 mmap：数据区是裸字节、紧密排列、无压缩， 所以可以直接映射进地址空间，按需缺页（第四节）。 压缩或分块编码会毁掉这个性质。
  • 可被任何语言读：格式说明只有三行，写个解析器十几行。

代价是表达力：存不了自定义对象、存不了稀疏结构、存不了元数据以外的东西。 这是一个刻意的取舍——把格式的能力砍到刚好够用， 换来安全性、零拷贝和跨语言。

判据：当一个格式要被大量不受信任的来源分发时， "能表达什么"的优先级应该低于"解析它要不要承担风险"。

7.2 三套命名是必要的税

磁盘上是 q_proj/k_proj/v_proj 三个张量，引擎里是一个融合的 QKV。 为什么不直接按引擎需要的格式存？

因为引擎的最优布局依赖于并行方式。张量并行切 2 路和切 8 路， QKV 的融合方式和切分点都不同；不同引擎的融合策略也不同。 checkpoint 如果按某一种布局存，就绑死了一种部署方式。

所以磁盘上存最中性的形式（每个 Linear 一个张量，就是数学上的定义）， 由加载器在启动时翻译成当前部署需要的布局。 代价是每个引擎都要维护一张名字映射表，而且模型一出新结构就要更新。

这是"通用格式 + 适配层"的经典形态：把变化限制在适配层， 让格式保持稳定。2.0 §4.1 里 dispatcher 的正交扩展是同一个思路的另一个实例。

7.3 量化格式的碎片化是没有解决的问题

AWQ 和 GPTQ 同样是 4 bit、同样 group_size=128、 同样存 qweight/scales/qzeros，但 qweight 的 shape 是转置的。 这意味着两套反量化 kernel、两套加载路径、两套测试。

这不是谁做错了，而是没有人在早期把它标准化。 每个方法先有 kernel 再有格式，格式跟着 kernel 的最优访存布局走。 等到要互通时，双方都已经有大量部署，改不动了。

可带走的判断：当一个领域的格式由"当前最优实现"倒推出来时， 碎片化几乎是必然的。 要避免它，需要在性能还没定型的时候 就先定一个稍微次优但中立的格式——而那个时机通常没人愿意付代价。

  2. 写一个 20 行的脚本，只用标准库列出任意 safetensors 的所有张量名和形状。 这能验证你真的理解了那三段结构。
  3. 把 AWQ 的 qweight 解包出来（每个 int32 含 8 个 4-bit）， 用 scales/qzeros 还原成 fp16，和未量化模型的对应权重比余弦相似度。 这是理解量化格式最直接的一步，也是 4.3 的前置。
  4. 检查你手上其它模型的 tie_word_embeddings 与实际张量列表是否一致—— 本章找到两个不一致的例子，值得知道这有多普遍。

九 · 陷阱

  1. 给 get_tensor() 计时量不到 I/O。 它只建 mmap 视图， 真正的读在第一次访问时发生（本章 112.6 GB/s vs 2.7 GB/s）。
  2. config.json 的字段描述模型结构，不描述文件内容。 tie_word_embeddings=True 不保证文件里没有 lm_head（本章两个反例）。
  3. 分片不保证一层的张量在同一个文件里（本章 Qwen3-8B 第 7 层被切开）。
  4. "4 bit"不是等效位宽。 算上 scales/zeros 是 4.16 bit，压缩比 3.85× 不是 4×。
  5. 量化模型里 embedding 通常没被量化。 本章 GPTQ 文件里它占 41%。
  6. AWQ 与 GPTQ 的 qweight 布局是转置的，kernel 不能互换。
  7. .bin/.pth 是 pickle，加载等于执行代码。 来源不明的权重不要用这两种格式。
  8. 别用张量数量判断模型大小。 量化模型的张量数是原来的 2–3 倍 （本章 AWQ 731 个 vs 未量化 311 个），因为一个权重被拆成了三四个张量。

十 · 自测题

1. 只给你一个 .safetensors 文件和标准库，怎么列出所有张量名？

读前 8 字节当 u64 小端得到 N，再读接下来 N 字节做 JSON 解析， key 就是张量名（除了 __metadata__）。

import json, struct
with open(path, "rb") as f:
    n = struct.unpack("<Q", f.read(8))[0]
    hdr = json.loads(f.read(n))
print([k for k in hdr if k != "__metadata__"])

不需要读数据区，也不需要任何第三方库。 这就是这个格式的全部复杂度。 每个张量的 dtype、shape、data_offsets 也都在这个 JSON 里。

2. 一个模型 config 写 tie_word_embeddings=True，你数参数量时该怎么算？

按结构算：embedding 和输出层共用一份权重，只算一次。

但文件大小是另一回事——本章两个例子里，文件都额外存了一份 逐位相同的 lm_head.weight（Qwen3-1.7B 占 15.3%，AWQ 那个占 445 MB）。

所以： - 报"模型有多少参数"→ 按 config，算一份 - 报"下载要多少字节 / 加载要多少显存"→ 去读文件头，别猜

两个数字不一致是正常的，把它们混为一谈才是错。

3. 你测出某个 checkpoint 的加载速度是 100 GB/s，磁盘是 NVMe（约 7 GB/s）。哪里错了？

几乎肯定是在给 mmap 建立映射计时，而不是给真实 I/O 计时。

safe_open(...).get_tensor(name) 返回的是一个映射到文件的张量视图， 函数返回时一个字节都还没读。数据在你第一次访问那些页时才通过 缺页中断读进来。

验证方法：拿到张量之后做一次 t.float().abs().sum()（强制碰每一页）， 给这一步单独计时。本章实测 get_tensor 0.223 ms（112.6 GB/s）、 完整读一遍 9.167 ms（2.7 GB/s）。

通用判据：任何超过物理介质带宽的 I/O 速度，都是没有真的读。 （同样的道理，任何超过 DRAM 带宽的显存吞吐，都是命中了 cache——L2.0/L2.7/L3.3 反复出现。）

4. 把一个 1.5B 模型量化到 4 bit，文件应该从 3 GB 降到多少？实际是多少？为什么？

朴素预期：16/4=4×，3 GB → 0.75 GB。

实际（本章 GPTQ）：1096.5 MB。两个原因：

  1. 等效位宽是 4.16 而不是 4：每 128 个权重要额外存一个 fp16 scale 和一个 4 位零点。压缩比是 3.85× 不是 4×。
  2. embedding 没被量化：[151936, 1536] 的 F16 表占 445.1 MB， 是文件的 41%。它完全没有参与量化。

第 2 条影响大得多。词表 151936、hidden 只有 1536， embedding 本身就占原模型很大比例（4.0 §5 算过 1.7B 模型上是 18.3%）。 模型越小、词表越大，量化的实际收益越低。

5. 为什么不把 checkpoint 直接按推理引擎需要的融合布局存？

因为最优布局依赖于部署方式，而 checkpoint 要服务所有部署方式。

QKV 要不要融合、怎么融合，取决于张量并行切几路（切 2 路和切 8 路的切分点不同）、 用哪个引擎（融合策略不同）、什么硬件（对齐要求不同）。 按某一种布局存，就把模型绑死在那种部署上。

所以磁盘上存数学定义的中性形式（每个 Linear 一个张量）， 加载器在启动时翻译。代价是每个引擎维护一张名字映射表。

这是"通用格式 + 适配层"的标准形态：把变化关在适配层里，让格式保持稳定。 反例就是第七节讲的量化格式——AWQ 和 GPTQ 的布局各自跟着自己的 kernel 走， 结果谁也读不了谁的。
