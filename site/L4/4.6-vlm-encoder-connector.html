4.6

VLM（二）：视觉编码器与 connector

ViT 的前向、patch embedding 的实际张量、connector（MLP / resampler / cross-attn）把视觉特征投到语言维度的全过程；以及哪些模块被冻结、哪些参与训练。 从视觉编码器基础训练到 VLM connector/视觉塔微调。

实测机器 crater (RTX 5090 D, sm_120) · torch 2.13.0+cu130 · transformers 5.17.0 · Qwen3-VL-4B-Instruct前置 4.5（patch 与 grid）· 4.1（层实现）· 3.1（attention 的账）· 0.2（roofline）

本章回答的三个问题

4.5 把像素变成了 pixel_values 与 grid_thw。这一章接着问：这些 patch 经过哪些层、在哪里被压缩成视觉 token、又以什么形式进入语言模型。

  1. 视觉塔里有哪些阶段？ patch embedding、24 个 block、merger、DeepStack 注入点各自的形状、维度与 norm 位置。
  2. connector 是什么？ 为什么不能概括成"一个 linear"？它的输入输出长度与维度怎么算？
  3. 分段成本与缓存载荷是什么？ processor / ViT / merger / LLM prefill 各占多少，batch 与分辨率怎么影响它们？要被缓存的特征有多少字节？

心智模型：塔内的两条出口——主 merger 与 DeepStack

机制拆解

视觉塔的配置与阶段

Qwen3-VL-4B-Instruct 的 vision_config：

depth                  24          hidden_size        1024
intermediate_size      4096        num_heads          16
out_hidden_size        2560        spatial_merge_size 2
patch_size             16          temporal_patch_size 2
num_position_embeddings 2304       deepstack_visual_indexes [5, 11, 17]
  • out_hidden_size = 2560 就是 LLM 的 hidden：视觉塔的输出维度必须与语言模型的嵌入维度对齐，这个映射由 merger 完成。
  • spatial_merge_size = 2：2×2 个 patch（每个 1024 维）拼成 1 个视觉 token（2560 维）。所以 token 数是 patch 数的 1/4。
  • deepstack_visual_indexes = [5, 11, 17]：除最后一层外，另有三个中间层被送进 LLM。

对一张 640×480 的图（4.5 的规则给出 grid [1,30,40] = 1200 patch），逐层挂 hook 的记录：

patch_embed (1200, 1024) bfloat16 14.04 2.344 MiB
block_0 (1200, 1024) bfloat16 21.99 2.344 MiB
block_5 (1200, 1024) bfloat16 13.70 2.344 MiB

三件可以直接读出来的事：

  • block_23 的 L2 是 patch_embed 的 66 倍（924.5 vs 14.0）。塔内是残差结构，激活幅度逐层累积；这也是为什么后面必须有 norm/merger 把它压回可用范围。
  • merger 是"降长度、升维度"：1200×1024 → 300×2560。总元素数从 1.23M 降到 0.77M（-37%），但序列长度少了 4×，这对后面 LLM 的 attention（O(S2)）是决定性的。
  • tower 返回三个字段：last_hidden_state（1200×1024，merger 之前的序列）、pooler_output（merger 之后的 300×2560）、deepstack_features（3 个 300×2560）。

connector 不是"一个 linear"

Qwen3VLVisionPatchMerger（modeling_qwen3_vl.py:174-187）的结构：

merger.norm        LayerNorm(1024)       ← use_postshuffle_norm=False 时作用在拼接前
merger.linear_fc1  Linear(4096, 4096)
merger.act_fn      GELU
merger.linear_fc2  Linear(2560, 4096)

手写实现（同权重、同调用顺序）：

z = merger.norm(x)                       # x: [1200, 1024]
z = z.reshape(-1, 4 * 1024)              # 2×2 拼接 → [300, 4096]
y = merger.linear_fc2(merger.act_fn(merger.linear_fc1(z)))     # [300, 2560]

对拍结果：max|diff| = 0.000e+00。

DeepStack 的 merger 用的是另一种 norm 位置（use_postshuffle_norm=True）：先拼成 4096 维再 LayerNorm。手写同样得到 0.000e+00。

把顺序写错会怎样？两类 merger 的 norm 维度不同（1024 vs 4096），把主 merger 当成 post-shuffle 直接在形状上报错：

RuntimeError: Given normalized_shape=[1024], expected input with shape [*, 1024], but got ...

"connector 是一个 linear"这个说法错得有多远？ 用一个 4096→2560 的单层 linear 代替整条 merger（把 4 个 patch 直接拼起来过 linear），与官方输出的相对差是 1.021——量级等于 1，说明两者完全不相关。connector 里有 LayerNorm、两层线性与 GELU，省掉任何一步都不是"近似"，而是另一个函数。

分段成本：贵的是 24 层编码，不是压缩

固定一张 640×480 的底图，扫分辨率与 batch（先做一次预热以排除首次调用的冷启动）：

分辨率 batch 视觉 token processor ViT（含 merger） 其中 merger LLM prefill 完整请求 峰值
320×240 1 80 1.03 ms 13.11 ms 0.09 ms 10.28 ms 23.39 ms 8548 MiB
320×240 8 640 3.71 18.04 0.20 42.30 60.34 8868
640×480 1 300 1.46 9.90 0.12 22.79 32.69 8657
640×480 8 2400 10.45 58.97 0.68 115.57 174.54 9724
1280×720 1 880 4.57 25.68 0.27 48.67 74.35 8963
1280×720 8 7040 34.84 207.95 1.78 349.48 557.42 11999

四条结论：

  • merger 只占 ViT 的 1.2%（0.12 / 9.90 ms）。把 1200 个 patch 压成 300 个 token 几乎不花时间——成本在 24 层 Transformer 里。优化 connector 的收益远小于优化塔本身（层数、分辨率、或干脆少送 patch）。
  • 各阶段对 batch 的扩展性不同：B=1→8 时 processor 7.2×、ViT 6.0×、LLM 5.1×、完整 5.3×。processor 是 CPU 且逐图独立（接近线性），ViT 与 LLM 在 batch 增大后受算力与显存带宽限制。
  • 分辨率的影响比 batch 更陡：1280×720 的视觉 token 是 320×240 的 11 倍（880 vs 80），完整请求从 23 ms 涨到 74 ms（B=1）。视觉 token 直接进入 LLM 的 prefill 长度。
  • 峰值显存随 batch 增长：9724 MiB（640×480, B=8）→ 11999 MiB（1280×720, B=8）。权重约 8.4 GiB 是底，其余是激活。

DeepStack：三个注入点的载荷

DeepStack 让第 5/11/17 层的特征也进入 LLM（modeling_qwen3_vl.py:847-851 的 _deepstack_process 按 layer_idx 逐层相加）。单张 640×480 图的完整视觉载荷：

载荷 形状 dtype 字节
deepstack_0_layer5 (300, 2560) bfloat16 1.465 MiB
deepstack_1_layer11 (300, 2560) bfloat16 1.465 MiB
deepstack_2_layer17 (300, 2560) bfloat16 1.465 MiB
main_merger (1200, 1024) bfloat16 2.344 MiB
合计 6.738 MiB

注意最后一行：主出口 2.344 MiB 是 merger 之前的序列（1200×1024），而三个 DeepStack 载荷是 merger 之后的（300×2560）。缓存设计（4.8）必须把这四个张量当成一个整体，键里要包含模型、processor 配置、图像内容与分辨率——少一个张量就不是同一份特征。

分析性消融。 把三个 DeepStack merger 的输出置零（其余保持官方配置），在 24 张合成图（OCR 与计数各 12 张，贪心生成 12 token）上比对：

条件 严格命中（答案子串） 归一化命中（去连字符/大小写） 平均生成耗时
原模型 24/24 24/24 93 ms
去掉 DeepStack 注入 22/24 24/24 80 ms

两点必须说清楚：

  • 严格判据下的 2 个"失败"都是格式差异：模型答 TOKEN-04AB7、TOKEN-0?AB7（少一个连字符），去掉非字母数字后两条件都是 24/24。判据本身会制造假失败——报告质量差异时必须同时给出严格与归一化两套数字，否则会把格式差异当成能力退化。
  • 耗时降 14%（93 → 80 ms），与"注入的计算量很小"一致；但"去掉注入仍能作答"不等于"DeepStack 没有作用"：这个任务集（合成 OCR/计数、12 个样本对）太窄，测不出精细的视觉理解差异。

结论：在这个任务集上，置零注入带来的质量差异为 0（归一化后都是 24/24），只有 14% 的耗时下降。因此能说的只有"这类合成 OCR/计数任务不需要 DeepStack"；要判断它的收益需要更细的任务（需要多层视觉细节的组合推理）与更大的样本量——不能反过来声称"DeepStack 没有作用"。修改后的模型不能称为官方配置。

两个实现细节值得记：

  • 两类 merger 的 use_postshuffle_norm 不同：主体是 False（norm 作用在 1024 维的 patch 上，拼接后不再 norm），DeepStack 是 True（先拼成 4096 维再 norm）。写反了会在形状上直接报错，属于"友好的错误"。
  • 注入是"加在视觉位置上"，不是替换或拼接：_deepstack_process 用 visual_pos_masks 选出视觉 token 的位置做加法，文本位置的 hidden 不受影响。这意味着 4.8 的缓存可以只存视觉位置的张量。

工程实现 · 自己写一遍

labs/L4/vision_connector.py：

# 逐层特征清单：给关键模块挂 hook
handles = [vis.patch_embed.register_forward_hook(hook("patch_embed"))]
handles += [vis.blocks[i].register_forward_hook(hook(f"block_{i}")) for i in (0,5,11,17,23)]
handles += [vis.merger.register_forward_hook(hook("merger"))]
handles += [m.register_forward_hook(hook(f"deepstack_merger_{j}"))
            for j, m in enumerate(vis.deepstack_merger_list)]
with torch.no_grad():
    vout = vis(pixel_values, grid_thw=image_grid_thw)

# 手写 merger（两种 norm 位置）
def my_merger_plain(x, m):          # use_postshuffle_norm=False
    return m.linear_fc2(m.act_fn(m.linear_fc1(m.norm(x).reshape(-1, 4 * x.shape[-1]))))
def my_merger_post(x, m):           # use_postshuffle_norm=True
    z = x.reshape(-1, 4 * x.shape[-1])
    return m.linear_fc2(m.act_fn(m.linear_fc1(m.norm(z))))

# 分析性消融：把 DeepStack 注入置零（其余保持官方）
originals = {id(m): m.forward for m in vis.deepstack_merger_list}
def zero_forward(self, x):
    return torch.zeros_like(originals[id(self)](x))

前沿

视觉 token 的数量与长度正在成为服务的第一约束。 本章实测 1280×720 的图给出 880 个视觉 token（B=1），完整请求 74 ms；B=8 时 7040 token、557 ms、峰值 12.0 GiB。视觉 token 与文本 token 在 LLM 里是同一种序列，因此图像的分辨率选择直接与文本上下文竞争——这解释了 4.5 的预算曲线为什么在服务端是准入控制问题，而不只是预处理参数。

DeepStack 这类"多层特征注入"把缓存载荷从 1 个张量变成 4 个。 主出口是 merger 前的 1200×1024，三个注入点是 merger 后的 300×2560，合起来 6.74 MiB/图（bf16）。它们的序列长度、注入层、dtype 都不同，缓存键必须覆盖模型 revision、processor 配置、图像内容与分辨率（4.8 会给出实现）。"视觉特征是一个向量"这个直觉在这里失效了。

压缩发生在最后一步，但代价在整个塔。 merger 只占 ViT 时间的 1.2%，24 层编码占了 98.8%。想省视觉成本，三个杠杆的优先级是：减少送进塔的 patch（分辨率/裁剪）> 用更小的塔或更少的层 > 优化 connector。这个次序与"connector 是瓶颈"的直觉相反，值得在设计阶段先用分段计时确认。

陷阱

  1. connector 不是"一个 linear"。 用 4096→2560 的单层 linear 代替官方 merger，输出相对差 1.021（完全不相关）。
  2. 两类 merger 的 norm 位置不同：主体 use_postshuffle_norm=False（先 norm 1024，再拼 4096）、DeepStack True（先拼 4096，再 norm）。写反了会报形状错。
  3. merger 是"降长度、升维度"：1200×1024 → 300×2560。token 数少 4×，单 token 维度升到 2560。
  4. merger 只占 ViT 的 1.2%（0.12/9.90 ms）。优化它几乎没有收益。
  5. 视觉塔的激活幅度会涨到很大（block_23 的 L2 = 924.5，是 patch_embed 的 66 倍）；不要用前几层的尺度去估计后面。
  6. tower 的返回值里有三个字段（last_hidden_state、pooler_output、deepstack_features），主出口在 pooler_output 而不是 last_hidden_state。
  7. DeepStack 的载荷序列长度与主出口不同（300 vs 1200），缓存不能用一个张量概括。
  8. 注入是"在视觉位置上相加"，不是替换；文本位置的 hidden 不受影响。
  9. 首次调用的冷启动会污染计时：本章第一次未预热时 ViT 显示 238 ms，预热后是 9.9 ms（24×）。分段计时必须先预热。
  10. 峰值显存随 batch 增长（9724 → 11999 MiB），权重（≈8.4 GiB）只是底。
  11. batch 的扩展性各阶段不同（processor 7.2×、ViT 6.0×、LLM 5.1×，B=1→8），不能用"线性"估容量。
  12. 合成 6 张图上的 6/6 vs 5/6 不是质量结论；样本量、任务集与评测协议都不足以下结论。

自测题

1. 一张 640×480 的图，视觉塔的输入序列多长、输出多长、维度怎么变？

4.5 的规则给出 grid [1, 30, 40] → patch 数 30×40=1200。

  • 输入：1200 个 patch，每个 1024 维（patch_size=16 切块后有 256 个像素 × 3 通道 × temporal 2 = 1536，经 patch_embed 的卷积投到 1024 维，见 A 段 pixel_values (1200,1536)）。
  • 塔内：24 层，宽度不变（1200×1024），L2 从 14.0 涨到 924.5。
  • 输出：
  • last_hidden_state = (1200, 1024)：merger 之前；
  • pooler_output = (300, 2560)：merger 之后，1200/22=300，维度投到 LLM 的 2560；
  • deepstack_features = 3 × (300, 2560)：第 5/11/17 层的 merger 输出。

所以"视觉 token 数 = 300"说的是进入 LLM 的长度；塔内部的序列长度是 1200，两者差 4 倍。

2. 为什么说"connector 是一个 linear"是错的？用本章的数字说明。

本章的 merger（modeling_qwen3_vl.py:174-187）是 LayerNorm → Linear(4096,4096) → GELU → Linear(4096,2560)。用它和"把 4 个 patch 拼起来过一个 4096→2560 linear"对照，同一个随机输入上：

  • 官方 vs 手写完整 merger：max|diff| = 0.000e+00（同权重同顺序，逐位一致）；
  • 官方 vs 单个 linear：相对差 1.021（量级 1 = 完全不相关）。

也就是说，单 linear 连"近似"都算不上。原因有三：LayerNorm 决定了每个 token 的尺度；两层线性加 GELU 提供了非线性与更大的容量；4096→4096→2560 的瓶颈结构与直接 4096→2560 是不同的映射。

另外别忘了 norm 的位置：主体 merger 的 norm 作用在拼接前的 1024 维上，DeepStack 的 norm 作用在拼接后的 4096 维上。把它当成一个 linear，连"输入维度"这件事都说不清。

3. 视觉塔里最该优化的是哪一步？用分段计时回答。

按"占 ViT 时间比例"排序（640×480、B=1）：

阶段 时间 占 ViT
24 层编码 ≈9.78 ms 98.8%
merger 0.12 ms 1.2%

所以优化的次序是：

  1. 少送 patch（降分辨率、裁剪、区域选择）——直接减少塔内的序列长度与 LLM 的 token 数，两个阶段同时受益；
  2. 换更小/更浅的塔——1.2% 之外的 98.8% 全在这里；
  3. 优化 connector——上限只有 1.2%。

这与"connector 是瓶颈"的直觉相反。注意这个结论依赖分辨率与 batch：如果将来 connector 变复杂（例如多层融合），它的占比会变，必须先测再优化。

4. DeepStack 给缓存带来了什么额外要求？

它把"一份视觉特征"变成四个形状不同的张量：

deepstack_0_layer5   (300, 2560)   1.465 MiB   ← merger 之后
deepstack_1_layer11  (300, 2560)   1.465 MiB
deepstack_2_layer17  (300, 2560)   1.465 MiB
main_merger          (1200, 1024)  2.344 MiB   ← merger 之前
合计 6.738 MiB（640×480，bf16）

三个要求：

  1. 必须整组存取：只缓存主出口会让 LLM 前 3 层缺少注入，输出与官方配置不同。
  2. 键要包含模型与配置：deepstack_visual_indexes、out_hidden_size、merge 大小都在 config 里；换 revision 就是另一份载荷。
  3. 不能按"视觉 token 数 × 维度"估算字节：主出口的序列长度是 1200 而不是 300，按 300 估算会少算 5.4 MiB。

这三点直接决定 4.8 的 feature cache 的键与容量预算。

5. 你测出第一次调用的 ViT 用了 238 ms，预热后是 9.9 ms。差在哪？

第一次调用包含了一次性成本，且这些成本不属于稳态：

  • CUDA kernel 的首次装载/JIT（Triton/FlashInfer 的 autotune、cuBLAS 的 kernel 选择）；
  • 分配器首次扩张：显存池从零开始建立；
  • 权重首次被读取（从 CPU/磁盘到 GPU 的拷贝若还没发生）；
  • Python/框架的首次路径（缓存、懒初始化）。

本章的 B 段因此在计时前跑了一次完整的 model(**inputs) 预热，第一格从 238 ms 降到 13.1 ms（320×240 的 ViT）。

工程含义：任何分段计时都必须先预热，并明确"预热几次"；服务容量规划关心的是稳态，冷启动是另一个单独的指标（8.7）。

6. 为什么"注入"用加法而不是拼接或替换？这对缓存意味着什么？

_deepstack_process（modeling_qwen3_vl.py:861）在视觉位置上把 DeepStack 特征加到 hidden states 上，文本位置不动。用加法的好处是：

  • 序列长度不变：拼接会让 LLM 的序列变长（300→600），attention 成本与 KV cache 都要跟着变；
  • 与残差结构同构：LLM 本来就是"层层相加"的结构，把视觉中间层当成一路残差注入是最自然的做法；
  • 掩码即可控制：用 visual_pos_masks 选出位置，实现上不需要重排序列。

对缓存的要求：只要缓存视觉位置的张量（不用管文本位置），但四个张量的序列长度不同（主出口 1200、注入点 300），所以"按位置切片"这件事必须分别处理——这也是 4.8 缓存实现里最容易错的地方。
