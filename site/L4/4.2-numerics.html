数值系统与确定性

分析浮点格式、舍入和累加顺序，解释结果为何会随运行配置或 batch 改变。 同时分析梯度、优化器更新和混合精度的误差来源。

实测机器 crater (RTX 5090 D, sm_120) · torch 2.13.0+cu130 · vLLM 0.29.0 · Qwen3-1.7B前置 0.0b（反向与梯度精度）· 2.0（dispatch 与 dtype）· 2.3（归约顺序）· 4.1（逐层对齐）

本章回答的三个问题

  1. bf16、fp16、fp8 各自能表示哪些数？"4 bit 更省、精度更差"这类说法在数值上怎么量化？
  2. 同一条 prompt、温度 0、同一个模型，为什么两次可能给出不同答案？这种差异有多大？
  3. allow_tf32、use_deterministic_algorithms、batch_invariant 三个开关各管什么？它们能保证到哪一级？

本章的所有误差都用同一组定义，避免"一个小数点"式的含糊：

平均绝对误差=mean|xi−ri|最大绝对误差=max|xi−ri|

最大相对误差=max|xi−ri|max|ri|误差比=最大绝对误差平均绝对误差

其中 r 是 FP64 参照。误差比接近 1 说明误差均匀铺开，远大于 1 说明个别项主导。

机制拆解

格式解剖：把每个编码都枚举出来

"fp16 有 5 位指数、10 位尾数"只是位宽的事实。把每个格式的全部位模式解码一遍，才能看到它真正能表示什么：

格式 位 零 次正规 正规 inf nan binade 数 每 binade 编码 最大有限 最小正规 最小次正规
bfloat16 16 2 254 65024 2 254 254 256 3.3895e+38 1.175e-38 9.18e-41
float16 16 2 2046 61440 2 2046 30 2048 65504 6.104e-05 5.96e-08
float8_e4m3fn 8 2 14 238 0 2 14 16 448 0.01562 0.001953
float8_e5m2 8 2 6 240 2 6 30 8 57344 6.104e-05 1.526e-05
float32 32 — — — 1 — — — 3.4028e+38 1.175e-38 —

这张表里有几条不看枚举看不出来的事：

  • 次正规的个数等于尾数空间大小的一半：bf16 有 254 个次正规编码（每个符号 127 个），fp16 有 2046 个。它们填满了 2最小指数 到最小正规之间的空隙，所以 fp16 的下界能到 5.96e-08 而不是 6.1e-05。
  • fp8_e4m3fn 没有 inf 编码（fn = finite only）：指数全 1 且尾数非全 0 的编码是 nan，指数全 1 且尾数全 0 这个位置在 fn 变体里也不代表 inf。溢出只能落到 nan，不会像 e5m2 那样变成 inf。
  • 同是 8 位，e4m3 与 e5m2 的取舍完全不同：e4m3 每 binade 16 个编码、上限 448；e5m2 每 binade 8 个编码、上限 57344。前者要精度，后者要范围。
  • bf16 与 fp32 的正规指数范围一致（都是 8 位指数），但 bf16 每 binade 只有 256 个编码，分辨率差 216 倍。动态范围相同不代表能表示同一个数。

舍入：ties-to-even、截断与上溢

bf16 在 1.0 附近的相邻间距是 eps = 2^-7 = 0.0078125。取两个可表示数的中点 1.00390625：

bf16 在 1.0 附近：相邻间距 0.0078125（= eps），可表示 1 / 1.0078125
两数中点 1.00390625 舍入到 1

落在正中间时舍向"尾数最低位为偶"的那个，这就是 round-to-nearest-even（ties-to-even）。它与直接截断低位的差别不小：

20 万个随机 fp32：截断低 16 位与库转换不同的比例 0.4999，截断的最大绝对误差 0.031237

一半的输入会因截断得到不同的 bf16 值。截断总是偏向零，这种系统性偏差在长链计算里会累积成另一种结果，所以"反正 bf16 精度低，截断和舍入差不多"是错的。

从 fp32 到各格式的边界行为：

         输入           fp16           bf16     fp8_e4m3fn       fp8_e5m2
        65504          65504          65536            448            inf
        65519          65504          65536            448            inf
        65520            inf          65536            448            inf
        1e5              inf          99840            448            inf
    6.104e-05    6.10352e-05    6.10352e-05              0    6.10352e-05
     5.96e-08    5.96046e-08    5.96046e-08              0              0
        1e-08              0    1.00117e-08              0              0

三个可直接用于判断的观察：

  • 65519 在 fp16 下还是 65504，65520 就变成 inf：65520 正好是 65504 与 65536 的中点，ties-to-even 把它推到尾数为偶的 65536，而 65536 超出 fp16 上限 → 上溢。接近上限的值不是"被截断"，而是"被舍入后溢出"。
  • 65504 在 bf16 下是 65536：bf16 的动态范围装得下，但分辨率装不下这个数。
  • 最小次正规 fp16 的位模式是 0000000000000001，而 1e-8 的位模式是全零——后者直接下溢成 0。梯度里的小量就是这样消失的。

两点结论：

  • 两条路径的误差量级不同，不能互相替代。 在这组数据上，bf16 的累加误差（8.8e-03）比输入误差（2.5e-05）大两个数量级；fp16 反过来，输入误差（3.0e-06）与累加误差（3.3e-05）相当。想知道"该升哪个"，必须分开测。
  • 误差比在 21–26 之间：误差不是均匀铺开的，个别项主导最大值。只报平均误差会低估尾部风险。

抵消：Kahan 也会失效

[1e8, 1, -1e8] float64    顺序 1        Kahan 1        Neumaier 1
[1e8, 1, -1e8] float32    顺序 0        Kahan 0        Neumaier 1
[1e8, 1, -1e8] bfloat16   顺序 0        Kahan 0        Neumaier 1
[1e8, 1, -1e8] float16    顺序 nan      Kahan nan      Neumaier nan

精确值是 1.0。fp32 的顺序累加把它吞掉（1e8 的 ulp 是 8，加 1 等于没加）。Kahan 补偿在这里也救不回来——补偿量本身又是一个 1 量级的数，它同样被 1e8 吞掉。Neumaier 变体按量级决定把补偿归到哪一侧，才把 1.0 拿回来。fp16 的情况更直接：1e8 溢出成 inf，inf + (-inf) = nan。

batch 不变性：200 条输入的配对测量

设计一个干净的实验：200 条长度 7–22 token 的输入，全部左 padding 到同一长度（保证最后一个位置始终是真实 token），逐条前向得到 batch=1 参照，再按 batch=2/8/32 分批前向。数学上 causal attention 下每一条的输出与同批里还有谁无关。

batch=1   前向 200 次  逐位相同 200/200  翻转  0  max|diff| 0.000e+00
batch=2   前向 100 次  逐位相同   0/200  翻转  0  max|diff| 6.875e-01
batch=8   前向  25 次  逐位相同   0/200  翻转  1  max|diff| 3.750e-01
batch=32  前向   7 次  逐位相同   0/200  翻转  0  max|diff| 7.188e-01

变长批次把"padding 量"和"batch 组成"两个变量混在了一起，所以另做一组统一长度的对照：所有输入都左 padding 到长度 22，唯一变化的是 batch 维大小。

统一长度 22，batch=1   逐位相同 200/200  翻转  0  max|diff| 0.000e+00
统一长度 22，batch=2   逐位相同   0/200  翻转  1  max|diff| 7.266e-01
统一长度 22，batch=8   逐位相同   0/200  翻转  2  max|diff| 6.250e-01
统一长度 22，batch=32  逐位相同   0/200  翻转  3  max|diff| 6.250e-01

对照的结论很干净：batch=1 时逐位相同（padding 本身不改变结果），而从 batch=2 起就没有一条逐位相同。 差异不来自 padding，来自 GEMM 形状改变后归约切分的变化。

位次也有影响：把 32 条样本轮换到批次的 32 个位次，逐位相同 0/32，max|diff| 在 0.156–0.719 之间。也就是说，同一条请求的结果取决于它在批次里的位置——而这个位置由调度器决定，用户控制不了。

决策翻转与 margin。 200 条参照的 top-2 margin 分布：最小 0.0、p10 0.25、中位数 1.875、最大 7.0。统一长度 batch=32 下翻转 3 条：

样本 58：参照 margin 0.0（两个 logit 都是 20.625）
样本 78：参照 margin 0.25
样本 197：参照 margin 0.125

样本 58 是精确并列——两个 token 的 logit 完全相同，谁"应该"赢没有数值依据。比翻转计数更稳的判据是"决策余量与偏差量级"：统一长度 batch=32 下观测最大偏差 0.625，200 条中有 36 条（18%）的 margin 小于这个偏差；变长批次下是 44 条（22%）。这些样本的 top-1 无法由该配置保证，即使本次没有翻转。

贪心生成 8 条样本 × 16 token，batch=1 与 batch=8 的序列完全相同（8/8）。这些 prompt 的下一个 token 余量都很大，16 步内没有被末位差推翻；"这一次没变"不等于"不会变"。

第 0.0b 与 2.3 讨论过前两行的区别，这里给出它们的实测范围：

tf32_off   5 次逐位相同 True  最大差 0.000e+00

三种配置各自都是位级确定的。

TF32 与 deterministic 在 bf16 模型上是空操作：切换开关后 logits 差 0.0。原因不同：TF32 只作用于 fp32 矩阵乘，模型权重是 bf16，这条路径根本不参与；deterministic 只改原子类算子的实现，而这个模型的前向没有走到那类算子。想看 TF32 的真实作用，要直接测 fp32 矩阵乘：

allow_tf32=False  fp32 2048³ 矩阵乘 vs FP64：max|diff| 1.332e-04  相对最大 5.923e-07
allow_tf32=True   fp32 2048³ 矩阵乘 vs FP64：max|diff| 7.006e-02  相对最大 3.116e-04

同样的 fp32 输入，开启 TF32 后相对误差放大约 500 倍，到 1e-3 量级。

torch.compile 与 eager 逐元素不同。 同一输入、同一权重，编译后的 logits 与 eager 的最大差 0.1875，argmax 不变；编译产物本身在 4 次重跑里逐位相同（冷编译 10.8 s）。这又是一类"确定但不等于 eager"的差异：compile 改了算子的实现与归约顺序，属于前面第 ③ 层的调度差异。

第一处差异定位到层

把 batch=1（长度 L=20，只跑第 0 行）与 batch=32（同一长度、同一批输入）的每一层隐藏状态用 forward hook 抓下来比较：

第一处非零差异在第 0 层
逐层最大差 6.25e-02（第 0 层）→ 32.0（第 27 层）
隐藏状态量级 11.44 → 2304.00

差异从第 0 层就出现——那一层就有 RMSNorm 的归约与 QKV 的 GEMM，两者的切分都会随 batch 变。此后每层都在自己的归约上再引入 1 个末位量级的扰动，同时批间差异沿残差累积，28 层后从 0.0625 长到 32.0，放大约 500 倍。这正是"末位差如何变成决策翻转"的放大机制。

把 HF 的 logits 与 vLLM 引擎的输出对拍（5 条 prompt 的第一个生成 token，top-5）：

vllm top-1 12095 / hf 12095  相同 True  top-5 logprob 最大差 0.0872
vllm top-1   279 / hf   279  相同 True  top-5 logprob 最大差 0.0674
...
5 条 prompt 的 top-5 logprob 最大绝对差 0.1474

argmax 5/5 一致，logprob 的绝对差到 0.147（单位是 nat，约 15% 的概率比）。这是跨引擎同精度的实际容差范围，也是 5.5 的投机解码接受率与 7.6 的 RL 策略同步在跨引擎对拍时必须设定的量级——用"逐位相同"要求它是做不到的。

vLLM 0.29 提供了引擎侧的 batch 不变模式（VLLM_BATCH_INVARIANT=1）。同一进程配置下，把 8 条 prompt 的"逐条 generate"与"32 条同批 generate"对照：

模式 贪心 token 相同 top-1 logprob 最大绝对差
默认 8/8 0.064349
VLLM_BATCH_INVARIANT=1 8/8 0.000000

开启后单条与同批解码的 logprob 完全一致。这直接说明第 ③ 层的差异是可消除的，代价是改走一套专用的批量无关 kernel；同时它也让上表第一行的 0.064 有了归因：那不是模型或精度问题，就是 batch 形状带来的。

工程实现 · 源码解析：开关落在哪段代码上

量化与累加精度的分离

"输入什么格式、用什么累加"在框架里是两个独立参数。torch.matmul 走 cuBLAS 时，fp16/bf16 输入的累加器固定是 fp32（tensor core 的累加器精度），这是硬件层面的分工，不是可选项。要在实验里把两者分开，只能像本章的 A3 那样手工构造：量化输入后用 FP64 算乘法与累加，或者保持 FP64 输入而逐步用低精度累加。

TF32 的作用点

torch.backends.cuda.matmul.allow_tf32 控制 cuBLAS 是否允许把 fp32 输入降到 TF32（19 位：1 符号 + 8 指数 + 10 尾数）参与 tensor core 运算。它只作用于 fp32 路径——torch.backends.cudnn.allow_tf32 是卷积侧的同类开关。本章实测：bf16 模型上切换它没有任何差异。

deterministic 的作用点

torch.use_deterministic_algorithms(True) 让有多种实现的算子选确定的那一个，典型是 scatter_add、index_put 这类涉及原子加的算子。它不改变 GEMM 的 tile 选择，因此对 batch 不变性无效（0.0b 的梯度对比与 2.0c 的流竞态里都出现过这个区别）。

引擎的 batch 不变模式

vLLM 0.29 的实现集中在 vllm/model_executor/determinism/batch_invariant.py：

:592  mm_batch_invariant            Triton 持久化 matmul，固定每行的归约切分
:646  bmm_batch_invariant
:754  mean_batch_invariant          固定切分的均值
:831  rms_norm_batch_invariant
:908  enable_batch_invariant_mode() 在 dispatcher 上替换算子实现
:1001 init_batch_invariance()       由 envs.VLLM_BATCH_INVARIANT 触发

分派点有三处：layers/linear.py:234 与 layers/layernorm.py:101 在开关打开时改走上面这些实现；v1/attention/selector.py:166 把 use_batch_invariant 传给 attention 后端选择，:229 要求后端声明 supports_batch_invariance()，不支持就直接报错。开关本身定义在 vllm/envs.py:92（默认 False）。

设计取舍

为什么默认不做 batch 不变。 批量无关要求"每一行的归约切分与 batch 无关"，而 GEMM 的最优 tile 本来就依赖形状：batch=1 与 batch=64 的最优切分完全不同（2.7 实测过 cuBLAS 在瘦长与方阵上的差异）。强制统一切分等于在大多数形状上使用次优 kernel，代价是实打实的吞吐。默认路径优先考虑性能，需要确定性时显式选择并测量开销。

为什么取消"温度 0 就复现"的承诺更省事。 复现需要"同样的输入"且"同样的 batch 构成"，后者由调度器决定。前两节的数据说明：即使同批里的其他请求与目标请求的 token 完全无关，目标请求的 logits 也会变。服务端要给出逐字可复现的承诺，就得同时固定批构成与 kernel 选择——这通常不是用户能控制的条件。

为什么格式选择是分层的。 一个现代模型里同时存在好几种精度：权重存 bf16/fp8/int4（4.0、4.3），矩阵乘累加用 fp32，RMSNorm 归约升 fp32，softmax 的 max/sum 用 fp32（3.1），梯度累加用 fp32（L7）。规律是存储用低精度、归约用高精度：存储量正比于参数量与序列长度，是带宽瓶颈；归约误差随项数累积，必须高精度。A3 的分层测量正是这条规律的数据支撑。

def seq_acc(v, dt):                            # 逐项顺序累加，模拟低精度累加器

③ 配对 batch 不变性。 参照与对照必须逐条配对，否则"batch 化了以后整体变差"这种说法会把位置效应混进来：

def batched(idx_list):                 # 左 padding + attention_mask

前沿

batch 不变从"做不到"变成了"有代价可选项"。 本章实测的 VLLM_BATCH_INVARIANT=1 把单条与同批解码的 logprob 差压到 0.000000，做法是给 matmul、RMSNorm、均值、log_softmax 各写一套固定归约切分的 Triton kernel（determinism/batch_invariant.py），并要求 attention 后端声明 supports_batch_invariance()。这条路线对推理服务的意义是把"温度 0 可复现"从一个营销说法变成一个可以开启的配置；代价是放弃 cuBLAS/Triton autotune 的形状自适应，在长序列与大 batch 上通常有明显吞吐损失。本章只测了解码路径的数值效果，没有测它的吞吐代价——那属于 5.1/5.4 的范围，也和 5.5 投机解码的验证方式直接相关。

误差预算正在从"单算子"走向"整条链"。 本章的逐层数据（第 0 层 0.0625 → 第 27 层 32.0）说明末位差会被残差结构放大两个多数量级。这意味着对长链任务（多轮对话、agent 循环、RL rollout）做数值可复现承诺时，单算子的容差没有意义，必须给出端到端的分布级判据——例如 logprob 的最大绝对差、或者"决策余量小于偏差量级"的样本比例。本章给出的 0.147 nat 跨引擎 logprob 差就是这类判据的一个样本。

低精度格式正在把"误差"变成"必须显式建模的对象"。 fp8 训练与 MXFP4/NVFP4 这类块缩放格式把 scale 自身也纳入数值系统（4.3 会展开）。本章 A3 的分层方法（输入格式、乘法、累加分开测）就是这类格式必须做的第一步；只报一个端到端 PPL 无法区分是格式选错还是累加精度不够。

陷阱

  1. bf16 与 fp32 的动态范围相同，只差分辨率。别把两者的差异描述成"范围小"。
  2. fp16 的 65504 上限是训练不用它的主因，不是精度；接近上限的值可能被舍入后溢出成 inf（65520 → inf）。
  3. 把负零、次正规与上溢边界混为一谈。 fp16 的最小次正规是 5.96e-08（位模式 ...0001），1e-8 直接变成 0。
  4. 截断不等于舍入。 fp32→bf16 的截断与库的 RNE 在约 50% 的输入上不同，且偏差方向固定。
  5. "GPU 计算不确定"多数时候是错的。 同配置跑 5 次逐位相同。真正的问题通常是"不同形状走了不同 kernel"。
  6. use_deterministic_algorithms 解决不了 batch 不变性。 两者是不同的现象；在 bf16 模型上这个开关可能完全不生效。
  7. allow_tf32 只影响 fp32 矩阵乘。 bf16/fp16 模型上切换它没有任何效果，别用它来解释观察到的不一致。
  8. 温度 0 不等于可复现。 复现还要求 batch 构成相同，而那由调度器决定；同批里的其他请求会改变本请求的 logits。
  9. "这一次没翻"不是证据。 本次 8×16 token 的贪心序列完全一致，但 18% 的样本 margin 小于观测偏差。
  10. 误差比远大于 1 时，平均误差不能代表尾部。 本章 A3 的误差比在 21–26 之间。
  11. Kahan 补偿不是万能的。 量级悬殊的抵消里补偿量自己会被吞掉，需要 Neumaier 变体。
  12. 跨引擎对拍不能用"逐位相同"当门槛。 HF 与 vLLM 的 top-5 logprob 差到 0.147 nat；该按分布级容差判断。

自测题

1. 用户报告"同样的 prompt、temperature=0，两次得到不同答案"。你怎么排查？

先分清三种可能，各自有独立的判据：

  • 真·非确定（同配置跑两次就不同）：查原子加类算子（scatter_add、index_put），用 use_deterministic_algorithms(True) 验证。本章实测同配置 5 次逐位相同，说明这个模型的前向没有走到那类算子。
  • batch 不变性（同 batch 相同，不同 batch 不同）：本章的主题。两次请求落在不同大小或构成的批次里，走了不同的 GEMM 归约切分。判据是"逐条前向 vs 同批前向"的 logprob 差，实测 0.064 nat。
  • 后端/编译差异：eager 与 torch.compile 之间差 0.1875。

排查顺序：先在同一配置下重复（排除真·非确定），再对照不同 batch 构成，最后对照不同后端。三者都不是"随机"，只是确定的行为不是你想要的。

2. 为什么训练用 bf16 而不是尾数更多的 fp16？用本章的数字说明。

fp16 尾数多 3 位（10 vs 7），分辨率确实更好：在 1.0 附近 bf16 的间距是 0.0078125，fp16 是约 0.00098。但它只有 5 位指数，最大 65504、最小正规 6.1e-05。

本章的两组数字：1e-08 在 fp16 下位模式变成全零（下溢成 0），bf16 保住了 1.00117e-08；[1e8, 1, -1e8] 在 fp16 下直接 inf，连表示都做不到，而在 bf16 下至少能得到 0（Neumaier 能拿回 1.0）。训练时梯度的动态范围很宽，fp16 必须配 loss scaling：乘大数、反向后除回、动态调整、检测溢出、跳过坏 step。

bf16 与 fp32 的正规指数范围接近（都是 8 位指数），通常不需要同样的缩放；但这不是精度更好，而是范围够用。fp32 累加也只能降低进一步的误差，不能恢复低精度存储时丢掉的信息——本章 A3 的"输入误差"一栏就是这部分不可恢复的损失。

3. 一条输入在 batch=1 与 batch=32 下 logits 最大差 0.625，argmax 只有 3/200 翻转。这算"稳定"吗？

不能只看翻转计数。本章的判据是决策余量：

  • 200 条参照的 top-2 margin 分布：p10 0.25、中位数 1.875。
  • 有 36 条（18%）的 margin 小于观测到的最大偏差 0.625。

对这些样本，top-1 只差一个比偏差更小的余量，翻转与否取决于具体 batch 构成，而不是"稳定"。本次只翻转 3 条是因为 200 条里 margin 极小的样本本来就少（margin < 0.25 的只有 6 条）。

样本 58 是最好的例子：两个候选的 logit 完全相等（都是 20.625，margin 0.0），谁赢没有任何数值依据。

要给出"稳定"的结论，应报"margin 小于偏差量级的样本比例"，而不是单次运行的翻转率。

4. 你在 bf16 模型上切换 `allow_tf32`，发现结果完全一样，于是认为 TF32 没影响。错在哪？

错在把"开关对这个模型无效"当成了"开关对整个系统无效"。

allow_tf32 只控制 fp32 矩阵乘是否降精度。模型权重是 bf16 时，矩阵乘走的是 bf16 tensor core 路径，TF32 根本不参与，所以逐层最大差是 0.0。

要测 TF32 的作用，必须直接构造 fp32 矩阵乘：本章用 2048³ 的 fp32 矩阵乘对 FP64 参照，关闭时相对误差 5.923e-07，开启时 3.116e-04，放大约 500 倍。

推广：任何开关都要先确认它作用于哪条代码路径，再设计实验。use_deterministic_algorithms 同理——它只改原子类算子的实现，本模型没有触发。

5. 写出把"输入格式误差"与"累加精度误差"分开测量的最小代码，并说明为什么不能只测端到端误差。

关键在于固定一端、只让另一端降精度：

def quant(v, dt):                 # 输入量化，乘法与累加留在 FP64
    return v.float().to(dt).float().double()

def seq_acc(v, dt):               # FP64 输入，低精度累加器
    acc = torch.zeros((), dtype=dt)
    for i in range(v.numel()):
        acc = (acc + v[i].to(dt)).to(dt)
    return acc.double()

只用端到端误差无法判断该升哪一端。本章的数据：bf16 的累加误差（8.8e-03）比输入误差（2.5e-05）大两个数量级，说明在这个规模上换更宽的累加器收益更大；fp16 则两端相当（输入 3.0e-06、累加 3.3e-05）。如果只看端到端数值，这两个结论都得不出来。

另外注意误差的分布：本章 A3 的误差比（最大/平均）在 21–26 之间，说明最大误差由少数项主导，只报平均会低估风险。

6. 同一条输入在 batch=1 与 batch=32 下第 0 层就有差异。为什么不是"层数越深越不准"，而是"从第一层就不同"？

因为第 0 层里就已经有随形状变化的归约：RMSNorm 的平方和与 QKV 的 GEMM 都会按 batch 大小选择切分方式。batch 从 1 变到 32，GEMM 的 tile 配置与归约树深度随之改变，累加顺序不同，末位结果就不同——这是浮点加法不满足结合律的直接后果，不是误差累积到后面才出现。

后面的层做的是放大：每层自己再引入一个末位量级的扰动，同时残差结构把已有的差异一起传递下去。本章实测 28 层内从 0.0625 放大到 32.0。所以"差异出现在第 0 层"与"差异很大"是两个事实，前者说明来源是形状相关的 kernel 选择，后者说明残差链的放大作用。

反过来，如果要定位到具体算子，可以在第 0 层内部继续细分子模块（attention 前的 norm、QKV、attention、MLP），把第一处非零差异压到一个具体归约上。
