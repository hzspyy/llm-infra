4.9

语音输入：从波形到识别与理解

覆盖 ASR（把语音转成文字）与音频理解，走通采样、分帧、声学编码和流式状态；比较转写级联与直接音频理解。 覆盖独立 ASR 基础训练、现代模型 SFT 与蒸馏资料。

实测机器 crater (RTX 5090 D, sm_120) · torch 2.13.0+cu130 · transformers 5.17.0 · Qwen3-ASR-0.6B前置 0.4（tokenizer 与序列）· 4.1（层实现）· 5.1（prefill/decode）· 2.0c（卷积与下采样）

本章回答的三个问题

  1. 波形怎么变成序列？ 16 kHz PCM 如何分帧、算 log-mel、归一化，长度怎么从采样数传到帧数再传到音频 token。
  2. 分块输入与流式输出是什么关系？ 每次喂累计音频、缓存增量、伪流式 transcript 三者的区别在哪。
  3. 边界在哪里？ 错误采样率、空音频、截断、静音、超长各会得到什么？

本章只完成了问题 1 与问题 3 的实测（A 段）。第二个问题和质量评测（B/C 段）没有完成，原因是一个具体的加载失败（见"陷阱"第 1 条）——正文把已测到的部分与未测到的部分分开写。

心智模型：波形 → 帧 → 特征 → 序列，长度一路在变

机制拆解

前端配置：Whisper 式的固定 30 秒窗口

Qwen/Qwen3-ASR-0.6B 的 preprocessor_config.json：

{"chunk_length": 30, "dither": 0.0, "feature_extractor_type": "WhisperFeatureExtractor",
 "feature_size": 128, "hop_length": 160, "n_fft": 400, "n_samples": 480000,
 "nb_max_frames": 3000, "padding_side": "right", "padding_value": 0.0,
 "processor_class": "Qwen3ASRProcessor", "return_attention_mask": true}

三件事直接决定长度：

  • hop = 160：16 kHz 下每帧 10 ms。帧数 = ceil(采样数 / 160)。
  • n_samples = 480000 = 30 s：输入先被补零或截断到 30 秒。
  • nb_max_frames = 3000：特征张量固定 (batch, 128, 3000)——形状不携带长度信息。

长度传播与采样级 mask

3 条真实语音（LibriSpeech dummy，16 kHz 单声道，用 soundfile 解码 FLAC）：

样本 采样 时长 有效帧（ceil(n/160)） 官方特征 mask 有效采样
ls_dummy_0 93,680 5.86 s 586 (1, 128, 3000) 93,680
ls_dummy_1 77,040 4.82 s 482 (1, 128, 3000) 77,040
ls_dummy_2 199,760 12.48 s 1,249 (1, 128, 3000) 199,760

特征形状永远是 (1, 128, 3000)，长度在 attention_mask 里，而且是采样级的。 这一点很容易搞错：

  • mask 的值是"有效采样数"（93,680），不是帧数（586），也不是 0/1 序列的长度；
  • mask 的上限是 480,000：60 秒音频的 mask 是 480000（30 秒），31 秒输入的 mask 也是 480000——超过 30 秒的部分被丢掉；
  • 因为 return_attention_mask: true，缺了它就只能拿到一个固定形状的特征张量，"有多长"完全看不出来。

边界与非法输入

输入 结果
采样率 8 kHz（不重采样） ValueError: The model corresponding to this feature extractor ... was trained using a sampling rate of 16000
重采样到 16 kHz 正常 (1, 128, 3000)
空音频（0 采样） 不报错，特征 (1,128,3000)，mask = 0
纯静音 1 s 不报错，mask = 16000（静音与语音没有区别）
截断到 0.2 s 不报错，mask = 3200
60 s / 31 s 不报错，mask = 480000（截断到 30 s）

两条值得记：

  • 采样率不匹配会直接报错（不会自动重采样）。本章手写了一条线性插值重采样来演示"正确做法"，但生产代码应使用高质量的 polyphase 重采样（torchaudio.functional.resample）。
  • 静音、空音频、截断都不报错：它们只体现在 mask 上（0 / 16000 / 3200）。这意味着下游必须自己用 mask 判断"有没有内容"，否则会把静音当成一段正常语音送进 encoder。

与官方特征的对拍：做到一半

手写前端：线性重采样 → Hann 窗 STFT（n_fft=400、hop=160、center=True）→ mel 滤波器组（128 × 80/128 三角）→ log10 → Whisper 归一化：

def whisper_norm(m):                 # Whisper 的官方归一化
    m = m.clamp_min(m.max() - 8.0)   # 抬底 8 个数量级
    return (m + 4.0) / 4.0           # 压到约 [-1, 1]

与 proc.feature_extractor 的输出在有效帧上逐元素比较：

样本 原始 log10 mel 的最大差 HTK mel + 归一化 Slaney mel + Slaney 归一化 再换对称 Hann 窗
ls_dummy_0 11.204 1.670 0.863 0.813
ls_dummy_1 11.270 1.613 1.185 1.054
ls_dummy_2 11.321 1.721 0.847 0.848

三步改进把差从 ~11.2 一路降到 ~0.8：① 归一化（11.2 → 1.67）；② 换成 Whisper 真正使用的 Slaney mel 刻度 + Slaney 滤波器归一化（1.67 → 0.86）——这是本章第一版实现的主要错误（用了 HTK 的 2595·log10(1+f/700) 与未归一化的三角滤波器）；③ 把 Hann 窗从周期（periodic）改成对称（1.0 → 0.81）。另外做了补零与不补零的对照：两者结果完全一致，说明差异不是"先补零到 30 秒"造成的。

两个条件同时满足才逐元素一致：① 换成官方的 mel_filter_bank（Slaney 刻度 + Slaney 归一化的正确实现）；② Hann 窗必须用周期窗（torch.hann_window(n_fft)，torch 的默认）而不是对称窗。

自写 Slaney 滤波器组 + 周期窗 0.85–1.19

工程结论：坐标系与长度账自己算，特征值直接用官方 feature_extractor——这与 4.5 的图像前端结论完全一致（那里也是几何全对、像素有残差）。

用替代模型跑 B/C（whisper-small）

由于 Qwen3-ASR-0.6B 在当前环境依赖不齐备，B/C 阶段采用结构对照模型 openai/whisper-small 进行实验验证。所有测量数字均归属于结构对照模型，不可直接外推为 Qwen3-ASR 的指标。

B：分块重放与稳定前缀。 取一条 23.32 s 的 LibriSpeech test-clean 语音，按 1/2/4 s 的前缀依次送入（每次都是"累计音频"）：

chunk 重新编码次数 总耗时 相对整段 末块等于整段 稳定前缀达到一半的时刻
整段 1 468 ms 1.0× — —
1 s 23 2752 ms 5.9× True 13.0 s
2 s 11 1294 ms 2.8× False（末块只有 22 s） 14.0 s
4 s 5 596 ms 1.3× False（末块只有 20 s） 16.0 s

三条结论：

  • 代价是平方级的重编码：1 s 分块把总耗时推到整段的 5.9 倍——因为每次都在重新编码之前的所有音频。这就是"切片重放"，不是增量流式。
  • "末块等于整段"是判断流式实现的一个陷阱：2 s/4 s 的末块只覆盖到 22 s/20 s，自然不等于整段；要看的是末块的截取范围，而不是字符串相等。
  • 中间前缀长期不稳定：23 s 的音频，稳定前缀直到 13–16 s 才覆盖到最终转写的一半。"逐 token 返回"或"末块正确"都不能证明中间字幕稳定——这正是 B 段要区分的三件事（输入 chunk、计算 chunk、输出 chunk）。

C：整段 vs 分块的 WER 与成本。 LibriSpeech test-clean 前 24 条（1.94–23.32 s，合计 190.7 s）：

方式 WER RTF 峰值显存
batch=1 整段 0.029 0.045 557 MiB
batch=4 整段 0.026 0.022 741 MiB
batch=1 每 5 s 切一段 0.467 0.032 —
  • 整段的 WER 约 3%（24 条、511 词），batch=4 把 RTF 从 0.045 降到 0.022（2.1×），峰值只涨 33%。
  • 朴素切片把 WER 推到 0.467（16 倍恶化）：切在词中间、丢失上下文、边界处产生重复/漏字。"能流式"与"切片后还准"是两件事——要么用带状态的流式解码（保留上下文与注意力窗口），要么接受明显更差的错误率。
  • 样例里可以看到典型差异：整段 THE ENGLISH FORWARDED TO… 被切成 The English voted to…（漏字/替换），这类错误在 WER 上体现为 0.02，而整体切片的 0.467 主要来自边界。

主例仍不可用：Qwen/Qwen3-ASR-0.6B 的 config 声明 Qwen3ASRForConditionalGeneration，但权重键带 thinker. 前缀且模块命名结构性不同（thinker.audio_tower.proj1/proj2 vs 类期望的 audio_tower.layers.N.fc1/fc2），逐一试过 HF 与 Omni 三类与一次键重映射都失败；本机包索引只提供 transformers ≤5.17.0（transformers>5.17.0 无解），所以这条路靠升级也走不通。

工程实现 · 源码解析：processor 的两个入口

Qwen3ASRProcessor.__call__(text, audio, output_labels=False, ...)
    必须同时给文本；audio 可以是 ndarray / Tensor / 它们的列表
Qwen3ASRProcessor.feature_extractor(raw_speech, sampling_rate=..., ...)
    WhisperFeatureExtractor：固定补到 30 s / 3000 帧，返回 attention_mask（采样级）

两个调用约定上的坑（都踩到了）：

  • __call__ 需要 text 参数：只传 audio 会报 missing 1 required positional argument: 'text'。做纯特征提取要用 feature_extractor 而不是 processor。
  • feature_extractor 的关键字是 raw_speech，不是 audio：写 audio= 会报 missing 1 required positional argument: 'raw_speech'。

另外，本环境的 datasets 的 Audio 特征不可用（缺少 torchcodec/ffmpeg），所以本章改为直接读 parquet 的字节 + soundfile 解码 FLAC。这是一条通用的绕行方案：datasets 的解码链路断了，但数据本身（parquet 里的 bytes）还是拿得到的。

def resample_linear(x, sr_in, sr_out):          # 演示用；生产用 polyphase
    n_out = int(round(len(x) * sr_out / sr_in))
    return np.interp(np.arange(n_out) / sr_out,
                     np.arange(len(x)) / sr_in, x).astype(np.float32)

def frame_signal(x, frame_len, hop):            # 分帧与边界补齐
    if len(x) < frame_len:
        return np.pad(x, (0, frame_len - len(x))).reshape(1, -1), 1, frame_len - len(x)
    n = 1 + (len(x) - frame_len) // hop
    idx = np.arange(frame_len)[None, :] + hop * np.arange(n)[:, None]
    return x[idx], n, 0

def logmel(x, sr=16000, n_fft=400, hop=160, n_mels=128):
    spec = torch.stft(torch.from_numpy(x).float(), n_fft, hop_length=hop,
                      window=torch.hann_window(n_fft), center=True,
                      return_complex=True).abs() ** 2
    return torch.log10((mel_filterbank(sr, n_fft, n_mels, 0, 8000) @ spec).clamp_min(1e-10))

采样 93680 → 补零到 480000 → 帧 ceil(93680/160)=586 → 特征 (1,128,3000)

 50 def resample_linear(x, sr_in, sr_out):
 51     """线性插值重采样（手写，用于验证重采样规则）。"""

 60 def frame_signal(x, frame_len, hop):
 61     """分帧：返回 [n_frames, frame_len] 与有效长度。"""
 62     if len(x) < frame_len:
 63         pad = frame_len - len(x)
 64         x = np.pad(x, (0, pad))
 65         return x.reshape(1, -1), 1, pad
 66     n = 1 + (len(x) - frame_len) // hop
 67     idx = np.arange(frame_len)[None, :] + hop * np.arange(n)[:, None]
 68     return x[idx], n, 0

 71 def logmel(x, sr=16000, n_fft=400, hop=160, n_mels=80, fmin=0, fmax=8000,
 72            mel_scale="htk", periodic=True, fb_override=None):
 73     """手写 log-mel：Hann 窗 → rfft → mel 滤波器组 → log10。"""
 74     win = torch.hann_window(n_fft, periodic=periodic)
 75     spec = torch.stft(torch.from_numpy(x).float(), n_fft, hop_length=hop,
 76                       win_length=n_fft, window=win, center=True,
 77                       return_complex=True).abs() ** 2
 78     fb = fb_override if fb_override is not None else \
 79         mel_filterbank(sr, n_fft, n_mels, fmin, fmax, scale=mel_scale)
 80     m = fb @ spec
 81     return torch.log10(m.clamp_min(1e-10))

 99 def hz_to_mel_slaney(f):
100     """Slaney mel：1 kHz 以下线性、以上对数（Whisper/transformers 用的就是它）。"""
101     f = np.asarray(f, dtype=np.float64)
102     f_sp = 200.0 / 3.0                      # 200/3 Hz 一个 mel
103     mels = f / f_sp
104     min_log_hz = 1000.0
105     min_log_mel = min_log_hz / f_sp
106     logstep = np.log(6.4) / 27.0
107     if np.ndim(f) == 0:
108         if f >= min_log_hz:
109             return min_log_mel + np.log(f / min_log_hz) / logstep
110         return mels
111     hi = f >= min_log_hz
112     mels[hi] = min_log_mel + np.log(f[hi] / min_log_hz) / logstep
113     return mels

116 def mel_to_hz_slaney(m):
117     m = np.asarray(m, dtype=np.float64)
118     f_sp = 200.0 / 3.0
119     min_log_hz = 1000.0
120     min_log_mel = min_log_hz / f_sp
121     logstep = np.log(6.4) / 27.0
122     hz = f_sp * m
123     hi = m >= min_log_mel
124     hz[hi] = min_log_hz * np.exp(logstep * (m[hi] - min_log_mel))
125     return hz

128 def mel_filterbank(sr, n_fft, n_mels, fmin, fmax, scale="htk"):
129     """三角滤波器组；scale="slaney" 时用 Slaney mel 刻度并做 Slaney 归一化。"""
130     n_freqs = n_fft // 2 + 1
131     if scale == "slaney":
132         mels = np.linspace(hz_to_mel_slaney(fmin), hz_to_mel_slaney(fmax), n_mels + 2)
133         hz = mel_to_hz_slaney(mels)
134     else:
135         mels = np.linspace(hz_to_mel(fmin), hz_to_mel(fmax), n_mels + 2)
136         hz = mel_to_hz(mels)
137     bins = np.floor((n_fft + 1) * hz / sr).astype(int)
138     fb = np.zeros((n_mels, n_freqs), dtype=np.float32)
139     for i in range(n_mels):
140         l, c, r = bins[i], bins[i + 1], bins[i + 2]
141         if c == l:
142             c = l + 1
143         if r == c:
144             r = c + 1
145         for k in range(l, min(c, n_freqs)):
146             fb[i, k] = (k - l) / (c - l)
147         for k in range(c, min(r, n_freqs)):
148             fb[i, k] = (r - k) / (r - c)
149         if scale == "slaney":
150             fb[i] *= 2.0 / (hz[i + 2] - hz[i])       # Slaney 归一化
151     return torch.from_numpy(fb)

452         for i, rw in enumerate(r, 1):
453             prev, dp[0] = dp[0], i

前沿

流式 ASR 的难点不在模型，而在"三个 chunk 不是同一个对象"。 输入 chunk（用户怎样把音频切块送来）、模型计算 chunk（每次前向实际编码了多长的音频）、网络输出 chunk（SSE 逐个返回的 token）三者相互独立。本章 B 段原计划用"chunk=1/2/4 s、feed step=20/100 ms、unfixed tokens=0/5/10"来分别记录，没有跑起来；但机制层面的判据可以写清楚：

  • 重新编码累计音频：每次把 audio[:t] 整段送进模型 → 不是流式，只是"切片重放"，计算量随块数平方增长；
  • 缓存增量编码：保留 encoder 的卷积状态/注意力 KV，只编码新到的帧 → 真正的流式；
  • 伪流式 transcript：后端逐 token 返回，但输入仍是整段 → 延迟看起来像流式，实际首字延迟等于整段处理时间。

"最后转写正确"不能证明中间字幕稳定——这也是为什么需要"稳定前缀"这个指标（连续两次输出中不再变化的部分）。

音频前端的固定窗口是长音频的第一道硬边界。 30 秒上限意味着更长的音频必须先切段；切在哪里（静音处、能量谷、还是固定网格）直接影响词错误率。本章实测 60 s 与 31 s 输入的 mask 都是 480000（30 s），超出的部分静默丢弃——下游若不做分段，就会丢内容且不会收到任何错误。

自测题

1. 一段 5.86 秒的 16 kHz 单声道音频，经过 Qwen3-ASR 的前端后，特征张量多大？有效长度记在哪？
  • 采样数 93,680；前端把信号补零到 n_samples = 480000（30 s）；
  • 特征张量固定 (1, 128, 3000)：128 个 mel 通道 × 3000 帧（nb_max_frames）；
  • 有效长度不在形状里，而在 attention_mask 中，取值是有效采样数 93,680（不是帧数）。

要算帧数：ceil(93680 / 160) = 586（hop=160 对应 10 ms）。

三个数字（93,680 采样、586 帧、3000 帧张量）指的是不同的东西："有多长"必须用 mask 表达，否则下游只能看到 30 秒的固定窗口。

2. 60 秒的音频送进去会发生什么？

静默截断到 30 秒：attention_mask 的有效采样数是 480,000，超出的 480,000 个采样（30 s）被丢掉，而且不报错。

本章实测：60 s（5,620,800 采样，因为原音频被拼了 60 次）与 31 s（496,000 采样）的 mask 都是 480000。同时特征张量仍是 (1, 128, 3000)。

工程含义：长音频必须在外层分段。分段策略（静音切分、能量谷、固定网格）会直接影响 WER；而且要在分段时记录每段的时间偏移，否则无法把转写映射回时间轴（4.11 的音画对齐需要这个映射）。

3. 你的音频是 8 kHz 采样率，直接送进去会怎样？

ValueError: The model corresponding to this feature extractor: WhisperFeatureExtractor was trained using a sampling rate of 16000 ...——不会自动重采样。

这是"友好失败"：采样率是显式参数，前端用它做校验。如果它不校验而按 8 kHz 解释，你会得到一段被当作 16 kHz 的音频（时长和音高都错），而模型仍会输出一段"看起来合理"的转写——那才是最难查的错误。

正确做法：先用 torchaudio.functional.resample(x, 8000, 16000) 做高质量重采样（polyphase），不要用本章演示用的线性插值（它只用于说明长度关系，会有明显混叠）。

4. 静音音频会报错吗？如果不会，下游要注意什么？

不会。1 秒静音的实测结果是：特征 (1, 128, 3000)、attention_mask 有效采样数 16,000，与一段正常语音的处理路径完全相同。空音频（0 采样）也只是 mask = 0。

下游要注意三点：

  1. 必须用 mask 判断"有没有内容"，否则会把静音送进 encoder 并生成幻觉文本（ASR 模型对静音的典型失败模式就是输出训练集里的高频句）；
  2. mask=0 的请求应该短路（不调 encoder），这既是正确性问题也是成本问题；
  3. 静音检测（VAD）与 mask 是两件事：前者是内容判断（能量/模型），后者是长度表达。两者都做才不会漏。
5. 为什么"逐 token 返回"不等于"支持实时输入"？

因为它们是两个不同的对象：

层 对象 判据
输入 用户怎样把音频送进来 能否持续上传（流式 socket/WS），而不是"上传完再等"
计算 每次前向编码了多少音频 是重编码累计音频（切片重放）还是只编码增量（缓存 encoder 状态）
输出 token 怎么返回 SSE 逐 token 返回很容易做到，与输入无关

本章的 B 段原计划把三者分开记录（chunk=1/2/4 s、feed step=20/100 ms、unfixed tokens=0/5/10），但没有跑起来。判据仍然有效：如果每次都是把 audio[:t] 整段送进模型，那么它是"切片重放 + 伪流式 transcript"，首字延迟等于当前累计音频的处理时间，且总计算量随段数平方增长。

要看真流式，需求是：encoder 侧保留卷积/注意力状态，只处理新帧，并显式记录"稳定前缀"（连续两次输出不再变化的部分）。

6. 手写前端与官方特征差 1.67，能直接用吗？

分用途，与 4.5 的图像前端结论一致：

  • 长度、mask、坐标、分段策略可以直接用——这些是几何量，本章逐项核对过（有效帧 586 = ceil(93680/160)，mask 是采样级、上限 480000）。
  • 特征值不要自己算：残差 1.61–1.72（原始 log10 差 11.20–11.32）意味着下游 encoder 的输入分布不同，任何"逐位对比""缓存命中判定"的实验都会引入额外变量。已排除"先补零到 30 s"这一假设；剩余原因（fbank 的窗/边界/mel 归一化细节）没有定位。

工程判据：自写前端的价值在于理解与优化（例如把特征提取放进 GPU pipeline），而不是替代官方实现；替换时必须逐元素对拍通过，否则保留官方实现。
