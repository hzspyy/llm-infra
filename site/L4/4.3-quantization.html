4.3

量化工程

手工解包 AWQ 的 qweight（nibble 顺序是 0,4,1,5,2,6,3,7）并自检；量化误差的绝对值均匀、相对值集中在小权重上，组间 scale 差 212 倍。实测：显存 2.7×、质量退化 2-4%，但 batch=64 小模型上 decode 反而慢 10% —— 量化最稳的收益是装得下，不是快。fp8 GEMM 1.50×。

实测机器 crater (RTX 5090 D, sm_120) · vLLM 0.29.0 · Qwen2.5-1.5B bf16/AWQ/GPTQ数据日期 2026-09-10前置 4.0（量化 checkpoint 的结构）· 4.2（数值格式）· 3.3（decode 的账）

本章回答三个问题

4.0 看到了量化 checkpoint 的结构（qweight/scales/qzeros）。 这一章把那些整数解包还原，看清楚它损失了什么，再量它换来了什么。

  1. 4 bit 的权重具体是怎么存的？能不能自己解包还原出 fp16？
  2. 量化误差有多大？落在哪些权重上？
  3. 量化换来了多少——显存、速度、质量各变了多少？

本章最反直觉的一条实测

在 batch=64、1.5B 模型这个配置下，AWQ 和 GPTQ 的 decode 吞吐都比 bf16 低 （11610 / 11701 vs 12914 tok/s）。量化省的是显存， 不是在所有配置下都省时间。

一 · 手工解包 AWQ

quantization_config: bits=4 group_size=128 zero_point=True version=gemm

第 0 层 q_proj 的四个张量：

bias      (1536,)         torch.float16
qweight   (1536, 192)     torch.int32
qzeros    (12, 192)       torch.int32
scales    (12, 1536)      torch.float16

打包关系：

qweight (1536, 192) int32 -> 每个 int32 装 8 个 4-bit -> 展开后 1536×1536
scales  (12, 1536) = [in/128, out]，每 128 行共享一个缩放
qzeros  (12, 192) int32，同样打包，每 128 行共享一个零点

还原公式：

wij=(qij−z⌊i/128⌋,j)×s⌊i/128⌋,j

但有个坑：8 个 nibble 在 int32 里不是顺序排的。 AWQ 的 GEMM 版按 0,4,1,5,2,6,3,7 交错存放（为了让反量化 kernel 能一次性凑出对齐的向量）。

59def unpack_awq(qweight, qzeros, scales, bits=4, group_size=128):

61
62    qweight: [in_features, out_features // 8]  int32
63    qzeros : [in_features // group_size, out_features // 8]  int32
64    scales : [in_features // group_size, out_features]  fp16
65    返回 [in_features, out_features] 的 fp16
66    """
67    # AWQ 的 GEMM 版把 8 个 nibble 按这个顺序放：0,4,1,5,2,6,3,7
68    order = torch.tensor([0, 4, 1, 5, 2, 6, 3, 7])
69    shifts = (order * bits).to(qweight.device)
70
71    def unpack(x):
72        # x: [..., n] int32 -> [..., n*8]
73        out = (x.unsqueeze(-1) >> shifts.view(1, 1, -1)) & 0xF
74        return out.reshape(*x.shape[:-1], -1)

自检：还原对不对

不需要和原权重比就能自检——同一组内的取值必须落在 16 个等距格点上， 间隔恰好等于该组的 scale：

取第 0 列的前 128 行（同一组，共享一个 scale/zero）
不同取值个数: 15   （上限是 2^4 = 16）
取值: [-0.01624, -0.01392, -0.0116, -0.00928, -0.00696, -0.00464, -0.00232,
       0.0, 0.00232, 0.00464, 0.00696, 0.00928, 0.0116, 0.01624, 0.01855]
相邻间隔（= scale）: 0.002319
scales[0,0] = 0.002319  <- 应当相等

间隔 0.002319 与 scales[0,0] 精确相等。 如果 nibble 顺序解错了， 取值会散开成非等距的一堆，这个自检立刻失败。 （15 而不是 16 是因为这一组恰好没用满所有格点。）

二 · 误差有多大，落在哪

和未量化的同一个权重逐元素比：

与未量化权重对照 (1536, 1536)
  max|err|  = 1.718750
  mean|err| = 0.014152
  权重本身 mean|w| = 0.033141
  平均相对误差 = 42.70%
  余弦相似度 = 0.960913

平均相对误差 42.7%。 这个数字看起来吓人，但余弦相似度是 0.9609—— 方向基本保住了，是幅度上的量化噪声。

误差落在哪些权重上

最大的 0.1% 权重：平均 |err| = 0.145685，占其自身的 39.21%
最小的 50% 权重：平均 |err| = 0.004600，占其自身的 45.47%

绝对误差对大小权重是同一量级（同组共享一个 scale，格点间隔一样）， 所以相对误差在小权重上更大。

这解释了为什么 outlier 是量化的核心难题：一个组里只要有一个大值， scale 就被它撑大，同组的所有小值都被压到很粗的格点上。

scale 的分布：group_size 存在的理由

scale 分布: min=0.001054  中位数=0.008041  max=0.223145  max/min=211.8×

量化误差的上界是 scale/2：
  最好的组: ±0.000527
  最差的组: ±0.111572

组与组之间的 scale 差 212 倍。 如果整个矩阵共用一个 scale， 所有权重都要按最大的那个 outlier 缩放——小权重会被直接压成 0。

group_size 的取舍（按定义算）：

group_size 等效 bit/权重 scales+zeros 开销
32 4.62 15.6%
64 4.31 7.8%
128 4.16 3.9%
256 4.08 2.0%
1024 4.02 0.5%

组越小量化越准（组内动态范围更窄），但元数据开销越大。128 是当前的常见折中。

三 · 换来了什么

用 vLLM 跑真实的量化 kernel（transformers 里 AWQ/GPTQ 要额外装 gptqmodel/optimum，而 vLLM 自带，而且这才是这些 checkpoint 实际被用的路径）：

模型 困惑度 相对 bf16 权重文件 MB decode tok/s
bf16 原版 1.8697 1.000× 2944.4 12913.8
AWQ 4bit 1.9113 1.022× 1539.8 11610.4
GPTQ 4bit 1.9445 1.040× 1096.6 11701.4

三件事：

  1. 显存确实省了：2944 → 1540 / 1097 MB（1.9× / 2.7×）。 注意不是 4×——4.0 §六 讲过，embedding 没被量化，占了很大一块。
  2. 质量退化 2.2% / 4.0%（困惑度）。
  3. 速度反而更慢。 两个量化版都比 bf16 低约 10%。

关于困惑度这一列

用的是一段固定文本，不是标准数据集。它只能说明"没有量级上的崩塌"， 不能说明 AWQ 比 GPTQ 好（2.2% vs 4.0% 的差距在单样本上没有意义）。 真正的评测要跑标准集并报方差，本轮没有做。

为什么量化了反而更慢

这不矛盾，回到 0.2 的账本：

  • decode 的瓶颈是带宽（3.3 实测算术强度 = 1）——但那说的是 KV cache。 权重的读取在 batch 大时是摊薄的：64 条请求共享一次权重读取。
  • batch=64、1.5B 模型的这个配置下，权重带宽已经不是瓶颈； 而量化引入了额外的反量化计算（解包、乘 scale、减 zero）。

所以量化的收益随配置变：

配置 权重带宽占比 量化的收益
batch=1，大模型 高（每步都要读全部权重） 大
batch 很大，小模型 低（权重读取被摊薄） 可能为负（本章实测）
显存装不下 — 决定性（能不能跑）

量化最稳的收益是"能不能装下"，不是"快多少"。

四 · fp8：这张卡原生支持

L1.2 实测：bf16 511 FLOP/clk/SM，fp8 1022——纯发射率正好 2×。 端到端的 4096³ GEMM：

路径 ms TFLOP/s 相对 bf16
bf16 @ bf16 0.6245 220.1 1.00×
fp8_e4m3 @ fp8_e4m3 0.4163 330.1 1.50×

拿到 1.50×，不是 2×。 纯发射率翻倍，但 GEMM 还要搬数据： 4096³ 的 bf16 输入是 64 MB，fp8 是 32 MB——算力翻倍而访存只减半， 这个尺寸上已经不是纯算力受限了。

精度：

fp8 结果与 fp32 参照的平均相对误差: 3.7711%
（权重值域 ~N(0,1)，fp8_e4m3 上限 448，这里没有溢出）

4.2 那张表说过 fp8_e4m3 的相对分辨率是 0.125——3.77% 的平均误差 与之量级相符（累加在 fp32 里做，所以比单个数的分辨率好）。

五 · KV cache 量化：只给字节账

3.3 的结论是 decode 时间 = KV 字节 ÷ 带宽，所以 KV 的 dtype 减半，时间就该减半。

我试着量了一下，结果是反的：

  kv_len      dtype      KV 大小        ms    相对 bf16
    8192   bfloat16    256.0MB    0.1731      1.00×
    8192 float8_e4m3fn    128.0MB    0.5021      0.34×
   32768   bfloat16   1024.0MB    0.6500      1.00×
   32768 float8_e4m3fn    512.0MB    2.0319      0.32×

这个 0.34× 是我的实现方式造成的，不是 fp8 KV 的代价

我的做法是在框架层把 fp8 显式转回 bf16，再走普通的 SDPA。 这多了一次「读 fp8 + 写 bf16」的全量往返，比省下的还多。

真实的 fp8 KV attention 在 kernel 内部反量化——只读 fp8 那一份字节， 在寄存器里转成计算精度，不产生中间张量。

这和 3.3 §四 分页那次是完全同一类错误： 框架层的模拟量不出 kernel 内部做这件事的代价。 我在同一本书里连续犯了两次，所以这次直接写进正文。

本 lab 没有可用的真实 fp8 KV kernel，所以只给字节账：

kv_len bf16 fp8 / int8 int4
8192 256.0 MB 128.0 MB 64.0 MB
32768 1024.0 MB 512.0 MB 256.0 MB
131072 4096.0 MB 2048.0 MB 1024.0 MB

字节减半意味着同样显存能装两倍的并发，或者同样并发下 decode 快近两倍 （如果 kernel 实现得当）。要验证后者，需要用 vLLM 的 --kv-cache-dtype fp8 跑真实负载——那属于 5.x 的范围。

KV 量化不只有 fp8

vllm/config/cache.py 的 CacheDType 有 17 个取值（源码事实）：

auto, bfloat16, float16,
fp8, fp8_e4m3, fp8_e5m2, fp8_inc, fp8_ds_mla, fp8_per_token_head,
int8_per_token_head, int4_per_token_head,
nvfp4, nvfp4_4over6,
turboquant_3bit_nc, turboquant_4bit_nc, turboquant_k3v4_nc, turboquant_k8v4

三件事值得读出来：

  1. int8 / int4 是真实选项，不只是上表的字节账。 int4 把 128K 上下文的 KV 从 4 GB 压到 1 GB——这是长上下文能不能跑的分界。
  2. 后缀 _per_token_head 是量化轴。KV 的形状是 [tokens, heads, dim]， 逐 (token, head) 求 scale，等于把 group_size 沿 dim 取满。 这和权重量化的 group_size 是同一个设计参数（§7.1）： 轴选得越细，元数据越多，误差越小。
  3. turboquant_k3v4 给 K 和 V 不同位宽（K 用 3 bit，V 用 4 bit）。 因为 K 参与 QK⊤ 后过 softmax，误差会被指数压缩； V 是直接加权求和，误差线性进入输出。 同一个 cache 里两个张量的误差敏感度不同，所以位宽也不该相同。

第 3 点是本节最值得带走的：量化的粒度不该由张量的名字决定， 而该由它的误差如何传播到输出决定。

轴 问的问题 例子

6.1 容器：compressed-tensors 与 §7.3 的矛盾

§7.3 说格式是从 kernel 的最优访存倒推的，所以碎片化很难修复。 compressed-tensors 是对这个问题的正面回应：它不发明新算法， 而是定义一套描述——在 config.json 里声明位宽、量化轴、 group_size、是否对称、哪些层被跳过，让加载器按描述去挑 kernel。

这是很典型的一步：当实现无法统一时，先统一元数据。 AWQ 和 GPTQ 的 kernel 仍然各写各的，但"这份权重是什么" 不再需要靠文件名和目录结构去猜（4.0 §七 讲过靠猜的代价）。

modelopt（NVIDIA）、quark（AMD）、torchao（PyTorch）是同一层的东西， 各自绑着一个生态。所以容器层现在也有四五个——统一元数据的努力本身又分裂了。 这不讽刺，是常态：标准化的收益归全体，成本归先动的人。

6.2 作用域：MoE 的专家值得单独量化

experts_int8、moe_wna16、deepseek_v4_fp8 这三个是按作用域切的。

4.4 算过：MoE 模型的参数绝大部分在专家里，而每个 token 只激活其中很小一部分。 这给量化一个特殊的形状：

  • 收益特别大 —— 专家占了绝大多数参数，量化它们几乎等于量化整个模型的显存
  • 精度损失特别小 —— 每个专家只被一小部分 token 用到， 单个专家的误差不会传播到所有输出
  • 但访存模式不同 —— 专家权重是按 token 路由结果动态选取的（4.4 §三）， 反量化必须和 grouped GEMM 融合在一起，不能先整块解包

moe_wna16 这个名字直接写着它的形状：weight-only、n-bit、 activation 保持 16 bit。也就是不动激活，只压专家权重—— 正好对上上面三条。

可带走的判断：量化的作用域应该跟着「参数量占比 ÷ 激活频率」走。 占比大而激活少的部分，是最划算的量化目标。 稠密模型里所有权重每步都被读，没有这个不均衡可利用；MoE 有，所以它值一套专门的格式。

七 · 设计取舍

7.1 group_size：两个方向的误差

这是一个罕见的两端都有明确代价的参数：

  • 组太大 → 组内动态范围宽 → scale 被 outlier 撑大 → 小权重损失惨重 （本章实测组间 scale 差 212 倍，可见分布多不均匀）
  • 组太小 → 元数据开销大 → 等效位宽上升（32 时是 4.62 bit，比 4 高 15%）

128 之所以成为默认，是因为它落在"元数据开销已经降到 4% 以下" 和"组内还足够窄"的交点附近。这个交点位置依赖权重分布， 所以不同模型的最优 group_size 未必相同——但没人愿意为每个模型调它。

7.2 AWQ 和 GPTQ 解决的是同一个问题的两面

本章第二节的核心观察：误差的绝对值均匀，相对值集中在小权重上； 而 scale 被 outlier 支配。

  • GPTQ 从"重建误差"入手：逐列量化，用 Hessian 信息补偿已量化列带来的误差。 它优化的是"给定 4 bit，怎么让输出误差最小"。
  • AWQ 从"哪些权重重要"入手：用激活的幅度找出关键通道， 在量化前给它们做通道级缩放，让它们落在更细的格点上。 它优化的是"哪些权重值得给好待遇"。

两者都不改变 4 bit 这个约束，都在约束内重新分配误差。 这是量化方法的共同形态：位宽是外生的，方法竞争的是误差分配。

7.3 为什么量化格式没有统一

4.0 §七 提过这一点，本章给了更具体的证据：AWQ 的 nibble 顺序是 0,4,1,5,2,6,3,7——这个顺序不是随意的，它是为了让反量化 kernel 能一次凑出对齐的向量而选的。

也就是说，格式是从 kernel 的最优访存倒推出来的。 GPTQ 的 kernel 不同，最优布局就不同，于是 shape 转置、多一个 g_idx。

这类碎片化很难事后修复：改格式要重新量化所有已发布的模型， 而收益只是"少维护一套 kernel"。没有人有动机付这个代价。

可带走的判断：当格式由性能倒推时，标准化的窗口期在性能定型之前。

 45def timeit(fn, n=30, warmup=10):
 46    for _ in range(warmup):
 47        fn()
 48    torch.cuda.synchronize()
 49    a, b = torch.cuda.Event(True), torch.cuda.Event(True)
 50    a.record()
 51    for _ in range(n):
 52        fn()
 53    b.record()
 54    torch.cuda.synchronize()
 55    return a.elapsed_time(b) / n

 59def unpack_awq(qweight, qzeros, scales, bits=4, group_size=128):
 60    """AWQ 的打包：每个 int32 装 8 个 4-bit，但顺序是交错的。
 61
 62    qweight: [in_features, out_features // 8]  int32
 63    qzeros : [in_features // group_size, out_features // 8]  int32
 64    scales : [in_features // group_size, out_features]  fp16
 65    返回 [in_features, out_features] 的 fp16
 66    """
 67    # AWQ 的 GEMM 版把 8 个 nibble 按这个顺序放：0,4,1,5,2,6,3,7
 68    order = torch.tensor([0, 4, 1, 5, 2, 6, 3, 7])
 69    shifts = (order * bits).to(qweight.device)
 70
 71    def unpack(x):
 72        # x: [..., n] int32 -> [..., n*8]
 73        out = (x.unsqueeze(-1) >> shifts.view(1, 1, -1)) & 0xF
 74        return out.reshape(*x.shape[:-1], -1)
 75
 76    w = unpack(qweight)                       # [in, out]
 77    z = unpack(qzeros)                        # [in/gs, out]
 78    gs = group_size
 79    z = z.repeat_interleave(gs, dim=0)[: w.shape[0]]
 80    sc = scales.repeat_interleave(gs, dim=0)[: w.shape[0]]
 81    return ((w.float() - z.float()) * sc.float()).half()

建议的消融

  1. 把 nibble 顺序改成 0,1,2,3,4,5,6,7（顺序解包），再跑一次 [A] 的自检。 预测：取值不再等距，与 scales[0,0] 对不上。 这验证了那个自检确实有判别力。
  2. 用 vLLM 的 --kv-cache-dtype fp8 跑一次真实负载，补上第五节缺的那个测量。 这是本章最大的一个缺口。
  3. [C] 换成真正的评测集（wikitext-2 的困惑度），并报多次运行的方差。 本章那三个困惑度数字只能说明"没崩"。
  4. 把 [C] 的 batch 从 64 改成 1，看量化的速度收益是否转正。 按第三节的分析应该会——先预测再验证。

九 · 陷阱

  1. nibble 在 int32 里不是顺序排的（AWQ 是 0,4,1,5,2,6,3,7）。解错了不报错， 还原出的权重看似合理但全错。用"取值等距且间隔=scale"自检。
  2. "4 bit"不等于 4× 压缩。 本章实测 1.9×/2.7×，因为 embedding 没量化（4.0）。
  3. 量化不一定更快。 本章 batch=64 小模型上两个量化版都慢约 10%。
  4. 平均相对误差 42.7% 听起来很糟，但余弦相似度 0.96。 看单一指标会误判。
  5. 框架层的 dtype 转换量不出 kernel 内量化的代价。 本章第五节测出 0.34×， 是实现方式的问题（同 3.3 §四）。
  6. 一段文本的困惑度不是质量评测。 2.2% vs 4.0% 的差距在单样本上无意义。
  7. 同进程建第二个 vLLM 引擎前必须 engine_core.shutdown()，否则显存不还， 第二个模型直接起不来。
  8. fp8 端到端拿不到发射率的 2×（本章 1.50×），因为访存只减半。

十 · 自测题

1. 你解包了一个 4-bit 权重，怎么在没有原始权重的情况下验证解对了？

同一组内的取值必须落在 2bits 个等距格点上，间隔恰好等于该组的 scale。

本章实测：取第 0 列的前 128 行（同一组），得到 15 个不同取值， 相邻间隔 0.002319，而 scales[0,0] = 0.002319——精确相等。

如果 nibble 顺序解错了，你会把不同组/不同位置的 4-bit 值混在一起， 取值会散成非等距的一堆，这个检查立刻失败。

这是一个自洽性检查：不需要外部参照，靠格式自身的约束就能验证。 写解析器时应该优先找这类检查。

2. 量化后模型更慢，是不是说明量化没用？

不是。量化最稳的收益是显存，不是速度。本章实测 2944 → 1097 MB。

速度收益取决于权重带宽在总时间里的占比： - batch=1 或大模型：每步都要读全部权重，权重带宽是瓶颈 → 量化收益大 - batch 很大、模型小：权重读取被 64 条请求摊薄，已经不是瓶颈 → 反量化的额外计算反而拖慢（本章实测慢约 10%）

而且还有一类收益是二值的：显存装不下的时候，量化决定能不能跑。 这时候"快多少"根本不是问题。

判断方法：先量出你的配置下权重读取占多少时间（用 0.2 的账本 + 2.6 的 profiler）。

3. 为什么量化误差的相对值在小权重上更大？这对 AWQ 意味着什么？

因为同一组共享一个 scale，格点间隔对组内所有权重都一样。 绝对误差上界是 scale/2，与权重本身的大小无关。

所以小权重的相对误差更大。本章实测：最大的 0.1% 权重相对误差 39.21%， 最小的 50% 权重 45.47%（绝对误差分别是 0.146 和 0.0046，差 32 倍）。

而 scale 本身被组内的 outlier 支配（本章组间 scale 差 212 倍）。

AWQ 的应对是：用激活的幅度找出"重要"的通道，在量化前给它们做通道级缩放， 把它们移到能被更细格点表示的位置。它没有改变 4 bit 这个约束， 只是重新分配了误差——把误差从重要通道挪到不重要的通道上。

4. fp8 的纯发射率是 bf16 的 2×，为什么 GEMM 只快 1.50×？

因为 GEMM 不只是算，还要搬数据。

4096³ 的输入：bf16 是 2×40962×2B=64 MB，fp8 是 32 MB。 算力翻倍，但访存只减半。 如果这个尺寸上已经有一部分时间花在访存上， 那部分只快 2× 中的一半。

一般规律：一个优化在纯指标上的收益，端到端只有在"该指标确实是唯一瓶颈"时才能拿满。 本书里反复出现同一形态—— 3.2 的 exp 占比、4.3 的量化速度、2.7 的 max-autotune，都是这个道理。

判据：先用 roofline（0.2）确认瓶颈在哪一侧，再估收益上限。

5. vLLM 支持 30 种量化方法。要不要一个个学？

不要。它们不在同一个层级上，拆成三个正交的轴就只剩三件事：

  • 算法（4 bit 之内怎么分配误差）：AWQ · GPTQ · round-to-nearest
  • 容器（怎么存、怎么描述）：compressed-tensors · modelopt · quark · torchao
  • 作用域（哪一部分被量化）：全部线性层 · 只有 MoE 专家 · KV cache

30 个名字里很多只是某个组合被单独起了名（gpt_oss_mxfp4 = mxfp4 算法 + 特定模型的作用域约定）。认轴，不认名字。

这是读任何一个大选项空间的通法：先找出正交的维度， 剩下的名字就是组合，不需要逐个记。

6. 为什么 MoE 值得一套专门的量化格式（experts_int8 / moe_wna16）？

因为 MoE 有一个稠密模型没有的不均衡：参数量占比 ÷ 激活频率。

专家占了绝大多数参数，但每个 token 只激活其中很小一部分（4.4）。于是：

  • 收益特别大：量化专家几乎等于量化整个模型的显存
  • 精度损失特别小：单个专家只被一小部分 token 用到，误差不会传播到所有输出
  • 但访存模式不同：专家权重是按路由结果动态选取的， 反量化必须和 grouped GEMM 融合，不能先整块解包——所以要专门的 kernel

moe_wna16 的名字直接写着它的形状：weight-only、n-bit、 activation 保持 16 bit。

稠密模型里所有权重每步都被读，没有这个不均衡可利用，所以不需要这一套。

可带走的判断：量化的作用域应该跟着「参数量占比 ÷ 激活频率」走。

7. `turboquant_k3v4` 给 K 用 3 bit、V 用 4 bit。为什么不一样？

因为同一个 cache 里两个张量的误差敏感度不同：

  • K 参与 QK⊤，结果要过 softmax。softmax 对输入的小扰动有压缩作用 （尤其在分数差距明显时），K 的误差被指数压掉一部分。
  • V 是直接被 attention 权重加权求和，误差线性进入输出，没有任何衰减。

所以在同样的字节预算下，从 K 拿一个 bit 给 V 是划算的。

一般化：量化的粒度不该由张量的名字决定，而该由它的误差如何传播到输出决定。 同样的思路解释了为什么 embedding 和 lm_head 常常不量化（4.0 §六）， 以及为什么 §7.2 里 AWQ/GPTQ 都在"重新分配误差"而不是改变位宽。
