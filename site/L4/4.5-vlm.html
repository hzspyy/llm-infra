VLM（一）：图像与视频预处理

从原始像素、视频帧与时间戳到 resize/crop/normalize、patch/grid 和视觉 token，核对 processor 配置、动态分辨率及合法输入；主模型与结构对照按任务和资源选择。 分析训练数据增强、标注对齐和特征缓存。

实测机器 crater (RTX 5090 D, sm_120) · torch 2.13.0+cu130 · transformers 5.17.0 · Qwen3-VL-4B-Instruct前置 0.4（文本输入）· 4.1（层实现）· 3.3（decode 的账）

本章回答的三个问题

多模态模型的输入不是文本，而是像素。这一章只做一件事：把"一张图/一段视频"变成模型真正吃到的张量，并把这条链上的每个数字核对一遍。

  1. 像素怎么变成 patch？ patch、temporal patch、merge 三个参数如何决定张量的形状与视觉 token 数？
  2. resize / normalize / 采帧的规则是什么？ 尺寸夹取、32 对齐、单帧沿时间复制、fps 与 num_frames 的采帧各自怎么算？
  3. 视觉 token 预算换成什么？ 预算设成 128/512/2048 时，实际 token 数、CPU 时间、后续 GPU 输入规模与小任务正确率各是多少？

本章的图像全部由脚本用 PIL 生成（自有、许可明确、答案在生成时写死），因此每个任务的正确与否都可以自动判定。

机制拆解

配置：三个参数决定形状

Qwen/Qwen3-VL-4B-Instruct 的 preprocessor_config.json：

patch_size            16          temporal_patch_size   2
merge_size            2           image_mean/std        [0.5, 0.5, 0.5]
size.shortest_edge    65536  (= 256²)   size.longest_edge  16777216 (= 4096²)
video: shortest_edge  4096   (= 64²)    longest_edge       25165824 (= 5016²)
  • 对齐因子 = patch × merge = 16 × 2 = 32：任何输入尺寸都会被对齐到 32 的整数倍，这样 merge 2×2 才能整齐地把 4 个 patch 合成 1 个 token。
  • size 是像素数边界（不是边长）：65536 = 256² 是下界、16777216 = 4096² 是上界。小图会被放大到至少 256²，大图会被缩小到 4096² 以内——实测 5000×5000 被压到 4096×4096（grid 256×256）。
  • 视频的边界比图像更宽（下界 4096 = 64²）：视频帧小一些可以接受，因为帧数会放大 token 数。

手写 resize / normalize / patchify

smart_resize（本章手写，与官方逐张对尺寸）：

def smart_resize(h, w, factor=32, min_pixels=256**2, max_pixels=4096**2):
    if h * w > max_pixels:
        beta = math.sqrt((h * w) / max_pixels); h, w = math.floor(h/beta), math.floor(w/beta)
    elif h * w < min_pixels:
        beta = math.sqrt(min_pixels / (h * w)); h, w = math.ceil(h*beta), math.ceil(w*beta)
    return max(factor, round(h/factor)*factor), max(factor, round(w/factor)*factor)

normalize 与 patchify：

norm = (img_tensor - 0.5) / 0.5                    # 逐通道
x = norm.reshape(C, gh, 16, gw, 16).permute(1, 3, 0, 2, 4)      # [gh,gw,C,ph,pw]
x = x.reshape(gh//2, 2, gw//2, 2, C, 16, 16)
x = x.permute(0, 2, 1, 3, 4, 5, 6)                 # merge 块主序（块行主序、块内行主序）
x = x.reshape(-1, C, 16, 16).unsqueeze(2).expand(-1, -1, 2, -1, -1)
x = x.reshape(-1, C * 2 * 16 * 16)                 # patch 内排布 (c, t, ph, pw)

第三行是这张表里最容易搞错的一步：单帧沿时间维复制 2 次，且 patch 内的排布是「通道在前、时间其次」。用 patch-ramp 图逐个解码官方 pixel_values 可以确证：一个 patch 向量的取值游程是「20 × 512、23 × 512、26 × 512」——512 = temporal(2) × 16 × 16，对应 RGB 三个通道，说明通道是最外层。

对照实验：把排布写成 (t, c, ph, pw)，形状完全一样，但 12 张图的平均绝对差变成正确顺序的 1.8–66.7 倍。

对拍结果：找到并修掉了 patch 顺序的坑

img07_ocr_1280x720 1280×720 1280×704 [1, 44, 80] 880 10.36 ms
img11_count_480x640 480×640 480×640 [1, 40, 30] 300 6.19 ms
  • 几何与像素都一致：12/12 的 grid_thw、patch 行数、patch 维度与官方相同；把 patch 顺序与 resize 都对齐之后，平均绝对差 ≤6.4e-10、逐元素最大差 ≤5.9e-08（float32 舍入量级），差 >0.5 的元素占比 0.0000%。
  • 像素值没有做到逐元素相同：平均绝对差 1.8e-03–5.7e-02（取值域 [-1,1]），最大差 1.86，最高 4.9% 的元素差超过 0.5。残差集中在高对比细笔画像素上（把官方输出反 patch 回来的图像与独立实现做整数偏移搜索，最优偏移是 (0,0)，平均绝对差 6.9e-03——即没有几何错位）。
  • 原因已定位，需要同时满足三件事：① patch 的遍历顺序是「merge 块主序」——用一张「每个 16×16 patch 一个唯一常量」的斜坡图解码官方 pixel_values 的序列，官方前 8 个 patch 对应源图的索引是 [0, 1, 16, 17, 2, 3, 18, 19]，即 2×2 的 merge 块按行主序、块内 4 个 patch 再按行主序，而不是 [0,1,2,3,…]；② patch 内是 (c, t, ph, pw)；③ resize 用 torchvision 的双三次 + 抗锯齿（官方 processor 走的就是这条），而不是 PIL 的默认/双三次。
  • 只把 patch 顺序修好是不够的：此时 12 张图里 9 张已达到 5.9e-08，3 张含细笔画文字的图仍有 7.8e-03 的差——换成官方的 resize 实现（torchvision 双三次 + 抗锯齿）后这 3 张也降到 5.9e-08。残差的最终消除往往依赖多个独立预处理环节的同时对齐，排查微小数值残差时需对各预处理算子执行正交消融。
resize 实现（其余步骤相同） 最大逐元素差
PIL 默认 7.843e-03
PIL 双三次 7.843e-03
PIL 双线性 1.725e-01
torchvision 双三次 + 抗锯齿 5.914e-08
  • 两个顺序都要对，错一个都会静默出错：patch 内是 (c, t, ph, pw)，patch 间是 merge 块主序。只改其中一个的对照实验里，平均绝对差是正确实现的 7.6e+05 ~ 4.0e+10 倍（后者是因为在整块错位下几乎完全不相关）。

结论的用法：几何与 token 账可以直接用（它们逐张一致）；像素级复现需要直接用官方 processor，不要自己写 resize。

视频采帧：fps 与 num_frames 是两种口径

合成视频 16 帧、源 8 fps：

模式 取帧数 时间戳
fps=1 2 [0.0, 1.0]
fps=2 4 [0.0, 0.5, 1.0, 1.5]
fps=4 8 [0.0, 0.25, 0.5, 0.75, 1.0, …]
num_frames=4 4 [0.0, 0.625, 1.25, 1.875]
num_frames=16 16 [0.0, 0.125, 0.25, 0.375, …]

两种口径的时间戳分布不同：fps=2 是等间隔 0.5 s 的抽样（每 4 帧取 1 帧）；num_frames=4 是把 16 帧均匀压成 4 个采样点（间隔 0.625 s）。同一个视频用不同口径会得到不同的时间覆盖，做时间定位任务时必须记录用的是哪一种。

官方 video processor 的输出：grid_thw = [2, 16, 20]，grid_t × temporal_patch_size = 4 帧 —— 16 帧被按 temporal_patch_size=2 折成 grid_t=2（2×2=4 帧的实际输入），中间有采样。这也说明"帧数"有三个不同的口径：文件里的帧数、采帧后的帧数、temporal patch 后的 grid_t。

边界与非法输入

输入 结果
32×32 小图 不报错，被放大到 256×256 → grid [1,16,16]
5000×5000 大图 不报错，被压到 4096×4096 → grid [1,256,256]，16384 token（单图就吃掉 16k token）
fps=0 ZeroDivisionError（脚本侧采样）
单帧视频 ValueError: t:1 must be larger than temporal_factor:2

两条值得记的：大图不报错，而是静默变成 16k 视觉 token（会挤占上下文预算）；单帧视频直接报错，因为 temporal_patch_size=2 需要至少 2 帧——把单张图当视频喂是常见错误。

视觉 token 预算：512 是这批任务的拐点

同一批 12 张图，把 size 的边界设成 token 预算 128/512/2048（min_pixels = token × 32 × 32）：

预算 实际 token（中位） 像素张量 CPU 中位 生成耗时中位 任务命中
128 120 1.41 MiB 4.40 ms 72 ms 7/12
512 540 6.33 MiB 3.38 ms 98 ms 12/12
2048 2120 24.84 MiB 10.26 ms 230 ms 12/12

三件事：

  • 设置值与实际值不同：120/540/2120 而不是 128/512/2048。原因是面积夹取 + 32 对齐，以及 resize 后面积只能落在离散的网格上。
  • 正确率在 512 处饱和：128 token 时丢 5/12（OCR 的小字与计数的小圆点先消失），2048 与 512 相同。信息损失发生在 resize 这一步——降到 120 token 意味着分辨率被压掉约 4×，之后再怎么算都补不回来。
  • 成本随 token 近似线性：生成耗时 72 → 98 → 230 ms。视觉 token 数直接进入 attention 的 O(S2)（3.1）与 prefill 的算力账（0.2）。

与 Gemma3 的结构对照

Gemma3ImageProcessor（HF 默认构造）的实测属性：size = 224×224 固定、resample = BILINEAR、mean/std 都是 0.5；四张测试图的输出都是 [1, 3, 224, 224]、num_crops=1。

两种结构的差别：

Qwen3-VL Gemma3
输出尺寸 随输入变（面积夹取 + 32 对齐） 固定边长（真实 gemma-3-4b-it 用 896×896）
大图策略 缩到上界内，降低分辨率 可选 pan-and-scan，把大图切成多块分别编码
token 数 由 grid 决定，连续可变 由 crop 数决定，离散
缩放插值 见上文（未定位） BILINEAR（实测）

跨模型质量差异没有测：google/gemma-3-4b-it 的权重受许可限制，本章只比较了 processor 的结构与输出布局，未做任务正确率对照（UNVERIFIED）。

工程实现 · 源码解析：processor 的入口与返回值

preprocessor_config.json  image_processor_type = "Qwen2VLImageProcessorFast"

但 AutoProcessor.from_pretrained(...).image_processor 实际给出的是 Qwen2VLImageProcessor（慢速 PIL 版），并且它没有 min_pixels/max_pixels 属性——边界只在 size = {"shortest_edge": …, "longest_edge": …} 里，也不在构造参数里。改预算必须直接改 ip.size：

old = dict(ip.size)
ip.size = {"shortest_edge": budget * 32 * 32, "longest_edge": int(budget * 32 * 32 * 1.02)}

返回值里与 token 账直接相关的字段：

out = processor.image_processor(images=img, return_tensors="pt")
out["pixel_values"]      # [grid_t*grid_h*grid_w, C*temporal*patch*patch] = [N, 1536]
out["image_grid_thw"]    # [1, H/16, W/16]

注意 pixel_values 的第一维是 patch 数（不是 batch）：单张 320×240 的图，在默认预算下是 [256, 1536]。视频侧同理，video_grid_thw 的第一位是 grid_t（已按 temporal_patch_size 折过）。

 50 def smart_resize(h, w, factor=32, min_pixels=256 * 256, max_pixels=4096 * 4096):

 70 def patchify(img, patch=16, temporal_patch=2, merge=2):
 71     """[3,H,W] -> [grid_t*grid_h*grid_w, 3*temporal_patch*patch*patch]。
 72 
 73     与 Qwen2/3-VL 的约定一致：单个 patch 内的排布是
 74     (c, t, patch_h, patch_w) 展平（通道在前、时间其次），且单帧沿时间维重复
 75     temporal_patch 次。实测把 (t,c,ph,pw) 当成官方顺序会在形状全对的情况下得到
 76     1.86 的最大差（归一化后的整个取值范围才 2.0）。
 77     """
 78     C, H, W = img.shape
 79     gh, gw = H // patch, W // patch
 80     x = img.reshape(C, gh, patch, gw, patch).permute(1, 3, 0, 2, 4)   # [gh,gw,C,ph,pw]
 81     # 官方顺序是「merge 块主序」：块按行主序，块内 m×m 个 patch 再行主序
 82     x = x.reshape(gh // merge, merge, gw // merge, merge, C, patch, patch)
 83     x = x.permute(0, 2, 1, 3, 4, 5, 6).reshape(-1, C, patch, patch)
 84     # 单帧沿时间维复制；patch 内的排布是 (c, t, ph, pw)——通道在前、时间其次

 86     x = x.reshape(gh * gw, C * temporal_patch * patch * patch)
 87     return x, (1, gh, gw)

155     """Qt 的采帧规则：按目标 fps 等间隔取帧，返回帧号与时间戳。"""

前沿

"动态分辨率"—token 数正成为显式的服务预算。 Qwen3-VL 用面积夹取把一张图映射到连续可变的 token 数；Gemma3 用固定边长加 pan-and-scan 把大图切成离散的 crop 数。两种路线在服务端的差别很直接：前者让请求的 token 成本随图连续变化（需要准入控制与配额），后者让成本按块跳变（更容易估算但浪费）。本章的实测给出这条曲线的量级：预算 128→2048 时，实际 token 120→2120、像素张量 1.4→24.8 MiB、生成耗时 72→230 ms，而任务正确率在 512 处已经饱和。

预处理正在被"patch 化"以复用视觉编码器的 KV。 视觉 token 一旦确定，后续的编码器与语言模型都在这个长度上工作；把图像切成 patch 也让"同图复用"成为可能（4.8 的 feature cache）。本章的 patch 内排布 (c, t, ph, pw)、temporal 复制与 merge 2×2 就是这份缓存载荷的格式定义——4.6 会给出逐层特征清单，4.8 会把它们缓存起来。

跨模型结构对照仍缺质量侧的证据。 本章只对比了 Qwen3-VL 与 Gemma3 的 processor 结构（输出尺寸、crop 策略、resample），因为 gemma-3-4b-it 的权重受许可限制没有下载。要判断"哪种 crop/merge 结构在 OCR/计数/时间定位上更好"，需要在同一任务集上跑两个模型——这是 4.6/4.7 之后可以回填的对照（见 STATUS）。

陷阱

  1. patch 内的排布是 (c, t, ph, pw)，形状对不代表数值对。 用 (t,c,ph,pw) 时平均绝对差是正确顺序的 1.8–66.7 倍。
  2. 对齐官方需要三件事同时满足：merge 块主序的 patch 遍历、(c,t,ph,pw) 的 patch 内排布、torchvision 双三次+抗锯齿的 resize。漏掉顺序时形状与 grid 完全正确而像素值错（平均 5.7e-02、最大 1.86）；只修顺序仍有 7.8e-03（3 张文字图）；三件齐备后是 5.9e-08。形状对不代表顺序对，顺序对也不代表数值对。
  3. size 是像素数边界，不是边长。 65536 = 256²、16777216 = 4096²；写 256 会得到完全不同的缩放。
  4. 小图会被放大。 32×32 被拉到 256×256——"小图更省 token"在低于下界时不成立。
  5. 大图不报错，而是静默变成 16k token（5000×5000 → grid 256×256）。它会挤占上下文预算。
  6. 单帧视频会报错：t:1 must be larger than temporal_factor:2。把单张图当视频喂是常见错误。
  7. fps 与 num_frames 是两个口径，时间戳分布不同（0.5 s vs 0.625 s 间隔）；做时间定位必须记录用的是哪一种。
  8. "帧数"有三个口径：文件帧数、采帧后的帧数、grid_t × temporal_patch_size。
  9. 预算设置值 ≠ 实际 token 数（128 → 120、512 → 540、2048 → 2120）：面积夹取 + 32 对齐。
  10. token 数相同不代表成本相同。 300 token 的 640×480 与 480×640 在 CPU 上差 2×（2.32 vs 4.64 ms）。
  11. 降低预算的损失发生在 resize 这一步，不可逆：先降采样再切 patch，后面的层补不回来。
  12. image_processor 的类型与 config 声明可能不一致：config 写 Qwen2VLImageProcessorFast，实际拿到的是慢速 Qwen2VLImageProcessor，而且没有 min_pixels/max_pixels 属性。

自测题

1. 一张 640×480 的图，patch 16、temporal 2、merge 2、上下界 256²/4096²，视觉 token 是多少？

面积 307200，在 [65536, 16777216] 内 → 不缩放。对齐到 32 的倍数：640→640、480→480（都能整除 32）。

grid = [1, 480/16, 640/16] = [1, 30, 40]；merge 2×2 把 4 个 patch 合成 1 token：

token=1×30×4022=300

本章实测该图就是 300 token、像素张量 3600 KiB、CPU 2.32 ms。（注意 grid_thw 里 grid_t=1 是单帧复制 2 次后的结果，公式里仍按 1 算，因为 merge 只在 h/w 方向合并。）

2. 你把 32×32 的图标送进去，发现 token 数比 640×480 的照片还多。为什么？

因为下界是像素数 65536 = 256²。32×32 = 1024 像素远低于下界，smart_resize 会把面积放大到至少 65536：

β=65536/1024=8,h,w=32×8=256

得到 256×256 → grid [1,16,16] → token = 256/4 = 64。而 640×480 是 300 token。

所以小图在触到下界之前会被放大；"小图省 token"只在面积已经高于下界时成立。这条对图标、验证码、扫描小票类输入很关键：它们会被放大后按像素数收费。

3. 为什么 patch 内的排布顺序错了，形状却完全一样？

因为排布只是把同一个 patch 的 1536 个数（3×2×16×16）按不同顺序写进向量。总元素数、patch 数、每 patch 的维度都不变，所以 shape、stride、dtype 全部正常，只有语义错位。

要发现它只有两条路：

  1. 与官方逐元素对拍（本章的做法）——但前提是其他环节已经一致，否则残差会掩盖它；
  2. 构造可解码的输入：给每个 patch 一个唯一值、给每个通道一个偏移，然后解码官方输出的游程，直接读出排布。本章用这个方法确认了官方是 (c, t, ph, pw)：一个 patch 的游程是「值 20 × 512、值 23 × 512、值 26 × 512」，512 = 2×16×16 正好是一个通道的时间×空间面。

这条对任何"打包/展平"格式都适用（4.0 的量化打包、4.0 的 safetensors 布局同理）。

4. 视觉 token 预算设成 512，为什么实际是 540？

因为 min_pixels = 512 × 32 × 32 只是下界，而实现步骤是：

  1. 先按面积把图缩放到 [min,max] 区间内（max 还乘了 1.02 的余量）；
  2. 再把高宽四舍五入到 32 的整数倍（round(h/32)*32）；
  3. token 数由最终的 grid 反算，而不是由预算直接给出。

四舍五入的方向（上或下）、以及 max_pixels 的 1.02 余量，都会让实际值偏离设置值。本章的实测：128→120、512→540、2048→2120。

做法：预算只用来设边界，报告时一律用 image_grid_thw 反算出的真实 token 数（grid_t*grid_h*grid_w/merge²）。

5. fps=2 与 num_frames=4 在 16 帧、8 fps 的视频上取到的帧一样吗？

不一样。

  • fps=2：按"每秒采 2 帧"抽样，源 8 fps → 每 4 帧取 1 帧 → 帧号 [0,4,8,12]，时间戳 [0.0, 0.5, 1.0, 1.5]。
  • num_frames=4：把整段均匀压成 4 个采样点 → 帧号 [0,5,10,15]（round(i×15/3)），时间戳 [0.0, 0.625, 1.25, 1.875]。

两者帧数相同、覆盖的总时长相同，但采样位置不同（0.5 s 均匀 vs 两端对齐的均匀）。做时间定位任务时，如果评测的时间戳来自 fps 采样而模型输入是 num_frames 采样，就会出现系统性的时间偏差。

另外别忘了还有第三层：temporal_patch_size=2 会把采到的帧再折一次（16 帧 → grid_t × 2 = 4 帧的实际输入），所以"进入模型的帧"比"采样的帧"更少。

6. 你的手写预处理与官方 processor 的平均差是 5e-2，但 grid 完全一致。能不能直接用？

要分用途：

  • 几何与 token 账可以直接用：grid_thw、patch 数、每 patch 维度、token 数 12/12 一致，预算曲线与容量估算不受影响。
  • 像素级复现不能用：平均绝对差最高 5.7e-2、最大 1.86（取值域 2.0）、最高 4.9% 的元素差超过 0.5。这意味着下游特征会有可测的差异，做"同一输入逐位对比"的实验（例如 4.2 的确定性、4.8 的缓存命中判定）时会引入额外变量。

本章的结论是把这条残差如实记录为未定位（候选是 processor 内部 resize 的实现细节：PIL 的 BICUBIC/BILINEAR/LANCZOS 与 torchvision 的 antialias 路径都试过，最大差都在 1.86 附近；整数偏移搜索的最优偏移是 (0,0)，排除了几何错位）。

工程判据：坐标系与 token 账自己算，像素值直接调官方 processor。 自己重写 resize 只在需要优化这条链的效率（例如把 resize 放进 GPU pipeline）时才值得，那时必须逐元素对拍通过。
