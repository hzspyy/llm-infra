GPU 微架构与内存层次

通过微基准学习寄存器、共享内存、缓存与显存的延迟、带宽和并行访问方式。

实测机器 crater (RTX 5090 D, sm_120) + worldvln (L40S, sm_89)前置 L0.2（roofline 与账本）

本章回答三个问题

  1. 从寄存器到显存，每一级的延迟和带宽各是多少？拐点在哪里？这些数字规格表上没有。
  2. 要把显存带宽打满，需要多少并发？为什么"线程开得越多越快"是错的？
  3. FlashAttention 的 tile 尺寸为什么是 <128, 64, 128, 4> 而不是别的数？

先区分两个概念：延迟是一次访问需要等多久，带宽是单位时间能搬多少数据。 GPU 可以让许多访问同时进行，因此带宽高不代表单次访问延迟低。 本章先认识 SM（执行线程块的计算单元）及其寄存器、共享内存和缓存， 再用测量结果理解分块计算。硬件容量能排除放不下的 tile， 但不能单独决定哪组 tile 参数最快。

心智模型：一座延迟递增、带宽递减的金字塔

机制拆解

SIMT：warp 是真正的调度单位

GPU 的最小调度单位不是线程，是 warp = 32 个线程。一条指令被整个 warp 同时执行 （Single Instruction, Multiple Threads）。三个直接后果：

  1. 分支发散（divergence）：warp 内如果 if 两侧都有线程走，硬件会两条路径都执行一遍， 用掩码屏蔽不该生效的线程。实际代价取决于分支长度、活跃线程和编译结果， 不能只看到 if (tid % 2) 就认定性能减半。
  2. 访存合并（coalescing）：warp 的 32 个线程如果访问连续地址，硬件合并成少数几个 128 字节事务；如果地址散开，最坏要发 32 个事务。这是 L2.3 的主题。
  3. 延迟靠切换掩盖：一个 warp 卡在等访存时，SM 立刻切到另一个就绪的 warp。 GPU 不像 CPU 那样靠乱序执行和大缓存掩盖延迟，它靠"手上有足够多的活"。

本机实测：每 SM 最多常驻 1536 个线程 = 48 个 warp，共 170 个 SM。

延迟：三段平台，拐点精确落在容量边界

指针追逐（每次访存依赖上一次结果，硬件无法并行发射）测出的纯延迟：

工作集 5090 周期 5090 ns L40S 周期 L40S ns 命中层级
4–64 KiB 44.1 15.22 40.0 15.91 L1
128 KiB 285.0 98.24 222.1 88.38 L1 边界（部分被 smem 占走）
256 KiB – 64 MiB 360 124.1 279 111.0 L2
96 MiB 575.6 198.4 354.2 141.0 L2 已到容量边界
128–512 MiB 929 320.3 636 253.4 显存

三段平台的代表读数为：44 / 360 / 929（5090），40 / 279 / 636（L40S）。 中间的两个跳变分别发生在 128 KiB 和 96 MiB —— 正好是 L1 与 L2 的容量。

这条链测的是依赖延迟：下一次访问的地址来自上一次读出的值（idx = buf[idx]）， 硬件无法提前发射下一次请求，所以迟到的是纯延迟，不是带宽。 把链换成连续地址，或让相邻两次访问跨 2 MiB 页，结果几乎不变：

工作集（L2 的倍数） 随机 连续 跨页 随机 ns 独立 load 带宽 在途 = 带宽 × 延迟
0.25×（24 MiB） 359.8 359.9 360.0 124.1 19,826 GB/s 2,403 KB
0.5×（48 MiB） 359.9 359.9 359.9 124.2 6,902 GB/s 837 KB
1×（96 MiB） 576.1 570.4 576.9 198.7 4,976 GB/s 966 KB
2×（192 MiB） 929.4 919.2 930.5 320.6 2,015 GB/s 631 KB
4×（384 MiB） 932.8 919.3 931.4 321.8 1,699 GB/s 534 KB

（crater RTX 5090 D。随机/连续/跨页均为同一 chase_kernel，只改链的构造方式； 独立 load 带宽沿用实验 B 的多遍读取口径，因此 24–96 MiB 落在 L1/L2， 192 MiB 的第二遍能复用一部分 L2，只有 384 MiB 是干净的单遍显存读数。）

依赖链里顺序访问更快不成立：地址由数据决定，预取器对下一次地址一无所知， 连续、随机、跨页拿到的都是同一级存储的完整往返延迟（三列差异 ≤1.5%）。 顺序与合并真正省下的是独立 load 的吞吐——地址预先已知、可以同时发射， 同一张表右侧两列才会随存储层级变化。用依赖链去测预取有没有生效会得到 1.0× 的 假结论；依赖链只回答这一级延迟多少。384 MiB 一行的独立带宽 1,699 GB/s 乘上 321.8 ns 是 534 KB，正好等于前面 Little's Law 估出的在途字节数， 这说明延迟本身没有变小，只是被足够的并发掩盖了。

跨架构的观察很反直觉：5090 在每一级的延迟都比 L40S 高 （L2 360 vs 279 周期，显存 929 vs 636 周期），但它的带宽高 2.5 倍。

延迟与带宽反映不同的物理属性。仅凭两台设备的对照，尚不能草率将延迟差异全部归因于 GDDR7 的 bank 架构或流水深度。但这一事实揭示了一个关键定律：「理论带宽更高的显存」在单次访存延迟上完全可能更慢。 对于 decode 这种拥有充裕并发 warp 掩盖延迟的负载而言影响有限；但对于访存依赖链长且并发度不足的 kernel，这种延迟增加则是实打实的性能损失。

带宽：随工作集掉三级

工作集 5090 GB/s L40S GB/s 主要命中
1 MiB 10 427 9 511 L1（各 SM 私有）
4 MiB 24 071 17 476 L1
16 MiB 27 017 19 396 L1（接近聚合上限）
32 MiB 12 866 9 362 开始溢出 L1
64–96 MiB ~5 400 ~4 270 L2
128 MiB 3 006 1 644 过渡
512 MiB – 1 GiB 1 674 681 显存

两个边界都能被解释：

  • 第一个悬崖在 16 → 32 MiB：全卡 L1 聚合容量 = 170 SM × 128 KiB = 21.25 MiB。 工作集超过它就掉进 L2。
  • 第二个悬崖在 96 → 128 MiB：正好是 L2 的 96 MiB。

存储层级之间的带宽比：L1 : L2 : 显存 ≈ 16 : 3.3 : 1。 由于片上缓存与外部显存之间存在数量级的带宽差距，算子优化的首要原则便是将高频复用的数据尽量保留在片上高速存储中。分块计算（tiling）的核心思想就是把大规模计算任务拆分为适配高速缓存的小块，在数据被逐出前进行充分复用。但需注意，存储带宽比并不直接等价于程序的端到端加速比，数据加载、块间同步、算术计算及结果回写都会产生额外耗时（L2.4 将逐步剖析这些开销）。

这解释了 L0.2 里一个悬而未决的数字

L0.2 用 probe_hw.py 测出 copy 带宽 1519 GB/s、只读 1608 GB/s。 本章用完全不同的 kernel（float4 grid-stride 读）测出 1674 GB/s。 三个数字都在 1.5–1.7 TB/s 区间，互相印证。 而厂商标称是 1792 GB/s —— 实测能到 93%，已经相当接近上限。

共享内存与 bank conflict

共享内存分成 32 个 bank。一个 warp 的 32 个线程如果落在不同 bank， 一拍完成；如果多个线程落在同一 bank，就要串行。用每线程连发 8 个互不依赖 load 的方式扫描 stride：

stride（float 元素） 5090 周期/次 L40S 周期/次 5090 相对 stride=1
1 6.51 6.65 1.00×
2 6.60 6.37 1.01×
4 9.79 9.54 1.50×
8 17.79 17.54 2.73×
16 33.79 33.54 5.19×
32 65.79 65.54 10.11×

stride=1 和 2 都接近无冲突；从 stride=4 起，冲突代价才随 stride 增加而显现， 但倍率低于"撞了几个 bank"的朴素计数。

依赖链无法测出这里的 bank 冲突差异

使用依赖链（idx = s[idx]），测出 stride=1 与 stride=32 都是 44 周期， 两者比值为 1.0×，未能区分访问模式。

原因：bank conflict 损失的是吞吐，而依赖链一次只有一个在途请求，吞吐根本不是瓶颈。 必须让每个线程同时发出多个互不依赖的访存，冲突才会显现。

一般规律：测延迟用依赖链，测吞吐用独立操作。 用错了就会测出「没有效应」的假结论。

这里的 10.1× 只是时间差，机制在 L2.6 被直接读了出来

本节测到的是时间比，「这是 bank conflict」是一个解释，不是观测。 时间变慢有很多可能的原因。

L2.6 在 spark 上用硬件计数器直接读了同一件事（那台机器能读性能计数器）： 同样的三元对照（stride 1 / 32 / 33），wavefront / request 分别是 1.00 / 32.00 / 1.00，冲突计数 0 / 6,094,848 / 0， 而 6,094,848=196,608×31 与请求数吻合。

判据是 wavefront/request 这个比值，不是时间。 它直接给出冲突路数。 时间比在那台机器上是 9.83×，与这里的 10.1× 同量级—— 但要注意这是两台不同的 GPU，能对上的是机制，不是绝对数值。 spark 计数器只覆盖 stride 1/32/33；中间 stride 的倍率来自 crater 与 L40S 的计时， 没有对应的硬件计数器，不能把计时倍率直接当成冲突路数。

理论上界是 32×（一次广播变成 32 次串行事务），实测 10× 是因为循环本身的加法、 索引计算等开销稀释了。10 倍已经足够说明问题： 一个 stride 写错，kernel 的访存部分慢一个数量级。 这正是 L2.4 里 swizzle 布局要消灭的东西。

带宽-延迟积与访存并行度

Little's Law：

达到的带宽=在途字节数延迟⟹在途字节数=带宽×延迟

代入实测值：

  • 5090：1674 GB/s×320.3 ns= 536 KB 必须始终在途（E 表 384 MiB 行的同口径实测为 1699×321.8=534 KB）
  • L40S：681 GB/s×253.4 ns= 173 KB

达到更高带宽通常需要更多并发访存。 在这组测量中， 5090 的带宽是 L40S 的 2.5 倍，而所需的在途请求数为 3.1 倍。

实测并发扫描印证了这一点：

blocks/SM 5090 GB/s 占峰值 L40S GB/s 占峰值
1 1550 93% 651 96%
2 1680 100% 669 98%
4 1690 101% 680 100%
8 1695 101% 681 100%

好消息是：2 个 block/SM（16 warp）就已经饱和。因为每个 warp 的一次 float4 load 就是 32 × 16 B = 512 B 在途，2720 个 warp × 512 B = 1.39 MB ≫ 536 KB。

但这有个前提：访存是"宽"的（float4）且合并良好。 在“每个 warp 只有一个这类在途 load”的简化模型中， 改为每线程读取一个 float 后，每 warp 从 512 B 降到 128 B， 维持相同在途字节数需要 4 倍的 warp 数。真实执行还受发射率和队列容量约束。 如果访存不合并，情况还要更糟。这就是 L2.3 的核心。

把横轴从 blocks/SM 细化成每 SM 常驻 warp 数（固定 1 GB 工作集、单遍扫描）， 饱和过程看得更清楚：

warps/SM 1 2 4 8 16 24 32 48
5090 GB/s 243 493 962 1550 1680 1693 1695 1700
L40S GB/s 241 473 699 732 755 753 751 741

1–8 warp 近似线性，说明瓶颈是"在途请求数不够"；8 warp 已到峰值的 92%， 16 warp 基本饱和，之后收益消失。真实 kernel 不需要把 48 个 warp 都填满。 需要注意的是，这里每个 warp 的在途请求并不止一个：编译器会把 grid-stride 循环展开，同时发射多个独立 load。按"每 warp 只有一个在途 float4 load" 的朴素 Little's Law 会估出约 1072 个 warp（6.3 个/SM），比实测饱和所需的 8 个/SM 还多；真实并发放大来自每个 warp 的 ILP。

访存的"有效载荷"与 DRAM 实际流量是两回事。 固定 1 GiB span， 只把相邻访问的 stride 从 1 个 float4（16 B）加到 32 个，结果：

stride（float4） 有效载荷 有效载荷带宽 估算 DRAM 流量 DRAM 带宽
1 1073.7 MB 1689.8 GB/s 1073.7 MB 1689.8 GB/s
2 536.9 MB 847.6 GB/s 1073.7 MB 1695.3 GB/s
4 268.4 MB 844.4 GB/s 536.9 MB 1688.9 GB/s
8 134.2 MB 801.5 GB/s 268.4 MB 1603.0 GB/s
16 67.1 MB 626.8 GB/s 134.2 MB 1253.5 GB/s
32 33.6 MB 601.2 GB/s 67.1 MB 1202.5 GB/s

（crater 实测。DRAM 流量按 32 B sector 粒度估算：stride 为 1 时两个相邻 float4 共用同一 sector；stride ≥ 2 时每次 load 独占一个 sector， 所以有效载荷减半、DRAM 流量不变。L40S 上同一张表的趋势一致， stride=1 为 709.0 GB/s，stride=32 时有效载荷带宽降到 208.5 GB/s。）

stride=2 的有效载荷带宽腰斩，但 DRAM 带宽几乎不动，说明带宽并没有变差， 只是每次事务搬回的字节用不上了。stride 增到 16/32 后 DRAM 带宽也开始下降， 这时总 load 指令数已经少了 16–32 倍，访存并行度不足以填满流水线。 非合并访问要先问"sector 用了几成"，再谈带宽。这就是 L2.3 的核心。 同一次运行的 stride=1 为 1689.8 GB/s，与旧实验 B 在 1 GiB 工作集下测到的 1674 GB/s 相差约 0.9%，属于单遍扫描的批间波动；后文 Little's Law 仍用旧值， 不改变结论。

工程实现 · 源码解析：硬件容量如何约束 tile

L0.1 的 kernel trace 里，prefill 阶段跑的 attention kernel 全名是：

void flash::flash_fwd_splitkv_kernel<
    Flash_fwd_kernel_traits<128, 64, 128, 4, false, false, cutlass::bfloat16_t,
                            Flash_kernel_traits<128, 64, 128, 4, cutlass::bfloat16_t> >,
    true, false, false, false, ...>

按 FlashAttention-2 的 traits 约定，前四个参数是 <kHeadDim, kBlockM, kBlockN, kNWarps>，即 head_dim=128、Q tile 64 行、KV tile 128 行、4 个 warp。

第一个参数有个硬交叉验证：Qwen3-1.7B 的 config.json 里 "head_dim": 128（L0.1 原始现场 ①）。 对上了。

现在用本章测出的硬件常数解释后三个数字。

一个 tile 要在共享内存里放下 Q、K、V 三块（bf16，2 字节）：

64×128×2⏟Q = 16 KB+128×128×2⏟K = 32 KB+128×128×2⏟V = 32 KB=80 KB

而本机实测 sharedMemPerBlockOptin = 99 KB。80 < 99，刚好放得下。

如果把 kBlockN 从 128 提到 256：16+64+64=144 KB > 99 KB，编译期就会失败。 如果降到 64：smem 只用 48 KB，但每个 Q tile 要多循环一倍次数，K/V 循环次数翻倍，但每次块大小减半，总读取量不因此自动翻倍。

通过共享内存容量的静态预算，可以直接排除超出硬件物理上限的候选尺寸。但需强调的是，能够装得下并不等同于性能最优：实际算子中的多级双缓冲流水线（double buffering）、共享内存复用、寄存器分配压力以及指令级并发调度等，都会共同决定最终的最优配置。因此，硬件常数界定了可行参数的搜索边界，而具体的参数调优仍需结合 kernel 源码的内存编排与实测数据综合判定。

resident blocks 由哪项资源限制

"80 KB < 99 KB"只说明这个 tile 能启动，没有说明同一 SM 上能同时放几个。 把 L0.1 实测到的真实 launch 参数与设备上限放在一起算：

设备上限（cudaDeviceGetAttribute，sm_120）：共享内存 100 KiB/SM、寄存器 256 KiB/SM、 线程 1536/SM、block 槽 24/SM。寄存器按 warp 以 256 个（32-bit）为单位分配， 共享内存按 256 B 取整。一个 block 的常驻数量取四项约束的最小值。

kernel 线程/block 寄存器/block smem/block grid 上限（线程/寄存器/smem/槽） 常驻 限制
QKV GEMM（CUTLASS wmma） 32 4,096 16,896 B 256 48/16/6/24 6 smem
attention prefill（FA2 64×128） 128 32,768 81,920 B 16 12/2/1/24 1 smem
attention decode（FA2 64×64） 128 23,552 49,152 B 8 12/2/2/24 2 寄存器与 smem 同时到 2
decode GEMM（cuBLAS gemvx） 64 10,752 272 B（取整 512 B） 37,984 24/6/200/24 6 寄存器

（网格与资源占用来自 L0.1 的 profiler 工件，见 results/crater/0.1/20260913-lifecycle/op-kernel/op_to_kernel.json；设备上限由 labs/L1/mem_hierarchy.cu revision 与独立属性查询实测。）

QKV GEMM 的 smem 还能从 kernel 名反推，交叉验证这套算法。 cutlass_80_wmma_tensorop_bf16_s161616gemm_bf16_16x16_128x2_tn_align8 中， 16x16 是 threadblock 的 M×N，与 256 个 block 的 grid 吻合； 128x2 对应 K tile 与流水级数（两者相乘为 256）。按 K=128、两级流水计算， bf16 双缓冲的 A、B 两份 tile 是 2×(16×128+128×16)×2 B=16,384 B， 实测 16,896 B，多出的 512 B 是布局 padding。名字、公式、profiler 三者一致。

几个直接结论：

  • 能启动不等于高占用。 attention prefill 的 80 KB tile 只允许 1 个 block/SM， 4 个 warp 的占用率是 8.3%；QKV GEMM 因 16.9 KB smem 只能放 6 个 block/SM， 占用率 12.5%。
  • 限制项会随 tile 改变。 decode attention 把 KV tile 从 128 减到 64 后， smem 从 80 KB 降到 48 KB，常驻从 1 变成 2，限制项也从纯 smem 变成 寄存器与 smem 同时卡在 2。
  • 实际是否用满常驻容量，还要看 grid。 attention prefill 只有 16 个 block， 即使每 SM 能放 1 个，也只用到 16 个 SM；QKV GEMM 256 个 block 约 1.5 个/SM， 远低于 smem 允许的 6 个。小 batch 场景的瓶颈是"总 block 数不够"， 不是占用率；decode GEMM 有 3.8 万个 block，才真正吃满寄存器允许的 6 个/SM。

把 tile 放回完整的存储层级看，寄存器与 smem 决定"能同时算多宽"， L2 与 DRAM 决定"数据喂不喂得上"。QKV GEMM 的权重是 4096×2048 的 bf16（16 MiB），prefill 输入只有 11 个 token，一次投影的 FLOP 约 1.84×108， 算术强度约 11 FLOP/B；按实测 1674 GB/s 的 DRAM 带宽，读一遍权重需要约 10 µs， profiler 实测 13.2 µs，约为 DRAM roofline 的 76%。它的 tile 小、寄存器多， 但真正的上界是权重的显存读取，不是 16×16 tile 的计算能力。 attention prefill 是另一个极端：Q/K/V 合计不到 0.1 MiB，80 KiB tile 一次装下， 16 个 block 每个只跑 6.8 µs，瓶颈是 block 数太少、延迟没被掩盖， 而不是 L2 或 DRAM 带宽。

tile 改动后的容量预测

同一个 smem 预算可以直接预测改动：

head_dim kBlockM kBlockN Q K V 合计 单 block 能否启动 smem 允许的常驻
128 64 128 16 KiB 32 KiB 32 KiB 80 KiB 是 1
128 64 256 16 KiB 64 KiB 64 KiB 144 KiB 否 —
256 64 64 32 KiB 32 KiB 32 KiB 96 KiB 是 1

kBlockN=256 需要 144 KiB，超过单 block 上限 99 KiB，也超过每 SM 的 100 KiB， 连启动都不行。head_dim 翻倍到 256 时把 kBlockN 砍到 64，总 smem 96 KiB， 仍然只够 1 个 block/SM——占用率不会因为 tile 变小而回来。 想给 K/V 再加一级双缓冲，等于把 32 KB 翻倍到 64 KB，80 KB 变 144 KB， 同样放不下。这就是"先算容量、再调 tile"的硬边界；FA2 traits 的选择 不是审美偏好，而是被这张表约束出来的。

（计算过程与真实 kernel 的输入见 results/crater/1.1/20260913-memory-hierarchy-revision/c_tile_budget.json； 每 SM 共享内存上限是 100 KiB，单 block 上限是 99 KiB，两者不能混用。）

kNWarps=4 呢？4 warp = 128 线程。回到带宽-延迟积： 一个 block 要能持续供上访存，同时寄存器又不能溢出（每 SM 只有 256 KB 寄存器文件）。 warp 太少喂不饱访存带宽，过多则每线程可用寄存器配额受限，累加器放不下便会发生寄存器溢出（register spilling）并退化至本地内存。

硬件约束思维的价值

单纯记住「FlashAttention 采用 64×128 tile」并无工程实用价值；真正重要的是理解约束参数取值的底层物理边界：共享内存上限、寄存器文件配额以及带宽-延迟积决定的访存并行度。当迁移至新架构、调整数据精度或 head_dim 时，首先根据硬件约束推导可行的参数空间，再进行针对性基准测试。L3.2 将沿着这一逻辑，系统梳理 FA1 至 FA4 在不同代际硬件演进下的 tile 演变历程。

另一处：sharedMemPerBlockOptin 为什么是 "Optin"

本机实测每 block 最多 99 KB，但默认只给 48 KB。超过 48 KB 必须显式申请：

cudaFuncSetAttribute(kernel, cudaFuncAttributeMaxDynamicSharedMemorySize, 99 * 1024);

历史原因：48 KB 是 Kepler/Maxwell 时代的上限，为了向后兼容， 超出部分要求 kernel 主动"opt in"。所有现代 attention/GEMM kernel 都会调这个 API， 忘了调就会在启动时报 invalid argument —— 一个很常见又很难查的错误。

而且 L1 与共享内存是同一块 128 KiB 物理 SRAM 分割出来的。 申请 99 KB 共享内存，L1 就只剩 29 KB。这解释了实测里的一个现象： 128 KiB 工作集的指针追逐已经掉到 285 周期，而不是 L1 的 44 周期—— 因为可用的 L1 数据缓存并没有整整 128 KiB。

工程实现 · 自己写一遍

labs/L1/mem_hierarchy.cu。默认 A–D 四个基础实验，revision 模式再加 E–H 四个修订实验，每个都有一个方法学要点：

A. 测延迟 → 必须用依赖链 + 走遍工作集

__global__ void chase_kernel(const uint32_t* __restrict__ buf, int steps,
                             uint32_t* out, long long* cycles) {
    uint32_t idx = 0;
    for (int i = 0; i < steps; ++i) idx = buf[idx];   // 预热
    long long t0 = clock64();
    for (int i = 0; i < steps; ++i) idx = buf[idx];   // ← 每次都依赖上一次
    long long t1 = clock64();
    *out = idx;                                       // 防止整个循环被优化掉
    *cycles = t1 - t0;
}

三个必须做对的地方，缺一个结论就是假的：

const size_t LINE = 128;                    // ① 每个链节点占一整条 cache line
size_t n_lines = bytes / LINE;
std::shuffle(order.begin() + 1, order.end(), rng);   // ② 随机，打掉硬件预取器
size_t steps = std::max((size_t)min_steps, n_lines * 3);  // ③ 走遍整个工作集 3 遍

分配容量不等于实际访问的工作集

若对所有 buffer 固定访问 4096 步，对 1 GiB 的 buffer， 4096 次随机访问只碰到 4096 条 cache line ≈ 512 KB —— 整个"工作集"一直待在 L2 里。 此时，分配容量从 1 MiB 增至 1 GiB，结果都约为 360 周期，未测到显存访问延迟。

改成 steps = n_lines × 3 之后，三段平台立刻显现。 曲线没有变化时，应先确认实验实际访问了足够多的数据。

B. 时钟自校准 → 不要相信 cudaDevAttrClockRate

clock64() 数的是真实 SM 周期，但要换算成纳秒就得知道频率。 cudaDevAttrClockRate 报的是基频（5090 是 2.41 GHz），而 GPU 会 boost。 自校准的做法是同时用两种计时器：

CHECK(cudaEventRecord(ea));
chase_kernel<<<1, 1>>>(...);
CHECK(cudaEventRecord(eb));
CHECK(cudaEventElapsedTime(&ms, ea, eb));      // 墙钟
CHECK(cudaMemcpy(&cyc, d_cyc, ...));           // 周期
double ghz = (double)(cyc * 2) / (ms * 1e6);   // 两者相除 = 本次运行的实际频率

标定实测：5090 得 2.90 GHz（基频 2.41，最大 boost 3.09 —— 落在区间内，合理）； L40S 得 2.51 GHz（基频 2.52）。

标定 kernel 必须运行足够长。运行 4096 步（约 0.1 ms）， kernel launch 的几微秒被算进 event 时间，把频率压到 1.45 GHz —— 低了整整一倍。 改成 200 万步（约 0.1 秒）后才稳定。

C / D 的要点已在上面机制部分讲过：测吞吐要用独立操作； 测饱和带宽要用远超 L2 的工作集且只扫一遍。

动手 lab

nvcc -O3 -std=c++17 -arch=sm_120 -o mem_hierarchy labs/L1/mem_hierarchy.cu

-arch 必须匹配你的卡（5090 是 sm_120，L40S 是 sm_89）。 架构不匹配时 nvcc 不会报错，驱动会 JIT PTX，性能特征可能变化（L2.2 详解）。

revision 模式的四个实验分别对应本章的四处修订：E 用随机/连续/跨页三种 依赖链扫 L2 的 0.25–4 倍，区分"依赖延迟"与"地址可预取的独立吞吐"； F 固定 1 GiB span 扫 stride，并按 32 B sector 估 DRAM 实际流量； G 把 blocks/SM 细化成每 SM 常驻 warp 数，给出带宽饱和曲线； H 把 bank conflict 从 1/32 两个点扩展到 1/2/4/8/16/32。 一次完整运行在 crater 约 32 秒（含 384 MiB 链），输出约 60 行。

消融建议

改什么 你应该看到什么
把 LINE 从 128 改成 32 每条 cache line 上放 4 个链节点 → 实际触碰的字节数只有 1/4，三段平台会退化。该对比可直观展示缓存行空间局部性变化对台阶特征的削弱效应
把随机链换成连续链（revision 的 E） 延迟基本不变，而不是"预取后大幅变快"——依赖链的下一地址来自数据，预取器无法提前发出请求
把连续链再改成跨 2 MiB 页（revision 的 E） 本机的 384 MiB 工作集只有 192 个页，TLB 装得下，延迟与随机链相同；这验证的是依赖链口径，不是 TLB 没有成本
smem_kernel 里 stride 试 2/4/8/16（revision 的 H） 冲突倍率从 ~1.0× 起步，随 stride 增加到 ~10×，但远低于"撞了几个 bank"的朴素计数
bw_read_kernel 里把 float4 换成 float 每 warp 在途字节从 512 B 掉到 128 B，饱和需要的 warp 数应该涨约 4 倍
把 stride 从 1 加到 32（revision 的 F） 有效载荷带宽从 1696 掉到 599 GB/s，而按 32 B sector 估算的 DRAM 带宽先保持峰值、再因并行度不足下降
在 worldvln 上改 CUDA_VISIBLE_DEVICES 到 3 GPU3 在另一个 NUMA 节点，观察是否影响（应该不影响显存延迟，只影响 H2D —— 见 L1.3）

倒数第二项实验用于观察访存宽度变化后，达到峰值带宽所需的并发是否改变。

前沿

方向 与本章的关系
异步拷贝与 TMA Ampere 的 cp.async 让"搬数据到 smem"不占寄存器、不阻塞计算；Hopper 的 TMA 进一步把整块搬运交给专用硬件。本质都是在提高"在途字节数"以逼近带宽-延迟积（L1.2、L2.4）
分布式共享内存（DSMEM） Hopper 起，同一 cluster 内的 block 可以互相访问 smem，等于把有效 smem 容量放大到 cluster 级。这直接放宽了本章算出的 99 KB 上界
Tensor Memory（TMEM） sm_100 独有的、tensor core 专用的片上存储，把累加器从寄存器文件里搬出去。sm_120 没有（L1.2）
L2 驻留控制 cudaStreamSetAttribute 的 access policy window 可以把某段显存"钉"在 L2 里。对 KV cache 的热前缀理论上有用，但目前主流引擎都没用（L5.2 的一个开放方向）
FlashAttention-4 的软件仿真 exp() 因为 MUFU（超越函数单元）的吞吐跟不上 Blackwell 的 tensor core，FA4 改用多项式近似在 FMA 单元上算 exp。这是"某一级硬件资源成为瓶颈后，算法绕过它"的典型（L3.2）

除本章实测外的内容来自各自文档与论文，尚未复现未实测。

陷阱

1. 用独立且顺序的访问测延迟。 如果下一次地址预先已知，顺序访问会让预取器把延迟掩盖，测出的显存延迟可能只有真实值的 1/5。测延迟要用依赖链；但在依赖链里改成顺序或跨页并不会让延迟变快（E 实测），因为下一地址来自数据，预取器同样发不出请求。

2. 工作集没走遍。 本章踩过：固定步数的指针追逐，对大 buffer 而言只触碰了很小一部分，三段平台会消失。

3. 用依赖链测吞吐 / 用独立操作测延迟。 两者测的是不同的东西，用反了会得到"没有效应"的假结论。本章用不同依赖关系对照了这两种测量口径。

4. 相信 cudaDevAttrClockRate。 那是基频。要么自校准，要么只报周期数不报纳秒。

5. 标定 kernel 太短。 launch 开销几微秒，对 0.1 ms 的 kernel 是 5% 误差，对更短的就是数倍误差。

6. 忘了 smem 和 L1 是同一块 SRAM。 共享内存 carveout 会影响可用于 L1 的容量，但不能用总容量减申请值直接确定有效 L1 容量。这解释了为什么 128 KiB 工作集的延迟已经不是 L1 的 44 周期。

7. 把"占用率高"当成"性能好"。 实测 2 个 block/SM 就饱和了带宽，再往上加没有收益。占用率只是掩盖延迟的手段，不是目标（L2.6 会展开 occupancy vs ILP 的取舍）。

8. 用 cache line 大小估 DRAM 流量。 非合并访问下，一个 128 B line 可能只用一个 32 B sector。按 line 计流量会算出超过峰值带宽的假结果；应按 32 B sector 粒度核算（F 实测：stride=2 时有效载荷腰斩，DRAM 带宽不变）。

9. 把"能装进 smem"当成"能高占用"。 80 KB tile 能启动，但每 SM 100 KB 只够 1 个 block，占用率 8.3%。resident blocks 取线程、寄存器、smem、block 槽四项最小值，限制项还会随 tile 改变。

自测题

1. 我的 kernel 每个线程只 load 一个 float（4 字节），访存完全合并。要打满 5090 的显存带宽，需要多少个 warp 同时在跑？

带宽-延迟积 = 1674 GB/s × 320.3 ns ≈ 536 KB 必须在途。

每个 warp 的一次合并 float load = 32 线程 × 4 B = 128 B。

假设每个 warp 同时只有 1 个未完成的 load：

536KB/128B=4288 个 warp

而全卡最多常驻 170 SM × 48 warp = 8160 个 warp。所以需要 52% 的占用率。

如果换成 float4（每 warp 512 B），只要 1072 个 warp = 13% 占用率就够了—— 这就是为什么向量化访存（float4/LDG.128）几乎是所有 memory-bound kernel 的第一步优化。

注意这个估算的假设：每 warp 只有 1 个在途 load。真实情况下编译器会展开循环、 同时发多个独立 load，所需 warp 数会更少。实测（[D]）显示 2 blocks/SM 即饱和， 正是因为编译器为 float4 循环做了展开。

2. 为什么 5090 的延迟每一级都比 L40S 高，带宽却高 2.5 倍？这对 LLM 推理意味着什么？

GDDR7 用更多的 bank、更深的流水、更高的信号速率换带宽，代价是单次访问的往返路径更长。 L2 变大（同为 96 MiB 但 Blackwell 的分片更多、跨片距离更远）也会增加延迟。 这是带宽与延迟的经典取舍，不是"5090 更差"。

对 LLM 推理的影响：

  • decode：几乎不受影响。decode 是大规模并行访存（几千个 warp 同时读权重和 KV）， 延迟被并发完全掩盖，只有带宽重要。所以 5090 在 decode 上快 2.48×（L0.3 实测）。
  • 有长依赖链的小 kernel：受影响。比如采样里的某些串行归约、 block table 的指针追逐、以及 CPU-GPU 同步点附近的小操作。
  • 一般规律：现代 GPU 的设计假设就是"你有足够多的并行度"。 如果你的负载没有，你拿不到它标称的任何好处。
3. FlashAttention 的 tile 是 <head_dim=128, BlockM=64, BlockN=128, 4 warps>。如果我用一个 head_dim=256 的模型，tile 会怎么变？为什么？

smem 需求变成：

64×256×2⏟Q=32KB+128×256×2⏟K=64KB+128×256×2⏟V=64KB=160 KB

远超 99 KB 上限，编译不过。必须缩小 tile，通常是把 kBlockN 砍到 64：

32+32+32=96 KB<99 KB✓

代价：KV tile 减半意味着每个 Q tile 要循环两倍次数，循环次数翻倍；总 K/V 流量还取决于缓存与循环组织，不能直接写成翻倍。 所以 head_dim 越大，attention 的实际效率越低——这是一个纯粹由 smem 容量决定的硬约束。

（这也解释了为什么大部分模型的 head_dim 停在 128：再大就打不满 tensor core 又装不下 tile。 DeepSeek 的 MLA 之所以能用 576 维的压缩 KV，是因为它的 kernel 是专门重写的， 不是通用 FlashAttention —— L3.3。）

4. 我把 GEMM 的 tile 从 128×128 改成 64×64，smem 用量降到 1/4，占用率翻倍。性能会变好吗？

大概率变差。 因为 tile 变小会让数据复用率下降。

对 M×K 乘 K×N 的 tile GEMM，一个 T×T 的输出 tile 需要读入 2TK 个元素， 产出 T2 个结果，算术强度 ∝T。tile 边长减半 → 算术强度减半 → 访存量翻倍。

用本章的数字：L1 与显存的带宽比是 16:1。tiling 的全部价值就是把复用留在 smem 里。 tile 变小 = 少复用 = 更多流量掉回 L2/显存。

而占用率翻倍带来的收益是有限的——[D] 实测显示 2 blocks/SM 就已经饱和带宽， 更高的占用率买不到更多带宽。

这就是 occupancy 的经典误区：占用率是掩盖延迟的手段，一旦延迟已经被掩盖住， 再提高它只会挤占寄存器和 smem，反而伤害每线程的工作效率（ILP）。L2.6 会用 ncu 量化这个取舍。

5. 用本章的数字估算：Qwen3-1.7B 在 batch=1、ctx=1024 时 decode 一步，理论上要多少纳秒？和 L0.3 实测的 4.48 ms 差多少？

L0.2 算过：这一步要搬 3.441 GB 权重 + 0.117 GB KV = 3.558 GB。

按本章实测的显存带宽 1674 GB/s：

3.558 GB/1674 GB/s=2.126 ms

（L0.2 用的是 probe_hw.py 的 copy 带宽 1519 GB/s，得 2.34 ms。两个分母都合理， 差别在于 copy 计入读+写、本章只读。只读带宽是更贴切的分母，因为 decode 主要是读权重。）

实测 GPU 忙时 3.085 ms，墙钟 4.48 ms。

拆解差距： - 2.126 ms → 3.085 ms（GPU 忙时）：效率 69%。差的部分是 kernel 效率、 非 GEMM 小算子、以及 attention 那部分不是纯顺序读。 - 3.085 ms → 4.48 ms（墙钟）：1.4 ms 的 CPU launch 开销（444 次 × 2.68 µs ≈ 1.19 ms）。

上述差值只是待解释的残差，不是已测得的互斥时间段。带宽估计、GPU 忙时与墙钟时间来自不同口径，需要同次运行时间线才能做归因。 每一段对应一层优化：带宽（换卡/量化）、kernel 效率（L2）、launch 开销（CUDA Graph，L5.4）。

6. 一个 kernel 的 block=128 线程、每线程 200 个寄存器、smem/block=64 KiB。smem/SM=100 KiB、寄存器/SM=256 KiB、线程/SM=1536、block 槽/SM=24。每个 SM 能常驻几个 block？限制项是什么？把 smem 降到 40 KiB 后会怎样？

寄存器按 warp 分配：每 warp 200 × 32 = 6,400 → 取整到 256 的倍数得 6,400；4 个 warp 共 25,600 个寄存器。四项上限分别是：

  • 线程：1536 / 128 = 12
  • 寄存器：65536 / 25600 = 2
  • smem：102400 / 65536 = 1
  • block 槽：24

取最小值，常驻 1 个 block/SM，限制项是 smem，占用率 128 / 1536 = 8.3%。 把 smem 降到 40 KiB（40,960 B）后，smem 上限变成 2，四项最小值是 2， 限制项变成寄存器与 smem 同时卡在 2，占用率 16.7%。 这个例子说明："tile 能启动"和"每个 SM 能放几个"是两个问题； 改小一个资源后，限制项可能转移到另一项。
