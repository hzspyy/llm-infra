1.3

主机侧：NUMA、PCIe 与 DMA

沿主机到显存的路径，比较 pageable 与 pinned 内存、小块传输、NUMA 与 PCIe 拓扑；分析多流重叠还受哪些资源限制。

实测机器 crater (RTX 5090 D, PCIe 5.0) + worldvln (5× L40S, PCIe 4.0, 双 NUMA)数据日期 2026-09-10前置 L1.1（带宽-延迟积）

本章回答三个问题

  1. pin_memory=True 到底做了什么？为什么它能让传输快一倍？
  2. NUMA 亲和性对 GPU 传输有多大影响？（答案可能和你听说的不一样）
  3. H2D 与 D2H 能同时跑吗？决定它的不是拷贝引擎数量。

这一章关注数据如何在主机内存和 GPU 显存之间移动。 H2D 表示主机到设备，D2H 表示设备到主机；PCIe 是这里的连接通道。 NUMA 表示不同 CPU 对不同内存区域的访问成本可能不同。 我们会分别检查内存类型、传输大小和连接拓扑，而不是用一个带宽数字解释所有情况。

心智模型：主机内存、PCIe 与显存的连接

机制拆解

pinned 内存：为什么快一倍

pageable（普通）内存可以被操作系统换出到磁盘，物理地址随时可能变。 而 DMA 引擎只认物理地址、且传输期间地址不能变。所以 driver 必须：

  1. 分配一块临时的 pinned 缓冲
  2. CPU 把数据从 pageable 拷到 pinned（一次完整的内存拷贝）
  3. 从 pinned DMA 到 GPU

pinned（页锁定）内存由 cudaHostAlloc / pin_memory=True 分配， 内核保证它不被换出，物理地址固定 → 直接 DMA，省掉第 2 步。

实测（crater，PCIe 5.0，256 MB）：

h2d_pinned           47.2 GB/s
d2h_pinned           42.1 GB/s
h2d_pageable         23.6 GB/s        ← 恰好一半
d2h_pageable         15.3 GB/s
pinned 相对 pageable 的加速：H2D 2.00×，D2H 2.75×

H2D 正好 2.00×：因为多出的那次 CPU 拷贝要占用同样多的内存带宽。 D2H 更差（2.75×），因为写 pageable 内存还要处理页错误。

代价：pinned 内存不能被换出，占满物理内存会让整个系统变慢甚至 OOM。 所以引擎都用固定大小的 pinned 缓冲池，而不是把所有 host 张量都 pin 住。

传输大小：小块传输几乎全是开销

[B] 传输大小 vs 有效带宽（crater, pinned, H2D）
        大小      GB/s       耗时us    固定开销占比
      4 KB       0.8        5.3        100%
     16 KB       3.1        5.3        101%
     64 KB      12.3        5.3        101%
    256 KB      38.6        6.8         79%
      1 MB      45.0       23.3         23%
      4 MB      46.0       91.3          6%
     16 MB      46.8      358.8          1%
    256 MB      47.3     5675.0          0%

4 KB 到 64 KB 的耗时完全一样（5.3 µs） —— 这段全部是固定开销： kernel launch、DMA 描述符设置、同步。数据本身的传输时间可以忽略。

有效带宽=Stfixed+S/BWpeak

要达到峰值的 90%，需要 S≥9×tfixed×BW： crater 上是 9×5.3μs×47GB/s≈2.2 MB。

worldvln（PCIe 4.0）的固定开销是 11.3 µs，是 crater 的两倍多—— 主机 CPU 单核性能差（L1.1 里 kernel launch 也是 5.03 vs 2.68 µs，同一个原因）。

工程含义：PD 分离传 KV 时（L6.4），如果按 16 token 的块逐块传， 每块只有 1.8 MB（Qwen3-1.7B）—— 勉强够。但如果按更细的粒度传， 固定开销会吃掉一切。必须批量聚合。

NUMA：为什么这组传输测试的差异较小

worldvln 是双路 Xeon 8476C，GPU 分属两个 NUMA 节点：

GPU0  bus=16:00.0  numa_node=0
GPU1  bus=38:00.0  numa_node=0
GPU2  bus=4a:00.0  numa_node=0
GPU3  bus=a8:00.0  numa_node=1
GPU4  bus=d8:00.0  numa_node=1

常见建议是"把 pinned 内存分配在 GPU 所在的 NUMA 节点上"。测一下 2×2 矩阵：

内存/CPU 绑定 目标 GPU GPU 的 NUMA h2d_pinned d2h_pinned
node 0 GPU0 0（本地） 25.0 27.0
node 0 GPU3 1（跨节点） 25.0 27.0
node 1 GPU0 0（跨节点） 25.0 27.0
node 1 GPU3 1（本地） 25.1 27.0

四种组合完全一样。NUMA 亲和性对 H2D/D2H 没有可测量的影响。

这个负结果有两种可能的解释，必须用对照实验区分：

  • (a) 这台机器的跨 NUMA 链路根本不慢
  • (b) 跨 NUMA 确实慢，但 PCIe 更慢，瓶颈不在那里

把 GPU 拿掉，只测 CPU 侧内存带宽（labs/L1/numa_bandwidth.py）：

node distances:      node   0   1
                       0:  10  21          ← 跨节点"距离"是本地的 2.1 倍
                       1:  21  10

CPU 在 node0，内存绑 node0（本地）：  copy 20.5 GB/s   read 8.9 GB/s
CPU 在 node0，内存绑 node1（跨节点）：copy 16.0 GB/s   read 6.8 GB/s
                                      ↓ 慢 22%          ↓ 慢 24%
8 进程聚合（本地）：                   58.2 GB/s
8 进程聚合（跨节点）：                 61.6 GB/s → 之前测得，同量级

结论是 (b)：跨 NUMA 确实有 22–24% 的惩罚，但即使跨节点也能提供 远超 PCIe 4.0（25 GB/s）的带宽，所以 PCIe 始终是瓶颈，NUMA 的影响被完全掩盖。

什么时候 NUMA 又会重要起来

  1. PCIe 5.0 / CXL 上：管子变宽到接近内存带宽时，NUMA 惩罚就会显现。
  2. CPU 侧的重活：分词、detokenize、采样后处理、dataloader（L7.4）—— 这些是纯 CPU 内存访问，22% 的惩罚直接生效。
  3. GPUDirect RDMA：网卡与 GPU 跨 NUMA 时，惩罚会显现（L1.5、L6.1）。
  4. 统一内存 / Grace-Blackwell：CPU 与 GPU 共享内存空间时，NUMA 就是一等公民。

所以「绑 NUMA」的建议不是错的，只是在这台机器的这个测试上不生效。 知道原因，你才知道换台机器要不要重测。

P2P：真正决定带宽的不是 NUMA，是链路宽度

worldvln 五张卡的点对点带宽矩阵（单向，256 MB）：

             GPU0          GPU1          GPU2          GPU3          GPU4
GPU0      -            22.6(NODE)    11.3(NODE)    22.6(SYS )    22.6(SYS )
GPU1     22.6(NODE)     -            11.3(NODE)    22.6(SYS )    22.6(SYS )
GPU2     13.5(NODE)    13.5(NODE)     -            13.5(SYS )    13.5(SYS )
GPU3     22.7(SYS )    22.7(SYS )    11.3(SYS )     -            22.7(NODE)
GPU4     22.6(SYS )    22.7(SYS )    11.3(SYS )    22.7(NODE)     -

按链路类型汇总：
    NODE   n=8   中位 18.1 GB/s   范围 11.3 – 22.7
    SYS    n=12  中位 22.6 GB/s   范围 11.3 – 22.7

第一个反常：SYS（跨 NUMA）的中位数居然比 NODE（同节点）高。

第二个反常：所有涉及 GPU2 的传输都只有一半带宽（11.3–13.5）。

nvidia-smi topo -m 的链路标注解释不了这个。去查 PCIe 链路本身：

index, pcie.link.gen.current, gen.max, width.current, width.max
0,     4,  4,  16, 16
1,     4,  4,  16, 16
2,     4,  4,   8, 16      ← ★ GPU2 只跑在 x8
3,     4,  4,  16, 16
4,     4,  4,  16, 16

GPU2 的 PCIe 链路是 x8 而不是 x16（上限明明是 x16）。带宽正好减半。 把 GPU2 从统计里剔除，NODE 与 SYS 的中位数都是 22.6–22.7 GB/s，完全一致。

这对 L6 的分布式实验是硬约束

GPU2 的较窄链路可能限制包含它的集合通信，但不能据此断言每次 all-reduce 都慢一半。 影响还取决于算法、消息大小和实际拓扑。实验应单独比较包含与不包含 GPU2 的配置。

所以后面 L6.1 / L6.2 的实验必须： - 要么用 GPU0/1/3/4 四张卡（避开 GPU2） - 要么把 GPU2 的影响单独测出来并在结论里说明

不查这一步就跑分布式实验，会得到一堆无法解释的数字。

多流重叠：除了拷贝引擎，还要检查主机内存

H2D 与 D2H 走不同方向，理论上应该能完全重叠。实测：

机器 串行 并发 重叠收益
crater（PCIe 5.0） 12.16 ms 12.03 ms 1.01×（几乎没重叠）
worldvln（PCIe 4.0） 20.67 ms 11.86 ms 1.74×

第一反应是"crater 的拷贝引擎少"。查一下：

crater   asyncEngineCount = 2
worldvln asyncEngineCount = 2

一样。 所以不是引擎数量。

一个与这些数据相容的解释是主机内存带宽限制。全双工传输时，主机内存要同时承受 「被读走 H2D 的量」+「被写入 D2H 的量」：

机器 H2D D2H 需要的主存流量 实测主存聚合带宽 预测重叠比 实测重叠比
crater 47.2 42.1 89.3 GB/s 48.4 GB/s 48.4/47.2 = 1.03× 1.01×
worldvln 25.0 27.0 52.0 GB/s 58.2 GB/s（单节点） 封顶 2× 1.74×

crater 的预测 1.03× 与实测 1.01× 几乎重合。

原因也很直白：crater 是 AMD Ryzen 9 9950X3D，单路消费级双通道 DDR5； worldvln 是双路 Xeon 8476C，每路 8 通道。 PCIe 5.0 太快了，快到主机内存跟不上。

这是一个很有代表性的现象：当某一层被大幅加速后，瓶颈会跳到相邻的一层。 PCIe 从 Gen4 到 Gen5 翻倍，于是主机内存成了新的墙。

工程实现 · 源码走读：引擎在哪里用到这些

1. vLLM 的 pinned 缓冲池

L0.1 第 14 阶段的 _prepare_inputs 每步都要把 CPU 上算好的 token id、 位置、slot mapping、block table 传到 GPU。这些张量小（几 KB 到几百 KB）， 正好落在上面测出的"固定开销主导区"。

所以引擎不会每步 cudaHostAlloc，而是维护复用的 pinned 缓冲， 并且尽量把多个小张量打包成一次传输。这是"批量聚合"原则的直接体现。

2. KV 卸载：为什么值得

L5.2 的自测题算过一笔账：把 3000 token 的前缀 KV（344 MB）卸载到主机， 命中时再拉回来。用本章的数字：

  • crater（PCIe 5.0）：344MB/47.2GB/s=7.3 ms
  • worldvln（PCIe 4.0）：344/25.0=13.8 ms
  • 重算的成本：L5.2 实测 41.5 ms

即使在 PCIe 4.0 上，拉回来也比重算快 3 倍。 这就是 Mooncake / LMCache 那条路线的经济学基础（L6.4）。

而且注意 344 MB ≫ 2.2 MB 的"有效传输门槛"，固定开销可以忽略—— KV 卸载天然是大块传输，正好落在 PCIe 的舒适区。

3. PD 分离的 KV 传输：账不一样

L0.3 的自测题问过：prefill 在 L40S、decode 在 5090，KV 怎么传？

两台机器之间没有 PCIe 直连，只有以太网。即使有 100 GbE（12.5 GB/s）， 传 470 MB 也要 38 ms —— 比本机重算（L0.3 实测 prefill 4096 token 约 79 ms） 省不了多少，还多了一跳延迟。

所以 PD 分离在没有高速互连的集群上是不划算的——这正是 L0.2 前沿一节 提到的「fleet simulation 显示 PD 分离并非总是有利」的具体原因。 L6.4 会在 worldvln 内部（有 PCIe P2P，22.6 GB/s）真跑一次。

工程实现 · 自己写一遍

三个脚本，每个对应一类实验。要点是记录上下文：

def numa_context() -> dict:
    """把当前进程实际的 NUMA / CPU 绑定情况记下来。

    这非常重要：如果你不记录"这次跑在哪个节点上"，
    NUMA 实验的结果就无法解释，也无法复现。
    """
    out = {"cpu_affinity": sorted(os.sched_getaffinity(0))[:8],
           "n_cpus_allowed": len(os.sched_getaffinity(0))}
    r = subprocess.run(["numastat", "-p", str(os.getpid())], ...)
    out["numastat"] = r.stdout.strip().splitlines()[-3:]
    return out

跑 NUMA 实验时，输出里必须能看到 前几个核 [0,1,2,...] 还是 [48,49,50,...]， 否则你无法证明 numactl 真的生效了。本章的输出里就有这一行。

从 sysfs 读 GPU 的 NUMA 归属，而不是靠猜：

def gpu_numa_node(idx: int) -> str:
    bus = nvidia_smi_query("pci.bus_id", idx).lower().removeprefix("00000000:")
    p = Path(f"/sys/bus/pci/devices/0000:{bus}/numa_node")
    return p.read_text().strip() if p.exists() else "?"

建议你做的消融

改什么 你应该看到什么
--mb 1（1 MB 传输） 有效带宽掉到峰值的 ~50%（固定开销占 23%）
在 crater 上重复 NUMA 实验 crater 是单 NUMA 节点（numactl --hardware 只有 node0），实验无从做起——这本身是个信息
把多流实验改成两个 H2D（同方向） 应该完全不重叠：同方向共用一个拷贝引擎且共享 PCIe 上行带宽
在 worldvln 上只用 GPU0/1/3/4 重跑 P2P NODE 与 SYS 的差异应该消失（GPU2 是唯一的异常）
传输时用 nvidia-smi -q -d PCIE 观察链路 空闲时链路会 downtrain（crater 空闲报 gen.current=1，实际是 Gen5）——必须在传输中查

最后一行是个重要陷阱：本章第一次查 crater 的 PCIe 代数时看到 gen.current = 1， 差点得出"PCIe 1.0"的错误结论。实际是 ASPM 省电降速，一有流量立刻回到 Gen5。

单线程的绝对值远低于这颗 CPU 的峰值（受单线程访存并行度限制， 和 L1.1 里 GPU 的 Little's Law 是同一个道理）。要看的是比值，不是绝对值。

聚合（8 个并行进程）：crater 48.4 GB/s，worldvln 单节点 58.2 GB/s。

⑤ 拷贝引擎数量：一个被证伪的假设

两台机器的拷贝引擎数量完全一样，但重叠收益是 1.01× vs 1.74×。 硬件属性解释不了这个差异，必须去找别的原因（主机内存带宽）。

前沿

方向 与本章的关系
GPUDirect Storage (GDS) 让 NVMe 直接 DMA 到显存，绕过主机内存与 CPU。本章测出主机内存已经成为 PCIe 5.0 的瓶颈——GDS 正是绕开它的手段（L1.5）
GPUDirect RDMA / IBGDA 网卡直接读写显存，绕过主机。DeepEP 的 low-latency kernel 依赖它；NVSHMEM 的 IBGDA 更进一步让 GPU 直接驱动网卡（L6.3）
NVLink-C2C / Grace-Hopper / GB10 CPU 与 GPU 之间 900 GB/s 的一致性互连，本章的"32 倍窄管子"不复存在。spark 上的 GB10 会在 L8.5 做对照
CXL 把内存挂到 PCIe 通道上，NUMA 的层级会更多、更复杂。本章的"NUMA 被 PCIe 掩盖"结论在 CXL 上会反转
KV 卸载与多级存储 Mooncake 的 HBM/DRAM/SSD 三级；本章的传输大小实验决定了它的块粒度必须足够大（L6.4）

除本站实测外的内容来自各自文档，未在本站复现未实测。

陷阱

1. 用 pageable 内存做大批量传输。 白白慢一倍。但也别把所有东西都 pin 住—— pinned 内存不可换出，会挤压系统。

2. 小块传输。 低于约 250 KB 时几乎全是固定开销。批量聚合。

3. 空闲时查 PCIe 链路代数。 ASPM 会 downtrain，本章差点因此得出"crater 是 PCIe 1.0"。

4. 不查链路宽度就跑多卡实验。 worldvln 的 GPU2 跑在 x8， 带宽减半，会污染所有 5 卡集合通信的结果。

5. 相信"NUMA 一定要绑"。 本章实测在 PCIe 4.0 + DMA 的场景下毫无影响。 但也别反过来相信"NUMA 不重要"——CPU 侧确实差 22–24%。 结论必须带上场景。

6. 用硬件属性解释性能差异而不验证。 asyncEngineCount 两台都是 2， 却有 1.01× vs 1.74× 的差异。属性只是必要条件。

7. 忘了记录绑定是否生效。 numactl 可能因为权限或参数问题静默失效。 输出里必须有 CPU 亲和性列表作为证据。

自测题

1. 我要把 16 GB 的模型权重从主机加载到 GPU。crater 上理论最快多久？实际会更慢吗？

理论：16GB/47.2GB/s=339 ms（pinned，大块传输）。

实际会更慢，原因有三：

  1. 权重先要从磁盘/NFS 读到主机内存。如果没有 page cache 命中， 这一步可能比 PCIe 传输还慢（L1.5 会测）。
  2. safetensors 是 mmap 的（L0.1 原始现场 ②）， 传输时页会按需触发缺页，实际路径是 pageable 而非 pinned → 按本章实测可能慢到 2×，即 ~680 ms。
  3. 逐张量传输：310 个张量（Qwen3-1.7B）， 其中很多是几 KB 的 norm 权重，落在固定开销区。

这就是为什么引擎的模型加载都做了专门优化：多线程、pinned 缓冲池、 大张量分块流水。vLLM 启动日志里的 Loading safetensors checkpoint shards 那几秒， 主要就花在这里。

2. 我在 worldvln 上跑 4 卡 TP（GPU0-3）。每步 all-reduce 的时间下界是多少？GPU2 会有多大影响？

先算通信量。TP 的每层要做两次 all-reduce（attention 后、FFN 后）， 每次的数据量 = batch × seq × hidden × 2 字节。

以 Qwen3-1.7B、batch=32、decode（seq=1）为例： 32×1×2048×2=128 KB 每次，28 层 × 2 次 = 56 次，共 7 MB。

但 128 KB 落在"固定开销主导区"（本章测出 worldvln 的固定开销 11.3 µs）。 56 次 × 11.3 µs = 0.63 ms 纯开销，而 decode 每步本来才 11 ms（L0.3 实测）。

GPU2 的影响：ring all-reduce 的完成时间由最慢的边决定。 GPU2 的边只有 11.3 GB/s（其他 22.6），所以整个 ring 降到一半速度。

结论：小 batch 的 TP decode 在没有 NVLink 的机器上， 通信开销可能吃掉一半以上的时间，而且 GPU2 会让它雪上加霜。 L6.2 会实测这个，本题的估算是那次实验的预测值。

3. 为什么 crater 的 PCIe 更快（47 vs 25 GB/s），多流重叠反而更差（1.01× vs 1.74×）？

因为瓶颈跳到了主机内存。

全双工传输需要主机内存同时承受「H2D 读走的量 + D2H 写入的量」：

  • crater：47.2+42.1=89.3 GB/s，而实测主存聚合只有 48.4 GB/s → 做不到
  • worldvln：25.0+27.0=52.0 GB/s，主存有 58.2 GB/s（单节点）→ 勉强够

预测：crater 的重叠比 ≈ 48.4/47.2=1.03。实测 1.01×。

根因是平台差异：crater 是单路消费级（Ryzen 9950X3D，双通道 DDR5）， worldvln 是双路服务器（Xeon 8476C，每路 8 通道）。

一般规律：某一层被大幅加速后，瓶颈会跳到相邻的一层。 这在整套材料里会反复出现——PCIe→主存、算力→带宽（L0.2）、 tensor core→MUFU（L3.2 的 FA4）。

4. 我读到一篇博客说「pinned memory 能带来 10 倍加速」。可信吗？

大概率不可信，或者场景很特殊。

理论上限很清楚：pageable 多了一次 CPU 内存拷贝。 如果主机内存带宽远大于 PCIe，这次拷贝的代价约等于一次 PCIe 传输， 所以上限是 2×。本章实测 H2D 恰好 2.00×，D2H 2.75×（写 pageable 还要处理页错误）。

能超过 3× 的情况： - 传输很小，而 pageable 路径的固定开销大得多 - 主机内存严重受限或有 swap 活动 - 测量方法有问题（比如没预热，第一次传输包含缺页）

判断方法：任何加速比都要问「上限是多少，为什么」。 说不出机制的加速比，都要存疑。这也是 M3（如何跟前沿）的核心检查项。

5. 如果把 worldvln 的 PCIe 从 Gen4 升到 Gen5，H2D 会翻倍吗？多流重叠会怎么变？

H2D 大概率会接近翻倍（25 → ~47 GB/s），因为它当前明显受 PCIe 限制 （NUMA 实验证明主存不是瓶颈：跨节点也有 58 GB/s）。

但多流重叠会变差。 升级后需要的主存流量变成 47+47=94 GB/s， 而 worldvln 单节点实测 58.2 GB/s → 重叠比会从 1.74× 掉到约 1.24×。

除非你把两个方向的 pinned 缓冲分别放在两个 NUMA 节点上—— 那样总带宽是两个节点之和（~116 GB/s），重叠可以恢复。

这时候 NUMA 绑定就重要了。 呼应本章的核心结论： 「NUMA 不重要」是这台机器这个配置下的结论，不是普适真理。 换代硬件必须重测。
