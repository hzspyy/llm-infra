1.5

网络与存储底座

沿权重加载过程，分析存储读取、主机暂存和设备传输的路径与带宽。

实测机器 crater (NVMe overlay) + worldvln (btrfs on loop, SeaweedFS/FUSE, RoCE 25 Gb/s)前置 L1.3（PCIe 与 pinned 内存）· L1.4（驱动分层）

本章回答三个问题

  1. 权重从磁盘到显存要过几段？每段各占多少时间？瓶颈在哪一段？
  2. 为什么 .to("cuda") 加载模型只有 15 GB/s，而 L1.3 测出 PCIe 是 47 GB/s？
  3. 如何确认当前机器能否使用 GPUDirect Storage 或 GPUDirect RDMA？

大模型权重的加载绝非简单的单一文件读取。数据必须穿透底层存储驱动、操作系统页缓存（Page Cache）、主机用户态内存以及 PCIe 总线，最终抵达 GPU 显存；整个链路中往往交织着缺页中断调页、内存格式转换以及非页锁定内存拷贝开销。本章将对权重加载的全链路耗时进行细粒度拆解，揭示冷启动瓶颈并厘清各阶段的物理制约。

心智模型：沿权重的数据路径逐段检查

机制拆解

存储介质：同一份脚本，64 倍差距

存储 冷读 热读（页缓存） 加速比 机器
overlay on NVMe 9.61 GB/s 36.73 GB/s 3.8× crater
btrfs on loop device 0.56 GB/s 5.14 GB/s 9.2× worldvln 本地
SeaweedFS over FUSE 0.15 GB/s 0.31 GB/s 2.1× worldvln /root/nfs

冷读差 64 倍。 换算成模型加载时间（16 GB 的 8B 模型）：

  • crater NVMe：1.7 秒
  • worldvln 本地：29 秒
  • worldvln 网络存储：107 秒

上述时间是基于实测顺序读取带宽的理论下限推算。在实际系统中，worldvln 上的所谓“本地盘”并非物理裸 NVMe，而是挂载在 /dev/loop8 虚拟循环设备上的 btrfs 文件系统，其实际 I/O 效率较物理裸盘低了一个数量级。

一个容易忽略的事实

df -hT 显示 worldvln 的 /root/nfs 是 fuse.seaweedfs —— 不是 NFS，是 FUSE。 FUSE 把部分操作交给用户态守护进程，但缓存模式下，部分读取可以由内核页缓存满足。 0.15 GB/s 冷读、热读也只有 0.31 GB/s（页缓存对 FUSE 帮助有限）。

读文件前先看 df -hT 确认文件系统类型，否则你会把 FUSE 的开销 误判成网络带宽不足。

页缓存的加速比也值得看：NVMe 上是 3.8×，loop 设备上是 9.2×（本身太慢，缓存收益更大）， FUSE 上只有 2.1×（因为 FUSE 的开销在缓存命中时依然存在）。

「冷态」必须有证据：mincore 与 read_bytes

说「冷读」之前得先证明页缓存真的被逐出了。本章用两条独立证据 （labs/L1/storage_path.py，crater，2026-09-13，独立复制的 3.44 GB 分片）：

mincore 逐出前驻留 100.0%  →  posix_fadvise(DONTNEED) 成功  →  逐出后 0.0%
冷读      9.75 GB/s   （进程 read_bytes 增量 3.20 GiB，缺页 7989+0）
热读     37.37 GB/s   （第二次 38.15；read_bytes 增量 0.00 GiB）
  • mincore 给出逐页驻留比例：逐出前 100%、逐出后 0%。脚本会把「逐出后 仍 >20% 驻留」标成不可信的冷态。
  • /proc/self/io 的 read_bytes 给出真正下到块层的字节：冷读 3.20 GiB、 热读 0.00 GiB。rchar 会把缓存命中也算进去，必须两个一起看。

`drop_caches` 与 mincore 的两个坑

  1. 绝不在共享机器上 echo 3 > /proc/sys/vm/drop_caches：那会清掉整台机器的 页缓存，别人的实验一起报废。用 posix_fadvise(POSIX_FADV_DONTNEED) 只逐出目标文件。
  2. 用 Python 的 mmap.mmap 做 mincore 会永远「不可用」：只读映射不是可写 缓冲区，ctypes.c_char.from_buffer(mm) 直接抛异常。要自己调 libc 的 mmap/munmap 拿地址，mincore 只要求映射存在、不要求可写。
  3. 冷态控制要用独立文件：如果别的进程也在读同一个模型文件，页缓存会被 重新填热。脚本支持 --work，先把分片复制成私有副本再做冷热实验。

端到端：每段单独计时，外加缺页与字节账

labs/L1/storage_path.py 把加载拆成五段（crater，3.44 GB 分片，310 个张量， 2026-09-13）：

张量数 310（文件头里 310 项）
C0 读文件头 + JSON 解析      0.9 ms  （rchar 0.0 MiB，只读了头部）
C1 建立 mmap 视图         31.4 ms   （不读数据：rchar 0.0 MiB）
C2 强制读入主机内存      503.4 ms  ( 6.84 GB/s)  ← 真正的磁盘/缓存读；
                          缺页 906884+8630，read_bytes 3232.6 MiB
C2b CPU 侧精度转换       251.4 ms  （bf16→fp16，纯 CPU，缺页 840186）
C3 主机内存 -> 显存      224.5 ms  ( 15.32 GB/s)
⇒ 冷启动总计约 1011 ms
  磁盘/缓存占 50%，CPU 转换占 25%，PCIe 占 22%

三处新增的可交付内容：

  • C0 与 C1 的 rchar 都是 0.0 MiB：读文件头和建 mmap 视图确实没有读数据。 这一行数字是「不能只给 mmap 计时」的直接证据。
  • C2 的缺页计数（90.7 万次软缺页 / 8630 次硬缺页）与 read_bytes 3.20 GiB 对得上：这才是「磁盘读」的定义。只报耗时和带宽说明不了是哪一种读。
  • C2b 是纯 CPU 工作，占冷启动的 25%。checkpoint 存的精度和 kernel 要的精度 经常不同，转换既不属于磁盘读、也不属于 H2D，混进任一段都会让归因出错。

mmap 建立映射与实际读取应分别计时

直接对 safe_open(...).get_tensor(k) 计时，测出冷加载 104 GB/s—— 比任何磁盘都快。原因是 safetensors 返回的是建立在 mmap 之上的视图， 调用它并不真的读字节。真正的磁盘读被推迟到后面 .to("cuda") 触碰内存的那一刻， 于是 H2D 阶段只有 6.7 GB/s，因为这段计时还包含实际读取。

一般规律：凡是 mmap，就要警惕"什么时候真的读"。 计时必须包含一次真实触碰。

H2D 吞吐差异的两组诊断对照

C3 的 14.94 GB/s 与 L1.3 实测的 PCIe 5.0 上限 47.2 GB/s 差了 3 倍。两个候选解释：

假设一：传输太碎。 310 个张量，很多只有几 KB，落在 L1.3 测出的 「小于 250 KB 几乎全是固定开销」区间。

测法：把所有张量拼成一个连续块，只传一次。

C4 假设一：传输太碎？拼成 1 次传输：219.4 ms (15.68 GB/s)  ← 只快 1.05×，假设被证伪

合并传输后的改善较小，说明仅减少传输次数不足以解释本配置下的主要差距。

假设二：源是 pageable 内存。 safetensors 的 mmap 内存不是页锁定的， L1.3 测过 pageable H2D 只有 pinned 的一半。

测法：把同样的字节先拷进 pinned 缓冲，再传。

C5 假设二：源是 pageable？换成 pinned：73.5 ms (46.81 GB/s)  ← 快 2.98×，这才是原因

换用 pinned 源缓冲后，传输段的带宽接近 L1.3 的记录，支持继续检查内存类型的影响。

本例中，源缓冲类型的影响比合并传输更明显；这不等于小传输开销不存在。

这也解释了引擎为什么要做"加载优化"——不是玄学，就是加一个 pinned 中转缓冲：

mmap→pinned 缓冲⏟CPU 拷贝→DMA→显存⏟47 GB/s

多一次 CPU 拷贝，但换来 3 倍的 PCIe 吞吐。在 PCIe 是瓶颈时这笔账划算—— 这与 L1.3 的 pinned 暂存思路相同，此处由应用层显式管理。

两条捷径：都要绕过主机内存

既然主机内存这一跳这么贵，能不能绕过？两条路，本机都不可用：

GPUDirect Storage（GDS）：让 NVMe 通过 DMA 直接写进显存。

/proc/driver/nvidia-fs/stats         不存在
/dev/nvidia-fs0                      不存在
libcufile.so.0 (用户态库)             存在

用户态库存在，内核模块不在。 libcufile 是 torch 默认就链接的 （L1.4 原始现场 ① 里能看到），所以很容易误以为 GDS 可用。 实际上它会静默回落到"经主机内存"的兼容模式。

判断标准是内核侧：/dev/nvidia-fs0 或 /proc/driver/nvidia-fs/stats 存在才算数。

GPUDirect RDMA：让网卡直接读写显存。worldvln 有 RoCE 网卡：

$ ls /sys/class/infiniband/
irdma0  irdma1
  irdma0: 4: ACTIVE  rate=25 Gb/sec (1X EDR)  link=Ethernet
  irdma1: 4: ACTIVE  rate=25 Gb/sec (1X EDR)  link=Ethernet

$ ls /sys/kernel/mm/memory_peers/
（无 memory_peers）

记录中网卡在线（25 Gb/s 约为 3.1 GB/s），但未发现 nvidia-peermem。 这还不足以排除 GPUDirect RDMA：支持的配置也可能使用 DMA-BUF 路径。 这里应标为“直接路径尚未验证”，而不是“已证明不可用”。 参见 NVIDIA 对两类配置的说明。

L6 需要先确认实际传输路径

区分“某种 GPU 直连路径不受支持”和“整个分布式方案无法运行”。 跨机 PD 分离也可以采用主机中转等传输方式，只是成本与部署条件不同。 DeepEP、NVSHMEM 等具体模式需要分别检查版本和要求，不能一并判为不可用。 当前只把链路记录作为规划输入；正式运行前还需重新确认拓扑与传输能力。

read() 与 mmap 的加载路径对照

[B] 读法对比（页缓存已热）
    read() 顺序读       36.03 GB/s
    mmap + 逐页触碰     24.57 GB/s

mmap 慢 32%（逐页缺页中断的开销）。那 safetensors 为什么还用 mmap？

因为它要的是按需：safe_open(...).get_slice(name) 能只读一个张量， 而不把 3.44 GB 全读进来（L0.1 原始现场 ①）。这对以下场景是必需的：

  • 只加载模型的一部分（PP 并行时每个 stage 只要自己那几层，L7.2）
  • 检查 shape/dtype 而不读数据（L4.0 逐字节解析时用的就是这个）
  • 多进程共享同一份权重的页缓存（TP 时 8 个进程读同一个文件，物理内存只占一份）

最后一条是关键：mmap 让多个 worker 进程天然共享页缓存。 如果用 read()，8 路 TP 就要 8 份主机内存副本。

传输后端对照：先把「能测的」和「不能测的」分开

任务 B 要求在项目端点上比较 TCP 与可用传输后端。这个环境有一半做不了， 而且必须先把不能做的那半的证据摆出来：

crater 侧路由：  192.168.105.0/24 dev net1（无默认路由）
worldvln 侧路由：192.168.26.0/24 dev eth0（网关 192.168.26.1）
ping 双向不通，两台机器不在同一个可达网络里 → 跨机 TCP 对照做不了

能做的部分（labs/L1/net_transport.py，worldvln，每连接 64 MiB， 收发两端 fork 成独立进程，避免 GIL 把 Python 协议开销算进链路）：

transport 64 KiB × 1 1 MiB × 1 1 MiB × 4 1 MiB × 16 16 MiB × 1 64 MiB × 1
TCP loopback 2.24 3.13 8.14 10.77 0.77 0.46
TCP eth0（自己） 2.34 3.04 8.51 10.26 0.77 0.43
Unix domain socket 3.00 3.14 7.60 9.28 0.63 0.31
裸 socket 对照（单连接） — 2.77 — — 2.22 1.98

单位 GB/s，均为聚合值，每格都校验了内容（抽样块的 SHA256 + 块序号连续性） 与完成语义（接收端回长度前缀的完成事件，带总字节数与哈希）。

三个结论，以及一个必须说明的边界：

  1. 三种 transport 在同一协议下差异 < 15%：loopback、过网卡、UDS 基本同速。 说明在这个容器里测到的是协议栈与 Python 的实现成本，不是链路能力。 这也正是任务 B 要防的那个误判。
  2. 并发 16 才把聚合推到 ~10 GB/s（单连接只有 3.1 GB/s）。真正的并联收益 来自多个连接，不是把单连接调大。
  3. 块变大反而变慢（16/64 MiB 单连接只有 0.3–0.8 GB/s）：与裸 socket 对照 （2.0–2.2 GB/s）同向，是单线程协议栈 + 大缓冲区首次触碰的共同结果。 不能把这一档读成「链路在 64 MiB 时变差」。
  4. RDMA 侧只有可用性判定，没有实测：
infiniband_devices  ['irdma0', 'irdma1']      rdma link: ACTIVE / LINK_UP
ib_uverbs           []                        ← /dev/infiniband 不存在
memory_peers        []
libs                ['libibverbs.so.1', 'librdmacm.so.1', 'libmlx5.so.1']
headers             []                        ← 无 verbs.h / rdma_cma.h
python_bindings     {'pyverbs': False, 'rdma': False, 'ibverbs': False}
⇒ 无法注册 buffer、无法建立 QP：本环境未启用 RDMA

「库存在」与「功能可用」是两件事：libibverbs.so.1 在，端口 ACTIVE， 但没有 /dev/infiniband、没有头文件、没有任何绑定，就既注册不了 buffer 也发起不了传输。所以这一节只保留接口级对照：NIXL / Mooncake 的 register → transfer → wait → release 形态在下一节用一个小适配器写出来， 换后端时只替换实现。

传输适配器：注册 / 传输 / 等待 / 释放与失败注入

labs/L1/transfer_adapter.py 用 TCP 实现传输库那套生命周期接口， 并注入两类真实故障（2026-09-13，worldvln）：

[正例] 4 块 1 MiB：内容一致=True，服务端一致=True，未释放句柄=0，
       fd 5→4，58.73 ms
[重复完成] 内容一致=True，被忽略的重复事件=1，未释放句柄=0
[接收端中断] 完成 1 块后失败：ConnectionResetError('接收端在完成前关闭了连接')
             有界结束 6.75 ms，未释放句柄=0，fd 5→4，
             服务端记录=2 块后中断

四件事被验证：

  • 内容哈希一致：客户端与接收端各自对收到的字节算 SHA256，逐块比对。
  • 幂等：同一个 transfer id 的完成事件发两次，适配器只处理一次 （duplicate_done_ignored），不会重复计数、也不会提前释放句柄。 真实传输库在超时重传时会产生这种重复事件。
  • 有界失败与清理：接收端在第 2 块后断开，发送端在 6.75 ms 内抛错退出循环， 所有句柄释放、fd 从 5 回到 4。失败路径也要有账，否则长跑服务会泄漏句柄。
  • 完成事件必须长度前缀、定长读取：直接 recv(256) 可能一次读到两个事件、 也可能只读到半个 JSON，接收端会卡在等一条永远拼不齐的消息上。

注册成本的边界

本适配器的「注册」只是句柄登记，实测 0.0 µs/次。真实传输库的注册要锁页、 建 DMA 映射，那部分成本本环境测不到（无 RDMA）。所以「注册成本是否被摊销」 这个问题在这里保持 UNVERIFIED，只给出接口形态与失败语义， 不给出通用的注册开销结论。

工程实现 · 源码解析

vLLM 的加载路径与 --load-format

vLLM 的模型加载在 model_executor/model_loader/ 下，默认走 safetensors + mmap。 本章测出的 748 ms（3.44 GB）对应 L1.4 里那个「一次性启动成本」的下半段。

不同的 load_format 对应不同的加载方式：

format 路径 代价
auto / safetensors mmap + 逐张量 .to(cuda) 本章实测：PCIe 段只有 15 GB/s
runai_streamer 流式读取 + 后台预取 把 ② 与 ④ 重叠起来
sharded_state 每个 TP rank 只读自己那份 减少总读取量，但要预先切分
dummy 随机初始化，不读盘 benchmark 专用——想单独测引擎而不含加载时间时用它

最后一行很实用：做性能实验时用 --load-format dummy 可以把加载时间从测量中剔除。

服务模型名称与权重路径分别配置

从 HF Hub 直接拉模型时，第一次运行要走网络。本章测出 worldvln 的 网络存储只有 0.15 GB/s——生产环境必须把权重预先落到本地快盘， 或者至少预热到页缓存。这也是 L8.2 讲 K8s 部署时"init container 预拉权重"的理由。

动手 lab

# A：冷热证据 + 每段缺页/字节账（--work 先复制成私有副本，避免别人把缓存弄热）

③ RDMA 与 GPUDirect 的可用性判定 
$ ls /sys/class/infiniband/
irdma0
irdma1

$ for d in /sys/class/infiniband/*/; do ... done
  irdma0: 4: ACTIVE  rate=25 Gb/sec (1X EDR)  link=Ethernet
  irdma1: 4: ACTIVE  rate=25 Gb/sec (1X EDR)  link=Ethernet

$ ls /sys/kernel/mm/memory_peers/
（无 memory_peers）

$ ls /dev/nvidia-fs*
（无 nvidia-fs，GDS 不可用）

逐项解读：

  • irdma 是 Intel 的 RDMA 驱动，link=Ethernet 说明是 RoCE（RDMA over Converged Ethernet），不是原生 InfiniBand。
  • state: 4: ACTIVE 表示端口在线。
  • rate=25 Gb/sec = 3.1 GB/s。注意括号里的 (1X EDR) 是内核对速率的 IB 术语映射，别被 "EDR" 误导——物理层是 25 GbE。
  • memory_peers 目录不存在只是该探针没有找到对应接口， 不能排除 DMA-BUF 等其他路径，也不能据此证明正在使用主机中转。

这些记录提供排查入口，不是完整的可用性测试。

方向 内容
GPUDirect Storage NVMe → 显存直连，绕过主机内存。本章测出主机内存这一跳占了冷启动的 65%，GDS 正是针对它。需要 nvidia-fs 内核模块 + 支持的文件系统
权重流式加载 Run:ai Streamer、vLLM 的 runai_streamer load-format：把"读盘"与"传 PCIe"流水化重叠。理论上限是两段中较慢的那段（本机是读盘 7.1 GB/s）

陷阱

1. 不看文件系统类型就下结论。 worldvln 的"NFS"是 FUSE，"本地盘"是 loop 设备。 df -hT 是第一步。

2. 给 mmap 计时却没有真实触碰。 会测出"104 GB/s 的冷加载"。 凡是 mmap，必须显式触碰每一页。

3. 以为用户态库存在就等于功能可用。 libcufile.so.0 是 torch 默认链接的， 但没有 nvidia-fs 内核模块，GDS 就是不可用。判断可用性一律看内核侧。

4. 忘了 mmap 内存不是 pinned 的。 本章实测：这一点让 PCIe 段慢了 3 倍。

5. 用一个假设解释现象而不去证伪。 本章的"传输太碎"听起来非常合理， 实测只快 1.05×。至少要有两个互斥假设，各测一遍。

6. 在共享机器上 echo 3 > /proc/sys/vm/drop_caches。 会清空整台机器的页缓存， 影响所有人。用 posix_fadvise(POSIX_FADV_DONTNEED) 只针对目标文件。

7. 用 ctypes 调 mincore 不设 argtypes。 64 位指针会被截断。 更常见的是用 Python 的 mmap 对象去取地址：只读映射不是可写缓冲区， from_buffer 直接抛异常，于是 mincore 永远报"不可用"。 要自己调 libc 的 mmap/munmap（或先确认缓冲区可写）。这是 L1.4 那个坑的同类。

8. 不做冷态证据就宣称"冷读"。 页缓存可能已被别人填热。 至少给两条独立证据：mincore 的逐页驻留比例，以及 /proc/self/io 的 read_bytes 增量（rchar 会把命中缓存的读也算进去，不能单用）。

9. 在不同传输后端之间直接比数字。 两端在同一个进程里用线程收发， GIL 会把 Python 协议开销混进"链路吞吐"，测出来只有 0.3–3 GB/s。 收发要 fork 成两个进程，并且先用裸 socket 对照确认上限在哪。

10. 把完成事件当成普通消息 recv。 不用长度前缀，一次 recv 可能读到 两个事件、也可能只读到半个 JSON。而且同一个 transfer id 的完成事件要幂等—— 超时重传在真实传输库里很常见，重复计数会导致句柄被提前释放。

11. 只测 happy path。 传输库的接口价值一半在失败语义： 接收端中途断开时，发送端能不能有界失败、句柄和 fd 能不能回收。 本章的适配器把这条也纳入验收。

自测题

1. 我在 worldvln 上部署一个 8B 模型（16 GB 权重），从 /root/nfs 加载。预计要多久？怎么优化？

按本章实测（SeaweedFS/FUSE 冷读 0.15 GB/s）：

16 GB/0.15 GB/s=107 秒

加上 PCIe 段（pageable 15 GB/s → 1.1 秒）和进程初始化（L1.4 的 838 ms）， 总共接近 2 分钟。

优化，按收益排序：

  1. 复制到本地盘：0.56 GB/s → 29 秒。3.7× 收益，最简单。
  2. 预热页缓存（cat model.safetensors > /dev/null）：热读 5.14 GB/s → 3.1 秒。 但要占 16 GB 主机内存（worldvln 有 188 GB，可以）。
  3. pinned 中转缓冲：PCIe 段 1.1 秒 → 0.34 秒。相比前两项收益很小—— 因为瓶颈不在这里。
  4. 流式重叠：把读盘与 PCIe 传输流水化。上限是较慢的那段， 在 NFS 上仍是 107 秒，基本无用。

这里 95% 的时间用于读盘，仅优化 PCIe 对总时间的改善有限。

2. 为什么页缓存对 FUSE 的加速比（2.1×）远低于对 NVMe 的（3.8×）和 loop 设备的（9.2×）？

这些带宽差异不能单独确定原因。应检查是否使用 direct I/O、页缓存是否命中、 请求大小、客户端缓存以及服务端状态。 Linux 的 cached FUSE 模式允许从页缓存满足读取，不能假定每次 read 都经过用户态守护进程。 参见 Linux FUSE I/O 模式。 本组数据说明这条具体路径值得优化，不意味着所有 FUSE 文件系统预热收益都小。

3. 我看到 libcufile.so.0 在 torch 的依赖里，是不是说明 GPUDirect Storage 已经在用了？

不是。 用户态库存在只说明编译时链接了它，运行时能不能用是另一回事。

GDS 需要三样东西同时具备： 1. 用户态库 libcufile.so（本机✓） 2. 内核模块 nvidia-fs（本机✗ —— /dev/nvidia-fs0 不存在） 3. 支持的文件系统 + 存储栈（EXT4/XFS on NVMe，或支持的分布式文件系统）

缺任何一项，cuFile 会静默回落到"经主机内存"的兼容模式（POSIX 路径）， 不报错、只是没有加速。

这就是"库存在 ≠ 功能可用"的典型。 同类的还有： 装了 nccl 不代表有 NVLink；装了 nvshmem 不代表有 GPUDirect RDMA。 可用性一律查内核侧的设备节点或 sysfs。

4. 8 路 TP 的时候，8 个 worker 进程都要读同一份 16 GB 权重。主机内存会占 128 GB 吗？

不会，如果用 mmap。

mmap 建立的是文件到虚拟地址的映射，多个进程映射同一个文件时， 物理页只有一份（在页缓存里），各进程的页表指向同一批物理页。 所以 8 个进程共享 16 GB，而不是 128 GB。

但有两个前提：

  1. 必须是只读映射且不写。一旦写（copy-on-write 触发），就会各自分裂出私有页。
  2. 不能 .clone() 或拷进 pinned 缓冲。本章 C2 段的 clone() 就是 为了强制读入而做的真实拷贝——那会各占一份。

所以引擎的实际做法是：mmap 共享读，然后逐张量拷到显存， 中途不保留完整的主机副本。这既省主机内存，又避免了 8 份重复读盘。

这正是 safetensors 选 mmap 而不是 read() 的核心理由之一， 尽管本章测出 mmap 的顺序读吞吐低 32%。

5. 本章测出没有 GPUDirect RDMA。这对后面 L6 的实验有哪些具体限制？请列出来。

已有探针不足以判断 GPUDirect RDMA 不可用，应先确认实际传输路径。 L6 应先记录实际链路、驱动与 transport，再区分直接访问显存、主机中转和机内 P2P。 不同路径会改变带宽、CPU 占用与同步开销；一个路径不支持，不等于所有跨机并行都无法运行。 具体实验范围应在完成预检后确定。

这些限制要写进 L6 每个实验的"设置"里，否则测出来的数字会被 误读成"分布式本来就这么慢"。环境的限制必须和结论一起报告， 这也是 M2（可信测量）的一条基本要求。
