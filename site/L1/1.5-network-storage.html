1.5

网络与存储底座

按文件读取、缺页与设备传输拆解权重加载；比较存储与缓冲方式，学习如何检查实际传输路径，而不由单个库或模块判断功能可用性。

实测机器 crater (NVMe overlay) + worldvln (btrfs on loop, SeaweedFS/FUSE, RoCE 25 Gb/s)数据日期 2026-09-10前置 L1.3（PCIe 与 pinned 内存）· L1.4（驱动分层）

本章回答三个问题

  1. 权重从磁盘到显存要过几段？每段各占多少时间？瓶颈在哪一段？
  2. 为什么 .to("cuda") 加载模型只有 15 GB/s，而 L1.3 测出 PCIe 是 47 GB/s？
  3. GPUDirect Storage / GPUDirect RDMA 在我这台机器上到底可不可用？（"库存在"不等于"能用"）

加载权重不是一次文件读取。数据需要经过文件系统、主机内存和设备传输路径， 期间还可能发生缺页、复制或格式转换。本章按这些步骤拆分耗时， 比较“小张量传输较多”和“源内存未页锁定”两种候选解释。 它们可以同时存在，不能仅因一种解释较符合数据，就排除其余开销。

心智模型：沿权重的数据路径逐段检查

机制拆解

存储介质：同一份脚本，64 倍差距

存储 冷读 热读（页缓存） 加速比 机器
overlay on NVMe 9.61 GB/s 36.73 GB/s 3.8× crater
btrfs on loop device 0.56 GB/s 5.14 GB/s 9.2× worldvln 本地
SeaweedFS over FUSE 0.15 GB/s 0.31 GB/s 2.1× worldvln /root/nfs

冷读差 64 倍。 换算成模型加载时间（16 GB 的 8B 模型）：

  • crater NVMe：1.7 秒
  • worldvln 本地：29 秒
  • worldvln 网络存储：107 秒

这些是按带宽换算的读取时间估计，不是 8B 模型的完整启动实测。还应注意， worldvln 的"本地盘"其实是 /dev/loop8 上的 btrfs —— 容器镜像的循环设备，比裸 NVMe 慢一个数量级。

一个容易忽略的事实

df -hT 显示 worldvln 的 /root/nfs 是 fuse.seaweedfs —— 不是 NFS，是 FUSE。 FUSE 把部分操作交给用户态守护进程，但缓存模式下，部分读取可以由内核页缓存满足。 0.15 GB/s 冷读、热读也只有 0.31 GB/s（页缓存对 FUSE 帮助有限）。

读文件前先看 df -hT 确认文件系统类型，否则你会把 FUSE 的开销 误判成网络带宽不足。

页缓存的加速比也值得看：NVMe 上是 3.8×，loop 设备上是 9.2×（本身太慢，缓存收益更大）， FUSE 上只有 2.1×（因为 FUSE 的开销在缓存命中时依然存在）。

端到端：三段时间与两个假设

labs/L1/storage_path.py 把加载拆成三段分别计时（crater，3.44 GB 分片，310 个张量）：

C1 建立 mmap 视图         32.9 ms   （不读数据，所以"带宽"没有意义）
C2 强制读入主机内存      484.6 ms  (  7.10 GB/s)  ← 真正的磁盘/缓存读
C3 主机内存 -> 显存      230.4 ms  ( 14.94 GB/s)
⇒ 冷启动总计约 748 ms；磁盘/缓存占 65%，PCIe 占 31%

C1/C2 的分离是踩坑换来的

第一版把 safe_open(...).get_tensor(k) 直接计时，测出冷加载 104 GB/s—— 比任何磁盘都快。原因是 safetensors 返回的是建立在 mmap 之上的视图， 调用它并不真的读字节。真正的磁盘读被推迟到后面 .to("cuda") 触碰内存的那一刻， 于是 H2D 只测出 6.7 GB/s。两段时间串了台。

一般规律：凡是 mmap，就要警惕"什么时候真的读"。 计时必须包含一次真实触碰。

为什么 H2D 只有 15 GB/s：两个假设，各测一遍

C3 的 14.94 GB/s 与 L1.3 实测的 PCIe 5.0 上限 47.2 GB/s 差了 3 倍。两个候选解释：

假设一：传输太碎。 310 个张量，很多只有几 KB，落在 L1.3 测出的 「小于 250 KB 几乎全是固定开销」区间。

测法：把所有张量拼成一个连续块，只传一次。

C4 假设一：传输太碎？拼成 1 次传输：219.4 ms (15.68 GB/s)  ← 只快 1.05×，假设被证伪

合并传输后的改善较小，说明仅减少传输次数不足以解释本配置下的主要差距。

假设二：源是 pageable 内存。 safetensors 的 mmap 内存不是页锁定的， L1.3 测过 pageable H2D 只有 pinned 的一半。

测法：把同样的字节先拷进 pinned 缓冲，再传。

C5 假设二：源是 pageable？换成 pinned：73.5 ms (46.81 GB/s)  ← 快 2.98×，这才是原因

换用 pinned 源缓冲后，传输段的带宽接近 L1.3 的记录，支持继续检查内存类型的影响。

本例中，源缓冲类型的影响比合并传输更明显；这不等于小传输开销不存在。

这也解释了引擎为什么要做"加载优化"——不是玄学，就是加一个 pinned 中转缓冲：

mmap→pinned 缓冲⏟CPU 拷贝→DMA→显存⏟47 GB/s

多一次 CPU 拷贝，但换来 3 倍的 PCIe 吞吐。在 PCIe 是瓶颈时这笔账划算—— 和 L1.3 讲 pinned 时是同一个道理，只是这次由我们自己在应用层做。

两条捷径：都要绕过主机内存

既然主机内存这一跳这么贵，能不能绕过？两条路，本机都不可用：

GPUDirect Storage（GDS）：让 NVMe 通过 DMA 直接写进显存。

/proc/driver/nvidia-fs/stats         不存在
/dev/nvidia-fs0                      不存在
libcufile.so.0 (用户态库)             存在

用户态库存在，内核模块不在。 libcufile 是 torch 默认就链接的 （L1.4 原始现场 ① 里能看到），所以很容易误以为 GDS 可用。 实际上它会静默回落到"经主机内存"的兼容模式。

判断标准是内核侧：/dev/nvidia-fs0 或 /proc/driver/nvidia-fs/stats 存在才算数。

GPUDirect RDMA：让网卡直接读写显存。worldvln 有 RoCE 网卡：

$ ls /sys/class/infiniband/
irdma0  irdma1
  irdma0: 4: ACTIVE  rate=25 Gb/sec (1X EDR)  link=Ethernet
  irdma1: 4: ACTIVE  rate=25 Gb/sec (1X EDR)  link=Ethernet

$ ls /sys/kernel/mm/memory_peers/
（无 memory_peers）

记录中网卡在线（25 Gb/s 约为 3.1 GB/s），但未发现 nvidia-peermem。 这还不足以排除 GPUDirect RDMA：支持的配置也可能使用 DMA-BUF 路径。 这里应标为“直接路径尚未验证”，而不是“已证明不可用”。 参见 NVIDIA 对两类配置的说明。

L6 需要先确认实际传输路径

区分“某种 GPU 直连路径不受支持”和“整个分布式方案无法运行”。 跨机 PD 分离也可以采用主机中转等传输方式，只是成本与部署条件不同。 DeepEP、NVSHMEM 等具体模式需要分别检查版本和要求，不能一并判为不可用。 当前只把链路记录作为规划输入；正式运行前还需重新确认拓扑与传输能力。

read() vs mmap：为什么 safetensors 选 mmap

[B] 读法对比（页缓存已热）
    read() 顺序读       36.03 GB/s
    mmap + 逐页触碰     24.57 GB/s

mmap 慢 32%（逐页缺页中断的开销）。那 safetensors 为什么还用 mmap？

因为它要的是按需：safe_open(...).get_slice(name) 能只读一个张量， 而不把 3.44 GB 全读进来（L0.1 原始现场 ①）。这对以下场景是必需的：

  • 只加载模型的一部分（PP 并行时每个 stage 只要自己那几层，L7.2）
  • 检查 shape/dtype 而不读数据（L4.0 逐字节解析时用的就是这个）
  • 多进程共享同一份权重的页缓存（TP 时 8 个进程读同一个文件，物理内存只占一份）

最后一条是关键：mmap 让多个 worker 进程天然共享页缓存。 如果用 read()，8 路 TP 就要 8 份主机内存副本。

工程实现 · 源码走读

vLLM 的加载路径与 --load-format

vLLM 的模型加载在 model_executor/model_loader/ 下，默认走 safetensors + mmap。 本章测出的 748 ms（3.44 GB）对应 L1.4 里那个「一次性启动成本」的下半段。

值得注意的是它提供了多种 load_format，每种对应本章的不同权衡：

format 路径 代价
auto / safetensors mmap + 逐张量 .to(cuda) 本章实测：PCIe 段只有 15 GB/s
runai_streamer 流式读取 + 后台预取 把 ② 与 ④ 重叠起来
sharded_state 每个 TP rank 只读自己那份 减少总读取量，但要预先切分
dummy 随机初始化，不读盘 benchmark 专用——想单独测引擎而不含加载时间时用它

最后一行很实用：做性能实验时用 --load-format dummy 可以把加载时间从测量中剔除。

为什么 vLLM 要 --served-model-name 与本地路径

从 HF Hub 直接拉模型时，第一次运行要走网络。本章测出 worldvln 的 网络存储只有 0.15 GB/s——生产环境必须把权重预先落到本地快盘， 或者至少预热到页缓存。这也是 L8.2 讲 K8s 部署时"init container 预拉权重"的理由。

两个容易误判的地方：

  1. "本地盘"是 /dev/loop8 上的 btrfs —— 容器镜像的循环设备， 不是裸 NVMe。冷读 0.56 GB/s，比 crater 慢 17 倍。
  2. "NFS"其实是 fuse.seaweedfs —— FUSE 用户态文件系统， 每次读都要经过守护进程。热读也只有 0.31 GB/s， 说明页缓存对它帮助有限（FUSE 的开销在命中时依然存在）。

下任何"存储慢"的结论之前，先 df -hT 看清楚是什么文件系统。

③ RDMA 与 GPUDirect 的可用性判定 
$ ls /sys/class/infiniband/
irdma0
irdma1

$ for d in /sys/class/infiniband/*/; do ... done
  irdma0: 4: ACTIVE  rate=25 Gb/sec (1X EDR)  link=Ethernet
  irdma1: 4: ACTIVE  rate=25 Gb/sec (1X EDR)  link=Ethernet

$ ls /sys/kernel/mm/memory_peers/
（无 memory_peers）

$ ls /dev/nvidia-fs*
（无 nvidia-fs，GDS 不可用）

逐项解读：

  • irdma 是 Intel 的 RDMA 驱动，link=Ethernet 说明是 RoCE（RDMA over Converged Ethernet），不是原生 InfiniBand。
  • state: 4: ACTIVE 表示端口在线。
  • rate=25 Gb/sec = 3.1 GB/s。注意括号里的 (1X EDR) 是内核对速率的 IB 术语映射，别被 "EDR" 误导——物理层是 25 GbE。
  • memory_peers 目录不存在只是该探针没有找到对应接口， 不能排除 DMA-BUF 等其他路径，也不能据此证明正在使用主机中转。

这些记录提供排查入口，不是完整的可用性测试。

前沿

方向 内容
GPUDirect Storage NVMe → 显存直连，绕过主机内存。本章测出主机内存这一跳占了冷启动的 65%，GDS 正是针对它。需要 nvidia-fs 内核模块 + 支持的文件系统
权重流式加载 Run:ai Streamer、vLLM 的 runai_streamer load-format：把"读盘"与"传 PCIe"流水化重叠。理论上限是两段中较慢的那段（本机是读盘 7.1 GB/s）
KV 多级存储 Mooncake 的 HBM/DRAM/SSD 三级。本章的数字直接决定各级的成本：DRAM↔HBM 47 GB/s，SSD↔DRAM 9.6 GB/s（crater）（L6.4）
GPUDirect RDMA + IBGDA 网卡直接读写显存，且由 GPU 驱动网卡 doorbell（和 L1.4 的用户态提交是同一思想）。DeepEP 的低延迟 kernel 依赖它（L6.3）
CXL 与内存池化 把内存挂到 PCIe 通道上做池化。会让本章的"主机内存"这一层变成分层结构
模型格式的演化 safetensors 的 mmap 友好性是设计出来的（L4.0）；GGUF 走另一条路（量化内嵌 + 单文件）；两者在加载路径上的取舍不同

除本站实测外的内容来自各自文档，未在本站复现未实测。

陷阱

1. 不看文件系统类型就下结论。 worldvln 的"NFS"是 FUSE，"本地盘"是 loop 设备。 df -hT 是第一步。

2. 给 mmap 计时却没有真实触碰。 会测出"104 GB/s 的冷加载"。 凡是 mmap，必须显式触碰每一页。

3. 以为用户态库存在就等于功能可用。 libcufile.so.0 是 torch 默认链接的， 但没有 nvidia-fs 内核模块，GDS 就是不可用。判断可用性一律看内核侧。

4. 忘了 mmap 内存不是 pinned 的。 本章实测：这一点让 PCIe 段慢了 3 倍。

5. 用一个假设解释现象而不去证伪。 本章的"传输太碎"听起来非常合理， 实测只快 1.05×。至少要有两个互斥假设，各测一遍。

6. 在共享机器上 echo 3 > /proc/sys/vm/drop_caches。 会清空整台机器的页缓存， 影响所有人。用 posix_fadvise(POSIX_FADV_DONTNEED) 只针对目标文件。

7. 用 ctypes 调 mincore 不设 argtypes。 64 位指针会被截断。 本章的缓存驻留检测就因此失败了（输出里的"mincore 不可用"）—— 这是 L1.4 那个坑的同类。

自测题

1. 我在 worldvln 上部署一个 8B 模型（16 GB 权重），从 /root/nfs 加载。预计要多久？怎么优化？

按本章实测（SeaweedFS/FUSE 冷读 0.15 GB/s）：

16 GB/0.15 GB/s=107 秒

加上 PCIe 段（pageable 15 GB/s → 1.1 秒）和进程初始化（L1.4 的 838 ms）， 总共接近 2 分钟。

优化，按收益排序：

  1. 复制到本地盘：0.56 GB/s → 29 秒。3.7× 收益，最简单。
  2. 预热页缓存（cat model.safetensors > /dev/null）：热读 5.14 GB/s → 3.1 秒。 但要占 16 GB 主机内存（worldvln 有 188 GB，可以）。
  3. pinned 中转缓冲：PCIe 段 1.1 秒 → 0.34 秒。相比前两项收益很小—— 因为瓶颈不在这里。
  4. 流式重叠：把读盘与 PCIe 传输流水化。上限是较慢的那段， 在 NFS 上仍是 107 秒，基本无用。

关键判断：先看瓶颈在哪一段，再决定优化哪一段。 这里 95% 的时间在读盘， 优化 PCIe 是白费力气。

2. 为什么页缓存对 FUSE 的加速比（2.1×）远低于对 NVMe 的（3.8×）和 loop 设备的（9.2×）？

这些带宽差异不能单独确定原因。应检查是否使用 direct I/O、页缓存是否命中、 请求大小、客户端缓存以及服务端状态。 Linux 的 cached FUSE 模式允许从页缓存满足读取，因此旧稿中 “每次 read 都经过用户态守护进程”的解释不成立。 参见 Linux FUSE I/O 模式。 本组数据说明这条具体路径值得优化，不意味着所有 FUSE 文件系统预热收益都小。

3. 我看到 libcufile.so.0 在 torch 的依赖里，是不是说明 GPUDirect Storage 已经在用了？

不是。 用户态库存在只说明编译时链接了它，运行时能不能用是另一回事。

GDS 需要三样东西同时具备： 1. 用户态库 libcufile.so（本机✓） 2. 内核模块 nvidia-fs（本机✗ —— /dev/nvidia-fs0 不存在） 3. 支持的文件系统 + 存储栈（EXT4/XFS on NVMe，或支持的分布式文件系统）

缺任何一项，cuFile 会静默回落到"经主机内存"的兼容模式（POSIX 路径）， 不报错、只是没有加速。

这就是"库存在 ≠ 功能可用"的典型。 同类的还有： 装了 nccl 不代表有 NVLink；装了 nvshmem 不代表有 GPUDirect RDMA。 可用性一律查内核侧的设备节点或 sysfs。

4. 8 路 TP 的时候，8 个 worker 进程都要读同一份 16 GB 权重。主机内存会占 128 GB 吗？

不会，如果用 mmap。

mmap 建立的是文件到虚拟地址的映射，多个进程映射同一个文件时， 物理页只有一份（在页缓存里），各进程的页表指向同一批物理页。 所以 8 个进程共享 16 GB，而不是 128 GB。

但有两个前提：

  1. 必须是只读映射且不写。一旦写（copy-on-write 触发），就会各自分裂出私有页。
  2. 不能 .clone() 或拷进 pinned 缓冲。本章 C2 段的 clone() 就是 为了强制读入而做的真实拷贝——那会各占一份。

所以引擎的实际做法是：mmap 共享读，然后逐张量拷到显存， 中途不保留完整的主机副本。这既省主机内存，又避免了 8 份重复读盘。

这正是 safetensors 选 mmap 而不是 read() 的核心理由之一， 尽管本章测出 mmap 的顺序读吞吐低 32%。

5. 本章测出没有 GPUDirect RDMA。这对后面 L6 的实验有哪些具体限制？请列出来。

先纠正题目的前提：已有探针没有完整证明 GPUDirect RDMA 不可用。 L6 应先记录实际链路、驱动与 transport，再区分直接访问显存、主机中转和机内 P2P。 不同路径会改变带宽、CPU 占用与同步开销；一个路径不支持，不等于所有跨机并行都无法运行。 具体实验范围应在完成预检后确定。

这些限制要写进 L6 每个实验的"设置"里，否则测出来的数字会被 误读成"分布式本来就这么慢"。环境的限制必须和结论一起报告， 这也是 M2（可信测量）的一条基本要求。
