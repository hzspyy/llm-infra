Tensor Core 的指令演进与架构差异

比较各代 Tensor Core 的指令和编译目标，解释指令吞吐与 GEMM 性能的关系。

实测机器 crater (RTX 5090 D, sm_120) · CUDA 13.0.88 · PyTorch 2.13.0+cu130前置 L1.1（内存层次与并发）

本章回答三个问题

  1. tensor core 指令从 Volta 到 Blackwell 演化了五代。每一代具体多了什么，为什么必须换指令而不是加速旧指令？
  2. 「Blackwell」是一个架构还是两个？sm_100 和 sm_120 的代码能互换吗？
  3. 自写 GEMM 达到 cuBLAS 的 95% 就算到头了吗？硬件的真正上限怎么测？

Tensor Core 是 GPU 内部专门执行低精度矩阵乘加（MMA）的硬件计算单元。在实际编写算子时，程序员无法直接将任意尺度的矩阵交给它，而是必须依据特定硬件指令的几何形状进行分块，并将其严格编排到指定线程的寄存器或共享内存布局中。本章沿着 Tensor Core 指令接口的代际演进，深入剖析其编排规则的演变逻辑与硬件架构分叉，并通过实际基准测试与指令探针测定硬件的真实算力天花板。

心智模型：五代指令，两条分叉

机制拆解

mma.sync 的输入、输出与线程分工

先把最基础的一条看清楚：

mma.sync.aligned.m16n8k16.row.col.f32.bf16.bf16.f32
    {%0,%1,%2,%3},           // D：4 个 float
    {%4,%5,%6,%7},           // A：4 个 uint32（每个装 2 个 bf16）
    {%8,%9},                 // B：2 个 uint32
    {%0,%1,%2,%3};           // C：累加进 D

各字段的含义如下：

  • mma — matrix multiply-accumulate，D=A×B+C
  • sync — 整个 warp 必须一起执行。这不是 32 个线程各做各的， 而是 32 个线程各持有矩阵的一小片（fragment），硬件把它们拼成完整矩阵
  • m16n8k16 — 形状：A 是 16×16，B 是 16×8，D 是 16×8
  • row.col — A 行主序、B 列主序。这是硬件规定的，不匹配就得先转置
  • f32.bf16.bf16.f32 — D、A、B、C 的类型。输入 bf16，累加 f32

每条指令完成的浮点运算量为：2×16×8×16=4096 FLOP。

寄存器布局由硬件硬性规定：每个线程具体持有分块矩阵的哪几个元素，在 ISA 手册中有严格映射。手写底层 Tensor Core kernel 的核心复杂度正源于此——数据在载入寄存器时必须精确匹配硬件要求的 fragment 分布。为此，NVIDIA 专门提供了 ldmatrix 等高效数据重排指令（详见 L2.4）。

fragment 排列：按 ISA 装矩阵，再和 FP64 参照对拍

映射规则可以直接验证：把一个已知矩阵按 ISA 的 lane 映射装进寄存器，发一条 mma，把结果写回来与 CPU 上的 FP64 乘法逐元素比较。排列写错时错的是成片的元素，而不是最后一位的舍入——这个实验的判据因此非常干脆。

m16n8k16（bf16）的映射规则（groupID = lane >> 2，tig = lane & 3）：

寄存器 持有 A 的哪些元素 说明
a0 行 groupID，列 tig*2 + {0,1} 每个 uint32 装 2 个 bf16
a1 行 groupID+8，列 tig*2 + {0,1} 行方向的下半块
a2 行 groupID，列 tig*2+8 + {0,1} k 方向的后半段
a3 行 groupID+8，列 tig*2+8 + {0,1}
b0 / b1 k = tig*2+{0,1} / 再 +8，列 groupID B 按列主序取
d0..d3 行 groupID / groupID+8，列 tig*2+{0,1} 累加器 4 个 float

m16n8k32（e4m3）的规则同构，只是每个寄存器装 4 个字节、k 方向一次跨 32：a0 取行 groupID 的列 tig*4+{0..3}，a2 取 tig*4+16+{0..3}。

实测（整数输入，两种格式都能精确表示）：

m16n8k16 bf16：16x8 输出与 FP64 参照的最大绝对差 0.000e+00
    D[0][0]=1.0 D[0][1]=-12.0 D[8][0]=9.0 D[15][7]=7.0
m16n8k32 e4m3：最大绝对差 0.000e+00
    D[0][0]=3.0 D[0][1]=0.0 D[8][0]=-3.0 D[15][7]=0.0

两条指令的 128 个输出元素全部与参照精确相等，说明这份映射表与硬件一致。这是后面所有吞吐数字的前提：如果 fragment 装错，kernel 照样能跑、照样能测出 TFLOPS，只是算的不是矩阵乘。

五代演化，每一代解决一个具体矛盾

代 架构 指令 解决了什么
1 Volta (sm_70) mma.sync.m8n8k4 首次把矩阵乘做成一条指令。形状很小，需要大量指令
2 Turing (sm_75) + int8/int4 推理量化
3 Ampere (sm_80) mma.sync.m16n8k16 + cp.async 形状变大摊薄指令开销；异步拷贝让搬数据不占寄存器、不阻塞计算
4a Ada (sm_89) + fp8 m16n8k32 fp8 元素 1 字节，同样的寄存器装两倍数据 → k 翻倍 → 吞吐翻倍
4b Hopper (sm_90) wgmma.mma_async + TMA 从 warp 级升到 warp-group 级（4 个 warp 协作）；异步执行；TMA 把整块搬运交给专用硬件
5a Blackwell 数据中心 (sm_100) tcgen05.mma + TMEM 累加器从寄存器文件搬到专用的 Tensor Memory，tensor core 不再和 CUDA core 抢寄存器带宽
5b Blackwell 消费级 (sm_120) mma.sync + FP4 + block_scale 没有 tcgen05，没有 TMEM。走 Ampere 血统，加上 FP4 与块缩放

这些设计扩大了单条指令处理的矩阵规模，并引入异步数据搬运，以减少供数和同步对 Tensor Core 的限制。

编译探针：区分 sm_100a 与 sm_120a 的指令支持

以下探针检查指定指令能否通过相应目标的编译：

__global__ void tcgen05_smoke(uint32_t* tmem_addr) {
    asm volatile("tcgen05.alloc.cta_group::1.sync.aligned.shared::cta.b32 [%0], 32;\n"
                 :: "r"((uint32_t)(uintptr_t)tmem_addr));
}

nvcc -arch=sm_120a -cubin -o /dev/null tcgen05_probe.cu   # 消费级 Blackwell
nvcc -arch=sm_100a -cubin -o /dev/null tcgen05_probe.cu   # 数据中心 Blackwell

三条不靠版本号就得不到的结论：

  • bf16 只有 f32 累加一种形式。 「fp16 有半速/全速两档，bf16 应该也有」是错的，ptxas 直接拒绝 .f16.bf16.bf16.f16。
  • fp8 不存在 m16n8k64。 k 想再翻倍必须换数据格式（FP4），并且要带 .kind:: 前缀。
  • wgmma 与 tcgen05 都编不过。 消费级 Blackwell 既没有 Hopper 的 warp-group 指令，也没有数据中心 Blackwell 的 TMEM 指令。

同一份源码，一个架构编不过，另一个直接通过。 这就是为什么：

  • L0.1 的 kernel trace 里，5090 上跑的 GEMM 叫 cutlass_80_tensorop_... —— 80 是 sm_80（Ampere）。消费级 Blackwell 用的是 Ampere 血统的 kernel。
  • CUTLASS 的 Blackwell 模板用 sm_100a 编译，在 sm_120 上根本编不过； 移植到工作站卡要走另一套模板。
  • 「支持 Blackwell」这句话没有信息量。必须问：sm_100 还是 sm_120？

`a` / `f` / 裸架构：三种编译目标

你会看到 sm_120、sm_120a、sm_120f 三种写法：

  • sm_120：只用通用指令，生成的 cubin 在 sm_120 上跑
  • sm_120a（architecture-specific）：允许该架构独有的指令， 只能在 sm_120 上跑，连 sm_121 都不行
  • sm_120f（family-specific）：介于两者之间，可在 sm_12x 全家族上跑

L0.1 原始现场 ⑤ 里的 PTX 头写着 .target sm_120a， 而 FlashInfer 的 JIT 缓存目录叫 120f —— 一个用架构专属，一个用家族兼容。 库作者要在"用尽硬件"和"一份二进制覆盖更多卡"之间选。

纯发射吞吐：先把「上限」这个词说清楚

cuBLAS 报出来的 TFLOPS 里混着访存、tile 调度与尾效应。想知道 tensor core 本身多快，就写一个完全不碰内存的 kernel：数据全在寄存器，反复发同一条 mma。

这类测量有两个容易踩的坑，tensor_core_ladder.cu 都避开了：

  1. 依赖链。把所有 mma 累加到同一组寄存器上，量到的是指令延迟而不是发射间隔。必须用多组互不依赖的累加器把流水填满。
  2. 频率。用墙钟除以 FLOP 得到 TFLOPS，再除以采样来的频率换算 FLOP/clk/SM，会把频率采样的误差直接带进结论。改成在 kernel 内部读 clock64() 数周期，这一项就消失了。

延迟与发射间隔：同一条指令的两个数

以 m16n8k16 bf16 -> f32 为例，链数从 1 加到 16、每 block 4/8/16 个 warp（blocks/SM = 1）：

链数 warps TFLOPS 周期/指令 FLOP/clk/SM
1 4 221.2 34.95 468.8
1 16 250.0 128.50 510.0
4 4 248.6 32.00 511.9
16 16 251.9 127.75 513.0

单 warp 单链（整卡只有一个 warp 在发）量到 34.85 周期/指令，这是纯依赖延迟。链数一多，每个 warp 的「周期/指令」就收敛到 32（4 warp）、64（8 warp）、128（16 warp）——乘上 warp 数都是同一个常数：一个 SM 每 8 个周期接受一条 HMMA，即 512 FLOP/clk/SM。

延迟 35 周期、发射间隔 8 周期，两者差 4.4 倍。这就是为什么手写 GEMM 必须同时维护多组累加器：只用一组时，tensor core 有 3/4 的时间在等。

七条指令的发射上限

同样的方法跑完七种 PTX 形式，并用 nvdisasm 确认每条编成了哪个 SASS 操作码：

PTX 形式 SASS FLOP/指令 延迟（周期） 峰值 FLOP/clk/SM 峰值 TFLOPS
m16n8k16 bf16 -> f32 HMMA.16816.F32.BF16 4096 34.85 513.0 253.1
m16n8k16 f16 -> f16 HMMA.16816.F16 4096 29.81 994.5 484.9
m16n8k32 e4m3 -> f32 QMMA.16832.F32.E4M3.E4M3 8192 34.87 1026.0 503.6
kind::f8f6f4 m16n8k32 e4m3 -> f32 同上（同一条 SASS） 8192 34.89 1026.0 503.6
m16n8k32 e4m3 -> f16 QMMA.16832.F16.E4M3.E4M3 8192 29.81 1989.1 968.3
kind::mxf8f6f4.block_scale e4m3 -> f32 QMMA.SF.16832.F32.E4M3.E4M3.E8 8192 29.88 1974.1 958.3
kind::mxf4.block_scale m16n8k64 e2m1 -> f32 OMMA.SF.16864.F32.E2M1.E2M1.E8 16384 29.88 3805.3 1428.9

读出来的四件事：

(1) 上限落在整齐的四档：512 / 1024 / 2048 / 4096 FLOP/clk/SM。 实测 513、994.5、1026、1989、1974、3805 分别贴着这四档。

(2) .kind::f8f6f4 只是 PTX 层的前缀。 它和不带 kind 的写法编译成完全相同的 SASS（QMMA.16832.F32.E4M3.E4M3），实测吞吐也一模一样。SASS 普查里这条指令出现 1799 次，正是两个变体各 899 条之和——同一条硬件指令，两种写法。

(3) 延迟只有两档。 半速的三条都是 34.9 周期，全速的四条都是 29.8 周期。「跑得快的那几条同时也更短延迟」，说明它们走的不是同一条流水配置。

(4) 消费卡的 FP32 累加确实半速，但这条限制只管 mma.sync 的老形式。 e4m3 -> f32 是 1026，e4m3 -> f16 是 1989（2 倍）；而 block-scaled 的 e4m3 -> f32 也是 1974——同样是 f32 累加，换到 QMMA.SF 就没有半速限制。这条事实是下一节解开矛盾的关键。

一个未解释的趋势

全速的四条指令在链数 = 1、warps = 8 时达到峰值，链数加到 16 反而掉到 1200 左右；半速的三条则是链数越多越稳、最终贴住 1024。这条趋势本章未解释，不要直接引用。需要的诊断是 tensor 流水的发射与 stall 计数器（sm__inst_executed_pipe_tensor、smsp__issue_*），而 crater 的容器没有计数器权限，spark 能采但是另一块芯片（sm_121）。

真实 GEMM：频率要在运行时量，不能事后采样

把同一张卡上的 cuBLAS GEMM 放到这组上限里对照，先要解决频率。做法是在 GEMM 持续运行的同时，另起一条流跑一个只占 1 个 block 的 clock64 自旋 kernel（170 个 SM 里的 1 个，扰动可忽略），用「周期数 / 墙钟」直接得到被测区间的真实频率：

空闲时          2.541 GHz
bf16 GEMM 运行时 2.894 GHz（5 次采样 2.891–2.898）
fp8  GEMM 运行时 2.618 GHz（5 次采样 2.615–2.618）

三个频率互不相同，而且空闲时最低——GPU 在空闲时降频，跑起来才 boost。事后同步再读频率，读到的就是这个已经掉下来的值。

81923 的 GEMM（1.100 TFLOP）实测：

路径 ms TFLOPS 运行时 GHz FLOP/clk/SM 实际 kernel
bf16 torch.mm 4.996 220.1 2.894 447 cutlass_80_tensorop_bf16_s16816gemm_relu_bf16_128x64_64x3_nn_align…
fp8 torch._scaled_mm 2.047 537.2 2.618 1207 nvjet_sm120_qqtst_mma_128x128x64_6_64x64x64_tmaAB_bz_TNNN

bf16 这条很干净：447 / 513 = 87% 的指令发射上限，kernel 名里的 80 说明它走的是 Ampere 血统的 CUTLASS 模板（L0.1 的 trace 里也是这个名字）。

一个「超过上限」的数字该怎么拆

换一种常见的测法：跑完 GEMM、synchronize() 之后再读 NVML 的 SM 频率，得到 2.12 GHz，折算出 fp8 GEMM 1501 FLOP/clk/SM——比 QMMA.16832.F32 的发射上限 1026 高出 46%。一个要读写 HBM 的真实 GEMM 不可能超过它所用指令的发射上限，所以至少有一个假设是错的。拆开看，一半在测量方法，一半在参照的指令。

第一，频率。 2.12 GHz 是 GPU 已经开始降频之后采到的。按运行中实测的 2.618 GHz 重算：

rac537.2imes10122.618imes109imes170=1207 extFLOP/clk/SM

第二，参照的指令不对。 1207 仍然高于 QMMA.16832.F32 的 1026，所以 cuBLAS 不可能跑在这条指令上。候选有两个：f16 累加（上限 1989）和 block-scaled 的 f32 累加（上限 1974）。

第三，用数值把 f16 累加排除掉。 取 A=B=240（e4m3 可精确表示），单个乘积 240imes240=57,600 在 f16 里还能表示，两项相加 115,200 就超过 f16 上限 65,504。如果累加器是 f16，结果必然溢出成 inf：

K=   32  精确值       1,843,200   实测     1,843,200.0   一致
K=   64  精确值       3,686,400   实测     3,686,400.0   一致
K=  256  精确值      14,745,600   实测    14,745,600.0   一致
K= 1024  精确值      58,982,400   实测    58,982,400.0   一致

一路精确，累加器是 f32。

结论：cuBLAS 的 fp8 GEMM 跑在 f32 累加、且不受半速限制的那条路径上，也就是 block-scaled 的 QMMA.SF 一族；_scaled_mm 本身就要传缩放因子，kernel 名 nvjet_sm120_qqtst_… 也指向同一族。按这条参照，1207 / 1974 = 61% 的发射上限，与一个要读写 HBM 的真实 GEMM 相符。

这条推断还差最后一步直接证据：nvjet_* 系列由 cuBLASLt 在运行时生成，库文件里搜不到同名 cubin，因此没有拿到它的 SASS 做逐指令确认，这一项标记 UNVERIFIED。补法是用有计数器权限的机器采 sm__inst_executed_pipe_tensor 与指令混合，或在 CUTLASS 里用 QMMA.SF 写一个同尺寸 GEMM 做对照。

这一节的方法比结论重要

一个数字超过物理上界时，先怀疑测量，再怀疑参照，最后才怀疑硬件。本章的排查顺序是：验正确性（fp8 相对误差 0.0378）→ 验频率（并发测出 2.618 而不是 2.12）→ 验参照指令（补齐 7 条指令的上限）→ 用数值实验排除候选（f32 还是 f16 累加）。

排查过程表明：当实测指标异常超出理论基准时，关键在于系统性校准测量环境与参照基准，硬件本身的物理机制始终是一致的。

"+f" = 读写的 float 寄存器，"r" = 只读的 32 位寄存器。 volatile 阻止编译器把它当纯函数优化掉。

(2) 测吞吐必须用多组独立累加器

float c[4][4];              // 4 组累加器
for (int i = 0; i < iters; ++i) {
    #pragma unroll
    for (int rep = 0; rep < 4; ++rep)
    #pragma unroll
    for (int j = 0; j < 4; ++j) {          // ← 4 组轮转，互不依赖
        asm volatile("mma.sync..." : "+f"(c[j][0]), ... );
    }
}

独立累加器与 warp 数是同一件事的两种填法：要把 35 周期的延迟藏起来，靠「一个 warp 开多条链」或「一个 SM 上摆多个 warp」都行。本章阶梯实测：4 warp 单链 221.2 TFLOPS，4 warp 四链 248.6，16 warp 单链 250.0——warp 够多时单链也能填满，warp 少时就必须开多链。

这条结论依架构而变。Hopper 的 wgmma 是异步指令、延迟长得多，填法完全不同。

(3) 防优化

float s = 0;
for (int j = 0; j < 4; ++j) s += c[j][0] + c[j][1] + c[j][2] + c[j][3];
if (s == 1234.5f) *sink = s;    // 结果被"用"了，但几乎不产生额外开销

如果不写这行，编译器会发现 c 从未被读取，把整个循环删掉，你会测出无穷大的 TFLOPS。本章阶梯脚本踩过这个坑的变体：把结果写成 if (s == 1234.5f) *sink = s; 时循环被整段消掉，clock64() 的差值直接是 0、TFLOPS 报到六位数。改成无条件写回 sink[blockIdx.x] 才测到真实数字。

172 __global__ void ladder_kernel(int iters, float* sink, unsigned long long* cycles) {
173     uint32_t a0 = 0x3f803f80u, a1 = 0x3f803f80u, a2 = 0x3f803f80u, a3 = 0x3f803f80u;
174     uint32_t b0 = 0x3f803f80u, b1 = 0x3f803f80u;
175     uint32_t sa = 0x7f7f7f7fu, sb = 0x7f7f7f7fu;   // ue8m0 的 1.0（指数偏置 127）
176     if (V != V_BF16_F32 && V != V_F16_F16) {
177         a0 = a1 = a2 = a3 = 0x38383838u;      // e4m3 的 1.0
178         b0 = b1 = 0x38383838u;
179     }
180     float f32acc[CHAINS][4];
181     uint32_t f16acc[CHAINS][2];
182 #pragma unroll
183     for (int c = 0; c < CHAINS; ++c) {
184         f32acc[c][0] = f32acc[c][1] = f32acc[c][2] = f32acc[c][3] = 0.f;
185         f16acc[c][0] = f16acc[c][1] = 0u;
186     }
187     __syncthreads();
188     unsigned long long t0;
189     asm volatile("mov.u64 %0, %%clock64;" : "=l"(t0) :: "memory");
190     for (int i = 0; i < iters; ++i) {
191 #pragma unroll
192         for (int c = 0; c < CHAINS; ++c) {
193             if (V == V_BF16_F32) { MMA_BF16_F32(f32acc[c][0], f32acc[c][1], f32acc[c][2], f32acc[c][3]); }
194             else if (V == V_F16_F16) { MMA_F16_F16(f16acc[c][0], f16acc[c][1]); }
195             else if (V == V_FP8_F32) { MMA_FP8_F32(f32acc[c][0], f32acc[c][1], f32acc[c][2], f32acc[c][3]); }
196             else if (V == V_FP8_F16) { MMA_FP8_F16(f16acc[c][0], f16acc[c][1]); }
197             else if (V == V_KIND_F8_F32) { MMA_KIND_F8_F32(f32acc[c][0], f32acc[c][1], f32acc[c][2], f32acc[c][3]); }
198             else if (V == V_MXF8_BLOCK) { MMA_MXF8_BLOCK(f32acc[c][0], f32acc[c][1], f32acc[c][2], f32acc[c][3]); }
199             else { MMA_MXF4_BLOCK(f32acc[c][0], f32acc[c][1], f32acc[c][2], f32acc[c][3]); }
200         }
201     }
202     unsigned long long t1;
203     asm volatile("mov.u64 %0, %%clock64;" : "=l"(t1) :: "memory");
204     if (threadIdx.x == 0) cycles[blockIdx.x] = t1 - t0;
205     float s = 0;
206     uint32_t u = 0;
207 #pragma unroll
208     for (int c = 0; c < CHAINS; ++c) {
209         s += f32acc[c][0] + f32acc[c][1] + f32acc[c][2] + f32acc[c][3];
210         u ^= f16acc[c][0] ^ f16acc[c][1];
211     }
212     // 无条件写回：让累加器成为真正的输出，编译器不能把 mma 循环消掉
213     if (threadIdx.x == 0) sink[blockIdx.x] = s + (float)u;
214 }

221 template <int CHAINS, Variant V>
222 Result run_ladder(int sm_count, int iters, double flop_per_mma,
223                   int blocks_per_sm, int warps_per_block) {
224     int grid = sm_count * blocks_per_sm, block = warps_per_block * 32;
225     float* d_sink;
226     unsigned long long* d_cyc;
227     cudaMalloc(&d_sink, sizeof(float) * grid);
228     cudaMalloc(&d_cyc, sizeof(unsigned long long) * grid);
229     ladder_kernel<CHAINS, V><<<grid, block>>>(iters / 10 + 1, d_sink, d_cyc);
230     cudaDeviceSynchronize();
231 
232     cudaEvent_t a, b;
233     cudaEventCreate(&a); cudaEventCreate(&b);
234     cudaEventRecord(a);
235     ladder_kernel<CHAINS, V><<<grid, block>>>(iters, d_sink, d_cyc);
236     cudaEventRecord(b); cudaEventSynchronize(b);
237     float ms = 0; cudaEventElapsedTime(&ms, a, b);
238 
239     std::vector<unsigned long long> cyc(grid);
240     cudaMemcpy(cyc.data(), d_cyc, sizeof(unsigned long long) * grid, cudaMemcpyDeviceToHost);
241     unsigned long long med = 0;
242     for (auto c : cyc) med += c;
243     med /= grid;                                   // 各 block 的平均周期数
244 
245     double n_warps = (double)grid * warps_per_block;
246     double total_flop = n_warps * iters * CHAINS * flop_per_mma;
247     Result r;
248     r.ms = ms;
249     r.cycles = med;
250     r.tflops = total_flop / (ms * 1e-3) / 1e12;
251     r.cycles_per_mma = (double)med / ((double)iters * CHAINS);   // 每 warp 每条 mma 的周期
252     // 一个 SM 上同时有 blocks_per_sm 个 block、每 block warps_per_block 个 warp
253     double flop_per_sm = (double)blocks_per_sm * warps_per_block * iters * CHAINS * flop_per_mma;
254     r.flop_per_clk_sm = flop_per_sm / (double)med;
255     cudaEventDestroy(a); cudaEventDestroy(b);
256     cudaFree(d_sink); cudaFree(d_cyc);
257     return r;
258 }

陷阱

1. 以为 compute capability 越高越强。 sm_120 > sm_100 但用不了 tcgen05。 指令集不是单调递增的。

2. 以为「支持 Blackwell」是一句有意义的话。 必须问 sm_100 还是 sm_120。

3. -arch 写错了不会报错。 用 sm_89 编译在 5090 上照样能跑（驱动 JIT）， 但可能用不上新指令。这是最隐蔽的性能坑——没有任何报错，只是慢。

4. 忘了防优化。 结果没被使用，编译器会删掉整个循环，你会测出天文数字。

5. 跨实验比较 TFLOPS。 频率会因功耗墙、温度、负载类型变化 38%。 要比就比 FLOP/clk/SM。

6. 在 synchronize() 之后采样频率。 本章踩过：读到 0.18 GHz。 必须并发采样。

7. 把「消费卡 FP32 累加半速」当成整卡的性质。 本章实测：这条限制对 mma.sync 的老形式成立（e4m3->f32 1026 vs e4m3->f16 1989），但 block-scaled 的 QMMA.SF 同样是 f32 累加却跑满 1974。每换一代、每换一条指令都要重测。

8. 把自己测出的上限当成硬件上限。 本章第一版的 fp8 上限被 cuBLAS「超」了 47%，原因是只测了一条指令、又用事后采样的频率换算。「上限」永远要加限定词：哪条指令、什么累加精度、哪段区间的频率。

9. 用 -arch=sm_120a 编译架构专属指令。 nvcc 仍会额外生成 compute_120 的 PTX，ptxas 在这个非 a 目标上拒绝 .kind:: 特性，报错信息里写的是 .target 'sm_120'，很容易看成「这张卡不支持」。用 -gencode arch=compute_120a,code=sm_120a。

自测题

1. 为什么 fp8 的吞吐正好是 bf16 的 2.00 倍，而不是 1.8 或 2.3？

因为它是指令级的，不是硬件魔法：

  • bf16：m16n8k16，每条指令 2×16×8×16=4096 FLOP
  • fp8：m16n8k32，每条指令 2×16×8×32=8192 FLOP

而两条指令的发射速率相同（每 SM 每时钟能发同样多条 mma）。 所以吞吐比 = FLOP/指令 之比 = 2.00，精确到小数点后两位。

k 维之所以能翻倍：fp8 元素只有 1 字节，同样的 4 个 uint32 寄存器 （16 字节）能装 16 个 fp8 而只能装 8 个 bf16。寄存器容量固定，元素变小，k 就能变大。

推论：fp4（0.5 字节）能到 m16n8k64，每条指令 16384 FLOP。本章实测 kind::mxf4.block_scale 的上限是 3805 FLOP/clk/SM，相对 bf16 的 513 是 7.4 倍而不是 8 倍——因为发射间隔并没有完全跟上（延迟 29.88 周期这一档）。

但「发射速率相同」这个前提本身要验证：本章实测 e4m3->f32 与 e4m3->f16 的 FLOP/指令完全一样（都是 8192），吞吐却差 1.94 倍，正是因为两者的发射间隔不同。所以 2.00 倍这个结论只在「同一档发射速率」内成立。

2. 我在 5090 上跑 CUTLASS 的 Blackwell GEMM 模板，编译报一堆 tcgen05 错误。怎么办？

不是配置问题，是架构不匹配。 CUTLASS 的 Blackwell 模板针对 sm_100a （数据中心 Blackwell，有 TMEM 和 tcgen05）。sm_120 没有这些硬件。

正确做法：用 CUTLASS 面向 sm_120 / sm_89 的模板（mma.sync 血统）， 或者直接用 cutlass_80_tensorop_* 那条路径——L0.1 的 trace 显示 vLLM 在 5090 上跑的正是它。

不要试图"修"这个编译错误。 它不是错误，是硬件事实。

3. 我的自写 GEMM 达到了 cuBLAS 的 95%。还有优化空间吗？怎么判断？

分两步判断。

第一步：cuBLAS 自己离硬件上限有多远？ 本章实测 bf16 是 447 / 513 = 87%。 所以达到 cuBLAS 的 95% ≈ 硬件上限的 83%，还剩约 17%，但这部分要从访存与调度里抠。

第二步：确认自己用的是哪条指令。 fp8 上 cuBLAS 折算出 1207 FLOP/clk/SM， 而 QMMA.16832.F32（即 mma.sync.m16n8k32 ... f32）的上限只有 1026。 如果你的 fp8 GEMM 用的是这条指令，天花板就是 1026，无论怎么调 tile 都追不上 cuBLAS—— 它跑在上限 1974 的 block-scaled 一族上。这时候要换指令，不是调 tile。

方法要点：永远先确定当前所选指令的吞吐上限是多少，再分析实测离上限的差距，最后评估是否存在更高效的指令选择。 只盯着 cuBLAS 的百分比，会在错误的层面上优化。

4. 我的 kernel 在 nsight 里显示 tensor core 利用率 60%，但换成访存更少的版本后利用率降到 55%，总时间反而变短了。为什么？

两个原因，本章都测到了。

(1) 频率。 访存少 → 功耗低 → 频率高。本章用并发的 clock64 探针实测：空闲 2.541 GHz、 bf16 GEMM 运行时 2.894 GHz、fp8 GEMM 运行时 2.618 GHz。 fp8 GEMM 每秒搬的字节更多、算得也更满，频率反而被压低 9.5%。 即使「利用率」降了，绝对吞吐也可能涨；反过来频率掉了也不代表算得少。

(2) "利用率"的分母是时间。 利用率 = tensor core 忙的时间 / 总时间。 如果你把总时间缩短了，而 tensor core 的绝对工作量不变，利用率反而可能下降。

结论：利用率是诊断指标，不是优化目标。唯一的目标是墙钟时间。 L2.6 会讲怎么正确使用 ncu 的各项指标。

5. cuBLAS 的 fp8 GEMM 折算出 1501 FLOP/clk/SM，而纯发射基准只有 1022。这个矛盾怎么拆？

结论先说：一半是频率测错，一半是参照的指令选错。硬件没有问题。

第一步，验正确性。 fp8 GEMM 对 bf16 参照的相对误差 0.0378，量级正常——它确实在算这个矩阵乘，不是跳过了计算。

第二步，验频率。 1501 用的是 synchronize() 之后采到的 2.12 GHz，而那时 GPU 已经开始降频。改成在 GEMM 持续运行时、用另一条流上只占 1 个 block 的 clock64 自旋 kernel 直接量：2.618 GHz（5 次采样 2.615–2.618）。重算得 1207 FLOP/clk/SM。

第三步，验参照。 1207 仍高于 QMMA.16832.F32 的 1026，说明 cuBLAS 不在这条指令上。把七条候选指令的上限都测出来之后，只剩两个候选：f16 累加（1989）与 block-scaled f32 累加（1974）。

第四步，用数值排除一个。 取 A=B=240：单个乘积 57,600 在 f16 里还能表示，两项相加 115,200 就溢出。实测到 K=1024 仍精确等于 58,982,400，累加器是 f32，f16 累加被排除。

剩下的就是 block-scaled 一族——_scaled_mm 本来就要传缩放因子，kernel 名 nvjet_sm120_qqtst_… 也指向同一族。按这条参照，cuBLAS 达到发射上限的 61%。

还差一步：nvjet_* 由 cuBLASLt 运行时生成，库里搜不到同名 cubin，没能拿到它的 SASS 做逐指令确认。补法是用有计数器权限的机器采 tensor 指令计数，或用 CUTLASS 写一个同尺寸的 QMMA.SF GEMM 做对照。

方法上的要点：实测指标若异常超出标称物理上界，标准排查顺序应为「测量方法 → 参照基准 → 理论假设 → 硬件规格」，逐层排除测量环境、动态主频与累加格式对基准线的影响。
