8.2

编排：K8s / Ray / Slurm

gang scheduling、GPU 共享(MIG/MPS)；llm-d / NVIDIA Dynamo / vLLM production-stack / SGLang router 架构对比。含滚动更新与租户边界。

实测机器 worldvln（2× L40S，PCIe）· crater2（RTX 5090）· Qwen3-1.7B · vLLM 0.29.0前置 6.0（集合通信与进程组）· 8.1（路由与网关）· 8.7（冷启动与权重分发）

本章回答三个问题

  1. GPU 资源怎样变成一个可用的 worker？ 实测从"选定显卡"到"能服务"要 46.1 s（冷编译缓存）或 27.1 s（热缓存），其中"进程活着但接不了请求"的窗口占 36.8 s / 21.5 s。
  2. 就绪、排空和重启怎样影响请求？ 1600 条持续重放请求里，一次 SIGKILL 崩溃 + 一次滚动更新导致 1 条在途请求重试 3 次后失败并被记录，其余 1599 条成功；副本分别停机 55.5 s 与 60.6 s。
  3. 不同编排器的职责边界在哪里？ K8s、Ray Serve、Slurm 都把"分配资源"和"进程可用"分成两层；把它们混成一层，就会出现"pod Running 但请求全 502"。

本章的边界

本项目的两台 GPU 机器都是容器，没有集群控制面：没有 kubelet、没有多个节点、没有 Slurm 控制机，也没有 MIG 能力（实测 nvidia-smi mig -lgip 在两台机器上都返回 No MIG-supported devices found）。因此本章只做容器内能真实复现的部分：真实 worker 进程的六阶段、三级就绪探针、崩溃与滚动更新、TP=2 的整组/部分分配。K8s / Ray Serve / Slurm / MIG / MPS 的真实部署在本机没有执行，只做固定版本源码与官方文档的字段映射，并明确标注为未完成。

心智模型：三种"活着"之间的空隙

机制拆解与推导

1. 六阶段，以及每一段由什么触发

状态 进入条件 能接请求吗 实测（crater2 冷 / 热）
ALLOCATED 选定的 GPU 显存空闲（本机以 nvidia-smi 核对） 否 0.004 s / 0.0003 s
LOADING 进程已起，权重文件在读 否 22.0 s / 16.4 s
WARMING 权重加载完，正在编译与捕获图 否 24.1 s / 10.7 s
READY 一次真实补全返回 200 且有 token 是 累计 46.1 s / 27.1 s
DRAINING 已从路由中摘除，等在途请求归零 不再接新请求 实测 0.0069 s（当时无在途）
STOPPED 进程退出且显存回到基线 否 SIGTERM 后 1.0 s 内回收 32.6 GB

三点值得单独说明。一，"进程存活"覆盖了 80% 的启动时间（36.8 s / 46.1 s）。任何只检查 PID 或只检查 TCP 端口就宣布就绪的做法，都会在这段时间里把请求送进一个必然失败的目标。二，/v1/models 并不早于服务能力：本次 148 次冷启动探测里，http_ready 为真但 serving 为假的情况是 0 次——vLLM 0.29 的 HTTP 层在引擎可服务之后才对外。所以"HTTP 200 但不可服务"这个常见假设在本版本上不成立；真正的假就绪窗口在它之前。三，退出比启动快一个数量级以上：SIGTERM 到显存归还实测 0.4–2.1 s，而启动要 27–46 s。扩容与缩容的代价天然不对称。

2. 就绪判据必须是"真实请求"，但探测本身有代价

三级探针的成本完全不同：读 /proc 是微秒级；GET /v1/models 是毫秒级；发一次真实补全是几十毫秒到几百毫秒，而且会占用引擎的一个批处理位置。本次把真实补全探测放在 250 ms 的轮询周期上，探测本身就在给正在启动的引擎加压。生产做法是分层：

  • 高频（1–5 s）：/health 或 /v1/models，承担"进程还在不在"；
  • 低频（启动后一次、或每 N 秒）：真实请求探测，承担"能不能真出 token"；
  • 结果进入一个滞回判据（连续 k 次成功才 READY，连续 m 次失败才摘除），避免单次超时抖动导致流量抖动。

3. 滚动更新的容量算术

设副本数 R、单副本就绪时间 Tready、更新一个副本的时间 Troll。maxUnavailable=0（先起新再停旧）要求同时存在 R+1 份资源；maxSurge=0（先停旧再起新）则在 Troll 内只有 R−1 个副本可用，剩余副本的负载变成 R/(R−1) 倍。

本次实测的两次事件（worldvln，两个副本，10 QPS 持续重放）：

事件 时刻（重放开始后） 在途请求 恢复时刻 停机时长
SIGKILL 崩溃 worker-0 30.08 s 1 85.74 s 55.5 s
滚动更新 worker-1（排空→SIGTERM→新进程） 90.08 s 0 150.66 s 60.6 s

在这两段窗口里，另一个副本独自承担全部 10 QPS。如果两个副本同时不可用，就没有任何副本可接请求；这正是 maxUnavailable: 0 + maxSurge: 1 存在的理由，也是本次实验中"崩溃恢复还没完成就开始滚动更新"这一操作的直接风险（测试设计中显式构造了该重叠窗口以验证风险边界）。

单副本的重启本身（lease→READY）：崩溃重启 54.8 s（权重 32.6 s + 就绪 22.2 s），滚动更新新进程 57.0 s（权重 34.4 s + 就绪 22.6 s）。两者都明显快于最初的并发冷启动 117.3 s——同机同缓存的对比说明：并发启动不是免费的，两个进程同时读权重、同时编译，单副本就绪时间会显著拉长。

4. gang scheduling：分配不等于就绪

TP=2 的 worker 要么拿到两张卡、要么一张都别要。实测三种情形（worldvln，L40S，默认编译缓存）：

情形 可见 GPU TP 结果 耗时
两卡可见 1,3 2 READY 86.1 s
只给一张卡 1 2 立即失败，exit 1 14.0 s
单卡 1 1 READY 58.0 s

部分分配的失败原因是引擎自己拒绝启动，原文是

Value error, World size (2) is larger than the number of available GPUs (1) in this node.

这是好的失败方式：在加载权重之前就报错，不浪费 86 s。真正危险的是另一种情形——调度器分别、非原子地分配两张卡，第一张给出去以后第二张永远等不到，进程就卡在集合通信初始化里，既不失败也不就绪。这就是"不能把获得两块 GPU 的时间当成模型就绪时间"的完整含义：分配是瞬时事件，就绪是 58–86 s 的过程，两者之间还夹着一个可能永久阻塞的状态。

5. 隔离机制的能力边界

机制 提供什么 不提供什么 本机可用性
MIG 把受支持的 GPU 切成多个实例，每份有独立的计算与显存 只在受支持的型号上存在；同一实例内无二级隔离 不可用：nvidia-smi mig -lgip 在 L40S 与 RTX 5090 上都返回 No MIG-supported devices found
MPS 多进程共享同一 GPU，减少上下文切换，提供 SM/显存分区的控制接口与优先级 进程间没有内存与故障隔离；一个进程崩溃可能影响同组其他进程 二进制存在（/usr/bin/nvidia-cuda-mps-control、nvidia-cuda-mps-server），但本机是共享机器，未启用
进程隔离 独立地址空间、独立 CUDA 上下文 仍共享显存带宽与 L2；显存超卖会互相挤占 可用，是本章所有实验的基础
应用层配额 请求数/并发/Token 预算 不阻止越权进程直接吃显存 可用（8.8 展开）

工程实现：源码解析与设计取舍

Kubernetes：三种探针 + 两个时间窗

staging/src/k8s.io/api/core/v1/types.go（commit 467cf7b）里的字段定义了容器可用的全部就绪语义：

  • Probe（:3013）：InitialDelaySeconds（:3019）、FailureThreshold（:3036）；
  • StartupProbe（:3348）、ReadinessProbe（:3339）、LivenessProbe（:3333）；
  • TerminationGracePeriodSeconds（Pod 级 :3048，容器级 :4496）。

startupProbe 的语义是"在它成功之前，readiness 与 liveness 都不生效"。 这正好对应本章的 WARMING 阶段：把 failureThreshold × periodSeconds 设成大于冷启动到可服务的时间（本次 46.1 s，加上两个副本并发启动的放大取 300 s），容器才不会在编译阶段被判死。terminationGracePeriodSeconds 是排空窗口：kubelet 先执行 preStop，再发 SIGTERM，超过这个时限才 SIGKILL。它与 8.2-B 里的 drain() 是同一件事的两种实现。

Ray Serve：副本状态机

python/ray/serve/_private/deployment_state.py（commit 03aa07f）里 ReplicaState 有 STARTING（:172）、RECOVERING（:173）、RUNNING（:174），另有 PENDING_ALLOCATION / PENDING_INITIALIZATION（:541-544）。两个 PENDING 状态恰好把"资源分配"和"进程初始化"分开——这就是本章六阶段里 ALLOCATED 与 LOADING/WARMING 的对应物。graceful_shutdown_timeout_s 是它的 terminationGracePeriodSeconds。

Slurm：allocation / step / 进程内就绪

Slurm 的三层是 sbatch（拿到节点与 --gres=gpu:N）、srun（启动作业步里的进程）、以及进程自己加载模型。srun 返回不等于模型可用：本机实测从进程启动到可服务是 46.1–86.1 s，这段时间在 Slurm 视角里只是"作业步在运行"。--exclusive 提供的是节点级独占，等价于 K8s 的 nvidia.com/gpu 独占语义。

gang scheduling

自调度式的"逐个 pod 抢资源"无法表达"要么全给、要么不给"。Kubernetes 的做法是 PodGroup：kubernetes-sigs/scheduler-plugins 的 coscheduling 插件（Beta）用标签 scheduling.x-k8s.io/pod-group 把一组 Pod 绑成同生共死的一个调度单位。TP=2 的 worker 就该这么申请——本次 D 段实测的"只给一张卡时引擎直接报错退出"说明，没有 PodGroup 时至少还有引擎自己兜底；但兜底发生在加载权重之后（14.0 s），而 PodGroup 是在调度阶段就不放行。

设计取舍

选择 代价 依据
就绪判据用真实补全，而不是 /health 探测本身占用批处理位置 本版本 /v1/models 与可服务同时出现（0 次假就绪），但这是实现细节而非契约；跨版本跨引擎不可依赖
排空用"等在途归零"而不是固定 sleep 需要网关维护在途计数 固定 sleep 要么浪费容量、要么切在请求中途
崩溃重启不保留请求状态 在途请求只能靠客户端重试 引擎本身无跨进程请求状态；重试必须由客户端按 request_id 幂等处理
TP>1 用整组分配 调度成功率下降、资源碎片增加 部分分配要么被引擎拒绝（浪费加载时间），要么卡死在集合通信初始化

工程实现：mini 实现

labs/L8/worker_lifecycle.py 用真实子进程实现六阶段，三个探针互相独立：

labs/L8/worker_lifecycle.py 三级探针与阶段切分 
class ProbeClient:
    def http_ready(self) -> bool:
        code, _ = self._http("GET", "/v1/models", timeout=3.0)
        return code == 200

    def serving(self) -> bool:
        body = json.dumps({"model": self.model, "prompt": [9707],
                           "max_tokens": 1, "temperature": 0.0}).encode()
        code, raw = self._http("POST", "/v1/completions", body, timeout=30.0)
        ...

phase_segments() 按每次 gpu_lease 切段。这一点不是细节：同一个 supervisor 会经历"首次启动 → 崩溃 → 重启"多次启动，只取第一条 ready 会把重启算成 117 s 而不是 55 s（本项目第一次统计就踩了这个坑，修正后段统计为 54.8 s）。

labs/L8/run_8_2.py 是驱动：A 段做冷/热启动时间线，B 段用两个真实副本做崩溃与滚动更新重放，客户端对失败的请求用同一个 request_id 重试并把 attempts 逐条记下来。labs/L8/gang_probe.py 做 D 段的 TP=2 与部分分配探针。

前沿

  1. 副本状态机是编排器的共同抽象。 Ray Serve 把副本分成 STARTING / RECOVERING / RUNNING 与 PENDING_ALLOCATION / PENDING_INITIALIZATION；Kubernetes 用 startupProbe 把"启动中"从"就绪"里单独切出来。两者都在回答同一个问题：哪一段时间允许把请求发进来。
  2. 整组调度。 kubernetes-sigs/scheduler-plugins 的 coscheduling（Beta）用 scheduling.x-k8s.io/pod-group 表达 all-or-nothing；Volcano 等批调度器提供同一语义。TP/PP 并行的 worker 天然属于这一类。
  3. 隔离能力取决于硬件。 MIG 只在受支持的型号上存在（本机 L40S 与 RTX 5090 均不支持），且它提供的是实例内的资源切分而非安全边界；MPS 提供利用率与分区接口，但不提供内存与故障隔离。把"共享 GPU"当成"隔离"是 8.8 要展开的陷阱。
  4. 服务侧的编排层。 Gateway API Inference Extension 与 llm-d 把"哪个 pod 可以接流量"做成 Endpoint Picker 的就绪集合，和本章的三级探针是同一层语义（材料见 results/worldvln/8.1/20260914-refs/）。

陷阱

  1. 用 PID 或端口当就绪。 实测进程存在但不可服务的窗口有 36.8 s（冷）/ 21.5 s（热）。
  2. 把 startupProbe 的窗口设得比冷启动短。 结果是容器在编译阶段被反复重启，永远到不了 READY。
  3. 忘了排空就给 SIGTERM。 本次崩溃（无排空）当场打掉 1 条在途请求；滚动更新那次因为刚好无在途，排空只花了 0.0069 s——排空的代价取决于流量，不是常数。
  4. 在另一个副本还没恢复时就滚动更新它。 两个副本同时不可用就没有兜底；maxUnavailable: 0 + maxSurge: 1 是为此存在的。
  5. 把"分到两张卡"当成"TP=2 可用"。 分配是瞬时的，就绪要 86.1 s；非原子分配还会卡死在集合通信初始化。
  6. 跨机器比较启动时间。 本章 A 段在 RTX 5090 上、B/D 段在 L40S 上，绝对值不可比；只有同机同缓存的前后对比（117.3 s → 54.8 s）才说明问题。
  7. 并发启动当并行扩容。 两个副本同时冷启动各需 117.3 s，而不是各自 46.1 s 的并行版本——权重 I/O 与编译都在抢同一台机器的资源。

自测题

1. 为什么"进程存活"不能作为就绪判据？请给出本机实测的窗口大小。

答案： 因为模型加载与编译都发生在进程启动之后。crater2 上 Qwen3-1.7B 冷启动时，lease → READY 是 46.1 s，其中 147 次探测（≈36.8 s，占 80%）处在"进程存在但不能服务"的状态；热编译缓存下这个窗口是 21.5 s。只检查 PID 或 TCP 端口会把这段时间误判为可用，请求必然失败。

2. vLLM 0.29 上"HTTP 200 但不服务"的假就绪窗口有多大？这说明什么？

答案： 实测为 0 次——/v1/models 返回 200 的时刻与真实补全成功几乎同时。这说明在该版本里 HTTP 层在引擎可服务之后才对外，但不能把这条当成契约：它是实现细节，换版本、换引擎（SGLang、TensorRT-LLM）或换成经网关暴露的服务都会变。就绪判据应当显式声明依赖的是哪一层语义，并在升级时重测。

3. 为什么滚动更新的停机时间（60.6 s）不是"排空时间 + 启动时间"的简单相加？

答案： 因为排空时间为 0.0069 s（那一刻恰好没有在途请求），所以停机时间几乎完全等于"老进程停止到新进程 READY"的 57.7 s，而启动时间里又包含权重加载（34.4 s）与编译/图捕获（22.6 s）两段。排空是流量相关的，启动是资源相关的；两者要分开测、分开优化，不能合成一个"更新耗时"。

4. TP=2 只分到一张卡时会发生什么？为什么这个失败方式是可接受的？

答案： 引擎在参数校验阶段就报 World size (2) is larger than the number of available GPUs (1) in this node 并退出（14.0 s，exit 1），没有进入权重加载。这比"卡在集合通信初始化里既不失败也不就绪"好得多：前者是有界失败，后者会一直占用已分配的 GPU 直到超时。真正的防护仍是调度阶段的整组分配（PodGroup / --exclusive），引擎报错只是最后一道兜底。

5. 为什么并发冷启动两个副本比串行启动更慢（每个 117.3 s vs 46.1 s）？

答案： 两个进程同时读同一份权重文件、同时跑编译与图捕获，争用同一台机器的磁盘/页缓存、CPU 与内存带宽，于是各自的阶段都被拉长。这说明"扩容 N 个副本"的延迟不是单副本延迟，而是资源争用下的放大量；容量规划必须按并发启动的实测值算，而不是单副本值乘 N。
