8.7

冷启动与权重分发

'拉一个模型要几分钟'直接决定能不能自动扩容。加载加速、权重分发、镜像与缓存策略。1.5 量过存储路径，这一章把它连到扩容延迟。

实测机器 crater2（RTX 5090 32 GB）· Qwen3-1.7B（权重在 NFS4 上）· vLLM 0.29.0前置 1.5（网络与存储）· 4.0（checkpoint 格式）· 8.2（编排与就绪）· 8.3（到达轨迹与 SLO）

本章回答三个问题

  1. 从进程到首个有效请求经过哪些阶段？ 同机同模型，冷编译缓存 39.4 s、热编译缓存 19.3 s，其中编译一项就差 11.7 s。
  2. 文件、JIT 与图缓存怎样改变成本？ 三次运行把两笔账拆开：编译缓存值 11.7 s（外加引擎初始化里 5.0 s），而"权重页缓存"这一维在 NFS 存储上没有测到（定点驱逐 3.8 GiB，实际只从设备读了 11 MiB）。
  3. 扩容滞后怎样进入容量预算？ 用 8.3 的真实到达轨迹模拟：预热池（就绪 0 s）在 120 s 窗口内把 SLO 违规压到 0，代价是 90% 的副本秒处于空闲；用实测的 27.1 s / 55.5 s 扩容滞后，违规率分别升到 28.2% / 56.0%。

本章的边界

本章只做单机、单进程的启动账本，以及基于真实轨迹的扩容模拟。Kubernetes 的镜像分发、Slurm 的作业启动、跨机权重广播都不在本机能力范围内（8.2 已说明容器内没有集群控制面）。容量结论因此限定为"用实测就绪时间与实测容量曲线推出来的预算"，不是集群实测。

心智模型：就绪账本的八段

机制拆解与推导

1. 八段各自的含义与实测

段 由什么触发结束 冷编译 热编译 说明
进程启动 → 引擎初始化 vLLM 打印 Initializing a V1 LLM engine 14.7 s 9.7 s 含 Python 导入；单独测 import 只有 3.4–3.7 s（torch 0.55 + vllm 0.94 + transformers 0.40 + flashinfer 0.73）
→ 开始加载模型 Loading model from scratch 1.1 s 1.1 s 建模块、算 shape
→ 权重加载完 Loading weights took X seconds 2.32 s 0.71 s safetensors 反序列化 + H2D
→ 权重阶段结束 Model loading took ... GiB memory 1.0 s 1.0 s 3.22 GiB 权重驻留
→ 编译结束 torch.compile took X s in total 12.40 s 0.60 s 差异最大的一项

→ READY 一次真实补全返回 200 4.8–6.6 s 3.6 s HTTP 层与引擎的握手

合计：冷 39.4–39.5 s，热 19.3 s。 两条独立证据说明差异来自编译缓存而不是别的：engine_init 段差了 5.0 s（14.7 vs 9.7，引擎初始化时会读编译缓存），compile 段差了 11.8 s；而权重段在两组的"热数据"条件下只差 0.01 s。

2. 三次运行构成的 2×2 分解

要求"区分冷进程/热文件缓存、冷 JIT/热 JIT 与热图"，就得让两个因子独立变化。三次运行的设计与结果：

运行 编译缓存 权重页缓存（尝试） READY read_bytes 权重段 编译段
1 cold_compile_cold_data 冷（新目录） 已驱逐 3.799 GiB 39.5 s 10.99 MiB 2.32 s 12.40 s
2 warm_compile_warm_data 热（同一目录） 热 19.3 s 0.00 MiB 0.71 s 0.60 s
3 cold_compile_warm_data 冷（另一个新目录） 热 39.4 s 0.00 MiB 0.70 s 12.29 s

从 2 与 3 的对比拿到干净的编译缓存效应：39.4 − 19.3 = 20.1 s，其中编译 11.7 s、引擎初始化 5.0 s、其余约 3.4 s。从 1 与 3 的对比本该拿到页缓存效应，但两条都显示权重段几乎不变（2.32 vs 0.70 s），read_bytes 只有 11 MiB——权重并没有真的从设备重读。

3. 为什么"换了文件名/驱逐了缓存"不等于冷读

本机的权重目录在 NFS4 上（vLLM 自己打印 Filesystem type for checkpoints: NFS4），而 posix_fadvise(POSIX_FADV_DONTNEED) 对网络文件系统上的客户端页缓存是否真的丢弃、以及服务端是否仍缓存这些块，都不由调用者控制。实测证据是：驱逐接口报告 12 个文件 / 3.799 GiB，但下一次运行的 read_bytes 只有 11.0 MiB（权重 3.78 GiB），且权重段仍是 2.32 s。

结论：本机在不动 drop_caches、不改共享机器状态的前提下，拿不到可证明的"冷文件缓存"条件。 这一维按事实标为 UNVERIFIED，不作为结论使用。要做到可控冷读，需要：独占机器且有 root 时按分区 drop_caches，或把权重放到可控的本地块设备上并用 O_DIRECT/fadvise 验证，或在另一台确实没有该文件页缓存的机器上跑。这三条本章都不具备。

4. 权重"取回"与"本地加载"必须分列

第一批运行（用仓库名 Qwen/Qwen3-1.7B 启动）里，vLLM 的 weight_utils 阶段打印：

Time spent downloading weights for Qwen/Qwen3-1.7B: 325.377769 seconds
Filesystem type for checkpoints: NFS4. Checkpoint size: 3.78 GiB. Available RAM: 0.44 GiB.
WARNING Network filesystem (NFS4) detected but checkpoint total size (3.78 GiB)
        exceeds 90% of available RAM (0.44 GiB). Skipping auto-prefetch.

同一份权重、同一台机器，取回阶段 325.4 s，而真正的本地加载只有 35.9 s（该次日志的 Loading weights took）。两者相差近十倍，且都发生在"模型加载"这个笼统的说法里。这正是任务书要求"权重下载与本地加载分列"的理由：把 325 s 记成"加载慢"，优化方向会完全错（该优化存储路径与内存压力，而不是换 loader）。

那 0.44 GiB 可用内存是这个阶段被放大的直接原因：vLLM 检测到网络文件系统后，本可以预取（prefetch）整个 checkpoint 到内存再加载，但预取要求约 3.78 GiB 可用内存，而当时机器只剩 0.44 GiB，于是自动预取被跳过，改为逐分片现读。同一台机器上"可用内存"会把取回时间从几秒放大到几百秒——这是一个可复现的环境条件（当时另有进程占用内存），不是随机噪声。

第二、三批运行改用显式本地快照路径（--model-path）后，取回阶段消失，账本只剩反序列化与 H2D（0.70–2.32 s），三次运行因此可以只差"缓存状态"这一个变量。

5. 扩容滞后进入容量预算

预热副本、按需扩容与不扩容的差别，只有放进真实到达轨迹里才看得见。用 8.3 的 1.1× 档轨迹（1378 条请求、119.9 s、平均 11.49 QPS）对 8.3 实测的参考容量 10.317 QPS 做离散事件模拟，扩容阈值取队列长度，就绪时间取实测值（0 s = 预热池；27.1 / 39.4 s = 8.7 的热/冷启动；55.5 s = 8.2 的崩溃重启）：

读法（这是模拟，不是实测）：

  1. 阈值越晚触发，扩容滞后越致命。 阈值 4 时等 27.1 s 的代价是 15.3% 违规；阈值 64 时同样的滞后代价是 53.9%。晚扩容意味着队列已经很长，而这段时间所有请求都在等。
  2. 预热池买到的是"零滞后"，代价是空闲。 阈值 4 的预热池把违规压到 0，但 304 副本秒里有 274 秒是空闲的（90%）。也就是说，在这个 120 秒的负载窗口里，用约 4.6 倍的副本时间换掉了全部违规。
  3. 阈值不能只看队列长度。 阈值 16 的预热池违规 1.5%，比阈值 4 的 0% 差，但副本秒少 22%。阈值的选择是把"违约定价"与"空闲定价"放在一起做，而两者的价格来自 8.5 的假设文件。

模型的边界必须写清楚：排队时延用 8.3 实测的 (利用率, TTFT p50) 四点做分段线性插值、超出最高实测点后线性外推；副本容量按线性叠加（乐观，未考虑显存与批处理上限）；窗口只有 120 s，"空闲副本秒"占比会随窗口长度变化。因此表中数值用于比较策略方向，不用于承诺绝对容量。

工程实现：源码解析与设计取舍

vLLM 侧与启动账本相关的三个真实入口

  • 分片预取线程数：vllm/config/load.py:11 定义 DEFAULT_SAFETENSORS_PREFETCH_NUM_THREADS = 8；是否启用多线程加载另有条件，vllm/model_executor/model_loader/default_loader.py:121 给出"不支持"的情形说明。本次三次运行的 weights 段在热数据下都是 0.70 s，说明分片读取不是瓶颈——在 NFS + 低内存条件下它才成为瓶颈（第一节的 325 s）。
  • 权重取回阶段：vllm/model_executor/model_loader/weight_utils.py 打印 Time spent downloading weights、Filesystem type for checkpoints 与自动预取开关（三行日志都在本次工件里）。这三行是把"取回"与"本地加载"分开的依据。
  • 就绪判据：vLLM 的 /v1/models 与 /health 都在引擎可服务之后对外（8.2 实测 0 次"HTTP 200 但不可服务"），所以本章的账本以一次真实补全为终点，而不是 HTTP 端点。

设计取舍

选择 代价 依据
阶段标记直接对齐 vLLM 日志行 绑定该版本的日志文案 比"按时间猜"可复算；升级后需重新核对标记，正文已写出全部标记
逐段增量读日志、取首次出现 需要维护读取偏移 只读尾部窗口会漏掉早期标记（PIECEWISE 的完成行会被 FULL 覆盖，本章第一版就踩到）
用 posix_fadvise 定点驱逐而不是 drop_caches 在 NFS 上可能无效 共享机器不允许改全局状态；宁可承认没测到冷读，也不伪造条件
显式 --model-path 固定其余变量 与生产里"按仓库名拉取"不同 只有这样三次运行才只差缓存状态；"取回"单独用第一批数据说明
扩容用离散事件模拟而非真实扩容 容量线性叠加是乐观假设 本机只有一个 GPU，真实扩容需要集群；模拟的输入全部来自实测

MARKERS = [
    ("Initializing a V1 LLM engine", "engine_init"),
    ("Loading model from scratch", "model_load_scratch"),
    ("Time spent downloading weights", "weights_fetch_done"),
    ("Loading weights took", "weights_loaded"),
    ("Model loading took", "model_loaded"),
    ("torch.compile took", "compile_done"),
    ("Capturing CUDA graphs (PIECEWISE)", "capture_start"),
    ("Graph capturing finished", "graph_capture_done"),
]

def evict_paths(paths):
    """对给定文件做定点页缓存驱逐 (POSIX_FADV_DONTNEED)。"""
    for p in paths:
        fd = os.open(p, os.O_RDONLY)
        try:
            os.posix_fadvise(fd, 0, 0, os.POSIX_FADV_DONTNEED)
        finally:
            os.close(fd)

scale_out_budget.py 是 8.7-C 的模拟器：到达时刻直接读 8.3 的逐请求记录，容量与时延曲线用 8.3 实测值，就绪时间用 8.2/8.7 实测值；输出里带 steps_out_of_measured_range，用来标记有多少时间步落在实测曲线之外（本次全部落在内插区间，外推只用于阈值 64 的少数步）。

前沿

  1. 无服务器推理的冷启动。 Torpor（arXiv:2306.03622）用实例复用与状态保持压低无服务器推理的启动延迟；它与本章"预热池用 4.6 倍副本时间换掉全部违规"是同一个权衡的两种表达——预热池就是把空闲资源当成延迟的替代品。
  2. 训练/推理作业的资源编排。 GPU 数据中心调度综述（10.1145/3638757）系统整理了放置、抢占与碎片问题；本章的"扩容阈值与就绪时间共同决定 SLO"是其中最小的一格。
  3. 权重加载的工程接口。 vLLM 在 vllm/config/load.py 暴露预取线程数、在 default_loader.py 记录多线程加载的适用条件；分片数与并行读取是"本地加载"这一侧可调的全部旋钮。本章测到的 0.70 s（热数据）说明在这一侧没有多少可优化空间，真正的放大项在存储路径与内存压力。
  4. 能耗与启动的交叉。 8.5 的能耗账说明空闲也在耗电（本次 28.8 W 待机），把 8.5 的空闲功率乘上预热池的空闲副本秒，就是"零违规"的价格；两章的数据可以直接相乘，读者可以用自己的价格假设复算。

陷阱

  1. 把"模型加载"当一个数。 本次同一台机器上，权重取回是 325.4 s，本地加载是 35.9 s；记成一个数会让优化方向全错。
  2. posix_fadvise(DONTNEED) 不等于冷读。 在 NFS 上它可能无效；用 read_bytes 与权重体积对照才能证明（本次 10.99 MiB vs 3.78 GiB）。
  3. 换文件名不代表冷数据。 本章没有换名字，而是定点驱逐，并由 read_bytes 判定——判定结果就是"没有冷读"。
  4. 只读尾部日志会漏标记。 PIECEWISE 与 FULL 两阶段都打印 Graph capturing finished，只读尾部会取到 FULL 的那一行（本章第一版因此把 33 s 的捕获记成 2 s）。
  5. 可用内存会改变取回路径。 vLLM 在检测到网络文件系统时先看可用内存再决定是否预取；本次 0.44 GiB 可用内存让它放弃预取，取回时间因此放大近十倍。
  6. 把模拟当实测。 第 5 节的表全部来自模拟；容量线性叠加、时延曲线插值与 120 s 窗口都是模型假设，只能用来比较策略方向。
  7. 扩容阈值不能只看队列长度。 阈值 4 与 16 的差别在预热池下是 0% 与 1.5% 违规、但副本秒差 22%；阈值必须和"违约定价"一起定。

自测题

1. 同一台机器、同一个模型，为什么两次启动相差 20.1 s？

答案： 差异来自编译缓存。三次运行构成 2×2 分解后可以看到：冷编译的两次是 39.4–39.5 s，热编译的一次是 19.3 s。拆开算，torch.compile 本身差 11.7 s（12.3 vs 0.6），引擎初始化差 5.0 s（14.7 vs 9.7，初始化时也会读编译缓存），其余约 3.4 s 落在图捕获与就绪握手上。权重段几乎不变（0.70 s 对 0.70 s）。

2. 为什么"驱逐了 3.799 GiB 页缓存"却不能说条件已经是冷读？

答案： 因为证明冷读的证据是 /proc/<pid>/io.read_bytes：如果权重真的从设备重读，它应该接近 3.78 GiB，而本次只有 11.0 MiB；权重段也仍是 2.32 s。权重目录在 NFS4 上，客户端与服务端是否真的丢弃这些块不由 posix_fadvise 决定。所以这一维按事实标为 UNVERIFIED，不做结论。

3. 为什么 vLLM 的权重"取回"阶段会让 0.44 GiB 可用内存变成一个关键变量？

答案： vLLM 在检测到 checkpoint 位于网络文件系统（本次 NFS4）时，会尝试把整个 checkpoint 预取到内存再加载；这一步要求约 3.78 GiB 可用内存。当时机器只剩 0.44 GiB，预取被跳过，改为逐分片现读，取回阶段因此用了 325.4 s。可用内存影响的是"走哪条加载路径"，不只是"能不能装下"。

4. 扩容阈值 4 的预热池用 4.6 倍副本时间换掉全部违规，这个交换值不值？

答案： 取决于违约定价与空闲定价。若一次违规的代价（用户侧损失、SLA 罚金、转人工）折算后远高于空闲副本秒的成本，预热池划得来；反之应按需扩容并把阈值调低、接受少量违规。本章给出的是两侧的实测/模拟量（304 副本秒对 0 违规；168 副本秒对 44% 违规），把定价留成显式假设，而不是替读者下结论。

5. 为什么"首个真实请求"要单独计时？

答案： 因为编译与图捕获有实现可能推迟到第一次推理时才发生（例如按形状动态编译）。若账本止于 HTTP 端点就绪，这段成本会被漏掉，表现为"服务就绪了但第一个请求特别慢"。本次三次运行的 ready → first_request 都是 0.05 s，说明这一版的编译发生在启动阶段；但这是实现细节，账本必须能容纳相反的情况。
