8.5

成本、能耗与硬件选型

$/Mtok、功耗实测、Ada vs Blackwell vs 统一内存 vs 边缘的选型逻辑。

实测机器 crater2（RTX 5090 32 GB，功耗上限 575 W）· Qwen3-1.7B · vLLM 0.29.0前置 8.3（事件口径与冻结 SLO）· 0.2（资源账本）· 1.3（主机、PCIe 与 NUMA）

本章回答三个问题

  1. 单位有效输出成本怎么定义？ 分母必须是"在冻结 SLO 下达标的输出 token"，而不是"吐出来的所有 token"。
  2. 功率与能量怎么测？ 采样要写出分辨率与传感器自身的平均窗口；power.draw 是功率读数，能量必须积分。
  3. 容量、利用率与质量怎样影响选型？ 同一张卡上，批大小从 1 提到 32，每千 token 增量能耗降 4.7 倍；代价是 TTFT p99 从 42 ms 涨到 924 ms。

本章的立场

这一章只测单张 GPU 的能耗：采样对象是 power.draw。主机 CPU、内存、网卡、存储（本机权重在 NFS 上，见 8.7）和机房 PUE 都不在里面，所以本章得到的数字不能当整机或机房成本用。价格与电价不是读数，单独放在假设文件里，并做敏感度扫描。

心智模型：能量账的三层

机制拆解与推导

1. 从功率到每 token 能量

设采样序列 (ti,Pi)，工作窗口 [ts,te] 的能量用梯形积分：

E=∑i12(Pi+Pi+1)(ti+1−ti)

设备在没有请求时仍在耗电（本次 28.8 W），所以"这次负载花了多少电"应该用增量能量：

Einc=Ework−P¯idle·(te−ts)

每 token 增量能耗 Einc/Ntoken。分母用服务端 usage.completion_tokens 求和——8.3 已经证明 SSE 数据块数不等于 token 数。

功率与能量的区别在这里很实际：c1 的平均功率 395.6 W 只有 c32（544.8 W）的 0.73 倍，但 c32 的每 token 增量能耗只有 c1 的 0.21 倍。看功率会得出"大 batch 更费电"，看每 token 能量才是相反的结论。

2. 为什么批处理省能量，代价是什么

单请求的解码是访存受限的：每生成一个 token 要把权重读一遍。batch 变大时，同一份权重服务更多 token，权重读取被摊薄，于是每 token 的能耗下降。实测从 batch 1 到 32：

配置 完成请求 输出 token 平均功率 每 token 增量能量 相对 c1
闭环并发 1 137 17 536 395.6 W 1.2532 J 1.00×
闭环并发 8 552 70 656 446.7 W 0.3578 J 0.29×
闭环并发 32 928 118 784 544.8 W 0.2646 J 0.21×

代价出现在尾时延：并发 1 的 TTFT p99 是 42 ms，并发 32 是 924 ms（+22 倍），TPOT p50 从 3.1 ms 涨到 15.3 ms。原因是并发越大，新请求越容易排在已有批次后面等待。省下的能量是用尾时延换的，而尾时延正是 SLO 的判据。

3. 有效 token 与 SLO 门槛

C1k=GPU 时间成本+增量电量成本#{达标请求的输出 token}×1000

分母只算在冻结 SLO 下达标的请求（8.3 的 TEACHING_SLOS）。本次实测（crater2，\$0.80/GPU-h、\$0.12/kWh 假设）：

配置 输出 token 达标 token（1 s/50 ms） J / 千达标 token \$ / 千达标 token
闭环并发 1 17 536 17 536 1 253.2 0.000801
闭环并发 8 70 656 70 656 357.8 0.000202
闭环并发 32 118 784 117 760 266.9 0.000124
开环 0.3× 35 968 35 968 584.9 0.000393
开环 0.9× 101 120 101 120 295.8 0.000143

并发 1 有 100% 的 SLO 达标率，但每千达标 token 成本是并发 32 的 6.5 倍；并发 32 只丢掉 1 024 个 token（8 个请求在 1 s 门槛外）。在这个负载和这三档 SLO 下，"把批做大"同时改善了成本与（几乎）不损失达标 token 数——但代价是 p99 的 924 ms 已经贴住 1 s 门槛，再大一点就会跨过去。

4. GPU 小时价与电价的相对权重

c32 一分钟窗口的账：GPU 时间 60.9 s × \$0.80/h = \$0.01353；增量电量 31 433 J = 0.00873 kWh × \$0.12 = \$0.00105。电费只占 GPU 时间费的 7.8%。也就是说，在"按 GPU 小时付费 + 工业电价"这一档假设下，省电几乎不省钱，省 GPU 时间才省钱；能源账的价值在于换硬件/换机房时评估容量与散热约束，而不是直接算出账单差异。

敏感度（都在 c32 的 SLO-1s/50ms 达标 token 上）：

\$/GPU-h \ \$/kWh 0.06 0.12 0.24
0.4 0.000062 0.000066 0.000075
0.8 0.000119 0.000124 0.000133
1.6 0.000234 0.000239 0.000248

电价翻两番只让每千 token 成本涨约 7–8%，而 GPU 小时价翻两番会让它涨约一倍。结论对 GPU 价格的敏感度远高于对电价的敏感度。

工程实现：读数与来源

功率读数来自 NVML：pynvml.nvmlDeviceGetPowerUsage()（单位 mW，换算成 W）、nvmlDeviceGetMemoryInfo()、nvmlDeviceGetUtilizationRates()、nvmlDeviceGetClockInfo(NVML_CLOCK_SM)。两点必须写进方法说明：

  • 采样间隔不等于传感器的平均窗口。 power.draw 是硬件在某个内部窗口上的平均值，本工具每 0.1 s 采一次，只能说明"每 0.1 s 取到一个平均值"，不能说明功率在 0.1 s 内是常数。
  • 功耗上限是可读的：crater2 的 RTX 5090 报 power.limit = 575 W，worldvln 的 L40S 报 350 W（nvidia-smi --query-gpu=power.limit），这两个数是我们判断"实测功率是否接近上限"的依据。

token 数来自服务端响应里的 usage.completion_tokens（vLLM 0.29 的 OpenAI 兼容接口在 stream_options.include_usage=true 时于最后一块给出）。SLO 判定复用 8.3 的 request_metrics.attained()，门槛来自同一份 TEACHING_SLOS 常量。

设计取舍

选择 代价 依据
增量能量（减 idle 均值）而不是总能量 需要单独测一段 idle 并假设 idle 功率稳定 设备空闲也在耗电；总能量会把"开机时间"算进"这次负载"
分母只算达标 token 需要一个冻结的 SLO 集合 达标率低的配置不该因为"吐得多"而显得便宜
价格写成假设文件、不写进代码常量 结论不是"某个价格下的答案" 价格会变，读数不会；分开才能让别人用自己的价格重算
只测 GPU 功率 低估整机能耗 本机是容器，拿不到主机功耗；宁缺勿造
不锁时钟 同一配置多次运行功率浮动 锁频需要管理员权限，且会改变服务行为；改为记录 sm_clock_mhz 作为条件

工程实现：mini 实现

labs/L8/energy_cost_ledger.py 功率采样与能量积分 
class PowerSampler:
    """以固定间隔采 NVML 读数; 采样分辨率与传感器平均窗口分开记录。"""
    def _run(self) -> None:
        import pynvml
        pynvml.nvmlInit()
        h = pynvml.nvmlDeviceGetHandleByIndex(self.gpu_index)
        while not self._stop.is_set():
            pw = pynvml.nvmlDeviceGetPowerUsage(h) / 1000.0        # mW -> W
            ...
            self._stop.wait(self.interval_s)

def integrate_energy(samples, t0, t1):
    seg = [s for s in samples if "power_w" in s and t0 <= s["t_s"] <= t1]
    e = 0.0
    for a, b in zip(seg, seg[1:]):
        e += 0.5 * (a["power_w"] + b["power_w"]) * (b["t_s"] - a["t_s"])
    return {"energy_j": e, "power_mean_w": sum(s["power_w"] for s in seg)/len(seg), ...}

cost_ledger.py 把"假设"与"读数"分开落盘：price_assumptions.json 记录每个价格的币种、单位、来源、取用日期与 kind（assumption/override），cost_table.json 记录可复算的每千达标 token 成本与敏感度网格。

前沿

  1. 推理能耗的量级与趋势。 Desislavov 等（Sustainable Computing 2023）系统测量了不同代际模型在推理阶段的能耗，指出"参数量—能耗"的简单外推不可靠，必须按实际负载测。本章的做法（同一模型固定输入输出、只改批与到达率）就是这条建议的最小实现。
  2. GPU 无服务器与冷启动能耗。 Torpor（arXiv:2306.03622）针对无服务器推理的低延迟与资源效率做了实例复用设计；它的核心权衡（常驻实例的空闲能耗 vs 冷启动延迟）与本章第 4 节的"GPU 小时价主导"是同一枚硬币的两面，8.7 会把冷启动那一侧量化。
  3. 权重加载与并行读取。 vLLM 在 vllm/config/load.py:11 定义了 DEFAULT_SAFETENSORS_PREFETCH_NUM_THREADS = 8，model_executor/model_loader/default_loader.py:121 还区分了多线程加载的适用条件；分片数与预取线程数是 8.7 的实测对象。
  4. 测量口径的行业做法。 MLCommons Inference 的功耗测量要求同时记录设备与整机、并给采样分辨率；本章受容器权限限制只做到设备侧，因此所有结论都限定在"单卡能耗"。

陷阱

  1. 只看功率，不看每 token 能量。 并发 32 的平均功率比并发 1 高 38%，但每 token 能量低 79%。方向相反。
  2. 把 idle 能耗算进负载。 设备空闲也在耗电（本次 28.8 W，占工作段平均功率的 5–8%），不减去会让长窗口的"能效"看起来更好。
  3. 拿 GPU 功率冒充整机。 本章没有任何主机侧数据；本机权重还在 NFS 上（8.7 实测），存储与网络能耗完全没进来。
  4. 把价格当结论。 电价翻两番只影响 7–8%，GPU 小时价翻两番影响约一倍；反过来，若按"自建机房 + 极低电价"算，电价项会进一步缩小。任何"每千 token 多少钱"都必须带价格假设。
  5. 用总 token 当分母。 并发 32 的 TTFT p99 已经到 924 ms，紧贴 1 s 门槛；如果 SLO 更严一点，达标 token 会掉下来，成本立刻反转。
  6. 缩短输出而不重查质量。 本章输出固定 128 token，没有做量化或截断实验，因此不能把"更省电"与"质量不变"绑在一起说。

自测题

1. 为什么每 token 增量能量随批大小下降，而平均功率反而上升？

答案： 解码阶段每生成一个 token 都需要把权重读一遍，是访存受限的。批变大后同一份权重服务更多 token，权重读取被摊薄，单位 token 的能耗下降；但设备整体跑得更满（SM 利用率与频率更高），所以平均功率上升。两者不矛盾：能量效率看的是"总能量 / token 数"，不是"功率高低"。

2. 本次账里电费只占 GPU 时间费的 7.8%，这个比例说明什么？

答案： 说明在按 GPU 小时付费的场景下，主导成本是设备时间而不是电费。所以"省电"本身几乎不省钱，省 GPU 时间（提高吞吐、减少空闲）才省钱。它的直接推论是：能效指标的意义在于容量与散热约束（一间机房能放多少卡、能跑多满），而不是账单上的电费项。这个比例对价格假设很敏感，所以必须与假设一起报。

3. 为什么分母要用"达标输出 token"而不是总输出 token？

答案： 总 token 会把"吐得快但违反 SLO"的请求也算成产出，等于用速度掩盖服务质量。用达标 token 做分母后，任何一个配置只有在满足时延门槛的前提下才计入成本；本次并发 1 的总 token 少、达标率高，但因能量效率差，每千达标 token 成本是并发 32 的 6.5 倍；如果反过来把总 token 当分母，差距会更大且掩盖 SLO 风险。

4. 采样间隔 0.1 s 能不能说明"功率在 0.1 s 内是常数"？

答案： 不能。power.draw 是硬件在自身内部窗口（通常远大于采样间隔）上的平均值，采样得到的是平均值序列。要把积分做得更精确，需要缩短采样间隔并观察积分是否收敛；本次没有做收敛性检验，因此能量数值只承诺在 0.1 s 采样下的可复算性。

5. 如果要比较"两张不同卡上跑同一个模型"的能效，需要控制哪些变量？

答案： 至少四个：同一模型与同一 dtype、同一输入输出长度与 batch、同一 SLO 门槛、同一功率采样口径；此外两卡的功耗上限不同（本次 RTX 5090 是 575 W、L40S 是 350 W），必须同时报告实测功率与上限，否则"更省电"可能只是被限了频。跨卡还要求两者都不与他人共享——本次 worldvln 上有其它租户进程，所以本章的能耗对比只在 crater2 一张卡内进行。
