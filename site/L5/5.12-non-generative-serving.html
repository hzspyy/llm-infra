5.12

非生成模型的服务

按服务任务和模型架构分别分析 embedding、rerank、classifier 与 pooling；区分一次前向返回和生成式打分，核对持续状态、容量、padding、数值语义与 batching。

实测机器 crater (RTX 5090 D, sm_120) · Qwen2.5-1.5B-Instruct · BAAI/bge-small-en-v1.5 · vLLM 0.29.0 · transformers 5.17.0数据日期 2026-09-12前置 0.2（资源账本）· 3.1（attention 内存墙）· 5.1（两相）· 5.11（前门）

本章回答三个问题

全书到目前为止默认「模型 = 自回归生成」。embedding、rerank、classifier 不是： 本章关注其中一次前向返回向量或分数的服务路径，没有自回归 decode 阶段。这一章补上这个盲区。

  1. 没有 decode 的模型，瓶颈在哪一侧？
  2. 为什么 embedding 服务能用大得多的 batch？
  3. 变长输入的 padding 浪费在这里为什么更严重？

结论先给：

  • 本章把一次前向返回向量的 pooling 服务与自回归生成对照。pooling 不需要跨 decode 步保留 KV；前向内部仍有 Q/K/V，具体引擎也可能分配缓存或临时 buffer。
  • 大 batch 的容量取决于权重、激活、workspace 与持久状态。权重读取的摊薄影响吞吐，不能直接决定显存容量。
  • 既有框架计时支持比较所测形状的耗时。roofline 的 FLOP 与字节均为公式估计；图中位置不能单独证明实际瓶颈。旧容量实验存在执行范围和对象释放问题，不能用于两类服务的容量比值。
  • 本批补齐容量公式与 meta 参数对拍；rerank、classifier 和 SGLang 真实链路仍为 UNVERIFIED，不标整章验收完成。

心智模型：一次前向 vs 一串前向

上图按每次前向读取一遍权重作简化记账；它不是 DRAM 事务计数。生成的每个 decode step 也会在 batch 内共享权重，实际搬运量还受缓存、分块和融合影响。

机制拆解与推导

1. 算术强度决定了落在哪一侧

用 0.2 那套账本，把一次前向的成本拆成 FLOP 与字节两项：

权重 FLOP   = 2 · N_body · tokens
attention   = causal:  2 · d · n_l · L² · B      （只有一半的 L² 被算）
              双向:    4 · d · n_l · L² · B
decode attn = 4 · d · n_l · C · B                （1 个 query 对 C 个 key）
权重字节    = N_body · dtype_bytes
KV 读取     = 2 · n_l · n_kv_head · d_head · dtype_bytes · C · B

N_body 是不含词嵌入与 lm_head 的参数量。算术强度 = FLOP / 字节：

  • decode：分子里 2·N_body·B，分母里 N_body·dtype_bytes。B 很小时分子分母同阶， 强度趋近 2/dtype_bytes——bf16 下就是 1。批量上去之后分子随 B 线性增长、 分母的权重项不变，强度才慢慢爬。
  • 编码：分子是 2·N_body·(B·L)，分母还是那一个 N_body·dtype_bytes。 强度正比于总 token 数，轻松上到几千。

crater 上 BF16 GEMM 峰值 232.0 TFLOP/s、纯读带宽 1608.6 GB/s（hw_crater_5090.json）， 脊点落在 144 FLOP/byte。这是简化模型的分类边界，不是实测瓶颈判据。字节式未计入全部激活读写、缓存复用及 kernel 中间量；需用目标形状的 profiler 证据确认瓶颈。

2. 没有 KV，就没有随上下文增长的状态

一次完成的 encoder 前向不保留跨步 KV；这里容量账本的持久 KV 项为 0。这不是「省了一点显存」，而是状态空间变了：

生成 编码
每请求的常驻状态 KV cache，随上下文线性增长 无
显存随 batch 增长的部分 权重 + KV + 激活 权重 + 激活
请求之间能否共享一次前向 只有同一 iteration 里的请求 同一 batch 的全部请求

KV 项的缺失减少了随 B × C 增长的持久状态。容量上限由各项占用之和决定；权重搬运的摊薄属于时间模型。两种模型不能互相替代。

  • CLS 取每段的第一行，LAST 取最后一行——索引数量为 O(B)，实际复制向量涉及 O(BH) 个元素，H 为 hidden size。
  • MEAN 要把每段所有行加起来（methods.py:60-105）：用 repeat_interleave 把 prompt_lens 展开成 segment_ids，再 index_add_ 分段累加。为了不让中间张量炸掉， 它按 _MEAN_POOL_ACCUMULATION_CHUNK_BYTES = 16 MiB 分块累加。

这里有一个约束值得记住：CLS 和 MEAN 都显式拒绝 partial prefill （methods.py:44 与 67，直接抛 RuntimeError）。这是该实现的约束。双向 attention 的 CLS 依赖整段上下文；MEAN 要求全部位置或额外维护分段累加状态。不能推广成所有模型的部分序列都无法池化。

5. 「chunked」在两个语境里不是一回事

同一个词在两个地方指两件不同的事，混起来会得出错误结论。

生成侧的 chunked prefill：一条请求被拆到多个 iteration 里算，KV 逐段累积， 请求始终是同一条。它让「32k 的 prompt」在 512 token 的预算下也能跑。

embedding 侧的 chunked processing：一条超长输入被拆成多条独立请求， 各自算完 embedding，再按权重平均（entrypoints/pooling/embed/io_processor.py:121-169， 开关是 enable_chunked_processing，默认 False）。这里没有 KV，没有状态跨段传递。

而 pooling 请求本身，默认不会被 chunk。调度器里写得很直接 （v1/core/sched/scheduler.py:988-996）：

# chunked prefill has to be enabled explicitly to allow
# pooling requests to be chunked
if (
    not self.scheduler_config.enable_chunked_prefill
    and num_new_tokens > request_token_budget
):
    break

后果是：max_num_batched_tokens 成了 pooling 模型序列长度的硬上限。 vLLM 在启动时就拒绝非法组合——同一组参数用在生成模型上没问题，用在 pooling 模型上直接退出：

max_num_batched_tokens (256) is smaller than max_model_len (512).
This effectively limits the maximum sequence length to max_num_batched_tokens
and makes vLLM reject longer sequences.

6. padding 的代价为什么在这里更贵

padding 让一部分 token 位置是空的，但前向照样算它们。浪费比例是 L_max / mean(L)。生成服务里这份浪费被摊薄了：prefill 只占整条请求的一小段， 后面还有 N 个 decode 步。embedding 服务里没有后面——一次前向就是全部成本。

而且这个浪费是二次的：attention 的 FLOP 正比于 L²，把批内最长的那条序列 当作所有序列的长度，attention 部分按 L_max² 计费，而真正需要的是 mean(L²)。

B. 调度：pooling 请求默认不被 chunk

见上一节。这一条同时解释了为什么 embedding 服务的 max_num_batched_tokens 要设得不小于 max_model_len：它不是吞吐旋钮，而是长度上限。

C. runner：扁平张量 + pooling cursor

PoolingRunner.pool() 拿到的是扁平 hidden states，build_pooling_cursor 把 num_scheduled_tokens、seq_lens 和 query_start_loc 三者绑成一个游标对象， 池化层靠它定位每一段。第 142 行有一句注释：

# Pooling has no speculative tokens, so this CPU upper bound is exact.

「没有投机 token，所以这个上界是精确的」——生成侧为了省一次同步只能用 seq_lens 的上界估计，pooling 侧因为一次算完，可以精确知道每段有多长。 这里的精确性仅指该注释描述的 token 数上界，不能推广到全部元数据。

D. 池化层：取行、求和、分块

见机制第 4 节。三种池化都很短，但 MEAN 的分块累加值得注意：它把 「一次 index_add_」换成了「按 16 MiB 分块多次 index_add_」， 用一点循环开销换中间张量的内存上限。这是把 OOM 风险换成常数开销的典型做法。

E. 超长输入：拆成多条独立请求再加权平均

enable_chunked_processing 打开后，超长输入按 max_model_len 切段， 每段变成一条独立的引擎请求，id 形如 {request_id}-prompt-{i}-chunk-{j}， 最后在线聚合。默认关闭——所以默认行为是截断或拒绝，不是自动处理。

设计取舍

状态归属与不变量。 scheduler 管 token 预算，runner 提供扁平 hidden states 与 cursor，pooler 按序列取值。cursor 的分段边界必须与有效 token 一致。CLS/MEAN 的 partial-prefill 错误在 pooler 内发现；预算与最大长度不兼容则在启动配置校验中发现。

分块需要匹配语义。 双向 encoder 的早期位置依赖后续 token，不能直接照搬因果模型的 KV 递推。MEAN 的分段累加还需要状态与计数。独立切段再平均是另一种输入处理策略，不保证与整段 embedding 等价。

响应与容量。 当前 embeddings 路由一次返回完整向量。响应时间还包含排队、输入处理和序列化。容量账本把持久 KV 与单次激活区分开；两类前向都可能受 workspace 限制。

增加实现对照。 新后端需核对 tokenizer、mask、输出维度、归一化、cursor 和取消回收，随后再比较性能。只有池化公式相同不足以保证 embedding 相同。SGLang 端到端及 rerank/classifier 对照待实现。

时延差值的边界。 客户端均值与引擎直方图均值的差涵盖客户端线程调度、建连、网络、前后处理和指标窗口差异。它是待分解的残差，不能全部计入 HTTP 服务端。

 23 def pack(seqs):
 24     """把变长序列拼成扁平数组，返回 (ids, query_start_loc)。"""

 28         starts.append(len(flat))

 32 def pad(seqs):
 33     """补齐到批内最长，返回 (ids_2d, mask)。"""
 34     L = max(len(s) for s in seqs)
 35     ids = [[0] * L for _ in seqs]
 36     mask = [[0.0] * L for _ in seqs]
 37     for i, s in enumerate(seqs):
 38         for j, t in enumerate(s):
 39             ids[i][j] = t
 40             mask[i][j] = 1.0

 44 def pool_packed(hidden, starts, method):
 45     """hidden: [total_tokens, d] 的扁平列表。"""
 46     out = []
 47     for i in range(len(starts) - 1):
 48         seg = hidden[starts[i]:starts[i + 1]]
 49         if method == "MEAN":
 50             d = len(seg[0])
 51             out.append([sum(row[k] for row in seg) / len(seg) for k in range(d)])
 52         elif method == "CLS":
 53             out.append(list(seg[0]))
 54         elif method == "LAST":
 55             out.append(list(seg[-1]))
 56         else:
 57             raise ValueError(method)
 58     return out

 62     """hidden: [B, L_max, d]；mask: [B, L_max]。padding 位置不参与。"""
 63     out = []

 67             d = len(row[0])

 69         elif method == "CLS":
 70             out.append(list(row[0]))
 71         elif method == "LAST":
 72             out.append(list(row[int(sum(m)) - 1]))

第二个服务端的报错原文：

Value error, max_num_batched_tokens (256) is smaller than max_model_len (512).
This effectively limits the maximum sequence length to max_num_batched_tokens
and makes vLLM reject longer sequences.

生成模型能接受这组参数，是因为 chunked prefill 把「预算」和「长度」解耦了： 32k 的 prompt 可以拆成 512 token 一段慢慢算。pooling 请求默认不被 chunk （scheduler.py:988-996），于是 max_num_batched_tokens 直接变成长度上限， vLLM 索性在启动时拦住。

这条约束的实践含义：给 embedding 服务调 max_num_batched_tokens 时， 它不是一个可以随便压小的吞吐旋钮——压到 max_model_len 以下，服务根本起不来。

模型与版本。 Qwen/Qwen3-Reranker-0.6B，revision e61197ed，0.6B 因果 LM（Qwen3ForCausalLM，28 层，hidden 1024，1.6B 词嵌入共享，完整参数量 595,776,512）。vLLM 0.29.0，crater，RTX 5090 D。HF 前向峰值显存 1,242,823,680 bytes（约 1.16 GiB，bf16 加载）。

9. 消融与未测范围

建议消融，每种配置另存结果：

  • 把 bge-small 换成 --dtype float32 跑一遍，看权重字节翻倍后 roofline 点怎么移动；
  • 打开 --enable-chunked-processing，给超过 512 token 的输入，量拆段与聚合的开销；
  • 用 MEAN / CLS / LAST 三种池化各跑一次同样的 batch 扫描，看池化本身是否可测；
  • 打开 chunked prefill 后重跑第 6 节，验证 pooling 请求是否真的被 chunk、以及 CLS/MEAN 是否如源码所示直接抛错；
  • 给 batch 上限的账本加一个标定步：先实测一个点，用实测/账本的比值修正后再外推。

未测：

  • SGLang / TensorRT-LLM 的 pooling 路径未对照。 只走了 vLLM 0.29.0。
  • max_num_batched_tokens 边界只测了启动行为，没有测「启动成功之后， 接近上限的请求会怎样排队」。
  • 生成侧在 256 token 预算下跑长 prompt 没有实测。 第 6 节第一个服务端只记录了 「启动成功」；用它跑 1024 token 的 prompt 需要另起一次服务并用 chat 接口， 本批次用的是 embeddings 接口，返回 404。
  • enable_chunked_processing 未打开，超长输入的分段与加权平均只有源码依据。
  • batch 上限的实测用的是 transformers 前向，不是 vLLM 服务，两者对激活的 处理不同（vLLM 有预分配与 CUDA Graph）。

  1 #!/usr/bin/env python3
  2 """5.12 三点 roofline：同一台机器上，LLM prefill / LLM decode / encoder-only 编码。
  3 
  4 三个点量的都是**同一个东西**：一次 transformer body 前向。
  5 不同的是形状——
  6   decode    每序列 1 个 query token，要读完整段 KV
  7   prefill   每序列 L 个 query token，因果 mask
  8   encode    每序列 L 个 query token，双向 mask，之后 mean-pool
  9 
 10 FLOPs 与字节量按公式算，耗时用 CUDA event 实测，两者相除得到实际达到的吞吐。
 11 公式（单位：FLOP 与 byte，d = d_model，N = body 参数量，n_l = 层数，B = 序列数）：
 12 
 13   权重项      2 · N · tokens
 14   attention   causal:     2 · d · n_l · L² · B        （平均只有一半的 L² 被算）
 15               双向:       4 · d · n_l · L² · B
 16   decode attn 4 · d · n_l · C · B                     （1 个 query 对 C 个 key）
 17   权重字节    N · dtype_bytes
 18   KV 读取     2 · n_l · n_kv_head · d_head · dtype_bytes · C · B
 19 
 20 算术强度 = FLOPs / 字节。本章用它判断这个形状落在 roofline 的哪一侧。

 63 def flops_bytes(stats, mode, B, L, C=None, bidirectional=False, dtype_bytes=2):
 64     """返回 (flops, bytes, 分项)。"""

 72     else:
 73         attn_flops = 2 * d * n_l * L * L * B

 78     kv_bytes = kv_per_token * (C if mode == "decode" else L) * B

 33 def arch(cfg: dict) -> dict:
 34     d = cfg["hidden_size"]
 35     n_head = cfg["num_attention_heads"]
 36     n_kv = cfg.get("num_key_value_heads", n_head)
 37     d_head = cfg.get("head_dim") or d // n_head
 38     n_l = cfg["num_hidden_layers"]
 39     d_ffn = cfg.get("intermediate_size", 4 * d)
 40     vocab = cfg["vocab_size"]
 41     tied = bool(cfg.get("tie_word_embeddings", False))
 42     # 只支持本章已固定的架构，未知结构拒绝套用近似公式。
 43     kind = cfg["model_type"]
 44     attn = 2 * d * (n_head * d_head) + 2 * d * (n_kv * d_head)
 45     if kind == "qwen2":
 46         ffn = 3 * d * d_ffn
 47         # Q/K/V bias、两处 RMSNorm，以及最终 RMSNorm。
 48         n_body = n_l * (attn + ffn + n_head * d_head + 2 * n_kv * d_head + 2 * d) + d
 49         extra = 0
 50         head = 0 if tied else vocab * d
 51     elif kind == "bert" and cfg.get("architectures") == ["BertModel"]:
 52         ffn = 2 * d * d_ffn
 53         # 四个 attention bias、FFN bias、两处 LayerNorm。
 54         n_body = n_l * (attn + ffn + 4 * d + d_ffn + d + 4 * d)
 55         # 位置/类型嵌入、embedding LayerNorm、BertModel pooler。
 56         extra = (cfg["max_position_embeddings"] + cfg["type_vocab_size"]) * d + 2 * d + d * d + d
 57         head = 0
 58     else:
 59         raise ValueError(f"unsupported architecture: {kind}")

 67 def ledger(a: dict, mode: str, B: int, L: int, dtype_bytes=2, act_per_token=16):
 68     """返回三项字节。act_per_token 是每个 token 的激活字节数（按 d_model 的倍数估）。"""
 69     weights = a["parameter_count"] * dtype_bytes
 70     if mode == "decode":
 71         kv = 2 * a["n_layer"] * a["n_kv_head"] * a["d_head"] * dtype_bytes * L * B
 72         act = act_per_token * a["d_model"] * dtype_bytes * B          # 1 个 token/序列
 73     else:
 74         kv = 0                                                        # encoder-only 不留 KV
 75         act = act_per_token * a["d_model"] * dtype_bytes * B * L
 76     return {"weights": weights, "kv": kv, "act": act, "total": weights + kv + act}

 79 def max_batch(a: dict, mode: str, L: int, budget: int, dtype_bytes=2, act_per_token=16):
 80     if ledger(a, mode, 0, L, dtype_bytes, act_per_token)["total"] > budget:
 81         return 0
 82     lo, hi = 0, 1
 83     while ledger(a, mode, hi, L, dtype_bytes, act_per_token)["total"] <= budget and hi < 1 << 20:
 84         hi *= 2
 85     while lo < hi:
 86         mid = (lo + hi + 1) // 2
 87         if ledger(a, mode, mid, L, dtype_bytes, act_per_token)["total"] <= budget:
 88             lo = mid
 89         else:
 90             hi = mid - 1
 91     return lo

前沿

沿本章机制继续扩展，而不是只调参数：

  • Matryoshka 与维度截断。 pooler_config.dimensions 支持把 1536 维输出截成 512 维。 这会改变返回字节数与下游存储成本，但不改变前向的计算量——前向仍要算完整维度。 收益在哪一侧需要单独测。
  • late interaction（ColBERT 一类）。 输出从「每序列一个向量」变成「每 token 一个向量」， 返回数据量涨 L 倍，池化从 MEAN 变成 ALL。这会把瓶颈从计算推向序列化与带宽。
  • rerank 与 classifier。 cross-encoder 打分是「一次前向、一个标量」， 形状比 embedding 更极端；classifier 通常带分类 head；具体分数变换需按模型核对。两者的 batch 行为都没有实测。
  • 多向量与多模态。 图像/视频 embedding 的输入不再是变长 token 序列， 打包策略要重做。
  • 数据并行部署。 pooling 没有 KV，请求之间完全独立，是最适合做 DP 的负载； 但每个副本都要装一份权重，收益取决于模型大小。

陷阱

  1. 把 decode 的调优结论套到 embedding 上。max_num_seqs、chunked prefill、 KV 容量、prefix caching 在这里要么不适用，要么含义完全不同。
  2. 把 max_num_batched_tokens 当成吞吐旋钮压小。对 pooling 模型它等于长度上限， 压到 max_model_len 以下服务直接起不来。
  3. 把两种 chunked 混为一谈。生成的 chunked prefill 是「一条请求分多步」， embedding 的 chunked processing 是「一条输入拆成多条请求」。
  4. 以为引擎会 padding。vLLM 的 pooling 路径是打包寻址，pad token 是客户端造出来的。
  5. 用 CLS 或 MEAN 池化还打开 chunked prefill。源码里这两种池化直接拒绝 partial prefill。
  6. 拿 roofline 上的 TFLOP/s 当作 kernel 上限。本章测的是框架级前向， 本章的 47–50% 是估计 FLOP 除以框架时间，再相对 GEMM 基准归一化；原因尚未定位。
  7. 用 embedding 的 batch 上限去规划生成服务，或反过来。
  8. 只看吞吐不看客户端时延。本章并发 256 时引擎时间几乎没变，客户端时延涨了 15 倍。

自测题

  1. 为什么单序列 decode 的算术强度接近 1，而编码能到几千？
  2. bge-small 在并发 1→256 之间吞吐涨 7.6 倍，但引擎侧单请求时间几乎不变。 这两件事为什么不矛盾？
  3. 变长输入的吞吐和固定长度几乎一样。这说明引擎做了什么？
  4. --max-num-batched-tokens 256 --max-model-len 512 用在生成模型上没问题， 用在 pooling 模型上直接退出。为什么？
  5. CLS 和 MEAN 池化为什么拒绝 partial prefill，而 LAST 不拒绝？
  6. 256 条长度 4–512 的输入，按批内最长补齐的浪费是 2.11 倍， 按长度分 8 条一桶是 1.03 倍。为什么分桶能省这么多？
答案
  1. decode 每一步只处理 1 个 token，却要把 N_body 的权重全部读一遍： 分子 2·N_body·B、分母 N_body·dtype_bytes，B=1 时强度趋近 2/dtype_bytes（bf16 下为 1）。 编码的分子是 2·N_body·(B·L)，分母还是那一个权重字节数，强度正比于总 token 数。
  2. 客户端提交请求数、调度器 batch 和每请求时间是不同指标；需要实际 batch 轨迹才能解释吞吐变化。现有数据不能证明 inference 下降来自权重摊销。
