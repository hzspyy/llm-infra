5.4

执行层：CUDA Graph 与流水重叠

2.6b 量到图把 CPU launch 降 16.2 倍，这里量它值多少 tok/s：1.19–1.41×。最清楚的一条是开图后每步时间几乎与 batch 无关（3.16–3.86 ms）。代价：启动 5.5→9.5 s、捕获 51 个尺寸、KV 变小。prefill 上完全没有收益（1.00×）；padding 的代价在 CPU 受限区间量不出来。

实测机器 crater (RTX 5090 D, sm_120) · vLLM 0.29.0 · Qwen3-1.7B数据日期 2026-09-10前置 2.6b（图的 launch 计数）· L1.4（launch 开销）· 5.1（两相）

本章回答三个问题

2.6b 量过：CUDA Graph 把 CPU 侧 launch 从 14,003 降到 863（16.2×）， 而 GPU 上执行的 kernel 数一个没少（12,147 不变）。

这一章问的是下一步：这 16 倍的 launch 减少，在 tok/s 上值多少？代价是什么？

  1. 开图之后 decode 快多少？
  2. 捕获要付出什么？
  3. 什么时候图完全没有收益？

一 · 开图之后每步时间几乎与 batch 无关

batch eager ms/步 图 ms/步 eager tok/s 图 tok/s 加速
1 4.444 3.156 225 317 1.41×
4 4.563 3.710 877 1078 1.23×
16 4.597 3.855 3480 4150 1.19×
64 5.007 3.770 12782 16977 1.33×

最清楚的一条在两列 ms 上：

  • eager 每步 4.44 → 5.01 ms（随 batch 增长）
  • 图每步 3.16 → 3.86 ms（基本不随 batch 变）

这个区间里 step 时间由 CPU 提交主导，而图把它压成了近似常数。 按 L1.4 的实测（每次 launch 2.68 µs），14,003 次 launch 就是 37 ms 的 CPU 时间—— 虽然它和 GPU 执行重叠，但重叠不完全时就直接体现在每步时间上。

加速比不是单调的，我没查清原因

我原本预期加速比随 batch 单调下降（batch 大 → GPU 忙 → CPU 提交被藏住）。 数据不支持：1.41 → 1.23 → 1.19 → 1.33，batch=16 是最低点，64 又回升。

没有查清原因，不要引用这条趋势。可能的方向： eager 路径在大 batch 上的 python/dispatch 开销、或图捕获尺寸的 padding（第三节）。 判据：用 2.6 的 nsys 方法分别抓两条路径在 batch=16 和 64 上的 CPU 时间线对比。

二 · 代价一：启动时间与显存

eager（无图）    启动    5.48 s   启动后驱动可见空闲   9.45 GiB
CUDA Graph      启动    9.50 s   启动后驱动可见空闲   9.63 GiB

启动慢了 4 秒（5.48 → 9.50 s）。图捕获发生在启动时： 要为每个准备捕获的 batch 尺寸各跑一遍前向并录下来， 本次捕获了 51 个尺寸（见第三节），所以这 4 秒是 51 次前向的成本。

对服务的含义：弹性伸缩的冷启动变慢。L1.4 算过一个 torch 进程 光初始化就要 0.8 秒，加上加载权重和图捕获，一个新副本上线要十几秒。

显存那一列不能直接读成"图的开销"

两行的空闲显存看起来差不多（9.45 vs 9.63 GiB），但这不代表图不占显存。

vLLM 会按 gpu_memory_utilization 把剩下的显存全部分给 KV cache， 所以图占多少，KV 就少多少——两者此消彼长，总的空闲量不变。

真正被图吃掉的那部分，表现为 KV cache 变小、可容纳的并发变少。 要量它，得读引擎报告的 KV block 数（2.0 §4.3 里 cudagraph_memory_estimate_applied 就是从预算里扣掉的那一项）。

三 · 代价二：只有捕获过的尺寸能用图

CUDA Graph 把张量地址和形状都固化在图里，所以每个 batch 尺寸都要单独捕获。 vLLM 捕获一组离散尺寸，运行时把实际 batch 向上取整到最近的那个：

本次捕获的尺寸（共 51 个）：
[1, 2, 4, 8, 16, 24, 32, 40, 48, 56, 64, 72, 80, 88, 96, 104, 112, 120, 128, ...,
 256, 272, 288, ..., 496, 512]

小的地方密（1,2,4,8），大的地方按 8 递增，再大按 16。 所以 batch=17 会被 pad 到 24——多算 41% 的行。

判据：若 padding 真的有代价，batch=17 的每步时间应当接近 batch=24， 而明显高于 batch=16。

batch pad 到 浪费 ms/步 tok/s
8 8 1.00× 3.747 2135
16 16 1.00× 3.859 4146
17 24 1.41× 3.505 4850
24 24 1.00× 3.623 6624
32 32 1.00× 3.580 8940
33 40 1.21× 3.549 9299
48 48 1.00× 3.627 13233
64 64 1.00× 3.731 17154

所有 batch 的每步时间落在 3.505–3.859 ms，极差只有 10.1%—— 而且 batch=17（pad 1.41×）比 batch=16 还快一点。

padding 的代价在这个区间里量不出来。 原因和第一节是同一个： 每步时间由 CPU 提交主导，多算几行 GPU 计算根本不构成瓶颈。

那 padding 什么时候才要紧？当 step 变成算力受限时—— batch 大到 GPU 真的忙起来（5.1 算过 batch≈72 越过平衡点），或者序列很长。 本 lab 的 batch 上限 64 还没到那里。

四 · 什么时候图完全没有收益

prefill（4 条，只生成 1 个 token）：

prompt 长度 eager ms 图 ms 加速
512 35.42 35.07 1.01×
2048 135.01 134.68 1.00×

一点差别都没有。 这直接印证 2.6b 的结论： 图减少的是提交次数，而 prefill 的时间由 GPU 计算主导（5.1 §一： prefill 的算术强度是 2048，牢牢在算力一侧）。

而且 prefill 的形状随 prompt 长度变，本来也没法用固定形状的图—— 这就是 2.6b 里 FULL_AND_PIECEWISE 这个默认值的含义： decode 走整图，prefill/混合批走分段图或 eager。

五 · 设计取舍

5.1 图为什么必须固定形状

CUDA Graph 记录的是一串已经绑定好参数的 kernel launch—— 包括 grid 大小、共享内存量、以及每个指针参数的具体地址。 重放时不重新解释这些，直接把命令流交给 GPU。这正是它省下 CPU 时间的原因。

代价就是这些参数不能变。换 batch 大小 → grid 变 → 要另一张图。 换输入张量 → 地址变 → 要么重捕获，要么把输入复制进图捕获时那块固定的缓冲区 （vLLM 用的是后者）。

这是一个把"灵活性"完全换成"提交速度"的设计。 它之所以在 decode 上成立， 是因为 decode 的形状本来就只由 batch 决定，而 batch 的取值可以离散化。 prefill 的形状由 prompt 长度决定，连续且范围极大，离散化的代价就不可接受。

5.2 捕获 51 个尺寸是个什么量级的决定

51 个尺寸 = 51 次额外前向（4 秒启动时间）+ 51 份图结构的显存。

如果只捕获 8 个尺寸，启动会快很多，但 padding 的浪费会大幅上升 （比如 65 要 pad 到 128）。如果捕获 512 个，padding 几乎为零， 但启动要几十秒、显存也吃不消。

51 这个数是在"启动时间 + 显存"与"padding 浪费"之间选的点。 而第三节的实测说明：在 batch ≤ 64、CPU 受限的区间里， padding 浪费根本量不出来——也就是说这个折中在小 batch 上偏保守了， 密集的捕获点没有换来可测的收益。

（这不是说 vLLM 选错了：大 batch、长序列、别的模型上结论可能相反。 本章只测了一个配置。）

5.3 一条反复出现的判据

本章第三节和第一节都撞上同一件事：一个优化/代价能不能被测到， 取决于当前的瓶颈在哪一侧。

  • padding 多算 41% 的 GPU 工作 → 在 CPU 受限时完全看不见
  • 图省 16 倍的 CPU launch → 在 GPU 受限的 prefill 上完全看不见

所以"这个优化有没有用"这个问题永远要带配置。 本书里同一形态已经出现多次：2.7 的 max-autotune、4.3 的量化速度、 3.2 的 exp 占比。判断方法都一样：先用 roofline 定位瓶颈，再估收益上限。

建议的消融

  1. 查清第一节那个非单调：用 nsys 抓 batch=16 和 64 两条路径的 CPU 时间线， 看 eager 在大 batch 上多花的时间在哪。这是本章唯一没解释的现象。
  2. 读引擎启动日志里报告的 KV block 数，对比 eager 与开图两种配置—— 这才是第二节里"图吃了多少显存"的正确量法。
  3. 把 batch 扫到 128/256/512，看 padding 的代价什么时候开始显现。 按 5.1 的账，batch≈72 越过平衡点之后应该出现。
  4. 用 compilation_config={"cudagraph_capture_sizes": [1, 8, 64, 512]} 只捕获 4 个尺寸，对比启动时间与 batch=17/33 的每步时间。

七 · 陷阱

  1. "启动后空闲显存差不多"不等于"图不占显存"。 vLLM 把剩余显存全给 KV， 图占多少 KV 就少多少。要看 KV block 数。
  2. 图对 prefill 没有收益（本章 1.00–1.01×）。别指望它改善 TTFT。
  3. padding 的代价在 CPU 受限区间量不出来（本章极差 10.1%）。 不能因此说"padding 没有代价"，只能说"这个配置下量不到"。
  4. 开图会让启动慢几秒（本章 5.48 → 9.50 s）。弹性伸缩要算进去。
  5. 加速比不一定随 batch 单调变化（本章 1.41/1.23/1.19/1.33），别外推。
  6. 图要求输入地址固定。 自己写图捕获时，输入必须拷进固定缓冲区， 不能直接用新分配的张量（2.0 §4.3 的 allocator 会给你不同地址）。

八 · 自测题

1. CUDA Graph 把 launch 减少了 16 倍，为什么吞吐只快 1.2–1.4 倍？

因为 launch 省的是 CPU 时间，而每步的总时间是 CPU 提交与 GPU 执行的 重叠结果，不是相加。

按 L1.4，14,003 次 launch × 2.68 µs ≈ 37 ms 的 CPU 时间。 但 GPU 同时在算，两者部分重叠。图把 CPU 侧压掉之后， 剩下的 GPU 执行时间成了下界——本章图路径的每步稳定在 3.16–3.86 ms， 就是这个下界附近。

一般规律：一个只影响其中一条流水的优化，收益上限是它消掉的那部分 超出另一条流水的量。 2.6b 已经量过 GPU 忙时在两种模式下几乎不变 （137.8 vs 133.4 ms），所以收益必然有限。

2. batch=17 被 pad 到 24，多算 41%，为什么测不到变慢？

因为这个区间里 step 时间由 CPU 提交主导，不是 GPU 计算。 本章实测图路径的每步时间在 batch 1→64 之间只在 3.16–3.86 ms 之间波动—— 几乎与 batch 无关，说明 GPU 那部分远没吃饱。

多算 7 行（17→24）的 GPU 工作，落在一个本来就闲着的部件上，自然量不出来。

padding 要紧的条件是 step 变成算力受限：batch 大到越过平衡点 （5.1 算的 batch≈72），或者序列很长。消融 3 就是去找这个点。

这也是一条通用判据：一个代价能不能被测到，取决于它落在哪个部件上， 以及那个部件是不是当前的瓶颈。

3. 为什么 prefill 不用 CUDA Graph？

两个独立的理由：

  1. 没收益。 prefill 的时间由 GPU 计算主导（5.1：算术强度 2048， 牢牢在算力一侧）。本章实测 eager 与图在 prefill 上差 1.00–1.01×。
  2. 做不到。 图要求形状固定，而 prefill 的形状由 prompt 长度决定， 连续且范围极大（1 到几万）。离散化会导致巨大的 padding 浪费。

decode 恰好相反：形状只由 batch 决定，batch 可以离散化成几十个点； 而且它是 CPU 受限的，正好是图能帮上忙的地方。

这就是 2.6b 里 FULL_AND_PIECEWISE 这个默认值的含义—— decode 走整图，prefill/混合批走别的路径。
