5.4

执行层：CUDA Graph 与流水重叠

比较 eager 与 CUDA Graph 执行，分析启动开销、捕获尺寸和 padding 的影响。

实测机器 crater · RTX 5090 D · sm_120 · vLLM 0.29.0 · Qwen3-1.7B前置 2.1（执行模型）· 2.6b（图与 launch 计数）· 2.0c（内存池）· 5.1（prefill 与 decode）

本章回答的三个问题

2.6b 数过：CUDA Graph 把 CPU 侧 launch 从 14,003 降到 863，而 GPU 上执行的 kernel 数一个没少。 这一章沿着那条线继续问三个具体问题：

  1. 当前版本实际有哪些图模式，运行时按什么规则选中其中一个？
  2. 捕获桶与 padding 的代价有多大，什么条件下量得出来？
  3. CPU 的调度与输入准备、GPU 的前向、采样这三段怎么重叠？

心智模型：一次 decode step 的两条流水

一次 decode step 由两条流水组成：主机侧把这一步「翻译」成 GPU 能执行的命令流，设备侧把它算出来。 CUDA Graph 改变的只有主机侧那条流水：把中间上百次提交压成一次图重放。

机制拆解

1. 图模式不是开关，而是三组语义的组合

CUDAGraphMode（vllm/config/compilation.py:53）的取值里有三个「运行时模式」NONE / PIECEWISE / FULL， 另外三个是它们的组合：

取值 value 语义
NONE 0 不捕获，逐算子提交
PIECEWISE 1 在 torch.compile 的切分点之间各捕获一张小图，切分算子留在图外
FULL 2 整步（含 attention）一张图
FULL_DECODE_ONLY (FULL, NONE) decode 用整步图，prefill 不捕获
FULL_AND_PIECEWISE (FULL, PIECEWISE) decode 用整步图，prefill 用段图

后两个值的 value 是元组，因此它们带 separate_routine()：decode_mode() 取元组第一个元素， mixed_mode() 取第二个。默认配置解析出来就是 FULL_AND_PIECEWISE，所以 decode 走 FULL、 prefill 与混批走 PIECEWISE。

PIECEWISE 与 FULL 的差别不在「有没有用图」，而在图覆盖到哪里。 compilation_config.splitting_ops 有 19 个算子，前几个是 vllm::unified_attention_with_output、vllm::mamba_mixer*、vllm::linear_attention、vllm::sparse_attn_indexer： 它们是图的分段边界。PIECEWISE 在边界处停下来，attention 自己跑；FULL 把这些算子也装进同一张图。

2. 分派是一次查表

CudaGraphManager（vllm/v1/worker/gpu/cudagraph_utils.py:111）在初始化时做两件事： 按 cudagraph_capture_sizes 构造描述符（_init_candidates，同文件 :188）， 再为每个可能的 token 数预先把「能服务它的描述符」按优先级排好。运行时 dispatch （同文件 :409）只做一次字典查找加一次兼容性判断 _is_compatible（同文件 :84）：

# vllm/v1/worker/gpu/cudagraph_utils.py:409（摘录）
def dispatch(self, num_reqs, num_tokens, uniform_token_count,
             num_active_loras, max_query_len=None):
    key = (num_tokens, self._resolve_effective_loras(num_active_loras))
    if self._graphs_captured and num_tokens > 0 and key in self._candidates:
        for desc in self._candidates[key]:
            if _is_compatible(desc, num_reqs, num_tokens,
                              uniform_token_count, effective_loras, max_query_len):
                return desc
    return BatchExecutionDescriptor(cg_mode=CUDAGraphMode.NONE, ...)

兼容性判断只有四条：query 长度上限、每个请求的 token 数是否一致、请求数是否超过图能容纳的、token 数是否超过图的桶。 超了任何一条就换下一个候选；候选用尽就返回 NONE。

这套规则产生四个可实测的结论：

  • 桶决定 padding。 实际 num_tokens=17 时，候选表里最小的可用桶是 24，于是按 24 行算，浪费 41%。
  • FULL 有请求数上限。 num_tokens ≤ max_num_seqs × decode_query_len = 256 才有 FULL 图；257 个 token 只能退到 PIECEWISE（它不限制请求数）。
  • 超过最大捕获尺寸不是 padding，而是直接不用图。 3000 token 的 prefill 落在 NONE，而不是被 pad 到 512。
  • prefill 与混批走 mixed_mode。 8 条 64-token prompt 的一次 prefill（512 token）分派到 PIECEWISE，不是 FULL。

labs/L5/mini_graph_dispatch.py 用约 90 行复现了这套规则，对真实引擎观测到的 16 组分派结果逐条核对，不一致 0 条。

3. 图绑定地址，所以输入必须写进固定缓冲区

捕获时，ModelCudaGraphManager.capture（同文件 :493）把 input_buffers.input_ids[:num_tokens]、 positions、is_padding 交给模型，torch.cuda.graph 记下这些指针。运行时不再重新解释参数， 直接重放命令流。所以输入必须写进同一块缓冲区：引擎在 capture() 里抓的就是那批常驻张量 （vllm/v1/worker/gpu/input_batch.py:28 起的 InputBuffers），之后每步只改内容、不改地址。

实测三轮不同 batch 的请求之后，input_ids / positions / is_padding 三个指针完全不变。 把运行时缓冲区换成一个新分配的等价张量，重放仍然读旧地址：贪心输出的第一个 token 相同， 之后逐位置分叉（results/crater/engine/graph-dispatch-20260913/tamper_pointer.txt）。 这就是「图要求输入地址固定」的可复现反例。

4. 捕获桶的成本不止 padding

图的代价分三块，它们的可观测性完全不同。下表由「一个配置一个干净进程」测得， gpu_memory_utilization 固定 0.35：

配置 启动 s KV blocks 整步图 捕获尺寸
NONE（eager） 10.34 4064 0 0
COMPILE_ONLY 10.56 4082 0 0
PIECEWISE 13.80 3920 0（段图不计入） 51
FULL_DECODE_ONLY 12.29 4012 35 51
FULL_AND_PIECEWISE 14.14 3896 35 51

三块代价是：启动多 3.8 秒（10.34 → 14.14）、KV 少 168 个 block（4064 → 3896，−4.1%）、 以及 padding。第三块最容易被误读：padding 多算的是设备工作，只有当设备是瓶颈时它才出现在每步时间上。 decode 阶段每一步都要把 3.4 GB 权重从头读一遍，属于权重带宽受限，batch 16 与 64 的设备时间几乎相同 （3.63 ms 与 3.44 ms）。把 17 行 pad 成 24 行，多出来的 7 行落在同一个带宽瓶颈上， 既没有增加权重读取量，也没有拉长关键路径，所以在这个区间里量不出来。

KV blocks 那一列只有在各配置分处不同进程时才有意义。同进程连续建引擎时， 前一个引擎的显存不一定归还，实测空闲显存会从 13.2 GiB 逐次降到 3.0 GiB， 后建的引擎拿到更小的预算，比出来的就是「谁的预算大」而不是「图的代价」。

5. 分段编译与 CUDA Graph 是两件事

torch.compile 会把算子融合成更大的 kernel；CUDA Graph 只是把这些 kernel 的提交方式换成一次图重放。 两者可以独立开关，效果也完全不同。在同一个 decode 负载上关掉图、只留编译， 主机侧提交次数基本不变（6,034 次），设备侧 kernel 数从 6,962 降到 6,034——减少的 928 个是融合掉的算子； 打开 PIECEWISE 后 kernel 数不变，提交次数掉到 2,898；再打开 FULL，提交次数掉到 378。

捕获顺序（:317 的注释与代码一致）：先 PIECEWISE 再 FULL，且每个模式内部按尺寸从大到小。 先捕大的，小的图可以复用已经分配好的图池内存；PIECEWISE 的激活比 FULL 大， 先捕它能让 FULL 的激活落进已分配的缓冲区。

有一个容易看错的地方：cgm.graphs 里只有 FULL 图。非 breakable 的 PIECEWISE 在 capture 里走 forward_fn(CUDAGraphMode.PIECEWISE) 然后 continue，段图由编译产物内部的 cudagraph trees 持有，不进 cgm.graphs。所以「引擎日志打印 Capturing CUDA graphs (PIECEWISE) 51/51」 与「len(cgm.graphs) 只有 35」并不矛盾。

设计取舍

这套设计把「灵活性」换成了「提交速度」。 图里记录的是已经绑定好参数的 kernel launch： grid 大小、共享内存量、每个指针的地址。重放不重新解释这些，直接把命令流交给 GPU， 这正是它省下主机时间的原因，也是这些参数不能变的原因。

  • 形状必须离散化。 decode 的形状只由 batch 决定，而 batch 可以离散成 51 个桶； prefill 的形状由 prompt 长度决定，连续且跨度极大，离散化的代价不可接受。这就是默认 FULL_AND_PIECEWISE 而不是「全都用整步图」的原因。
  • 输入必须先进固定缓冲区。 引擎用常驻 InputBuffers 承担这个角色，代价是每步多一次拷贝， 收益是地址永远合法。自己写图捕获时如果不这么做，第二次请求就会重放错数据。
  • 桶的密度是在启动时间与 padding 之间选的。 51 个桶启动约 10 秒；只捕 4 个桶启动更快， 但 batch 17 会被 pad 到 64（3.76 倍）。实测在这个 decode 负载上，两种选择的每步时间差不到 4% （3.51 vs 3.38 ms），因为设备侧本来就不是瓶颈。
  • FULL 与 PIECEWISE 的取舍在覆盖范围。 整步图覆盖 attention，提交次数最少， 但它要求每个请求的 query 长度一致且请求数不超过桶；段图不限制请求数，能服务混批， 代价是切分算子每次都要单独提交。

不变量：每张图的 num_tokens 大于等于实际 token 数；重放时输入地址与捕获时一致； NONE 描述符永远可用，调度不会因为找不到图而失败。

 49 def src_loc(module_name, symbol):

 74 def safe_util(reserve_gib=6.0, cap=0.55, floor=0.22):
 75     """按当前空闲显存留出 reserve_gib 余量，再折算 gpu_memory_utilization。

 79     """
 80     import torch
 81     free, total = torch.cuda.mem_get_info()
 82     gib = 1024 ** 3

 85           f"-> gpu_memory_utilization={max(min(cap, util), floor):.4f}", flush=True)

  2. 候选表不等于最终选择：M=8/16 上启发式 top-1 是 splitK=5 的 s16816 家族， 运行时却选了不带归约的 wmma 实例——torch 走的是自己的 cuBLASLt 查询路径， 偏好、epilogue 与可用 kernel 集合都可能不同。因此这里的结论限于 「换档的 M 区间与 kernel 名称」，具体启发式的打分函数仍保持 UNVERIFIED。

同一个 decode step，在 batch 16 与 64 上被 cuBLAS 选中的 GEMM 算法不同（一个用 split-K 归约，一个不用）， 连带的 elementwise kernel 数量也不同。这是「decode 每步时间不随 batch 单调」的直接原因： 每步时间由权重带宽与所选 kernel 的效率共同决定，而后者随桶跳变。 这个机制解释了形状，但不构成对具体 cuBLAS 启发式选择的完整解释，该选择本身保留为 UNVERIFIED。

breakable CUDA graph。 PIECEWISE 依赖 torch.compile 把图切开。vLLM 0.29.0 里有另一条路 （vllm/compilation/breakable_cudagraph.py）：不编译，直接用可中断的图包装器，在指定算子处断开。 它把「分段」从编译期决定变成运行期决定，代价是失去 Inductor 的融合。本机的 use_breakable_cg 为 False。

图内存的估计与实收。 引擎启动时会先跑一轮 profile_cudagraph_memory （vllm/v1/worker/gpu/cudagraph_utils.py:718），只捕获最大的若干张 FULL 图， 用它们的显存增量外推总量，再按估计值从 KV 池里扣。实测估计 0.32 GiB、实际池 0.13 GiB， 差 141%；这一项可以通过 VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS=0 关掉， 关掉后必须自己给 KV 留余量。先捕大图再捕小图的捕获顺序正是为了让外推偏保守。

按 LoRA 数量特化图。 cudagraph_specialize_lora 默认开启， _get_lora_cases 会为「无 adapter」与若干 num_active_loras 档位分别捕获。 多租户场景下这一步会把图的数量乘上档位数，5.10 的槽位容量与它直接相关。

切分发生在编译的哪个阶段。 use_inductor_graph_partition 决定 PIECEWISE 的切分点由谁决定： 默认（False）在 Dynamo FX 层按 splitting_ops 切开再逐段编译；置 True 时先让 Inductor 跑完全部 pass 与融合，再在 codegen 阶段切分（config/compilation.py:520-530）， 编译因此能看到整图。labs/L5/inductor_partition_probe.py 在同一负载下分别构造引擎：

编码器图与它的 token 预算。 多模态模型的 vision encoder 有独立的图管理 （vllm/v1/worker/encoder_cudagraph.py）与 token 预算配置；它与 decode 图的桶是两套。

陷阱

  1. 「开了图所以更快」是错的方向。 图减少的是主机提交次数，设备侧 kernel 数一个不少 （本节 6,034 对 6,034）。收益上限等于主机时间超出设备时间的那部分。
  2. len(cgm.graphs) 不等于引擎捕获的图数。 非 breakable 的段图不进这个字典， 只看它会漏掉 51 张 PIECEWISE 图。
  3. num_tokens 超过最大捕获尺寸时不会 padding。 它落到 NONE，回到逐算子提交； 3000 token 的 prefill 就是这样。
  4. 换掉输入缓冲区不会报错，只会算错。 图读的是捕获时记录的地址，重放不校验。 官方实现只在 VLLM_LOGGING_LEVEL=DEBUG 下断言地址一致。
  5. 图占的显存不是「空闲显存变少了」。 引擎按 gpu_memory_utilization 把余量全给 KV， 图占多少、KV 就少多少；要看 KV blocks 或引擎自报的 graph pool。
  6. 同进程连续建引擎时显存不会干净归还。 逐个建引擎比容量会得到递减的 KV blocks； 要么固定预算，要么一个配置一个进程。
  7. torch.profiler 的 device 时间不能当 GPU 忙时间。 同一负载下它给出「每步 GPU 忙 5.8 ms」 而墙钟只有 4.4 ms；归因要用 nsys 的 kernel device 时间或不插桩的差分计时。
  8. --cuda-graph-trace=node 会放大 cudaGraphLaunch 的 CPU 时长。 实测被放大到 6.1 ms/次； 节点展开适合数图内 kernel，不适合量提交开销。

自测题

1. 图把提交次数从 6,034 压到 378，为什么吞吐只快 1.2–1.4 倍？

因为提交次数省下的是主机时间，而每步墙钟是主机流水与设备流水重叠后的结果。 同一份负载上，图路径的设备时间是 2.93/3.63/3.44 ms（batch 1/16/64）， 它构成下界；主机时间从 4.45 ms 压到 0.58 ms 之后，剩下的收益就只能是设备时间之上的那部分。

按同一份实测：eager 在 batch 64 的每步是 5.209 ms、设备 3.669 ms，图路径 3.602 ms。 收益上限 5.209 − 3.669 = 1.54 ms，实测拿到 1.61 ms，与「把主机时间藏到设备时间之下」一致。

一般规律：只影响其中一条流水的优化，收益上限是它消掉的那部分超出另一条流水的量。

2. batch=17 被 pad 到 24，多算 41%，为什么测不到变慢？

多算的是设备侧的行数，而这组配置的设备侧是权重带宽受限：decode 每步都要读完 3.4 GB 权重， batch 16 与 64 的设备时间分别是 3.633 ms 与 3.441 ms，几乎不随行数变化。 多出来的 7 行并没有增加权重读取量。

把桶换稀疏（B=17 直接 pad 到 64，3.76 倍）后每步反而略低（3.384 对 3.510 ms）， 进一步说明 padding 的成本落在一个不是瓶颈的部件上。

padding 要紧的条件是设备侧成为瓶颈：batch 大到越过 roofline 平衡点，或序列很长使 attention 主导。

3. 为什么 `cgm.graphs` 里没有 PIECEWISE 图，引擎却报告捕获了 51 张？

因为两条路径的图归属不同。非 breakable 的 PIECEWISE 在 capture() 里调用 forward_fn(CUDAGraphMode.PIECEWISE) 后 continue，把段图的捕获交给 torch.compile 产物的 cudagraph trees；只有 FULL 图才由 torch.cuda.CUDAGraph() 显式创建并存入 self.graphs。 use_breakable_cg 为真时才会走另一个包装器。

判据：FULL_AND_PIECEWISE 下 len(cgm.graphs) 是 35（全部为 FULL）， 而 nsys 的节点展开显示除了那张 365 节点的整步图之外还有 29 张 8 节点的段图。

4. 加速比在 batch 16 触底、64 回升，怎么判断它是噪声还是真实现象？

先用重复样本把噪声压下去：batch 在 1/4/16/64 之间轮转 5 轮交错测量， FULL_AND_PIECEWISE 在 batch 16 的极差是 3.73–3.75 ms，batch 64 是 3.55–3.59 ms， 两者不重叠，所以 16 比 64 慢是真实差值，不是抽样噪声（单次采样时这个结论不成立）。

再定位到流水：nsys 显示设备时间是 3.633 ms（batch 16）对 3.441 ms（batch 64）， 主机时间两档都只有 1 ms 量级，因此差异在设备侧。 最后看分派：整步图在两个桶里分别有 365 与 421 个 kernel 节点， splitKreduce_kernel 一个没有、一个有 56 次，说明 cuBLAS 为不同 M 选了不同算法。

机制解释了形状；具体是哪个启发式规则选了哪套算法，本章没有取到，保持 UNVERIFIED。
