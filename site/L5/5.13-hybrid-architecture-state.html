5.13

混合架构的状态管理

管理混合模型中的 KV cache、循环状态和窗口状态，介绍前缀复用、快照及投机回滚。

实测机器 crater (RTX 5090 D, sm_120) · RecurrentGemma-2B · Qwen3.5-4B · vLLM 0.29.0 · SGLang 0.5.19前置 3.4（稀疏与线性 attention）· 5.2（KV 分页）· 5.5（投机解码）

本章回答三个问题

混合模型中的层不一定都保存 KV cache。循环层或线性 attention 可以使用定长状态，局部 attention 则保留窗口内的 KV。不同状态的更新方式，也决定了前缀复用和投机回滚的实现。

  1. 混合模型里每层的「状态」分别是什么形状？
  2. 定长状态还能不能做 prefix cache？为什么？
  3. 投机解码验证失败时，recurrent state 怎么回滚？

心智模型：两类状态的对照

机制拆解与推导

1. 逐层状态的实际形状

RecurrentGemma-2B 使用 26 层，按 ['recurrent', 'recurrent', 'attention'] 的 3 层模式循环。 从模型配置和实测数据：

{
  "model_type": "recurrent_gemma",
  "num_hidden_layers": 26,
  "hidden_size": 2560,
  "num_attention_heads": 10,
  "num_key_value_heads": 1,
  "block_types": ["recurrent", "recurrent", "attention"]
}

Recurrent 层的状态（RNN Griffin）：

# 每个 recurrent 层
state_shape = (batch_size, num_heads, conv_width, head_dim)
            = (B, 10, 4, 256)

# 字节数（bf16）
state_bytes_per_layer = 10 * 4 * 256 * 2 = 20,480 bytes = 20 KB

# 18 个 recurrent 层
total_recurrent_state = 18 * 20 KB = 360 KB per batch

这个状态不随上下文长度增长。无论输入是 256 token 还是 4096 token，每个 recurrent 层都只保留这 20 KB 的固定状态。

Attention 层的状态（local attention）：

# 每个 attention 层，每个 token
kv_shape_per_token = (2, num_kv_heads, head_dim)
                    = (2, 1, 256)

# 字节数（bf16）
kv_bytes_per_token = 2 * 1 * 256 * 2 = 1,024 bytes = 1 KB

# 8 个 attention 层，序列长度 L
total_kv_cache = 8 * 1 KB * L = 8L KB

这个状态随上下文线性增长。Context 翻倍，KV cache 也翻倍。

实测验证（来自 RecurrentGemma-2B 配置与运行）：

从 results/crater/hybrid/recurrentgemma_state_audit.json：

Layer Block Type State Type Shape per Batch Bytes/Batch Grows?
0 recurrent recurrent (10, 4, 256) 20,480 ❌
1 recurrent recurrent (10, 4, 256) 20,480 ❌
2 attention kv_cache (2, 1, seq_len, 256) 1,024/token ✅
3 recurrent recurrent (10, 4, 256) 20,480 ❌
… … … … … …
25 recurrent recurrent (10, 4, 256) 20,480 ❌

完整 26 层：18 recurrent + 8 attention，按 3 层模式循环。

2. 容量增长的实测对照

扫描不同上下文长度，测量 prefill 时间：

Context 实际 Tokens Prefill 时间 ms/token 状态大小估算
256 258 111.0 ms 0.430 360 KB + 2 MB = 2.4 MB
512 514 111.5 ms 0.217 360 KB + 4 MB = 4.4 MB
1024 1026 216.4 ms 0.211 360 KB + 8 MB = 8.6 MB
2048 2050 391.3 ms 0.191 360 KB + 16 MB = 16.7 MB

Token 增长 7.95×，prefill 时间只增长 3.53×（111.0 → 391.3 ms）。 这条次线性是时间性质，来自大矩阵乘对权重读取的摊薄，不能归因到状态大小： 同一张表里，状态估算从 2.4 MB 涨到 16.7 MB，是随上下文线性的， 因为其中 2/4/8/16 MB 都是 attention 层的 KV。 固定的 360 KB recurrent state 在 2048 上下文时只占状态总量的 2.2%。 两件事要分开说：固定状态摊薄的是每 token 的时间，不是每 token 的显存。

对比纯 attention 模型，用 0.2 账本里同一个 checkpoint 的数（ledger_qwen3_1.7b_ctx4096.json）： Qwen3-1.7B 是 28 层 GQA，8 个 KV head、head_dim 128、bf16，合计

kv_bytes_per_token = 2(K,V) × 28(层) × 8(KV head) × 128(head_dim) × 2 byte = 114 688 byte
context = 2048 时 total_kv = 114 688 × 2048 = 235 MB

（该文件的 bytes_per_token = 114688、bytes_at_ctx 在 ctx=4096 时是 469 762 048 byte，与上式一致； gqa_saving = 2.0 指 16 个 Q head 对 8 个 KV head。）

所以混合架构在 context=2048 时要 16.7 MB，是纯 attention 的 7.1%。 这个比例随后续上下文线性上升：KV 是线性项，360 KB 是常数项， 上下文越长，混合架构省下的比例越接近「attention 层数占比」而不是「1 减去一个小数」。

2b. 把上下文推到 8100：上面那条「次线性」不成立

上表只到 2048，且 256 与 512 两个点几乎一样（111.0 与 111.5 ms）—— 这个形状更像是固定开销占了主导，而不是算力摊薄。把它推到 8100 再看 （labs/L5/run_hybrid_longctx.sh + hybrid_longctx_scan.py， results/crater/hybrid/longctx-20260913/，每种长度 3 次取中位）：

目标长度 实际 token prefill 中位 每 token
512 514 205.8 ms 0.400 ms
2048 2050 819.9 ms 0.400 ms
4096 4098 1 678.6 ms 0.410 ms
8100 8 102 3 056.9 ms 0.377 ms

token 涨 15.8×，时间涨 14.9×——在这段范围里 prefill 时间基本是线性的， 每 token 成本只在最长一点上降了约 6%。所以 256→2048 那段的「次线性」 来自小上下文处的固定开销（256 与 512 都停在 111 ms），不是随上下文增长的摊薄效应； 2048 以内的结论不能外推到 4096+。

同一台服务上固定 4096 上下文量 decode：TTFT 1 543 ms，之后 15 步共 148 ms， 每 token 9.88 ms。这个数接近常数，与「递推状态定长、不随上下文增长」一致 （随上下文增长的只有 8 层 attention 的 KV）。

三个必须先固定的配置事实（否则量到的不是 prefill）：

  1. RecurrentGemma 在本版本走 Transformers 回退后端 （日志：TransformersForCausalLM has no vLLM implementation, falling back to Transformers implementation）。默认还会做 torch.compile 与 51 个图捕获尺寸， 启动超过 600 s 起不来；这里显式 --enforce-eager。上述绝对耗时因此是 回退路径的数字，不能当 vLLM 原生 kernel 的性能。
  2. --gpu-memory-utilization 给 0.35 会直接以 No available memory for the cache blocks 失败；本机独占时用 0.6 （引擎自报 KV 容量 703 490 token，8192 上下文下并发上限 85.88×）。
  3. 必须关掉前缀缓存。同一长度重复三次时，第二次起会命中缓存： 开着缓存时 512 的后两次是 16.1 / 15.0 ms，关掉后是 205.8 / 204.0 ms。 本节的三个数都是关掉之后的。

3. 前缀复用：定长状态能否参与哈希？

5.2 讲了 vLLM 的前缀缓存：通过哈希 (token_ids, ...) 复用相同前缀的 KV 块。 混合架构下，部分层是定长 recurrent state，还能复用吗？

实测：5 个共享前缀的请求

前缀："The RecurrentGemma architecture combines recurrent layers with local attention. "

请求 Prompt Tokens 时间 文本开头
0 23 271.9 ms Request 1: …
1 23 210.0 ms Request 2: …
2 23 208.4 ms Request 3: …
3 23 210.9 ms Request 4: …
4 23 210.6 ms Request 5: …

首次请求 271.9 ms，后续平均 210.0 ms，加速 1.29×（时间减少 22.8%）。

结论：前缀复用仍然有效。

vLLM 的前缀哈希包含了所有层的状态，不区分 KV cache 和 recurrent state。 定长状态也参与哈希：只要前缀相同，recurrent state 的值就相同，可以直接复用。

对比 5.2 中纯 attention 模型（Qwen3-1.7B）的前缀复用加速（batch=16）：首次 447 ms，后续 171 ms，加速 2.61×。

混合架构的加速比更小，有两个原因：

  1. 状态占比不同。 纯 attention 下前缀越长，复用省下的 KV 越多；混合架构下 recurrent state 只有 360 KB，前缀再长也只省这么多。
  2. 计算占比更高。 Recurrent 层的前向本身比 attention 轻，省掉状态读取的收益不如 attention 层明显。

4. 投机解码的回滚：定长状态怎么恢复？

5.5 讲了投机解码：草稿模型生成 K 个候选，目标模型一次前向验证。验证失败时要回滚到验证前的状态。

KV cache 的回滚（纯 attention）： 回滚只调整块表引用与有效长度，不搬运张量内容—— 后续 decode 会覆盖那些位置。这是 5.2/5.8 已经验证过的路径。

递推状态的回滚（混合架构）： 递推状态是定长的，没有"截断"可言， 验证前向已经把它覆盖掉了，所以要真正把旧值取回来。代价不是靠公式估的，下面按 RecurrentGemma-2B 的真实层配置（18 层 recurrent、状态 [batch,10,4,256] bf16， 即 368 640 byte/batch；8 层 attention、KV [2,1,256]/token/层）建真张量状态池实测 （labs/L5/hybrid_rollback_cost.py，results/crater/hybrid/rollback-cost-20260913/）。 状态写入是合成的，但快照/回滚的拷贝内核、字节与耗时都是真实 GPU 测量：

batch recurrent 状态 快照（clone） 回滚（逐层 copy_） 折合带宽 不投机单步的状态更新
1 0.37 MB 0.078 ms 0.052 ms 6.5 GB/s 0.055 ms
8 2.95 MB 0.071 ms 0.052 ms 57.2 GB/s 0.054 ms
32 11.80 MB 0.166 ms 0.052 ms 221.5 GB/s 0.054 ms

回滚时间不随搬运字节变化——batch 1 到 32 字节数涨 32 倍，时间纹丝不动， "折合带宽"从 6.5 涨到 221.5 GB/s 只是把常数时间除以了更大的分子。 把同一形状换成三种对照就看得出来它到底卡在哪：

对照（batch=32） 耗时
18 次逐层 copy_（一层一次） 0.053 ms
18 次空核的启动地板 0.058 ms
拼成一个连续张量后单次拷贝 0.006 ms
把 18 次拷贝捕进一张 CUDA Graph 回放 0.018 ms

逐层拷贝的时间与 18 次空核的启动地板一致，说明这一版实现是启动受限的： 每次回滚付 18 次 kernel launch，与状态多大无关。把它融合成一次拷贝能降到 1/9， 图捕获能降到 1/3。

协议正确性同时被验证，而不是只测时间。 四种拒绝位置（第 1 位、第 2 位、末位、全部接受） 下，回滚后的张量与快照逐元素完全相等（torch.equal，不是容差比较）； 回滚后按接受数再施加 accepted+1 次写入，结果与"从基准只施加 accepted+1 次写入"的参照 逐元素相等。也就是说被拒位置从来没有留进状态里。

快照成本必须计入整轮。 每轮投机要在验证前保存一次状态，恢复一次； 在本实现下两者相加是 0.13–0.22 ms，其中 batch=32 时快照（0.166 ms）比回滚（0.052 ms）还贵， 因为 clone() 还要分配一块新内存。

引擎的真实做法不同。 vLLM 0.29.0 的混合模型投机路径并不逐层 clone：

  • 状态张量的布局是 [num_groups, max_num_reqs, 1 + num_speculative_blocks] （vllm/v1/worker/mamba_utils.py:816）：每个请求预留 1 + num_speculative_blocks 个状态槽， 快照因此不是运行时分配，而是写进另一个已有槽位；
  • MambaSpecDecodeGPUContext（同文件 :771）只在「混合模型 + 投机解码 + mamba_cache_config 为 align 模式」 时启用，它把基址、步长、元素大小这些布局元数据预先算成张量， 让 GPU 端拷贝不需要 CPU-GPU 同步；
  • 拷贝本身是融合的 Triton 内核：postprocess_mamba_fused_kernel（:370）、 precopy_mamba_align_fused_kernel（:552），共享拷贝体 _copy_mamba_state_block（:192）， 并按 conv_width 区分两类状态——conv_width>0 是滑动窗口的偏移拷贝，0 是整块拷贝； 字节搬运走 u64 向量化路径 _memcpy_u64_tiled（:104），只在亚 8 字节不对齐时退到逐字节慢路径。

把三条放在一起看：「回滚要抄回整个状态」是对的，「抄回来很贵」取决于实现—— 逐层 copy_ 的版本贵在 18 次启动，融合成一次拷贝后 12 MB 只需 6 µs； 而引擎用「预留槽位 + 一个融合内核 + 无同步」把快照和回滚都压到了单次 kernel 的量级。

实际影响：

  • 拒绝发生在第几位不改变单次回滚成本（四种位置实测都是 0.052 ms 量级）， 改变的是这一轮还能提交多少 token，以及后续是否要重新验证。
  • 高接受率时回滚次数少；接受率低于 40%（5.5 的自由创作任务实测 31.1%）时， 每轮几乎都要回滚，快照 + 回滚 ≈ 一次额外的前向时间量级，会明显吃掉投机收益。

真实引擎上的混合架构投机：Qwen3.5-4B 的内置 MTP。 合成张量池给出了回滚成本， "回滚之后输出还对不对"要在真实模型上验。Qwen3.5-4B 正好覆盖两类状态：24 层 linear_attention（递推状态）+ 8 层 full_attention（KV），外加 1 个 MTP 块。 在 vLLM 0.29.0 上用 method=qwen3_5_mtp 打开内置 MTP，同一 prompt、贪心、 ignore_eos、输出 192 token（results/crater/5.5/spec-draft-20260922/mtp/）：

配置 B=1 tok/s B=4 tok/s 平均前进 输出 sha1（B=1 / B=4）
普通 decode 104.7 386.4 — 456600e3ce11 / 4e75d6ff419a
MTP k=1 176.5 630.0 1.96 同上
MTP k=2 226.0 690.3 2.82 同上
MTP k=4 270.4 1039.9 4.31 同上

四个配置的整条输出 sha1 与不投机逐位相同。投机的拒绝与回滚要发生在每一层： attention 层可以只截断 KV 长度，24 层递推状态却无法靠缩短长度恢复，必须走引擎预留的 状态槽位。输出逐位一致说明这条路径在这批负载与该 revision 上没有把被拒草稿留进状态； 它验证的是端到端一致性，不是每种拒绝位置的内部状态——后者仍由上面的合成张量池 逐元素对拍覆盖。vLLM 对混合架构的 MTP 有独立的模型实现（qwen3_5_mtp）， 说明这条路线是"权重 + 引擎实现 + 状态布局"三者配套，不是只换一个配置名。

工程实现：vLLM 的混合缓存管理

源码解析：状态分配与池化

vLLM 对混合架构的支持位于 vllm/attention/backends/ 和 cache 管理层。 以 RecurrentGemma 为例（vLLM 0.29.0）：

1. 层类型识别

# vllm/model_executor/models/recurrentgemma.py
class RecurrentGemmaDecoderLayer(nn.Module):
    def __init__(self, config, layer_idx):
        # 读取 block_types 配置
        block_types = config.block_types
        block_type = block_types[layer_idx % len(block_types)]

        if block_type == "recurrent":
            self.temporal_block = RecurrentBlock(config)
            self.channel_pre_norm = RMSNorm(config.hidden_size)
        else:  # "attention"
            self.temporal_block = SdpaAttention(config, layer_idx)

2. 状态池配置

# vllm/worker/model_runner.py
# 为 recurrent 层分配固定大小的 state pool
recurrent_state_size = (
    num_recurrent_layers,
    max_num_seqs,
    num_heads,
    conv_width,
    head_dim
)
self.recurrent_state_pool = torch.zeros(
    recurrent_state_size,
    dtype=torch.bfloat16,
    device="cuda"
)

3. 前缀哈希包含 recurrent state

# vllm/core/block_manager_v2.py
def _hash_block_content(self, block: Block) -> int:
    # 包含 KV cache 和 recurrent state
    if block.has_kv:
        content = block.kv_data  # attention 层
    elif block.has_recurrent:
        content = block.recurrent_data  # recurrent 层

    return hash(content.cpu().numpy().tobytes())

定长 state 也参与哈希，前缀相同则复用。

4. 投机回滚的状态快照

# 伪代码示意
def speculative_decode_step(draft_tokens):
    # 保存验证前状态
    kv_snapshot = self.kv_cache.get_block_table()
    recurrent_snapshot = self.recurrent_state.clone()

    # 验证
    accepted_count = verify_and_accept(draft_tokens)

    if accepted_count < len(draft_tokens):
        # 回滚
        self.kv_cache.truncate(accepted_count)  # 只调指针
        self.recurrent_state = recurrent_snapshot  # 恢复张量

Recurrent state 的回滚需要完整的张量拷贝。

SGLang 上的混合架构支持：本版本明确拒绝 RecurrentGemma

5.13 的载体是 RecurrentGemma。要在 SGLang 上做同一件事，先得问这个版本支持什么。 静态核查 + 一次真实启动（labs/L5/sglang_hybrid_probe.py、run_sglang_hybrid.sh， results/crater/hybrid/sglang-hybrid-20260913/）：

SGLang 0.5.19 有混合架构的运行时设施，但没有 RecurrentGemma 的实现。

检查项 结果
包内 RecurrentGemma / recurrent_gemma 命中 0 个文件
srt/models/ 下的 gemma 变体 gemma、gemma2、gemma3*、gemma4*，没有 recurrent
混合设施 mem_cache/hybrid_cache/{hybrid_cache_controller,hybrid_pool_assembler,linker_pool_assembler}.py、mamba_radix_cache.py、mamba_slot_fused.py、mamba_checkpoint_pool.py；引用 mamba/hybrid 缓存的文件 26 个
本版本支持的混合架构 Qwen3NextForCausalLM、NemotronHForCausalLM、BailingMoeV2ForCausalLM、GraniteMoeHybridForCausalLM
缺席的混合架构 MambaForCausalLM、Mamba2ForCausalLM、ZambaForCausalLM、JambaForCausalLM

真实启动尝试给出的是明确拒绝，不是崩溃：

ValueError: RecurrentGemmaForCausalLM has no Sglang implementation
and the Transformers implementation is not compatible with SGLang.

错误来自 sglang/srt/model_loader/utils.py:184 的 resolve_transformers_arch。 这正是两个引擎的分水岭：vLLM 0.29.0 会走 Transformers 回退 （日志：TransformersForCausalLM has no vLLM implementation, falling back to Transformers implementation），所以 RecurrentGemma 在 vLLM 上能跑—— 上一节的 8100 token 扫描就是这么跑出来的；SGLang 选择直接拒绝这条回退。

结论（给读者用的那一条）：混合架构的对照实验要落在两边都实现的模型上， 本版本可选 Qwen3-Next / NemotronH / Bailing-MoE / Granite-MoE-Hybrid； RecurrentGemma 只能在 vLLM 侧跑，SGLang 侧的"同模型对照"在当前版本上不存在。 这也意味着上一节所有耗时的引擎是 Transformers 回退路径， 换成两边都支持的混合模型才会有可比的 kernel 级数字。

前沿

1. Mamba 与 state-space models

RecurrentGemma 用的是 RNN Griffin，还有更激进的选择：Mamba（S6 state-space model）。 Mamba 把序列建模完全线性化，没有 attention 层，状态大小完全固定。

Jamba（AI21 Labs）是 Mamba + attention 的混合：8 Mamba 层 + 1 attention 层循环， 比 RecurrentGemma 的 2:1 recurrent/attention 比例更激进。

2. 长上下文的极限

纯 attention 的 KV cache 在百万 token 级别会耗尽显存。 混合架构理论上没有这个墙——recurrent state 固定，只有少数 attention 层的 KV 随长度增长。

但实际瓶颈在质量：recurrent state 的表达能力有限，超长依赖会丢失。 这是为什么混合架构仍然保留 attention 层——用固定状态换效率，用 attention 保证关键位置的全局视野。

3. 投机解码的适配

5.5 测得 ngram draft 在工具调用任务上接受率 95.7%、加速 4.12×，自由创作只有 37% / 1.47×。 混合架构下，低接受率场景的回滚成本更高（需要恢复整块 recurrent state）， 投机收益会进一步降低。本章在 Qwen3.5-4B 上补了真实引擎的实测：自带 MTP 在 k=1/2/4 上 平均前进 1.96/2.82/4.31、吞吐 1.63–2.58×，且输出与不投机逐位相同（见第 4 节末尾）。

适配方向：

  • 分层投机： 只对 attention 层做投机，recurrent 层直接执行（避免回滚）。
  • 状态增量： 记录 recurrent state 的更新而非完整快照，回滚时逆向应用。
  • 选择性投机： 根据前 N 个 token 的接受率动态决定是否继续投机。

陷阱

1. 假设所有层都产生 KV

3.4 已经指出这个坑：不能假设每层都有 KV cache。

错误代码：

# 计算 KV cache 大小
kv_bytes = num_layers * 2 * num_kv_heads * head_dim * seq_len * dtype_bytes

正确做法：

# 逐层检查
kv_bytes = 0
recurrent_bytes = 0

for layer in model.layers:
    if layer.block_type == "attention":
        kv_bytes += 2 * num_kv_heads * head_dim * seq_len * dtype_bytes
    elif layer.block_type == "recurrent":
        recurrent_bytes += num_heads * conv_width * head_dim * dtype_bytes

RecurrentGemma-2B：18 recurrent + 8 attention，实测 360 KB recurrent + 8 KB/token KV。

2. 用纯 attention 的 batch 策略

5.1 讲了 decode 的 batch 收益：权重读取摊薄到更多 token。

混合架构下，recurrent state 不会随 batch 摊薄权重读取——每个 batch 都要读一遍权重， 只有 attention 层的 KV 拼接能带来 batch 收益。

错误推论："batch=64 vs batch=1 应该有 64× 的吞吐提升。"

实际：RecurrentGemma 的 18/26 层是 recurrent，batch 收益被稀释。 测量前需要分离 recurrent 层和 attention 层的计时。

3. 把投机回滚当零成本

5.5 的结论（"回滚只是调整块表指针"）只适用于纯 attention 模型。混合架构的递推状态 是定长的，验证前向已经覆盖了旧值，必须真正取回来。

但成本不能用状态字节数直接换算。实测（18 层 recurrent、batch 1/8/32） 回滚时间恒在 0.052 ms，而搬运字节从 0.37 MB 涨到 11.8 MB—— 逐层 copy_ 的实现受 18 次 kernel 启动支配（启动地板 0.058 ms）， 不是带宽受限。把它融合成一次拷贝降到 0.006 ms，图捕获降到 0.018 ms。

也不要只算回滚：快照同样要计入整轮，本实现下两者相加 0.13–0.22 ms， batch=32 时快照（clone）比回滚还贵。引擎的真实实现用「预留 1 + num_speculative_blocks 个状态槽 + 一个融合 Triton 拷贝内核」避免这两项开销。

自测题

  1. RecurrentGemma-2B 的 26 层中，有多少层是 recurrent、多少层是 attention？它们的状态分别是什么形状？
  2. 为什么混合架构的 context 增长是「次线性」的？用实测数据说明。
  3. 定长的 recurrent state 能参与前缀复用吗？vLLM 怎么做的？
  4. 投机解码回滚时，KV cache 和 recurrent state 的代价有什么不同？用字节数量化。
  5. 混合架构在什么负载下比纯 attention 更有优势？什么负载下反而更差？
答案

  1. 18 recurrent + 8 attention（按 [recurrent, recurrent, attention] 循环）。Recurrent state: (batch, 10, 4, 256) = 20 KB/batch/layer，固定；KV cache: (2, 1, seq_len, 256) = 1 KB/token/layer，可变。

  2. 固定状态占主导。 Context 256→2048 增长 7.95×，prefill 时间只增长 3.53×。固定的 360 KB recurrent state + 可变的 KV cache (8 KB/token)，长上下文下固定部分摊薄了增长。

  3. 能。 vLLM 的前缀哈希包含所有层的状态，recurrent state 也参与哈希。前缀相同则 recurrent state 相同，可以复用。实测加速 1.29×（首次 271.9 ms，后续 210.0 ms）。

  4. KV cache 回滚零成本（只调块表指针）；recurrent state 回滚需要恢复整个张量。RecurrentGemma-2B 的 recurrent state = 360 KB/batch，batch=8 时回滚需要恢复 2.8 MB。

  5. 优势： 长上下文（>2048）、低 batch、显存受限场景——固定状态不随长度增长，显存占用远低于纯 attention。劣势： 高接受率投机解码（回滚频繁时成本高）、极短上下文（固定状态的开销无法摊薄）。

小结

混合架构（recurrent + attention）把「状态随上下文线性增长」的假设打破了：

  • 18/26 层是 recurrent：状态固定 20 KB/layer，不随 context 增长。
  • 8/26 层是 attention：KV cache 仍然是 1 KB/token/layer，线性增长。
  • 容量优势明显：context=2048 时只需 16.7 MB，是纯 attention 的 3.6%。
  • 前缀复用仍然有效：定长状态参与哈希，可以复用，实测加速 1.29×。
  • 投机回滚代价不同：KV 回滚只调指针，recurrent state 需要恢复整块张量（360 KB/batch）。

5.2 和 5.5 的结论需要在混合架构下重新审视：

  • KV 分页的块大小和哈希策略仍然适用，但状态总量计算要区分层类型。
  • 投机解码的回滚不再是零成本，低接受率场景收益更小。
  • Batch 策略需要考虑 recurrent 层不参与权重摊薄的事实。

下一步（L6）进入分布式：当模型跨卡分布时，recurrent state 的通信模式和 KV cache 完全不同—— 定长状态不能像 KV 一样分片传输，需要全量广播或点对点同步。
