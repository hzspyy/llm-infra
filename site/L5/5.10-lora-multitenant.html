5.10

LoRA 多租户服务

让多个请求共享基础模型、使用不同 LoRA adapter，分析批处理、显存占用和 adapter 换入换出。 使用公开已训练 adapter 学习训练产物与服务的接口，保留缺失训练信息的边界。

实测机器 crater · RTX 5090 D · vLLM 0.29.0 · SGLang 0.5.19前置 4.1 Transformer 解剖 · 5.3 调度 · 5.4 执行层

本章回答三个问题

多 LoRA 服务让请求共享基础模型，并分别使用各自的 adapter。引擎需要将请求、GPU 权重槽位和 token 行对应起来，在槽位不足时安排等待或换入。

  1. 一个 batch 混入不同 adapter，怎样实现共享 base GEMM 与逐行低秩增量？
  2. adapter 的逻辑身份、CPU 缓存、GPU 槽位和 KV cache 怎样保持一致？
  3. adapter 数量从 1 增到 64 时，吞吐下降来自 kernel，还是调度容量？

本章用随机生成的 adapter 验证系统机制，不评价微调质量。实测的核心结论是：固定 8 个 GPU adapter 槽位时，8→9 个 adapter 让这组等长请求从一轮拆成两轮，端到端耗时接近翻倍。 这里限制并行执行的是配置的槽位数。

心智模型

adapter 是附加在 base 模型上的小权重集合。请求携带逻辑 ID；worker 把它映射到可复用的物理槽位。低秩 kernel 读取的是槽位，不应拿外部 ID 直接当数组下标。

图中的数字是教学示例，不是固定槽位分配规则。槽位会复用；同一逻辑 ID 下一次可能驻留在不同位置。prefill 中一个请求展开成多行 token，decode 中通常只产生一行，两阶段不能共用未经展开的 request→adapter 数组。

机制拆解与推导

1. 低秩更新避免为每个租户复制完整模型

设 base 权重 W∈ℝO×H，adapter 的 A∈ℝr×H、B∈ℝO×r。r 是 rank，即低秩中间维度。普通 LoRA 的缩放 s=α/r，一行输入满足：

y=xWT+s(xAT)BT.

先算 xAT 把 H 维压成 r 维，称为 shrink；再乘 BT 展开到 O 维，称为 expand。它们是两次矩阵乘法，不是把 A、B 逐元素加到 W。

共有 M 行输入时，base 计算量约为 2MHO FLOPs；低秩分支约为 2Mr(H+O) FLOPs。BF16 adapter 权重字节数为：

Dadapter=2r(H+O).

本章 Qwen3-1.7B 的 q_proj 使用 H=O=2048、28 层、r=8，因此全部层的 q_proj adapter 张量共 2×8×(2048+2048)×28=1835008 字节，即 1.75 MiB。这是张量净数据，不包括 safetensors 文件头、CPU 对象、GPU padding 和其他被包装层的预分配空间。

单个 q_proj 的理论额外 FLOPs 比例为 r(H+O)/(HO)=0.0078125。0.78125% 的 FLOPs 不等于 0.78125% 的时延。 小 GEMM、metadata 整理、额外 kernel 发射、槽位复制和中间 buffer 都不在这个比例中。

2. 混批要求逐行选择权重

令 a(i) 是 token 行 i 的 adapter ID，sa(i) 是对应缩放：

Yi=XiWT+sa(i)(XiAa(i)T)Ba(i)T.

base 的 XWT 仍能对整个 batch 做一次 GEMM。低秩部分按 adapter 分组：取属于同一 adapter 的行，做两次小 GEMM，再写回原行号。实现可以只排序行号并间接寻址，不必物理搬动整个 X。

不能把 ∑jBjAj 合并进一份 W 供所有请求使用，那会把每个租户的更新同时应用到所有请求。逐 adapter 合并成 Wj=W+sjBjAj 在代数上可行，但会重新承担多份 dense 权重的存储和分组执行成本。

3. 三种容量不能混为一谈

容量 本次扫描配置 限制的对象
提交请求数 64 一次离线 generate 的请求集合
max_cpu_loras 64 worker 保留的 adapter 缓存数量
max_loras 8 同一步可用的 GPU adapter 槽位数量

64 个请求只用一个 adapter 时，一个槽位足够。64 个请求各用一个不同 adapter 时，即使模型和 KV 显存有余量，也不能在这套配置下把 64 种 adapter 同时装进 8 个槽位。

驻留选择还会影响 KV 容量。粗略预算为：

MGPU=Mbase+Madapter slots+MKV+Mactivation+Mworkspace.

增大槽位数可能减少换入或调度分轮，但会增加预分配、metadata 和潜在的图捕获组合；不能只按磁盘上的 adapter 文件大小估算 GPU 成本。

4. 换入成本应分层测量

文件解析、CPU 缓存命中、CPU→GPU 复制、目标槽位清零、mapping 更新是不同阶段。若 CPU 权重已经存在，传输部分可用 D/BH2D 作理想化预测，但实测的整个 activate_adapter 还包括 Python 调度与多层小复制，不能反过来当成 PCIe 峰值带宽。

是否驻留可按预期复用次数分析：若保留该 adapter 节省的累计换入时间大于其挤占 KV 或其他 adapter 所增加的等待代价，保留才有意义。这是设计分析；本章没有拟合线上到达过程，也没有得出通用驻留阈值。

  • v1 的三次输出完全一致（24 个点）
  • v2 输出与 v1 不同（"? the ...? is . "）

这个方向不成立，正文在此改正。 旧实验每步都在换 lora_int_id，又没有记录缓存命中， 所以它无法区分"权重生效"与"缓存复用"。重做的实验 （labs/L5/lora_cache_identity_test.py，results/crater/lora/cache-identity-20260914/） 把 name / id / path / 权重内容四个量分开动，并在每步读 llm.get_metrics() 里的 prefix cache 计数——判据是命中计数，不是文本比对：

步 name / id / path 输出 prefix_cache_hits 增量
S1 A / 1 / P1（v1） v1 token 0（queries 101）
S2 A / 1 / P1（v1）再发一次 v1 token 96
S3 A / 1 / P1，把 P1 的权重原地换成 v2 v1 token 96
S4 A / 1 / P2（v2 的副本） v1 token 96
S5 B / 2 / P1（此时权重已是 v2） v2 token 0
R1 同 S4，但关闭 prefix caching v2 token —
S6 同 S4，但换成新引擎 v2 token —

三条结论：

  1. 同名热更新的旧值来自 adapter 权重缓存，不是前缀缓存。 S3 的输出与命中增量跟 S2 一模一样（96 hits）。把两处成因分开的实验（同一脚本 --mode split）在同一批 adapter 上跑三种引擎配置（results/crater/lora/hot-split-20260922/）：
配置 前缀缓存 adapter 槽 更新前先挤掉 S3 输出 S3 命中增量
cache_on_cpu3 开 max_loras=2 / max_cpu_loras=3 否 v1 token 96
cache_off_cpu3 关 max_loras=2 / max_cpu_loras=3 否 v1 token 0
cache_on_cpu1_evict 开 max_loras=1 / max_cpu_loras=1 是（先加载另一个 adapter） v2 token 96

关掉前缀缓存后仍返回 v1（命中 0）：旧值不需要前缀缓存来解释。 挤掉 adapter 槽后返回 v2（命中仍是 96）：前缀缓存命中 96 个 token 也没有拦住新权重 生效。两者合起来说明——权重缓存按 name/id 常驻，才是"同名热更新无效"的主因； 前缀缓存只是复用 KV，不决定输出是哪一版。

  1. 换 path 不换 name 时，输出仍由 adapter 缓存决定。 S4 换成 v2 的副本路径、 lora_name 仍是 A，请求仍然命中缓存里的旧权重（输出 v1、前缀缓存 96 hits）； 同一请求在新引擎（S6）下得到 v2。这与上一条一致：换 name 才能换到新 KV， 换 name/id 或清空缓存才能换到新权重。
  2. lora_int_id 不是缓存身份。 S5 只把 name 换成 B（id 同时换成 2）， 命中立刻变成 0、输出立刻变成 v2——而它读的路径 P1 本来就是已经更新过的权重。 与源码一致：进入 hash key 的是 lora_name（v1/core/kv_cache_utils.py:542–554）， 权重版本不在里面。

给服务设计的结论要反过来读：同名热更新不仅不会自动失效旧 KV， 在权重已经换掉之后，同名的请求会继续命中旧 KV。生产上必须用版本化名称 （如 modelA-v2），或在更新时显式清掉该名称的全部 KV。

H0. SGLang 侧 top-k logprob 的取法

跨引擎对照 logprob 时先要读对字段——两边的形状完全不同：

vLLM（OpenAI 兼容） logprobs=k（或 prompt_logprobs） choices[0].logprobs.top_logprobs 是 [{token 文本: logprob}, …]
SGLang（/generate） 顶层字段 return_logprob=True、top_logprobs_num=k meta_info.output_token_logprobs 每位置 [logprob, token_id, None]；top-k 在另一个键 output_top_logprobs 里，每位置 [[logprob, token_id], …]

labs/L5/sglang_topk_logprob.py 对着真实服务读了一遍 （results/crater2/5.10/sglang-logprob-20260921/，top_logprobs_num=5、输出 16 token）：

              output_token_logprobs, output_token_logprobs_length, output_top_logprobs, …

首元素：len=3: [logprob=-1.1711, token_id=4891, third=None]
  位置 token=4891  logprob=-1.1711  topk_ids=[4891, 220, 24562]

  位置 token=235   logprob=-0.0     topk_ids=[235, 103, 107]

三个容易踩的坑，都在这次的实测里对上了：

  1. return_logprob/top_logprobs_num 是 GenerateReqInput 的顶层字段 （srt/managers/io_struct.py:226/231），放进 sampling_params 会被服务端拒绝 （HTTP 500）——第一次请求就是这样失败的。
  2. top-k 不在逐位置元素的第三个槽里：output_token_logprobs[i] 只有 [logprob, token_id, None]，真正的候选列表在 output_top_logprobs[i]。 按第三个槽取值会得到"top-k 尺寸为空"的假结论。
  3. SGLang 返回的是 [logprob, token_id] 数对，vLLM 返回的是 {token 文本: logprob}。 后者要小心文本匹配（yes/Yes/YES 是不同 token，见 5.12 的 rerank 对照）， SGLang 侧用 token_id 就没有这个问题。

一致性核对：16 个位置全部满足"top-1 == 该位置实际采到的 token"， 长度也与输出 token 数相等——字段读对之后，这两条是最低限度的一致性检查。

H1. SGLang 的 unload 是「驱逐」，不是「移除」

源码先把语义摆清楚（sglang 0.5.19）：

  • /unload_lora_adapter（srt/entrypoints/http_server.py:1574）要求请求体带 lora_name（srt/managers/tokenizer_control_mixin.py:768-771 断言）， 最终由 LoRAManager._unload_lora_adapter（srt/lora/lora_manager.py:332） 按 lora_id 从内存池、configs、loras、lora_refs 里删除；而请求带的是 lora_path，两者不是同一个键。
  • 每个带 lora_path 的请求都会先走 _resolve_lora_path （srt/managers/tokenizer_manager.py:3344）：它向注册表问"哪些路径已不在注册表里" （lora_registry.get_unregistered_loras），然后从 lora_ref_cache 隐式重新加载 它们（日志 Reloading evicted adapter，:3364-3378），再 acquire 拿 id。

labs/L5/sglang_lora_unload_semantics.py 用五个动作把这条语义跑出来 （Qwen3-4B + trl-lib/Qwen3-4B-LoRA，results/crater2/5.10/sglang-unload-20260921/）：

动作 结果
A 装载 pub HTTP 200，loaded_adapters={"pub": …}
A' 用 lora_path=pub 生成 HTTP 200，输出 token [4891, 231, 235, 103630, …]
B 卸载 pub HTTP 200，loaded_adapters={}（内存池里确实没了）
C 再请求同一路径 HTTP 200，输出与 A' 逐 token 相同；服务端日志出现 Reloading evicted adapter: pub
D 请求从未装载的路径 HTTP 400 Got LoRA adapter that has never been loaded: … All loaded adapters: dict_keys(['pub'])
E 卸载不存在的名字 HTTP 400 LoRA with name no-such-name does not exist. Loaded LoRAs: odict_keys(…)

三条结论：

  1. unload 只保证"此刻不占槽位"，不保证"之后不会被装回来"。 C 步的输出与 A' 逐 token 相同、且日志里出现了隐式重载，说明卸载后可观测状态 取决于之后有没有请求点到同一个路径——这正是"卸载行为看起来不一致"的成因。
  2. D 步的报错正好是第 1 条的镜像：隐式重载把 pub 重新注册回了注册表， 所以"已装载列表"里又能看到它；而一个真正从未装载过的路径会被明确拒绝。
  3. 两个键不能混用：请求用 lora_path、卸载用 lora_name。 按名字卸载、按路径重载，中间靠 lora_ref_cache 的路径做桥。

要把适配器真正从服务里移除，得同时断开重载路径（把 lora_ref_cache 里的条目也清掉， 或让请求不再指向该路径）；max_loaded_loras 的 LRU 驱逐走的是同一条隐式重载路径， 所以"被驱逐"同样只是暂时状态。

H2. qkv_proj 的切片对齐：v 落在哪几行

SGLang 把适配器的 q/k/v 三个模块归一成一条融合模块 qkv_proj （srt/lora/lora.py:264 normalize_qkv_proj）：按 [q, k, v] 的顺序拼接， 适配器没有 k_proj 时用 zeros_like(v) 补零；融合输出维由 get_hidden_dim （srt/lora/utils.py:175）给出 head_dim × (num_attention_heads + 2 × num_key_value_heads)。

labs/L5/lora_qkv_slice_alignment.py 在 CPU 上只读第 0 层的 q/k/v 与适配器对应张量 （results/crater/5.10/qkv-align-20260921/）：

量 值
基座权重 q (4096, 2560)、k (1024, 2560)、v (1024, 2560)
公式核对 128×(32+2×8)=6144=4096+1024+1024 ✓
归一化后的 B (6144, 8) = [q; k 全零; v]，v 的行区间 [5120, 6144)
归一化后的 A (24, 2560) = [A_q; A_k 全零; A_v]
只拼 [q; v] 的负例 B (5120, 8)，v 的行区间变成 [4096, 5120) —— 相差 1024 行
数值对拍（融合 vs 分别合并） q 段 max|Δ| 0，v 段 max|Δ| 0
错位写入（v 写到 [4096, 5120)） v 段 max|Δ| 6.10e-04（正好是 LoRA 增量本身的量级）

两条结论：

  1. "v 紧跟在 q 后面"是错的，中间必须留出 k 的 1024 行。 这里 1024 = num_key_value_heads × head_dim，不是常数——换模型就变。 错位不会报错：形状仍然合法（5120 + 1024 行也能拼出来），只是注意力的 K 与 V 段被写乱，误差量级与"少加一次 LoRA"相同。
  2. 适配器不带 k_proj 时，k 段必须是精确的零块（实测 True）。 没有这一步，SGLang 的 [q;k;v] 行序就无从与基座的融合权重对齐。

  2. merged 与 unmerged 的首 token 分布在 6.5e-02 ~ 1.2e-01 之间，四个 prompt 的 argmax 全相同；生成序列在 4 个里有 3 个中途分岔——这与本节前面测到的 "同一配置重复运行之间也会分岔"是同一类现象，所以不能用文本是否相同来判断合并对不对， 要比的是同一上下文下的分布差。
  3. 低秩分支的代价可以量化：4 条 prompt × 32 token，merged 0.271 s、unmerged 0.597 s， merged 快 2.2 倍（省掉 shrink/expand 两个 kernel）。 代价是每份合并权重占 7.6 GB（单个 safetensors），而 adapter 本体只有 11.8 MB—— 这就是"每租户一份 dense 模型"与"共享 base + 低秩"之间的实际交换比。

本节没有做的：没有在 SGLang 上跑同一组对照；没有固定 RNG 去消除运行间抖动； merged 侧的显存占用没有单独测（只记了磁盘体积）。同 checkpoint 的固定 RNG 复现、 qkv_proj 切片对齐与 unload 语义见后文 I/K 两节的补测。

L. SGLang 的 LoRA 异常路径：非法请求之后还能不能服务

任务 C 要求在 HTTP 服务上测「非法 rank 后合法请求」「请求执行中卸载/替换」， 并把「重启恢复与同进程恢复分开」。vLLM 侧已有 lora_recovery_test.py， SGLang 侧这次补上（labs/L5/sglang_lora_recovery_test.py + run_sglang_lora_recovery.sh， results/crater/sglang/lora-recovery-20260914/）。服务只注册一个合法 rank-8 adapter， 然后按顺序打六种请求：

但 rank 超限的失败方式不一样，这是本节真正的发现。 S3 用的是"路径"， 被 400 挡在门外——原因不是 rank，而是路径没注册。要真正触发 rank 校验， 得在启动时把它注册进去：把 rank=16 的 adapter 写进 --lora-paths pub=<valid> big=<rank16>，服务启动并没有拒绝； 直到第一次真正发到 lora_path=big 的请求，才在加载权重时炸：

AssertionError: LoRA buffer shape torch.Size([24, 2048]) does not match
weight shape torch.Size([48, 2048]).

位置在 sglang/srt/lora/mem_pool.py:1226 的 load_lora_weight_to_buffer， 客户端看到的是 curl 的"Empty reply from server"（HTTP 000）—— 也就是连接被打断，而不是干净的 4xx。

结论有三条：

  1. 校验点太晚：--max-lora-rank 8 只在真正加载权重时生效， 启动注册阶段不校验，所以一个配置错误能进到线上并炸在一次真实请求上。 对照 vLLM：那边 lora_recovery_test.py 记录的也是"rank 超限后同引擎继续失败、 重建引擎才恢复"——两个引擎在这一点上都不能靠启动校验兜住。
  2. 失败形态不同：SGLang 这里是连接中断（000），不是带错误信息的 400； 前三种非法（名字/路径/坏目录）都是 400 + 明确文案。 对客户端来说，"缺少 LoRA 配置"与"服务端崩了"是两种完全不同的故障， 而它们在这里看起来只差一个 HTTP 状态码的有无。
  3. 同进程恢复仍然成立：这次 rank-16 的失败发生在另一个服务实例上 （第三配置），所以它没有污染 S1–S7 那一轮； 也就是说"注册了超限 adapter 的服务会崩在第一次用到它时"与 "正常服务能扛住非法请求"是两件独立的事实，不要混在一起说。

本节没有做的：没有测"同名不同版本热更新"在 SGLang 侧的表现 （§F 那套命中计数只在 vLLM 上做过）；没有测运行中的 adapter 卸载/替换 API。

  3. 把两种顺序分开跑，就能把这件事钉死（labs/L5/sglang_lora_unload_probe.py + run_sglang_lora_unload_probe.sh，results/crater/sglang/unload-probe-20260914/）：
顺序 结果
A：unload → 不请求 → 显式 load 同名 200 成功（说明注册表真的空了）
B：unload → 请求一次 → 显式 load 同名 请求 200；显式 load 400 because it is already loaded

B 里的 400 是那次请求把名字装回来造成的，不是账本自相矛盾； 而 B 的请求输出与参照逐位相同（implicit_reload_same_weights: true）， 说明隐式重载装回的是同一份权重。服务端日志里 Reloading evicted adapter 恰好出现一次——就是 B 的请求触发的。

所以 SGLang 的语义应该这样读：unload 把 adapter 从注册表移除、释放运行时占用， 但 lora_ref_cache 保留引用，下一个同名请求会把它按需装回来。 它是"卸载即按需重载"（unload-on-idle + reload-on-demand）， 而不是"卸载后不可再用"。运维上要真正让一个 adapter 消失， 还必须清掉它的缓存引用——这一点接口没有直接提供。

本节没有做的：没有测"先前已有的请求还在生成时替换权重"（S6 只测了卸载）； 没有测 max_loaded_loras 触发的 LRU 驱逐与隐式重载的交互。

设计取舍

核心不变量：一个 token 行的请求身份、adapter 版本、GPU slot 和输出位置必须一致。 从调度完成到该步 kernel 完成，slot 不能被另一 adapter 覆盖；rank padding 不得残留；base 行不得误加增量。

状态归属分为四层：入口管理名称、版本与授权；scheduler 管可接纳请求；worker 管 CPU 缓存和 GPU 槽位；kernel 只消费本步 metadata。prefix cache 则必须带上足以区分有效权重的身份。把所有状态压到一个全局“当前 adapter”变量中，单请求测试可能正常，混批必然不可靠。

  1. 同一引擎内继续使用失败。 rank 超限后，即使后续请求的 adapter 是有效的（rank 8 < max 16），仍报同样的 LoRA rank 32 is greater than max_lora_rank 16. 错误。异常被捕获并不意味着引擎的 LoRA 请求队列、adapter mapping 或内部状态已回滚到干净状态。

前沿与待验证路线

沿本章机制继续扩展，而不是只增加 adapter 数量：

  • 统一分页与异构 rank。 把 adapter 和 KV 的容量管理一起考虑，减少固定最大 rank padding 的浪费；应比较碎片、寻址和搬运成本。S-LoRA、Punica 是相关系统路线的阅读入口，不代表本章复现了它们的全部设计。
  • 计算与加载重叠。 当前快照含辅助 stream、overlap loader 等代码；没有运行本章负载的开关对照，收益为 UNVERIFIED，尤其要检查 slot 生命周期与 stream 依赖。
  • 图捕获与量化组合。 eager 结果不能预测 CUDA Graph、量化 base、FP8 LoRA 或 MoE adapter 的表现；需要专门的 shape、dtype、误差和图缓存测试。
  • 线上公平性。 adapter-aware batching 可能改善吞吐，但长尾租户、取消、deadline 与权限需要独立测试。SGLang 全引擎、TensorRT-LLM 和其他服务实现的端到端对照为 UNVERIFIED；未配置对应服务与本章负载。

陷阱

  1. 只测单 adapter，掩盖混批 mapping 和容量边界。
  2. 把逻辑 ID 当 GPU slot，忽略槽位复用与 base 哨兵。
  3. 以为 alpha/r 必须在 kernel 中乘；loader 可以预先折进权重，重复缩放会出错。
  4. 从 q_proj 文件净字节推断所有 GPU 预分配，遗漏 packed slice、rank padding 和其他层。
  5. 把 64 个已缓存 adapter 当作 64 个 GPU 常驻 adapter。
  6. 把带同步插桩的换入调用耗时当成 PCIe 传输基准。
  7. 把 profiler kernel 时间之和写成端到端占比。
  8. 同名替换 adapter 却默认旧 KV 仍正确；只捕获 loader 异常却假定请求状态已经回滚。

自测题

  1. 给定 H=4096、O=4096、r=16、BF16，一个 linear adapter 的净字节数是多少？
  2. token ID 映射 [7,9,7,0]、GPU slot 表 [9,7] 应转换为什么？
  3. 为什么 64 请求、9 个 adapter、8 个 GPU slot 不一定只比 8 个 adapter 慢一点？
  4. “只有 0.8% 额外 FLOPs，所以只慢 0.8%”缺了哪些开销？
  5. 应怎样证明非法 rank 请求没有破坏后续服务？
答案
  1. 2×16×(4096+4096)=262144 字节，即 256 KiB；未计文件头与运行时 padding。
  2. [1,0,1,-1]。7 在 slot 1，9 在 slot 0，base 用内部哨兵 -1。
  3. 请求接纳受不同 adapter 数限制。本章等长突发负载从 16 个执行步变为 32 个，后轮还伴随换入和较小 batch；9 不是硬件阈值。
  4. metadata、分组、额外发射、小 GEMM 利用率、读写低秩 buffer、槽位加载与排队。FLOPs 不能单独决定 wall time。
  5. 除检查错误类型外，还必须继续发起后续合法请求，严格校验其执行完成状态、文本输出、调度请求表、KV 缓存及槽位生命周期账本。若后续请求未能正确完成，则不能判定异常已安全恢复。
