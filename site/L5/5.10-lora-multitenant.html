LoRA 多租户服务

一个 base 模型 + N 个 adapter 同时服务（S-LoRA / punica 路线）：按请求选 adapter、同一 batch 里混不同 adapter、adapter 的显存与换入换出。

实测机器 crater · RTX 5090 D · vLLM 0.29.0 · SGLang 0.5.19数据日期 2026-09-11 / 2026-09-12前置 4.1 Transformer 解剖 · 5.3 调度 · 5.4 执行层

本章回答三个问题

多 LoRA 服务共享一份 base 权重，但不共享每个请求的 adapter 身份。 真正困难的部分，是把请求身份、GPU 权重槽位和这一轮的 token 行对应起来，并在容量不足时正确等待或换入。

  1. 一个 batch 混入不同 adapter，怎样实现共享 base GEMM 与逐行低秩增量？
  2. adapter 的逻辑身份、CPU 缓存、GPU 槽位和 KV cache 怎样保持一致？
  3. adapter 数量从 1 增到 64 时，吞吐下降来自 kernel，还是调度容量？

本章用随机生成的 adapter 验证系统机制，不评价微调质量。实测的核心结论是：固定 8 个 GPU adapter 槽位时，8→9 个 adapter 让这组等长请求从一轮拆成两轮，端到端耗时接近翻倍。 这不是“第九个 adapter 触发了某种 GPU 硬件极限”。

心智模型

adapter 是附加在 base 模型上的小权重集合。请求携带逻辑 ID；worker 把它映射到可复用的物理槽位。低秩 kernel 读取的是槽位，不应拿外部 ID 直接当数组下标。

图中的数字是教学示例，不是固定槽位分配规则。槽位会复用；同一逻辑 ID 下一次可能驻留在不同位置。prefill 中一个请求展开成多行 token，decode 中通常只产生一行，两阶段不能共用未经展开的 request→adapter 数组。

机制拆解与推导

1. 低秩更新避免为每个租户复制完整模型

设 base 权重 W∈ℝO×H，adapter 的 A∈ℝr×H、B∈ℝO×r。r 是 rank，即低秩中间维度。普通 LoRA 的缩放 s=α/r，一行输入满足：

y=xWT+s(xAT)BT.

先算 xAT 把 H 维压成 r 维，称为 shrink；再乘 BT 展开到 O 维，称为 expand。它们是两次矩阵乘法，不是把 A、B 逐元素加到 W。

共有 M 行输入时，base 计算量约为 2MHO FLOPs；低秩分支约为 2Mr(H+O) FLOPs。BF16 adapter 权重字节数为：

Dadapter=2r(H+O).

本章 Qwen3-1.7B 的 q_proj 使用 H=O=2048、28 层、r=8，因此全部层的 q_proj adapter 张量共 2×8×(2048+2048)×28=1835008 字节，即 1.75 MiB。这是张量净数据，不包括 safetensors 文件头、CPU 对象、GPU padding 和其他被包装层的预分配空间。

单个 q_proj 的理论额外 FLOPs 比例为 r(H+O)/(HO)=0.0078125。0.78125% 的 FLOPs 不等于 0.78125% 的时延。 小 GEMM、metadata 整理、额外 kernel 发射、槽位复制和中间 buffer 都不在这个比例中。

2. 混批要求逐行选择权重

令 a(i) 是 token 行 i 的 adapter ID，sa(i) 是对应缩放：

Yi=XiWT+sa(i)(XiAa(i)T)Ba(i)T.

base 的 XWT 仍能对整个 batch 做一次 GEMM。低秩部分按 adapter 分组：取属于同一 adapter 的行，做两次小 GEMM，再写回原行号。实现可以只排序行号并间接寻址，不必物理搬动整个 X。

不能把 ∑jBjAj 合并进一份 W 供所有请求使用，那会把每个租户的更新同时应用到所有请求。逐 adapter 合并成 Wj=W+sjBjAj 在代数上可行，但会重新承担多份 dense 权重的存储和分组执行成本。

3. 三种容量不能混为一谈

容量 本次扫描配置 限制的对象
提交请求数 64 一次离线 generate 的请求集合
max_cpu_loras 64 worker 保留的 adapter 缓存数量
max_loras 8 同一步可用的 GPU adapter 槽位数量

64 个请求只用一个 adapter 时，一个槽位足够。64 个请求各用一个不同 adapter 时，即使模型和 KV 显存有余量，也不能在这套配置下把 64 种 adapter 同时装进 8 个槽位。

驻留选择还会影响 KV 容量。粗略预算为：

MGPU=Mbase+Madapter slots+MKV+Mactivation+Mworkspace.

增大槽位数可能减少换入或调度分轮，但会增加预分配、metadata 和潜在的图捕获组合；不能只按磁盘上的 adapter 文件大小估算 GPU 成本。

4. 换入成本应分层测量

文件解析、CPU 缓存命中、CPU→GPU 复制、目标槽位清零、mapping 更新是不同阶段。若 CPU 权重已经存在，传输部分可用 D/BH2D 作理想化预测，但实测的整个 activate_adapter 还包括 Python 调度与多层小复制，不能反过来当成 PCIe 峰值带宽。

是否驻留可按预期复用次数分析：若保留该 adapter 节省的累计换入时间大于其挤占 KV 或其他 adapter 所增加的等待代价，保留才有意义。这是设计分析；本章没有拟合线上到达过程，也没有得出通用驻留阈值。

相同 prompt 在不同 adapter 下可能产生不同隐藏状态，不能无条件共用 KV。服务设计还需要让名称与权重版本保持一致，或在更新时可靠失效缓存。本章性能实验显式关闭 prefix caching。

同名热更新测试（lora_kv_invalidation_test.py）使用相同 lora_name="test" 和相同 prompt，分四步生成：v1 权重首次、v1 权重第二次、v2 权重（同名覆盖）、v1 权重第三次。观察到：

  • v1 的三次输出完全一致（24 个点）
  • v2 输出与 v1 不同（"? the ...? is . "）

结论： v1 第二次与第三次输出相同，说明 v2 覆盖后，引擎没有继续使用 v1 的旧 KV cache，而是用新权重重新计算或失效了缓存。这与 lora_name 作为 hash key 的设计一致：同名意味着"同一逻辑 adapter"，引擎相信调用者已正确管理版本。如果服务端热更新了权重但客户端仍用旧名称，KV 可能不会失效，导致不一致。生产环境应使用版本化名称（如 modelA-v2）或确保更新时显式清理该名称的所有 KV。

设计取舍

核心不变量：一个 token 行的请求身份、adapter 版本、GPU slot 和输出位置必须一致。 从调度完成到该步 kernel 完成，slot 不能被另一 adapter 覆盖；rank padding 不得残留；base 行不得误加增量。

状态归属分为四层：入口管理名称、版本与授权；scheduler 管可接纳请求；worker 管 CPU 缓存和 GPU 槽位；kernel 只消费本步 metadata。prefix cache 则必须带上足以区分有效权重的身份。把所有状态压到一个全局“当前 adapter”变量中，单请求测试可能正常，混批必然不可靠。

提高 GPU 槽位容量，可能减少波次，却会挤占其他显存用途。按 adapter 重排请求，可能提高局部复用，却改变公平性和尾延迟。本章只测等长突发请求，没有评估这些替代策略的线上收益；这张表是分析，不是上游否决方案的记录。

新增后端至少涉及层的布局与 TP slice、metadata 契约、rank/缩放语义、base 哨兵、输出累加、dtype，以及 graph capture 的地址和形状稳定性。错误应尽早发现：rank、target module、base revision 在加载前验证；槽位数量在调度时验证；shape、stride、输出误差在 kernel 测试中验证。租户授权与文件来源仍须由服务入口检查，LoRA 数值路径本身不是权限隔离机制。

  • 统一分页与异构 rank。 把 adapter 和 KV 的容量管理一起考虑，减少固定最大 rank padding 的浪费；应比较碎片、寻址和搬运成本。S-LoRA、Punica 是相关系统路线的阅读入口，不代表本章复现了它们的全部设计。
  • 计算与加载重叠。 当前快照含辅助 stream、overlap loader 等代码；没有运行本章负载的开关对照，收益为 UNVERIFIED，尤其要检查 slot 生命周期与 stream 依赖。
  • 图捕获与量化组合。 eager 结果不能预测 CUDA Graph、量化 base、FP8 LoRA 或 MoE adapter 的表现；需要专门的 shape、dtype、误差和图缓存测试。
  • 线上公平性。 adapter-aware batching 可能改善吞吐，但长尾租户、取消、deadline 与权限需要独立测试。SGLang 全引擎、TensorRT-LLM 和其他服务实现的端到端对照为 UNVERIFIED；未配置对应服务与本章负载。

陷阱

  1. 只测单 adapter，掩盖混批 mapping 和容量边界。
  2. 把逻辑 ID 当 GPU slot，忽略槽位复用与 base 哨兵。
  3. 以为 alpha/r 必须在 kernel 中乘；loader 可以预先折进权重，重复缩放会出错。
  4. 从 q_proj 文件净字节推断所有 GPU 预分配，遗漏 packed slice、rank padding 和其他层。
  5. 把 64 个已缓存 adapter 当作 64 个 GPU 常驻 adapter。
  6. 把带同步插桩的换入调用耗时当成 PCIe 传输基准。
  7. 把 profiler kernel 时间之和写成端到端占比。
  8. 同名替换 adapter 却默认旧 KV 仍正确；只捕获 loader 异常却假定请求状态已经回滚。

自测题

  1. 给定 H=4096、O=4096、r=16、BF16，一个 linear adapter 的净字节数是多少？
  2. token ID 映射 [7,9,7,0]、GPU slot 表 [9,7] 应转换为什么？
  3. 为什么 64 请求、9 个 adapter、8 个 GPU slot 不一定只比 8 个 adapter 慢一点？
  4. “只有 0.8% 额外 FLOPs，所以只慢 0.8%”缺了哪些开销？
  5. 应怎样证明非法 rank 请求没有破坏后续服务？
答案
  1. 2×16×(4096+4096)=262144 字节，即 256 KiB；未计文件头与运行时 padding。
  2. [1,0,1,-1]。7 在 slot 1，9 在 slot 0，base 用内部哨兵 -1。
  3. 请求接纳受不同 adapter 数限制。本章等长突发负载从 16 个执行步变为 32 个，后轮还伴随换入和较小 batch；9 不是硬件阈值。
  4. metadata、分组、额外发射、小 GEMM 利用率、读写低秩 buffer、槽位加载与排队。FLOPs 不能单独决定 wall time。
  5. 除检查错误类型，还要再发合法请求，检查完成、输出、请求表、KV 与槽位账，以及后续多轮运行。旧实验第二次 generate 仍失败，因此不能宣称恢复通过。
