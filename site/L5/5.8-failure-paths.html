失败路径：取消、超时、背压、断连、OOM 与资源回收

注入取消、超时、断连、背压和块池耗尽，检查请求结束后资源能否正确回收。

实测机器 crater (RTX 5090 D, sm_120) · Qwen3-1.7B · vLLM 0.29.0 · nanoserve前置 5.1（两相）· 5.2（块池与引用计数）· 5.3（调度）· 5.7（nanoserve）

本章回答三个问题

正常请求跑得快只是一半。另一半是：出事的时候，谁负责把资源收回来？

  1. 客户端断连之后，那条请求的 KV 块什么时候被释放？怎么证明它真的被释放了？
  2. 队列积压时靠什么反压？不反压会怎样，反压过头又会怎样？
  3. 块池不够用时会发生什么？抢占要付多少代价？

本章在 5.7 的 nanoserve 上补四条路径（抢占、超时、背压、泄漏）， 再拿真实 vLLM 对照。最重要的一条结论：泄漏不会报错。 把 abort() 写错一行，引擎不崩、日志干净、输出正确， 只是从第 16 条请求开始再也不产出任何 token。

心智模型：一条请求有三处状态，取消要同时处理三处

机制拆解

取消的清理内容取决于请求当时在哪

同一条 abort()，让受害者分别停在三种状态（labs/L5/nanoserve/run_failures.py case 1）：

取消时的状态 在等待队列 在运行集 持有的块 空闲块 归还 旁边那条请求的引用计数
waiting 是 否 [] 48 → 48 0 未变
prefill 否 是 [5,6,7,8,9] 38 → 43 5 未变
decode 否 是 [5,6,7,8,9] 38 → 43 5 未变

三点：

  • waiting 状态下取消不需要还块，因为块是在准入那一刻才分配的。 一个只处理"运行中取消"的实现，在这条路径上会静默地什么都不做——看起来是对的。
  • prefill 和 decode 归还的块数一样，因为 nanoserve 在准入时就按整段 prompt 分好了块表。 换成"边算边分"的实现，这两格就会不同。
  • 旁边那条请求的引用计数一格没动。这是最容易写错的地方： 取消时把别人共享的前缀块也释放掉，症状是另一条请求的 KV 被后来者覆盖， 输出变成乱码，而且只在有前缀复用时才出现。

三条路径跑完都做泄漏检查，全部 leaked: 0。

断连：引擎跑在客户端前面

在 HTTP 完整链路上执行断连测试（labs/L5/nanoserve/drive_server.py 的 C 场景）。 客户端读到第 5 个 token 就关掉 socket，服务端日志：

{"kind": "disconnect", "req": "C1", "aborted": true, "blocks_freed": 2, "sent_tokens": 18}
{"kind": "close", "req": "C1", "state": "aborted", "finish_reason": "client-disconnect", "free_blocks": 512}

客户端收到 5 个，服务端已经发出 18 个。 中间 13 个 token 是白算的： 引擎按自己的节奏推进，SSE 的写入先进内核缓冲区，客户端还没读到就走了。

这解释了为什么"断连要尽快传下去"是有价值的：晚一步，就多浪费一步的算力。 也解释了为什么不能靠 writer.drain() 单独发现断连—— 缓冲区没满时 drain() 立刻返回，什么都察觉不到。nanoserve 的做法是 同时挂一个 reader.read(1)，对端半关时它先醒：

# labs/L5/nanoserve/server.py
watcher = asyncio.create_task(reader.read(1))
...
done, _ = await asyncio.wait({get, watcher}, return_when=asyncio.FIRST_COMPLETED)
if watcher in done:
    get.cancel()
    raise ConnectionResetError("client closed")

断连之后 /health 报 free_blocks: 512，与启动时一致。

超时：队列里超时和运行中超时是两件事

给两条请求各挂一个 deadline，一条注定在队列里等到超时，一条在 decode 中途超时：

{"kind": "timeout", "req": "queued", "from_state": "waiting", "waited_ms": 53.48}
{"kind": "abort",   "req": "queued", "from_state": "waiting", "blocks_returned": 0, "free": 60}
{"kind": "timeout", "req": "slow",   "from_state": "decode",  "waited_ms": 254.57}
{"kind": "abort",   "req": "slow",   "from_state": "decode",  "blocks_returned": 5, "free": 64}

queued 一个 token 都没产出就被砍了，归还 0 块； slow 已经吐了 25 个 token，归还 5 块。

"超时"这个词在两种情况下含义完全不同：前者是"请求根本未开始处理"， 后者是"处理执行到一半发生中断或放弃"。对上游来说，第一种应当重试，第二种盲目重试大概率仍会超时。 只回一个 504 的 API 把这两件事混在了一起。

抢占：块不够时踢谁，丢什么

nanoserve 把块池压到 24 块（384 个 token 的 KV），塞 6 条各要 104 token 的请求， 显然装不下。开与不开抢占：

抢占开 抢占关（5.7 的行为）
结果 6 条全部完成 OutOfBlocks 崩在第 26 步
产出 token 384 150（然后崩）
step 数 128 26
墙钟 1.51 s 0.29 s
抢占次数 4 0
丢弃并重算的 KV token 279 0
结束后块池 leaked: 0 24 块全部卡死

代价是 279 / 384 = 73% 的重算。 这不是小数目： 为了不崩，系统多算了将近一倍的 token。

抢占的具体动作（labs/L5/nanoserve/failure.py）：

victim = max(victims, key=lambda r: r.arrival)   # 踢最新来的
self._free(victim)                                # 块全部归还
victim.num_computed = 0
victim.output_ids.clear()                         # 已生成的 token 一并丢弃
self.waiting.appendleft(victim)

如果抢占后仍允许新请求立即进入，资源不足可能反复发生： 刚腾出来的块在同一个 step 里被 _schedule() 的准入立刻吃掉， 下一步照样不够，最后还是崩了（preempted: 2 之后 crashed: 块池空了）。 因此，准入还需要检查剩余资源水位：

def _grow_block_table(self, req, upto):
    if req.state is State.WAITING:            # 只拦准入路径
        need = ceil(upto / block_size) - len(req.block_table)
        if self.pool.num_free - need < self._running_reserve():
            raise OutOfBlocks("watermark：要给正在跑的请求留块")
    super()._grow_block_table(req, upto)

「腾出资源」和「不让新请求立刻抢走」必须成对出现，否则前者是无效功。

背压：都慢，还是一部分被拒

24 条请求同时到达，max_num_seqs=4。等待队列设不设上限：

队列上限 接受 拒绝 接受者的 p50 延迟 最大延迟 step 数
不设 24 0 734.1 ms 1100.1 ms 96
12 12 12 366.1 ms 548.9 ms 48
4 4 20 183.0 ms 183.0 ms 16

延迟几乎与队列长度成正比（734 / 366 / 183 ms，比值 4 : 2 : 1）， 这是排队论最朴素的形态：队列只会把延迟往后推，不会让系统变快。

所以"不设上限"不是更友好，而是把拒绝换成了超时—— 排在第 24 位的用户等 1.1 秒，如果他的客户端设了 500 ms 超时， 他既没拿到结果，还占了引擎 1.1 秒的算力。显式拒绝至少是快的、可重试的、 不浪费算力的。

队列上限该设多少，取决于你能接受的 p99： 本章的负载下，队列 12 对应 p50 366 ms、最大 549 ms。

但一次性突发是一个不真实的到达过程（24 条同时到，之后系统空转）。 换成泊松到达再看一次（labs/L5/nanoserve/arrival_backpressure.py, results/crater/nanoserve/arrival-bp-20260913/）：先用并发 6、大块池量出容量基线 21.15 请求/秒，再按它的 0.3/0.6/0.9/1.1 倍生成指数间隔到达，每档各跑 max_waiting = 无上限 / 12 / 4：

三条结论：

  1. 欠载时队列上限完全不起作用。 0.3× 与 0.6× 两档的队列峰值只有 2–3， 三种上限的拒绝率都是 0：没有超额到达，准入规则没有可执行的机会。 只在 0.9× 以上，上限才把"排队变慢"换成"部分被拒"。
  2. 上限买的是被接收请求的尾延迟，不是吞吐。 1.1× 时吞吐在三种上限下 都是 391–400 tok/s（引擎本来就饱和），但等待 p50 从 549 ms 降到 147 ms、 p99 从 851 ms 降到 254 ms，代价是 20% 的请求被拒。这就是"延迟换拒绝率" 的定量形式：省下的延迟不在系统里，而在被拒的那部分请求身上。
  3. 上限 12 与无上限几乎一样。 1.1× 下上限 12 仍让队列排到 12、 p50 516 ms，只拒掉 6.7%；因为上限只是把队列封顶，超额的那部分 依然要等前面的做完。要真正压低尾延迟，上限必须显著小于过载时的排队长度 （本例 16 → 取 4）。

三条可以分开引用的现象：

  1. 无界队列的代价是线性的、可预测的。 等待 p50 随到达率单调上升 （320 → 665 → 914 → 1173 → 1410 ms），p99 到 2906 ms，而吞吐不变。 这就是"把延迟藏起来"的教科书形态，也是 8.2/8.4 要讲的排队论起点。
  2. 有界准入把过载换成拒绝，且把尾延迟钉住。 上限 4 时拒绝率从 13.3% 一路涨到 55.6%，但等待 p50 始终在 110–220 ms、p99 在 256–317 ms—— 拒绝率随过载线性上升，延迟几乎不动。上限 12 是中间形态（p99 钉在约 570–700 ms）。 选哪个上限，本质是"你愿意拒多少"而不是"你能扛多少"。
  3. 容量附近就会有拒绝。 0.9× 配上限 12 已经出现 1.1% 拒绝： Poisson 到达在短窗口里本来就会聚集，所以"平均到达率低于容量"不等于"不会过载"。 这也是为什么只报平均利用率而不报拒绝率是不够的。

泄漏：唯一一条不报错的失败路径

把 abort() 写错——请求从队列里摘掉了，块表清空了，但引用计数没减：

target.block_table = []            # 表清空了，引用计数没减

反复"接一条、跑三步、取消"，20 次：

第几条请求 0 … 15 16 17 18 19
取消后的空闲块（32 块池） 30 … 0 0 0 0 0
产出 token 3 … 3 0 0 0 0

每次取消漏 2 块，第 16 条把池子抽干。从第 16 条开始， 每条请求产出 0 个 token——而引擎没有抛任何异常。

原因是准入路径上的 OutOfBlocks 被 _schedule() 捕获了（那是设计如此： 块不够就先不收），于是请求永远停在 waiting，引擎每步都在空转。 日志干净，/health 也返回 200。

对照组（正确的 abort）：20 条全部产出 3 个 token，每次取消后空闲块都回到 32。

这就是为什么 nanoserve 每条路径结束都跑一次 leak_check()：

def leak_check(self):
    held = {b.block_id: b.ref_count for b in self.pool.blocks if b.ref_count}
    return {"held_blocks": held, "free": self.pool.num_free,
            "total": len(self.pool.blocks), "leaked": len(held)}

泄漏检查不是测试的装饰，它是这条失败路径唯一的探测器。

工程实现 · 源码解析：真实 vLLM 怎么做

固定版本 vLLM 0.29.0。把 KV 预算压到 gpu_memory_utilization=0.15 （实测 460 块 × 16 = 7360 个 token 的 KV），塞 48 条各生成 512 token 的请求， 需要的 KV 约 25 000 个 token —— 装不下三倍多。

A. 抢占：踢最新的，全部重算

v1/core/sched/scheduler.py:705，非优先级模式下就一行：

else:
    preempted_req = self.running.pop()

self.running 按加入顺序排，pop() 取最后一个——踢最新加入的。 nanoserve 的 max(victims, key=lambda r: r.arrival) 是同一个策略。

被抢占的请求做什么（scheduler.py:1405 的 _preempt_request）：

self._free_request_blocks(request)
self.encoder_cache_manager.free(request)
self._inflight_prefills.discard(request)
request.status = RequestStatus.PREEMPTED
request.num_computed_tokens = 0

num_computed_tokens = 0：已经算过的全部作废，重来。 和 nanoserve 一样，vLLM 选的是"丢弃重算"而不是"换出到 CPU"。

实测（把 _preempt_request 包一层数出来）：

含义很实际：线上服务被抢占打得半死时，日志里看不出来。 必须去看 metrics，或者像本章一样自己包一层。

B. 取消：块确实回来了

对一条正在跑的请求调 abort_request，前后读块池：

归还 2 块（该请求 prompt 约 20 个 token，占 2 块），未完成请求数 1 → 0。 调用链是 LLMEngine.abort_request（v1/engine/llm_engine.py:212）：

request_ids = self.output_processor.abort_requests(request_ids, internal)
self.engine_core.abort_requests(request_ids)

两处都要动：output_processor 管输出通道（对应 nanoserve 的 Stream）， engine_core 管调度器与块池。少动一处就是前面那两类 bug 之一。

C. 预算太小时的失败：连块都分不出来

第一次实验用 gpu_memory_utilization=0.12 直接起不来：

ValueError: No available memory for the cache blocks. Try increasing
`gpu_memory_utilization` when initializing the engine ...

v1/core/kv_cache_utils.py:859 的 _check_enough_kv_cache_memory。 0.12 × 31.4 GiB = 3.77 GiB，而权重加激活约 4.0 GiB，剩给 KV 的是负数。

这是唯一一条在启动时就报错的失败路径，因此也是最好处理的一条。 其余几条（抢占、泄漏、断连）全都在运行时静默发生。

设计取舍

1. 丢弃重算 vs 换出到 CPU

两家都选了丢弃重算。代价一目了然：本章实测 55%（vLLM）与 73%（nanoserve）的重算。 先把版本事实固定下来：vLLM 0.29.0 的 _preempt_request （vllm/v1/core/sched/scheduler.py:1405）在抢占时只做两件事——释放块、 把 request.num_computed_tokens 置 0（:1425），没有任何拷贝路径的状态。 本版本里唯一带 CPU 块的机制是 vllm/v1/simple_kv_offload/（SimpleCPUOffloadWorker， worker.py:26），那是显式开启的 KV offload 连接器，不在抢占路径上。 所以「换出」只能按计划在 nanoserve 上实现并测量。

引擎自带的 CPU 层在这套负载下没有被用上。 把 offload 连接器真正打开 （SimpleCPUOffloadConnector，cpu_bytes_to_use 从 0.25 GiB 扫到 4 GiB， lazy_offload False/True 各一遍），并加大压力到让 anchor 的前缀真的被挤掉 （120 条填充请求 × 800 token，GPU KV 占用一度到 91%）：

  1. 被挤掉这件事确实发生了：关掉 offload 时，被挤掉后的 anchor 是 22.15 ms， 而完全命中是 11.12 ms、首次调用是 62.56 ms——它既不等于"完全命中"也不等于"全部重算"， 是前缀被部分淘汰的结果。
  2. CPU 层查了 308 万次、命中 0 次（external_prefix_cache_queries=3,080,295、 external_prefix_cache_hits=0）。轻压力那一组是 22,487 次查询、同样 0 命中。 也就是说这个连接器在本机版本上从不返回命中，offload 是否开启对被挤掉后的 TTFT 没有可测影响（22.06 对 22.15 ms）。
  3. 代价是可测的：填充阶段墙钟 15.32 s → 19.45 s（+27%）。容量从 0.25 GiB 扫到 4 GiB 也没有任何趋势——因为这一层从来没有真正服务过请求。

所以本机可验收的结论是「这个版本的 CPU offload 层在这套负载下不命中，只增加开销」， 而不是「CPU offload 没有价值」；要区分这两者需要一个能确认写入路径生效的观测点 （连接器侧的 store/load 计数），当前版本没有暴露。

协议实现（labs/L5/nanoserve/swap.py）：换出时把该请求块表覆盖的槽位从 model.k_cache/v_cache gather 出来，拷进 pinned host 缓冲，然后释放块， 并保留 num_computed 与 output_ids；换入时重新分配块、把字节按新块号 scatter 回去、 恢复 num_computed，请求从 decode 直接续跑，不重算。

设计原则没有变：重算是"用算力换实现简单"。 换出把一个同步的状态机变成异步的—— 块池要区分"在 GPU"和"在 CPU"，恢复要等拷贝完成才能调度，调度器要处理"拷了一半"的 中间态，PD 分离时还要和 KV 传输抢 PCIe。上面的数字说明这笔交易在算力紧张、 拒绝率高时值得做，在抢占本来就罕见的服务里不值得。

实现过程中撞到的两个约束值得记下来，它们正是"异步化"的具体形态： 准入与换入必须共用同一道 watermark（否则换入会立刻把刚换出的空闲块吃光，形成抖动）， 而且 watermark 必须把被换入的这条请求自己也算进保留量， 否则它会在同一个 step 的 decode 扩容里把块用光。

1b. 真实引擎里的可用换出路径：SimpleCPUOffloadConnector

上面的换出是在 nanoserve 上按协议实现的。真实 vLLM 0.29.0 里确实有一条可用的 CPU 换出通道，但它不在抢占路径上：它是 v1/simple_kv_offload/ 这个 KV connector（SimpleCPUOffloadConnector，注册在 kv_transfer/kv_connector/factory.py:234），通过 --kv-transfer-config '{"kv_connector":"SimpleCPUOffloadConnector","kv_role":"kv_both", "kv_connector_extra_config":{"cpu_bytes_to_use":<bytes>,...}}' 打开， 并且要求 prefix caching 处于开启状态（源码里显式检查， simple_cpu_offload_connector.py:127）。

把它接到真实服务上问一个可判定的问题：GPU KV 被挤掉之后，再请求同一段前缀， 是从 CPU 换回来还是重算？ 实验（labs/L5/kv_offload_audit.py， results/crater/nanoserve/kv-offload-20260914/）把 GPU 的 KV 压到 9 232 token（--gpu-memory-utilization 0.16），然后按 「请求 anchor → 再请求一次（GPU 命中参照）→ 用填充分子把它挤掉 → 再请求 anchor」 重复三轮：

配置 anchor 首次（冷） anchor GPU 命中 被挤掉后再请求（3 轮 / 中位）
不开 offload 60.8 ms 10.98 ms 21.38 / 21.55 / 20.78 → 21.38 ms
开 offload（CPU 2 GB，1170 块） 60.4 ms 12.89 ms 18.71 / 19.24 / 17.14 → 18.71 ms

三条结论：

  1. 这条通道是真的，而且效果可测：被挤掉后再请求，TTFT 从 21.38 ms 降到 18.71 ms（−2.67 ms）。两种配置的三次样本区间不重叠 （不开 20.78–21.55，开 17.14–19.24），所以这个差不是抖动。
  2. 但它恢复不了"命中"的速度：完全命中是 11.0–12.9 ms， 换回只把"重算代价"（21.38 − 10.98 ≈ 10.4 ms）里的 约 26% 拿了回来， 其余仍在重算或耗在换回路径上。不要把"开了 offload"说成"等于命中"。
  3. 它不是抢占路径：抢占（scheduler.py:1405）依然只重算； CPU 换出是独立于抢占的一层缓存，靠 prefix cache 的淘汰触发， 所以它救的是"被淘汰后再次命中同一前缀"，不是"被抢占的请求"。

这正好补上架构设计中"可用换出路径"的定义：nanoserve 中按协议规范实现了显存换出， 真实引擎里有一条现成的替代路线，两者解决的是不同触发条件下的同一件事。

2. 有界队列以拒绝率换取延迟约束

背压那张表说明了一件反直觉的事：不设队列上限并不更友好。 24 条请求下，不设上限的 p50 是 734 ms、最大 1100 ms； 上限 12 时是 366 / 549 ms。多出来的那 12 条并没有"被服务"， 它们只是在队列里把所有人的延迟推高了一倍。

如果客户端有超时（真实系统总是有的），排在后面的请求最终既拿不到结果、 又已经消耗了引擎的资源——这是最糟的一种结局。显式拒绝可避免继续消耗模型计算，但入口处理、重试和负载恢复仍有成本。

泊松到达下的复测把这句话量化了：1.1× 容量时，无上限让 p99 等到 851 ms， 上限 4 把它压到 254 ms，代价是 20% 拒绝率，吞吐几乎不变（400 → 391 tok/s）。

这条判断在 8.2/8.4 会再出现：任何没有上限的队列都是一个把延迟藏起来的地方。

3. 资源不变量需要可执行的断言与告警

本章五条路径里，四条会以某种方式暴露自己：崩溃、超时、拒绝、日志。 只有泄漏不会。它的症状是"引擎慢慢停止接客"， 而且从症状到原因之间隔着任意长的时间。

nanoserve 在块池中统一保存引用计数（5.7 §2），由 leak_check() 检查请求结束后是否仍有占用。 代价是每条测试路径末尾都得记得调它——本章和 5.7 一共 14 处。

反过来说，如果块的归属信息分散在请求对象、调度器和池子三处， 这个断言就写不出来，泄漏也就无从检测。 集中管理状态后，资源回收条件更容易检查。

4. 抢占与准入必须成对

抢占之后还需要限制新请求进入，否则 腾出来的资源会被立刻消耗掉，抢占退化成纯粹的浪费（丢了 128 个 token 的 KV， 系统照样崩）。

vLLM 用 watermark 做同一件事。这条规律在别处也成立： 任何"回收资源"的机制都要配一个"暂缓分配"的机制， 否则回收只是给新的分配让路。

  2 """L5.8：在 5.7 的 nanoserve 上补四条失败路径。
  3 
  4 5.7 的 `Engine` 只处理正常结束和显式取消，块池耗尽时直接抛 `OutOfBlocks`。
  5 这里用子类补上：
  6 
  7   抢占  —— 块不够时踢掉最新的请求，把块还回去，它稍后重算

 35 class ResilientEngine(Engine):
 36     def __init__(self, *args, max_waiting: int | None = None,
 37                  leak_on_abort: bool = False, **kw):
 38         super().__init__(*args, **kw)
 39         self.max_waiting = max_waiting
 40         self.leak_on_abort = leak_on_abort
 41         self.stats = FailureStats()

 43     # ------------------------------------------------------------ 背压
 44     def try_add(self, req: Request) -> bool:
 45         """队列满就拒绝。返回 False 时上层应该回 503，而不是让请求干等。"""
 46         if self.max_waiting is not None and len(self.waiting) >= self.max_waiting:
 47             self.stats.rejected += 1
 48             req.state, req.finish_reason = State.ABORTED, "queue-full"
 49             req.finished_at = time.perf_counter()
 50             self.done[req.req_id] = req
 51             self.stats.log("reject", req=req.req_id, waiting=len(self.waiting),
 52                            limit=self.max_waiting)
 53             return False
 54         self.add(req)
 55         return True

 57     # ------------------------------------------------------------ 取消
 58     def abort(self, req_id: str, reason: str = "aborted") -> bool:
 59         """加一层统计；leak_on_abort 打开时故意不还块（用来验泄漏检查）。"""
 60         where = None
 61         for r in self.waiting:
 62             if r.req_id == req_id:
 63                 where = r.state.value
 64                 break
 65         if where is None:
 66             for r in self.running:
 67                 if r.req_id == req_id:
 68                     where = r.state.value
 69                     break
 70         if where is None:
 71             return False
 72         held = 0
 73         if self.leak_on_abort:
 74             target = next((r for r in list(self.waiting) + self.running
 75                            if r.req_id == req_id), None)
 76             held = len(target.block_table)
 77             # 只把请求摘出去，块留在原地：这是最常见的一种泄漏写法。
 78             if target in self.waiting:
 79                 self.waiting.remove(target)
 80             else:
 81                 self.running.remove(target)
 82             target.state, target.finish_reason = State.ABORTED, reason
 83             target.finished_at = time.perf_counter()
 84             target.block_table = []            # 表清空了，引用计数没减
 85             self.done[req_id] = target
 86             ok = True
 87         else:
 88             free_before = self.pool.num_free
 89             ok = super().abort(req_id, reason)
 90             held = self.pool.num_free - free_before
 91         self.stats.aborted += 1
 92         self.stats.log("abort", req=req_id, from_state=where, reason=reason,
 93                        blocks_returned=held, free=self.pool.num_free,
 94                        leak_mode=self.leak_on_abort)
 95         return ok

 97     # ------------------------------------------------------------ 超时
 98     def check_deadlines(self, now: float | None = None) -> list[str]:
 99         now = now or time.perf_counter()
100         hit = []
101         for r in list(self.waiting) + list(self.running):
102             deadline = getattr(r, "deadline", None)
103             if deadline is not None and now > deadline:
104                 state = r.state.value
105                 self.abort(r.req_id, "timeout")
106                 self.stats.timed_out += 1
107                 self.stats.log("timeout", req=r.req_id, from_state=state,
108                                waited_ms=round((now - r.arrival) * 1000, 2))
109                 hit.append(r.req_id)
110         return hit

112     # ------------------------------------------------------------ 抢占
113     def _preempt_one(self) -> str | None:
114         """踢掉最新加入的运行请求：它已经算的最少，重算最便宜。"""
115         victims = [r for r in self.running if r.state is State.DECODE] or self.running
116         if not victims:
117             return None
118         victim = max(victims, key=lambda r: r.arrival)
119         wasted = victim.kv_len
120         blocks = len(victim.block_table)
121         self._free(victim)
122         self.running.remove(victim)
123         victim.state = State.WAITING
124         victim.num_computed = 0
125         victim.output_ids.clear()          # 重算：已生成的 token 一并丢弃
126         victim.cached_prefix_blocks = 0
127         self.waiting.appendleft(victim)
128         self.stats.preempted += 1
129         self.stats.recomputed_tokens += wasted
130         self.stats.log("preempt", req=victim.req_id, freed_blocks=blocks,
131                        discarded_kv_tokens=wasted, free=self.pool.num_free)
132         return victim.req_id
133 
134     def _running_reserve(self) -> int:
135         """正在 decode 的请求，下一步每条最多再要一块。这些块必须留住。"""
136         return sum(1 for r in self.running if r.state is State.DECODE)
137 
138     def _decode_blocks_needed(self) -> int:
139         """这一步真正会跨进新一块的 decode 请求数。"""
140         return sum(1 for r in self.running if r.state is State.DECODE
141                    and r.kv_len % self.block_size == 0)
142 
143     def _grow_block_table(self, req: Request, upto: int) -> None:
144         """准入路径上加一道 watermark：不能把正在跑的请求要用的块分光。
145 
146         没有这道闸，抢占会变成空转：刚腾出来的块在同一个 step 里
147         被 `_schedule()` 的准入立刻吃掉，下一步照样不够。
148         vLLM 的 watermark 解决的是同一个问题。
149         """
150         if req.state is State.WAITING:
151             need = ((upto + self.block_size - 1) // self.block_size
152                     - len(req.block_table))
153             if self.pool.num_free - need < self._running_reserve():
154                 self.stats.log("admission_blocked", req=req.req_id, need=need,
155                                free=self.pool.num_free,
156                                reserve=self._running_reserve())
157                 raise OutOfBlocks("watermark：要给正在跑的请求留块")
158         super()._grow_block_table(req, upto)
159 
160     def step(self) -> StepTrace:
161         """先确认这一步的块够用，不够就抢占——检查发生在任何前向之前。
162 
163         5.7 的 step 把「长块表」放在前向前面，所以 OutOfBlocks 会在
164         prefill 已经算完之后才抛出来，状态半新半旧。放到这里检查，
165         抢占就永远发生在一个干净的边界上。
166         """
167         while self._decode_blocks_needed() > self.pool.num_free:
168             if self._preempt_one() is None:
169                 break
170         try:
171             return super().step()
172         except OutOfBlocks:
173             self.stats.log("out_of_blocks", free=self.pool.num_free,
174                            running=len(self.running), waiting=len(self.waiting))
175             raise

前沿

  • 抢占之外的第三条路：把 KV 存到别处。 8.6 会讲 KV 分层存储 （GPU → CPU → 远端）。抢占时不丢也不换出，而是降级到更慢的一层。 代价是恢复时的延迟不确定。
  • 优先级调度。 vLLM 已经有 SchedulingPolicy.PRIORITY （scheduler.py:670），抢占时按 (priority, arrival_time) 选受害者。 一旦引入优先级，"谁被牺牲"就成了产品决策而不是工程决策（8.8 租户隔离）。
  • 把断连传得更快。 现在的链条是 socket → 协程 → engine.abort。 在多进程引擎里这还要跨一次进程边界。本章实测断连时已经浪费了 13 个 token， 额外通信可能增加取消延迟，但需测量，不能直接按跳数推算多生成的 token 数。
  • （已做）崩溃恢复。 见下面的「worker 崩溃」一节：四种策略都实测了。 结论是现状会静默挂起，而独立进程重启是唯一无条件可用的恢复方式； 同进程重启循环在本实验的崩溃点上可用，但那只说明注入的异常没有破坏不变量。

worker 崩溃：四种策略的实际结果

本章此前没有覆盖 worker 崩溃。补这一条要先看清对象： nanoserve 的 server.py 把引擎放在同一个事件循环里，没有独立 worker 进程； 而 engine_loop 里那行 trace = self.engine.step() 没有任何 try/except：

async def engine_loop(self):
    while True:
        if not self.engine.waiting and not self.engine.running:
            await asyncio.sleep(self.idle_sleep); continue
        trace = self.engine.step()      # 抛异常 → 这个任务带着未处理异常结束
        ...

所以"引擎崩了会怎样"必须实测。实验（labs/L5/nanoserve/crash_recovery.py， results/crater/nanoserve/crash-rec-20260914/）注入一次确定性异常，跑四种策略， 每种都发同一条流式请求（24 token 上限）：

三条要写进结论：

  1. 现状的失败形态是"静默挂起"，不是报错。 循环任务死后 HTTP 仍在 accept： 在飞请求停在 11 个 token 上，既不报错也不关门，客户端只能靠超时发现； 之后每一个新请求都是同样的 0 事件 + 挂起。这正是 5.8 反复强调的那条—— "连接断开"与"资源回收"是两件事，反过来"连接没断"也不代表服务还活着。
  2. "泄漏 0"在这里不是好消息。 四种策略的泄漏块都是 0，但原因是客户端超时后 自行断开、服务端的 reader 协程随即 engine.abort()（日志里能看到 disconnect → aborted → blocks_freed）。所以泄漏 0 不能当作"崩溃被处理了"的证据， 它只说明断开路径还在工作。这正是计划里那条反例： 捕获异常不代表恢复。
  3. 可无条件推荐的只有独立进程重启（D）：重启前后都是 25 事件 + EOF （2.46 s → 2.29 s），新进程的状态一定干净。 同进程重启循环（C/C2）在本实验里也能恢复（第三个请求正常完成）， 但这是一个有条件的结论：注入点虽然在 _run() 内部（块已分配、块表已扩）， 却没有半写的关键状态——num_computed 只在 _run() 成功返回后才更新， KV 写入也是按槽位逐层完成的。若崩溃发生在写 KV 的中途， 这个结论需要重测，那才是"半写状态"真正的风险点。

那就把崩溃点挪进写路径重测一次。 五种注入点各跑一遍，每种都做三件事： 崩溃后继续跑同一个引擎（受害者仍在 running 里，看半写状态会不会被沿用）、 把残留请求 abort 掉（看块池能不能清干净）、再发一条同样的请求（看能否继续服务）。 参照是同一引擎上一次干净运行的输出（labs/L5/nanoserve/crash_points.py， results/crater/nanoserve/crash-points-20260914/）：

四条结论：

  1. KV 写入中途的崩溃不构成静默错误（P1）。 续跑之后受害者的 16 个 token 与干净参照逐 token 相同。原因是 step() 里所有状态更新都在 _run() 成功 返回之后，重跑这一步会把每一层的 KV 重写一遍——写入是幂等的。 上一轮标为"需要重测"的那条，现在有了答案。
  2. P2 的"不一致"是注入代码自己写坏的，不是引擎的问题。 那个注入点为了 制造"token 已记录"的状态，先手动 output_ids.append(0) 再抛异常； 多出来的这个假 token 当然会让结果与参照不同。这一格不能当证据引用， 它只说明"注入本身改了状态"这件事要写清。
  3. _free 之内崩溃是唯一清不掉的（P3）。 注入把第一个块还掉后抛异常， req.block_table 没被清空；之后再 abort 也无从知道哪些块已经还过， 于是泄漏 2 块。这与本章主线一致：释放路径上的崩溃只能靠重建恢复， 重跑不但修不好，还会让账更乱。
  4. 只要把残留请求 abort 掉，后续请求都能正常服务（五格全部"是"）， 所以"引擎还能不能干活"与"引擎的账对不对"是两件事—— 这与前面 worker 崩溃那节的结论同向。

顺带一条与 5.7 的对照：vLLM 把引擎放在独立进程（EngineCore）， HTTP 与引擎的生死是分开的——这本身就是"崩溃恢复"的第一层设计： 进程边界让"重启"成为一个可用的动作。

陷阱

  1. 泄漏不报错。 本章实测：每次取消漏 2 块，第 16 条请求开始产出 0 token， 引擎不崩、日志干净、/health 返回 200。只有块池断言能发现。
  2. "取消"在三种状态下清理的东西不同。 只处理"运行中取消"的实现， 在 waiting 状态下静默无操作，看起来是对的。
  3. 取消要同时动输出通道和块池。 vLLM 的 abort_request 两处都动 （llm_engine.py:212），少一处就是泄漏或者悬挂的连接。
  4. 不能靠 drain() 发现断连。 缓冲区没满时它立刻返回。要另挂一个读任务。
  5. 抢占必须配准入闸。 只抢占不拦准入，腾出来的块会被同一步的准入吃掉， 该错误配置丢弃了 128 个 token 的 KV 后，仍因块不足而失败。
  6. 抢占的代价是重算，而且不小。 实测 vLLM 55%、nanoserve 73%。
  7. vLLM 不打抢占日志，只进 metrics。线上要自己观测。
  8. 无上限的队列不是更友好，它把拒绝换成了超时，而且浪费算力。
  9. 两种超时含义不同：队列里超时（从未被服务，可重试）vs 运行中超时 （服务到一半放弃，重试大概率还超时）。只回 504 把两者混为一谈。
  10. gpu_memory_utilization 太小时是启动期报错，反而是最好处理的失败。

自测题

1. 客户端断连后，那条请求的 KV 块什么时候被释放？怎么证明？

链条包含五步（本章实测验证）：

  1. 客户端关 socket → 服务端挂着的 reader.read(1) 返回 EOF；
  2. HTTP 协程抛 ConnectionResetError；
  3. except 里调 engine.abort(rid, "client-disconnect")；
  4. abort 把请求从运行集摘掉，遍历它的 block_table 逐块 release()，引用计数归零的块回到空闲链；
  5. finally 里清掉输出通道的 Stream。

块是在第 4 步释放的，实测这条请求归还 2 块，之后 /health 报 free_blocks: 512，与启动时一致。

请求结束后，使用断言检查块池是否回到初始状态： leak_check() 要求结束后没有任何 ref_count > 0。 本章和 5.7 一共 14 处这样的断言。

顺带一个实测细节：客户端只收到 5 个 token，服务端已经发出 18 个—— 中间 13 个的算力白花了。断连传得越快，浪费越少。

2. 队列积压时靠什么反压？不反压会怎样？

靠给等待队列设上限，满了就直接拒绝（HTTP 503），而不是让请求排着。

本章实测，24 条请求同时到达、max_num_seqs=4：

队列上限 接受 / 拒绝 p50 最大
不设 24 / 0 734 ms 1100 ms
12 12 / 12 366 ms 549 ms
4 4 / 20 183 ms 183 ms

延迟几乎与队列长度成正比（4 : 2 : 1）。队列只会把延迟往后推，不会让系统变快。

缺乏背压机制的后果并非仅是全局延迟均匀增大，而是：客户端超时触发后，排在队尾的请求 既拿不到有效结果，又已空耗了引擎核心算力。显式拒绝可减少无效计算；重试仍需退避、期限和次数限制，避免进一步放大过载。

队列上限设定取决于目标 p99 延迟预算：在本章测试负载下，队列深度设为 12 对应最大 549 ms 延迟。

3. 块池不够用时会发生什么？为什么"只抢占"不够？

不处理就是 OutOfBlocks 崩掉：本章实测在第 26 步崩，24 块全部卡死，0 条请求完成。

处理方式是抢占：踢掉最新加入的请求，把它的块全部归还， num_computed = 0、已生成的 token 一并丢弃，放回队列重算。 vLLM 做的是同一件事（scheduler.py:705 的 self.running.pop() + _preempt_request 里的 num_computed_tokens = 0）。

只抢占不够，因为腾出来的块会在同一个 step 里被 _schedule() 的准入吃掉—— 该错误配置中抢占了 2 次、丢弃了 128 个 token 的 KV，最终仍然失败。 必须再加一道 watermark：准入时要留够正在跑的请求下一步要用的块。

代价是重算：nanoserve 实测 279 / 384 = 73%，真实 vLLM 实测 13437 / 24576 = 55%。

4. 为什么两家引擎都选"丢弃重算"而不是"换出到 CPU"？

现在有实测可以回答：在同一份轨迹上换出确实更快（1.196 s 对 1.523 s， p99 1196 ms 对 1523 ms），而且保住了逐 token 的输出；重算那组有一条请求在第 18 个 token 上分叉了。所以"更划算"这半句成立，代价也量得出来：换出要多搬 51.38 MB， 稳态拷贝约 1.4 ms（首轮还要多付一次约 6 ms 的 pinned 分配）。

_preempt_request（scheduler.py:1405）现在只做两件事（释放块、 num_computed_tokens = 0），是一个同步操作；换出会引入块池的 "在 GPU / 在 CPU"两态、恢复要等拷贝、调度器要处理"拷了一半"的中间态， PD 分离时还要和 KV 传输抢 PCIe。换出把一个同步的状态机变成了异步的， 而抢占本来是异常路径。实测里那两个必须共用的 watermark 约束就是这份复杂度的具体形态。

结论是分场景的：算力紧张、拒绝率高时换出值得；抢占罕见时， "用算力换实现简单"仍然是更好的交易。

5. 一个引擎跑了几小时之后开始拒绝所有新请求，日志干净，没有报错。先查什么？

先查块池的引用计数，而不是查日志。

本章复现过这个症状：把 abort() 写错一行（请求摘掉了、块表清空了， 但引用计数没减），每次取消漏 2 块。32 块的池子在第 16 条请求上被抽干， 之后每条请求产出 0 个 token，引擎没有抛任何异常—— 因为准入路径上的 OutOfBlocks 被调度器捕获了（设计如此：块不够就先不收）， 请求永远停在 waiting，引擎每步空转。

诊断方法就是本章的 leak_check()：

held = {b.block_id: b.ref_count for b in self.pool.blocks if b.ref_count}

结束（或空闲）时不应该有任何 ref_count > 0。如果有，看看它们属于谁—— 本章的泄漏模式下，32 块全部 ref_count = 1，而 running 和 waiting 都是空的。 "没有请求在跑，却没有空闲块"就是泄漏的签名。

一般化：把这个断言做成周期性的监控，就是从"事后排查几小时"变成"几分钟内告警"。
