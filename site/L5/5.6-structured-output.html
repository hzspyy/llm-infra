5.6

结构化输出与约束解码

XGrammar / llguidance / outlines_core 三库逐位对照、FSM 与下推自动机、structural tag 与 function calling、tool-call 流式解析；并置 vLLM 与 SGLang 的约束解码路径。

实测机器 crater (RTX 5090 D, sm_120) · vLLM 0.29.0 · SGLang 0.5.19 · Qwen3-1.7B数据日期 2026-09-11前置 0.5（采样）· 5.3（调度器每步做什么）· 5.4（执行层）

本章回答三个问题

约束解码（constrained decoding）是指在采样之前把不合法的 token 的 logit 设成 −∞， 让模型只能在语法允许的 token 里选。它保证的是输出形状，不是输出内容。

  1. 一个 JSON schema 怎样变成每一步的一张 bitmask？这张 mask 长什么样，能打印出来吗？
  2. xgrammar、llguidance、outlines_core 给的是同一个保证吗？不是的话，差在哪里？
  3. 这个保证要花多少钱？钱花在哪个环节？

本章的所有结论都建立在同一份材料上：同一个 tokenizer、同两份 schema、同一条目标轨迹， 三个库逐步导出的 bitmask 逐位比较。三个库在同一份 schema 下给出的合法集合并不相同， 差异可以逐个 token 解释；其中一处差异是真正的语义漏洞，另外几处只是空白与分词策略。

心智模型：语法是一个只管形状的过滤器

机制拆解

为什么需要它：不加约束时输出格式取决于 prompt，不取决于模型

同一个模型、同一条抽取任务，两次实验：

运行 prompt 形式 采样 json.loads 成功
results/crater/structured/20260911-0250/previous_ace.txt 裸补全 "…\nJSON: " temperature=0.8, top_p=0.95 0 / 64
results/crater/structured/20260911-0250/completed/none/summary.json chat template + "Return only a JSON object… No explanation." temperature=0 24 / 24

失败样例逐字取自第一次运行的日志：

[parse-fail] '{"name": "Zhang", "city": "Shenzhen", "age": 31}\n```json\n{"name": "Zhang", "city": "Shenzhen", "age": 31}\n``` '
[parse-fail] '{"name": "Zhang", "city": "Shenzhen", "age": "31"}\n```json\n{"name": "Zhang", "city": "Shenzhen", "age": "31"}\n'
[parse-fail] '{"name": "Zhang", "city": "Shenzhen", "age": 31}\nYes, that\'s correct.\n\nThe text mentions the person\'s name, ci'

三条里 JSON 本身都是对的，毁在后面多出来的解释和围栏。

这两行数字放在一起才说明问题："不加约束时合法率多少"不是模型的属性， 换 prompt 和采样参数可以从 0% 变成 100%。所以约束解码要解决的不是"平均合法率低"， 而是没有下界——你无法对第 10001 条请求给出承诺。下面所有开销都是在买这个下界。

schema → 语法 → 每一步的 bitmask

链条有三段，三个库在每一段的做法都不同：

  1. schema → 语法制品。 编译期，一次。产物是 EBNF（xgrammar）、lark JSON（llguidance）或正则（outlines_core）。
  2. 语法 → 当前状态的合法 token 集合。 每步一次，在 CPU 上，结果写进 bitmask。
  3. bitmask → logits。 每步一次，在 GPU 上，一个 elementwise kernel 把非法位置写成 −∞。

第三段三家一样（SGLang 直接 vendor 了 xgrammar 的 Triton kernel， srt/constrained/bitmask_ops.py:13）。区别全在前两段，而成本也全在前两段。

第 3 段的实测：mask 的确切效果

把捕获的 mask 喂给真实 logits，逐位检查（labs/L5/mask_apply_probe.py， 原始输出 results/crater/structured/grammar-apply-20260910-1916/apply.log）：

输入 mask allowed 置 −∞ 合法位 logit 是否被改 argmax 落点
xgrammar tight 第 12 步 12 151924 否 77767
xgrammar loose 第 3 步 147145 4791 否 151668
outlines_core tight 第 13 步 13 151923 否 481

三点可检查的事实：

  • mask 是跨库通用的字节格式。 第三行的 mask 由 outlines_core 写出， 却能直接喂进 xgrammar 的 kernel——因为它们约定的都是「小端 int32 数组，第 t 位对应 token t」。
  • 合法位的 logit 一个字节都没动（legal_logits_unchanged）。约束解码不是重打分，是删除选项。
  • argmax 一定落在合法集合内。这里 logits 是人造的 arange，所以 argmax 落在最大的合法 id 上。

bitmask 的尺寸账

每请求每步=⌈15193632⌉×4 B=4748×4=18992 B

max_num_seqs=32 时，vLLM 一次性分配 32×18992=608 KB （v1/structured_output/__init__.py:240，开投机时还要乘 1+k）。 这点显存可以忽略，但每步都要 H2D 拷一遍，而且填它的是 CPU。 下面会看到，贵的从来不是这 18 KB。

工程实现 · 源码走读

A. vLLM：backend 是可换的，contract 是 StructuredOutputGrammar

v1/structured_output/backend_types.py 定义了后端必须实现的五个方法： accept_tokens / validate_tokens / rollback / fill_bitmask / is_terminated。 三个后端各自适配一个第三方库。

调度器每步做两件事：先让语法吃掉上一步产出的 token，再填 mask。 吃 token 的那一步没有容错：

# v1/core/sched/scheduler.py:1991
if advance_token_ids and not grammar.accept_tokens(
    req_id, advance_token_ids
):
    logger.error(
        "Unexpected: grammar rejected tokens %s for request %s. "
        "Terminating request.",
        advance_token_ids,
        req_id,
    )
    request.status = RequestStatus.FINISHED_ERROR
    request.resumable = False
    stopped = True

语法拒绝一个自己刚刚允许过的 token，被当作不可恢复的内部错误。 这个分支本该走不到——mask 里没有的 token 采样不会选中。但本章测到它会走到（见下）。

填 mask 的路径：

# v1/structured_output/__init__.py:62
self.fill_bitmask_parallel_threshold = 128

只有同时排队的结构化请求超过 128 条才会用线程池并行填。 低于这个数（本章实验 max_num_seqs=32，线程池根本没创建）， 填 mask 完全串行地跑在调度器循环里——它在关键路径上。

B. SGLang：编译结果缓存 + 每请求 copy()

SGLang 把「编译好的语法」和「请求的游标」分开：

# srt/constrained/base_grammar_backend.py:207
self.cache: Dict[Tuple[str, str], BaseGrammarObject] = {}

命中缓存后不是共用同一个对象，而是 copy() 出一个全新的 matcher：

# srt/constrained/xgrammar_backend.py:145
def copy(self):
    matcher = GrammarMatcher(
        self.ctx,
        max_rollback_tokens=MAX_ROLLBACK_TOKENS,
        override_stop_tokens=self.override_stop_tokens,
    )

self.ctx 是编译产物（不可变、可共享），matcher 是可变游标（每请求一份）。 这条边界本章实测过：grammar_adapter_probe.py 里对一个已经吃完整条轨迹、 已经终止的 grammar 调 copy()，新对象的 mask 里 EOS 位是 0—— 说明拷贝出来的是一条全新请求，不是当前状态的快照 （results/crater/structured/20260911-0250/completed/sglang-adapter.log： copy_is_fresh_request: true）。

C. jump-forward：语法已经定死的部分不必让模型生成

SGLang 多一条 vLLM 没有的路径（srt/constrained/xgrammar_backend.py:164）：

def try_jump_forward(self, tokenizer) -> Optional[Tuple[List[int], str]]:
    s = self.matcher.find_jump_forward_string()

如果从当前状态出发只有唯一一条字节路径，就直接把那段文本写进输出， 跳过若干次前向，然后 jump_and_retokenize 重新对齐 token 边界。

本章沿目标轨迹逐步问 xgrammar「此刻被强制的续写是什么」 （labs/L5/grammar_jump_forward.py，原始输出 results/crater/structured/grammar-jump-20260910-1915/run.log）：

前缀 被强制的续写 字符数
`` { 1
{" name" 5
{"name " 1
{"name":" （无） 0
{"name":"Zhang", " city" 5
{"name":"Zhang","city " 1
…"Shenzhen", " age" 4

整条 43 字符的输出里，18 个字符（42%）是语法强制的， 分布完全对应 JSON 的骨架：花括号、键名、引号、冒号。真正需要模型决定的只有三个值。

18 这个数不是加速比

它是「沿这条已经采样出来的轨迹，逐步询问 find_jump_forward_string() 得到的字符数之和」。 真跳的时候后续状态会变，可跳的字符数也会变；而且省下的前向次数取决于这些字符 被重新分词成几个 token。本章没有测 jump-forward 打开后的端到端时间， crater 上的 SGLang 环境本轮没有起服务。这是本章最值得补的实验。

D. function calling：structural tag 把约束限制在一段区间里

真实的 tool call 不是「整条回复都是 JSON」，而是「散文里嵌一段严格 JSON」：

Let me check the weather. <tool_call>{"name":"get_weather","arguments":{"city":"Shenzhen"}}</tool_call>

xgrammar 为此提供了一个语法构造 TagDispatch。把上面这段声明成 StructuralTagItem(begin="<tool_call>", schema=…, end="</tool_call>")， 编译出来的 EBNF 顶层是：

triggered_tags_group ::= (("" root_0 "</tool_call>"))
triggered_tags ::= TagDispatch(
  ("<tool_call>", triggered_tags_group),
  loop_after_dispatch=true,
  excludes=()
)
root ::= ((triggered_tags))

语义：先允许任何输出，直到看见 trigger，才切到对应的语法； 看到 end 之后回到自由模式（loop_after_dispatch=true 表示可以再次触发， 所以一次回复里可以有多个 tool call）。

沿这条 22 token 的轨迹逐步量合法数（labs/L5/structural_tag_probe.py， 原始输出 results/crater/structured/structural-tag-20260910-1930/run.log）：

步 token 区域 合法 token 数
0–6 Let ␣me ␣check ␣the ␣weather . ␣ 外 151669
7 <tool_call> (id 151657) 外 151669
8 {" 内 7
11 get 内 3
16 city 内 4
18 Sh 内 6
21 </tool_call> (id 151658) 内 3

外面 8 步全部是 151669——正好等于 len(tokenizer)，即完全不约束； 进入标签后掉到 3–14。</tool_call> 之后 is_terminated() 仍是 False， 模型可以继续写。约束的开关就是这两个 token。

对 Qwen3 来说 <tool_call> / </tool_call> 各是词表里的一个特殊 token （151657 / 151658），所以 trigger 不可能被切碎到跨 token—— 这是模型侧的设计，不是引擎给的保证。换一个用普通文本当分隔符的模型， trigger 的字节可能落在不同 token 里，TagDispatch 必须在字节层面匹配。

E. tool call 的格式由模型决定，所以引擎里堆着几十个 parser

语法只保证形状，把形状还原成 OpenAI 的 tool_calls 结构是另一件事， 而每个模型家族的格式都不一样。两家引擎为此各带一大堆解析器（固定版本下实测文件数）：

引擎 目录 文件数
vLLM 0.29.0 vllm/tool_parsers/ 51
SGLang 0.5.19 sglang/srt/function_call/*detector*.py 33

流式接口是难点。ToolParser.extract_tool_calls_streaming （vllm/tool_parsers/abstract_tool_parser.py:201）拿到的是 「累计文本 + 这一步的增量」，要吐出「这一步该发给客户端的 delta」。 Hermes 的实现是每次重新解析整段 current_text，再和已发送的部分做差：

# vllm/tool_parsers/hermes_tool_parser.py:192
def _compute_args_diff(
    self, index: int, tc_json: str, is_complete: bool
) -> str | None:
    """Return new argument text not yet sent for tool `index`, or None."""
    args = self._extract_tool_args(tc_json, is_complete)
    if args is None or len(args) <= len(self.streamed_args_for_tool[index]):
        return None
    diff = args[len(self.streamed_args_for_tool[index]) :]
    self.streamed_args_for_tool[index] = args

这条路径每个 token 都要重扫一遍全文，长度上是二次的。 这是读代码得出的复杂度，本章没有测它在长 tool call 上的实际耗时。

设计取舍

1. 三个库把成本放在不同的地方，而且差三个数量级

同一 tokenizer、同两份 schema，直接调库测（labs/L5/grammar_libs_compare.py， 报告 results/crater/structured/grammar-libs-20260910-1907/report.json）：

库 词表预处理 编译（冷） 编译（热） 填 mask 中位数 推进 matcher（整条轨迹）
xgrammar 0.2.6 215.3 ms 7.63 / 2.36 ms 0.004 ms 0.94 / 0.67 µs 8.2 / 7.6 µs
llguidance 1.7.6 624.6 ms 0.20 / 0.009 ms 0.005 ms 8.55 / 10.29 µs 16.2 / 14.1 µs
outlines_core 0.2.14 684.5 ms 171.7 / 198.5 ms 154.5 / 176.5 ms 1.85 / 1.31 µs 6183 / 195 µs

两个数字用 loose / tight 表示。三家的语法制品分别是 EBNF（1638 / 1937 字符）、 lark JSON（301 / 398）和正则（179 / 145）——原文见「原始现场」。三处必须说明的口径：

  • xgrammar 的"热"是 GrammarCompiler 内部缓存命中，不是重新编译。
  • llguidance 的"编译"只做了 schema → lark JSON 的序列化，看制品就知道—— 它基本就是把 schema 原样包了一层。真正的自动机是懒构造的，成本因此落在填 mask 那一列。
  • outlines_core 的编译每次都真的重建 DFA index，本章的探针没有走 vLLM 的 get_outlines_cache()。所以 154–176 ms 是每个新 schema 的首次成本，不是每请求成本。

结论不是"某个库快"，而是三个库在同一条曲线上选了不同的点： 预编译得越彻底，运行期越便宜。outlines_core 把全部工作压进编译期， 换来 1.3 µs 的 mask 填充；llguidance 几乎不预编译，运行期就要现算。

2. 同一份 schema，三个库的合法集合不一样

沿同一条目标轨迹逐步比较 mask（legal_count，已排除词表 padding 位）：

步 目标 token loose: xgrammar llguidance outlines_core
0 {" 7 7 2
1 name 4 1 4

差异逐个可解释（labs/L5/grammar_mask_diff.py 把 mask 解码回 token 文本， 原始输出 results/crater/structured/grammar-libs-20260910-1907/mask_diff_loose.txt）：

  • 第 0 步、第 2 步、第 13 步：空白策略。 xgrammar 与 llguidance 多出来的 正是 '{\n'、'{\r\n'、'":\n'、421 个纯空白 token；outlines_core 的正则里 只写了 [ ]?（一个可选空格）。三家生成的都是合法 JSON，宽松程度不同。
  • 第 1 步：分词规范化。 xgrammar / outlines_core 允许 'n'、'na'、'nam'、'name' 四种切法，llguidance 只允许 'name'——它强制规范（最长匹配）分词。 同一个字符串，允许的 token 序列集合不同。
  • 第 16 步：停止 token 的来源。 xgrammar 多的那一位是 <|endoftext|>， 因为探针把 generation_config.eos_token_id（两个 id）都传给了 TokenizerInfo。 另外两个库只知道一个 EOS。这不是库的差别，是初始化参数的差别。
  • 第 3 步的 147145 / 147105 / 147158：三家各有几十个 token 的出入， 差集里是替代码点、\uXXXX 片段和 <|vision_start|> 之类的特殊 token—— 即各库对"字符串里能不能出现特殊 token / 非法 UTF-8"的口径不同。

紧 schema 下三家在枚举位置逐位一致：enum: ["Beijing","Shanghai","Shenzhen"] 在第 8 步（已生成 {"name":"Zhang","city":"）恰好允许 7 个 token，三家给出同一个集合：

['B', 'S', 'Sh', 'Be', 'She', 'Sha', 'Bei']

这 7 个就是三个城市名所有可能的首 token。枚举是三家实现得最一致的构造。

3. 真正的语义漏洞只有一处：outlines_core 丢掉了数值范围

用 6 个输入喂给三个库，逐 token 送进去，记录在哪里被拦下：

输入 jsonschema 判定 xgrammar llguidance outlines_core
合法对象 valid 全接受 全接受 全接受
age: "31"（类型错） INVALID 停在 tok12 停在 tok12 停在 tok12
age: 200（超 maximum:120） INVALID 停在 tok15 停在 tok15 全接受
city: "London"（不在枚举） INVALID 停在 tok8 停在 tok8 停在 tok8

六项里五项三家一致。差的那一项在制品里看得一清二楚。xgrammar 的 EBNF 把 minimum: 0, maximum: 120 编成了一条逐位数的产生式：

root_1 ::= (("0") | ([1-9]) | ([1-9] [0-9]) | ("1" "0" [0-9]) | ("1" "1" [0-9]) | ("1" "2" "0"))

于是 20 之后再来一个 0 无路可走——正好对应实测的「停在 tok15，拒绝 '0'」。 而 outlines_core 的正则是：

\{[ ]?"name"[ ]?:[ ]?("[A-Z][a-z]{2,9}")[ ]?,[ ]?"city"[ ]?:[ ]?("Beijing"|"Shanghai"|"Shenzhen")[ ]?,[ ]?"age"[ ]?:[ ]?(-)?(0|[1-9][0-9]*)[ ]?\}

minimum / maximum 整个消失了，还多出一个可选的负号 (-)?。 mask 层面也对得上：紧 schema 第 13 步 outlines_core 比另外两家多允许 '-' 和 ' -'。

可带走的判断：约束解码的"保证"是由 schema → 语法这一步的翻译完备性决定的， 不是由"开了约束解码"决定的。 换后端可能悄悄换掉你的保证。 要检查一个后端到底保证了什么，最省事的办法就是把它的语法制品打印出来读一遍。

4. 终止契约三家不同，而且这个不同已经变成线上 bug

沿轨迹走到最后一个 } 之后，再送 EOS：

库 } 之后已终止？ mask 里有 EOS？ EOS 被接受？
xgrammar 否 有（2 位） 是，之后终止
llguidance 是 有（1 位） 否
outlines_core 是 有（1 位） 否

llguidance 和 outlines_core 在闭合括号处就认为语言已经接受完毕， 之后的 mask 只是"礼节性"地把 EOS 摆出来，状态机本身不会消费它。 vLLM 的两个适配器各自打了补丁：

5. 端到端的钱花在推进 matcher，不是填 mask

同一批请求（batch 8 × 3 轮，每轮 172 个输出 token，enforce_eager，关闭 prefix caching）， 四个配置的整批耗时中位数：

outlines 在松 schema 上贵 43%、在紧 schema 上不贵，这条形状很奇怪，值得追。 把每一步拆开量（fill_per_step.py 与 grammar_accept_cost.py）：

loose 第 i 步 合法 token 数 outlines 填 mask outlines 推进 matcher
0–2（骨架） 2–8 1.36 µs 0.34 µs
3、4（字符串内部） 147158 127.3 µs 1028 µs
13–15（数字与闭合） 13 1.34 µs 0.31 µs

两条机制各自成立：

  • 填 mask 的成本正比于合法 token 数。 用四个不同的状态回归： 127.27/147158=0.86、13.45/16313=0.82、9.52/10509=0.91、4.99/5132=0.97 ns/token。 也就是 write_mask_into 是 O(合法数)，不是 O(V/32)。
  • 推进 matcher 的成本更高一个量级，且只在进入/停留于自由字符串状态时出现。 探针按 vLLM 适配器的调用顺序做了 accepts_tokens + advance 两次遍历 （backend_outlines.py:133–143），所以这 1 ms 里有一半是那次多余的预检查。

粗算：8 条请求 × 6.18 ms（推进）+ 8 × 6 × 127 µs（填 mask）≈ 55 ms， 实测差值 46 ms。同一个量级，但高估了约 20%——因为端到端跑出来的文本带空格 （{"name": "Zhang", …}），分词和步数都和探针里那条 43 字符的紧凑轨迹不同。

未闭合的账

xgrammar 的库内成本合计只有约 87 µs/请求（≈0.7 ms/批），实测却贵了 4.3 ms； guidance 库内约 160 µs/请求，实测贵 13.2 ms。剩下的几毫秒本章没有定位。 它们同时存在于三个后端，可能是 bitmask 的 H2D 拷贝、GPU kernel 与 grammar_bitmask() 每步的簿记，但这只是分析，没有测。 需要的诊断是在 vLLM 里对 grammar_bitmask() 与 apply kernel 单独计时。 不要引用"约束解码固定开销是 X ms"这类说法。

三条可以带走的：

  1. 贵的是推进状态机，不是 mask 那 18 KB。 直觉容易搞反。
  2. 成本随语法的"松"增长。 松 schema 意味着大合法集合， 而两个环节都随合法集合规模变大。把 schema 写紧既提高保证，也降低开销—— 这是少见的没有 trade-off 的方向。
  3. 它在 CPU 上、在调度器的关键路径上（<128 条请求时连线程池都不建）。 所以在小 batch、低延迟的场景里，这笔开销是直接加到 TPOT 上的。

6. 语法和 parser 必须共用同一份格式定义，否则错误路径会永远开着

tool call 这条链上有两个独立的组件在描述同一件事：

  • 语法（structural tag）说「<tool_call> 之后必须是符合此 schema 的 JSON」；
  • parser（hermes_tool_parser.py 之类）说「我按 <tool_call> 切段， 再按这个形状读出 name 与 arguments」。

两者由不同的配置项决定：语法来自请求里的 structured_outputs， parser 来自服务启动时的 --tool-call-parser。它们可以不一致，而且不一致时不会报错， 只会变成运行时的解析失败。

这就解释了 parser 里那些看似多余的容错分支——它们是为「模型没有被约束」准备的。 反过来，如果把同一份格式同时喂给语法与 parser， parser 的错误路径在原理上就不可达了；但没人会因此删掉它们， 因为同一个 parser 要同时服务约束和不约束两种请求。

这是一个通用形状：当两个组件各自维护同一份契约的副本时， 系统的正确性取决于两份副本是否同步，而这件事没有任何机制来保证。 本章第 4 节那个 outlines 的 bug 是同一个形状的另一个实例—— 「mask 说 EOS 合法」和「状态机说 EOS 不可接受」也是同一契约的两份副本。

 15class Matcher:

 22    def allowed(self, token_id):

它必须满足三条契约，self_check() 用穷举验证：

  1. 接受的语言正确。 穷举所有被允许的 token 序列，解码结果集合恰好等于 {'{"x":0}', '{"x":1}'}——注意同一个字符串有多种分词（{ + "x" + : 与 {"x":）， 实测 accepted tokenizations = 4。
  2. 拒绝不推进状态。 拒绝一个非法 token 之后，(prefix, mask) 必须逐位不变。
  3. rollback 可逆。 每次 accept 压栈，rollback(1) 精确还原到上一步的 mask。

181def walk(lib, compiled, ids, eos, vocab_size, tok_len, label, out_dir, tok):
182    """Walk the target trajectory, recording the bitmask at every step."""
183    m = lib.matcher(compiled)
184    mask = lib.allocate()
185    rows = []
186    directory = out_dir / f'{lib.name}-{label}'
187    directory.mkdir(parents=True)
188    for step, tid in enumerate(list(ids) + [eos]):
189        lib.fill(m, mask)
190        words = mask_words(mask, vocab_size)
191        real = list(words)
192        if tok_len % 32:
193            real[tok_len // 32] &= (1 << (tok_len % 32)) - 1
194        del real[tok_len // 32 + 1:]
195        blob = b''.join(w.to_bytes(4, 'little') for w in words)
196        (directory / f'mask-{step:03d}.bin').write_bytes(blob)
197        allowed = bool((words[tid // 32] >> (tid % 32)) & 1)
198        row = {'lib': lib.name, 'schema': label, 'step': step, 'token_id': tid,
199               'piece': tok.decode([tid]), 'legal_count': popcount(words),
200               'legal_count_real_vocab': popcount(real),
201               'word_index': tid // 32, 'bit_index': tid % 32,
202               'word_hex': f'{words[tid // 32]:08x}', 'allowed': allowed,
203               'shape': list(mask.shape), 'stride': list(mask.stride()),
204               'dtype': str(mask.dtype), 'bytes': len(blob)}
205        accepted = lib.accept(m, tid)
206        row['accepted'] = accepted
207        row['terminated_after'] = lib.terminated(m)
208        rows.append(row)
209        emit('mask_step', **row)
210        if not accepted:
211            break
212    return rows, m

215def rejection_contract(lib, compiled, vocab_size):
216    """A rejected token must not advance the state. Compare masks around it."""
217    import torch
218    m = lib.matcher(compiled)
219    mask = lib.allocate()
220    lib.fill(m, mask)
221    before = mask.clone()
222    words = mask_words(mask, vocab_size)
223    bad = next(i for i in range(vocab_size) if not ((words[i // 32] >> (i % 32)) & 1))
224    rejected = not lib.accept(m, bad)
225    lib.fill(m, mask)
226    return {'rejected_token_id': bad, 'rejected': rejected,
227            'mask_unchanged': bool(torch.equal(before, mask))}

前沿

  • jump-forward / 压缩 FSM。 SGLang 2024 年就在做（outlines_jump_forward.py 顶部引用了 lmsys 的 compressed-FSM 博文）；vLLM 的 guidance 后端把它留成 TODO， 注释里点名了难点：compute_ff_tokens() 只对"canonical"分词器可用， 字节层面的强制续写要重新对齐 token 边界才能用。本章测到这条路径上有 42% 的字符可跳。
  • structural tag。 三家都在往「文档里嵌一段受约束区域」的方向走 （vLLM 的 StructuredOutputOptions.STRUCTURAL_TAG、llguidance 的 StructTag）。 这是 tool-call 的真实形状：自由文本 + <tool_call> + 严格 JSON + </tool_call>。 本章没有测它的开销。
  • reasoning 与约束的交界。 vLLM 有 trim_reasoning_for_advance （scheduler.py:1987），SGLang 有整个 reasoner_grammar_backend.py： 思考段不受语法约束，遇到结束标记后才开始喂给 matcher。 这个边界一旦画错，就会出现本章第 4 节那种"语法拒绝自己允许过的 token"。
  • 把 matcher 挪出关键路径。 vLLM 的 128 条阈值说明现在的默认就是串行。 自然的方向是让 mask 填充与 GPU 前向重叠（它们本来就在不同的设备上）， llguidance 已经提供了 fill_next_token_bitmask_par。本章没有测重叠后的收益。

陷阱

  1. "不加约束时合法率 X%"不是模型的属性。 本章同一模型换 prompt 与采样， 合法率从 0/64 变成 24/24。约束解码买的是下界，不是平均值。
  2. 换后端可能悄悄换掉你的保证。 outlines_core 的 schema→正则丢掉了 minimum/maximum，age: 200 一路放行。要确认保证，读语法制品。
  3. "输出合法"不等于"请求成功"。 outlines 后端 48/48 输出全对， finish_reason 全是 error。只看内容的评测发现不了。
  4. 贵的是推进状态机，不是那 18 KB 的 mask。 本章实测 outlines_core 在 自由字符串状态下推进一次约 1 ms，填 mask 只要 127 µs。
  5. 成本随 schema 变松而上升。 把 schema 写紧同时提高保证、降低开销。
  6. mask 填充默认串行在调度器里（vLLM 要 >128 条并发才用线程池）， 所以它直接加在 TPOT 上。
  7. 约束不改变合法 token 之间的相对概率，只删除选项。它不会让模型"更聪明"， 只会让模型在被限死的路径上把错误答案写成合法格式。
  8. 撞上 max_tokens 时输出可以是不合法的——语法只保证"是某个合法串的前缀"， 不保证走到终止态。截断和违约是两回事，要分开统计。
  9. 词表预处理是冷启动成本（本机 215–685 ms），每个进程一次， 和每请求的编译成本不是一回事。
  10. structural tag 在标签外面完全不约束。 本章实测标签外每步 151669 个合法 token （= 整个词表）。它约束的是「一旦开始写 tool call，就必须写对」， 不是「必须写 tool call」。要强制调用工具是另一件事。
  11. 语法和 tool parser 是两套独立配置（请求里的 structured_outputs vs 启动时的 --tool-call-parser），不一致时不报错，只在运行时解析失败。
  12. tool call 的格式是模型属性：vLLM 0.29.0 带 51 个 parser 文件， SGLang 0.5.19 带 33 个 detector。换模型基本上要换 parser。

自测题

1. 同一份 JSON schema，三个库给的合法 token 集合不同。这说明有实现是错的吗？

大部分差异不是错。 本章逐位比较后，差异分成四类：

  • 空白策略：xgrammar/llguidance 允许 '{\n' 这类带换行的 token， outlines_core 的正则只写了 [ ]?。两者生成的都是合法 JSON。
  • 分词规范化：llguidance 在键名处只允许 'name' 一个 token， 另外两家允许 'n'/'na'/'nam'/'name'。同一个字符串，允许的切法不同。
  • 停止 token：xgrammar 多允许一个 <|endoftext|>，因为初始化时传了两个 eos id。 这是参数差别，不是库差别。
  • 特殊 token 与非法 UTF-8 的口径：自由字符串处三家差几十个 token。

只有一类是真的错：outlines_core 把 minimum/maximum 丢掉了， 所以 age: 200 在它那里合法。判断方法是打印语法制品—— xgrammar 的 EBNF 里有 root_1 ::= ... | ("1" "2" "0")，outlines 的正则里只有 (0|[1-9][0-9]*)。

2. 一个后端在松 schema 上让整批耗时涨 43%，紧 schema 上不涨。怎么解释？

因为两个环节的成本都正比于当前状态的合法 token 数。

  • 松 schema 里 "name" 的取值是任意字符串，该状态有 147158 个合法 token； 紧 schema 里它被 ^[A-Z][a-z]{2,9}$ 限成 5132 个。
  • 实测 outlines_core 填 mask 的单位成本是 0.82–0.97 ns/合法 token （四个不同状态回归得到），所以 147k 个要 127 µs，5k 个只要 5 µs。
  • 推进 matcher 更贵：自由字符串状态一次约 1.03 ms，紧 schema 的对应状态 63–97 µs。

一条轨迹里有 6 步落在自由字符串状态，8 条请求 → 约 50 ms， 和实测的 46 ms 同量级（探针轨迹与真实输出的分词不同，所以不精确对齐）。

推论：把 schema 写紧既提高保证，也降低开销。 这个方向上没有 trade-off。

3. 调度器为什么会打出 "grammar rejected tokens"？mask 里明明有这个 token。

因为 mask 和状态机的终止契约可以不一致。

outlines_core 在闭合括号处就 is_finished()，之后 mask 里仍然摆着 EOS 位， 但 advance(EOS) 返回 False。vLLM 的适配器只在 is_terminated() 上延迟了一步 （backend_outlines.py:123），没有在 accept_tokens 上做同样的处理， 于是调度器 scheduler.py:1991 拿到 False，把请求标成 FINISHED_ERROR。

实测后果：48/48 条请求文本完全正确、schema 完全合法，finish_reason 全是 error。

一般化的教训：跨库适配时，"允许集合"和"状态推进"是两个独立契约， 必须分别验证。只验证输出内容的测试对这类 bug 完全免疫。

4. 约束解码的开销主要在哪？为什么"mask 才 18 KB，能有多贵"这句话是错的？

18992 字节是 mask 的尺寸，不是产生它的成本。

本章实测，一步的 CPU 工作分两块：

xgrammar llguidance outlines_core
填 mask（松，中位数） 0.94 µs 8.55 µs 1.85 µs
推进 matcher（整条 16 步轨迹） 8.2 µs 16.2 µs 6183 µs

差三个数量级的是推进状态机。而且这两件事都在 CPU 上、都在调度器循环里 （vLLM 要并发超过 128 条才用线程池，__init__.py:62）， 所以它们直接加在每一步的延迟上。

同时也要说清楚：本章的库级测量只解释了端到端差值的一部分 （outlines 松 schema 那 43% 能对上量级，xgrammar 的 4.3 ms 里只解释了 0.7 ms）， 剩下的没有定位。

5. 语法说下一步只能是 "name":"，为什么还要跑一次前向？

不必跑。 这就是 jump-forward：当从当前状态出发只有唯一一条字节路径时， 直接把那段文本写进输出，跳过若干次前向，再重新对齐 token 边界 （SGLang xgrammar_backend.py:164 的 try_jump_forward + jump_and_retokenize）。

本章沿目标轨迹逐步询问，43 个字符里有 18 个（42%）是被语法强制的， 全是 JSON 骨架：{、name"、"、city"、"、age"、"。

难点在重新分词：强制的是字节，而模型的状态是按 token 记的。 把 name" 塞进去之后，它和后面的字符可能合并成不同的 token， 必须回滚到最后一个相同的 token 再重放（jump_and_retokenize 就在做这件事）。 vLLM 的 guidance 后端把这条留成了 TODO，注释里点名 compute_ff_tokens() 只对 canonical 分词器可用。

本章没有测打开 jump-forward 之后的端到端收益，42% 只是可跳字符的占比。

6. 开了 structural tag 约束，模型还会不会不调用工具、或者胡编一个工具名？

会不调用；不会胡编。 两件事分开看。

  • 标签外不受任何约束。 本章实测「散文 + tool call」那条轨迹， <tool_call> 之前的每一步都有 151669 个合法 token，正好等于 len(tokenizer)。 TagDispatch 的语义就是"先允许任何输出，直到看见 trigger"。 所以模型完全可以从头到尾只写散文。要强制调用工具，得换成 「以 begin 开头」的语法，或者由上层拒绝没有 tool call 的回复。
  • 标签内的工具名被枚举锁死。 编译出来的产生式里 root_prop_0 ::= (("\"get_weather\""))——只有这一个取值。 实测第 11 步（已写出 {"name":"）只剩 3 个合法 token。

还有一件独立的事：即使语法保证了形状，把这段文本还原成 tool_calls 结构 是 parser 的工作，parser 由启动参数决定，和语法不共享配置。 两者不一致时不会报错，只会解析失败。
