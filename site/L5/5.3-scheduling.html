5.3

调度：continuous batching 与 chunked prefill

逐 step 计时看调度：一条 8192 token 的 prefill 让稳态 4.7ms 的步涨到 53ms，连续 5 步所有 decode 停摆。把块切到 512 后尖峰从 165.9 降到 15.9ms，而总时间不变——chunked prefill 在这个配置下近乎免费。max_num_batched_tokens 过了并发数就完全无效（拐点实测）。

实测机器 crater (RTX 5090 D, sm_120) · vLLM 0.29.0 · Qwen3-1.7B数据日期 2026-09-10前置 5.1（两相的性质）· 5.2（KV 分页）· 0.1（引擎的调用栈）

本章回答三个问题

5.1 证明了 prefill 与 decode 的要求相反。调度器就是处理这个矛盾的地方。

  1. 一个 step 里到底发生了什么？
  2. 一条长 prompt 插进来时，正在 decode 的请求会被拖多久？
  3. max_num_batched_tokens 到底管什么？调小了会伤害什么？

本章的方法：逐 step 计时

不用 LLM.generate（它把整个批跑完才返回），而是用底层的 add_request + step()，每一步单独计时。 调度的行为只有在这个粒度上才看得见——平均值会把所有尖峰抹平。

一 · 一个 step 里有什么

三条请求（prompt 64，生成 6）：

 step     耗时 ms     运行中     等待中
    0     6.051          3       0
    1     5.064          3       0
    2     4.692          3       0
    3     4.632          3       0
    4     4.583          3       0
    5     4.631          3       0
    6     0.300          0       0

第 0 步 6.051 ms（含三条的 prefill），之后每步 ~4.6 ms 给三条各出一个 token。 最后一步 0.300 ms 是收尾。

"运行中/等待中"这两个数就是调度器的全部状态。 等待中不为 0 意味着有请求排队——那段时间全部算进它的 TTFT（5.1 §三）。

二 · 长 prefill 插进来会怎样

先让 8 条短请求进入 decode 稳态，再插入一条 8192 token 的 prefill：

稳态每步中位数 4.735 ms（8 条 decode）
插入一条 8192 token 的 prefill 之后：
  最慢的一步 53.326 ms（是稳态的 11.3×）
  超过稳态 2 倍的步数：5 / 40
  前 12 步: [4.76, 31.38, 41.02, 47.18, 53.33, 49.86, 5.39, 4.9, 4.81, 5.03, 4.77, 4.9]

看那串数字：4.76 之后连续 5 步是 31/41/47/53/50 ms，然后回到 ~4.9。

这 5 步里，8 条正在 decode 的请求一个 token 都没出。 它们的 TPOT 在这段时间被拉长了 10 倍。用户看到的就是"字突然卡住一下"。

一个观察：默认已经在切了

我原本写的是"一条长 prefill 会占住一整个 step"。但数据显示是 5 步， 不是 1 步——说明这个版本的 vLLM 默认就开了 chunked prefill， 只是每块还是很大（8192 / 5 ≈ 1638 token/块）。

所以问题不是"要不要切"，而是"切多细"。

三 · 切多细：一个几乎免费的交易

同样的实验，只改 max_num_batched_tokens：

配置 稳态 ms 最慢一步 ms 尖峰倍数 吸收长 prefill 共用 ms
不切分（16384） 4.607 165.852 36.0× 529.5
切分成 2048 4.679 53.624 11.5× 539.6
切分成 512 4.651 15.926 3.4× 514.6

尾延迟从 165.9 ms 降到 15.9 ms，降了一个数量级。

我预期这里会有一个交易，结果没有

我写这一节时的假设是"切得越细，总时间越长"——把尾延迟换成吞吐。 最后一列否定了它：吸收整条 prefill 的总时间是 529.5 / 539.6 / 514.6 ms， 三档相差在噪声范围内，切得最细的那档反而最快。

所以在这个配置下 chunked prefill 近乎免费： 尾延迟降一个数量级，总吞吐没有可测的损失。

理论上切得更细会有代价——每块的 GEMM 变瘦，而 2.7 §六 量过瘦长 GEMM 的效率 远低于方阵。切到 512 还没看到这个代价，要更细才会显现。 这是一个明确的、可以自己去找的边界（见消融 2）。

四 · max_num_batched_tokens 到底管什么

它同时管两件事：

  1. 一个 step 最多处理多少 token（prefill 被切成多大块，第三节）
  2. decode 的批能凑多大——每条 decode 每步只贡献 1 个 token

第 2 条意味着：它只在 max_num_batched_tokens < 并发数 时才限制 decode。 固定并发 64，把这个参数扫过 64 这条线：

max_num_batched_tokens 能否喂满 稳态 ms tok/s 相对最好
16 否 4.387 3647 0.26×
32 否 4.436 7214 0.52×
64 是 4.574 13993 1.00×
128 是 5.247 12197 0.87×
512 是 5.178 12361 0.88×
8192 是 5.162 12399 0.89×

在 64 以下是线性的（16→0.26×、32→0.52×，正好是 16/64 和 32/64）， 因为每步只有那么多条请求能前进。

过了 64 就完全平了（甚至略降）——decode 每步只需要 64 个 token， 给它 8192 的预算也用不上。

我第一版把这个测错了

第一版用并发 32 去扫 256/512/2048/8192，四档结果全在 6277–6408 tok/s， 差 2%。我据此写了"太小会限制 decode 的并发"——但那四档全都大于 32， 根本没碰到限制。

要测一个参数的影响，必须让扫描跨过它起作用的那条线。 把并发提到 64、把参数扫到 16 才看见那条线。

五 · 设计取舍

5.1 为什么调度的粒度是 token 而不是请求

朴素的想法是"一批凑够 N 条请求就跑"。vLLM 的预算单位是 token， 不是请求。原因从上面两节就能读出来：

  • 一条 decode 请求这一步只要 1 个 token
  • 一条 prefill 请求这一步可能要 8192 个

用请求数当预算，两者的成本相差三个数量级， 一个混合批的耗时会完全不可预测（第二节那个 11.3× 的尖峰就是这么来的）。

用 token 当预算，每一步的工作量就有了上界，step 时间因此可控。 这是 chunked prefill 能成立的前提：prefill 可以被切成任意大小的块， 正好填满预算的空隙。

判据：调度的预算单位应该选那个与耗时成正比的量。 选错了，SLA 就无法保证。

5.2 尾延迟与吞吐通常是交易，这次不是

第三节的结果值得单独说：切细 32 倍，尾延迟降 10 倍，吞吐没有可测损失。

为什么这么便宜？因为被切的是 prefill，而 5.1 证明了 prefill 在 batch=1 时就已经算力受限——切成 512 一块，每块仍然有 512 的算术强度， 远高于 144 的平衡点。它还在算力一侧，效率没掉。

所以这个"免费"是有条件的：块大到还能保持算力受限。 块小到进入带宽一侧（或者小到 launch 开销显著，L1.4 的 2.68 µs）就不免费了。

一般化：当一个操作在很宽的规模范围内都保持同一种瓶颈时， 沿这个维度切分几乎是免费的。 先确认瓶颈不变，再谈切分。

5.3 参数的"无效区间"比"有效区间"更常被误用

第四节那张表有一个很大的平台区（64 以上全一样）。 一个只在 128/512/8192 之间比较的人会得出"这个参数没用"， 一个只在 16/32 之间比较的人会得出"越大越好"。两个结论都是错的。

扫描必须跨过拐点。 而拐点在哪里，要先从机制推—— 这里是"并发数"，因为每条 decode 每步只要 1 个 token。 先有机制假设，再设计扫描范围，是 M2 会讲的核心方法。

 72def run_steps(eng, reqs, max_steps=100000):
 73    """手动驱动引擎，逐 step 记录耗时与该步处理的 token 数。"""

七 · 陷阱

  1. 用 LLM.generate 看不到调度行为。 它把整批跑完才返回， 所有尖峰被平均掉。要逐 step 计时。
  2. 一条长 prefill 会让所有 decode 停住。 本章实测 5 步共约 220 ms。
  3. vLLM v1 默认已经在切 prefill，问题是切多细，不是切不切。
  4. 参数扫描必须跨过拐点。 本章第一版在 max_num_batched_tokens 的平台区里扫，得出"没影响"的错误结论。
  5. max_num_batched_tokens 过了并发数就没有作用。 调大它不会提高 decode 吞吐。
  6. 别假设"细粒度 = 更慢"。 本章实测切细 32 倍总时间不变。 先量，再下结论。

八 · 自测题

1. 为什么调度预算的单位是 token 而不是请求数？

因为成本与 token 数成正比，与请求数无关。

一条 decode 请求这一步要 1 个 token；一条 prefill 请求可能要 8192 个。 用请求数当预算，一个"8 条请求"的批可能是 8 个 token，也可能是 65536 个—— 耗时相差三个数量级，step 时间完全不可控。

用 token 当预算，每步的工作量有上界，step 时间可预测， 才谈得上保证 TPOT 的 SLA。

这也让 chunked prefill 成为可能：prefill 可以切成任意大小填进预算的空隙。

2. 用户反馈"输出偶尔会卡一下"，怎么定位？

大概率是长 prefill 插队。诊断步骤：

  1. 逐 step 记录耗时（不能用平均值，本章第二节的方法）。
  2. 找出超过稳态 2 倍的那些 step。
  3. 看这些 step 前后有没有新请求进入 prefill。

本章实测：一条 8192 token 的 prefill 让稳态 4.735 ms 的步涨到 53.3 ms， 连续 5 步——期间所有 decode 一个 token 都不出。

缓解：调小 max_num_batched_tokens。本章实测切到 512 时尖峰从 165.9 降到 15.9 ms，而总吞吐没有可测损失。

（如果尖峰与新请求无关，再查抢占/换出——那是 5.8 的内容。）

3. 你调大了 max_num_batched_tokens 但 decode 吞吐没变，为什么？

因为它已经大于你的并发数了。decode 每条请求每步只贡献 1 个 token， 所以并发 64 时每步最多只需要 64 个 token 的预算。

本章实测：并发 64 时，64 / 128 / 512 / 8192 四档的吞吐分别是 13993 / 12197 / 12361 / 12399 tok/s——过了 64 就是平的。

反过来，如果设成 16，只有 16 条能前进，吞吐直接掉到 0.26×。

要测一个参数有没有用，扫描范围必须跨过它起作用的那条线。 这条线在哪，要先从机制推出来。

4. 为什么把 prefill 切细几乎不损失吞吐？这个"免费"什么时候结束？

因为 prefill 在很宽的规模范围内都是算力受限的（5.1）。 一块 512 token 的 prefill，算术强度仍是 512，远高于平衡点 144—— 它还在 roofline 的算力一侧，效率没掉。

所以切分只是把同样的工作换个顺序做，总量不变。 本章实测：16384 / 2048 / 512 三档，总时间 529.5 / 539.6 / 514.6 ms，无差别。

"免费"在块小到瓶颈改变时结束： - 块的算术强度掉到 144 以下 → 进入带宽一侧 - 块小到 kernel launch 开销（2.68 µs，L1.4）占比显著

消融 1 就是让你去找这个边界。
