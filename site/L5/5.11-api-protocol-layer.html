5.11

API 与协议层

引擎的前门：OpenAI 兼容层、SSE streaming、请求生命周期、tokenization 会不会成为 CPU 瓶颈。5.8 讲失败路径，这一章讲那些路径跑在什么之上。

实测机器 crater (RTX 5090 D, sm_120) · Qwen3-1.7B · vLLM 0.29.0 · SGLang 0.5.19 · uvicorn 0.52.4 · starlette 1.6.0数据日期 2026-09-12前置 0.1（请求全链路）· 5.3（调度）· 5.7（nanoserve）· 5.8（失败路径）

本章回答三个问题

前面十二章都在引擎内部。这一章退到引擎门口，看请求进来和 token 出去的那一段。

  1. 一个 HTTP 请求到进入 scheduler，中间经过哪些层？每层花多少时间？
  2. streaming 的每个 chunk 是怎么产生和推出去的？一个 token 对应几个字节？
  3. tokenization 在高并发下会不会成为瓶颈？

结论先给：前门在端到端时延里占比很小，但它的位置决定了两件大事——它决定了谁会被别人的 工作阻塞，也决定了 token 以什么粒度离开进程。本章实测 24 token 的流式请求：客户端墙钟 77.75 ms，其中引擎推理 76.32 ms，进程内前端 0.79 ms、进程外 0.63 ms，非推理部分合计 1.84%。 但把 tokenizer 放回事件循环，一个 16k token 的请求会让所有在跑的请求停顿 11.4 ms—— 正好等于它自己的编码耗时。

心智模型：两道进程边界，三层分帧

机制拆解与推导

1. 请求在 HTTP 层要过四道门

ASGI 服务器的调用栈是嵌套的：每个中间件包住下游，请求自外向内穿过，响应自内向外回来。 vLLM 注册中间件的顺序（entrypoints/serve/middleware/register.py:19-75）是 CORS → 鉴权 → request-id → 扩缩容状态，最后才是用户通过 --middleware 传入的。 Starlette 的 add_middleware 是后加的先执行，所以列表顺序和实际执行顺序相反。 中间件越多，每个请求的固定开销越大，而且流式响应也走完整条链——返回 StreamingResponse 不代表绕过了中间件。

2. SSE 是叠在 chunked 上的第二层分帧

一个流式响应在 HTTP/1.1 上同时有两层分帧。外层是传输层的 chunked： 长度(十六进制) CRLF 负载 CRLF，最后以 0 CRLF CRLF 结束。内层是 SSE 的事件： 字段行加一个空行构成一个事件。

两层都有「一个逻辑单元可能被拆到多次 recv」的问题。本章实测的 24 token 响应里， 25 个 chunked 帧恰好被 25 次 recv 读到——这是偶然，不是保证。 客户端必须按字节流处理：先把 chunked 还原成 body，再把 body 喂给 SSE 解析器。 labs/L5/mini_sse.py 的 SSEDecoder 只吃 body 字节，就是为了让这两层解耦。

SSE 的规范细节容易漏的有四条，都在 mini_sse.py 里做了自检：

  • 行分隔符 CR、LF、CRLF 都算，而 CRLF 可能被拆在两次读之间；
  • 冒号后紧跟的一个空格被吃掉，多出来的属于数据；
  • 以冒号开头的行是注释，客户端必须忽略——vLLM 的 keep-alive 就走这条路；
  • EOF 不是事件结束符，没等到空行就结束的半个事件要丢掉。

3. 引擎指标能拆出前端段和运行段

vLLM 的请求时延指标（v1/metrics/stats.py:218-245）在 engine core 里盖章， arrival_time 则在前端进程、tokenization 之前打上（v1/engine/input_processor.py:321-322）。 于是：

段 算法 内容
前端段 e2e − inference − queue tokenization + 序列化 + 送进 core
排队段 queue WAITING 状态
运行段 inference = prefill + decode core 里的前向与采样
回程段 客户端墙钟 − e2e 增量 detokenize + SSE 编码 + 回写

这个减法能成立，靠的是「各时间戳盖在哪个进程」这一件事。换个引擎、换个版本， 时间戳位置变了，减法就不再成立——先读代码确认戳在哪，再做减法。

4. 一个 token 不一定对应一个 SSE 事件

engine core 每步吐出的是 token id，推给客户端的是文本增量。中间隔着增量 detokenizer： vLLM 的 FastIncrementalDetokenizer 用 tokenizers 库的 DecodeStream.step() 解码单个 token， 而 DecodeStream 会把不完整的 UTF-8 前缀扣住，等下一个 token 到了再一起吐 （v1/engine/detokenizer.py:211-248）。扣住的那一步返回空串，前端就不发事件。

所以「生成 24 个 token」不等于「收到 24 条 data:」。本章这次实测正好相等： 24 个 delta 事件 + 1 个 [DONE]，没有空 delta。相等是常见情况，不是不变量—— 多字节字符被切开、或 BPE 合并跨 token 时就会不等。

5. tokenization 的成本不在总量，在它跑在哪

先看绝对量级。Qwen3-1.7B 的 tokenizer 在 crater 的 CPU 上：

输入字符 token 数 编码中位耗时
69 17 0.021 ms
552 129 0.091 ms
4 416 1 025 0.616 ms
17 664 4 097 2.468 ms
70 656 16 385 9.941 ms

约 0.6 µs/token。16k token 的长上下文请求编码一次只要 9.9 ms， 而同一台机器上 1.7B 模型一个 decode step 是 20.6 ms。从吞吐看，tokenizer 不是瓶颈。

但从延迟看，它是。Python 的 async def 里直接调 tok.encode() 会占住事件循环： 这段时间里所有协程都不推进，包括正在给别的请求推 token 的那个。 这就是本章要复现的失败模式——它的危害不来自耗时总量，来自位置。

修法有两个层次，可以叠加：

  1. 挪出去。 await asyncio.to_thread(tok.encode, ...) 或 run_in_executor， 把阻塞调用放到线程池。vLLM 对 raw prompt 走的就是这条路，注释写得很直白： 「Raw prompts require tokenization and possibly multimodal processing, which must not block the event loop.」（v1/engine/async_llm.py:440-441）
  2. 合起来。 挪出去之后每次调用仍是一次独立编码，N 个并发请求就是 N 次。 SGLang 的 AsyncDynamicbatchTokenizer 把这两件事一起做：请求进队列， 后台任务在 2 ms 窗口内攒到最多 32 条，一次 tokenizer(...) 批量编码， 再按 future 分回各请求（managers/async_dynamic_batch_tokenizer.py:58-152）。

代价也要说清：挪出去要多一次线程往返，而线程的结果只能在事件循环空闲时投递。 本章实测同一份 16k token 输入，in-loop 编码 11.0 ms，to_thread 后服务端侧变成 31.7 ms—— 多出来的部分是「等事件循环腾出手」。保护了别人，自己变慢。

这段代码值得逐行读，因为它绕开了两个 asyncio 的坑：

  • asyncio 不允许对同一个异步生成器并发调用 __anext__，所以必须保留一个 task， 不能每轮重新创建；

H. 两边的增量 detokenize 都在处理同一个问题：半个字符

SGLang 的 DecodeStatus 带两个游标（srt/managers/detokenizer_manager.py:75-81）： surr_offset 是「用来当上下文但不输出」的窗口，read_offset 是「已经输出到哪」。 每步把 decode_ids[surr_offset:read_offset] 解码一次当上下文，再把新的一段输出， 然后 surr_offset = read_offset; read_offset = len(decode_ids)（394–395 行）。

vLLM 用 tokenizers 库的 DecodeStream 达到同样效果。两边的共同点是： 解码器需要回头看一眼已经吐出去的字符，才能决定新 token 的文本。 这就是「一个 token 不一定产生一个事件」的根源。

设计取舍

前端进程做多少事。 vLLM 把 tokenize、detokenize、SSE 编码都放在前端进程， engine core 只管调度和前向；SGLang 把 detokenize 又拆了一个进程出去。 前端做得多，IPC 少、延迟低，但前端一卡全线卡；拆得越细，越能独立扩缩， 代价是每一段都要序列化，而且时间戳散在多个进程里，性能归因更难做。 本章的减法能成立，正是因为它建立在「戳在前端、推理在 core」这个具体切法上。

流式响应的背压放在哪。 SSE 没有应用层流控，背压只能由 TCP 窗口传导。 writer.drain() 会等到对端把数据收走（labs/L5/nanoserve/server.py:137）， 慢客户端因此把整个引擎拖住。要在应用层解决，就得给每个流加有界队列并定义丢弃策略—— 这不是 HTTP 层能单独决定的事，它要和 5.3 的调度、5.8 的背压一起设计。

keep-alive 注释是给中间设备看的，不是给客户端看的。 客户端必须忽略它， 但它确实占带宽。间隔设小了，长连接的空闲期会持续产生注释；设大了，代理照样掐断。 默认 0 表示不产生，只有部署在会掐连接的代理后面才需要打开。

取消由谁负责。 vLLM 用装饰器包路由，SGLang 用 background 任务。 前者要求「请求体已经被读完」，因为装饰器会消费掉后续消息来找断连 （entrypoints/serve/utils/api_utils.py:51-71 的注释明确写了这条前提）； 后者挂在响应对象上，天然知道流什么时候结束。两种都能用， 但装饰器版本不安全——把它用到没读完 body 的路由上会丢数据。

5. tokenization 曲线

输入字符 token 数 中位耗时 ms 单 token µs

单 token 成本在 1k token 以上收敛到约 0.59 µs。这条曲线是线性的， 没有拐点，说明 HF 的 Rust tokenizer 在常见长度区间没有需要回避的复杂度。 把它和上表的 prefill 比：16k token 的编码 9.6 ms，同规模的 prefill 在 GPU 上 远快于此——CPU 侧的 tokenization 确实是长上下文请求里 CPU 与 GPU 之间 最不匹配的一对，但它的绝对量级（毫秒）还不足以成为吞吐瓶颈。

同一进程内顺序编码 16 段 256-token 文本共 9.78 ms，折合 2.39 µs/token； 而一次编码 4097 token 的长文本只要 2.397 ms，折合 0.59 µs/token。 同样的 token 总量，合成一次调用比拆成 16 次便宜约 4 倍。 这是下一节「合起来」那条路线的依据：合批省下的不是算法复杂度， 是每次调用的固定开销与短输入下 tokenizer 内部的低效。

6. 把 tokenizer 放回事件循环

单看耗时不能说明问题，得看它阻塞了谁。实验设计：先起一条流式请求 A， 等它稳定吐 token（稳态间隔约 20.6 ms，即一个 decode step）； 然后发请求 B，只测 B 到达那一刻 A 的间隔有没有多出来。

B 走一个只做编码、不进引擎的端点，这样「事件循环被占住」和 「引擎多了一条请求」是分开的两件事。B 的 prompt 长度用 --b-reps 控制， 用 4 段（65 token）当对照组。

B 的规模 写法 B 编码耗时 ms A 在 B 到达前间隔最大 ms B 到达后 A 间隔最大 ms 多出来的部分 ms
16 001 token tok.encode() 直调 11.02 20.35 31.76 +11.4
16 001 token asyncio.to_thread 31.71 21.04 21.53 +0.5
65 token tok.encode() 直调 0.96 20.66 21.10 +0.4
65 token asyncio.to_thread 1.13 21.25 21.40 +0.2

读法：

  • in-loop 组多出来的 11.4 ms，等于 B 自己的编码耗时 11.0 ms。 事件循环被占多久， 别人就等多久，一一对应。
  • 对照组（65 token）几乎不动，说明这个尖峰来自 tokenization，不是「B 到达」这件事本身。
  • to_thread 组没有尖峰，尽管它的编码耗时反而更长（31.7 ms）。它保护了别人， 自己却多等了 20 ms——多出来的正是「线程干完了，但事件循环还在忙」的那一段。

同一个负载走完整的生成路径（B 也是一条真实请求，prompt 同样是 16k token）时， A 的最大间隔在两种写法下分别是 373.4 ms 和 373.9 ms，没有区别。 因为 B 的 prefill 要占 47 个 chunked prefill 步，引擎侧的负载才是主导， tokenization 的 11 ms 被淹没了。这条对照说明：只有当引擎侧的扰动小于 tokenization 的耗时时，这个实验才测得出东西。 在小模型、短输出、单请求的场景下， in-loop tokenization 的代价才显现；大模型长输出的生产负载里，它通常不是第一瓶颈。

7. keep-alive 注释：一次真实的样本

--sse-keep-alive-interval 是整秒，所以注释只在流空闲超过 1 秒时出现。 把 --max-num-seqs 压到 1、并发发 20 条请求，排队时间拉到均值 732 ms、 TTFT 最大 1 483 ms，20 条流里有 7 条各收到一条注释。

字节流里它的样子（data-keepalive2/conc20-slowest.bin）：

e\r\n: keep-alive\n\n\r\nf0\r\ndata: {"id":"cmpl-922d22fce1e26002",...

e 是十六进制的 14——注释自成 14 字节的 chunked 帧，正好等于 : keep-alive 12 字节加两个 \n。紧随其后的 f0 帧（240 字节）才是下一个 token。 它落在两次 data: 之间，SSE 客户端必须跳过；但代理的读超时会把它算成流量， 这正是它的作用。

8. 消融与未测范围

建议消融，每种配置另存结果：

  • 把 --b-reps 在 100 到 3000 之间扫描，找出「in-loop 尖峰」从什么时候开始 超过稳态间隔的一半；
  • 打开 --enable-dynamic-batch-tokenizer 起 SGLang，测攒批窗口 2 ms 对 低并发延迟的影响；
  • 把 --sse-keep-alive-interval 设为 1 秒并把 --max-num-seqs 压到 1， 观察排队流的注释频率与代理行为；
  • 用 --middleware 挂一个计时中间件，把 ASGI 解析与路由的耗时单独量出来。

未测：

  • SGLang 端的完整对照未跑。 本章的 SGLang 只做了源码走读， AsyncDynamicbatchTokenizer 的实际收益没有实测，标 UNVERIFIED。
  • keep-alive 的间隔与代理行为未对照。 本章只抓到「间隔 1 秒 + 强排队」 这一种条件下的注释，注释频率与排队时长的定量关系、以及真实反向代理 （NGINX proxy_read_timeout、Cloudflare Tunnel）在有无注释时的行为差异都没有测。
  • HTTP/2 与 HTTP/3 未测。 服务端是 uvicorn 的 HTTP/1.1。HTTP/2 没有 chunked 这一层，SSE 直接走 DATA 帧；多路复用会改变前端的排队行为。
  • 多 worker 未测。 本章都是单进程。--api-server-count 或 uvicorn 多 worker 会把前端开销并行化，但 per-request 队列和 prefix cache 的共享会变复杂。
  • empty_delta_events 在这次运行里是 0，所以「token 数 ≠ 事件数」 只有源码依据，没有本章的实测样本。

 32 def raw_stream(host, port, path, payload, timeout=120.0):
 33     """发一个请求，把收到的每一个字节按到达顺序记下来。返回 (头部, 原始字节块, 时间戳)。"""
 34     body = json.dumps(payload).encode()
 35     head = (f"POST {path} HTTP/1.1\r\nHost: {host}:{port}\r\n"
 36             f"Content-Type: application/json\r\nAccept: text/event-stream\r\n"
 37             f"Content-Length: {len(body)}\r\nConnection: close\r\n\r\n").encode()
 38     sock = socket.create_connection((host, port), timeout=timeout)
 39     sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY, 1)
 40     t_send = time.perf_counter()
 41     sock.sendall(head + body)
 42     chunks, stamps = [], []
 43     try:
 44         while True:
 45             data = sock.recv(65536)
 46             if not data:
 47                 break
 48             chunks.append(data)
 49             stamps.append(time.perf_counter() - t_send)
 50     finally:
 51         sock.close()
 52     raw = b"".join(chunks)
 53     sep = raw.find(b"\r\n\r\n")
 54     return raw[:sep].decode("latin1"), chunks, stamps, raw, t_send

 57 def dechunk(raw_body: bytes) -> tuple[bytes, list[int]]:
 58     """解开 HTTP/1.1 chunked 分帧，返回 body 与每个 chunk 的字节长度。"""
 59     out, sizes, pos = bytearray(), [], 0
 60     while True:
 61         eol = raw_body.find(b"\r\n", pos)
 62         if eol < 0:
 63             break
 64         size_field = raw_body[pos:eol].split(b";")[0].strip()
 65         if not size_field:
 66             break
 67         try:
 68             size = int(size_field, 16)
 69         except ValueError:
 70             break
 71         pos = eol + 2
 72         if size == 0:
 73             break
 74         out += raw_body[pos:pos + size]
 75         sizes.append(size)
 76         pos += size + 2
 77     return bytes(out), sizes

本批次两个服务端各启动一次（主审计 8100、keep-alive 对照 8101）， api_layer_audit.py 一次运行内完成原始字节流抓取、层间分解、tokenization 曲线 和并发三档。事件循环对照在 nanoserve 上另起 6 个进程，每个进程重新加载模型与 tokenizer，互不共享状态。

前沿

沿本章机制继续扩展，而不是只调参数：

  • 前端与 core 的边界往哪挪。 本章的减法依赖「tokenize 在前端、推理在 core」。 把 tokenize 挪进 core（或再拆一个 tokenizer 进程）会改变这条边界， 也随之改变哪些时延指标可比。值得系统测量的是挪动边界对尾延迟的影响， 而不是某一次的平均值。
  • 应用层背压。 SSE 把流控完全交给 TCP，慢客户端会把引擎拖住。 有界队列 + 丢弃/降级策略需要在 HTTP 层和调度层之间定义一个接口， 这个接口目前没有标准形态。
  • 协议升级。 HTTP/2 的 DATA 帧、HTTP/3 的流、以及 gRPC 双向流， 都会改变本章的三层分帧。哪些结论能保住、哪些要重做，需要实测。
  • tokenizer 的并行度。 SGLang 用单线程执行器，源码说明的理由是「保持事件循环响应」。 Rust tokenizer 默认不释放 GIL，因此多开线程预期不会并行——本章没有单独实测多线程编码， 这一条是推断，不是测量结果。真正的加速方向是批内合并（SGLang 的做法）或换实现 （如 tiktoken 风格的分词），两者都需要在自己的负载上测，不能只看单次编码耗时。

陷阱

  1. 把 recv 次数当成服务端写的 chunk 数。本章 25 个 chunked 帧恰好对应 25 次 recv，这是偶然；TCP 合并是常态。
  2. 用 requests / httpx 抓 SSE 再谈分帧——它们只给你解完 chunked 的 body。
  3. 把 e2e_request_latency 当成客户端感知的时延。它从输入处理开始、到最后一个 token 在 core 里生成为止，不含 detokenize 与回写。
  4. 拿不同引擎的指标直接相减。时间戳盖在哪个进程、包不包括 detokenize， 各引擎不同。
  5. 以为「生成 N 个 token」就一定有 N 个 SSE 事件。增量 detokenizer 会扣住 不完整的 UTF-8 前缀。
  6. 以为返回 StreamingResponse 就绕过了中间件。它照样走完整条链。
  7. 只测 tokenization 的单次耗时，不看它阻塞了谁。0.6 µs/token 看起来很便宜， 放在事件循环里就变成了别人的延迟。
  8. 把 keep-alive 注释当成数据。它是注释，客户端必须忽略，但它占带宽。
  9. 以为 SSE 有应用层流控。没有，背压只能靠 TCP 窗口传导。

  6. 为什么本章要关掉 prefix caching？
答案
  1. 外层 HTTP/1.1 chunked（长度 + CRLF + 负载 + CRLF），内层 SSE（字段行 + 空行）。 两层都可能把一个逻辑单元拆到多次 recv，所以只能按字节流增量解析， 不能假定一次读到一个完整帧。
  2. 差 = 请求从 sendall 到「输入处理开始」的时间（网络 + ASGI 解析 + 中间件） 减去回程（detokenize + SSE 编码 + 回写）。本章并发 1 时客户端墙钟 77.75 ms 比 e2e 77.12 ms 大 0.63 ms（进程外段为正）；并发 32 时这个差涨到 4.15 ms。 正负取决于入站与出站两侧各占多少，而两侧都随负载变化。
  3. 不在排队（queue 始终约 0.01 ms），而在两处：batch 变大后每个 decode step 变长（decode 71.77 → 84.81 ms），以及 32 条流同时在事件循环里做 detokenize 与 SSE 编码，进程外段从 0.85 ms 涨到 4.15 ms。 两项相加仍解释不了全部差值，剩下的落在 prefill（5.12 → 10.69 ms）与统计口径差异上。
  4. 因为成本是自己的，收益是别人的。in-loop 时这 11 ms 会加到所有在跑的 请求的 token 间隔上；to_thread 后尖峰消失，代价只是发起方多等一次线程往返。 多租户下这笔交易成立。
  5. 4 个 ASCII 字符的 token 编码成 JSON 是 {"token": 1234} 这类形式，约 20 字节； 加 data: 前缀和两个 \n，一条事件约 27 字节；再套 chunked 的长度前缀、 CRLF 和响应头摊销。协议开销是有效载荷的十倍量级。
  6. 本章所有请求用同一条 prompt。开着前缀复用，第一条之后的 prefill 会塌到接近 0， 运行段的构成就失真了；prefill/decode 的对照和前端段的减法都会失去意义。
