5.1

prefill 与 decode 的系统性质

比较 prefill 与 decode 的工作量、批量收益和计时口径，分析缓存与传输成本。

实测机器 crater (RTX 5090 D, sm_120) · vLLM 0.29.0 · Qwen3-1.7B前置 0.2（roofline）· 3.1/3.3（两相的 attention）· 5.2（KV 分页）

本章回答三个问题

3.1 和 3.3 分别从 attention 的角度看过 prefill 和 decode。 这一章从整个引擎的角度看：这两相对硬件的要求是相反的， 于是引擎的每一个调度决策都要在它们之间做取舍。

  1. 两相分别落在 roofline 的哪一侧？
  2. 加 batch 对它们的影响为什么完全不同？
  3. 一个请求的时间花在哪里？该用什么指标衡量？

一 · 两相在 roofline 上的位置

Qwen3-1.7B，权重 bf16 = 3.20 GiB，机器平衡点 144.2 FLOP/byte：

相 batch 序列 FLOP 权重字节 算术强度 落在哪一侧
prefill 1 2048 7.05e12 3.44e9 2048.0 算力
prefill 1 4096 1.41e13 3.44e9 4096.0 算力
decode 1 1 3.44e9 3.44e9 1.0 带宽
decode 8 1 2.75e10 3.44e9 8.0 带宽
decode 64 1 2.20e11 3.44e9 64.0 带宽
decode 256 1 8.81e11 3.44e9 256.0 算力

上表由 labs/L5/prefill_decode.py:96–112 的公式生成，不是硬件流量实测。它把主要参数都近似为每位置参与矩阵乘的权重，并假设一批共享一次读取，得到 I≈BS。实际 embedding 查表、只计算末位置 lm_head、KV 和中间张量都需要另算，较细的账见 L0.2。

按这组参照，bf16 线性层的权重模型平衡点为 232000/1608.6≈144.2 FLOP/byte。普通 decode 的 S=1，因此简化模型对应 batch 约 144（若未将乘加算作 2 次浮点运算则为 72）。该数值为理论简化模型的平衡点，并非实测的瓶颈切换点。

长 prefill 具有更多权重复用机会，小 batch decode 的权重成本较难分摊；但请求整体可能同时受 KV、提交、同步等因素影响。

二 · 本组负载中 decode 的批量收益更大

同一个引擎、同一台机器、同样的 batch 扫描：

prefill（每条 1024 token，只生成 1 个）

batch 总耗时 ms 每条 ms prompt tok/s 相对 batch=1
1 20.0 20.0 51177 1.00×
2 35.0 17.5 58454 1.14×
8 130.8 16.3 62632 1.22×
32 514.6 16.1 63679 1.24×

decode（每条 prompt 128 token，生成 64）

batch 每步 ms output tok/s 相对 batch=1
1 4.496 222 1.00×
4 4.531 883 3.97×
16 4.752 3367 15.14×
32 4.791 6679 30.03×
64 5.134 12467 56.05×

batch 从 1 到 32：prefill 吞吐只涨 1.24×，decode 涨 30×。

原因就是第一节那张表：prefill 在 batch=1 时就已经算力受限， 加 batch 只是把更多工作排队，单位时间做的事没变多。 decode 的每步时间从 4.496 涨到 5.134 ms（只涨 14%）， 却同时服务了 64 倍的请求——权重读取被 64 条请求分摊了。

这两张表是引擎所有调度决策的出发点

本组长 prompt 的 prefill 批量收益小于短 prompt decode；短 prefill 和其他形状仍需单独测量。

推论一串： - 调度器应该优先把 decode 的批凑大（5.3 的 continuous batching） - chunked prefill 可限制单轮工作量，但要测量其对吞吐与延迟的影响 - 两相甚至可以放到不同的机器上（PD 分离，L6.4） - 评估引擎不能只报一个"吞吐"（0.3 §陷阱 1）

三 · 首 token 调用时间与后续步耗时估计

脚本分别计时只生成 1 个与生成 65 个 token 的离线 LLM.generate() 调用，以两者差值除以 64 估算后续步耗时。首个调用包含请求处理、prefill 和采样，不是 HTTP 客户端 TTFT；原日志的“生成 64”列实际表示额外 64 步。下表保留原始读数并改正列名。

prompt 长度 额外生成步数 首 token 调用 ms 差分 ms/步 65-token 调用 ms 首 token 调用占比
128 64 5.67 4.489 293.0 1.9%
512 64 11.03 4.430 294.5 3.7%
2048 64 37.04 4.515 326.0 11.4%
4096 64 75.54 4.493 363.1 20.8%
  • 首 token 调用时间随 prompt 长度增加（5.67 → 75.54 ms，prompt 涨 32 倍， TTFT 涨 13 倍——不是严格线性，因为有固定开销）。
  • TPOT 基本不变（4.43–4.52 ms）。这里 KV 还很小， 按 3.3 的账，KV 长了 TPOT 才会涨。

所以负载形态决定了该看哪个指标：

负载 主导指标 例子
长 prompt + 短输出 TTFT 文档问答、代码补全、分类
短 prompt + 长输出 TPOT 对话、创作、推理链
两者都长 都要看 Agent、长文摘要

只报"吞吐"会同时掩盖这两个。 一个把 TTFT 做到很差、 靠大批把吞吐堆上去的引擎，在交互场景里是不能用的。

四 · 长度不齐的浪费

16 条请求，两种输出长度分布：

长度一致（都生成 64）
  实际生成 1024 token，耗时 333.3 ms，吞吐 3073 tok/s
  最长 64，若静态批处理要按最长算：1024 个 step 的位置
  利用率 = 1024 / 1024 = 100.0%

长度不齐（1..128 均匀）
  实际生成 949 token，耗时 551.9 ms，吞吐 1720 tok/s
  最长 114，若静态批处理要按最长算：1824 个 step 的位置
  利用率 = 949 / 1824 = 52.0%

静态批处理在长度不齐时只能拿到 52% 的利用率—— 一批一起开始、一起结束，最长的那条决定整批时长， 先结束的请求占着位置什么也不干。

但第二行的吞吐也掉了一半，而 vLLM 已经是连续批处理

这两件事要分开：

  1. 52% 是按静态补齐计算的有效位置比例，浪费比例约为 48%。
  2. 吞吐从 3073 掉到 1720，是因为这里没有排队的新请求可以补位。 批在跑的过程中不断有请求结束，活跃数从 16 一路掉到 1， 最后几步是在按 batch=1 的速度跑（第二节：batch=1 只有 222 tok/s）。

连续批处理消除的是「等最慢的那条」，不是「没活干」。

给它一个队列，收益就出来了：

一次提交 64 条（长度同样 1..128 不齐）
  实际生成 4162 token，耗时 748.1 ms，吞吐 5563 tok/s

对照 16 条不齐时的 1720 tok/s——3.2×。 早结束的请求空出的位置立刻被后面的补上，批一直是满的。

本实验是一次性提交后等待整批结束的批量测试。它不等同于维持固定并发、完成一条再补一条的闭环压测，也不是按独立到达过程持续发请求的开环压测。两种压测都可用于分析连续批处理，但分别回答固定并发与给定到达率下的问题。

五 · 设计取舍

5.1 为什么不能用一套参数同时优化两相

两相的最优配置是冲突的：

prefill decode
想要的 batch 小（已经算力受限，大批只增加延迟） 大（越大越摊薄权重）
想要的 kernel 形状 方阵（2.7 §六：cuBLAS 在这里到 92% 峰值） 瘦长（M 很小）
对 KV 的操作 写入 读取
瓶颈 算力 带宽
延迟指标 TTFT TPOT

一个引擎在同一个 step 里既做 prefill 又做 decode（混合批）， 就必须在这两组要求之间折中。chunked prefill（把长 prompt 切成小块 插进 decode 批里）就是这个折中的具体形态： 它牺牲一点 prefill 的效率，换 decode 批不被长 prefill 打断。

5.2 PD 分离的动机与代价

既然两相要求相反，最彻底的解法是放到不同的机器上： prefill 集群配算力强的卡，decode 集群配带宽大、显存大的卡。

代价是 KV 要跨机传输——prefill 算出的 KV 必须送到 decode 机器。 1.5 实测本机跨机带宽上限只有 3.1 GB/s，而 3.3 算过 一条 4096 上下文的请求 KV 为 448 MiB，即 469762048 B。按 3.1 GB/s 估计，单向传输约 152 ms， 比 prefill 本身（75 ms）还久。

所以 PD 分离在慢网络上是负收益。 它需要高速互联才成立—— 这也是为什么它先出现在有 NVLink/InfiniBand 的集群上。L6.4 会展开。

5.3 分离处理需要覆盖协调成本

本章的形态在系统里反复出现：当一个系统里存在两种性质相反的工作时， "统一处理"和"分开处理"之间的选择，取决于分开的协调成本。

  • 协调成本低（同一进程内切换）→ 混合批 + chunked prefill
  • 协调成本高（跨机传 KV）→ 只有在互联足够快时才分离

比较时需要计入协调成本。 3.3 的分页和 4.3 的 KV 量化对照都说明， 框架层的模拟会把协调成本量错。

 40 def safe_util(reserve_gib=4.0, cap=0.55):
 41     """按**当前空闲显存**算一个安全的 gpu_memory_utilization。
 42 
 43     crater 是共享机器，可能有别人的作业在跑（本轮就撞上过一次
 44     loopserve 的 lightnav_replay_gate 占了 14 GB）。
 45     写死 0.55 会在别人占了一半时直接启动失败，
 46     更糟的是在别人**之后**才启动时把对方挤掉。
 47     所以按空闲量算，并额外留 reserve_gib 给对方增长。
 48     """
 49     free, total = torch.cuda.mem_get_info()
 50     gib = 1024 ** 3
 51     usable = max(free / gib - reserve_gib, 1.0)
 52     util = min(cap, usable / (total / gib))
 53     print(f"  [显存] 空闲 {free / gib:.1f}/{total / gib:.1f} GiB，"
 54           f"留 {reserve_gib:.0f} GiB 给他人 -> gpu_memory_utilization={util:.2f}")
 55     return util

运行前核算 GPU 显存预算

本实验需要为权重、KV 和临时空间分配显存。先检查 GPU 当前占用，再设置与负载匹配的预算。脚本中 safe_util(reserve_gib=4.0, cap=0.55) 是早期实验默认值，既不是全项目上限，也不能保证共享运行安全。独占 GPU 可按实验需要使用可用容量；共享运行不得挤占其他任务。

建议的消融

  1. 把 [B] 的 decode 部分扫到 batch=256，看 tok/s 什么时候不再线性上涨。 按第一节的表，越过平衡点（简化权重模型的 batch≈144）之后应该开始转向算力受限。
  2. [C] 换成 prompt 固定 128、生成长度扫 16/64/256/1024， 看 TTFT 占比怎么变。
  3. [D] 把提交数从 64 加到 256，看吞吐还能不能继续涨。 这条曲线的拐点就是这台机器的最大并发。
  4. 打开 enforce_eager=False（用 CUDA Graph）重跑 [B] 的 decode， 对照 2.6b 测到的"CPU 侧 launch 从 14003 降到 863"—— 看在 tok/s 上体现为多少。

七 · 陷阱

  1. 只报一个"吞吐"会同时掩盖 TTFT 和 TPOT。 必须分相位报。
  2. 本组 prefill 加 batch 的收益为 1.24×。 短 prompt 或其他形状不能沿用这一结论。
  3. decode 的 batch 收益接近线性（本章 56×），但要 KV 显存装得下。
  4. 一次性批量测试包含尾部排空。 没有后续请求补入时， 最后几步退化成 batch=1（本章 3073 → 1720 tok/s）。
  5. 共享机器上不要写死 gpu_memory_utilization。 按空闲量算并留余量。
  6. TPOT 在短上下文下几乎不变，别用短测试外推长上下文的 TPOT（3.3）。
  7. PD 分离要先量 KV 传输成本。 按 3.1 GB/s 传输 448 MiB 的公式估计约为 152 ms， 比 prefill 本身还久。

八 · 自测题

1. 为什么 prefill 加 batch 几乎没收益，而 decode 有 56 倍？

看算术强度。权重字节是常数（每步读一遍全部权重），FLOP 正比于处理的 token 数。

  • prefill 一次处理 S 个 token，算术强度 ≈S。S=1024 时已经是 1024， 远超平衡点 144，已经算力受限。加 batch 只是排更多队。
  • decode 一次处理 1 个 token，算术强度 = batch。batch=1 时是 1， 严重带宽受限。加 batch 直接把权重读取分摊掉。

本章实测：decode 每步时间从 4.496 只涨到 5.134 ms（14%）， 却服务了 64 倍的请求。

2. 你的服务 P99 TTFT 很差但吞吐很高，可能是什么原因？

最可能是调度偏向 decode：为了把 decode 批凑大， 新到的请求要等当前批跑完才能 prefill，排队时间全算进 TTFT。

或者长 prompt 阻塞：一条 4096 token 的 prefill 要 75 ms（本章实测）， 这段时间所有 decode 都停着，其它请求的 TTFT 和 TPOT 都被拖长。

chunked prefill 就是针对后者：把长 prefill 切成小块插进 decode 批， 让每一步的时间可控。代价是 prefill 的效率略降（切碎了不如整块）。

诊断：分别记录排队时间和 prefill 时间，看 TTFT 主要花在哪一段。

3. 一次提交 16 条与 64 条，为什么吞吐可能不同？

更多请求使引擎拥有更大的可调度集合，也改变了运行中 batch 的分布。但本次没有记录完整调度轨迹，不能直接断言 64 条时“批始终满载”。

应保存每轮活跃请求数、准入与完成时间，区分初始并发、更长的饱和区间和尾部排空效应。持续负载还需用开环或固定并发闭环测试。

4. PD 分离听起来很合理，什么情况下它是负收益？

当 KV 跨机传输的时间超过它省下的时间时。

按本书的实测：一条 4096 上下文请求的 KV 为 448 MiB（3.3）， 按 1.5 中 3.1 GB/s 的带宽记录估计，单向传输约 152 ms， 而 prefill 本身只要 75 ms（本章）。传输比计算还贵。

所以 PD 分离要求高速互联（NVLink/InfiniBand/RDMA）。 在普通以太网上做，等于给每个请求加一段比 prefill 还长的延迟。

这也是一个通用判据：分离的收益必须大于协调成本， 而协调成本要实测，不能假设"网络很快"。
