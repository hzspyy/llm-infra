5.9

采样引擎

比较 vLLM 与 SGLang 的采样顺序、并列候选和 logprobs 处理，分析数值与性能差异。

实测机器 crater · RTX 5090 D · vLLM 0.29.0 · SGLang 0.5.19 · FlashInfer 0.6.18前置 0.5 logits 到文本 · 4.2 数值系统 · 5.6 约束解码

本章回答三个问题

采样引擎把一行 logits 变成一个 token。它还负责惩罚重复、裁剪候选、管理随机数，并按请求返回 logprobs。即使参数名称相同，处理顺序和边界条件不同也会改变结果。

  1. temperature、top-k、top-p、min-p 和三种重复惩罚分别改了什么，怎样自己实现？
  2. vLLM 与 SGLang 的处理顺序、并列值和返回概率有何差异？
  3. 采样与 logprobs 在 GPU 和真实生成请求中分别花多少时间？

实验覆盖采样函数、SGLang 的 CPU/GPU 路径及 vLLM 端到端生成。大 batch 下，Triton 过滤与排序参照仍有一个候选 token 的差异，原因尚未确定。

心智模型

logits 是模型为词表中每个 token 输出的分数。概率分布由这些分数计算得到；修改分数或候选集合，都会改变采样分布。

下图是本版本 vLLM 中随机采样的主线。左侧的 raw logprobs 从处理前的 logits 计算，右侧才是真正参与采样的分布。temperature 为 0 时走 greedy 分支，直接从惩罚后的 logits 选 argmax，不执行右侧随机过滤链。

raw logprobs 表示原始分布下的对数概率，processed logprobs 表示处理后的对数概率。一个 token 被 top-k 强制选中时，后者可以是 0，前者仍小于 0。下文会调用真实 Sampler 验证。

机制拆解

1. temperature 改变分布的尖锐程度

对 temperature T>0，

pi=exp(zi/T)∑jexp(zj/T).

降低 T 会放大分数差距；增大 T 会让概率更接近。实际实现先减去最大值以避免 exp 溢出。T=0 应走 argmax，不能直接除以零。

greedy 只在给定 logits上确定。模型计算可能因 batch、数值精度和 kernel 路径变化而产生不同 logits；temperature 为 0 不能证明整个系统逐位确定。

2. 三种惩罚不是同一个开关

设 token i 的原始 logit 为 zi，已生成次数为 ci，repetition penalty 为 r>0。本版本 vLLM 对 prompt 或 output 中出现过的 token 做：

zi(r)={zi/r,zi>0,zir,zi≤0.

当 r>1 时，两种符号的分数都下降。把负数也除以 r，反而会提高它。

frequency penalty 按生成次数扣分，presence penalty 只看生成过没有：

zi′=zi(r)−αci−β1[ci>0].

这里 frequency/presence 的计数来自 output，repetition 的出现集合则包含 prompt 与 output。三种操作需要按各自定义构造历史计数或出现标记。

可核对的小例子：原始 logits 为 [-1, 2, 1, 0.5]，prompt ids 为 [0,1]，output ids 为 [3,3,1]，r=1.5、α=0.25、β=0.5。token 3 的计算是 0.5/1.5 − 2×0.25 − 0.5。完整向量与真实 GPU penalty 操作的结果在原始日志中。

3. top-k、top-p、min-p

top-k 保留分数最高的候选。遇到第 k 名并列时，按“阈值”保留可能多于 k 个，按“位置”保留则恰好 k 个；本章确实测到了两种做法。

top-p 又叫 nucleus sampling：按概率从大到小累积，保留覆盖指定概率质量 p 的前缀，至少留下一个候选。计算累计概率前是否先做 top-k 并归一化，会改变结果。

min-p 按最大概率的比例设阈值，保留满足 pi≥mpmax 的 token。它不是“保留概率大于 m 的 token”。对同一 softmax 分布，该条件可写成：

zi≥zmax+logm.

这里的 z 是已经除以 temperature 的分数。m=0 表示禁用 min-p，不应计算 log 0 后继续一般参数路径。

这些操作通常通过把丢弃位置设为负无穷实现。下一次 softmax 中这些位置概率为零。过滤后的合法集合必须非空；NaN、全负无穷和越界 token id 都应作为错误处理。

4. 顺序改变候选集合

取概率 [0.5,0.3,0.15,0.05]，k=2、p=0.6。先 top-k 后归一化，前两项成为 [0.625,0.375]，top-p 只需第一项。若在原概率上同时求 top-k 与 top-p，第一项只有 0.5，需要保留第二项。

5. 从概率分布抽一个 token

标准库 mini 实现用累计概率与均匀随机数比较。vLLM 的 native 路径则使用指数噪声：对每个 token 生成独立 qi~Exp(1)，选择使 pi/qi 最大的项。

原因是 qi/pi 服从速率为 pi 的指数分布。其成为最小值的概率为：

∫0∞pie−pit∏j≠ie−pjtdt=pi∑jpj.

因此它与 categorical sampling 具有相同的理想分布，但随机数消耗顺序可以不同。相同 seed 不足以保证换后端后得到同一串 token；应分别测试分布正确性和同一路径的重复性。

设计取舍

不变量是参数、history、随机状态和 logits 必须属于同一请求、同一步、同一词表。输出 token 必须来自规定的候选集合；返回的 logprobs 必须注明来自处理前还是处理后分布。

引擎持有请求的历史与采样配置，sampler 接收整理后的 batch metadata，GPU kernel 执行张量变换。按请求保存 generator 可以减少其他请求对随机序列的影响，但本版本 vLLM 的 FlashInfer 路径遇到 per-request generator 时会回退 native。可复现性要求会影响执行路径。

增加一个采样后端，至少要处理调度选择、过滤顺序、并列值、数值精度、随机状态和返回字段。验证不仅包括“能抽到 token”，还包括 mask 边界与 logprobs 的语义。错误也应分层发现：非法参数在入口检查；全非法 logits、越界 id 和 kernel 输出异常在执行路径检查。

设计选择 收益 代价或适用边界
完整排序后过滤 参照实现直观，便于检查每个边界 生成排序值、索引与累计概率；大词表代价可观
pivot / rejection sampling 可以避免完整排序 数值边界、并列值及随机路径更难核对

单独保存每请求 RNG 更清楚的请求级随机状态归属 可能失去批量采样快路径；跨后端仍不保证同 token

两引擎的端到端对照

上面几节都在库层比过滤与概率。这一节往上走一层：同一份 input_ids 分别提交 vLLM /v1/completions 与 SGLang /generate，比贪心 token、逐 token logprob 和同 seed 的采样重复性（labs/L5/sampling_engine_e2e.py + run_sampling_e2e.sh， results/crater/sampling/sampling-e2e-20260913/）。输入用本地 tokenizer 编出的 id， 两端都不再走自己的分词，所以比较的是引擎本身。

prompt greedy token 数 逐 token 相同 首个不同位置 可比区间内最大 |Δlogprob|
0 32 / 32 否 0 无可比区间
1 32 / 32 是 — 9.14e-02
2 32 / 32 否 11 7.85e-02（前 11 个位置）

读法有一条前提：logprob 只在两端 token 相同的位置上可比。 一旦某个位置分岔，后续就是两条不同的轨迹，逐位置相减没有意义。 所以第 0 条 prompt 虽然也能算出 1.66 这样的差值，但它没有可比区间，不能当反驳。 真正能引用的是后两行：两引擎在同轨迹上的逐 token logprob 差在 7.8e-02 ~ 9.1e-02 量级（bf16 数值），而 greedy 是否逐 token 相同取决于 有没有撞上近似并列——第 2 条 prompt 在第 11 个位置分岔，之前 11 个位置的 logprob 差只有 7.85e-02。

同 seed 采样的重复性两端不同：temperature=0.8, top_k=50, top_p=0.9 下， vLLM 用 seed=1234 三次请求逐 token 相同（3/3）， SGLang 用 sampling_seed=1234 三次各不相同（3/3 不同）。这是接口语义差异， 不是数值差异；本节只记录现象，没有进一步定位它的随机数来源。

seed 这个参数名在 SGLang 上会 500。 第一次跑时按 vLLM 的习惯传 seed， SGLang 直接返回 Internal Server Error，服务端日志是 TypeError: Unexpected keyword argument 'seed'——它的字段叫 sampling_seed （srt/sampling/sampling_params.py:87）。这条差异不会在编译期暴露， 只在真实请求时炸在 HTTP 500 上，属于端到端对照才能发现的那类问题。

beam search：只有一个引擎有

计划里的「beam search 对照」在固定版本上做不成跨引擎版本： vLLM 0.29.0 的 v1 已经没有 beam search（use_beam_search 不在 sampling_params.py 与 arg_utils.py 里，v1/ 下唯一的 "beam" 命中是一个 无关的 ROCm attention 后端文件）；SGLang 0.5.19 有原生实现 （sglang/srt/beam_search/，参数是 sampling_params.beam_width， n 表示返回多少条，n ≤ beam_width）。

在 SGLang 上 beam_width=4, n=4 的请求确实跑了，逐 beam 序列也已经取到 （labs/L5/sglang_beam_probe.py，原始响应 beam-raw-*.json 一并落盘）。 beam 请求的响应结构与普通请求不同，键位是：

body.output_ids                       最好一条 beam 的 token id（24 个）
body.meta_info.completion_tokens      4 条之和（96 = 4 × 24）
body.meta_info.sequence_score         该请求的 beam 分数（per-request，不是逐 beam）
body.meta_info.beam_results[i]        {output_ids, text, meta_info}，4 条

逐 beam 分数是可以读出来的：每条 beam_results[i] 自带 meta_info.sequence_score， 是该 beam 自己的长度归一化分数（beam_group.py:239：cum_logprob / num_tokens ** length_penalty）， 顶层 sequence_score 只是最高分那条的副本。

labs/L5/beam_search_scan.py 在 GSM8K 固定 96 题上扫 beam_width 1/2/4/8 （max_new_tokens=256、temperature=0、按最终数字判对错，与 9.4 同一套提取口径； results/crater/5.9/beam-scan-n96-20260921/）：

四条结论：

  1. beam 确实比贪心好，但幅度远小于代价。 width=4 时 0.188 → 0.250（+6 题，相对 +33%）， 而墙钟 6.1 → 23.0 s（3.8×）、completion_tokens 严格等于 width × 256。
  2. 聚合涨幅掩盖了逐题的大幅换位。 相对贪心新增 17 题正确、同时丢掉 11 题： 96 题里有 28 题（29%）的对错发生了变化。只报总准确率会把这件事藏掉。
  3. 候选里有正确答案的比例明显高于选中比例：width=4 时 0.333 对 0.250， 即 8/96 题里某条 beam 已经答对、但长度归一化分数没有把它排到第一。 这就是"逐 beam 分数"这一层证据的价值：beam 的上限不是搜索宽度，而是打分与选择规则。
  4. width=8 反而更差（0.229，候选内 0.250）：更多候选没有带来更好的排序， 而计算量翻倍。本版本的长度惩罚固定在 1.0——beam_group.py:68 的默认值， 而 coordinator.py:200 构造 BeamGroup 时没有传 length_penalty， SamplingParams 里也没有这个字段（传进去直接 500）。 要扫长度惩罚必须改源码或换版本，因此"惩罚改变选中哪条 beam"在本版本不可测。

KV 分叉是可测的、而且会先撞上限：把 96 题一次性发出去时， width≥4 的请求直接返回 HTTP 500（KV 池不够）——分块提交（每批 16 条）后才跑通。 也就是说 beam 的容量代价是 width × 序列数 条并存的 KV，而不是"多几条候选"。

消融与未测范围

  • 改变词表维度、batch、k/p 与概率分布形状，覆盖平坦分布、尖峰与并列值；不要只用一种随机 logits。

  • SGLang 端到端已补一部分：同一批 input_ids 下的贪心、logprob 与同 seed 重复性已对照 （见「两引擎的端到端对照」），并发现 seed/sampling_seed 的接口差异； 但 beam 请求的逐 beam 输出提取路径未覆盖，高并发下的排队与尖峰也未对照。

前沿

高效采样不一定先完整排序。FlashInfer 将多轮 rejection sampling 放进 GPU kernel，并提供 top_k_first 与 joint 两种过滤方式；选择时要同时看性能与分布语义。FlashInfer 官方文档

本地 vLLM 的 Triton 文件注明采用 Qrita 的 pivot-based 思路。该方向把选择问题转化为阈值搜索，减少完整排序，但边界值仍需与参照核对。本章已经发现未解释的候选差异，因此不引用论文速度作为本实现的正确性或性能保证。Qrita

训练与推理需要一致的概率定义时，raw/processed、temperature、过滤顺序和精度都必须固定。SGLang 源码为部分 RL 路径单独计算 log-softmax，也说明“生成的 token 相同”和“训练所需 logprob 相同”是两项检查。

陷阱

  1. 把负 logit 也除以 repetition penalty。 r>1 时这会奖励而非惩罚负分 token。
  2. 只对齐参数名。 top-p 归一化位置、min-p 顺序和 ties 都能改变候选集。
  3. 把 logprobs=0 当成关闭。 它仍返回 sampled token 的 logprob；关闭用 None。
  4. 把 raw logprob 当成实际采样概率。 top-k=1 时实际选择可为必然，raw 分数仍小于 0。
  5. 把同 seed 当成跨引擎相同输出。 随机算法、请求位置与随机数消耗方式都可能不同。
  6. 只测 batch 1 或只测大 batch。 会错过实现切换；本章在 7→8 两侧测量。
  7. 丢掉正确性失败，继续只报速度。 本章保留了 batch 64/256 的候选差异，尚不能声称等价。
  8. 把 beam search 写成不存在。 本版本有明确实现，但本章未运行其性能对照。

自测题

1. top-k=2 是否一定只剩两个 token？ 不一定。按第 k 名的值作阈值，可能保留所有同分项；按排序位置裁剪才会只保留 k 个。本章还测到同一引擎的 CPU/GPU 路径对此行为不同。
2. 输入概率为 [0.5,0.3,0.15,0.05]，为什么 k=2、p=0.6 有时只留下 token 0？ top-k 后归一化得到 [0.625,0.375]，第一项已经超过 p。若 top-p 使用原始分布，则需要保留第二项。先确定顺序，再谈参数是否相同。
3. 选出的 token 概率为 1，返回 logprob 却是负数，是否一定有错？ 不是。若返回的是 raw logprob，它来自过滤前的原始分布。应先检查 logprobs_mode；本章的实际 Sampler 分别返回 -0.6931471824645996 与 0.0。
4. 采样函数比另一个快，但候选集合相差一个 token，能直接替换吗？ 不能把它称为等价替换。先核对预期语义、数值边界、ties 与终止条件，再决定差异是否可接受；不能用速度抵消未解释的正确性差异。
5. logprobs 从 5 增到 20，GPU 时间几乎不变，是否可以忽略成本？ 不可以。GPU 仍有全行计算和选择；返回记录数、CPU 处理和序列化体积还会变化。应同时测 GPU 工作和真实请求，而不是从一个独立计时概括整个服务。
