5.2

KV cache 管理：PagedAttention 与 prefix cache

介绍 block table、引用计数和前缀缓存，比较 vLLM 的块哈希与 SGLang 的基数树。

实测机器 crater (RTX 5090 D) 与 crater2 (RTX 5090) · vLLM 0.29.0 · SGLang 0.5.19前置 L0.2（KV 账本）· L0.1（调用栈第 10–11 阶段）

本章回答三个问题

  1. KV cache 为什么必须分页？不分页会发生什么，能量化吗？
  2. 两个请求共享一段前缀时，KV 复用的粒度是什么？如何通过物理实验测出这一粒度？
  3. vLLM 的块哈希表和 SGLang 的基数树，各自换来了什么、放弃了什么？

这一章把两个问题分开：分页解决 KV 放在哪里，前缀缓存解决哪些 KV 可以再次使用。 block table 记录逻辑块对应的物理块编号；哈希表或基数树帮助寻找可复用的前缀。 本章包含一个最小分配器和已有的耗时记录。块数的理论预测与引擎实际命中量 不是同一份证据，下文会明确区分。2026-09-10 补测已把命中量直接读出来 （见「动手 lab」末尾的补测一节）：块数与公式逐点一致， 但"每少算一块省多少时间"仍然只是预测。

心智模型：把 KV cache 当虚拟内存

机制拆解

分页与连续预分配的容量对照

假设不分页——每条序列的 KV 必须是一整段连续显存。那么你必须在请求到达时就 按 max_model_len 预留空间（因为你不知道它会生成多长）。

用 L0.2 的账本算（Qwen3-1.7B，max_model_len=40960）：

每条序列预留=40960×114.69KB=4.70 GB

一张 32 GB 卡去掉 3.44 GB 权重与杂项，剩约 25 GB，只能开 5 条并发。 而实际请求平均可能只用 2048 token —— 95% 的预留是浪费的。

这就是 PagedAttention 论文里说的两类碎片：

  • 内部碎片：预留 40960，实际用 2048 → 浪费 38912 个 token 的空间
  • 外部碎片：连续块之间的空隙无法被别的序列使用

分页把两者同时消掉：按需分配 16 token 的小块，内部碎片上界是 15 个 token （最后一块没填满），外部碎片直接消失（因为不要求连续）。

本机实测：gpu_memory_utilization=0.35 时引擎报 num_gpu_blocks = 4064。 反推 4064×16=65024 个 token 的 KV，即 65024×114.69KB=7.46 GB。 而 33.7×0.35−3.44(权重)−杂项≈7.5 GB —— 和 L0.2 的账本对上了。

复用的粒度是「块」，不是「token」

一个块只有填满（16 个 token）才会被哈希、才能被复用。这意味着：

  • 共享 16 个 token 的前缀 → 复用 1 块
  • 共享 31 个 token 的前缀 → 也只复用 1 块（第二块只有 15 个 token，没填满）

这可以直接测出来，而且是本章最漂亮的实验（下面 lab 一节）。

块哈希将前缀纳入缓存身份

hash_block_tokens 的签名很说明问题：

def hash_block_tokens(hash_function, parent_block_hash, curr_block_token_ids, extra_keys):
    if not parent_block_hash:
        parent_block_hash = NONE_HASH
    return BlockHash(hash_function((parent_block_hash, tuple(curr_block_token_ids), extra_keys)))

哈希的输入包含 父块的哈希。所以第 k 块的哈希实际上编码了「前 16k 个 token 的完整内容」。

为什么必须这样？因为 KV 是上下文相关的：同样 16 个 token，跟在不同前缀后面， 算出来的 K/V 完全不同（attention 要看前面所有 token）。 如果只哈希块内容，就会错误复用——这是正确性问题，不是优化问题。

extra_keys 是缓存身份的另一半。vLLM 0.29.0 的 generate_block_hash_extra_keys （v1/core/kv_cache_utils.py:583）把它拼成四类：

来源 内容 生效范围
LoRA request.lora_request.lora_name（_gen_lora_extra_hash_keys，:541） 所有块
多模态 (mm_feature.identifier, offset − start_token_idx)（_gen_mm_extra_hash_keys，:470） 含该输入的块
cache_salt 请求带的隔离串（只在 start_token_idx == 0 时加入） 第 0 块
prompt_embeds 每块嵌入的 sha256（_gen_prompt_embeds_extra_hash_keys，:556） 有嵌入的块

labs/L5/cache_key_identity.py 直接用引擎自己的哈希器（get_hash_fn_by_name + init_none_hash + get_request_block_hasher）对同一串 token 逐字段做对照：

  用例                                      首个不同块      共有前缀块                          结论
  LoRA 名字 A（其余不变）                             0          0                 进键：第 0 块即不同
  LoRA 名字 A vs B                              0          0                  进键：名字不同即不同
  同名 A、不同路径/权重                                —          6                   不进键：同名即同键
  cache_salt = tenant-1                       0          0  进键：salt 只加在第 0 块，尾 5 块相同 0
  temperature/top_p/seed 改变                   —          6                         不进键
  同一块 token、不同父块哈希                            0          0                     进键：滚动哈希

三条读法：

  1. 进键的是 adapter 的"名字"，不是它的权重或 revision。 同一个名字换掉权重文件， 块哈希逐位不变——引擎会继续复用旧 adapter 算出的 KV。5.10 的实测与此一致： 同名热更新后请求仍命中旧前缀缓存，输出与旧版本相同。
  2. cache_salt 只加在第 0 块，但父链会让后面每一块都不同（上表"尾 5 块相同 0"）。 一行隔离串换来整条序列独立缓存，这是多租户隔离最省的实现。
  3. 采样参数不进键。 temperature/top_p/seed 不改变 KV，只改变从 logits 到 token 的 那一步（5.9），所以同一 prompt 换采样参数仍能命中前缀缓存。

模型权重与 revision 也不在键里。换模型要换引擎实例，进程内的块表本来就是空的， 所以"同一引擎内改权重"不是这套缓存承诺支持的更新方式。

还有一个细节：NONE_HASH 由一个可配置的 seed 派生，代码注释写着 「Components that must agree on NONE_HASH across processes (the P2P tier…)」—— 因为 PD 分离时，prefill 机器算出的块哈希必须和 decode 机器一致， 否则 KV 传过去认不出来（L6.4）。一个种子的设计，牵着整个分离架构。

工程实现 · 源码解析

A. vLLM：块哈希表 + 双向链表空闲池

块的元数据（v1/core/kv_cache_utils.py:166）：

class KVCacheBlock:
    block_id: int                    # 0 .. num_gpu_blocks-1
    ref_cnt: int = 0                 # 有几条序列在引用它
    _block_hash: BlockHashWithGroupId | None = None   # 满块且已缓存时才有
    _block_hash_num_tokens: int | None = None
    prev_free_block: "KVCacheBlock | None" = None     # 空闲链表指针
    next_free_block: "KVCacheBlock | None" = None
    is_null: bool = False

注意 ref_cnt 与两个链表指针在同一个对象上。这是有意的——见下面。

空闲池是手写的双向链表（v1/core/kv_cache_utils.py，FreeKVCacheBlockQueue 的 docstring 把理由写得很清楚）：

This class organizes a list of KVCacheBlock objects to a doubly linked
list of free blocks. We implement this class instead of using Python
builtin deque to support removing a block in the middle of the queue
in O(1) time. To close the performance gap to the builtin deque which is
implemented in C++, this class does not allocate any Python objects when
manipulating the linked list. Instead, this class manipulates the
prev_free_block and next_free_block attributes of the given blocks.

三个设计决策，每个都有代价：

  1. 不用 collections.deque，因为要支持「从队列中间 O(1) 删除」—— 一个已缓存的空闲块被命中复用时，要立刻从空闲链表里摘掉，它可能在任意位置。
  2. 不新建任何 Python 对象——指针直接存在 KVCacheBlock 上。 因为这是每步都跑的热路径，Python 对象分配的开销会直接变成 TPOT。 （L0.1 测过：decode 每步只有 4.3 ms，其中约 1.24 ms 已经被 kernel launch 吃掉。）
  3. 代价是耦合：块对象既是数据又是链表节点，不能同时挂在两个链表上。

LRU 顺序也是手工维护的，同一段 docstring：

The queue is ordered by block ID in the beginning. When a block is allocated
and then freed, it will be appended back with the eviction order:
1. The least recent used block is at the front (LRU).
2. If two blocks have the same last accessed time (allocated by the
   same sequence), the one with more hash tokens (the tail of a block
   chain) is at the front.
Note that we maintain this order by reversing the block order when free
blocks of a request.

第 2 条很妙：同一条序列释放的多个块，尾部的块先被淘汰。 因为前缀（头部块）更可能被别的请求复用，尾部块是这条序列独有的。 实现方式是「释放时把块列表反转再 append」——一行 reversed() 承载了一条缓存策略。

分配（v1/core/block_pool.py:647）：

def get_new_blocks(self, num_blocks: int) -> list[KVCacheBlock]:
    if num_blocks > self.get_num_free_blocks():
        raise ValueError(f"Cannot get {num_blocks} free blocks from the pool")
    ret = self.free_block_queue.popleft_n(num_blocks)

    # In order to only iterate the list once, we duplicated code a bit
    if self.enable_caching:
        for block in ret:
            self._maybe_evict_cached_block(block)   # 从哈希表里摘掉旧内容
            assert block.ref_cnt == 0
            block.ref_cnt += 1
            ...
    else:
        for block in ret:
            block.ref_cnt += 1
            ...

注释 we duplicated code a bit 说明，这里通过重复少量代码避免再次遍历列表；该函数在每个 decode step 中调用。

_maybe_evict_cached_block 做的是：这个块被重新分配前，如果它还挂在 cached_block_hash_to_block 里（即"内容还在，只是没人引用"）， 就把哈希条目摘掉并发出淘汰事件。"空闲"和"已缓存"是两个正交状态： 一个块可以既空闲又缓存着有效内容——这正是 prefix cache 能跨请求命中的原因。

B. SGLang：基数树

mem_cache/radix_cache.py:238 的 TreeNode：

class TreeNode:
    def __init__(self, id=None, priority: int = 0):
        self.children = defaultdict(TreeNode)
        self.parent: TreeNode = None
        self.key: RadixKey = None            # 这个节点覆盖的 token 片段
        self.value: Optional[torch.Tensor] = None   # 对应的 KV 槽位索引
        self.lock_ref = 0                    # 相当于 vLLM 的 ref_cnt
        self.last_access_time = time.monotonic()
        self.hit_count = 0
        # ↓ 这三行是「KV 分级存储」，vLLM 的块对象里没有对应物
        self.host_ref_counter = 0
        self.host_value: Optional[torch.Tensor] = None   # 卸载到主机内存的副本
        self.write_through_pending_id: Optional[int] = None
        self.hash_value: Optional[List[str]] = None      # 每页的哈希（对外发事件用）
        self.priority = priority             # 支持优先级感知的淘汰

host_value / host_ref_counter 那三行很关键：SGLang 的树节点原生支持把 KV 卸载到主机内存 （backuped 属性、protect_host() / release_host()）。 在 vLLM 里这是一个外挂的 connector 层；在 SGLang 里它长在数据结构上。 这直接对应 L6.4「KV 作为数据平面」——树本身就是 HBM/DRAM 两级的目录。

匹配前缀（radix_cache.py:679）：

def _match_prefix_helper(self, node: TreeNode, key: RadixKey):
    access_time = time.monotonic()
    node.last_access_time = access_time
    child_key = key.child_key(self.page_size)
    value = []
    while len(key) > 0 and child_key in node.children.keys():
        child = node.children[child_key]
        child.last_access_time = access_time
        prefix_len = child.key.match(key, page_size=self.page_size)
        if prefix_len < len(child.key):
            new_node = self._split_node(child.key, child, prefix_len)   # ← 部分匹配就劈开
            value.append(new_node.value)
            node = new_node
            break
        else:
            value.append(child.value)
            node = child
            key = key[prefix_len:]
            if len(key):
                child_key = key.child_key(self.page_size)
    return value, node

_split_node 是基数树相对普通字典树的全部精髓。 当新请求和已有节点只匹配了一部分， 就把那个节点从中间劈成两个：公共部分变成父节点（可以被两边共享）， 剩余部分变成子节点。这样树的节点数始终等于"分叉数"，而不是 token 数。

def _split_node(self, key: RadixKey, child: TreeNode, split_len: int):
    new_node = TreeNode(priority=child.priority)
    new_node.hit_count = child.hit_count
    new_node.children = {key[split_len:].child_key(self.page_size): child}
    new_node.parent = child.parent
    new_node.lock_ref = child.lock_ref
    new_node.key   = child.key[:split_len]
    new_node.value = child.value[:split_len].clone()
    child.parent = new_node
    child.key   = child.key[split_len:]
    child.value = child.value[split_len:].clone()
    new_node.parent.children[key.child_key(self.page_size)] = new_node
    new_node.hash_value, child.hash_value = split_node_hash_value(
        child.hash_value, split_len, self.page_size)
    return new_node

注意 lock_ref 被原样继承给父节点：劈开后，原来引用 child 的请求现在 同时依赖 new_node 和 child，两者都不能被淘汰。

设计取舍：块哈希与基数树

维度 vLLM 块哈希表 SGLang 基数树
查一个前缀 O(块数) 次哈希查表，每次 O(1) O(前缀长度) 树遍历 + 可能的节点劈分
复用粒度 块（16 token） 页（可配），且节点可劈分
能否表达前缀间的包含关系 不能——每个块独立 能——父子节点即前缀关系
淘汰粒度 单块 LRU（双向链表） 整棵子树 LRU（叶子优先）
调度器能利用吗 只知道"块在不在" 能做 LPM（最长前缀优先）选批
分级存储（DRAM/SSD） 外挂 connector 长在节点上（host_value）
实现复杂度 低（约 700 行） 高（约 900 行 + 分裂/合并逻辑）
热路径开销 极低（无对象分配） 树遍历有指针追逐

没有哪个"更好"。 哈希表在高吞吐、前缀关系简单的场景下更快； 基数树在多轮对话、agent 会话树、few-shot 分支这类前缀高度嵌套的场景下赢面大—— 因为它能让调度器"看见"请求之间的相似性。

工程实现 · 自己写一遍

一个能跑的最小块分配器 + 前缀缓存，约 60 行。三个数据结构对应三件事：

class MiniBlockPool:
    """把 vLLM 的三件核心机制压到最小：ref_cnt、LRU 空闲链、块哈希表。"""

    def __init__(self, num_blocks: int, block_size: int = 16):
        self.block_size = block_size
        self.ref_cnt = [0] * num_blocks
        self.block_hash: list[int | None] = [None] * num_blocks
        self.free = collections.deque(range(num_blocks))   # 真实实现用手写双链表
        self.hash_to_block: dict[int, int] = {}            # 已缓存：hash -> block_id

    def _rolling_hash(self, parent: int | None, tokens: tuple[int, ...]) -> int:
        # 必须带上父块哈希：同样的 16 个 token 跟在不同前缀后，KV 完全不同
        return hash((parent, tokens))

    def match(self, token_ids: list[int]) -> tuple[list[int], int]:
        """返回 (可复用的物理块列表, 已覆盖的 token 数)。"""
        blocks, parent, n = [], None, 0
        for i in range(0, len(token_ids) - self.block_size + 1, self.block_size):
            chunk = tuple(token_ids[i:i + self.block_size])
            h = self._rolling_hash(parent, chunk)
            bid = self.hash_to_block.get(h)
            if bid is None:
                break                       # 前缀一断，后面全部作废
            blocks.append(bid)
            self.ref_cnt[bid] += 1
            if bid in self.free:            # 命中一个"空闲但仍缓存"的块 → 从空闲链摘掉
                self.free.remove(bid)
            parent, n = h, i + self.block_size
        return blocks, n

    def alloc(self, n: int) -> list[int]:
        if n > len(self.free):
            raise MemoryError("没有空闲块了——真实引擎在这里会去抢占别的请求")
        out = []
        for _ in range(n):
            bid = self.free.popleft()
            if self.block_hash[bid] is not None:        # 复用一个仍带缓存内容的块
                self.hash_to_block.pop(self.block_hash[bid], None)   # 先摘旧哈希
                self.block_hash[bid] = None
            self.ref_cnt[bid] = 1
            out.append(bid)
        return out

    def free_blocks(self, blocks: list[int]) -> None:
        # 逆序归还：尾部块排在前面，优先被淘汰（前缀更可能被复用）
        for bid in reversed(blocks):
            self.ref_cnt[bid] -= 1
            if self.ref_cnt[bid] == 0:
                self.free.append(bid)       # 内容与哈希保留 → 之后仍可能被命中

以下三处决定了状态如何更新：

  1. match 里的 break：前缀一旦断掉，后面就算内容相同也不能用——因为 KV 上下文相关。
  2. free_blocks 不清哈希：块归还到空闲链，但内容和哈希还留着。 这就是"空闲 ≠ 失效"，也是跨请求命中的来源。真正清除发生在 alloc 里被重新分配时。
  3. reversed()：一行代码 = 一条缓存策略。

容量拐点是阶跃的

前面的扫描都让工作集远小于池。把两者压到同一数量级后，曲线不是渐变的 （labs/L5/prefix_eviction_scan.py：40 条互异前缀 × 256 token、块 16、工作集 640 块、 逐条顺序提交，vLLM 侧固定 max_num_batched_tokens=512）：

池容量（块） 工作集/池 填充后即刻回访末条 第 2 轮命中 第 3 轮命中 第 2 轮最小
240 / 400 / 560 2.67 / 1.60 / 1.14 93.8% 0.0% 0.0% 0
640 1.00 93.8% 87.7% 93.8% 224
720 / 960 0.89 / 0.67 93.8% 93.8% 93.8% 240

三点：

  1. "0 命中"不是缓存被关掉。 池 560 块时，40 条前缀填完立刻回访最后一条仍有 93.8% 命中；而第 2 轮从第一条按同一顺序再遍历一遍，命中是 0。这是 LRU 的顺序扫描 退化：每次 miss 都要拿新块并驱逐"最久未用"的那一条，被驱逐的恰好是这一轮还没访问 到的下一条。池相对工作集越小，扫描越接近"每条都在驱逐下一条"。
  2. 拐点在池 ≈ 工作集。 池=640 块时第 2 轮 87.7%、第 3 轮回到 93.8%；720 块时两轮 都稳定。容量再大也不会超过 93.8%，因为每条前缀的最后一块会被请求自己生成的 token 改写、哈希不再匹配——256 token 的 prompt 只复用前 240 个。
  3. 两引擎拐点位置一致，临界点行为不同。 同一负载在 SGLang 0.5.19 上 （page_size=16，池由 max_total_tokens 控制，工作集 10240 token）：池 3840/6400/8960 时第 2/3 轮 0、末条回访 93.8%；池 10240（=1.00×）时第 2/3 轮只有 2.3%；池 11520（1.125×）回到 93.8%。vLLM 在 1.00× 处仍保住 87.7%，SGLang 在 1.00× 处几乎全丢：两者分配粒度相同（16 token），差别在结构——vLLM 是块池上的 逐块 LRU，SGLang 按基数树叶子整链回收，临界状态下整链回收会连带丢掉还没访问的分支。

驱逐策略：同负载下 LRU 与 LFU/SLRU 只在热点回访上分开

把池压到工作集的一半（320 块 / 5120 token），跑三段负载：热点 8 条前缀各访问 3 次、 冷点 32 条各访问 1 次冲刷、再回访热点与冷点。vLLM 0.29.0 的块池只有一种顺序； SGLang 0.5.19 的基数树可选 radix_eviction_policy=lru/lfu/slru/priority，于是这一组 是"同一负载、不同策略"的直接对照：

引擎 / 策略 热点第 1/2/3 次 冷点冲刷 回到热点 再问冷点
vLLM（块池 LRU） 0 / 93.8 / 93.8% 0.0% 0.0% 0.0%
SGLang lru 0 / 93.8 / 93.8% 0.0% 0.0% 0.0%
SGLang lfu 0 / 93.8 / 93.8% 0.0% 93.8% 0.0%
SGLang slru 0 / 93.8 / 93.8% 0.0% 93.8% 0.0%

两个引擎的 LRU 逐格一致：冷点各 16 块的冲刷量远超半个池，把热点整链挤出去，回访时 全 miss。换成按频次（lfu）或分段最近使用（slru）后，访问过 3 次的热点在冲刷后 仍命中 93.8%，而只访问过 1 次的冷点在两种策略下都不命中——策略差异只出现在"回访 仍有价值的热点"上。没有可区分热点的负载上，几种策略退化成同一条曲线。

③ SGLang 的 TreeNode 完整字段（原样） 
class TreeNode:
    counter = 0
    def __init__(self, id: Optional[int] = None, priority: int = 0):
        self.children = defaultdict(TreeNode)
        self.parent: TreeNode = None
        self.key: RadixKey = None
        self.value: Optional[torch.Tensor] = None
        self.lock_ref = 0
        self.last_access_time = time.monotonic()
        self.creation_time = time.monotonic()
        self.hit_count = 0
        # indicating the node is locked to protect from eviction
        # incremented when the node is referenced by a storage operation
        self.host_ref_counter = 0
        # store the host indices of KV cache
        self.host_value: Optional[torch.Tensor] = None
        self.write_through_pending_id: Optional[int] = None
        # store hash values of each pages
        self.hash_value: Optional[List[str]] = None
        # Namespace-aware hashes used only for external KV events.
        self.event_hash_value: Optional[List[str]] = None
        # priority for priority-aware eviction
        self.priority = priority
        self.id = TreeNode.counter if id is None else id
        TreeNode.counter += 1

    @property
    def evicted(self):
        return self.value is None

    @property
    def backuped(self):
        return self.host_value is not None

evicted 与 backuped 这两个属性把状态空间说清楚了：一个节点可以是 在 GPU 上（value 非空）、只在主机内存里（value 空但 host_value 非空）、 或彻底没了。三态，不是两态。

event_hash_value 的注释 "Namespace-aware hashes used only for external KV events" —— 对外广播 KV 事件时用带命名空间的哈希，这是多租户下防止跨租户误复用的设计（L8.1）。

④ vLLM 空闲链表的完整 docstring（设计理由都写在里面） 
class FreeKVCacheBlockQueue:
    """This class organizes a list of KVCacheBlock objects to a doubly linked
    list of free blocks. We implement this class instead of using Python
    builtin deque to support removing a block in the middle of the queue
    in O(1) time. To close the performance gap to the builtin deque which is
    implemented in C++, this class does not allocate any Python objects when
    manipulating the linked list. Instead, this class manipulates the
    prev_free_block and next_free_block attributes of the given blocks.

    The queue is ordered by block ID in the beginning. When a block is allocated
    and then freed, it will be appended back with the eviction order:
    1. The least recent used block is at the front (LRU).
    2. If two blocks have the same last accessed time (allocated by the
       same sequence), the one with more hash tokens (the tail of a block
       chain) is at the front.
    Note that we maintain this order by reversing the block order when free
    blocks of a request. This operation is outside of this class.
    """

读源码时，写得好的 docstring 比代码本身信息量大。 这一段把 「为什么不用标准库」「为什么不建对象」「淘汰顺序是什么」「顺序在哪里维护」 四件事全说了。找这种 docstring 是 M1（读大型代码库）的核心技巧之一。

陷阱

1. 混淆共享长度、命中长度和耗时。 本例只缓存满块，但同样的预测块数 不保证调用耗时相同；调度、采样和测量波动也会影响时间。

2. 把变化的内容放在 prompt 开头。 滚动哈希意味着前缀一断全断。 时间戳、请求 ID、随机 few-shot 顺序放在开头 = 缓存全废。

3. 测前缀缓存时忘了它已经命中。 重复使用同一前缀时会出现以下测量偏差： ttft_ms() 里的预热调用把完整 prompt 也写进了缓存， 于是阶梯变成一条水平线（7.7–7.9 ms 恒定）。 测「首次命中」必须真的只跑一次，且每次换新后缀。

4. 用平均值报 TTFT。 冷启动那一次比后面慢 5.5 倍，混进平均值会把结论毁掉。 本章全部用中位数，并把冷/热分开报。

5. 以为 enable_prefix_caching=False 就没有复用。 关掉后实测 37.16 ms， 而开着但完全未命中是 41.46 ms——关掉反而略快，因为省掉了哈希计算与查表开销。 这说明前缀缓存本身有成本，只有在有命中的负载下才划算。

6. 同进程建第二个引擎不释放第一个。 会报 Free memory on device cuda:0 (12.45/31.36 GiB) is less than desired。 del 不够，要 engine_core.shutdown()。

7. 命中块数不等于节省的时间。 命中 240 个 token 的那条请求墙钟 5.5 ms，命中 0 的 7.1 ms；差 1.6 ms，而 240 token 的 prefill 单独算是 3.6 ms 量级。省下的不止是重算， 还有被它顺带避免的分块与调度开销——反之，命中率很低的负载里哈希与查表的开销都是净支出。

8. 同名 adapter 热更新不会使旧 KV 失效。 块哈希里只有 lora_name， 换了权重文件但名字不变时哈希逐位相同，引擎会继续用旧 adapter 算出的 KV（5.10 实测）。

9. 把"池装不下"读成"命中按比例下降"。 池小于工作集时，按同一顺序重复扫描的命中 是 0 而不是部分命中：每次 miss 分配新块都会驱逐这一轮还没访问到的下一条。要判断缓存 是否还在，得在填充后立刻回访最后一条，而不是看下一轮的均值。

10. 用"运行次数"而不是"命中量"判断复用。 前缀缓存是实例本地的：另一台机器、 另一个进程、或调用过显式驱逐之后，同一段文本的命中都会回到 0。

自测题

1. 为什么块哈希必须包含父块哈希？举一个不包含会出错的具体例子。

因为 KV 是上下文相关的。

反例：block_size=16。 - 请求 A 的 token 是 [X…X(16个), "今天天气"…] - 请求 B 的 token 是 [Y…Y(16个), "今天天气"…]

第二块的内容完全相同（都是 "今天天气"…），但 A 的第二块要 attend 到 16 个 X， B 的要 attend 到 16 个 Y。算出的 K、V 数值完全不同。

如果只哈希块内容，B 会命中 A 缓存的第二块，直接读到错误的 K/V —— 输出会是错的， 而且不会报错，只是悄悄地生成垃圾。这是正确性 bug，不是性能问题。

带上父块哈希后，两个第二块的哈希不同，不会误命中。

2. 一个块被释放（ref_cnt=0）后，它的内容还能被命中吗？在什么时刻才真正失效？

能。 free_blocks 只把块归还到空闲链表，不清 _block_hash，也不从哈希表里摘掉。 所以一个"空闲但仍缓存"的块可以被后来的请求命中并复活（此时要从空闲链表中间 O(1) 摘掉它—— 这正是 vLLM 手写双向链表而不用 deque 的原因）。

真正失效的时刻是它被 get_new_blocks 重新分配给别的用途时， _maybe_evict_cached_block() 才把哈希条目摘掉并发出淘汰事件。

所以 "空闲" 和 "有效缓存" 是两个正交状态。 这是 prefix cache 能跨请求生效的全部机制： 缓存容量 = 全部块，而不只是"没被引用的那些"。

3. 同一个 adapter 名字换了权重文件，前缀缓存会自动失效吗？怎么才能让缓存按预期隔离？

不会。vLLM 0.29.0 的 _gen_lora_extra_hash_keys 只把 lora_request.lora_name 放进 extra_keys，权重路径与 revision 都不参与哈希。同名换权重时块哈希逐位相同， 引擎复用旧 adapter 算出的 KV，输出与旧版本一致（5.10 的同名热更新实测）。

要让缓存按预期隔离，有三条路：换 adapter 名字（最直接）、给请求带 cache_salt（第 0 块换键，整条序列随之失效）、或换引擎实例。 labs/L5/cache_key_identity.py 可以逐字段验证这三条是否生效。

4. block_size 从 16 改成 64，有哪些收益和代价？在什么负载下你会改大？

收益： - block table 变短 4 倍 → _prepare_inputs 里的 CPU 指针算术变少（L0.1 第 14 阶段） - attention kernel 的块寻址开销变小 - 元数据（每块一个 Python 对象 + 哈希条目）少 4 倍

代价： - 内部碎片上界从 15 个 token 涨到 63 个。1000 条并发就是最多浪费 63000 个 token 的空间 - 复用粒度变粗：共享 63 个 token 的前缀变成完全白共享（本章的阶梯变宽 4 倍） - 抢占时被换出的粒度也变粗

改大的场景：长序列、少并发、前缀共享少（比如长文档批量摘要）。 此时碎片占比小，而元数据开销的节省是实打实的。

改小的场景：多轮对话、agent（前缀高度共享且长度零碎）、短请求高并发。

顺带：这也解释了为什么 SGLang 的 radix tree 在 page_size=1 时最灵活—— 它可以做真正的 token 级复用，代价是树更深、遍历更慢。

5. 我的服务有 1000 个用户，每人一个 3000 token 的私有 system prompt，之后是短问题。前缀缓存能帮上忙吗？

跨用户帮不上（每人的 system prompt 不同，没有公共前缀）， 同一用户的多次请求能帮上（第二次起 3000 token 全命中）。

但有个容量问题：1000 × 3000 token × 114.69 KB = 328 GB 的 KV， 远超单卡 25 GB。所以缓存会不停被 LRU 淘汰，命中率取决于用户请求的时间局部性。

工程解法（都指向后面的章节）： 1. 会话亲和路由（L8.1）：把同一用户路由到同一台机器，让局部性变强。 2. KV 分级存储（L6.4）：把冷的 3000-token 前缀卸到 DRAM/SSD，命中时拉回来。 拉回来的成本是 344 MB / PCIe 47.5 GB/s ≈ 7 ms，仍然远快于重算的 41 ms。 这就是 Mooncake 那条路线的经济学。 3. 重排 prompt：如果 system prompt 里有公共部分（比如统一的工具定义）， 把它提到最前面，让 1000 个用户至少共享那一段。

顺带：这道题也说明为什么 vllm:external_prefix_cache_hits 这个指标存在。

6. SGLang 的基数树在什么负载下明显赢过 vLLM 的哈希表？在什么负载下反而是负担？

赢的场景 —— 前缀高度嵌套的树状结构： - 多轮对话：第 1 轮是第 2 轮的前缀，第 2 轮是第 3 轮的前缀……天然是一条链 - agent 的分支探索：同一个上下文分叉出多条推理路径 - few-shot 的不同组合：共享前 k 个示例

这些场景下，树不仅能命中，还能让调度器按最长公共前缀选批（LPM）， 让共享同一子树的请求同批执行，KV 只读一次。哈希表方案给不出"这两个请求有多像"这个信息。

是负担的场景： - 前缀几乎不共享（每个请求独立的长文档）→ 树退化成一堆独立的链， 遍历开销和节点分裂纯属额外成本 - 极高 QPS 的短请求 → 树遍历是指针追逐（cache 不友好）， 而哈希表是 O(1) 且无对象分配

判断方法：先测你的负载的前缀共享率（可以用本章的 prefix_cache_hits/queries）， 再决定。这比读任何 benchmark 都可靠——因为 benchmark 用的是别人的负载。
