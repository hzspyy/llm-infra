推理引擎架构对比与 nanoserve 实现

比较四种推理引擎，并实现一个支持请求调度、分页缓存、前缀复用和流式输出的 nanoserve。

实测机器 crater (RTX 5090 D, sm_120) · Qwen3-1.7B · vLLM 0.29.0 · SGLang 0.5.19 · llama.cpp df03399b · TensorRT-LLM 7bbf99e5前置 5.1（两相）· 5.2（分页与前缀）· 5.3（调度）· 5.4（执行层）· 4.1（手写 Qwen3 前向）

本章回答三个问题

前面六章各自拆了一个部件。这一章把它们装到一起：一个能收 HTTP 请求、 能同时服务多条请求、能复用前缀、能被取消的引擎，最少需要哪些状态？

  1. 四家引擎（vLLM V1 / SGLang / TensorRT-LLM / llama.cpp）在进程模型、调度、 显存、执行、扩展点上分别做了什么选择？分歧在哪？
  2. 自己从零写一个，六次迭代各增加什么能力？每一次能测出什么？
  3. 一条请求在引擎内部的完整状态是什么？怎么证明它被完整地收回来了？

本章的 nanoserve 复用 4.1 那份手写 Qwen3 前向，只往上加服务层。 它跑出来的 token 与 transformers.generate 的贪心解码逐个相同， 所以后面所有关于调度和显存的数字都建立在一个正确的模型之上。

心智模型：引擎 = 三张表 + 一个循环

机制拆解：并发上限从哪来

四家引擎在最上层其实只分成两派，判据是"最多同时跑几条请求"这个数是怎么定的。

一派把它写死在启动参数里。 llama.cpp 的 server 开 n_parallel 个 slot， 每个 slot 是一个独立的状态机，启动时就把 KV 按 slot 切好：

// tools/server/server-context.cpp:152
if (params.n_parallel < 0) {
    SRV_TRC("%s", "n_parallel is set to auto, using n_parallel = 4 and kv_unified = true\n");
    params.n_parallel = 4;
}
...
params.n_ctx = params.n_parallel * params.kv_unified_per_slot;

TensorRT-LLM 也有同一个东西，叫 sequence slot （tensorrt_llm/_torch/pyexecutor/seq_slot_manager.py:6）：

class SeqSlotManager(BaseResourceManager):
    def __init__(self, max_num_sequences: int):
        self.slot_manager = SlotManager(max_num_sequences)

另一派让它由剩余块数决定。 vLLM 和 SGLang 没有 slot：请求要几块给几块， 块用完了就不再收新请求（本章 nanoserve 走的是这条）。 max_num_seqs 存在，但它是上界，不是预留。

这个分歧解释了后面很多差异：

  • 有 slot 的引擎容量是确定的，一条超长请求不会挤掉别人，代价是短请求也占着一整个 slot 的额度。
  • 无 slot 的引擎容量随负载浮动，显存利用率高，代价是必须处理"块不够了"这件事—— 于是就有了抢占、换出和重算（5.3、5.8）。

llama.cpp 的做法很能说明代价：块不够时它在 update_slots() 里退回去用更小的 batch 重试：

// tools/server/server-context.cpp:3733

实现中有三个细节：

  • 只有 llama.cpp 把"复用"做在 slot 粒度上：它不切块，而是找一个"上次跑过相似 prompt"的 slot 接着用。 这在 n_parallel 很小、请求高度相似时非常划算，而且实现极简； 代价是复用是全或无的，两条只共享一半前缀的请求分不到好处。
  • 只有 TensorRT-LLM 把调度拆成两级。 「装不装得下」和「这一拍谁上」是两个问题： 前者关心显存，后者关心 batch 形状与 in-flight 的微批。vLLM 把两件事揉在一个函数里。
  • 进程边界的位置决定了故障边界。 vLLM 与 SGLang 把引擎放进独立进程， HTTP 侧崩了引擎还在；llama.cpp 与 TRT-LLM 是一个进程，一起生一起死。5.8 会用到这条。

这张表的证据强度不一样

vLLM 与 SGLang 是 crater 上实际安装并跑过的版本（本章及 5.1–5.6 的实验都在其上）。 llama.cpp 与 TensorRT-LLM 只读了源码，没有编译、没有运行、没有任何性能数字。 表里关于它们的每一格都可以在上面给出的 file:line 处核对，但 「它们实际跑起来什么样」本章 UNVERIFIED。 要补的话：llama.cpp 需要在 crater 上编译（CUDA 后端）， TensorRT-LLM 需要匹配 CUDA 的构建；这两条运行对照均为 UNVERIFIED。

117         c = self.cfg

123     @torch.inference_mode()
124     def forward(self, input_ids, positions, slot_mapping, gather_idx, ctx_lens):
125         """一次批量前向。
126 
127         input_ids   [B, Q]   本步要算的 token（prefill chunk 或 1 个 decode token）
128         positions   [B, Q]   每个 token 的绝对位置，喂 RoPE
129         slot_mapping[B, Q]   每个 token 的 KV 写到池子的哪个槽位；-1 表示 padding
130         gather_idx  [B, C]   读 KV 时收集哪些槽位（C = 本批最长上下文）
131         ctx_lens    [B]      收完这一步之后每条序列的上下文长度
132         返回 logits [B, Q, V]。padding 位置的输出是垃圾，由调用方按 q_len 取。
133         """
134         c = self.cfg
135         B, Q = input_ids.shape
136         C = gather_idx.shape[1]
137         x = self.embed[input_ids]                                   # [B, Q, H]
138         cos = self.cos[positions]                                   # [B, Q, hd]
139         sin = self.sin[positions]
140 
141         # 写入槽位用的下标：padding 位置统一指向 0 号槽，再用 valid 掩掉。
142         write = slot_mapping.reshape(-1)
143         valid_write = write >= 0
144         write_safe = torch.where(valid_write, write, torch.zeros_like(write))
145 
146         # 读 mask：ctx 里位置 < ctx_len 的才是真数据；再叠一层因果。
147         ctx_pos = torch.arange(C, device=self.device)[None, :]      # [1, C]
148         keep = ctx_pos < ctx_lens[:, None]                          # [B, C]
149         causal = ctx_pos[None, :, :] <= positions[:, :, None]       # [B, Q, C]
150         mask = (keep[:, None, :] & causal)[:, None]                 # [B, 1, Q, C]
151         bias = torch.zeros(mask.shape, device=self.device, dtype=self.dtype)
152         bias.masked_fill_(~mask, float("-inf"))
153 
154         for i, lay in enumerate(self.layers):
155             h = rms_norm(x, lay.n1, c.eps)
156             q = (h @ lay.wq.T).view(B, Q, c.n_q, c.head_dim)
157             k = (h @ lay.wk.T).view(B, Q, c.n_kv, c.head_dim)
158             v = (h @ lay.wv.T).view(B, Q, c.n_kv, c.head_dim)
159             q = rms_norm(q, lay.qn, c.eps)
160             k = rms_norm(k, lay.kn, c.eps)
161             q = q * cos[:, :, None] + rotate_half(q) * sin[:, :, None]
162             k = k * cos[:, :, None] + rotate_half(k) * sin[:, :, None]
163 
164             # ---- 写：slot_mapping 决定这一步的 KV 落在池子哪里 ----
165             kf = k.reshape(-1, c.n_kv, c.head_dim)
166             vf = v.reshape(-1, c.n_kv, c.head_dim)
167             keep_rows = valid_write.nonzero(as_tuple=True)[0]
168             self.k_cache[i].index_copy_(0, write_safe[keep_rows], kf[keep_rows])
169             self.v_cache[i].index_copy_(0, write_safe[keep_rows], vf[keep_rows])
170 
171             # ---- 读：block table 展开成的 gather_idx 决定收集哪些槽位 ----
172             kk = self.k_cache[i][gather_idx].transpose(1, 2)         # [B, n_kv, C, hd]
173             vv = self.v_cache[i][gather_idx].transpose(1, 2)
174             o = F.scaled_dot_product_attention(
175                 q.transpose(1, 2), kk, vv, attn_mask=bias, enable_gqa=True)
176             x = x + o.transpose(1, 2).reshape(B, Q, c.n_q * c.head_dim) @ lay.wo.T
177 
178             h = rms_norm(x, lay.n2, c.eps)
179             x = x + (F.silu(h @ lay.gate.T) * (h @ lay.up.T)) @ lay.down.T
180 
181         x = rms_norm(x, self.norm_f, c.eps)
182         return x @ self.lm_head.T

这不是 paged attention kernel

forward() 先按 gather_idx 把 KV 收集成连续张量再交给 SDPA， 分页只体现在寻址上，不体现在 kernel 内部。3.3 量过这条路的代价上界。 本章所有耗时数字都带着这个前提，不能拿去和真实引擎比。

迭代 1 · 单请求端到端执行

引擎最小的样子：一个 step()，一条请求，四个状态。 把预算压到 8 个 token，中间态就现形了（s1_trajectory）：

step state num_computed block_table kv_len 本步 prefill / decode
— waiting 0 [] 0 —
0 prefill 8 [0, 1] 8 8 / 0
1 prefill 16 [0, 1] 16 8 / 0
2 decode 17 [0, 1] 17 1 / 0
3 decode 17 [0, 1] 18 0 / 1
4 finished 17 [] 19 0 / 1

17 个 prompt token 分成 3 个 chunk；结束时 block_table 变回空 —— 块归还是状态的一部分。

这里有一个必须踩对的坑：最新采样出来的那个 token 还没有 KV。

# labs/L5/nanoserve/engine.py
@property
def kv_len(self) -> int:
    if not self.output_ids:
        return self.num_computed
    return self.num_computed + len(self.output_ids) - 1

该 token 在下一步输入模型后才写入块池。少减 1 会导致位置错位，并可能使 all_ids[kv_len] 越界。

怎么检查这个最小实现：同一条 prompt、同样贪心，和 transformers.generate 逐 token 比：

24 个 token 全同。分页寻址、chunked prefill、块回收都不改变输出—— 这是后面所有实验的前提。

迭代 5 · chunked prefill 与 token 预算

一条 1201 token 的长 prompt 插进 3 条正在 decode 的请求里。 稳态每步 11.6 ms，扫 max_batched_tokens：

token 预算 prefill 分几块 插入期间最慢一步 相对稳态 长 prompt 占用的 step 数
64 20 24.6 ms 2.1× 20
256 5 29.0 ms 2.5× 5
1024 2 54.8 ms 4.7× 2

这组数据中，预算越大，长 prompt 越快算完（20 步 → 2 步）， 但同批 decode 的那一步越慢（24.6 ms → 54.8 ms）。

它对应的是真实系统里的 TPOT 抖动：一条长 prompt 进来， 客户端可能观察到输出间隔增大，token 预算会影响这种延迟。 5.1 讲过为什么两相不能用一套参数——这里是那句话的可测版本。

这条曲线的形状取决于本实现

nanoserve 一步里跑两次前向（一次 prefill 组、一次 decode 组）， 共用一个 token 预算。真实引擎（vLLM）把两者拼进同一次 varlen 前向， 所以它们的绝对开销更低。本章测到的是"预算怎么切"这个取舍的形状， 不是 vLLM 的实际数字。

188     def _grow_block_table(self, req: Request, upto: int) -> None:
189         """保证 block_table 能装下 upto 个 token。只在需要时分配。"""
190         need = (upto + self.block_size - 1) // self.block_size
191         while len(req.block_table) < need:
192             req.block_table.append(self.pool.allocate())
193 
194     def _try_prefix_cache(self, req: Request) -> None:
195         """按块滚动哈希，命中就直接接上别人的块，命中的部分不用再算。
196 
197         复用来的块是**只读共享**的，所以复用只能停在块边界上。
198         如果整段 prompt 都命中，必须退掉最后一块重算——
199         否则这一步没有任何 token 要前向，采样就拿不到 logits。
200         """
201         if not self.enable_prefix_cache:
202             return
203         parent, hit = NONE_HASH, 0
204         for b in range(len(req.prompt_ids) // self.block_size):
205             chunk = tuple(req.prompt_ids[b * self.block_size:(b + 1) * self.block_size])
206             h = block_hash(parent, chunk)
207             block_id = self.pool.reuse(h)
208             if block_id is None:
209                 break
210             req.block_table.append(block_id)
211             parent, hit = h, hit + 1
212         if hit and hit * self.block_size >= len(req.prompt_ids):
213             self.pool.release(req.block_table.pop())
214             self.pool.stat_reuse -= 1
215             hit -= 1
216         req.cached_prefix_blocks = hit
217         req.num_computed = hit * self.block_size
218 
219     def _publish_full_blocks(self, req: Request) -> None:
220         if not self.enable_prefix_cache:
221             return
222         parent = NONE_HASH
223         ids = req.all_ids
224         for b in range(min(len(req.block_table), req.kv_len // self.block_size)):
225             chunk = tuple(ids[b * self.block_size:(b + 1) * self.block_size])
226             parent = block_hash(parent, chunk)
227             self.pool.publish(req.block_table[b], parent)
228 
229     def _free(self, req: Request) -> None:
230         for block_id in req.block_table:
231             self.pool.release(block_id)
232         req.block_table = []

234     def abort(self, req_id: str, reason: str = "aborted") -> bool:
235         """取消：从队列或运行集里摘掉，释放块。5.8 会沿这条路径继续往上接。"""
236         for q in (self.waiting,):
237             for r in list(q):
238                 if r.req_id == req_id:
239                     q.remove(r)
240                     r.state, r.finish_reason = State.ABORTED, reason
241                     r.finished_at = time.perf_counter()
242                     self.done[req_id] = r
243                     return True
244         for r in list(self.running):
245             if r.req_id == req_id:

247                 self._free(r)
248                 r.state, r.finish_reason = State.ABORTED, reason
249                 r.finished_at = time.perf_counter()
250                 self.done[req_id] = r

254     # ---------------------------------------------------------------- 调度
255     def _schedule(self):
256         """先安排 decode（它们已经占着块了），剩下的预算给 prefill chunk。"""
257         budget = self.max_batched_tokens
258         decode = [r for r in self.running if r.state is State.DECODE]
259         decode = decode[:budget]
260         budget -= len(decode)
261 
262         prefill: list[tuple[Request, int]] = []
263         # 已经在跑但 prompt 没算完的，优先接着算。
264         pending = [r for r in self.running if r.state is State.PREFILL]
265         while budget > 0 and pending:
266             r = pending.pop(0)
267             take = min(budget, len(r.prompt_ids) - r.num_computed)
268             if take <= 0:
269                 continue
270             prefill.append((r, take))
271             budget -= take
272         # 再从等待队列里放新的进来。
273         while (budget > 0 and self.waiting
274                and len(self.running) < self.max_num_seqs):
275             r = self.waiting[0]
276             try:
277                 self._try_prefix_cache(r)
278                 self._grow_block_table(r, len(r.prompt_ids))
279             except OutOfBlocks:
280                 self._free(r)
281                 r.num_computed, r.cached_prefix_blocks = 0, 0
282                 break                       # 块不够，这一步就不收新请求了
283             self.waiting.popleft()
284             r.state = State.PREFILL
285             self.running.append(r)
286             take = min(budget, len(r.prompt_ids) - r.num_computed)
287             prefill.append((r, take))
288             budget -= take

303     def _run(self, groups: list[tuple[Request, int, int]]):
304         """groups: (请求, 本步起始位置, 本步 token 数)。返回每条序列最后一个位置的 logits。"""
305         dev = self.model.device
306         Q = max(n for _, _, n in groups)
307         C = max(start + n for _, start, n in groups)
308         B = len(groups)
309         input_ids = torch.zeros((B, Q), dtype=torch.long)
310         positions = torch.zeros((B, Q), dtype=torch.long)
311         slot_map = torch.full((B, Q), -1, dtype=torch.long)
312         gather = torch.zeros((B, C), dtype=torch.long)
313         ctx_lens = torch.zeros(B, dtype=torch.long)
314         last = []
315         for b, (req, start, n) in enumerate(groups):
316             ids = req.all_ids[start:start + n]
317             input_ids[b, :n] = torch.tensor(ids)
318             positions[b, :n] = torch.arange(start, start + n)
319             slot_map[b, :n] = torch.tensor(self._slots(req, start, n))
320             ctx_lens[b] = start + n
321             gather[b] = torch.tensor(self._gather(req, start + n, C))
322             last.append(n - 1)
323         logits = self.model.forward(
324             input_ids.to(dev), positions.to(dev), slot_map.to(dev),
325             gather.to(dev), ctx_lens.to(dev))
326         return logits[torch.arange(B, device=dev),
327                       torch.tensor(last, device=dev)]        # [B, V]

331         t0 = time.perf_counter()

335         if not prefill and not decode:

337             trace.pool = self.pool.snapshot()
338             self.traces.append(trace)

341         # ---- prefill 组：可能只是 prompt 的一段 ----
342         if prefill:

344             logits = self._run(groups)
345             trace.prefill = [r.req_id for r, _ in prefill]
346             trace.prefill_tokens = sum(n for _, n in prefill)
347             for b, (r, n) in enumerate(prefill):
348                 r.num_computed += n
349                 r.prefill_chunks += 1
350                 if r.num_computed >= len(r.prompt_ids):
351                     r.state = State.DECODE
352                     self._emit(r, logits[b], trace)
353                     self._publish_full_blocks(r)
354 
355         # ---- decode 组：每条 1 个 token ----
356         if decode:
357             groups = [(r, r.kv_len, 1) for r in decode]
358             for r in decode:
359                 self._grow_block_table(r, r.kv_len + 1)
360             logits = self._run(groups)
361             trace.decode = [r.req_id for r in decode]
362             trace.decode_tokens = len(decode)
363             for b, r in enumerate(decode):
364                 self._emit(r, logits[b], trace)
365                 self._publish_full_blocks(r)
366 
367         trace.pool = self.pool.snapshot()
368         trace.seconds = time.perf_counter() - t0
369         self.traces.append(trace)

设计取舍

1. 状态放在哪里，决定了取消有多难写

nanoserve 里一条请求的状态分布在三处：队列（它在 waiting 还是 running）、 自己的 block_table、以及 HTTP 协程里的那个 asyncio.Queue。 abort() 必须同时处理前两处，第三处由 finally 兜底。

四家引擎的做法差别就在这三处离得有多远：

  • llama.cpp 把它们放进同一个 server_slot 结构体（server-context.cpp:239）， 一个 slot 就是请求的全部状态。取消 = 把 slot 打回 SLOT_STATE_IDLE。 简单，但也意味着状态和资源绑死：slot 空着也占着 KV。
  • vLLM 把请求状态放在 scheduler 进程里，输出通道在另一个进程。 取消要跨进程传递（这也是它有 RequestStatus.FINISHED_ABORTED 这类显式状态的原因）。 换来的是 HTTP 侧崩溃不影响正在跑的请求。

设计原则：状态的分布决定了失败路径的复杂度。 状态越集中越好写，越分散越能隔离故障。这两件事不可兼得。

2. 块池引用计数与空闲状态需要保持一致

nanoserve 有意不维护"某条请求用了几块"这个派生字段—— 要知道就去数 block_table，要知道块是不是自由就看 ref_count。 leak_check() 因此只需要一句断言：结束之后不应该有任何 ref_count > 0。

反例是很容易写出来的：如果同时维护 num_free 计数器和 free 链表， 两者就会在某条罕见路径上分叉，而且分叉之后系统还能跑很久才暴露。 5.2 里 vLLM 的块池也是同一个选择：空闲链表就是空闲状态本身。

块的归属由引用计数统一记录，其他字段只能保存可重建的派生信息。

3. token 预算控制本轮准入规模

_schedule() 一共只有一个数：max_batched_tokens。 decode 先占（它们已经拿着块了），剩下的给 prefill。

这个顺序不是随便定的。反过来（prefill 优先）会导致 长 prompt 到达时所有 decode 停摆——迭代 5 那张表里 54.8 ms 那一格 就是"prefill 一次吃掉 1021 个预算"的后果，只不过 decode 还占着 3 个名额。 如果 decode 不优先，那一步就是纯 prefill，正在聊天的用户直接卡住一整步。

vLLM 的调度器同样把"已经在跑的"排在"新来的"前面（5.3）。 优先推进已运行请求可以减少重复工作，但不是通用最优策略；还需检查新请求等待时间、期限与公平性。

4. 加一个后端要改哪些地方

nanoserve 的模型层与引擎层之间只有一个接口：forward(input_ids, positions, slot_mapping, gather_idx, ctx_lens)。换模型只需要换 model.py， engine.py 一行不动——只要新模型愿意接受"KV 写到我指定的槽位"这个约定。

四家引擎的扩展点都落在同一处，因为这是唯一必须约定的东西：

  • vLLM 的 attention backend 接口要的就是 slot_mapping 与 block_table；
  • SGLang 同理；
  • llama.cpp 的 ggml backend 接口在更低一层（算子），所以换后端不涉及 KV 布局， 但也因此换 KV 组织方式要改的地方更多。

扩展点的位置 = 你允许别人替换的那一层的边界。放低了灵活但改动大， 放高了好接但能做的事少。

 33 async def sse(port, prompt, max_tokens, req_id, stop_after=None):
 34     """发一条请求，逐个事件读回来。stop_after 不为 None 时读够就关 socket。"""
 35     reader, writer = await asyncio.open_connection("127.0.0.1", port)
 36     body = json.dumps({"prompt": prompt, "max_tokens": max_tokens,
 37                        "id": req_id}).encode()
 38     writer.write(b"POST /generate HTTP/1.1\r\nHost: localhost\r\n"
 39                  b"Content-Type: application/json\r\n"
 40                  + f"Content-Length: {len(body)}\r\n\r\n".encode() + body)
 41     await writer.drain()
 42     t0 = time.perf_counter()
 43     await reader.readuntil(b"\r\n\r\n")            # 跳过响应头
 44     stamps, pieces, done = [], [], False
 45     while True:
 46         try:
 47             line = await asyncio.wait_for(reader.readuntil(b"\r\n\r\n"), timeout=30)
 48         except (asyncio.IncompleteReadError, asyncio.TimeoutError):
 49             break
 50         text = line.decode().strip()
 51         if not text.startswith("data: "):
 52             continue
 53         payload = text[6:]
 54         stamps.append(time.perf_counter() - t0)

 56             done = True

 59         if stop_after is not None and len(pieces) >= stop_after:
 60             writer.close()                          # 客户端主动跑路

 66             "ttft_ms": round(stamps[0] * 1000, 2) if stamps else None,

前沿

  • 调度拆成两级。 TensorRT-LLM 的 CapacityScheduler / MicroBatchScheduler 把"装得下吗"和"这一拍谁上"分开。当引擎要同时处理 PD 分离、多微批、 encoder 请求时，揉在一起的调度函数会迅速失控。L6.4 会回到这里。
  • 进程边界继续外移。 vLLM 把 EngineCore 拆成独立进程之后， 下一步是把 tokenizer、detokenizer、结构化输出的语法编译都挪出关键路径 （5.6 测到语法填 mask 现在还在调度器里串行）。
  • slot 与 block 的融合。 llama.cpp 的 kv_unified 是从"每 slot 一段" 往"共用一个池"挪的中间形态。两派在收敛。
  • nanoserve 缺的最大一块是抢占。 现在块不够就抛异常。 真实引擎要么换出到 CPU，要么丢弃重算（5.3），这决定了系统在过载下 是优雅降级还是直接拒绝。5.8 补这一段。

陷阱

  1. 最新采样的 token 通常尚未经过下一次前向。 KV 长度应按已完成前向的位置计数；完整 prefill 后普通逐步生成可写为 prompt 长度加 output 长度减一，不能再加到已经包含输出的 num_computed 上。 少减 1 会造成位置错位，即使程序继续运行，输出也可能错误。
  2. "跑完了"不等于"资源回来了"。 每条路径结束后都要断言块池回到初始状态。 nanoserve 的 leak_check() 在六个阶段都跑，全部为 0。
  3. 复用来的块是只读共享的，复用只能停在块边界。整段 prompt 命中时 必须退掉最后一块重算，否则这一步没有 token 要前向。
  4. TTFT 要区分冷热。 本章第一条 228 ms、之后 36.5 ms，差 6 倍全是预热。
  5. 端到端量的 token 间隔不是 TPOT。 内核缓冲会把多个 token 一起交付 （本章前 7 个约 30 ms，之后掉到 0.0x ms）。
  6. 连续批处理对延迟与吞吐的收益不同。 本章 n=8/16 时吞吐只差 4–5%， 因为 decode 在这个规模上是带宽受限的（5.1）。
  7. 有 slot 的引擎容量确定但利用率低，无 slot 的相反。 选哪个取决于 你更怕"容量不确定"还是"显存浪费"。
  8. 框架层的分页不等于 paged attention kernel。 nanoserve 先 gather 再 SDPA， 它证明的是寻址正确，不是 kernel 代价。

自测题

1. 一条请求被取消时，需要动哪些状态？漏掉任何一处会怎样？

nanoserve 里一条请求的状态在三处：

  1. 它在哪个队列里（waiting 还是 running）——漏掉它，调度器下一步还会调度它。
  2. 它的 block_table——漏掉它，那些块的 ref_count 永远不归零， 池子会慢慢饿死。这是最难发现的一种：系统跑几小时之后开始拒绝新请求， 但没有任何一条报错。
  3. 输出通道（HTTP 协程里的 asyncio.Queue）——漏掉它，协程永远等不到 None，连接挂着不释放。

本章的做法是让 abort() 处理前两处，finally 兜底第三处， 再用 leak_check() 对第 2 处做事后断言：结束之后不应有任何 ref_count > 0。

只测"输出对不对"发现不了其中任何一种。

2. 为什么连续批处理在本章的吞吐上几乎没赢，延迟却赢了 1.14–1.44 倍？

因为这个规模的 decode 是带宽受限的（5.1、5.5 都测过）： batch 从 1 涨到 16，每步耗时几乎不变。因此，这组测试中继续增加 batch 的吞吐收益有限——n=8 和 n=16 时吞吐比只有 1.04× 和 1.05×。

延迟赢的是另一件事：静态批让后到的请求干等上一批跑完。 本章实测最大延迟 313 vs 511 ms（n=4）、363 vs 521 ms（n=8）、423 vs 524 ms（n=16）。

n=4 那一档吞吐也赢了 1.41×，原因不同：静态批多花了 18 个 step（48 vs 30）， 其中大段时间在跑只有一条请求的批。

推论：报连续批处理的收益必须说明看的是延迟还是吞吐，以及负载有多重。

3. 把 max_batched_tokens 从 64 调到 1024，谁变好谁变坏？

本章实测（一条 1201 token 的长 prompt 插进 3 条 decode）：

预算 prefill 分几块 插入期间最慢一步
64 20 24.6 ms
256 5 29.0 ms
1024 2 54.8 ms

稳态一步是 11.6 ms。所以：

  • 变好的：长 prompt 算完得更快（20 步 → 2 步）。
  • 变坏的：同批 decode 那一步从 2.1× 慢到 4.7×，正在聊天的用户看到卡顿。

这就是 chunked prefill 存在的理由：把 TTFT 和 TPOT 之间的取舍变成一个可调的旋钮， 而不是一个由 prompt 长度决定的意外。

4. llama.cpp 的 slot 和 vLLM 的 block，本质区别是什么？

"最多同时跑几条"这个数是怎么定的。

  • llama.cpp：启动时定死 n_parallel 个 slot（server-context.cpp:152， auto 时是 4），KV 按 slot 切好。TensorRT-LLM 的 SeqSlotManager 是同一个东西。
  • vLLM / SGLang：没有 slot，请求要几块给几块，块用完了就不收新的。

代价对称：

  • 有 slot → 容量确定，一条超长请求不会挤掉别人；但短请求也占着一整个 slot 的额度， 显存利用率低。
  • 无 slot → 显存利用率高；但必须处理"块不够了"，于是有了抢占、换出与重算（5.3、5.8）。

llama.cpp 遇到块不够时的做法很能说明问题：退回去用更小的 batch 重试 （server-context.cpp:3733 那条日志）。这是有 slot 一派的典型处理方式—— 因为容量本来就是确定的，不够只可能是这一拍要得太多。

5. nanoserve 的分页和真实的 PagedAttention 差在哪？本章的耗时数字能拿去比吗？

寻址一样，kernel 不一样，所以耗时不能比。

一样的部分：slot_mapping（写 KV 到哪个槽）、block_table / gather_idx （读 KV 收集哪些槽）、table[p/16]*16 + p%16 这个翻译。名字都和 vLLM 一致， 本章把 pos 0/15/16/31/32 的槽位逐个打出来验过。

不一样的部分：nanoserve 先把 KV 收集成一个连续张量再调 SDPA。 真实的 paged attention kernel 在 kernel 内部按块寻址，不做这次拷贝。 3.3 量过"显式 gather"这条路的代价，它是分页代价的上界。

所以本章的 11.6 ms/步、54.8 ms 峰值这些数字只能用来看取舍的形状 （预算大→峰值高），不能和 vLLM 的绝对值比。
