6.5

长上下文分布式

sequence / context parallel、ring attention、超长 KV 的分片与调度。

实测机器 worldvln（2/4× L40S，PCIe，无 NVLink）· Qwen3-8B 结构参数 · BF16前置 6.0b（DTensor 布局）· 6.1（集合通信成本）· 3.2（FlashAttention 世代）· 3.4（稀疏与线性 attention）

本章回答三个问题

序列长度是唯一一个会让所有账同时爆炸的维度。权重不随 S 变，KV 随 S 线性长，而 attention 的注意力矩阵随 S² 长。到 32K 上下文时，一份"不重算"的训练激活能比推理 KV 大两个数量级以上。

上下文并行（CP）切的就是这个维度。它看起来最直观——把序列切开，每张卡只算一段——但切开之后 attention 不再局部：每个查询都要看到它前面所有的键值，而那些键值现在在别的卡上。

  1. 序列分片怎样改变 attention？归一化统计量怎样跨 rank 合并？
  2. 通信、重算与状态，什么时候谁主导？
  3. CP 和 TP 能怎么组合？合法性的边界在哪？

心智模型：切开序列之后，attention 变成一个跨 rank 的归约

机制拆解与推导

1. 归一化统计量怎样跨 rank 合并

attention 的归一化不是「先算完整 softmax 再除」——那样需要 O(S²) 的中间矩阵。它是流式的：每处理一个键值块，就更新三个运行量：

m_new = max(m, rowmax(s))                    运行最大值
l     = l · exp(m − m_new) + Σ exp(s − m_new) 运行归一化因子
O     = O · exp(m − m_new) + exp(s − m_new) · V  运行输出

exp(m − m_new) 这一项是整件事的关键：上一轮的结果是按旧的 m 归一的，m 变大之后必须整体缩放。一个块被完全掩码掉时 rowmax(s) = −∞，m_new 会保持住旧值（max(m, −∞) = m），缩放因子为 1，不出错；但如果 m 初值是 −∞ 而第一个块全被掩码，m − m_new = −∞ − (−∞) = NaN，所以实现里要把非有限的 m 归零再算 exp。这一条是本机实现里唯一需要小心处理的数值细节。

CP 的合并正是在这个层面发生的：每个 rank 拿到的不是「一半的注意力」，而是同一次归约的另一个加数。ring 的做法是把 KV 块沿环转一圈，每个 rank 用所有块更新自己那份 (m, l, O)；ulysses 的做法是先换维，让每个 rank 在完整序列上算自己那几个 head，直接得到完整的 (m, l, O)。两条路的最终数值相同（实测 8.9e-16 与 0.0，都在 FP64 噪声地板内）。

2. 掩码必须用全局位置

本地 Q 只覆盖全局位置 [offset, offset+L)，而键列如果来自完整序列就是 [0, S)。用 arange(L) 去和 arange(S) 比大小，在 CP=1 时碰巧对（offset=0），CP>1 时全错且不报错——它会静默地让每个 rank 按「自己段内的相对位置」做因果掩码。

本机第一版实现就踩了这个坑，报的是形状不匹配（(32) vs (128)），因为掩码形状对不上。如果 S 恰好等于 L×CP 且两边形状碰巧一致，就会静默算错。修法是给参照实现加 q_offset，掩码两侧都用全局位置。

3. dK/dV 不是局部量

这是 CP 最容易搞错的地方：

  • dQ 是局部的。本 rank 的查询只由本 rank 的 Q 产生，autograd 直接对。实测 dQ 误差 0.0。
  • dK/dV 不是。本 rank 的 K/V 块会被所有 rank 的查询用到（ring 里它被传了一圈，ulysses 里它被换维后所有 rank 共享），所以它的梯度是若干份局部贡献之和。

而 PyTorch 的 dist.batch_isend_irecv、dist.all_to_all 没有注册 autograd kernel——直接让 autograd 穿过它们，PyTorch 只发一条 UserWarning，然后给出静默错误的结果。实测：

梯度 正确做法 直接穿 P2P
dQ 0.0 7.8e-16（对，因为它是局部的）
dK 2.7e-15 2.04
dV 2.7e-15 2.66

误差 2.04 与真值同量级，也就是说结果完全不可用，而且没有任何报错。正确做法有两条：手写通信的转置（ring 的反向环、all-to-all 的逆变换），或者把「本地反向得到的每块梯度」跨 rank 归约一次。本机用后者验证：把各 rank 的 K/V 收齐、用本地 Q 在完整序列上跑一次 attention、autograd 得到每块的局部贡献、再 all_reduce 求和，得到 2.7e-15，与参照一致。

4. 两种换维方案的适用条件与通信量

方案 通信模式 轮次 每 rank 字节 前提
ring P2P 环传 KV CP−1 (CP−1) × 2·G·(S/CP)·D·2B 无（非整除也行）
ulysses 两次 all-to-all 2 2 × 2·S·H·D·2B S%CP==0 且 H、G 都被 CP 整除

CP=2、S=8192、Qwen3-8B 结构（H=32, G=8, D=128）实测的每 rank 字节：ring 16.0 MiB，ulysses 256 MiB——ulysses 是 ring 的 16 倍。原因在公式里：ring 每轮只传 KV 块（G=8 个头），而 ulysses 每次 all-to-all 要搬全部 H=32 个头的隐藏状态，还搬两次。

换来的是适用性：ulysses 要求 S % CP == 0，实测 S=70、CP=4 时直接报错拒绝（ValueError: S=70 不能被 CP=4 整除，Ulysses 需要等长分块），而 ring 在同一用例下正常通过（值差 4.4e-16，段长 [18, 18, 17, 17]）。非整除时 ring 是唯一选择；整除时 ulysses 用 16 倍的通信换更简单的计算和更好的 kernel 效率。

5. 容量账：KV 是线性的，激活是平方的

这是本章最重要的一个数。Qwen3-8B（36 层、8 个 kv_head、head_dim 128、BF16）每 rank 的状态（CP 只切序列，不切 head）：

S CP 推理 KV/rank 训练激活/rank（不重算） 激活 ÷ KV
2048 1 288.0 MiB 9.8 GiB 34×
2048 4 72.0 MiB 2.4 GiB 34×
8192 1 1152.0 MiB 146.3 GiB 130×
8192 4 288.0 MiB 36.6 GiB 130×
16384 4 576.0 MiB 145.1 GiB 258×
32768 4 1152.0 MiB 578.4 GiB 514×

两条读法：

CP 对两者的缩放是一样的（都按 1/CP 降），所以比值与 CP 无关，只随 S 线性增长：34× → 130× → 258× → 514×，正好是 S 的 8 倍、16 倍、32 倍关系。用「全局 token 数除以卡数」估算显存，在这两者上会得到完全不同量级的错误——推理 KV 是 S/CP 的线性函数，训练激活是 (S/CP)·S 的双线性函数。

不重算的训练在长上下文下根本放不下。 S=8192、CP=4 时每 rank 训练激活 36.6 GiB，而单卡 44 GiB；S=32768 时 578 GiB/rank。这还没有算权重、优化器状态和 MLP 的中间激活。所以长上下文训练的可行前提是分块 + 重算，CP 只是把 S/CP 这一半账变小，动不了 S 那一半。

6. 实测的显存墙与时间

在 2/4 张 L40S 上按 Qwen3-8B 结构（单层注意力，BF16）实测：

S CP=1 CP=2 CP=4
2048 11.4 ms 6.6 ms 6.0 ms
8192 177.6 ms 97.0 ms 58.3 ms
16384 前向 OOM 372.4 ms 202.3 ms
32768 — 前向 OOM 759.4 ms

（前向，3 次中位；单层。OOM 的原因是单个注意力矩阵 H×S/CP×S×2B：CP=1、S=16384 时它正好是 16 GiB，需要一次连续分配。）

前向本身就已经撞墙了。 CP=1 在 S=16384 上要一次分配 16 GiB 的分数矩阵；CP=2 在 S=32768 上同样。CP=4 能过 S=32768（每 rank 8 GiB 的分数矩阵），但反向仍然 OOM——autograd 要把每一轮的注意力矩阵全部留住，CP=4 时是 3 轮 × 8 GiB。这直接说明：CP 把每 rank 的注意力矩阵按 1/CP 缩小，但没有改变它的 O(S²) 性质；要让它装得下，必须分块（flash 式）+ 重算。

时间上的缩放也不是线性的：CP 从 1 加到 4，S=8192 的前向从 177.6 ms 降到 58.3 ms（3.05×），S=16384 从 OOM 变成 202.3 ms。而 batch 从 1 加到 2，CP=4 的前向从 60.5 ms 变成 115.4 ms（1.9×）——说明在这个规模上时间主要还是被计算而不是被通信主导。

7. CP 与 TP 的组合：切的东西不同

用 profiler 抓到两条方案的实际 collective 顺序（CP=2、S=8192）：

ring    ：c10d::send ×1, c10d::recv_ ×1, nccl:coalesced ×1, c10d::send ×1, ...
ulysses ：c10d::alltoall_ ×1, nccl:all_to_all ×2, c10d::alltoall_ ×1, nccl:all_to_all ×1, ...

CP=4 的 ring 是 3 轮 P2P（CP−1 = 3），与设计一致；ulysses 始终是 2 次 all-to-all，与 CP 无关。

CP 与 TP 的合法性边界不同：

维度 切什么 整除条件 非整除时
CP 序列 ulysses 要 S%CP==0；ring 不要求 ring 可用，段长不等
TP head / 权重 H、G、intermediate 都要被 TP 整除 直接报错（6.2 已测）

两者可以叠加：CP 切序列、TP 切 head，条件互不冲突（S%CP==0 且 H%TP==0、G%TP==0）。实测 CP=4 用 H=16, G=8 组合通过，ulysses 的换维在 head 维上做的正是 TP 也在切的那个维度——所以 Ulysses 常被拿来和 TP 联合调优：它把 CP 的通信放到 head 维上，与 TP 的 all-reduce 共享同一条链路的账。

设计取舍

为什么 CP 只切序列、不切 head。 切 head 是 TP 做的事。CP 的动机是「单卡的序列太长」，所以它切序列；代价是 attention 变成跨 rank 归约。把两者搞混会出现「既切了序列又切了 head」的布局，KV 的分片关系变得难以推理。

为什么 ring 不要求整除而 ulysses 要求。 ring 的每一轮传的是一个「本来就不等长」的段，接收方按对方的段长分配缓冲即可；ulysses 的 all-to-all 要求对等分块，非整除只能补 padding，而补 padding 会污染注意力（padding 位置的分数不能参与 softmax）。所以本机实现选择明确报错，而不是静默补零。

为什么 CP 的反向必须显式写通信。 因为 dK/dV 的贡献来自其他 rank 的查询。框架不可能猜到这一点——all_to_all、isend/irecv 对 autograd 来说只是「一个把数据搬走的黑盒」，梯度穿过去得到的是「把上游梯度原样搬回」，而正确值是「所有 rank 的局部贡献之和」。实测误差 2.04/2.66 说明这不是精度问题，是数量级错误。

为什么 CP 不减少必须要算的 FLOPs。 注意力本身是 O(S²) 的，切成 CP 份之后每 rank 只算 S/CP × S 的分数矩阵，总 FLOPs 不变。CP 换来的是每卡的显存和并行度，不是总计算量。真正减少 FLOPs 的是 3.4 讲的稀疏/线性 attention。

实测数字

  • 值：ring 值差 8.9e-16、ulysses 0.0（FP64 参照，5 个用例覆盖基础/非整除/GQA/窗口/CP=4）。
  • 梯度：正确 CP 梯度 dQ=0.0、dK=dV=2.7e-15；直接穿 P2P 的 dK/dV 误差 2.04/2.66。
  • 适用性：S=70、CP=4 时 Ulysses 明确拒绝，ring 通过（段长 [18,18,17,17]）。
  • 通信量（S=8192、CP=2）：ring 16.0 MiB/rank，ulysses 256 MiB/rank，差 16 倍。
  • 容量：S=32768、CP=4 时推理 KV 1152 MiB/rank，而不重算的训练激活 578.4 GiB/rank，比值 514×。
  • 显存墙：CP=1 前向在 S=16384 OOM（单个分数矩阵 16 GiB）；CP=4 前向能过 S=32768（759.4 ms）但反向仍 OOM（3 轮 × 8 GiB）。
  • collective 顺序：ring 每轮 send/recv_ + nccl:coalesced，共 CP−1 轮；ulysses 固定 2 次 alltoall_ + nccl:all_to_all。

消融建议

  1. 把 ring_attention 的 m 初始化从 -inf 改成 0，观察全掩码块是否产生 NaN——用来确认「非有限 m 归零」这条分支是必需的。
  2. 把掩码换成局部相对位置（arange(L) 对 arange(S)），观察 CP=2 时值差是否立刻变大——这是本章最容易静默出错的一处。
  3. 把 ring 的分块从整块改成 flash 式小块（例如 1024），重新跑 S=16384/32768，观察前向与反向的显存墙是否被推后。
  4. 在 cp_gradients 里去掉 all_reduce，观察 dK/dV 是否正好变成「只有本 rank 查询的贡献」——用来量化跨 rank 归约到底贡献了多少。

前沿

ring attention 与它的变体。 ring attention 的价值在于通信量随 CP 线性增长而不随 S 增长（每轮只传 1/CP 的 KV），且能与计算重叠。变体主要在两处做文章：块大小与重叠策略（把 KV 传输与本地 flash 计算压到不同流上），以及负载均衡（因果掩码下每轮的 KV 块长度不同，需要按「负责多少查询」重新分配）。

Ulysses 与 TP 的联合。 Ulysses 在 head 维上做 all-to-all，而 TP 也在切 head，所以两者可以复用同一条链路的账，甚至可以把 CP 的换维和 TP 的 all-reduce 合并。这条路的复杂度在于布局：(B, H, S, D) 在 CP、TP、DP 三维上的分片关系必须一次性推清楚。

重算与分块是长上下文的硬前提。 本章测到 S=32768、CP=4 时训练激活 578 GiB/rank。任何不重算的方案都放不下。真正的解法是 flash 式分块（把 O(S²) 的分数矩阵变成 O(S·Bc) 的块）+ 选择性重算（把激活换时间）。CP 与它们是正交的：CP 缩小每卡的 S/CP，分块与重算把 S 那一半的常数压下来。

与稀疏/线性 attention 的关系。 3.4 讲的稀疏与线性 attention 是减少必须算的 FLOPs；CP 是把同样的 FLOPs 分到更多卡上。两者不冲突也不互相替代：一个 32K 上下文的模型可以同时用滑动窗口（减 FLOPs）和 CP（分显存）。本机没有做两者叠加的实测，保持 UNVERIFIED。

陷阱

1. 用相对位置做因果掩码。 本地 Q 的全局行号是 offset+i，键列是全局位置。CP=1 时碰巧对，CP>1 时全错且可能不报错。

2. 让 autograd 穿过 P2P 或 all_to_all。 这两个算子没注册 autograd kernel，PyTorch 只发一个警告然后给出静默错误的结果。实测 dK/dV 误差 2.04/2.66，与真值同量级。CP 的反向必须显式写通信转置或跨 rank 归约。

3. 把 dQ 和 dK/dV 当成同一类量。 dQ 是局部的（本 rank 查询），autograd 直接对；dK/dV 是全局的（所有 rank 的查询都要用）。两者在 CP 下的性质完全不同。

4. 用「全局 token 数 ÷ 卡数」估算显存。 推理 KV 是 S/CP 的线性函数，训练激活是 (S/CP)·S 的双线性函数。S=32768、CP=4 时两者差 514 倍。

5. 认为 CP 能减少总计算量。 CP 把 S×S 的分数矩阵按 1/CP 切开，总 FLOPs 不变。它换的是每卡显存和并行度。减少 FLOPs 要靠稀疏/线性 attention。

6. 以为切了 CP 就能训长上下文。 S=8192、CP=4 时每 rank 训练激活 36.6 GiB，S=32768 时 578 GiB。不重算的路线在任何 CP 度下都放不下；分块 + 重算是前提。

7. 用 Ulysses 处理非整除序列。 S=70、CP=4 时它直接报错。要么改用 ring，要么补 padding——而补 padding 会污染 softmax（padding 位置的分数不能参与归一化）。

8. 忽略在线 softmax 的数值边界。 一个块被完全掩码时 rowmax = -inf；若此时运行最大值还是初值 -inf，exp(-inf - (-inf)) = NaN。实现里必须把非有限的 m 归零。实测的 FP64 值差 8.9e-16 说明这条分支处理对了。

自测题

1. CP=4、S=32768、Qwen3-8B 结构时，每 rank 的推理 KV 是多少？训练激活呢？

推理 KV = 2 × 36 层 × 8 kv_head × (32768/4) × 128 × 2 B = 1152 MiB/rank。 训练激活（不重算）= 36 层 × (32 head × 8192 × 32768 × 2 B + 32 × 8192 × 128 × 2 B) ≈ 578.4 GiB/rank。 两者相差 514 倍，而这个比值 = S / 6 ≈ S 的线性函数；它只与 S 有关，与 CP 无关。

2. 为什么 dQ 可以直接用 autograd，而 dK/dV 不行？

本 rank 的查询只由本 rank 的 Q 产生，所以 dQ 是局部的，autograd 沿着本地计算图就能得到正确值（实测误差 0.0）。而本 rank 的 K/V 块会被所有 rank 的查询用到——ring 里它被传了一圈，ulysses 里它被换维后共享——所以 dK/dV 是若干份局部贡献之和，必须跨 rank 归约。PyTorch 的 P2P 与 all_to_all 没有注册 autograd kernel，直接穿过去只会得到「把上游梯度原样搬回」的错误结果（实测误差 2.04/2.66）。

3. ring 与 ulysses 的通信量差多少？为什么？

CP=2、S=8192、Qwen3-8B 结构下 ring 是 16.0 MiB/rank，ulysses 是 256 MiB/rank，差 16 倍。 ring 每轮只传 KV 块 2·G·(S/CP)·D，G=8；ulysses 每次 all-to-all 要搬全部 H=32 个头的隐藏状态 S·H·D，而且要搬两次。16 = (2 × 32) / (1 × 8) × … 用公式看：ring 总量 = (CP−1)·2·G·(S/CP)·D·2B，ulysses = 4·S·H·D·B，比值 = 2H·CP/((CP−1)·G) = 2×32×2/(1×8) = 16。

4. S=70、CP=4 时两条路各是什么结果？

ring 通过：段长 [18, 18, 17, 17]，值差 4.44e-16，3 轮通信。ulysses 直接报错：S=70 不能被 CP=4 整除，Ulysses 需要等长分块。这条限制不是实现偷懒——all-to-all 需要对等分块，补 padding 会让 padding 位置的分数进入 softmax，必须排除。所以非整除时 ring 是唯一选择。

5. 在线 softmax 里 `m` 的初值是 −inf，如果第一个键值块被完全掩码会发生什么？

rowmax(s) = −inf，m_new = max(−inf, −inf) = −inf，于是 exp(m − m_new) = exp(−inf − (−inf)) = exp(NaN) = NaN，整个输出变成 NaN。修法是把非有限的 m_new 归零再算指数（此时 alpha = exp(−inf − 0) = 0，正确地把旧贡献清掉），并对 p 也做同样的有限性检查。

6. CP 能减少注意力的总 FLOPs 吗？

不能。完整的注意力是 O(S²)，切成 CP 份之后每 rank 算 S/CP × S 的分数矩阵，加起来还是 S²。CP 换到的是每卡显存和并行度。要减少 FLOPs 得靠 3.4 讲的稀疏（滑动窗口/sink）或线性 attention——而两者可以叠加：滑动窗口减 FLOPs，CP 分显存。

7. 为什么 CP=4 能跑通 S=32768 的前向，反向却 OOM？

前向只需要当前的分数矩阵，CP=4 时每 rank 是 32 × 8192 × 32768 × 2B = 8 GiB，一次分配放得下。反向要保存每一轮的分数矩阵用于计算梯度，ring 有 3 轮，就是 3 × 8 = 24 GiB，加上其他的就超出 44 GiB 卡。这说明 CP 把注意力矩阵按 1/CP 缩小，但没有改变它的 O(S²) 性质——要真正放下必须分块 + 重算。
