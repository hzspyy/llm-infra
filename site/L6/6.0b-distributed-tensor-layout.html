分布式张量：DeviceMesh、DTensor 与布局变换

从全局张量、局部 shard 和进程组构造 DeviceMesh，剖析 Shard、Replicate、Partial 与 redistribute，连接布局传播、autograd 和 FSDP2。

实测机器 本地（macOS，CPU，torch 2.14.0）· worldvln（2× L40S，sm_89，torch 2.13.0+cu130）前置 6.0（进程组与完成语义）· 7.0（autograd 图）

本章回答三个问题

6.0 讲了 rank 手里有什么、谁和谁配对、什么时候算完成。但「每个 rank 该持有哪些元素」这件事还没有被形式化。PyTorch 的答案是 DeviceMesh + placement：把一个逻辑上的全局张量描述成「在哪些 rank 上、以什么方式切开」，然后让算子沿着这个描述传播。

这套描述的价值在于把并行策略变成可以写下来、可以检查、可以被框架自动传播的东西。代价是它引入了一个新的失败模式：局部 shape 相同不代表全局语义相同，而布局变化可能在你没写任何通信调用的地方触发通信。

  1. 全局张量怎样表示为局部片段？三类 placement 的数值语义分别是什么？
  2. 布局怎样沿算子传播？哪些算子会隐含通信？
  3. Partial 在前向和反向里怎么表现？梯度对拍怎么做？

心智模型：一个全局张量，三张局部视图

机制拆解与推导

1. rank 坐标与切分规则

DeviceMesh 把一组 rank 组织成多维网格。rank 到网格坐标的映射是行主序（最后一个 mesh 维变化最快），这与 torch.arange(shape).reshape(shape) 的展开顺序一致：

def mesh_coord(rank, mesh_shape):
    coord = []
    for size in reversed(mesh_shape):
        coord.append(rank % size)
        rank //= size
    return list(reversed(coord))

对一个 mesh 维上的 Shard(dim)，第 i 段的大小按 torch.chunk 的规则切分：前 n % k 段各多 1。7 切 2 得 [4, 3]，5 切 2 得 [3, 2]。段起始下标是前面各段之和，也就是 i * (n // k) + min(i, n % k)。

实测（labs/L6/mini_dtensor.py，本地 Gloo，2 rank）：

全局张量 placement rank 0 rank 1
8×6 S(0) (4,6) stride (6,1) offset [0,0] (4,6) stride (6,1) offset [4,0]
8×6 S(1) (8,3) stride (6,1) offset [0,0] (8,3) stride (6,1) offset [0,3]
8×6 R (8,6) (8,6) 完全相同的副本
7×5 S(0) (4,5) offset [0,0] (3,5) offset [4,0]
7×5 S(1) (7,3) offset [0,0] (7,2) offset [0,3]

S(1) 那一行的 stride 值得单独看：局部块的 shape 是 (8,3)，但 stride 是 (6,1)——它是全局张量的一个视图，不是一块连续内存。把 to_local() 直接交给要求连续的 kernel，得到的是错的。 这也是「局部 shape 相同不保证全局语义相同」的最直接例子：两个 rank 的局部 shape 都是 (8,3)，但一个从第 0 列开始，一个从第 3 列开始。

手写的放置函数与 DTensor 的 to_local() 在 8×6 与 7×5 两个张量、S(0)/S(1)/R 三类 placement、2 rank 与 2×2（4 rank）两种 mesh 上共 6 个组合全部逐元素相等；把各 rank 的局部块按 offset 拼回去，也与全局张量逐元素相等。

2. Partial 不是副本，是一个加数

Partial(sum) 的语义是：全局张量等于所有 rank 的局部张量逐元素之和。局部 shape 与全局相同——这一点最容易骗人，因为一个 (8,6) 的张量看上去就是一份完整数据。

Shard(0) → Partial(sum) 的转换是纯本地的：每个 rank 把自己的那段放进一个同 shape 的全零张量，位置对上就行。实测 rank 0 的局部和是 276、rank 1 是 852，逐元素相加得到 1128，正好等于全局张量的和；对 rank 0 来说，局部和 276 恰好等于全局前 24 个元素之和。

这个转换在不同版本上的可用性不同

同一句 redistribute(mesh, [Partial()])，本地 torch 2.14.0 直接执行并与手写结果逐元素相等；worldvln 的 torch 2.13.0 报错：

RuntimeError: Can not redistribute from S(0) to P(sum),
redistributing to Partial is for internal use only!

版本差异不改变 Partial 的数值语义，但决定了它是不是一个公开的 API 路径。凡是依赖「显式转换到 Partial」的代码都要按版本核对。

3. 布局传播是一次纯局部推理

torch/distributed/tensor/_sharding_prop.py 的 ShardingPropagator.propagate（:710）为每个算子推导输出 placement。本章对 10 个表达式先写下预测、再跑真实 DTensor，两种后端上都是 10/10 命中：

表达式 输出 placement 局部 shape 描述
matmul(xS0, Wr) S(0) (2,6) x 的分片维不与收缩维重合，逐 rank 独立算
matmul(xr, WS1) S(1) (4,3) W 的第 1 维被切走，输出第 1 维随之分片
linear(xS1, WS1) P(sum) (4,6) 列并行，各 rank 只算了一部分和
linear(xr, WS0) S(1) (4,3) 行并行，输出直接在最后一维分片
linear(xr, WS1) P(sum) (4,6) 列并行，输出是部分和
sum(xS0) P(sum) [] 全量求和消掉分片维
sum(dim=1)(xS1) P(sum) [4] 被求和维正是分片维
reshape(xS0) S(0) (1,12) 分片边界在 reshape 后仍落在第 0 维
t(xS1) S(0) (3,4) 转置把分片维搬到第 0 维
redistribute S0→S1 S(1) (4,3) 显式换分片维，必须交换数据

这 10 个表达式里，只有最后一行在算子执行期间产生了通信。 前 9 个的 placement 都是局部规则算出来的，通信被推迟到「把结果物化」的那一刻：

操作 算子内通信 full_tensor() 时的通信
matmul(xS0, Wr) / matmul(xr, WS1) 0 all_gather_into_tensor ×1
linear(xS1, WS1) / linear(xr, WS1) 0 all_reduce ×1
linear(xr, WS0) 0 all_gather_into_tensor ×1
sum(xS0) / sum(dim=1)(xS1) 0 all_reduce ×1
reshape(xS0) / t(xS1) 0 all_gather_into_tensor ×1
redistribute S0→S1 1（见下） 0

Partial 物化走 all_reduce，Shard 物化走 all_gather_into_tensor——这条对应关系不依赖后端。「布局推理本身不发通信」和「布局变化会隐含通信」这两句话并不矛盾：前者说的是传播阶段，后者说的是边界阶段。只统计显式 dist.all_reduce 调用，会漏掉物化阶段这 10 次。

4. 换分片维：同一条 redistribute，两种后端实现

Shard(0) → Shard(1) 必须做一次「换维」，两个后端的实现路径不同：

后端 dispatch 到的算子 底层
Gloo（CPU） all_gather_into_tensor 先 all-gather 再按维切开（见下）
NCCL（CUDA） _dtensor::shard_dim_alltoall nccl:all_to_all

CPU 侧的 fallback 在源码注释里写得很直白（torch/distributed/tensor/_collective_utils.py:107-110）：

def shard_dim_alltoall(input, gather_dim, shard_dim, mesh, mesh_dim):
    if mesh.device_type == "cpu" and local_tensor_mode() is None:
        # Gloo does not support alltoall, so falling back to allgather + chunk
        warning_once(
            logger,
            "CPU process group does not support alltoall yet, falling back with allgather + chunk!",
        )

也就是说：同一段 DTensor 代码在 CPU 上跑，走的是「把整个全局张量聚起来再切」的路径；在 GPU 上跑，走的是真正的 all-to-all。两者数值相同，通信量不同——all-gather 方案每个 rank 收到完整的全局张量，all-to-all 方案只需要收发自己那一份。

5. Partial 在前后向里的位置

用 x 行分片、W 复制的两 rank 线性层做对拍（y = linear(x, W)，loss = (y²).sum()，float64）：

量 实测 placement 说明
y S(0) 前向零通信
loss P(sum) 局部标量 16.485886，全局 31.605360，单机参照 31.605360
grad_x S(0) 与输入同布局，与单机梯度最大绝对差 0
grad_W P(sum) 梯度是部分和，必须归约后才能当完整梯度用

grad_W 是这张表里最关键的一行。每个 rank 只用自己的那部分激活算出了权重的部分梯度，所以 W.grad 天然是 Partial。把它 full_tensor() 之后与单进程梯度逐元素比较，完全一致。通信字节账：

  • loss 物化：all_reduce 在标量上，8 字节。
  • grad_W 物化：all_reduce 在 (3,4) 的 float64 上，96 字节。
  • 前向与反向本身：0 次通信。

换成列并行（x 复制、W 按输入维分片）之后，位置换了一处：

量 实测 placement
y P(sum)
loss R（在 sum() 内部就已经归约完毕）

列并行下必须做一次 all_reduce，而它发生在 .sum() 内部（(8,3) float64 = 192 字节），不是物化的时候。同一个 loss = (y**2).sum() 表达式，前面的布局不同，通信发生的位置就不同——一个在算子内，一个在物化时。这正是「不能只计显式 collective 调用」的含义。

6. redistribute 的临时 buffer

Shard(0) → Replicate 需要一个完整副本，临时 buffer 就是全局张量本身。用一个 4096×1024 的 float32 张量（全局 16 MiB，每 rank 8 MiB）在 2×L40S 上做 3 轮 redistribute：

指标 实测
每次 redistribute 的通信 all_gather_into_tensor ×1，输入是 8 MiB/rank 的局部块
分配峰值（max_memory_allocated） 40.26 → 72.26 MB
循环结束后已分配 40.26 → 56.26 MB（+16 MiB，正好是一份 Replicate 结果）
释放后（del + gc.collect() + empty_cache()） 回到 40.26 MB，reserved 从 90 MB 回到 58 MB

reserved 涨到 90 MB 而 allocated 只涨 16 MB，差额是 CachingAllocator 为这次 all-gather 预留的段。把结果引用释放掉并清空缓存后，两者都回到基线——临时 buffer 的「释放」分成两件事：引用释放让 allocated 立刻回落，缓存清空才让 reserved 回落。

设计取舍

为什么把 placement 做成数据而不是函数。 Shard/Replicate/Partial 是三个可以比较、可以打印、可以参与传播规则匹配的值。这让「算子支持哪些输入布局组合」变成一张可以机械查询的表（_sharding_prop.py 里的 ShardingPropagator），而不是散落在每个算子实现里的 if-else。代价是每接一个新算子都要给出这张表的对应行，否则传播会失败或退化。

为什么 Partial 存在。 没有 Partial，列并行的输出就必须在算子内部立刻归约，通信无法与后续计算重叠；有了 Partial，「这是一个还没归约的部分和」变成类型系统里的一等信息，归约可以推迟到真正需要完整值的时候。代价是任何把 Partial 当完整副本用的代码都会静默拿到错值。

为什么 CPU 上退化。 Gloo 不提供 all-to-all，CPU 侧的 shard_dim_alltoall 只能先 all-gather 再切。这不影响正确性，但让同一段代码在两个后端上的通信量和显存峰值不同。跨设备复用布局代码时，这个差异要按后端核对。

为什么 reshape 不总是免费的。 只有当分片维的块边界在 reshape 后仍然对齐时，传播才能保持 S(dim) 不变（本例 (4,6) → (1,12) 的第 0 维刚好整除）。一旦 reshape 把分片维打散到多个维上，就必须先 redistribute 成 Replicate 再 reshape。这类「看起来是 view、实际上是通信」的改动，是跨并行度复用模型代码时最常见的性能回归来源。

 96 def split_sizes(n, k):
 97     """把长度 n 切成 k 段，前 n%k 段多 1。与 torch.tensor_split 的分法一致。"""
 98     base, rest = divmod(n, k)
 99     return [base + (1 if i < rest else 0) for i in range(k)]

103     """第 i 段在长度 n 上的起始下标。"""
104     base, rest = divmod(n, k)
105     return i * base + min(i, rest)

108 def place(global_tensor, mesh_shape, placements, coord):
109     """返回 coord 这个 mesh 坐标上应该持有的局部张量。"""

重建全局张量时，Partial 与另外两类走的是两条不同的路径——前者求和，后者按 offset 摆放：

155 def reconstruct(shards: dict, mesh_shape, placements, global_shape, device="cpu"):
156     """shards: {rank: local tensor}。返回全局张量。
157 
158     Partial 的语义是「全局 = 各 rank 之和」，其余两类是「按 offset 摆放」。
159     """
160     if any(isinstance(p, Partial) for p in placements):
161         acc = None
162         for r in sorted(shards):
163             acc = shards[r].clone() if acc is None else acc + shards[r]
164         return acc
165     out = torch.zeros(global_shape, dtype=torch.float64, device=device)
166     for r in sorted(shards):
167         coord = mesh_coord(r, mesh_shape)
168         start = local_offset(global_shape, mesh_shape, placements, coord)
169         t = shards[r]
170         idx = tuple(slice(start[d], start[d] + t.shape[d]) for d in range(len(global_shape)))
171         out[idx] = t
172     return out

消融建议

  1. 把 mini_dtensor.py 的 7×5 换成 6×6，观察不整除切分的 [4,2] 变成 [3,3] 后 offset 表如何变化——这是验证「切分规则」而不是「碰巧对上」的最快方式。
  2. 在任务 B 里把 reshape(2,12) 改成 reshape(3,8)。第 0 维 4 不能整除以 3，传播会失败或先 redistribute，可以直接看到「view 变成通信」。
  3. 在任务 C 里把 loss 换成 y.sum() 之外的、不消掉分片维的表达式（例如 (y * c).sum() 保留 S(0)），观察通信从「物化时」挪回「算子内」。
  4. 把 2×2 mesh 上的 [Shard(0), Shard(1)] 改成 [Shard(0), Shard(0)]，确认框架明确报错而不是静默变换。

前沿

编译期布局求解。 当前传播是「按算子逐条查表」。更激进的方向是把整张计算图上的布局选择当成一个带通信代价的优化问题：给定 mesh 拓扑和算子代价模型，搜索一组 placement 使总通信最小。PyTorch 的 _redistribute.py 里已经有按代价排序的 transform 规划（_redistribute_cost_sort_key，:57），但它仍然是对单次 redistribute 的局部选择，不是全局搜索。

自动并行与图重写。 TensorRT-LLM、JAX 的 shard_map/GSPMD 与 PyTorch 的 torch.compile 在 DTensor 之上做图级重写。这条路线与本章的关系是：本章的传播规则是它们的输入契约，placement 不合法时它们只会报「不支持」，不会替你猜。

通信合并。 _redistribute.py:414-435 描述了把多个小 collective 合并成一次的做法（MERGEABLE_COMMUT_TYPES 明确排除了 all-to-all）。这条对长尾小张量（比如每层都有一次小块 all-reduce）收益明显，代价是合并后必须等齐所有参与者，延迟方差变大。本章没有做合并前后的实测，保持 UNVERIFIED。

FSDP2 与 DTensor。 FSDP2 用 Shard(0) 表示参数分片、用 Partial 表示未归约的梯度累积，本章的三类 placement 正是它的状态表示。6.2 与 7.2 会在这个基础上继续。

陷阱

1. 把局部 shape 相同当成全局语义相同。 S(1) 下两个 rank 的局部 shape 都是 (8,3)，但一个从第 0 列开始、一个从第 3 列开始。跨 rank 对齐时只能比全局视图，不能比局部 shape。

2. 把 Partial 当完整副本。 行并行下 loss 的 placement 是 P(sum)，局部标量 16.485886，真值是 31.605360——差了整整一倍。任何在归约前读 Partial 局部值的代码都会静默拿到错值。

3. 只统计显式 collective 调用。 本章 10 个表达式里有 9 个在算子执行期间零通信，但每一个在 full_tensor() 时都产生一次通信。若仅按显式调用 dist.all_reduce 的次数评估通信开销，会系统性低估隐式通信代价。

4. 直接消费 to_local()。 S(1) 的局部块 stride 是 (6,1)、shape 是 (8,3)，不是连续内存。需要连续输入时必须显式 .contiguous()，那是一次复制。

5. 假定 reshape 不通信。 只有当分片维的块边界在 reshape 后对齐才能保持布局不变。边界打散时会触发 redistribute，代价是一次 all-gather 级别的通信。

6. 忽略 CPU 与 GPU 的路径差异。 同一句 redistribute(S0→S1)，Gloo 走 all-gather + chunk，NCCL 走 all-to-all。数值一样，通信量与显存峰值不同。

7. 把「转换到 Partial」当成稳定 API。 torch 2.13 直接拒绝，2.14 允许。依赖这条路径的代码要先核对版本。

自测题

1. 全局张量形状 `(10, 6)`，mesh 大小 4，`Shard(0)` 下各 rank 的局部 shape 是什么？

[3, 3, 2, 2]。切分规则是「前 n % k 段各多 1」，10 = 3+3+2+2。前两个 rank 拿 3 行，后两个拿 2 行。

2. `Shard(1)` 的局部块 shape 是 `(128, 32)`，全局 shape 是 `(128, 128)`，mesh 大小 4。这个局部块的 stride 是多少？

(128, 1)。它仍然是全局张量的视图，第 1 维的步长等于全局的行宽，不是局部的 32。

3. 两个 rank 上的张量局部 shape 都是 `(4, 6)`，能断定它们在全局视图里占同一段吗？

不能。S(0) 下 rank 0 的 offset 是 [0,0]、rank 1 是 [4,0]，形状相同、位置不同。要判断必须看 placement 和 offset。

4. `loss = (y ** 2).sum()`，`y` 的 placement 是 `P(sum)`。局部 loss 是 16.49，全局是多少？

至少是 16.49 加上其他 rank 的局部和。实测两 rank 下全局是 31.61，与单机参照一致。局部值在归约前只是「本 rank 的加数」。

5. 为什么 `x` 行分片、`W` 复制时，`W.grad` 是 `Partial`？

每个 rank 只用自己的那部分激活算权重梯度，算出来的是完整权重梯度的一部分。反向传播不会自动把它们加起来，所以 W.grad 带着 Partial(sum) 布局，直到有代码把它归约成完整梯度。实测 full_tensor() 触发一次 96 字节的 all_reduce，结果与单机逐元素一致。

6. 把 `to_local()` 交给一个要求连续输入的 kernel，会发生什么？

如果 placement 是 S(1)，局部块是全局张量的非连续视图（stride 里带着全局行宽），kernel 会按错误的步长读数据。需要先 .contiguous()，那会复制一份。

7. 同一段 DTensor 代码在 CPU 和 GPU 上跑，`redistribute(S0→S1)` 的通信量一样吗？

不一样。Gloo 没有 all-to-all，退化成 all-gather + chunk，每个 rank 都要收下完整的全局张量；NCCL 走 all_to_all，每个 rank 只收发自己那一份。数值相同，通信量和显存峰值不同。
