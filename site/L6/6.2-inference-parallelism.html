6.2

推理并行：TP / PP / EP / CP

各自的通信量分析与实测；无 NVLink 下 TP 的真实代价。

实测机器 worldvln（2×/4× L40S，PCIe，无 NVLink）· vLLM 0.29.0 · Qwen3-8B（BF16）前置 6.0b（DTensor 布局）· 6.1（集合通信成本）· 4.4（MoE 路由）· 5.3（调度）

本章回答三个问题

6.1 量到了链路的价钱：这台机器上 all_reduce 的每方向速率是 14.8 GB/s，一次 64 MiB 的归约要 4.6 ms。把模型切开之后，每一步都要付这笔钱。所以并行不是一个「更多卡等于更快」的问题，而是一个「切分省下的时间能不能盖住通信」的问题。

  1. TP / PP / EP / CP 各自切什么？聚合发生在哪一层？
  2. 哪些形状必须整除？不整除会怎样？
  3. 多大的负载才足以覆盖通信成本？

这一章先用两 rank 的手写实现把四种切分的语义钉死，再在 worldvln 上用 Qwen3-8B 实测 TP=1/2/4 与 PP=2。结论的边界是明确的：单机 PCIe、无 NVLink。换到 NVLink 机器上，通信与计算的相对价格会变，最优并行度也会变。

心智模型：四种切法，四处通信

机制拆解与推导

1. 列并行与行并行：通信位置的差别

切权重矩阵有两种切法，通信位置完全不同。

列并行（column parallel） 按输出维切 W ∈ R^{out×in}：每个 rank 拿 W[rank·out/n : (rank+1)·out/n, :]。因为每行输出只依赖完整的输入，各 rank 用同一份输入算自己那段输出，前向不需要任何通信。MLP 的第一个线性层、attention 的 QKV 投影都属于这类。

行并行（row parallel） 按输入维切：每个 rank 拿 W[:, rank·in/n : (rank+1)·in/n]，对应的输入也必须按最后一维切好。每个 rank 算出的是一部分和，必须 all_reduce 才能拼成完整输出。MLP 的第二个线性层、attention 的输出投影属于这类。

一次完整的 MLP 因此是「列并行 → 激活 → 行并行」：

def mlp_tp(x, W1_local, W2_local, group=None):
    h = gelu(col_parallel_linear(x, W1_local))   # 零通信
    return row_parallel_linear(h, W2_local, group=group)   # 一次 all_reduce

通信量正好是一次 all_reduce 的 S × hidden 元素。 每层每 token 两次（MLP 一次、attention 一次），与 TP 度无关——切得越细，单次 all_reduce 的字节数不变（因为输出维度是 hidden，不随 TP 变），但参与的 rank 变多，按 6.1 的公式时间反而上升。这就是 TP 收益不线性增长的原因。

把两 rank 的 MLP 与 attention 与单进程 FP64 参照逐元素对拍：

| 算子 | 局部分片 | 与单进程参照最大绝对差 | 结果 | |—|—|—|—:|—| | MLP（列+行并行，TP=2） | 中间激活 (64, 3072) | 3.9e-16 | 一致 | | attention（GQA，TP=2） | 局部 Q (64, 1024) | 2.8e-16 | 一致 |

（CUDA/NCCL 两卡；CPU/Gloo 上分别是 3.2e-15 与 6.7e-16。）

attention 这一侧的切分要小心：head 维切开之后，Q 的每个 head 只在本 rank 上，K/V 因为 GQA 而是每 heads/kv_heads 个 Q head 共享一个。按 (S, heads, head_dim) 直接做 q @ k.transpose(1,2) 会把 head 维当成 batch 维，必须先排成 (heads, S, head_dim)。这不是精度问题，是形状对不上的硬错误。

2. 整除条件

TP 不是任意度都合法。每个被切开的维度都必须能被 TP 整除：

结构参数 Qwen3-1.7B TP=1 TP=2 TP=4 TP=8 TP=16
num_attention_heads 16 ✓ ✓ ✓ ✓ ✓
num_key_value_heads 8 ✓ ✓ ✓ ✓ ✗
intermediate_size 6144 ✓ ✓ ✓ ✓ ✓
vocab_size 151936 ✓ ✓ ✓ ✓ ✓
hidden_size 2048 ✓ ✓ ✓ ✓ ✓

限制来自 GQA 的 KV head 数：Qwen3-1.7B 只有 8 个 KV head，TP=16 时每 rank 分到 0.5 个。手写实现里这一点是显式报错而不是静默变换：

def shard_rows(W, tp_rank, tp_size, dim=0):
    n = W.shape[dim]
    if n % tp_size:
        raise ValueError(f"维度 {dim} 长度 {n} 不能被 TP={tp_size} 整除")

Qwen3-8B 的对应参数是 heads=32、kv_heads=8、hidden=4096、inter=12288、vocab=151936，限制同样落在 kv_heads 上：TP ≤ 8。

词表是另一个容易踩的点。 151936 = 2⁷ × 1187，能被 128 整除，所以词表切分不是限制；但很多模型的词表带零头（例如 152064 或 32000 之外的奇数），TP 一大就会在 lm_head 上分不匀，需要 padding 或者让最后一个 rank 多拿一行。这类条件在换模型时必须重新算，不能沿用上一次的 TP 度。

3. 两阶段流水：气泡在哪里

PP 切的是层，通信量是每微批的激活量 S × hidden，与切了多少层无关。代价是气泡：第一个微批在 stage0 算的时候 stage1 闲着，最后一个微批在 stage1 算的时候 stage0 闲着。

手写两阶段流水（hidden=512、inter=2048、S=64、FP64，2 rank）实测：

微批数 总时间 stage0 计算 + 发送 stage1 计算 + 等收 计算利用率
1 1.36 ms 0.96 + 0.40 ms 0.90 + 1.47 ms 68.2%
2 2.73 ms 2.24 + 0.48 ms 1.70 + 1.96 ms 72.3%
4 5.39 ms 4.78 + 0.59 ms 3.44 + 2.84 ms 76.4%
8 11.27 ms 10.01 + 1.26 ms 6.80 + 5.32 ms 74.6%

每个微批的输出与单进程参照逐元素相等（max|diff| = 0）。两条读法：

stage0 永远是瓶颈。 它的「计算 + 发送」占满了整个观测窗口（空闲 0.00–0.01 ms），stage1 则一直有空闲。在这个玩具里两个 stage 的 FLOPs 相同，但 stage0 多付了发送的成本，所以先到极限。真实模型里 stage 之间层数不等时，「最慢的 stage 拖住整条流水」是同一个现象。

利用率在 68%–76% 之间徘徊，不随微批数单调改善。 在亚毫秒量级上，每次迭代的固定开销（分配缓冲、Python 粘合、gloo 的每消息成本）与计算同量级，测出来的「气泡」里混着这些开销。所以这张表只用来演示气泡存在、以及气泡由谁造成，不用来给出利用率的上界。

在 GPU 上这个实验会暴露另一个事实：把 dist.send 逐个微批同步调用，4 个微批里发送占了 44.6 ms 中的 44.60 ms——同步的、未批量化的 P2P 每次微批都新参与一次通信子建立（6.0 已经确认过这条路径的开销）。真实的 PP 实现用 batch_isend_irecv 成对提交，并把发送与计算叠在不同流上，不会这样写。

4. 真实部署：Qwen3-8B 的 TP 与 PP

固定 BF16、关闭 prefix caching、关闭 CUDA Graph（enforce_eager=True），输出固定 128 token，贪心解码。TTFT 取批内各请求首 token 时刻的中位数，TPOT 取「(完成 − 首 token) / (输出 token − 1)」的中位数。

三条结论：

TP=2 是这台机器上的最优点。 decode 每 token 的延时降了 26%–31%，吞吐涨了三成——因为 decode 是权重带宽受限的：TP=2 把每个 rank 每步要读的权重字节砍半，而每次 all_reduce 只搬运 S × hidden 的激活（S=1 时是 2 × 4096 × 2 字节 = 16 KiB），代价很小。

TP=4 反而更差。 TPOT 只降 17%–25%（不如 TP=2），TTFT 却涨了 57%–87%。原因有两个：all_reduce 的参与 rank 变多、每步的固定开销上升；prefill 阶段每层都要同步，而 prefill 的通信量与计算量之比本来就比 decode 高。这就是「小模型多卡减速」——切分省下的时间没有盖住通信。

PP=2 改善的是 TTFT，不是 TPOT。 B=8、S=2048 时 TTFT 降 18%（两个 stage 并行处理不同微批，prefill 被摊开），而 TPOT 几乎不变（decode 每步只处理 1 个 token，PP 无法把单步拆开，反而多了一次跨 stage 传递）。B=1 时 TPOT 甚至微微变差。PP 对延迟的作用取决于负载里 prefill 与 decode 的比例。

S=8192 的长上下文下 TP=2 的收益依然存在（B=8：TTFT −5.6%、TPOT −32.9%、吞吐 +29.3%），说明结论不只是短序列的偶然。

5. 权重分片与显存

TP 的收益来自权重被真正切开了。vLLM 启动日志里每个 worker 自己报告加载量：

配置 每 worker 权重 可用 KV cache 说明
TP=1 15.27 GiB 14.72 GiB 单卡放下全部 8B 权重
TP=2 7.64 GiB 22.65 GiB 权重正好减半；KV 也按 head 切分，所以每 rank 能装更多 token

7.64 × 2 = 15.28 ≈ 15.27，两个 rank 的加载量之和等于单卡。这是「权重按输出/输入维切开」这条规则在真实引擎里的直接体现，也是不能把各卡显存简单相加的原因：显存里除了权重还有激活、KV cache、通信缓冲和框架开销，能用多少 KV 取决于 gpu_memory_utilization 与运行时峰值。

6. 专家并行：切的是路由，不是形状

EP 与 TP 的代价模型不同。MoE 层里每个 token 按路由结果被送到 top-k 个专家，EP 把这些专家分散到不同 rank：每个 rank 只持有 num_experts / EP 个专家。通信是 all-to-all——把 token 送到专家所在的 rank，算完再送回。

因此 EP 的通信量由路由分布决定，而不是由权重形状决定：token 越多、top-k 越大、路由越倾斜，通信量越大。它与 TP 不能互相代入：TP 的通信量随 hidden 走，EP 的通信量随 token 数走。6.3 会完整展开 dispatch/combine 与负载均衡。

配置 每 rank 专家 引擎初始化 TTFT TPOT 总时间 吞吐
EP=1（TP=1 基线） 64 41.2 s 194.88 ms 13.800 ms 1.1 s 477.5 tok/s
EP=2（TP=2 + EP） 32 148.3 s 481.22 ms 3243.870 ms 209.8 s 2.4 tok/s

EP=4 正常但比 EP=1 慢。 TTFT 涨 152%、TPOT 涨 55%、吞吐掉 42%。注意这里的 EP=4 是用 tensor_parallel_size=4 加 enable_expert_parallel 实现的，所以这个差距里混着 TP=4 的通信代价，不能全部记在 EP 头上。要单独分离 EP，需要「专家并行 + 张量并行=1」的布置，vLLM 的这个开关不直接表达它。

EP=2 是一个可复现的异常。 每 token 3.24 s，8 个请求全部输出退化成同一个 token（位置 2 之后一直是 1023），总时间 209.8 s。它不是预热不足造成的：同一份代码已经改成「用测量时的形状预热」再跑，EP=1 与 EP=4 的 TPOT 都因此回到正常量级，EP=2 的数字没有任何变化。根因未定位，保持 UNVERIFIED——已知的是它发生在这个版本、这个模型、这两个 rank 的组合上，而 4 rank 的同一条路径正常。

输出一致性要分开看。 EP=4 的第 0 个请求与基线逐 token 相同到第 14 位之后才分叉，EP=2 在第 2 位就分叉（退化输出）。贪心解码下并行度改变会改变归约顺序，从而改变浮点结果与并列项的取舍，逐 token 完全相同不是可预期的验收标准；能作为判据的是「输出没有退化」与「困惑度量级正常」，而不是与某个基线的 token 序列逐位相等。

设计取舍

为什么列并行不通信、行并行要通信。 这是矩阵乘的代数性质，不是实现选择：输出维独立 ⇒ 每个 rank 的输出块只依赖完整输入；输入维切分 ⇒ 每个 rank 只算出一部分和。把 MLP 排成「列 → 激活 → 行」而不是「行 → 激活 → 列」，就是为了让一次 MLP 只付一次 all_reduce。

为什么 QKV 要单独一个 QKVParallelLinear。 因为 GQA 下 Q 与 KV 的 head 数不同（Qwen3-8B：32 vs 8），一次切分要同时满足两个整除条件，还要把三个权重拼在一个 kernel 里。这比两个独立的列并行层复杂，但省掉了两次 kernel 启动与两次输入读取。

为什么 PP 的通信量与层数无关。 stage 之间只传边界处的激活 S × hidden。切得越深，每次传递的量不变、传递次数不变，但每张卡上的层数变少。所以 PP 的主要收益是显存，不是单步延迟——延迟要靠微批流水填气泡才好看。

为什么 KV cache 也跟着 TP 切。 KV head 与 Q head 一起被切到 rank 上，所以每个 rank 只需要存自己那些 head 的 KV。TP=1 时可用 KV 是 14.72 GiB，TP=2 时每 rank 22.65 GiB：分母少了权重，分子里的 head 也少了，两头都有利。

127     partial = x_local @ W_local.t()
128     dist.all_reduce(partial, group=group)
129     return partial

134     return row_parallel_linear(h, W2_local, group=group)

137 def attention_tp(x, Wq_l, Wk_l, Wv_l, Wo_l, cfg, tp_size, group=None, causal=True):
138     """head 维切分：q/k/v 列并行，输出投影行并行。"""
139     S, H = x.shape
140     hd = cfg["head_dim"]
141     q = col_parallel_linear(x, Wq_l).view(S, cfg["heads"] // tp_size, hd)
142     k = col_parallel_linear(x, Wk_l).view(S, cfg["kv_heads"] // tp_size, hd)
143     v = col_parallel_linear(x, Wv_l).view(S, cfg["kv_heads"] // tp_size, hd)
144     # GQA：每个 kv head 被 heads/kv_heads 个 q head 共享
145     rep = (cfg["heads"] // tp_size) // (cfg["kv_heads"] // tp_size)
146     k = k.repeat_interleave(rep, dim=1)
147     v = v.repeat_interleave(rep, dim=1)
148     # 排成 (heads, S, hd) 之后再做 score：直接对 (S, heads, hd) 转置会把 head 维当 batch
149     qp, kp, vp = q.permute(1, 0, 2), k.permute(1, 0, 2), v.permute(1, 0, 2)
150     att = (qp @ kp.transpose(1, 2)) / (hd ** 0.5)
151     if causal:
152         mask = torch.triu(torch.ones(S, S, dtype=torch.bool, device=x.device), 1).unsqueeze(0)
153         att = att.masked_fill(mask, float("-inf"))
154     att = torch.softmax(att, dim=-1)
155     o = (att @ vp).permute(1, 0, 2).reshape(S, -1)
156     return row_parallel_linear(o, Wo_l, group=group)

实测数字

  • 手写 TP 对拍：MLP 3.9e-16、attention 2.8e-16（CUDA/NCCL，2 卡），与单进程 FP64 参照一致。
  • 整除条件：Qwen3-1.7B 在 TP=16 上因 kv_heads=8 不整除而失败。
  • 两阶段流水：4 个微批的计算利用率 76.4%，stage0 计算+发送占满窗口，stage1 空闲 1.95 ms。
  • Qwen3-8B：TP=2 相对 TP=1 的 TPOT −26%（B=1）到 −33%（B=8, S=8192），吞吐 +29%–32%；TP=4 的 TTFT +57%–87%，TPOT 只降 17%–25%。
  • 权重分片：TP=1 每 worker 15.27 GiB，TP=2 每 worker 7.64 GiB。
  • 引擎冷启动：8B 建引擎约 46–49 s（含读盘与 KV 池化），四个配置各建一次。
  • 专家并行（OLMoE，B=8、S=2048）：EP=1 基线 TPOT 13.800 ms / 477.5 tok/s，EP=4 为 21.408 ms / 275.1 tok/s，EP=2 退化为 3243.870 ms / 2.4 tok/s 且输出重复同一 token（根因未定位，标 UNVERIFIED）。
  • 预热口径：MoE 的 fused_moe_kernel 按形状 JIT。第一次运行用不匹配的形状预热，EP=2 的 TPOT 与基线都被编译时间污染；改成「用测量时的形状预热」后基线回到 13.800 ms。这类污染在 MoE 模型上必须先排除再报告数字。

消融建议

  1. 把 B=1、S=2048 的 TP=2 换到 --gpu-util 0.9，看可用 KV 变大后吞吐是否改善——用来分离「算力/带宽受限」与「KV 容量受限」。
  2. 在 mini_tp_pp.py 里把 attention 的 kv_heads 改成 4（TP=2 时每 rank 2 个 KV head），观察对拍是否仍然一致——GQA 的 repeat 逻辑最容易在这里出错。
  3. 把两阶段流水的微批数从 1 加到 16，画出利用率曲线，确认瓶颈在 stage0 而不是微批数。
  4. 给手写 PP 换上 batch_isend_irecv，在 GPU 上对比同步 send 的 44.6 ms/4 微批——这是 6.0 中 P2P 配对结论的直接应用。

前沿

并行度的自动选择。 本章的结论是「TP=2 最优、TP=4 变差」，但这个拐点取决于链路的通信/计算比、模型形状与负载构成。把这件事做成自动搜索（给定拓扑与负载，搜 TTFT/TPOT 的 Pareto 前沿）是推理框架的活跃方向；6.1 测到的「默认调优不是最优」说明这类搜索有真实空间。

PD 分离下的并行度选择。 prefill 与 decode 对并行度的偏好不同：prefill 是算力受限、容忍通信；decode 是权重带宽受限、对每步延迟敏感。把两者放在同一套 TP 度上是一种妥协，6.4 会讨论拆分之后各自选并行度。

EP 的通信库分层。 本章只用到 vLLM 内建的专家并行路径（NCCL all-to-all）。DeepEP / UCCL-EP / NVSHMEM 提供的是更底层的 dispatch/combine，触发条件与硬件耦合，6.3 按抽象层次展开。本机没有可用的 RDMA 设备，那些路径在这里只能做源码与协议分析。

CUDA Graph 与并行度的交互。 本章所有测量都关掉了 CUDA Graph，为的是让不同并行度在同一口径上可比。打开图模式之后 decode 的每步开销会下降，但图的捕获对通信形态与显存池有额外要求，最优并行度可能随之移动。这条路线在本项目里保持 UNVERIFIED。

陷阱

1. 把 TP 的收益外推到 EP/CP。 三者切的东西不同：TP 切权重（通信 ∝ hidden × token），EP 切专家（通信 ∝ 路由分布），CP 切序列（权重不切、省的是激活与 KV）。TP=2 的 26% 不能预期在 EP=2 上重现。

2. 不看整除条件就加并行度。 kv_heads=8 把 Qwen3 系列的 TP 上限定在 8。写死一个 TP 度的部署脚本换模型就会崩。

3. 把各卡显存相加当作可用容量。 TP=2 时每 rank 权重 7.64 GiB，不代表可以用 45 GiB 装模型；激活、KV、通信缓冲与框架开销都要算进去，能装多少 KV 由运行时的峰值决定。

4. 用微批数论证流水利用率会单调改善。 在亚毫秒的玩具上，每次迭代的固定开销与计算同量级，利用率在 68%–76% 之间波动。气泡的来源（最慢的 stage）比那个百分比更重要。

5. 同步、逐微批地发 P2P。 GPU 上实测 4 个微批的发送占 44.6 ms，因为每次未批量化的 P2P 都要新参与一次通信子建立。真实实现用 batch_isend_irecv。

6. attention 切分时把 head 维当 batch 维。 (S, heads, head_dim) 直接 q @ k.transpose(1,2) 是错的，必须先排成 (heads, S, head_dim)。这类错误不会给出数值误差，而是直接抛形状异常；如果误打误撞形状碰巧对上（例如 S == heads），还会静默算错。

7. 用不匹配的形状预热 MoE 引擎。 fused_moe_kernel 按 (专家数, 形状) JIT 编译。用 B=1、S=128 预热然后测 B=8、S=2048，第一次测量会撞上编译，实测把 EP=2 的 TPOT 抬到 3.24 s/token。预热必须覆盖测量时用的那个形状。

8. 把并行度切换后的逐 token 一致当作验收标准。 改变并行度会改变归约顺序，贪心解码在并列项上的取舍随之改变。实测 EP=4 与基线在第 14 位之后分叉。判据应该是「输出未退化 + 困惑度量级正常」，不是 token 序列逐位相等。

9. 把 EP 的性能差全部归给 EP。 本章的 EP=k 是用 tensor_parallel_size=k 加 enable_expert_parallel 实现的，所以 EP=4 相对 EP=1 的差距里混着 TP=4 的通信代价。要单独给 EP 归因需要「EP>1 且 TP=1」的布置。

10. 认为 PP 能降低 decode 的单步延迟。 decode 每步只有一个 token，PP 无法把单步再拆开，反而多一次跨 stage 传递。PP 的收益在吞吐与显存，长 prefill 时才在 TTFT 上体现。

自测题

1. 一次 MLP 的 TP 前向里有几次 all_reduce？通信量是多少？

一次。列并行部分零通信，行并行部分需要一次 all_reduce，搬运 S × hidden 个元素。以 Qwen3-8B、S=1、BF16 为例是 4096 × 2 = 8 KiB（一次 all_reduce 的每 rank 有效载荷）。attention 的输出投影同样需要一次，所以每层共两次。

2. 为什么 TP=4 在这台机器上比 TP=2 差？

每次 all_reduce 的字节数不随 TP 变（输出维是 hidden），但参与的 rank 变多、每步的固定开销上升。decode 的收益来自「每 rank 少读一半权重」，TP=2 已经拿到这份收益，TP=4 再切一半的边际收益很小，而通信成本继续涨。prefill 阶段受影响更大，因为它的通信/计算比本来就高——实测 TTFT 涨 57%–87%。

3. PP=2 为什么改善了 B=8、S=2048 的 TTFT，却没有改善 TPOT？

PP 把不同的微批分到不同 stage 上并行处理，所以有并发时可以重叠；TTFT 是「第一个请求出第一个 token 的时间」，微批被摊开后确实变短。而 decode 阶段每个请求每步只产生 1 个 token，无法在 stage 之间切分，反而多了一次跨 stage 传递，所以 TPOT 不变甚至略差。

4. Qwen3-8B 的 heads=32、kv_heads=8、vocab=151936。TP 能开到多少？

受 kv_heads 限制，TP ≤ 8。vocab=151936=2^7×1187 能被 128 整除，不构成限制；intermediate=12288 也够。若换成一个 kv_heads=4 的模型，上限就降到 4。

5. TP=1 时每 worker 报 15.27 GiB，TP=2 时每 worker 报 7.64 GiB。这说明什么，不能说明什么？

说明权重确实按输出/输入维切开并分别装入各 rank（7.64×2 ≈ 15.27）。不能说明「每张卡因此多出 7.6 GiB 可用显存」——KV cache 的可用量还取决于 gpu_memory_utilization、激活峰值与通信缓冲，实测 KV 从 14.72 GiB 升到 22.65 GiB，涨幅（约 7.9 GiB）与权重减少量接近但不相等。

6. 手写两阶段流水里，stage0 的「空闲」几乎为 0，能不能说流水没有气泡？

不能。stage0 是瓶颈，它的空闲为 0 恰恰说明它一直在忙、而 stage1 一直在等——气泡落在 stage1 身上（实测 1.95 ms / 5.39 ms）。看气泡要看每个 stage 的空闲，只看一个会得出相反结论。

7. 如果这台机器换成 NVLink，本章哪些结论需要重测？

所有与通信/计算比相关的结论：TP=4 相对 TP=2 的劣势、PP=2 的收益、以及最优点本身。NVLink 上 all_reduce 的速率比 PCIe 高一个量级，TP=4/TP=8 很可能反超 TP=2。而「整除条件」「权重分片比例」「GQA 的 head 排布」这些是结构与代数事实，与链路无关。
