6.3

MoE 分布式与 all-to-all

EP、DeepEP v1(NVSHMEM) → v2(NCCL Gin)、IBGDA、UCCL-EP。

实测机器 worldvln（4× L40S，PCIe，无 NVLink）· NCCL 2.29.7 · OLMoE-1B-7B-0924（64 专家 / top-8）前置 6.2（TP/PP/EP）· 4.4（MoE 路由与不均衡）· 6.1（集合通信成本）

本章回答三个问题

4.4 量到了 MoE 的两个结构性事实：每一层都有自己的热专家，逐层最热/最冷可达数百倍；而且 batch 一大，稀疏性在带宽角度就消失了。这两件事把「MoE 怎么并行」变成一个通信问题——token 必须离开它所在的卡，去到专家所在的卡，算完再回来。

  1. pack / dispatch / combine 具体怎样实现？反排列靠什么保证不出错？
  2. all-to-all 和 all-gather 两条路线，谁的通信量更小？什么时候会翻转？
  3. 专家布局的均衡收益，能不能盖住迁移的代价？

这一章的实验边界同样是单机 PCIe、无 NVLink、无 RDMA。这个边界直接决定了第 3 节的支持矩阵：DeepEP、UCCL-EP、NVSHMEM 三条路线在这台机器上都跑不起来，只能做源码与协议分析。

心智模型：一次 MoE 前向里的四次数据流动

机制拆解与推导

1. pack / dispatch / combine 的四步

MoE 的专家并行把前向拆成四步，每一步都有明确的输入输出：

① pack。 本 rank 的每个 token 有 top-k 个专家，先算出每个 (token, k) 的目标 rank（专家归谁），然后按 (目标 rank, 专家 id) 排序，得到发送缓冲。排序的意义在于让接收端能按专家分段。每行必须携带 (token_id, k, expert_id)——这是接收端能反排列的唯一依据。

② counts 交换。 发送方告诉每个目标 rank「我要给你多少行」；接收方还需要知道「每个发送方给我的每个本地专家多少行」，才能算出 expert offsets。这一步只交换 O(N·E) 个整数。

③ dispatch。 把打包好的行按 counts 分段发给各 rank。

④ 局部重排 + grouped GEMM + combine。 收到的行是按发送方分段的，不是按专家分段的；接收端要用 ② 里拿到的 (发送方, 专家) 计数，做一次本地重排把行摆成 expert-major。这一步不发通信，但它是真实存在的一步——少了它，grouped GEMM 就得按发送方分段来算，同一个专家的行会散落在多段里。

反排列的键是 (token_id, k)：combine 回来后按这个键放回原位置，再按 top-k 权重加权求和。

2. 正确性验证：唯一 ID + 完备性

只用整数就能把正确性钉死。判据是三条：

  • 无丢失：接收端收到的行数之和等于发送端发出的总数。
  • 无重复：每个 (token_id, k) 在全局只被投递一次。
  • 无错位：expert-major 重排后，每个本地专家的段 [offset_e, offset_e + count_e) 里的 expert_id 全部等于 e。

实测覆盖五种输入（labs/L6/moe_dispatch.py，512 token、8 专家、top-2、EP=4）：

用例 pairs 分发到 无丢失/重复/错位 每 rank 负载 零 token rank 空专家槽
均匀 1024 1024 ✓ [251, 245, 265, 263] — 0
倾斜 20% 1024 1024 ✓ [408, 196, 212, 208] — 0
倾斜 50% 1024 1024 ✓ [638, 123, 131, 132] — 0
空专家（8 token、64 专家） 16 16 ✓ [4, 6, 4, 2] — 50
全部倾斜到一个 rank 1024 1024 ✓ [1024, 0, 0, 0] [1, 2, 3] 7

最后两行是容易被漏掉的边界：空专家（专家数远大于 token 数时，64 个专家槽里 50 个一行都没有）与零 token rank（全部 token 都路由到 rank 0 持有的专家，另外三个 rank 一行都收不到）。这两种情况下 counts 里出现 0，offset 的构造与接收缓冲的零长度分段都要能正确处理。

3. 两条路线的通信量：一个有明确翻转点的判据

两条路线的字节数来自不同的量：

  • all-to-all 路线：每个 (token, k) 副本只发给一个目标 rank，每 rank 发出 K·T·H 字节、收到约 K·T·H 字节，合计 ≈ 2·K·T·H。与 rank 数无关，随 top-k 线性增长。
  • all-gather 路线：先 gather 所有 token（每 rank 收 (N-1)·T·H、发 T·H），再对 N·T·H 的贡献做一次 all_reduce（收发各 N·T·H），合计 ≈ 3·N·T·H。与 top-k 无关，随 rank 数线性增长。

两者相等的位置在 2K = 3N，即 K = 1.5N：

  • K > 1.5N：all-gather 的字节更少。
  • K < 1.5N：all-to-all 的字节更少。

本机实测正好落在两侧：

配置（T=4096，N=4） all-to-all 每 rank all-gather 每 rank 谁更快
top-k=2，H=256 8288 KiB 20864 KiB all-to-all（2.5× 少）
top-k=8，H=256 33152 KiB 20864 KiB all-gather 字节少，但实测反而慢 31%
top-k=8，H=2048 262528 KiB（256 MiB） 164224 KiB（160 MiB） all-gather（字节少 37%，时间快 31%）

K=8、N=4 时 8 > 6，所以 all-gather 的字节更少——这与「MoE 就该用 all-to-all」的直觉相反，但它是 byte 账的直接推论，也被实测证实。

不过字节少不等于时间短。 H=256、top-k=8 那一行里 all-gather 字节少 37%，时间却慢 31%：那时每 token 的载荷只有 1 KiB，整条路线被集合通信的启动与同步开销支配，而不是被字节数支配。把 H 提到 OLMoE 真实的 2048，载荷变大、固定开销被摊薄，字节账才重新主导，all-gather 才在时间上也赢。

4. 分阶段实测

labs/L6/moe_dispatch.py 把 dispatch 拆成三个阶段分别计时（CUDA event，中位数，4 卡，H=256）：

tokens top-k counts dispatch combine 发送字节/rank 峰值
32 2 85.0 µs 48.9 µs 60.4 µs 65 KiB 0.001 GiB
32 8 61.4 µs 55.3 µs 59.4 µs 259 KiB 0.002 GiB
256 2 67.8 µs 99.3 µs 104.4 µs 518 KiB 0.004 GiB
256 8 104.4 µs 301.1 µs 289.8 µs 2072 KiB 0.015 GiB
4096 2 52.2 µs 1050.6 µs 1132.5 µs 8288 KiB 0.065 GiB
4096 8 46.1 µs 3575.8 µs 4536.3 µs 33152 KiB 0.249 GiB

三条读法：

counts 是一个与规模无关的固定成本（42–104 µs）。token 数从 32 涨到 4096（128×），counts 交换的时间几乎不变。在 32 token、top-2 时它是主要开销（85 µs vs 载荷 49 µs）——小 batch decode 的 MoE 通信不是在传数据，是在交换元数据。

载荷阶段近似线性。 4096 token 相对 256 token，字节涨 16×，dispatch 涨 11.9×、combine 涨 15.7×，规模效应明显。

峰值显存随 top-k 与 token 数涨。 4096 token、top-8 时 peak allocated 是 0.249 GiB，主要是发送缓冲 (T·K, H+3) 与接收缓冲。

倾斜对时间几乎没有影响（256 token、top-8 下 s=0/20%/50% 的 dispatch 是 301/377/210 µs，非单调，落在噪声内）。这是合理的：倾斜只改变行的分布，不改变总行数与总字节数。倾斜的代价表现在下一节的负载不均衡上。

5. 专家布局：一次复制就够了

4.4 的逐层数据显示每层都有热专家（最热/最冷可达数百倍），所以自然的想法是给热专家做复制、把副本放到空闲的 rank 上（EPLB 类做法）。问题是均衡收益能不能盖住迁移代价。

用每层独立的热专家集合重建这个场景（4096 token、64 专家、top-8、EP=4、倾斜 30%、16 层）：

布局 max/mean（16 层中位） 最差层 最平衡层 迁移
静态连续切分 1.50 1.52 1.10 —
EPLB，热专家 1 份副本 1.09 1.14 1.07 72 MiB/次求解
EPLB，热专家 2 份副本 1.11 1.15 1.05 144 MiB/次求解

1 份副本拿走了几乎全部收益，第 2 份只多花一倍迁移。 最差层的 max/mean 从 1.50 降到 1.08（−28%），但第 2 份副本把中位数从 1.09 抬到 1.11、在第 2 层上甚至出现 −1% 的负收益。

原因是收益的上界由最差层决定：静态布局下最差层的 max/mean 已经是 1.10 左右（因为路由本身近似均匀），只有少数层出现 1.5 以上的尖峰；把尖峰削平之后就接近下界了，继续加副本只是在均匀的层上做无用功。

重平衡周期直接决定迁移量（一个 epoch 遍历 16 层）：

重平衡周期 每 epoch 求解次数 迁移
每 1 层 16 1152 MiB/epoch
每 4 层 4 288 MiB/epoch
每 16 层 1 72 MiB/epoch

周期缩短 16 倍，迁移量涨 16 倍，而均衡指标（上表）是同一个数量级。 所以周期应该按「热专家集合变化的快慢」来定，而不是越频繁越好。

这张表的乐观之处

负载分流模型假设副本能精确均分该专家的 token。真实 router 是逐 token 独立选择的，不会精确均分；所以上表给的是 EPLB 收益的上界，实际收益要打折。要给出可信下界，需要接真实 router 的输出分布做在线重放，本章没有做。

路线 后端 入口 硬性要求 本机

DeepEP V2 NCCL Gin deep_ep.ElasticBuffer SM90+、CUDA 12.3+、NCCL ≥2.30.4、跨机需 RDMA ✗ sm_89、NCCL 2.29.7

DeepEP V2 的两条硬门槛都可以在本机直接判定：setup.py 默认把 TORCH_CUDA_ARCH_LIST 设为 9.0 并校验；README 要求 NCCL 2.30.4 以上，而本机是 2.29.7。这台 L40S（sm_89）不是 DeepEP 的目标平台，不冒充。

L40S 上能跑的只有 NCCL 自己的 all_to_all_single，本章的第 3、4 节就是用它测的。这不是 DeepEP 那种「0-SM、GPU 发起」的实现——它的 dispatch 是由 CPU 逐次提交的集合通信，与 DeepEP 的 SM 占用模型、RDMA 直连路径都不在同一层。把本章的数字当作「MoE 通信在这台机器上的下界」是错的：它测的是 NCCL all-to-all 的能力，不是 MoE 通信的极限。

设计取舍

为什么反排列要带 (token_id, k) 而不是位置。 位置在跨 rank 之后会变（接收端的顺序由发送端与网络决定），而 (token_id, k) 是全局唯一的语义键。代价是每行多 2 个整数——这也是为什么本章的字节账里把 header 单列（(H+3) 而不是 H）。

为什么接收端要再做一次局部重排。 发送方按目标 rank 分段，接收端拿到的自然是「按发送方分段」的布局；而 grouped GEMM 要的是「按专家分段」。把行在本地搬一次比让 GEMM 处理多段便宜得多，所以真实实现都选前者。这一步不发通信，但会多占一份等长缓冲。

为什么 all-to-all 的字节随 top-k 走，all-gather 随 rank 数走。 这不是实现细节，是两种算法的定义：all-to-all 发的是「每个 (token,k) 一次」，all-gather 发的是「每个 token 到每个 rank 一次」。知道这个差别就能在选路线之前先算一遍，不必先跑。

为什么 DeepEP 要 0-SM 与 RDMA。 它的目标是让通信不占 SM、让 GPU 直接发起传输（IBGDA/NVSHMEM），从而在小 batch decode 上把 CPU 提交与 SM 竞争都去掉。这些机制依赖 SM90 的 PTX 能力与 RDMA 网卡的 peer-memory 注册，所以在 SM89 + PCIe 上无法复现其收益模型。

labs/L6/moe_dispatch.py 的计划构造是纯整数逻辑，可以脱离 GPU 单独验证：

 80 def build_plan(expert_ids, ep_size, num_experts):
 81     """由路由结果算出 dispatch 计划：send/recv counts、offsets 与两组排列。
 82 
 83     排列用 (token_id, k_index) 作为唯一键，这是能证明「无错位」的最小信息量：
 84     接收端靠它把结果放回原来的位置。
 85     """
 86     T, K = expert_ids.shape
 87     owner = (expert_ids * ep_size // num_experts)          # (T,K) 目标 rank
 88     # 本 rank 需要发往各 rank 的 (token,k) 个数
 89     send_counts = [int((owner == r).sum()) for r in range(ep_size)]
 90     send_offsets = [0]
 91     for c in send_counts:
 92         send_offsets.append(send_offsets[-1] + c)
 93     # 发送顺序：按目标 rank 分段，段内按 (token,k) 原始顺序
 94     order = []
 95     for r in range(ep_size):
 96         idx = (owner == r).nonzero(as_tuple=False)
 97         order.extend([(int(t), int(k)) for t, k in idx])
 98     assert len(order) == sum(send_counts)
 99     # 每个 (token,k) 的发送位置
100     src_pos = {}
101     for pos, key in enumerate(order):
102         src_pos[key] = pos
103     # 接收侧：按 (专家) 分组，专家内部按到达顺序
104     recv_experts = [e for e in range(num_experts)
105                     if expert_owner(e, num_experts, ep_size) is not None]
106     return {
107         "owner": owner, "send_counts": send_counts, "send_offsets": send_offsets,
108         "order": order, "src_pos": src_pos,
109     }

labs/L6/moe_placement_bench.py 把「复制热专家」与「迁移代价」放在同一个模型里算，负载分流对副本数敏感：

59 def rank_loads_replicated(ids, placement, replicas, ranks, experts):
60     """把每个专家的 token 均分给它的所有持有者（主副本 + 复制副本）。
61 
62     这是「理想分流」下的负载：真实 router 不会把 token 精确均分，所以这条曲线给出的是
63     EPLB 收益的乐观上界，实际收益要打折。
64     """
65     counts = torch.bincount(ids.reshape(-1), minlength=experts).tolist()
66     loads = [0] * ranks
67     for e in range(experts):
68         holders = [placement[e]] + list(replicas.get(e, []))
69         per, rem = divmod(counts[e], len(holders))
70         for i, r in enumerate(holders):
71             loads[r] += per + (1 if i < rem else 0)
72     return loads

# 任务 B：真实通信（4 卡），两条路线
python labs/L6/moe_dispatch.py B --world-size 4 --tokens 4096 --topk 8 --skew 0.0 \

python labs/L6/moe_dispatch.py B --world-size 4 --tokens 4096 --topk 8 --skew 0.0 \
    --hidden 2048 --route allgather --out results/worldvln/6.3/run/B

# 任务 C：支持矩阵
python labs/L6/moe_dispatch.py capability --out results/worldvln/6.3/run/C

# 任务 D：静态布局与 EPLB 对照
python labs/L6/moe_placement_bench.py D --tokens 4096 --skew 0.3 \
    --replicas 1,2 --rebalance-periods 1,4,16 --out results/local/6.3/run/D

实测数字

  • 正确性：5 个用例、18 次真实通信运行，全部「无丢失/重复/错位」与「往返正确」，expert-major 分组全部连续。
  • 固定成本：counts 交换 42–104 µs，与 token 数无关；32 token 时它比载荷还贵。
  • 载荷：4 卡 top-8 下从 32 token 的 259 KiB/rank 涨到 4096 token 的 33152 KiB/rank，dispatch 从 55 µs 涨到 3576 µs。
  • 路线翻转：K=8、N=4 时 all-gather 字节少 37%、时间快 31%（H=2048）；K=2、N=4 时 all-to-all 字节少 2.5×。
  • 峰值：H=2048、4096 token、top-8 时 all-to-all 1.96 GiB、all-gather 3.16 GiB。
  • EPLB：1 份副本把最差层的 max/mean 从 1.50 降到 1.08，第 2 份副本只多花一倍迁移、中位数反而升到 1.11。
  • 迁移周期：每 1 层重平衡 = 1152 MiB/epoch，每 16 层 = 72 MiB/epoch。

消融建议

  1. 把 --hidden 从 2048 降到 256 再跑一次两条路线，观察「字节账主导」与「固定开销主导」两个区间的分界。
  2. 把 top-k 从 8 调到 2、EP 从 4 调到 8，验证 K = 1.5N 这个翻转点是否真的落在实测的换边位置上。
  3. 在任务 A 里把 (token_id, k, expert_id) 的 header 去掉，只靠 counts 推断归属，观察空专家与零 token rank 两个用例是否还能通过。
  4. 在任务 D 里把 replicas 加到 4，看均衡指标是否继续改善——用来确认「收益上界由最差层决定」这个解释。

前沿

GPU 发起通信与 0-SM。 DeepEP 的核心卖点是通信不占 SM、由 GPU 直接发起传输，从而在小 batch decode 上把 CPU 提交与 SM 竞争一起去掉。这条路线要求 SM90+ 与 RDMA（或 NVLink），本机两者都不具备，保持 UNVERIFIED。

EPLB 与在线重平衡。 本章的 EPLB 是离线的、按层静态求解的。生产系统更关心在线重平衡：在不打断服务的前提下迁移专家权重、在迁移期间保持路由正确。这需要「新旧布局并存 + 逐步切换」的机制，本章没有覆盖。

分层的 EP 通信库。 6.1 已经说明 NCCL、NVSHMEM、DeepEP、UCCL 不是同一抽象层的四个可互换库：NCCL 提供集合通信原语，NVSHMEM 提供 PGAS 内存模型，DeepEP 与 UCCL-EP 是建立在它们之上的 MoE 专用运行时。选型要按抽象层与硬件条件，不能按峰值带宽排名。

MoE 的批次与稀疏性。 4.4 已经量到 batch≥64 时每层所有专家都会被读到，稀疏性在带宽角度消失。这意味着 MoE 的通信优化重点在小 batch（decode）——也正是 DeepEP 那类实现的目标场景，而本章的测量都在 token 数较大的 prefill 侧。

陷阱

1. 以为 MoE 就该用 all-to-all。 字节账是 2K·T·H 对 3N·T·H。当 K < 1.5N 时 all-to-all 更省，当 K > 1.5N 时 all-gather 更省。K=2、N=4 与 K=8、N=4 落在两侧，实测证实了翻转。

2. 以为字节少就快。 H=256、K=8、N=4 时 all-gather 字节少 37% 却慢 31%（固定开销主导）；H=2048 时同一对配置才反过来。小载荷下必须把启动开销算进去。

3. 忽略 counts 交换这个固定成本。 42–104 µs，与 token 数无关。在 32 token 的 decode 场景它比载荷还贵，成为主项。

4. 少了接收端的局部重排。 发送方按目标 rank 分段，接收端拿到的是按发送方分段的布局。不重排就直接喂 grouped GEMM，同一个专家的行会散落多段，分段 GEMM 的效率直接掉下去。

5. 用位置做反排列的键。 跨 rank 之后位置会变。键必须是 (token_id, k) 这样的语义标识。

6. 只测均匀路由。 均匀分布下所有实现都好看。必须覆盖空专家与零 token rank——本章的 64 专家 / 8 token 用例里有 50 个空专家槽，全部倾斜用例里有 3 个 rank 一行都收不到。

7. 假定倾斜会增加通信时间。 倾斜只改变行的分布，不改变总行数，实测 dispatch 时间在噪声内（301/377/210 µs，非单调）。倾斜的代价在负载不均衡上，不在通信量上。

8. 认为 EPLB 副本越多越均衡。 收益上界由最差层决定。1 份副本把最差层从 1.50 降到 1.08，第 2 份只多花一倍迁移、中位数反而变差。而且本章的分流模型是理想均分，是收益上界。

9. 把 NCCL all-to-all 的数字当成 MoE 通信的下界。 它测的是 NCCL 集合通信在这台机器上的能力，不是 DeepEP 那类 0-SM、GPU 发起实现的能力。两者不在同一层。

自测题

1. 4 卡、top-8、T=4096、H=2048，两条路线每 rank 各搬多少字节？

all-to-all：每 rank 发出 K·T·H·2 字节（FP16 载荷）再加 header，实测发送 256 MiB/rank；合起来收发各 256 MiB。 all-gather：gather 阶段收 (N-1)·T·H·2 = 3×4096×2048×2 = 48 MiB，all_reduce 阶段对 N·T·H·2 = 64 MiB 收发各一次，合计约 160 MiB/rank。

2. 什么条件下 all-gather 路线比 all-to-all 更省字节？

2K·T·H > 3N·T·H，即 K > 1.5·N。K=8、N=4 时 8 > 6 成立；K=2、N=4 时 2 < 6 不成立。注意 all-gather 的字节与 top-k 无关，all-to-all 的与 rank 数无关，两者随不同自变量增长。

3. 为什么接收端还要做一次局部重排？

发送方按 (目标 rank, 专家) 排序，所以接收端收到的是「按发送方分段」的布局，同一个专家的行会分散在多个发送方段里。grouped GEMM 需要「按专家分段」的连续布局，所以接收端用交换来的 (发送方, 专家) 计数把行本地搬一次。这一步不发通信，但要多占一份等长缓冲。

4. 一个 64 专家、top-8 的模型在 8 个 token 上运行，EP=4。有多少个专家会拿到 0 个 token？

最多 64 个里的大部分。8 token × top-8 = 64 个 (token,k) 对，最极端情况恰好覆盖 64 个不同专家、一个不空；实测（随机路由）64 个专家槽里 50 个是空的。所以 counts 里大量为 0，offset 构造必须能处理零长度段。

5. 为什么倾斜 50% 的 dispatch 时间没有明显变长？

倾斜改变的是行落到哪个目标 rank，不改变总行数（T×K 不变）、也不改变每行的字节数。总字节数不变，所以 all-to-all 的时间基本不变。倾斜的代价出现在 rank 之间的负载差上（实测每 rank 负载 [638,123,131,132]，max/min = 5.2×），表现为「某些卡在算、某些卡在等」。

6. EPLB 给热专家加第 2 份副本，为什么均衡指标反而变差？

因为收益的上界由最差层决定。静态布局下大多数层的 max/mean 已经在 1.10 附近（路由本身近似均匀），只有少数层有 1.5 以上的尖峰。削掉尖峰后已经接近下界，再加副本只是把均匀层上的 token 也拆开，指标不再改善；同时副本数增加使每次求解的迁移字节翻倍。本章的分流模型还是理想均分，实际收益只会更低。

7. 本机为什么跑不了 DeepEP V2？

两条硬门槛：架构上要求 SM90+（本机 L40S 是 sm_89），源码 setup.py 默认把 TORCH_CUDA_ARCH_LIST 设为 9.0 并校验；依赖上要求 NCCL ≥ 2.30.4（本机 2.29.7）。跨机还需要 RDMA，本机没有 /dev/infiniband。所以只能做协议与源码分析，不冒充其目标平台。
